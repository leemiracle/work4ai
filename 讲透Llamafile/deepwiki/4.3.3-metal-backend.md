## Purpose and Scope

 The Metal backend provides Apple Silicon GPU acceleration for llamafile on macOS and iOS. It implements a dynamic compilation and loading system that extracts Metal source files from the executable's embedded ZIP filesystem, compiles them into a self-contained dynamic library (DSO) using the system compiler, and links them at runtime.

 This approach ensures compatibility across different macOS versions without requiring pre-built binaries for every possible environment. For NVIDIA or AMD acceleration, see [CUDA Backend](https://deepwiki.com/mozilla-ai/llamafile/4.3.1-cuda-backend) or [ROCm/HIP Backend](https://deepwiki.com/mozilla-ai/llamafile/4.3.2-rocmhip-backend).

 
---

 
## Architecture Overview

 The Metal backend operates by transforming embedded source code into a functional GPU provider at runtime. Unlike the CUDA/ROCm backends which attempt to load pre-built DSOs [llamafile/cuda.c24-31](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.c#L24-L31) the Metal backend prioritizes a JIT (Just-In-Time) compilation pipeline to ensure optimal performance on the host's specific hardware and OS version.

## Source File Management

 The Metal backend carries its own source code within the executable. It "yoinks" (embeds) the necessary `llama.cpp` and `ggml` files using the Cosmopolitan `__static_yoink` macro.

 
### Embedded Assets

 The following files are embedded and tracked in the `metal_srcs` array for runtime extraction:

 
| File Type | Examples | Source Reference |
|---|---|---|
| GGML Core | ggml.c, ggml-alloc.c, ggml-quants.c, ggml-threading.cpp | llamafile/metal.c56-61 |
| Headers | ggml.h, ggml-metal.h, ggml-impl.h, ggml-cpu-impl.h | llamafile/metal.c64-76 |
| Metal Kernels | ggml-metal.metal, ggml-metal-ops.cpp, ggml-metal-common.cpp | llamafile/metal.c79-82 llamafile/metal.c87-90 |
| Objective-C | ggml-metal-device.m, ggml-metal-context.m | llamafile/metal.c83-86 |

 
### Extraction and Dependency Logic

 At runtime, `BuildMetal` checks if the files in the application directory (`~/.llamafile/`) are up to date using `llamafile_is_file_newer_than` [llamafile/metal.c205](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L205-L205) If the embedded ZIP versions are newer, it extracts them [llamafile/metal.c215](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L215-L215)

 A key step in the pipeline is `PreprocessMetalShader` [llamafile/metal.c166](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L166-L166) which inlines header files into `ggml-metal.metal` to create a self-contained shader source before compilation. The backend specifically targets Apple Silicon; if `IsXnuSilicon()` returns false, the initialization terminates [llamafile/metal.c335-336](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L335-L336)

## Compilation Process

 If a rebuild is required (e.g., first run or `FLAG_recompile` is set), llamafile invokes the system compiler (`cc`) via `posix_spawnp` [llamafile/metal.c254](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L254-L254) Compilation is skipped if `FLAG_nocompile` is true [llamafile/llamafile.h32](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/llamafile.h#L32-L32)

 
### Compiler Flags and Rationale

 The compilation command uses specific flags to ensure the resulting DSO is compatible with the Cosmopolitan Libc environment:

 
| Flag | Purpose | Code Reference |
|---|---|---|
| -O3 | High optimization for math kernels | llamafile/metal.c231 |
| -fPIC | Position Independent Code for shared library | llamafile/metal.c232 |
| -shared | Produce a .dylib / .so | llamafile/metal.c233 |
| -ffixed-x28 | Critical: Reserves x28 register for Cosmo TLS (Thread Local Storage) | llamafile/metal.c237 |
| -framework Metal | Links Apple's Metal framework | llamafile/metal.c247 |
| -framework Foundation | Links Apple's Foundation framework for Objective-C support | llamafile/metal.c248 |

## API Integration

 The Metal backend provides standard `ggml` entry points that wrap the dynamic function pointers stored in `g_metal`.

 
### Key Functions

 
 - **`ggml_backend_metal_init()`**: Checks for Metal support and returns a `ggml_backend_t` instance [llamafile/metal.c361-365](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L361-L365)
 - **`ggml_backend_is_metal()`**: Identifies if a specific backend instance is using the Metal implementation [llamafile/metal.c367-371](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L367-L371)
 - **`ggml_backend_metal_reg()`**: Returns the backend registration structure required for the GGML backend registry [llamafile/metal.c373-377](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L373-L377)
 
 
### Cross-Module Memory Management

 A critical patch in `llama.cpp.patches/patches/ggml_src_ggml-metal_ggml-metal.cpp.patch` adds `ggml_backend_metal_buffer_free_struct` [llama.cpp.patches/patches/ggml_src_ggml-metal_ggml-metal.cpp.patch75-77](https://github.com/mozilla-ai/llamafile/blob/43551265/llama.cpp.patches/patches/ggml_src_ggml-metal_ggml-metal.cpp.patch#L75-L77) This ensures that when the Metal backend is loaded as a dynamic library, the buffer structure (allocated by the dylib's `new`) is freed by the dylib's own `delete` operator, preventing memory corruption across module boundaries.

 
### Logging Control

 Llamafile redirects Metal-specific logging through `ggml_log_set`. If a log callback is requested before the Metal DSO is loaded, it is stored in `g_metal_pending_log` [llamafile/metal.c146-150](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L146-L150) and applied immediately after the library is linked [llamafile/metal.c316-320](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L316-L320)
