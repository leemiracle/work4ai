## Purpose and Scope

 This document describes the CUDA backend implementation in llamafile, which provides GPU acceleration for NVIDIA GPUs (via CUDA) and AMD GPUs (via ROCm/HIP). The CUDA backend uses a dynamic loading strategy where it attempts to load pre-built shared objects (DSOs) bundled within the executable or located in specific system directories. It targets architectures from Pascal through Hopper for NVIDIA, and various GFX architectures for AMD.

 For information about the Metal backend for Apple Silicon, see [4.3.3](https://github.com/mozilla-ai/llamafile/blob/43551265/4.3.3) For details about GPU matrix multiplication kernels (tinyBLAS), see [4.3.4](https://github.com/mozilla-ai/llamafile/blob/43551265/4.3.4) For the general backend architecture abstraction, see [4.1](https://github.com/mozilla-ai/llamafile/blob/43551265/4.1)

 
## Architecture Overview

 The CUDA backend operates through a multi-stage initialization process that determines GPU availability and handles dynamic linking via `cosmo_dlopen`. Unlike the Metal backend, which JIT-compiles sources at runtime, the CUDA backend focuses on loading pre-compiled DSOs (`ggml-cuda.so` or `ggml-cuda.dll`) to avoid the overhead of `nvcc` or `hipcc` during standard execution.

## Dynamic DSO Loading

 llamafile prioritizes loading pre-compiled binaries to minimize startup latency. It uses `cosmo_dlopen` (wrapped in `gpu_backend_link`) to load `.so` (Linux) or `.dll` (Windows) files.

 
### Search and Link Mechanics

 
 - **Identity Selection**: The backend uses two descriptors (`CUDA_DESC` and `ROCM_DESC`) over a single `GpuBackend` structure. This allows it to share symbol resolution logic while distinguishing between NVIDIA and AMD at the UI level [llamafile/cuda.c42-44](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.c#L42-L44)
 - **Dynamic Thunks**: Functions like `LinkCudaNvidia` and `LinkCudaAmd` act as thunks that pass the correct descriptor to the shared `gpu_backend_link` machinery [llamafile/cuda.c65-71](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.c#L65-L71)
 - **Symbol Resolution**: The system resolves symbols defined in the descriptors, such as `ggml_backend_cuda_init` and `ggml_backend_cuda_get_device_count` [llamafile/cuda.c49-51](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.c#L49-L51)
 
 
### Runtime Wrappers

 The CUDA backend provides wrapper functions that check for backend support before dispatching to the loaded DSO symbols:

 
 - `ggml_backend_cuda_init(int device)`: Calls the loaded `backend_init` pointer, handling `__ms_abi__` calling convention on Windows [llamafile/cuda.c157-168](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.c#L157-L168)

## Compilation and Build System

 While the runtime primarily loads DSOs, llamafile includes scripts for users to compile the CUDA/ROCm backends if pre-built binaries are missing.

 
### NVIDIA CUDA Compilation (`cuda.sh` / `cuda.bat`)

 The build scripts use `nvcc` to compile the GGML CUDA backend.

 
 - **Architecture Targeting**: Targets include `sm_75` (Turing), `sm_80` (Ampere), `sm_86` (Ampere Mobile), `sm_89` (Ada), and `sm_90` (Hopper). Support for Blackwell (`sm_120f`) is included when using CUDA 13+ [llamafile/cuda.sh198-204](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.sh#L198-L204) [llamafile/cuda.bat159-161](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.bat#L159-L161)
 - **Virtual PTX**: For minimal size builds, the script uses `compute_75` and `compute_90` virtual PTX to allow JIT-compilation on newer hardware while keeping the binary small [llamafile/cuda.sh191-196](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.sh#L191-L196) [llamafile/cuda.bat126-131](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.bat#L126-L131)
 - **TinyBLAS vs cuBLAS**: By default, the scripts compile with `GGML_USE_TINYBLAS`, but can be switched to `GGML_USE_NVIDIA_CUBLAS` (or `cuBLAS`) via the `--cublas` flag [llamafile/cuda.sh142-156](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.sh#L142-L156) [llamafile/cuda.bat92-102](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.bat#L92-L102)
 
 
### AMD ROCm Compilation (`rocm.sh` / `rocm.bat`)

 The ROCm build scripts use `hipcc` (or `clang++` with HIP support) to target AMD GPUs.

 
 - **GFX Targets**: Targets include `gfx906` (Vega 20), `gfx942` (MI300), `gfx1030` (RDNA2), and `gfx1100`-`gfx1103` (RDNA3) [llamafile/rocm.bat96-121](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/rocm.bat#L96-L121)
 - **HIP Abstraction**: Uses `-DGGML_USE_HIP=1` and `-D__HIP_PLATFORM_AMD__` to compile the shared CUDA/HIP codebase for AMD hardware [llamafile/rocm.bat135](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/rocm.bat#L135-L135)
 - **Binary Size**: The `--offload-compress` flag is used to shrink the fat binary for ROCm [llamafile/rocm.bat138](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/rocm.bat#L138-L138)

## Size and Optimization Flags

 The build system provides several flags to control the footprint of the resulting CUDA DSO:

 
| Flag | Effect | Code Reference |
|---|---|---|
| --minimize-size | Enables minimal archs, excludes IQ quants, and enables compression. | llamafile/cuda.sh61-66 |
| --no-iq-quants | Excludes IQ quant MMQ template instances to reduce binary size. | llamafile/cuda.sh70-72 |
| --compress | Passes --compress-mode=size to nvcc (requires CUDA >= 12.8). | llamafile/cuda.sh220-229 |
| --fa-all-quants | Compiles all flash-attention vector quantization combinations. | llamafile/cuda.sh58-60 |

## Comparison with Metal Backend

 Unlike the Metal backend which focuses on macOS ARM64 and performs dynamic source extraction and preprocessing, the CUDA backend relies on external toolchains (`nvcc`/`hipcc`) and external driver libraries (`nvcuda.dll`/`libcuda.so`).

 
| Feature | CUDA Backend | Metal Backend |
|---|---|---|
| Language | CUDA C++ / HIP | Metal Shading Language |
| Compilers | nvcc / hipcc | System cc (for dylib) + metal |
| Dynamic Loading | DSO via cosmo_dlopen | Dylib via cosmo_dlopen |
| Self-Contained | No (requires external driver) | Yes (includes ggml core) |
| Compilation | External scripts (cuda.sh) | In-process JIT (metal.c) |
