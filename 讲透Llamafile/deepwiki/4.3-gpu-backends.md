## Purpose and Scope

 This page documents the GPU backend abstraction layer in llamafile, which provides unified access to NVIDIA CUDA, AMD ROCm/HIP, Apple Metal, and Vulkan compute APIs. It covers runtime detection, dynamic compilation, DSO (Dynamic Shared Object) loading, and the shared backend selection logic. For implementation details of individual backends, see [CUDA Backend](https://deepwiki.com/mozilla-ai/llamafile/4.3.1-cuda-backend), [ROCm/HIP Backend](https://deepwiki.com/mozilla-ai/llamafile/4.3.2-rocmhip-backend), [Metal Backend](https://deepwiki.com/mozilla-ai/llamafile/4.3.3-metal-backend), and [GPU GEMM Kernels](https://deepwiki.com/mozilla-ai/llamafile/4.3.4-gpu-gemm-kernels). For CPU compute details, see [CPU Backend](https://deepwiki.com/mozilla-ai/llamafile/4.2-cpu-backend).

 The GPU backend system enables llamafile to run on heterogeneous hardware without requiring users to install SDKs beyond the base GPU driver. The system automatically detects available GPUs, extracts source files, and dynamically links the appropriate compute library using `cosmo_dlopen`.

 
## Architecture Overview

 The GPU backend system is designed around dynamic loading to maintain the "Actually Portable Executable" (APE) nature of llamafile. It uses a shared probing infrastructure to handle cross-platform differences, such as the `ms_abi` calling convention on Windows.

### GPU Backend Selection Flow

 llamafile attempts to load backends in priority order based on the platform and user flags. In `AUTO` mode, it favors native high-performance backends (Metal on Mac, CUDA/ROCm on Linux/Windows) before falling back to Vulkan or CPU.

## Shared Probing and Crash Guard

 A significant challenge in dynamic GPU loading is that driver initialization (triggered by checking device counts) can crash the process if the driver is broken or incompatible. llamafile implements two layers of protection:

 
 - **In-Process Crash Guard**: On POSIX systems, `gpu_run_guarded` installs signal handlers (SIGSEGV, SIGILL, etc.) and uses `sigsetjmp`/`siglongjmp` to recover from faults during the `get_device_count` call [llamafile/gpu_backend.c159-190](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/gpu_backend.c#L159-L190)
 - **Out-of-Process (OOP) Probe**: On Windows, where signal handling is less robust for foreign driver faults, `gpu_backend_probe_oop` re-executes the binary in a child process to probe the GPU. This prevents process corruption from C++/SEH exceptions that bypass `siglongjmp` [llamafile/gpu_backend.c108-118](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/gpu_backend.c#L108-L118)

## Metal Backend Integration

 The Metal backend is unique because it is compiled at runtime on macOS ARM64. Since `cosmo_dlopen()` cannot resolve symbols from the parent APE process on macOS, llamafile builds a **self-contained dylib**. This dylib includes the core GGML implementation (`ggml.c`, `ggml-alloc.c`, etc.) alongside the Metal backend code [llamafile/metal.c29-31](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L29-L31)

 The JIT pipeline involves:

 
 - **Extraction**: Extracting source and header files from the ZIP [llamafile/metal.c93-133](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L93-L133)
 - **Preprocessing**: Handling the `.metal` shader source [llamafile/metal.c25](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L25-L25)
 - **Compilation**: Invoking the system compiler to produce a `.dylib` [llamafile/metal.c26](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L26-L26)
 - **Loading**: Dynamic loading via `cosmo_dlopen()` and symbol resolution [llamafile/metal.c27](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/metal.c#L27-L27)

## CUDA, ROCm, and Vulkan Loading

 These backends follow a shared pattern of loading pre-built DSOs. llamafile looks for these libraries in priority order:

 
 - The embedded `/zip/` filesystem (extracted to a temporary app directory) [llamafile/cuda.c24-26](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.c#L24-L26)
 - The user's home directory `~/.llamafile/` [llamafile/cuda.c25](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/cuda.c#L25-L25)
 
 
### Calling Convention Handling

 On Windows, GPU DSOs typically use the `ms_abi` calling convention, while the Cosmopolitan host uses System V. The `gpu_call_*` helpers in `gpu_backend.c` wrap these calls to ensure the correct ABI is used based on the `IsWindows()` check [llamafile/gpu_backend.c39-78](https://github.com/mozilla-ai/llamafile/blob/43551265/llamafile/gpu_backend.c#L39-L78)
