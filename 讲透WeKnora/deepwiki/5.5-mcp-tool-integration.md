## Purpose and Scope

 This page documents the Model Context Protocol (MCP) tool integration subsystem within WeKnora. MCP provides a standardized protocol for external services to expose tools and resources that agents can dynamically discover and execute during reasoning loops.

 **Topics covered:**

 
 - MCP service configuration, SSRF protection, and separation of secrets via dedicated subresources (`types.MCPService`, `internal/handler/mcp_service.go`).
 - Client connection management, principal-scoped OAuth caching, and lifecycle handshakes (`mcp.MCPManager`, `mcp.MCPClient`).
 - Tool wrapper implementation, name sanitization, first-wins collision defense, and timeout extensions (`tools.MCPTool`, `tools.ToolRegistry`).
 - Human-in-the-loop (HITL) approval gating and OAuth runtime authorization (`approval.Gate`, `OAuthRequiredError`).

## MCP Architecture and Data Flow

 The MCP subsystem bridges external tool servers with internal agent execution loops. The architecture relies on persistent service definitions stored in PostgreSQL, managed by `service.mcpServiceService`, instantiated through `mcp.MCPManager`, and exposed to agents via `tools.MCPTool` registered in `tools.ToolRegistry`.

## Service Configuration, Auth, and Security Constraints

 MCP services are defined by the `types.MCPService` struct `[internal/types/mcp.go:24-45]`, which stores transport types, endpoints, custom headers, and authentication profiles.

 
### Transport Protocols and SSRF Protection

 WeKnora supports Server-Sent Events (`sse`) and HTTP Streamable (`http-streamable`) transports `[internal/types/mcp.go:18-21]`.

 
 - **Stdio Ban:** The `stdio` transport is strictly disabled in both the service layer `[internal/application/service/mcp_service.go:40-43]` and manager `[internal/mcp/manager.go:97-100]` to prevent local command execution vulnerabilities on host environments.
 - **SSRF Validation:** All outbound service URLs are validated against Server-Side Request Forgery (SSRF) rules via `secutils.ValidateURLForSSRF` during creation `[internal/handler/mcp_service.go:94-100]` and client creation `[internal/mcp/client.go:159-161]`.
 
 
### Authentication Strategies and Credential Separation

 The `types.MCPAuthConfig` struct `[internal/types/mcp.go:87-107]` manages credentials. The `applyAuthHeaders` function `[internal/mcp/client.go:86-117]` injects authentication headers based on the selected `AuthType` (`api_key`, `bearer`, or `oauth`) while applying tenant-specific `CustomHeaders`.

 Secrets (`api_key`, `token`) are isolated behind a dedicated `/credentials` subresource handled by `MCPCredentialsHandler` and are omitted from the main resource responses via `dto.MCPServiceResponse` `[internal/types/mcp.go:77-81]`.

## Client Connection Lifecycle and `MCPManager`

 The `mcp.MCPManager` struct `[internal/mcp/manager.go:16-23]` caches and coordinates active `mcp.MCPClient` connections. For OAuth-enabled services, connections are keyed per user principal (`cacheKey` `[internal/mcp/manager.go:75-80]`) to maintain isolated tokens across principals.

## Tool Wrapper, Registry, and Execution

 Discovered tools from an MCP server are wrapped by `tools.MCPTool` `[internal/agent/tools/mcp_tool.go:21-36]` to satisfy the internal agent `types.Tool` interface.

 
### Name Sanitization, First-Wins, and Security Prefixing

 
 - **Function Names:** The `Name()` method `[internal/agent/tools/mcp_tool.go:62-88]` formats tool names as `mcp_{service_name}_{tool_name}`. It sanitizes special characters and truncates strings to adhere to LLM provider function naming constraints (maximum 64 characters).
 - **First-Wins Collision Policy:** The `ToolRegistry.RegisterTool` method implements first-wins semantics to reject duplicate registrations and prevent tool execution hijacking (`GHSA-67q9-58vj-32qx`) `[internal/agent/tools/registry.go:53-58]`.
 - **Security Prefixing:** The `Description()` method `[internal/agent/tools/mcp_tool.go:92-98]` injects a mandatory `[MCP Service: ... (external)]` prefix to mitigate indirect prompt injection attacks.
 - **Execution Timeouts:** Tool execution honors `AdvancedConfig.Timeout`. Through `callToolTimeout()`, the engine's default tool budget (60s) is extended when the service specifies a longer timeout value (`#3135`) `[internal/agent/tools/mcp_tool.go:130-138]`.
 
 Sources: `[internal/agent/tools/mcp_tool.go:21-138]`, `[internal/agent/tools/registry.go:53-58]`

## Human-in-the-Loop Approval and OAuth Gating

 When executing tools, `tools.MCPTool.Execute` `[internal/agent/tools/mcp_tool.go:141-192]` enforces runtime security policies and user interaction flows.

 
### Approval Gates

 If a tool is configured to require human supervision (`MCPToolApproval` `[internal/types/mcp.go:139-142]`), execution suspends via `approval.Gate.RequestAndWait` `[internal/agent/tools/mcp_tool.go:169-182]` (issue #1173). The execution thread blocks until the user approves or rejects the action in the frontend UI.

 
### OAuth Authorization Errors

 When an MCP server returns an unauthorized response accompanied by RFC 9728 protected-resource metadata, the client raises an `OAuthRequiredError` `[internal/mcp/client.go:124-136]`, prompting the user to complete the OAuth2 authorization-code flow rather than failing with a generic error code.
