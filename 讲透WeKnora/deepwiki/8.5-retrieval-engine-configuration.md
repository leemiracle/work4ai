  This document describes the configuration and architecture of retrieval engines in WeKnora. Retrieval engines are responsible for storing and querying vector embeddings and keyword indexes, enabling semantic and hybrid search across knowledge base content. WeKnora supports multiple vector database backends that can be configured at deployment time and optionally overridden at the tenant level.

 For information about configuring embedding models that generate vectors, see [Model Configuration and Integration](https://deepwiki.com/Tencent/WeKnora/8.3-model-configuration-and-integration). For details on retrieval strategies and search algorithms, see [Hybrid Retrieval Strategies](https://deepwiki.com/Tencent/WeKnora/11.6-hybrid-retrieval-strategies). For tenant-level configuration overrides, see [Agent and Conversation Configuration](https://deepwiki.com/Tencent/WeKnora/8.2-agent-and-conversation-configuration).

## Hybrid Search and Indexing Architecture

 
### Parallel Indexing Implementation

 WeKnora uses the `KeywordsVectorHybridRetrieveEngineService` which supports hybrid search combining vector and keyword retrieval.

 Key indexing steps:

 
 - **Sanitization**: Content is sanitized to truncate overly long text inputs (above 20,000 runes) and replace embedded base64 image payloads with the placeholder `[image]` via `embeddingImagePayloadPatterns`. This prevents malformed inputs from causing embedding API errors.
 - **Batch Embedding with Exponential Backoff**: Uses up to 5 retry attempts with increasing delays (200 ms doubled each retry) for calls to `BatchEmbedWithPool`, ensuring robustness against transient embedder failures.
 - **Concurrent Batch Save**: Saves batches of embeddings concurrently with a configurable maximum concurrency (default 5) for performance efficiency and backend overload protection.

 Each retrieval engine implementation provides an `EstimateStorageSize` function to project storage requirements of the indexed embeddings:

 
| Engine | Storage Size Estimation Details | Reference |
|---|---|---|

| Elasticsearch v8 | Content size + vector size (4 bytes per dim) + metadata overhead (~250B) + 0.5x expansion index overhead | internal/application/repository/retriever/elasticsearch/v8/repository.go117-137 |

### Schema and Field Mapping / Collection Creation

 Repositories automatically ensure the required collections or indexes are created on first use, with appropriate schema and index settings:

 
 - **Milvus** creates a collection with fields like `id` (primary key), `embedding` (float vector), `content` (varchar with analyzers), and `content_sparse` (sparse vector). Adds a BM25 scoring function on `content` for sparse retrieval. It creates HNSW index on vectors and auto indexes on metadata fields. [internal/application/repository/retriever/milvus/repository.go121-203](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/repository/retriever/milvus/repository.go#L121-L203)
 - **SQLite** leverages `sqlite-vec` virtual table for vector search and `FTS5` full-text search for keywords. Implements custom tokenizer logic for improved retrieval on CJK bigrams. [internal/application/repository/retriever/sqlite/repository.go62-126](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/repository/retriever/sqlite/repository.go#L62-L126)

## Connection Configuration Security

 Sensitive fields in the `ConnectionConfig` such as passwords and API keys are automatically encrypted and decrypted using AES-GCM encryption when saved to or loaded from the database.

 
 - **Encryption** is performed via the GORM `Value()` interface hook before persisting.
 - **Decryption** occurs via the GORM `Scan()` interface hook when loading records.
 
 This ensures secret credentials for retrieval engine backends are protected at rest in the database.

# Summary

 WeKnora accommodates a wide variety of vector and keyword retrieval backends through a flexible configuration system that supports environment variables, tenant-level vector store specifications, and dynamic repository initialization. The system auto-manages collection creation, partitioning by vector dimension, and indexing schemas tailored for each backend's capabilities. Hybrid retrieval strategies leveraging multiple retriever types are supported transparently by the `KeywordsVectorHybridRetrieveEngineService`, providing robust, performant, and scalable RAG capabilities.
