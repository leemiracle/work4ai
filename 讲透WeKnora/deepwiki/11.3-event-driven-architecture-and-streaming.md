## Purpose and Scope

 This page provides a comprehensive technical deep dive into the event-driven architecture employed in WeKnora for real-time chat and streaming. It elaborates on the central `EventBus` implementation, the Server-Sent Events (SSE) streaming approach, the management of event streams via `StreamManager` (Redis or in-memory backends), and the real-time communication flow from backend to frontend.

## Architecture Overview

 WeKnora adopts an event-driven architecture to decouple the chat pipeline execution from streaming delivery and frontend consumption.

 
### Components and Layers

 
 - **Chat Pipeline Layer**: Implements a multi-stage RAG + LLM processing pipeline. The pipeline is managed via the `ChatManage` struct which holds immutable configuration (`PipelineRequest`), mutable execution state (`PipelineState`), and runtime context (`PipelineContext`) for each chat request [internal/types/chat_manage.go149-153](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/chat_manage.go#L149-L153)
 - **Event Bus Layer**: `EventBus` is a synchronous in-process publish-subscribe mechanism. It dispatches granular events such as incremental tokens, tool calls, references, and final answers during a chat request's lifetime. Each streaming request instantiates a dedicated `EventBus` to isolate event flows [internal/handler/session/agent_stream_handler.go33-47](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/handler/session/agent_stream_handler.go#L33-L47) [internal/event/event.go1-20](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/event/event.go#L1-L20)
 - **Streaming Layer**: The `AgentStreamHandler` subscribes to the `EventBus` and bridges these internal events to a `StreamManager`. The `StreamManager` handles event emission to clients over SSE, managing buffering and delivery [internal/handler/session/agent_stream_handler.go105-157](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/handler/session/agent_stream_handler.go#L105-L157) [internal/handler/session/handler.go20-68](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/handler/session/handler.go#L20-L68)
 - **Frontend Layer**: Implements the SSE client using `fetchEventSource` from the `@microsoft/fetch-event-source` library. It listens to streaming events, incrementally updating UI components such as chat bubbles and typing indicators [frontend/src/api/chat/streame.ts1-43](https://github.com/Tencent/WeKnora/blob/10973ed3/frontend/src/api/chat/streame.ts#L1-L43)

## The Internal EventBus

 The `EventBus` is the backbone for intra-process event delivery within a single chat request.

 
### Key Characteristics

 
 - **Synchronous Pub/Sub:** Handlers subscribe via `.On(eventType, callback)` and are synchronously notified on `.Emit(ctx, event)`.
 - **Per-Request Instance:** For streaming chat, each request creates a dedicated `EventBus` instance to avoid multi-session event filtering complexity. This ensures all events belong to the single conversation turn.
 - **Event Filtering:** Subscriptions are by event type, e.g., `EventAgentThought`, `EventAgentFinalAnswer`.
 
 
### Principal Classes and Interfaces

 
| Entity | File | Description |
|---|---|---|
| EventBus | internal/event/event.go | Implements the pub/sub pattern with concurrent-safe handlers registry. |
| Event | internal/event/event.go | Represents emitted events with metadata (ID, Type, SessionID, data payload). |
| ChatManage | internal/types/chat_manage.go | Carries pipeline configuration and state; includes embedded EventBusInterface field internal/types/chat_manage.go140-153 |
| AgentStreamHandler | internal/handler/session/agent_stream_handler.go | Subscribes to EventBus for relevant chat events and pushes them to SSE via StreamManager. |

 
### Event Types

 Common event types found in the streaming pipeline:

 
 - `EventAgentThought`: Reasoning or thinking message chunks emitted from the agent.
 - `EventAgentToolCall`: When the LLM decides to invoke external tools.
 - `EventAgentToolResult`: Tools returning results.
 - `EventAgentFinalAnswer`: Streaming the final answer tokens.
 - `EventAgentComplete`: Signaling completion of an agent run.

## Chat Pipeline and History Processing

 The chat pipeline coordinates multiple processing stages including query rewriting, retrieval, reranking, multi-turn context handling, and final LLM completion.

 
### Pipeline Request and State

 
 - **PipelineRequest**: Immutable input to the pipeline, including session ID, user ID, query, knowledge bases, model settings, retrieval thresholds, and flags [internal/types/chat_manage.go5-76](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/chat_manage.go#L5-L76)
 - **PipelineState**: Mutable internal data across plugins, holding interim results such as rewritten queries, intent classification, history, search results, merged results, and final chat response [internal/types/chat_manage.go113-137](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/chat_manage.go#L113-L137)
 - **PipelineContext**: Holds runtime handles such as references to `EventBus` and message IDs [internal/types/chat_manage.go139-144](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/chat_manage.go#L139-L144)
 
 
### History Loading

 Conversation history is loaded on-demand from persistent message storage for multi-turn chats. The system does not use a dedicated cross-turn cache; `sessionService` rebuilds history from the database during each request [internal/application/service/session.go108-112](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/service/session.go#L108-L112)

 
### Intent Classification and Retrieval Control

 
 - Based on the classified intent (`kb_search`, `web_search`, `greeting`, etc.), the pipeline decides whether knowledge retrieval or web search should be performed [internal/types/chat_manage.go83-109](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/chat_manage.go#L83-L109)
 - Web search is gated by the `web_search_enabled` parameter [internal/types/chat_manage.go68-76](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/chat_manage.go#L68-L76)

## SSE Streaming Implementation

 WeKnora uses Server-Sent Events (SSE) for real-time streaming responses from the backend to the frontend.

 
### Flow of a QA Request with Streaming

 
 - **Request Parsing and Validation**:
 The HTTP handler parses the incoming knowledge QA request including query, knowledge base IDs, attachments, mentions, and agent enablement flags [internal/handler/session/qa.go125-165](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/handler/session/qa.go#L125-L165)
 - **Dedicated EventBus and AgentStreamHandler Creation**:
 A new `EventBus` instance is created for the request, isolating event streams. An `AgentStreamHandler` is instantiated and subscribes to relevant `EventBus` events like `EventAgentThought` and `EventAgentFinalAnswer` [internal/handler/session/agent_stream_handler.go105-157](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/handler/session/agent_stream_handler.go#L105-L157)
 - **Service Invocation**:
 The `sessionService` executes the knowledge QA or Agent QA flow. These services invoke the chat pipeline and emit events on the `EventBus` as partial tokens or tool results become available [internal/types/interfaces/session.go58-70](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/interfaces/session.go#L58-L70)
 - **Event Streaming to Client**:
 `AgentStreamHandler` listens to `EventBus` events, transforms them into stream events, and appends them to the `StreamManager`. The `StreamManager` pushes these as SSE chunks to the client [internal/handler/session/agent_stream_handler.go136-157](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/handler/session/agent_stream_handler.go#L136-L157) [internal/handler/session/handler.go20-68](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/handler/session/handler.go#L20-L68)
 
 
### Session Ownership and Security Enforcement

 
 - The framework enforces strict session ownership semantics.
 - `loadSessionForRead` allows tenant admins or IM/embedding platform users to read sessions with proper scoping [internal/application/service/session.go62-101](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/service/session.go#L62-L101)
 - Write operations use `GetOwnedSession` to prohibit unauthorized modifications [internal/types/interfaces/session.go11-24](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/types/interfaces/session.go#L11-L24)

## Stream Managers: Redis and Memory Backends

 While details on stream managers are abstracted behind the `StreamManager` interface, the backend supports multiple implementations for real-time event persistency and delivery:

 
 - **Redis Stream Manager**: Uses Redis PUB/SUB or streams to persist and deliver events. This allows scalable distributed streaming and clustered deployment.
 - **In-Memory Stream Manager**: Stores event streams in local memory for simpler, single-instance deployments, trading off scalability.
 
 These managers buffer incremental data emitted by `AgentStreamHandler` before sending it as SSE to client connections.

## Summary

 WeKnora’s event-driven architecture elegantly decouples the chat processing pipeline from streaming delivery, enabling robust real-time communication for knowledge-based and agent-enhanced chat.

 
 - The **dedicated EventBus per request** isolates streams, minimizes filtering complexity, and supports fine-grained event emission.
 - The **AgentStreamHandler** subscribes to events and pushes updates via the `StreamManager` over SSE.
 - The **frontend SSE client**, implemented using `fetchEventSource`, consumes these streams to update the UI reactively.
 - The **pipeline architecture** supports multi-turn context, retrieval, streaming token emission, and tool calls while enforcing strict session access and ownership.
 
 This design facilitates extensibility, observability, and responsiveness for conversational AI interactions.
