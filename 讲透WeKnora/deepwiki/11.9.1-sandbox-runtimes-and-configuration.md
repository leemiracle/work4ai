  This page documents the sandbox runtimes supported by WeKnora, their configuration, session sandbox lifecycle management, the template/catalog system, idle sandbox sweeping, and tenant sandbox policies. The sandbox subsystem provides isolated execution environments for running untrusted scripts via three main backends: **Docker engine**, **E2B**, and **Cube**. The sandbox manager handles session-scoped sandbox allocation, reuse, and cleanup, delegating provider-specific operations to adapter clients ([internal/sandbox/session_manager.go1-167](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L1-L167)). Detailed implementation, data flow, and configuration considerations are described below.

 
---

 
## Overview

 WeKnora supports three primary sandbox runtimes:

 
 - **Docker**: A session-persistent backend where each session owns a dedicated long-lived container on a Docker daemon ([internal/sandbox/docker_remote_client.go1-36](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L1-L36)).
 - **E2B**: Hosted MicroVM sandbox provider via the `go-e2b` client ([internal/sandbox/e2b_remote_client.go1-43](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/e2b_remote_client.go#L1-L43)).
 - **CubeSandbox (Cube)**: Tencent's microVM backend with native support for snapshots and advanced networking ([internal/sandbox/cube_remote_client.go1-24](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_remote_client.go#L1-L24)).
 
 All runtimes preserve session state, allowing multiple script executions within the same session to share installed packages, files, and running services.

 Sandbox lifecycle management, session-to-sandbox bindings, and resource cleanup are unified via the `SessionBoundManager` type ([internal/sandbox/session_manager.go76-92](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L76-L92)). It delegates concrete backend operations to the corresponding adapter implementing the `RemoteSandboxClient` interface.

## 1. Sandbox Backends: Docker, E2B, and Cube

 
### 1.1 Docker Backend

 
 - **Implementation**: The Docker backend uses a container-per-session model ([internal/sandbox/docker_remote_client.go1-36](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L1-L36)). Each session corresponds to a container that runs indefinitely with a `sleep infinity` PID 1 process ([internal/sandbox/docker_remote_client.go61-78](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L61-L78)). All script executions, file operations, and shell commands execute via Docker exec into this container.
 - **API Usage**:

 
 - **Create**: `POST /containers/create` + `/start`, with metadata stored as container labels ([internal/sandbox/docker_remote_client.go12-18](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L12-L18)).
 - **Connect**: `GET /containers/{id}/json`, restarting stopped or paused containers as necessary ([internal/sandbox/docker_remote_client.go12-18](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L12-L18)).
 - **Exec**: `POST /containers/{id}/exec` + `/exec/{id}/start` hijack for command execution ([internal/sandbox/docker_remote_client.go12-18](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L12-L18)).
 - **Delete**: `DELETE /containers/{id}?force=1` ([internal/sandbox/docker_remote_client.go12-18](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L12-L18)).
 - **Filesystem**: Uses exec commands (`cat`, `mkdir`, `find`) instead of Docker archive API to enforce explicit user execution context and timeout control ([internal/sandbox/docker_remote_client.go19-24](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L19-L24)).
 - **Small but critical design decisions**:

 
 - Script timeouts are enforced inside the container using `timeout(1)` to kill runaway processes ([docs/sandbox-docker-backend.md55-59](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L55-L59)).
 - An externally maintained "activity marker" file (`/var/lib/weknora-sandbox-activity`) tracks sandbox usage; its modification time is used for idle sweep decisions since Docker does not natively support TTL ([internal/sandbox/docker_remote_client.go56-78](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/docker_remote_client.go#L56-L78) [docs/sandbox-docker-backend.md61-68](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L61-L68)).
 - Script execution uses an explicit user identity (`root` by default) for all exec calls to maintain consistent permissions ([docs/sandbox-docker-backend.md78-85](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L78-L85)).
 - Network modes are restricted to `bridge` or `none`, disallowing `host` or container-shared networks for security ([docs/sandbox-docker-backend.md124-126](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L124-L126)).
 - This backend is intended for single-host or private deployments where Docker Engine API is available. It does not support cross-host scheduling or kernel-level isolation (which Cube/E2B do) ([docs/sandbox-docker-backend.md151-157](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L151-L157)).
 - **Configuration**:

 
 - Controlled via fields like image, CPU/memory/pids limits, Docker daemon host, TLS certs for remote daemons, idle TTL, network mode ([docs/sandbox-docker-backend.md118-126](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L118-L126)).
 - The Docker backend may be disabled by default for security; enabling requires explicit admin configuration ([docs/sandbox-docker-backend.md16](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L16-L16)).
 - Sandbox images must include GNU `find` (with `-printf`) and `timeout` utilities and must have writable `/workspace` directory ([docs/sandbox-docker-backend.md131-135](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L131-L135)).
 
 
### 1.2 E2B Backend

 
 - **Implementation**: Uses the `go-e2b` SDK client to communicate with the hosted E2B MicroVM backend ([internal/sandbox/e2b_remote_client.go25-43](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/e2b_remote_client.go#L25-L43)). Provides long-lived session sandboxes with support for pause/resume, snapshots (via templates), and networking controls ([internal/sandbox/e2b_remote_client.go176-191](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/e2b_remote_client.go#L176-L191)).
 - **Features**:

 
 - Supports reconnecting, metadata, pause/resume, timeout refresh ([internal/sandbox/e2b_remote_client.go176-191](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/e2b_remote_client.go#L176-L191)).
 - Uses HTTP API endpoints for sandbox lifecycle.
 - Sandbox creation includes network policies and environment variable injection.
 - Does not support named volume mounts in WeKnora's current abstraction ([internal/sandbox/e2b_remote_client.go187-190](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/e2b_remote_client.go#L187-L190)).
 - **Configuration**:

 
 - API URL, API key, sandbox domain, HTTP timeouts, templates are all tenant-configurable ([internal/sandbox/tenant_config.go94-106](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L94-L106)).
 - Network policies are supported and enforced ([internal/sandbox/tenant_config.go107-134](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L107-L134)).
 - **Adapter details**: The `E2BRemoteClient` type wraps the `go-e2b` client and manages inbound traffic tokens for secure sandbox communication ([internal/sandbox/e2b_remote_client.go25-43](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/e2b_remote_client.go#L25-L43)).
 
 
### 1.3 Cube Backend

 
 - **Implementation**: Uses Tencent CubeSandbox SDK with the `envd` daemon inside the microVMs for command execution and filesystem control ([internal/sandbox/cube_remote_client.go25-43](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_remote_client.go#L25-L43)). Similar to E2B but with additional support for snapshots, volume mounts (though disabled in WeKnora), and extended networking features ([internal/sandbox/cube_remote_client.go158-178](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_remote_client.go#L158-L178)).
 - **Features**:

 
 - Supports session persistence with reconnect and metadata recovery.
 - Supports snapshots stored as templates; skills use snapshots as images ([internal/sandbox/cube_remote_client.go166-171](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_remote_client.go#L166-L171)).
 - Contains built-in requirements for template health readiness via `envd`.
 - Supports interactive terminals through PTY service ([internal/sandbox/cube_remote_client.go172-174](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_remote_client.go#L172-L174)).
 - **Configuration**:

 
 - Tenant-configurable API URL, proxy URL, sandbox domain, template ID, HTTP timeout, sandbox TTL ([internal/sandbox/tenant_config.go75-92](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L75-L92)).
 - DNS servers and network policy settings may be overridden ([internal/sandbox/tenant_config.go87-92](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L87-L92)).
 - **Adapter details**: The `CubeRemoteClient` implements `RemoteSandboxClient` wrapping Cube SDK types and normalizes Cube-specific errors and behaviors ([internal/sandbox/cube_remote_client.go25-43](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_remote_client.go#L25-L43)).

## 2. Session Sandbox Lifecycle and Manager (`SessionBoundManager`)

 The `SessionBoundManager` type orchestrates sandbox lifecycle management with emphasis on one persistent sandbox per tenant session (`[internal/sandbox/session_manager.go:3-23]`, [internal/sandbox/session_manager.go76-92](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L76-L92)):

 
 - **Responsibilities**:

 
 - Bind each unique `SessionID` to a remote sandbox instance.
 - Lazily create sandboxes on first `Execute` call referencing a session ([internal/sandbox/session_manager.go12-17](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L12-L17)).
 - Reuse sandboxes for subsequent calls in the same session.
 - Serialize lifecycle operations using a distributed lifecycle lock to prevent concurrent bind/create/race conditions ([internal/sandbox/session_manager.go12-17](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L12-L17)).
 - Delegate backend-specific operations to the injected `RemoteSandboxClient` ([internal/sandbox/session_manager.go4-10](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L4-L10)).
 - Support ephemeral stateless sandboxes when `ExecuteConfig.SessionID` is empty (executes script in a fresh sandbox and destroys it immediately) ([internal/sandbox/session_manager.go18-20](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L18-L20)).
 - Delegate session existence validation by a `SessionExistenceChecker` ([internal/sandbox/session_manager.go140-142](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L140-L142)).
 - Handle workspace directory preparation on every execution, including input attachment mounts and artifact output directories (`[internal/sandbox/session_manager.go:39-48]`, [internal/sandbox/session_manager_test.go111-141](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager_test.go#L111-L141)).
 - Provide cleanup operations, ensuring sandbox deallocation and orphan cleanup on session termination or failures ([internal/sandbox/session_manager.go66-70](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L66-L70)).
 - Support provider-neutral sandbox APIs with backend-specific configuration managed in `Config` ([internal/sandbox/session_manager.go71-75](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L71-L75)).
 - **Key constants for paths and environment variables**:

 
 - Durable attachments input at `/workspace/input` (`SessionInputRoot`, read-only) ([internal/sandbox/session_manager.go39-41](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L39-L41)).
 - Skill artifacts output at `/workspace/output` (`SessionOutputRoot`, read-write) ([internal/sandbox/session_manager.go43-47](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L43-L47)).
 - Environment variables used within sandboxes: 
 - `WEKNORA_SKILL_OUTPUT_DIR` (`skillOutputEnvVar`) for output directory ([internal/sandbox/session_manager.go49-50](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L49-L50)).
 - `WEKNORA_SESSION_INPUT_DIR` (`sessionInputEnvVar`) for input attachments ([internal/sandbox/session_manager.go52-56](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L52-L56)).
 - Workspace root inside the sandbox is `/workspace` (`SessionWorkspaceRoot`) ([internal/sandbox/session_manager.go58-60](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L58-L60)).

## 3. Template Catalogs

 
 - **Concept**:

 
 - All sandboxes are created from pre-baked templates (images).
 - Templates serve as reusable base environments with pre-installed tools.
 - **Cube Specifics**:

 
 - Cube maintains a template catalog via its API ([internal/sandbox/cube_remote_client.go188](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_remote_client.go#L188-L188)).
 - Snapshots are stored within this catalog but filtered out when listing templates for selection ([internal/sandbox/cube_template_catalog_test.go178-204](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_template_catalog_test.go#L178-L204)).
 - Standard templates are recognized by image info or naming conventions ([internal/sandbox/cube_template_catalog_test.go35-97](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_template_catalog_test.go#L35-L97)).
 - Templates expose metadata such as name, version, creation time, instance type, network type, and internet access policy ([internal/sandbox/cube_template_catalog_test.go128-157](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/cube_template_catalog_test.go#L128-L157)).
 - **Docker Specifics**:

 
 - Docker images serve as templates.
 - The default Docker image is `wechatopenai/weknora-sandbox:main`.
 - Images must comply with required setup (GNU find, timeout, writable workspace) ([docs/sandbox-docker-backend.md131-135](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L131-L135)).
 - **E2B Specifics**:

 
 - Uses template IDs managed on the backend side.
 - Template info is maintained in API but appears largely opaque to the client.

## 4. Idle Sweeping and Sandbox Cleanup

 
 - **Idle Sweeping**:

 
 - Each backend treats idle resource cleanup differently ([internal/sandbox/session_manager.go21-23](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L21-L23)).
 - **Docker**:

 
 - No native TTL or idle timeout in Docker Engine API ([docs/sandbox-docker-backend.md61-62](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L61-L62)).
 - WeKnora implements idle sweeping by reading modification times of the **activity marker file** (`/var/lib/weknora-sandbox-activity`, `dockerActivityMarker`) inside containers (`[internal/sandbox/docker_remote_client.go:56-59]`, [docs/sandbox-docker-backend.md61-68](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L61-L68)).
 - Container is considered idle if the activity marker's mtime exceeds configured threshold (`DockerIdleTTL`) ([docs/sandbox-docker-backend.md61-63](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L61-L63)).
 - Cleaning is rate limited and occurs asynchronously during create/connect operations ([docs/sandbox-docker-backend.md63-65](https://github.com/Tencent/WeKnora/blob/10973ed3/docs/sandbox-docker-backend.md?plain=1#L63-L65)).
 - **E2B and Cube**:

 
 - Both providers support native idle timeouts and will reap sandboxes themselves on timeout ([internal/sandbox/session_manager.go21-22](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L21-L22)).
 - WeKnora respects their TTLs configured in sandbox creation requests.
 - **Session Cleanup**:

 
 - `SessionBoundManager` performs cleanup on session close or orphan detection.
 - Lifecycle coordinator serializes cleanup with a timeout (`sessionLifecycleCleanupTimeout`, 30 seconds) ([internal/sandbox/session_manager.go66-69](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/session_manager.go#L66-L69)).

## 5. Tenant Sandbox Configuration and Policy Resolution

 
 - **Tenant Configuration (`types.TenantSandboxConfig`)**:

 
 - Defines per-tenant sandbox runtime settings ([internal/sandbox/tenant_config.go38-41](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L38-L41)).
 - Includes backend selection (`cube`, `e2b`, or `docker`) and all provider-specific parameters ([internal/sandbox/tenant_config.go55-128](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L55-L128)).
 - Holds network policies (`SandboxNetworkPolicy`), environment variables, template/images, and timeouts ([internal/sandbox/tenant_config.go62-74](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L62-L74)).
 - **Global Defaults and Inheritance**:

 
 - The system has a base global default config ([internal/sandbox/tenant_config.go40-44](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L40-L44)).
 - Tenant configs are *self-contained*; provider-specific fields are not inherited from global for security and clarity ([internal/sandbox/tenant_config.go50-54](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/sandbox/tenant_config.go#L50-L54)).
