  This page documents the security mechanisms and multi-tenant isolation model implemented across the WeKnora codebase. It covers tenant access control, Role-Based Access Control (RBAC), API key capabilities, knowledge base organization sharing, and core security protections including Server-Side Request Forgery (SSRF) defense, XSS mitigation, and path traversal validation.

 
---

 
## Multi-Tenancy Model

 WeKnora uses a tenant-per-deployment database schema combined with per-tenant isolation keys. Users belong to a primary home tenant (`TenantID`) but can participate across multiple tenants via `TenantMember` relationships. All persistent resources—such as knowledge bases, chunks, chat sessions, and custom agents—carry a `tenant_id` column and are filtered by it in every repository query.

 
### Tenant Resolution and Context Flow

 The system resolves active tenant context via incoming request metadata, JWT claims, and tenant headers. The `tenantService` handles tenant lifecycle operations, including validation of unique storage buckets and default storage backend creation [internal/application/service/tenant.go33-100](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/service/tenant.go#L33-L100)

## Role-Based Access Control (RBAC) and API Key Authorization

 WeKnora enforces a granular RBAC matrix distinguishing between tenant-wide infrastructure roles and resource-specific ownership. The logic is centralized inside `rbacGuards` [internal/router/rbac.go113-149](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/rbac.go#L113-L149)

 
### Tenant Roles and Guard Selection

 The authorization framework defines four tenant-level roles [internal/router/rbac.go19-23](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/rbac.go#L19-L23):

 
 - `Viewer`: Read-only access to tenant resources. Enforced by `RequireRole(types.TenantRoleViewer)` [internal/middleware/rbac.go67-111](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/middleware/rbac.go#L67-L111)
 - `Contributor`: Can create resources (KBs, agents) and manage items they created. Enforced by `RequireRole(types.TenantRoleContributor)` [internal/middleware/rbac.go48-51](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/middleware/rbac.go#L48-L51)
 - `Admin`: Can manage tenant-wide infrastructure (Models, Vector Stores, Sandbox Configs). Enforced by `RequireRole(types.TenantRoleAdmin)` [internal/middleware/rbac.go40-45](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/middleware/rbac.go#L40-L45)
 - `Owner`: Full administrative authority over the workspace.
 
 When designing or auditing routes, developers choose between role-only guards and ownership guards using two criteria [internal/router/rbac.go26-38](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/rbac.go#L26-L38):

 
 - **Resource Creator**: Resources stamped with `creator_id` (KBs, documents, chunks, custom agents) use `OwnedXxxOrAdmin` guards. Tenant-wide infrastructure (models, vector stores, IM channels) uses `Admin()` guards.
 - **Side Effect Scope**: Actions that modify shared state or expose resources require ownership or admin privileges [internal/router/rbac.go53-65](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/rbac.go#L53-L65)

## Knowledge Base Access and Organization Sharing

 Access to a Knowledge Base is resolved dynamically via `RequireKBAccess` [internal/middleware/kb_access.go158-169](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/middleware/kb_access.go#L158-L169) The resolution checks three mechanisms:

 
 - **Direct Ownership**: The KB belongs to the active tenant.
 - **Organization Sharing**: The KB is shared with an organization of which the tenant is a member, validated via `CheckTenantKBPermission` [internal/middleware/kb_access_test.go44-49](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/middleware/kb_access_test.go#L44-L49)
 - **Agent Sharing**: The caller accesses the KB via a shared custom agent [internal/middleware/kb_access_test.go121-127](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/middleware/kb_access_test.go#L121-L127)
 
 Successful resolution stores a `KBAccess` struct in the Gin context under `KBAccessContextKey` and updates the request context with the authoritative resource tenant ID [internal/middleware/kb_access.go20-36](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/middleware/kb_access.go#L20-L36)

## Security Implementation and Best Practices

 
### Input Sanitization and XSS Protection

 Backend utilities protect against injection attacks and cross-site scripting (XSS) [internal/utils/security.go26-46](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L26-L46)

 
 - **`SanitizeHTML`**: Inspects input against compiled `xssPatterns` (such as `<script>`, `javascript:`, and event handlers) and escapes strings if malicious patterns match [internal/utils/security.go49-70](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L49-L70)
 - **`ValidateInput`**: Validates control characters, ensures valid UTF-8, and rejects disallowed patterns [internal/utils/security.go80-106](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L80-L106)
 
 Sources: [internal/utils/security.go26-106](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L26-L106)

 
### Path Traversal Prevention

 File and object storage routines ensure operations stay within designated directories [internal/utils/security.go108-146](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L108-L146)

 
 - **`SafePathUnderBase`** and **`SafeJoinUnderBase`**: Canonicalize and verify that target paths fall strictly under `baseDir`, rejecting `../` traversal attempts [internal/utils/security.go110-146](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L110-L146)
 - **`SafeFileName`** and **`SafeObjectKey`**: Clean file names and object storage keys, forbidding path traversal sequences and enforcing length limits [internal/utils/security.go148-176](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L148-L176)
 
 Sources: [internal/utils/security.go108-176](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L108-L176)

 
### SSRF and Network Request Protection

 To prevent Server-Side Request Forgery, outbound HTTP requests and web fetching tools evaluate target URLs against blocked hostnames and restricted IP ranges [internal/utils/security.go217-248](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L217-L248) The `Fetcher` struct integrates SSRF-safe HTTP clients and transport layers [internal/infrastructure/web_fetch/fetcher.go93-102](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/infrastructure/web_fetch/fetcher.go#L93-L102)

 
 - **Restricted Hostnames**: Blocks internal hostnames such as `localhost`, `127.0.0.1`, cloud metadata services (`metadata.google.internal`, `metadata.tencentyun.com`), and container orchestrator endpoints (`kubernetes`, `host.docker.internal`) [internal/utils/security.go217-234](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L217-L234)
 - **Restricted Suffixes**: Blocks domains ending in `.local`, `.internal`, `.svc.cluster.local`, and similar internal TLDs [internal/utils/security.go236-248](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/utils/security.go#L236-L248)
