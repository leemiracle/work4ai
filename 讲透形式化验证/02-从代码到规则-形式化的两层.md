# 02 · 从代码到规则：形式化的两层

> [00](./00-为什么形式化+Lean4SOTA.md) §七 已经预告了形式化验证的四个层次。本章把最关键的对子——**形式化代码**（seL4/Atmosphere 路线）vs **形式化因果规则**（神经符号新范式）——彻底拆开。这是 2024-2026 形式化方法正在发生的**范式分裂**：一边是"把系统代码证到二进制级"，一边是"把 LLM 蒸馏出的世界规则证到 trace 上保持"。理解这两层的边界，是判断"形式化能保证什么"的前提。
>
> 配套：[00 §七](./00-为什么形式化+Lean4SOTA.md)（蓝海判断）+ [`讲透神经符号`](../讲透神经符号/)（规则蒸馏）

---

**2025 年春。** 一位 PhD 在组会上汇报：用 Lean4 验证了一个"机器人绝不能把人放进洗碗机"的因果规则。导师皱眉："你这是形式化验证吗？seL4 的传统是验证**代码忠实实现规范**——你这里根本没有代码，你验证的是一段从 world model 蒸出来的逻辑命题。"学生愣住——他从来没想过**自己做的"形式化"和 seL4 的"形式化"不是一回事**。三周后他写出论文，提出"**形式化代码** vs **形式化规则**"的框架，明确两者验证对象、TCB、健全性来源都不同。**这件事定义了 2025-2026 形式化方法的一个新分支**。

---

## 一、形式化代码：seL4 的传统路线

### 1.1 验证对象

**代码忠实实现规范**——即 refinement：

$$
\text{抽象规范} \sqsupseteq \text{设计规范} \sqsupseteq \text{C 代码} \sqsupseteq \text{二进制}
$$

每一层证明"下层是上层的精化"，最终结论：**二进制忠实执行了抽象规范**。

### 1.2 TCB（Trusted Computing Base）

- 规范本身（人写的，可能写错）
- 验证器内核（Lean4 / Isabelle / Coq——见 [00 §6.1](./00-为什么形式化+Lean4SOTA.md) 的 #14576 漏洞）
- **不**包括：被验证的代码本身（它被证明了）

### 1.3 代表项目

| 项目 | 验证器 | proof-to-code |
|------|--------|---------------|
| seL4 | Isabelle/HOL | 20:1 |
| CompCert | Coq | ~10:1 |
| Atmosphere（SOSP 2025）| Verus + Z3 | **3.32:1** |
| seLe4n | Lean4 | 仍进行中 |

### 1.4 成本与边界

- 成本：每行 C 代码 3-20 行证明代码
- 边界：必须显式声明**未验证部分**（seL4 没验证多核并发、DMA、时序侧信道——见 [00 §2.3](./00-为什么形式化+Lean4SOTA.md)）

## 二、形式化因果规则：神经符号的新范式

### 2.1 验证对象

**从事件流蒸馏出的因果规则在所有合法 trace 上保持**。规则形如：

```lean
-- 一条从 world model 蒸馏的因果规则
theorem never_put_human_in_dishwasher
    (trace : EventTrace s₀ sₙ)
    (hRobot : trace.all_actions_by_robot)
    (hSafety : safety_inv s₀) :
    ∃ never : ∀ t ∈ trace, t.action ≠ put_human_in_dishwasher := by
  ...
```

这里**没有"代码 vs 规范"的层级**——规则本身就是被验证物，trace 是其语义域。

### 2.2 规则从哪里来

**关键差异**：传统形式化的规范是人写的；因果规则的来源是 **LLM / world model 蒸馏**：

```
LLM/world model
    ↓ 蒸馏（神经符号 pipeline，见 [讲透神经符号]）
候选规则集（自然语言 / 半形式化）
    ↓ 人工 + LLM 翻译为 Lean4
Lean4 规则集
    ↓ 形式化验证（本章）
证明：规则在所有 trace 上保持
```

### 2.3 TCB 完全不同

| 部分 | 传统形式化代码 | 形式化因果规则 |
|------|--------------|---------------|
| 规范来源 | 人写 | **LLM 蒸馏**（噪声来源）|
| 验证对象 | 代码 vs 规范的精化 | 规则 vs trace 的保持 |
| 健全性风险 | 验证器内核 bug | **规范本身错**（LLM 幻觉）+ 内核 bug |

> 🟥 **铁律**：形式化因果规则的**最大风险不是 Lean4 内核 bug，而是 LLM 蒸馏出的规则本身错了**——你证了一条错的规则。**人审 + 多 LLM 交叉验证** 是必须的，不是可选的。

## 三、为什么两者必须分清

### 3.1 误用 1：用"形式化代码"标准指责"形式化规则"

有人质疑"seLe4n 没有完整 OS 验证就不算形式化"——这是**层次错位**：seLe4n 做的是形式化代码（验证 OS 实现），而形式化因果规则**不需要也不应该**证 OS 实现，它证的是规则在抽象 trace 上的保持性。

### 3.2 误用 2：用"形式化规则"冒充"形式化代码"

反过来更危险：声称"我用 Lean4 形式化了我的 AI 系统"——但只是蒸馏了几条规则。**没有代码 refinement，不能声称系统是 seL4 级别 verified**。这是 [00 §六](./00-为什么形式化+Lean4SOTA.md) "验证剧场"的新变种。

### 3.3 误用 3：忽视 trace 模型的语义假设

形式化因果规则依赖一个**事件 trace 形式化**——这个模型本身要不要证？如果 trace 模型漏了某种事件类型，规则可能"在错误的世界里被证明正确"。**trace 模型的完备性是隐藏 TCB**。

## 四、两者的交叉点

### 4.1 形式化代码提供"基础不变式"

形式化代码（seL4/Atmosphere）证明的系统不变式（如"用户态无法直接访问内核内存"），可以作为**形式化因果规则的 trace 模型的前置假设**——这样规则证明建立在已被验证的系统层之上。

### 4.2 形式化规则提供"应用层安全"

形式化代码只证"机制层"（kernel 正确），证不了"应用层策略对"（如"机器人不该这么做"）。**因果规则填补这个空白**。

> 🎯 **组合**：形式化代码（机制）+ 形式化规则（策略）= **从硬件到应用的完整可信栈**。这是 2026 的前沿方向（⚡ 推断，未成熟）。

## 五、反模式与陷阱（L4）

### 5.1 陷阱 1：以为蒸馏的规则"看起来对"就行

LLM 蒸馏的规则**经常表面合理但语义错**——尤其在边界条件（极端情况、长 trace）。**必须在 Lean4 里跑通证明，不能只人审自然语言版本**。

### 5.2 陷阱 2：忽视 trace 模型完备性

trace 模型若漏了某种事件类型，规则证明在"残缺世界"里成立——上线后必崩。**trace 模型要从世界本体出发，不能从 LLM 输出反推**。

### 5.3 陷阱 3：混淆"规则保持"和"规则有用"

Lean4 能证明"规则 X 在所有 trace 上保持"——但**规则 X 可能根本没用**（比如 `True`）。形式化只保证 soundness，**有用性要靠下游评测**。

### 5.4 陷阱 4：忽视 [00 §6.1](./00-为什么形式化+Lean4SOTA.md) 的 #14576 类风险

Lean4 内核本身可能漏——形式化因果规则同样受影响。**CI 加固 checklist（[00 §6.3](./00-为什么形式化+Lean4SOTA.md)）对两层都适用**。

## 七、费曼回炉（L2 自检）

- **F2 卡壳点**：我曾以为"形式化验证就是 Lean4"——重读后发现 **Lean4 只是工具**，**验证对象的层次**才是关键：seL4 证"代码 vs 规范"，因果规则证"规则 vs trace"，两者**完全不同的形式系统**，只是恰好都用 Lean4。
- **F3 术语翻译**：
  - "refinement" → 一层一层证明"下面那层没歪曲上面那层"，最终代码忠实执行规范
  - "trace 上的保持性" → 不管世界经历多少步，这条规则永远成立
  - "TCB（可信计算基）" → "我们承认不证自明的部分"——人写的规范、Lean4 内核、trace 模型都是 TCB
- **F4 回炉**：v1 我把"形式化代码"和"形式化规则"混在一节讲；v2 拆成两节并加 TCB 对比表——**最大的 gap 是"健全性来源不同"**，v1 完全没讲清。

---

> 🎯 **一句话**：形式化方法在 2024-2026 分裂成两层——**形式化代码**（seL4 路线，证 refinement）vs **形式化因果规则**（神经符号路线，证规则在 trace 上保持）。两者验证对象、TCB、健全性风险都不同，**不能混用术语，更不能互相冒充**。
