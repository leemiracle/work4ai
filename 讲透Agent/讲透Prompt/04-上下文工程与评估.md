# 04 — 上下文工程与 Prompt 评估

> 00-03 讲了 prompt 的技术（条件/Few-shot/CoT/结构化）。这一篇讲两个工程层面：**长上下文怎么组织信息**（上下文工程），**prompt 怎么评估和优化**。本篇概念为主。
>
> 配套：无新实验（概念方法论）。

---

## 1. 上下文工程（Context Engineering）

随着模型上下文从 4K 涨到百万 token，"能塞很多"不等于"塞得好"。**上下文工程**研究：怎么把信息组织好放进 prompt。

### Lost in the Middle（中间丢失现象）

Liu et al. 2023 发现：模型对**长上下文的开头和结尾**记得好，**中间的信息容易被忽略**。

```
准确率(信息在上下文位置):
  开头 ████████████ 高
  中间 ████         低   ← "中间丢失"
  结尾 ████████████ 高
```

**含义**：放 RAG 检索结果时，**最相关的放首尾**，别堆中间。

### 信息密度

- **冗余 prompt**：啰嗦、重复、无关信息 → 模型注意力被稀释。
- **高密度 prompt**：每句话都承载必要信息 → 模型聚焦。

**原则**：prompt 要像好代码——无废话，每行有用。删掉"请你帮我"、"非常感谢"这类噪声。

### 位置策略

| 信息 | 放哪 |
|---|---|
| 核心指令 | **开头**（系统提示）或 **结尾**（紧贴问题） |
| RAG 检索文档 | 最相关的放**首尾**，其余中间 |
| Few-shot 例子 | 任务前，格式统一 |
| 最终问题 | **结尾**（recency 优势） |

## 2. Prompt 评估（怎么知道 prompt 好不好）

prompt 是概率的，不能"写完就上线"。必须评估。

### 三层评估

| 层 | 方法 | 目的 |
|---|---|---|
| **单元测试** | 准备 N 个典型输入，看输出对不对 | 基础正确性 |
| **LLM-as-Judge** | 用强模型当裁判给输出打分 | 主观质量、规模可扩 |
| **人工评测** | 真人评 | 金标准，贵 |

### A/B 测试

线上：两个 prompt 版本各跑一部分流量，比指标（准确率/满意度/点击）。统计显著才换。

### 自动 prompt 优化

- **DSPy**：把 prompt 当可优化参数，用数据自动调（甚至自动生成/选择 Few-shot 例子）。
- **Prompt 容错**：测 prompt 对输入扰动的鲁棒性（换说法、加噪声）。

---

## 3. Prompt 优化的通用 checklist

写 prompt 时自检：
1. **角色清晰**：给模型一个明确身份（"你是医学专家"）。
2. **任务明确**：要它做什么，无歧义。
3. **格式指定**：要 JSON/列表/某结构，写清。
4. **给约束**：长度、语气、禁做的事。
5. **Few-shot 必要时**：复杂格式给例子。
6. **CoT 必要时**：推理任务加"一步步思考"。
7. **分隔符**：用 ```、XML 标签把指令/数据/例子分开，避免混淆。
8. **防越界**：明确"只基于给定信息"防幻觉。

---

## 4. 一句话总结

> **上下文工程关注信息怎么放进 prompt：警惕"中间丢失"（关键信息放首尾）、保持高信息密度（删冗余）、合理定位（指令开头/问题结尾）。Prompt 评估不能省——单元测试 + LLM-as-Judge + 人工三层，线上 A/B，必要时用 DSPy 自动优化。好 prompt 像好代码：角色清、任务明、格式定、约束全、无废话。**
