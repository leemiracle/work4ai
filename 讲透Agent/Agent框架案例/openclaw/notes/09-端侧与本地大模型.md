# 09 · 端侧与本地大模型：瘦网关 + 三条本地推理路径

> 一句话：**openclaw 的端侧哲学是"Gateway 中枢尽量瘦、推理可以完全本地、手机只当外设"——本地模型不是二等公民，但每条本地路径都为"工具调用不可靠"这个现实做了大量防御工程。**
>
> 证据基准：钉版 `f612675284`。docs/install/raspberry-pi.md · docs/providers/{ollama,lmstudio,vllm}.md · docs/concepts/memory-search.md · extensions/llama-cpp/（19 文件 ~3.3K 行深读）。姊妹篇：06/07/08（memory/context），本篇=**部署与推理层**。

## 1. 端侧拓扑：中枢 + 外设 + 后端三层

**默认/派生具体模型**：llama-cpp 对话默认=`gemma-4-E4B-it` Q4_K_M（4.98GB，pin revision+sha256，E4B=Gemma4 "有效 4B" 档）；嵌入=`embeddinggemma-300m-qat` Q8_0（328MB）；杂务派生 anthropic 主力时=`claude-haiku-4-5`（plugin.json:82）、openai 主力时=`gpt-5.6-luna`（:41）；Ollama 引导建议 gemma4，云签入建议 kimi-k2.5:cloud/glm-5.1:cloud。全是各家产品线**最小可用档**。推理三种进程形态：managed llama-server（spawn pinned b10357，supervisor 管生命周期）/ 外部 ollama daemon（native /api/chat）/ 云 API——openclaw 本身不含引擎，永远是 HTTP 客户端。

```
┌─ Gateway（中枢）────────────────┐   ┌─ Nodes（外设）──────────┐
│ 树莓派4/5 · VPS · Mac · Linux   │◄──│ Android/iOS/Watch/Mac   │
│ 跑全部 harness：会话/审批/      │WS │ 菜单栏app/无头主机       │
│ 记忆/插件/频道                  │   │ 只暴露 camera/screen/   │
│ 最低 1GB RAM + swap            │   │ location/voice 命令面    │
└──────────┬──────────────────────┘   │ 不跑模型不跑 gateway    │
           │ 模型调用                  └─────────────────────────┘
   ┌───────┴────────┬─────────────────┬──────────────┐
   │ 云 API(默认)    │ LAN 推理机       │ 同机本地      │
   │ anthropic 等   │ gpu-box:11434   │ 127.0.0.1    │
   │                │ (可作 node 挂载) │ ollama/llama-server │
   └────────────────┴─────────────────┴──────────────┘
```

- **树莓派官方定位**（raspberry-pi.md:10,176）：Pi 只跑 Gateway，"$35-80 一次性成本"；**明确警告"不要在 Pi 上跑本地 LLM，再小的模型也慢到没用"**。最低规格 Pi 4 1GB+swap，推荐 Pi 5/USB SSD；调优项=NODE_COMPILE_CACHE+OPENCLAW_NO_RESPAWN+禁 GPU 内存
- **手机是 node 不是主机**：Android/iOS app 经 WebSocket 连 Gateway，暴露屏幕/相机/定位/语音唤醒（platforms/android.md:17 "Android does not host the Gateway"）；配对走设备审批。**但安卓有第二条路**：Termux 跑完整 Gateway 被**代码级支持**——home-dir.ts:22-33 `resolveTermuxHome`（PREFIX 正则 `com.termux/files/usr` + ANDROID_DATA 双验证，排进解析链第三位）；tools-manager.ts:387-395 检测 android 平台不下载 Linux 二进制（Bionic libc 不兼容），改提示 `pkg install`。**Termux 本地推理的硬边界**：llama-cpp managed 是 glibc 预编译资产（glibc≥2.34，musl 拒绝），Bionic 不是 glibc → managed 装不上；现实 = Gateway+云 API，或 Termux 自编译 ollama（体验等同 Pi："再小的模型也慢到没用"）。手机跑 LLM 是电池/散热/内存三杀
- **ARM64 一等公民**：Node/Telegram/Chromium 全兼容，偶缺 arm64 构建的是可选 Go/Rust 工具（:193）

## 2. 本地推理三路径对比

| | **Ollama**（主推） | **llama-cpp 扩展**（managed） | **LM Studio / vLLM** |
|---|---|---|---|
| 协议 | **native `/api/chat`**（非 /v1!） | OpenAI-compat（spawn llama-server） | OpenAI-compat `/v1` |
| 工具调用 | 原生支持（/api/show capabilities 检测） | 原生 delta.tool_calls + **GBNF schema 清洗** | 走 openai-completions，vLLM 需正确 parser |
| 安装 | `ollama pull`，自动发现 | 自动下载 pinned llama-server（SHA-256 双验证） | 用户自装 |
| embedding | `nomic-embed-text`（自动拉） | `embeddinggemma-300m-qat`（~0.3GB） | /v1/embeddings |
| 适合 | 大多数本地场景 | 零 API key 全托管 | 已有服务器复用 |

**Ollama 铁律**（ollama.md:23-25,540）：`baseUrl` 绝不带 `/v1`——OpenAI 兼容层会**破坏工具调用**（模型把 tool-call JSON 当纯文本吐出）。native API 流式+工具调用同时可用；`/api/show` 报 tool 能力 + ≥16K 上下文才自动推荐模型。

**llama-cpp 扩展双模式**（README.md:5-9）：**Managed**=OpenClaw 全托管（pinned b10357 构建，6 平台资产各带 sha256）；**External**=连用户自跑的 llama-server（绝不 install/start/stop）。非 node-llama-cpp 绑定——**spawn 预编译二进制**，宿主 supervisor 管生命周期（ready 30s 超时/空闲 10min 自停/lease 引用计数共享单实例）。

## 3. 本地模型的工具调用防御工程（最有含金量的部分）

1. **GBNF schema 清洗**：llama.cpp 把 JSON Schema 编译成 GBNF 语法，`pattern` 与 `maxLength≥2000` 的重复展开会**超规则上限**——扩展递归删除这些字段（clean-for-llamacpp-gbnf.ts:3-60）；动因是 cron 工具 65536 字符的 script 上限
2. **能力双验**：external 模式要求 `/props` 的 `chat_template_caps.supports_tools && supports_tool_calls` 双真才开工具（models.ts:95-97），且需 tool-capable Jinja 模板
3. **逃生舱**：`compat.supportsTools: false`——模型实在处理不了 schema 就诚实关掉工具换稳定（ollama.md:770-771）
4. **thinking 循环抑制**：小 Qwen 思考模型会"loop or spend budget on hidden reasoning"——`params.thinking: false` + API 级 `think` 顶层字段（非 options.think）（ollama.md:982-984）
5. **乱码当失败**：Kimi/GLM 长串非语言符号=provider 失败而非成功回复，走正常重试（ollama.md:1253-1257）

## 4. 资源现实：数字说话

- **16 GiB RAM 门槛**：llama-cpp managed 模式 <16GiB 不提供默认模型下载，指路小 GGUF/Ollama/云（llama-cpp defaults.ts:46-52）
- **为什么 contextWindow 默认 65536**：**OpenClaw 系统提示词本身就 ~31K tokens**——8K 上下文模型首轮即溢出（defaults.ts:30-33）。这是 08 篇分层提示在本地侧的直接代价
- **双预算对齐**：`contextTokens`（cap OpenClaw 输入预算）与 `params.num_ctx`（cap Ollama 运行时上下文）要一起调，硬件跑不动广告上下文时两边都压（ollama.md:1298-1326）
- **冷启动**：大模型首次加载慢→`timeoutSeconds: 300` + `keep_alive: "15m"` 防反复卸载；cron 对本地 provider 先探 `/api/tags`（5min 缓存），守护进程没起直接记 skipped 不打失败请求（ollama.md:234-239）
- **量化默认**：Q4_K_M（chat）+ Q8_0（embedding）；唯一 QAT 痕迹=embeddinggemma-300m-**qat**（量化感知训练版，~0.3GB）
- **WSL2 崩溃循环**（ollama.md:1139-1175）：ollama.service `Restart=always` + GPU 模型加载钉住内存→Hyper-V 无法回收→Windows 杀 VM→systemd 重启→循环；openclaw 检测到该组合会在启动时警告

## 5. 全本地化：四个推理位都能换成本地

| 推理位 | 本地化配置 | 证据 |
|---|---|---|
| 主对话 | `model.primary: "ollama/qwen3.5:9b"` | ollama.md |
| 子代理/兜底 | fallbacks 数组混搭云+本地；**显式 /model 选择是严格的**——本地模型挂了直接报错，不静默换云 | model-failover.md:263 |
| 记忆嵌入 | `memory.search.provider: "ollama"/"local"/"lmstudio"`（11 家中 3 家本地零 key） | memory-search.md:51-63 |
| dreaming/日记 | `plugins.entries.memory-core.config.dreaming.model` | 06 篇 |
| 压缩前 flush | `compaction.memoryFlush.model: "ollama/qwen3:8b"` | 08 篇 |
| 图像理解 | `imageModel.primary: "ollama/qwen2.5vl:7b"` + `num_ctx: 2048` 防低配机崩溃 | ollama.md:400-437 |

**lean 削面**（ollama.md:730-777）：`experimental.localModelLean: true` 把 browser/cron/message/media/voice/PDF 重工具移出直达面（进 Tool Search）——本地小模型处理不了大工具面时的**先削工具再动全局运行时**次序。

## 6. node-local inference：GPU 盒当推理外设

端侧最有想象力的模式（ollama.md:267-357）：GPU 工作站跑 `openclaw node run` 挂到 Pi/NAS 上的 Gateway，经配对审批后 agent 获得工具 `node_inference`（discover→run），**推理跑在节点自己的 loopback**，prompt/响应走已认证的 Gateway 连接。默认 512 token 输出（硬顶 8192）、强制关 thinking、`/api/ps` 排已加载模型优先。隐私边界清晰：节点推理不复用远端云配置。

## 7. 默认模型与"小模型补强工程学"

**默认本地模型**（llama-cpp defaults.ts:20-36）：对话=`gemma-4-E4B-it` Q4_K_M（~5GB，有效 4B 的中小模型）+ 嵌入=`embeddinggemma-300m-qat`（~328MB QAT 版）。选择逻辑=资源下限：16GiB RAM 门槛（"below 16 GiB the default model thrashes"）；Ollama 侧 onboarding 仅在 `/api/show` 确认 **tool 支持 + ≥16K 上下文**才自动推荐（setup-model-selection.ts:17）。

**八层补强——没有一层是"指望模型变强"**：

1. **格式兜底**：tool-call-repair 3165 行——把小模型写成纯文本的工具调用（`[tool] {...}` 括号/Harmony `<|channel|>`/XML-ish/`[END_TOOL_REQUEST]`）解析修复回结构化事件，工具名过白名单（attempt-tool-call-text-promotion.ts）
2. **语法约束**：llama-server 把 JSON Schema 编译成 GBNF——输出文法上强制合法 JSON
3. **工具面瘦身**：`localModelLean`（移重工具进 Tool Search）+ `compat.supportsTools:false`（诚实关）+ 子代理 `promptMode:minimal`
4. **任务分层**：`defaultUtilityModel` 干杂活；dreaming/flush/active-memory/子代理每个推理位独立配模型——小模型对话、云模型巩固的混搭是一等用法
5. **行为监控**：loop-detection（文档明说小模型建议开启）、`thinking:false` 防思考循环、乱码=失败
6. **安全兜底**：≤300B 参数 + 无沙箱 + web 工具 = 启动安全警告（小模型更易被注入）
7. **准入门槛**：16K+tool 双检测；默认 contextWindow 65536 是给弱模型留的生存空间（系统提示 ~31K，8K 模型首轮溢出）
8. **failover 语义**：云地混搭默认链；显式选择严格失败不偷换

**本质**：不是"克服小模型能力不足"，而是**把小模型当不可靠外设工程化对待**——需要智能的活默认仍指向更强模型，架构是"模型能力异构"系统。GBNF 只保证格式合法不保证调用正确，全本地能用但甜点区是混搭。

### 7.1 推理位体系详解（任务分层的完整实现）

**十个推理位全景**：主对话（primary+fallbacks）/ 杂务（utilityModel：标题/进度播报/UI工具标题/Dashboard摘要/companion）/ 压缩（compaction.model）/ 压缩前抢救（memoryFlush.model）/ dreaming 巩固（dreaming.model）/ 深召回（active-memory 四级链：显式→会话→primary→modelFallback）/ 图像（imageModel）/ 语音（voiceModel）/ fast 档（/fast——**非换模型**，auto=前 fastAutoOnSeconds 秒走 provider 优先服务档，fast-mode.ts:74-98）/ 子代理（allowedModels 白名单）。

**utilityModel 三态**（utility-model.ts:21-29）：explicit（直接用）/ disabled（`""` 显式禁用，后台调用都不发）/ auto（派生）。auto 派生链=主 provider 的 manifest `defaultUtilityModel`→主模型；**派生模型继承主模型 auth profile**（:102-110——否则隔离凭证设置走默认凭证，认证隔离破功）。

**三种失败语义**（设计重点）：①**exact**——显式 override 不继承 fallback 链（memoryFlush/compaction 显式时），点名要隐私就诚实失败；②**借链**——compaction unset 失败可临时走会话 fallback 链（"temporary, not written back"）；③**跳过**——flush/召回失败不阻塞主回复（杂务永不杀死主线）。dreaming 的信任/白名单失败不重试保持可见；diary 模型不可用重试一次换会话默认。

**隐私分级配方**（本地主力+云巩固）：对话+flush 留本地（原始内容不出门），compaction/dreaming 上云（蒸馏任务要聪明）——但注意**洞**：压缩模型要看对话原文才能摘要，真隐私敏感连 compaction 也得本地。

**批判**：十个 key 散落三处心智负担重；provider 不声明 defaultUtilityModel 时静默用主模型烧旗舰，用户无感知。

## 8. 批判性评估

**值得偷的**：
1. **"协议陷阱"文档化**——`/v1` 破坏工具调用这种坑被写成 Warning 放最顶上；乱码=失败不入转录，都是踩坑结晶
2. **GBNF 清洗**——通用教训：本地推理的 schema→语法编译有规则上限，工具面要主动瘦身
3. **能力探测分级**：native capabilities → 名字启发式（r1/reason/think）→ 手动声明，三级降级
4. **显式选择严格、默认选择宽松**的 failover 语义——用户点名本地模型就尊重失败，不给惊喜
5. node-local inference 把"端侧算力"变成可审批的外设资源

**短板**：
1. **系统提示 31K 起步**对本地小模型极不友好——8 篇的分层/瘦身工程在云端是省钱，在本地是生存门槛；contextWindow 65536 默认值等于劝退 <16GB 机器
2. GPU 探测按平台静态选（darwin/arm64=Metal，其余 CPU），**CUDA/ROCm 不自动选**——N 卡用户被迫走 external 模式或 Ollama
3. 本地路径仍英文中心（thinking 控制文档全英文模型名举例）
4. 三条路径（ollama/llama-cpp/lmstudio）能力面不齐：embedding 仅 llama-cpp managed 模式可用、external 不装模型——选择矩阵对新手是迷宫

**一句话定位**：openclaw 端侧=**"便宜的中枢 + 诚实的本地"**——Pi 当 7×24 网关（$35-80），本地模型走 Ollama 原生协议或托管 llama-server，每个坑（/v1、GBNF 上限、thinking 循环、WSL2 内存）都有显式防御；但它默认仍是为"云端大模型 + 本地小嵌入"设计的系统，**全本地跑 agent 是支持但不是甜点区**。
