# 07 · 记忆数据管线：从一句对话到一条可召回的记忆

> 一句话：**openclaw memory 的本质是一条"采集→清洗→打标→切块→嵌入→索引→回流"的数据管线——它对数据质量的纪律，比对检索算法的投入更重。**
>
> 证据基准：钉版 `f612675284`。缩写 `SDK`=packages/memory-host-sdk/src/host · `MC`=extensions/memory-core · `LDB`=extensions/memory-lancedb。姊妹篇：[06-memory体系深读](06-memory体系深读.md)（架构/安全视角），本篇是**数据视角**。

## 0. 直觉：污水处理厂，不是图书馆

多数人以为记忆系统是图书馆（存进去、检索出来）。读完数据管线你会发现它更像**污水处理厂**：原水（对话转录）进来时混着大量污泥（元数据信封、心跳噪音、工具输出、API 密钥），进厂第一件事不是"建索引"而是**沉淀过滤**；每一滴出厂的水都带着**化验单**（溯源标签）；只有反复被用到的水才蒸馏进**清水库**（MEMORY.md）。索引和检索只是最后的水龙头。

## 2. 采集：七条入口（数据从哪来）

| # | 入口 | 触发时机 | 落点 | 证据 |

| 2 | **memory flush** | compaction 摘要**之前**的静默 turn，抢救未落盘事实 | 当日日记 | `src/auto-reply/reply/agent-runner-memory.ts`（1688 行）；工具面清空 `agent-tools.ts:871`，写路径强制 workspace 内 :144-166 |
| 3 | session-memory hook | `/new` `/reset` 日重置/闲置过期 | `memory/YYYY-MM-DD-HHMM.md`（默认取最近 15 条消息） | `src/hooks/bundled/session-memory/HOOK.md:19-28`；transcript 每消息一行 JSON 编码防伪造 `transcript.ts:18-25` |

| 5 | lancedb auto-capture | `agent_end` 钩子，每轮最多 3 条 | LanceDB `memories` 表 | `LDB/index.ts:559-636`；incognito 跳过 :561 |

## 3. 清洗：三层过滤（数据质量的第一道关）

**层 1 · 脱敏**：每条消息入摄取管线前过 `redactSensitiveText`——`OPENAI_API_KEY=sk-...` → `OPENAI_API_KEY=***`（边界由 `redaction-product-boundaries.test.ts:111-160` 固化成回归测试）。

**层 2 · 剥壳**（`SDK/session-files.ts:601-632`，逐行剥离五类污泥）：
- 入站元数据信封（`⟦openclaw:ctx⟧` 标记行、`[Channel sender +5m]` 前缀、信封 JSON）
- cron 前缀 `[cron:...]`、心跳 prompt/HEARTBEAT_OK、静默回复
- compaction checkpoint 与 .bak 归档（:124-143）
- 转录渲染侧：NO_REPLY、tool_calls/role 标签块、模型特殊 token、delivery-mirror（与前一 assistant 重复的投递镜像）、跨会话投递的 user 消息（`hooks/bundled/session-memory/transcript.ts:27-44,90-92`）
- **整段跳过两类轮次**：heartbeat 轮、memory_search 召回轮（session-files.ts:945-947）——防止"系统自言自语"和"检索结果被当成新对话"

**层 3 · 防毒性长行**：>800 字符按空格回绕（session-files.ts:57,510-555）；lancedb 侧还有 10K 字符预截断防 ReDoS（`LDB/memory-capture-sanitization.ts:466-567`）。

**为什么这么狠**：文档引用的实证——生产审计发现 always-on agent 的自动捕获记忆**绝大多数是脚手架复述、心跳噪音、召回回环**（memory-architecture.md:87-89）。垃圾进=垃圾出，且垃圾会被 dreaming 反复巩固成"事实"。

## 4. 打标：逐行溯源（数据自带化验单）

摄取时**每一行**导出内容都携带四元组：`lineMap(JSONL 行号) + timestamp + {originClass, sessionKind, observedAt}`（session-files.ts:958-966），hash 覆盖全部+reset 边界（:974-984）。

分类决策表（`classifySessionMessageOrigin` session-files.ts:642-670）：

| 消息 | 判定 |
|---|---|
| assistant + 轮污染标记 `turnTainted` | **untrusted**（该轮引用过外部内容） |
| assistant + owner 轮 | **agent**（从主人内容派生） |
| user + `provenance.kind=internal_system` | **system**（脚手架） |
| user + `__openclaw.senderIsOwner` | **owner** |
| 其他 user（群聊外人、工具投递） | **untrusted** |

三条纪律：①**保守默认**——判定不了的遗留行回填 `untrusted/unknown`，绝不默认 owner（`memory-schema-provenance.ts:38-41`）②**session-kind gate**——cron/heartbeat/subagent 会话整体不产生 durable 候选 ③**recall-loop 标记**——`isRecalledMemoryMessage`（session-files.ts:634-640）：凡是从 memory_search/memory_get 召回到上下文的内容，结构标记后**永不再当新记忆学**——"一条事实被召回一百次还是一条事实"。

## 5. 切块：chunkMarkdown（`SDK/internal.ts:511-604`）

- **逐行累计**而非字符硬切：`maxChars = tokens × CHARS_PER_TOKEN_ESTIMATE`（400 tok ≈ 估算字符上限），行边界天然对齐 → 每个 chunk 记 `startLine/endLine`，这就是 `Source: path#Lx-Ly` 引用的来源
- **overlap 携带**：切块后从尾部回扫累计 ≥overlapChars 的行作为下一块开头（:552-573）——语义连续性
- **curated 逐条切块**（`perEntry`）：MEMORY.md/USER.md 按**条目**边界切（splitCuratedMarkdownEntries），且同一条目炸成的多个碎片**继承完整注解 span**——注释明言"dropping scope on later fragments can leak them"（:575-585，防 trigger/project 注解在碎片上丢失导致越权注入）
- chunk hash = 内容哈希 → 增量同步的最小单位

## 6. 嵌入：11 家 provider + 归一化 + 缓存

- Provider 是**插件注册制**（`SDK/engine-embeddings.ts`）：openai（默认 text-embedding-3-small）/voyage/mistral/gemini/lmstudio/bedrock/deepinfra/llama-cpp 本地（默认 `embeddinggemma-300m-qat`）/openai-compatible…各家 extension 注册 adapter
- 输入上限：远程默认 8192 token、本地 2048（`SDK/embedding-model-limits.ts:6-19`）
- **入库前清洗 + L2 归一**（`SDK/embedding-vectors.ts:4-11`）——非法坐标替换、非空向量归一，保证 cosine/内积一致
- **维度自适应**：首个向量写入时按其长度建 `FLOAT[N]` vec0 虚拟表；维度变=drop 重建（`MC/memory/manager-sync-base.ts:588-599`）
- **embedding_cache 表**：PK=(provider, model, provider_key, hash)（`memory-schema-base.ts:16-25`）——同内容跨重建零成本
- 显式 provider 失败**不静默降级**到 FTS：报 unavailable（memory-search.md:132-138）——静默降级会让用户误以为语义搜索在生效

## 7. 索引：一张 SQLite 五张皮

每 agent 一个 `openclaw-agent.sqlite`（WAL：NFS/SMB 降级 rollback、SSHFS 拒开、30min PASSIVE checkpoint——`src/infra/sqlite-wal.ts:344-427`）：

| 表/索引 | 存什么 | 数据要点 |
|---|---|---|
| `memory_index_sources` | 文件级：path/source/hash/mtime/size | INTEGER rowid 身份（FTS VACUUM 稳定）；(path,source) 唯一 |
| `memory_index_chunks` | 块级：行号范围+text+embedding+hash | 增量最小单位 |
| `memory_index_chunks_fts` | FTS5 全文（text 索引+元数据 UNINDEXED） | unicode61 或 **trigram case_sensitive 0**（中日韩）；bm25 rank |
| `memory_index_chunks_vec` | vec0 虚拟表 KNN | 原生 `MATCH + k=?`，余弦在 SELECT 补算（vec0 默认 L2，manager-search.ts:477-495） |
| `memory_index_chunk_provenance` | 溯源四列（CHECK 约束） | §4 的化验单落库 |
| `memory_index_chunk_recall_metadata` | importance(1-10)/triggers/project_key | 尾注解析产物（`curated-annotations.ts:6` 正则：`<!--trigger|importance|project:...-->`，行级不跨换行） |
| `memory_index_state` | revision 单行 | **6 个触发器**自动递增（memory-schema.ts:619-649）——增量同步的版本号 |

## 8. 增量同步：watch + 防抖 + 全量重建边界

- 文件 watching 触发 **1.5s 防抖**重索引（memory-builtin.md:105-106）——编辑器保存风暴不打爆索引器
- 每文件按 sources 表 hash/mtime/size 对比，变才重切；chunk 级 hash 复用 embedding 缓存
- **配置变更触发全量重建**：provider/model/chunking/sources/scope 任一变化（:107-108）——维度变了旧向量就废了，重建是唯一正确解
- 索引身份不匹配时**暂停结果而非返回脏数据**（memory-search-tool-query.ts:123-139）

## 9. 使用即学习：召回信号回流（最容易被忽略的一环）

`memory_search` 每次被调用，若 dreaming 开启，后台 `queueShortTermRecallTracking`（`MC/src/tools.ts:432-448`）把"这条 chunk 在什么查询下被召回、打分多少"喂进短期信号库 `memory/.dreams/`。这就是六信号里 **relevance/frequency/diversity** 的数据来源——**记忆不因"写得自信"而晋升，因"持续被用"而晋升**。短期库上限：512 条、单条 800 字符、32 个查询哈希、16 个召回日（short-term-promotion-utils.ts:19-22）——信号本身也有防膨胀预算。

## 10. 生命周期：修剪、supersede 与"遗忘"

- **supersedes_key**：新观察替代旧观察的谱系键——consolidation 用它"退休"过期条目而不是并排堆积
- **预算压缩**：MEMORY.md 超 10,000 字符（`memory-budget.ts:33`）时 `compactMemoryForBudget` **只丢最老的机器生成晋升块，用户手写内容无条件保留**（:181-197）——文件是人的，机器只租空间
- **遗忘=降权而非删除**：时间衰减只影响排序分数（temporal-decay.ts:37-43，exp(-λt)，30 天半衰期；MEMORY/USER evergreen 豁免 :72-81）——磁盘上什么都不删，"忘"只是"想不起来"
- **回滚链**：每次接受的 MEMORY.md 重写，pre-image 存 SQLite 插件态；回填/晋升全可 `--rollback`

## 11. 批判：数据视角的短板

1. **清洗规则英文中心**：lancedb 捕获触发词表覆盖英/捷/中/日/韩（memory-policy.ts:109-122）算用心了，但剥壳正则（信封/时间戳/动词形态）全是英文形状；中日韩长句在 400-token 估算切块下边界质量未验证
2. **token 估算 vs 真分词**：`CHARS_PER_TOKEN_ESTIMATE` 是常数估算，中文 1 字≈1 token 而英文 4 字符≈1 token——同一 chunk 预算下中文实际 token 数可能超出数倍
3. **双库一致性**：lancedb（自己的 memories 表）与 memory-core（SQLite）并存时，同一事实可能两处两格式——靠"slot 归一 + sidecar 透传"约定，无跨库去重
4. **导入即隔离的代价**：`memory/imports/` 永不合并进 MEMORY.md——安全但用户"导入了为什么没记住"的疑惑需要 UI 解释成本
5. **信号库的幸存者偏差**：六信号的 relevance/frequency 依赖"被 memory_search 召回"——从未被搜到的候选事实上被系统性埋没（diversity 门槛加剧此效应）
