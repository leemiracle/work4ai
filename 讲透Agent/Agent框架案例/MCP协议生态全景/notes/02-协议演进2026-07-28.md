# MCP 协议规范演进——从有状态握手到彻底无状态

> 一句话：**2026-07-28 版把 MCP 的"有状态基因"全部切掉——没有 initialize 握手、没有 session、没有 ping、Sampling/Roots/Logging 进弃用清单。协议哲学从"双向对话"转向"client 问、server 答、问完即忘"。**

> ⚠️ 本篇是 [`工程化手册库/MCP工程手册/`](../../../../工程化手册库/MCP工程手册/README.md)（2026-08 版，按 2025 规范写的 initialize 握手/Sampling/Roots 教学）的**必要更新层**：手册的 Tools/Resources/Prompts 三能力与 FastMCP 实操依然有效，但握手流程、反向能力、传输细节以本篇 2026-07-28 规范为准。

## 1. 版本时间线（直觉层）

```
2024-11-05  首发版            Anthropic 开源发布；stdio + HTTP+SSE 双传输；initialize 握手
2025-03-26  Streamable HTTP   HTTP+SSE 转为不推荐；OAuth 2.1 授权框架
2025-06-18  elicitation 等    结构化工具输出、elicitation、task 概念
2025-11-25  上一次修订        URL-mode elicitation、includeContext 软弃用
2026-07-28  ★无状态化重构     当前 latest；SDK v2 同步发布（Python/TS 均为重写）
```

**直觉**：前三个版本在做加法（新能力、新传输、新授权），2026-07-28 突然做减法——一次砍掉三件"看起来是核心"的东西：sessions、initialize 握手、server→client 反向请求。这不是修补，是架构哲学转向。

## 2. Major Changes 九条（机制层）

> 全部来自官方 Key Changes 页，括号内为 SEP 提案号。

### 2.1 砍掉协议级 session（SEP-2567）

- 移除 `Mcp-Session-Id` header（Streamable HTTP）
- `tools/list`、`resources/list`、`prompts/list` 不再按连接变化
- server 需要跨调用状态？**自己铸造显式 handle，当普通 tool 参数传**——状态从"协议隐式"变"参数显式"

### 2.2 彻底无状态：删掉 initialize 握手（SEP-2575）

- 移除 `initialize` / `notifications/initialized` 两条消息
- 每个请求在 `_meta` 里自带版本与能力：
  - `io.modelcontextprotocol/protocolVersion`
  - `io.modelcontextprotocol/clientCapabilities`
  - （SHOULD）`io.modelcontextprotocol/clientInfo`；server 在结果 `_meta` 里回 `serverInfo`
- 版本不匹配返回 `UnsupportedProtocolVersionError`

### 2.3 新增 `server/discover` RPC（SEP-2575）

server **必须**实现：广播自己支持的协议版本、能力、身份。client 可在任何请求前调用它做版本选择，或在 STDIO 上当向后兼容探针。**一个 RPC 替代了原握手的一半职能，另一半（能力协商）摊薄到每个请求。**

### 2.4 `subscriptions/listen` 统一变更通知（SEP-2575）

- 替代 HTTP GET endpoint + `resources/subscribe`/`unsubscribe`
- 单一长活 POST 响应流，client 按类型选择性订阅：`toolsListChanged` / `promptsListChanged` / `resourcesListChanged` / `resourceSubscriptions`
- server 确认后给通知打 `io.modelcontextprotocol/subscriptionId` 标签
- 请求级通知（progress/message）仍在原请求的响应流上，不混流

### 2.5 删掉 `ping`、`logging/setLevel`、`roots/list_changed`（SEP-2575）

日志级别改为**按请求**经 `_meta` 的 `io.modelcontextprotocol/logLevel` 设置；server 不得给没带该字段的请求发 `notifications/message`。

### 2.6 tasks 移出核心协议 → 官方扩展（SEP-2663）

- 长任务从核心规范移入扩展 `io.modelcontextprotocol/tasks`
- 阻塞式 `tasks/result` 改为 `tasks/get` 轮询 + `tasks/update`（client→server 补充输入）
- 删除 `tasks/list`；server 可不经 per-request opt-in 主动返回 task handle

### 2.7 MRTR：多轮往返请求模式（SEP-2322）★设计最精妙

替代一切 server 主动请求（`roots/list`、`sampling/createMessage`、`elicitation/create`）：

```
client ──请求──► server
server ──InputRequiredResult（resultType:"input_required", inputRequests:[...]）──► client
client （收集输入：问用户/调本地 LLM）
client ──重试原请求 + inputResponses──► server
server ──complete 结果──► client
```

server 不再"反过来调用 client"，而是**把原请求打回"缺输入"状态，等 client 带着输入重试**。控制流始终单向，重试语义天然幂等。

### 2.8 所有结果带 `resultType`（SEP-2322）

`"complete"`（完成）或 `"input_required"`（要输入）。旧版 server 漏带此字段时 client 必须按 `"complete"` 处理——向后兼容的兜底写进规范。

### 2.9 删掉 SSE 流可恢复性（SEP-2575）

移除 `Last-Event-ID` header 与 SSE event ID（消息重投递）。流断了就丢了在途请求，client **必须换新请求 ID 重发**。可恢复性 = 有状态的最后一根稻草，也砍了。

## 3. Minor / Deprecated / 治理（速览）

**Minor（12 条择要）**：

| 变更 | 一句话 |
|---|---|
| `extensions` 能力字段 | Client/ServerCapabilities 可声明官方扩展（核心收敛，生态外溢） |
| OpenTelemetry 传播 | `_meta` 约定 `traceparent`/`tracestate`/`baggage` |
| `tools/list` 确定性顺序 | **为 LLM prompt cache 命中率设计**——协议开始为 token 经济学优化 |
| `CacheableResult` | list/read 结果带 `ttlMs` + `cacheScope`（public/private），HTTP 缓存语义回流 |
| 标准请求头 | Streamable HTTP POST 必带 `Mcp-Method`/`Mcp-Name`；tool 参数可注 `x-mcp-header` |
| 错误码分区 | -32020~-32099 保留给规范自身；HeaderMismatch → -32020 |
| JSON Schema 2020-12 | inputSchema/outputSchema 放宽到全关键词 |

**Deprecated（4 条，新实现不应再采用）**：

1. **Roots、Sampling、Logging 三特性整体弃用**（SEP-2577）。迁移：目录/文件走 tool 参数或 resource URI；要 LLM 就直连 provider API；日志走 stderr / OpenTelemetry
2. HTTP+SSE transport 正式归类 Deprecated（自 2025-03-26 起不推荐）→ 全员 Streamable HTTP
3. `includeContext` 的 `"thisServer"`/`"allServers"` 弃用
4. OAuth 2.0 DCR（RFC7591）弃用 → Client ID Metadata Documents

**治理**：特性生命周期政策（Active/Deprecated/Removed，弃用窗口最少 12 个月）+ 弃用特性登记表；SEP 流程正式化（`seps/` 目录、PR 编号）。

## 4. 为什么这么改（批判层）

1. **无状态是分发的万能钥匙**：没有 session，server 可扔进 CDN/serverless/任意 LB；`CacheableResult` + 确定性 `tools/list` 顺序 = 每一层都能缓存。代价：server 若真有状态（购物车、会话记忆），得自己造 handle 传参——协议把复杂度"下放"给实现者。
2. **Sampling/Roots 被弃 = 承认 agent loop 在 client**。2024 年设计的"server 反向借 LLM"（sampling）看似优雅，实则造成权限/计费/安全的三重纠缠（server 拿谁的 key？谁付 token 钱？）。2026 年的答案：**server 就该是哑工具，智能留在 harness**——这与本项目 dsh 案例的"模型看到的⟺审计到的"信任平面设计同源（[`deepseek-harness插件化框架/notes/03-trust`](../../deepseek-harness插件化框架/notes/03-trust/01-信任平面与反欺骗.md)）。
3. **MRTR 是"重试语义"对"回调语义"的胜利**：server→client 回调要求双方都常驻、都能寻址——分布式系统经典噩梦。InputRequired + 重试把双向依赖折叠回单向请求。
4. **风险**：这是一次**破坏性重构**而非渐进演进。旧 server/client 不经适配无法对话新版（SDK v1.x 只保 bug fix 6 个月）。64k 生态仓的迁移成本真实存在——这也是 SDK v2 与 Registry 同期发布的原因（见 [03-官方仓与SDK格局](03-官方仓与SDK格局.md)）。
