# 从 Coding Agent 到安卓个人助手：一套完整 Agent 架构的场景迁移设计

> **本文是什么**：A05-技术博客-TencentDB-Agent-Memory.md 的场景迁移**扩展版**——不止迁移记忆系统，而是以它为骨架之一，设计**安卓个人助手 Agent 的完整架构**：循环层 / 工具层 / 记忆层 / 技能层 / 上下文层 / 模型层 / 治理层，七层一起过。
> **信源与诚实边界**：TencentDB 机制描述继承 A05 深读（官方 docs v2.0.0）；**完整架构设计是本笔记的工程练习**，融合本仓库讲透系列的方法论（讲透Loop 循环设计学 / 讲透KV Cache 09 谱系统一 / Open-AutoGLM 手机 Agent 实战）——非任何官方文档。
> **姊妹篇**：[A05 原版](A05-技术博客-TencentDB-Agent-Memory.md)（coding 场景）｜[Open-AutoGLM 手机 Agent](../../实战案例-Open-AutoGLM手机Agent/)（真机先例）

## TL;DR

- **场景换了，四个字没换**：Coding Agent 与个人助手共享同一个四层堆栈（Prompt→Context→Harness→Loop）和同一批循环定律——**换宿主不换数学，换的是每层的填充物**。
- **七层迁移总表**：记忆层最成熟可直接平移（金字塔+四动作判重）；工具层需要最大再创作（**App Graph**：操作图谱+影响分析）；上下文层直接吃讲透KV Cache 09 的谱系统一（**上下文物化谱系**决定端云分工）；治理层从团队 ACL 变隐私分级+电量经济学。
- **个人助手 = 沿三个轴全面加强的 Agent**：记忆轴（画像即产品）/ 循环轴（生活是无限 horizon 的 goal loop）/ 工具轴（整个设备是工具箱）——代价是隐私、电量、离线三条硬约束全面收紧。

## 一、先对齐：Agent 的骨架是宿主无关的

本仓库讲透Loop 12 章的结论直接引用：任何 Agent = 四层堆栈上的一台机器——

```
L3 Loop        谁触发、怎么验证、何时停、状态在哪     ← 助手=常驻 goal loop
L2 Harness     单次 run 的环境：工具/钩子/技能         ← 助手=设备能力壳
L1 Context     每轮窗口放什么、怎么压、什么留盘        ← 助手=画像+场景注入
L0 Prompt      单次调用怎么问                          ← 助手=指令+例程
```

Coding Agent 和个人助手的差异**全部发生在每层的填充物**，骨架一条不变。下面逐层填安卓的肉。

## 二、七层完整设计

### 2.1 循环层：从"任务级 goal loop"到"生活级常驻 loop"

Coding Agent 的循环是任务形状的（04 章：heartbeat/cron/hook/goal 四形状）。个人助手的循环形状谱系自然对上：

| 形状 | 个人助手实例 | 触发/停止 |
|------|------------|----------|
| **Hook** | 用户说话/推送到达/日历事件 | 事件响应完即停（最常见） |
| **Goal** | "帮我规划下月日本行并订好票" | 机器可查条件（订单确认+日历落位）或预算烧穿 |
| **Cron** | 每晚汇总明日日程/每周账单小结 | 批完成即止 |
| **Heartbeat** | 常驻监听（授权范围内）位置/健康信号 | 被杀/暂停——**默认不应有**（电量+隐私双否决） |

讲透Loop 的三守卫原样适用且更关键：goal loop 的 hard cap 在助手场景=**每任务 token/操作数上限**（自动订票跑飞是真实事故面）；熔断=连续无进展升级用户（"订不到你要的舱位，需要你决定"）；独立验证=**执行结果与用户意图分离校验**（订单号回查、日历 diff 展示）——maker≠checker 在花钱的场景是安全设计不是质量设计。状态文件（06 章）平移为**任务断点卡**：多日任务（旅行规划）跨会话续传，"读帧写验/事实非 vibes/resume 一行"三规则原样继承。

### 2.2 工具层：CodeGraph 的重生——App Graph 与设备能力壳

个人助手的工具箱 = 系统能力 + 应用生态 + 云服务三层，全部走**按需调用的工具接口**（原架构 `/v3/tools` 自发现 + MCP 的端侧版）：

```text
设备能力（系统 API，稳定）：  日历/通知/位置/健康/短信/支付/媒体控制
应用生态（App Graph）：       intent/deeplink 可达性、账号打通、数据依赖
云服务（MCP/HTTP）：          搜索/订票/购物/邮件——低频高价值
```

**App Graph 是场景迁移中最大的再创作**（对位 CodeGraph 的 caller/callee/impact）：

- 节点：App、系统能力、账号体系、订阅服务、Routine 步骤；
- 边：intent 可达、账号打通、数据依赖（日历读自邮箱）、权限耦合；
- **impact analysis 个人版**："关掉这个 App 的通知，哪些自动流程会断？""换默认日历，哪些 Routine 步骤失效？"——**自动化深度决定图谱价值**（用户托付越多，配置改动的爆炸半径越大，越需要先查图再动手）。

Open-AutoGLM 的实战教训接线：手机 GUI 操作（点击/滑动/填表）是工具层的兜底执行器——**API 优先、GUI 兜底**的双层执行，GUI 层的成功率与可复核性（截图回放）直接继承该案例。

### 2.3 记忆层：Semantic Pyramid 平移（最成熟的一层）

A05 核心机制几乎原样继承（详细翻译见前版压缩）：

| 机制 | 个人版 | 关键变形 |
|------|--------|---------|
| L0-L3 金字塔 | 对话(含 ASR)/个人事实/生活场景块/**画像=产品核心** | `maxScenes` 放宽；画像敏感度升顶 |
| 四动作判重 store/update/merge/skip | 个人事实时效性强→update/merge 高频；merge 轨迹=搬家史/口味演变史 | 端侧小模型判重质量降级→宁可 store 膨胀等云端重整（复用原文降级路径） |
| Sanitize 防反馈环 | +**语音版**：TTS/ASR 源标记，防"助手听见自己说的话" | 语音场景的环更毒 |
| 五级可见性 | 收敛三级：私密/家庭共享/云端 + **新增"对助手自身不可见"级** | 用户负指令："这件事别记" |

### 2.4 技能层：Skill → Routine（程序性记忆个人版）

带版本/触发边界/执行步骤/验证规则的资产化设计原样保留，语义换成个人惯例："给妈订生日蛋糕"Routine v2（妈的口味变了，v1 可回滚）。抽取管线的头部保意图/尾部保结果截断、重复成功 ≥2 次才提议固化、用户一键确认（个人场景审核者=用户本人，比团队审核轻一档）——全部平移。**Routine 与 App Graph 联动**是新增设计：每个 Routine 步骤标注其依赖的工具/账号节点，图谱变化时自动做影响扫描并提醒（"你换的输入法影响了 2 个 Routine"）。

### 2.5 上下文层：谱系统一的直接应用（讲透KV Cache 09 的落地）

个人助手的"上下文物化"正好用上 09 章的谱系——**上下文放在哪，按信息变化速率分层**：

```
精确外存端（KV cache）                    压缩状态端（TTT/fast weights）
├ 画像 L3 + Routine 清单：会话稳定          ├ 长期陪伴的个性化：
├ 场景块 L2：按场景切换                     │  端侧小模型用 TTT 式
├ L1 相关记忆：prepend user prompt          │  fast weights 持续吸收
└ L0/原始执行日志：下沉为按需工具            │  交互风格/纠错偏好
                                          └ 混合是常态：agent = 沿谱系
注入经济学（原架构三分法）：                     按变化速率分层放置
稳定进 system prompt 吃 KV-cache             "上下文"——09 章结论的
易变 prepend user prompt                     产品级实现
搜索限流 ≤3 次/轮（省 token + 省电双重动机）
```

TTT 端的遗忘地板定律（γ↑→记忆稳态↓，E4 实验已确认）在此变成产品参数：**个性化权重的 weight decay 决定"助手对用户印象的更新速度"**——decay 太大=每次都像初见，太小=三年前的习惯阴魂不散。这是把讲透Loop E5 的 $e^*=f/(r+f)$ 从循环经济学搬到个性化调参。

### 2.6 模型层：端云分工 + 离线降级

| 任务 | 端侧小模型 | 云侧大模型（私有云/e2e） |
|------|-----------|------------------------|
| 每轮应答+工具编排 | ✓（低延迟/离线/隐私） | 复杂规划兜底 |
| L1 抽取+判重 | ✓（轻量档：只 store） | 深夜充电时 merge 整理 |
| L2/L3 提炼 | WorkManager 充电约束任务 | 卸载主战场 |
| 判重四动作 | 降级版（store-only） | 全功能 |

**离线模式=降级管线的预先排练**（原架构"零配置全 store"的活口恰好用上）：地铁里的对话全量入库，WiFi+充电后云端深炼——新鲜度延迟换可用性，用户可感知可接受。全链路 LLM 依赖的批判在端侧加重（小模型 JSON 输出更不可控），端侧策略是**结构越简单越好**（store-only 就是最简单的结构）。

### 2.7 治理层：隐私 × 电量 × 审计

- **隐私五件套**：persona.md 端侧加密+云同步 e2e；凭证/API key 永不进 prompt（原文 serviceToken 铁律升格）；负指令级（"别记"）；家庭共享的 ACL（原文六段式权限函数裁剪版）；**一键导出/焚毁**（GDPR 式底线，也是用户信任的 UX 支点）。
- **电量经济学**：后台提炼全部走 WorkManager 约束（充电+不计费网络+空闲）——原架构的异步旁路原则对齐设备节奏为"两速档"（会话内轻抽取保新鲜，充电时深炼保质量）。
- **审计**：原文 MemoryGenerationLog（"谁在何时用什么 prompt 生成了我"）在个人场景是**信任 UI 的数据底座**——助手每条记忆可点开看来源对话，"你为什么觉得我怕狗？"必须能回答。append-only 审计表原样保留。

## 三、批判：这套设计最难的三件事（不是组件，是产品）

1. **信任的冷启动悖论**：画像越准越好用，但用户在信任建立前不愿给数据——L3 画像的增量模式（first→incremental）要配合**透明度递进**（先只记显式 instruction，观察可靠后再请求 persona 级深度）。原架构"每 50 条新记忆触发重算"的节奏给了工程锚点，但信任节奏不是记忆节奏，产品要自己调。
2. **自动化的责任边界**：goal loop 帮用户花钱（订票/购物）时，验证器再强也只是降低错误率——**不可逆操作的升级点设计**（超过阈值金额必须人确认）是比技术更重的产品决策，讲透Loop 的 blocked 终态在此是商业必需。
3. **换机/多设备的记忆连续性**：用户真正要的是"换手机助手还是我"——e2e 云同步+导出/导入格式标准化，是留存之战也可能是差异化壁垒（谁先做出"记忆可携带"，谁锁定用户）。

## 四、带走的设计模式（完整架构版，接前版 9-14 条）

15. **骨架宿主无关，填充物全换**：四层堆栈评估法——设计任何新 Agent，先画四层再填肉，缺失层显式标"无"而非默认不存在。
16. **记忆分层 × 上下文谱系 是同一张表的两列**：L0-L3 的稳定性划分与 KV/TTT 谱系按变化速率对齐——**记忆架构师和上下文工程师应是同一个人**。
17. **自动化深度 ↔ 影响分析需求**：工具图谱（代码/App/IoT 皆然）的价值与用户托付的自动化半径成正比——没有 App Graph 的 Routine 自动化是裸奔。
18. **个性化参数即循环定律**：weight decay=印象更新速度——把数学定律翻译成产品语义，是理论变现的最短路径。

## 五、结语

A05 原文结语说"没有 Memory，Loop 只是更快地重复"。完整架构版的结语要倒过来说：**个人助手是一个 Loop，Memory 是它最贵的零件，但不是它的全部**——循环守卫让它可信，App Graph 让它能干，谱系化的上下文让它认得用户，隐私分级让它被允许存在。七层缺一，产品塌一角。
