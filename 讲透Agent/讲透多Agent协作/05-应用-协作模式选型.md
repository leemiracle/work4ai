# 🚀 第 5 幕 · 应用：协作模式选型

## 五种拓扑选型表

| 拓扑 | 何时用 | 何时不用 | 框架 |
|---|---|---|---|
| **Orchestrator-Worker** | 可分解的并行子任务（多文件实现、多源研究） | 强耦合任务 | OpenAI Swarm, Cursor bg agents, Anthropic multi-agent |
| **Hierarchy** | 有明确上下级（产品→工程→测试） | 平权协作 | MetaGPT, ChatDev |
| **Debate** | 需多视角验证（红队、审查、医疗诊断） | 时间敏感 | multi-agent debate |
| **Peer-to-Peer** | 探索性/创意（brainstorm、设计） | 需确定性 | CrewAI |
| **Market/Auction** | 资源分配/调度 | 共识类 | Contract Net |

## 框架对比

| 框架 | 哲学 | 抽象级别 | 适合 |
|---|---|---|---|
| **LangGraph 0.2+** | 显式状态图，可断点/重放/人审 | 重（生产级）| 需可控可审计 |
| **AutoGen v0.4** | actor 模型 + 异步消息 | 中（高并发）| 事件驱动 |
| **CrewAI** | 角色 + 任务 + 流程 | 轻（快速原型）| 快速搭建 |
| **MetaGPT/ChatDev** | 模拟组织 SOP | 中（专用）| 软件开发流水线 |
| **OpenAI Swarm** | 极简 handoff | 极轻 | 不想用重框架 |

## 决策清单

上多 agent 前，问自己：
- [ ] 能拆出 ≥3 个**真正独立**子任务？否→单 agent
- [ ] 并行收益 > 通信开销？算一下
- [ ] 需要对抗验证吗？是→debate
- [ ] 有明确上下级吗？是→hierarchy
- [ ] 能容忍非确定性吗？否→单 agent + 规则

## 生产化清单

- [ ] DAG 化任务（无循环依赖）
- [ ] 每个 agent 权限最小化
- [ ] 全链路 trace
- [ ] 超时强退
- [ ] 最后一个「审查 agent」专门挑错（防责任扩散）
- [ ] 确定调度（固定种子）便于复现
- [ ] 关键信息外部验证（防幻觉级联）

## Anthropic 多 agent 研究系统（2025 工业级范本）

一个 lead agent：
1. 把研究问题拆成子问题
2. 派多个 sub-agent **并行**搜资料
3. 收集所有 sub-agent 的结果
4. 综合成报告

**关键**：sub-agent 之间**不直接通信**，只通过 lead 中转——这避免了 O(N²) 通信爆炸。**这是 orchestrator-worker 的最佳实践**。

## 五条经验法则

1. **拆不出 ≥3 独立子任务，就别上多 agent**。
2. **忍住不派多 agent，是高级智慧**（很多场景单 agent + 好 context 更熵减）。
3. **sub-agent 不直接通信**（通过 orchestrator 中转）。
4. **最后设审查 agent**（防责任扩散）。
5. **固定种子 + trace**（可复现可调试）。

## 🎬 五幕收束

> 多 agent 不是银弹，是「**用协调成本换能力上限**」的交易。判据：(并行收益 + 对抗增益) > (通信开销 + 级联风险)。Anthropic 多 agent 研究系统的最佳实践：**sub-agent 不直接通信，只通过 lead 中转**——这是控制 O(N²) 通信爆炸的关键。
>
> 用熵论收尾：**单 agent 是「核心收敛」，多 agent 是「边缘发散」**。世界级系统 = 两者兼用，按场景切换。
