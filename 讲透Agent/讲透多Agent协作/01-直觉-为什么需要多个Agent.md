# 🤝 第 1 幕 · 直觉：为什么需要多个 Agent

## 从一个尴尬的事实开始

你给一个 LLM agent 一个复杂任务：「研究 X 领域，对比 5 个方案，写一份技术报告」。你看着它跑——它读了 20 篇资料，开始写，写到一半**忘了开头读的关键信息**（context 爆了）；或者它对比到第 4 个方案时，**已经偏离了原始问题**（注意力稀释）。

这不是模型笨，是**单 Agent 的三道物理墙**：

```
墙 1 · context window 上限      （再大也是有限的）
墙 2 · 单次注意力的稀释          （任务越长，质量越降）
墙 3 · 单点失误的级联            （一步错，步步错，没有制衡）
```

**多 Agent 的全部动机，就是绕过这三道墙。**

---

## 单 Agent 的三大极限（为什么不够）

### 极限 1 · Context 爆炸
任何单 Agent，无论 context 多大，**总存在一个任务复杂度，会把它填满**。填满后要么截断（丢信息），要么检索（需要记忆层，见 `讲透记忆/`）。复杂任务的真实信息量往往是窗口的 10-100 倍。

### 极限 2 · 能力边界
一个 LLM 在所有任务上**不是同等强的**。它在写代码时强，在画图时弱；在逻辑推理时强，在创意发散时弱。**单 Agent = 用一个通才干所有事，每件事都不是最优**。

### 极限 3 · 单点失误
单 Agent 是**单线程的思考链**。一步幻觉，后续全错。**没有第二个视角来发现这个错误**。这就是为什么单 agent 写复杂代码经常「自信地一路跑偏」。

---

## 多 Agent 的四种收益（为什么要用）

把任务拆给多个 Agent，能换四种不同的东西：

| 收益 | 机制 | 生物学/社会学类比 |
|---|---|---|
| **分工** | 每个 Agent 专精一个子任务 | 蜂群的工蜂/雄蜂/蜂后分工 |
| **并行** | 独立子任务同时跑 | 蚁群多路觅食 |
| **对抗** | 一个 Agent 提案，另一个挑刺 | 法庭的控辩对抗 / 红队 |
| **制衡** | 多个 Agent 投票/复核 | 三权分立 / 同行评审 |

**注意**：这四种收益是**不同的**。很多人把「多 Agent」当万能药，其实它只在上述四种场景里值。其他场景，单 Agent 更熵减（见本幕末）。

## Brooks 定律的 AI 版：协调的诅咒

Fred Brooks 1975 年在《人月神话》里提出经典定律：

> **给一个延期的软件项目加人，只会让它更延期。** 因为新人之间的沟通成本是 O(N²)。

多 Agent 系统有**完全一样的诅咒**：

```
N 个 Agent 之间的潜在通信链路数 = N(N-1)/2 = O(N²)
```

每条链路都是**幻觉/误解/死锁/串谋**的潜在入口。**3 个笨 Agent 的协作，常常不如 1 个聪明的 Agent + 好的 prompt。**

这就是多 Agent 工程的核心判据：

> **(并行收益 + 对抗可靠性增益) > (通信开销 + 幻觉级联风险) 时才用多 Agent。**
>
> 否则，把多 Agent 退化为单 Agent + 更好的 context，往往是更熵减的选择。

## 三种典型协作模式（直觉版）

### 模式 A · Orchestrator-Worker（最常见）
一个 lead agent 把任务拆成子任务，派给多个 worker agent 并行做，最后汇总。

```
        [Orchestrator]
       /    |    |    \
   [W1]  [W2]  [W3]  [W4]   ← 并行干活
       \    |    |    /
        [汇总 + 整合]
```
**代表**：Anthropic 2025 的多 agent 研究系统——一个 lead 派多个 sub-agent 并行搜资料再综合（**Claude 在评审 Claude 写的报告**）。Cursor 的 background agents。

### 模式 B · Debate（对抗）
多个 Agent 就同一问题各持立场辩论，最后裁决。

```
   [Agent A: 正方] ←→ [Agent B: 反方]
            ↓
       [Judge / 投票]
```
**代表**：multi-agent debate 论文（2023-2025）。用于提升推理可靠性——但也是群体幻觉的温床。

### 模式 C · Hierarchy（科层）
模拟组织结构：产品 Agent → 工程 Agent → 测试 Agent，逐层下达。

```
   [Product Agent]
        ↓
   [Engineering Agent] ←→ [Design Agent]
        ↓
   [Test Agent]
```
**代表**：MetaGPT（2023，模拟软件公司）、ChatDev。把 SDLC 拆成角色。

## 什么时候**不要**用多 Agent（反直觉）

这是工程师最该读的部分：

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 任务是单线程、强耦合 | 单 Agent | 拆开反而要频繁同步，开销 > 收益 |
| 任务小（< 几分钟） | 单 Agent | 派发/汇总的固定开销不划算 |
| 需要 100% 确定性 | 单 Agent + 规则 | 多 Agent 的协调引入更多非确定性 |
| 子任务高度相互依赖 | 单 Agent | 并行不了，串行反而要传上下文 |

**经验法则**：**先问「这任务能拆成多少个真正独立的子任务？」** 拆不出 ≥3 个独立子任务，就别上多 Agent。

## 2024-2026 框架光谱

| 框架 | 哲学 | 适合 |
|---|---|---|
| **LangGraph 0.2+** | 把 agent 流程建模成**显式状态图**，可断点/重放/人审 | 需要可控可审计的生产系统 |
| **AutoGen v0.4** | **actor 模型 + 异步消息** | 高并发、事件驱动 |
| **CrewAI** | **角色 + 任务 + 流程** 的简洁抽象 | 快速搭原型 |
| **MetaGPT / ChatDev** | **模拟组织 SOP** | 软件开发流水线 |
| **OpenAI Swarm** | **极简 handoff**（一个 agent 把控制权交给另一个） | 轻量、不想用重框架 |
| **Anthropic multi-agent** | **lead + sub-agents 并行检索** | 研究类、信息聚合 |

**注意 OpenAI Swarm 的反讽**：它叫 swarm（群体），其实是**最轻量的显式编排**，不是真正的涌现自组织。真正的 swarm 见 `讲透群体智能/`。

## 🎬 本幕收束

> **多 Agent 不是银弹，它是一种用「协调成本」换「能力上限」的交易。** 判断值不值的公式很简单：并行收益 + 对抗增益 > 通信开销 + 级联风险 时才用。否则，把多 Agent 退化为单 Agent + 更好的 context，往往是更熵减的选择。
>
> 真正难的不是「派多个 agent」，而是「**什么时候忍住不派**」。
