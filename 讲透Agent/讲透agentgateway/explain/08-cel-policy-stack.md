## 一、角色定位（16 层架构 L10；策略/路由条件的表达式底座）

在 understand 图谱的 16 层架构中，CEL 栈属 **L10「CEL 表达式与策略求值栈」**（layers 数组第 10 项），层摘要原文即："贯穿全系统的表达式底座：cel-fork（上游 cel-rust 分叉，解析/求值/宏）、celx 扩展函数库（math/strings/cidr）、policy-core 策略表达式与属性求值……"。它是全系统唯一的说服力来源：**每一条"这个请求该不该限流/放行/改写/计费"的判断，最终都是一条 CEL 字符串**。

与相邻层的分界非常清晰：L01 的 CRD 只是把 CEL 当 `string` 字段类型存起来（`controller/api/v1alpha1/agentgateway/rbac.go:30` 定义 `type CELExpression string`，kubebuilder 校验仅 MinLength=1/MaxLength=16384，rbac.go:27-28）；L07 HTTP 过滤器矩阵、L10 LLM 翻译引擎、L08 MCP 网关则全是本层的**消费者**。整个栈是四层漏斗：

1. **语言本体** `cel-fork/cel`——ANTLR 解析器 + AST + 求值器 + 优化器（fork 自 cel-rust v0.13.0，Cargo.toml:5,7）；
2. **标准库** `celx`——对标 cel-go ext 与 Kubernetes CEL 库的扩展函数族；
3. **策略框架** `policy-core`——把"字符串"变成"带属性契约的编译产物"（`Expression`）；
4. **数据面绑定** `agentgateway/src/cel`——把表达式接到活的 `http::Request`/`Response` 上，并用属性驱动快照决策。

## 二、内部结构（四层各自解剖）

### 2.1 cel-fork/cel：解析 → AST → 优化管线

解析层是纯 ANTLR 生成物：语法文件 `crates/cel-fork/cel/src/parser/gen/CEL.g4` 头部保留 Google 2018 版权声明（CEL.g4:1），`gen/mod.rs` 注释钉死了再生方式——"generated by antlr4 based off the CEL.g4 grammar, which comes from Google's Golang CEL"，用 antlr4rust 的 fork 工具 `java -jar <tool.jar> -Dlanguage=Rust -package gen -visitor CEL.g4`（gen/mod.rs:1-15），产出 cellexer/celparser/celvisitor 三件套。`parser/parser.rs` 用 `antlr4rust` 的 `CommonTokenStream`/`ErrorStrategy` 组装出 `Parser`（parser.rs:9-18）。

编译入口是 `Program` 三兄弟（`crates/cel-fork/cel/src/lib.rs:199-213`）：`compile_with_optimizer` = `compile` 再套自定义优化器，`compile` = `compile_unoptimized` 再跑内建优化。内建优化（`src/optimize.rs`）做常量内联：全字面量 List 折成 `Value::List`（optimize.rs:100-110），Literal 一律转 Inline（optimize.rs:156-159）。自定义优化走 `Optimizer` trait——"optimize will be called on each node *after* default optimizations"（optimize.rs:26-35），免遍历整个 AST。

fork 的核心增量是 **AST 级特化节点**：`Expr::Optimized { original, optimized }` 保留原表达式兜底（`src/common/ast/mod.rs:47-52`），目前唯一的 `OptimizedExpr` 变体是 `HeaderLookup { request: bool, header: HeaderName }`（ast/mod.rs:53-62）。触发点在 optimize.rs:163-180——模式匹配 `request.headers["字面量"]` 或 `response.headers[...]`（INDEX 调用 + Select 到 `headers` 字段 + 标识符限定 request/response + `HeaderName::from_bytes` 合法），命中即整体替换。求值侧对应挂钩在 `objects.rs:571-587`：`Expr::Optimized` 先问 `resolver.resolve_direct(optimized)`，返回 `None`（resolver 不认识）就回退求 `original`——fork 特性与宿主解耦的关键设计（详见第五节）。`cel-derive` 则提供 `#[derive(DynamicType)]` 过程宏（cel-derive/src/lib.rs:9），让原生 Rust 类型零转换进入 CEL 求值。

`crates/celx/src/lib.rs:19-34` 的 `insert_all` 是唯一注册入口，按序装入六模块（图谱摘要也点名"crate 唯一公开注册入口"）：

### 2.3 policy-core：表达式即带属性契约的编译产物

`crates/policy-core/src/lib.rs:1-7` 的 crate 文档自我定位精确："**This crate is the dependency boundary between policy implementations and the gateway runtime**"——策略 crate 只依赖稳定接口，网关供给 CEL 求值/tracing/backend 分发。

核心类型 `Expression`（`src/expression.rs:32-36`）= 编译好的 `Program` + `FlagSet<Attributes>` + 原始字符串。`new_strict`（expression.rs:150-169）用 `Program::compile_with_optimizer(..., agent_celx::DefaultOptimizer)` 编译（:153），然后做**属性提取**。`Attributes` 是 21 个属性域的位集（expression.rs:77-109：Source/Destination/Request/RequestBody/Response/Llm*/Jwt/ApiKey/BasicAuth/Mcp/Guardrails/Extauthz/Extproc/Metadata/Proxy/Backend）。提取分两路：AST 路径走 `attributes_for`（expression.rs:189-264）——`properties.rs` 递归收集根标识符路径（Select 链前插字段名，properties.rs:22-25），再按 `["request","body",..]`、`["llm","prompt",..]` 等 17 组模式聚合；函数路径查 `CUSTOM_FUNCTION_ATTRIBUTES` 注册表（expression.rs:266-288）。**引用了 `variables()` 函数则直接全属性拉满**（expression.rs:157-162），因为该函数可访问任意变量。容错入口 `new_permissive`（expression.rs:124-148）编译失败时替换为 `fail("the expression ... could not be compiled")`——靠 celx 注册的 `fail` 函数（general.rs:324）在求值期报错而非配置期崩溃。serde 集成是严格的：`Deserialize` 直接 `new_strict`，本地配置解析失败即整体失败（expression.rs:47-56）。

接口面：`PolicyCel` trait 只暴露 `eval_request/eval_response` 两个方法——"Keeping this interface narrow allows policy crates to evaluate CEL without depending on the gateway's request log or snapshot implementation"（expression.rs:290-306）；`RequestPolicy::expressions()`（policy.rs:88-91）要求每个策略交出自己持有的全部表达式，供宿主统一注册属性。

### 2.4 数据面 cel 模块：全局上下文、快照决策、自定义函数引擎

`crates/agentgateway/src/cel/mod.rs`（文件头注明启发自 Kuadrant wasm-shim，Apache 2.0，mod.rs:1-2）：

- **ROOT_CONTEXT**：`OnceLock` 全局单例，惰性初始化时 `agent_celx::insert_all` 装满全部函数（mod.rs:18-32）。所有求值共享这一个函数表；

- **custom.rs 自定义函数引擎**：`register()`（custom.rs:38-70）是唯一入口——先手工解析定义文本（支持 `name(args) { cel }` 与 `this.name(args) { cel }` 两种形态、`rest...` 变参、`#` 注释、嵌套/引号内大括号，custom.rs:295-357），然后依次：查重名（:72-83）、**传递调用闭包+环检测**（:97-151）、传递属性合成（:153-179）、拒绝与内建冲突（:85-95）、逐个编译注册、把属性表安装进 policy-core（:63）。运行期闭包 `custom_function`（:203-239）用 `CustomResolver` 把参数遮蔽在调用者变量之上，其余变量透传（:241-269）；`Registered` 元数据用 `Box::leak` 换取与全局上下文同寿命——注释："Leaking this small metadata object gives the callback the same lifetime as the context and avoids a registry lookup on every call"（:181-191）；
- **types.rs Executor**：CEL 根变量（图谱摘要："聚合 request/response/proxy/env/source/destination/jwt/apiKey/mcp/backend/guardrails 等全部网关属性域"）。`new_request` 直接借 `&http::Request` 构造视图（types.rs:733-737）；`eval`（types.rs:784-812）以 `Value::resolve(expr.ast(), context(), &resolver)` 求值并接入 dtrace 计时（:786-805）；`resolve_direct`（types.rs:550-561）是 HeaderLookup 的热路径实现——注释点明动机"To avoid a conversion from a string key into a HeaderName, we have a hot path"，用 `get_all(header)` 取值，**重复头回退通用路径**（:558-560），缺失头返回 `Some(None)` 让 fork 层翻译成 `NoSuchKey`。

## 四、数据流（一条表达式从 CRD 字符串到求值结果）

以限流键 `request.headers["x-user"]`（localratelimit.rs:459 内联 policy_tests 模块中的同款实测用例）走全链：

1. **配置期-解析**：CRD 的 CELExpression 字符串经 translator 进 IR，数据面反序列化触发 `Expression::deserialize` → `new_strict`（expression.rs:47-56、150）。
2. **配置期-编译**：`Program::compile_with_optimizer(src, DefaultOptimizer)`（expression.rs:153 → cel lib.rs:199-204）→ ANTLR lexer/parser 产出 AST → 内建优化做字面量内联（optimize.rs:100-159）→ celx DefaultOptimizer 三类折叠（本例无 cidr/regex/json，跳过）→ **cel-fork 尾部特化**：识别 `request.headers["x-user"]` 命中 INDEX+Select+Ident+合法 HeaderName 四条件，整体替换为 `Expr::Optimized { original, HeaderLookup { request: true, header: "x-user" } }`（optimize.rs:163-180）。
3. **配置期-属性提取**：`references()` 收集函数/变量引用（cel lib.rs:238-249、references.rs:6-9）；`properties` 从 AST 收出路径 `["request","headers"]`（properties.rs:22-25）→ `attributes_for` 命中 `["request", ..]` 分支置 `Attributes::Request`（expression.rs:200-202）。
4. **装配期**：过滤器 `expressions()` 上交表达式（policy.rs:88-91），ContextBuilder 累加属性（mod.rs:62-65）；`maybe_snapshot_request` 因 Request 属性命中而做请求快照（mod.rs:118-135）——**这一步是属性契约的意义：不求值就知道要备好哪些数据**。
5. **请求期-求值**：`apply` 里 `Executor::new_request(req)` 借引用构造视图（localratelimit.rs:286 → types.rs:733）；`bucket()` 调 `exec.eval(key)`（localratelimit.rs:181）→ `Value::resolve(ast, context(), &ExecutorResolver)`（types.rs:787）→ 命中 `Expr::Optimized` → `resolve_direct`（objects.rs:574 → types.rs:550）：`get_all("x-user")` 单值直接 `str::from_utf8` 返回 `Value`，零 HeaderName 转换、零 map 构建（types.rs:552-561）；重复头回退 original 通用求值（types.rs:558-560）；头缺失则 `Some(None)` → fork 层翻译成 `NoSuchKey("request.headers['x-user']")`（objects.rs:577-583）。
6. **消费**：求值结果 `as_str()` 成功且非空即作为分桶键 `get_or_insert_with` 建/取令牌桶（localratelimit.rs:182-190），失败落共享桶并打 debug 日志（:183-184）。

## 五、设计决策

**fork 上游而非封装**：fork commit `4404d14d "CEL 2.0 (#877)"`（2026-01-29）的提交信息是最权威的设计文档，要点原文：CEL 执行三阶段——①编译（罕见、慢）②构建上下文"~JSON like struct"（每请求 0-5 次、pretty slow）③求值（每请求 20+ 次）；该 PR "completely removes the cost of (2), and makes (3) 5-20x faster"，手段是把解释器的 `Value` 类型从纯 owned 扩成**引用 + Dynamic trait**（原生 Rust 类型直接做输入，"take a `&http::Request` and run `request.headers['bar']` over it with zero allocations"），并为繁琐的 trait 实现配套 derive 宏；收益实测"86k/250k QPS → 400k QPS"。这解释了为什么必须 fork：**改的是 Value 类型系统本体，封装根本够不着**。用户可见的破坏性变更也在提交信息里明示：函数改名 `base64Encode`→`base64.encode`（旧名兼容保留，见 general.rs:45-49）、顶层变量从"恒存在可能为 null"改为"不可用即查找失败"（`has(jwt)` 语义变化）。上游化意向有注记：strings.rs:3 的 `TODO: cel-rust#103, have this upstreamed`——推断这代表 celx 侧函数族意在回流上游，而 fork 本体的引用化 Value 尚无回流计划（源码无注记，此半句为推断）。

**HeaderLookup 作为 AST 节点而非字节码**：特化结果保留 `original`（ast/mod.rs:47-52），求值时 `resolve_direct` 返回 `None` 即回退原表达式（objects.rs:574-586）——宿主不实现热路径时语义不损，只丢性能。这是"fork 提供能力、宿主选择性兑现"的增量设计（批 24 发现，源码复核属实）。Envoy 风格的对标由 `request/response + headers + 合法 HeaderName` 的匹配条件体现（optimize.rs:163-174），动态键、变量基座（如 `env.headers`）都不特化——宁缺勿错。

**自定义函数环检测的必要性**（批 9 发现，源码复核属实）：CEL 是无类型纯表达式语言，函数体是编译好的 `Program`（custom.rs:182），运行期互相调用是 Rust 闭包递归——**不检测就是栈溢出**。`transitive_custom_calls` 用不动点迭代算调用闭包，发现自环即拒绝并报错 `"custom CEL function recursion is not supported"`（custom.rs:121-148），注释点明闭包"used both to reject recursion and to propagate snapshot attributes"——一份数据两个用途：`transitive_attributes` 用它把多跳链、前向引用的属性并给调用者（"including forward references and multi-hop chains"，custom.rs:153-159），否则 `isInternal()` 调 `nested()` 时宿主不知道要快照 request，求值期才炸。配套防线：必须先于任何 CEL 使用注册（OnceLock 检查，custom.rs:42-49）、拒绝与内建重名（:85-95）、参数遮蔽但 `resolve_direct` 故意不转发——"optimized expressions may reference a variable this resolver masks"（:282-284，防止优化节点绕过遮蔽直读宿主变量）。

**编译期 vs 运行期**：能编译期做的绝不留到运行期——regex/cidr/ip 预解析（celx optimize.rs:43-82，提交信息原话"its not acceptable to compile a regex on each evaluation"）；属性提取在编译期完成，运行期只做快照决策；`new_permissive` 把编译错误也折叠成运行期 `fail()` 表达式而非延迟崩溃（expression.rs:124-148）。求值期设计上接受"每请求 20+ 次求值"，所以 Executor 全程借引用（types.rs:787）、函数表全局单例（mod.rs:18-32）、自定义函数元数据 `Box::leak` 免每次查注册表（custom.rs:183-191，注释原文）。

## 六、新人提示

**加一个 CEL 扩展函数**（以 celx 为例）：在 `crates/celx/src/` 选模块（新领域则建文件 + lib.rs:19-34 的 `insert_all` 加一行 + `mod` 声明）；简单函数 `ctx.add_function("name", f)`，命名空间函数用 `ctx.add_qualified_function("ns", "name", f)`（对照 general.rs:41-45，含新旧名并存写法）；自定义类型走 `crate::impl_opaque!(T, "type_name")` + 接收者方法用 `crate::impl_functions!` 宏声明 CEL 名（cidr.rs:18-33 是完整模板）；测试写进 `function_tests.rs`；若函数访问网关属性，必须像 custom.rs:413-416 那样参与属性提取——内置函数的属性语义目前写死在 expression.rs 的 `attributes_for_functions` 注册表消费端，新增"读请求体的内置函数"时这是最容易漏的一步（推断：更稳妥的做法是让新函数走 customFunctions 机制自动获得属性传播）。

**调试表达式**：首选 `cargo xtask cel [--ast] '<expr>' [json]`（xtask/cel.rs:5-42）——不带参数用 `full_example_executor()` 的示例上下文（types.rs:2447），带 JSON 用 `ExecutorSerde` 反序列化自定义上下文；`--ast` 用 `compile_unoptimized` 打印**未优化** AST 的 JSON（:18-19）。要看优化后形态，对照 cel-fork optimize.rs:163-180 手工核对，或写小测试断言 `program.expression` 匹配 `Expr::Optimized`（optimize.rs:288-308 的 test_optimize_function 是范例）。

**坑**：①`--ast` 看到的是未优化树，HeaderLookup/jsonField/precompiled_matches 都只在优化树里存在——排查"为什么没走热路径"先确认表达式形态是 `request.headers["字面量"]`（动态键、`env.headers`、非字符串字面量都不特化）；②customFunctions 里 `size`/`matches` 等内建名直接注册失败（custom.rs:85-95），递归（含互相递归，custom.rs:572-584 测试钉版）也失败，且必须在任何 CEL 表达式编译前注册（OnceLock，custom.rs:45-49）——本地配置里 customFunctions 放最前面不是风格建议是硬约束；③表达式里出现 `variables()` 立即全属性拉满（expression.rs:157-162），意味着全量快照+全 body 缓冲的性能下限；④重复 header 值会脱离 resolve_direct 热路径回退通用求值（types.rs:558-560），压测数据里"同名多值头"场景的 CEL 耗时会突增；⑤限流键求值失败不报错而是静默落共享桶（localratelimit.rs:182-184）——"限流好像没按用户分桶"排查时先看 debug 日志里的 "no rate limit key"；⑥ CEL 语法错误在 xDS/K8s 路径上不挡配置下发（运行期求值失败才暴露），本地配置路径才严格（expression.rs:47-56）——上线前用 xtask cel 过一遍最稳。
