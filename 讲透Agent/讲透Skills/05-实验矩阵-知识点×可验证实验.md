## 2. E1 详解：一次实验三个定律

```
zero-shot:  正例 0/5 | near-miss 0/3 | 负例 2/2
few-shot:   正例 2/5 | near-miss 0/3 | 负例 2/2
```

三条读数（每条都对应官方实践的一个设计决策）：

1. **欠触发是模型能力函数**。0.5B 在 zero-shot 下几乎全 NONE——不是 description 不好，是小模型的指令遵循撑不起路由任务。官方 skill-creator 的"pushy description"建议（"Make sure to use this skill whenever..."）正是对抗这个偏置的制度化手段；而触发机制文档说"复杂多步任务才可靠触发"——模型越弱，"能自己扛"的判断越失真。
2. **路由决策也吃 ICL**。仅仅加两个示范（1 个选技能 + 1 个拒识），总对率翻倍（2/10→4/10）。推论：**skill 系统的路由质量可以用路由层 few-shot 独立调节**——这是 harness 工程的一个可调旋钮。
3. **near-miss 是 description 质量的真考官**。N1（"LoRA 微调 loss NaN"）被"LoRA"关键词诱导到 llm-mastery，但任务本质是 debug——**关键词匹配 ≠ 意图匹配**。0.5B 上全军覆没正说明这层区分难度高；官方 run_loop 优化循环花大力气造 near-miss 负例（"共享关键词但实际需要别的工具"）就是在攻这一层。

> 诚实边界：0.5B 是教学级被试，生产级模型（Claude/GPT/DeepSeek 级）路由能力远强于此；但三条定律的方向性在强模型上同样成立（欠触发偏置由官方文档亲证，near-miss 由 run_loop 协议亲证）。E1 的价值是把"官方为什么这么设计"变成可见的失败样本。

## 3. E2 详解：渐进披露的经济学

三个数字三种含义：

- **93.1%**：渐进披露的结构性节省。如果 skills 是"打包的 prompt"（全部常驻），本机 38 个 skill 要吃 5.2 万 token；三层模型下常驻只要 3.6 千。**这就是 skills 相对 system prompt 堆砌的量化优势**。
- **2.5×**：dcf-model 的 1259 行正文超预算 2.5 倍——每次触发吃 13K 注意力。L2 超载不违反规范（500 行是"建议"），但违反经济学。
- **5 个**：CC 的 1% 清单预算（128K 窗口≈1280 字符）下，本机这种 200+ 字符的中文 description 只装得下 5 个 skill。这不是假想威胁，是**当前生产实现的硬约束**。对策三选一：压缩 description、用条件加载（frontmatter `paths`，未命中目录不进清单）、按项目分目录装。

## 4. E3 详解：规范不是纸面文章

117 个本机 skill 目录扫出 2 个真 C4 违规（`earnings-preview-beta` 里 name 写的 `earnings-preview-single`；`strip-profile` 里 name 写的 `fsi-strip-profile`）——**这在 agentskills.io marketplace 上架时会被 skills-ref validate 直接拒**。77 个警告里绝大多数是 C7（description > 250 字符，在 CC 实现里被截断）——跨工具发布的 skill 应按最严实现写。

顺手修法：`name` 改成与目录一致（或目录改名），description 压缩到 250 字符内（把 Triggers 关键词表保留、删功能叙述）。

## ✍️ 练习

1. 跑 E1，然后把 N1 的 debug-helper description 加一句 pushy 反例边界（"包括 LoRA/训练脚本报错等看似属于其他领域但本质是排错的任务"），重跑看 N1 是否翻转。
2. 跑 E2，若窗口 1M（当前旗舰级），1% 预算能装多少个？推出"description 平均长度 × 目标装载数 ≤ 窗口×1%"的装载规划公式。
3. 用 E3 扫你自己的 skills 目录，统计违规/警告率，挑一个警告修复。
