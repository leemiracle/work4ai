# 02 — 渐进披露与上下文经济学

> 「讲透 Skills」第三篇。Skills 的灵魂不是文件格式，是**加载模型**。本篇算清一笔账：为什么装 100 个 skill 不会撑爆上下文，以及什么时候它会爆（context rot）。

---

## 1. 直觉：图书馆 vs 大字报

让 agent 掌握 100 项技能，有两种极端做法：

```
做法A（大字报）：把 100 项技能的完整说明书全塞进 system prompt
  → 100 × 5000 tok = 50 万 token，任何上下文窗口都会爆
  → 就算窗口够大，attention 也早被稀释（lost in the middle）

做法B（图书馆）：门口挂一张 100 行的索引卡片（每技能一行），
  需要哪本就去书架取哪本，用完归还
  → 常驻 100 × ~100 tok = 1 万 token
  → 正文只在触发时进场
```

Skills 就是做法 B。规范原文："Agents load skills **progressively**, pulling in more detail only as a task calls for it."

## 2. 三层加载模型（规范规定，不是实现细节）

| 层 | 内容 | 何时进上下文 | 预算 |
|---|---|---|---|
| L1 元数据 | name + description | **启动时常驻**（所有已装 skill） | ~100 tokens/个 |
| L2 正文 | SKILL.md body | **触发时**才装 | <5000 tokens（<500 行） |
| L3 资源 | scripts/ references/ assets/ | **按需**读/用；scripts 可不进上下文直接执行 | 无限制 |

三层各自的经济学：

- **L1 是"地租"**——每个 skill 都要交，所以 description 必须短而准（这是 [03 章](03-路由与触发-description即检索键.md) 的主题）。
- **L2 是"用时付费"**——不触发的 skill 一分钱不花。这就是 skill 相对 system prompt 的结构性优势。
- **L3 是"外部记忆"**——references 按需读；**scripts/ 甚至可以零 token**：agent 只需知道"跑这个脚本"，进程执行不占上下文。官方 pdf skill 的文本抽取正是如此——LLM 不读 PDF，Python 读。

## 3. 代码铁证：Claude Code 的 1% 预算与 250 字符截断

本仓 ClaudeCode 源码深读（钉版 091cde4，`articles/14-skills-progressive-disclosure.md`，一手 file:line 证据）揭示了生产实现如何给 L1 上硬约束：

| 机制 | 代码位 | 行为 |
|---|---|---|
| **1% 上下文预算** | `SkillTool/prompt.ts:20-29, 88-142` | 清单（全部 skills 的 name+description）最多占窗口字符数的 **1%** |
| **250 字符硬截断** | 同上 | 单条 description 超过 250 字符直接截断——规范允许 1024，CC 只给你 250 |
| **超载逐级降级** | 同上 | 预算超了先截 bundled 之外的，bundled skills 永不截 |
| 五来源并行扫描 | `loadSkillsDir.ts:679-714` | 插件/项目/用户等五来源 + realpath 去重，first-wins |
| 条件 skill | frontmatter `paths` 字段 | 路径命中才进清单——**连 L1 地租都可以条件豁免** |

两个反直觉：

1. **规范 vs 实现的落差**：规范说 description ≤1024 字符，CC 实现截 250。跨工具的 skill description 应该按最严实现写（≤250 字符内说清"做什么+何时用"）。
2. **1% 预算意味着装 skill 数有物理上限**：200K 窗口 ≈ 2000 字符清单 ≈ **几十个 skill 就到顶**（每条 name+description 约几十字符）。"装满 1000 个 skill"在任何实现里都不现实——这是 registry/条件加载等机制存在的根本原因。

## 4. context rot：装载的真实代价

microsoft/skills README 官方警告（一手核实）：

> "Loading all skills causes context rot. Only install the skills needed for your current project."

context rot 的机制（与上下文工程研究一致）：

```
每多装一个 skill 的 L1 → attention 预算被摊薄一分
       ↓
两个后果同时发生：
  ① 触发精度下降（agent 在更长的清单里检索，匹配更容易错）
  ② 已触发 skill 的执行质量下降（正文与更长的系统提示竞争注意力）
       ↓
所以 android/skills 的官方选题判据是另一面：
  "只补 evals 证实的短板，不重复模型已熟练的领域"
  → 每个常驻 skill 都要有 L1 之外的净收益证明
```

这给了"要不要写这个 skill"一个经济学判据：

$$\text{skill 净值} = \underbrace{\Delta \text{任务质量}}_{\text{触发后的收益}} - \underbrace{c_1 \cdot \text{desc长度}}_{\text{L1 地租}} - \underbrace{c_2 \cdot \text{装载稀释}}_{\text{对其他 skill 的外部性}}$$

模型已经会的（如"写个 hello world"）净值必为负——这就是 android 判据的数学形式。

## 5. 与相邻机制的对照

| 机制 | 常驻成本 | 加载粒度 | 适合 |
|---|---|---|---|
| system prompt | 全量 | 无（永远全在） | 每次对话都需要的规则 |
| **skills L1 清单** | ~100 tok/个 | 三层渐进 | 偶发但重要的程序性知识 |
| MCP tools 定义 | 每工具 schema 数百 tok | 按需调（但定义常驻）* | 接外部能力 |
| RAG 检索 | 0 常驻 | 每次检索 | 大规模事实知识 |
| 条件 skill（paths） | 0（未命中路径） | 目录级 | 项目绑定技能 |

\* 2026 年 API 原生化正在改变这点：OpenAI `tool_search` + `defer_loading` / Anthropic `tool_reference` / Codex CLI 默认 BM25 tool_search——**工具定义也在向渐进披露演化**（AI-Agents-in-Depth 深读卡 2.4 节证据）。skills 领先了这一步。

## 6. 本机实测样本（活教材）

explore 盘点报告（2026-08-25）的两个对照样本：

- **正面**：`~/.config/opencode/skills/` 38 个 skill 全部两字段极简（name+description），无 scripts/references 子目录——L1 极简主义的活样本。
- **反面**：`~/.agents/skills/dcf-model` 的 SKILL.md 达 **1264 行**，是 500 行预算的 2.5 倍——L2 超载意味着每次触发都吃掉大量注意力（修复方案：拆 references/）。

本站实验室 [E2](experiments/02_progressive_tokens.py) 用 tokenizer 精确测量这两种形态的 token 差。
