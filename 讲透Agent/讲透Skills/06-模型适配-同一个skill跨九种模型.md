# 06 — 模型适配：同一个 skill 跨九种模型

> 「讲透 Skills」第七篇 ★（用户五问之二：**skills 怎么适配不同的模型**）。同一个 SKILL.md，从 0.5B 端侧模型到旗舰推理模型，行为会系统性漂移。本章给出漂移的五个维度、四种适配策略、以及一份"按模型形态改 skill"的实操矩阵。

---

## 1. 问题的根源：skill 的三个成分对模型能力的依赖不同

拆开一个 skill，它其实混了三种东西，各自对模型的依赖度不同：

| 成分 | 例子 | 对模型能力的依赖 |
|---|---|---|
| **事实/流程**（declarative） | "用 openpyxl 而不是手写 XML" | **零依赖**——任何模型都受益，纯知识注入 |
| **程序性指令**（procedural） | "先写失败测试再实现" | **中依赖**——弱模型走不完多步流程，强模型嫌约束多余 |
| **品味/判断**（judgmental） | "解释为什么比 MUST 排比句更有效" | **强依赖**——只有足够强的模型才能"理解精神而非字面" |

这个拆分直接预言了适配问题：**同一个 skill 在不同能力级的模型上，最优形态不同**。

## 2. 五个漂移维度（E1 实测 + 官方证据）

### ① 触发漂移（谁来路由）

E1 实测：0.5B 在 zero-shot 路由下几乎全拒（欠触发极端形态），few-shot 救回一半。官方 skill-creator 文档承认 Claude 也有欠触发倾向（所以才要 pushy description）。**模型越弱，越需要在 description 里做行为补偿**（更多触发词枚举、更强语气）；模型越强，越需要 near-miss 反例防误触发。

### ② 指令遵循深度（能不能走完流程）

skill-creator SKILL.md:302 的原话（一手）：

> "Today's LLMs are *smart*. They have good theory of mind... **If you find yourself writing ALWAYS or NEVER in all caps, or using super rigid structures, that's a yellow flag** — reframe and explain the reasoning."

这条建议隐含模型分级：**强模型 → 解释 why，弱化刚性约束；弱模型 → 需要更结构化的 checklist、每步更短、失败重试提示**。给 0.5B 写"解释为什么"是浪费，给旗舰模型写一堆 MUST 是干扰。

### ③ 长上下文利用（装载后能不能用好）

- 小窗口模型（4K-8K）：skill 正文 + 任务数据 + 输出可能直接溢出——L2 必须激进压缩，能推 scripts/ 的全推。
- 长窗口模型（128K-1M）：装得下≠用得好（lost in the middle 在所有模型上存在）。但长窗口允许更厚的 references/ 按需读取。
- E2 的 1% 预算对所有模型同样生效：**清单成本与窗口成比例，装载上限 = 窗口 × 1% ÷ 条均长**。

### ④ 工具调用能力（scripts/ 能不能真跑）

skills 的杀器是 scripts/——但前提是模型能可靠地 spawn 进程、传参、读输出。0.5B 级模型工具调用不可靠 → skill 要退化成"纯文本指导 + 人类执行"；旗舰模型 → 大胆把确定性逻辑全推进 scripts/，正文只留"何时跑哪个脚本"。

### ⑤ 推理模型（thinking 模型）的特殊性

推理模型（o 系/R1/GLM thinking）在 skill 适配上有独立课题：

- **CoT 类 skill 内容被内化**："一步步思考"这类指令对推理模型是噪声（模型自己会想），skill 应转向"告诉它想什么"（领域检查清单、证明义务、验证标准）。
- **正文装载时机与思考预算的交互**：skill 指令进入的是上下文，推理模型的思考阶段会消耗它——过长正文稀释思考质量。
- **本仓对应证据**：讲透Prompt HISTORY 的库恩式结论"推理模型消灭了 CoT 技巧但没有消灭 prompt 工程，它改变了重点"——skills 同理：**推理模型改变的是 skill 内容的最优配比（判断性↑、程序性↓、事实性不变），不是 skill 的存在价值**。

## 3. 四种适配策略

| 策略 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **A. 单一通用版** | 按最弱目标模型写，强模型将就 | 维护 1 份；弱模型上限 | skill 内容以事实性为主时可行 |
| **B. per-model 分发** | 同一 skill 多个变体，按宿主选择 | 维护 N 份 | 已有成熟分发渠道（microsoft 的语言后缀制 `-py`/`-ts`/`-java` 是同思路：**变体挂目录名，路由交给安装器**） |
| **C. 正文自适应** | 正文里写条件分支："若你是小窗口模型则只执行步骤 1-3；若可调用 Python 则直接跑 scripts/x.py" | 维护 1 份但内嵌复杂度 | 分支少（≤3）时有效 |
| **D. harness 层适配** | skill 保持纯净，宿主 agent 的 system prompt 负责按模型注入不同引导 | 需要 harness 控制权 | 生产环境推荐（prompt 手册 07 章策略 B 的 skills 版） |

**推荐默认：D 为主，B 兜底**——skill 文件保持模型中立（规范的本意），适配逻辑放 harness；只有当某个模型的差异大到无法用引导弥补（如端侧 0.5B 需要完全不同的流程切分），才 fork 出 per-model 变体。

## 4. 实操矩阵：按模型形态调 skill

| 模型形态 | L1 description | L2 正文风格 | L3 资源策略 | 例子改写 |
|---|---|---|---|---|
| 端侧小模型（0.5-3B） | 触发词密集、短句、避免抽象词 | 短步骤 checklist（≤7 步）、每步一个动作、失败重试提示 | 全部预展开（弱模型不会主动读 references）；scripts 给出精确调用行 | "第 3 步：运行 `python extract.py --input {file} --format csv`。若报 ModuleNotFoundError，先 `pip install pandas` 再重跑" |
| 中型通用（7-32B） | pushy + 反例边界 | 结构化流程 + 关键处解释 why | references 一层深可按需读 | "按 references/aws.md 部署（仅当你确认目标平台是 AWS）" |
| 旗舰对话（Claude/GPT/GLM 级） | 精准为主，near-miss 反例防误触 | 解释动机、原则化、少 MUST（skill-creator 黄旗警告） | 大胆用 references/ 分域文件 + scripts/ 卸载确定性 | "我们这样排序是因为检索相关性对首尾位置敏感——把最相关文档放首尾" |
| 推理/思考模型 | 同上，但删掉诱导性措辞 | 删 CoT 类指令，加领域判断标准（证明义务/验证清单） | 同上；正文更薄（思考预算珍贵） | 把"一步步分析这个不等式"换成"证明义务：每步放缩必须标注方向和依据的引理" |
| 多模态模型 | description 可引用模态关键词 | 指令可以引用"看图/截图"能力 | assets/ 里的图例真正有用 | "对照 assets/ui_pattern.png 判断布局类型" |

## 5. 一个具体的双向改写示例

同一个"代码审查"skill 的开头，两种形态：

**弱模型版（结构化、刚性、短步）：**
```markdown
## 流程（严格按序执行）
1. 读 diff：运行 `git diff main...HEAD`
2. 只查这 5 项：空指针 / 越界 / 资源泄漏 / 注入 / 并发
3. 每项输出一行：`[级别] 文件:行号 问题`
4. 不确定就写 SKIP，禁止猜测
```

**强模型版（原则化、解释 why、零刚性）：**
```markdown
## 审查哲学
历史上 80% 的高危缺陷集中在五类（注入/内存/资源/并发/逻辑边界），
优先扫这五类的投入产出比最高——但你的领域判断优先于本清单：
如果 diff 的上下文暗示其他风险（如密码学误用），直接展开。
输出格式服务于人：每条发现要能被一行 grep 定位到文件:行号。
```

同一知识，两种包装——**弱模型需要护栏，强模型需要品味**。

## ✍️ 练习

1. 取你一个 skill，按第 4 节矩阵分别写出端侧版和旗舰版的正文开头（各 ≤10 行）。
2. （实验）把 E1 的 8-skill 清单喂给你能访问的更强模型（API），同一组 10 query，对照 0.5B 结果验证"欠触发随能力减弱、near-miss 部分可解"。
3. （思考）为什么规范把 `compatibility` 字段设计成"只在有硬环境要求时写"，而不是让每个 skill 都声明支持哪些模型？（提示：声明爆炸 N×M、能力是连续谱不是离散标签、harness 层适配更收敛）
