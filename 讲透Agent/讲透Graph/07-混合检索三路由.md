# 07 · 混合检索三路由：vector / graph / SQL 与 retrieval-generation gap

> 讲透Graph 第 07 章 ★用户重点 | 实验 E5（`experiments/E5_perhop_accuracy.py`）

## 1. 直觉层：三种问题，三种工具

问句自带路由信号（vanja.io + GEM 2026 的合流判断）：

| 问题类型 | 例子 | 工具 |
|---------|------|------|
| "找像这个的" | 哪些 runbook 讲 checkout 超时？ | **vector**（相似度） |
| "顺着连接走" | 下周过期的证书阻塞了什么？ | **graph**（类型边遍历） |
| "给我精确数字" | 昨天多少笔支付失败？ | **SQL**（精确查询） |
| 混合型 | "为什么 release 81 之后失败激增、影响了谁？" | **router** 分派三路再汇合 |

2026 年反复赢的模式不是"图取代向量"，而是**三件套 + 路由器**。任何"单工具解决一切"的 pitch 都该警惕。

## 2. 数学层：每跳精度的乘法灾难（E5 实测）

图遍历 $k$ 跳、每跳准确率 $p$：

$$P(\text{链路正确}) = p^k, \qquad \mathbb{E}[\text{重试次数}] = \frac{1}{p^k}$$

E5 实测数字（`E5_result.json`，图 `E5_perhop.png`）：

| 每跳 p | 5 跳 | 8 跳 | 10 跳 |
|--------|------|------|-------|
| 0.99 | 0.951 | 0.923 | 0.904 |
| 0.95 | 0.774 | 0.663 | 0.599 |
| 0.90 | 0.590 | 0.431 | **0.349** |
| 0.80 | 0.328 | 0.168 | 0.107 |

**交叉点算术**：扁平检索单跳命中 $q$，图遍历 $k$ 跳要赢，需每跳
$$p \ge q^{1/k}$$
q=0.90、k=5 时 $p \ge 0.979$——E5 的 Q3 正是这个数：5×0.98=0.9039，跟单跳 0.90 **打平**。每 hop 掉到 0.95 就剩 0.774，彻底输。**图要赢，每跳必须极准**——这就是"数 hops，别数 top-10"的数学根据，也是图系统把实体链接/消歧做成了生死线的理由。

**评测哲学转向**：别查"对的文档有没有出现在 top-10"，要查**答案依赖的每个节点和每条边是否都对**（per-hop accuracy、未解析实体数、矛盾边数、能出示证据路径的答案占比）。20 个带溯源的正确节点 > 20000 个抽取出的幽灵。

## 3. retrieval-generation gap（GEM 2026 实证）

GEM 2026（aclanthology 2026.gem-main.40，9 场景实测）发现的怪事：**检索增强不按比例转化为生成质量**。扩大检索（更多 path、更多 subgraph），检索指标涨，端到端答案质量不涨。三个机制：

1. **位置注意力衰减**：材料在窗口里的位置影响利用率（← 讲透Context Ch02 首因/近因/中间盲区）；
2. **语义显著性偏好**：模型偏爱"看起来重要"的实体，不是答案需要的；
3. **基数效应**：检索回来的实体一多，答案跟着膨胀跑偏。

对策：上下文优化——GEM 的三元组表示把实体对表示为 `(entity1 --relation-- entity2)`，token 从 $O(n)$ 降到 $O(1)$；子图去重让上下文**亚线性增长**；batch agentic retrieval（ReAct+ReWOO 混合：一次批量发多个子查询）减少重发全历史的轮次——合计省 **19-53% token** 不掉点。

## 4. 代码层：router 的最小形态

```python
def route(q):
    if has_exact_aggregation(q):        return sql(q)      # "多少/统计/昨天"
    if has_hidden_verb(q):              return graph(q)    # "替代/依赖/阻塞/导致"
    return hybrid(q, k_vec=5, k_graph=2)                    # 默认混合，rerank 汇合
```

判据不是玄学：动词类型（隐藏动词→graph）、数字聚合→SQL、开放主题→vector。生产上 router 本身常是一个小 LLM 分类调用（一次几百 token，换来不用三路全跑）。

## 5. 不足与坑

- **router 错 = 全错**：路由是新的单点，误判时答案南辕北辙（用户不知道该怪检索还是怪路由）；
- **序列化损耗**：子图进窗口要序列化成文本，怎么序列化（邻接表/三元组/自然语言）直接改 E5 的 $p$——GEM 的 O(1) 三元组表示值得抄；
- **混合检索的融合排序**是开放问题：语义分、BM25 分、图 proximity 分怎么加权，没有理论最优，各家都是手调。
