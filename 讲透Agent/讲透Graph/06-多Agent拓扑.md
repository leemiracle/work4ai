# 06 · 多 Agent 拓扑：supervisor、swarm 与可优化图

> 讲透Graph 第 06 章

## 1. 直觉层：组织架构学

任务图说清了"做什么、什么顺序"；**agent 拓扑**说清"谁来做、谁跟谁说话"。把任务图铺到 agent 团队上，就是组织的两个正交视图：

- **任务图**（work organization graph）：工作怎么拆、怎么依赖；
- **agent 拓扑**（agent team graph）：组件怎么分工、怎么通信。

常见拓扑（按控制集中度排）：

| 拓扑 | 结构 | 适用 | 失败模式 |
|------|------|------|---------|
| Pipeline 流水线 | A→B→C | 阶段清晰的流水作业 | 上游错误向下游放大 |
| Supervisor 中心化 | 星型，主管派活/汇总 | 异构专长、需要全局视野 | 主管成瓶颈+单点故障 |
| Hierarchical 分层 | 树状主管 | 大规模（主管的 supervisor） | 层级损耗：信息逐级失真 |
| Swarm 去中心化 | 点对点握手（handoff） | 对等协作、低延迟 | 乒乓死循环、责任稀释 |
| 辩论/评审型 | 对抗+仲裁 | 需要独立验证（Ch02 的验证门人格化） | 成本翻倍、立场趋同 |

**Message graph（ContextOS 四图之一）**：显式建模"**谁允许告诉谁什么**"——不是所有 agent 都该看到所有消息。这条边类型（permitted information flow）在 supervisor 拓扑里隐含，在 swarm 里必须显式，否则上下文污染。

## 2. 核心作品线

- **GPTSwarm**（ICML 2024）：标题即论点——*Language Agents as Optimizable Graphs*。把整个多 agent 系统表达为计算图，节点=operator（LLM 调用/工具），边=交互；然后**对图本身做优化**（改连接、merge 节点）。这是"拓扑不再手拍"的宣言；
- **TDAG**（2402.10178）：动态任务分解 + **按任务生成 agent**——不是先定团队再派活，而是活来了长出团队；
- **AutoGen GraphFlow**：有向图执行（顺序/并行/条件/环）的框架化；
- **通信协议层**：MCP 连工具，A2A/A2A-X 连 agent——协议标准化的是接口，**不是图语义**（vanja.io 警告：MCP 标准化 `run_arbitrary_cypher` 的接口形状，标准化不了你的本体）。

## 3. 数学层：通信爆炸与委派收益递减

$n$ 个 agent 全连通 = $O(n^2)$ 条消息通道；每轮同步 = $O(n^2)$ 次信息交换。这是多 agent 系统规模不经济的根：**加人先加通信税**。

委派的收益模型：任务成功率为 $p_i$ 的子任务交给更专的 agent 使 $p_i \to p_i'$。总成功率按 Ch07 的乘法灾难算：$\prod p_i'$。结论：

- 每个子任务哪怕只提升 5pp，5 个串行子任务链上就是 $1.05^5 \approx 1.28$——**28% 的系统级提升**，这是委派的复利；
- 但每个新增 agent 也引入新边（任务传递、结果翻译、失败归因）——每条边有自己的错误率。**净收益 = 专业化复利 − 新边的错误与通信税**。团队规模的甜点通常比直觉小。

## 4. 不足与坑

- **failure attribution 是深水区**：结果错了，是哪个 agent 的锅？多 agent 系统的调试/归因本身成了研究问题（arXiv 2605.14892 综述专论此事）。图的好处：至少**边上有轨迹**可查（→ Ch08 decision lineage）；
- **社会性失误**：辩论型拓扑里 LLM 容易立场趋同（谄媚），独立验证人格要靠 prompt 硬隔离，或干脆用确定性工具当裁判；
- **组织开销复利**：每层管理（supervisor）自己也要 token、也会错。层级 ≠ 免费的规模化。
