# 04a · L4a 记忆层：JSONL + 去重 + 检索

> 回到本单元的使命本身：**端侧提取事实，最后存储为 memory**。
> 立场：端侧 CPU 无 embedding 预算 → 文件即记忆（ClaudeCode 源码深读同款结论：
> 生产编码 agent 的记忆同样无向量库）。

## 一、设计

**格式**：一行一事实的 `memory.jsonl`——人类可读可编辑。用户能直接打开删掉错误条目 = 最朴素也最有效的记忆治理（端侧设备上你没有 admin 界面，只有文件管理器）。

**写入去重**（[04a_memory.py](./experiments/04a_memory.py) 的 write）：

| 动作 | 触发 | 理由 |
|---|---|---|
| skip-dup | fact+category 完全相同 | 精确重复 |
| skip-covered | 新 fact 是已有 fact 的**子串** | 已被覆盖 |
| replace-upgraded | 新 fact 是已有 fact 的**超串** | 信息更全，升级替换 |
| append | 以上都不是 | 新知识 |

**检索**（query）：滑窗二元组词袋打分 + **类别兜底**——过滤后全 0 分时返回该类别最近 k 条。

## 二、实测（2026-08-24，容器+本机双跑一致）

8 条输入（含 3 组冲突）→ 库 total=6：
- 精确 dup 跳过 ✓、超串替换 ✓（"降压药每天吃一次"→"…早饭之后吃"）
- 检索 5/5（修兜底前 3/5）

## 三、两个诚实的教学点

1. **词面软去重抓不住同义重复**："房贷每月**还**3200块"与"房贷每月15号自动扣款3200块"字面互不为子串（一个有"还"一个有"15号自动扣款"），语义却高度重叠 → 共存了。根治需要语义级判重（小模型上代价高），务实解：接受冗余，检索时两条都返回，靠展示层去重（用户看到两条近似，删一条）。**端侧记忆的哲学：宁可冗余，不可丢失**。
2. **词袋检索有语义鸿沟**："这周有什么安排"与"周三下午三点…"bigram 零交集——query 修兜底前是 MISS。类别兜底救回，但这只是安全网。正解是 **LLM 查询改写**（L4b 的 scoring 能力可复用：把"安排"改写为"本周 日程 事件"再检索）——memory 与 LLM 的协作分工：**检索做召回，LLM 做语义桥**。

## 四、为什么不用 SQLite/向量库（批判性对照）

| 方案 | 检索能力 | 端侧成本 | 可治理性 |
|---|---|---|---|
| JSONL+词袋+类别兜底（本方案） | 字面命中+类别 | ~0 | 用户直接编辑文件 |
| SQLite FTS | 同上+索引 | 低 | 需工具查看 |
| 向量库+embedding | 语义召回 | 需跑 embedding 模型（CPU 上百 ms-秒级） | 不可读，误删难查 |

0.5B 场景下 embedding 模型本身也是额外 0.1-0.4B 参数。**在事实记忆这种"类别有限+查询短"的场景，向量库是过度设计**；等记忆规模到千条级、查询到自然语言长句级再升级（升级路径：bge-small 级 ONNX 量化模型 + sqlite-vec）。

## 六、不足

- 时间戳只有天粒度，无时区/来源会话信息（真端侧需要 device_session 字段）
- 无记忆淘汰（TTL/容量上限）：记忆无限增长是端侧存储的慢性病，未覆盖
- 去重未用模型：其实 0.5B 判"两句是否同一事实"的 scoring 可以做（同 L4b 思路），留作扩展练习
