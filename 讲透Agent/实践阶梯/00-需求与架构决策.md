# 00 · 需求与架构决策

> 本单元不从"用什么技术"出发，从"任务是什么性质"出发。这一章把设计决策全部摊开——每个决策都有实测证据支撑，绝无"感觉上更好"。

## 一、需求陈述（真实场景，非玩具）

**端侧事实记忆 Agent**，两条主链：

1. **事实抽取链**：用户自然话语 → 抽取事实（日程/账单/人际/档案/健康五类）→ 结构化存储为 memory
2. **意图识别链**：用户话语 → 识别意图（闭集）→ 触发对应动作（如"提醒我明天的复查"→ 查 memory → 生成提醒）

**硬约束**（这是"端侧"的含义，一条都不能破）：

| 约束 | 数值 | 来源 |
|---|---|---|
| 算力 | CPU-only，无 GPU | 端侧设备现实 |
| 模型 | Qwen2.5-0.5B-Instruct（494M 参数，f32） | CPU 上唯一能跑出交互级延迟的量级 |
| 速度 | 实测 7.0 tok/s @1 核；多线程无收益（4核6.8/8核6.7） | [smoke.log](./experiments/smoke.log) |
| 隐私 | 数据不出设备（这就是不用云端 API 的原因） | 场景定义 |

**核心矛盾**：0.5B 模型能力弱 + 幻觉（第零号证据：语义层 0/5 合格，category 越界 4/5，fact 塌缩成标签词）↔ 任务要求结构化可靠输出。**解法不是换大模型，是 agent 工程矫正**——本单元的全部内容。

## 二、四问决策树实操

通用决策树（来自 [harness精华笔记](../harness精华笔记.md) 与 Anthropic《Building Effective Agents》立场）逐问过：

```
Q1 任务输出可机器验证吗？
   → 能。事实抽取可验证三点：①JSON 可解析 ②category ∈ 枚举 ③fact 是原句子的子串（证据接地）
   → 结论：可验证，值得上工程矫正。这是本单元一切设计的地基。

Q2 一步能写清流程吗？
   → 大部分句子一步抽取即可；但意图链需要 查memory→组装上下文→生成 两步。
   → 结论：主链用最小循环（非重 agent），不用 workflow 引擎——端侧没有编排复杂度。

Q3 单 agent + 好工具能到多少？
   → 待 L1/L3 实测回答（这正是评估环存在的意义）。预期：few-shot+校验+接地能从 0/5 拉到 4/5。

Q4 失败模式是什么？
   → 幻觉（编造/塌缩）→ 证据接地过滤；越界 → 枚举校验；漏抽 → 多路召回。
   → 不需要多 agent。0.5B 场景下，多 agent = 多倍幻觉面。
```

**架构结论**：单 agent + 最小循环 + 每步可验证。复杂度预算全花在「矫正层」而不是「编排层」。

## 三、矫正手段分层（本单元的技术核心）

模型弱，但弱在两层，修法完全不同：

| 层 | 症状 | 修法 | 成本 | 章节 |
|---|---|---|---|---|
| **语法层** | JSON 格式崩、category 越界 | 约束解码（grammar/枚举校验重试） | 低，纯代码，零推理开销 | L1 |
| **语义层** | fact 塌缩成标签词、编造事实、漏抽 | few-shot 示例锚定格式；**证据接地**（fact 必须是原句子串，否则丢弃）；多句拆分 | 中，增加 prompt 长度与重试 | L1/L3 |
| **行为层** | 意图误判、过度自信 | 闭集似然排序 + margin 弃权（不确定就问用户，不硬答） | 低 | L4b |

**关键洞察**（第零号证据的引申）：语法层 5/5 + 语义层 0/5 = **格式合规是廉价幻觉**。如果只测"JSON 是否可解析"，你会以为模型很好。评估必须分层，否则指标本身在撒谎（Goodhart 的最小案例）。

## 四、抗变化设计（"变化太快怎么办"的实操答案）

把系统切成「易变插槽」与「不变资产」：

| 易变（外包给库/随时换） | 不变（自己的资产，逐级沉淀） |
|---|---|
| 模型（0.5B→下一代端侧模型） | 评估任务集 34 条 + 指标定义（L3） |
| 推理引擎（transformers→llama.cpp） | 证据接地规则、枚举 schema（L1） |
| prompt 措辞 | memory 格式与去重规则（L4a） |
| 框架（未来若引入） | 失败模式档案（每级阶梯积累的"什么坑"知识） |

**L5 验收标准**：换模型只改一个常量 + 30 分钟内出新旧对比报告。做不到 = 插槽边界画错了。

## 五、速度预算（为什么设计必须抠）

7 tok/s 意味着什么：

| 操作 | token 量 | 耗时 | 设计约束 |
|---|---|---|---|
| 单句抽取（输入+输出） | ~200+80 | ~12-25s | 交互勉强可忍，但**不能多轮重试超过 2 次** |
| few-shot 加 3 个示例 | +250 输入 | prefill 增 ~5-8s | 示例要短，选 3 个不选 8 个 |
| 意图识别（闭集排序） | 每候选 ~60 | 全闭集 8 候选 ~1-2 min | **用打分不用生成**：一次前向算所有候选 logprob，不逐个生成 |

最后一条是 L4b 的核心设计：闭集任务永远用似然排序（scoring），不用自由生成（generation）——同一次前向传播解决整个闭集，这是 CPU 端侧最重要的架构级速度技巧。

## 六、本单元地图

```
第零号证据(语法5/5语义0/5) ──→ 00 决策(本章)：矫正分层+速度预算
                                    │
    L1 裸loop：三版对照 ──验证──→ 语法层/语义层修法有效性
    L2 harness四文件 ──验证──→ 会话稳定性(harness≠模型的对照)
    L3 评估环34条 ─────────→ 一切设计决策的裁判(固定从此)
    L4a 记忆层 ──→ JSONL+去重+检索
    L4b 意图链 ──→ 闭集scoring+margin弃权
    L5 插槽化 ──→ 换模型30分钟(抗变化验收)
    07 批判 ──→ 实验室≠真端侧/量化展望/场景边界
```
