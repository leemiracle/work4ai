# 06 · L5 模型插槽：抗变化的架构验收

> "变化太快怎么办"的最终回答不是预测未来，是**把"换模型"从重写成变成配置**。
> 本章落插槽设计 + 验收协议；**实际换模验证未执行**（容器内仅有一个端侧模型，
> 无第二个可换——诚实标注，这是本章与 L1-L4 的区别）。

## 一、插槽设计（已落在本单元代码里）

回顾 00 章「易变 vs 不变」清单，本单元的代码实际切口：

| 插槽 | 当前值 | 换法 |
|---|---|---|
| 模型 | Qwen2.5-0.5B-Instruct | `MODEL_PATH` 常量（每脚本顶部）——**这是唯一的模型耦合点** |
| 推理引擎 | transformers f32 | `gen()/score_intents()` 两个函数——换 llama.cpp 只改函数体，调用方零感知 |

不随模型变的资产（全部已沉淀且可复用）：
- DATASET30 任务集 + judge 裁判（fact_agent.py）
- validate 校验器（枚举/塌缩/接地三查）
- FactMemory 记忆层（与模型零耦合）
- 全部实验日志与结论（换模后重跑即得新旧对照）

## 二、换模验收协议（下次拿到新模型时执行）

```
1. scp 新模型到容器 /work/models/<新名>/
2. 改 MODEL_PATH（一处常量）
3. 跑 03_eval30（约 8 分钟）
4. 对照表新旧行并排：json/cat_ok/grnd/colps/hallu/pass
5. pass 差 > ±3 条（±9pp）才算真差异（n=34 的噪声带）
```

**30 分钟验收标准的依据**：以上五步中人为动作只有 2（改常量）和 4（看表）；若第 2 步发现要改的不止一个常量——插槽边界画错了，回去重构。

## 三、为什么 L5 提前"设计完成"但不"验证完成"

诚实的三种选择：
1. 假装验证过（拿不出对照表）——造假，不做
2. 拉一个云端 API 模型对比——**违反端侧前提**（云端大模型赢 0.5B 毫无信息量，且数据出设备）
3. 明写"协议就绪、待第二个端侧模型"——本单元的选择

**这也是插槽化的元教训**：L5 的本质是把"未来的变化"变成"今天的配置"。协议存在且可执行，比凑一次演示更重要。

## 四、批判

- MODEL_PATH 目前散在各脚本顶部，未收口到单一 config——严格说插槽有 4 处入口，验收协议第 2 步会暴露这个问题（好事：协议本身就是插槽体检器）
- 未覆盖 tokenizer 差异风险（换非 Qwen 系模型时 chat template/tokenizer 行为变化，gen() 里的 apply_chat_template 是通用 API 但 few-shot 示例的 token 效率会变）
- llama.cpp/GGUF 量化路径未实测（07 章展开）
