# 03 · 领域对比与选型：codegraph 在六路线中的位置

> 全景表见上级 [`Agent上下文案例/README.md`](../../README.md) §2–3。本篇做深对比 + 决策。

## 1. 与最近竞品的逐项对比

| 维度 | **codegraph** | **Serena**（28k★） | **code-index-mcp**（1k★） | **Aider repo map** | **Greptile**（SaaS） |
|---|---|---|---|---|---|
| 本质 | 预构建图（R3） | LSP 实时语义（R4） | tree-sitter 索引（R2/R3 之间） | 图排序地图（R6） | 托管图 + agent swarm（R3+云） |
| 索引时机 | 预先 `init`，增量 auto-sync | **不建索引**，查询时问语言服务器 | 浅索引自动/深索引手动 | 每轮请求前现算 | 云端预建 |
| 新鲜度 | 秒级（三层机制，见笔记 01） | **实时**（语言服务器一直开着） | watcher 刷新浅索引 | **永远新鲜**（现算） | 云端随 push 更新 |
| 精确性 | 符号/调用/路由/桥接边；动态分发 hop；启发式边带 provenance | 编译器级精确（定义/引用/实现/类型层级） | 符号级（10 语言深解析） | 只有"重要性排名"，无精确边 | 符号图 + PR diff 影响面 |
| 能力范围 | **只读检索**（explore/callers/impact） | 检索 + **符号级编辑 + 重构**（rename/move/inline，JetBrains 后端更强）+ 记忆系统 | 检索 + 文件摘要 | 只提供上下文，不提供工具 | PR 审查 + 测试生成（TREX）+ 规范学习 |
| 语言 | 20+（Rust 原生 20） | **40+**（LSP 生态红利） | 10 深 + 50+ 浅 | tree-sitter 全系 | 12 全支持 |
| 本地性 | 100% 本地（SQLite） | 本地（语言服务器本地跑） | 本地 | 本地 | 云（可自托管，SOC 2） |
| 交付面 | MCP 单工具 + CLI + npm 库 | MCP 多工具 + HTTP 模式 | MCP 多工具 | prompt 注入 | GitHub App / MCP / Claude 插件 |
| token 经济 | 吞吐 -62%，驻留 +80%（笔记 02） | 符号级编辑极省 token（agent 不用贴整文件改） | 未公布同类基准 | 地图默认 1k token，极小 | 云侧消耗，PR 评论形式返回 |

**三个决定性差异**：

1. **codegraph vs Serena = 读 vs 读写**。codegraph 明确只做检索（"surgical context"）；Serena 的核心主张是"把脆弱的文本手术换成符号级编辑"。大仓库问答选 codegraph，跨文件重构选 Serena——两者甚至可以同时装（一个管看，一个管改）。
2. **codegraph vs Aider = 预付 vs 现付**。Aider repo map 每轮现算（永远新鲜但每轮都付解析成本，且只有排名没有精确调用边）；codegraph 一次 init 预付，之后查询近零成本，代价是要维护索引新鲜度（用三层机制把代价压到秒级）。这与 [`软件即熵治理`](../../../软件即熵治理.md) 的"预付熵减 vs 边走边还熵债"完全同构。
3. **codegraph vs Greptile = 个人 vs 团队**。Greptile 的护城河不在索引（也是图），而在 **PR 审查工作流 + 从团队历史评论里学习规范** + TREX 自动写测试。codegraph 的回应是"platform is coming"（每个 PR 知道测什么、什么会坏）——托管平台 beta 已在候补，说明单机图谱是通往团队图谱的必经站。

## 2. R3 vs R4 vs R5 路线的本质分歧

| 问题 | R3 预构建图 | R4 LSP 实时 | R5 嵌入向量 |
|---|---|---|---|
| "谁调用了 foo？" | 精确边，一次查询 | 精确，但要唤醒语言服务器 | 只能猜（无结构） |
| "处理鉴权的代码在哪？"（语义模糊） | FTS5 关键词 + 符号名 | find-symbol 按名 | **最强**（语义近邻） |
| 冷启动成本 | init 分钟级一次 | 每次会话启动语言服务器 | 首次嵌入全库（贵） |
| 新鲜度 | 增量同步（秒级） | 实时 | 重嵌入（慢） |
| 可解释性 | 边可回放、blast radius 可展开 | 编译器事实 | 黑箱相似度 |

codegraph 的选择是**R3 全押 + FTS5 补模糊**，放弃向量——理由隐含在其基准设计里：agent 的架构类问题（"X 怎么和 Y 通信"）绝大多数是**结构问题**，结构问题的最优解是图不是向量。语义模糊问题（"鉴权在哪"）用符号名+关键词已覆盖 80%。

## 3. 选型决策树

```
仓库 < ~500 文件？
├─ 是 → 什么都不装（R1：Claude Code/Codex 原生 grep+Read 足够；装索引是纯开销）
└─ 否 → 主要做什么？
   ├─ 理解/问答/影响面分析（读多写少）→ codegraph（大仓库、多语言、混合 iOS/RN 尤佳）
   ├─ 跨文件重构/精确编辑（写多）    → Serena（LSP 后端；预算够上 JetBrains 插件）
   ├─ 只要轻量搜索                    → code-index-mcp 或裸 ripgrep
   ├─ 团队 PR 审查/规范执行           → Greptile（云）；或等 codegraph platform
   └─ IDE 内 @codebase 语义搜索       → Cursor（闭源云）/ Continue（开源本地）
```

**组合模式（2026-08 的实践共识）**：codegraph（看）+ Serena（改）+ 原生 grep（兜底）三者并存并不冲突——MCP 是多服务器协议，dsh 这类 harness 还会用 `mcp__<server>__` 命名空间把它们隔离（见 dsh 案例 03-trust 笔记）。

## 4. 本案例的可迁移结论

1. **上下文层的分工已经清晰**：预付（图）/ 实时（LSP）/ 模糊（向量）/ 蒸馏（地图）四种熵治理策略各有胜场，"谁取代谁"是伪问题。
2. **Agent-first 工具设计**：默认单工具 `codegraph_explore` 优于多窄工具——工具面本身是 prompt 的一部分（引导 agent 行为），这是 MCP 时代的通用教训。
3. **索引的诚实义务**：staleness 横幅 + provenance 标注 + 覆盖率分语言披露——任何"给 agent 供证据"的基础设施都应抄这份作业（详见笔记 02 §5–6）。
4. **基准要先防自欺**：双臂封锁 + 污染计数 + 不利数字同页披露，是所有 AI 工具评测的最低标准。
