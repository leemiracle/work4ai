# 02 — 工具调用工程：Function Calling、工具设计与 MCP

> 「讲透 Agent」第三篇。上一篇对比了三种 Agent 范式（ReAct / Plan-Execute / Reflexion），但有个东西我们一直当作黑盒——**工具**。本篇把"工具"拆透：从 LLM 怎么选工具、到参数怎么传、到工具粒度怎么定、到 2024 年横空出世的 MCP 标准。
>
> 配套实验：`experiments/02_tools.py`。

---

## 1. 灵魂：一句话钉死

> **工具是 LLM 的手脚。工具描述是手脚的"说明书"——说明书写得清楚，LLM 才知道何时伸手、伸哪只手；参数 schema 是手脚的"关节约束"——约束越严，动作越准；工具粒度是手脚的"分工"，分工越细越灵活但协调越复杂；MCP 是手脚的"USB-C 接口"，让任何 LLM 都能即插即用任何工具。**

$$
\underbrace{\text{工具描述}}_{\text{何时用}}\;\times\;
\underbrace{\text{参数 Schema}}_{\text{怎么用}}\;\times\;
\underbrace{\text{工具粒度}}_{\text{拆多细}}\;\times\;
\underbrace{\text{MCP 协议}}_{\text{怎么接}}\;=\;\text{Agent 的能力边界}
$$

**核心论断**：一个 Agent 能力的上限，**不取决于 LLM 多聪明，而取决于工具工程多扎实**。GPT-4 给一堆描述糟糕的工具，照样选不准；GPT-3.5 给设计良好的工具，照样能干活。

## 2. 工具描述：决定 LLM 能不能选对

### 2.1 LLM 是怎么"选工具"的？

Agent 启动时，所有工具的描述会被塞进 system prompt：

```
你可以使用以下工具:
- get_weather(city): 查询指定城市的实时天气情况 温度 湿度 预报
- get_news(topic): 查询最新新闻时事资讯
- calculate(expr): 数学计算加减乘除
- translate(text, to): 文本翻译中英文多语言互译

用户: "北京今天天气怎么样?"
```

LLM 收到用户 query 后，**本质上是在做"语义匹配"**：query 与哪个工具描述语义最近，就选哪个。这和向量检索是同一回事——把 query 和每个工具描述都 embed，余弦相似度最高的胜出。

### 2.2 描述质量直接决定准确率（实验实测）

实验用 14 个 query × 200 次重复，对比三种描述质量：

| 描述质量 | 工具描述 | 选择正确率 | top-1 区分度 |
|---------|---------|:---------:|:----------:|
| **好描述** | keys 完整 + 与功能对齐（如 weather 含"天气/温度/湿度/下雨/预报/气候/晴天/雨天"）| **96.2%** | **1.477** |
| **模糊描述** | keys 只有 1 个核心词（如 weather 只含"天气"）| 46.4% | 0.345 |
| **误导描述** | keys 与功能错位（weather 写 news 的 keys）| **5.7%** | 0.917（区分度高但方向反）|

**结论**：描述质量的差距可达 **90 个百分点**。这不是 LLM 不行，是**工具设计不行**。

### 2.3 工具描述的 5 要素（工程最佳实践）

```python
{
    "name": "get_weather",
    "description": (
        "查询指定城市当前及未来 7 天的实时天气情况。"  # ① 功能: 干什么
        "包括温度、湿度、风力、降水概率、空气质量。"     # ② 覆盖: 包含哪些信息
        "适用于用户问'天气/温度/下雨/穿衣建议'等场景。"   # ③ 何时用: 触发场景
        "不适用于: 历史天气(用 get_weather_history)、"   # ④ 何时不该用
        "全球气候数据(用 get_climate)。"
    ),
    "parameters": {
        "city": {"type": "string", "description": "中国地级市以上城市名, 如'北京'"},
        "date": {"type": "string", "enum": ["今天","明天","后天"], "description": "查询日期"}
    },
    # ⑤ 示例 (放 description 末尾或单独字段):
    "examples": ["北京明天天气", "上海今天下雨吗"]
}
```

**关键原则**：
1. **覆盖广**：把用户可能用的同义词都列出来（天气/温度/湿度/下雨/晴/预报）。
2. **边界清**：明确"不该用这个工具"的场景（避免误选）。
3. **有示例**：1-2 个典型 query 让 LLM 学会模式。
4. **避免歧义**：不要用"信息""数据"这种万能词（容易和别的工具冲突）。
5. **参数描述也算描述**：每个参数都要写清楚类型、枚举、含义。

> ⚠️ **反模式**：很多人写 `description: "查天气"` 就完事。实验证明这种描述下，与"查新闻""查股价"等工具区分度极低，选择正确率从 96% 暴跌到 46%。

## 3. 参数 Schema：从"祈祷 LLM 别拼错"到"语法上不可能错"

### 3.1 自由文本时代的痛

2023 年 6 月之前，让 LLM 调工具基本靠 prompt engineering：

```
你可以调用工具, 输出格式: tool_name(arg1=value1, arg2=value2)
用户: 查北京明天天气
LLM: get_weather(city=北京, date=明天)
```

问题：LLM 经常拼错。实验模拟早期 LLM 的常见错误：

| 错误类型 | 频率 | 例子 |
|---------|:----:|------|
| 漏字段 | 30% | `get_weather(city=北京)` ← 漏了 date |
| 拼错 key | 10% | `get_weather(cit=北京, date=明天)` ← city 拼成 cit |
| 大小写不一致 | 15% | `get_weather(city=北京, Date=明天)` ← Date 不是 date |

**实测**：自由文本方案的"参数完整率"只有 **54.3%**——接近一半的工具调用参数有问题。

### 3.2 Function Calling：JSON Schema 强约束

2023 年 6 月 OpenAI 推出 [Function Calling](https://openai.com/blog/function-calling-and-other-api-updates)，把工具调用变成**结构化输出**：

```python
# 工具定义带 JSON Schema
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "enum": ["北京","上海","广州","深圳","成都"]},
                "date": {"type": "string", "pattern": "^(今天|明天|后天|本周五|\\d+月\\d+日)$"}
            },
            "required": ["city", "date"]   # ← 必填字段
        }
    }
}]

# LLM 直接输出符合 schema 的 JSON
response = openai.chat.completions.create(
    model="gpt-4",
    messages=[...],
    tools=tools
)
# response.tool_calls[0].function.arguments = '{"city": "北京", "date": "明天"}'
```

**实测对比**：

| 方案 | 参数完整率 | schema 合规率 | 可用调用率 |
|------|:--------:|:-----------:|:--------:|
| 自由文本（LLM 拼字符串）| 54.3% | 54.3% | 90.0% |
| **强 JSON Schema（Function Calling）**| **98.7%** | **98.7%** | **98.7%** |

**45 个百分点的提升**。这就是为什么 Function Calling 一出来就成了工业标准。

### 3.3 Schema 的核心要素

```json
{
    "type": "object",
    "properties": {
        "city": {
            "type": "string",
            "enum": ["北京", "上海", "广州"],        // 枚举约束
            "description": "中国地级市以上城市名"
        },
        "date": {
            "type": "string",
            "format": "date",                       // 格式约束
            "description": "YYYY-MM-DD 格式"
        },
        "days": {
            "type": "integer",
            "minimum": 1,                           // 范围约束
            "maximum": 30,
            "default": 1
        }
    },
    "required": ["city"],                            // 必填
    "additionalProperties": false                    // 禁止额外字段
}
```

**Schema 是给 LLM 用的"语法合同"**——只要 LLM 输出符合 schema，就一定可以被程序解析。把"LLM 拼 JSON"从"祈祷它别出错"变成"语法上不可能错"。

> 进阶：**Structured Outputs**（OpenAI 2024.8 推出）进一步保证 100% 符合 schema（旧版 Function Calling 仍有 ~5% 不合规）。

## 4. 工具粒度：粗 vs 细的权衡

### 4.1 同一个任务，两种拆法

任务："查北京和上海的天气，算两地温差"

**粗粒度（1 个工具）**：
```python
def compare_weather(city1: str, city2: str, metric: str = "temp") -> dict:
    """一次性返回两个城市的天气对比"""
    # 内部: get_weather(c1), get_weather(c2), compute_diff
    return {"city1": ..., "city2": ..., "diff": ...}
```

**细粒度（3 个工具）**：
```python
def get_weather(city: str) -> dict: ...
def calculate(expr: str) -> float: ...
# Agent 串: get_weather(北京) → get_weather(上海) → calculate("30-25")
```

### 4.2 实测对比

| 方案 | token/任务 | 单次错误率 | 实测成功率 | 灵活度 |
|------|:--------:|:--------:|:--------:|:----:|
| 粗粒度（1 工具）| 80 | 20.0% | 78.6% | 低 |
| 细粒度（3 工具）| 150 | 14.3% | **86.0%** | 高 |

### 4.3 为什么细粒度反而更准？

**直觉反差**：3 步串联，错误率不该是 $1-(1-0.05)^3 ≈ 14\%$，比 1 步的 20% 还低？

**真相**：粗粒度的"复杂参数"（city1, city2, metric, ...）让 LLM 更容易填错——它要同时处理多个字段，认知负担大。细粒度的每步只 1-2 个简单参数，单步正确率高（95%），即使串联也只 14% 错。

**核心权衡**：
- **细粒度优点**：参数简单 → 单步错误率低；可复用（get_weather 能被无数任务用）；灵活（任意组合）。
- **细粒度缺点**：调用次数多 → token 成本高；累积错误率（5 步以上会反超）。
- **粗粒度优点**：单次调用省 token；参数复杂但任务结构稳定时不易错。
- **粗粒度缺点**：参数多 → 填错率高；不可复用；不能灵活组合。

**工程经验**：
- **默认细粒度**：遵循 Unix 哲学（"做一件事，做好"）。
- **粗粒度的场景**：高频组合操作（如 `read_then_summarize(file)` 比 `read_file` + `summarize` 更省）。
- **粒度上限**：单工具参数 ≤ 3 个，单工具职责 ≤ 1 件事。

## 5. MCP（Model Context Protocol）：工具调用的"USB-C"

### 5.1 痛点：N × M 集成地狱

2024 年之前，每个 Agent 框架都有自己的工具协议：

| Agent 框架 | 工具定义格式 |
|-----------|-------------|
| LangChain | `BaseTool` 类，`_run()` 方法 |
| LlamaIndex | `ToolMetadata` + `FunctionTool` |
| AutoGen | `@user_function` 装饰器 |
| OpenAI Assistants | JSON Schema（API）|
| Claude (Anthropic) | `tool_use` content block |

**问题**：你写了一个 GitHub 工具给 LangChain 用，到 LlamaIndex 要重写；想给 AutoGen 用，再重写一遍。**N 个项目 × M 个工具 = N×M 个集成层**。

### 5.2 MCP 的解决方案：N + M

2024 年 11 月，Anthropic 推出 [Model Context Protocol](https://www.anthropic.com/news/model-context-protocol)（MCP），把工具调用标准化：

```
┌─────────────┐         ┌──────────────┐         ┌──────────────┐
│  MCP Client │ ◄─────► │  MCP Server  │ ◄─────► │  实际工具     │
│ (Claude等)  │  JSON   │  (工具提供方) │  SDK    │  GitHub/DB/  │
│             │  RPC    │              │         │  File/Slack  │
└─────────────┘         └──────────────┘         └──────────────┘
```

- **MCP Server**：工具提供方（如 GitHub、Slack、PostgreSQL）按 MCP 协议暴露工具。
- **MCP Client**：LLM 客户端（Claude Desktop、Cursor、Cline）按 MCP 协议消费工具。
- **协议**：基于 JSON-RPC，支持 tools / resources / prompts 三类能力。

**复杂度对比**（5 个项目 × 3 个工具）：

| 维度 | 私有协议 | MCP 标准化 |
|------|---------|----------|
| 初始集成成本 | 60 人时（5×3×4）| 54 人时（3×8 + 5×6）|
| **加 1 个新工具** | **20 人时**（5 项目 × 4）| **8 人时**（只写 1 个 server）|
| 换工具供应商 | 高（重写）| ~0（改配置）|
| 跨项目复用 | 不可 | 可以 |

> 项目数和工具数多了之后，MCP 的优势会指数级放大：**N × M → N + M**。

### 5.3 MCP 的核心能力

MCP 不只是"工具调用"，它定义了三种能力：

| 能力 | 用途 | 例子 |
|------|------|------|
| **Tools** | LLM 可调用的函数（有副作用）| `git_commit`, `send_email`, `sql_query` |
| **Resources** | LLM 可读取的数据（无副作用）| 文件内容、数据库 schema、配置 |
| **Prompts** | 预定义的提示词模板 | "代码审查 prompt"、"总结 prompt" |

**关键创新**：MCP 让工具从"被 Agent 硬编码调用"变成"被 LLM 动态发现"——LLM 启动时通过 `list_tools` 协议问 MCP Server "你有哪些工具"，再按需调用。这就是为什么 Claude Desktop 用户可以"装个 GitHub MCP 服务器"就让 Claude 突然能操作 GitHub。

### 5.4 一个最小 MCP Server 示例

```python
# Python SDK (pip install mcp)
from mcp.server import Server
from mcp.types import Tool, TextContent

server = Server("my-weather-server")

@server.list_tools()
async def list_tools() -> list[Tool]:
    return [Tool(
        name="get_weather",
        description="查询指定城市的实时天气",
        inputSchema={
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
        }
    )]

@server.call_tool()
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    if name == "get_weather":
        weather = fetch_weather(arguments["city"])
        return [TextContent(type="text", text=f"{arguments['city']}: {weather}℃")]

# 启动: stdio 或 sse 传输
```

写一次，Claude Desktop、Cursor、Cline、Windsurf 任何 MCP Client 都能用。

## 5.5 范式跃迁：从 JSON Tool-Call 到 Code Action（smolagents）

> 上一节 MCP 解决了"工具怎么接"，本节回到更底层的问题：**工具调用的 action 本身该长什么样？** 第 3 节把 Function Calling（LLM 输出 JSON）当成了终极方案——但 2024 年底 HuggingFace 的 [`smolagents`](https://github.com/huggingface/smolagents)（29k★，"Agents that think in code"）用一套反常识设计挑战了这个假设：**让 LLM 直接输出 Python 代码当 action**，实测少 30% 步骤。

### 5.5.1 直觉：JSON 的天花板是"一步一调"

第 3 节的结论是 JSON Schema 把参数完整率从 54% 拉到 99%。但 JSON tool-call 有个**结构性天花板**——**一个 action 只能调一个工具**。

任务："查北京、上海、广州三地天气，找最热的"

| 范式 | Action 形态 | 需要几步 | LLM 调用次数 |
|---|---|:---:|:---:|
| **JSON Tool-Call**（第 3 节）| `get_weather(city="北京")` | **4 步**（查×3 + 比较×1）| 4 次 |
| **Code Action**（smolagents）| 一段 Python | **1 步** | 1 次 |

Code Action 那一步，LLM 直接输出：

```python
cities = ["北京", "上海", "广州"]
results = {c: get_weather(c)["temp"] for c in cities}
hottest = max(results, key=results.get)
final_answer(f"最热的是{hottest}，{results[hottest]}℃")
```

一个 action 内部就完成了"3 次调用 + 比较 + 收尾"。**代码 = 图灵完备的 action 空间**，而 JSON 只能表达"单次函数调用"。

### 5.5.2 机制：CodeAgent 还是 ReAct，只是换了 action 语法

smolagents 的 [`CodeAgent`](https://huggingface.co/docs/smolagents) **本质上仍是上一篇讲的 ReAct 循环**——记忆 → 生成 → 执行 → 判停。唯一区别：**生成的不是 tool-call JSON，而是 Python 代码片段**。

```
┌──────────────────────────────────────────────────────────┐
│  ReAct 循环（smolagents CodeAgent）                       │
│                                                           │
│  Memory(chat messages) ──► LLM 生成                       │
│                              │                            │
│                              ▼                            │
│                     解析出 Python 代码块                   │
│                              │                            │
│                              ▼                            │
│                     在沙箱里 exec 代码                     │
│                     （工具 = 代码里的函数）                │
│                              │                            │
│              ┌───────────────┴───────────────┐            │
│              ▼                               ▼            │
│      没调 final_answer               调了 final_answer     │
│      → 日志塞回 Memory              → 返回参数作为答案      │
│      → 继续循环                                            │
└──────────────────────────────────────────────────────────┘
```

**工具怎么变成代码里的函数？** smolagents 在 system prompt 里声明每个工具是一个 Python 函数签名，再把工具对象注入代码执行的命名空间。LLM 写 `web_search("...")`，执行时这个名字就绑定到你传给 `CodeAgent(tools=[...])` 的那个工具对象。

### 5.5.3 证据：为什么代码 action 反而更准更强

直觉上"让 LLM 写代码"听起来更难更易错。但 HuggingFace 两篇论文给出反直觉结论：

| 指标 | JSON Tool-Call | Code Action | 来源 |
|---|:---:|:---:|---|
| **完成任务步数** | 基线 | **少 ~30%** | [arXiv 2402.01030](https://huggingface.co/papers/2402.01030) |
| **困难 benchmark 通过率** | 基线 | **更高** | [arXiv 2411.01747](https://huggingface.co/papers/2411.01747) |

**为什么代码反而更好？三个机制**：

1. **组合性降步数**：一个 action 能写循环/条件/中间变量，把"3 次串行调用"压成 1 步。步数少 → LLM 调用少 → 既省钱又减少多步累积错误。
2. **错误信号更丰富**：JSON 不合规只有"schema 报错"一个信号；代码报错有 traceback（NameError/TypeError/逻辑错），塞回 memory 后 LLM 能精准修——相当于**免费的自我调试**。
3. **表达力天花板更高**：JSON 永远只能"调一个现成工具"；代码能"现场组合工具 + 写临时逻辑"。遇到工具没覆盖的边角，代码 action 能临时算，JSON 不能。

> ⚠️ **代价 1 · 安全**：Code Action = **任意代码执行**。smolagents 明确警告内置 `LocalPythonExecutor` **不是安全沙箱**，生产必须用 E2B / Blaxel / Modal / Docker 隔离。这是 Code Action 相比 JSON 的最大代价。
>
> ⚠️ **代价 2 · 解析鲁棒性**：要 LLM 稳定输出"可运行代码"而非"伪代码"，对模型代码能力要求更高——这也是为什么 smolagents 的 benchmark 里 **DeepSeek-R1 这类强代码模型当 code agent 表现最好**（开源反超闭源）。

### 5.5.4 最小代码：CodeAgent vs ToolCallingAgent

smolagents 同一库提供两种 Agent，一行切换：

```python
# pip install "smolagents[toolkit]"
from smolagents import CodeAgent, ToolCallingAgent, WebSearchTool, InferenceClientModel

model = InferenceClientModel()  # 任意 LLM：HF Inference / LiteLLM / OpenAI / 本地 transformers

# ① Code Agent —— action 是 Python 代码（本节主角）
code_agent = CodeAgent(tools=[WebSearchTool()], model=model)
code_agent.run("对比 leopard 全速跑过 Pont des Arts 和 Brooklyn Bridge 各需几秒")

# ② Tool Calling Agent —— action 是 JSON（第 3 节的经典范式）
json_agent = ToolCallingAgent(tools=[WebSearchTool()], model=model)
json_agent.run("同上任务")
```

同一个任务，CodeAgent 通常 1-2 步收尾（代码里 for 循环算两座桥），ToolCallingAgent 要 4+ 步（每座桥一轮 ReAct）。**这就是 30% 步数差异的来源**。smolagents 还支持 `agent.push_to_hub()` / `from_hub()` 把整个 Agent 分享到 Hub。

### 5.5.5 何时选 Code Agent，何时选 JSON？

| 场景 | 推荐 | 理由 |
|---|---|---|
| 多步骤组合任务（查×N + 算 + 比）| **CodeAgent** | 代码组合性压步数 |
| 单工具简单调用（查个天气）| ToolCallingAgent | JSON 够用，且无需沙箱 |
| 有不可信输入 / 对抗环境 | ToolCallingAgent | Code Action 安全代价高 |
| 需要可审计的逐步日志 | ToolCallingAgent | JSON 每步语义清晰 |
| 强代码模型（R1 / Claude / GPT-5）| **CodeAgent** | 代码生成质量有保障 |
| 弱模型 / 小模型 | ToolCallingAgent | JSON schema 约束更宽容 |

**关键认知**：Code Action 不是"取代"Function Calling，而是**给 action 空间开了第二条路**。smolagents 把两种 Agent 并列提供，正说明各有适用场景。这条认知也是 [`讲透Agent`](./) 后面"规划与搜索"篇的伏笔——**当代码成为 action，Agent 的"规划"就可以直接写进代码的控制流**，而不必再外挂一个 planner。

## 6. 横评表：工具工程的五个维度

| 维度 | 错误做法 | 正确做法 | 实测差距 |
|------|---------|---------|:-------:|
| **工具描述** | "查天气" | 含功能+覆盖+边界+示例 | 96% vs 46% |
| **参数 Schema** | LLM 自由拼字符串 | Function Calling JSON Schema | 99% vs 54% |
| **工具粒度** | 一个工具干 N 件事 | 单一职责，参数 ≤3 | 86% vs 79% |
| **集成协议** | 每个项目硬编码 SDK | MCP server 标准化 | N+M vs N×M |
| **Action 形态** | 永远 JSON 一步一调 | 复杂任务用 Code Action | 少 30% 步（[2402.01030](https://huggingface.co/papers/2402.01030)）|

---

## 7. 一句话总结

> **工具是 LLM 的手脚。工具描述决定 LLM 能否选对（好 vs 模糊 vs 误导：96% / 46% / 6%）；参数 Schema 决定能否传对（自由文本 54% vs 强 Schema 99%）；工具粒度决定复用与组合（细粒度省错误率，粗粒度省 token）；MCP 决定能否跨框架复用（N×M → N+M）。Agent 的能力上限不取决于 LLM 多聪明，而取决于工具工程多扎实——这是工程师真正能发力的地方；而 action 形态（JSON 一步一调 vs 代码组合，[smolagents](https://github.com/huggingface/smolagents) CodeAgent 实测少 30% 步）是 2024 年底才被打开的第五个维度。**

## ✍️ 练习（`02_tools.py`）

1. **写描述**：给"GitHub 工具"写三种描述（好/模糊/误导），跑实验看选择正确率差距。
2. **加约束**：把 `get_weather` 的 city 参数从 `string` 改成 `enum: ["北京","上海",...]`，看 LLM 是否还会输出"Beijing"（英文）。
3. **粒度扫描**：把"细粒度工具数"从 1 扫到 10，画出"工具数 vs 累积错误率"曲线，验证"5 步以上反超"经验。
4. **接 MCP**：跑一个真实的 MCP server（如官方的 `mcp-server-filesystem`），让 Claude Desktop 调用它，看协议如何工作。
5. **造冲突**：在工具集里加两个 keys 高度重叠的工具（如 "get_weather" 和 "get_weather_v2"），看 LLM 会不会选错。这就是为什么工具不能"功能重叠"。
6. **范式对比**（§5.5）：装 `smolagents`，用同一强模型（如 DeepSeek-R1 via `InferenceClientModel`）分别跑 `CodeAgent` 和 `ToolCallingAgent` 解"查 3 个城市天气找最热"，记录各自步数与 LLM 调用次数，验证 §5.5.3 的"少 30% 步"结论。⚠️ CodeAgent 必须配 Docker/E2B 沙箱，别用 `LocalPythonExecutor` 跑不可信任务。
