# 06 · 编译与图模式：torch.compile 到底做了什么

> 这章是用户反复点名的核心。`torch.compile` 是 PyTorch 2.0 起的标志性特性，但它**很挑场景**——实验05 在 CPU 小模型上跑出 **0.72×（负收益）**，实验07 用 profiler 揭示了它真正的价值（算子融合）。讲透它，先要理解 PyTorch 的根本特性：**动态图**。

---

## 一、动态图 vs 静态图：PyTorch 的根本特性

### 1.1 Eager（动态图，define-by-run）—— PyTorch 的默认

每次 `forward` 就是普通 Python 执行：**边跑边建计算图**，跑完就扔。

- **优点**：易调试（可断点、可 print、可任意 if/for 控制流）。这是 PyTorch 当年战胜 TF1 的关键。
- **缺点**：每次前向都有 **Python 解释器开销**；且因为图是动态的，**编译器无法做全局优化**（融合、常量折叠）。

### 1.2 静态图（如 TF1 / JAX）

先定义完整图，再执行。

- **优点**：编译器能看全图，做激进优化。
- **缺点**：难调试，控制流受限（要写 `tf.cond` 这种）。

### 1.3 torch.compile 的精妙折中

**保持 eager 的易用性，但在"一段计算"上抓取静态图并编译**：

```
首次调用 model(x):
  → Dynamo 用 sys.settrace 跟踪 Python 字节码, 抓成 FX 静态图
  → 交给后端编译成优化代码
  → 缓存: 后续同形状输入直接走编译后的代码
```

> 🎯 本质 = **动态图的易用 + 静态图的性能**。这是 2.x 的核心叙事。

---

## 二、三段流水线（compile 的内部架构）

```mermaid
graph LR
    A[Python 代码<br/>model(x)] -->|Dynamo<br/>字节码跟踪| B[FX Graph<br/>静态图]
    B -->|AOTAutograd<br/>融合前向+反向| C[优化后的图]
    C -->|Inductor<br/>代码生成| D[Triton kernel<br/>(GPU) / C++/OpenMP (CPU)]
```

| 阶段 | 职责 | 技术 |
|------|------|------|
| **TorchDynamo** | 把 Python 字节码抓成静态 FX 图 | `sys.settrace` |
| **AOTAutograd** | 把前向图 + 反向图一起优化（融合）| 前向+反向联合优化 |
| **TorchInductor** | 生成后端代码 | GPU→**Triton**，CPU→C++/OpenMP |

> Inductor 生成的 Triton kernel 会做**算子融合**——这是性能的核心来源。

---

## 三、算子融合：性能的真正来源

### 3.1 融合的本质 = 减少内存读写

```python
# eager: 每个算子各跑一个 kernel, 中间结果写回显存
y = relu(x);  z = y * 2;  out = z + 1
# 3 个 kernel, 3 次读 + 3 次写 HBM

# fused: 编译器把三者合成一个 kernel, 中间结果留在寄存器
out = (relu(x) * 2) + 1   # 1 个 kernel, 1 次读 + 1 次写
```

GPU 上 **HBM 带宽**（A100 ~2TB/s）远低于算力，所以**减访存 = 加速**。融合让中间结果不落 HBM。

### 3.2 实验07 的 profiler 实证

```
eager:    算子调用 120 次 (一堆细碎算子: addmm/relu/dropout/mul...)
compiled: 算子调用 85 次  (融合后, 细碎算子合并)
```

> 即使 CPU 上 wall-clock 反而变慢（实验05 的 0.72×），**算子融合这件事确实发生了**（120→85）。CPU 上收益不明显是因为 CPU 计算本身就慢、访存占比小；GPU 上同样的融合能带来 1.5–3×。

---

## 四、compile 何时"灵" vs 何时"坑"（最重要）

### ✅ 真香场景

- **GPU + 中大模型 + 固定 shape**：算子融合大幅减访存，常见 1.5–3×。
- **训练**：AOTAutograd 把前向+反向整图优化，收益比纯推理更大。
- **重复模块**（如 Transformer 层）：regional compile（2.5）只编译一次，减冷启动。

### ⚠️ 翻车场景（实验05 就是这个）

- **CPU + 小模型**：融合省的访存 < Python 抓图开销，**负收益（0.72×）**。
- **数据依赖的 shape 变化**（变长序列、每步不同形状）：触发 **recompile**，越编越慢。
- **频繁调用的小函数**：抓图开销 > 融合收益。
- **动态控制流**：数据依赖的 if/for 导致 **graph break**（图被打断，退回 eager）。

> 🎯 **判断口诀**：GPU 大模型固定 shape 用 compile；CPU 小模型或动态 shape 慎用。

## 五、其他编译相关特性（2.x 演进）

| 特性 | 版本 | 作用 |
|------|------|------|
| **regional compile** | 2.5 | 重复模块只编译一次，减冷启动 |
| **combo-kernels** | 2.10 | 水平融合：无依赖的并行算子合成单 kernel，减 launch 开销 |
| **Compiled Autograd** | 2.5 prototype | 把**反向传播**也编译（不只前向），训练加速 |
| **CUDA Graphs 集成** | — | compile 可捕获成 CUDA Graph，消除 kernel launch 开销 |
| **max-autotune** | — | 编译时自动调优（选最快 kernel 实现）|

## 六、与 export / AOTInductor 的关系（部署侧）

`torch.compile` 是**即时编译（JIT）**：运行时抓图、编译、缓存。
`torch.export + AOTInductor` 是**提前编译（AOT）**：部署前编译成 `.so`，运行时无编译开销。

> 详见 [08-现代PyTorch](08-现代PyTorch(2.x特性).md) 的 export/AOTInductor 部分。两者同属 PyTorch 2.x 编译栈，JIT 用于训练加速，AOT 用于部署。

## 八、批判性视角

- **compile 不是银弹**。它有冷启动开销、recompile 风险、调试更难（报错指向生成的代码）。**先让 eager 跑通，再考虑 compile**。
- **Triton 依赖 GPU**。CPU 上 Inductor 用 C++/OpenMP 后端，融合收益有限（实验05 印证）。
- **动态 shape 是永恒痛点**。LLM 的变长序列是 compile 的天敌，需要 padding/grouping 或专门的 varlen kernel（2.10 的 `varlen_attn`）。
- **版本碎片化**。Dynamo/Inductor API 在 2.x 里变动频繁，生产代码要锁版本。
