# 04 · 数据管道：Dataset / DataLoader 的设计与陷阱

> 模型再好，喂数据不对也白搭。数据管道是训练的"血液系统"。PyTorch 的 `Dataset` + `DataLoader` 设计看似简单（两行 API），但**内部机制**决定了训练速度和正确性。本篇讲透"为什么这样设计"，不只是"怎么调"。

---

## 一、Dataset 的设计哲学：为什么是这两个方法

```python
class MyDataset(Dataset):
    def __len__(self): return self.n
    def __getitem__(self, i): return self.x[i], self.y[i]
```

**为什么只要实现 `__len__` 和 `__getitem__`？**

### 1.1 这是"迭代器协议"的最小契约

Python 的索引协议要求 `__getitem__`，长度协议要求 `__len__`。PyTorch 只要求这两个，意味着：
- **随机访问**：DataLoader 可以任意顺序取数据（shuffle）
- **可并行**：多个 worker 各自取不同索引，无冲突
- **懒加载**：`__getitem__` 里才真正读文件/解码图片——不必一次性载入内存

### 1.2 为什么不返回 batch？

因为 **batch 是 DataLoader 的职责**，不是 Dataset 的。关注点分离：
- Dataset：怎么取**一条**
- DataLoader：怎么把多条**拼成 batch** + 打乱 + 并行

### 1.3 常见陷阱

```python
# ❌ 陷阱：在 __getitem__ 里打开文件
def __getitem__(self, i):
    f = open(self.paths[i])  # 每个 worker 每次都打开 → 慢
    return f.read()

# ✅ 正确：缓存文件句柄或用内存映射
def __init__(self):
    self.data = np.load("big.npz")  # 一次加载，worker 继承
```

## 二、DataLoader 内部机制：不只是"拼批"

```python
dl = DataLoader(ds, batch_size=32, shuffle=True, num_workers=4,
                pin_memory=True, drop_last=True)
```

每个参数背后都有工程考量：

### 2.1 `num_workers`：多进程加载

- `num_workers=0`：主进程加载（简单但慢，GPU 等 CPU）
- `num_workers>0`：开 N 个子进程并行加载

**fork vs spawn（跨平台坑）**：
- Linux 默认 `fork`：子进程继承父进程内存（快，但 CUDA 上下文 fork 会崩）
- Windows/Mac 默认 `spawn`：重新启动 Python 解释器（慢，需 `if __name__=='__main__'` 保护）

**经验**：`num_workers` 不是越大越好——每个 worker 占内存（复制数据集），且 fork 有开销。经验值 `4-8`。

### 2.2 `pin_memory`：为什么加速 CPU→GPU 传输

普通 CPU 内存是**可换页的**（操作系统可把它换到磁盘）。CUDA 的 `cudaMemcpyAsync` 要求**锁页内存**（pinned/page-locked）才能异步 DMA 传输。

- `pin_memory=True`：DataLoader 把 batch 放进锁页内存 → `.to(cuda)` 用异步传输 → 快
- 代价：锁页内存不能换页，占用物理 RAM

### 2.3 `prefetch_factor`：预取

`num_workers>0` 时，每个 worker 预取 `prefetch_factor`（默认 2）个 batch。**流水线化**：GPU 训练当前 batch 时，CPU 已在准备下一个。

### 2.4 `drop_last`：形状一致性

最后一个 batch 可能不满（如 1000 样本，batch=32 → 最后只有 8 个）。`drop_last=True` 丢弃它——保证所有 batch 形状一致，利于 `torch.compile`/算子优化。

## 三、collate_fn：变长数据的拼批（NLP 必备）

默认 `collate_fn` 做 `torch.stack`——要求所有样本形状一致。但 NLP 的句子长度不一，需要自定义：

```python
def collate_fn(batch):
    # batch = [(tensor[len_i], label_i), ...]
    texts, labels = zip(*batch)
    lengths = torch.tensor([len(t) for t in texts])
    padded = pad_sequence(texts, batch_first=True)  # padding 到最长
    return padded, lengths, torch.tensor(labels)
```

**图/点云**等不规则数据同理：collate_fn 把异构样本打包成可批处理的结构。

## 四、Sampler：控制采样顺序

| Sampler | 用途 |
|---|---|
| `RandomSampler` | 训练（每个 epoch 打乱）|
| `SequentialSampler` | 验证/测试（固定顺序）|
| `WeightedRandomSampler` | **类别不均衡救星**：给少数类更高权重 |
| `BatchSampler` | 控制 batch 级采样（如 GroupBatchSampler 按尺寸分桶）|

### WeightedRandomSampler 示例

```python
# 类别 9:1 不均衡
class_counts = torch.tensor([900, 100])
weights = 1.0 / class_counts
sample_weights = weights[labels]  # 每个样本的权重
sampler = WeightedRandomSampler(sample_weights, len(sample_weights))
dl = DataLoader(ds, batch_size=32, sampler=sampler)  # 注意：用 sampler 时 shuffle 必须不设
```

这比过采样（复制少数类样本）更高效——不增加数据量，只调采样概率。

## 五、工程坑总结

1. **worker 太多反而慢**：fork 开销 + 内存复制 > 并行收益（小数据集尤其）
2. **数据在 worker 间复制**：大数据放共享内存（`torch.utils.data.DataLoader` 的 `persistent_workers` 可减少 fork 开销）
3. **CUDA DataLoader**（2024 新）：把数据加载直接放 GPU，省 CPU→GPU 传输（H100 上有效）
4. **IterableDataset**：流式数据（如 webdataset）无法随机访问，用 `IterableDataset` 替代

---

## 六、批判性

- **DataLoader 的多进程是"经典 Python"**：fork + pickle 传数据，2024 后的异步 I/O + GPU 直接加载在挑战这个范式
- **shuffle=True 不保证均匀**：大 batch 时，某些类别可能整 epoch 都没采到（用 WeightedRandomSampler）
- **数据管道常是瓶颈但被忽略**：大家盯着 GPU 利用率，忘了 GPU 闲着可能是因为 DataLoader 喂不饱
