## Purpose and Scope

This document describes vLLM's KV cache management system and its prefix caching implementation (Automatic Prefix Caching - APC). The KV cache manager handles memory allocation for key-value tensors during inference, enabling efficient reuse of cached computations across requests with common token sequences.

**Scope:**

  * Block-based memory allocation and management via `KVCacheManager`, `KVCacheCoordinator`, and `BlockPool`.
  * Prefix caching mechanism for deduplicating computations using `BlockHash`.
  * Block allocation strategies for various attention types (Full, Sliding Window, MLA, Mamba).
  * Integration with the scheduler for memory-aware request scheduling.
  * Integration with GPU execution via `InputBatch` and `KVBlockZeroer`.
  * External KV offloading and transfer coordination via `KVConnector`.

**Related Pages:**

  * For scheduler integration and request management, see [Scheduler and Resource Allocation](/vllm-project/vllm/3.3-scheduler-and-resource-allocation).
  * For GPU execution and model runner details, see [GPUModelRunner](/vllm-project/vllm/4.1-gpumodelrunner).
  * For distributed KV cache transfer, see [KV Cache Transfer and Disaggregated Serving](/vllm-project/vllm/9.4-kv-cache-transfer-and-disaggregated-serving).

## Core Concepts

### Blocks and Block Size

The KV cache is organized into fixed-size **blocks** , where each block stores KV tensors for a fixed number of tokens (typically 16). This block-based approach enables:

  1. **Efficient memory management** : Allocate and free memory in block-sized chunks.
  2. **Prefix caching** : Share blocks across requests with common token prefixes.
  3. **Memory fragmentation control** : Fixed-size allocations reduce fragmentation.

A block stores KV tensors for `block_size` tokens. The `KVCacheConfig` defines the `block_size` and physical cache layout [vllm/v1/kv_cache_interface.py149-150](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/kv_cache_interface.py#L149-L150)

  * Metadata for each block is tracked in `KVCacheBlock`, which stores the `block_id`, `ref_cnt`, and `_block_hash` [vllm/v1/core/kv_cache_utils.py162-174](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L162-L174)
  * Blocks are tracked in a `BlockPool` which maintains a mapping from `BlockHash` to `KVCacheBlock` [vllm/v1/core/block_pool.py30-45](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/block_pool.py#L30-L45)

Sources: [vllm/v1/kv_cache_interface.py143-172](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/kv_cache_interface.py#L143-L172) [vllm/v1/core/kv_cache_utils.py162-183](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L162-L183)

### Prefix Caching Overview

**Prefix caching** (APC) allows vLLM to reuse KV cache blocks across requests that share common token sequences. When a new request arrives, the system:

  1. Computes block hashes for full blocks in the request's token sequence via the request's `block_hasher` [vllm/v1/request.py105-115](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L105-L115)
  2. Looks up these hashes in the prefix cache via `BlockPool` [vllm/v1/core/block_pool.py102-120](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/block_pool.py#L102-L120)
  3. Reuses cached blocks for matching prefixes, incrementing their `ref_cnt`.
  4. Only computes new tokens that aren't cached.

Sources: [vllm/v1/core/kv_cache_manager.py143-166](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_manager.py#L143-L166) [vllm/v1/request.py105-115](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L105-L115) [tests/v1/core/test_prefix_caching.py230-250](https://github.com/vllm-project/vllm/blob/185cada3/tests/v1/core/test_prefix_caching.py#L230-L250)

### Block Hashing

Each full block is identified by a `BlockHash` (a `NewType` for bytes) [vllm/v1/core/kv_cache_utils.py47](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L47-L47)

  * **Hash Chain** : Each block hash depends on the tokens within the block and the hash of the preceding block.
  * **Extra Keys** : The hash includes `cache_salt`, LoRA information, and multimodal identifiers [vllm/v1/request.py105-115](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L105-L115)
  * **Reproducibility** : vLLM uses CBOR-based hashing (e.g., `sha256_cbor`) to ensure hashes are stable across different environments [vllm/v1/core/kv_cache_utils.py92-101](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L92-L101)

`init_none_hash` initializes the base seed (`NONE_HASH`) for the first block of any sequence [vllm/v1/core/kv_cache_utils.py146-158](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L146-L158)

### Block Eviction and LRU Policy

Blocks are evicted in LRU order when the free queue is exhausted. The `FreeKVCacheBlockQueue` maintains this using a doubly linked list [vllm/v1/core/kv_cache_utils.py230-237](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L230-L237)

  1. **Eviction Order** : The front of the queue is the least recently used.
  2. **Reference Counting** : Blocks are only added to the free queue when `ref_cnt` reaches 0 [vllm/v1/core/kv_cache_utils.py168-169](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L168-L169)
  3. **Efficiency** : `FreeKVCacheBlockQueue` supports O(1) removal of blocks in the middle of the queue by manipulating `prev_free_block` and `next_free_block` pointers [vllm/v1/core/kv_cache_utils.py230-237](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L230-L237)

Sources: [vllm/v1/core/kv_cache_utils.py230-264](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L230-L264) [vllm/v1/core/block_pool.py30-45](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/block_pool.py#L30-L45)

### KV Block Zeroing

To ensure correctness, newly allocated blocks are zeroed before use. This is managed by the `KVBlockZeroer` which uses a specialized Triton kernel to clear memory across multiple layers and segments in a single launch [vllm/v1/worker/utils.py102-108](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/utils.py#L102-L108)

  * **Efficiency** : Precomputes absolute byte addresses for all KV cache segments to avoid overhead during the forward pass [vllm/v1/worker/utils.py118-121](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/utils.py#L118-L121)
  * **Granularity** : Handles virtual block splitting where logical block sizes differ from kernel block sizes [vllm/v1/worker/utils.py129-132](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/utils.py#L129-L132)

### External Cache and Offloading

The `OffloadingConnectorScheduler` coordinates KV cache transfers between GPU memory and external storage (e.g., CPU memory or remote nodes) [vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py32-33](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py#L32-L33)

  * **Sliding Window Awareness** : Skips storing chunks that can never serve a load hit due to sliding window constraints [vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py129-134](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py#L129-L134)
  * **Mamba Alignment** : Enforces hit window alignment for Mamba layers in "align" or "all" cache modes [vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py149-158](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py#L149-L158)
  * **Partial Tail Hand-off** : Supports offloading partial blocks (tails) to external storage, ensuring high cache hit rates even for incomplete blocks [vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py178](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py#L178-L178)
