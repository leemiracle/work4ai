This document describes how requests flow through vLLM's V1 engine, the states they transition through, and how their progress is tracked. It covers the `Request` object lifecycle from creation to completion, state transitions managed by the scheduler, and the mechanisms for tracking request progress and outputs.

## Purpose and Scope

This page documents:

  * The `Request` class and its role in tracking request state.
  * Request status states and state transition logic.
  * Request lifecycle from submission through completion.
  * How the scheduler manages request queues and state.
  * Request metadata tracking (tokens computed, outputs generated, etc.).
  * Special request states (preemption, streaming, remote KV loading).

## Request Object Structure

The `Request` class serves as the central data structure tracking all state for a single inference request throughout its lifecycle. In the V1 architecture, `EngineCoreRequest` acts as the serializable DTO (Data Transfer Object) sent between the frontend and the `EngineCore` process, which is then expanded into a full `Request` object for internal tracking.

### Status Descriptions

  * **`WAITING`** : Request is in the `waiting` queue and eligible for scheduling [vllm/v1/request.py97](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L97-L97)
  * **`WAITING_FOR_STREAMING_REQ`** : A resumable request (multi-turn streaming) that has exhausted current input and is waiting for more data via `StreamingUpdate` [vllm/v1/request.py33-41](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L33-L41)
  * **`WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR`** : A request with structured output (JSON/Regex) waiting for the `StructuredOutputManager` to compile the grammar [vllm/v1/request.py114](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L114-L114)
  * **`WAITING_FOR_REMOTE_KVS`** : Request is waiting for its KV cache blocks to be loaded from a remote KV store via a `KVConnector` [vllm/v1/request.py102](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L102-L102)
  * **`PREEMPTED`** : Request was previously `RUNNING` but was evicted from the GPU to free KV cache blocks [vllm/v1/core/sched/scheduler.py159-160](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L159-L160)
  * **`RUNNING`** : Request is actively being processed in the current model execution step [vllm/v1/request.py127](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L127-L127)

## Scheduler State Management

### Request Queues

The `Scheduler` manages the lifecycle by organizing requests into queues:

  1. **Waiting Queue** : Contains all requests that have not yet started or have been preempted. It uses a `RequestQueue` which implements scheduling policies like FCFS [vllm/v1/core/sched/scheduler.py49-53](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L49-L53)
  2. **Running Queue** : Contains requests currently being executed in the model runner. These are requests that have passed the scheduler's resource checks (KV cache availability and token budgets) [vllm/v1/core/sched/scheduler.py114-115](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L114-L115)

### Scheduling Cycle

The `EngineCore` invokes the scheduler every iteration:

  * **`schedule()`** : The scheduler selects a batch of requests to run, allocating KV cache blocks via the `KVCacheManager` and checking `MultiModalBudget` if applicable [vllm/v1/core/sched/scheduler.py38](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L38-L38) This method returns a `SchedulerOutput` object containing `NewRequestData` and `CachedRequestData` [vllm/v1/core/sched/output.py42-48](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/output.py#L42-L48)
  * **`update_from_output()`** : After model execution, the scheduler updates the `num_computed_tokens`, appends new token IDs, and checks for finish conditions (e.g., EOS or length limits) [vllm/v1/core/sched/scheduler.py196-197](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L196-L197) It also processes `KVConnectorOutput` for disaggregated KV cache management [vllm/v1/outputs.py180](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/outputs.py#L180-L180)

**Sources:** [vllm/v1/core/sched/scheduler.py73-170](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L73-L170) [vllm/v1/core/sched/output.py42-48](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/output.py#L42-L48) [vllm/v1/outputs.py180](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/outputs.py#L180-L180)

## Output Processing and Metrics

The `OutputProcessor` manages the final stages of the request lifecycle in the frontend process.

### OutputProcessor

Located in `vllm/v1/engine/output_processor.py`, it handles:

  * **Detokenization** : Converting `new_token_ids` back to text using the tokenizer [vllm/v1/engine/output_processor.py141-142](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/output_processor.py#L141-L142)

## Special Request States

### Resumable Streaming

Requests can be marked as `resumable=True`. If a resumable request exhausts its current input, it can be updated via `StreamingUpdate` which contains lightweight fields for session continuation [vllm/v1/request.py33-46](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L33-L46)

### Structured Output Compilation

When a request includes structured output params, the status is initially set to `WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR` while the `StructuredOutputManager` handles the grammar state [vllm/v1/request.py113-114](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L113-L114) [vllm/v1/structured_output.py67](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/structured_output.py#L67-L67)

### Preemption and Async Scheduling

In async scheduling, `num_in_flight_tokens` tracks tokens of steps whose output is not yet processed [vllm/v1/request.py162](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L162-L162) If a request is preempted, the scheduler manages the resource release and re-queuing [vllm/v1/core/sched/scheduler.py159-160](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L159-L160)

### Remote KV Cache Loading

When disaggregated serving is enabled, a request enters the `WAITING_FOR_REMOTE_KVS` state if its KV cache blocks need to be loaded from a remote store via a `KVConnector` [vllm/v1/request.py102](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L102-L102) The scheduler uses `requires_kv_delivery` to manage these transfers [vllm/v1/core/sched/scheduler.py143](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L143-L143)
