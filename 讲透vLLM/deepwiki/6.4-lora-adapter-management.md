This page documents how to load, manage, and use LoRA adapters in vLLM through both static configuration and dynamic API endpoints. It covers the `LoRARequest` structure, the adapter lifecycle from loading to usage, and the specialized kernel implementations for dense and MoE layers.

* * *

## Overview

vLLM supports **multi-LoRA serving** : a single server can serve requests using different LoRA adapters simultaneously, all sharing the same base model. Adapters can be:

  1. **Statically loaded** at server startup via `--lora-modules`.
  2. **Dynamically loaded/unloaded** at runtime via HTTP endpoints when `VLLM_ALLOW_RUNTIME_LORA_UPDATING=True`.

Each adapter is identified by a unique name and integer ID. When a generation request includes a `LoRARequest` [vllm/lora/request.py11-30](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/request.py#L11-L30) vLLM applies that adapter's weights to the base model for that specific request using specialized kernels like Punica or Triton-based LoRA ops [vllm/lora/punica_wrapper/punica_gpu.py33-38](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/punica_wrapper/punica_gpu.py#L33-L38)

## LoRARequest Structure

The `LoRARequest` class represents a single LoRA adapter and is used both for static configuration and runtime API requests [vllm/lora/request.py11-30](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/request.py#L11-L30)

Field| Type| Required| Description  
---|---|---|---  
`lora_name`| `str`| Yes| Human-readable name for the adapter  
`lora_int_id`| `int`| Yes| Globally unique integer ID (must be > 0)  
`lora_path`| `str`| Yes| Local path or HuggingFace repo ID  
`base_model_name`| `str| None`| No  
`tensorizer_config_dict`| `dict| None`| No  
  
**Key behaviors:**

  * **Unique ID requirement** : The `lora_int_id` must be a positive integer [vllm/lora/request.py32-37](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/request.py#L32-L37) This ID is used internally to track and route adapter weights in the GPU memory slots [vllm/lora/model_manager.py113](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/model_manager.py#L113-L113)
  * **Path resolution** : The `lora_path` can be a local filesystem path or a HuggingFace Hub repository ID. Resolution is handled by `get_adapter_absolute_path` [vllm/lora/worker_manager.py119](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/worker_manager.py#L119-L119)
  * **Equality** : Two `LoRARequest` instances are considered equal if they have the same `lora_name` [vllm/lora/request.py53-57](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/request.py#L53-L57)

## Implementation Details: LoRAModelManager

The `LoRAModelManager` [vllm/lora/model_manager.py71-153](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/model_manager.py#L71-L153) is the central entity in the engine core responsible for the adapter lifecycle.

### Adapter Lifecycle Stages

  1. **Initialization** : `_create_lora_modules()` scans the model for supported layers and replaces them with LoRA-capable versions via `from_layer()` [vllm/lora/model_manager.py148](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/model_manager.py#L148-L148) [vllm/lora/utils.py107-125](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/utils.py#L107-L125)
  2. **Weight Loading** : `WorkerLoRAManager` uses `LoRAModel.from_local_checkpoint()` to load weights from disk into CPU memory [vllm/lora/worker_manager.py142-154](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/worker_manager.py#L142-L154)
  3. **Registration** : Loaded weights are registered with the manager, which assigns them to a physical slot in the GPU-side LoRA weight buffers [vllm/lora/model_manager.py106-114](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/model_manager.py#L106-L114)
  4. **Eviction** : If the number of adapters exceeds capacity, `AdapterLRUCache` triggers a `deactivate_fn` to offload the least recently used adapter [vllm/lora/model_manager.py60-68](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/model_manager.py#L60-L68)

### MoE LoRA Support

For Mixture-of-Experts (MoE) models, `FusedMoEWithLoRA` [vllm/lora/layers/fused_moe.py29-87](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/layers/fused_moe.py#L29-L87) is used. It manages LoRA weights for fused projections.

The `FusedMoEWithLoRA` layer handles the interaction between MoE routing and LoRA kernels. It initializes stacked weights for experts [vllm/lora/layers/fused_moe.py162-180](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/layers/fused_moe.py#L162-L180) and creates a `MoELoRAContext` to pass to the underlying modular kernels [vllm/lora/layers/fused_moe.py126-150](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/layers/fused_moe.py#L126-L150) This allows Triton kernels to perform fused expert and LoRA computations. For unquantized MoE, it typically selects a Triton backend automatically when LoRA is enabled [vllm/lora/layers/fused_moe.py77-83](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/layers/fused_moe.py#L77-L83)

The implementation supports expert parallelism (EP) by sharding the LoRA rank across the TP group when EP is active [vllm/lora/layers/fused_moe.py46-48](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/layers/fused_moe.py#L46-L48) It also supports dual-stream execution to overlap LoRA computation with base model GEMMs via `_lora_stream` and CUDA events [vllm/lora/layers/fused_moe.py113-124](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/layers/fused_moe.py#L113-L124)

## Punica and Triton Kernels

The actual application of LoRA weights happens via the `PunicaWrapperGPU` [vllm/lora/punica_wrapper/punica_gpu.py34-48](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/punica_wrapper/punica_gpu.py#L34-L48)

### Kernel Data Flow

Title: Multi-LoRA Kernel Data Flow

  * **`add_shrink`** : Projects input hidden states to the LoRA rank using `lora_shrink` [vllm/lora/punica_wrapper/punica_gpu.py93-124](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/punica_wrapper/punica_gpu.py#L93-L124) This utilizes `token_mapping_meta` to determine which tokens use which adapter.
  * **`add_expand`** : Projects the rank-sized intermediate back to the model's hidden dimension using `lora_expand` [vllm/lora/punica_wrapper/punica_gpu.py126-172](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/punica_wrapper/punica_gpu.py#L126-L172) It supports multiple output slices for packed modules.
  * **`fused_moe_lora`** : Specialized Triton kernels for MoE layers that handle token-to-expert routing while applying adapter weights [vllm/lora/ops/triton_ops/fused_moe_lora_op.py122-170](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/ops/triton_ops/fused_moe_lora_op.py#L122-L170) It supports a "one-shot" kernel for non-sharded MoE-LoRA where shrink and expand are combined to keep intermediates in registers [vllm/lora/ops/triton_ops/fused_moe_lora_op.py122-170](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/ops/triton_ops/fused_moe_lora_op.py#L122-L170)

### Triton Op Metadata

For GPU execution, `LoRAKernelMeta` maintains metadata tensors required by Triton kernels, such as `token_lora_mapping` [vllm/lora/punica_wrapper/punica_gpu.py58-63](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/punica_wrapper/punica_gpu.py#L58-L63) These are updated per-batch via `update_metadata` to reflect the current request pool [vllm/lora/punica_wrapper/punica_gpu.py76-91](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/punica_wrapper/punica_gpu.py#L76-L91) Kernel performance can be further optimized by loading tuned configurations from `VLLM_TUNED_CONFIG_FOLDER` [vllm/lora/ops/triton_ops/utils.py165-194](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/ops/triton_ops/utils.py#L165-L194)

## Dynamic LoRA Management via API

When `VLLM_ALLOW_RUNTIME_LORA_UPDATING=True`, vLLM exposes endpoints to manage adapters without restarting the engine.

### Load and Unload Flow

The `v1/load_lora_adapter` and `v1/unload_lora_adapter` routes in the API server communicate with the `LoRAModelManager` to update the active adapter set.

Title: Dynamic Adapter Management Flow

  * **Worker-side Management** : The `WorkerLoRAManager` handles the actual loading of weights from local checkpoints [vllm/lora/worker_manager.py106-172](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/worker_manager.py#L106-L172) It validates the LoRA configuration against legal requirements using `PEFTHelper` [vllm/lora/worker_manager.py129](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/worker_manager.py#L129-L129)
  * **Dummy LoRA** : For warmup and profiling, `add_dummy_lora` creates a temporary adapter with random weights to trigger kernel compilation and memory allocation [vllm/lora/worker_manager.py174-181](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/worker_manager.py#L174-L181)
  * **MoE EP Spec** : When using Expert Parallelism, the manager builds a `MoEEPLoadSpec` to ensure LoRA weights are correctly sharded and routed across devices [vllm/lora/model_manager.py150](https://github.com/vllm-project/vllm/blob/185cada3/vllm/lora/model_manager.py#L150-L150)
