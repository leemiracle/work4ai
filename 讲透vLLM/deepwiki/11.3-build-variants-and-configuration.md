## Purpose and Scope

This document explains the different build variants of vLLM (CUDA, ROCm, CPU, XPU), nightly PyTorch support, and build-time configuration options. It covers how vLLM detects the target platform, variant-specific dependencies, and the build-time environment variables that control compilation behavior. For Docker build architecture, see [11.1 Docker Multi-Stage Build](https://github.com/vllm-project/vllm/blob/185cada3/11.1 Docker Multi-Stage Build) For dependency management details, see [11.2 Dependency Management](https://github.com/vllm-project/vllm/blob/185cada3/11.2 Dependency Management) For runtime kernel compilation, see [11.4 Runtime JIT Compilation](https://github.com/vllm-project/vllm/blob/185cada3/11.4 Runtime JIT Compilation)

* * *

## Build Variant Overview

vLLM supports several build variants, each optimized for different hardware platforms. The build system is designed to be cross-platform, supporting Linux and macOS (CPU-only).

Variant| Target Hardware| PyTorch Backend| Default Dependencies| Primary Distribution  
---|---|---|---|---  
**CUDA**|  NVIDIA GPUs| `torch` (CUDA)| FlashInfer, CUTLASS, DeepGEMM| PyPI, Docker Hub  
**ROCm**|  AMD GPUs| `torch` (ROCm)| AITER, Triton (ROCm), DeepEP| AMD PyPI Index  
**CPU**|  x86/ARM/RISC-V/S390/Power| `torch+cpu`| OpenMP, tcmalloc| PyPI (VLLM_TARGET_DEVICE=cpu)  
**XPU**|  Intel GPUs| `torch+xpu`| Intel extensions, vllm-xpu-kernels| Source build only  
  
The build variant is determined at compile time and cannot be changed without rebuilding. Platform auto-detection occurs in `setup.py` based on the installed PyTorch version and environment variables.

## CUDA Build Variant (Default)

The CUDA variant is the primary build configuration, targeting NVIDIA GPUs with CUDA 12.x/13.x (defaulting to CUDA 13.0.3 in latest Docker configurations [docker/Dockerfile25](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile#L25-L25)).

### CUDA-Specific Dependencies

The build system relies on a set of core requirements for CUDA support:

  * `torch == 2.13.0`: The primary tensor library backend [requirements/cuda.txt7](https://github.com/vllm-project/vllm/blob/185cada3/requirements/cuda.txt#L7-L7)
  * `numba == 0.65.0`: Required for N-gram speculative decoding [requirements/cuda.txt4](https://github.com/vllm-project/vllm/blob/185cada3/requirements/cuda.txt#L4-L4)
  * `flashinfer-python == 0.6.17`: Optimized attention kernels for NVIDIA [requirements/cuda.txt17](https://github.com/vllm-project/vllm/blob/185cada3/requirements/cuda.txt#L17-L17)
  * `nvidia-cutlass-dsl[cu13] == 4.6.2`: Support for CUTLASS-based kernel generation [requirements/cuda.txt29](https://github.com/vllm-project/vllm/blob/185cada3/requirements/cuda.txt#L29-L29)
  * `quack-kernels == 0.6.4`: Specialized kernels for FA4 support [requirements/cuda.txt30](https://github.com/vllm-project/vllm/blob/185cada3/requirements/cuda.txt#L30-L30)
  * `humming-kernels[cu13] == 0.1.12`: Optimized kernels for quantization GEMM [requirements/cuda.txt36](https://github.com/vllm-project/vllm/blob/185cada3/requirements/cuda.txt#L36-L36)

### DeepGEMM and FlashMLA Integration

vLLM integrates specialized kernel libraries for Deepseek-style architectures:

  * **DeepGEMM** : Managed via `cmake/external_projects/deepgemm.cmake`. The build system supports JIT compilation for different architectures [cmake/external_projects/deepgemm.cmake65-79](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/deepgemm.cmake#L65-L79)
  * **FlashMLA** : Integrated for optimized Multi-Latent Attention (MLA) support on Hopper GPUs [cmake/external_projects/flashmla.cmake1-10](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/flashmla.cmake#L1-L10)

## ROCm Build Variant

The ROCm variant targets AMD GPUs. vLLM includes deep integration with ROCm-specific libraries and environment handling.

### ROCm Build Process and Dependencies

ROCm builds utilize environment variables to specify architectures, such as `gfx90a`, `gfx942`, or `gfx1250` [docker/Dockerfile.rocm_gfx12501-10](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile.rocm_gfx1250#L1-L10) Key libraries include:

  * **AITER** : AMD Integrated Triton Extension for ROCm.
  * **DeepEP** : DeepSeek-style MoE communication kernels, with the commit pinned in versions configuration [docker/versions.json59](https://github.com/vllm-project/vllm/blob/185cada3/docker/versions.json#L59-L59)
  * **tilelang** : Used for kernel generation [requirements/rocm.txt25](https://github.com/vllm-project/vllm/blob/185cada3/requirements/rocm.txt#L25-L25)
  * **amd-quark** : Required for Quark quantization on ROCm [requirements/rocm.txt24](https://github.com/vllm-project/vllm/blob/185cada3/requirements/rocm.txt#L24-L24)

ROCm builds often use `mold` as a faster linker where supported, though JIT stages fall back to default linkers [docker/Dockerfile.rocm45-47](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile.rocm#L45-L47)

## XPU Build Variant (Intel GPU)

The XPU variant targets Intel Data Center and ARC GPUs. It requires specific Intel OneAPI dependencies and a custom kernel package.

### XPU-Specific Dependencies

  * `vllm_xpu_kernels == 0.1.13.2`: Provides necessary custom kernels for Intel GPUs [requirements/xpu.txt23](https://github.com/vllm-project/vllm/blob/185cada3/requirements/xpu.txt#L23-L23)
  * `triton == 3.7.2+xpu`: A compatibility shim that resolves to `triton-xpu` to satisfy dependencies requiring the `triton` name.
  * **Intel UMD** : The Docker build installs Intel Graphics Compiler (IGC) and Compute Runtime packages.

Sources: [requirements/xpu.txt4-23](https://github.com/vllm-project/vllm/blob/185cada3/requirements/xpu.txt#L4-L23)

## CPU Build Variant

The CPU variant targets x86_64, arm64, RISC-V, S390, and PowerPC platforms using the standard PyTorch CPU backend [docker/Dockerfile.cpu1-8](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile.cpu#L1-L8)

### CPU-Specific Optimizations

  * **tcmalloc** : Bundled for performance on Linux x86_64/aarch64 platforms [setup.py128-135](https://github.com/vllm-project/vllm/blob/185cada3/setup.py#L128-L135) The build system attempts to locate `libtcmalloc_minimal.so` or `libtcmalloc.so` and bundle it into the wheel [setup.py171-186](https://github.com/vllm-project/vllm/blob/185cada3/setup.py#L171-L186)
  * **Zentorch** : The `vllm-openai-zen` target includes specific optimizations for AMD Zen architectures [docker/Dockerfile.cpu12](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile.cpu#L12-L12)

## Build-Time Configuration Options

### Parallelism and Resource Control

The build system calculates the number of parallel jobs based on the `MAX_JOBS` environment variable or available CPU cores [setup.py201-210](https://github.com/vllm-project/vllm/blob/185cada3/setup.py#L201-L210) It also controls NVCC compilation threads via `NVCC_THREADS` [setup.py212-216](https://github.com/vllm-project/vllm/blob/185cada3/setup.py#L212-L216)

### Compiler Caching

vLLM supports `ccache` and `sccache` to speed up repeated compilations:

  * `is_sccache_available()`: Checks for the binary and respects `VLLM_DISABLE_SCCACHE` [setup.py110-113](https://github.com/vllm-project/vllm/blob/185cada3/setup.py#L110-L113)
  * `is_ccache_available()`: Detects if `ccache` is present in the system path [setup.py116-117](https://github.com/vllm-project/vllm/blob/185cada3/setup.py#L116-L117)
  * **Docker Integration** : Dockerfiles for CUDA, ROCm, and CPU all include logic to install and configure `sccache` with S3 backends [docker/Dockerfile136-154](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile#L136-L154) [docker/Dockerfile.rocm82-106](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile.rocm#L82-L106) [docker/Dockerfile.cpu42-54](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile.cpu#L42-L54)

### Rust Frontend Build

The Rust frontend (`vllm-rs`) is integrated into the build pipeline via `setuptools_rust`.

  * **Precompiled Support** : If `VLLM_USE_PRECOMPILED` or `VLLM_USE_PRECOMPILED_RUST` is set, the build system uses existing `.so` artifacts [setup.py52-54](https://github.com/vllm-project/vllm/blob/185cada3/setup.py#L52-L54)
  * **Standalone Stage** : In Docker builds, the Rust frontend is built in a dedicated stage (`rust-build`) to isolate the Rust toolchain from the final runtime image [docker/Dockerfile.cpu132-182](https://github.com/vllm-project/vllm/blob/185cada3/docker/Dockerfile.cpu#L132-L182)
