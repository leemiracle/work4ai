## Purpose and Scope

This page documents the scheduling algorithm and resource allocation mechanisms in vLLM's v1 engine architecture. The `Scheduler` class is responsible for deciding which requests to process at each step, allocating GPU memory (KV cache blocks) to requests, and managing resource constraints to maximize throughput while preventing out-of-memory conditions.

For information about how the scheduler fits into the overall engine architecture, see [EngineCore and Client APIs](https://github.com/vllm-project/vllm/blob/185cada3/EngineCore and Client APIs)(). For details on request state transitions and lifecycle, see [Request Lifecycle and State Management](https://github.com/vllm-project/vllm/blob/185cada3/Request Lifecycle and State Management)(). For the KV cache block management implementation details, see [KV Cache Management](https://github.com/vllm-project/vllm/blob/185cada3/KV Cache Management)().

## Scheduling Algorithm

The `schedule()` method [vllm/v1/core/sched/scheduler.py331](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L331-L331) executes a multi-phase algorithm to fill the current batch while respecting hardware and memory limits.

### Phase 1: Schedule Running Requests

The scheduler first attempts to continue requests already in the `running` list. If GPU memory is insufficient to grow the KV cache for a running request, the scheduler performs preemption [vllm/v1/core/sched/scheduler.py456](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L456-L456)

**Sources:** [vllm/v1/core/sched/scheduler.py331-532](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L331-L532)

### Phase 2: Schedule Waiting Requests

After satisfying running requests, the scheduler pulls from the `waiting` queue until the `token_budget` or `max_num_running_reqs` is reached [vllm/v1/core/sched/scheduler.py543](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L543-L543)

**Sources:** [vllm/v1/core/sched/scheduler.py543-853](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L543-L853)

## KV Cache Slot Allocation

KV cache allocation is managed through the `KVCacheManager.allocate_slots()` method [vllm/v1/core/kv_cache_manager.py205](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_manager.py#L205-L205) The manager coordinates across multiple KV cache groups via the `KVCacheCoordinator` [vllm/v1/core/kv_cache_coordinator.py64](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_coordinator.py#L64-L64)

  1. **Prefix Caching:** Uses `get_computed_blocks()` to find existing blocks in the pool [vllm/v1/core/kv_cache_manager.py341](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_manager.py#L341-L341)
  2. **Growth Calculation:** The `SingleTypeKVCacheManager` determines how many new blocks are needed based on the current sequence length and `block_size` [vllm/v1/core/single_type_kv_cache_manager.py141](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/single_type_kv_cache_manager.py#L141-L141)

  4. **Hashing:** Full blocks are hashed and indexed for future reuse via `BlockHash` [vllm/v1/core/kv_cache_utils.py44](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/kv_cache_utils.py#L44-L44)

## Preemption Strategy

When memory is exhausted, the scheduler invokes `_preempt_request()` [vllm/v1/core/sched/scheduler.py855](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L855-L855)

### Preemption Behavior

  * **Memory Release:** Calls `kv_cache_manager.free(request.request_id)` to return blocks to the free pool [vllm/v1/core/sched/scheduler.py866](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L866-L866)
  * **State Reset:** Increments `request.num_preemptions` [vllm/v1/request.py202](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L202-L202) and sets status to `PREEMPTED`.
  * **Re-queuing:** Prepends the request back to the `waiting` queue to be prioritized in the next step [vllm/v1/core/sched/scheduler.py896](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L896-L896)

## Special Scheduling Cases

### Chunked Prefill

If chunked prefill is enabled, the scheduler limits the tokens processed for a single request in one step. The request remains in the `running` list but tracks progress via `num_computed_tokens` [vllm/v1/request.py174](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L174-L174)

### Mamba Block Alignment

For models with Mamba layers, the scheduler enforces block-aligned splitting. This is handled by `_mamba_block_aligned_split()` which ensures that prefill chunks align with the `block_size` required for Mamba state management [vllm/v1/core/sched/scheduler.py281-329](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L281-L329)

### Speculative Decoding

The scheduler allocates extra slots for draft tokens [vllm/v1/core/sched/scheduler.py503](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L503-L503) It tracks `scheduled_spec_decode_tokens` and coordinates with the model runner output to process `DraftTokenIds` [vllm/v1/core/sched/scheduler.py1276](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L1276-L1276)

## AsyncScheduler

The `AsyncScheduler` [vllm/v1/core/sched/async_scheduler.py16](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/async_scheduler.py#L16-L16) is a variant of the `Scheduler` designed for asynchronous execution, particularly when pipeline parallelism is enabled. It allows for multiple batches to be in-flight concurrently, improving GPU utilization.

### Key Differences from Standard Scheduler

  * **Overlapping Batches** : The `AsyncScheduler` can schedule a new batch before the previous one has completed its forward pass. This is managed by tracking `num_output_placeholders` [vllm/v1/request.py152](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L152-L152) on requests, which represent tokens that have been scheduled but not yet processed by the model.
  * **Pipeline Parallelism (PP)** : When `pipeline_parallel_size > 1`, the `AsyncScheduler` ensures that requests adhere to a specific cadence for decode steps, maintaining consistency across pipeline stages. This is tracked by `next_decode_eligible_step` [vllm/v1/request.py167](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L167-L167) on the `Request` object.
  * **Deferred Block Freeing** : With overlapping batches, a step might still be writing to a freed request's KV blocks. The `AsyncScheduler` defers freeing blocks until it's safe, preventing data corruption. This is controlled by the `defer_block_free` flag [vllm/v1/core/sched/scheduler.py160](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/scheduler.py#L160-L160) and `last_sched_seq` [vllm/v1/request.py171](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/request.py#L171-L171) on the request.
  * **`_inflight_prefills`** : A dictionary to track prefill requests that are currently being processed across pipeline stages [vllm/v1/core/sched/async_scheduler.py30](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/core/sched/async_scheduler.py#L30-L30)
