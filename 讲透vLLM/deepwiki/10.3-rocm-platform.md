## Purpose and Scope

This document describes the ROCm platform implementation in vLLM, which provides AMD GPU support through the HIP/ROCm ecosystem. The ROCm platform handles device detection, GCN architecture identification, AITER operations integration, and AMD-specific optimizations for MI300X, MI325X, and other AMD accelerators.

For general platform abstraction concepts, see [Platform Abstraction Layer](/vllm-project/vllm/10.1-platform-abstraction-layer). For CUDA platform specifics, see [CUDA Platform](/vllm-project/vllm/10.2-cuda-platform). For attention backend details, see [ROCm and Platform-Specific Attention](/vllm-project/vllm/8.4-rocm-and-platform-specific-attention).

## Platform Detection and Environment Setup

### Environment Variable Synchronization

The ROCm platform synchronizes GPU visibility environment variables at module import time to ensure consistency between HIP and CUDA conventions. This prevents runtime errors when tools or users set only one of the two standard variables. vLLM currently warns that `CUDA_VISIBLE_DEVICES` support is deprecated on ROCm in favor of `HIP_VISIBLE_DEVICES` [vllm/platforms/rocm.py133-139](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/rocm.py#L133-L139)

### GCN Architecture Detection

The platform detects the GCN (Graphics Core Next) architecture at module load time using `amdsmi` to avoid premature CUDA initialization. This is critical for Ray workers which may need to set visibility after the module is imported. If `amdsmi` fails, it falls back to `torch.cuda.get_device_properties` [vllm/platforms/rocm.py205-212](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/rocm.py#L205-L212)

## AITER Ops and Skinny GEMM

ROCm platform integrates specialized kernels for performance, including AITER ops and "Skinny GEMM" implementations for specific batch sizes.

### Skinny GEMM Implementation

vLLM provides specialized C++ kernels in `csrc/rocm/skinny_gemms.cu` to optimize GEMM operations where one dimension is significantly smaller than the others.

  * **LLMM1** : Optimized for $N=1$ (single token decoding). It fetches entire rows of matrix A and columns of matrix B, performing multiply-add operations on 8 elements at a time [csrc/rocm/skinny_gemms.cu174-231](https://github.com/vllm-project/vllm/blob/185cada3/csrc/rocm/skinny_gemms.cu#L174-L231)
  * **wvSplitK** : A split-K implementation that decomposes the K-dimension across multiple workgroups to increase occupancy for skinny matrices [csrc/rocm/skinny_gemms.cu418-500](https://github.com/vllm-project/vllm/blob/185cada3/csrc/rocm/skinny_gemms.cu#L418-L500)
  * **wvSplitKrc** : A specialized variant for GFX950 that utilizes skinny reduction counting [vllm/model_executor/layers/utils.py147-160](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/utils.py#L147-L160)

The dispatch logic in `rocm_unquantized_gemm_impl` selects these kernels based on the compute unit count and input shapes [vllm/model_executor/layers/utils.py116-200](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/utils.py#L116-L200)

### AITER Integration

AITER (AMD AI Toolkit for ROCm) provides high-performance kernels for various LLM operations. vLLM integrates these via tuned GEMM implementations and specialized attention backends. vLLM uses environment variables like `VLLM_ROCM_USE_AITER` to control feature enablement [vllm/envs.py135-152](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L135-L152)

Key AITER-based features include:

  * **Tuned GEMM** : Uses AITER-specific logic for optimized linear layers when enabled via `tgemm.mm` [vllm/model_executor/layers/utils.py197-200](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/utils.py#L197-L200)
  * **Triton GEMM** : Optimized Triton-based `gemm_a16w16` for specific hidden dimensions whitelisted in `use_aiter_triton_gemm` [vllm/model_executor/layers/utils.py95-113](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/utils.py#L95-L113)
  * **AiterFlashAttention** : A high-performance attention implementation [vllm/v1/attention/backends/rocm_aiter_fa.py20-29](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/attention/backends/rocm_aiter_fa.py#L20-L29)
  * **MLA Support** : ROCm AITER MLA backends are prioritized on CDNA 3+ architectures [vllm/_aiter_ops.py134-154](https://github.com/vllm-project/vllm/blob/185cada3/vllm/_aiter_ops.py#L134-L154)

## Platform Configuration and Features

### Attention Backends

The ROCm platform selects the optimal backend based on the GCN architecture and model configuration via `ROCMPlatform.get_attn_backend_cls()` [vllm/platforms/rocm.py348-380](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/rocm.py#L348-L380)

  * **ROCM_ATTN** : Standard ROCm attention backend providing wide support for various head sizes and dtypes, utilizing `PagedAttention` [vllm/v1/attention/backends/rocm_attn.py163-196](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/attention/backends/rocm_attn.py#L163-L196)
  * **Block Sizes** : ROCm paged attention native C++ kernels only support block sizes 16 and 32 due to LDS constraints, but Triton paths allow multiples of 16 [vllm/v1/attention/backends/rocm_attn.py178-188](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/attention/backends/rocm_attn.py#L178-L188)
