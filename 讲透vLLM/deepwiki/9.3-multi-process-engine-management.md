This document describes the process lifecycle management infrastructure in vLLM's distributed execution system. It covers the creation, initialization, monitoring, and shutdown of engine processes, Ray integration, request wave coordination, and data parallel load balancing.

## Overview

vLLM uses multiprocessing to manage distributed execution across multiple GPUs and nodes. The engine process management system is responsible for spawning and initializing engine core processes (one per data parallel rank), creating worker processes for model parallelism, and managing Ray actors for multi-node distributed inference.

## EngineCore and Executor Hierarchy

`EngineCore` initializes the model execution backend through an `Executor` abstraction. The choice of executor determines how processes are spawned and coordinated.

### Executor Selection

The factory method `Executor.get_class` selects the implementation based on `ParallelConfig`:

  * **`UniProcExecutor`** : Runs a single worker in the current process. Used for single-GPU execution.
  * **`MultiprocExecutor`** : Spawns local child processes using Python's `multiprocessing` module. Used for multi-GPU execution on a single node [vllm/v1/executor/multiproc_executor.py111](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L111-L111)
  * **`RayDistributedExecutor`** : Orchestrates workers across one or more nodes using Ray actors [vllm/v1/executor/ray_executor.py64](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor.py#L64-L64)
  * **`ExecutorWithExternalLauncher`** : Used when processes are launched by external tools like `torchrun`.

## Local Process Spawning: MultiprocExecutor

The `MultiprocExecutor` manages the lifecycle of local worker processes for Tensor Parallelism (TP), Pipeline Parallelism (PP), and Prefill Context Parallelism (PCP).

  1. **Initialization** : It calculates the required world size from `tp_size`, `pp_size`, and `pcp_size` [vllm/v1/executor/multiproc_executor.py125-131](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L125-L131)
  2. **Process Creation** : It uses `get_mp_context()` to obtain a multiprocessing context (typically `spawn` or `fork`) [vllm/v1/executor/multiproc_executor.py172-182](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L172-L182) It manages OpenMP thread affinity via `OMPProcessManager` [vllm/v1/executor/multiproc_executor.py188-190](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L188-L190)
  3. **Inter-Process Communication (IPC)** : 
     * **Control Plane** : Uses `multiprocessing.Pipe` or ZMQ for RPC commands wrapped in `collective_rpc`.
     * **Data Plane** : Uses a `MessageQueue` (based on shared memory `shm_broadcast`) to broadcast `SchedulerOutput` from the Engine process to all local workers [vllm/v1/executor/multiproc_executor.py164-170](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L164-L170)
  4. **Monitoring** : If `monitor_workers` is enabled, the executor tracks worker health and triggers failure callbacks if any process exits unexpectedly [vllm/v1/executor/multiproc_executor.py114-116](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L114-L116)

## Ray Integration: RayDistributedExecutor

For multi-node execution, vLLM leverages Ray to manage remote actors.

  * **Actor Creation** : `RayDistributedExecutor` creates `RayWorker` actors. Each actor is assigned specific GPU resources via Ray's `placement_group`.
  * **Lazy Initialization** : Workers are initialized lazily inside the actor via `RayWorkerWrapper` which inherits from `WorkerWrapperBase` to ensure environment variables are correctly captured [vllm/v1/worker/worker_base.py191-205](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/worker_base.py#L191-L205)
  * **Compiled DAG** : For high-performance inference, vLLM can use Ray's Compiled DAG API to minimize orchestration overhead [vllm/v1/executor/ray_executor.py70-76](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor.py#L70-L76) This involves a `forward_dag` that coordinates inputs and outputs between ranks.
  * **Environment Sync** : The executor copies relevant environment variables (excluding worker-specific ones like `CUDA_VISIBLE_DEVICES`) from the driver to all Ray actors [vllm/v1/v1/executor/ray_utils.py34-41](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/v1/executor/ray_utils.py#L34-L41)

## Data Parallelism and Expert Load Balancing

vLLM supports internal Data Parallelism (DP) and advanced load balancing for Mixture of Experts (MoE) via the Expert Parallelism Load Balancer (EPLB).

### Data Parallel Coordination

When running with `data_parallel_size > 1`, vLLM spawns multiple `EngineCore` processes [vllm/v1/engine/utils.py177-183](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/utils.py#L177-L183) A `DPCoordinator` may be used to synchronize request waves across DP ranks [vllm/v1/engine/coordinator.py12-25](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/coordinator.py#L12-L25)

### Expert Parallelism Load Balancer (EPLB)

EPLB dynamically rebalances MoE experts across EP ranks based on observed token loads.

  1. **Metrics Collection** : Workers track expert loads and share them with the load balancer.
  2. **Rebalancing** : The load balancer computes an optimal mapping of experts to ranks to minimize tail latency.
  3. **Weight Transfer** : Weights are moved between workers using the `WeightTransferEngine` [vllm/v1/worker/gpu_worker.py49-52](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L49-L52)

## Worker Lifecycle and State Management

All workers, whether local or Ray-based, follow a standardized initialization sequence managed by the `Executor`.

  1. **`init_worker`** : Sets up the distributed environment (NCCL/Gloo) and environment variables [vllm/v1/worker/gpu_worker.py143-162](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L143-L162)
  2. **`init_device`** : Initializes hardware (e.g., `torch.device("cuda")`) and allocates workspace memory via `init_workspace_manager` [vllm/v1/worker/gpu_worker.py20-22](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L20-L22)
  3. **`load_model`** : Loads model weights into GPU memory via the `model_loader` [vllm/v1/worker/gpu_worker.py89-91](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L89-L91)
  4. **`determine_available_memory`** : Profiles the device to calculate KV cache capacity [vllm/v1/worker/gpu_worker.py67-71](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L67-L71)

### Graceful Shutdown

The system ensures clean resource release through:

  * **Weakref Finalizers** : `MultiprocExecutor` uses `weakref.finalize` to ensure `shutdown()` is called upon object destruction [vllm/v1/executor/multiproc_executor.py121](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L121-L121)
  * **Ray Cleanup** : `RayDistributedExecutor` kills worker actors and tears down compiled DAGs.
  * **Distributed Teardown** : Components like `ec_transfer` and `kv_transfer` are explicitly shut down during worker termination [vllm/v1/worker/gpu_worker.py28-38](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L28-L38)
