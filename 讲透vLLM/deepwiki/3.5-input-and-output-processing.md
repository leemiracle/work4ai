## Purpose and Scope

This page documents how vLLM processes input prompts into model-ready tensors and transforms raw model outputs — sampled token IDs and log probabilities emitted by the `EngineCore` — into the `RequestOutput` and `PoolingRequestOutput` objects returned to callers. The pipeline covers multimodal input parsing, incremental detokenization, and streaming response generation.

For documentation on how tokens are sampled by the GPU model runner, see page [4.4. Sampling and Token Generation](https://github.com/vllm-project/vllm/blob/185cada3/4.4. Sampling and Token Generation) For how the scheduler produces `EngineCoreOutput` objects, see page [3.3. Scheduler and Resource Allocation](https://github.com/vllm-project/vllm/blob/185cada3/3.3. Scheduler and Resource Allocation)

## Input Preprocessing and Multimodal Handling

The `InputProcessor` [vllm/v1/engine/input_processor.py38](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L38-L38) is responsible for converting various prompt formats (text, tokens, or multimodal dictionaries) into a unified `EngineCoreRequest` [vllm/v1/engine/input_processor.py33](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L33-L33) format suitable for the V1 engine.

### Multimodal Registry and Data Flow

vLLM uses a `MultiModalRegistry` [vllm/v1/engine/input_processor.py44](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L44-L44) to dispatch data processing based on the model architecture. In the V1 engine, the `InputProcessor` initializes an internal `InputPreprocessor` [vllm/v1/engine/input_processor.py26](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L26-L26) which handles the heavy lifting of modality-specific transformations.

The preprocessing pipeline follows these steps:

  1. **Validation** : The `InputProcessor` validates sampling or pooling parameters against the model's supported tasks via `_validate_params` [vllm/v1/engine/input_processor.py84-159](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L84-L159) This includes verifying `SamplingParams` against `ModelConfig`, `SpeculativeConfig`, and the `Tokenizer` [vllm/v1/engine/input_processor.py97-102](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L97-L102)
  2. **Multimodal Budgeting** : For models with vision or audio, a `MultiModalBudget` [vllm/v1/engine/input_processor.py63](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L63-L63) is used to calculate the required encoder budget and determine if prompt length checks should be skipped [vllm/v1/engine/input_processor.py65-67](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L65-L67)
  3. **Tokenization** : The `InputProcessor` utilizes `process_inputs_async` [vllm/v1/engine/input_processor.py73-75](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L73-L75) which wraps the core `process_inputs` logic to handle tokenization and multimodal processing on a thread pool to avoid blocking the event loop.
  4. **Trace Replay** : If trace replay is enabled, `_normalize_trace_replay_params` [vllm/v1/engine/input_processor.py161-180](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L161-L180) adjusts the `SamplingParams` to match the trace length and generation semantics.
  5. **Request ID Assignment** : Every request is assigned a unique internal ID, while preserving the user-provided ID as `external_req_id` [vllm/v1/engine/input_processor.py246-248](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/input_processor.py#L246-L248)

## Output Processor and Detokenization

Raw token IDs and metadata from the `EngineCore` are processed into human-readable text and structured statistics by the `OutputProcessor` [vllm/v1/engine/async_llm.py141-146](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L141-L146)

### Detokenization and Output Mapping

The `OutputProcessor` [vllm/v1/engine/output_processor.py45](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/output_processor.py#L45-L45) converts raw `EngineCoreOutputs` into the final user-facing response formats.

  * **Incremental Detokenizer** : It utilizes the tokenizer provided during initialization [vllm/v1/engine/async_llm.py142](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L142-L142) to convert new token IDs back to strings.
  * **Logprobs Processing** : The engine supports gathering logprobs into `LogprobsTensors` [vllm/v1/outputs.py94](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/outputs.py#L94-L94) which are then converted to `LogprobsLists` [vllm/v1/outputs.py30](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/outputs.py#L30-L30) for final output.
  * **Finish Reason** : The processor maps internal engine `FinishReason` [vllm/v1/engine/__init__.py47-67](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/__init__.py#L47-L67) flags to user-facing strings such as `stop`, `length`, or `abort` [vllm/v1/engine/__init__.py35](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/__init__.py#L35-L35)

### Metrics and Performance Tracking

The `OutputProcessor` works with `StatLoggerManager` [vllm/v1/engine/async_llm.py161-168](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L161-L168) to record engine health.

  * **Throughput** : `IterationStats` [vllm/v1/metrics/stats.py55](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L55-L55) tracks the number of scheduled and generated tokens per step.
  * **Logging** : The `StatLoggerManager` coordinates multiple loggers, including default Prometheus loggers and custom plugins [vllm/v1/engine/async_llm.py161-169](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L161-L169)

## Streaming Response Generation

vLLM provides streaming updates through the `RequestOutputCollector` [vllm/v1/engine/async_llm.py45](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L45-L45)

### AsyncLLM Output Handling

The `AsyncLLM` [vllm/v1/engine/async_llm.py72](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L72-L72) class manages the lifecycle of request outputs in a background task:

  * **Output Handler** : The `_run_output_handler` [vllm/v1/engine/async_llm.py177](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L177-L177) method starts a loop that pulls outputs from the `EngineCoreClient`.
  * **Aggregation** : If `RequestOutputKind` [vllm/sampling_params.py33](https://github.com/vllm-project/vllm/blob/185cada3/vllm/sampling_params.py#L33-L33) is set to `DELTA`, the processor can emit only the incremental changes (deltas) rather than the full sequence.
  * **Streaming Protocol** : `StreamingInput` [vllm/engine/protocol.py22](https://github.com/vllm-project/vllm/blob/185cada3/vllm/engine/protocol.py#L22-L22) is supported to allow multi-turn streaming sessions where inputs are provided via an async generator.
