This document describes vLLM's parallelism strategies for distributed inference across multiple GPUs and nodes. It covers tensor parallelism (TP), pipeline parallelism (PP), data parallelism (DP), context parallelism (CP), and expert parallelism (EP) for mixture-of-experts (MoE) models.

## Overview

vLLM supports five parallelism strategies that can be combined to scale inference across multiple devices:

Parallelism Type| Purpose| ParallelConfig Field| CLI Argument| World Size Impact  
---|---|---|---|---  
**Tensor Parallelism (TP)**|  Splits model layers across devices| `tensor_parallel_size`| `-tp`, `--tensor-parallel-size`| Multiplies world_size  
**Pipeline Parallelism (PP)**|  Splits model layers into stages| `pipeline_parallel_size`| `-pp`, `--pipeline-parallel-size`| Multiplies world_size  
**Data Parallelism (DP)**|  Replicated instances for throughput| `data_parallel_size`| `-dp`, `--data-parallel-size`| Multiplies world_size  
**Context Parallelism (CP)**|  Splits sequence dimension in prefill| `prefill_context_parallel_size`| `--prefill-context-parallel-size`| Multiplies world_size  
**Expert Parallelism (EP)**|  Splits MoE experts across devices| `enable_expert_parallel`| `--enable-expert-parallel`| Shards experts  
  
The total world size is the product of `tensor_parallel_size`, `pipeline_parallel_size`, `data_parallel_size`, and `prefill_context_parallel_size` [vllm/config/parallel.py122-132](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/parallel.py#L122-L132)

## Tensor Parallelism (TP)

Tensor parallelism splits individual model layers (weight matrices) across multiple devices. Results are aggregated via all-reduce operations.

  * **Communication Backends** : vLLM implements several high-performance all-reduce backends, including `CustomAllreduce`, `FlashInferAllReduce`, and `AiterCustomAllreduce` for ROCm.
  * **Async Communication** : `AsyncIntermediateTensors` allows for lazy communication synchronization, enabling overlapping computation with communication [vllm/v1/worker/gpu_worker.py111-141](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L111-L141)
  * **Symmetric Memory** : vLLM utilizes symmetric memory to optimize cross-GPU communication on NVLink-enabled systems [vllm/distributed/parallel_state.py42](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/parallel_state.py#L42-L42)

## Expert Parallelism (EP)

Expert parallelism shards MoE experts across devices. This is critical for large MoE models like DeepSeek-V3/R1.

### Expert Parallel Load Balancer (EPLB)

The EPLB system manages the distribution of experts based on token load. It uses a sliding window of expert load metrics to trigger rebalancing [vllm/distributed/eplb/eplb_state.py169-182](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/eplb/eplb_state.py#L169-L182)

  * **EplbModelState** : Tracks `physical_to_logical_map` and `logical_to_physical_map` to route tokens to the correct device [vllm/distributed/eplb/eplb_state.py103-160](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/eplb/eplb_state.py#L103-L160)
  * **Async Rebalancing** : When `use_async=True` in `EPLBConfig`, a background `async_worker` thread handles weight transfers while the main thread continues inference [vllm/distributed/eplb/eplb_state.py190-219](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/eplb/eplb_state.py#L190-L219)
  * **Communication Backends** : vLLM supports specialized `All2AllBackend` types, including `deepep_v2`, `mori_high_throughput`, and `flashinfer_nvlink_two_sided` [vllm/config/parallel.py42-55](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/parallel.py#L42-L55)

## Pipeline Parallelism (PP)

Pipeline parallelism splits model layers into stages executed sequentially across different GPUs or nodes.

  * **Process Management** : Managed via the `pp_group` in `parallel_state` [vllm/distributed/parallel_state.py46](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/parallel_state.py#L46-L46)
  * **Non-blocking Sends** : `Worker` tracks `_pp_send_work` handles to manage asynchronous pipeline stage communication [vllm/v1/worker/gpu_worker.py188](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L188-L188)
  * **Executor Support** : Both `MultiprocExecutor` and `RayDistributedExecutor` support pipeline parallelism [vllm/v1/executor/multiproc_executor.py112](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L112-L112) [vllm/v1/executor/ray_executor.py68](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor.py#L68-L68)

## Data Parallelism (DP)

Data Parallelism replicates the model parallel group to process multiple request batches in parallel.

  * **Hybrid Load Balancing** : `data_parallel_hybrid_lb` enables running an `AsyncLLM` per node where vLLM load balances between local DP ranks, while an external LB balances between nodes [vllm/config/parallel.py156-162](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/parallel.py#L156-L162)
  * **External Load Balancing** : `data_parallel_external_lb` is useful for "one-pod-per-rank" setups in Kubernetes [vllm/config/parallel.py149-155](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/parallel.py#L149-L155)
  * **Elastic EP** : `ElasticEPScalingExecutor` allows for dynamic scaling of expert parallelism resources within a DP setup [vllm/v1/worker/gpu_worker.py166](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L166-L166)

## Context Parallelism (CP)

Prefill Context Parallelism (PCP) shards the sequence dimension specifically during the prefill phase.

  * **Group Definition** : `prefill_context_parallel_size` expands the process world size but does not increase the KV-cache shard count [vllm/config/parallel.py126-128](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/parallel.py#L126-L128)
  * **Interaction with EP** : MoE layers are sharded according to the product of TP, CP, and DP sizes [vllm/config/parallel.py129-131](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/parallel.py#L129-L131)
  * **Residual Scattering** : Workers check `is_residual_scattered_for_sp` to determine if residual connections need scattering in context parallel modes [vllm/v1/worker/gpu_worker.py85](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L85-L85)
