This page documents how vLLM loads model configurations from various formats and sources. Model configuration loading is a critical step that occurs after model architecture detection and before the model is instantiated. The configuration determines essential model properties like layer counts, attention mechanisms, vocabulary size, and architecture-specific parameters.

For information about how configurations are used to instantiate models, see **Model Registry and Architecture Detection (5.1)**. For details on configuration objects like `ModelConfig` and `VllmConfig`, see **VllmConfig and Specialized Configuration Objects (2.2)**.

## Configuration Format Support

The configuration loading system supports standard HuggingFace formats, Mistral-native formats, and automated detection.

Format| Description| Config File| Primary Use Case  
---|---|---|---  
`hf`| Standard Transformers format| `config.json`| Most models from HF Hub or local paths  
`mistral`| Mistral AI native format| `params.json`| Mistral-format checkpoints  
`auto`| Auto-detect at runtime| —| Tries Mistral detection first, falls back to HF

## Configuration Parser Architecture

The configuration loading system is built around the `ConfigParserBase` abstract class, with concrete implementations for HuggingFace and Mistral formats.

**Parser Factory Pattern**

`get_config_parser()` looks up `_CONFIG_FORMAT_TO_CONFIG_PARSER` and returns a new parser instance. Custom parsers can be registered using the `@register_config_parser()` decorator, which validates subclassing and overwrites any existing registration with a warning.

## Mistral Configuration Format

Mistral AI uses a custom configuration format with `params.json` instead of HuggingFace's `config.json`. The `MistralConfigParser` handles this format by adapting it to the expected structure.

**Mistral Configuration Adaptation**

The parser downloads `params.json` and performs adaptation via `adapt_config_dict()`. It uses the `_mistral_patch_hf_hub_constants` context manager to temporarily redirect `SAFETENSORS_SINGLE_FILE` to `consolidated.safetensors` and `SAFETENSORS_INDEX_FILE` to `consolidated.safetensors.index.json`.

Sources: [vllm/transformers_utils/config.py51](https://github.com/vllm-project/vllm/blob/185cada3/vllm/transformers_utils/config.py#L51-L51) [vllm/transformers_utils/config.py192-202](https://github.com/vllm-project/vllm/blob/185cada3/vllm/transformers_utils/config.py#L192-L202)

## Speculative Decoding Configuration

Speculative decoding requires loading a draft model configuration alongside the target model. This is managed via `SpeculativeConfig`.

**Diagram: Speculative Decoding Config Loading**

`SpeculativeConfig` supports various methods including `ngram`, `medusa`, `mlp_speculator`, `draft_model`, `suffix`, `custom_class`, `eagle`, `ngram_gpu`, and `dflash`. For methods like `eagle`, the draft model configuration is explicitly initialized and validated. Specialized validation logic exists for models like Qwen3-Omni DSpark to ensure block sizes and hidden sizes match between target and draft.
