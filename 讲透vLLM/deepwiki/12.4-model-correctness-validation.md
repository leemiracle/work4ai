This document describes vLLM's model correctness validation system, which ensures that models produce accurate outputs compared to reference implementations. For information about the broader test infrastructure and organization, see [12.1 Test Organization and Infrastructure](https://github.com/vllm-project/vllm/blob/185cada3/12.1 Test Organization and Infrastructure) For CI pipeline execution details, see [12.2 Buildkite CI Pipelines](https://github.com/vllm-project/vllm/blob/185cada3/12.2 Buildkite CI Pipelines)

Model correctness validation focuses on:

  * **Processing correctness** : Verifying that input tokenization and multimodal processing matches reference implementations.
  * **Generation correctness** : Comparing generated text outputs against reference models (typically HuggingFace Transformers).
  * **Benchmark-based validation** : Using standard datasets (e.g., ShareGPT, GSM8K) to verify model quality and numerical accuracy.
  * **Batch Invariance** : Ensuring deterministic outputs regardless of batch size or request ordering.
  * **Cross-implementation testing** : Validating vLLM models against reference `HfRunner` implementations.

## Batch Invariance and Determinism

vLLM provides a "Batch Invariance" mode to ensure that the output of a model is deterministic and independent of the batch size or the order of requests. This is critical for framework debugging, reinforcement learning (RL) reproducibility, and large-scale consistency guarantees.

### Implementation Mechanisms

When `VLLM_BATCH_INVARIANT=1` is set [vllm/model_executor/layers/layernorm.py101](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/layernorm.py#L101-L101) vLLM modifies its execution path:

  1. **Deterministic Kernels** : It uses specialized kernel implementations for operations like `RMSNorm` and attention that avoid non-deterministic atomic operations. For example, `RMSNorm` switches to `rms_norm_batch_invariant` [vllm/model_executor/layers/layernorm.py108-113](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/layernorm.py#L108-L113)
  2. **Persistent Kernels** : Linear layers and matmuls may use persistent Triton kernels like `matmul_kernel_persistent` to ensure consistent tiling and reduction order regardless of batch size [vllm/model_executor/layers/batch_invariant.py42-65](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/batch_invariant.py#L42-L65)
  3. **Communication** : It disables optimizations like custom all-reduce in tensor parallel mode, which may introduce non-determinism [tests/v1/determinism/test_batch_invariance.py193-197](https://github.com/vllm-project/vllm/blob/185cada3/tests/v1/determinism/test_batch_invariance.py#L193-L197)

### Validation Strategy

Determinism is verified using "needle" tests. A specific "needle" prompt is run alone (batch size 1) to establish a baseline [tests/v1/determinism/test_batch_invariance.py115-118](https://github.com/vllm-project/vllm/blob/185cada3/tests/v1/determinism/test_batch_invariance.py#L115-L118) Then, the same prompt is mixed into a large batch of random filler prompts [tests/v1/determinism/test_batch_invariance.py125-133](https://github.com/vllm-project/vllm/blob/185cada3/tests/v1/determinism/test_batch_invariance.py#L125-L133) The test passes only if the needle's output is bitwise identical across both runs [tests/v1/determinism/test_batch_invariance.py142-157](https://github.com/vllm-project/vllm/blob/185cada3/tests/v1/determinism/test_batch_invariance.py#L142-L157)

## Model Comparison Framework

The primary method for validating model correctness is the comparison of `vllm_runner` outputs against `hf_runner` (HuggingFace Transformers) outputs.

### Basic Correctness Testing

The validation process typically follows these steps:

  1. Initializes an `HfRunner` for a specific model [tests/models/language/generation/test_common.py153-157](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/language/generation/test_common.py#L153-L157)
  2. Generates greedy outputs and logprobs from the reference HF implementation using `generate_greedy_logprobs_limit` [tests/models/language/generation/test_common.py158-160](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/language/generation/test_common.py#L158-L160)
  3. Initializes a `VllmRunner` with equivalent parameters (e.g., `enforce_eager`, `attention_config`) [tests/basic_correctness/test_basic_correctness.py162-171](https://github.com/vllm-project/vllm/blob/185cada3/tests/basic_correctness/test_basic_correctness.py#L162-L171)
  4. Compares the outputs using `check_outputs_equal` [tests/basic_correctness/test_basic_correctness.py180-185](https://github.com/vllm-project/vllm/blob/185cada3/tests/basic_correctness/test_basic_correctness.py#L180-L185) or `check_logprobs_close` [tests/models/language/generation/test_common.py13](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/language/generation/test_common.py#L13-L13)

### Specialized Initialization and Embedding Validation

For models that require specialized embedding handling (e.g., `Gemma`, `MiniCPM`), the correctness suite verifies that prompt embeddings are correctly scaled before being passed to the engine [tests/models/language/generation/test_common.py168-187](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/language/generation/test_common.py#L168-L187)

## Benchmarking Tools

vLLM includes a suite of benchmarking tools to validate performance, serving stability, and offline throughput.

### Online Serving Benchmark (`vllm bench serve`)

The `vllm/benchmarks/serve.py` tool measures throughput and latency of a running OpenAI-compatible server [vllm/benchmarks/serve.py3-19](https://github.com/vllm-project/vllm/blob/185cada3/vllm/benchmarks/serve.py#L3-L19)

**Key Functions:**

  * `get_first_model_from_server`: Fetches the model ID directly from the server's `/v1/models` endpoint [vllm/benchmarks/serve.py149-154](https://github.com/vllm-project/vllm/blob/185cada3/vllm/benchmarks/serve.py#L149-L154)
  * `_align_prompts_to_server_tokenizer`: Ensures local prompt lengths match server-side tokenization by calling the `/tokenize` endpoint [vllm/benchmarks/serve.py74-85](https://github.com/vllm-project/vllm/blob/185cada3/vllm/benchmarks/serve.py#L74-L85)
  * `fetch_spec_decode_metrics`: Retrieves speculative decoding statistics (e.g., `num_accepted_tokens`) from the `/metrics` Prometheus endpoint [vllm/benchmarks/serve.py189-196](https://github.com/vllm-project/vllm/blob/185cada3/vllm/benchmarks/serve.py#L189-L196)

### Offline Throughput Benchmark (`vllm bench throughput`)

The `vllm/benchmarks/throughput.py` script measures the raw performance of the vLLM engine without the overhead of an API server [vllm/benchmarks/throughput.py3](https://github.com/vllm-project/vllm/blob/185cada3/vllm/benchmarks/throughput.py#L3-L3)

  * **vLLM Engine Mode** : Uses `LLM.generate` or `LLM.beam_search` to process a list of `SampleRequest` objects [vllm/benchmarks/throughput.py144-182](https://github.com/vllm-project/vllm/blob/185cada3/vllm/benchmarks/throughput.py#L144-L182)
  * **Profiling Integration** : Supports `llm.start_profile()` and `llm.stop_profile()` to capture hardware traces during the run [vllm/benchmarks/throughput.py131-151](https://github.com/vllm-project/vllm/blob/185cada3/vllm/benchmarks/throughput.py#L131-L151)

## Acceptance Criteria and Regression Testing

For a model or optimization to be considered "correct" and merged into vLLM:

  1. **Numerical Parity** : Logprobs must match reference implementations within a defined tolerance. `test_models` in `test_common.py` ensures that vLLM outputs align with HF for various architectures [tests/models/language/generation/test_common.py114-124](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/language/generation/test_common.py#L114-L124)
  2. **Initialization Integrity** : Models must be able to initialize without OOM or configuration errors. The `MINIMAL_MODEL_ARCH_LIST` ensures coverage for representative architectures like `Llama`, `Bert`, and `InternVL` [tests/models/test_initialization.py33-46](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/test_initialization.py#L33-L46)
  3. **Distributed Consistency** : Pipeline Parallel (PP) and Tensor Parallel (TP) outputs must be consistent with single-GPU runs. `test_pipeline_parallel.py` iterates through setups to ensure correctness in multi-node/multi-GPU environments [tests/distributed/test_pipeline_parallel.py92-98](https://github.com/vllm-project/vllm/blob/185cada3/tests/distributed/test_pipeline_parallel.py#L92-L98)
  4. **Profiling Verification** : When profiling is enabled via `ProfilerConfig`, the engine must correctly capture and flush traces without impacting the correctness of the generated tokens [vllm/config/profiler.py39-110](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/profiler.py#L39-L110)
