The Platform Abstraction Layer provides a unified interface for vLLM to operate across different hardware accelerators (NVIDIA CUDA, AMD ROCm, Intel XPU, Google TPU, and CPU). This layer encapsulates platform-specific device capabilities, kernel operations, backend selection logic, and configuration requirements, allowing the rest of vLLM's codebase to remain hardware-agnostic where possible.

For information about distributed communication backends, see [Distributed Execution](/vllm-project/vllm/9-distributed-execution). For attention backend implementation details, see [Attention Backend Selection](/vllm-project/vllm/8.1-attention-backend-selection).

## Architecture Overview

The platform abstraction layer consists of a base `Platform` class that defines the common interface, and platform-specific implementations that override methods to provide hardware-specific behavior. Each platform implementation handles device detection, capability queries, kernel imports, attention backend selection, and configuration validation.

### Platform Class Hierarchy

The hierarchy follows a strategy pattern where `current_platform` is a singleton instance of a `Platform` subclass determined at runtime.

## Platform Enumeration and Detection

### PlatformEnum

The `PlatformEnum` defines the supported hardware platforms used throughout the codebase for conditional logic.

Enum Value| Description  
---|---  
`CUDA`| NVIDIA GPUs with CUDA support  
`ROCM`| AMD GPUs with ROCm support  
`TPU`| Google Cloud TPUs  
`XPU`| Intel GPUs (Data Center GPU Max, Arc)  
`CPU`| x86, ARM, PowerPC, RISC-V CPUs  
`OOT`| Out-of-tree custom platforms (Plugin-based)

**Sources:** [vllm/platforms/interface.py67-76](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/interface.py#L67-L76)

### Detection Logic

Platform detection uses a set of plugin functions that check for the presence of hardware drivers and libraries without initializing the compute context. This "stateless" detection is critical for environments like Ray where device visibility might be set after the initial import. vLLM also supports a plugin system where `load_plugins_by_group` can register out-of-tree platforms.

## CUDA Platform

The CUDA platform supports NVIDIA GPUs. It utilizes NVML (via `pynvml`) to query device information without initializing the CUDA context.

### CUDA Attention Backend Selection

CUDA uses `_get_backend_priorities` to rank attention kernels based on the device's compute capability (major version 10 for Blackwell, 12 for Rubin) and whether Multi-Latent Attention (MLA) is requested.

Title: CUDA Attention Backend Priority Logic

**Sources:** [vllm/platforms/cuda.py83-160](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L83-L160)

### CUDA Configuration Updates

In `check_and_update_config()`, the CUDA platform:

  1. Sets the default worker class to `vllm.v1.worker.gpu_worker.Worker` if `worker_cls` is set to "auto". [vllm/platforms/cuda.py273-274](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L273-L274)
  2. Disables chunked multimodal input for specific model types like `mllama` or `minicpmv` when necessary. [vllm/platforms/cuda.py278-288](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L278-L288)
  3. Disables `cudnn_sdp` by default in PyTorch 2.5 to avoid crashes on certain models. [vllm/platforms/cuda.py53](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L53-L53)

## ROCm Platform

The ROCm platform supports AMD GPUs. It performs environment synchronization to ensure `HIP_VISIBLE_DEVICES` and `CUDA_VISIBLE_DEVICES` are consistent.

### ROCm Architecture Detection

ROCm detects architectures using `amdsmi` to avoid premature HIP initialization. This allows Ray workers to set visibility after the module is imported.

GCN Architecture| Detection Flag| Example Hardware  
---|---|---  
`gfx942`, `gfx950`| `_ON_MI3XX`| MI300X, MI325X  
`gfx90a`, `gfx942`| `_ON_GFX9`| MI200, MI300  
`gfx11`, `gfx12`| `_ON_GFX1X`| Radeon RX 7900

## CPU Platform

The CPU platform supports multiple architectures (x86, ARM, PowerPC, RISC-V) and is NUMA-aware.

### CPU Architecture and Memory

The CPU platform calculates memory availability by checking NUMA nodes. It uses `get_memory_node_info` to determine the total memory available on specific nodes for KV cache allocation. [vllm/platforms/cpu.py122-125](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L122-L125) During initialization, CPU-specific workers utilize NUMA node bindings to ensure locality. [vllm/v1/worker/cpu_worker.py45-71](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/cpu_worker.py#L45-L71)

**Sources:** [vllm/platforms/cpu.py51-107](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L51-L107) [vllm/v1/worker/cpu_worker.py45-71](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/cpu_worker.py#L45-L71) [vllm/utils/cpu_resource_utils.py1-50](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/cpu_resource_utils.py#L1-L50)

### CPU Configuration Constraints

  1. **Block Size** : Prefers `block_size` as multiples of 32 for performance, but overrides to 16 for reference CPU MLA support to avoid runtime dispatch failure. [vllm/platforms/cpu.py167-174](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L167-L174)
  2. **Scheduling** : Disables `async_scheduling` as it is not required for CPU. [vllm/platforms/cpu.py216-218](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L216-L218)
  3. **Compilation** : Supports `VLLM_COMPILE` mode using the `inductor` backend or `eager` for CI environments. [vllm/platforms/cpu.py243-266](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L243-L266)
  4. **Multiprocessing** : Forces `distributed_executor_backend` to "mp" (multiprocessing) if `VLLM_ENABLE_V1_MULTIPROCESSING` is set, as OpenMP requires distinct processes for correct thread affinity. [vllm/platforms/cpu.py220-228](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L220-L228)
  5. **Mamba Cache** : Resets `mamba_ssm_cache_dtype` to `float32` if AMX tiles or AVX-512BF16 are supported, as these require float32 SSM state. [vllm/platforms/cpu.py184-190](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L184-L190)

**Sources:** [vllm/platforms/cpu.py119-266](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cpu.py#L119-L266)

## XPU Platform

The XPU platform supports Intel GPUs and uses the `xccl` distributed backend. [vllm/platforms/xpu.py111](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/xpu.py#L111-L111)

### XPU-Specific Logic

  1. **Attention Backend** : Provides specific logic for selecting attention backends, prioritizing `TRITON_ATTN` for `float32` dtype and `FLASH_ATTN` otherwise. It also routes to `TURBOQUANT` if specified in `kv_cache_dtype`. [vllm/platforms/xpu.py142-200](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/xpu.py#L142-L200)
  2. **Multimodal Support** : Flash Attention on XPU does not support bidirectional masks for multimodal prefix-LM, so it falls back to `TRITON_ATTN` for these workloads. [vllm/platforms/xpu.py164-182](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/xpu.py#L164-L182)
  3. **Kernel Registration** : Imports custom XPU kernels from `vllm_xpu_kernels` (e.g., `_xpu_C`, `_moe_C`) during initialization. [vllm/platforms/xpu.py11-13](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/xpu.py#L11-L13)
  4. **Memory Queries** : Implements `get_mem_info_wrapper` which wraps `torch.ops._C_cache_ops.getMemoryInfo` to provide a standard `(free, total)` memory query interface. [vllm/platforms/xpu.py31-97](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/xpu.py#L31-L97)
  5. **Model Runner** : Utilizes `XPUModelRunner` and `XPUModelRunnerV2` which alias `torch.cuda` APIs to their `torch.xpu` equivalents, enabling the reuse of GPU-centric logic. [vllm/v1/worker/xpu_worker.py130-133](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/xpu_worker.py#L130-L133)
