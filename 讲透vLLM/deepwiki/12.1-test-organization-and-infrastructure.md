## Purpose and Scope

This document explains the organization of tests in the vLLM codebase, including the directory structure, pytest configuration, test categories, fixtures, and the test registry system. It covers how tests are structured, categorized, and selected for execution based on various hardware and functional criteria.

For information about the CI/CD pipeline configuration and test execution infrastructure, see [Buildkite CI Pipelines](/vllm-project/vllm/12.2-buildkite-ci-pipelines). For hardware-specific testing details, see [Hardware-Specific Testing](/vllm-project/vllm/12.3-hardware-specific-testing). For model correctness testing methodology, see [Model Correctness Validation](/vllm-project/vllm/12.4-model-correctness-validation).

## Model Test Registry System

vLLM uses a specialized registry system to manage the vast number of supported models and their testing requirements. This bridges the gap between HuggingFace architectures and vLLM's internal execution logic.

### HfExamplesInfo and Registry

The core of the model testing infrastructure is the registry which manages metadata for testing specific model architectures.

  * **`_HfExamplesInfo`** : A dataclass storing model-specific testing metadata, including default HF model IDs, required `transformers` versions, `tokenizer_mode`, and `max_model_len` [tests/models/registry.py16-121](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/registry.py#L16-L121)
  * **`check_transformers_version`** : Logic to skip or error if the environment doesn't meet model-specific requirements [tests/models/registry.py122-182](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/registry.py#L122-L182)
  * **`HF_EXAMPLE_MODELS`** : The singleton instance providing access to all registered test models [tests/models/registry.py200-210](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/registry.py#L200-L210)
  * **`MINIMAL_MODEL_ARCH_LIST`** : A subset of representative architectures (e.g., `LlavaForConditionalGeneration`, `BertForSequenceClassification`) used for standard regression testing to reduce CI time [tests/models/test_initialization.py33-46](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/test_initialization.py#L33-L46)

**Sources:** [tests/models/registry.py16-210](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/registry.py#L16-L210) [tests/models/test_initialization.py33-53](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/test_initialization.py#L33-L53)

## V1 Engine and Distributed Testing

The testing infrastructure for V1 and distributed execution focuses on resource isolation and correct initialization.

### Distributed Pipeline Parallelism

Tests for Pipeline Parallelism (PP) use a matrix of `ParallelSetup` configurations to verify stability across TP/PP splits.

  * **`ParallelSetup`** : Defines the `tp_size`, `pp_size`, and `eager_mode` for a specific test run [tests/distributed/test_pipeline_parallel.py30-33](https://github.com/vllm-project/vllm/blob/185cada3/tests/distributed/test_pipeline_parallel.py#L30-L33)
  * **`PPTestSettings`** : Categorizes models into `fast` (minimal TP/PP) or `detailed` (exhaustive combinations) test suites [tests/distributed/test_pipeline_parallel.py42-90](https://github.com/vllm-project/vllm/blob/185cada3/tests/distributed/test_pipeline_parallel.py#L42-L90)
  * **`create_new_process_for_each_test`** : A decorator used to ensure hardware isolation by spawning a fresh process for every test case, preventing VRAM leakage and signal handler conflicts [tests/models/test_initialization.py56-59](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/test_initialization.py#L56-L59)

## Hardware-Specific Testing Environment

vLLM adjusts its test environment based on the detected hardware platform via `current_platform`.

  * **ROCm Overrides** : ROCm testing uses `ROCM_EXTRA_ARGS` (e.g., `--no-enable-prefix-caching`, `--max-num-seqs 1`) to ensure deterministic results and reduce flakiness [tests/utils.py137-141](https://github.com/vllm-project/vllm/blob/185cada3/tests/utils.py#L137-L141)
  * **NVML/AMDSMI Integration** : The `_nvml` context manager handles initialization and shutdown of hardware management libraries to monitor memory usage during tests [tests/utils.py91-130](https://github.com/vllm-project/vllm/blob/185cada3/tests/utils.py#L91-L130)
  * **Multiprocessing Strategy** : The `requires_spawn_multiprocessing` helper determines if a platform (like ROCm or XPU) requires `spawn` instead of `fork` for test subprocesses [tests/utils.py190-193](https://github.com/vllm-project/vllm/blob/185cada3/tests/utils.py#L190-L193)
  * **AITER Kernel Testing** : Specific models like `Llama-3.2-1B` and `Qwen2.5` are tested with the ROCm AITER kernel enabled via `VLLM_ROCM_USE_AITER` environment variable [tests/models/language/generation/test_common.py25-31](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/language/generation/test_common.py#L25-L31) [tests/models/language/generation/test_common.py135-136](https://github.com/vllm-project/vllm/blob/185cada3/tests/models/language/generation/test_common.py#L135-L136)
