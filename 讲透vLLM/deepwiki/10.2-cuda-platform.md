This page documents the CUDA platform implementation in vLLM: the class hierarchy, device capability detection, attention backend selection logic, memory management, and configuration validation specific to NVIDIA GPUs.

For background on the abstract `Platform` interface that `CudaPlatform` implements, see [Platform Abstraction Layer](/vllm-project/vllm/10.1-platform-abstraction-layer). For the ROCm implementation that follows a similar pattern, see [ROCm Platform](/vllm-project/vllm/10.3-rocm-platform).

## Class Hierarchy

The CUDA platform is implemented across concrete classes that provide hardware-specific logic. At import time, vLLM automatically selects the appropriate implementation based on the environment and availability of NVML (NVIDIA Management Library).

## NVML vs. Non-NVML Selection

On import, `vllm/platforms/cuda.py` attempts to import `pynvml` via `import_pynvml()` [vllm/platforms/cuda.py49](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L49-L49) If successful, it uses `NvmlCudaPlatform`. Otherwise, it falls back to `NonNvmlCudaPlatform`, which uses `torch.cuda` calls directly.

Feature| `NvmlCudaPlatform`| `NonNvmlCudaPlatform`  
---|---|---  
Compute capability| Via `pynvml.nvmlDeviceGetCudaComputeCapability`| Via `torch.cuda.get_device_capability`  
Device name| Via `pynvml.nvmlDeviceGetName`| Via `torch.cuda.get_device_name`  
Total memory| Via `pynvml.nvmlDeviceGetMemoryInfo`| Via `torch.cuda.get_device_properties().total_memory`  
NVLink check| Via `pynvml.nvmlDeviceGetP2PStatus`| Returns `False`, logs a warning  
Device UUID| Via `pynvml.nvmlDeviceGetUUID`| Not implemented  
CUDA context init| Avoids it (NVML is independent)| Initializes CUDA context on first call  
  
The key advantage of NVML is that it queries device properties **without initializing the CUDA context** , which is critical for Ray-based deployments where workers set `CUDA_VISIBLE_DEVICES` after the module is imported [vllm/platforms/cuda.py3-5](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L3-L5)

Sources: [vllm/platforms/cuda.py49](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L49-L49) [vllm/platforms/cuda.py598-735](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L598-L735)

## Device Capability Detection

`DeviceCapability` is a `NamedTuple` with `major` and `minor` fields [vllm/platforms/interface.py89-91](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/interface.py#L89-L91) Comparison operators are implemented so that capability checks like `has_device_capability(80)` work cleanly [vllm/platforms/interface.py93-117](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/interface.py#L93-L117)

`NvmlCudaPlatform.get_device_capability` uses the `with_nvml_context` decorator to wrap `pynvml` init/shutdown around the call [vllm/platforms/cuda.py181-190](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L181-L190)

The mapping from logical to physical device IDs respects the `CUDA_VISIBLE_DEVICES` environment variable [vllm/platforms/cuda.py602-613](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L602-L613)

Sources: [vllm/platforms/cuda.py181-190](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L181-L190) [vllm/platforms/cuda.py602-613](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L602-L613) [vllm/platforms/interface.py89-132](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/interface.py#L89-L132)

## Build System and Architecture Support

The CMake build system handles architecture-specific flags and compiler requirements.

  * **Blackwell/Rubin Support** : CUDA 12.9+ introduces family-specific targets (e.g., `10.0`, `12.0`) to support entire generations [CMakeLists.txt123-126](https://github.com/vllm-project/vllm/blob/185cada3/CMakeLists.txt#L123-L126) CUDA 13.4 adds Rubin (`10.7`) support [CMakeLists.txt116-120](https://github.com/vllm-project/vllm/blob/185cada3/CMakeLists.txt#L116-L120)
  * **Architecture Filtering** : vLLM filters `CUDA_SUPPORTED_ARCHS` based on `CMAKE_CUDA_COMPILER_VERSION` [CMakeLists.txt116-132](https://github.com/vllm-project/vllm/blob/185cada3/CMakeLists.txt#L116-L132)
  * **Torch Compatibility** : CUDA builds expect specific PyTorch versions (e.g., `2.13.0`) [CMakeLists.txt71](https://github.com/vllm-project/vllm/blob/185cada3/CMakeLists.txt#L71-L71)

Sources: [CMakeLists.txt71-132](https://github.com/vllm-project/vllm/blob/185cada3/CMakeLists.txt#L71-L132)

## NVLink and P2P

`NvmlCudaPlatform.is_fully_connected` determines if all GPUs in a process group can communicate via NVLink [vllm/platforms/cuda.py647-671](https://github.com/vllm-project/vllm/blob/185cada3/vllm/platforms/cuda.py#L647-L671) It queries `NVML_P2P_CAPS_INDEX_NVLINK` to ensure full peer-to-peer connectivity for optimized distributed communication.
