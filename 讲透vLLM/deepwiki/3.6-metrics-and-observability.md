This page documents how vLLM collects, aggregates, and exposes runtime metrics. It covers the v1 stats dataclasses, the logger hierarchy, Prometheus metrics, request latency breakdowns, and the integration with custom plugin loggers.

## Architecture Overview

The metrics system consists of a **stats collection layer** that assembles data after each engine step and a **logger layer** that consumes those stats to write to standard output or expose them via a Prometheus-compatible endpoint.

Metrics are collected in the engine core during execution and processed by the frontend. In `AsyncLLM`, the `_run_output_handler()` loop receives `EngineCoreOutputs` [vllm/v1/engine/async_llm.py170-174](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L170-L174) which the `OutputProcessor` uses to update `IterationStats` [vllm/v1/engine/output_processor.py35-41](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/output_processor.py#L35-L41) These stats are then passed to a `StatLoggerManager` instance [vllm/v1/engine/async_llm.py158-165](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/async_llm.py#L158-L165)

## Stats Collection Layer

Stats objects are defined in `vllm/v1/metrics/stats.py` as dataclasses to facilitate easy transfer between the engine core and the frontend.

### SchedulerStats

Produced by the `Scheduler` after each step, carrying the current state of resource allocation and cache usage [vllm/v1/metrics/stats.py186-215](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L186-L215)

Field| Type| Description  
---|---|---  
`num_running_reqs`| `int`| Requests currently in model execution batches.  
`num_waiting_reqs`| `int`| Requests in the waiting queue.  
`kv_cache_usage`| `float`| Fraction of KV cache blocks in use (0.0–1.0).  
`prefix_cache_stats`| `PrefixCacheStats`| Local prefix cache hit/miss counts.  
`spec_decoding_stats`| `SpecDecodingStats`| Statistics for speculative decoding performance.  
`perf_stats`| `PerfStats`| MFU and hardware performance stats.  
`cudagraph_stats`| `CUDAGraphStat`| CUDA Graph capture and usage statistics.  
  
Sources: [vllm/v1/metrics/stats.py186-215](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L186-L215)

### IterationStats

Assembled by the `OutputProcessor` from a batch of `EngineCoreOutput` objects [vllm/v1/engine/output_processor.py35-41](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/output_processor.py#L35-L41) It tracks token counts and finished request summaries.

Field| Type| Description  
---|---|---  
`num_generation_tokens`| `int`| Total generation tokens in this step.  
`prompt_token_stats`| `PromptTokenStats`| Breakdown of prompt tokens (compute, local cache, external transfer).  
`finished_requests`| `list[FinishedRequestStats]`| Summary for completed requests in this iteration.  
`num_corrupted_reqs`| `int`| Number of requests corrupted (e.g., due to NaNs).  
`num_preempted_reqs`| `int`| Number of requests preempted.  
  
Sources: [vllm/v1/metrics/stats.py348-375](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L348-L375) [vllm/v1/engine/output_processor.py35-41](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/output_processor.py#L35-L41)

### CachingMetrics

Maintains a sliding window hit rate over the most recent $N$ requests (default 1000) [vllm/v1/metrics/stats.py35-42](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L35-L42)

  * **Implementation** : Uses a `deque` of `(requests, queries, hits)` tuples [vllm/v1/metrics/stats.py52](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L52-L52)
  * **Hit Rate** : Calculated as `aggregated_query_hit / aggregated_query_total` [vllm/v1/metrics/stats.py107-111](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L107-L111)
  * **Reset** : Triggered by `BaseCacheStats.reset` (e.g., after a manual cache clear) [vllm/v1/metrics/stats.py68-69](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L68-L69)

Sources: [vllm/v1/metrics/stats.py35-111](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L35-L111)

## Request Latency Breakdown

The system tracks several latency intervals for each request. These are stored in `RequestStateStats` [vllm/v1/engine/output_processor.py183](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/output_processor.py#L183-L183) and summarized in `FinishedRequestStats` when a request completes.

Interval| Description| Code Entity  
---|---|---  
`queue_time`| Time spent in the waiting queue.| `FinishedRequestStats.queue_time`  
`prefill_time`| Time from scheduling to first token generation.| `FinishedRequestStats.prefill_time`  
`decode_time`| Time spent generating subsequent tokens.| `FinishedRequestStats.decode_time`  
`e2e_latency`| Total time from arrival to completion.| `FinishedRequestStats.e2e_latency`  
  
Sources: [vllm/v1/metrics/stats.py246-263](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L246-L263) [vllm/v1/metrics/stats.py455-501](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L455-L501) [vllm/v1/engine/output_processor.py183](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/engine/output_processor.py#L183-L183)

## Performance and MFU Metrics

vLLM includes an analytic flops/memory estimation module. This is used to derive Model Flops Utilization (MFU) stats for a running model.

  * **PerfStats** : Dataclass containing `num_flops_per_gpu`, `num_read_bytes_per_gpu`, and `num_write_bytes_per_gpu` [vllm/v1/metrics/perf.py93-97](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/perf.py#L93-L97)
  * **Quantization Impact** : Weight byte sizes are adjusted based on the quantization method (e.g., FP8, INT8, AWQ) to accurately estimate memory bandwidth via `_QUANT_WEIGHT_BYTE_SIZE` [vllm/v1/metrics/perf.py52-74](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/perf.py#L52-L74)
  * **ExecutionContext** : Aggregates batch statistics across prefill and decode phases to provide context for FLOPs calculation [vllm/v1/metrics/perf.py101-167](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/perf.py#L101-L167)

## KV Cache Metrics and Observability

The `KVCacheManager` coordinates prefix caching and block allocation. It relies on `PrefixCacheStats` and `MultiModalCacheStats` to report efficiency.

  * **PrefixCacheStats** : Records hit/miss counts for the prefix cache [vllm/v1/metrics/stats.py115-130](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L115-L130)
  * **KVCacheEvictionEvent** : Captures details about KV cache block evictions, including `lifetime_seconds`, `idle_seconds`, and `reuse_gaps_seconds` [vllm/v1/metrics/stats.py162-169](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/stats.py#L162-L169)

## Plugin System for Custom Loggers

Users can implement custom loggers by subclassing `StatLoggerBase` and registering them via the `vllm.stat_loggers` entry point group [vllm/v1/metrics/loggers.py19](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/loggers.py#L19-L19)

  1. **Discovery** : `load_stat_logger_plugin_factories()` searches for plugins at runtime using `load_plugins_by_group(STAT_LOGGER_PLUGINS_GROUP)` [vllm/v1/metrics/loggers.py74-88](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/loggers.py#L74-L88)
  2. **Validation** : The system ensures all plugins are subclasses of `StatLoggerBase` [vllm/v1/metrics/loggers.py78-84](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/loggers.py#L78-L84)
  3. **Execution** : The `StatLoggerManager` calls `record()` and `log()` on all registered plugins [vllm/v1/metrics/loggers.py1022-1050](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/metrics/loggers.py#L1022-L1050)
