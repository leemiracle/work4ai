## Purpose and Scope

This page documents the configuration architecture of vLLM, centered around the `VllmConfig` root object and its specialized sub-configurations. It covers the structure, key fields, and validation logic of `ModelConfig`, `ParallelConfig`, `CacheConfig`, `SchedulerConfig`, and others located in `vllm/config/`.

For the CLI/YAML argument parsing pipeline that constructs these objects, see [2.1](https://github.com/vllm-project/vllm/blob/185cada3/2.1) For environment variables that supplement configuration, see [2.3](https://github.com/vllm-project/vllm/blob/185cada3/2.3) For `CompilationConfig` and `torch.compile` integration, see [2.4](https://github.com/vllm-project/vllm/blob/185cada3/2.4)

## Package Layout

All configuration classes are defined within the `vllm/config/` directory and re-exported through `vllm/config/__init__.py`. vLLM uses a custom `@config` decorator (defined in `vllm/config/utils.py`) that applies Pydantic validation to Python dataclasses, allowing for strict type checking and range validation (e.g., `ge`, `le`).

## VllmConfig — Root Container

`VllmConfig` is the central configuration object passed throughout the engine, workers, and execution pipeline. It aggregates all specialized configuration objects as typed fields.

Field| Type| Default| Description  
---|---|---|---  
`model_config`| `ModelConfig`| `None`| Model identity, dtype, and tokenizer settings.  
`cache_config`| `CacheConfig`| `CacheConfig()`| KV cache block allocation and memory limits.  
`parallel_config`| `ParallelConfig`| `ParallelConfig()`| Distributed execution (TP/PP/DP) degrees.

## ModelConfig

`ModelConfig` manages model-specific metadata, including architecture detection and tokenizer modes. It resolves the Hugging Face configuration (`hf_config`) during initialization using `get_config`.

Field| Type| Default| Notes  
---|---|---|---  
`model`| `str`| `"Qwen/Qwen3-0.6B"`| HF repo ID or local path.  
`tokenizer_mode`| `TokenizerMode`| `"auto"`| `"auto"`, `"hf"`, `"slow"`, `"mistral"`, `"deepseek_v32"`, `"deepseek_v4"`.  
`dtype`| `ModelDType`| `"auto"`| Resolved to `torch.dtype` or string representation.  
`max_model_len`| `int`| `None`| Auto-derived from HF config if unset.  
`runner`| `RunnerOption`| `"auto"`| `"auto"`, `"generate"`, `"pooling"`, `"draft"`.  
`trust_remote_code`| `bool`| `False`| Allow custom model code execution.  
  
**Sources:** [vllm/config/model.py124-186](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/model.py#L124-L186) [vllm/transformers_utils/config.py34-44](https://github.com/vllm-project/vllm/blob/185cada3/vllm/transformers_utils/config.py#L34-L44)

### Runner and Conversion Logic

The `runner` field determines the `runner_type` (e.g., `generate` or `pooling`). For pooling models, `ModelConfig` may trigger an adapter conversion (e.g., `embed` or `classify`) via the `convert` field. This is verified in `_verify_runner_and_convert`.

## CacheConfig

`CacheConfig` defines how the KV cache is partitioned and stored.

Field| Type| Default| Notes  
---|---|---|---  
`block_size`| `int`| `None`| Contiguous block size in tokens (defaults to 16).  
`gpu_memory_utilization`| `float`| `0.92`| Fraction of VRAM reserved for KV cache.  
`cache_dtype`| `CacheDType`| `"auto"`| `"auto"`, `"fp8"`, `"half"`, `"nvfp4"`, `"int8_per_token_head"`.  
`enable_prefix_caching`| `bool`| `True`| Enables prompt/prefix sharing.  
`mamba_cache_mode`| `MambaCacheMode`| `"none"`| Strategy for Mamba state caching.

## ParallelConfig

`ParallelConfig` describes the distributed execution topology. It supports Tensor Parallelism (TP), Pipeline Parallelism (PP), Data Parallelism (DP), and Expert Parallelism (EP).

Field| Type| Default| Notes  
---|---|---|---  
`tensor_parallel_size`| `int`| `1`| Shards per pipeline stage.  
`pipeline_parallel_size`| `int`| `1`| Number of pipeline stages.  
`data_parallel_size`| `int`| `1`| Number of engine replicas.  
`enable_expert_parallel`| `bool`| `False`| Shard MoE experts across ranks.  
`all2all_backend`| `All2AllBackend`| `"allgather_reducescatter"`| Communication backend for MoE.  
`eplb_config`| `EPLBConfig`| factory| Expert Parallel Load Balancing settings.

### Model-Specific Configuration Updates

The `VllmConfig` initialization process includes a step to apply model-specific configuration adjustments. This is handled by the `_apply_model_specific_config_updates` method, which iterates through a registry of `VerifyAndUpdateConfig` classes. These classes, defined in `vllm/model_executor/models/config.py`, can modify `VllmConfig` or `ModelConfig` fields based on the detected model architecture.

For example, `DeepseekV32ForCausalLM` adjusts the `cache_dtype` for DeepSeekV3.2 models, and `UnlimitedOCRForCausalLMConfig` configures attention backends and disables prefix caching for Unlimited-OCR models.

### Optimization Level Presets

`OptimizationLevel` (O0-O3) provides presets for performance. For example, `O2` (the default) enables piecewise CUDA graphs and various fusion passes in `PassConfig`.

Preset| CUDA Graph Mode| Fusion Passes  
---|---|---  
`O0`| `NONE`| All False  
`O1`| `PIECEWISE`| Norm/Act Fusion enabled  
`O2`| `FULL_AND_PIECEWISE`| All fusions (including AllReduce) enabled  
  
**Sources:** [vllm/config/vllm.py130-142](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/vllm.py#L130-L142) [vllm/config/vllm.py206-240](https://github.com/vllm-project/vllm/blob/185cada3/vllm/config/vllm.py#L206-L240)

### Configuration Hashing

`VllmConfig` implements `compute_hash()` to generate a unique fingerprint of the configuration. This hash is used to cache compiled artifacts (e.g., Triton kernels, CUDA graphs). Fields that do not affect the execution graph (like `seed` or `served_model_name`) are excluded from the hash via `get_hash_factors`.
