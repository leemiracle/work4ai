## Purpose and Scope

This page documents low-precision quantization methods in vLLM, focusing on FP8, MXFP4, and NVFP4 quantization schemes. It covers data formats, backend selection strategies, and the dispatch mechanisms for each quantization type. The page explains:

  * **FP8 quantization** : 8-bit floating point with per-token-group activation quantization, per-block weight quantization, scale factor formats (including UE8M0), and multi-backend GEMM dispatch.
  * **MXFP4 quantization** : Microscaling 4-bit format with 8-bit exponent-only scales, backend selection logic, and platform-specific optimizations.
  * **NVFP4 quantization** : NVIDIA 4-bit floating point format with group scales and specialized kernels for Blackwell (SM100) and Hopper (SM90).

For how these quantization methods are applied to MoE expert layers, see [vllm/model_executor/layers/fused_moe/layer.py1-138](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/layer.py#L1-L138) and [vllm/model_executor/layers/fused_moe/fused_moe.py1-3](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/fused_moe.py#L1-L3) for implementation details. For the general quantization method registry and how quantization methods are wired into the model loading pipeline, see [vllm/model_executor/layers/quantization/base_config.py1-56](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/quantization/base_config.py#L1-L56)

## Quantization Granularities

Block-FP8 (W8A8) in vLLM uses distinct quantization granularities for weights and activations to balance accuracy and performance:

Tensor| Granularity| Typical block shape| Scale tensor shape  
---|---|---|---  
Weights| Per-block (2D tile)| `[128, 128]` (N×K)| `(num_N_tiles, num_K_tiles)`  
Activations| Per-token-group (1D row group)| `[1, 128]` (one group per row segment)| `(M, K//128)`  
  
This matches the format required by models such as DeepSeek-V3, which uses 128-element groups in both dimensions [vllm/model_executor/layers/fused_moe/config.py190-192](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/config.py#L190-L192) The mapping of these flags to generic `GroupShape` objects is handled by `_quant_flags_to_group_shape` [vllm/model_executor/layers/fused_moe/config.py69-97](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/config.py#L69-L97)

## Scale Factor Formats

Three scale factor formats are used, selected by `DeepGemmQuantScaleFMT` based on hardware and configuration:

**`DeepGemmQuantScaleFMT` enum** — [vllm/utils/deep_gemm.py49-58](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/deep_gemm.py#L49-L58)

Enum value| Description| Used when  
---|---|---  
`FLOAT32`| Float32 scales in Float32 tensor| DeepGEMM disabled, or Triton/CUTLASS backends  
`FLOAT32_CEIL_UE8M0`| Float32 tensor, values ceiled to UE8M0| Hopper (SM90), `VLLM_USE_DEEP_GEMM_E8M0=1`  
`UE8M0`| Int32 tensor, 4 UE8M0 values packed| Blackwell (SM100+), `VLLM_USE_DEEP_GEMM_E8M0=1`  
  
The oracle decision is cached at startup via `DeepGemmQuantScaleFMT.init_oracle_cache()` [vllm/utils/deep_gemm.py61-84](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/deep_gemm.py#L61-L84) The helper `is_deep_gemm_e8m0_used()` [vllm/utils/deep_gemm.py103-124](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/deep_gemm.py#L103-L124) returns `True` when the UE8M0 path is active.

**UE8M0 scale encoding:** Each scale value `s` is stored as `2^ceil(log2(s))` — the next power-of-two ceiling of `s`. This enables efficient hardware-level dequantization on Blackwell [vllm/utils/deep_gemm.py52-54](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/deep_gemm.py#L52-L54) The function `transform_sf_into_required_layout` [vllm/utils/deep_gemm.py35](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/deep_gemm.py#L35-L35) is used to rearrange these scales for TMA (Tensor Memory Accelerator) alignment.

## MXFP4 and NVFP4 Quantization

### MXFP4 (Microscaling 4-bit)

MXFP4 uses the `GptOssMxfp4MoEMethod` [vllm/model_executor/layers/quantization/mxfp4.py142](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/quantization/mxfp4.py#L142-L142) for MoE layers. It supports rounding up hidden and intermediate sizes to meet hardware alignment requirements (typically 32-element blocks) via `mxfp4_round_up_hidden_size_and_intermediate_size` [vllm/model_executor/layers/quantization/mxfp4.py186](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/quantization/mxfp4.py#L186-L186)

**Backend Selection for MXFP4:** The `select_mxfp4_moe_backend` function [vllm/model_executor/layers/fused_moe/oracle/mxfp4.py30](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/oracle/mxfp4.py#L30-L30) determines the optimal backend from the `Mxfp4MoeBackend` enum [vllm/model_executor/layers/fused_moe/oracle/mxfp4.py102](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/oracle/mxfp4.py#L102-L102)

  * `Mxfp4MoeBackend.FLASHINFER_TRTLLM_MXFP4_MXFP8`: Preferred on SM100 for optimized performance [vllm/model_executor/layers/quantization/mxfp4.py163](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/quantization/mxfp4.py#L163-L163)
  * `Mxfp4MoeBackend.DEEPGEMM_MXFP4`: DeepSeek-style FP4 backend for SM100+ [vllm/model_executor/layers/fused_moe/oracle/mxfp4.py108](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/oracle/mxfp4.py#L108-L108)
  * `Mxfp4MoeBackend.MARLIN`: Used as a fallback or for weight-only paths [vllm/model_executor/layers/fused_moe/oracle/mxfp4.py116](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/oracle/mxfp4.py#L116-L116)

### NVFP4 (NVIDIA 4-bit)

NVFP4 is the native 4-bit floating point format for SM100+. vLLM provides specialized kernels like `CutlassNvFp4LinearKernel` [vllm/model_executor/kernels/linear/__init__.py139](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/kernels/linear/__init__.py#L139-L139) and `FlashInferTrtllmNvFp4LinearKernel` [vllm/model_executor/kernels/linear/__init__.py153](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/kernels/linear/__init__.py#L153-L153)

**Backend Selection for NVFP4:** The `select_nvfp4_moe_backend` function [vllm/model_executor/layers/fused_moe/oracle/nvfp4.py42](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/oracle/nvfp4.py#L42-L42) determines the optimal backend.

  * `Nvfp4MoeBackend.FLASHINFER_TRTLLM_NVFP4`: Utilizes FlashInfer's TRTLLM kernels for NVFP4.
  * `Nvfp4MoeBackend.TRITON`: A Triton-based implementation.
  * `Nvfp4MoeBackend.MARLIN`: Marlin kernel for NVFP4.
