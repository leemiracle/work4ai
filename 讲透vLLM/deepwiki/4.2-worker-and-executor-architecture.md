## Purpose and Scope

This page documents the two-layer abstraction vLLM uses to manage model execution across hardware: the **Executor** layer and the **Worker** layer.

  * The **Executor** is owned by the engine core and acts as a proxy to one or more worker processes or actors. It handles process lifecycle, RPC dispatch, and result collection.
  * The **Worker** runs inside each process (or Ray actor) and is responsible for device initialization, model loading, memory profiling, and executing forward passes.

This page focuses on the v1 implementations under `vllm/v1/executor/` and `vllm/v1/worker/`.

### The `collective_rpc` Interface

All executor implementations expose `collective_rpc()`, the core RPC primitive. It sends a method call (by name or serialized callable) with arguments to all workers, then collects results.

Higher-level methods like `determine_available_memory` [vllm/v1/executor/abstract.py148-149](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/abstract.py#L148-L149) and `get_kv_cache_specs` [vllm/v1/executor/abstract.py151-152](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/abstract.py#L151-L152) are implemented by delegating to `collective_rpc`.

## UniProcExecutor

`UniProcExecutor` ([vllm/v1/executor/uniproc_executor.py51-159](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/uniproc_executor.py#L51-L159)) runs a single worker **in the same process** as the engine core.

  * `_init_executor()` creates one `WorkerWrapperBase(rpc_rank=0)`, calls `init_worker()`, `init_device()`, and `load_model()` in-process [vllm/v1/executor/uniproc_executor.py54-74](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/uniproc_executor.py#L54-L74)
  * `collective_rpc()` calls `run_method(self.driver_worker, method, args, kwargs)` directly [vllm/v1/executor/uniproc_executor.py90-117](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/uniproc_executor.py#L90-L117)
  * It supports asynchronous scheduling by returning `AsyncOutputFuture` when `non_block=True` [vllm/v1/executor/uniproc_executor.py32-49](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/uniproc_executor.py#L32-L49)

## MultiprocExecutor

`MultiprocExecutor` ([vllm/v1/executor/multiproc_executor.py111-466](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/multiproc_executor.py#L111-L466)) spawns one worker subprocess per local GPU.

### Shared Memory Broadcast

For high-performance coordination, it uses a `MessageQueue` ([vllm/distributed/device_communicators/shm_broadcast.py31](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/device_communicators/shm_broadcast.py#L31-L31)) based on shared memory (`shm`). This allows the driver to broadcast `SchedulerOutput` to all workers with minimal latency.

## Ray Distributed Executors

vLLM supports two Ray-based backends: the legacy `RayDistributedExecutor` and the newer `RayExecutorV2`.

### RayDistributedExecutor

`RayDistributedExecutor` ([vllm/v1/executor/ray_executor.py64-191](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor.py#L64-L191)) distributes workers as Ray actors.

  * **Worker Creation** : `_init_workers_ray()` resolves placement groups and creates `RayWorkerWrapper` actors [vllm/v1/executor/ray_executor.py156-225](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor.py#L156-L225)
  * **Ray Compiled DAG** : It can use Ray's Compiled DAG for the execution path to minimize Python overhead during forward passes [vllm/v1/executor/ray_executor.py71-76](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor.py#L71-L76)
  * **Rank Adjustment** : Since Ray actor creation order is non-deterministic, it calls `adjust_rank` after all workers are up to align them with vLLM's internal rank mapping [vllm/v1/executor/ray_executor.py51-62](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor.py#L51-L62)

### RayExecutorV2

`RayExecutorV2` ([vllm/v1/executor/ray_executor_v2.py49-204](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor_v2.py#L49-L204)) is a hybrid that combines `MultiprocExecutor` logic with Ray orchestration.

  * It uses `RayWorkerProc` ([vllm/v1/executor/ray_executor_v2.py76-103](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor_v2.py#L76-L103)), which defers full initialization until physical GPU IDs are discovered via Ray runtime context [vllm/v1/executor/ray_executor_v2.py125-137](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor_v2.py#L125-L137)
  * Communication between the driver and workers uses shared memory for nodes co-located with the driver, and TCP for remote nodes [vllm/v1/executor/ray_executor_v2.py172-194](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/executor/ray_executor_v2.py#L172-L194)

## GPU Worker (`Worker`)

`Worker` ([vllm/v1/worker/gpu_worker.py143-191](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L143-L191)) is the primary implementation for NVIDIA/AMD GPUs.

### Device Management and Initialization

  * **Precision** : Configures `torch.set_float32_matmul_precision` based on `envs.VLLM_FLOAT32_MATMUL_PRECISION` [vllm/v1/worker/gpu_worker.py161-162](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L161-L162)
  * **Distributed State** : Initializes NCCL/XCCL via `init_distributed_environment` [vllm/v1/worker/gpu_worker.py25-27](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L25-L27) and ensures model parallel groups (TP/PP) are initialized [vllm/v1/worker/gpu_worker.py23-27](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L23-L27)
  * **Fault Tolerance** : If enabled, initializes a `WorkerSentinel` to monitor process health [vllm/v1/worker/gpu_worker.py168-169](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L168-L169)

### Memory Profiling

The `Worker` determines the KV cache capacity through `determine_available_memory()` [vllm/v1/worker/gpu_worker.py353-502](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L353-L502)

  1. It performs a "warmup" or dummy forward pass to trigger internal allocations (e.g., CUDA graphs, temporary buffers).
  2. It uses `vllm.utils.mem_utils.memory_profiling` to capture a memory snapshot [vllm/v1/worker/gpu_worker.py69](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L69-L69)
  3. It calculates the remaining free memory on the device and returns it to the `EngineCore` for KV cache block allocation.

### Sleep and Wake Coordination

The worker supports multi-level "sleep" modes to free up GPU resources:

  * **Level 1** : Offloads model weights to CPU memory [vllm/v1/worker/gpu_worker.py531-542](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L531-L542)
  * **Level 2** : Saves internal buffers and context to CPU, potentially allowing the process to release the GPU context [vllm/v1/worker/gpu_worker.py170-172](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L170-L172)
  * **Backend** : Resolved lazily via `_get_sleep_mode_backend` [vllm/v1/worker/gpu_worker.py192-205](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_worker.py#L192-L205)
