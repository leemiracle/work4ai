## Purpose and Scope

This document covers the runtime Just-In-Time (JIT) compilation infrastructure in vLLM. It details the integration of FlashInfer's JIT kernel generation, DeepGemm compilation, and the custom vLLM Inductor-based compilation framework. These components allow vLLM to generate and optimize GPU kernels at runtime based on specific model architectures, quantization schemes, and hardware capabilities.

For information about build-time compilation of vLLM's C++/CUDA extensions, see [Build Variants and Configuration](/vllm-project/vllm/11.3-build-variants-and-configuration).

* * *

## Overview

vLLM employs runtime JIT compilation to bridge the gap between generic model definitions and hardware-optimal execution. This is primarily achieved through:

  * **Custom vLLM Inductor Backend** : A specialized compilation pipeline that uses `torch.compile` with custom passes, caching, and piecewise compilation for shape specialization.
  * **FlashInfer JIT** : Dynamic generation of attention and MoE kernels tailored to specific head dimensions and data types, particularly for Blackwell (SM 10.0) and Hopper (SM 9.0) architectures [vllm/utils/flashinfer.py176-200](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/flashinfer.py#L176-L200)
  * **DeepGemm** : High-performance GEMM kernels for MoE models that support JIT warmup to generate kernels for various wave patterns and block sizes [cmake/external_projects/deepgemm.cmake106-108](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/deepgemm.cmake#L106-L108)
  * **FlashMLA** : Specialized Multi-Latent Attention kernels for Hopper (SM90a) and Blackwell (SM100) that are vendored and integrated via a torch-ops shim [cmake/external_projects/flashmla.cmake33-43](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/flashmla.cmake#L33-L43)

**Sources:** [vllm/utils/flashinfer.py176-200](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/flashinfer.py#L176-L200) [cmake/external_projects/deepgemm.cmake106-108](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/deepgemm.cmake#L106-L108) [cmake/external_projects/flashmla.cmake33-43](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/flashmla.cmake#L33-L43)

## FlashInfer JIT and TRTLLM Integration

FlashInfer provides high-performance attention kernels that can be JIT-compiled or loaded as pre-compiled cubins. vLLM uses a compatibility wrapper to handle various FlashInfer APIs [vllm/utils/flashinfer.py3-6](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/flashinfer.py#L3-L6)

### Cubin Loading and JIT

FlashInfer can load kernels from a remote repository or local path [vllm/utils/flashinfer.py27-33](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/flashinfer.py#L27-L33) If `flashinfer-cubin` is not available, vLLM checks for `nvcc` to perform JIT compilation of the required kernels [vllm/utils/flashinfer.py55-62](https://github.com/vllm-project/vllm/blob/185cada3/vllm/utils/flashinfer.py#L55-L62)

### TRTLLM Attention Dispatch

vLLM supports using TRTLLM-optimized attention kernels through FlashInfer wrappers for specific hardware families (SM90, SM100, SM120) [tests/kernels/attention/test_use_trtllm_attention.py92-115](https://github.com/vllm-project/vllm/blob/185cada3/tests/kernels/attention/test_use_trtllm_attention.py#L92-L115) The system uses `supports_trtllm_attention` to verify hardware compatibility and the availability of the Nvidia Artifactory for cubin downloads [tests/kernels/attention/test_use_trtllm_attention.py70-78](https://github.com/vllm-project/vllm/blob/185cada3/tests/kernels/attention/test_use_trtllm_attention.py#L70-L78)

## DeepGemm Compilation

DeepGemm is integrated as an external project and is built per-Python version to handle private CPython symbols in its pybind11 bindings [cmake/external_projects/deepgemm.cmake91-99](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/deepgemm.cmake#L91-L99)

### Build-time vs Runtime

While the core bindings are built during the vLLM installation [cmake/external_projects/deepgemm.cmake146-156](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/deepgemm.cmake#L146-L156) the kernels themselves support JIT optimization for different GPU architectures (SM90a, SM100f, SM120f) [cmake/external_projects/deepgemm.cmake64-82](https://github.com/vllm-project/vllm/blob/185cada3/cmake/external_projects/deepgemm.cmake#L64-L82) The `setup.py` for DeepGemm is modified during build to include necessary CUDA headers [tools/ep_kernels/install_python_libraries.sh170-173](https://github.com/vllm-project/vllm/blob/185cada3/tools/ep_kernels/install_python_libraries.sh#L170-L173)

### NVSHMEM Dependency

For Expert Parallelism (EP), DeepGemm kernels link against NVSHMEM, which is downloaded and configured during the build process [tools/ep_kernels/install_python_libraries.sh102-115](https://github.com/vllm-project/vllm/blob/185cada3/tools/ep_kernels/install_python_libraries.sh#L102-L115)

## Fused MoE and CuteDSL JIT

vLLM utilizes FlashInfer's `CuteDSL` for specialized MoE kernels, particularly for NVFP4 quantization [vllm/model_executor/layers/fused_moe/experts/flashinfer_cutedsl_moe.py31-38](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/experts/flashinfer_cutedsl_moe.py#L31-L38)

### Kernel Application

The `FlashInferCuteDSLExperts` class handles the runtime application of these kernels. It checks for hardware support via `is_device_capability_family(100)` (Blackwell) and verifies the availability of the `flashinfer_cute_dsl_fused_moe_nvfp4` functional API [vllm/model_executor/layers/fused_moe/experts/flashinfer_cutedsl_moe.py75-81](https://github.com/vllm-project/vllm/blob/185cada3/vllm/model_executor/layers/fused_moe/experts/flashinfer_cutedsl_moe.py#L75-L81)

### Shared Memory Synchronization

For distributed MoE execution, vLLM implements a `SpinCondition` for cross-process shared memory synchronization, ensuring that readers are notified when JIT-compiled results or weights are ready in shared memory [vllm/distributed/device_communicators/shm_broadcast.py112-127](https://github.com/vllm-project/vllm/blob/185cada3/vllm/distributed/device_communicators/shm_broadcast.py#L112-L127)

## Platform-Specific JIT (ROCm)

On ROCm, vLLM uses specialized build utilities to handle the HIP conversion of CUDA sources [cmake/utils.cmake54-82](https://github.com/vllm-project/vllm/blob/185cada3/cmake/utils.cmake#L54-L82)

  * **Hipify** : C++ and CUDA sources are transformed to HIP at build time using the `hipify_sources_target` function, which maps `.cu` files to `.hip` in the build directory [cmake/utils.cmake74-79](https://github.com/vllm-project/vllm/blob/185cada3/cmake/utils.cmake#L74-L79)
  * **Compiler Flags** : Platform-specific flags for ROCm (e.g., `-DUSE_ROCM`, `-DENABLE_FP8`) are dynamically determined via `get_torch_gpu_compiler_flags` [cmake/utils.cmake147-163](https://github.com/vllm-project/vllm/blob/185cada3/cmake/utils.cmake#L147-L163)

**Sources:** [cmake/utils.cmake54-163](https://github.com/vllm-project/vllm/blob/185cada3/cmake/utils.cmake#L54-L163)
