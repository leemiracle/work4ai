This page documents `vllm/envs.py`, vLLM's centralized environment variable registry. It covers the module's structure, the access mechanism, helper utilities, and a detailed technical reference of `VLLM_*` variables. For information on how these variables feed into strongly-typed configuration objects at engine startup, see [VllmConfig and Specialized Configuration Objects](/vllm-project/vllm/2.2-vllmconfig-and-specialized-configuration-objects). For compilation-specific settings, see [Compilation Configuration and Optimization Levels](/vllm-project/vllm/2.4-compilation-configuration-and-optimization-levels).

## Overview

`vllm/envs.py` serves as the single authoritative source for all environment variable definitions in vLLM. Rather than scattering `os.environ.get(...)` calls throughout the codebase, every variable is declared in one place with its type, default value, and validation logic. The rest of the codebase reads variables through a module-level `__getattr__` that lazily evaluates the appropriate callable from the `environment_variables` dict. [vllm/envs.py4-13](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L4-L13)

## Module Structure

The file is organized into three layers that work together to provide type safety and runtime flexibility.

**Module structure diagram:`vllm/envs.py`**

Sources: [vllm/envs.py14-173](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L14-L173) [vllm/envs.py250-463](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L250-L463) [vllm/envs.py473-1004](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L473-L1004)

### The `TYPE_CHECKING` Block

[vllm/envs.py14-173](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L14-L173) contains a block guarded by `if TYPE_CHECKING:`. This block declares all variables with their Python types and default values. It is **never executed at runtime** ; its sole purpose is to give type checkers and IDE tooling accurate type information when code does `import vllm.envs as envs; envs.VLLM_CACHE_ROOT`.

### The `environment_variables` Dict

[vllm/envs.py473-1004](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L473-L1004) defines the dict where each entry is a zero-argument callable (usually a lambda). These lambdas are evaluated **each time the variable is accessed** , ensuring that environment changes after import are reflected in the system.

### Module `__getattr__`

The module defines a `__getattr__` function that intercepts attribute access. It looks up the requested name in the `environment_variables` dictionary and executes the associated lambda. This implementation ensures that environment variables are not cached at the module level unless explicitly intended via `enable_envs_cache()`. [vllm/envs.py1007-1014](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L1007-L1014) [tests/test_envs.py58-87](https://github.com/vllm-project/vllm/blob/185cada3/tests/test_envs.py#L58-L87)

### CPU Backend Variables

The CPU backend utilizes specific variables for memory management and thread binding. `VLLM_CPU_KVCACHE_SPACE` is used to determine the size of the KV cache if not explicitly set via config. [vllm/envs.py51](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L51-L51) Threading is controlled by `VLLM_CPU_OMP_THREADS_BIND`. [vllm/envs.py52](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L52-L52)

For AMD Zen architectures, `VLLM_ZENTORCH_WEIGHT_PREPACK` (defaulting to `True`) controls whether weights are prepacked. [vllm/envs.py56](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L56-L56)

### ROCm and AITER

For ROCm platforms, a suite of `VLLM_ROCM_USE_AITER_*` variables controls the dispatch to optimized kernels. `VLLM_ROCM_USE_AITER` is the master switch, while sub-flags like `VLLM_ROCM_USE_AITER_MOE` and `VLLM_ROCM_USE_AITER_MLA` default to `True` to enable specific AITER-based execution paths. [vllm/envs.py135](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L135-L135) [vllm/envs.py139](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L139-L139) [vllm/envs.py143](https://github.com/vllm-project/vllm/blob/185cada3/vllm/envs.py#L143-L143)

The `vllm._aiter_ops` module uses these flags to determine if `aiter` extensions should be promoted to the global scope to resolve HIP symbols for JIT extensions. [vllm/_aiter_ops.py91-131](https://github.com/vllm-project/vllm/blob/185cada3/vllm/_aiter_ops.py#L91-L131) The function `is_aiter_found_and_supported()` specifically checks for CDNA 3 or better architectures on ROCm. ### Kubernetes Service Discovery

`get_vllm_port()` explicitly checks if `VLLM_PORT` contains a scheme (e.g., `tcp://`). This is a common failure mode in Kubernetes where a service named `vllm` causes an environment variable `VLLM_PORT` to be populated with a URL string. vLLM raises a `ValueError` in this case to guide the user to fix the service naming conflict.
