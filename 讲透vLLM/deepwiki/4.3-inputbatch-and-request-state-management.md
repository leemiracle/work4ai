This document describes the per-request state tracking and batched execution state management in vLLM's V1 worker architecture. It covers `CachedRequestState` for individual request metadata and `InputBatch` for managing batched execution across multiple requests.

For scheduler-side request management and scheduling decisions, see [Scheduler and Resource Allocation](/vllm-project/vllm/3.3-scheduler-and-resource-allocation). For model execution coordination using these structures, see [GPUModelRunner](/vllm-project/vllm/4.1-gpumodelrunner). For sampling configuration, see [Sampling and Token Generation](/vllm-project/vllm/4.4-sampling-and-token-generation).

**Scope** : This page focuses on the data structures and operations that maintain request state and batch composition during model execution. It does not cover the scheduler's decision-making logic or the actual model forward pass.

## Core Data Structures

### CachedRequestState

`CachedRequestState` stores all per-request metadata needed across multiple execution steps. Each request maintains its own instance that persists throughout its lifetime in the system.

**Key Fields** :

  * `prompt_token_ids`: Input token sequence (None if using `prompt_embeds`) [vllm/v1/worker/gpu_input_batch.py37](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L37-L37)

### InputBatch

`InputBatch` manages the batched execution state for all currently scheduled requests. It maintains both CPU and GPU tensors for efficient data transfer and supports dynamic batch composition. In the V1 architecture, there are two variants: one for managing the persistent state in the runner (`vllm/v1/worker/gpu_input_batch.py`) and a lightweight dataclass for the active execution batch (`vllm/v1/worker/gpu/input_batch.py`).

Title: "InputBatch Component Relationships"

**CPU/GPU Buffer Pattern** : Most tensors follow the synchronized CPU and GPU versions to enable overlapped CPU preparation and GPU execution.

  * CPU tensors are initialized with `pin_memory=True` where applicable to speed up transfers [vllm/v1/worker/gpu_input_batch.py156-172](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L156-L172)
  * GPU tensors (e.g., `temperature`, `top_p`) are allocated directly on the device [vllm/v1/worker/gpu_input_batch.py187-205](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L187-L205)
  * Special `StagedWriteTensor` and `UvaBackedTensor` are used in `RequestState` to minimize GPU memory pressure for large metadata like `all_token_ids` [vllm/v1/worker/gpu/states.py33-53](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/states.py#L33-L53)

**Sources** : [vllm/v1/worker/gpu_input_batch.py92-268](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L92-L268) [vllm/v1/worker/gpu/states.py9-82](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/states.py#L9-L82)

## Request State Management in GPUModelRunner

The `GPUModelRunner` maintains two levels of request state:

Title: "GPUModelRunner State Coordination"

**Separation of Concerns** :

  1. `self.requests`: Long-term storage for all request states, indexed by `req_id` [vllm/v1/worker/gpu/model_runner.py201](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/model_runner.py#L201-L201) Requests remain here even when unscheduled (preempted).
  2. `self.input_batch`: Short-term batch composition for the current execution step [vllm/v1/worker/gpu/model_runner.py202](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/model_runner.py#L202-L202)
  3. `self.req_states`: Manages GPU-backed tensors for request metadata, optimized for device access [vllm/v1/worker/gpu/model_runner.py203](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/model_runner.py#L203-L203)
  4. The `input_batch.req_id_to_index` mapping provides O(1) lookup from request ID to batch index [vllm/v1/worker/gpu_input_batch.py128](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L128-L128)

## Request Lifecycle and State Transitions

### Adding New Requests

When a request is scheduled for the first time, `GPUModelRunner` creates a `CachedRequestState` and adds it to the `InputBatch` and `RequestState`.

Title: "New Request Addition Sequence"

The `add_request()` operation in `InputBatch`:

  1. Calls `_register_add_request()` to allocate a batch index [vllm/v1/worker/gpu_input_batch.py284](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L284-L284)
  2. Reuses indices from recently removed requests via `batch_update_builder.pop_removed()` [vllm/v1/worker/gpu_input_batch.py274](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L274-L274)
  3. Copies prompt and output tokens to CPU tensors [vllm/v1/worker/gpu_input_batch.py314-323](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L314-L323)
  4. Initializes sampling parameters (temperature, top_p, top_k, penalties) [vllm/v1/worker/gpu_input_batch.py334-386](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L334-L386)

The `add_request()` operation in `RequestState`:

  1. Allocates a free index for the new request [vllm/v1/worker/gpu/states.py96](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/states.py#L96-L96)
  2. Initializes `max_seq_len`, `prompt_len`, `prefill_len`, `total_len`, `all_token_ids`, `num_computed_prefill_tokens`, `num_computed_tokens`, and `last_sampled_tokens` for the request [vllm/v1/worker/gpu/states.py100-123](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/states.py#L100-L123)
  3. Staged writes are applied to GPU tensors via `apply_staged_writes()` [vllm/v1/worker/gpu/states.py125-130](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu/states.py#L125-L130)

## Batch State Operations

### Condensation (Compaction)

The `condense()` operation removes gaps left by removed requests by sliding active requests to the lowest available indices [vllm/v1/worker/gpu_input_batch.py632-715](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L632-L715)

Title: "Batch Condensation Logic"

**Algorithm** :

  1. Iterate through `_req_ids` to find `None` entries (empty slots) [vllm/v1/worker/gpu_input_batch.py641](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L641-L641)
  2. For each empty slot, find the next non-`None` entry [vllm/v1/worker/gpu_input_batch.py645](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L645-L645)
  3. Call `move_row()` to shift the request down [vllm/v1/worker/gpu_input_batch.py650](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L650-L650)
  4. Update `req_id_to_index` mapping [vllm/v1/worker/gpu_input_batch.py651](https://github.com/vllm-project/vllm/blob/185cada3/vllm/v1/worker/gpu_input_batch.py#L651-L651)
