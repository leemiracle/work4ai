This document describes the Buildkite continuous integration (CI) pipeline configuration system used for automated testing in vLLM. It covers the pipeline organization, YAML configuration format, test categorization, hardware-specific pipelines, and the execution logic for various backends.

## Pipeline Organization

The Buildkite CI configuration is organized into a modular structure following a migration on February 18, 2026, which deprecated the monolithic `.buildkite/test-pipeline.yaml` in favor of specialized directories and files [`.buildkite/test-pipeline.yaml:1-8`]().

Directory/File| Purpose| Source  
---|---|---  
`.buildkite/test_areas/`| Test job definitions organized by functional area (e.g., `distributed.yaml`, `kernels.yaml`, `misc.yaml`, `models_multimodal.yaml`).| [`.buildkite/test-pipeline.yaml:3`]()  
`.buildkite/image_build/`| Jobs for building base and test Docker images.| [`.buildkite/test-pipeline.yaml:4`]()  
`.buildkite/hardware_tests/`| Hardware-specific test jobs (Intel XPU, Ascend NPU, Arm CPU, etc.).| [`.buildkite/test-pipeline.yaml:5`]()  
`.buildkite/ci_config.yaml`| Central configuration for the CI pipeline.| [`.buildkite/test-pipeline.yaml:6`]()  
`.buildkite/test-amd.yaml`| AMD GPU-specific test pipeline definitions and documentation.| [`.buildkite/test-amd.yaml:1-7`]()

## Test Step Configuration

There are two distinct YAML schemas used in the CI configuration.

### test_areas/*.yaml Schema (NVIDIA/General)

Each file in `.buildkite/test_areas/` defines a named `group` of steps. These steps utilize the standard vLLM CI schema.

Field| Type| Description| Source  
---|---|---|---  
`group`| string| Display group name in the Buildkite UI.| [`.buildkite/test_areas/distributed.yaml:1`]()  
`depends_on`| list| Step keys that must complete first (usually `image-build`).| [`.buildkite/test_areas/distributed.yaml:2-3`]()  
`label`| string| Display name for the specific test step.| [`.buildkite/test_areas/distributed.yaml:5`]()  
`num_devices`| int| Number of GPUs/devices required (e.g., 2, 4, 8).| [`.buildkite/test_areas/distributed.yaml:9`]()  
`device`| string| Specific hardware requirement (e.g., `h100`, `b200-k8s`, `h200_18gb`, `cpu-small`).| [`.buildkite/test_areas/kernels.yaml:47`](), [`.buildkite/test_areas/misc.yaml:8`]()  
`source_file_dependencies`| list| Path prefixes; step is skipped if no changes match these paths.| [`.buildkite/test_areas/distributed.yaml:10-12`]()  
`commands`| list| Shell commands to execute inside the container.| [`.buildkite/test_areas/distributed.yaml:13-17`]()  
`parallelism`| int| Number of parallel jobs to run for this step.| [`.buildkite/test_areas/kernels.yaml:28`]()  
`mirror`| map| Defines mirrored tests for other hardware (e.g., AMD).| [`.buildkite/test_areas/misc.yaml:33-40`]()  
  
### test-amd.yaml Schema (AMD Specific)

The AMD pipeline uses a schema that is fed into a Jinja2 template (`test-template-amd.j2`) [`.buildkite/test-amd.yaml:4-6`](). It includes specialized fields:

Field| Type| Description| Source  
---|---|---|---  
`fast_check`| bool| Whether to run on every commit in the fastcheck pipeline.| [`.buildkite/test-amd.yaml:10`]()  
`fast_check_only`| bool| Run this test on the fastcheck pipeline only.| [`.buildkite/test-amd.yaml:11`]()  
`mirror_hardwares`| list| List of selector tags for AMD pipelines that should include the test.| [`.buildkite/test-amd.yaml:16`]()  
`num_nodes`| int| Simulates multi-node by launching multiple containers on one host.| [`.buildkite/test-amd.yaml:20-22`]()  
`soft_fail`| bool| Allow step to fail without failing the entire pipeline.| [`.buildkite/test-amd.yaml:13`]()

## Test Categories and Sharding

Tests are categorized to optimize resource utilization and prevent interference.

### Distributed and Multi-GPU Testing

Distributed tests are partitioned by the number of devices and parallelism strategy (TP, DP, PP, or EP).

  * **Comm Ops** : Tests low-level communication primitives and shared memory buffers (`test_comm_ops.py`, `test_shm_broadcast.py`) [`.buildkite/test_areas/distributed.yaml:5-18`]().
  * **Data Parallel (DP)** : Tests `AsyncLLM` and speculative decoding with `DP_SIZE` and `TP_SIZE` environment variables [`.buildkite/test_areas/distributed.yaml:35-56, 165-181`]().
  * **Torchrun** : Validates multi-process execution using `torchrun --nproc-per-node` [`.buildkite/test_areas/distributed.yaml:99-121, 123-163`]().
  * **NCCL Configuration** : Sets `NCCL_CUMEM_HOST_ENABLE=0` to avoid specific driver issues in CI environments [`.buildkite/test_areas/distributed.yaml:52, 95, 117, 137, 178`]().

### Kernels and Performance

  * **vLLM IR** : Tests for the intermediate representation and platform-portable kernel framework [`.buildkite/test_areas/kernels.yaml:5-15`]().
  * **Quantization/MoE** : Specialized kernel tests for `fused_moe` and various quantization backends (FP8, INT8, DeepGEMM) [`.buildkite/test_areas/kernels.yaml:165-203`]().
  * **MLA/FlashMLA** : Specifically tested on H100 Hopper hardware for DeepSeek-style attention [`.buildkite/test_areas/kernels.yaml:147-163`]().

### Multimodal and LM Eval

  * **Multimodal Models** : Split into standard groups (qwen2, qwen3+gemma, llava+qwen2_vl) and extended generation tests [`.buildkite/test_areas/models_multimodal.yaml:5-85`]().
  * **LM Eval** : Correctness validation using benchmarks (GSM8K) across different hardware [`.buildkite/test_areas/lm_eval.yaml:5-151`]().
  * **V1 Engine Specifics** : Specialized groups for `V1 Spec Decode`, `V1 Sample + Logits`, and `V1 Core + KV + Metrics` [`.buildkite/test_areas/misc.yaml:5-100`]().

### Test Sharding

For large test suites, vLLM uses Buildkite's native parallelism.

  * The `parallelism` field in the YAML defines the number of shards [`.buildkite/test_areas/kernels.yaml:28, 116, 174`]().
  * The environment variables `$$BUILDKITE_PARALLEL_JOB` and `$$BUILDKITE_PARALLEL_JOB_COUNT` are used to distribute tests across agents via `pytest --shard-id` and `--num-shards` [`.buildkite/test-amd.yaml:24-25`](), [`.buildkite/test_areas/kernels.yaml:27, 115, 173`]().

## CI-Specific Environment Variables

The CI pipelines utilize several environment variables to control test behavior:

Variable| Usage| Source  
---|---|---  
`VLLM_WORKER_MULTIPROC_METHOD`| Set to `spawn` for tests requiring clean process isolation.| [`.buildkite/test_areas/misc.yaml:28, 78, 146, 160, 176, 189, 210`]()  
`VLLM_TEST_SAME_HOST`| Used in distributed tests to signal single-node multi-GPU simulation.| [`.buildkite/test_areas/distributed.yaml:118-119`]()  
`NCCL_CUMEM_HOST_ENABLE`| Typically set to `0` to prevent NCCL issues in containerized CI.| [`.buildkite/test_areas/distributed.yaml:52, 95, 117, 137, 178`]()  
`VLLM_USE_DEEP_GEMM`| Disabled on H100 for LM Eval as Triton is preferred for that arch.| [`.buildkite/test_areas/lm_eval.yaml:56`]()  
`VLLM_ALLOW_INSECURE_SERIALIZATION`| Required for certain speculative decoding and RLHF tests.| [`.buildkite/test_areas/distributed.yaml:153-154`](), [`.buildkite/test_areas/spec_decode.yaml:224`]()

## Speculative Decoding CI Structure

Speculative decoding tests are highly granular, covering various methods across different hardware.

  * **V1 Spec Decode** : Core tests for the V1 engine's speculative decoding implementation [`.buildkite/test_areas/spec_decode.yaml:5-23`]().
  * **Eagle** : Correctness tests for Eagle speculative decoding, mirrored on AMD hardware (MI300) [`.buildkite/test_areas/spec_decode.yaml:33-42, 60-69`]().
  * **Speculators & MTP**: Validates Multi-Token Prediction (MTP) and Speculators, with nightly runs on B200 Blackwell [`.buildkite/test_areas/spec_decode.yaml:99-111, 130-142`]().
  * **Ngram & Suffix**: Covers simpler heuristic-based speculative methods [`.buildkite/test_areas/spec_decode.yaml:144-155`]().
  * **Draft Model** : Tests for the standard draft-model speculative decoding setup [`.buildkite/test_areas/spec_decode.yaml:173-182`]().
