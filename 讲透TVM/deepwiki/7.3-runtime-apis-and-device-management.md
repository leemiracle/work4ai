  This document covers TVM's runtime APIs and device management infrastructure, which provides the foundation for executing compiled models across different hardware devices. This includes device initialization, memory allocation strategies, automatic data movement between devices, and the C/Python API interfaces that expose these capabilities to users.

 
## Overview and Architecture

 The runtime system provides a unified interface for managing computational devices (CPU, CUDA, WebGPU, etc.) and memory allocation across these devices. Key responsibilities include device initialization, memory management, and data movement.

## Device API and Management

 
### Abstract Device Interface

 The `DeviceAPI` class serves as the hardware abstraction layer for all backends. It provides virtual methods for memory management and device-specific properties.

 
| Function | Description | Source |
|---|---|---|
| AllocDataSpace | Allocate raw bytes on device | include/tvm/runtime/device_api.h173-185 |
| FreeDataSpace | Release allocated memory | include/tvm/runtime/device_api.h192 |
| CopyDataFromTo | Copy data between devices or host/device | include/tvm/runtime/device_api.h193-202 |
| GetAttr | Query device properties (e.g., WarpSize) | include/tvm/runtime/device_api.h146 |
| SetDevice | Set active device for the current thread | include/tvm/runtime/device_api.h138 |

 
### Device Attributes

 Runtime properties are queried via `DeviceAttrKind` in [include/tvm/runtime/device_api.h85-103](https://github.com/apache/tvm/blob/b16cdecb/include/tvm/runtime/device_api.h#L85-L103):

 
 - `kExist`: Check if device is present.
 - `kMaxThreadsPerBlock`: GPU block size limit.
 - `kWarpSize`: Hardware execution unit size.
 - `kComputeVersion`: CUDA/OpenCL version string.
 - `kTotalGlobalMemory`: Total capacity in bytes.
 - `kAvailableGlobalMemory`: Currently free memory.

## Threading and Parallelism

 TVM provides a built-in threading backend for CPU parallelization, supporting thread affinity and various scheduling modes.

 
### Thread Groups and Affinity

 The `ThreadGroup` class manages a pool of worker threads. It supports several affinity modes in [src/runtime/threading_backend.cc168-195](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/threading_backend.cc#L168-L195):

 
 - `kLittle`: Bind to "little" cores (ARM big.LITTLE).
 - `kBig`: Bind to "big" cores.
 - `kSpecifyOneCorePerThread`: Explicit mapping where each thread gets one core.
 - `kSpecifyThreadShareAllCore`: Threads share a specified set of cores.
 
 The physical binding is implemented in `SetThreadAffinity` using `pthread_setaffinity_np` or `sched_setaffinity` [src/runtime/threading_backend.cc115-144](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/threading_backend.cc#L115-L144)

 
### Parallel Launcher and Thread Pool

 The `ParallelLauncher` coordinates parallel task execution by resetting task requests and managing synchronization counters [src/runtime/thread_pool.cc71-148](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/thread_pool.cc#L71-L148)

 Worker threads consume tasks from a `SpscTaskQueue` (Single-Producer Single-Consumer). This queue uses a ring buffer and atomic head/tail pointers to achieve lock-free operation for performance [src/runtime/thread_pool.cc151-204](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/thread_pool.cc#L151-L204)

## RPC and Remote Management

 The RPC system allows TVM to manage devices remotely, facilitating cross-compilation and execution on mobile or embedded targets.

 
### RPC Sessions and Function Wrapping

 Clients interact with remote devices via `RPCSession` [python/tvm/rpc/client.py36-46](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/client.py#L36-L46) When a remote function is called, it is wrapped in an `RPCWrappedFunc` which handles the serialization of arguments to their remote variants (e.g., converting local `DLTensor` to remote handles) [src/runtime/rpc/rpc_module.cc91-153](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/rpc/rpc_module.cc#L91-L153)

 
### RPC Tracker

 The `RPCTracker` is a central hub that tracks available RPC resources. It uses a `PriorityScheduler` to distribute resources based on job priority and request order [python/tvm/rpc/tracker.py132-170](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/tracker.py#L132-L170)

## Runtime Module and Serialization

 
### Module Export and Packaging

 The `Module` class handles the packaging of compiled code. The `export_library` method packs the module and all its imports into a single shared library or system library [python/tvm/runtime/module.py148-185](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/runtime/module.py#L148-L185)

 
### Module Serialization

 `ModuleSerializer` is a utility used to convert a tree of runtime modules into a binary stream. It handles:

 
 - **DSO Merging**: Merging all `kCompilationExportable` modules into a single library entry [src/target/codegen.cc105-145](https://github.com/apache/tvm/blob/b16cdecb/src/target/codegen.cc#L105-L145)
 - **Import Tree Preservation**: Serializing the hierarchy of module imports so it can be reconstructed on load [src/target/codegen.cc173-200](https://github.com/apache/tvm/blob/b16cdecb/src/target/codegen.cc#L173-L200)
 - **Binary Serialization**: For non-DSO modules (like CUDA kernels or metadata), it calls the module's `SaveToBytes` method [src/target/codegen.cc76-82](https://github.com/apache/tvm/blob/b16cdecb/src/target/codegen.cc#L76-L82)
