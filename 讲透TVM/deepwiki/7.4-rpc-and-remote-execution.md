  The TVM RPC (Remote Procedure Call) infrastructure enables cross-compilation and remote execution by allowing a host machine (client) to control a remote device (server). This is critical for deep learning workflows where models are compiled on powerful x86 machines but executed on resource-constrained edge devices like Android phones, iOS devices, or embedded NPUs.

 
## System Architecture

 The RPC system consists of three primary components: the **Client**, the **Tracker**, and the **Server**. They communicate over TCP using a custom handshake and message protocol [python/tvm/rpc/server.py22-27](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/server.py#L22-L27)

 
### Communication Workflow

 
 - **Tracker**: A central hub that maintains a registry of available remote devices [python/tvm/rpc/tracker.py17-19](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/tracker.py#L17-L19)
 - **Server**: Runs on the target device, reports its availability to the Tracker, and waits for connections [apps/cpp_rpc/rpc_server.cc134-144](https://github.com/apache/tvm/blob/b16cdecb/apps/cpp_rpc/rpc_server.cc#L134-L144)
 - **Client**: Requests a device from the Tracker and establishes a direct session with the Server to upload modules and run functions [python/tvm/rpc/client.py36-45](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/client.py#L36-L45)

## RPC Server Implementation

 The RPC server can be implemented in C++ (for performance and portability) or Python. It handles module loading, function execution, and workspace management on the remote device.

 
### C++ RPC Server

 The C++ server (`apps/cpp_rpc`) is designed for embedded environments. It uses a `ListenLoopProc` to accept connections and typically forks a new process for each session to ensure isolation and timeout management [apps/cpp_rpc/rpc_server.cc134-188](https://github.com/apache/tvm/blob/b16cdecb/apps/cpp_rpc/rpc_server.cc#L134-L188)

 Key features include:

 
 - **RPCEnv**: Manages the server's working directory and provides global functions like `tvm.rpc.server.workpath` and `tvm.rpc.server.load_module` [apps/cpp_rpc/rpc_env.cc101-121](https://github.com/apache/tvm/blob/b16cdecb/apps/cpp_rpc/rpc_env.cc#L101-L121)
 - **Dynamic Linking**: On Linux/Android, it can compile uploaded `.o` or `.tar` files into shared libraries using `g++` or `clang` at runtime [apps/cpp_rpc/rpc_env.cc190-195](https://github.com/apache/tvm/blob/b16cdecb/apps/cpp_rpc/rpc_env.cc#L190-L195)
 - **Timeout Control**: Uses `waitpid` and `kill` to terminate worker processes that exceed the session timeout [apps/cpp_rpc/rpc_server.cc171-188](https://github.com/apache/tvm/blob/b16cdecb/apps/cpp_rpc/rpc_server.cc#L171-L188)
 
 
### Android/iOS Specifics

 For mobile platforms, TVM provides specialized apps:

 
 - **Android**: Uses JNI to bridge the Java UI with the C++ `tvm_runtime` [apps/android_rpc/app/src/main/jni/tvm_runtime.h21-30](https://github.com/apache/tvm/blob/b16cdecb/apps/android_rpc/app/src/main/jni/tvm_runtime.h#L21-L30) It overrides logging to redirect TVM messages to `logcat` [apps/android_rpc/app/src/main/jni/tvm_runtime.h98-107](https://github.com/apache/tvm/blob/b16cdecb/apps/android_rpc/app/src/main/jni/tvm_runtime.h#L98-L107)
 - **iOS**: Implements a similar bridge using Objective-C++ (`TVMRuntime.mm`).

## Data Flow and Remote Execution

 When a client invokes a function on a remote session, the arguments are serialized and sent via the `RPCEndpoint`.

 
### Argument Serialization

 The `EventHandler` within `RPCEndpoint` manages the state machine for sending and receiving packets [src/runtime/rpc/rpc_endpoint.cc58-74](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/rpc/rpc_endpoint.cc#L58-L74)

 
 - **Local to Remote**: Tensors are converted to a remote-compatible view where the `data` pointer refers to a handle on the server [src/runtime/rpc/rpc_module.cc55-65](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/rpc/rpc_module.cc#L55-L65)
 - **Session Masking**: Devices are encoded with a session-specific mask (`base.RPC_SESS_MASK`) to ensure the runtime knows which RPC session a device belongs to [python/tvm/rpc/client.py91-95](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/client.py#L91-L95)

## The Tracker and Proxy System

 To handle devices behind firewalls or to manage a pool of devices, TVM uses a Tracker and an optional Proxy.

 
### Tracker (RPCTracker)

 The Tracker implements a `PriorityScheduler` to distribute resources [python/tvm/rpc/tracker.py132-135](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/tracker.py#L132-L135)

 
 - **PUT**: Servers register themselves with a `match_key` [python/tvm/rpc/tracker.py34-37](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/tracker.py#L34-L37)
 - **REQUEST**: Clients request a device by key. The tracker returns the server's address and the `match_key` [python/tvm/rpc/tracker.py38-41](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/tracker.py#L38-L41)
 
 
### Proxy (RPCProxy)

 The Proxy acts as an intermediary when the Client and Server cannot see each other directly (e.g., the Server is on a private mobile network). Both Client and Server connect to the Proxy, which tunnels the RPC traffic [python/tvm/rpc/proxy.py](https://github.com/apache/tvm/blob/b16cdecb/python/tvm/rpc/proxy.py)

 
| Feature | Tracker | Proxy |
|---|---|---|
| Role | Resource Directory | Network Bridge / Tunnel |
| Protocol | JSON-based control messages | Transparent byte stream |
| Entity | PriorityScheduler | TCPProxy |

## Key Runtime Classes

 
### `RPCSession` (C++)

 The base class for all RPC sessions. It defines the interface for `CallFunc`, `GetFunction`, and `FreeHandle` [src/runtime/rpc/rpc_session.h](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/rpc/rpc_session.h)

 
### `RPCModuleNode` (C++)

 A specialized `ModuleNode` that represents a module residing on a remote server. When `GetFunction` is called on this module, it returns an `RPCWrappedFunc` that triggers a remote call when executed [src/runtime/rpc/rpc_module.cc184-190](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/rpc/rpc_module.cc#L184-L190)

 
### `RPCWrappedFunc` (C++)

 A `ffi::Function` implementation that wraps a remote function handle. It handles the translation of local `DLTensor` objects into remote handles before sending the call packet [src/runtime/rpc/rpc_module.cc91-114](https://github.com/apache/tvm/blob/b16cdecb/src/runtime/rpc/rpc_module.cc#L91-L114)
