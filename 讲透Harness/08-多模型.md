# 08 · 多模型 harness：验证即级联

> 核心实验：**E6 verify-then-escalate**（[experiments/e6_verify_cascade.py](../experiments/e6_verify_cascade.py)）

## 直觉

多模型系统的核心问题不是"用哪个模型"，是**"谁做决定、何时换"**。Ensemble 综述（arXiv:2502.18036）三阶段全家桶里，工程上最划算的是 cascade（c2）：便宜模型先答，**deferral rule** 决定是否升级。而 deferral rule 的谱系（用户判断→一致性→不确定性→打分器）都回避了一个问题：**如果你的任务有免费验证器，为什么要学一个打分器？**

## 本地复现（E6）

设计：Tier-1 glm-4-flash（成本权重 1）生成 → **V2 真执行验证**（E2 结论：3ms、零误杀）→ 失败才升级 glm-5（权重 20）带错误反馈重生成。三基线对决：

```bash
cd 讲透Harness/experiments && timeout 1150 python3 e6_verify_cascade.py
```

**结果（results/e6_verify_cascade.json）**：

| 方案 | 完成率 | 成本单位 |
|---|---|---|
| all_flash | 100% | 6 |
| **cascade（flash→V2→glm-5）** | **100%** | **6（升级 0 次触发）** |
| all_glm5 | 100% | 120（**20×**） |

![E6](../experiments/results/e6_verify_cascade.png)

## 读数：零遗憾属性与它的边界

1. **易分布上 cascade ≡ all_flash**：glm-4-flash 全过 6 题 → 升级路径零触发 → cascade 拿到 all_glm5 的完成率，付 all_flash 的钱（1/20）。这是"验证门控级联"的**零遗憾侧**：验证器通过就省钱，不通过才花钱。
2. **诚实标注不足**：升级路径（救回侧）未在本任务池触发——演示了不亏损，没演示救回。E6b 需要 flash 失败的难分布（更难的任务/结构化输出/长上下文）。**报告实验时写明哪些路径没被 exercise，和写结果一样重要。**
3. **方法论输出**：**验证免费（代码可 exec）的场景不需要学 router/打分器**——Ensemble 综述 (c2) 的 deferral rule 谱系是为"验证昂贵"的任务（开放生成）设计的；你的 harness 若已有 V2，直接用它当 deferral rule，一步省掉一个训练管线。
