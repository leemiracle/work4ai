## §0 全局视角：RAG 是 attention 的"外部记忆"延伸

| | 标准 attention | RAG |
|---|---------------|-----|
| 对齐对象 | 序列内 token ↔ token | query ↔ 外部文档 |
| 记忆来源 | 训练时学到的权重 | 推理时检索的外部库 |
| 更新成本 | 重训（极贵）| 重建索引（中）|
| 可解释性 | 弱 | 强（可指出处）|
| 适用规模 | 受 context window 限制 | 可扩展到亿级文档 |

> 🔑 **核心洞察**：**RAG 本质上是"把 attention 的 K/V 库从权重里搬到外部"**——这样 K/V 可以动态更新、可以更大、可解释。这是 attention 思想的自然延伸。

### 算法经验 G1：RAG = 外部化的 attention K/V 库

> 从 attention 视角看 RAG：
> - **embedding 库** = 外部的 K（key）
> - **文档内容** = 外部的 V（value）
> - **query 编码** = Q
> - **检索** = $\text{softmax}(QK^\top)$ 的 top-k 稀疏版
> - **生成** = 用检索到的 V 做 conditioned generation

可迁移：**任何"权重装不下"的知识，都可以用 RAG 式的外部 K/V 库**——这是 attention 的"外挂扩展"。

## §2 GraphRAG 的算法本质：图抽象 + 层次化摘要

### 2.1 GraphRAG 解决什么？

**朴素 RAG 的盲区**（Ch11 R9 天花板）：检索只能找局部片段，**全局问题**（"这批文档的核心主题"）拼不出全景。

### 2.2 算法本质

```
文档库 → [LLM 抽取实体+关系] → 知识图谱
       → [社区发现算法] → 主题社区
       → [LLM 生成社区摘要] → 层次化摘要
       
查询时:
  局部问题 → 图检索（找相关实体）
  全局问题 → 直接用社区摘要
```

### 2.3 算法经验 G2：层次化摘要是"全局理解"的通用方法

> GraphRAG 的核心算法 DNA：**层次化摘要（hierarchical summarization）**——把大量信息层层压缩成高层表示。
>
> 这个模式反复出现：
> - **CNN 的池化层**：低层特征 → 高层语义
> - **Transformer 的层**：低层 token → 高层表示
> - **决策树**：叶子节点 → 内部节点 → 根
> - **Map-Reduce**：分布式计算 → 中间结果 → 最终结果
> - **层次化注意力**（HAN）：word → sentence → document

可迁移：**任何"要理解全局"的任务，先想层次化摘要——把细节聚合成中间表示**。

### 算法经验 G3：图结构能编码关系，向量不能

> GraphRAG 用知识图谱而不是单纯向量库，因为**图能编码"实体间关系"，向量不能**。
>
> - 向量：编码"实体相似度"
> - 图：编码"实体的关系（朋友/敌人/师生/竞争）"

可迁移：
- **推荐**：user-item 矩阵（向量）vs social graph（图）
- **化学**：分子指纹（向量）vs 分子图（GNN）
- **知识图谱**：实体嵌入 vs 关系图

**经验**：**当任务依赖"关系"而非"相似度"，必须用图结构**。

## §3 Self-RAG 的算法本质：元认知 token

### 3.1 Self-RAG 解决什么？

朴素 RAG 不管什么问题都检索（"1+1=?" 也去查），引入噪声。

### 3.2 算法本质

训练模型输出**反思 token**：

```
[Retrieve] 这个问题需要检索吗？
[Relevant] 检索到的文档相关吗？
[Supported] 答案有文档支撑吗？
```

模型自适应决策——简单问题直接答，复杂问题才检索。

### 3.3 算法经验 G4：元认知 token = 模型自控的"控制流"

> Self-RAG 用特殊 token 让模型**控制自己的执行流**。这个模式来自 Ch9 的 RL with human feedback，但应用到了"控制检索"上。
>
> 通用模式：**给模型加上"决策 token"，让它自己决定下一步做什么**——这是 agentic 的雏形。

可迁移：
- **CoT**：`<think>...</think>` 让模型显式思考
- **Tool use**：`<call_tool>...</call_tool>` 让模型决定何时调工具
- **ReAct**：`<thought>/<action>/<observation>` 让模型规划-执行
- **Self-RAG**：`<retrieve>/<relevant>/<supported>` 让模型控制检索

### 算法经验 G5：自反思是提升可靠性的通用方法

> Self-RAG 的"自检答案是否忠于文档"是一种**自反思（self-reflection）**——模型不仅生成，还评估自己的输出。
>
> 这是提升可靠性的通用方法：
> - **代码生成**：生成后自审 + 测试
> - **数学推理**：生成后验证答案
> - **写作**：草稿 → 自审 → 修改
> - **RAG**：生成后检查 faithfulness

可迁移：**任何"可靠性要求高"的生成任务，都该加自反思环节**。

## §4 CRAG 的算法本质：评估-纠错循环

### 4.1 CRAG 解决什么？

朴素 RAG 检索到垃圾文档也硬着头皮生成，导致错误。

### 4.2 算法本质

```
检索 top-k → [检索评估器打分]
              ├── 正确 → 精炼使用
              ├── 含糊 → 部分采用 + 补充检索
              └── 错误 → 丢弃 + 网络搜索 / 重检 / 模型自身知识
```

### 4.3 算法经验 G6：评估-纠错循环是工程鲁棒性的核心

> CRAG 的"评估 + 纠错"是**控制论中的反馈循环**——在工程系统里无处不在：
> - **自动驾驶**：感知 → 决策 → 控制 → 监控异常 → 兜底
> - **数据库**：查询 → 验证 → 回滚
> - **CI/CD**：构建 → 测试 → 部署 → 监控 → 回滚
> - **RAG**：检索 → 评估 → 纠错（重检索/网络搜索/凭知识答）

可迁移：**任何"输入质量不可控"的系统，都该加评估-纠错环节**。这是工程鲁棒性的核心模式。

## §5 Agentic RAG 的算法本质：规划-执行-反思

### 5.1 Agentic RAG 解决什么？

复杂研究型问题（"对比 A 和 B 公司近三年财报"）需要多次检索、规划、整合。

### 5.2 算法本质

```
query → [Agent 规划: 分解成子问题]
        ├── 检索 1: A 公司 2022 财报
        ├── 检索 2: A 公司 2023 财报
        ├── 检索 3: B 公司 2022 财报
        ├── ...
        → [Agent 反思: 够不够? 不够继续查]
        → [Agent 综合: 整合多源信息]
        → 答案
```

### 5.3 算法经验 G7：规划-执行-反思是 Agent 的核心循环

> Agentic RAG 是**通用 Agent 框架**的具体实例——所有 agentic 系统都遵循"规划-执行-反思"循环：
>
> - **规划**（Plan）：把大目标分解成子任务
> - **执行**（Execute）：调用工具完成子任务
> - **反思**（Reflect）：评估结果，决定继续/调整/终止

可迁移（这是 Agent 时代的元范式）：
- **ReAct**（Reasoning + Acting）
- **Tree of Thoughts**（Ch9 §4.5）
- **AutoGPT / BabyAGI**
- **Devin / SWE-Agent**（编程 agent）
- **Research Agent**（科研 agent）

## §6 与 Ch9 后训练打通：偏好对齐 vs 忠实对齐

### 6.1 两种"对齐"

| | Ch9 RLHF/DPO | RAG 的 faithfulness |
|---|-------------|--------------------|
| 对齐什么 | 模型偏好 ↔ 人类偏好 | 模型回答 ↔ 检索文档 |
| 训练数据 | (prompt, chosen, rejected) | (query, doc, answer, supported?)|
| 目标 | 让 chosen 概率高 | 让答案忠于文档 |
| 失败模式 | Reward hacking | 幻觉、夹带私货 |
| 评估 | Chatbot Arena | RAGAS faithfulness |

### 6.2 算法经验 G8：RAG 让 LLM "对齐到证据"，不只对齐到偏好

> Ch9 的 RLHF 是**对齐到人类偏好**（让回答更受欢迎），RAG 是**对齐到证据**（让回答有依据）。
>
> 两种对齐互补：
> - 偏好对齐 → 让模型"说得好听"
> - 忠实对齐 → 让模型"说得有据"

可迁移：**任何生成系统都该有两种对齐——偏好对齐（用户体验）+ 证据对齐（事实正确）**。

## §7 与 Ch10 BERT 打通：双塔的本质

### 7.1 RAG 检索器的"双塔"就是 Ch10 的"独立编码"

| | BERT bi-encoder | RAG 检索器 |
|---|----------------|-----------|
| 架构 | query 塔 + doc 塔 | query 塔 + chunk 塔 |
| 输出 | 各自向量 | 各自向量 |
| 相似度 | cos | cos |
| 微调 | NLI 数据 | (query, positive, negative) 对 |

### 7.2 算法经验 G9：双塔的"独立编码"是工程必然

> 为什么所有大规模检索都用双塔？因为**独立编码 = 可预计算 = 可 ANN**。
>
> 这是工程上的硬约束——任何"无法预计算"的架构都上不了亿级规模。

可迁移（对应 Ch11 R4）：**大规模匹配系统的设计起点，永远是双塔**。

## §8 与 Ch11/Ch12 打通：检索对齐的演化

### 8.1 检索对齐的三个层次（与 Ch12 对齐演化同构）

| 阶段 | 对齐方式 | 算法 |
|------|---------|------|
| **BM25（2000s）** | 离散词重叠 | TF-IDF + IDF |
| **Dense Retrieval（2020s）** | 连续向量相似度 | DPR, BGE, E5 |
| **ColBERT（2020）** | token-level 对齐矩阵 | late interaction |
| **Cross-encoder** | 全交叉 attention | fine-grained |

### 8.2 算法经验 G10：检索对齐 = MT 对齐 = attention 对齐

> **三种"对齐"本质相同**（Ch12 T5）：
> - MT 的源-目标词对齐
> - 检索的 query-doc 对齐
> - attention 的 token-token 对齐
>
> 算法 DNA 完全一致——都是"算相似度 → 归一化 → 加权聚合"。

## §9 批判性：RAG 的工程边界

### 9.1 RAG 不是万能的

| 局限 | 表现 | 缓解 |
|------|------|------|
| 检索器是天花板（Ch11 R9）| 召回不到就答不出 | 混合检索 + rerank |
| 上下文污染 | 多个 chunk 拼接，噪声大 | 精排 + filter |
| lost in the middle | 长 prompt 中间信息被忽略 | 重排 + 重要信息放头尾 |
| 成本高 | 每次查询要检索 + 长上下文生成 | 缓存 + 模型蒸馏 |
| 评估难 | RAGAS 等指标不完美 | 人工评估 + 多指标 |

### 9.2 长上下文会替代 RAG 吗？

| 维度 | 长上下文 LLM | RAG |
|------|-------------|-----|
| 适合规模 | < 1M token | > 1M token |
| 单次成本 | 高（处理全部）| 低（只处理 top-k）|
| 可更新性 | 慢 | 快 |
| 可解释性 | 差 | 好 |

> **答案：互补，不是替代**。长上下文适合"小而精"的文档，RAG 适合"大而广"的库。

### 9.3 算法经验 G11：架构选择永远是权衡

> **没有任何架构是"银弹"**——朴素 RAG、GraphRAG、Agentic RAG、长上下文 LLM 都有自己的甜区。
>
> **工程原则**：先用最简单的（朴素 RAG），不够再升级。
