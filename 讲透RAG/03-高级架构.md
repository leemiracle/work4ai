# 03 — 高级 RAG 架构：GraphRAG / Agentic RAG / Self-RAG / CRAG

> 00-02 讲的是"朴素 RAG"（一次检索 + 生成）。但很多真实场景它不够用。这一篇讲四种进阶架构，各自解决朴素 RAG 的什么短板。本篇概念为主。

---

## 朴素 RAG 的四个短板

| 短板 | 表现 |
|---|---|
| **多跳推理弱** | "A 的发明者的导师是谁"要连查两次，一次检索不够 |
| **全局问题弱** | "整个文档库的核心主题是什么"——检索只能找局部片段 |
| **不该检索时也检索** | "1+1=?" 不需要文档，检索反而添乱 |
| **检索到垃圾不纠错** | 检索回不相关文档，模型仍硬基于它生成 |

四种进阶架构对症下药：

---

## 1. GraphRAG（微软 2024）：用知识图谱答全局问题

**朴素 RAG 的痛**：问"这批文档讲了什么主题/各主题关系"，向量检索只能返回零散片段，拼不出全局图景。

**GraphRAG 的解法**：
1. 先用 LLM 从所有文档**抽取实体+关系**，建知识图谱。
2. 用图算法（社区发现）把图谱**聚成主题社区**，每个社区生成摘要。
3. 查询时：局部问题走图检索，**全局问题直接用社区摘要回答**。

**适用**：文档库级的全局分析、主题梳理、多实体关系推理。

---

## 2. Agentic RAG：让 Agent 自主规划检索

**朴素 RAG 的痛**：复杂问题（"对比 A 和 B 公司近三年财报"）需要多次检索、规划、整合，单次检索搞不定。

**Agentic RAG**：把 RAG 包进 Agent，让 LLM **自己决定**：
- 检索几次、检索什么
- 中间结果够不够、要不要再查
- 多个信息源怎么整合

典型流程：query → Agent 规划 → 检索1 → 分析 → 检索2 → 综合 → 回答。

**适用**：复杂研究型问题、多跳推理、需要工具调用的场景。

---

## 3. Self-RAG（自反思 RAG）：模型自己判断要不要检索

**朴素 RAG 的痛**：不管什么问题都检索。"1+1=?" 也去查文档，浪费且可能引入噪声。

**Self-RAG**：训练模型输出**反思 token**：
- `[Retrieve]`：这个问题需要检索吗？
- `[Relevant]`：检索到的文档相关吗？
- `[Supported]`：生成的答案有文档支撑吗？

模型**自适应**：简单问题直接答（不检索），复杂问题才检索，且自检答案是否忠于文档。

**适用**：混合场景（有的问题要检索有的不要）、提升可靠性。

---

## 4. CRAG（Corrective RAG, 2024）：检索质量评估 + 纠错

**朴素 RAG 的痛**：检索回不相关文档，模型仍硬着头皮基于它生成，导致错误。

**CRAG**：加一个**检索评估器**，给检索结果打分：
- **正确**（相关）：直接用，精炼一下。
- **错误**（不相关）：丢弃检索结果，改用网络搜索 / 重新检索 / 让模型凭自身知识答。
- **含糊**：部分采用 + 补充检索。

**核心思想**：检索不是"查到就用"，而是"查到先评估、不好就纠错"。

---

## 5. 选择指南

| 场景 | 推荐 |
|---|---|
| 简单问答、文档查询 | **朴素 RAG**（够用，别过度工程） |
| 全局主题/多实体关系 | **GraphRAG** |
| 复杂多跳/研究型 | **Agentic RAG** |
| 混合（有的要检索有的不要）+ 高可靠 | **Self-RAG** |
| 检索质量参差、要纠错 | **CRAG** |

**提醒**：这些进阶架构都用更多 LLM 调用（建图/规划/反思/纠错），**成本和延迟显著上升**。先用朴素 RAG，不够再升级——别一上来就 GraphRAG。

---

## 6. 一句话总结

> **朴素 RAG 的短板由四种进阶架构补：GraphRAG 建知识图谱答全局问题；Agentic RAG 让 Agent 自主规划多次检索；Self-RAG 让模型自判要不要检索+自检答案；CRAG 评估检索质量并纠错。它们都更准但更贵，原则是"先朴素，不够再升级"。**
