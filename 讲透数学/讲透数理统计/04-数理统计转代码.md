# 04 · 数理统计转代码:推断的代码化身

> **本章回答五问之五:这个分支的问题怎么变成 code 问题?**

> 本章按三件套展开:**可机械化边界 / 代码走廊清单 / 工程师落点**。

## 一、可机械化边界:什么能算、什么算不了

**能机械化的**(有原理保证的"算"):

| 推断动作 | 机械化形态 | 保证来自 |
|---------|-----------|---------|
| 点估计(MLE/GLM) | 优化器调用(牛顿/IRLS/L-BFGS) | 指数族凸性+渐近正态(03 章) |
| 区间估计 | 公式版(精确分布)/bootstrap 版/конформ版 | Student 精确分布;Glivenko–Cantelli;交换性 |
| 假设检验 | 拒绝域查表代码/FDR 流水线 | Neyman–Pearson;BH(1995) |
| 贝叶斯后验 | MCMC/变分推断 | 遍历定理(马尔可夫链);ELBO 下界 |
| 试验设计 | 随机化+功效算力(power analysis) | Fisher 随机化原理 |

**机械化不了的边界**(为什么——原理级回答):
1. **"这次结论对不对"不可算**:频率保证属于程序长程,单次推断无真值可查——
   代码只能输出"程序的性质",不能输出"本次判决的可靠度"
2. **无假设的分布形状不可"学"出来**:非参数方法仍依赖光滑性/带宽选择;
   维数灾难=样本量需求随维数指数涨,这不是算力问题,是**信息下界**(03 章)
3. **p 值的自动化滥用恰好是最容易机械化的部分**——可机械化≠该机械化:
   "p<0.05 即输出显著"的流水线正是复现危机的机器形态。统计代码化的第一戒律:
   **先写假设与保证,再写循环**

## 二、代码走廊清单(从零到一的五条走廊)

**走廊 1:抽样分布的数值自检**(对应 00 章)
不查表,自己摸:模拟 10000 次样本均值 → 看直方图与 CLT 预言的正态重合度。
任何"分布长相"问题都可这样亲眼验证。

**走廊 2:Bootstrap——万能误差条**(对应 03 章)
```python
idx = rng.integers(0, n, (B, n))          # B 个重样本索引
theta_star = stat(data[idx], axis=1)      # 每个重样本算统计量
se, ci = theta_star.std(), np.quantile(theta_star, [.025, .975])
```
四行=一个无公式的置信区间。中位数/相关系数/任意统计量通用。

**走廊 3:FDR 流水线**(对应 01 章,家族实验 `experiments/00_fdr.py`)
多重检验的标准姿势:p 值排序→BH 阈值→报告"发现集+实测 FDR"。
A/B 平台与组学分析的法定出口。

**走廊 4:MCMC——后验的采样器**(对应贝叶斯支)
梅特罗波利斯-黑斯廷斯 20 行:提议-接受-记录。后验均值/区间全部从样本路径读出。
(进阶:共轭-吉布斯;工程级:PyMC/Stan。)

**走廊 5:仿真即实验**(对应试验设计支)
功效计算反过来用:**先造一个假世界,在里面跑你的检验**,看它多久能发现效应——
"这个实验需要多少样本"的答案不再靠查表,靠仿真。A/B 测试的样本量规划即此。

## 三、工程师落点(性能工程视角)

| 落点 | 统计原理 | 工程现场 |
|------|---------|---------|
| A/B 测试平台 | 假设检验+功效+序贯修正 | 增长团队的一切按钮:分流=随机化,看板=检验输出 |
| 可观测性指标的可信度 | 置信区间+方差缩减(对照/公共随机数) | "P99 涨了 3%"——是涨了还是噪声?CI 说 |
| 多重比较治理 | BH-FDR/分层检验 | 告警风暴:上千监控项同时检验,不校正=假警报工厂 |
| LLM 评测 | bootstrap 置信差+conformal 校准 | "模型 A 比 B 好 0.8 分"必须带不确定度,否则是玄学 |
| 缓存/负载的预测区间 | 时序预测+ conformal 壳 | 容量规划要的是 P97.5 需求,不是均值 |
| 实验速度 | CUPED(方差缩减=回归残差化) | 同样样本量,功效翻倍——统计直接省机器 |

**性能工程特别提示**:大规模仿真(bootstrap B=10⁶、蒙特卡洛功效扫描)是**天然可并行**
的(重样本间独立)——向量化的 numpy/多进程/GPU 全部适用;
但注意 RNG 种子的流管理(并行流独立性=统计独立性假设的代码化,用 SeedSequence spawn)。

## 四、一个完整案例:从问题到代码的全链路

**问题**:新推荐算法上线一周,CTR 从 2.10% 到 2.14%,该全量吗?

1. **翻译成统计问题**:两比例之差的检验(假设检验支)
2. **设计**→本例是事后数据,先检查随机化与样本量(试验设计支的"事后审计")
3. **推断代码**:`proportions_ztest` 得 p 值与 CI;若按天分段再看时序稳定性(时序支)
4. **多重性**:一周里同时测了 40 个指标→对决策指标做 BH(走廊 3)
5. **决策**:效应量+CI+成本,写成损失函数(判决理论支)——全量与否是风险问题不是 p 值问题
6. **复验**:预注册下次实验,防 data snooping(01 章选择性推断)

一条链走完十二支的一半——这就是"统计的语法,工程的句子"。

## 五、为什么不直接"全部交给 ML"

常见混淆:统计推断 vs 学习理论预测(成员 [`../讲透统计学习理论/`](../讲透统计学习理论/))——
预测问"下一个准不准"(泛化误差),推断问"参数/结构对不对"(置信与检验);
两者数学上共用浓度工具(高维概率),但**回答的合同不同**。工程里两者混装:
模型选型用泛化、定价用推断、监控用时序——错配合同是最常见的"统计事故"来源。
