## Purpose and Scope

 This page details the implementation of SGLang’s scheduling policies, batch formation strategies, memory budgeting techniques, and the specialized Diffusion LLM (DLLM) scheduler mixin. It explains how the scheduler selects requests for execution, forms batches respecting memory constraints, and dynamically manages prefix caching across device and host memory tiers.

 
## Scheduler Architecture and Scheduling Policies

 The scheduler manages request queuing, prioritization, and execution batching. It interfaces with the radix cache layer to exploit prefix matches, reducing memory footprint and computation by reusing previously computed KV (Key-Value) tokens.

 
### Scheduling Policies Overview

 The scheduler supports several scheduling policies, typically selected via `ServerArgs` [python/sglang/srt/server_args.py15-188](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/server_args.py#L15-L188) These policies determine the order in which requests are moved from the `waiting_queue` to an active `ScheduleBatch`.

 
| Scheduling Policy | Identifier | Description |
|---|---|---|
| FCFS | FCFS | First-Come-First-Served. Orders requests by arrival time. |
| LPM | LPM | Longest Prefix Match. Prioritizes requests with the largest existing prefix match in the RadixCache. |
| DFS | DFS_WEIGHT | Depth-First Search weighting. Prefers requests that extend deep into existing cache branches. |
| ROUTING_KEY | ROUTING_KEY | Prioritizes requests based on routing key frequency to optimize for specific multi-tenant scenarios. |

 The logic for these policies and the `SchedulePolicy` class are implemented in the request scheduler components [python/sglang/srt/managers/schedule_policy.py27-64](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_policy.py#L27-L64)

 
### Priority Scheduling and Preemption

 When priority scheduling is enabled, the scheduler can implement preemption. If the memory budget is exceeded by a high-priority request, the scheduler may retract lower-priority requests from the running batch back to the `waiting_queue`, releasing their KV cache allocations via the `release_kv_cache` mechanism [python/sglang/srt/mem_cache/common.py117-119](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/common.py#L117-L119)

 Before a request is scheduled, the system performs a prefix match against the `RadixCache`. ### Memory Budgeting and Allocation

 SGLang uses a sophisticated allocation system to manage KV cache across tiers. The `UnifiedRadixCache` manages components like `FullComponent` (standard MHA/MLA), `SWAComponent` (Sliding Window), and `MambaComponent` [python/sglang/srt/mem_cache/unified_radix_cache.py111-116](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/unified_radix_cache.py#L111-L116)

 Memory budgeting involves:

 
 - **Prefill Admission:** Ensuring enough free blocks exist to store the new KV tensors for the prompt.
 - **Decode Reservation:** Reserving space for the `max_new_tokens` to prevent runtime OOM (Out-of-Memory), though this is often clipped by `CLIP_MAX_NEW_TOKENS` (default 4096) to be less conservative [python/sglang/srt/managers/schedule_policy.py73-75](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_policy.py#L73-L75)
 - **Prefill Tile Budget:** On AMD/HIP hardware, the scheduler can use `PREFILL_TILE_BUDGET` to control the compute intensity of prefill batches [python/sglang/srt/managers/schedule_policy.py98-105](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_policy.py#L98-L105)
 
 
### Batch Modes

 Batches are formed in different `ForwardMode` states defined in `ForwardBatch` [python/sglang/srt/managers/schedule_batch.py122-126](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L122-L126):

 
 - **PREFILL:** Processing new prompt tokens.
 - **DECODE:** Generating one token for multiple requests simultaneously.
 - **EXTEND:** Extending an existing sequence.
 - **MIXED:** Combining prefill and decode in one forward pass.
 
 **Sources:** [python/sglang/srt/managers/schedule_policy.py69-135](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_policy.py#L69-L135) [python/sglang/srt/mem_cache/unified_radix_cache.py148-200](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/unified_radix_cache.py#L148-L200) [python/sglang/srt/managers/schedule_batch.py122-126](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L122-L126)

 
## Scheduler and Batch Formation Dataflow

 
### From Scheduler to ModelRunner

 The `ScheduleBatch` is a CPU-side container for requests currently being processed [python/sglang/srt/managers/schedule_batch.py200-207](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L200-L207) It holds `Req` objects which contain metadata like `prefix_indices` and `last_node` in the radix tree.

 When the batch is sent to the `ModelRunner`, it is transformed into a `ForwardBatch` [python/sglang/srt/model_executor/forward_batch_info.py96-99](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/forward_batch_info.py#L96-L99) This transformation involves converting the abstract request metadata into concrete CUDA tensors (e.g., `req_to_token` mappings) that the attention kernels use to locate KV data in the `TokenToKVPool`.

## Hierarchical Cache (HiCache) and DLLM

 
### HiCache Integration

 When `HiRadixCache` is used, the scheduler must account for tokens that exist on the **Host (CPU)** but not on the **Device (GPU)**. The `HiCacheController` manages the asynchronous `CacheOperation` to load these tokens back to the GPU before or during execution [python/sglang/srt/mem_cache/hiradix_cache.py172-188](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/hiradix_cache.py#L172-L188)

 
### Diffusion LLM (DLLM) Support

 For discrete diffusion models (e.g., LLaDA), the scheduler uses `DllmConfig` and the `SchedulerDllmMixin` to handle the iterative denoising process [python/sglang/srt/srt/managers/scheduler.py100](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/srt/managers/scheduler.py#L100-L100) Unlike standard auto-regressive decoding, DLLM scheduling involves multiple denoising steps where masked tokens are refined, requiring specific batch formation strategies that preserve the fixed-length sequence across iterations [python/sglang/srt/managers/schedule_batch.py96](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L96-L96)
