## Purpose and Scope

 This document provides a detailed explanation of SGLang's `RadixCache` system, which implements a radix tree structure for prefix sharing of KV caches across concurrent requests. This design enables efficient reuse of cached KV states for common prefixes, thereby reducing redundant computation and memory use when serving LLM and VLM requests.

 We cover the radix tree data structure, prefix matching and splitting algorithms, eviction policies, specialized cache variants, integration with schedulers, and highlight the C++ radix cache implementation. The page bridges conceptual prefix sharing ideas with concrete code entities in SGLang's codebase.

 For related memory management internals, see [Memory Pools and Token-to-KV Mapping (5.1)](https://github.com/sgl-project/sglang/blob/94183a8d/Memory Pools and Token-to-KV Mapping (5.1)) and for hierarchical cache design, see [HiCache Multi-Tier Storage (5.3)](https://github.com/sgl-project/sglang/blob/94183a8d/HiCache Multi-Tier Storage (5.3))

## RadixCache Tree Structure

 `RadixCache` organizes cached KV states using a radix tree (compact prefix tree) where each node corresponds to a contiguous token sequence with associated KV cache data.

 
### TreeNode Data Structure

 Each `TreeNode` (or `UnifiedTreeNode` in the unified implementation) stores:

 
 - `key`: The token sequence segment representing this node, encapsulated as a `RadixKey` [python/sglang/srt/mem_cache/radix_cache.py82](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L82-L82)
 - `value`: The device (e.g., GPU) memory indices where the KV cache corresponding to this node’s prefix is stored [python/sglang/srt/mem_cache/radix_cache.py83](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L83-L83)
 - `children`: A mapping from the next token ID to child TreeNode objects [python/sglang/srt/mem_cache/radix_cache.py80](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L80-L80)
 - `parent`: Reference to the parent TreeNode [python/sglang/srt/mem_cache/radix_cache.py81](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L81-L81)
 - `full_lock_ref`: A counter protecting active usage of this node’s KV cache, preventing eviction [python/sglang/srt/mem_cache/radix_cache.py91](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L91-L91)
 - `last_access_time`: Timestamp for LRU-based eviction policies [python/sglang/srt/mem_cache/radix_cache.py97](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L97-L97)
 - `hash_value`: List of hash strings for position-sensitive identification of token sequences [python/sglang/srt/mem_cache/radix_cache.py106](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L106-L106)
 - `host_value`: Optional tensor for host-level cached KV indices used in hierarchical caches [python/sglang/srt/mem_cache/radix_cache.py104](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L104-L104)

## Prefix Matching Algorithm

 Given a new request with token IDs, `RadixCache` performs a longest prefix match search to identify the deepest matching prefix in the tree and returns associated KV cache indices.

 
 - The match works on logical pages of tokens if `page_size > 1` (default 1) as a granularity optimization [python/sglang/srt/mem_cache/radix_cache.py150-155](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L150-L155)
 - Searching uses an efficient exponential search plus binary search scheme to find the first mismatching token in O(log n) time instead of linear [python/sglang/srt/mem_cache/radix_cache.py188-199](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L188-L199)

## Insertion and Cache Allocation

 After prefix matching, the unmatched token suffix is inserted as a new node or subtree:

 
 - **Allocation:** The cache allocator assigns contiguous KV cache slots for the new token pages.
 - **Creation:** If a partial match existed, the existing node is split first, then a new child node is created for the suffix tokens.
 - **Hashing:** New hash values are computed for the token sequence, chained from the parent node’s hash [python/sglang/srt/mem_cache/utils.py60](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/utils.py#L60-L60)
 
 The `insert` method (defined in `BasePrefixCache` [python/sglang/srt/mem_cache/base_prefix_cache.py24](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/base_prefix_cache.py#L24-L24)) is implemented by cache variants to carry this out atomically and update the tree structure.

## Eviction Policies

 RadixCache supports configurable eviction strategies to free device KV cache memory when capacity is constrained.

 
### Supported Strategies

 
| Strategy | Description |
|---|---|
| LRU (default) | Evicts least recently accessed nodes first based on node last_access_time python/sglang/srt/mem_cache/utils.py50 |
| LFU | Evicts least frequently used (min hit count) nodes. |
| FIFO | Evicts in insertion order. |

 
### Eviction Workflow

 
 - Gathers candidate leaf nodes with `full_lock_ref == 0` (unlocked for eviction) [python/sglang/srt/mem_cache/radix_cache.py91](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L91-L91)
 - Sorts candidates according to the chosen eviction policy [python/sglang/srt/mem_cache/utils.py50](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/utils.py#L50-L50)
 - Removes nodes until enough KV memory is freed and returns freed indices to the allocator for reuse [python/sglang/srt/mem_cache/base_prefix_cache.py20-21](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/base_prefix_cache.py#L20-L21)

## Node Hash Values and Identification

 To enable position-aware identification and hierarchical cache syncing, each TreeNode holds hash values derived from the token sequences.

 
 - `compute_node_hash_values` produces a list of SHA256 hashes chaining from the parent's last hash value, ensuring prefix sensitivity [python/sglang/srt/mem_cache/utils.py60](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/utils.py#L60-L60)
 - Each node's hash chain uniquely identifies its token sequence prefix and is used for consistent caching and storage operations.

## Integration with the Scheduler

 The scheduler uses `RadixCache` to optimize request batching by maximizing prefix reuse.

 Key steps:

 
 - **Longest Prefix Match (LPM):** Requests in the waiting queue are matched against the radix tree to find the longest cached prefix, allowing reuse of KV cache segments and reducing compute [python/sglang/srt/managers/schedule_policy.py156-167](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_policy.py#L156-L167)
 - **In-Batch Prefix Caching:** The scheduler deprioritizes requests that have high prefix matches within the waiting queue to prevent memory fragmentation and redundant prefill [python/sglang/srt/managers/schedule_policy.py81-90](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_policy.py#L81-L90)
 - **Cache Match Result:** Prefix match results update the request's `prefix_indices`, `last_node`, and `best_match_node` used by the scheduler to form batches [python/sglang/srt/managers/schedule_policy.py172-187](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_policy.py#L172-L187)

## C++ Radix Cache Implementation

 For high-performance needs, SGLang provides a C++ radix cache implementation exposed as `RadixCacheCPP`.

 
 - Implements the radix tree and prefix matching in C++ for minimal overhead in hot code paths.
 - Mirrors the structure and algorithms of the Python `RadixCache`.
 - Used to accelerate scheduling loops and KV cache management when enabled.
