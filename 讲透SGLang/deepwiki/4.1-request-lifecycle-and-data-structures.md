  This page documents the end-to-end lifecycle of a request within the SGLang Runtime (SRT), detailing the transformation of data structures and the flow of control across process boundaries, along with their implementation details, state transitions, and memory management.

 
## Overview

 A request in SGLang follows a well-defined multi-stage lifecycle with associated data structures that are transformed and passed across process boundaries:

 
 - **Input Stage**: The user request arrives via HTTP or Python Engine API as a `GenerateReqInput` that can carry textual or multimodal data [[python/sglang/srt/managers/io_struct.py168-185](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/io_struct.py#L168-L185)] [[python/sglang/srt/entrypoints/http_server.py127](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/entrypoints/http_server.py#L127-L127)].
 - **Tokenization Stage**: The `TokenizerManager` converts raw input into tokenized form, creating `TokenizedGenerateReqInput` [[python/sglang/srt/managers/tokenizer_manager.py86](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/tokenizer_manager.py#L86-L86)].
 - **Scheduling Stage**: The `Scheduler` manages readiness, batching, and assigns tokenized requests as `Req` objects grouped into a `ScheduleBatch` [[python/sglang/srt/managers/schedule_batch.py204-205](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/schedule_batch.py#L204-L205)].
 - **Execution Stage**: A `ScheduleBatch` is transformed into a `ForwardBatch` for GPU execution by the `ModelRunner` [[python/sglang/srt/managers/schedule_batch.py43-52](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/schedule_batch.py#L43-L52)].
 - **Sampling Stage**: Model logits are processed and sampled to generate next tokens [[python/sglang/srt/model_executor/model_runner.py81-82](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/model_executor/model_runner.py#L81-L82)].
 - **Output Stage**: Generated token IDs are detokenized by `DetokenizerManager` into strings returned as HTTP responses [[python/sglang/srt/managers/detokenizer_manager.py102-104](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/detokenizer_manager.py#L102-L104)].
 
 At each stage, specific data structures encapsulate request state, scheduling metadata, and batch execution elements, while lifecycle management includes memory allocation, KV cache handling, and termination conditions.

## State Transitions and Lifecycle Management

 
### KV Cache and Memory Management

 Memory pools orchestrate the mapping from request tokens to physical KV cache slots:

 
 - **ReqToTokenPool**: Maps each request to its allocated tokens' locations [[python/sglang/srt/model_executor/model_runner.py92](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/model_executor/model_runner.py#L92-L92)].
 - **BaseTokenToKVPoolAllocator**: Manages allocation of token indices to KV cache storage [[python/sglang/srt/model_executor/model_runner.py88](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/model_executor/model_runner.py#L88-L88)].
 
 Lifecycle tasks include:

 
 - **Allocation**: Handled via `alloc_for_decode` or `alloc_for_extend` [[python/sglang/srt/mem_cache/allocation.py1-20](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/mem_cache/allocation.py#L1-L20)] [[python/sglang/srt/managers/schedule_batch.py102-105](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/schedule_batch.py#L102-L105)].
 - **Release**: Triggered by `release_kv_cache` when a request finishes or is aborted [[python/sglang/srt/mem_cache/common.py117](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/mem_cache/common.py#L117-L117)].
 - **SWA Management**: `free_swa_out_of_window_slots` manages sliding window attention eviction [[python/sglang/srt/mem_cache/common.py54-64](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/mem_cache/common.py#L54-L64)].

### Termination and Finish Reasons

 Request termination is handled by identifying finish conditions. Common conditions include:

 
 - **Stop Tokens**: Reaching EOS or user-defined stop tokens [[python/sglang/srt/managers/detokenizer_manager.py187-190](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/detokenizer_manager.py#L187-L190)].
 - **Max Length**: Exceeding `max_new_tokens`.
 - **Abort**: Explicitly triggered via `AbortReq` [[python/sglang/srt/managers/io_struct.py117](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/io_struct.py#L117-L117)] or `FINISH_ABORT` [[python/sglang/srt/managers/schedule_batch.py201](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/managers/schedule_batch.py#L201-L201)].
 
 When a request terminates, `release_kv_cache` is called to free indices in the `ReqToTokenPool` and potentially insert the prefix into the `RadixCache` [[python/sglang/srt/mem_cache/common.py117](https://github.com/sgl-project/sglang/blob/94183a8d/[python/sglang/srt/mem_cache/common.py#L117-L117)].
