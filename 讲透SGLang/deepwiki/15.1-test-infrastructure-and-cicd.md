  This document describes SGLang's test infrastructure and CI/CD system, which validates code changes across multiple hardware platforms (NVIDIA, AMD, Intel, Ascend) using a staged testing approach with load-balanced test partitioning and developer-friendly automation tools.

 
---

 
## Test Suite Organization

 SGLang uses a **registry-based test system** that organizes tests by hardware backend, test suite, and execution frequency (per-commit vs nightly).

 
### Test Registration System

 Tests are registered using the `CIRegistry` system, which associates each test file with specific execution contexts. The registration system supports several primary hardware backends defined in the `HW_MAPPING`:

 
 - `cpu`: Intel Xeon and general CPU testing [test/run_suite.py:19].
 - `cuda`: NVIDIA GPU testing (H100, B200, H200, GB200, etc.) [test/run_suite.py:20].
 - `amd`: AMD ROCm testing (MI300X, MI325, MI35X) [test/run_suite.py:21].
 - `musa`: Moore Threads MUSA testing [test/run_suite.py:22].
 - `npu`: Huawei Ascend NPU testing [test/run_suite.py:23].
 - `xpu`: Intel GPU testing [test/run_suite.py:24].
 - `mlx`: Apple Silicon MLX testing [test/run_suite.py:25].
 
 
### Staged Test Execution

 Tests are organized into stages that execute sequentially for PR validation:

 **Stage A (Smoke Tests)**

 
 - Fast validation tests (~5-10 minutes).
 - Basic functionality checks and unit tests for core components [test/run_suite.py:34,71,41,113,117].
 - Runs on single GPU/XPU or CPU.
 
 **Stage B (Functional Tests)**

 
 - Comprehensive feature testing (~30-60 minutes).
 - Multi-GPU configurations (1, 2, 4 GPUs) [test/run_suite.py:72-75,42-47,114,118].
 - Includes specialized kernel unit tests and benchmarks [test/run_suite.py:76-79,48-50].
 - NPU-specific commit tests for A2/A3 hardware [test/run_suite.py:98-102].
 
 **Stage C (Integration Tests)**

 
 - Large-scale integration tests (~60-120 minutes).
 - Heavy workloads involving 4-8 GPUs [test/run_suite.py:80-87,51-53].
 - Validates advanced features like Expert Parallelism and multi-node disaggregation [test/run_suite.py:86-87,45].
 
 **Nightly Tests**

 
 - Extended accuracy and performance suites run every 24 hours [.github/workflows/nightly-test-amd.yml:5].
 - Includes evaluations for text models and VLMs [test/run_suite.py:149,156-173].
 - Covers full AMD ROCm nightly suites including MI35X and ROCm 7.2 specific configurations [test/run_suite.py:136-154], [.github/workflows/nightly-test-amd-rocm720.yml:1].
 - Nightly precision regression testing performs per-layer hidden state comparison using `test_nightly_precision_regression.py` [scripts/ci/utils/slash_command_handler.py:30].

## Test Runner Architecture

 
### Main Test Orchestrator: `run_suite.py`

 The `run_suite.py` script serves as the primary test orchestrator that:

 
 - Collects registered tests from the `CIRegistry` [test/run_suite.py:10-15].
 - Filters tests by hardware backend (`--hw`), suite name (`--suite`), and nightly flag [test/run_suite.py:18-26, 210-213].
 - Partitions tests across multiple parallel runners using an `auto_partition` algorithm [test/run_suite.py:13].
 - Executes tests via `run_unittest_files` with configurable timeouts [test/run_suite.py:16].

## CI/CD Workflow Architecture

 
### PR Test Workflow: `pr-test.yml`

 The main PR testing workflow coordinates multi-stage test execution with dynamic change detection and concurrency control.

 **Change Detection Logic** The workflow uses path filtering to detect file changes and conditionally run tests.

 
 - `main_package`: Triggers core SGLang server tests [.github/workflows/pr-test-amd.yml:132].
 - `multimodal_gen`: Triggers diffusion and VLM-specific tests [.github/workflows/pr-test-amd.yml:135].
 - `sgl_kernel`: Triggers the C++/CUDA kernel library tests [.github/workflows/pr-test-amd.yml:133].
 - `jit_kernel`: Triggers JIT-based kernel tests [.github/workflows/pr-test-amd.yml:134].
 
 **Execution Environment**

 
 - `SGLANG_IS_IN_CI`: Set to `true` to enable CI-specific behaviors [.github/workflows/pr-test.yml:58].
 - `SGLANG_CUDA_COREDUMP`: Set to `1` to capture diagnostic info on crashes [.github/workflows/pr-test.yml:59].
 - `SGLANG_JIT_DEEPGEMM_FAST_WARMUP`: Speeds up DeepGEMM JIT compilation in CI [.github/workflows/pr-test.yml:60].
 
 
### CI Maintenance and Gates

 SGLang implements a maintenance gate system to pause CI during infrastructure updates:

 
 - `check-maintenance`: An action that polls for maintenance status [.github/workflows/pr-test.yml:113,143].
 - `_check_rebase_gate`: A Python-based gate that enforces rebasing if a major update lands on `main` or maintenance mode is active [scripts/ci/utils/slash_command_handler.py:37-151].
 - `bypass-fastfail`: A PR label that allows downstream stages to dispatch in parallel by returning success immediately from wait jobs [.github/workflows/pr-test.yml:94-95].
 - `SKIP_PR_TEST_HEALTH_CHECK`: Environment variable to skip health checks for release branch cuts or manual dispatches [.github/workflows/pr-test.yml:61].
 
 Sources: [.github/workflows/pr-test.yml:58-161], [.github/workflows/pr-test-amd.yml:132-135], [scripts/ci/utils/slash_command_handler.py:37-151]

## CI Permissions and Monitoring

 
### CI Permissions Registry

 Permissions for CI commands are defined in `.github/CI_PERMISSIONS.json`, mapping GitHub usernames to specific capabilities [.github/CI_PERMISSIONS.json:1-230].

 
| Permission Key | Description |
|---|---|
| can_tag_run_ci_label | Ability to trigger CI via labels [.github/CI_PERMISSIONS.json:3]. |
| can_rerun_failed_ci | Ability to rerun failed workflows [.github/CI_PERMISSIONS.json:4]. |
| cooldown_interval_minutes | Rate limiting for CI commands [.github/CI_PERMISSIONS.json:5]. |

 
### Slash Command Handler

 The `slash_command_handler.py` utility processes PR comments (like `/rerun-test`) to trigger manual CI runs. It verifies permissions, checks maintenance status, and polls for the resulting workflow URL [scripts/ci/utils/slash_command_handler.py:154-184].

 
### CI Failure Analysis

 The `ci_failures_analysis.py` script monitors CI health by:

 
 - Querying GitHub API for recent workflow runs.
 - Categorizing failures (e.g., Infrastructure vs. Code).
 - Providing summaries for CI maintainers.
 
 Sources: [.github/CI_PERMISSIONS.json:1-230], [scripts/ci/utils/slash_command_handler.py:1-184]

## Test Execution Infrastructure

 
### Multi-Platform CI Workflows

 SGLang maintains specialized workflows for non-NVIDIA hardware:

 
 - **AMD (ROCm)**: Uses `pr-test-amd.yml` with MI300/MI325 runners. Supports dynamic stage reruns via `target_stage` [.github/workflows/pr-test-amd.yml:4, 16-42].
 - **AMD (ROCm 7.2)**: Specific workflow for testing against the ROCm 7.2 stack, including DeepSeek-V4 specific accuracy runs [.github/workflows/pr-test-amd-rocm720.yml:1, 47-48].
 - **AMD Nightly**: Comprehensive nightly testing for ROCm 7.0 and 7.2, covering high-parameter models like DeepSeek-R1-MXFP4 and Grok2 [.github/workflows/nightly-test-amd-rocm720.yml:52, 60].
 - **NPU (Ascend)**: Dedicated workflow for Huawei Ascend hardware, utilizing specialized NPU runners like `base-a-test-1-npu-a2` [test/run_suite.py:97].
 
 
### CI Utility Scripts

 The system tracks execution health through several mechanisms:

 
 - **Wait Jobs**: Sequential execution enforcement in `pr-test.yml` using `wait-for-jobs` action [.github/workflows/pr-test.yml:115-125].
 - **VRAM Management**: `ensure_vram_clear.sh` is executed before starting ROCm containers to prevent out-of-memory errors from previous failed runs [.github/workflows/nightly-test-amd.yml:152].
 - **Rerun Test**: The `rerun-test.yml` workflow allows developers to re-execute specific test commands on selected runners (e.g., `1-gpu-5090`) with custom install scripts [.github/workflows/rerun-test.yml:8-28].
