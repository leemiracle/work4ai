## Purpose and Scope

 This page documents SGLang's hardware detection and platform configuration system. SGLang is a high-performance, multi-platform serving framework that automatically identifies the available compute backend—including NVIDIA CUDA, AMD ROCm/HIP, Intel XPU, Ascend NPU, Moore Threads MUSA, Apple MPS, and CPUs—to configure runtime optimizations, kernel selection, and memory management strategies.

 The framework utilizes a lazy initialization pattern for platform discovery, ensuring that only the necessary dependencies and hardware-specific code paths are loaded for the active environment.

 
## Platform Detection Architecture

 SGLang uses a layered detection system that identifies the hardware platform, specific device capabilities, and available software features. Detection results are typically cached using `@lru_cache(maxsize=1)` to avoid repeated system calls [python/sglang/srt/utils/common.py131-230](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/common.py#L131-L230)

 
### Platform Discovery Flow

 The `current_platform` singleton serves as the central entry point for hardware queries. It is lazily initialized upon first access, triggering a discovery flow that checks for environment overrides, out-of-tree (OOT) plugins, and finally falls back to native hardware detection via `torch` utilities.

## Hardware Abstraction Layer (DeviceMixin)

 SGLang abstracts hardware differences through the `DeviceMixin` and `SRTPlatform` interfaces. This allows core server logic to query device properties without vendor-specific branching.

 
### Platform Identity Queries

 The utility functions in `sglang.srt.utils.common` are the primary mechanisms for identifying the runtime environment.

### Device Capability Mapping

 Hardware detection informs the selection of distributed backends and precision. For example, FP8 max values are adjusted for HIP [python/sglang/srt/utils/common.py136-141](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/common.py#L136-L141) Capability checks like `get_cuda_version()` are used to determine support for specific driver versions [python/sglang/srt/utils/common.py237-240](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/common.py#L237-L240) For XPU, specific device properties are registered for Torch Dynamo compatibility [python/sglang/srt/utils/common.py168-177](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/common.py#L168-L177)

## Platform-Specific Configuration

 SGLang adjusts configuration and dependencies based on the detected hardware via `pyproject.toml` and Dockerfiles.

 
### Environment Variable Control

 The `envs` singleton manages hardware-related environment variables, such as `SGLANG_USE_CPU_ENGINE` which forces the engine to run on host processors [python/sglang/srt/utils/common.py214-215](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/common.py#L214-L215) The engine entry point uses `is_cuda()` to determine initialization logic for CUDA-specific features like NCCL [python/sglang/srt/entrypoints/engine.py142](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/engine.py#L142-L142)

 
### Dependency Management

 The build system uses optional dependencies to handle platform-specific packages:

 - **AMD (HIP):** Includes `wave-lang` and `petit_kernel` [python/pyproject_other.toml114-123](https://github.com/sgl-project/sglang/blob/94183a8d/python/pyproject_other.toml#L114-L123)

## Multi-Platform Runtime Dispatch

 SGLang uses the detected platform to dispatch to hardware-specific implementations for critical operations like Profiling and Graph Capture.

 
### Profiling and Debugging

 The `SchedulerProfilerManager` and `ProfileManager` utilize platform checks to apply vendor-specific patches.

 
 - **NPU:** `torch_npu.profiler` is patched to map CUDA activities to NPU activities [python/sglang/srt/managers/scheduler_components/profiler_manager.py35-43](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/profiler_manager.py#L35-L43)
 - **Apple silicon:** Metal-specific profiler patches are applied [python/sglang/srt/managers/scheduler_components/profiler_manager.py44-47](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/profiler_manager.py#L44-L47)
 - **Generic OOT:** The platform interface provides `get_torch_profiler_activity_str()` to handle new backends [python/sglang/srt/managers/scheduler_components/profiler_manager.py189-196](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/profiler_manager.py#L189-L196)

 SGLang provides specialized utilities to export chrome traces during CUDA graph capture, namespaced by rank and runner [python/sglang/srt/utils/profile_utils.py52-71](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/profile_utils.py#L52-L71) This is controlled by the `SGLANG_ENABLE_CUDA_GRAPH_CAPTURE_TRACE` environment variable [python/sglang/srt/utils/profile_utils.py62-63](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/profile_utils.py#L62-L63)
