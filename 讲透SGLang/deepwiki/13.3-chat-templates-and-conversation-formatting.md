  Chat templates define how conversational messages (roles like `system`, `user`, and `assistant`) are formatted into a single string prompt for language models. This page documents SGLang's ChatTemplate system, which provides model-specific conversation formatting, role prefix/suffix handling, and automated detection of reasoning and tool-call parsers.

 For information about tokenization and detokenization processes that apply these templates, see [3.3 TokenizerManager and DetokenizerManager](https://github.com/sgl-project/sglang/blob/94183a8d/3.3 TokenizerManager and DetokenizerManager) For HTTP API endpoints that accept chat messages, see [13.2 HTTP Server and OpenAI-Compatible API](https://github.com/sgl-project/sglang/blob/94183a8d/13.2 HTTP Server and OpenAI-Compatible API)

## Reasoning and Tool-Call Parsing

 SGLang features specialized parsers to extract structured data (like chain-of-thought reasoning or function calls) from raw model outputs. This is critical for models like DeepSeek-R1, DeepSeek-V4, or Kimi-K3.

 
### Reasoning Parser System

 The `ReasoningParser` identifies and separates "thinking" blocks from the final answer.

 
 - **Supported Detectors**: Includes specific logic for `deepseek-r1`, `deepseek-v3`, `qwen3`, `kimi_k2`, `apertus2509`, and `gpt-oss` [python/sglang/srt/parser/reasoning_parser.py5-47](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/reasoning_parser.py#L5-L47)
 - **Streaming Logic**: The `parse_streaming_increment` method buffers tokens to avoid partial tag leakage. If `stream_reasoning` is enabled, it yields reasoning content as it is generated [python/sglang/srt/parser/reasoning_parser.py171-189](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/reasoning_parser.py#L171-L189)
 - **Thinking Mode**: The OpenAI server implementation supports a `ThinkingMode` enum to toggle between `CHAT` and `THINKING` encoding [python/sglang/srt/entrypoints/openai/serving_chat.py14-19](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/openai/serving_chat.py#L14-L19)
 
 
### Function Call Parsing

 The `FunctionCallParser` manages a registry of model-specific detectors to parse tool calls from text.

 
 - **Detector Registry**: Maps strings like `deepseekv32`, `deepseekv4`, `llama3`, `qwen25`, `gemma4`, and `inkling` to detector classes such as `DeepSeekV32Detector`, `DeepSeekV4Detector`, `Llama32Detector`, `Qwen25Detector`, `Gemma4Detector`, and `InklingDetector` [python/sglang/srt/function_call/function_call_parser.py68-105](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/function_call_parser.py#L68-L105)
 - **DeepSeek V3.2/V4 Specifics**: The `DeepSeekV32Detector` supports both XML-like parameter tags and direct JSON within `<｜DSML｜invoke>` blocks [python/sglang/srt/function_call/deepseekv32_detector.py21-71](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/deepseekv32_detector.py#L21-L71)
 - **Incremental Parsing**: `parse_stream_chunk` allows the engine to detect tool calls while the response is still being generated [python/sglang/srt/function_call/function_call_parser.py160-170](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/function_call_parser.py#L160-L170)
 - **Normalization**: Tool message content is normalized from OpenAI array format to plain strings to ensure compatibility with chat templates [python/sglang/srt/entrypoints/openai/serving_chat.py105-124](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/openai/serving_chat.py#L105-L124) Assistant history tool call arguments are also normalized in-place [python/sglang/srt/entrypoints/openai/serving_chat.py144-164](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/openai/serving_chat.py#L144-L164)

## Harmony and Advanced Interfaces

 For specific high-performance models (like `gpt_oss`), SGLang uses the "Harmony" interface, which includes specialized EOS-like tokens such as `<|return|>` and `<|call|>` [python/sglang/srt/parser/harmony_parser.py1-40](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/harmony_parser.py#L1-L40)

 
 - **HarmonyContext**: Provides specialized rendering for completion and tool-use scenarios [python/sglang/srt/parser/harmony_parser.py1-40](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/harmony_parser.py#L1-L40)
 - **Stop Token Handling**: Models using Harmony automatically extend `stop_token_ids` to include assistant action terminators.

## Template Management and Priority

 The `TemplateManager` handles the lifecycle of templates, including loading from local files, built-in registries, or HuggingFace `tokenizer_config.json`.

 **Template Loading Priority:**

 
 - **Explicit Argument**: If `--chat-template` is provided in `ServerArgs`, it checks the built-in registry, then local `.jinja` or `.json` files [python/sglang/srt/managers/template_manager.py150-170](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/template_manager.py#L150-L170)
 - **Model Path Inference**: Guesses based on regex patterns in `get_conv_template_by_model_path` [python/sglang/srt/parser/conversation.py900-1050](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/conversation.py#L900-L1050)
 - **HuggingFace Fallback**: Attempts to resolve the template directly from the tokenizer's configuration via `_resolve_hf_chat_template` [python/sglang/srt/managers/template_manager.py124-137](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/template_manager.py#L124-L137)
 
 **Special Encodings**: Certain models like DeepSeek-V4 or DeepSeek-V3.2 use specialized Python-based encoders (e.g., `encoding_dsv4`, `encoding_dsv32`) to handle complex multi-modal and tool-calling logic efficiently [python/sglang/srt/entrypoints/openai/serving_chat.py39](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/openai/serving_chat.py#L39-L39)
