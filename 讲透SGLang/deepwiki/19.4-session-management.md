  Session management in SGLang enables multi-turn conversations with persistent context. Sessions allow multiple requests to share KV cache and maintain conversational state without redundantly recomputing shared prefixes. This feature is particularly useful for chatbot applications, interactive agents, and scenarios requiring context continuity across multiple generation calls.

 For information about the Python Engine API that sessions integrate with, see [Python Engine API](https://github.com/sgl-project/sglang/blob/94183a8d/Python Engine API) For details on the underlying cache system that sessions leverage, see [RadixCache and Prefix Sharing](https://github.com/sgl-project/sglang/blob/94183a8d/RadixCache and Prefix Sharing)

 
## Overview

 Sessions provide a stateful interaction model where:

 
 - **Context Persistence**: KV cache is maintained across multiple requests within a session.
 - **Efficient Multi-Turn**: Shared prefixes are cached in the `RadixCache`, avoiding redundant computation.
 - **Streaming Sessions**: The `StreamingSession` class provides a specialized wrapper to handle KV save/restore operations between turns [python/sglang/srt/session/streaming_session.py134-142](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/session/streaming_session.py#L134-L142)
 - **Session Identifiers**: Requests are grouped using a `session_id` to ensure stable identity across turns.
 
 
## Core Session Components

 The SGLang Runtime (`SRT`) manages sessions through the `Engine` and its underlying manager processes. Requests can explicitly open and close sessions to manage resource allocation.

## Cache Management for Sessions

 SGLang uses a hierarchical memory system to manage session states. The `Scheduler` interacts with the `RadixCache` (or `StreamingSession` wrapper) to allocate and release memory.

 
### Session Memory Entities

 - **KV Pool Persistence**: `SessionSlot` keeps the `req_pool_idx` alive even after a request finishes, preventing the `ReqToTokenPool` from reclaiming those indices between turns [python/sglang/srt/session/streaming_session.py47-49](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/session/streaming_session.py#L47-L49)
 - **Mamba State Persistence**: For hybrid models, the slot also tracks `mamba_pool_idx`, `mamba_ping_pong_track_buffer`, and other tracking indices to maintain state across steps [python/sglang/srt/session/streaming_session.py60-65](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/session/streaming_session.py#L60-L65)

## Multi-Turn Performance and Observability

 Sessions are optimized for low inter-turn latency and high throughput.

 
### Output Streaming and Result Processing

 
 - **Accumulation**: Generation results are accumulated via `_GenerationStreamAccumulator` which handles the logic for mixed batches where some requests might be retracted or finished [python/sglang/srt/managers/scheduler_components/output_streamer.py164-188](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/output_streamer.py#L164-L188)
 - **Customized Info**: Sessions support passing `customized_info` (e.g., specialized model outputs) back to the client. The `SchedulerOutputStreamer` handles padding this info for mixed batches [python/sglang/srt/managers/scheduler_components/output_streamer.py180-182](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/output_streamer.py#L180-L182)
 - **Reasoning Tokens**: For models with reasoning capabilities, the `SchedulerBatchResultProcessor` tracks reasoning tokens and detects when reasoning is over to manage the transition to standard generation [python/sglang/srt/managers/scheduler_components/batch_result_processor.py218-232](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/batch_result_processor.py#L218-L232)
 
 
### Timeout Management

 The `Scheduler` implements specific timeouts to prevent sessions from hanging indefinitely:

 
 - **Waiting Timeout**: Aborts requests that stay in the waiting queue too long [test/registered/unit/managers/test_scheduler_timeouts.py60-80](https://github.com/sgl-project/sglang/blob/94183a8d/test/registered/unit/managers/test_scheduler_timeouts.py#L60-L80)
 - **Running Timeout**: Aborts requests that have been running for longer than the configured threshold without finishing [test/registered/unit/managers/test_scheduler_timeouts.py96-113](https://github.com/sgl-project/sglang/blob/94183a8d/test/registered/unit/managers/test_scheduler_timeouts.py#L96-L113)
