## Multi-Node Deployment Overview

 SGLang is designed to serve large language models (LLMs) and vision-language models (VLMs) efficiently at scale, often surpassing the capacity of a single machine. To enable scalable, high-performance serving, it supports multi-node deployment that allows:

 
 - Serving models too large for a single machine's memory (accounting for model weights, key-value cache, and activations).
 - Tensor parallelism (TP) spanning multiple GPUs distributed across multiple nodes.
 - Data parallelism (DP) to replicate models and increase throughput with batch parallelism.
 - Prefill-Decode disaggregation, splitting the model inference pipeline across nodes specialized for initial context conditioning ("prefill") and subsequent token decoding ("decode").
 
 The distributed system uses:

 
 - **PyTorch Distributed Framework (`torch.distributed`)** for initializing process groups and orchestrating communication between nodes [python/sglang/srt/distributed/parallel_state.py9-25](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L9-L25)
 - Backend communication libraries such as **NCCL** (NVIDIA), **RCCL** (AMD ROCm), and **HCCL** (Ascend NPU) for fast low-latency GPU interconnect communication [python/sglang/srt/distributed/parallel_state.py52-64](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L52-L64)
 - TCP and ZeroMQ (ZMQ) for control plane communication between core runtime components like tokenizer, scheduler, and detokenizer managers [python/sglang/srt/entrypoints/engine.py203-215](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/engine.py#L203-L215)
 - Kubernetes-native orchestration system **llm-d**, which manages fleet prefix-aware routing and distributed KV-cache synchronization to maximize cache reuse across nodes.
 
 These components collectively enable scalable coordination, efficient communication, and optimized routing in multi-node serving contexts.

## Distributed Initialization Architecture

 
### Coordination Parameters for Multi-Node Deployment

 Distributed setup in SGLang is driven by parameters primarily under the `ServerArgs` configuration that specify cluster topology and parallelism:

 
| Parameter | Description | Code Reference |
|---|---|---|
| nnodes | Number of physical nodes in the cluster. | python/sglang/srt/server_args.py461-463 |
| node_rank | Rank/index of the current node within the cluster (0-based). | python/sglang/srt/server_args.py465-467 |
| dist_init_addr | TCP rendezvous address string of the master node for coordination. | python/sglang/srt/server_args.py469-471 |
| tp | Tensor parallelism degree specifying how many devices/processes form the TP group. | python/sglang/srt/server_args.py421-423 |
| dp | Data parallelism degree specifying number of replicas. | python/sglang/srt/server_args.py433-435 |

 These parameters, often passed as CLI arguments or config file values, configure the distributed runtime environment to coordinate across multiple processes and nodes.

 
### Distributed Initialization Flow

 The engine startup includes distributed environment initialization with these key steps:

 
 - **Global Distributed Environment Initialization**: Using `torch.distributed.init_process_group` with the backend (e.g., NCCL, RCCL, or HCCL) and the provided rendezvous TCP address (`dist_init_addr`), a global process group covering all ranks (processes) and nodes is established [python/sglang/srt/distributed/parallel_state.py1017-1025](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L1017-L1025)
 - **Model Parallel Group Creation**: Higher-level process groups encapsulating tensor parallelism (TP), pipeline parallelism (PP), expert parallelism (EP), data parallelism (DP), and context parallelism (CP) are created to organize the distributed training or inference workflows [python/sglang/srt/distributed/parallel_state.py489-500](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L489-L500)
 - **GroupCoordinator Wrappers**: Each distributed process group is wrapped by a `GroupCoordinator` instance that provides communication primitives and manages group life-cycle for efficient collective operations [python/sglang/srt/distributed/parallel_state.py347-360](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L347-L360)
 
 This setup ensures that SGLang's runtime has the proper distributed communication groups to support parallel model execution, synchronization, and optimizations.

## Prefill-Decode Disaggregation and llm-d Orchestration

 
### Prefill-Decode Disaggregation Architecture

 SGLang supports a split model inference workload architecture called prefill-decode disaggregation:

 
 - **Prefill Nodes** run the initial context conditioning steps during which the model builds up the key-value cache (KV cache) representing the input prompt.
 - **Decode Nodes** perform subsequent token generation steps, reusing the KV cache received from prefill nodes. This separation allows scaling decode throughput independently and optimizes KV cache usage.
 
 A specialized efficient KV transfer mechanism between nodes exists, with transfer endpoints implemented using backends like **Mooncake** or **NIXL** to provide high-throughput, low-latency KV cache blocks over RDMA or TCP transport [python/sglang/srt/distributed/device_communicators/mooncake_transfer_engine.py37-40](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/device_communicators/mooncake_transfer_engine.py#L37-L40)

 
### llm-d Kubernetes Fleet Orchestration

 SGLang leverages **llm-d**, its Kubernetes-native fleet orchestration system, to manage large distributed deployments:

 
 - **Prefix-Aware Routing:** llm-d routes inference requests to the set of decode nodes that hold relevant KV cache prefixes, maximizing cache reuse and minimizing recomputation.
 - **Distributed KV Cache Events Management:** llm-d synchronizes KV cache updates and related events across the fleet to maintain coherence during disaggregated serving [python/sglang/srt/managers/scheduler_components/kv_events_publisher.py18-20](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/kv_events_publisher.py#L18-L20)
 
 This orchestrated system enables scalable multi-node serving architectures optimized for caching and request routing.

## Network Communication Stack

 SGLang builds atop PyTorch's distributed communication while introducing custom operators and optimized backends to enhance multi-node efficiency.

 
### 1. Custom All-Reduce Operators and FlashInfer Fusion

 SGLang registers custom communication operators to optimize reductions and all-gathers in distributed tensor operations:

 
 - `inplace_all_reduce`: Performs in-place all-reduce on a tensor across ranks in a distributed group [python/sglang/srt/distributed/parallel_state.py164-170](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L164-L170)
 - `outplace_all_reduce`: Returns a new tensor with the all-reduce result, leaving input unmodified [python/sglang/srt/distributed/parallel_state.py173-180](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L173-L180)
 
 For NVIDIA GPUs supporting SM90 and SM100 architectures, SGLang integrates with **FlashInfer** to perform highly optimized all-reduce fusion, minimizing latency and maximizing bandwidth:

 
 - Two primary FlashInfer allreduce fusion backends exist: `mnnvl` (for Blackwell/SM100 GPUs and multi-node support) and `trtllm` (single-node support) [python/sglang/srt/layers/flashinfer_comm_fusion.py46-63](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/layers/flashinfer_comm_fusion.py#L46-L63)
 
 This custom fusion greatly accelerates distributed all-reduce, especially critical in tensor parallel and attention gradient collectives.

 
### 2. Symmetric Memory Allocation for NCCL

 SGLang utilizes a symmetric memory allocator to satisfy NCCL requirements and optimize collective operations across distributed ranks:

 
 - The `use_symmetric_memory` context manager triggers symmetric memory allocation enabling CUDA IPC handles to be shared efficiently across ranks [python/sglang/srt/distributed/device_communicators/pynccl_allocator.py227-230](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/device_communicators/pynccl_allocator.py#L227-L230)
 - `nccl_alloc_plug` provides a memory allocation hook substituting `ncclMemAlloc`, enabling the allocator to provide memory accessible and addressable identically by all processes in the node [python/sglang/srt/distributed/device_communicators/pynccl_allocator.py97-106](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/device_communicators/pynccl_allocator.py#L97-L106)
 
 This cooperation optimizes collective communication on NVIDIA GPUs and can be adapted to other platforms.

 
### 3. Data Parallel Attention Communication

 
 - The `DpPaddingMode` enum controls how token sequences are padded in DP communication phases to efficiently batch tokens for attention computation [python/sglang/srt/layers/dp_attention.py69-81](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/layers/dp_attention.py#L69-L81)
 - Collective operations such as `dp_reduce_scatter_tensor` and `dp_gather_partial` orchestrate splitting inputs and aggregating attention results across DP groups for efficient scaling of attention layers [python/sglang/srt/layers/dp_attention.py534-540](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/layers/dp_attention.py#L534-L540)
 
 This ensures high communication efficiency for data parallelism especially with large batches and long sequences.

## Platform-Specific Distributed Configurations

 SGLang supports multiple hardware platforms, adapting distributed communication accordingly:

 
| Platform | Key Configuration and Features | Code Reference |
|---|---|---|
| NVIDIA CUDA | Uses NCCL backend. Supports FlashInfer allreduce fusion backends mnnvl and trtllm | python/sglang/srt/layers/flashinfer_comm_fusion.py46-63 |
| AMD ROCm | RCCL backend. Optimizations with aiter fused RMSNorm and quantization ops for communication | python/sglang/srt/layers/communicator.py97-108 |
| Ascend NPU | HCCL backend, with tunable buffer size via environment variable DEEPEP_HCCL_BUFFSIZE | python/sglang/srt/distributed/parallel_state.py84-99 |
| Intel XPU | Uses sgl-kernel-xpu optimized distributed ops and custom communication primitives | python/sglang/srt/utils/common.py165-168 |

 These adaptations ensure SGLang attains maximal throughput and minimal latency for distributed execution on each platform.
