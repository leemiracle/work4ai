## Purpose and Scope

 The Multi-Platform Layer Abstraction system in SGLang provides a unified programming model for implementing neural network layers and operations that can execute efficiently on a variety of hardware backends. It is designed to support NVIDIA CUDA GPUs, AMD HIP/ROCm GPUs, Ascend NPUs, Intel XPUs, Moore Threads MUSA GPUs, Apple MPS, and CPUs with optimized platform-specific implementations.

 This system ensures that high-level model code remains hardware-agnostic while low-level execution leverages specialized kernels (e.g., `sgl-kernel`, `flashinfer`, `aiter`, `CANN`). It extends beyond simple kernel dispatch to include platform-specific memory management (e.g., NPU Paged KV Cache), graph runners, and disaggregation transfer engines.

## Platform Discovery and Initialization

 SGLang uses a lazy-loading plugin architecture to detect the underlying hardware. The `current_platform` singleton in `sglang.srt.platforms` resolves the active hardware at runtime.

 
### Discovery Flow

 
 - **Explicit Selection**: If the environment variable `SGLANG_PLATFORM` is set, SGLang loads only the specified plugin [python/sglang/srt/platforms/__init__.py79-106](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/platforms/__init__.py#L79-L106)
 - **Auto-Discovery**: If unset, SGLang imports all discovered plugins via `entry_points` and activates the one matching the machine's hardware [python/sglang/srt/platforms/__init__.py109-150](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/platforms/__init__.py#L109-L150)
 - **Fallbacks**: If no plugin is found, it falls back to standard `torch` checks for CUDA, ROCm, XPU, or CPU [python/sglang/srt/platforms/__init__.py121-139](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/platforms/__init__.py#L121-L139)
 
 
### Platform Identity and Capabilities

 Each platform implements a `DeviceMixin` that provides identity methods (e.g., `is_cuda()`, `is_npu()`) and capability checks. The `DeviceCapability` class uses a `NamedTuple` to allow direct comparison of hardware versions (e.g., SM90 vs SM80) [python/sglang/srt/platforms/device_mixin.py65-81](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/platforms/device_mixin.py#L65-L81)

## MultiPlatformOp and Hardware Dispatch

 The `MultiPlatformOp` pattern dispatches the `forward()` call of a layer to the most appropriate backend implementation based on `current_platform`.

 
### Hardware Dispatch Dataflow

 When a layer's `.forward()` is called, the system queries the `current_platform` and routes the call to specialized methods. For example, in the NPU backend, the `ModelRunner` uses an `NPUGraphRunner` which issues async `NPUGraph.update` calls for sequence lengths before replaying the captured graph [python/sglang/srt/hardware_backend/npu/graph_runner/npu_graph_runner.py16-25](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/hardware_backend/npu/graph_runner/npu_graph_runner.py#L16-L25)

## Specialized Hardware Backends

 
### NPU (Ascend) Architecture

 The NPU implementation provides a full stack of platform-specific overrides:

 
 - **Memory Pool**: `NPUMHATokenToKVPool` manages a contiguous buffer layout optimized for Ascend's transmission backend [python/sglang/srt/hardware_backend/npu/memory_pool_npu.py56-129](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/hardware_backend/npu/memory_pool_npu.py#L56-L129) It supports `ASCEND_USE_FIA` for specialized memory views [python/sglang/srt/hardware_backend/npu/memory_pool_npu.py131-143](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/hardware_backend/npu/memory_pool_npu.py#L131-L143)
 - **Graph Runner**: `NPUGraphRunner` and `EAGLEDraftNpuGraphRunner` use `torch.npu.NPUGraph` and support `torch.compile` via the `npugraph_ex` backend [python/sglang/srt/hardware_backend/npu/graph_runner/npu_graph_runner.py69-82](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/hardware_backend/npu/graph_runner/npu_graph_runner.py#L69-L82)
 - **Disaggregation**: `AscendKVManager` and `AscendTransferEngine` utilize `memfabric_hybrid` for RDMA/SDMA transfers between Prefill and Decode nodes [python/sglang/srt/disaggregation/ascend/conn.py32-46](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/ascend/conn.py#L32-L46) [python/sglang/srt/disaggregation/ascend/transfer_engine.py24-52](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/ascend/transfer_engine.py#L24-L52)
 
 
### Profiling Abstraction

 The `SchedulerProfilerManager` and `ProfileManager` handle platform-specific profiler patches. For NPU, it applies patches to `torch_npu.profiler` and maps `CUDA` activities to `NPU` [python/sglang/srt/managers/scheduler_components/profiler_manager.py35-43](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_components/profiler_manager.py#L35-L43) [python/sglang/srt/utils/profile_utils.py26-34](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/utils/profile_utils.py#L26-L34)

## Summary of Platform Support

 
| Feature | CUDA (NVIDIA) | ROCm (AMD) | NPU (Ascend) | CPU |
|---|---|---|---|---|
| Detection | is_cuda() | is_rocm() | is_npu() | is_cpu() |
| Dist. Backend | nccl | nccl | hccl / zbal | gloo |
| Graph Runner | DecodeCudaGraphRunner | DecodeCudaGraphRunner | NPUGraphRunner | N/A |
| KV Cache Pool | MHATokenToKVPool | MHATokenToKVPool | NPUMHATokenToKVPool | MHATokenToKVPool |
| PD Transfer | Mooncake | Mooncake | MemFabric | N/A |
| Profiler | torch.profiler | rpd | torch_npu.profiler | torch.profiler |
