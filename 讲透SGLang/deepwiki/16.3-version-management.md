  This page describes how SGLang's version numbers are defined, resolved at runtime, and kept in sync between the `sglang` and `sgl-kernel` packages. It also describes the automated release coordination scripts and how multiple `pyproject.toml` variants configure version derivation across different hardware platforms.

 For information on the wheel build and PyPI publishing pipeline that consumes these versions, see page [16.1](https://github.com/sgl-project/sglang/blob/94183a8d/16.1) For Docker image tagging using these version strings, see page [16.2](https://github.com/sgl-project/sglang/blob/94183a8d/16.2)

## Version Numbering Scheme

 SGLang follows a `MAJOR.MINOR.PATCH[.postN]` or `MAJOR.MINOR.PATCHrcN` scheme for release tags. Versioning logic is primarily managed through `setuptools_scm`, which derives versions from Git tags and history [python/pyproject.toml242-248](https://github.com/sgl-project/sglang/blob/94183a8d/python/pyproject.toml#L242-L248)

 
### Runtime Version Resolution

 The `python/sglang/version.py` file handles version resolution at runtime using several fallback mechanisms:

 
 - It first attempts to import from the generated `sglang._version.py`, which is created by `setuptools_scm` during the build process [python/sglang/version.py1-2](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/version.py#L1-L2)
 - If the file is missing, it uses `importlib.metadata.version("sglang")` to check the installed package metadata [python/sglang/version.py5-8](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/version.py#L5-L8)
 - As a fallback for development environments, it uses `setuptools_scm.get_version` pointing to the project root or defaults to `0.0.0.dev0` [python/sglang/version.py10-24](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/version.py#L10-L24)
 
 The engine startup process logs this version immediately upon initialization to aid in debugging and telemetry [python/sglang/srt/entrypoints/engine.py137-139](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/engine.py#L137-L139)

 
### Version Derivation Logic

 The `setuptools_scm` configuration uses a custom command `python3 scripts/release/get_version_tag.py` to determine the current version tag from the Git state [python/pyproject.toml246](https://github.com/sgl-project/sglang/blob/94183a8d/python/pyproject.toml#L246-L246) This allows the project to dynamically generate version strings that include the commit hash for non-tagged builds, following PEP 440.

## Release Coordination and Automation

 SGLang uses GitHub Actions and update scripts to ensure that specific versions of core components are locked during the release process.

 
### CI Environment Configuration

 CI installation scripts like `scripts/ci/cuda/ci_install_dependency.sh` use `CU_VERSION` (defaulting to `cu130`) to control PyTorch index URLs and variant selection for dependencies like FlashInfer [scripts/ci/cuda/ci_install_dependency.sh30-36](https://github.com/sgl-project/sglang/blob/94183a8d/scripts/ci/cuda/ci_install_dependency.sh#L30-L36) The script also detects hardware capabilities, such as Blackwell GPUs, to adjust the installation strategy (e.g., choosing between `pip` and `uv`) [scripts/ci/cuda/ci_install_dependency.sh82-107](https://github.com/sgl-project/sglang/blob/94183a8d/scripts/ci/cuda/ci_install_dependency.sh#L82-L107)

 
### Release and Nightly Tagging

 Docker release workflows utilize complex tag configurations to manage `dev`, `nightly`, and versioned tags. The `prepare` job in the development Docker build workflow computes a `TAG_CONFIG` JSON that handles aliases for CUDA 12 and 13, including dated nightly tags with short SHAs [.github/workflows/release-docker-dev.yml87-93](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-dev.yml#L87-L93)

## Kernel Version Synchronization

 The `sglang-kernel` package is a critical dependency that must be kept in sync with the main engine. It is explicitly pinned in build configurations to ensure compatibility.

 
### Kernel Version Definition

 The kernel library version is managed through various configuration files across the monorepo to support multiple hardware backends. For the current release cycle, version `0.4.6.post1` is the standard:

 
 - `python/pyproject.toml`: Specifies `sglang-kernel==0.4.6.post1` as a core dependency [python/pyproject.toml73](https://github.com/sgl-project/sglang/blob/94183a8d/python/pyproject.toml#L73-L73)
 - `docker/Dockerfile`: Sets `ARG SGL_KERNEL_VERSION=0.4.6.post1` for the image build process [docker/Dockerfile7](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L7-L7)
 - `python/pyproject_xpu.toml`: Uses a Git-based reference for `sgl-kernel @ git+https://github.com/sgl-project/sgl-kernel-xpu.git` [python/pyproject_xpu.toml57](https://github.com/sgl-project/sglang/blob/94183a8d/python/pyproject_xpu.toml#L57-L57)

## Platform-Specific Version Management

 SGLang uses multiple `pyproject.toml` files to manage dependencies across different hardware backends. While the core versioning logic remains consistent (using `setuptools_scm`), the dependency trees and PyTorch versions vary.

 
| File | Target Platform | Package Name | Key Dependencies |
|---|---|---|---|
| python/pyproject.toml | NVIDIA (CUDA) | sglang | torch==2.13.0, flash-attn-4>=4.0.0b18 python/pyproject.toml35-82 |
| python/pyproject_cpu.toml | Intel Xeon | sglang-cpu | torch==2.12.0, triton==3.7.0 python/pyproject_cpu.toml63-68 |
| python/pyproject_xpu.toml | Intel GPU | sglang | torch==2.13.0+xpu, sgl-kernel-xpu python/pyproject_xpu.toml57-62 |

### Version Synchronization for CPU/XPU

 For specialized platforms like CPU or XPU, the `pyproject.toml` files pin specific versions of `torch` and `torchvision` to ensure compatibility. For example, XPU requires `torch==2.13.0+xpu` [python/pyproject_xpu.toml62](https://github.com/sgl-project/sglang/blob/94183a8d/python/pyproject_xpu.toml#L62-L62) while the standard CUDA build uses `torch==2.13.0` [python/pyproject.toml82](https://github.com/sgl-project/sglang/blob/94183a8d/python/pyproject.toml#L82-L82) The AMD-specific build uses external wheel URLs for ROCm-compatible PyTorch builds [3rdparty/amd/wheel/sglang/pyproject.toml83-86](https://github.com/sgl-project/sglang/blob/94183a8d/3rdparty/amd/wheel/sglang/pyproject.toml#L83-L86)
