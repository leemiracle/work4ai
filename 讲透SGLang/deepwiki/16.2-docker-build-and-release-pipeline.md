## Purpose and Scope

 This document describes the Docker image build and release pipeline for SGLang. It covers the multi-stage Docker build architecture, build argument configuration, dependency management, and the automated release process to container registries (Docker Hub). The pipeline produces production-ready Docker images for multiple CUDA versions, ROCm versions, NPU (Ascend CANN), and hardware architectures (x86_64 and ARM64).

 For Python wheel building and release, see [Wheel Build and Release Pipeline](https://deepwiki.com/sgl-project/sglang/16.1-wheel-build-and-release-pipeline). For deploying the resulting Docker images, see [Docker Deployment](https://deepwiki.com/sgl-project/sglang/2.3-docker-deployment). For the `sgl-kernel` build system used within Docker, see [Build System and Multi-Architecture Support](https://deepwiki.com/sgl-project/sglang/11.1-build-system-and-multi-architecture-support).

 
## Multi-Stage Docker Build Architecture

 The SGLang Docker build system uses a multi-stage approach defined in `docker/Dockerfile` with distinct stages to optimize layer caching and reduce final image size.

### Base Stage

 The `base` stage establishes the foundational environment:

 
 - **Base Image**: Uses `nvidia/cuda:${CUDA_VERSION}-cudnn-devel-ubuntu24.04` (defaulting to CUDA 13.0.3) to provide the CUDA toolkit and cuDNN [docker/Dockerfile1-2](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L1-L2)
 - **Python Setup**: Installs Python 3.12, setting it as the default. It also handles PEP 668 workarounds for Ubuntu 24.04 by setting `break-system-packages true` [docker/Dockerfile42-53](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L42-L53)
 - **System Dependencies**: Includes core utilities, build essentials (`cmake`, `ccache`), MPI/NUMA support (`libopenmpi-dev`, `numactl`), and RDMA/InfiniBand support (`libibverbs-dev`, `libfabric-dev`) [docker/Dockerfile59-128](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L59-L128)
 - **GDRCopy**: Installed from source (v2.5.1) for GPU Direct RDMA support [docker/Dockerfile136-143](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L136-L143)
 
 Sources: [docker/Dockerfile1-152](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L1-L152)

 
### Framework Stage

 The `framework` stage builds a complete development environment. It is the primary target for development and CI testing.

 Key components installed in this stage:

 
 - **SGLang Source**: Copied from local build context or cloned based on `BRANCH_TYPE` [docker/Dockerfile5-6](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L5-L6)
 - **sglang-kernel**: Pre-built wheels installed based on CUDA version (e.g., cu126, cu129, or cu130) [docker/Dockerfile192-205](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L192-L205) The version is pinned via `SGL_KERNEL_VERSION` (default 0.4.6.post1) [docker/Dockerfile7](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L7-L7)

### Runtime Stage

 The `runtime` stage creates a production-optimized image by copying only the necessary artifacts from the `framework` stage. This process involves:

 
 - **Fresh Base**: Starts from the CUDA devel image to support JIT compilation for kernels at runtime.
 - **Python Packages**: Copies the site-packages from the framework stage to minimize layer bloat.
 - **Workspace**: Copies `/sgl-workspace` containing SGLang and associated binaries.
 - **Size Optimization**: Typically ~50% smaller than the framework image by excluding build-only dependencies like the Rust toolchain and intermediate C++ build artifacts.
 
 Sources: [docker/Dockerfile25-33](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L25-L33) [.github/workflows/release-docker-runtime.yml4-5](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-runtime.yml#L4-L5)

 
## Multi-Platform Image Variants

 SGLang provides specialized Dockerfiles and release pipelines for diverse hardware accelerators.

 
### 1. Ascend NPU (CANN)

 The NPU pipeline uses `docker/npu.Dockerfile` and is automated via `release-docker-npu.yml`.

 
 - **Base Image**: Inherits from `quay.io/ascend/cann:$CANN_VERSION-$DEVICE_TYPE-$OS-$PYTHON_VERSION` [docker/npu.Dockerfile6](https://github.com/sgl-project/sglang/blob/94183a8d/docker/npu.Dockerfile#L6-L6)
 - **NPU Dependencies**: Installs `torch_npu`, `triton-ascend`, and `sgl-kernel-npu` via `scripts/ci/npu/npu_ci_install_dependency.sh` [scripts/ci/npu/npu_ci_install_dependency.sh47-68](https://github.com/sgl-project/sglang/blob/94183a8d/scripts/ci/npu/npu_ci_install_dependency.sh#L47-L68)
 - **Custom Ops**: Downloads and installs specialized Ascend custom operators for transformer acceleration [scripts/ci/npu/npu_ci_install_dependency.sh71-80](https://github.com/sgl-project/sglang/blob/94183a8d/scripts/ci/npu/npu_ci_install_dependency.sh#L71-L80)
 - **Matrix Build**: Supports multiple CANN versions (default 9.0.0) and device types (e.g., 910b, a3) [.github/workflows/release-docker-npu.yml16-18](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-npu.yml#L16-L18)
 
 Sources: [docker/npu.Dockerfile1-122](https://github.com/sgl-project/sglang/blob/94183a8d/docker/npu.Dockerfile#L1-L122) [scripts/ci/npu/npu_ci_install_dependency.sh1-87](https://github.com/sgl-project/sglang/blob/94183a8d/scripts/ci/npu/npu_ci_install_dependency.sh#L1-L87) [.github/workflows/release-docker-npu.yml1-93](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-npu.yml#L1-L93)

 
### 2. AMD ROCm

 The ROCm pipeline uses `docker/rocm.Dockerfile` and is automated via nightly release workflows [.github/workflows/release-docker-amd-nightly.yml1-5](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-amd-nightly.yml#L1-L5)

 
 - **Architectures**: Targets `gfx942` (MI30x) and `gfx950` (MI35x) architectures across ROCm 7.0, 7.2.0, and 7.2.4 stacks [docker/rocm.Dockerfile31-36](https://github.com/sgl-project/sglang/blob/94183a8d/docker/rocm.Dockerfile#L31-L36)
 - **ROCm Stack**: Includes builds for `aiter`, `triton`, and `mooncake` optimized for ROCm [docker/rocm.Dockerfile47-49](https://github.com/sgl-project/sglang/blob/94183a8d/docker/rocm.Dockerfile#L47-L49)
 - **Expert Parallelism**: Integrates `ENABLE_MORI=1` for expert load balancing (using `mori` JIT for NIC auto-detection) and `ENABLE_NIXL=1` for disaggregation transfer [docker/rocm.Dockerfile14-28](https://github.com/sgl-project/sglang/blob/94183a8d/docker/rocm.Dockerfile#L14-L28)
 - **Flavor Notes**: The ROCm 7.2.4 flavor uses Python 3.12 and torch 2.11, while 7.2.0 remains on Python 3.10 and torch 2.9.1 [docker/rocm.Dockerfile9-12](https://github.com/sgl-project/sglang/blob/94183a8d/docker/rocm.Dockerfile#L9-L12)
 - **IPC Workaround**: Sets `HSA_ENABLE_IPC_MODE_LEGACY=1` for ROCm 7.2.4 to avoid GPU memory leaks in the CUDA/ROCm IPC path [docker/rocm.Dockerfile79-83](https://github.com/sgl-project/sglang/blob/94183a8d/docker/rocm.Dockerfile#L79-L83)

## Automated Release Pipelines

 SGLang maintains several automated workflows for building and pushing images to Docker Hub.

 
### Development and Nightly Pipeline

 
 - **NVIDIA Dev**: Runs daily to build `dev` and `dev-cu13` tags [.github/workflows/release-docker-dev.yml35-36](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-dev.yml#L35-L36)
 - **Workflow Orchestration**: Uses `_docker-build-and-publish.yml` as a reusable workflow to handle parallel builds for x86 and ARM64 [.github/workflows/_docker-build-and-publish.yml1-7](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/_docker-build-and-publish.yml#L1-L7)
 - **Overlay Builds**: Supports optional "overlay" Dockerfiles for adding layers (e.g., custom plugins) without a full repo checkout [.github/workflows/release-docker-dev.yml23-26](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-dev.yml#L23-L26)
 - **AMD CI Mirroring**: Freshly published ROCm images are mirrored to an in-network Docker registry (e.g., `10.44.14.109:5000`) to avoid Docker Hub rate limits during CI runs [.github/workflows/release-docker-amd-nightly.yml158-164](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-amd-nightly.yml#L158-L164)
 
 
### Patch and Staging Pipeline

 
 - **Patching**: The `patch-docker-dev.yml` workflow allows fast-patching an existing image by applying a binary git diff between the image's base commit and latest main/PR, avoiding a full rebuild [.github/workflows/patch-docker-dev.yml153-175](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/patch-docker-dev.yml#L153-L175)
 - **GB200 Nightly**: A specialized pipeline for Blackwell (GB200) cluster testing, building ARM64 images from PRs or branches to `lmsysorg/sglang-staging` [.github/workflows/nightly-72-gpu-gb200.yml38-40](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/nightly-72-gpu-gb200.yml#L38-L40)
