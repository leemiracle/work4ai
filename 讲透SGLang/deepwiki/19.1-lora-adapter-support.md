  This document describes SGLang's support for serving Low-Rank Adaptation (LoRA) adapters alongside base models. SGLang integrates techniques from "S-LoRA: Serving Thousands of Concurrent LoRA Adapters" and "Punica: Multi-Tenant LoRA Serving" to efficiently support multiple LoRA adapters for different sequences within a single forward batch [python/sglang/srt/lora/lora_manager.py15-16](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora_manager.py#L15-L16)

 **Scope**: This page covers LoRA configuration, memory management, adapter lifecycle, and multi-LoRA batch execution.

 
---

 
## Architecture Overview

 The LoRA system in SGLang is distributed across the multi-process architecture, with the `LoRARegistry` managing adapter metadata and the `LoRAManager` managing weight buffers and kernels in the Model Executor [python/sglang/srt/lora/lora_manager.py63-116](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora_manager.py#L63-L116)

## Memory Management and Memory Pool

 SGLang pre-allocates a LoRA memory pool to avoid frequent allocations and fragmentation during inference. This pool stores the `A` and `B` matrices of loaded adapters [python/sglang/srt/lora/mem_pool.py131-150](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/mem_pool.py#L131-L150)

 
### LoRAMemoryPool Structure

 The `LoRAMemoryPool` manages large buffers for different model layers (QKV, Gate-Up, Down, etc.). It organizes weights into tensors optimized for segment GEMM operations. Standard LoRA uses 3D buffers, while MoE LoRA uses 4D buffers to account for expert dimensions [python/sglang/srt/lora/mem_pool.py199-206](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/mem_pool.py#L199-L206)

 
| Buffer Type | Shape | Description |
|---|---|---|
| A_buffer | (max_loras, stacked * max_rank, input_dim) | Row-major tensors for LoRA A python/sglang/srt/lora/mem_pool.py199-200 |
| B_buffer | (stacked, max_loras, output_dim, max_rank) | Column-major tensors for LoRA B python/sglang/srt/lora/mem_pool.py200-201 |
| embedding_A_buffer | (num_loras, rank, vocab_size) | Weights for embedding lookup python/sglang/srt/lora/mem_pool.py202 |
| lm_head_B_buffer | (num_loras, sharded_vocab, rank) | Sharded weights for column-parallel head python/sglang/srt/lora/mem_pool.py206 |

### Eviction Policies

 When the memory pool is full (`max_loras_per_batch` reached), the `LoRAManager` triggers eviction based on the configured policy in `ServerArgs` [python/sglang/srt/lora/lora_manager.py99-107](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora_manager.py#L99-L107)

 
 - **LRU (Least Recently Used)**: Evicts the adapter that has not been used for the longest time. This is the default policy for better cache efficiency [python/sglang/srt/lora/lora_manager.py99](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora_manager.py#L99-L99) via `LRUEvictionPolicy`.
 - **FIFO (First-In-First-Out)**: Evicts the oldest loaded adapter regardless of usage frequency.
 
 The eviction logic is encapsulated in policies retrieved via `get_eviction_policy` in `LoRAMemoryPool` [python/sglang/srt/lora/mem_pool.py197-198](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/mem_pool.py#L197-L198)

## Multi-LoRA Serving Lifecycle

 
### 1. Adapter Registration

 The `LoRARegistry` assigns a unique `lora_id` to every adapter to prevent conflicts between identical paths or names. Metadata is stored in `LoRARef` [python/sglang/srt/lora/lora_registry.py37](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora_registry.py#L37-L37)

 
### 2. Loading and Weight Normalization

 When an adapter is loaded, `LoRAAdapter` iterates through weights and performs normalization, specifically for stacked layers like QKV and Gate-Up [python/sglang/srt/lora/lora.py143-162](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora.py#L143-L162)

 
 - **QKV Normalization**: If an adapter only provides `q_proj` weights, SGLang initializes `k_proj` and `v_proj` with zeros to maintain the stacked tensor format [python/sglang/srt/lora/lora.py176-197](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora.py#L176-L197)
 - **Gate-Up Normalization**: Merges `gate_proj` and `up_proj` into a single `gate_up_proj` weight [python/sglang/srt/lora/lora.py210-234](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora.py#L210-L234)
 - **MoE Normalization**: Renames expert weights (e.g., `w1`, `w2`, `w3`) to standard projection names for consistency [python/sglang/srt/lora/lora.py164-171](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/lora.py#L164-L171)

## Special LoRA Types

 
### Embedding LoRA

 SGLang supports LoRA for `VocabParallelEmbedding`. The implementation uses an efficient embedding lookup for `LoRA A` and a standard SGEMM for `LoRA B` [python/sglang/srt/lora/layers.py84-163](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/layers.py#L84-L163)

 
 - **TP Handling**: For Embedding LoRA with TP > 1, weights are kept fully replicated (unsharded) on every rank unless `input_scattered` mode is active [python/sglang/srt/lora/layers.py113-118](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/layers.py#L113-L118)
 - **Extra Tokens**: Supports processing added/extra tokens beyond the base vocabulary via `run_lora_a_embedding` [python/sglang/srt/lora/layers.py165-180](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/lora/layers.py#L165-L180)

### Fused MoE LoRA

 SGLang includes specialized support for applying LoRA to Mixture-of-Experts (MoE) layers [python/sglang/srt/layers/moe/fused_moe_triton/layer.py](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/layers/moe/fused_moe_triton/layer.py)
