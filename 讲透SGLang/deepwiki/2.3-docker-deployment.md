  This page documents the Docker deployment for SGLang, detailing the Docker image variants, the multi-stage build system, platform-specific image variants (NVIDIA CUDA, AMD ROCm, Huawei NPU, Intel XPU), key build arguments, CI/CD pipelines for releasing images, and deployment best practices.

## Overview

 SGLang provides Docker images as the primary method for deploying the inference server in production. The build system employs a **multi-stage build pattern** to produce variants optimized for production runtime or development environments.

 
 - **Runtime Image**: Minimal production image with reduced size, containing only runtime libraries and Python packages.
 - **Framework Image**: Full environment with build dependencies, source code, profiling tools, and development utilities.
 
 All Docker images include the full CUDA/ROCm toolkit to enable **JIT kernel compilation** for optimized GPU kernels at runtime, such as DeepGEMM FP8 GEMM, Triton kernels, and FlashInfer attention mechanisms.

## Image Variants and Multi-Stage Build Architecture

 
### Multi-Stage Build Flow

 The Docker build process leverages Docker BuildKit's parallelism, organizing build steps in stages to optimize cache usage and build speed.

 
```

```

 **Details:**

 
 - **Base Stage:** Builds the base image containing system libraries, Python 3.12, GPU direct RDMA (GDRCopy), OpenMPI, and InfiniBand/RDMA drivers necessary for high-performance communication [docker/Dockerfile41-128](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L41-L128)
 - **Parallel Builder Stages:** In parallel, multiple builder stages prepare specific components: 
 - `torch_deps`: Builds and installs `sgl-kernel` and core torch dependencies [docker/Dockerfile176-215](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L176-L215)
 - `deepep_builder`: Builds the NCCL EP communication and RDMA libraries for distributed model parallelism.
 - `mooncake_builder`: Builds Mooncake, SGLang’s transfer engine used for distributed KV cache management [docker/Dockerfile316-347](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L316-L347)
 - `gateway_builder`: Compiles the Rust-based routing components: `sgl-router` and `sgl-model-gateway` [docker/Dockerfile349-366](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L349-L366)
 - **Framework Stage:** Consolidates all built artifacts, installs the editable SGLang source code, and includes development tools for profiling and debugging [docker/Dockerfile442-530](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L442-L530)
 - **Runtime Stage:** Produces a minimal runtime image by copying only the Python packages and runtime dependencies from the framework stage, stripping development tools to reduce image size [docker/Dockerfile546-580](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L546-L580)
 
 This multi-stage build structure enables flexible and efficient builds for both development and production deployment.

 Sources: [docker/Dockerfile1-580](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L1-L580)

### Platform Support and Image Variants

 SGLang is designed to run efficiently on multiple hardware platforms, each with tuned Docker image variants to match the platform-specific dependencies and optimizations.

 
| Platform | Dockerfile | Image Repository | Supported Architectures / Notes |
|---|---|---|---|
| NVIDIA CUDA | docker/Dockerfile | lmsysorg/sglang | Supports CUDA architectures SM80, SM90, SM100 |
| AMD ROCm | docker/rocm.Dockerfile | lmsysorg/sglang-rocm | Supports gfx942 (MI30x), gfx950 (MI35x); multiple ROCm versions (7.0, 7.2, 7.2.4) docker/rocm.Dockerfile2-13 |
| Huawei NPU | docker/npu.Dockerfile | lmsysorg/sglang | Supports Ascend 910b with CANN 9.0.0 |
| Intel XPU | N/A (Python-based) | N/A | Targeted by Python packaging python/pyproject_xpu.toml |

 
#### AMD ROCm Docker Image Variant Details

 
 - The ROCm Docker image supports several GPU architectures (`gfx942` and `gfx950`) with fine-grained control over ROCm stack versions and Python versions.
 - Multiple build arguments allow enabling/disabling Mori NIC auto-detection (`ENABLE_MORI`), and NIXL KV cache transfer backend (`ENABLE_NIXL`) [docker/rocm.Dockerfile112-128](https://github.com/sgl-project/sglang/blob/94183a8d/docker/rocm.Dockerfile#L112-L128)

## Core Build Arguments

 Several build arguments influence the Docker build, allowing customization for versions, hardware, and builder options:

 
| Argument | Default | Description |
|---|---|---|
| CUDA_VERSION | 13.0.3 | NVIDIA CUDA base image version used in CUDA Dockerfile docker/Dockerfile1 |
| SGL_KERNEL_VERSION | 0.4.6.post1 | Version tag of prebuilt sgl-kernel used in build docker/Dockerfile7 |
| GPU_ARCH | gfx950 | AMD GPU architecture for ROCm builds; gfx942 or gfx950 docker/rocm.Dockerfile30 |
| ENABLE_MORI | 0 | Enable Mori NIC auto-detection in ROCm image (1 = enable) docker/rocm.Dockerfile112 |
| ENABLE_NIXL | 1 | Enable NIXL asynchronous KV transfer backend in ROCm image docker/rocm.Dockerfile121 |
| SGL_BRANCH | main | Git branch or tag for source checkout during image build docker/rocm.Dockerfile88 |

 These build arguments provide flexibility to adapt the Docker images for specific hardware generations, driver versions, or experimental features (e.g., RDMA NIC detection).

 Sources: [docker/Dockerfile1-20](https://github.com/sgl-project/sglang/blob/94183a8d/docker/Dockerfile#L1-L20) [docker/rocm.Dockerfile30-130](https://github.com/sgl-project/sglang/blob/94183a8d/docker/rocm.Dockerfile#L30-L130)

## CI/CD and Release Pipelines

 SGLang automates Docker image building and publishing via GitHub Actions workflows, with separate workflows and tags for CUDA and ROCm images.

 
### Nightly and Release Builds

 
| Workflow File | Description | Platforms |
|---|---|---|
| .github/workflows/release-docker-dev.yml | Builds and pushes nightly development images with dated tags | NVIDIA CUDA |
| .github/workflows/release-docker-amd-nightly.yml | Builds and pushes nightly ROCm 7.0 AMD images | AMD ROCm 7.0 |
| .github/workflows/release-docker-amd-rocm720-nightly.yml | Builds and pushes nightly ROCm 7.2 and 7.2.4 AMD images | AMD ROCm 7.2 & 7.2.4 |
| .github/workflows/release-docker.yml | Official release build that tags images with semantic versions | Cross-platform |

 
### Tagging and Image Naming

 
 - Tags use semantic versioning with GPU arch suffixes, e.g., `v0.5.10-rocm720-mi35x`.
 - Nightly builds embed dates and commit SHA suffixes, e.g., `nightly-dev-cu13-20240616-g1a2b3c4`.
 
 
### Local Registry Mirroring and CI Usage

 
 - AMD CI runners mirror images from Docker Hub to internal registries (`10.44.14.109:5000`) to avoid Docker Hub rate limits [.github/workflows/release-docker-amd-rocm720-nightly.yml160-173](https://github.com/sgl-project/sglang/blob/94183a8d/.github/workflows/release-docker-amd-rocm720-nightly.yml#L160-L173)
 - The CI test suite (`test/run_suite.py`) runs containerized tests selecting images based on hardware backend (CUDA, AMD), ensuring that Docker images validate expected functionality [test/run_suite.py18-26](https://github.com/sgl-project/sglang/blob/94183a8d/test/run_suite.py#L18-L26)

## Deployment Best Practices

 
### Recommended Container Launch Configuration

 To optimize runtime behavior and efficiency for the multi-process SGLang server, containers are recommended to be started with the following considerations:

 
| Aspect | Recommendation | Notes |
|---|---|---|
| GPU Access | --gpus all (NVIDIA) or --device /dev/kfd --device /dev/dri (AMD) | Needed for GPU access inside the container scripts/ci/amd/amd_ci_start_container.sh97-102 |
| Shared Memory | --shm-size=32g or --ipc=host | Increases IPC buffer via /dev/shm for ZMQ communication between Engine, Scheduler, DetokenizerManager |
| Networking | --network=host | Recommended especially for multi-node or distributed deployment for low-latency connectivity |
| VRAM Cleaning | Use ensure_vram_clear.sh script before container start | Prevents OOM errors caused by stale GPU processes in CI environments .github/workflows/nightly-test-amd-rocm720.yml150-160 |

 
### Container Runtime Notes

 
 - SGLang uses ZMQ over Unix domain sockets or IPC shared memory for manager communication internally; adequate shm size is necessary.
 - For multi-node distributed serving, host network mode reduces overhead and simplifies service discovery.
 - Persistent volumes are typically mounted at `/sgl-data` for cache persistence and logs.
