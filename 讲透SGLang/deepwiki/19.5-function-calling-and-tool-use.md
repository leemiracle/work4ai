  SGLang provides a high-performance infrastructure for function calling and tool use, supporting a wide array of model-specific formats through a modular detector-based architecture. It handles both one-time (non-streaming) and incremental (streaming) parsing, allowing for low-latency tool call detection during LLM generation.

 
## Architecture Overview

 The function calling system is centered around the `FunctionCallParser`, which acts as a dispatcher to various model-specific `BaseFormatDetector` implementations.

 
### Key Components

 
 - **`FunctionCallParser`**: The main entry point for the server to handle tool calls. It manages the lifecycle of a tool call request and selects the appropriate detector based on the model configuration [python/sglang/srt/function_call/function_call_parser.py58-117](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/function_call_parser.py#L58-L117)
 - **`BaseFormatDetector`**: An abstract base class defining the interface for all format detectors. It provides common utilities for JSON parsing, buffer management, and streaming state tracking [python/sglang/srt/function_call/base_format_detector.py32-57](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/base_format_detector.py#L32-L57)
 - **`ToolCallItem`**: A data structure representing a parsed tool call, including the tool index, function name, and arguments [python/sglang/srt/function_call/core_types.py9-16](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/core_types.py#L9-L16)
 - **`StreamingParseResult`**: Encapsulates the output of a parsing step, containing both `normal_text` (to be displayed to the user) and any detected `calls` [python/sglang/srt/function_call/core_types.py19-27](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/core_types.py#L19-L27)

## Streaming and Incremental Parsing

 For streaming responses, SGLang must distinguish between normal conversation text and tool call metadata. The `BaseFormatDetector` maintains internal state to handle tokens split across multiple network chunks.

 
### State Management

 The detector tracks the following state during a stream [python/sglang/srt/function_call/base_format_detector.py38-52](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/base_format_detector.py#L38-L52):

 
 - `_buffer`: Accumulates incomplete patterns.
 - `current_tool_id`: Tracks which tool in a parallel call sequence is being generated.
 - `current_tool_name_sent`: Ensures the tool name is only sent once before streaming arguments.
 - `streamed_args_for_tool`: Stores the raw JSON string content streamed to client for each tool's arguments to calculate deltas.
 
 
### Partial Token Handling

 Detectors use `_ends_with_partial_token` to check if the end of a buffer matches the start of a tool delimiter (e.g., the model has output `[TOOL_` but not yet `CALLS]`). In such cases, the parser holds back the text until the token is completed or invalidated [python/sglang/srt/function_call/base_format_detector.py112-123](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/base_format_detector.py#L112-L123)

## Reasoning Parser

 SGLang introduces advanced parsing for models that separate reasoning (thinking) from final output, such as DeepSeek-R1, Kimi-K3, or Gemma 4.

 
### Reasoning Parser Implementation

 The `ReasoningParser` manages the separation of "thinking" blocks from normal response text. It uses a `BaseReasoningFormatDetector` initialized with tokens like `think_start_token` (e.g., `<think>`) [python/sglang/srt/parser/reasoning_parser.py62-87](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/reasoning_parser.py#L62-L87)

 
 - **One-time Parsing**: `detect_and_parse` extracts reasoning and normal text from a full string [python/sglang/srt/parser/reasoning_parser.py116-170](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/reasoning_parser.py#L116-L170)
 - **Streaming Parsing**: `parse_streaming_increment` manages buffers to stream reasoning content as it arrives, handling cases where reasoning might be interrupted by tool calls [python/sglang/srt/parser/reasoning_parser.py171-200](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/reasoning_parser.py#L171-L200)
 - **Model Specifics**: Special detectors like `DeepSeekV4Detector`, `Gemma4Detector`, and `KimiK3Detector` handle model-specific tokens like `<|thought|>` or `THINK_OPEN`/`THINK_CLOSE` [python/sglang/srt/parser/reasoning_parser.py5-25](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/parser/reasoning_parser.py#L5-L25)

## Tool Call Formats and Constraints

 
### Structural Tags and JSON Schema

 SGLang can guide models to follow specific tool formats using structural tags or JSON Schema constraints.

 
 - **JSON Schema**: The `get_json_schema_constraint` utility generates constraints for tool parameters [python/sglang/srt/function_call/utils.py50-53](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/utils.py#L50-L53)
 - **Normalization**: `normalize_json_schema_types` walks a JSON Schema and rewrites non-standard types (e.g., `varchar`, `int`, `enum`) to their standard JSON Schema equivalents (e.g., `string`, `integer`) [python/sglang/srt/function_call/utils.py113-176](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/utils.py#L113-L176)
 
 
### Type Inference and Coercion

 Some models output parameters in formats that require coercion to JSON types.

 
 - **XML/DSML Parsing**: `DeepSeekV32Detector` supports both XML-like parameter tags and direct JSON within its `<｜DSML｜invoke>` blocks [python/sglang/srt/function_call/deepseekv32_detector.py115-160](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/deepseekv32_detector.py#L115-L160)
 - **Type Coercion**: Detectors often use `_partial_json_loads` to handle incomplete JSON streams, ensuring that even partially generated arguments can be processed for UI updates [python/sglang/srt/function_call/utils.py188-214](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/utils.py#L188-L214)
 - **GLM Parsing**: `Glm4MoeDetector` and `Glm47MoeDetector` use state-based logic to convert XML-like `<arg_key>` and `<arg_value>` tags into JSON arguments incrementally [python/sglang/srt/function_call/glm4_moe_detector.py148-163](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/function_call/glm4_moe_detector.py#L148-L163)
