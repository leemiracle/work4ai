  This page documents SGLang's multi-process architecture and inter-process communication (IPC) mechanisms. It details the server's process model, the ZMQ-based IPC channels, key data flow, and inter-process communication patterns that enable efficient serving of large language and vision-language models.

 
---

 
## Process Architecture Overview

 SGLang adopts a multi-process architecture that partitions the serving workload into isolated processes to circumvent Python's GIL limitations, improve concurrency, and enable scalable GPU and multi-device utilization.

 
### Core Processes

 
 - **Main Process**: Contains the HTTP server (FastAPI), the orchestrator `Engine`, and the `TokenizerManager` which handles input tokenization and request state lifecycle [python/sglang/srt/entrypoints/engine.py155-216](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/engine.py#L155-L216)
 - **Scheduler Process**: Manages request scheduling, batching, and performs the core model forward execution on GPUs or accelerators via the `ModelRunner` abstraction [python/sglang/srt/managers/scheduler.py14](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler.py#L14-L14)
 - **DetokenizerManager Process**: Responsible for converting output token IDs from the Scheduler into strings asynchronously to avoid blocking GPU workloads [python/sglang/srt/managers/detokenizer_manager.py1-20](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/detokenizer_manager.py#L1-L20)
 
 Additional optional processes include:

 
 - **DataParallelController**: Handles coordination of distributed data parallelism across devices [python/sglang/srt/managers/data_parallel_controller.py1-30](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/data_parallel_controller.py#L1-L30)
 - **MultiTokenizerRouter**: Manages routing for multi-tokenizer setups to improve tokenization throughput or support specialized tokenizers [python/sglang/srt/managers/multi_tokenizer_mixin.py1-50](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/multi_tokenizer_mixin.py#L1-L50)

## Process Components

 
### Main Process: Engine and TokenizerManager

 The **Main Process** integrates several critical functionalities:

 
 - **HTTP Server**: Implements OpenAI-compatible HTTP API endpoints using FastAPI, handling incoming user requests and routing them to the TokenizerManager [python/sglang/srt/entrypoints/http_server.py86-111](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/http_server.py#L86-L111)
 - **Engine**: The core orchestrator handling lifecycle management, subprocess launching (Scheduler, DetokenizerManager), and exposing the Python inference API [python/sglang/srt/entrypoints/engine.py207-216](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/engine.py#L207-L216)
 - **TokenizerManager**: Converts textual or multimodal inputs into token IDs, manages per-request state (`ReqState`), maintains scheduling metadata, and dispatches tokenized requests to the Scheduler using ZMQ [python/sglang/srt/managers/tokenizer_manager.py215-221](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/tokenizer_manager.py#L215-L221)

| TokenizerManager | TokenizerManager | Input tokenization, state management, IPC initiation |

### Scheduler Process

 The **Scheduler** subprocess encapsulates core GPU work and scheduling logic:

 
 - **Batch Scheduling**: Maintains request queues, decides batch formation strategies, and creates `ScheduleBatch` metadata objects representing CPU-side batch info [python/sglang/srt/managers/schedule_batch.py36-48](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L36-L48)
 - **Model Execution**: Invokes `ModelRunner` to perform the actual model forward passes on GPU/accelerator, supporting prefill, decode, and mixed execution modes [python/sglang/srt/model_executor/model_runner.py14](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/model_runner.py#L14-L14)
 - **Memory Management**: Controls allocation of request token pools and prefix caches to optimize KV cache memory and reuse [python/sglang/srt/managers/schedule_batch.py89-106](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L89-L106)

### DetokenizerManager Process

 The **DetokenizerManager** handles asynchronous conversion of token IDs to strings:

 
 - Receives output token ID batches (`BatchTokenIDOutput`) from Scheduler via ZMQ.
 - Performs incremental and batch detokenization to generate output strings.
 - Sends detokenized results (`BatchStrOutput`) back to the TokenizerManager for response streaming.
 
 
| Component | Function | Responsibility |
|---|---|---|
| DetokenizerManager | run_detokenizer_process | Converts tokens to strings asynchronously |

## IPC Channels and Communication Patterns

 SGLang uses **ZeroMQ (ZMQ)** for high-performance and asynchronous IPC between processes. Sockets use either UNIX domain sockets or TCP endpoints, depending on configuration.

 
### Primary IPC Channels in SGLang

 
| IPC Channel Name | ZMQ Pattern | Direction | Message Type | Purpose |
|---|---|---|---|---|
| scheduler_input_ipc_name | PUSH → PULL | TokenizerManager → Scheduler | TokenizedGenerateReqInput | Transmit tokenized generation requests |
| detokenizer_ipc_name | PUSH → PULL | Scheduler → DetokenizerManager | BatchTokenIDOutput | Batch output token IDs for detokenization |
| tokenizer_ipc_name | PUSH → PULL | DetokenizerManager → TokenizerManager | BatchStrOutput | Return detokenized strings |
| rpc_ipc_name | DEALER ↔ ROUTER | Engine ↔ Scheduler | RpcReqInput / RpcReqOutput | Internal RPC control, monitoring |

## Implementation Details and Techniques

 
 - **Serialization and MsgPack**: IPC messages are serialized using `msgspec` with optional pickle wrapping (`PickleWrapper`) to support transmitting complex Python objects such as multimodal inputs or tracing contexts without loss of fidelity [python/sglang/srt/managers/io_struct.py104-115](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/io_struct.py#L104-L115)
 - **Asynchronous IO and Event Loop**: The `TokenizerManager` and other components utilize `zmq.asyncio` and the high-performance `uvloop` event loop for non-blocking, concurrent request processing and message dispatch [python/sglang/srt/managers/tokenizer_manager.py43-135](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/tokenizer_manager.py#L43-L135)
 - **Shared Memory and Zero-Copy**: For large multimodal data payloads (images, videos), shared memory and specialized transport proxies like `CudaIpcTensorTransportProxy` are used to minimize serialization overhead and data copying between processes [python/sglang/srt/managers/schedule_batch.py114-116](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L114-L116)
 - **RPC Control Channel**: The `Engine` uses a ZMQ DEALER/ROUTER socket pair to send control RPC commands (`RpcReqInput`) and receive responses from the Scheduler, facilitating lifecycle management, monitoring, and dynamic configuration changes [python/sglang/srt/entrypoints/engine.py81-89](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/engine.py#L81-L89)

## Performance and Optimization Considerations

 
 - **CUDA Graph Capture**: The Scheduler process manages CUDA graph capture and replay strategies for repeated model execution patterns such as decoding loops to boost throughput and reduce CPU scheduling overhead [python/sglang/srt/model_executor/model_runner.py116-120](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/model_runner.py#L116-L120)
 - **Multi-Tokenizer Support**: SGLang supports scaling tokenization throughput and specialized text processing by spawning multiple tokenizer workers managed via the `MultiTokenizerRouter` process [python/sglang/srt/entrypoints/engine.py91-94](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/entrypoints/engine.py#L91-L94)
 - **Detokenization Offload**: The detokenization work is offloaded to a separate process (DetokenizerManager) to prevent blocking the Scheduler's GPU-bound execution and achieve parallelism in response synthesis [python/sglang/srt/managers/detokenizer_manager.py1-20](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/detokenizer_manager.py#L1-L20)
