  This page defines the core technical terms used within the SGLang Runtime (SRT). It covers the data structures, scheduling logic, and memory management systems that enable high-performance LLM and VLM serving.

 
## 1. Request and Batch Data Structures

 SGLang uses a tiered set of data structures to represent work as it moves from the high-level scheduler to the low-level GPU kernels.

 
### Req (Request)

 The `Req` class is the primary representation of a single inference request within the `Scheduler`. It tracks the entire lifecycle of a request, including its token IDs, KV cache state, and sampling status.

 
 - **Key Fields**: `origin_input_ids`, `output_ids`, `prefix_indices` (locations in KV cache), and `status`.
 - **Implementation**: [python/sglang/srt/managers/schedule_batch.py204-205](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L204-L205)
 
 
### ScheduleBatch

 Managed by `scheduler.py`, this object groups multiple `Req` objects for a single forward pass. It contains high-level scheduling data, mostly residing on the CPU.

 
 - **Implementation**: [python/sglang/srt/managers/schedule_batch.py205](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/schedule_batch.py#L205-L205)
 
 
### ForwardBatch

 The lowest-level representation, managed by `ModelRunner`. It consists primarily of GPU tensors ready for kernel execution, such as `input_ids`, `position_ids`, and `sampling_info`. It is constructed directly from a `ScheduleBatch` via `ForwardBatch.init_new`.

 
 - **Forward Modes**: Defined in `ForwardMode` (IntEnum), including `EXTEND` (prefill), `DECODE`, `MIXED` (chunked prefill), `TARGET_VERIFY` (speculative decoding), `SPLIT_PREFILL` (for PD multiplexing), and `DLLM_EXTEND` (for discrete diffusion).
 - **Implementation**: [python/sglang/srt/model_executor/forward_batch_info.py97](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/forward_batch_info.py#L97-L97)

## 2. Server Configuration

 
### ServerArgs

 The `ServerArgs` dataclass stores all configuration parameters for the SRT server, ranging from model paths and hardware settings to optimization flags like quantization and attention backends.

 
 - **Key Params**: `model_path`, `tp_size`, `quantization`, `mem_fraction_static`, `enable_cuda_graph`, `attention_backend`.
 - **Implementation**: [python/sglang/srt/server_args.py202](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/server_args.py#L202-L202) (within dataclass definition)

## 3. Memory Management and KV Cache

 SGLang manages GPU memory through a hierarchical system of pools and caches to maximize prefix sharing and minimize fragmentation.

 
### ReqToTokenPool

 A memory pool that maps a `Req` to its token locations. It maintains a 2D tensor `req_to_token` of shape `(max_batches, max_context_len)`.

 
 - **Implementation**: [python/sglang/srt/model_executor/model_runner.py92](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/model_runner.py#L92-L92)
 
 
### TokenToKVPool (KVCache)

 This is the physical storage for Key and Value tensors. It is managed by an allocator (e.g., `BaseTokenToKVPoolAllocator`) that provides indices for new tokens.

 
 - **Implementation**: [python/sglang/srt/model_executor/model_runner.py88](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/model_runner.py#L88-L88)
 
 
### RadixCache

 A tree-based caching mechanism that stores KV cache tensors for prefixes. It allows multiple requests to share the same prefix (e.g., a common system prompt) without redundant computation or storage.

 
 - **Key Functions**: `match_prefix` to find existing cache hits and `evict` to manage memory via LRU/LFU policies.
 - **Implementation**: [python/sglang/srt/mem_cache/radix_cache.py50-54](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/radix_cache.py#L50-L54)
 
 
### HiCache (HiRadixCache)

 A multi-tier extension of the RadixCache that supports offloading KV cache tokens to host memory (CPU) or external storage backends (e.g., Mooncake).

 
 - **HiCacheController**: Manages data movement between GPU and storage tiers. [python/sglang/srt/mem_cache/unified_radix_cache.py42-44](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/unified_radix_cache.py#L42-L44)
 - **HiSparse**: A coordination system for managing sparse memory pool patterns via `HiSparseCoordinator`. [python/sglang/srt/managers/hisparse_coordinator.py14-20](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/hisparse_coordinator.py#L14-L20)
 - **UnifiedRadixCache**: A unified interface that manages different cache components (Full KV, SWA, Mamba) under a single tree core. [python/sglang/srt/mem_cache/unified_radix_cache.py148-152](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/unified_radix_cache.py#L148-L152)
 - **Implementation**: [python/sglang/srt/mem_cache/unified_radix_cache.py148-206](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/mem_cache/unified_radix_cache.py#L148-L206)

## 4. Execution and Scheduling

 
### Scheduler

 The `Scheduler` is the heart of the runtime. It decides which requests to include in the next batch based on memory availability and scheduling policies. It uses mixins for specialized logic like `SchedulerDisaggregationPrefillMixin` and `SchedulerDllmMixin`.

 
 - **Implementation**: [python/sglang/srt/managers/scheduler.py238-240](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler.py#L238-L240) (within Scheduler class)
 
 
### ModelRunner

 The `ModelRunner` executes the forward pass of the model. It handles tensor preparation, CUDA graph management, and interaction with specific model implementations.

 
 - **Implementation**: [python/sglang/srt/model_executor/model_runner.py166-168](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/model_runner.py#L166-L168) (within ModelRunner class)
 
 
### CUDA Graphs

 SGLang uses CUDA Graphs to reduce CPU overhead during the `Decode` phase and certain `Prefill` scenarios.

 
 - **CudaGraphRunner**: Captures and replays CUDA graphs for fixed batch sizes. [python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py26-28](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/runner/decode_cuda_graph_runner.py#L26-L28)
 - **Breakable CUDA Graph**: A mechanism implemented in `BreakableCudaGraphBackend` to allow certain operations to "break" the graph capture. [python/sglang/srt/model_executor/runner_backend/breakable_cuda_graph_backend.py18-25](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/runner_backend/breakable_cuda_graph_backend.py#L18-L25)
 - **Piecewise CUDA Graph**: Captures the model in multiple segments (pieces) to allow for more flexible execution. [python/sglang/srt/model_executor/runner_backend/tc_piecewise_cuda_graph_backend.py20-30](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/model_executor/runner_backend/tc_piecewise_cuda_graph_backend.py#L20-L30)
