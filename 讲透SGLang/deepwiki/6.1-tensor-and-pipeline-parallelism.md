  This document explains SGLang's implementation of **Tensor Parallelism (TP)** and **Pipeline Parallelism (PP)** for distributing model execution across multiple GPUs. These parallelism strategies enable serving large language models that exceed single-GPU memory capacity and improve throughput through parallel computation.

 **Scope:** This page covers TP, including weight sharding and collective communication, and PP, including asynchronous pipeline scheduling and communication. For **Expert Parallelism** used in MoE models, see [6.2](https://github.com/sgl-project/sglang/blob/94183a8d/6.2) For **Data Parallelism** and batch splitting, see [6.3](https://github.com/sgl-project/sglang/blob/94183a8d/6.3)

 
---

 
## Tensor Parallelism Overview

 **Tensor Parallelism (TP)** partitions model weights across multiple GPUs within the same layer. Each GPU holds a shard of the weight matrices and processes the same input tokens in parallel.

 
### Weight Sharding Strategy

 SGLang implements Megatron-style weight partitioning in linear layers. Two main sharding patterns are used:

 
| Layer Type | Sharding Dimension | Output Behavior | Communication |
|---|---|---|---|
| ColumnParallelLinear | Output dimension (columns) | Each rank computes a shard of the output activations | Can require AllReduce or Gather to combine outputs |
| RowParallelLinear | Input dimension (rows) | Each rank processes input shards, output remains replicated or partly reduced | Optional AllReduce to aggregate partial results |

 
### Communication Mechanisms: NCCL and GroupCoordinator

 SGLang implements communication primitives essential for TP in `parallel_state.py`. Core concepts include:

 
 - **GroupCoordinator**: An abstraction managing process groups and communication operations (AllReduce, AllGather, ReduceScatter) [python/sglang/srt/distributed/parallel_state.py160-210](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L160-L210) It tracks communication backends and handles different hardware platforms (CUDA, ROCm, NPU, XPU, MUSA).
 - **AllReduce Implementations**: 
 - `inplace_all_reduce(tensor, group_name)` lowers to the `GroupCoordinator` instance and performs in-place NCCL or custom all-reduce operations [python/sglang/srt/distributed/parallel_state.py168-175](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L168-L175)
 - `outplace_all_reduce(tensor, group_name, method)` supports out-of-place all-reduce with optional method variants (e.g., using fusion) [python/sglang/srt/distributed/parallel_state.py178-185](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L178-L185)
 - **NPU (Ascend) Specialization**: `get_torch_distributed_pg_options` sets HCCL options for buffer sizes (e.g., `DEEPEP_HCCL_BUFFSIZE`) and group creation supporting NPU backend environment tuning [python/sglang/srt/distributed/parallel_state.py89-104](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L89-L104)
 
 
### Fused Communication and Kernel Execution

 To reduce overhead, SGLang supports communication fusion for AllReduce:

 
 - **FlashInfer AllReduce Fusion**: When enabled (on NVIDIA SM90+/SM100 GPUs), it merges AllReduce calls with residual/RMSNorm computations. This fusion is gated by `apply_flashinfer_allreduce_fusion(batch_size)` and is typically used for batch sizes up to 2048 tokens [python/sglang/srt/layers/communicator.py165-179](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/layers/communicator.py#L165-L179)
 - **Aiter AllReduce Fusion**: For ROCm/AMD platforms, this fusion improves performance for certain tensor sizes (e.g., total bytes <= 64 MB) and requires the `SGLANG_USE_AITER` flag [python/sglang/srt/layers/communicator.py182-194](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/layers/communicator.py#L182-L194)
 - **Fused RMSNorm + FP8 Quantization**: On ROCm/aiter, `_fused_rmsnorm_fp8_per_token_quant` optionally adds residual additions, performs RMSNorm, and outputs FP8 quantized tensors in a single kernel [python/sglang/srt/layers/communicator.py114-157](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/layers/communicator.py#L114-L157)

## Pipeline Parallelism Overview

 **Pipeline Parallelism (PP)** partitions the model’s layers across multiple GPU stages. Each stage processes different layers, enabling execution of very deep models.

 
### Pipeline Scheduler (`SchedulerPPMixin`)

 The core scheduling loop for pipeline parallelism is implemented in the `SchedulerPPMixin` class. It employs an asynchronous event loop for managing forwarding micro-batches through pipeline stages.

 **Key Functions and Workflow:**

 
 - **`event_loop_pp`**: The main scheduler loop that coordinates micro-batch (mb) execution. It iterates through `pp_loop_size` and manages the transition of batches between stages [python/sglang/srt/managers/scheduler_pp_mixin.py74-101](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_pp_mixin.py#L74-L101)
 - **`recv_requests`**: Stage P receives request metadata from Stage P-1 [python/sglang/srt/managers/scheduler_pp_mixin.py107-108](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_pp_mixin.py#L107-L108)
 - **`_pp_recv_proxy_tensors`**: Stage P receives hidden states (proxy tensors) from Stage P-1 [python/sglang/srt/managers/scheduler_pp_mixin.py127](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_pp_mixin.py#L127-L127)
 - **`_pp_launch_batch`**: Launches the GPU forward pass for the current micro-batch stage [python/sglang/srt/managers/scheduler_pp_mixin.py140-146](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_pp_mixin.py#L140-L146)
 - **`_pp_send_pyobj_to_next_stage`**: Asynchronously sends request metadata to Stage P+1 [python/sglang/srt/managers/scheduler_pp_mixin.py112-115](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_pp_mixin.py#L112-L115)

### Communication and Micro-batching

 SGLang optimizes PP communication by skipping output sends for pure chunked prefill when logprobs aren't required, controlled by `_pp_can_skip_output_comm` [python/sglang/srt/managers/scheduler_pp_mixin.py55-64](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_pp_mixin.py#L55-L64) It also supports asynchronous batch depth (`pp_async_batch_depth`) to buffer outputs and minimize bubbles by overlapping CPU processing with GPU computation [python/sglang/srt/managers/scheduler_pp_mixin.py131-137](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/managers/scheduler_pp_mixin.py#L131-L137)

## Distributed Communication Implementation

 SGLang integrates multiple communication technologies to optimize distributed execution:

 
### NCCL and Platform Abstraction

 
 - **GroupCoordinator**: Acts as the primary interface for distributed operations, handling the initialization and execution of collectives across different backends [python/sglang/srt/distributed/parallel_state.py160-210](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L160-L210)
 - **Platform Detection**: The system detects `is_cuda`, `is_hip`, `is_npu`, etc., to select the appropriate distributed backend (e.g., `nccl`, `hccl`) [python/sglang/srt/distributed/parallel_state.py57-69](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/distributed/parallel_state.py#L57-L69)
 
 
### Disaggregation Communication

 For prefill-decode disaggregation, SGLang uses specialized managers and backends (Mooncake, NIXL, Mori) to transfer KV caches between nodes.

 
 - **`poll_and_all_reduce`**: Synchronizes the state of KV transfers across TP ranks using a `MIN` reduction to ensure no rank commits before its peers [python/sglang/srt/disaggregation/utils.py205-230](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/utils.py#L205-L230)
 - **`poll_and_all_reduce_pp`**: Maps authoritative pipeline consensus (from Stage P) to poll states for disaggregated requests without re-polling [python/sglang/srt/disaggregation/utils.py52-67](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/utils.py#L52-L67)
 - **CommonKVManager**: Manages topology information (TP/CP/DP/PP sizes) and handles the lifecycle of KV senders and receivers [python/sglang/srt/disaggregation/common/conn.py146-193](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/common/conn.py#L146-L193)
 
 
### Backend Specifics

 
 - **Mooncake**: Uses a custom transfer engine for RDMA-based KV cache movement [python/sglang/srt/disaggregation/mooncake/conn.py198-210](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/mooncake/conn.py#L198-L210)
 - **NIXL**: Provides specialized transport for KV indices and auxiliary data [python/sglang/srt/disaggregation/nixl/conn.py154-206](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/nixl/conn.py#L154-L206)
 - **Mori**: Implements an IOEngine-based RDMA backend for high-performance transfers [python/sglang/srt/disaggregation/mori/conn.py17-27](https://github.com/sgl-project/sglang/blob/94183a8d/python/sglang/srt/disaggregation/mori/conn.py#L17-L27)
