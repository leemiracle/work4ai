# 讲透需求工程 · 从模糊愿望到可验证规格

> **定位**:这支负责方法论最软也最贵的环节——**需求**: elicitation( elicitation 的社会学)、规格化、变更管理。软件缺陷的最大来源地(返工成本沿 V 模型右翼指数放大)。
> 自定主干支(GB/T 12050 未单列;2026-09-07 立宪)。

## 诞生

1960s 系统工程的需求规格条款(DoD 标准)→ 软件危机(1968 NATO 会议)把"需求不清"确认为头号杀手 → 需求工程独立成科(1990s, RE 会议系列)→ 敏捷把需求变成用户故事(持续 elicitation)。

## 核心问题(3-5 条)

| 问题 | 状态 |
|------|------|
| 需求能否无歧义表达 | ✅ 否定式:自然语言规格本质欠拟合(形式化规格补位但成本高) |
| 隐含需求如何显式化 | 🔄 elicitation 方法学(访谈/观察/原型),无完备程序 |
| 需求变更如何管理 | ✅ 基线+影响分析+追溯(工程成熟) |
| 需求优先级如何裁决 | 🔄 MoSCoW/Kano 实践法;本质是利益裁决(链系统评估) |

**这支最美的一个事实**:需求工程的最高技巧不是问"你要什么",而是问**"你现在的做法哪里让你疼"**——用户表述的是解(solution space),痛点才是真需求(problem space);**从解到痛点的逆向翻译**是这门手艺的全部内容(与数学建模的"从应用问题到数学结构"同构)。

## 假设与依赖

用户能表达需求(实际只能表达不满);需求可预先捕获 vs 可持续涌现(瀑布/敏捷的分野);规格可验证。前置:家族层 [`../02-语言特征.md`](../02-语言特征.md)。
