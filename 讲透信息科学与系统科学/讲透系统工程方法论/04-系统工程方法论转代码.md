# 04 · 系统工程方法论转代码:把流程变成可执行制度

> **本章回答五问之五(家族层)。** 方法论进代码**四条走廊**;工程师落点是最实在的一条:
> **你的 git/CI 流水线就是半个系统工程方法论**——基线、评审、追溯的软件化身。

---

## 一、四条走廊总表

| # | 走廊 | 输入→输出 | 代表工具 |
|---|------|----------|---------|
| 1 | MBSE 建模 | 需求/结构/行为→统一模型+视图 | SysML(Cameo/Capella)、开源 Capella |
| 2 | 生命周期自动化 | 代码变更→构建/测试/部署 | git+CI/CD(GitHub Actions/Jenkins) |
| 3 | 需求追溯 | 需求条目→代码→测试的双向链接 | DOORS/Jama/git issue 链接约定 |
| 4 | 过程仿真 | 流程参数→工期/风险分布 | 蒙特卡洛(实验脚本即最小版) |

## 二、逐条速写

**走廊 1(MBSE)**:三步法——直觉:给系统建一个"总账本",图都是账本的视图;严格:SysML 用 profile 机制把 UML 约束到系统域(需求/结构/行为/参数四视图);最小例子:Capella 免费工具三小时入门。
**工程师落点**:性能工程里"指标-瓶颈-代码"的追溯链,手工维护必断——用模型单点真相替代三份互相漂移的文档。

**走廊 2(生命周期自动化)**:V 模型的左翼(设计)住 issue/PR,右翼(验证)住 CI——**基线=tag,评审=PR review,追溯=fixes #N**。为什么这条走廊最成熟:它把元语言三概念(阶段/基线/评审)全部变成 git 原语,零额外工具。

**走廊 3(需求追溯)**:需求条目→commit→test 的可回答性("这条需求谁实现、哪个测试守着?")。LLM 时代新玩法:自然语言需求→结构化条目的半自动抽取(01 章方向二)。

**走廊 4(过程仿真)**:方法论自身的数字化实验——Brooks 仿真、蒙特卡洛工期估计(PERT 三点估计→分布)。**为什么重要**:让"加人/砍功能/延期"的争论变成参数讨论。

## 三、可机械化边界(三件套之一:为什么)

| 可全自动 | 半自动 | 不可机械化 |
|---------|--------|-----------|
| 基线/追溯/CI 全流程、模型语法检查 | 需求抽取(LLM 起草,人裁决)、模型语义评审 | **利益分歧的裁决**(SSM 的核心环节)、架构审美、跨组织信任 |

**为什么是这样**:语法可形式化所以自动;语义靠共识所以半自动;**方法论最软的腹部(人的同意)永远不可自动生成**——LLM 能整理分歧,不能消灭分歧。

## 四、裂缝清单

1. **文档-模型双轨**:MBSE 理想是单点真相,现实常是"模型+过时文档"双维护(比只有文档更糟)——裂缝本质:组织未把模型定为法定基线
2. **追溯的粒度悖论**:太细(每行代码挂需求)没人维护,太粗追溯失效
3. **Conway 阻力**:工具换了组织没换,新走廊跑旧拓扑——**工具链改造必须伴随组织改造**(03 章)
4. **仿真参数拍脑袋**:走廊 4 的参数(μ、ramp)常无实测——仿真剧场化

## 五、代码走廊(工程师落点,三件套之三)

```python
# 走廊 4 最小核心(Brooks 净速率,完整版见 experiments/)
def net_rate(n, p=1.0, mu=0.02):
    return n * p - mu * n * (n - 1) / 2   # 线性产出 - 二次沟通税
```

性能工程视角:CI 流水线本身是系统(排队/缓存/失败重试),用本家族语言(V 模型/基线/评审)审视你的 CI 配置,常能发现"评审仪式存在但基线缺失"的裂缝。
