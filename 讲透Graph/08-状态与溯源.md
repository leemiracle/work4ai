# 08 · 状态与溯源：decision lineage、checkpoint 与 graph-native OS

> 讲透Graph 第 08 章

## 1. 直觉层：台账与黑匣子

agent 系统跑起来后最贵的问题不是"怎么做"，是事后三问：

- **做到哪了？**（断点续跑：crash/human-in-loop/跨会话交接）
- **为什么这么做？**（审计：这个动作是谁批准的、基于什么证据）
- **能不能重来？**（replay：回归测试、事故复盘、版本对比）

综述 2608.21156 的第三支柱 Runtime State Management 给了清单：track progress / reconcile concurrent updates / **preserve provenance** / isolate failures / recover or adapt。执行信息散在 context 和日志里是**不可审计**的；变成图上的节点和边，才可查、可恢复、可回放。

## 2. Decision lineage：第四张图

ContextOS 四图分类的最后一张：**decision-lineage graph**——节点是 runs / evidence / policies / approvals / effects，边是 used / approved / caused / wrote。回答生产环境最要命的问题：

> "为什么这个节点跑了？这条边上过了什么证据？join 为什么在一个分支缺席时还是进行了？哪个审批授权了这个副作用？同一条路能重放吗？该回滚到哪个图版本？"

注意它与 execution graph 的分工：**execution graph 说"接下来什么可以跑"；lineage graph 说"过去为什么这么跑"**。一个管编排，一个管解释。生产系统两张都要，用稳定的 run/trace/node ID 互连。

Zep/Neo4j 把这个思想装进记忆侧：decision traces 挂上知识图谱（= context graph 定义本身）。Eiffrem 的愿景：给组织编码 institutional knowledge 和 decision traces，会变得像写单元测试一样**无趣而必要**（standard hygiene）。

## 3. 数学层：event sourcing 与 replay

事件溯源（event sourcing）视角：**状态 = 事件流的确定性归约**。

$$S_t = \text{fold}(E_{1..t}), \qquad \text{replay}(E_{1..t}) \equiv S_t$$

- **checkpoint** = 周期性物化 $S_{t'}$，crash 后从 $S_{t'}$ + $E_{t'+1..t}$ 快速重建（不从头 fold）；
- **回滚** = truncate 事件流到 $t''$ 重放（前提：副作用可补偿——LangGraph checkpoint + ContextOS 的 effect idempotency/compensation 合同）；
- **分叉（fork）** = 从 $t''$ 起换一条边走（what-if 分析、A/B 两个图版本对比）。

arXiv 2605.21997 的标题就是纲领："**The Log is the Agent**"——事件溯源的反应式图，天然可审计、可分叉（🔁转引，深读前先核实 abs 页）。

## 4. Graph-native agent OS：综述的未来提案

2608.21156 §7 的收束：如果任务、agent、能力、运行状态都是 typed + versioned 的一等图对象，就不该每个框架自己造轮子（workflow 调度/资源分配/持久状态/通信/恢复）。共享图运行时应该提供：

> graph scheduling · capability discovery · state storage · event & provenance logging · **structural transactions** · permission enforcement · checkpointing · replay · rollback · graph-level observability

其中 **structural transaction（结构事务）**最值得玩味：图的修改（加节点/删边/换拓扑）也要有事务语义——要么全成要么全不成。这直接回应 Ch11 的 cross-graph evolution：改任务图可能作废 agent 团队的假设，换 agent 可能作废通信关系——跨图变更需要一致性保证，不能各图自己偷偷改。

## 5. 不足与坑

- **溯源存储税**：lineage 全记 = 每次运行多存一份图变更日志，长期存储成本线性于活动量。生产折衷：热迹全记、冷迹采样/压缩；
- **双写一致性**：execution graph 和 context graph 各自演进，靠什么同步？（SurrealDB 的答案是每轮 read-think-write 的写回协议，但"协议"目前是纪律不是机制）；
- **replay 的前提是确定性**：LLM 调用非确定，真 replay 要么固定 seed/温度=0（脆弱），要么记录响应而不是重发请求（记的是"发生了什么"，不是"会再发生什么"）。
