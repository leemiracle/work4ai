# 批次 16-项目·工具（20 条）

本批是 awesome-ebpf 的 Tools 小节，覆盖 eBPF 工具生态的三个世代：①高层追踪语言（bpftrace/ply）及其速查资源；②K8s/容器化调度与守护进程化框架（kubectl-trace/inspektor-gadget/bpfd 两代/greggd/bpfman）；③Android/嵌入式跨界（BPFd/adeb）。整体看，工具层正从"单机一次性命令"演进为"集群守护进程+声明式规则+eBPF 程序分发（CO-RE/OCI 镜像）"的形态，bpfman 是这条线的现代正统，而 2019 年前后的 bpfd/BPFd 两个同名项目均已停滞成为考古材料。观测类新工具（ptcpdump/ebpfmon/oryx/AgentSight）证明 eBPF 在包捕获、TUI 监控、网络抓包、LLM agent 可观测性等细分场景仍有持续创新。应用侧两篇（FUSE 加速 PDF、upf-bpf 5G 用户面）展示了 eBPF 从观测走向数据面加速的路径。对学习者的最优路径：bpftrace cheat sheet → bpftrace one-liners → Inspektor Gadget（K8s 场景）→ bpfman（加载器原理）。对 AI agent 而言，本批 15 个本地仓是"如何封装 eBPF 成产品"的完整案例库，README+入口文件可直接 grep 复用模式。

## [234] ply

- 是什么：面向嵌入式系统的轻量动态追踪器，类 dtrace/awk 的 C 风格小语言，github.com/iovisor/ply。
- 核心内容：官网给出 4 个经典示例——`kprobe:SyS_*` 全系统 syscall 计数（`@syscalls[caller] = count()`）、read(2) 返回值 quantize 直方图、kprobe 捕获内核栈（`print(stack)`）、opensnoop（`printf("%v(%v): %s\n", comm, pid, str(arg1))`）。
- 亮点：零依赖哲学——纯 C 实现，只要 libc + 支持 BPF 的内核，无 LLVM 无 Python（对比 bpftrace/bcc 的重型依赖），支持 aarch64/arm/powerpc/x86_64；聚合影射与 JIT 在内核态完成，开销极低。
- 坑：语言能力远弱于 awk/dtrace；项目近年维护趋于缓慢，主站点示例还是 `SyS_*` 时代符号（新内核已改 `__x64_sys_*`）。
- 对人类学习者：理解"DSL → BPF 字节码"最小编译器的最佳教材，语法是 bpftrace 的直系先辈。
- 对 AI agent：本地 md 路径 web/md/234.md，可 grep `quantize|kretprobe|count()` 提取教学示例；嵌入式/无 LLVM 场景选型时引用其零依赖论证。

- 坑：本 md 是壳页，无实质教程内容，学习要去 one-liners 页或 GitHub docs/。

## [236] bpftrace Cheat Sheet（Brendan Gregg）

- 是什么：Brendan Gregg 的 bpftrace 速查表（可打印），出自其 BPF Performance Tools 书附录 B 的网络版，2021 年更新。
- 核心内容：四张核心表——①语法 `probe[,probe...] /filter/ { action }`；②probe 类型速记别名表 15 种（t=tracepoint/k=kprobe/f=kfunc/u=uprobe/w=watchpoint/p=profile/i=interval/iter 等）；③变量四类（`@name` 全局、`@name[key]` hash、`@name[tid]` thread-local、`$name` scratch）；④builtin 变量 16 个（pid/comm/curtask/arg0-args/retval/kstack/cgroup…）与 builtin 函数 30+（printf/str/buf/ksym/usym/ntop/override/`hist/lhist/stats` 聚合族）。
- 亮点：明确告诫"动态插桩不是稳定 API，版本间会碎，优先用静态 probe 类型"——这是写可维护 bpftrace 工具的第一原则。
- 对人类学习者：单页即覆盖日常 90% 用法，bpftrace 学习效率最高的资产。
- 对 AI agent：web/md/236.md 是本地最权威的 bpftrace 语法参考，生成/校验脚本时 grep `probe|retval|lhist|watchpoint` 对照表项即可，无需联网。

## [239] bpfd（genuinetools）

- 是什么：以守护进程方式按规则运行 BPF tracer 的 Go 框架，容器感知。与 [248] bpfman 同名不同源——此为 2019 年 genuinetools 版，最后提交 2019-05-25，已死。

- 对人类学习者：理解"eBPF 加载器为什么要守护进程化+规则化"的最小案例，Go 实现（含 vendor）易读。

## [240] BPFd（joelagnel/bpfd）

- 是什么：Berkeley Packet Filter Daemon——通过简单 stdio 接口加载 eBPF 程序的守护进程，为跨机器/跨架构跑 BCC 工具而设计（Android 调试场景）。C/C++（CMake），最后提交 2019-06-22，README 顶部即挂 Deprecated。
- 核心内容：核心思想是把 BCC 的"编译+加载"与"运行"分区：内核源码留在开发机，eBPF 代码经 stdio 协议加载到远程目标机（如 Android 手机），解决 BCC 在嵌入式设备上无法自举的问题。仓库含 android/、bcc-deps/、patches/。
- 亮点：README 明确记录了弃用史——Android 社区转向 androdeb（即 [241] adeb）跑 BCC、未来聚焦 bpftrace on Android，并给出 iovisor/bcc PR#1675/#2298 两条社区讨论链接，是 eBPF 工具演化史的一手材料。
- 坑：已死项目；stdio 协议无继任者，思路被 libbpf/CO-RE 远程加载取代。
- 对人类学习者：跨边界加载 eBPF 的早期尝试范本，适合研究"为什么 BCC 难以跨架构"。
- 对 AI agent：repos/joelagnel/bpfd；grep `INSTALL.md|stdio|android` 看协议设计与依赖清单。

## [241] adeb（joelagnel/adeb / androdeb）

- 是什么：在 Android 设备上提供完整 Linux shell 开发环境的工具（debootstrap 造 Debian chroot），让 BCC/perf 等重型工具直接跑在手机上。最后提交 2023-02-04，README 声明不再适配新 Android/Debian 版本但"略加努力即可用"。

## [242] greggd（olcf/greggd）

- 是什么："Global runtime for eBPF-enabled gathering daemon"——Oak Ridge Leadership Computing Facility（OLCF 超算中心）出品，把 eBPF 查询守护进程化并把输出吐到本地 socket 供消费。Go+C（csrc/），最后提交 2024-12-18。
- 核心内容：编译加载 eBPF 程序→读出二进制流→解析→发 socket。内置 4 个 sensor：opensnoop（文件 open）、execsnoop（exec 系统调用）、biolatency（块 I/O 延迟直方图）、tcplife（TCP 会话生命周期）。配置走 YAML：每 source 声明 kprobe/kretprobe 绑定与 BPF_PERF_OUTPUT 的 struct 字段格式（name/type 逐字段描述二进制布局）。
- 亮点：超算/HPC 场景的 eBPF 常驻采集器，YAML 声明式描述 perf 事件结构体的做法简洁可借鉴；与 prometheus/bcc 生态互补。
- 坑：README 自述 "tooling that works as a sensor"——sensor 面窄，社区小。
- 对人类学习者：看懂"eBPF 事件 → 二进制 perf buffer → 用户态解析 → socket"全链路的干净小样本。
- 对 AI agent：repos/olcf/greggd；configs/config.yaml 是数据格式声明的最佳样例，csrc/ 下有四 sensor 的 C 源；grep `BPF_PERF_OUTPUT|loadFunc|attachTo`。

## [243] When eBPF Meets FUSE（PDF, Georgia Tech）

- 是什么：Ashish Bijlani（Georgia Tech）2017 年 Linux Foundation 演讲幻灯片，提出 ExtFUSE——用 eBPF 给用户态文件系统（FUSE）做内核态扩展以提速。
- 核心内容：①FUSE 痛点量化：tar 解压 overhead HDD 78.8%/SSD 81.1%，内核编译 make -j4 overhead 17.54%，且快介质上更痛；②现有 FUSE 优化（128K 大写、splice 零拷贝、writeback_cache、entry/attr_timeout）收效有限——lookup 虽降 4 倍，但 read() 期间 atime 变化会反复失效属性缓存，VFS 还为每个 write() 发 getxattr() 读 security label；③ExtFUSE 方案：FUSE daemon 注册"thin"BPF 扩展在内核直接应答请求（免用户态上下文切换），daemon 与扩展经 BPF maps 共享/缓存元数据——示例 getattr() 扩展用 HASH map 以 ino 为 key 缓存 fuse_attr_out，setattr() 时 delete 失效；④结果：overhead 17.54%→5.71%，最坏 50MB 内存；⑤应用面：Gluster readdirahead 缓存、Android SDCardFS 的 uid 检查下沉、内核态转发 I/O 到 lower FS。
- 亮点：eBPF 从"观测"跨入"数据面加速"的早期代表作；"BPF map 当内核态元数据缓存"的模式此后被大量复用。
- 坑：2017 work-in-progress，PDF 为横排幻灯片文本抽取，图表坐标轴已散（Lookup/Getattr 等标签错位），需按语义拼读。
- 对人类学习者：FUSE 架构（VFS→FUSE Driver→QUEUE→daemon 上下文切换链）+ eBPF verifier/maps 的联合教学，一份顶两份。
- 对 AI agent：web/pdf-txt/243.txt；grep `ExtFUSE|splice|getxattr|17.54` 取量化数据；论文版可查 extfuse.github.io（FAST'20 期刊版）。

## [244] upf-bpf（navarrothiago/upf-bpf）

- 对 AI agent：repos/navarrothiago/upf-bpf；src/ 为 C++ 管理层+内核 BPF 源；grep `PFCP|TEID|FAR|XDP` 看 PFCP 会话如何映射为 BPF map 规则。

## [245] redbpf（foniod/redbpf）

- 对人类学习者：对照 redbpf 与 libbpf（C）/aya（Rust）三家加载器实现，可吃透 eBPF 加载的通用流程。
- 对 AI agent：repos/foniod/redbpf；grep `#[kprobe]|ProgramArray|RingBuf` 取宏 API 设计；TUTORIAL.md 可直接作为 Rust eBPF 教学素材。

## [248] bpfman（bpfman/bpfman）

- 是什么：CNCF Sandbox 的 eBPF 管理器（原名 bpfd，即 [239] 的直系继任者），聚焦 eBPF 程序的部署与管理简化。最后提交 2026-11-02——本批最活跃的工具。
- 核心内容：三大能力——①System Overview（洞察系统内 eBPF 使用情况）；②程序加载器：内置 XDP/TC 程序协作（dispatcher 多程序链式挂载）+ 从 OCI 镜像分发 eBPF 字节码；③eBPF 文件系统管理：无额外特权即可部署 eBPF 应用。Rust 实现，工作区含 bpfman 主 crate、bpfman-api（gRPC）、bpfman-ns、bpf-log-exporter/bpf-metrics-exporter（可观测性配套）、csi（K8s CSI 驱动）、clients（多语言客户端）、changelogs/、完整 Containerfile 矩阵（含 OpenShift 专用）。
- 亮点：本批唯一"现代正统"——eBPF 程序当 OCI 镜像分发是当前生态标准方向（与 Inspektor Gadget 同路线）；三重 license（Apache-2.0/BSD-2/GPL-2.0）体现内核边界与用户态的合规切分；文档 book 在 bpfman.io。
- 坑：体量大（Cargo workspace 数十 crate），上手成本高于直接 libbpf；K8s 深度集成对单机用户略重。
- 对人类学习者：研究"eBPF 程序生命周期管理"（加载/挂载/pinning/特权收敛/镜像签名分发）的第一参考。
- 对 AI agent：repos/bpfman/bpfman；入口 bpfman/ crate 与 cmd/；grep `OCI|dispatcher|csi|ProgramType` 定位镜像加载与多程序协作实现；changelogs/ 可追溯能力演进。

## [249] ptcpdump（mozillazg/ptcpdump）

- 是什么：eBPF 驱动的 tcpdump 兼容包分析器，抓包时自动给每个包标注进程/容器/Pod 元数据（灵感来自 skbdump）。Go+eBPF，最后提交 2026-11-01，活跃维护，自带中文 README。
- 核心内容：特性清单——按 `--pid/--pname/--container-id/--pod-name` 过滤；兼容 tcpdump flag（`-i/-w/-c/-s/-n/-C/-W/-A`）与 pcap-filter(7) 语法；输出 tcpdump 风格但带进程/容器上下文；verbose 模式展示详细元数据；写 PcapNG 内嵌元数据（Wireshark 可直接打开）；`--netns` 跨 namespace 抓包；过滤在内核态 BPF 完成降低 CPU；集成 Docker/containerd 运行时。
- 亮点：解决 tcpdump 最大痛点——"这个包是谁发的"；README 附与 tcpdump 的逐项对比表和 Wireshark 截图；x86_64/arm64 双架构 e2e CI+覆盖率徽章全绿。
- 坑：进程元数据依赖 cgroup/容器运行时探测，裸金属进程之外的场景（如 skb 被 GRO 聚合）可能标注不到。
- 对人类学习者：eBPF 做包捕获（非仅过滤）的工程范本，学 kprobe/tracepoint 混合抓包思路首选。
- 对 AI agent：repos/mozillazg/ptcpdump；bpf/ 为 C 侧、internal/ 与 lib/ 为 Go 侧；grep `container|pod|pcapng|netns` 取元数据关联链实现；中英文 README 可对齐术语。

## [250] oryx（pythops/oryx）

- 是什么：eBPF 网络流量嗅探 TUI——实时流量检视/统计/防火墙/指标浏览器/模糊搜索一体。Rust（aya 风格 workspace：oryx-common/oryx-ebpf/oryx-tui/xtask），最后提交 2026-10-18，活跃。
- 核心内容：支持协议矩阵——传输层 TCP/UDP/SCTP，网络层 IPv4/v6、ICMPv4/v6、IGMP v1-3，链路层 ARP；要求 Linux 6.10+（Debian 13/Ubuntu 24.04 起）与 nerdfonts 字体；Arch 官方 extra 仓库收录（`pacman -S oryx`），也提供预编译二进制。
- 亮点：TUI 内置防火墙功能（不只是看还能拦）是同类工具中少见的；crate 切分（ebpf/tui/common/xtask）是标准 Rust eBPF 工程模板。
- 坑：内核版本门槛高（6.10+）；仓内 Readme.md 大小写非常规（脚本注意）；errors.txt 滞留仓根属卫生瑕疵。
- 对人类学习者：读 oryx-ebpf 到 oryx-tui 的数据流，可学会 eBPF 事件→TUI 渲染的完整 Rust 模式。
- 对 AI agent：repos/pythops/oryx；grep `SCTP|IGMP|firewall` 看协议解析与拦截实现；Justfile/xtask 是 Rust eBPF 构建脚手架参考。

## [251] GhostScope（swananan/ghostscope）

- 是什么："下一代 eBPF 用户态运行时追踪器"（v0.1.7），基于 DWARF 调试信息的源码级用户态 tracing——printf debugging 进化版，不停目标进程。Rust 多 crate（compiler/loader/dwarf/debuginfod/process/protocol/platform/ui），最后提交 2026-11-06（本批最新），GPL-3.0/MIT 双许可，附中文 README 与 AGENTS.md。
- 核心内容：能力——函数/源码行/指令粒度挂探针，读取真实局部变量/参数/全局变量与复杂数据结构，输出 DWARF 展栈的源码感知调用栈；C 语言端到端覆盖最强，Rust 支持常用值类型+符号 demangle。README 罕见地给出"When NOT to Use"与四工具对比表（vs perf/GDB/bpftrace/SystemTap，docs/comparison.md）。
- 亮点：定位精准——"生产服务不能停、GDB stop-the-world 太重、bpftrace 又读不了源码级局部变量"的空档；比 perf probe 强在可复用 CLI trace 脚本，比内核模块方案安全边界好。
- 坑：v0.1.x 早期；没 DWARF 调试信息的模块做不了源码级变量追踪；Rust 支持有明确边界（docs/limitations.md）。
- 对人类学习者：DWARF 与 eBPF 结合的最佳实战教材（debuginfod 集成、行表→探针地址、变量位置表达式）。
- 对 AI agent：repos/swananan/ghostscope；grep `DWARF|debuginfod|source-line|demangle`；docs/comparison.md 与 docs/limitations.md 是工具选型一手依据；AGENTS.md 说明该仓本身用 agent 协作开发。

## [252] AgentSight（eunomia-bpf/AgentSight）

- 是什么：eBPF 驱动的系统级 AI agent profiling 与监控工具——给 Claude Code/Codex/Gemini CLI/OpenCode 等 agent 做 top/strace 式本地观测，零 SDK/零代理/零厂商集成（eBPF+TLS 流量追踪，闭源 CLI 也能观测）。论文 arXiv:2508.02736（DOI 10.1145/3766882.3767169），最后提交 2026-10-23，活跃。
- 核心内容：四大用途——看 agent 正在干什么（会话/进程/资源/模型与工具调用/文件与网络活动）；把 prompt/skill 关联到错误以改进指令；找时间/token/资源去向（慢步骤、重试环、重复调用）；审计数据流动与安全敏感效应。CLI 三视图：`agentsight top`（按模型/token/健康度/进程族排名的实时会话表）、`agentsight vis`（Agent Nebula 回放 agent 对文件的增删改）、semantic flamegraph（语义化火焰图 top200 agent 栈）。安装 `cargo install agentsight` 即用。
- 亮点：与本流水线语境高度共振——它就是"用 eBPF 观测 AI agent harness"的先行者；仓库含 CLAUDE.md/AGENTS.md（agent 协作开发）与 controller/control-plane/frontend 完整分层。
- 坑：功能多依赖 eBPF 权限（root）；TLS 追踪需解密 hook，特定运行时版本可能有兼容边界。
- 对人类学习者：eBPF 观测对象从"系统"扩展到"agent 行为"的代表作，学进程 lineage 关联模型调用的最佳样本。
- 对 AI agent：repos/eunomia-bpf/AgentSight；grep `model call|token|lineage|tls` 看如何把 syscall 级事件上卷成语义事件；bpf/ 与 collector/ 为数据面。

## [253] ActPlane（eunomia-bpf/ActPlane）

- 是什么：面向 AI agent harness 的 eBPF IFC（信息流控制）policy 引擎——声明安全/合规策略，eBPF 在内核层确定性强制执行。论文 arXiv:2606.25189，与 [252] AgentSight 同族（eunomia-bpf），最后提交 2026-10-16。
- 核心内容：口号"prompt 约束与模型 guardrail 是概率性的，ActPlane 是确定性的"——工具调用检查看不见间接行为（如 sh 脚本），而策略跟进程血缘走。四类可表达策略：细粒度沙箱（"codex 不许 git push、不许写 /src 外"，bash/python 绕不过）；条件豁免（"makefile 缓存除非明说否则不许删"）；因果通知（"改了 specs/* 就提醒 SDK/文档过期"，不拦只通知）；因果顺序（"提交前必须跑 make check 与 npm test"）。工作流 `actplane init/compile/doctor/run`；eBPF 程序预编译 CO-RE 分发，无需 clang/llvm/libbpf；命中即 kill 并把 reason 通过 hook 反馈给 agent 让其改道。
- 亮点：把 eBPF 从"观测"（AgentSight）推进到"对 agent 的内核态强制管控"，`actplane doctor` 诊断 hooks/MCP/内核支持的设计很工程化；KILLED 输出把拒绝原因回喂 agent 是 agent 治理的关键交互模式。
- 坑：需要 Linux 5.10+ 带 BTF；MCP 自动 attach 依赖 passwordless sudo；强制语义强，策略写错会误杀 agent 任务。
- 对人类学习者：IFC/进程血缘策略如何映射为 eBPF 程序（policy→compile→load→enforce 全链）的前沿案例。
- 对 AI agent：repos/eunomia-bpf/ActPlane；grep `IFC|lineage|policy|KILLED` 看策略 DSL 与执行路径；policies/ 与 actplane.yaml 是策略语法样例；CLAUDE.md/AGENTS.md 表明仓本身 agent 协作开发。
