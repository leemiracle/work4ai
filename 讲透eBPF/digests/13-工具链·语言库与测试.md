# 13-工具链·语言库与测试（14 条）

**本批总评**：本批覆盖 eBPF 用户态工具链的三大支柱——BCC（LLVM 重运行时编译 + Python/Lua 前端，观测工具的祖师爷）、Go 阵营双库（cilium/ebpf 纯 Go 无 CGO、libbpfgo 直接包 libbpf C 库）与 Rust 阵营 aya 全家桶（含 aya-template + cargo generate 脚手架），外加两条小众路线（zbpf 的 Zig 原生 eBPF 编译器、eunomia-bpf 的 wasm+JSON 配置化免编译分发）与两个跨平台/测试环境（微软 eBPF for Windows 把 uBPF 解释器/JIT 移植进 Windows 内核驱动、bcc-docker 与 bpfcompat 解决"没有测试内核环境怎么办"）。整体图景：语言库层已从"绑死 libbpf 胶水"进化为三条清晰路线——纯语言重实现（cilium/ebpf、aya、zbpf）、C 库薄封装（libbpfgo）、配置/wasm 化分发（eunomia）；测试侧则是容器化与多内核兼容矩阵两条路。对学习者的价值梯度：cilium/ebpf 与 aya 是当前生产与社区最活跃的两条主线（cilium/ebpf 已成 Go 生态事实标准、aya 是 Rust 事实标准），BCC 更多作为 70+ 现成观测工具的"工具箱"而非开发首选。对 AI agent 而言，本批仓都是可直接 grep 的本地代码库，适合做"如何正确加载程序/管理 map 生命周期"的参考实现检索。注意两条 iproute2 条目（138/139）抓取时撞上 kernel.org 的 Anubis 反爬盾，本地 md 为壳页。

## [136] bcc

- **是什么**：iovisor 出品的 BPF Compiler Collection——eBPF 时代最早也最全的 tracer 开发框架与现成工具集，最后提交 2026-10-02 仍活跃维护。
- **核心内容**：C 写内核侧程序，用户态包装 LLVM 现场编译（重运行时依赖 clang/LLVM 头文件），前端 Python（`src/python/bcc/`：BPF 对象、table/perf、USDT、syscall 封装）与 Lua（`src/lua/`）。真正的宝藏是 `tools/` 277 个文件（约 130+ 个 .py 成品观测工具：biolatency/biosnoop/tcpconnect/execsnoop/opensnoop…每个配 `*_example.txt` 示例输出）+ `libbpf-tools/` 213 个文件的 CO-RE 版工具（BCC 官方自己也在向 libbpf+CO-RE 迁移）。C++ 核心在 `src/cc/`（含 clang 前端、usdt、export/helpers、内嵌 libbpf）。
- **亮点/坑**：动态编译带来最大灵活性（可在 tracer 里拼 C 字符串插值），代价是部署重（目标机要有内核头+LLVM）；新项目官方都建议走 libbpf-tools 的 CO-RE 路线。`docs/reference_guide.md` 是 BPF Python API 的权威参考。
- **对人类学习者价值**：70+ 现成工具即学即用（排障生产力直接起飞）；读 tools/*.py 源码是学"一个 tracer 由哪几块组成"的最佳教材；BCC Python 教程（docs/tutorials.md 索引）是 eBPF 观测入门经典路径。
- **对 AI agent 用法**：本地路径 `/usr-data/data2/kylin/network/awesome-ebpf/repos/iovisor/bcc`。可 grep 关键词：`BPF_PERF_OUTPUT`、`attach_kprobe`、`BPF_HASH`（工具源码模式）；`bpf_obj_get`、`BPF_MAP_TYPE_RINGBUF`（libbpf-tools 的 CO-RE 写法）；查某个具体观测需求（如 `tcpretrans`、`runqlat`）直接找同名工具当参考实现。

## [146] cilium/ebpf

- **是什么**：ebpf-go——纯 Go（零 CGO）的 eBPF 加载/编译/调试库，Go 生态事实标准（Cilium、Datadog agent、Pixie、Hubble 等都用它），最后提交 2026-11-05 极活跃。

- **亮点/坑**：纯 Go 带来静态单二进制跨分发部署的优势；代价是要跟内核 syscall 细节自行同步（新版内核特性等库更新）。features 包做运行时能力探测是写可移植 agent 的关键。Windows 也有 collection_windows 等适配层（对接 eBPF for Windows）。
- **对人类学习者价值**：官方 Getting Started 教程 + examples 是"Go + eBPF"最正统入门路径；bpf2go 的 generate 工作流是工业界标配，学会即通用技能。
- **对 AI agent 用法**：本地路径 `/usr-data/data2/kylin/network/awesome-ebpf/repos/cilium/ebpf`。可 grep：`links.NewKprobe`、`NewCollectionFromFile`、`ringbuf.NewReader`（加载/挂载/读事件三件套范式）；`//go:generate go run github.com/cilium/ebpf/cmd/bpf2go`（bpf2go 用法）；`features.HaveProgramType`（能力探测）。

## [147] libbpfgo

- **是什么**：Aqua Security（Tracee 背后团队）出品的 libbpf Go 薄封装——CGO 直接包 C 库 libbpf，保证与上游 libbpf 行为 1:1，最后提交 2026-09-29 活跃。
- **核心内容**：核心抽象三层：`Module`（NewModuleFromFile 包一个 .o，BPF 功能单元）→ `BPFProg`（load + attach kprobe/raw_tracepoint 等）→ `BPFMap`/`RingBuffer`/`PerfBuffer`（map 操作与事件 channel 回调）。胶水在 `libbpfgo.c/.h` + `libbpf_cb.go`（C 回调转 Go channel）；`builder/` 内置 Vagrantfile-ubuntu 做 CI 虚机；`selftest/` 50 个自测目录（attachgenericfd、map-batch、map-of-maps、iter、global-variable、tchook 等）本身就是用法大全。静态/动态链接两种模式（Tracee 用 submodule 静态链 libbpf 免运行时依赖）。
- **亮点/坑**：与 cilium/ebpf 的选型权衡教科书案例——libbpfgo 跟上游 libbpf 新特性零延迟（bpf_link、迭代器、TC hook 第一时间可用），代价是 CGO 交叉编译麻烦、二进制绑定 libc；libbpfgo 把 C 返回码翻成 Go error、事件用 channel 吐，API 手感 Go 化。
- **对人类学习者价值**：想"复用 libbpf 全部能力但写 Go"的最短路径；selftest 每个子目录一个最小可跑特性样例，是学 libbpf 特性的现成 lab。
- **对 AI agent 用法**：本地路径 `/usr-data/data2/kylin/network/awesome-ebpf/repos/aquasecurity/libbpfgo`。可 grep：`NewModuleFromFile`、`GetMap`、`InitRingBuf`、`AttachRawTracepoint`；selftest 目录名即特性清单（`ls selftest/`）；`logger_cb` 看如何接 libbpf 日志。

## [148] aya

- **是什么**：Rust 生态 eBPF 事实标准库——纯 Rust 从零实现，不依赖 libbpf 也不依赖 bcc，只用 libc crate 发 syscall，最后提交 2026-11-05 极活跃。
- **核心内容**：workspace 含 20 个 crate，主线四层：`aya`（用户态：Ebpf::load_file → program_mut → load → attach 的 API，tokio/async-std async 支持）、`ebpf/aya-ebpf`（内核侧 no_std 运行时+helper bindings）、`aya-ebpf-macros`（`#[kprobe]`/`#[xdp]`/`#[map]` 等过程宏）、`aya-log` 双端日志框架（内核侧宏 → 用户态解析打印）。配套：`aya-obj`（ELF 解析/重定位）、`aya-tool`（生成内核类型 bindings 的 bpftool 包装）、`aya-build`（build.rs 集成）、`test/integration-test`（VM 集成测试，靠 `cargo xtask` 构建 ebpf target）。
- **亮点/坑**：README 三大卖点——BTF/CO-RE 透明启用（musl 链接即"compile once, run everywhere"单二进制）、函数调用重定位+全局变量 map、构建秒级（无需内核源码树/C 工具链，内核侧用 bpf-linker 链出 .o）。坑：内核侧 target 是 `bpfel-unknown-none` 特殊 target（RUSTFLAGS `--cfg bpf_target_arch=x86_64` 等按架构设置），默认 members 不含 ebpf crate，必须走 xtask 或 aya-build。仓内 lint 文化极重（clippy pedantic 全开 + rust 2024 edition + rust-version 1.98），代码质量参考级。
- **对人类学习者价值**：官方 book（aya-rs.dev/book）是 Rust+eBPF 最系统教程；"一个 Cargo workspace 三 crate（用户态/common 共享类型/ebpf）"的项目组织方式值得照抄。
- **对 AI agent 用法**：本地路径 `/usr-data/data2/kylin/network/awesome-ebpf/repos/aya-rs/aya`。可 grep：`Ebpf::load_file`、`program_mut`、`#[map]`、`PerfEventArray`、`AsyncPerfEventArray`（map 双端 API）；`aya/BREAKING-CHANGES.md` 追 API 迁移；`xtask/` 看官方构建编排。

- **是什么**：aya 官方 cargo-generate 模板仓——`cargo generate aya-rs/aya-template` 一条命令生成完整可编译的 Rust eBPF 项目骨架，最后提交 2026-11-03。

- **亮点/坑**：生成即含 license section 声明（`Dual MIT/GPL` static LICENSE）——漏这个程序加载会被内核拒，模板帮你避免经典新手坑；支持 macOS 交叉编译（rust-lld + musl target，写明可编完拷去 Linux 跑）。
- **对人类学习者价值**：Rust eBPF 入门第一步就是它；19 种程序类型的模板源码本身就是"各挂载点程序签名长什么样"的速查表（返回 u32/i32/i64、Context 类型、错误动作常量全齐）。

## [151] zbpf

- **是什么**：个人项目（tw4452852）的 Zig 语言 eBPF 框架——用 Zig comptime + BTF 给 eBPF 两端（编译期+运行期）配强类型系统，最后提交 2026-04-19（低频维护）。
- **核心内容**：两大卖点：①按 ctx 类型生成可用方法——`bpf.Kprobe{.name="path_listxattr"}.Ctx()` 之后 `ctx.arg0()..arg3()`/`ctx.ret()` 类型与内核函数原型一一对应，访问不存在的参数直接编译报错（Ksyscall/Tracepoint/Fentry 同理，靠 BTF 提取原型）；②消灭 C 式样板错误处理——`bpf.Map` update/delete、`PerfEventArray` 输出、`RingBuffer` 预留、`Xdp` 指针校验的失败都在框架内部处理，出错时把文件/行号/返回值写 trace buffer（`bpftool prog tracelog` 可看）。构建一条命令 `zig build zbpf -Dbpf=prog.zig -Dmain=main.zig`，交叉编译指定 `-Dtarget`，可 `-Dvmlinux` 指定目标内核 BTF。`src/` 含 bpf、btf_sanitizer、btf_translator、tools/trace；内置 `trace` 工具（类 retsnoop 的函数级 tracer，改进点=按类型打印参数）。samples/ 有样例。
- **亮点/坑**：亮点是"语言级类型系统直通内核函数签名"这一路线的极致展示（比 C 头文件生成更顺滑）；坑是单人维护、Zig 0.15.2 版本锁定、生态几乎为零，只适合研究思路不适合生产。
- **对人类学习者价值**：理解 BTF 能提供什么元数据的活教材（btf_translator/btf_sanitizer 源码）；对比 aya 看不同语言对同一问题的解法。
- **对 AI agent 用法**：本地路径 `/usr-data/data2/kylin/network/awesome-ebpf/repos/tw4452852/zbpf`。可 grep：`Kprobe`、`arg0`、`tracelog`（类型化 ctx 模式）；`src/tools/trace/` 是完整的 tracer 参考实现。

## [152] eunomia-bpf

- **是什么**：eunomia 实验室出品的"eBPF 编译+分发"框架——核心理念：只写内核侧 C 代码，用户态完全自动生成，产物打包成 Wasm/OCI 镜像一行命令分发运行，最后提交 2026-08-09。
- **核心内容**：三大组件：`compiler`（ecc 工具链：clang 编译内核侧 .bpf.c → .o + 自动生成 JSON config 描述导出数据/CLI 参数）、`bpf-loader-rs`（Rust 加载器：按 JSON config 或 Wasm 模块动态加载，自动接 perf/ringbuf 事件、自动采样 hash map 打印 hist、自动生成命令行参数）、`ecli`（push/pull/run OCI 镜像：`sudo ./ecli run ghcr.io/eunomia-bpf/execve:latest` 一行 bash 从注册表跑预编译 eBPF 工具，跨内核版本跨架构）。`eunomia-sdks/`（eunomia-rs Rust SDK、eunomia-otel）、`examples/bpftools`（现成工具集）。配套 wasm-bpf 子项目支持 C/C++/Rust/Go 写 Wasm 用户态。
- **亮点/坑**：亮点是把"CO-RE 免重编译"推到"OCI 镜像免安装免编译"的云原生分发形态，tutorial 仓（bpf-developer-tutorial）是中文社区著名教程；坑：README 自述老的 ecli HTTP 远程模式已从主分支删除（归档分支保留），说明形态在收缩；项目活跃度中等偏下，生产采用前需自评估。

## [168] eBPF for Windows

- **是什么**：微软官方项目——把 Linux eBPF 工具链与 API 搬到 Windows 上跑（非 fork，而是给 uBPF + PREVAIL verifier 加 Windows 宿主层），C/C++ 代码库，最后提交 2026-11-05 持续活跃。
- **核心内容**：三条执行路径：①**Native（推荐）**：`bpf2c` 工具把过检字节码逐条翻译成等价 C 语句，再编成 .sys 驱动（对 HVCI 最安全）；②JIT：用户态服务 `eBPFSvc.exe` 用 uBPF JIT 编出原生码送内核执行上下文；③Interpreter：仅 debug build（被认为欠安全）。组件布局：`ebpfcore`（内核驱动）、`ebpfapi`（ebpfapi.dll 暴露 **Libbpf API**，bpftool/Netsh 都走它）、`ebpfsvc`、`netebpfext`（网络扩展驱动）、`libs/`（含 execution_context、thunk、ubpf 移植）、`undocked`（与 OS 版本解耦的部分）。目标是**源码级兼容**（常见 hooks/helpers 跨 OS 可用，Linux 特有结构除外）。支持 Win11+/Server 2022+。`tests/` 覆盖 bpftool_tests、end_to_end、libfuzzer、stress、cilium 等 20 类。
- **亮点/坑**：亮点是"eBPF 不是 Linux 专属"的工程实证，且坚持复用 Linux 生态（PREVAIL verifier/uBPF/libbpf API 全是现成开源件）；坑：hooks/helpers 是 Linux 子集，Linux 程序不能假定直接跑；HVCI 开启时只有 native 模式可用。
- **对人类学习者价值**：看"verifier 如何与执行引擎解耦"的最佳大型样本（PREVAIL 是独立 verifier，可与任何后端组合）；docs/tutorial.md 与 docs/debugging.md（verifier 失败调试）是跨平台通用的好教程。
- **对 AI agent 用法**：本地路径 `/usr-data/data2/kylin/network/awesome-ebpf/repos/microsoft/ebpf-for-windows`。可 grep：`bpf2c`（字节码→C 翻译）、`bpf_hook`、`helper`（hook/helper 支持面）；`libs/execution_context` 看内核侧运行时结构；FAQ 节对"HVCI/兼容性"问题有权威口径可引用。

## [170] bpfcompat

- **是什么**：Kernel-Guard 开源的**编译产物级 eBPF 兼容性验证器**——"你的 .bpf.o 到底能不能在我关心的内核上 load/attach？"用真内核 VM 给出经验答案而非 CO-RE 理论推断，Go 编写，最后提交 2026-10-28（周更级活跃）。注：清单克隆今天 11:41 中断成空壳（.git/HEAD 0 字节+shallow.lock），本次已用浅克隆修复就位。
- **核心内容**：工作方式：每个目标内核 boot 一个真发行版 cloud image 的 QEMU/KVM 一次性 VM（也可选 virtme-ng/firecracker/host runner）→ 把 C/libbpf validator 连同 .bpf.o 经 per-run SSH key 送进 guest → 在真内核里跑真 `bpf()` load（load_attach 模式还做 attach）→ 回收结构化结果弃 VM；留证 serial.log/qemu.log/validator-result.json。**command 模式**可把你项目的真实 loader（libbpf 或 ebpf-go）送进每个矩阵内核 VM，退出码即判。`matrices/` 内置 30+ 内核矩阵（Ubuntu 4.15→6.17 全代、RHEL 系 AlmaLinux/CentOS-Stream/Rocky/Oracle UEK、RHCOS、arm64、minimal 变体）+ quirk-library（"版本≠特性支持"的坑内核库：ringbuf 5.8 边界、无 BTF、厂商 backport）。已进上游 CI：Falco modern_bpf（falcosecurity/libs#3024/#3061）与 Inspektor Gadget OCI gadget 周更 lane（#5708）。供应链姿势完整（cosign 签名+CycloneDX SBOM+SLSA provenance）；还有 GitHub Action（action.yml）供 CI 门禁，配 Zenodo DOI 的 research 数据集。
- **亮点/坑**：定位精准——CO-RE/BTFHub 解决"原则上可移植"，bpfcompat 解决"实际能加载"（BTF 缺失、CO-RE 重定位失败、map/attach 类型不支持、内核配置差异都是真失败源）；坑：要跑 KVM（CI 上 GitHub-hosted runner 可用但本地需嵌套虚拟化），矩阵全扫耗时。
- **对人类学习者价值**：矩阵 YAML 目录就是"企业内核兼容性该测哪些"的现成清单；kernel-quirk-library 文档是内核版本差异的坑百科；学 CI 门禁化（报告 JSON/MD + 回归即 fail）的完整范例。
- **对 AI agent 用法**：本地路径 `/usr-data/data2/kylin/network/awesome-ebpf/repos/Kernel-Guard/bpfcompat`。可 grep：`load_attach`、`command-binary`、`quirk-library`（验证模式与坑内核库）；`ls matrices/*.yaml` 拿内核矩阵模板；`--quick` 免矩阵快速跑适合 agent 自动化回归检查。
