## [24] A brief introduction to XDP and eBPF

- **是什么**：igalia 工程师 Diego Pino 2019-01 的入门博客，从"为什么需要 XDP"讲起，落到 BPF/eBPF 本体。
- **核心内容**：先讲 kernel bypass 路线（DPDK/VPP/PF_RING/Snabb）的代价——用户态要自带驱动、重造内核网络栈、丧失内核安全层与 OS 集成；XDP 反其道行之：把用户态网络程序（filter/映射/路由）**搬进内核**，包一进 NIC 就执行。然后是 BPF 简史：1992 McCanne & Van Jacobson 论文（BPF 字节码仿 Motorola 6502 ISA）→ Linux v2.5 引入 → 2011 Eric Dumazet 加 JIT → 2014 Alexei Starovoitov 推出 eBPF。eBPF 五大扩展：64 位 10 寄存器仿 x86-64、与网络子系统解耦（可挂 kprobe/tracepoint）、Maps 全局 KV 存储、helper functions、tail-call 突破 4096 字节限制。
- **亮点**：`tcpdump -d "tcp dst port 80"` 反汇编出的 cBPF 指令序列逐条讲解（offset 12=ethertype 判 IPv4/IPv6），是理解"过滤表达式如何变字节码"的最佳演示；tracex4 例子（kprobe/kmem_cache_free + kretprobe/kmem_cache_alloc_node 记录 slab 对象年龄）完整走通 kern/user 两文件结构 + objdump 看 ELF section + /sys/kernel/debug/tracing/kprobe_events。
- **对人类学习者**：把"XDP vs DPDK"的架构对立和 cBPF→eBPF 演进时间线一次讲清，适合作为第一篇读物。
- **对 AI agent**：web/md/24.md；可 grep `kernel bypass`、`tcpdump -d`、`BPF_MAP_TYPE_HASH`、`SEC\("kprobe` 找代码样例；tracex4 双文件范式（XXX_kern.c + XXX_user.c）是解释 samples/bpf 结构的现成素材。

## [25] An eBPF overview, Part 1: Introduction

- **是什么**：Collabora Adrian Ratiu 2019-04 五部曲之首，定位是"低层 eBPF 栈的浓缩深潜"，系列后 4 篇（工具层/嵌入式交叉编译/用户态追踪）本清单未收录但文首有导览。
- **核心内容**：eBPF 定义为"内核内寄存器型 VM，64 位 RISC 指令集，JIT 成原生代码运行，可访问内核函数与内存子集"。关键设计：**故意非图灵完备**——无循环（当时 bounded loops 还在 WIP）、内存访问全部边界+类型检查、单 main 函数单 context 参数、BPF_MAXINSNS=4096，由此 verifier 才能把程序解析成 DAG 做快速正确性验证。历史锚点：v3.18（2014）bpf() syscall 暴露给用户态，指令集冻结成公共 ABI；GPLv2 之外另有 Apache 许可的用户态实现 uBPF。运行五步：用户态发字节码+程序类型 → verifier 检查 → JIT 编译挂载 → 写 map/ringbuffer → 用户态读结果。
- **亮点**：sock_example.c 全文精读——手写 `BPF_MOV64_REG/BPF_LD_ABS/BPF_RAW_INSN` 宏拼出"读包 protocol 字节→map_lookup_elem→原子 xadd 计数"的最小程序，配 `bpf_load_program(BPF_PROG_TYPE_SOCKET_FILTER,...)` + `SO_ATTACH_BPF`；program array map 触发的 tail-call "jump with no return" 嵌套语义讲得比多数文章清楚。
- **坑**：2019 年快照，"no loops are allowed (WIP)" 在 5.3+ 已过时（bounded loops 已落地），引用时须校对 kernel-versions.md。
- **对人类学习者**：概念密度最高的单篇入门，"为什么内核里要一个 VM"的安全论证（对比 LTTng/SystemTap 第三方模块）值得背下来。
- **对 AI agent**：web/md/25.md；grep `BPF_MAXINSNS`、`BPF_PROG_TYPE_SOCKET_FILTER`、`bpf_load_program`、`uBPF` 取精确定义；五部曲导览段可用来给用户规划后续阅读路径。

## [26] An eBPF overview, Part 2: Machine & Bytecode

- **是什么**：五部曲第二篇，把 eBPF VM 当一台真实 CPU 拆解：11 个 64 位寄存器（r0 返回值 / r1-r5 调用参数且程序启动时 r1=context / r6-r9 跨调用保留 / r10 只读栈指针）+ 512 字节固定栈，寄存器在 32 位 ARM 内核里也恒为 64 位（高 32 位清零即得 32 位子寄存器）。
- **核心内容**：指令集 ~100 条、8 个 class、定长 64 位编码，`struct bpf_insn` 位域布局（opcode/dst:4/src:4/off:16/imm:32）配 ASCII 图；helper 由内核核心经 BPF_CALL_* 宏定义（类 syscall API，模块不可扩展），verifier 在每次加载时做寄存器类型与被调函数参数类型的匹配检查。然后逐条重解 Part 1 的 sock_example 字节码：`BPF_JMP_IMM(BPF_JEQ, R0, 0, 2)` 编码为 0x020015 这个"检查函数调用返回值是否为 NULL"的高频模式被点破。
- **亮点**：把 r1-r5 "只能存数字或栈指针、永不能存任意内存直接指针"这一限制与"简化 verifier 内存模型"的因果关系讲透——这是读懂 verifier 报错的前提知识。
- **对人类学习者**：想真正读懂 `llvm-objdump` 反汇编的 eBPF 或手写指令宏，此篇是中文圈外最细致的英文材料之一。
- **对 AI agent**：web/md/26.md；grep `struct bpf_insn`、`0x020015`、`BPF_CALL_5`、`r10` 拿寄存器约定表；生成/校验 eBPF 字节码逐条注释时可对照此篇的 sock_example 逐行讲解格式。

## [28] eBPF, part 1: Past, Present, and Future

- **是什么**：Ferris Ellis 2017-04 的长文（作者自述研究 40+ 小时、逐条脚注引 kernel commit），公认最好的 eBPF 历史叙事。
- **核心内容**：①历史——1993 Winter USENIX McCanne & Van Jacobson 论文（LBNL），BPF 的颠覆点在于"内核内 VM + 精心设计的内存模型"，与 CSPF 的区别是判别过滤在内核态完成、配 buffer 避免每包一次上下文切换；原始论文五条 VM 设计原则（协议无关/指令集通用/最小化包数据引用/单 C switch 解码/抽象寄存器落物理寄存器）逐条引用。**关键数字**：SPARCstation 2（40MHz）上拒绝一个包最少仅 184 条 CPU 指令（≈4.6μs），理论 2.6 Gbps 吞吐，而一次上下文切换要 2840-16000+ 条指令——这就是 BPF 存在的根本理由。tcpdump 用 BPF 已 24+ 年。②现状——Linux 3.18（2014-12）落地 bpf() syscall（铺垫工作从 3.15 JIT 开始）；当时已有 12 种 program type；使用三步曲：LLVM 编 C 成 ELF 字节码（除入口函数外全 inline）→ bpf syscall 加载+建 map → 按类型 attach。③未来——Smart NIC offload（Netronome Agilio CX，每 FPC 3Mpps×72-120 FPC 理论 4.3Tbps）；"eBPF 更应叫 Functional Virtual Machine"（无对象无状态代码，只有函数+数据结构存储状态，兼容同步/异步/并行/分布式）；引 Microsoft Deconstructing Process Isolation 研究——硬件隔离代价 25-33%，故内核态 VM 执行可让程序最高快 50%，呼应 Bernhardt 的 PyCon 演讲《The Birth and Death of Javascript》。
- **亮点**：脚注考古功夫极深——如 SCO 2003 年指控 Linux BPF 侵权始末（Jay Schulist 按规范独立实现，SCO 并不拥有原始 BPF 代码）、Linux 社区"BPF 即 eBPF"的命名混乱澄清。
- **坑**：2017 快照——12 种 program type / 11 种 map type 现已各翻数倍；Smart NIC 一节的历史预测部分兑现（P4/offload 走了别的路）。
- **对人类学习者**：把"eBPF 为什么长这样"用三条历史因果链（BPF 的诞生动机、eBPF 的泛化、VM 隔离的性能红利）讲透，是不可替代的第一课。
- **对 AI agent**：web/md/28.md；grep `184 CPU instructions`、`SPARCstation`、`Functional Virtual Machine`、`3.18`、`SCO` 取史实锚点；写 eBPF 背景介绍/汇报开篇时的事实库。

## [29] eBPF, part 2: Syscall and Map Types

- **是什么**：系列第二篇，逐命令、逐 map 类型拆解 `bpf()` syscall，基准 kernel 4.11，全部字段配 kernel 源码链接。
- **核心内容**：`int bpf(int cmd, union bpf_attr *attr, unsigned int size)` 的 union 复用设计；当时 10 个命令全表——BPF_PROG_LOAD / MAP_CREATE / MAP_{LOOKUP,UPDATE,DELETE}_ELEM / MAP_GET_NEXT_KEY（哈希迭代语义四象限：找不到给定 key 时返回首元素这个行为最反直觉）/ OBJ_PIN+OBJ_GET（4.4 引入 pin 到 /sys/fs/bpf 实现程序退出后持久化）/ PROG_ATTACH+DETACH（4.10，cgroup）。11 种 map 类型逐一讲：HASH/ARRAY（3.19）→ PROG_ARRAY（4.2，tail-call 载体）→ PERF_EVENT_ARRAY（4.4，perf 集成，指出全内核只有 tracex6/trace_output 两个范例且 commit message 比代码好懂）→ PERCPU_{HASH,ARRAY}（4.6，无锁）→ STACK_TRACE（配 bpf_get_stackid helper）→ CGROUP_ARRAY（bpf_skb_in_cgroup 判 skb 归属）→ LRU_{HASH,PERCPU_HASH}（4.11，并点破 LRU_PERCPU 的命名陷阱：不是每核一张表而是共享表+每核独立 LRU 结构）→ LPM_TRIE（最长前缀匹配，1-256 字节前缀，转发表场景）。
- **亮点**：对当时 bpf.2 man page 停更于 2015-07-30、4 个命令零文档的"文档荒"做了考古式补齐（每个特性都溯源到具体 commit hash）——这是它至今仍被引用的原因：相当于一份带 git 考古的 UAPI 注释。
- **坑**：map/程序类型数量是 4.11 时点快照，当代内核 map type 已 30+；引用数据须以 include/uapi/linux/bpf.h 现版为准。
- **对人类学习者**：理解 bpf syscall "一个 multiplexor + union attr" 的设计范式与 map 类型选型逻辑（什么时候用 PERCPU/LRU/LPM）的最佳材料。
- **对 AI agent**：web/md/29.md；grep `BPF_MAP_TYPE_`、`BPF_OBJ_PIN`、`GET_NEXT_KEY`、`enum bpf_cmd` 拿命令与类型清单及各引入版本；排查老代码 map 选型或写版本兼容说明时的对照表。

## [30] A BPF reference guide（bcc 官方 reference_guide.md）

- **是什么**：iovisor/bcc 仓 docs/reference_guide.md 的本地克隆（master 版，非历史快照——内容含 kfuncs/LSM probes/iterators/BPF_RINGBUF_OUTPUT 等 5.x+ 特性，与本批 2017-2019 的文章形成新旧对照）。官方定位"为 Ctrl-F 检索而设"。
- **核心内容**：三大部分。**BPF C 侧**：12 种事件源写法（kprobe__/kretprobe__ 前缀约定、tracepoint、uprobe/uretprobe、USDT、raw tracepoint、syscall `syscall__*` 约定、kfunc/kretfunc、LSM probes、BPF iterators）+ 12 个数据 helper（bpf_probe_read_kernel/_str、bpf_ktime_get_ns、bpf_get_current_pid_tgid/uid_gid/comm/task、bpf_get_ns_current_pid_tgid 等）+ 输出双通道（bpf_trace_printk 调试用、BPF_PERF_OUTPUT 与 BPF_RINGBUF_OUTPUT——后者 5.8+ 官方推荐，含 reserve/submit/discard 两用 API）+ 18 种 BPF_* map 宏（含 DEVMAP/CPUMAP/XSKMAP/SOCKHASH 等网络向类型）+ 34 个 map 方法。**bcc Python 侧**：BPF()/USDT() 初始化、attach_kprobe/tracepoint/uprobe/xdp/func 全家、trace_print/perf_buffer_poll/ring_buffer_poll、print_log2_hist/print_linear_hist（ASCII 直方图，汇总在内核态完成只传 count 列——bcc 的招牌效率模式）。**排错**：verifier "Invalid mem access" 与 "Cannot call GPL only function from proprietary program" 两大经典错误的解释。
- **亮点**：每节都有语法签名 + 可运行最小例 + 指向 bcc examples/tools 的 GitHub 搜索链接，是"从知道概念到写出第一个可运行 bcc 脚本"之间最短的桥。
- **对人类学习者**：写 bcc 程序时的案头手册；尤其 print_log2_hist 的多峰分布示例（块 IO 大小 128-255KB 占 800 次）演示了内核态聚合的价值。
- **对 AI agent**：web/md/30.md，全批最常被检索的一条；grep `kprobe__`、`BPF_RINGBUF_OUTPUT`、`BPF_HISTOGRAM`、`attach_xdp`、`Invalid mem access` 可直接取语法与样例；生成 bcc 脚本或解释 verifier 报错时的第一参考。

## [34] IO Visor @SCaLE 14x（Brenden Blanco 演讲 PDF）

- **是什么**：IO Visor 项目联合创始人、bcc 主要作者 Brenden Blanco 2016-01-23 在 Southern California Linux Expo 的演讲，项目动机 + eBPF/BCC 入门 + Clang/LLVM 集成机制 + 网络与 tracing 双 demo。
- **核心内容**：①动机——做 SDN 网络应用但"不想变成 kernel developer"，类比 Node.js（事件模型对齐思维而非 CPU 架构、v8 JIT 不牺牲性能、npm 分发生态）；基础设施应用的四需求（高性能数据访问/永不崩溃/原地升级/调试工具）与四限制（无自定义内核/模块/无 debug 符号/不重启）。②BCC 用 Clang 的独特机制（本 PDF 最有料部分）：BPFModule 内存中跑 `clang -c`，**pass 1 用 clang::Rewriter 做源码重写**——把 bpf_trace_printk 展开成带 fmt 数组的 helper 调用、把 `prev->pid` 这类内核指针解引用重写成 bpf_probe_read+offsetof、把 cursor_advance 包解析重写成 bpf_dext_pkt 直接读包、把 map 访问替换成 bpf_pseudo_fd 占位符——再由 LLVM MCJIT 出 BPF 字节码。IO Module 概念=C 代码+map+描述对象的 REST 可管理组合单元。
- **亮点**：Rewrite Sample 三连（tracing 参数/内核结构体解引用/包解析器）是理解 bcc"为什么能直接写似 C 代码"的唯一拆解材料；Hello World 用 5 行 Python+3 行 C 的 kprobe__sys_clone。
- **坑**：2016 快照，tunnel_monitor/distributed_bridge 示例在 bcc examples 仍可对照；当时 hooks 清单尚无 XDP。
- **对人类学习者**：把 bcc 从"魔法"变成"Clang 重写+MCJIT"的透明工程，适合想读 bcc 源码或自研前端的人。
- **对 AI agent**：web/pdf-txt/34.txt；grep `clang::Rewriter`、`bpf_pseudo_fd`、`BPFModule`、`IO Module` 取 BCC 编译管线细节；解释 bcc 与 libbpf+CO-RE 路线差异时的历史论据。

## [36] BPF — in-kernel virtual machine（Alexei Starovoitov, netconf 2015）

- **是什么**：eBPF 作者本人 2015-02 的演讲（vger.kernel.org netconf2015），eBPF 设计决策的第一手答辩材料，本批史料价值最高的一条。
- **核心内容**：①两大**失败原型**自述——从零设计 VM 太慢且工具链要重造；让内核直接验证 x86 指令则组合爆炸、每架构都要重写 verifier。②正解："真 CPU 指令的混合物"（cBPF 10% + x86 70% + arm64 25% + risc 5%，幻灯片口径加总 110% 属笔误），x86 指令改名 mov rax,rbx→mov r1,r2，统一调用约定，定长编码，复用 cBPF 编码以做经典→扩展的平凡转换。③寄存器到 x86 一对一映射表（R0=rax/R1-r5=rdi,rsi,rdx,rcx,r8/R6-R9=rbx,r13-r15/R10=rbp），"用户态编译器以为在生成简化 x86"。④verifier 三层机制：CFG 环检测（DFS 找 back-edge）、逐指令模拟（寄存器类型状态机：PTR_TO_CTX/FRAME_PTR/CONST_IMM，条件跳变 fork 状态）、state pruning（旧状态更严格则剪枝）。⑤五大用例分类（networking/tracing/内核内加速如 nft/p4+rocker 硬件建模/"reverse BPF"等狂想）。⑥cBPF 史料：Linux 2.1.75（1997）引入、seccomp 2012 起 Chrome 沙箱用 cBPF 过滤 syscall 参数、cBPF 自带 verifier（仅前向跳转）、经典扩展靠 LD_ABS 负偏移黑魔法。
- **亮点**：write() syscall 直方图 kern/user 双侧完整代码（BPF_MAP_TYPE_ARRAY + log2 分桶 + __sync_fetch_and_add 原子自增，用户态遍历打印）——十行内核代码讲清"in-kernel aggregation"范式。
- **勘误交叉**：本片说 BPF 于 1997 年 2.1.75 进内核，与 id=24 所述"v2.5 由 Jay Schullist 引入"存在版本口径差（2.1.75 为 2.2 开发线；24 的说法疑似不准），引用时以作者口径为准。
- **对人类学习者**：想懂"eBPF 指令集为什么长成 x86 的样子"和 verifier 内部三步，这篇是唯一权威出处。
- **对 AI agent**：web/pdf-txt/36.txt；grep `Failed approach`、`PTR_TO_CTX`、`state pruning`、`2.1.75`、`mov r1, r2` 取设计论据；写 verifier/JIT 原理讲解时的骨架来源。

## [37] Extending extended BPF（LWN, Jonathan Corbet, 2014-07-02）

- **是什么**：LWN 对 Starovoitov 2014 年 6 月 eBPF patch set 的即时报道——bpf() syscall 首次面世时点的新闻纪事，eBPF 从内核内部机制变成用户态 ABI 的历史现场。
- **核心内容**：patch 三大动作——①BPF 解释器搬出 networking 子系统到 kernel/bpf 独立维护；②新增 bpf() 系统调用（multiplexor 模式，当时原型用 netlink nlattr 传程序体、prog_id 全局命名空间、仅 BPF_PROT_TYPE_UNSPEC 一个类型、CAP_SYS_ADMIN 门槛）；③maps KV 存储（只能由用户态建删、eBPF 侧无创建权、每处挂载点须显式授权 map 访问）。verifier 早期形态：模拟执行、寄存器未初始化读即拒、类型追踪、禁循环保证终止。GPL license 参数争议现场（比内核模块更严引发 reviewer 质疑，Starovoitov 承诺未来按 module 式分级）；attach 方式：SO_ATTACH_FILTER_EBPF 套接字选项 + 写 debugfs filter 文件的 `bpf__ID_` 串挂 tracepoint。
- **亮点**：文末评论区是预言墙——Josh 评"eBPF 可当组合/批量 syscall 用"、wichert 问"为什么 map 不做成文件系统"（后来 BPF FS/pin 真实现了）、MrWim 提议"用 fd 而非 int id"（正是后来采用的方案）、elanthis 吐槽"新 syscall 永远要留 flags 字段"——四条评论在后续十年全部应验。
- **坑**：文中 API 签名（nlattr 传参、sock_filter_int、bpf_delete_map）均为合入前草稿，与最终 3.18 版本不同，不能当代码参考，只能当演化史。
- **对人类学习者**：体会"ABI 冻结前的公共审查"如何塑造接口，以及社区对一个新 syscall 的典型质疑清单。
- **对 AI agent**：web/md/37.md；grep `SO_ATTACH_FILTER_EBPF`、`bpf__ID_`、`CAP_SYS_ADMIN`、`license` 取早期 ABI 形态与争议记录；梳理 eBPF 接口演进（草稿→3.18 定稿）时的起点锚。
