# 第2章 eBPF 虚拟机与指令集

> 本章导读：想读懂 `llvm-objdump` 反汇编出的 eBPF 字节码、看懂 verifier 报错里的寄存器状态、或者评估"eBPF 能不能跑在我的平台/用户态运行时上"的工程师与 AI agent。前置：第1章的 eBPF 历史与总体架构（cBPF→eBPF 演进、bpf() syscall 全景）。读完你能：手工逐字段解码一条 eBPF 指令；说清 11 个寄存器与调用约定的来历；区分解释器与 JIT 双执行模式及其安全含义；知道 RFC 9669 把这套 ISA 标准化到了什么程度、用户态实现（uBPF/rbpf）证明了什么。

## 2.1 直觉层

把 eBPF 虚拟机想象成一台**被刻意造小、造笨的 RISC CPU**：它有 11 个 64 位寄存器、一个隐含的程序计数器、一块固定 512 字节的栈，以及约 100 条定长 8 字节的指令。所有"聪明"的部分都不在这台 CPU 里——循环不能随意跳（早期干脆禁止）、内存不能随意摸、函数不能随意调，取而代之的是加载前的 verifier 静态检查（后续章节）与白名单 helper 函数。**指令集负责"能表达什么"，verifier 负责"能不能跑"，JIT/解释器负责"怎么跑"**——三者共同构成内核里的安全沙箱。

为什么指令集长成这个样子？作者 Alexei Starovoitov 在 2015 年的演讲里自述了两个失败原型 [id=36]：①从零设计一个 VM——太慢，且整套编译器工具链要重造；②让内核直接验证 x86 指令——指令组合爆炸，且每种架构都要重写 verifier。正解是第三条路：**取"真 CPU 指令的混合物"**（作者口径：约 10% classic BPF + 70% x86 + 25% arm64 + 5% risc，幻灯片百分比加总 110% 属笔误），把 `mov rax, rbx` 这类真实指令"改名"成 `mov r1, r2`，统一调用约定，编码定长（解释器取指快），并**复用 cBPF 的编码骨架**让经典程序能被平凡转译 [id=36]。结果正如 BPF Design Q&A 的定性：BPF 不是通用 ISA 也不是通用 VM，而是"**带 C calling convention 的通用指令集**"——与内核 C 调用约定兼容，所以 helper 调用零 FFI 开销，JIT 之后与原生内核 C 代码无异 [id=11]。

这套设计的历史动机可以追到 1992 年 McCanne & Jacobson 的原始 BPF 论文：在 SPARCstation 2（40MHz）上，用内核内过滤器拒绝一个包最少只需 184 条 CPU 指令（约 4.6μs），而一次用户态/内核态上下文切换就要 2840-16000+ 条指令——"把判别逻辑搬进内核 + 内核内 VM"的收益从第一天起就是数量级的 [id=28]。

它在整条 eBPF 栈里的位置：

```mermaid
flowchart TB
    A["BPF C 源码 (受限 C)"] -->|clang -target bpf, LLVM BPF backend| B["ELF: eBPF 字节码<br/>（本章对象）"]
    B -->|bpf(BPF_PROG_LOAD)| C["verifier 静态检查<br/>（后续章节）"]
    C --> D{"bpf_prog_select_runtime"}
    D -->|JIT 可用| E["arch/*/net/bpf_jit_comp.c<br/>翻译为本机机器码"]
    D -->|JIT 不可用| F["kernel/bpf/core.c<br/>___bpf_prog_run 解释器"]
    E --> G["挂载点执行<br/>XDP / tc / kprobe / ..."]
    F --> G
    B -.同一份字节码.-> H["用户态运行时<br/>uBPF / rbpf / PREVAIL 验证"]
    H --> I["用户态解释器 / JIT<br/>（ISA 可移植性实证）"]
```

同一份字节码向上面对编译器（LLVM 用 `-mcpu=v1/v2/v3` 表达指令集代次 [id=12]），向下面对三种执行者：内核 JIT、内核解释器、用户态运行时——这正是 RFC 9669 要把它标准化成独立 ISA 的原因。

## 2.2 原理层

### 2.2.1 寄存器组与调用约定

eBPF VM 是寄存器型 RISC 机：**11 个 64 位寄存器 r0-r10 + 隐含程序计数器 + 512 字节固定栈**。即使在 32 位 ARM 内核里，寄存器也恒为 64 位宽；32 位子寄存器语义靠"高 32 位清零"实现 [id=26]。

| 寄存器 | 角色 | 说明 |
|---|---|---|
| r0 | 返回值 | helper 调用返回值 + 程序退出码（语义由 program type 决定）[id=26] |
| r1-r5 | 函数调用参数 | 程序启动时 r1 = context 指针；helper 最多 5 个参数即由此而来 [id=15][id=26] |
| r6-r9 | 被调方保留（callee-saved） | 跨 helper/BPF-to-BPF 调用保持 |
| r10 | 只读帧指针 | 指向本程序 512 字节栈顶；程序不可写 r10 [id=11][id=26] |

三个容易忽略的硬边界（BPF Design Q&A）：程序**不能**访问 IP/返回地址/真实栈指针，只能摸 r10 这个 frame pointer；LLVM 后端私有定义了 R11 当 SP 但保证永不使用；只能调 helper/kfunc，不能调任意内核函数 [id=11]。

调用约定不是随便选的：它被精心设计成 amd64/arm64 ABI 的子集，使 JIT 后一对一映射（x86_64 侧：r0=rax、r1-r5=rdi/rsi/rdx/rcx/r8、r6-r9=rbx/r13-r15、r10=rbp），"用户态编译器以为自己在生成简化版 x86" [id=36]。这也解释了 r1-r5 的另一条纪律：**它们只能存数字或栈指针，永不存任意内存的直接指针**——所有数据先落到栈再使用。这个限制是刻意加给 verifier 的：把内存模型简化到可以做正确的类型检查 [id=26]。

r1-r5 是 caller-saved、r6-r9 是 callee-saved 的分工在真实实现里清晰可见：rbpf 解释器做 BPF-to-BPF 调用时把 `reg[6..=9]` 存进 `StackFrame`，返回时恢复（`repos/qmonnet/rbpf/src/stack.rs` 的 `save_registers`）；内核侧同理。

### 2.2.2 指令编码：8 字节定长

每条指令 64 位，`struct bpf_insn`（内核 UAPI）与 RFC 9669 的 basic encoding 完全一致：

```c
struct bpf_insn {          // 内核 include/uapi/linux/bpf.h [id=26 引用的 v4.20 定义]
    __u8   code;           /* opcode */
    __u8    dst_reg:4;     /* dest register   */
    __u8    src_reg:4;     /* source register */
    __s16  off;            /* signed offset   */
    __s32  imm;            /* signed immediate constant */
};
```

```
msb                                                        lsb
+--------------------------------+----------------+----+----+--------+
| imm (32)                       | off (16)       |src |dst |opcode  |
+--------------------------------+----------------+----+----+--------+
opcode = specific(高5位) + class(低3位)
```

uBPF 的 `struct ebpf_inst` 逐字节相同（`repos/iovisor/ubpf/vm/ebpf.h`），rbpf 按同布局解码（`INSN_SIZE: usize = 8`，`repos/qmonnet/rbpf/src/ebpf.rs`）——同一编码跨越内核/GPL/用户态实现，是 ISA 可移植的最直接证据。

**字节序有一个真坑**：RFC 9669 §3.1 明确，regs 字节在 little-endian 主机上是 `src<<4 | dst`、在 big-endian 主机上是 `dst<<4 | src`，`off/imm` 多字节字段也按主机字节序存放。规范原文的例子：同一条 `r1 += 0x11223344`，LE 主机编码 `07 01 00 00 44 33 22 11`，BE 主机是 `07 10 00 00 11 22 33 44`。手解码或写反汇编器时必须先问宿主端序 [id=16]。

### 2.2.3 八个指令类

opcode 低 3 位是 class（RFC 9669 Table 3 [id=16]）：

| class | 值 | 语义 |
|---|---|---|
| BPF_LD | 0x0 | 非标准加载（ldimm64 宽立即数、legacy 包访问） |
| BPF_LDX | 0x1 | 从内存加载进寄存器（`dst = *(size *)(src + off)`） |
| BPF_ST | 0x2 | 存立即数到内存（`*(size *)(dst + off) = imm`） |
| BPF_STX | 0x3 | 存寄存器到内存（`*(size *)(dst + off) = src`） |
| BPF_ALU | 0x4 | 32 位算术逻辑（写回时高 32 位清零） |
| BPF_JMP | 0x5 | 64 位比较跳转（含 call/exit） |
| BPF_JMP32 | 0x6 | 32 位比较跳转 |
| BPF_ALU64 | 0x7 | 64 位算术逻辑 |

ALU/JMP 类的 opcode 高 5 位再拆成 `code(4bit) | s(1bit) | class(3bit)`，s 位选源操作数：`K=0` 用 32 位 imm，`X=1` 用 src_reg [id=16]。load/store 类则拆成 `mode | sz | class`：mode 有 IMM/ABS/IND/MEM/MEMSX/ATOMIC，sz 有 W(4)/H(2)/B(1)/DW(8) [id=16]。

算术指令表（code：ADD/SUB/MUL/DIV/SDIV/OR/AND/LSH/RSH/NEG/MOD/SMOD/XOR/MOV/MOVSX/ARSH/END）里有几个值得记住的语义决定 [id=16]：

- **除零不陷阱**：DIV 除零 → dst=0；MOD 除零 → ALU64 下 dst 原值不变、ALU（32 位）下 dst 高 32 位清零。verifier 之外，运行时也不引入异常路径。
- **有符号取模必须用截断除法**（`-13 % 3 == -1`，C/Go 语义），规范点名 Python/Ruby 语义不符——写用户态解释器的人最容易在这里背离标准。
- **SDIV/SMOD/MOVSX 是仅有的三个 offset≠0 的算术指令**（offset 被复用为标志位），反汇编器要专门处理。
- **移位量有掩码**：64 位操作 `& 0x3F`，32 位 `& 0x1F`。
- 32 位 ALU 写回即零扩展（`(u32)` 语义），Design Q&A 还提到 verifier 可在 alu32 后插显式 zext 指令减轻 JIT 负担 [id=11]。

### 2.2.4 宽指令：ldimm64 与伪加载

64 位立即数放不进 32 位 imm 字段，于是有了唯一的宽指令形态：`{IMM, DW, LD}`（opcode 0x18）后跟一条全零的伪指令，凑成 128 位 [id=16 §3.2]。第一条的 src_reg 字段被复用为子类型 [id=16 §5.4]：

| src_reg | 语义 | 内核侧名字 |
|---|---|---|
| 0x0 | `dst = (next_imm << 32) \| imm` 普通整数 | ldimm64 |
| 0x1 | `dst = map_by_fd(imm)` | BPF_PSEUDO_MAP_FD |
| 0x2 | `dst = map_val(map_by_fd(imm)) + next_imm` | map value 首地址 |
| 0x3 | `dst = var_addr(imm)` | 平台变量地址 |
| 0x4 | `dst = code_addr(imm)` | 代码地址 |
| 0x5 | `dst = map_by_idx(imm)` | BPF_PSEUDO_MAP_IDX |

这就是"map fd 是加载期重定位"的机制本体：编译器埋伪指令，verifier 在加载时把 fd 改写成真实 map 指针（第 3 章 verifier 详述）。用户态实现同样要消费双指令——rbpf 解释器 `LD_DW_IMM` 分支显式 `insn_ptr += 1` 跳过伪指令（`repos/qmonnet/rbpf/src/interpreter.rs`）。

### 2.2.5 调用与退出：call 的三副面孔

`{CALL, K, JMP}`（opcode 0x85）按 src_reg 分三种 [id=16 §4.3]：

- src_reg=0：按静态 ID 调 helper（imm=helper 编号）。helper 由内核核心经 `BPF_CALL_*` 宏定义，类 syscall API，模块不可扩展；verifier 在加载时用 `struct bpf_func_proto` 对寄存器类型与被调参数类型做匹配 [id=26]。helper 上限 5 参数、每个 program type 只能用子集、调用直连编译后的内核函数零 FFI 开销 [id=15]。
- src_reg=1：BPF-to-BPF 调用（program-local function），imm 是相对偏移，函数内 EXIT 返回调用方。
- src_reg=2：按 BTF ID 调 helper（kfunc 时代的入口）。

tail call 则是另一个 opcode：`BPF_JMP | BPF_X | BPF_CALL` = 0xc5（rbpf `ebpf.rs` 中 `TAIL_CALL` 常量）。语义是"复用栈帧的跳转而非调用"：失败则 fall-through 继续执行，成功则整个原程序终止；32 层嵌套上限；跨程序传状态只能靠 per-CPU map 或 skb->cb [id=13][id=54/55]。

EXIT（0x95）读 r0 作为程序返回值，返回码语义由 program type 决定（如 SOCKET_FILTER：返回 0=丢包、非 0=接受并截断到该长度 [id=20]）。

### 2.2.6 原子指令

RFC 9669 §5.3 把原子操作编码为 `ATOMIC` mode（0xc0）的 STX：只支持 W(32) 与 DW(64)，imm 复用算术 code 表——ADD=0x00/OR=0x40/AND=0x50/XOR=0xa0，加 FETCH=0x01 修饰（回写旧值到 src）、XCHG=0xe1、CMPXCHG=0xf1（与 **R0** 比较交换）[id=16]。老的 `BPF_XADD`（`BPF_STX|BPF_XADD|BPF_DW` = 0xdb，imm=0）与新编码中"不带 FETCH 的 atomic add"位型完全一致——历史指令被吸收为标准子集。sock_example 里那句 `xadd r0 += r1` 用的就是它（见 2.3）。

### 2.2.7 栈与程序规模约束

- **栈 512 字节**（rbpf `STACK_SIZE: usize = 512`；uBPF 同），Design Q&A 补充：x86-64/arm64 等"大栈"架构 JIT 下可达 2 KiB、含 BPF-to-BPF 调用链合计 [id=11]。
- **BPF_MAXINSNS = 4096** 是对非特权程序的对外可见上限；verifier 内部路径探索上限 100 万条指令 [id=11]。
- 无全局变量（早期）——用单条目 array map 模拟，这是 loader 与 clang 之间的契约 [id=55]。
- 循环：早期 CFG 无环硬性禁止（编译期常量循环必须展开），5.3 起支持 bounded loop [id=22][id=25 坑注]。
- BPF-to-BPF 调用深度：内核与用户态实现各有上限（uBPF/rbpf 均为 `MAX_CALL_DEPTH = 8`）。

### 2.2.8 双执行模式：解释器与 JIT

`bpf()` 加载并通过 verifier 后，`bpf_prog_select_runtime`（kernel/bpf/core.c）二选一 [id=268 内核源码 digest]：

- **JIT 编译**：`arch/<arch>/net/bpf_jit_comp.c` 把 eBPF 中间码翻译为本机机器码（x86_64 后端主循环 `do_jit`，寄存器按 2.2.1 的映射表一对一翻译）。生产环境主流路径：ebpf.io 官方卖点即"JIT 近原生速度" [id=6]。架构支持是逐个落的：x86-64/ARM32/ARM64 自 3.18，riscv 自 5.1 [id=13]；2016 年时点矩阵是 x86_64/arm64/ppc64/s390 四家 [id=52]。
- **解释器**：`___bpf_prog_run`（kernel/bpf/core.c）单 switch 逐指令模拟，JIT 不可用时的兜底。

但 RFC 9669 Security Considerations 给出了明确的倾向性：**解释器被视为不安全源**——推测执行侧信道（Spectre 类）可把解释器代码当 gadget 用，与机密数据同地址空间时尤甚，规范推荐用编译器（JIT）而非解释器 [id=16 §6]。内核侧对应物正是 `CONFIG_BPF_JIT_ALWAYS_ON`（Spectre 缓解，同时是某些无 JIT 架构的必选项）[id=13]。JIT 自身的安全加固见后续安全章节；与本章相关的两个事实：constant blinding（把立即数拆分防 JIT spraying）2016 年已是通用基础设施 [id=52]；调试三件套 `bpf_jit_enable=2` + `bpf_jit_disasm` + `modprobe test_bpf` 可 dump JIT 产物 [id=14]。

### 2.2.9 RFC 9669：从内核私有 ISA 到互联网标准

2024 年 10 月，RFC 9669（BPF Instruction Set Architecture，D. Thaler 编，Standards Track）把这套 ISA 升格为 IETF 标准 [id=16]。对本章最相关的三块：

1. **术语钉死**：eBPF 不再是缩写——"BPF 已是独立术语，不代表 Berkeley Packet Filter"；旧版称 cBPF [id=16 §1]。
2. **conformance groups**：base32（实现 MUST 支持）⊂ base64、atomic32 ⊂ atomic64、divmul32 ⊂ divmul64、packet（Historical，legacy 包访问指令已 deprecated）。运行时与编译器靠组名互操作——LLVM 的 `-mcpu=v1/v2/v3` 正与之对齐（v3 自 LLVM 20 起默认，`-mcpu=probe` 探测内核能力）[id=12]。PREVAIL 用户态验证器的 conformance groups 开关（atomic32/64、base32/64、callx、divmul32/64、packet）直接照抄这组名词 [id=165]。
3. **IANA 两个注册表**（Conformance Groups + Instruction Set）：新增指令需 Standards Action 或 IESG 批准——指令集演进从"内核维护者说了算"变成有治理的流程 [id=16 §7]。

注意标准化的**边界**：RFC 9669 只管指令编码与语义；helper 集合、verifier 行为、map 语义都明确"留给平台文档/未来工作"（§4.3.1 只定义了 CALL 编码，helper ID 表不在 RFC 里）。所以"BPF 程序跨平台可移植"目前成立的是**指令层**，不是生态层。

### 2.2.10 用户态实现：ISA 可移植性的活证据

三个仓构成本地语料里的"用户态三角"：

- **uBPF**（iovisor，Apache-2.0）：因内核 eBPF 是 GPL 无法被闭源项目复用而生。含汇编器/反汇编器/全平台解释器 + x86-64 与 Arm64 JIT；README 直接引用 RFC 9669 为规范基准（`repos/iovisor/ubpf/README.md`）。其解释器 `ubpf_exec_ex`（`vm/ubpf_vm.c`）展示了用户态的自主裁量：`reg[1]=mem` 且额外 `reg[2]=mem_len`（内核只约定 r1=ctx）、`uint16_t pc`、`UBPF_MAX_INSTS=65536`、`UBPF_MAX_EXT_FUNCS=64`、可设 `instruction_limit` 防死循环、可选 shadow stack 检测未初始化内存读。新一代 **Safe Execution Profile** 是解释器专用档：寄存器来源追踪（provenance）、每个指针带 region 身份/边界/权限、歧义指针算术直接拒绝而非事后范围扫描恢复、类型化 helper 元数据——把内核 verifier 的指针追踪思想压缩进运行时本身 [id=160]。
- **rbpf**（qmonnet，Rust，MIT/Apache 双许可）：从 uBPF 移植的教学级实现。解释器 `execute_program` 里 `let mut reg: [u64; 11]`、`reg[10] = stack 顶`、`reg[1] = mbuff/mem 指针`——寄存器布局在源码里一目了然（`repos/qmonnet/rbpf/src/interpreter.rs`）；BPF-to-BPF 调用用 `StackFrame` 数组模拟（保存 r6-r9 + 返回地址 + r10 回退量）；解释器**不支持 tail call**（直接报错）。含 x86_64 JIT、反汇编器、汇编器，可跨 Linux/macOS/Windows 编译（JIT 暂不支持 Windows）[id=164]。
- **PREVAIL**（vbpf/ebpf-verifier）：用户态验证器（PLDI'19 论文的工业延续），`--termination` 可验证终止性、`--failure-slice` 输出导致错误的最小指令切片、conformance groups 对齐 RFC 9669 [id=165]。

这三个项目证明了一件本章层面的事：**eBPF ISA 本身是平台无关的**——脱离 Linux 内核、脱离 GPL、换一门宿主语言，同一份 8 字节编码照常工作。分歧只出现在 ISA 之外的决策上（r2 是否预置 mem_len、是否支持 tail call、调用深度上限、指令数上限）。

## 2.3 实践层

### 2.3.1 手工解码一条真实指令

语料中最经典的字节码样本是内核 `samples/bpf/sock_example.c`——一个"统计 loopback 上 TCP/UDP/ICP 包数"的最小程序，Collabora 的 Part 2 教程逐条讲解了它 [id=26]。先解码教程点破的那条"高频模式"指令：

```c
BPF_JMP_IMM(BPF_JEQ, BPF_REG_0, 0, 2)
```

按宏展开（定义见内核 `samples/bpf/bpf_insn.h` [id=26]）逐字段算位：

```
code = BPF_JMP | BPF_JEQ | BPF_K
     = 0x05  |  0x10   | 0x00  = 0x15   ← class=JMP(5), s=K, code=JEQ(1)
regs = (src_reg=0) << 4 | (dst_reg=0)   = 0x00
off  = 2                                = 0x0002   （小端字节序：02 00）
imm  = 0                                = 0x00000000

内存字节流（小端主机）: 15 00 02 00 00 00 00 00
汇编语义:              if r0 == 0 goto +2
```

教程说"算出来会发现它是 0x020015"——即把前三字节当小端 24 位数读：`0x15 | 0x00<<8 | 0x02<<16 = 0x020015` [id=26]。这个位型是所有 eBPF 程序里出现频率最高的模式之一：**紧跟在 call 之后的 NULL 检查**（helper 返回 NULL 则跳过后续解引用）。

### 2.3.2 完整程序逐条对照表

sock_example 的 12 条指令全列（十六进制由本章按 2.2 的编码规则从 [id=26] 的宏序列推出，`0x020015` 一条与原文互校吻合；汇编列与 llvm-objdump 风格一致）：

| # | 宏（源码写法 [id=26]） | 字节（LE） | 汇编语义 |
|---|---|---|---|
| 1 | `BPF_MOV64_REG(FR6, FR1)` | `bf 16 00 00 00 00 00 00` | r6 = r1 （备份 ctx） |
| 2 | `BPF_LD_ABS(BPF_B, ETH_HLEN+9)` | `30 00 00 00 17 00 00 00` | r0 = *(u8 *)(skb+23) （ip->protocol） |
| 3 | `BPF_STX_MEM(BPF_W, FR10, FR0, -4)` | `63 0a fc ff 00 00 00 00` | *(u32 *)(r10-4) = r0 （协议号入栈） |
| 4 | `BPF_MOV64_REG(FR2, FR10)` | `bf a2 00 00 00 00 00 00` | r2 = r10 |
| 5 | `BPF_ALU64_IMM(BPF_ADD, FR2, -4)` | `07 02 00 00 fc ff ff ff` | r2 += -4 （r2 指向 key） |
| 6 | `BPF_LD_MAP_FD(FR1, map_fd)` | `18 11 00 00 fd 00 00 00` + `00 00 00 00 00 00 00 00` | r1 = map_by_fd(fd) ll （宽指令+伪加载，src=1 即 BPF_PSEUDO_MAP_FD） |
| 7 | `BPF_RAW_INSN(BPF_JMP\|BPF_CALL,…,BPF_FUNC_map_lookup_elem)` | `85 00 00 00 01 00 00 00` | call map_lookup_elem(r1, r2) |
| 8 | `BPF_JMP_IMM(BPF_JEQ, FR0, 0, 2)` | `15 00 02 00 00 00 00 00` | if r0 == 0 goto +2 （=0x020015 模式） |
| 9 | `BPF_MOV64_IMM(FR1, 1)` | `b7 01 00 00 01 00 00 00` | r1 = 1 |
| 10 | `BPF_RAW_INSN(BPF_STX\|BPF_XADD\|BPF_DW, FR0, FR1, 0, 0)` | `db 10 00 00 00 00 00 00` | lock *(u64 *)(r0+0) += r1 （legacy XADD=atomic add） |
| 11 | `BPF_MOV64_IMM(FR0, 0)` | `b7 00 00 00 00 00 00 00` | r0 = 0 |
| 12 | `BPF_EXIT_INSN()` | `95 00 00 00 00 00 00 00` | exit （返回 r0） |

读这张表可以验证本章所有机制：#1/#4 的 `0xbf` 是 ALU64+MOV+X 位型；#2 是 deprecated 的 legacy 包访问（packet 组）；#3/#10 分别演示 STX 的 MEM 与 ATOMIC(XADD) 两种 mode；#6 是 128 位宽指令双槽；#7/#12 是 call/exit；#8 是 NULL 检查模式。程序逻辑线：**读协议号 → 压栈当 key → 伪加载 map fd → helper 查表 → NULL 检查 → 原子自增 → 返回 0**——这就是"in-kernel aggregation"的最小完整形态。

### 2.3.3 上手工具链

- **看自己的程序被编译成什么**：`clang -O2 -g --target=bpf -c prog.c` 后 `llvm-objdump -S prog.o`（`--target=bpf` 保证指针/long 为 64 位；默认 native target 会生成 switch jump table 导致加载必败，需 `-fno-jump-tables` [id=12]）。指令集代次用 `-mcpu=v1/v2/v3` 控制，`-mcpu=probe` 探测内核 [id=12]。
- **手工汇编**：内核树 `tools/bpf/bpf_asm`（把 `ldxh/jeq/stb` 助记符汇编成字节码，配 `bpf_dbg` 喂 pcap 单步调试；属 cBPF 时代遗留工具）[id=157/158 digest]；内核 `samples/bpf/bpf_insn.h` 宏 + `BPF_RAW_INSN` 是手写字节码的正规姿势（sock_example 即此写法）。
- **用户态跑字节码（无需内核/Root）**：rbpf 四步——建 VM（传字节码）→ `register_helper` 注 helper → `prog_compile()`（可选 JIT）→ `execute_program()`（`repos/qmonnet/rbpf/README.md` API 节）；uBPF 提供同名 C API（`ubpf_create/ubpf_register/ubpf_load/ubpf_exec`，`repos/iovisor/ubpf/vm/inc/ubpf.h`）。
- **验证字节码而不加载**：PREVAIL CLI `bin/prevail <elf> <section> <function>` 输出 PASS/FAIL，`--asm` 可替代 llvm-objdump 反汇编，`--failure-slice` 给出致错最小指令切片 [id=165]。
- **看 JIT 产物**：`sysctl net.core.bpf_jit_enable=2` 后 `bpf_jit_disasm`（内核树工具）反汇编本机机器码 [id=14]。

## 2.4 深水区与坑

1. **字节序双坑（写解码器必踩）**：regs 字节的 nibble 顺序随宿主端序翻转、off/imm 按宿主端序存放（RFC 9669 §3.1 原文例证见 2.2.2）。在小端机器上 debug 好好的反汇编器，拿去分析大端平台（或反过来）会静默错位。另注意 BTF 头 `magic 0xeB9F` 反而可以拿来做端序探测——不同层协议的端序策略不一致。
2. **offset 字段被三类指令复用**：SDIV/SMOD/MOVSX 用它当标志位（RFC 9669 §4.1），不全是"指针偏移"；跳转指令里它是 16 位有符号相对偏移（单位是 64 位指令条数，且相对"跳转指令的下一条"）。朴素解码器把 offset 一律当内存偏移会解错这三族。
3. **JMP32 的 JA 用 imm 不用 offset**：`{JA, K, JMP}` 跳 16 位 offset，`{JA, K, JMP32}` 跳 32 位 imm（gotol）——同一操作码 0x05/0x06 分属两个 class [id=16 §4.3]。超过 16 位的条件跳转要拆成"短条件跳 + 32 位无条件跳"。
4. **legacy 包访问指令已 deprecated 但到处都是**：`BPF_LD | BPF_ABS/IND`（0x20/0x28/0x30/0x38/0x40/0x48/0x50 族）属 packet 组（Historical），libpcap 生成的经典代码仍用它，C 代码不能表达，现代写法一律 direct packet access（先 `data/data_end` 边界检查再解引用）[id=20][id=16 §5.5]。sock_example 的 #2 指令就是这类。
5. **XADD 与 ATOMIC 的代际差**：老资料（含 sock_example）写 `BPF_STX|BPF_XADD|BPF_DW`=0xdb；RFC 9669 之后的写法是 ATOMIC mode（imm 编码操作：0x00 恰与 legacy XADD 位型相同，另支持 OR/AND/XOR/FETCH/XCHG/CMPXCHG）。读老代码/老文章时须意识到这是两个时代的同一槽位。CMPXCHG 比较的对象固定是 **R0**——不是任意寄存器 [id=16 §5.3]。
6. **除零/取模零语义跨实现有漂移**：RFC 规定 MOD 除零时 ALU（32 位）要清 dst 高 32 位；rbpf 当前实现 `MOD32_IMM if imm==0 => ()` 保持 dst 原值不动（`repos/qmonnet/rbpf/src/interpreter.rs`），与规范存在边缘分歧（DIV 侧 rbpf 则正确实现了除零置 0）。跨运行时移植程序时，除零路径要单测覆盖。同理，有符号取模的"截断除法"要求（-13%3==-1）筛掉了一批用 Python 语义实现的玩具解释器。
7. **"无循环"是时间敏感事实**：2017-2019 的经典材料（Collabora Part 1 等）写"no loops allowed (WIP)"；5.3 起 bounded loop 已落地 [id=25 坑注][id=22]。引用旧文必须校对 kernel-versions 矩阵。
8. **解释器是 Spectre 时代的二等公民**：RFC 9669 §6 明示解释器被视为侧信道 gadget 源、推荐只用 JIT；内核对应 `CONFIG_BPF_JIT_ALWAYS_ON`（既是 Spectre 缓解也是无 JIT 架构必选）[id=16][id=13]。在用户态嵌入场景（uBPF/rbpf）里没有内核级 verifier 兜底，这个风险评估要自己做——uBPF Safe Profile 的寄存器 provenance 追踪就是为此而生 [id=160]。
9. **tail call 的三重限制**：仅同类型程序可互相 tail call；JIT 与解释模式不能混用；跨程序传状态只能靠 per-CPU map 或 skb->cb（52 页 netdev 论文的补充约束）[id=55]。且 rbpf 解释器干脆不支持 tail call——用户态运行时选型时这是个硬筛选项。
10. **r10"只读"是程序视角**：程序不能写 r10（verifier 拒绝），但运行时在做 BPF-to-BPF 调用时会内部调整 r10 分配子栈帧（rbpf `reg[10] -= stack_usage` 于 CALL 分支）[repos/qmonnet/rbpf/src/interpreter.rs]。读解释器源码时别把"r10 不可变"误解为运行时常量。
11. **uBPF 与内核的 context 差异**：uBPF 解释器启动时 `reg[1]=mem、reg[2]=mem_len`（r2 预置长度是 uBPF 扩展，内核只承诺 r1=ctx）；配 PREVAIL 验证过的程序喂 uBPF 时，context 指针约定有专门文档 `docs/VerifiedPrograms.md` 要读 [id=160]。"ISA 相同"不等于"运行时契约相同"。
12. **指令数上限三套口径**：内核非特权 4096（BPF_MAXINSNS）、verifier 内部探索 100 万、uBPF 65536（uint16_t pc 的自然上界）[id=11][repos/iovisor/ubpf/vm/inc/ubpf.h]。为用户态运行时生成超大程序时先查上限。
13. **LLVM 版本与指令代次耦合**：`-mcpu` 决定能否用新指令（原子/MOVSX/gotol 等）；跑 BPF selftests 必须 `-mcpu=probe` 且用同版本内核测试树 [id=12]。老 distro 编不了新特性时的标准解法是挂 apt.llvm.org 装新 clang [id=141]。
14. **"eBPF 缩写"勘误钉死**：RFC 9669 §1 明文"BPF 现在是独立术语，不代表 Berkeley Packet Filter"；写文档/论文别再展开缩写 [id=16]。另外历史版本口径差：BPF 进内核是 1997 年 2.1.75（作者口径 [id=36]），"v2.5 引入"的说法（[id=24]）疑似不准。
