  The hook system is the core mechanism in TransformerLens for intercepting and modifying activations. It enables activation caching, patching, and real-time intervention on intermediate computations by wrapping standard PyTorch modules with identity-function "HookPoints".

 
## Core Components

## Hook Execution Logic

 
### Forward Hook Lifecycle

 When a `HookPoint` is called during a forward pass, it executes hooks in the following order:

 
 - **Input Conversion**: If `hook_conversion` is set, the tensor is transformed (e.g., from `[batch, pos, d_model]` to a specialized shape). [transformer_lens/hook_points.py211-212](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/hook_points.py#L211-L212)
 - **Hook Execution**: Each hook in `fwd_hooks` is called. If a hook returns a tensor, it replaces the current activation; if it returns `None`, the activation remains unchanged. [transformer_lens/hook_points.py220-227](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/hook_points.py#L220-L227)
 - **Output Reversion**: If a hook modified the activation and a conversion was applied, the transformation is reverted. [transformer_lens/hook_points.py231-233](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/hook_points.py#L231-L233)
 
 Sources: [transformer_lens/hook_points.py198-240](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/hook_points.py#L198-L240)

 
### Backward Hook Scaling

 To work around PyTorch bugs where element-wise multiplication in backward hooks gives incorrect sums, TransformerLens uses a `_ScaledGradientTensor` wrapper. This ensures that `backward_scale` is applied correctly to the result of `sum` operations during backpropagation. [transformer_lens/hook_points.py54-79](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/hook_points.py#L54-L79) [transformer_lens/hook_points.py208-210](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/hook_points.py#L208-L210)

 
## Activation Access Patterns

 
### Hook Naming Convention

 Hook points are named based on their location in the model hierarchy.

 
 - **Residual Stream**: `blocks.{i}.hook_resid_pre`, `blocks.{i}.hook_resid_post`.
 - **Attention**: `blocks.{i}.attn.hook_q`, `blocks.{i}.attn.hook_k`, `blocks.{i}.attn.hook_v`, `blocks.{i}.attn.hook_z`.
 - **MLP**: `blocks.{i}.mlp.hook_pre`, `blocks.{i}.mlp.hook_post`.
 
 
### TransformerBridge vs HookedTransformer

 In `TransformerBridge` (v3), hooks work identically to `HookedTransformer`, but they are often attached to `GeneralizedComponent` modules (like `AttentionBridge`) that wrap original HuggingFace modules.

 
 - **Compatibility Mode**: If `TransformerBridge` is in compatibility mode, hooks can be added using legacy names (e.g., `hook_embed`), and the system uses `_AliasedHookPoint` to present the expected name to the hook function. [transformer_lens/hook_points.py95-141](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/hook_points.py#L95-L141)

## Advanced Usage

 
### Activation Caching

 `run_with_cache` is a high-level wrapper around the hook system. It internally creates a `save_hook` for every requested hook point, which detaches the activation and stores it in a dictionary. [transformer_lens/HookedRootModule.py566-649](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/HookedRootModule.py#L566-L649)

 
### Activation Patching

 Patching involves a "clean" run (cached) and a "corrupted" run. A hook is placed on the corrupted run that replaces specific activation slices with values from the clean cache. [transformer_lens/patching.py138-160](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/patching.py#L138-L160)
