  The `ArchitectureAdapter` is the foundational base class for the TransformerLens v3.0 `TransformerBridge` system. It acts as the translation layer between external model architectures (typically from Hugging Face) and the canonical components of TransformerLens.

 An adapter defines how to map module paths, how to reshape weight tensors, and what architectural configurations (like normalization types or attention variants) are required for the bridge to function.

 
## Core Implementation

 The `ArchitectureAdapter` class [transformer_lens/model_bridge/architecture_adapter.py29-35](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/architecture_adapter.py#L29-L35) provides a standardized interface for:

 
 - **Component Mapping**: Associating canonical TransformerLens names (e.g., `blocks.0.attn.q`) with specific modules in a remote model [transformer_lens/model_bridge/architecture_adapter.py136-147](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/architecture_adapter.py#L136-L147)
 - **Weight Conversion**: Defining `ParamProcessingConversion` rules to transform Hugging Face weight layouts into the layouts expected by TransformerLens [transformer_lens/model_bridge/architecture_adapter.py93-119](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/architecture_adapter.py#L93-L119)
 - **Path Translation**: Resolving internal TransformerLens paths to the actual attributes of a wrapped model [transformer_lens/model_bridge/architecture_adapter.py149-165](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/architecture_adapter.py#L149-L165)

## Key Components and Functions

 
### Component Mapping

 The `component_mapping` attribute is a dictionary of `GeneralizedComponent` instances. It tells the bridge which modules to wrap. For example, in a GPT-2 adapter, the "embed" key points to an `EmbeddingBridge` targeting `transformer.wte` [transformer_lens/model_bridge/supported_architectures/gpt2.py177-180](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/supported_architectures/gpt2.py#L177-L180)

 
### Path Translation

 The bridge uses `get_remote_component` [transformer_lens/model_bridge/architecture_adapter.py149-165](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/architecture_adapter.py#L149-L165) to traverse the remote model's attribute tree based on the mapping. If a user asks for `bridge.blocks[0].attn.q`, the adapter translates this path into the specific attribute access needed for the underlying Hugging Face model.

 
### Weight Processing Conversions

 Weights in Hugging Face often use different layouts (e.g., GPT-2 uses `Conv1D` weights which are transposed relative to `nn.Linear`). The adapter provides a dictionary of `ParamProcessingConversion` objects [transformer_lens/model_bridge/architecture_adapter.py66](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/architecture_adapter.py#L66-L66)

 
 - **Standard Conversions**: The helper `_qkvo_weight_conversions` [transformer_lens/model_bridge/architecture_adapter.py93-119](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/architecture_adapter.py#L93-L119) provides default einops patterns for standard Q/K/V/O projections.
 - **Custom Conversions**: Adapters can define complex logic, such as `QKVSplitRearrangeConversion` [transformer_lens/model_bridge/supported_architectures/gpt2.py29-37](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/supported_architectures/gpt2.py#L29-L37) to split a single joint QKV tensor into separate heads.
 
 
### ProcessWeights Utility

 The `ProcessWeights` class [transformer_lens/weight_processing.py21-35](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/weight_processing.py#L21-L35) uses the adapter to perform interpretability-related transformations like LayerNorm folding. It calls `_get_param_key` [transformer_lens/weight_processing.py38-52](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/weight_processing.py#L38-L52) to translate TransformerLens weight names (e.g., `W_Q`) into the bridge-style component paths (e.g., `q.weight`) which the adapter then resolves to the HF key.

## ArchitectureAdapterFactory and Registration

 The `ArchitectureAdapterFactory` [transformer_lens/factories/architecture_adapter_factory.py](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/factories/architecture_adapter_factory.py) is the central registry for all adapters. It selects the appropriate adapter based on the `architecture` string found in a model's `config.json`.

 
### Registration Methods

 
 - **Native Registration**: Internal adapters (GPT-2, Llama, etc.) are pre-registered in the factory.
 - **Runtime Registration**: Users can call `ArchitectureAdapterFactory.register_adapter(name, class)` [tests/unit/model_bridge/test_architecture_adapter_factory.py61-64](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/tests/unit/model_bridge/test_architecture_adapter_factory.py#L61-L64)
 - **Entry-Point Discovery**: External packages can register adapters via `pyproject.toml` using the `transformer_lens.architectures` group [docs/source/content/adapter_development/external-adapter-registration.md27-34](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/docs/source/content/adapter_development/external-adapter-registration.md?plain=1#L27-L34)

## Implementation Example: GPT-2

 The `GPT2ArchitectureAdapter` [transformer_lens/model_bridge/supported_architectures/gpt2.py97-115](https://github.com/TransformerLensOrg/TransformerLens/blob/4ba2187b/transformer_lens/model_bridge/supported_architectures/gpt2.py#L97-L115) demonstrates the complexity of weight conversion.
