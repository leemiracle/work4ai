# 14.4 · V8 sandbox 与安全边界：内存隔离的当代架构

> V8 sandbox 把 V8 堆关进 1TB 级受控地址区，堵住"JS 层任意读写→进程内任意写"。本篇讲它与 9.2 的 OS 沙箱如何双层互补、开关矩阵与定制边界——内核线收官。

## ① 角色定位

渲染安全是双层结构：外层=9.2 的 OS 沙箱（namespace+seccomp，管**进程边界**，renderer 被攻破也摸不到系统）；内层=V8 sandbox（纯软件，管**进程内边界**，V8 堆被任意读写也写不出保留区）。Site isolation（9.1）决定进程怎么切，V8 sandbox 决定单进程内 JS 可达内存的围墙。主体代码在 `v8/src/sandbox/`，API 面在 `v8/include/v8-sandbox.h`，Chromium 接线在 gin/blink（ArrayBuffer 必须落进沙箱）。上游：14.1 的 isolate/heap（指针压缩 cage 安放在沙箱头部）、14.3 的 flag 面（沙箱是**编译期**开关，异于 9.2 的运行期 `--no-sandbox`）；下游：14.2 的自定义 JS API（native 指针必须走外部指针表）。它决定你的 fork 在内存布局、native 兼容、安全承诺上的天花板。

## ③ 关键源码走读：从保留区到一个 ArrayBuffer

**布局与初始化。** sandbox.h:50-60 结构图：32GB guard｜1TB 沙箱体（头部 4GB=V8 堆/指针压缩 cage，其余给 ArrayBuffer 与 WASM 内存）｜32GB guard；大小按平台编译期定死（v8-internal.h:221-250）。`Sandbox::Initialize`（sandbox.cc:346）先探测地址空间（:261-344：x64 读 CPUID、ARM64 Android 硬编码 40bit、RISCV 读 /proc/cpuinfo），**预留上限=地址空间/4**（:355），不够则逐级减半转 partially-reserved（:389-408，下限 8GB）——partial 无完整 guard、无关映射可落入，即 `SandboxMode` 三个 kInsecure 态（v8-initialization.h:218-244，判定 api.cc:6704-6724）。成功路径（sandbox.cc:444）硬约束：**沙箱内最高权限 kReadWrite，永无可执行页**（:462-468）；子空间命名 "v8-sandbox"（:486，/proc/pid/maps 可见）；保留区 `madvise(MADV_DONTDUMP)`（:45）；空 backing store 放 `end_-1`（:621-625）误访问必崩。进程内拓扑：指针压缩 cage 精确落在 `sandbox->base()`（isolate-group.cc:172-175）；trusted space 在沙箱外、4GB 对齐（trusted-range.cc:28-38）；JIT 代码同在沙箱外（external code space 硬前置，BUILD.gn:892）。

**主线：sandbox 开启下 `JSArrayBuffer` 的字段表示**（js-array-buffer.h:243-249，一对象两技术）：

- `backing_store_` 是 **SandboxedPointer**：读时 `offset = raw >> shift`（1TB 时 shift=24，v8-internal.h:264）再 `cage_base+offset`（sandboxed-pointer-inl.h:18-30）。**左移存储保证任意值解出的指针必落沙箱内**——堆内该字段被改成任何数也出不去；写侧 `CHECK(Contains)`（:33）。
- `extension_`（`ExternalPointerMember<kArrayBufferExtensionTag>`）指向**沙箱外 C++ 对象**，堆内只存 32 位 handle（v8-internal.h:394）。读路径（v8-internal.h:1479-1507）：`index = handle >> 6`（shift 保证索引必在 512MB 表内）→ 原子读 8B 表项 → **tag 检查**（bits 49-55，:377-385）：匹配返回 payload，否则 `safe_entry=0`——**类型不符返回 nullptr，解引用即崩，绝不交出错型指针**。

表族全在沙箱外，机制同构（句柄+索引+tag，GLOSSARY.md 类比 unix fd 表）：EPT（external-pointer-table.h:39，freelist/evacuation 支持 GC 压缩；外部字符串走 shared EPT，v8-internal.h:696-700）；CppHeapPointerTable（Blink wrapper 专用，v8-sandbox.h:154-216）；TrustedPointerTable（指向 bytecode/Code 元数据，trusted-pointer-table.h:27-31）；JSDispatchTable（js-dispatch-table.h:168-186：**JS 调用前向 CFI**（entrypoint+参数计数同存、条目写保护 :36）+**廉价 tiering**；16B/entry，globals.h:617）。

**违规的结局**（皆非静默）：(1) tag 不符→nullptr 崩溃；(2) TypedArray 越界最坏情形（32bit 索引×8B+32GB 偏移）被 64GB guard 接住（v8-internal.h:295-302）——小 VA 平台无 trailing guard 改用访问掩码（:311-329，性能代价）；(3) "区内数据不可信"的不变量用 `SBXCHECK`（check.h:37-62），失败即受控 abort。测试模式 crash filter（testing.cc:1098）把"崩在区内"判无害、"崩在区外"标记 violation——安全验收的机器判据。

## ④ 实操：两个最小 patch

**A. 自家 OS（用户态 VA<1TB）显式配置沙箱，避免静默降级。** 默认 1TB 预留在 39-bit 内核上会减半重试落 partial（安全降级+启动变慢）。正解=加平台分支，**两处同改**：

```diff
--- a/v8/include/v8-internal.h
 （kSandboxSizeLog2 分支群 :243 一带）
+#elif defined(V8_TARGET_OS_MYOS)
+// 39-bit VA（userspace 256GB）：128GB 沙箱+2x64GB guard 恰好铺满
+constexpr size_t kSandboxSizeLog2 = 37;  // 128 GB
 （kAdditionalTrailingGuardRegionSize 分支群 :311-326）
+#elif defined(V8_TARGET_OS_MYOS)
+// 放不下额外 224GB trailing guard，与 Android 同策略：退化为
+// TypedArray 访问掩码（kRequiresTypedArrayAccessMasks=true）
+constexpr size_t kAdditionalTrailingGuardRegionSize = 0;
```

配套：sandbox.cc:280-320 VA 探测平台群加 `#elif` 硬编码位数（否则按 48bit 探测重试拖慢启动）。Android"128GB+2×64GB=256GB 铺满 39-bit 用户态"是官方算术样板。改完跑 `v8_unittests --gtest_filter=SandboxTest*`（sandbox.h:289）。

**B. 14.2 注入的自家 C++ 对象走带 tag 的 v8::External。** 沙箱下 External 指针也入 EPT，tag 由调用方传（v8-external.h:16-19）：

```cpp
constexpr v8::ExternalPointerTypeTag kTagMyDecoder = 5;  // 每类型一个
Local<External> ext = External::New(isolate, my_decoder_ptr, kTagMyDecoder);
auto* d = static_cast<MyDecoder*>(ext->Value(kTagMyDecoder));
// handle 被换成别的 EPT 条目：tag 不符→Value 返回 nullptr→崩溃，
// 而非拿到别家类型指针（类型混淆被掐灭）
```

tag 池超 40 类型时扩 v8-internal.h:466 `V8_EXTERNAL_POINTER_TAG_COUNT 48` 重编（api.cc:7617-7620 检查自动放宽）。Blink DOM wrapper 走另一张表（`Wrap/Unwrap`+CppHeapPointerTag，v8-sandbox.h:28），两套 tag 勿混。

## ⑤ 依赖与数据流：双层沙箱模型

```mermaid
flowchart TB
    SYS[系统·文件/设备/其它进程]
    subgraph RP["renderer 进程——9.2 OS 沙箱(namespace+seccomp+broker)"]
        OUT["沙箱外·进程内(JS 不可任意写)：<br/>句柄表族 EPT/TPT/JSDispatchTable｜trusted space｜code range(JIT)｜Blink C++/DOM"]
        subgraph SBX["V8 sandbox(1TB 级；头 4GB=V8 堆 cage)：<br/>JS 对象｜ArrayBuffer backing store｜WASM 线性内存"]
        end
        SBX -->|"sandboxed pointer 偏移必落区内"| SBX
        SBX -->|"handle→tag 校验"| OUT
    end
    RP -->|"syscall 白名单/broker"| SYS
```

配合关系：V8 利用链第一步"构造 JS 层任意读写"——sandbox **假设其已成立**（README.md 攻击者模型：区内任意并发读写+区外可读），把损害封在区内；OS 沙箱防后续进程级任意代码执行。**两层各挡一段，缺一即裸**：关 V8 sandbox，一个类型混淆就能改写 EPT 本身；关 OS 沙箱，renderer 沙箱外代码漏洞直通系统。Chromium 接线：gin/v8_initializer.cc:551-593 在 V8 初始化后把 PartitionAlloc 的 ConfigurablePool（ArrayBuffer 分区）安进沙箱（:571-598）；gin/array_buffer.cc:49-70 禁 GWP-ASan 钩子与内存工具 override（保证 backing store 必落沙箱）；blink 注册 `InSandboxAllocator`（blink v8_initializer.cc:1068→api.cc:6700）。

**沙箱开关矩阵**：

| 维度 | on（默认 64bit） | off |
|---|---|---|
| VA 预留 | 1TB/128GB/16GB+guard（是 VA 非 RSS） | 无整块预留 |
| 堆内指针 | sandboxed pointer 偏移必落区内 | 退化裸 64 位指针 |
| 外部指针 | 32bit handle→EPT+tag | **EPT 仍存在**（pointer compression 下兼作对齐优化，v8-internal.h:674-680） |
| JIT/调用 | 代码在沙箱外；JSFunction 经 JSDispatchTable | 机制基本保留（leaptiering 已解耦） |
| 兼容性 | 唯一受测配置；新 API 按沙箱假设写 | 部分 API/assert 编不过或未定义（BUILD.gn:892-909） |
| 安全 | V8 漏洞→区内 DoS | V8 漏洞→进程内任意写，退回单层 |

## ⑥ 坑与勘误

- **运行期关不掉**：无 `--no-v8-sandbox` 式 flag，纯编译期（BUILD.gn:399-403）；`--sandbox-testing/--sandbox-fuzzing` 是测试模式非开关，与 9.2 的 `--no-sandbox` 语义不同（源码实证）。
- **关沙箱≠回老架构**：EPT（含 tag）、JSDispatchTable、trusted space 在 off 构建下依然工作（v8-internal.h:674-680）；"关掉就零开销"是误解。
- **GB 级预留是 VA 不是内存**：现代 OS 近零成本，但 Windows<8.1 预留 1TB 真涨 ~2GB private usage（sandbox.cc:366-371 注释）→走 partial。小内存设备先量 VA 位数再定大小。
- **LSan 构建 EPT 是 16B 胖条目且明注 NOT SECURE**（external-pointer-table.h:146-161 旁路 tag）；memory corruption API 与 LSan/component build 互斥（BUILD.gn:898-907）。安全评测须在非 sanitizer 构建上做。
- **沙箱内永无可执行内存**（sandbox.cc:462-468）：往 JS 堆塞自家 JIT/动态代码是死路，正确位置是沙箱外 code range 走 Code 对象。
- **TypedArray 掩码税是平台条件项**（v8-internal.h:328-329）：桌面 guard 兜底、Android 掩码兜底，性能对比须分平台归因。
- **改大小必过 static_assert 群**（:307/:366/:278）：编译期炸是保护，绕过强编=埋雷。
- 口径以仓内 README.md+GLOSSARY.md 为准；v8.dev 博客是背景读物，表族细节以源码为准。

## ⑦ 验证方法

1. **状态观测**：`v8::V8::GetSandboxMode()`（v8-initialization.h:218）与 `IsSandboxConfiguredSecurely()`（api.cc:6726）打进自家 about 页；UMA 看 `V8.SandboxMode`/`V8.SandboxReservationSizeGB`（gin/v8_initializer.cc:557/566）。发布配置挂 `--sandbox-prohibit-insecure-mode` 硬断言。
2. **布局实证**（Linux）：`grep v8-sandbox /proc/<pid>/maps`——子空间就叫这个名字（sandbox.cc:486），可见 1TB 区+两侧 PROT_NONE guard。
3. **攻击面自测**：args.gn 加 `v8_enable_memory_corruption_api=true`，d8 跑 `--sandbox-testing`：`new Sandbox.MemoryView(0, 0x100000000)`+`Sandbox.getAddressOf(obj)` 任意改堆（README.md:57-76 样例）——崩溃应全判"区内无害"退出码 0；出现区外写=你的 fork 引入逃逸。Chrome 经 `--js-flags=--sandbox-testing` 透传（14.3 链路），crash filter 仅 Linux。
4. **回归**：`v8_unittests --gtest_filter=Sandbox*`；patch 后 JetStream 量掩码税/表访问开销。
