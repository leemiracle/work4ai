# 6.4 证书与安全定制：CertVerifier 覆写/内网根证书/HSTS 全景

> 姊妹篇：6.1（网络服务化，已钉 CertVerifierService 独立服务化 + MojoCertVerifier 远程调用）、6.2（URLLoader 拦截，拦截器保留证书校验）、11.2（pref/policy 体系，证书 policy 注入通道）、5.2（Android 差异）。

## 1. 角色定位

Chromium 的证书体系横跨图谱四层：**net/（L11）算法层**（`net/cert/` 163 个文件：链构建、CT、CRLSet、EV 元数据）、**services/cert_verifier/ 服务层**（browser 进程内 in-process 持有的 mojo 服务，`network_service_instance_impl.cc:931` 起工厂）、**services/network（L10）消费层**（`NetworkContext` 装配的 `MojoCertVerifier` 远程调用链）与 **chrome/browser 策略层**（`profile_network_context_service.cc` 的 `GetCertificatePolicy` 把企业 policy/平台信任库翻译成 `AdditionalCertificates` mojo 结构）。证书校验结果是整个 Web 安全模型的根：omnibox 安全指示、WebAuthn 可用性（`chrome_content_browser_client.cc:7317` 检查 SecurityLevel）、interstitial 拦截页、HSTS 强制升级全部由它派生。

2018 年网络服务化 + 2020 年证书服务化 + 2022 年 Chrome Root Store（CRS，详见坑 #6）三次改造后，当前形态是：**公网信任锚只认 Chrome Root Store**（`net/data/ssl/chrome_root_store/root_store.textproto` 编译期 + PKI Metadata 组件热更 `pki_metadata_component_installer.cc:339-352`），系统平台库只贡献"用户/企业添加的根"，全部验证跑在 browser 进程的 `MultiThreadedCertVerifier` 工作线程上。对定制者的直接后果：改信任集 → 喂 `AdditionalCertificates`（零代码 policy 或一行 patch）；改校验逻辑 → `services/cert_verifier/cert_verifier_creation.cc`；改错误呈现 → security_interstitials 组件 + chrome 导航 throttle。

**第 1 站：装配期**（谁把验证器接进网络服务）。`StoragePartitionImpl::InitNetworkContext`（`content/browser/storage_partition_impl.cc:3538`）向 embedder 要两样东西：`NetworkContextParams` + `CertVerifierCreationParams`。chrome 侧 `ChromeContentBrowserClient::ConfigureNetworkContextParams`（`chrome_content_browser_client.cc:7179`）转给 `ProfileNetworkContextService`，后者在 `:1544/:1548` 把 `GetCertificatePolicy()` 的产出塞进 `initial_additional_certificates`。`GetCertificatePolicy`（`profile_network_context_service.cc:764`）是**全部信任策略的汇合点**：ChromeOS 政策证书（:771-789）、`kCAHintCertificates` 路径构建提示（:796）、`kCACertificates` 信任锚（:806 → `trust_anchors_with_enforced_constraints`，锚点约束+有效期强制）、`kCACertificatesWithConstraints` 外置约束（:821，`permitted_dns_names/permitted_cidrs` 字典）、`kCADistrustedCertificates` 按 SPKI 拉黑（:905-916）、`CAPlatformIntegrationEnabled`（:919）。这些经 `GetCertVerifierParams`（`network_service_instance_impl.cc:975`）送达 browser 进程内 in-process 的 `CertVerifierServiceFactoryImpl`（`:934-950` 起动，不单独起进程），每个 NetworkContext 拿到独立 `CertVerifierService`。**注意**：网络服务进程侧 `NetworkContext::MakeURLRequestContext` 在 `network_context.cc:2891` 用 `MojoCertVerifier` 包远程服务、`:2902-2904` 再包 Caching+Coalescing 两层压 IPC 开销、`:2907` 套 `IgnoreErrorsCertVerifier`（SPKI 白名单）——这是 6.1 钉过的三层洋葱，本篇只展开证书这一路。

**第 2 站：验证期**。`CertVerifyProcFactoryImpl::CreateCertVerifyProc`（`cert_verifier_creation.cc:44`）按 buildflag 三分支：`CHROME_ROOT_STORE_ONLY`（win/mac/linux/chromeos，`net/features.gni:73`）或 Android 显式 CRS → `CreateNewCertVerifyProc`（:110）：构造 `TrustStoreChrome`（:128，CRS 根 + 组件热更数据），再按 `include_system_trust_store` 决定 `CreateSslSystemTrustStoreChromeRoot`（CRS+平台用户库合并）或 `CreateChromeOnlySystemTrustStore`（:135-141）；ChromeOS 固定 Chrome-only（:132）。最终 `CreateCertVerifyProcBuiltin` 产出同步验证器，由 `CreateCertVerifier`（:207）装进 `MultiThreadedCertVerifier`。`CertVerifyProcBuiltin` 构造函数（`net/cert/cert_verify_proc_builtin.cc:1240` 起）按注释 :1254-1264 的优先级把 `InstanceParams` 的附加证书倒进 `additional_trust_store_`（`bssl::TrustStoreInMemory`）：**distrusted SPKIs > 带外置约束锚 > 带内置约束锚 > 无约束锚 > 无表达证书**——同证书多路配置时优先级决定命运。链构建用 boringssl PathBuilder；SCT 校验后 `CheckCompliance` + `RequireCTDelegate::CheckCTRequirements`（`net/cert/require_ct_delegate.cc:10`）——`!is_issued_by_known_root` 直接 `CT_NOT_REQUIRED`（:19-20），这就是**自建 CA 天然免疫 CT 强制**的源码根据。

**第 3 站：结果裁决**。回到 socket 线程 `OnVerifyComplete`（`ssl_client_socket_impl.cc:1195` 起）：若 result==OK 或 CT 失败，先查 PKP 静态 pins（:1215，`CheckPublicKeyPins` 用 `is_issued_by_known_root` 区分——本地锚 BYPASSED、公网根违规则改写为 `ERR_SSL_PINNED_KEY_NOT_IN_CERT_CHAIN`）；然后算 `is_fatal_cert_error_`（:1234，`ShouldSSLErrorsBeFatal` = HSTS 或 HPKP 命中该主机，`transport_security_state.cc:254`）；最后若 `ssl_config_.ignore_certificate_errors`（:1247）则任何证书区间错误→OK。**HSTS 的两个作用点**由此贯通：请求前 `URLRequestHttpJob::Create`（`url_request_http_job.cc:345` 的 `GetSSLUpgradeDecision`）升级 http→https；错误后把该主机证书错误升级为不可放行（fatal）。响应头 `Strict-Transport-Security` 在 `url_request_http_job.cc:1188` 经 `AddHSTSHeader` 写入动态状态，`TransportSecurityPersister` 异步落盘到 `TransportSecurity` 文件（`url_request_context_builder.cc:425-428`）。

**第 4 站：错误呈现**。导航失败带 cert_status → `SSLErrorNavigationThrottle::WillFailRequest`（`components/security_interstitials/content/ssl_error_navigation_throttle.cc:65`，仅主帧/guest 主帧，https 升级场景让位回退逻辑）→ `HandleSSLErrorWrapper`（`chrome_content_browser_client_navigation_throttles.cc:202`，读 `SSLErrorOverrideAllowed` 系 policy :216-219）→ `SSLErrorHandler::HandleSSLError`（`ssl_error_handler.cc:542`）分诊：时钟错→BadClock 页、captive portal→门户页、匹配 MITM 软件特征（`SSLErrorAssistant` 组件配置）→专用页、否则普通 `SSLBlockingPage`。`CalculateSSLErrorOptionsMask`（`ssl_error_options_mask.cc:42`）依据 `IsCertErrorFatal` 分级表（:14-38：`AUTHORITY_INVALID`/`DATE_INVALID`/`COMMON_NAME_INVALID` 等 soft，`REVOKED`/`INVALID`/`CONTAINS_ERRORS` hard）+ hard_override_disabled + `ssl_info.is_fatal_cert_error` 算出 SOFT_OVERRIDE_ENABLED；`SSLBlockingPage::IsOverridable`（`ssl_blocking_page.cc:97`）最终决定"高级→继续访问"按钮存否。老资料里的 `ContentBrowserClient::AllowCertificateError`（`content/public/browser/content_browser_client.h:1222`）如今在 chrome 实现里只剩 DENY（`chrome_content_browser_client.cc:3947-3988`）——**拦截页主入口已迁移到导航 throttle**，这是 2.1 定位过的方法在本主题下的现状勘误。

## 4. 实操

### 4.1 最小配置：自建 CA 抓包全配置（零代码，双保险）

**保险一：NSS 用户库装根（Linux，信任进入验证链）**

```bash
# CA 证书入库（~/.pki/nssdb 不存在时 certutil 自动建）
certutil -d sql:$HOME/.pki/nssdb -A -t "C,," -n "CorpMITM" -i corp-ca.pem
certutil -d sql:$HOME/.pki/nssdb -L   # 验证在列
```

消费链：`crypto/nss_util.cc:53` 定位 DB → `TrustStoreNSS::ListCertsIgnoringNSSRootsImpl`（`trust_store_nss.cc:166`）枚举证书并跳过"仅在 NSS 内置根模块中"的证书（:177 `IsCertOnlyInNSSRoots`）——即只有你手工加的根会变成锚点，NSS 自带 Mozilla CA 列表不会污染 CRS。win/mac 对应走系统证书管理器（切入点 2）。

**保险二：SPKI 白名单（即使信任链没配好也能放行）**

```bash
# 提取 CA 公钥 SPKI 的 sha256/base64（不是证书指纹！见坑 #7）
openssl x509 -in corp-ca.pem -pubkey -noout \
  | openssl pkey -pubin -outform der \
  | openssl dgst -sha256 -binary | base64
```

```bash
chrome --ignore-certificate-errors-spki-list="sha256/<上面输出的base64>"
```

源码根据：`MaybeWrapCertVerifier`（`ignore_errors_cert_verifier.cc:34`）在 `network_context.cc:2907` 装配；`CreateSPKIHashSet`（`spki_hash_set.cc:20`）按 `"sha256/"+值` 解析；`Verify`（:57-96）遍历服务端发来的整条链（:63 `cert_buffers()`）提取 SPKI 哈希，任一命中白名单即直接构造全绿 `CertVerifyResult` 返回 OK（:81-91）——OCSP 响应存在时连 `GOOD` 状态都替你伪造（:85-89）。开关经 `utility_process_host.cc:411` 的转发表进入网络服务进程。

### 4.2 产品级：自有 PKI 根证书（policy 注入，含硬编码备选）

**policy 通道**（推荐，per-profile + 动态刷新，`CACertificates.yaml` 声明 `dynamic_refresh: true`）：

```json
// Linux: /etc/chromium/policies/managed/corp-certs.json（域名改你的产品）
{
  "CACertificates": ["<PEM 去 header/footer 后 base64，或直接 DER 的 base64>"]
}
```

生效链：policy → pref `certificates.ca_certificates`（`pref_names.h:3147`）→ `GetCertificatePolicy` :806 → `UpdateCertVerifierInstanceParams`（`cert_verifier_creation.cc:221`，落 `additional_trust_anchors`）→ `CertVerifyProcBuiltin` 构造时入 `additional_trust_store_`。变更时 `UpdateAdditionalCertificates`（`cert_verifier_service.cc:149`）热替换 `UpdateVerifyProcData`，无需重启。

**硬编码通道**（无 policy 基础设施的发行版）：在 `GetCertificatePolicy` 尾部（`profile_network_context_service.cc:921` 的 return 前）追加：

```cpp
  //++ 定制：内置企业根（cert_bytes 为 DER 字节的 base64 解码结果）
  additional_certificates->trust_anchors_with_enforced_constraints.push_back(
      std::vector<uint8_t>(std::begin(kCorpRootDer), std::end(kCorpRootDer)));
```

选 `trust_anchors_with_enforced_constraints` 而非裸 `trust_anchors` 的原因：前者带锚点约束+有效期强制语义（`cert_verify_proc_builtin.cc:1278` 起以 `ForTrustAnchor().WithEnforceAnchorConstraints().WithEnforceAnchorExpiry()` 加入），行为与 policy 通道一致。

## 5. 依赖与数据流

- **输入**：服务端证书链（TLS 握手）+ OCSP 响应 + SCT 列表（`CertVerifier::RequestParams`，`net/cert/cert_verifier.h:182`）；信任源四元组（CRS 组件数据、平台用户库、mojo `AdditionalCertificates`、CRLSet 组件）。
- **输出**：`net::CertVerifyResult`（cert_status 位掩码、verified_cert、public_key_hashes、scts、is_issued_by_known_root）→ socket 层 net error → 导航 throttle / omnibox security_state / WebAuthn。
- **持久化**：动态 HSTS → `<profile>/TransportSecurity` JSON；组件状态 → `chrome://components` 的 PKI Metadata（根存储+CT log list+MTC 元数据三合一，`registration.cc:185` 注册）。
- **热更新通道**：`CertVerifierServiceUpdater.UpdateAdditionalCertificates`（policy/用户证书变更）、`CertVerifierServiceFactory.UpdateCRLSet/UpdateCtLogList/UpdateChromeRootStore`（`cert_verifier_service_factory.mojom:96-114`）——`NetworkContextParams` 快照之外的所有动态面都走这两个 updater pipe。
- **契约**：`CertVerifyProc` 是同步线程安全接口（`net/cert/README.md` 明示设计意图：可能要调同步 OS API）；`CertVerifier` 是异步门面；跨 mojo 边界时结果必须可序列化，所以 `AdditionalCertificates` 用裸 DER 字节数组而非句柄。

## 6. 坑与勘误

1. **`--ignore-certificate-errors` 并未死透（对 6.1 坑 #7 的修正）**。本仓快照实证：该 switch 仍在 `network_session_configurator.cc:835-837` 被解析进 `HttpNetworkSession::Params::ignore_certificate_errors`，且在转发表 `utility_process_host.cc:431` 中随网络服务进程带过去，最终 `ssl_client_socket_impl.cc:1246-1248` 把证书区间错误改写为 OK——**包括刚算出的 PKP 违规结果**（`ERR_SSL_PINNED_KEY_NOT_IN_CERT_CHAIN` 同属证书区间）。6.1 所说"只剩 UI 消费"不成立；但它确实只作用于 socket 层结果映射，不做信任、不进验证链，产品化请用切入点 3/4。（来源：源码实证）
2. **HSTS 动态状态无豁免通道**。`hsts_policy_bypass_list` 只在 `GetStaticSTSState`（`transport_security_state.cc:624`）查询静态 preload 时生效；对响应头学来的动态 HSTS，任何 policy/开关都绕不过。唯一物理手段是关闭浏览器后删 `TransportSecurity` 文件或用 `chrome://net-internals/#hsts` 的 Delete（`net_internals_ui.cc:249` 消息 `domainSecurityPolicyDelete`）。连带效果：HSTS 主机上证书错误被强制 fatal（`ShouldSSLErrorsBeFatal` :254 → `is_fatal_cert_error_` :1231 → interstitial 无"继续访问"）。（源码实证）
3. **静态数据有 10 周保鲜期**。`IsBuildTimely`（`transport_security_state.cc:594`，`base::GetBuildTime` 距今 ≥70 天返回 false）过期后静态 HSTS/pins 查询全部落空——长期不重编的定制构建会"神秘地"不再升级某些预载域名。（源码实证）
4. **Android 双轨制**。`chrome_root_store_optional = is_android && !is_cronet_build`（`net/features.gni:69`）：clank 启动即 `SetUseChromeRootStore(true)`（`system_network_context_manager.cc:705`），用户装的 CA 经 `X509Util.getUserAddedRoots`（`net/android/java/src/org/chromium/net/X509Util.java:455`，按 alias 前缀 `user:` 过滤）进 `TrustStoreAndroid`（`trust_store_android.cc:24-40`）与 CRS 合流；WebView 则走平台验证器 `CertVerifyProcAndroid`。注意 Android 7+ "应用默认不信用户 CA"是框架对 app 的行为，Chrome 浏览器自身显式枚举用户根，不受影响。（源码实证 + 平台文档）
5. **非 Google 品牌构建静态 pins 默认关闭**。`transport_security_state.cc:241-244`：`!GOOGLE_CHROME_BRANDING` 时 `enable_static_pins_ = false`——自研产品天然免 google.com 域 pins 崩溃面，但也意味着你无法靠 pins 保护自己的域（要自建需启用并接组件更新）。（源码实证）
6. **"加系统根就能让 Chrome 信任公网站点"已过时**。CRS 时代（win/mac/linux/chromeos 为 `CHROME_ROOT_STORE_ONLY`，`features.gni:73`）系统库只剩"用户/企业添加的根"这一角色（`CreateSslSystemTrustStoreChromeRoot` 的合并语义）。给系统库塞一张公网根的旧测试手法不再改变公网信任判定；Linux 没有系统库，`~/.pki/nssdb` 就是"平台库"。（源码实证）
7. **SPKI 白名单格式坑**。值是 `sha256(base64(SPKI 结构体))`，不是证书指纹、也不是公钥裸哈希之外的变体；漏写 `sha256/` 前缀会 `LOG(ERROR)` 静默丢弃（`spki_hash_set.cc:21`）。（源码实证）
8. **CT 强制只打公网链**。`CheckCTRequirements` 开头的 `!is_issued_by_known_root → CT_NOT_REQUIRED`（`require_ct_delegate.cc:19-20`）意味着自建 CA 抓包不会触发 `ERR_CERTIFICATE_TRANSPARENCY_REQUIRED`；反过来，走公网 CA 的内网站点若缺 SCT，用 `CertificateTransparencyEnforcementDisabledForCas`（按 SPKI）豁免。（源码实证）
9. **证书管理 UI 有两代**。v1（NSS 系，Linux/CrOS 的 settings 内嵌）与 v2 `chrome://certificate-manager`（`chrome/browser/ui/webui/certificate_manager/`，`CHROME_ROOT_STORE_CERT_MANAGEMENT_UI = is_win||is_mac||is_linux||is_chromeos`，`chrome/common/features.gni:42`）。v2 下用户证书进 `ServerCertificateDatabaseService`，启用后 `wait_for_update=true`（`profile_network_context_service.cc:1541`）会把首个验证请求排队到证书库就绪（`cert_verifier_service.cc:203` 的 `queued_requests_`）。证书查看器 URL 也已改为 `chrome://view-cert/`（`webui_url_constants.h:66`），旧的 certificate-viewer 写法失效。（源码实证）

## 7. 验证方法

- **信任是否生效**：访问内网 https 站点看锁标；`chrome://net-export` 抓 NetLog，过滤 `CERT_VERIFY_PROC_CREATED` 与 `CERT_VERIFY_PROC_ADDITIONAL_CERT` 事件（打点在 `cert_verify_proc_builtin.cc:1274` 起，additional cert 会带 trust 说明）。6.1 的老办法（`cert_verifier_creation.cc:128` 打 trust store 大小）仍可用。
- **HSTS 状态**：`chrome://net-internals/#hsts`（Domain Security Policy 视图，`domain_security_policy_view.js:159`）查询某域动态/静态状态，或直接 Add/Delete；文件级验证：关浏览器后 cat profile 下 `TransportSecurity`。
- **policy**：`chrome://policy` 看 `CACertificates` 等是否 Applied；pref 层 `chrome://version` 的命令行 + `~/.config/chromium/` 下 managed 目录。
- **SPKI 白名单**：值错时启动日志有 `Invalid SPKI:` ERROR（`spki_hash_set.cc:22`）；命中与否可用 `chrome://net-export` 里验证结果对比。
- **单测**：`services/cert_verifier/cert_verifier_service_unittest.cc`（含 additional certs 热更用例）、`net/cert/cert_verify_proc_builtin_unittest.cc`（信任锚优先级）、`net/http/transport_security_state_unittest.cc`（HSTS/pins）、`chrome/browser/ssl/cert_verifier_browser_test.cc`（端到端）。
- **工具链**：CRS 增删根用 `net/tools/root_store_tool`（输入 `root_store.textproto`，见 `net/data/ssl/chrome_root_store/README.md:15`）；快速验证书用 `openssl verify -CAfile corp-ca.pem -untrusted chain.pem leaf.pem`。
