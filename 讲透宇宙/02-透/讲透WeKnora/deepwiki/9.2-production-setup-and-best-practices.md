## Security Hardening

 
### Network Isolation and Access Control

 **Production deployments should never expose WeKnora services directly to the public internet.** Instead, isolate the components in internal networks and expose only the frontend via a secured ingress or reverse proxy with TLS termination.

 
#### WeKnora Production Network Topology

 
```

```

 
 - The system is segmented into layers: public internet users access the system only via the TLS-terminating reverse proxy.
 - The frontend UI (`wechatopenai/weknora-ui`) serves on port 80 internally and proxies requests to the backend API server (`wechatopenai/weknora-app`).
 - The backend connects to document parser (`docreader`) via gRPC, the PostgreSQL database (`paradedb/paradedb`) for relational and vector data, Redis for caching and queues, and optionally Neo4j for graph data.
 - Infrastructure ports like 5432 (PostgreSQL) and 6379 (Redis) must be firewalled and not exposed publicly.
 
 **Implementation Notes:**

 
 - TLS termination at ingress is configured via the Helm chart’s ingress resources [helm/templates/ingress.yaml1-5](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/ingress.yaml#L1-L5)
 - Backend communicates with `docreader` service on port 50051 [helm/templates/app.yaml117-118](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/app.yaml#L117-L118)
 - Frontend configures environment variables `APP_HOST` and `APP_PORT` to target the backend service (`app`) within the cluster DNS [helm/templates/frontend.yaml45-48](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/frontend.yaml#L45-L48)

### Encryption and Secret Management

 Sensitive data in WeKnora (such as API keys, tenant secrets, encryption keys, and passwords) is protected using AES-256 encryption driven by a centrally managed system key.

 
 - `SYSTEM_AES_KEY` encrypts tenant API keys, model API keys, vector store credentials, and web search provider keys [helm/templates/secrets.yaml47-50](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/secrets.yaml#L47-L50)
 - During cloud image first boot (`firstboot.sh`), a strong 32-byte random AES key and cryptographically secure passwords for PostgreSQL, Redis, and JWT secrets are generated dynamically to avoid credential reuse [scripts/cloud-image/firstboot.sh59-77](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/firstboot.sh#L59-L77)
 - The Helm chart secret manifests reuse generated AES keys on upgrades via Kubernetes `lookup` to avoid unwanted key rotation that could cause data irrecoverability [helm/templates/secrets.yaml20-28](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/secrets.yaml#L20-L28)

## Production Environment Configuration

 
### Critical Environment Variables

 Set the following environment variables for production deployments to optimize performance, security, and compatibility:

 
| Variable | Recommended Value | Purpose / Notes |
|---|---|---|
| GIN_MODE | "release" | Optimize Gin framework for production, disables debug logs |
| RETRIEVE_DRIVER | "postgres" | Use ParadeDB (PostgreSQL + pgvector) for vector retrieval |
| STORAGE_TYPE | "minio" / "cos" / "s3" / "tos" | Use cloud-native object storage for persistent file storage |
| STREAM_MANAGER_TYPE | "redis" | Synchronize streaming events across pods for multiple replicas |
| AUTO_RECOVER_DIRTY | "true" | Recover interrupted asynchronous tasks |
| CONCURRENCY_POOL_SIZE | "5" or higher | Number of concurrent processing workers for chat and tasks |

 These variables are defined in the Helm chart and passed to the containers as environment variables [helm/values.yaml89-108](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L89-L108) [helm/templates/app.yaml50-128](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/app.yaml#L50-L128)

### Container Orchestration (Kubernetes with Helm)

 WeKnora includes a well-defined Helm chart that packages all system components with configurable replicas, resource requests/limits, security settings, and probes.

 
#### Key Helm Chart Best Practices

 
 - **Resource Limits**: Default for `app` container is 1 CPU, 1Gi memory limit with requests of 100m CPU/256Mi memory. Adjust based on load [helm/values.yaml75-81](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L75-L81)
 - **Security Context**: Use runtime default seccomp profile, and disable privilege escalation [helm/values.yaml32-40](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L32-L40)
 - **Health Probes**: Liveness and readiness probes ensure traffic is routed only to healthy pods [helm/values.yaml120-138](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L120-L138)
 - **Writable volumes for frontend**: The `frontend` (Nginx) requires writable directories for cache and runtime, provided by ephemeral `emptyDir` volumes [helm/templates/frontend.yaml73-83](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/frontend.yaml#L73-L83)
 - **Secrets Management**: Environment variables containing secrets are injected from Kubernetes secrets created by Helm [helm/templates/secrets.yaml1-56](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/secrets.yaml#L1-L56)
 - **Pod Affinity and Node Selection**: Options are configurable to optimize pod scheduling for high availability or node constraints.

## High Availability and Scaling

 
### Horizontal Scaling

 WeKnora supports horizontal scaling of stateless components:

 
 - **Backend API (`app`)**: Increase replica count, but ensure `STREAM_MANAGER_TYPE=redis` is set so Server-Sent Events for chat streaming synchronize correctly across pods [helm/values.yaml97-102](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L97-L102)
 - **Document Parser (`docreader`)**: Increase replica count to handle bursty document ingestion workloads [helm/values.yaml203-205](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L203-L205)
 - **Frontend**: Scale frontend replicas independently for user-facing load.
 - **Database Scaling**: PostgreSQL (ParadeDB) should be backed by reliable persistent storage and can be horizontally scaled or replaced with external vector stores like Qdrant via profiles [helm/templates/NOTES.txt77-79](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/templates/NOTES.txt#L77-L79)
 
 
### Persistent Storage in Production

 Avoid ephemeral volumes for data persistence in production:

 
 - Use Persistent Volume Claims (PVCs) with an appropriate StorageClass defined in Helm values (`global.storageClass`) [helm/values.yaml13-16](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L13-L16)
 - ParadeDB and Redis volumes should be durable to avoid data loss.
 - Switch `STORAGE_TYPE` from `local` to cloud storage backends (e.g., MinIO, COS, S3) for file persistence [helm/values.yaml98-99](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L98-L99)

## Cloud Image Deployment (Tencent Lighthouse)

 WeKnora provides cloud-agnostic scripts to prepare a pre-configured cloud image (AMI / snapshot) deploying WeKnora runtime containers ready to run on any Linux instance with systemd + Docker.

 
### Preparation and Cleanup Scripts

 
 - **`prepare.sh`**

 
 - Installs Docker (supports configuring mirrors for Docker repository and Docker Hub registry acceleration for China mainland or restricted environments) [scripts/cloud-image/prepare.sh46-121](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/prepare.sh#L46-L121)
 - Downloads only 4 lightweight runtime files (`docker-compose.yml`, `.env.example`, `config/config.yaml`, skill preload config) via `curl + tar` to avoid cloning the full repo [scripts/cloud-image/prepare.sh123-148](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/prepare.sh#L123-L148)
 - Pulls and starts 5 core containers: frontend, app, docreader, postgres, redis [scripts/cloud-image/prepare.sh175-178](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/prepare.sh#L175-L178)
 - Pre-pulls sandbox skill container images for agent execution to avoid delays at runtime [scripts/cloud-image/prepare.sh179-180](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/prepare.sh#L179-L180)
 - **`cleanup.sh`**

 
 - Stops all containers gracefully [scripts/cloud-image/cleanup.sh20-28](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/cleanup.sh#L20-L28)
 - Clears all user data, logs, and credentials [scripts/cloud-image/cleanup.sh30-38](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/cleanup.sh#L30-L38)
 - Removes Docker volumes linked to the deployment project to avoid leaking data [scripts/cloud-image/cleanup.sh43-46](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/cleanup.sh#L43-L46)
 - Truncates and deletes OS system logs and SSH keys to prevent host-specific secrets leakage [scripts/cloud-image/cleanup.sh56-69](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/cleanup.sh#L56-L69)
 - Resets machine ID and cloud-init metadata to ensure unique instance identity on launch [scripts/cloud-image/cleanup.sh75-79](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/cleanup.sh#L75-L79)
 - Cleans cache and temporary files, then safely powers off the machine for snapshot creation [scripts/cloud-image/cleanup.sh80-94](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/cleanup.sh#L80-L94)
 
 
### First-Boot Initialization

 
 - **`weknora-firstboot.service`** runs once, triggered before the main `weknora.service` Docker compose start [scripts/cloud-image/systemd/weknora.service3-4](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/systemd/weknora.service#L3-L4)
 - Executes `firstboot.sh` which generates and writes random secure secrets into `.env`, creates a `.firstboot.done` marker to avoid regeneration, and starts containers [scripts/cloud-image/firstboot.sh27-101](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/firstboot.sh#L27-L101)
 - Writes generated credentials to `/root/weknora-credentials.txt` for administrator reference [scripts/cloud-image/firstboot.sh108-131](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/firstboot.sh#L108-L131)
 - Disables the firstboot service upon successful initialization to ensure idempotence and data consistency [scripts/cloud-image/firstboot.sh137](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/firstboot.sh#L137-L137)

## Backup and Disaster Recovery

 
### Data Persistence and Backup Targets

 
 - PostgreSQL (ParadeDB) stores knowledge base metadata, vector embeddings, and chat histories.
 - Object storage (local file storage or S3-compatible backend) stores uploaded documents and artifacts.
 - Configuration and secrets (especially `SYSTEM_AES_KEY` in Kubernetes secrets) crucial for decrypting encrypted data.
 
 
### Recommended Backup Practices

 
 - Use volume snapshots or scheduled dumps of PostgreSQL and Redis data volumes.
 - Back up object storage buckets or file directories defined by `LOCAL_STORAGE_BASE_DIR`.
 - Securely back up Kubernetes secrets or `.env`-style secret files. Loss of `SYSTEM_AES_KEY` means irreversible loss of encrypted credentials.
 - Pin deployment image versions using `WEKNORA_REF` to ensure version reproducibility during restores [scripts/cloud-image/prepare.sh30](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/prepare.sh#L30-L30)
 - Use docker registry mirrors (`DOCKER_REGISTRY_MIRROR`) to speed image pulls in restricted networks [scripts/cloud-image/prepare.sh35](https://github.com/Tencent/WeKnora/blob/10973ed3/scripts/cloud-image/prepare.sh#L35-L35)
 - Set `AUTO_RECOVER_DIRTY=true` in container environments to enable recovery of interrupted asynchronous tasks during pod restarts [helm/values.yaml101](https://github.com/Tencent/WeKnora/blob/10973ed3/helm/values.yaml#L101-L101)

# Summary

 WeKnora production deployments leverage Kubernetes Helm charts with strict network isolation, secure AES-256 key management, and configuration best practices. Tencent Lighthouse cloud image scripts provide a streamlined path for creating portable, secure WeKnora-ready VM images. Scaling is achieved by horizontally replicating stateless components with Redis-backed synchronization for streamed chat. Reliable persistent storage and secret backup are critical to ensure high availability and disaster recovery readiness.
