## Purpose and Scope

 WeKnora employs [Asynq](https://github.com/Tencent/WeKnora/blob/10973ed3/Asynq) a Redis-backed Go library, as its asynchronous task queue system to decouple latency-sensitive HTTP request handling from heavy or long-running background processes. This design enhances system resilience and throughput by enabling:

 
 - Asynchronous document ingestion and chunk processing.
 - Post-processing enrichment such as summaries, question generation, and knowledge graph extraction.
 - Wiki ingestion and knowledge base maintenance.
 - External data source synchronization.
 
 The system supports multiple worker pools isolated by workload types, task prioritization, retries with custom backoff, and rich observability including progress tracking and cancellation support.

## Architecture Overview

 
### System Components and Data Flow

 WeKnora’s async task processing architecture follows a multi-pool worker model. User requests enqueue tasks to Redis queues via an Asynq client, and dedicated Asynq worker servers consume tasks from queues according to their pool assignments. Each worker server runs isolated concurrency to prevent resource contention between workload types.

 
```

```

 
 - **Producers** like `knowledgeService` enqueue tasks as JSON payloads with metadata specifying task type, queue, and retry policy ([internal/router/task.go94-102](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L94-L102)).
 - **Redis** stores these task messages reliably with support for visibility timeout, retries, and dead letter queues ([internal/router/task.go71-92](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L71-L92)).
 - **Worker Servers** run separate Asynq servers with isolated concurrency for each logical pool: Core, Enrichment, PostProcess, Wiki, and Shared ([internal/router/task.go24-51](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L24-L51)).
 - **Task Handlers** implement specific logic for each task type ([internal/router/task.go41-46](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L41-L46)).

## Async Task Queues and Worker Pools

 
### Queue and Pool Definitions

 Task routing is defined in the centralized `internal/types/task.go`. Queues correspond to logical pools which receive weighted concurrency.

 
| Pool Name | Internal Constant | Default Concurrency | Typical Queues and Task Types |
|---|---|---|---|
| Core | WorkerPoolCore | 8 | default (e.g. document/manual process tasks), chat_attachment |
| PostProcess | WorkerPoolPostProcess | 2 | postprocess (knowledge post-processing tasks) |
| Enrichment | WorkerPoolEnrichment | 12 | multimodal (image multimodal), summary (summary gen), graph (chunk extract), question (question gen) |
| Maintenance | WorkerPoolMaintenance | 4 | sync (data source sync), low (misc maintenance and KB clone/delete) |
| Wiki | WorkerPoolWiki | 8 | wiki (wiki ingest, finalize) |
| Shared | WorkerPoolShared | 6 | Subscribes to core and enrichment queues elastically |

 Task to queue mappings:

 
| Task Type | Queue Name | Pool Name |
|---|---|---|
| TypeDocumentProcess | default | Core |
| TypeTemporaryDocumentProcess | chat_attachment | Core |
| TypeKnowledgePostProcess | postprocess | PostProcess |
| TypeImageMultimodal | multimodal | Enrichment |
| TypeChunkExtract | graph | Enrichment |
| TypeDataTableSummary | summary | Enrichment |
| TypeDataSourceSync | sync | Maintenance |
| TypeKBClone | low | Maintenance |
| TypeWikiIngest | wiki | Wiki |

 
### Server Construction and Concurrency Configuration

 Each worker server is instantiated via `newAsynqServer()` which configures concurrency, assigned queues with weights, and a custom retry backoff function ([internal/router/task.go135-145](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L135-L145)).

 The concurrency for each pool is determined via system settings and environment variables ([internal/router/task.go159-168](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L159-L168)):

 
 - `NewCoreAsynqServer` provides guaranteed capacity for document/manual parsing ([internal/router/task.go170-171](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L170-L171)).
 - `NewPostProcessAsynqServer` isolates post-processing tasks from LLM-heavy queues ([internal/router/task.go32](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L32-L32)).
 - `NewEnrichmentAsynqServer` runs LLM- and model-intensive tasks like OCR, captioning ([internal/router/task.go33](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L33-L33)).
 - `NewSharedAsynqServer` subscribes to core and enrichment queues to elastically borrow idle capacity ([internal/router/task.go35](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L35-L35)).
 - `NewWikiAsynqServer` handles wiki ingestion separately due to different workload profiles ([internal/router/task.go36](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task.go#L36-L36)).

## Task Inspector and Cancellation

 
### Task Inspection Interface

 WeKnora defines `interfaces.TaskInspector` to monitor and manipulate asynchronous tasks. Its implementation `asynqTaskInspector` uses the Asynq Redis inspection API to list, cancel, or retry tasks across queues and states by matching knowledge IDs in task payloads ([internal/router/task_inspector.go30-43](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task_inspector.go#L30-L43)).

 Key capabilities include:

 
 - Listing and scanning queues (`queuesScanned`) to locate pending tasks ([internal/router/task_inspector.go75-81](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task_inspector.go#L75-L81)).
 - `CancelTasksForKnowledge` which removes queued tasks referencing a given `knowledge_id` and signals active workers to stop ([internal/router/task_inspector.go109-124](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task_inspector.go#L109-L124)).
 - `HasQueuedTasksForKnowledge` as a read-only counterpart used by housekeeping sweeps ([internal/router/task_inspector.go167-172](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/task_inspector.go#L167-L172)).

## Progress Tracking with SpanTracker

 The system uses `SpanTracker` ([internal/application/service/knowledge_span_tracker.go85-150](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/service/knowledge_span_tracker.go#L85-L150)) to record per-attempt progress trees mirroring Langfuse vocabulary (`root`, `span`, `generation`).

 
 - **Attempts**: `OpenAttempt` allocates an incremental attempt number and root span (`[internal/application/service/knowledge_span_tracker.go:89-89]`).
 - **Stages & Subspans**: `BeginStage`, `BeginSubSpan`, `EndSpan`, `FailSpan`, and `SkipSpan` manage lifecycle transitions ([internal/application/service/knowledge_span_tracker.go100-119](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/service/knowledge_span_tracker.go#L100-L119)).
 - **Cross-Process Bridge**: `LookupStage` allows distributed Asynq workers (such as `ImageMultimodalService`) to locate parent stage spans and attach subspans ([internal/application/service/knowledge_span_tracker.go125](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/service/knowledge_span_tracker.go#L125-L125)).
 - **Persistence**: Backed by `knowledge_processing_spans` table via `KnowledgeSpanRepository` ([internal/application/repository/knowledge_span_repo.go14-47](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/application/repository/knowledge_span_repo.go#L14-L47)).

## SyncTaskExecutor: Lightweight Task Execution

 In "Lite" configurations without Redis, `SyncTaskExecutor` serves as a drop-in alternative to `asynq.Client` ([internal/router/sync_task.go17-22](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/sync_task.go#L17-L22)).

 
 - Dispatches tasks directly to background goroutines ([internal/router/sync_task.go37-40](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/sync_task.go#L37-L40)).
 - Implements custom retry logic with exponential backoff ([internal/router/sync_task.go90-113](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/sync_task.go#L90-L113)).
 - Tags execution contexts with `types.WithBackgroundTask` to ensure model concurrency limits remain consistent with the Redis-backed worker pools ([internal/router/sync_task.go86](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/router/sync_task.go#L86-L86)).
