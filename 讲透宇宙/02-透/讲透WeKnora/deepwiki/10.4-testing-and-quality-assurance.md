## Purpose and Scope

 This document describes the comprehensive testing strategies, tools, and quality assurance (QA) practices employed in the WeKnora codebase. It covers how tests are organized and executed for the Go backend, Vue.js frontend, Python document processing services, and CLI contract suites. Additionally, it details CI/CD workflows, linting configurations, error code contract tests, and QA dataset sampling tools used to validate performance and correctness.

## Testing Infrastructure and Execution

 WeKnora applies a polyglot testing approach aligned with its microservices architecture.

 
### Backend Testing (Go)

 
 - Backend tests use the native `testing` package with `_test.go` suffixes colocated with source packages.
 - CI and local execution run `go vet` and `go test` across modules, while specialized build tags (such as `-tags anydoc`) exercise the Rust-backed document parser library [.github/workflows/app.yml116-122](https://github.com/Tencent/WeKnora/blob/10973ed3/ .github/workflows/app.yml#L116-L122) [.github/workflows/anydoc.yml77-81](https://github.com/Tencent/WeKnora/blob/10973ed3/.github/workflows/anydoc.yml#L77-L81)
 - Contract testing enforces CLI error code integrity. For instance, `TestAllReferencedCodesAreRegistered` uses Go's `go/ast` and `go/parser` packages to scan `cli/cmd/` for literal `cmdutil.NewError` and `cmdutil.Wrapf` invocations, verifying that every referenced `ErrorCode` is registered in `cmdutil.AllCodes()` [cli/acceptance/contract/errorcodes_test.go36-57](https://github.com/Tencent/WeKnora/blob/10973ed3/cli/acceptance/contract/errorcodes_test.go#L36-L57)
 
 
### Frontend Testing (Vue.js)

 
 - Unit and component tests utilize the Vitest framework and run via npm test scripts.
 - Specialized terminology tests verify user-facing strings, ensuring workspace terminology consistency across locale files [frontend/src/i18n/locales/workspaceTerminology.test.ts41-53](https://github.com/Tencent/WeKnora/blob/10973ed3/frontend/src/i18n/locales/workspaceTerminology.test.ts#L41-L53)
 
 
### Document Processing Testing (Python & gRPC)

 
 - The `docreader` component uses Python's `unittest` framework (`python -m unittest discover`) to validate document conversions and parsing logic [docreader/tests/test_ppt_convert.py20-57](https://github.com/Tencent/WeKnora/blob/10973ed3/docreader/tests/test_ppt_convert.py#L20-L57) [.github/workflows/docreader.yml72-73](https://github.com/Tencent/WeKnora/blob/10973ed3/.github/workflows/docreader.yml#L72-L73)
 - Go client integration tests verify gRPC communication with the running DocReader service [docreader/client/client_test.go19-35](https://github.com/Tencent/WeKnora/blob/10973ed3/docreader/client/client_test.go#L19-L35) [.github/workflows/docreader.yml97-98](https://github.com/Tencent/WeKnora/blob/10973ed3/.github/workflows/docreader.yml#L97-L98)

## Span Tracking: Observability of Parsing Pipeline

 Span tracking records detailed lifecycle events of document parsing and indexing attempts across multi-stage asynchronous workers.

 
### Key Concepts

 
 - **Span**: An in-memory handle representing a unit of work with metadata like ID, kind, name, status, and execution timestamps.
 - **Attempt**: A top-level parse operation distinguished by an increasing attempt counter per knowledge ID.
 - **Stage**: Canonical parse phases such as `DocReader`, `Chunking`, or `Embedding`.
 - **SubSpan**: Nested spans representing asynchronous or fan-out child operations.
