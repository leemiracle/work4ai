  This page documents WeKnora's database migration system, version management, and database maintenance procedures. It details how the system handles schema evolution across multiple database engines (PostgreSQL/ParadeDB, MySQL, and SQLite), implements automated recovery mechanisms for interrupted operations, and verifies database schema consistency through tests.

 
## Overview

 WeKnora uses a versioned migration system powered by `github.com/golang-migrate/migrate/v4` [internal/database/migration.go12](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/database/migration.go#L12-L12) Migrations run automatically at application startup to ensure the database schema matches the required application version. The system supports PostgreSQL (primary), ParadeDB (a Postgres variant), MySQL, and SQLite.

 The migration logic is centralized in `internal/database/migration.go` [internal/database/migration.go1](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/database/migration.go#L1-L1) while SQL migration scripts are organized by database dialect:

 
 - **PostgreSQL/ParadeDB**: `migrations/paradedb/` (initial schema) and `migrations/versioned/` (incremental evolution).
 - **MySQL**: `migrations/mysql/` [migrations/mysql/00-init-db.sql1](https://github.com/Tencent/WeKnora/blob/10973ed3/migrations/mysql/00-init-db.sql#L1-L1)
 - **SQLite**: `migrations/sqlite/` (consolidated baseline and incremental evolution for Lite mode and testing) [migrations/sqlite/000000_init.up.sql1](https://github.com/Tencent/WeKnora/blob/10973ed3/migrations/sqlite/000000_init.up.sql#L1-L1)

## Migration Architecture and Runner Implementation

 The migration runner is tightly integrated into the application's startup lifecycle. On launch, the system detects the database type from the DSN and executes all pending migrations.

 
### Core Functions and Control Flow

 
 - `RunMigrations(dsn string) error`: Entry point called at application startup, which delegates to `RunMigrationsWithOptions(dsn, MigrationOptions{AutoRecoverDirty: false})` [internal/database/migration.go83-85](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/database/migration.go#L83-L85)
 - `RunMigrationsWithOptions(dsn string, opts MigrationOptions) error`: Configurable runner that initializes the `migrate.Migrate` instance. For SQLite, it opens the database handle directly via `sql.Open` and passes a `sqlite3` driver instance via `sqlite3migrate.WithInstance` to avoid path parsing errors [internal/database/migration.go101-145](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/database/migration.go#L101-L145)
 - **Dirty State Handling**: Before applying migrations, the runner checks version and dirty flags using `m.Version()` [internal/database/migration.go148](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/database/migration.go#L148-L148) If a dirty state is detected and `AutoRecoverDirty` is enabled, it attempts recovery; otherwise, it halts and records a failure [internal/database/migration.go161-176](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/database/migration.go#L161-L176)

## Schema Evolution and SQLite Sync Verification

 The database schema evolves through ordered migration scripts. To ensure SQLite (used in WeKnora Lite and local testing) remains fully compatible with PostgreSQL versioned migrations, automated schema synchronization tests are maintained.

 
### SQLite Versioned Schema Tests

 The test suite in `internal/database/migration_sqlite_versioned_schema_test.go` verifies that SQLite migrations create all required versioned tables (such as task queues, system settings, processing spans, knowledge multi-tags, and browser authorizations) and columns at the expected version (`expectedSQLiteMigrationVersion = 19`) [internal/database/migration_sqlite_versioned_schema_test.go18-47](https://github.com/Tencent/WeKnora/blob/10973ed3/internal/database/migration_sqlite_versioned_schema_test.go#L18-L47)
