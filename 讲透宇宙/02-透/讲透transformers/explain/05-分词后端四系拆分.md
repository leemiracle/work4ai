# 05 分词后端体系（tokenization_* 四系拆分）

## ① 角色定位

transformers 的分词层在 2026 版经历了一次彻底重构：**旧的 `tokenization_utils.py` 单文件已不存在**，拆成"一基座三后端一特化"五个文件。`tokenization_utils_base.py` 是基座（用户 API 面：`__call__`/`encode`/`pad`/特殊 token 管理）；`tokenization_python.py`（纯 Python 慢速实现）、`tokenization_utils_sentencepiece.py`（SentencePiece 加载）、`tokenization_utils_tokenizers.py`（Rust tokenizers 快速实现）是三个平行后端；`tokenization_mistral_common.py` 是 mistral-common 特化。设计哲学从"每型慢/快一对类"变为"**每型一个类，后端由基类决定**"——这是理解本版分词层的钥匙。

## ② 内部结构

- `tokenization_utils_base.py`：`BatchEncoding`（L195，UserDict 包装）、`TruncationStrategy`（L154）、`PreTrainedTokenizerBase`（L962，全部分词器公共门面：from_pretrained/save_pretrained/special tokens/编码入口）；工具函数 `get_fast_tokenizer_file`（L3461）、`find_sentencepiece_model_file`（L3493）、`load_vocab_and_merges`（L3553）、`generate_merges`（L3669，从 vocab+scores 重建 BPE merges）。
- `tokenization_python.py`（1424 行）：`Trie`（L45）/`ExtensionsTrie`（L276）做子词匹配；`PythonBackend`（L400）——纯 Python 分词基类，`tokenize`（L625）/`_tokenize`（L680）/`_convert_token_to_id`（L699）；L1424 别名 `PreTrainedTokenizer = PythonBackend`。
- `tokenization_utils_sentencepiece.py`（315 行）：`SentencePieceBackend`（L45）——注意它继承的是 `PreTrainedTokenizer`，即上一行的别名，展开后**真实基类是 PythonBackend**（批产物 batch-86-part-2 甄别）；`SentencePieceExtractor`（L289）从 sentencepiece.model 导出词表。
- `tokenization_utils_tokenizers.py`（1514 行）：`TokenizersBackend`（L86）包装 Rust `tokenizers.Tokenizer`（`self._tokenizer`）；`convert_to_native_format`（L104）classmethod 把 tokenizer.json/sentencepiece model/tekken.json/vocab+merges 四路统一成 `TokenizerFast` 对象；L513 `_patch_mistral_regex`（vocab>10 万且带 pre_tokenizer 时打正则补丁）；L1514 别名 `PreTrainedTokenizerFast = TokenizersBackend`。
- `tokenization_mistral_common.py`：`MistralCommonBackend`（L194），整类 `@requires(backends=("mistral-common",))`——依赖缺失时由 `utils/dummy_mistral_common_objects.py` 占位类顶替（batch-88-part-1 甄别）。

## ③ 外部连接

- 入口别名（`__init__.py` L836-838）：旧模块路径 `tokenization_utils_fast`→`tokenization_utils_tokenizers`、`tokenization_utils`→`tokenization_utils_sentencepiece`，经 `_create_module_alias` 透明转发——旧 import 语句不断裂。
- Auto 分发（tokenization_auto.py）：`TOKENIZER_MAPPING_NAMES`（L64）V5 起每型映射**单字符串**（L516 注释明示）；L435 `MODEL_IDS_TO_TOKENIZERS_BACKEND` 白名单按 repo id 强制走 TokenizersBackend；`_use_mistral_format`（L473）探测 tekken.json 决定是否切 MistralCommonBackend。
- Fast 名字回退链在两处兜底：`_LazyModule.__getattr__`（import_utils.py L2593 起）对 `*TokenizerFast` 自动 removesuffix 回退；tokenization_auto L846-852 同样逻辑。所以 `BertTokenizerFast` 与 `BertTokenizer` 在本版经常指向同一个类。
- 图谱侧 `is_base_mistral` 走 hub API 探测属函数体延迟 import（batch-86-part-2），即 TokenizersBackend 对 hub 工具的依赖是惰性的。

## ④ 数据流

`AutoTokenizer.from_pretrained("meta-llama/Llama-3-8B")`：①AutoConfig 拿 model_type="llama"；②查 `TOKENIZER_MAPPING_NAMES["llama"]` 得类名字符串（tokenizers 可用时），`tokenizer_class_from_name`（tokenization_auto L517）反查模块并 getattr 成类；③`PreTrainedTokenizerBase.from_pretrained`（基座 L962 体系）下载文件、识别 `tokenizer.json` 存在 → 走 TokenizersBackend 路线 `convert_to_native_format`（L104）直接 `TokenizerFast.from_file` 得 Rust 对象；④`__init__`（L366 起）把 truncation/padding 配置写入 `self._tokenizer`，added tokens 经 `add_tokens` 同步进 Rust 侧；⑤`__call__`/`encode` 全部委托 Rust 批量编码，`BatchEncoding` 包装返回并附 offset mapping。SentencePiece 路线的差异在第③步：无 tokenizer.json 时 `find_sentencepiece_model_file` 找 .model 文件，SentencePieceExtractor 抽 vocab，或经 `generate_merges` 重建 BPE。

## ⑤ 设计决策（含勘误）

- **勘误一（本篇核心）："PreTrainedTokenizer 是慢速基类、PreTrainedTokenizerFast 是快速基类"的旧图景已失效**。两者现在都只是别名：`PreTrainedTokenizer = PythonBackend`（tokenization_python.py:1424）、`PreTrainedTokenizerFast = TokenizersBackend`（tokenization_utils_tokenizers.py:1514）。每个模型家族通常只剩一个分词类（多数直接基于或继承 TokenizersBackend 语义），"Fast"后缀靠 getattr 回退维持兼容。
- **勘误二：SentencePieceBackend 的继承链经过别名间接指到 PythonBackend**——读 `class SentencePieceBackend(PreTrainedTokenizer)` 时必须先解开别名，否则 MRO 理解错位。这是重构过渡期的典型"别名套别名"地形。
- `convert_to_native_format` 的注释（L127-131）透露一个细节优化：从 tokenizer.json 重建子类时**不整文件 from_file**，而是空词表初始化后只抽 post_processor/padding/truncation——Unigram（Albert/Llama/T5 类）例外，必须非空 vocab 才能在 Rust 侧初始化。
- 四路输入统一到 Rust 对象的设计让"每个后端类只管自己擅长的事"：PythonBackend 管 vocab 字典与 Trie，TokenizersBackend 管一切有 tokenizer.json 的模型，SentencePieceBackend 只加 .model 文件加载层。
- mistral 特化独立成文件而非塞进 TokenizersBackend，因为 mistral-common 的语义根本不同（special token 永不被直接编码，batch-88-part-1 甄别），值得隔离。

## ⑥ 新人提示

读码顺序：基座 `PreTrainedTokenizerBase.__call__`/`_add_special_token` → tokenization_python.PythonBackend._tokenize（看纯 Python 分词的最小实现）→ TokenizersBackend.convert_to_native_format（看四路归一）。坑：①`tokenizer.is_fast` 仍存在（基座属性），但本版它更多表示"是否 Rust 后端"而非"是否存在独立的慢速孪生类"；②offset mapping/word_ids 只在 TokenizersBackend 路线可靠，PythonBackend 多数未实现；③调试词表用 `tokenizer.backend_tokenizer`（直通 Rust 对象）或 `tokenizer.get_vocab()`；④新模型家族要选后端：有 tokenizer.json 无脑 TokenizersBackend，只有原生 .model 才碰 SentencePieceBackend；⑤`generate_merges` 重建的 merges 顺序对评分敏感，复刻旧分词行为时对照 `vocab_scores` 参数。
