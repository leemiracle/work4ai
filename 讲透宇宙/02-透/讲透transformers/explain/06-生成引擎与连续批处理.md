# 06 生成引擎（generation/utils.py 与 continuous_batching/）

## ① 角色定位

`src/transformers/generation/` 是自回归解码的心脏，2026 版最大的结构性变化是 `GenerationMixin`（utils.py L485）**直接继承 `ContinuousMixin`**——即"传统逐批 generate"与"vLLM 式常驻连续批处理服务"合并为一条继承链。目录分两层：`utils.py`（4420 行）承载经典 generate 循环（贪心/采样/beam/辅助解码四模式）；`continuous_batching/` 子包（11 个文件）是一座内嵌推理引擎——分页 KV cache、调度器、后台线程、CUDA graph 预热一应俱全。配套的 `stopping_criteria.py` 与 `logits_process.py` 是可组合的停止条件与 logits 加工管线，两套体系共用。

## ③ 外部连接

- `GenerationMixin(ContinuousMixin)` 这条继承边（L485）是图谱里 generation/utils.py 与 continuous_batching/continuous_api.py 的关键 inherits 边——传统模型类（如 LlamaForCausalLM）经 PreTrainedModel→（可选混入 GenerationMixin）一步就获得连续批处理能力。
- `ProtoPretrainedModel`（L73）用结构化 duck-typing（只要求 config/device/dtype 等）解掉"引擎要 import 模型基类、模型基类又 import 引擎"的环；asyncio 事件循环经 `call_soon_threadsafe` 与生成线程对接（batch-87-part-2）。
- `GenerationConfig` 与模型 config 的分工：生成参数在 config `__init__` 时被 pop 走，`adjust_generation_fn` 找不到独立 generation_config 才回落 config.json（utils.py L555-560）。
- `PagedAttentionCache` docstring（L93-99）官方致谢 vLLM PR #11382 与 Jenga 论文（arXiv 2503.18292）——sector 机制系社区成果移植。

## ④ 数据流

经典路径 `model.generate(input_ids, do_sample=True)`：①`generate`（L2557）合并 GenerationConfig/kwargs，校验模型类型；②组装 `LogitsProcessorList`（按 config 顺序叠 RepetitionPenalty/Temperature/TopK/TopP/MinP…）与 `StoppingCriteriaList`（MaxLength+Eos+可选 StopString/MaxTime/Confidence）；③`_prefill`（L4238）处理首步：多模态输入、从既有 cache 续跑时的输入切片、`inputs_embeds` 分支；④`_sample`（L3091）自回归循环：forward→logits_process 流水线加工→candidate 选 token→stopping_criteria 判停→`StopCheck`/`DeferredStopCheck` 决定本步中断还是收尾统一中断。连续批处理路径 `with model.continuous_batching_context_manager() as mgr:`：①`init_continuous_batching`（L1239）建/复用 `ContinuousBatchingManager`（缓存于 `_cached_continuous_batching_manager`，复用前 `switch_to_cb_friendly_attn`）；②`add_request`（L895）投递请求，Scheduler 决定 prefill/decode 混排（FIFO 或 PrefillFirst）；③`ContinuousBatchProcessor`（L298）在后台线程每步重组 batch：完成的请求出列、新请求插队、`PagedAttentionCache` 按 page/block/sector 分配 KV；④输出经 `OutputRouter` 路由回流。

## ⑤ 设计决策（含勘误）

- **勘误一：连续批处理不是 vLLM 的调用包装，而是原生实现**。`PagedAttentionCache`（cache.py L71）自管一整块 flat tensor，三级分配：page（层内页）→block（请求块）→sector（注意力类型区）。对 sliding/full 混合层模型，两类 allocator 块大小不同，用 LCM 定 sector 尺寸（docstring 以 4 层 [sliding,full,sliding,sliding] 演算：1 个 sliding block = 3 个 full block）；物理 tensor 头两个 sector 是永不分配的 trash sector，留给 padding token。灵感注明来自 vLLM #11382 与 Jenga，但代码全在仓内。
- **勘误二：`generate()` 不再是唯一入口**。`ContinuousMixin` 三入口显式写进 docstring（L1231-1237）且"改任一入口须同步另两个"——`generate_batch` 只是 context manager 的便捷皮。高频服务场景应直接用 manager 复用（cached manager + `destroy_cached_continuous_batching_manager` L1314 释放）。
- `_prefill` 从主循环拆出是近期手术：辅助解码中 assistant 连续多次 generate 同一批输入，`is_first_iteration` 参数（L4244）就是为这条复用路径打的补丁。
- `StopCheck`/`DeferredStopCheck` 的区分消除了"某序列中途停导致整批提前断"的经典 bug：单请求停止只标记，步末统一收割。
- CI 视角：继承 GenerationMixin 会自动纳入 generate 相关测试（类 docstring L489-491 明示），BarkModel 这类自定义 generate 接口不兼容的模型**不应**混入——文档举了反例。

## ⑥ 新人提示

读码顺序：`generate`（L2557）主干 → `_sample` 循环体（盯 logits_process 与 stopping_criteria 的插入点）→ `ContinuousMixin` 三入口 → `ContinuousBatchingManager.add_request` → `PagedAttentionCache` docstring（本目录最好的架构文档）。坑：①调试采样差异先对比 `LogitsProcessorList` 的实际顺序（`_get_logits_processor` 内序即生效序），warper 与 processor 混排敏感；②连续批处理的注意力实现会被 `switch_to_cb_friendly_attn` 换掉，行为与普通 forward 可能不同，对照实验要显式固定 attn_implementation；③sector 机制意味着 KV 显存上限在 `ContinuousBatchingConfig` 里预算，OOM 先调小页配置而非 batch；④beam search 路径与 continuous batching 互不兼容，别在 manager 里塞 beam 请求；⑤`_prefill` 的输入切片规则（cache 续跑时 input_ids 可能是全序列或仅新增 token，靠 attention_mask 长度判别，L4257-4260 注释）是复用 KV 调试的必读段。
