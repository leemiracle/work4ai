## Introduction

 This document covers transaction management in the OpenHarmony Distributed Relational Database Management System (RDBMS). Transactions provide atomicity, consistency, isolation, and durability (ACID) guarantees, allowing applications to execute multiple operations as a single unit that either completely succeeds or completely fails.

 For information about the core store implementation, see [RdbStoreImpl](https://deepwiki.com/openharmony/distributeddatamgr_relational_store/2.1-rdbstoreimpl). For information about SQL query building, see [SQL Query Building](https://deepwiki.com/openharmony/distributeddatamgr_relational_store/2.4-sql-query-building).

 The system provides two approaches to start a transaction:

 
 - `BeginTransaction()` - Starts a transaction and returns a status code.
 - `BeginTrans()` - Starts a transaction and returns both a status code and a transaction ID.
 
 The `RollBack()` and `Commit()` methods have two variants:

 
 - Without a transaction ID - Operates on the current transaction.
 - With a transaction ID - Operates on a specific transaction identified by the ID.
 
 The `IsInTransaction()` method checks if a transaction is active.

 The `CreateTransaction(int32_t type)` method creates a Transaction object, providing an object-oriented way to work with transactions.

### Beginning a Transaction

 A transaction begins when one of the begin methods is called. The system executes the `BEGIN_TRANSACTION_SQL` statement and tracks the transaction.

 
### Performing Operations

 Operations performed during an active transaction using methods like `Insert`, `Update`, or `Delete` are executed within the transaction's context. If the transaction is committed, these changes become permanent. If rolled back, all changes are discarded.

 
### Committing a Transaction

 When `Commit()` is called, the system executes the `COMMIT_TRANSACTION_SQL` statement to permanently apply all changes made during the transaction.

 
### Rolling Back a Transaction

 When `RollBack()` is called, the system executes the `ROLLBACK_TRANSACTION_SQL` statement to discard all changes made during the transaction.

## Transaction Performance Considerations

 
 - Keep transactions as short as possible to minimize lock contention
 - Group related operations into a single transaction to ensure data consistency
 - Use transaction IDs when working with multiple concurrent transactions
 - Consider using the DEFERRED transaction type for read-heavy workloads
