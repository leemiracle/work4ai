  The JavaScript Store Helper provides a set of utility functions for creating, accessing, and managing relational database stores from JavaScript applications in OpenHarmony. It serves as the entry point for JavaScript applications to interact with the relational database system, offering methods to create new database instances, delete existing ones, and check for advanced feature support.

 For information about the NAPI RdbStore implementation that handles actual database operations, see [NAPI RdbStore](https://deepwiki.com/openharmony/distributeddatamgr_relational_store/6.1-napi-rdbstore).

 
## Architecture

 The JavaScript Store Helper sits in the JavaScript API layer of the distributed relational database management system and acts as a bridge between JavaScript applications and the native C++ implementation. It provides the necessary interfaces for creating and managing database instances.

## Key Functions

 The JavaScript Store Helper provides four main functions that are exposed to JavaScript applications:

 
 - `getRdbStore` - Creates or opens a relational database store
 - `deleteRdbStore` - Deletes a relational database store
 - `isVectorSupported` - Checks if vector database is supported
 - `isTokenizerSupported` - Checks if a specific tokenizer is supported

### Creating RDB Stores

 The `getRdbStore` function creates a new RDB store or opens an existing one. It accepts a context parameter and a configuration object.

 The function has both asynchronous and synchronous versions:

 
 - `getRdbStore(context, config)`: Asynchronous version
 - `getRdbStoreSync(context, config)`: Synchronous version
 
 
#### Parameters

 
| Parameter | Type | Description |
|---|---|---|
| context | Context | Application context providing access to database directory |
| config | StoreConfig | Configuration for the RDB store including name, security level, etc. |

 
#### Configuration Options

 
| Property | Type | Description |
|---|---|---|
| name | string | The name of the database |
| securityLevel | SecurityLevel | The security level of the database (S1, S2, S3, S4) |
| encrypt | boolean | Whether to encrypt the database |
| persistWal | boolean | Whether to persist Write-Ahead Logging (WAL) |
| isReadOnly | boolean | Whether the database is read-only |
| tokenizer | Tokenizer | Tokenizer used for full-text searches |
| isSearchable | boolean | Whether the database is searchable |
| rootDir | string | Root directory for the database (optional) |

### Deleting RDB Stores

 The `deleteRdbStore` function deletes an existing RDB store. Like `getRdbStore`, it also has both asynchronous and synchronous versions.

 
#### Parameters

 
| Parameter | Type | Description |
|---|---|---|
| context | Context | Application context providing access to database directory |
| config | StoreConfig or string | Configuration object or database name |

 When the second parameter is a string, it represents the database name, and the function will delete both SQLite and vector database files with that name.

## Context Handling

 The JavaScript Store Helper requires a context parameter to determine the appropriate location for database files and to check application permissions. The context is obtained from the JavaScript application environment.

 The helper uses the `JSAbility` class to extract the context from JavaScript and create a `Context` object that provides:

 
 - Database directory path
 - Bundle name
 - Module name
 - Permission information
 - System application status
 
 For system applications, additional capabilities are available such as accessing system databases.

## Error Handling

 The JavaScript Store Helper implements comprehensive error handling to provide clear feedback when operations fail. Errors are mapped from native error codes to JavaScript error codes with descriptive messages.

| Error Code | Description |

| 14800010 | Invalid file path |
| 14800000 | Inner error |
| 14800020 | Invalid secret key |
| 801 | Capability not supported |

 Error handling in the JavaScript Store Helper implements multiple layers of validation:

 
 - Input parameter validation
 - Path validation
 - Configuration validation
 - Encryption key validation
 - Operation-specific validation

## Best Practices

 
 - **Use Async Operations**: For better performance and to avoid blocking the main thread, use asynchronous versions of the API when possible.
 - **Error Handling**: Always implement try-catch blocks when using the API to handle potential errors gracefully.
 - **Database Security**: Choose the appropriate security level based on your data sensitivity requirements:

 
 - S1: Basic security
 - S2: Enhanced security
 - S3: High security
 - S4: Highest security
 - **Resource Management**: Close database connections when they are no longer needed to free up resources.
 - **Path Handling**: Avoid using absolute paths; let the system determine the appropriate database location based on the context.
 - **Version Management**: Set and maintain database versions to handle schema upgrades properly.

## Implementation Details

 The JavaScript Store Helper is implemented using the Node-API (NAPI) to bridge JavaScript and C++ code. The implementation includes:

 
 - A `DefaultOpenCallback` class that implements the `RdbOpenCallback` interface to handle database creation and upgrades.
 - Functions to convert between JavaScript and C++ data types, particularly for context and configuration parameters.
 - Support for both synchronous and asynchronous operation patterns.
 - Comprehensive error handling to convert native errors to JavaScript-friendly errors.
 
 The helper works closely with the RdbHelper native class to perform actual database operations while providing a JavaScript-friendly interface.
