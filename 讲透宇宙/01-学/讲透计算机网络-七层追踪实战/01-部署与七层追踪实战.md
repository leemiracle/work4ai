## 1. 部署方案：受限环境倒逼出的"纯 Python 观测栈"

**环境侦察结论**（决定一切设计）：

| 探测项 | 结果 | 对策 |
|---|---|---|
| 容器内 tcpdump/ethtool/openssl/ping/iptables | 全部 MISSING（yum 源不通，容器仅内网白名单） | **自写纯标准库工具** |
| python3 | 3.11.6 + `ssl`(OpenSSL 3.0.12) 可用 | TLS 用 python `ssl` 模块 |
| NET_RAW / NET_ADMIN 权限 | 可加（docker `--cap-add`） | AF_PACKET 抓包 + ioctl 探测可行 |
| 容器网络 | bridge 模式 172.17.0.4/16，网关 172.17.0.1 | veth/docker0/NAT 全可观测 |

这个限制反而是**最好的课程设计**：买不来 tcpdump，就只能把 tcpdump 的原理亲手写一遍。

**部署物**（`/root/luowz/netlab/`，容器 `luowz-netlab`，代码源头在本地仓 `remote/netlab/`）：

| 组件 | 职责 | 替代的工业工具 |
|---|---|---|
| `sniffer.py` | AF_PACKET 抓包，逐字节解析 Eth/ARP/IP/ICMP/TCP/UDP，JSONL+pcap 双输出 | tcpdump |
| `l1probe.py` | /sys + ioctl(SIOCETHTOOL) 链路事实 | ethtool |
| `myping.py` | raw ICMP socket 自造 echo request | ping |
| `mytraceroute.py` | TTL 递增 + ICMP time-exceeded | traceroute |
| `flows.py` | JSONL → TCP 会话时间线（L5 视图） | tshark conversations |
| `tracehttp.py` | 被追踪的 L7 应用（多端点+JSONL 访问日志） | nginx+access log |
| `snapshot7.sh` | 七层证据一键快照（L1–L7 各一文件） | — |
| `start/stop_stack.sh` | 双接口抓包器+服务编排 | — |

**网络拓扑**（全链路可观测的真实环境）：

```
宿主机(10.44.11.13)
 ├─ curl 127.0.0.1:8188 ──→ docker-proxy ──→ veth ──→ luowz-netlab eth0 (172.17.0.4:8080)
```

## 2. 流量剧本（为了让七层都有真数据）

| # | 动作 | 目标层 |
|---|---|---|
| T1–T3 | 宿主侧 GET / · POST /api/login(带密码) · GET /files/hello.txt | 全栈（eth0 路径） |
| T4/T5 | keep-alive 两请求一连接 vs `Connection: close` 每请求一连接 | L5 |
| T6 | 容器内 curl 127.0.0.1:8080 | lo 接口对照 |
| T7/T8 | myping 网关 · mytraceroute 跨网段 | L3 |
| T9 | getaddrinfo('open.bigmodel.cn') | L7(DNS)→L4(UDP) |
| T10 | luowz-dev 直连 172.17.0.4:8080 | L2/L3 横向路径（安全轮素材） |

T4 的 keep-alive 实测（curl `-w` 字段，教科书级对比）：

```
两个 URL 一次 curl 进程:  第1个请求 num_connects=1 time_connect=0.000083s
                          第2个请求 num_connects=0  ← 连接复用，省掉整个三次握手
Connection: close 各请求: num_connects=1 ×2        ← 每次都重新握手+挥手
```

## 3. 七层逐层数据详解

### L1 物理层（data-r1/r1_L1.txt）

直觉：物理层回答"链路存在吗、多快、错了多少"。本容器的"物理层"是 **veth 虚拟以太网对**——一端在容器网络命名空间，另一端挂在宿主 docker0 网桥，"传输介质"是内核内存队列。

```
speed=10000(Mb/s)  duplex=full   ← veth 名义值（10G 全双工）
carrier=1  operstate=up          ← 载波在、状态机 UP
rx_packets=104 tx_packets=88 rx_errors=0 collisions=0   ← 收发计数与零错误
对照 lo: mtu=65536, rx_bytes==tx_bytes 恒等(1293==1293) ← 回环"发即收"
```

踩坑实录：`ioctl(SIOCETHTOOL, GLINK)` 在 veth 上返回 `EOPNOTSUPP`——虚拟接口不实现全部 ethtool 接口；数据改从 `/sys/class/net/eth0/` 取（内核导出的事实表，零权限依赖）。

### L2 数据链路层（r1_L2.txt）

直觉：同一网段内"用 MAC 地址说话"。谁要把 IP 包交给谁，先得问 ARP。

实测抓到**一段完整的 ARP 双向对话**（42 字节小帧，教学金料）：

```
172.17.0.4 → 广播: request "172.17.0.4 is-at 02:42:ac:11:00:04" 问 172.17.0.1
172.17.0.1 → .4  : request "172.17.0.1 is-at 02:42:b3:d8:21:5c" 问 172.17.0.4   ← 网关借机反问
172.17.0.4 → .1  : reply   "我是 .4，MAC 02:42:ac:11:00:04"
172.17.0.1 → .4  : reply   "我是 .1，MAC 02:42:b3:d8:21:5c"
```

细节都是知识点：request 的 target MAC 填 `00:00:00:00:00:00`（还不知道才问）；容器 MAC `02:42:ac:11:00:04` = `02:42`（本地管理位）+ `ac:11:00:04`（172.17.0.4 的十六进制！docker 按 IP 派生 MAC，一眼可读）；`ip neigh` 的 `REACHABLE` 状态是内核邻居状态机的确认态。

### L3 网络层（r1_L3.txt）

路由表两条（默认路由 + 直连网段）：

```
default via 172.17.0.1 dev eth0        ← 出网段全找网关
172.17.0.0/16 dev eth0 proto kernel scope link src 172.17.0.4
```

**自写 ping 实测**（构造 ICMP type=8，rtt 0.02–0.10ms——veth 到宿主桥，亚毫秒合理）：

```
seq=1 reply from 172.17.0.1: ttl=64 rtt=0.10ms payload='netlab-l3-ping'
```

**自写 traceroute 到宿主内网 IP 10.44.11.13**：第一跳直接"到达"——因为网关 172.17.0.1 就是宿主机本体的另一个身份（一台机器多个 IP，路由意义上是同一跳）。这是理解"路由跳=三层设备"而非"物理机"的好例子。

**DNS 115ms 拆解案**（数据不会说谎，但要交叉验证）：`getaddrinfo` 名义耗时 115ms，抓包揭示真相——

```
resolv.conf 有 4 个 nameserver: 10.42.96.10 / 10.10.100.13 / 223.5.5.5 / 114.114.114.114
抓包: 查询→10.42.96.10(有回)  查询→10.10.100.13  查询→223.5.5.5(成功返回)
```

glibc resolver 对多 nameserver 的尝试策略 + 内网 DNS 对外网域名的表现共同构成 115ms。**最初 `head -3` 只看到两个内网 DNS 时，抓包与配置"矛盾"，翻全文才解释通**——多问一句、交叉验证，是读网络数据的第一美德。

### L4 传输层（r1_L4.txt）

三次握手逐字段（sniffer 实录，每个字段都可讲一课）：

```
[SYN]     seq=735774302 win=64240 mss=1460   ← 客户端：初始序号(随机防猜测)、通告窗口、MSS
[SYN/ACK] seq=3501541715 ack=735774303 win=65160 mss=1460 ← 服务端：自己的 ISN + ACK=对端ISN+1
[ACK]     seq=735774303 ack=3501541716 win=502 ← 完成握手；注意窗口已从 64240 收缩
```

三个观察点：① `ack = 对端 seq + 1` 的"下一个期望字节"语义贯穿全程；② 握手时窗口 64240（含窗口缩放选项的初始值）→ 数据期 502（应用消费速度的实时反馈=流控）；③ `mss=1460` 恰好 = MTU 1500 − IP 头 20 − TCP 头 20，L1 的 MTU 决定 L4 的段大小上限——层间耦合的活例子。

### L5 会话层（r1_L5.txt，flows.py 输出）

一条完整会话的 12 包（1.5ms 一生）：三次握手 → 3 组 PSH 数据往返 → 四次挥手（FIN×2 + 各自 ACK）。TLS 轮（r2）同一视图仍 17 包——**L5 的连接生命周期对 L6 是否加密完全透明**，加密只发生在载荷字节上。

### L6 表示层（r1_L6.txt）

三个实验：① gzip 内容编码——同一页面 identity 616B vs gzip 后传输字节数对比（`Content-Encoding: gzip`，"表示"变了、语义没变）；② 网络字节序——sniffer 里所有 `!H/!I` 结构体格式=大端，x86 是小端，解析必须显式转换（端口 8080=0x1F90：线上字节 `1f 90`，本机内存 `90 1f`）；③ r1 无加密——payload ASCII 直接可读（这正是 03 安全文档 A1 的靶子）。

### L7 应用层（r1_L7.txt + access.log）

双视角互证：应用侧 JSONL access.log（client/method/path/headers/body/resp_code/rt_ms）×网络侧 payload 还原（`POST /api/login HTTP/1.1..Host:...user=alice&pass=S3cret!`）。**同一个请求在两份证据里都能找到**——应用日志说"发生了什么"，抓包说"字节怎么过的线"。

## 4. 工程坑实录（本轮最有学习价值的部分）

| # | 现象 | 根因 | 修复 | 层级归属 |
|---|---|---|---|---|
| 1 | myping 报超时，但 sniffer 抓到 reply 0.2ms 就回来了 | Linux raw socket 接收数据**含 20 字节 IP 头**（man 7 raw），我却从 data[0] 按 ICMP 解析，读到 0x45（IP 版本+IHL） | 剥 `ihl*4` 再解 ICMP | L3 |
| 2 | jsonl/pcap 0 字节但 sniffer"正常" | Python 文件块缓冲，进程不退出不落盘；第一轮靠 kill→close→flush 的巧合 | 每包显式 `flush()` | 通用 |
| 3 | `kill -INT` 杀不死 nohup 后台 sniffer | POSIX：后台作业对 SIGINT 置 SIG_IGN 且被子进程继承 | 注册 SIGTERM handler 优雅退出 | 通用 |
| 4 | guard.sh 拦截 `docker run --rm` | 护栏正则把 `run --rm` 误判为 `docker rm` 危险操作 | 建 netlab.sh 封装、不带 `--rm` | 工程 |
| 5 | 路径遍历"失败"实为数错深度 | `/root/luowz/netlab/files` 距 `/` 有 4 层，3 个 `../` 只到 `/root` | 数准层级（安全轮详解） | L7 |

坑 1 的教训值得放大：**"工具说超时"和"包没回来"是两回事**——sniffer 在 L2 的客观观测纠正了我应用层代码的主观判断。交叉验证不是口号。
