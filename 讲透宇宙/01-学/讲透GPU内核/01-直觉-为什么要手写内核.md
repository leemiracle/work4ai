# 一 · 直觉：为什么要手写内核

## 1.1 PyTorch 已经很好了，问题在哪

`y = F.gelu(F.linear(x, W))` 这样一行代码，在 GPU 上实际发生了什么？**两个 kernel、一次中间张量落地**：

1. launch `linear` kernel → 写出中间结果 `h`（几 MB 到几 GB 的显存写）；
2. launch `gelu` kernel → 把 `h` 读回来、逐元素变换、再写出 `y`。

两个问题在 LLM 的算力尺度下变成账面数字：

- **访存浪费**：中间结果写了又读，纯粹为了配合"一个 kernel 干一件事"的抽象。当每个元素只做一次乘加（GELU）时，**读写中间张量的字节是有效计算的几十倍**——算力闲置，带宽打满；
- **launch 开销**：每个 kernel 启动有微秒级固定成本，小算子串联时（experts 路由、RoPE、norm 这种碎活），GPU 在"等下一个 kernel 上车"。

**手写内核的第一动机不是"写得更快"，是"把该在一起的放在一起"**——融合（fusion）。

## 1.2 融合的本质：让数据在寄存器里过完一生

硬件的事实层级：寄存器（~ns，每 SM 私有）→ 共享内存/一级缓存（~10ns）→ HBM 显存（~100ns+，全局共享）。PyTorch 的算子边界=HBM 边界；手写 kernel 的自由=**让 `h[i]` 从寄存器直接进 GELU，从未见过 HBM**。

FlashAttention 是这个直觉的封神一战：attention 朴素实现要把 $s \times s$ 的注意力分数矩阵物化到 HBM（$s=4096$ 时每头 100MB 级），FA 用 online softmax+tiling 让分数矩阵**只在寄存器/共享内存里存在**——不是把计算变快，是把搬运变没。I/O 复杂度从 $O(s^2)$ 降到 $O(s)$，长上下文的 attention 从"显存爆炸"变"可算"。

## 1.3 第二动机：算子的形状是个性化需求

框架算子服务通用形状（大矩阵、规整 batch），但 LLM 的真实形状千奇百怪：

- **decode 的 GEMV**：batch=1 时"矩阵乘"退化成向量乘，通用 GEMM kernel 的 tiling 全部落空——需要专门的 skinny kernel；
- **MoE 分组 GEMM**：64 个专家、每组 token 数运行时才知道（路由决定）——静态图假设全部作废（[讲透DeepGEMM](../../02-透/讲透DeepGEMM/README.md)：FP8 分组 GEMM 就是为这个形状而生）；
- **变长序列打包**：连续批处理下同一 batch 内序列长度不一，attention 要按每条真实长度掩码——需要"懂 batch 语义"的 kernel 而不是纯数学库。

**框架的通用性就是你要付的税**；手写 kernel 是退税申报。

## 1.4 第三动机：硬件代际的先发红利

每代新硬件都重新洗牌：Hopper 的 TMA/warp specialization、Blackwell 的 tcgen05 张量核心——编译器跟上的窗口期以年计，**手写 kernel 是吃到新硬件红利的唯一姿势**（TensorRT-LLM 对 Blackwell 的适配领先通用框架数月就是这个机理）。国产卡更是如此：[讲透TIRx](../../02-透/讲透TIRx/README.md)（沐曦 kernel 库）整仓的存在理由就是"自家硬件自家 kernel 先行"。

## 1.5 本章心智模型

> 手写内核 = 用"数据放对地方"（层级）+ "该在一起的在一起"（融合）+ "形状专属"（特化）+ "硬件先发"（代际）四件事，把通用算子抽象漏掉的物理赢回来。
