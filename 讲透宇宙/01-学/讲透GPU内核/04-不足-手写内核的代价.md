# 四 · 不足：手写内核的代价

## 4.1 数值一致性：ULP 的原罪

03 幕模拟器的 `np.allclose` 给人安全感，但真实世界：**浮点加法不结合**——tiling 改变归约顺序，结果在 ULP（最低有效位）级漂移。后果链条：

- 一次前向没问题；训练里百万步累积，ULP 漂移可放大为 loss 曲线分叉——"kernel 数学等价"≠"训练等价"；
- 产业界的应对已经内卷到位级断言：[讲透TileKernels](../../02-透/讲透TileKernels/README.md) 精读记录的 `torch.equal` 位级断言（融合与不融合产出逐位一致才算过关）——**融合的"零数值代价"从宣传语升格为证明义务**；
- FP8/FP4 量化把这个问题再放大一个数量级（缩放因子per-128 块的排布不同，误差路径完全不同）。

## 4.2 平台特异性：一次编写，处处重写

kernel 的性能灵魂=对具体硬件资源排布的精算（shared memory 容量、warp 调度、张量核心形状、TMA）：

- A100 最优 tile 在 H100 上未必最优（代际资源比变化），Blackwell 的 tcgen05 更是换了编程范式；
- Triton 的 autotune 缓解但不消除——搜索空间是离散的，跨代硬件常要改候选集；
- 国产卡的更深一层：指令集语义差异（详见 [讲透TIRx](../../02-透/讲透TIRx/README.md) 沐曦栈、[讲透FlagGems](../../03-查/讲透FlagGems/deepwiki/INDEX.md) 异构算子库）——"写一次 kernel"在异构现实里是一厢情愿。

## 4.3 调试与观测：黑盒里的黑盒

- kernel 内部不可断点（printf 调试毁性能语义、compute sanitizer 慢一个数量级）；
- 性能归因要跨层拼图：nsight 看占有率/带宽、Nsight Compute 看指令 stall、nccl log 看通信重叠——**一个"kernel 慢"的问题可能根源在 launch 间隙、缓存抖动或 grid 排布**；
- 经验断层：知道怎么写与知道为什么慢之间隔着 profile 工具链的深水区（本机 skill `hpc-perf` 的 TMAM 四象限/roofline 定位法是这个断层上的桥）。

## 4.4 维护税与正确性陷阱

- **专家盲区**：kernel 作者通常不懂上层框架语义（vLLM 的 batch 维度语义、SGLang 的 prefix 共享），集成期冒出形状/流同步 bug；反过来框架工程师读不懂 kernel——两不管地带最长情；
- **静默错误**：shared memory 越界在部分架构上不崩只错（返回错误数据）——[讲透DeepGEMM](../../02-透/讲透DeepGEMM/README.md) 精讲里"断言护栏"的存在（越界早死优于错数据晚死）就是对这个陷阱的制度化防御；
- **版本漂移**：CUDA 版本升级改变默认编译行为，去年最快的 kernel 今年悄悄变慢——没有回归 benchmark 的 kernel 迟早背叛你。

## 4.5 判据：什么时候不该手写

- **算子还在变**（模型结构迭代期）——手写固化得太早，白写；
- **shape 长尾多样**——为每个形状手写不经济，等编译器（TVM/Triton autotune 类，见 [讲透TVM](../../03-查/讲透TVM/deepwiki/INDEX.md)）或先 torch.compile 榨一波；
- **带宽口离算力口还远**（强度远低于屋脊）——先做融合/量化这种结构性优化，手写微调收益排在后。
