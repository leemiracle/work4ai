# 02 · 中间件栈全景：11 个环的职责与顺序语义

## 角色定位

`agents/middlewares/` 目录 11 个文件 + langchain 内置两件（SummarizationMiddleware、TodoListMiddleware 基类）构成 lead agent 的全部横切面。每个中间件都是 `AgentMiddleware` 子类，靠四个钩子族介入循环：`before_agent/after_agent`（轮次边界）、`before_model/after_model`（每次 LLM 调用前后）、`wrap_model_call`（包住模型调用可改写消息）、`wrap_tool_call`（包住工具执行可拦截/兜底）。装配顺序在 `lead_agent/agent.py:207-254`，顺序语义的唯一权威是 agent.py:197-206 的十行注释块：ThreadData 在 Sandbox 之前（保证 thread_id 可用）、Summarization 尽早（先压缩再处理）、Clarification 恒最后（模型调用全部结束后再拦截澄清）。

## 内部结构

按装配序逐环：

1. **ThreadDataMiddleware**（thread_data_middleware.py:17）：中间件链第 1 环。`before_agent` 从 runtime.context 取 thread_id（thread_data_middleware.py:74），lazy_init=True 时只计算 workspace/uploads/outputs 三路径不建目录（thread_data_middleware.py:78-80），路径写进 `thread_data` 状态供全链消费。
2. **UploadsMiddleware**（uploads_middleware.py:23）：插在链表 1 号位（tool_error_handling_middleware.py:86 `insert(1, ...)`）。从 HumanMessage 的 `additional_kwargs.files` 提取本轮新文件（uploads_middleware.py:96），文件名过 `Path(name).name` 穿越校验（uploads_middleware.py:105）+ 磁盘存在性复核（uploads_middleware.py:107）；历史文件扫 uploads 目录补齐（uploads_middleware.py:159）；拼 `<uploaded_files>` 块**原位替换**最后一条人类消息（uploads_middleware.py:193-199），保留原 additional_kwargs 供前端读流。
3. **SandboxMiddleware**（sandbox/middleware.py:21，住在 sandbox/ 目录）：lazy_init=True 时 before_agent 直接放行（middleware.py:54-55），真正的获取动作由工具层的 `ensure_sandbox_initialized` 惰性触发；`after_agent` 每轮结束调用 provider.release（middleware.py:71）——对 local 是空操作、对 aio 是"停入温池"。
4. **DanglingToolCallMiddleware**（dangling_tool_call_middleware.py:28）：修补用户打断造成的悬空 tool_calls。精妙点在选 `wrap_model_call` 而非 before_model：before_model + add_messages reducer 只能追加到消息列表尾部，无法在悬空 AIMessage 的正确位置插占位 ToolMessage（dangling_tool_call_middleware.py:11-13 docstring 钉版）；实现上先收集全部 ToolMessage id（:44-47），再在缺口处插入 `status="error"` 的合成消息（:76-83），最后 `request.override(messages=patched)`（:98）。
5. **ToolErrorHandlingMiddleware**（tool_error_handling_middleware.py:19）：同步 `wrap_tool_call`（:38）与异步 `awrap_tool_call`（:53）成对把工具异常转成 error ToolMessage，细节 500 字符截断（:26-27），`GraphBubbleUp` 原样放行保住 interrupt/_resume 控制流信号（:45-47）。本文件同时是共享基座工厂：`_build_runtime_middlewares`（:68）产出 ThreadData+Sandbox 基础两项（:78-81），`build_lead_runtime_middlewares`（:97）加 Uploads+Dangling，`build_subagent_runtime_middlewares`（:106）两者皆不加——主/子 agent 差异在此单点定义。
6. **SummarizationMiddleware**（langchain 内置，agent.py:40 工厂）：接近 token 上限时保留近期消息、摘要旧消息；模型未配置时走 thinking 关闭的轻量模型（agent.py:64）。
7. **TodoMiddleware**（todo_middleware.py:47）：继承 langchain TodoListMiddleware 并补上"上下文丢失检测"——write_todos 调用被摘要截断后，`before_model` 检测 state 有 todos 但消息里已无 write_todos 痕迹（todo_middleware.py:63-68），注入 `name="todo_reminder"` 的 HumanMessage（:79-91），防重复靠 `_reminder_in_messages`（:29）。
8. **TitleMiddleware**（title_middleware.py:19）：首轮完整交换（恰 1 条 human + ≥1 条 ai，:40-44）后用轻量模型生成标题（:60），失败回退用户消息前 50 字符（:78-81）；结果写 `title` 状态由 checkpointer 持久化（:91）。
9. **MemoryMiddleware**（memory_middleware.py:86）：`after_agent` 把过滤后的对话交给 30s 防抖队列（memory_middleware.py:146-147），详见 04 篇。
10. **ViewImageMiddleware**（view_image_middleware.py:19）：仅视觉模型装配。`before_model` 检查最后一条 AIMessage 含 view_image 调用且全部落定（:61、:92），把 viewed_images 状态里的 base64 组装成带 image_url 块的 HumanMessage 注入（:119-124）；防重复注入靠探测固定标记文本（:160）。
11. **SubagentLimitMiddleware**（subagent_limit_middleware.py:24）：after_model 截断超额并行 task 调用——只留前 max_concurrent 个（:54-60），`model_copy(update=)` 同 id 原位替换 AIMessage（:66），限额硬钳在 [2,4]（:15-21）。
12. **LoopDetectionMiddleware**（loop_detection_middleware.py:76）：P0 安全环。对工具调用集（名+参数）排序后 md5 哈希消除顺序噪声（:36-61），threading.Lock + OrderedDict LRU（max 100 线程，:102-105）按线程隔离滑窗（20 次，:156）；同指纹 3 次注入警告 SystemMessage（:173-186）、5 次直接剥掉 tool_calls 强制产出文本（:161-171、:199-203）。
13. **ClarificationMiddleware**（clarification_middleware.py:20）：链尾。wrap_tool_call 拦截 `ask_clarification`（:147），把参数格式化成带类型图标的用户消息（:61-89），返回 `Command(update=..., goto=END)`（:126-129）中断运行等用户回答——工具本体是 return_direct 空壳（clarification_tool.py:6），执行语义全部上移到中间件层。

## 外部连接

栈的装配消费者有三：make_lead_agent（主链）、`subagents/executor.py:172`（子链复用基座）、`scripts/tool-error-degradation-detection.sh:38`（直接 import `_build_middlewares` 验证降级）。状态契约统一挂在 `thread_state.py:48-55` 的 ThreadState：`viewed_images` 有专用 reducer 且空 dict 语义为清空（thread_state.py:31-45），`artifacts` 用 dict.fromkeys 去重保序（:21-28）。各中间件的 State 类（如 ThreadDataMiddlewareState，thread_data_middleware.py:11）都声明"Compatible with ThreadState"，靠 TypedDict 结构兼容而非继承复用。

## 数据流

一轮对话流经中间件两次：进入时 before_agent（ThreadData 算路径 → Uploads 改写最后一条人类消息）→ before_model（Todo 提醒 → ViewImage 注图）→ wrap_model_call（Dangling 修补消息表）→ 模型 → after_model（SubagentLimit 截断 → LoopDetection 哈希记账）→ wrap_tool_call（ToolError 兜底 → Clarification 拦截）→ after_agent（Sandbox release → Memory 入队 → Title 生成）。这个"装配序 ≠ 执行序"的错位是读代码最大陷阱：链表顺序只决定同类钩子的嵌套顺序，异类钩子由 langchain 的固定生命周期调度。

## 设计决策

1. **同步/异步成对实现是硬规范**：所有自定义钩子都写 sync+async 双版本（clarification_middleware.py:132/154 等），缺一个就在对应运行模式下静默失效。
2. **消息修补用 override 而非 append**：Dangling 与 Uploads 都面临"改历史而非加新消息"的需求，前者用 wrap_model_call+override，后者借 before_agent 返回整表替换——两条路线都绕开 add_messages 只会追加的 reducer 语义。
3. **拦截型能力放中间件、工具只做壳**：ask_clarification 与 write_todos 的执行体都在中间件/框架层，工具 schema 仅面向 LLM 声明，是 LangGraph human-in-the-loop 的标准拆法。
4. **限额靠截断不靠 prompt**：SubagentLimitMiddleware 注释直言"比 prompt 限制更可靠"（subagent_limit_middleware.py:29）。

## 新人提示

- 排查"工具报错但对话死了"先查 ToolErrorHandlingMiddleware 是否在链里（检测脚本一键验证）；排查"agent 死循环"看 LoopDetection 的 logger.error（loop_detection_middleware.py:162）。
- ViewImageMiddleware 的 print 调试（view_image_middleware.py:184）与 TitleMiddleware 的 print（title_middleware.py:88）未走 logger，日志检索时别只 grep logger 格式。
- UploadsMiddleware 的消息原位替换会保留消息 id（uploads_middleware.py:195），前端靠 id 去重，改动时勿丢。
- 新写中间件记得在 CLAUDE.md 链清单与 agent.py 注释块同步登记，否则重演"9/10/11 计数漂移"。
