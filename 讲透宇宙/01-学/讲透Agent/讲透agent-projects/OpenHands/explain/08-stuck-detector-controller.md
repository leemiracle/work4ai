# 08 · openhands/controller/：AgentController 主循环、State 与 StuckDetector 卡死检测

## 1. 角色定位

`openhands/controller/` 是 Legacy-V0 时代的**agent 编排中枢**：`agent_controller.py`（1392 行）驱动"LLM 产动作→事件流→runtime 执行→观察回流"的主循环并管辖迭代/预算/确认三道闸门；`state/state.py` 是可 pickle 持久化的会话状态机；`stuck.py` 的 `StuckDetector` 用纯文本模式匹配识别五种 agent 死循环。全目录顶着最醒目的弃用头注（`openhands/controller/agent_controller.py:1-8`：V0 自 1.0.0 弃用、定于 2026-04-01 移除，V1 的 agent 核心在外部仓 software-agent-sdk、V1 应用服务在同仓 `openhands/app_server/`）。但"弃用"不等于"死了"：V0 服务端仍在线跑，且 `state.py`、`view`、condenser 消费链都还活着——这是理解整个大重构代际的最佳切片：**文件级弃用标记 × 运行时仍在服役**。

## 2. 内部结构

**AgentController**（`openhands/controller/agent_controller.py:112`）字段区声明了 delegate 树（`parent`/`delegate`，`openhands/controller/agent_controller.py:121-122`）与 pending action 元组（`openhands/controller/agent_controller.py:123`）。`__init__`（`openhands/controller/agent_controller.py:127-214`）做五件事：非 delegate 才订阅事件流（`openhands/controller/agent_controller.py:178-181`，`EventStreamSubscriber.AGENT_CONTROLLER` 槽）；建 `StateTracker`（`openhands/controller/agent_controller.py:183`）并 `set_initial_state`（`openhands/controller/agent_controller.py:186-192`）；挂 `StuckDetector`（`openhands/controller/agent_controller.py:202`）；建 `ReplayManager`（`openhands/controller/agent_controller.py:206`，回放轨迹测试用）；写系统消息（`openhands/controller/agent_controller.py:214`）。`openhands/controller/agent_controller.py:194` 的 TODO 自曝架构债：state 在 manager 与 controller 间共享只为向后兼容。

核心 `_step`（`openhands/controller/agent_controller.py:863`）的守卫链：状态非 RUNNING 直接返回（`openhands/controller/agent_controller.py:865-871`）；有 pending action 不步进（`openhands/controller/agent_controller.py:873-881`）；预算同步（`openhands/controller/agent_controller.py:890`）；**卡死检测**——`enable_stuck_detection` 开启且 `_is_stuck()` 为真就抛 `AgentStuckInLoopError` 走 `_react_to_exception`（`openhands/controller/agent_controller.py:891-895`）；控制旗标超限拦截（`openhands/controller/agent_controller.py:898-902`）。然后三选一：回放模式取 `_replay_manager.step()`（`openhands/controller/agent_controller.py:906-909`）；正常模式调 `self.agent.step(self.state)` 拿动作（`openhands/controller/agent_controller.py:912`），LLM 响应异常分两级——解析类错误发 `ErrorObservation` 返回（`openhands/controller/agent_controller.py:916-929`），context window 类错误靠**字符串匹配八种供应商文案**识别（`openhands/controller/agent_controller.py:930-950`，'prompt is too long'、SambaNova 双模式等），命中后若 `enable_history_truncation` 就发 `CondensationRequestAction`（`openhands/controller/agent_controller.py:951-955`）交给 condenser 家族自愈，否则抛 `LLMContextWindowExceedError`。可运行动作走确认闸门（`openhands/controller/agent_controller.py:978-1030`）：八类动作在 confirmation_mode 下先过 `_handle_security_analyzer`（`openhands/controller/agent_controller.py:990`），HIGH 风险或"无分析器的 UNKNOWN"进 `AWAITING_CONFIRMATION`（`openhands/controller/agent_controller.py:997-1021`），最后 `add_event` 入流（`openhands/controller/agent_controller.py:1035`）。

**卡死恢复**：`_is_stuck`（`openhands/controller/agent_controller.py:1129-1139`）先递归查 delegate 再查本体；`attempt_loop_recovery`（`openhands/controller/agent_controller.py:1141-1178`）是 CLI 专属——发 `LoopDetectionObservation` 给出 `/resume 1|/resume 2|/exit` 三选项（`openhands/controller/agent_controller.py:1157-1170`），再用 `ChangeAgentStateAction(PAUSED)` 暂停（`openhands/controller/agent_controller.py:1174-1177`）；真正执行在 `_perform_loop_recovery`/`_truncate_memory_to_point`/`_restart_with_last_user_message`（`openhands/controller/agent_controller.py:1304`/`:1325`/`:1348`）。代理委托走 `start_delegate`/`end_delegate`（`openhands/controller/agent_controller.py:735`/`:796`）。

**StuckDetector**（`openhands/controller/stuck.py:28`）输出 `StuckAnalysis`（loop_type/重复次数/起始下标，`openhands/controller/stuck.py:35-39`）。`is_stuck`（`openhands/controller/stuck.py:45`）先按模式裁历史：交互模式只看最后一条用户消息之后（`openhands/controller/stuck.py:57-68`），再滤掉用户消息与 Null 事件（`openhands/controller/stuck.py:74-85`），不足 3 事件直接放过（`openhands/controller/stuck.py:88-89`）。五场景按序探测：
1. **4 组相同动作-观察**（`openhands/controller/stuck.py:140-171`）：取末尾 4 动作+4 观察（`openhands/controller/stuck.py:97-104`），全等即卡；
2. **3 次动作-错误**（`openhands/controller/stuck.py:173-244`）：末 3 动作相同且观察全为 `ErrorObservation`（`openhands/controller/stuck.py:188-198`），或 3 次 IPython `SyntaxError`——后者还要过两道一致性检查：`_check_for_consistent_invalid_syntax` 要求 traceback 至少 6 行、首行 `Cell In[1], line` 全同（`openhands/controller/stuck.py:246-287`），`_check_for_consistent_line_error` 校验倒数第三行错误行全同（`openhands/controller/stuck.py:289-316`）；
3. **agent 独白**（`openhands/controller/stuck.py:318-357`）：末 3 条 AGENT 源 `MessageAction` 相同且**中间夹着任何 Observation 就不算**（`openhands/controller/stuck.py:343-349`，"也许还能恢复"的宽容）；
4. **6 步交替模式**（`openhands/controller/stuck.py:359-407`）：`(A1,O1),(A2,O2),(A1,O1)...` 隔步全等；
5. **context window 错误环**（`openhands/controller/stuck.py:409-462`）：10 个 `AgentCondensationObservation` 之间无其他事件即判死循环（`openhands/controller/stuck.py:433-437`）——压缩器失效的兜底。
噪声消除在 `_eq_no_pid`（`openhands/controller/stuck.py:464-488`）：`edit_file_by_replace` 只比代码前 3 行（`openhands/controller/stuck.py:471-477`，躲开 thought 噪声），`CmdOutputObservation` 忽略 command_id/pid 只比命令与退出码（`openhands/controller/stuck.py:481-485`）。

**State**（`openhands/controller/state/state.py:55`，dataclass）字段分五组：迭代旗标 `iteration_flag`（`openhands/controller/state/state.py:90-94`）、历史 `history`（`openhands/controller/state/state.py:98`）、委托层级 `delegate_level` 与事件区间（`openhands/controller/state/state.py:105-108`）、`extra_data`（`openhands/controller/state/state.py:115`，condenser 元数据住这里）、**六字段弃用区**（`openhands/controller/state/state.py:118-125`，注释"30 天内删除"）。持久化是 pickle+base64：`save_to_session`（`openhands/controller/state/state.py:129`）先摘掉 `conversation_stats`（`openhands/controller/state/state.py:132-133`），`pickle.dumps`→`base64.b64encode` 落 FileStore（`openhands/controller/state/state.py:135-141`），还顺手删旧目录残留（`openhands/controller/state/state.py:143-149`）；`__getstate__`（`openhands/controller/state/state.py:198`）**不 pickle history**（事件流自己恢复，`openhands/controller/state/state.py:199-201`）并弹出弃用字段与 view 缓存（`openhands/controller/state/state.py:205-214`）；`__setstate__`（`openhands/controller/state/state.py:218`）做老版本迁移——检测 `'iteration' in state` 就把旧整数迭代转成 `IterationControlFlag`（`openhands/controller/state/state.py:222-233`）。`view` property（`openhands/controller/state/state.py:305-318`）用 `len(history)` 校验和缓存 View 重建。

## 3. 外部连接

上游：`AgentSession` 持有并驱动 controller（`openhands/server/session/agent_session.py:451` 传入 security_analyzer）；`openhands/resolver/issue_resolver.py:454` 的 `run_controller` 是 headless 消费入口。controller 依赖 `openhands/controller/agent.py:33` 的 `Agent` 抽象（`step(state)` 在 `openhands/controller/agent_controller.py:912` 被调）、`state/state_tracker.py`（`openhands/controller/agent_controller.py:183`，save/get trajectory）、`state/control_flags.py` 的 `IterationControlFlag/BudgetControlFlag`（`openhands/controller/agent_controller.py:890`/`:898` 消费）。StuckDetector 只依赖 events 动作/观察类型（`openhands/controller/stuck.py:13-25`）与 State——零外部 IO，纯函数式判定，测试性极佳。State 被三方共享：controller 读写、agent 读（`openhands/agenthub/codeact_agent/codeact_agent.py:169` 的 step）、condenser 写元数据（`openhands/memory/condenser/condenser.py:114`）。动作类型全来自 `openhands/events/action`（`openhands/controller/agent_controller.py:59-84`），`CondensationRequestAction`/`CondensationAction` 与 memory/condenser 家族闭环（`openhands/controller/agent_controller.py:80-84`）。

## 4. 数据流

一次完整步进：观察事件入流 → `on_event`（`openhands/controller/agent_controller.py:454`）→ `_on_event` 判 `should_step`（`openhands/controller/agent_controller.py:499`，观察到达即步进）→ `_step`（`openhands/controller/agent_controller.py:863`）→ 守卫链 → `agent.step(state)` 产 `CmdRunAction` → 确认闸门（无风险直通）→ `add_event` → runtime 订阅者执行 → `CmdOutputObservation` 入流 → 触发下一步。用户消息走 `_handle_message_action`（`openhands/controller/agent_controller.py:572`）设回 RUNNING 并步进；`MessageAction` 带 `image_urls` 时 `_first_user_message`（`openhands/controller/agent_controller.py:1261`）有缓存。异常线：任何未捕获异常进 `_react_to_exception`（`openhands/controller/agent_controller.py:323`），`LLMContextWindowExceedError` 停机、`AgentStuckInLoopError` 进错误态并写 `last_error`。

## 5. 设计决策

Legacy-V0→V1 语境下三个决策：其一，**字符串匹配识别 context window 错误**（`openhands/controller/agent_controller.py:930-950`）——注释自认"FIXME: this is a hack until a litellm fix is confirmed"，litellm 不一致地包装异常，工程上只能白名单匹配各供应商文案；这债随 V0 一起迁移进 SDK。其二，**State 弃用字段的" pickle 迁移"策略**（`openhands/controller/state/state.py:218-252`）：不一次性删字段，而是在 `__setstate__` 里做版本探测+转换，`__getstate__` 里再静默弹出——旧会话文件永远可恢复，代价是每个读代码的人都要同时理解两套字段。其三，**卡死检测从"观察计数"升维到"语义场景"**：五场景不是通用算法而是对真实失败模式的枚举（尤其场景 5 专为"压缩自愈失效"设计，`openhands/controller/stuck.py:409-462` docstring 明说"反复 trim 但 trim 不管用"），这种"问题驱动而非完备性驱动"的检测器设计在 agent 工程里非常典型。V1 把整个 controller 移出本仓（头注指向 software-agent-sdk），但 StuckDetector/State/condenser 的**语义**都被继承——弃用的是实现，不是问题域。

## 6. 新人提示

- **头注勘误**：`openhands/controller/agent_controller.py:8` 与 `openhands/agenthub/codeact_agent/codeact_agent.py:8` 都写"V1 replacement lives in the Software Agent SDK"，但 controller 的 V1 替代是**外部仓**（github.com/OpenHands/software-agent-sdk），本仓内搜不到——别在仓内找对应物。
- `openhands/controller/stuck.py:1-7` 同款 Legacy-V0 头注，但 `state_tracker.py`、`control_flags.py` 也属本目录且同样服役中；`agent.py`（191 行）的 `Agent.register/get_cls` 注册表是 agenthub 的挂载点（`openhands/controller/agent.py:129`/`:144`）。
- `openhands/controller/state/state.py:118-119` 注释说弃用字段"Will be remove in 30 days"——这句注释的年龄远超 30 天，是典型的"临时补丁永生化"，读代码时别相信任何带天数的注释。
- 五场景计数不对称是**故意的**：场景 1 要 4 次（动作+观察全同已经很确定）、场景 2 只要 3 次（错误更致命）、场景 5 名义 10 连 condensation 但 `loop_repeat_times=2`（`openhands/controller/stuck.py:457`）——语义是"两相邻 condensation 之间零其他事件即成环"。
- `_eq_no_pid` 的 edit 前三行比较（`openhands/controller/stuck.py:471-477`）有隐藏坑：代码少于 3 行的 edit 走 `obj1 == obj2` 分支（`openhands/controller/stuck.py:480`），小编辑的检测灵敏度反而更高。
- 安全发现（全仓语境）：`_handle_security_analyzer` 的 docstring 说"无分析器则设 HIGH"（`openhands/controller/agent_controller.py:220`），**代码实际设 UNKNOWN**（`openhands/controller/agent_controller.py:248-254`）——效果等价（UNKNOWN+无分析器同样强制确认，`openhands/controller/agent_controller.py:998-1001`），但文档与实现不符，二改时以代码为准。
- `attempt_loop_recovery` 仅 CLI 线可用（`openhands/controller/agent_controller.py:1141-1143` docstring "Only supports CLI for now"），Web 端卡死直接走异常停机——两条恢复路径不要混测。
