# 09 · openhands/resolver/：自主 issue 解决器全链路

## 1. 角色定位

`openhands/resolver/` 是 OpenHands 的**无人值守垂直应用**：给它一个 GitHub/GitLab/Bitbucket/Bitbucket DC/Forgejo/Azure DevOps 的 issue 编号，它克隆仓库、把 issue 渲染成提示词、拉起完整 agent 循环在沙箱里改代码、抽出 git diff、必要时开 PR 并回帖。它不是框架代码而是"框架的第一个也是最大的消费者"——`IssueResolver` 通过 `openhands/core/main.py` 的 `run_controller` 复用全部 V0 基建（`openhands/resolver/issue_resolver.py:28` import `create_runtime, run_controller`），因此整条链顶着 Legacy-V0 头注（`openhands/resolver/resolve_issue.py:3-9` 等），其 V1 对应物是独立的 OpenHands Resolver 仓库。对读代码的人，它是学习"如何把 agent 核心组装成产品"的样板：CLI 层→编排层→平台抽象层→diff 引擎四段式。

## 2. 内部结构

**CLI 层** `openhands/resolver/resolve_issue.py:15` 的 `main()`：13 个参数的 argparse（`openhands/resolver/resolve_issue.py:24-133`），`--selected-repo`/`--issue-number` 必填（`:26-30`/`:68-72`），`--issue-type` 二选一 issue|pr（`:117-122`），`--comment-id` 支持传 `"none"`（`int_or_none`，`:18-22`）。组装后 `asyncio.run(issue_resolver.resolve_issue())`（`:137-138`）。

**编排层** `openhands/resolver/issue_resolver.py:59` 的 `IssueResolver`：构造期先做 token 环境变量六连降级（`GITHUB_TOKEN`→`GITLAB_TOKEN`→`BITBUCKET_TOKEN`→`AZURE_DEVOPS_TOKEN`→`FORGEJO_TOKEN`，`openhands/resolver/issue_resolver.py:87-94`），再 `identify_token`（`openhands/resolver/issue_resolver.py:102-107`，实现在 `openhands/resolver/utils.py`）探测 token 属于哪个平台；提示词模板按 issue_type 选默认——issue 用 `prompts/resolve/basic-with-tests.jinja`、pr 用 `basic-followup.jinja`（`openhands/resolver/issue_resolver.py:118-126`），并强约定同名 `-conversation-instructions.jinja` 伴生文件（`openhands/resolver/issue_resolver.py:130-133`）。`update_openhands_config`（`openhands/resolver/issue_resolver.py:191-220`）写死 `default_agent='CodeActAgent'`、`max_budget_per_task=4` 美元、`disabled_microagents=['github']`（`openhands/resolver/issue_resolver.py:202-211`）；容器镜像默认 `ghcr.io/openhands/runtime:{version}-nikolaik`（`openhands/resolver/issue_resolver.py:238-240`），base 与 runtime 镜像二选一互斥（`openhands/resolver/issue_resolver.py:230-231`）。GitLab CI 分支处理 chown/sudo 差异（`openhands/resolver/issue_resolver.py:261-267`、`:302-306`、`:364-367`）。

运行时三段式：`initialize_runtime`（`openhands/resolver/issue_resolver.py:281-321`）cd /workspace、关 git pager、跑 `.openhands/setup.sh` 与 `.openhands/pre-commit.sh`（`:317-321`）；主循环 `process_issue`（`openhands/resolver/issue_resolver.py:411-531`）每次 `shutil.rmtree`+`copytree` 重铺工作区（`:426-428`），建 runtime、拿 `get_instruction` 渲染的指令（`:443-450`），以 `MessageAction` 为初始动作跑 `run_controller`，`fake_user_response_fn=codeact_user_response`（`:454-460`）让 agent 的提问得到自动应答；`complete_runtime`（`openhands/resolver/issue_resolver.py:323-400`）`git add -A` 后 `git diff --no-color --cached {base_commit}`，失败重试 5 次、超时递增（`openhands/resolver/issue_resolver.py:375-395`）。成功与否由 `issue_handler.guess_success(issue, state.history, git_patch)`（`openhands/resolver/issue_resolver.py:488-490`）判定，PR 模式逐条打勾输出结果清单（`:492-514`）。产物是 `ResolverOutput`（`openhands/resolver/resolver_output.py`，含 issue/patch/history/metrics/success 全量）追加写 `output.jsonl`（`openhands/resolver/issue_resolver.py:617-675`），断点续跑靠"已处理编号跳过"（`:621-629`）。

顶层 `resolve_issue()`（`openhands/resolver/issue_resolver.py:549-678`）：提取 issue（`extract_issue`，`:533-547`）→ git clone（`:586-597`）→ `git rev-parse HEAD` 定 base_commit（`:600-604`）→ 仓库内 `.openhands_instructions` 文件兜底 repo_instruction（`:607-614`）→ PR 模式 fetch+checkout head_branch 并刷新 base_commit（`:638-666`）→ `process_issue`。

**平台抽象层**是标准 Strategy 模式：`openhands/resolver/issue_handler_factory.py:31` 的 `IssueHandlerFactory.create()` 按 issue_type×platform 十二路分发（`:52-211`），六平台 handler 各自成对（Issue/PR）：github.py 644 行、gitlab.py 617、bitbucket.py 527、bitbucket_data_center.py 357、forgejo.py 487、azure_devops.py 434；Azure 特殊在 owner 要按 `organization/project` 二段拆（`:109-118`）且 PR 复用 Issue handler（`:198-207` 注释"For now"）。Strategy 的公共面是 `openhands/resolver/interfaces/issue_definitions.py:26` 的 `ServiceContext`——持 `strategy: IssueHandlerInterface` 与 `llm_config`（`:30-38`），`ServiceContextPR.issue_type='pr'`（`:40-41`）、`ServiceContextIssue`（`:277`）。prompt 渲染在 `get_instruction`（`:122-178`）：两套 Jinja2 模板（user_instructions + conversation_instructions，`:130-133`），渲染变量含 issues_str 与 repo_instruction（`:167-175`）。`guess_success`（`:52`）委托三个 jinja 检查器：`_check_review_thread`（`:191-204` 用 `prompts/guess_success/pr-feedback-check.jinja`）、`_check_thread_comments`（`:220-233`）、`_check_review_comments`（`:248-261`），共同基座 `_check_feedback_with_llm`（`:180`）。

**diff 引擎** `patching/patch.py`（984 行）fork 自 whatthepatch（`patching/README.md` 明证，MIT）：模块顶部按方言铺正则——通用 diff（`:30-35`）、context diff（`:37-42`）、ed/rcs-ed（`:44-47`）、default（`:49-51`）、git（`:56-65`，含 binary patch 与 base85 串 `:62-65`）、bzr（`:67-69`）、svn（`:71-73`）、cvs（`:75-79`）。入口 `parse_patch`（`:82-109`）按六个候选头部正则切分多文件 diff；`parse_header`（`:112`）先试 SCM 头（`:119`）再退普通头（`:159`）；`parse_diff`（`:180-200`）把 hunk 分发给六个解析器：`parse_default_diff`（`:510`）、`parse_unified_diff`（`:563`）、`parse_context_diff`（`:630`）、`parse_ed_diff`（`:770`）、`parse_rcs_ed_diff`（`:850`）、`parse_git_binary_diff`（`:898`，base64+zlib 解 git 二进制增量，imports `:9-11`）；头部侧另有 `parse_git_header`（`:202`）、`parse_svn_header`（`:274`）、`parse_cvs_header`（`:342`）——合计覆盖九种 diff 方言。产出是 `Change` namedtuple（old/new/line/hunk，`:24`）。`openhands/resolver/patching/apply.py:18` 的 `_apply_diff_with_subprocess` 另有一路"调系统 patch 程序"的兜底。

**PR 发送层** `send_pull_request.py`：`apply_patch`（`:43-136`）是 patch.py 的应用端——剥 `a/`、`b/` 前缀（`:57-66`）、`/dev/null` 删除语义（`:69-74`）、rename from 特判（`:77-97`）、按原文件探测 CRLF/LF 行尾再写回（`:104-110`）；`initialize_repo`（`:139`）、`make_commit`（`:177`）、`send_pull_request`（`:248`，fork_owner 时推 fork 且 GitHub/Forgejo 用 `fork_owner:branch` 头（`:367`/`:393-394`））、`update_existing_pull_request`（`:461`）、`process_single_issue`（`:608`）、`main()`（`:705`）。

## 3. 外部连接

resolver 是纯消费者：上游依赖 `core/main.py` 的 `run_controller`（`openhands/resolver/issue_resolver.py:28`）、`openhands/controller/state/state.py:24`（读 state.history/last_error）、`core/config/utils.py` 的 `load_openhands_config`（`:26`）、`llm/llm_registry.py`（`:38`）、integrations 六平台 service 层（handler 家族内部各自调 `openhands/integrations/*/service/`）。下游被 GitHub Actions workflow `.github/workflows/openhands-resolver.yml` 以容器方式调起，也被 enterprise 增强层 `enterprise/integrations/resolver_context.py` 包装。diff 引擎反向被 send_pull_request 自身与测试消费，无其他仓内消费者——它是一块"自带测试的飞地"。prompt 资产三族：`prompts/resolve/`（basic 系 4+3 个 jinja）、`prompts/guess_success/`（4 个判定 jinja）、`prompts/repo_instructions/`（3 个 txt：openhands 本体、openhands-resolver、rss-parser）。

## 4. 数据流

单 issue 全程：`resolve_issue.py main()` → `IssueResolver(args)` 构造（token 探测→平台 handler→config 装配）→ `resolve_issue()`（clone→base_commit→instructions 文件探测）→ `process_issue`（重铺 workspace→runtime 连接→setup.sh→`get_instruction` 渲染 `{{ body }}`/`{{ repo_instruction }}` 等变量→`run_controller` 全循环）→ agent 在沙箱改代码 → `complete_runtime`（git add -A→diff--cached 抽 patch）→ `guess_success` LLM 判定 → `ResolverOutput` 落 `output.jsonl` → （可选）`send_pull_request.py main()` 读同一 output.jsonl → `apply_patch` 复放补丁 → `make_commit` → `send_pull_request`/`update_existing_pull_request` 回平台。

## 5. 设计决策

Legacy-V0→V1 语境下的四个决策：其一，**Strategy 而非继承**做六平台抽象（`openhands/resolver/issue_handler_factory.py:52-211`）——新增平台只需 handler 对+factory 两行，代价是 factory 十二路 if-elif 的重复膨胀（每路都是五参数构造，明显该提表驱动却没提）。其二，**diff 引擎整块 fork whatthepatch**（`patching/README.md`）而非 pip 依赖：resolver 对"解析 agent 产出的不完美 diff"有强定制需求（剥前缀、rename 特判、行尾保真，`openhands/resolver/send_pull_request.py:57-110`），上游库跟不上就内化——典型的"垂直应用吃掉依赖"决策。其三，**guess_success 用 LLM 判定 LLM**（`openhands/resolver/interfaces/issue_definitions.py:52-116`）：issue 是否被解决无法静态判定，交给带四套 jinja 模板的检查器，失败可解释（PR 模式逐条 [X]/[ ] 清单，`openhands/resolver/issue_resolver.py:492-514`）。其四，**提示词双文件强约定**（`openhands/resolver/issue_resolver.py:130-133`）：user_instructions（进首条消息）与 conversation_instructions（进系统提示）分离，`-conversation-instructions.jinja` 后缀靠 `replace('.jinja', ...)` 推导——脆弱但自文档化。V1 把 resolver 整体拆去独立仓，本目录成为"应用层如何长在框架上"的化石标本。

## 6. 新人提示

- **勘误（对照旧文档/图谱）**：全仓**不存在** `runtime/utils/resolver_templates`——提示词模板唯一住在 `openhands/resolver/prompts/`（resolve/guess_success/repo_instructions 三族），仓内 grep `resolver_templates` 零命中；enterprise/ 消费的是 `resolver_context.py` 而非另一套模板。
- `IssueResolver` 构造在无 token/username 时抛 ValueError（`openhands/resolver/issue_resolver.py:96-100`），但 username 只查 `GIT_USERNAME` 一个环境变量（`:95`）——六平台 token 都照顾了，username 没有 PR 探测，填错平台会炸在很深的 HTTP 层。
- `max_budget_per_task=4` 硬编码（`openhands/resolver/issue_resolver.py:205`）：这是"单个 issue 最多烧 4 美元"的产品级保险丝，别当默认配置改着玩。
- `process_issue` 每次重铺 workspace 用 `shutil.rmtree`（`openhands/resolver/issue_resolver.py:426-427`）——上一次运行的未提交修改会静默丢失，断点续跑语义完全依赖 output.jsonl 而非工作区。
- `complete_runtime` 的 diff 命令带 600+100*n 秒递增超时（`openhands/resolver/issue_resolver.py:378-379`）与大仓库 `git diff` 慢的现实对齐；5 次全失败返回 `git_patch=None` 而非抛错（`:376-395`），下游要把 None 当合法值。
- patch.py 是外部 fork，行号与上游 whatthepatch 对不上时要先看 `patching/README.md` 溯源；`apply_patch`（`openhands/resolver/send_pull_request.py:43`）与 `patching/apply.py` 是**两套 apply**：前者文件级（含 rename/delete/行尾），后者 diffobj 级 subprocess 兜底。
- 安全发现：`--token` 明文进 CLI 参数与环境变量链（`openhands/resolver/issue_resolver.py:87-94`），clone URL 由 `issue_handler.get_clone_url()` 拼 token（`openhands/resolver/issue_resolver.py:588-594`）——token 可能落 git remote 与进程列表；Skills 教 agent "用 token 拼 git URL" 属同类风险面。
- `openhands/resolver/interfaces/issue_definitions.py:40-41` 的 `issue_type: ClassVar[str]` 是类级变量——`ServiceContextPR`/`ServiceContextIssue` 的 isinstance 分支判断全靠它，覆盖时改错层级会静默串类型。
