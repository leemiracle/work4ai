# 第 3 章 推理与训练负载

假设一个服务平均每秒收到四个请求，每个请求输入 4,608 个 token、输出 1,152 个 token。第二章已经教我们按输入和输出长度计算模型工作量。现在把平均工作量乘以每秒请求数，是否就能决定需要多少资源？

两种服务可以具有完全相同的平均数：一种始终均匀接收请求，另一种前一分钟集中处理长文档，后一分钟集中生成长回答。前者各阶段的资源需求较为稳定，后者则在不同时段分别需要更多输入处理能力或生成能力。智能体（Agent）是通过模型决定下一步操作、调用工具并根据结果继续工作的程序，它在模型与工具之间往返，GPU 暂停生成时，上下文状态仍需保留，供后续调用使用。训练中的序列长度、有效标签和更新次数，也会影响运算量和状态需要保存的时间。

第二章给出了单次调用的容量、运算量和读取量。本章再加入三个问题：工作何时到达，哪些步骤必须等待，什么结果才算任务完成。由此依次建立排队、状态寿命、关键路径和成功任务成本的模型，再综合计算训练与长期服务的成本。

## 3.1 从单次请求到持续到达的负载

### 3.1.1 Prefill 与 Decode

负载是一定时间内到达系统、等待和执行的工作集合。先按时间顺序分析一个请求。预填充（prefill）指处理本次已知输入的阶段，解码（decode）指利用已有上下文逐步生成后续输出的阶段。恢复 $S$ 个上下文位置，处理 $P$ 个新输入，返回 $G$ 个 token，调用链由一次 prefill 和 $n_d=G-1$ 次 decode 构成。把后续 decode 从 $j=0$ 开始编号，第 $j$ 次开始时，已有上下文为 $S+P+j$。因此，每次调用的资源需求可以由第二章计算，调用之间的顺序则由生成依赖确定。[^model]

![恢复 6144 个上下文位置，处理 2048 个新输入并生成四个输出。首输出来自 prefill，后续三次 decode 各追加一个位置；纵向表示调用次序，间距用于示意。](ch03/figure-3-1-stages.svg)

*图 3-1　恢复 6144 个上下文位置，处理 2048 个新输入并生成四个输出。首输出来自 prefill，后续三次 decode 各追加一个位置；纵向表示调用次序，间距用于示意。*

两个阶段使用同一套权重，却提出不同的资源需求。以一组权重矩阵为例，prefill 的输入包含 $BP$ 行，单步 decode 只有 $B$ 行。输入位置较多时，一次读入的权重可以参与更多乘加运算；低并发 decode 则可能为很少几个 token 读取整组权重。这是“prefill 常偏计算密集、decode 常偏带宽密集”的来源。

不同请求之间可以形成新的复用机会。多个 decode 同时执行时，共同使用权重，各自读取上下文；一条长输入到来时，prefill 可以同时处理较多已知 token，它们的特征向量组成行数更大的输入矩阵。服务系统需要在这些不同形状的工作之间分配时间。仅把总 token 数相加，会丢掉它们分别属于哪个阶段、何时能够执行的信息。

> **练习 3-1〔延伸〕：相同输出总量的不同生成过程**
>
> 分别考虑一条请求输出 1024 个 token，以及八条请求各输出 128 个 token。每条请求的输入均为 1024 个 token。求两种情况下的 prefill 次数、后续 decode 总步数，以及各请求结束时的上下文长度。假设八条请求同步生成，比较每批共享一次权重时的读取轮数，再解释总输出相同为什么不足以判断完成时间。

### 3.1.2 任务目标与评价指标

模型请求与用户任务通常不是一一对应的。回答一个问题可能只需一次生成，修复一个函数却可能需要读文件、改代码、运行测试、根据错误再修改。评估系统时，先写出什么算完成，再决定统计什么。

先在时间线上标出三个事件：请求到达 $t_a$、首个 token 返回 $t_1$、最后一个 token 返回 $t_G$。它们给出

$$
T_{\mathrm{TTFT}}=t_1-t_a,\qquad T_{\mathrm{request}}=t_G-t_a,\qquad
\overline T_{\mathrm{token}}=\frac{t_G-t_1}{G-1}\quad(G>1).
$$

TTFT 是 time to first token，即从请求到达到首个 token 返回的时间。首响应衡量多久开始输出，完整请求延迟衡量多久生成完，平均 token 间隔衡量输出节奏。把某一段时间缩短，只会直接改变包含这段时间的指标。例如，减少请求开始前的排队会改善 TTFT，却不会自动缩短已经开始生成后的 token 间隔。

![请求到达、首输出与末输出决定三个计时区间。首响应包含开始生成前的等待，输出间隔描述生成过程，完整请求时间从到达累计到结束。](ch03/figure-3-request-clocks.svg)

*图 3-2　请求到达、首输出与末输出决定三个计时区间。首响应包含开始生成前的等待，输出间隔描述生成过程，完整请求时间从到达累计到结束。*

首个 token 到达客户端之前，请求要依次经过排队、输入准备、设备计算和结果返回等阶段。输入原来在主机还是设备，决定数据传输发生在哪里；计算完成后，结果还要经过主机处理和连接发送。记录同一请求在各阶段的开始和结束时间，就能看出 TTFT 主要花在哪些环节。第五章将展开设备提交、传输与完成的具体时序。

客户端按块接收多个 token 时，可以直接记录每块的到达时间与 token 数，再统计输出节奏。reasoning（推理）模型在给出可见回答前生成中间推理内容，这些内容称为思考 token。这类模型又增加了一个观察点：首个内部 token 出现时，用户未必已看到答案。因此，内部生成、用户可见输出和任务完成分别对应不同的时间点。语音的首次播放还要再经过解码与设备缓冲，稍后讨论。

| 要回答的问题 | 需要的指标或记录 |
| --- | --- |
| 多久开始回应？ | TTFT；reasoning 另记首个有用输出 |
| 输出是否连续？ | 逐 token／逐块间隔及其分布 |
| 多久把事情做完？ | 完整请求时间、完整任务时间 |
| 每秒完成多少合格任务？ | 在质量与时限要求下的有效吞吐 |
| 得到一个成功结果花多少？ | 全部尝试的模型、工具和环境成本／成功任务数 |
| 等待期间还占着什么？ | 状态所属的请求与模型版本、大小、驻留位置和寿命 |

p95 是第 95 百分位数，用来描述所选指标中较慢的一部分观测。本章采用最近秩法：把 $n$ 个观测从小到大排列，取第 $\lceil0.95n\rceil$ 个。四条请求的 p95 是最大值，480 条请求的 p95 是第 456 个。请求完成、排队与首响应分别排序，就能看出长等待发生在哪一段；全程 p95 则直接对每条请求的全程时间排序得到。

状态保存得越久，同样的容量能同时服务的任务就越少。令任务状态大小为 $M(t)$，状态占用时间的积分为

$$
A_M=\int_{t_{\mathrm{start}}}^{t_{\mathrm{end}}}M(t)\,\mathrm dt.
$$

将各时间段占用的空间乘以持续时间再相加，就得到占用空间随时间变化的曲线下面积。它的单位是 byte·s：保留 1 GiB 状态等待 10 秒，对应 10 GiB·s。状态没有变大，但这段时间内无法将空间用于其他请求。若任务以平均每秒 $\lambda$ 个的速度持续到达，每个任务都占用 $M_0$ 字节、平均等待 $\tau$ 秒，稳定情况下仅这些等待任务的平均占用就约为 $\lambda M_0\tau$。工具等待由此也会成为容量问题。

![保留 1 GiB 状态等待十秒，对应面积为 10 GiB·s。横轴为状态存活时间，纵轴为占用空间；面积描述这段等待期间的累计存储占用。](ch03/figure-3-state-time-area.svg)

*图 3-3　保留 1 GiB 状态等待十秒，对应面积为 10 GiB·s。横轴为状态存活时间，纵轴为占用空间；面积描述这段等待期间的累计存储占用。*

成功任务成本把所有尝试的成本相加，再除以成功任务数。这样，失败生成、工具测试和环境运行都进入分子，分母对应用户得到的合格结果。一个批次零成功时，记录其总消耗与失败原因；取得成功结果后，再用全部尝试的总成本除以成功任务数。[^cost]

### 3.1.3 请求分布

TTFT 和输出间隔描述单个请求的体验。多个请求陆续到达时，这些指标还取决于它们是否争用同一时段的处理能力。因此，只知道平均长度和平均请求率还不够，还要看长短请求怎样组合、何时到达。

负载描述应保留到达时间、输入与输出长度的联合分布。长请求既增加自身服务时间，也可能延长状态驻留；短请求提前完成，则可能让后续请求较早开始。因此，平均工作量相同，也可能有不同的等待时间、完成时间和状态占用峰值。先用章首的两分钟负载把这个区别算清，再观察真实系统。

实际请求往往来自不同客户。某个客户主要提交长文档，另一个主要生成长回答；即使各自的请求形状稳定，各客户请求到达速率的变化也会改变整体负载。ServeGen 对生产服务的研究观察到了这种现象，并用客户组成与时间变化重建请求分布。[^servegen] 因此，下面保持请求总量和平均长度相同，只改变它们到来的顺序。

**例题 3-1：平均处理能力足够，为什么仍会积压？** 判断每秒可完成 6144 个后续 decode 步的资源，能否持续承接章首负载。

| --- | ---: | ---: |
| 均匀混合 | 18,432 | 4,604 |
| 时段变化，前一分钟 | 29,900.8 | 1,736.8 |
| 时段变化，后一分钟 | 6,963.2 | 7,471.2 |

**队列假设：窗口内均匀到达、处理率固定。** 使用流体队列模型，把离散的生成工作近似为连续流量；每个窗口内均匀到达，处理率固定，初始队列为空。单位是一条请求的一次后续 decode 步，prefill 能力单独核算。

![工作先进入队列，再由处理资源完成。到来快于处理时差额留在队列中；处理快于到来时，资源逐步消化已有积压。](ch03/figure-3-queue-mechanism.svg)

*图 3-6　工作先进入队列，再由处理资源完成。到来快于处理时差额留在队列中；处理快于到来时，资源逐步消化已有积压。*

以一个时间窗内的工作为单位，积压可以递推为：

$$
Q_{k+1}=\max(0,Q_k+A_k-\mu_k\Delta t).
$$

其中 $Q_k$ 是窗口开始时的待处理工作，$A_k$ 是窗口内新到达的工作，$\mu_k\Delta t$ 是可完成量。到达速度低于处理速度时，积压逐渐减少，直至队列排空；到达速度超过处理速度时，未完成的工作留到下一窗口。

每秒四个请求的首个输出由 prefill 产生，所以 4608 个输出中有 4604 步属于后续 decode。令 decode 队列初始为空、服务能力为每秒 6144 步，先把请求的生成工作均匀汇入各窗口。前一分钟的处理能力足够，后一分钟每秒多到来 $7471.2-6144=1327.2$ 步，60 秒便留下 79,632 步；停止到达后，再用 $79632/6144$，得到约 12.96 秒排空时间。前一分钟未使用的能力无法保存到后一分钟，这正是全局均值掩盖积压的原因。[^workload]

![每秒完成 6144 个 decode 步的流体模型。后一分钟积压至 79,632 步，120 秒后停止到达，再经过约 12.96 秒排空。](ch03/figure-3-queue-backlog.svg)

两次回放的完整请求 p95 与最后完成时间接近，TTFT 和初次调度等待却相差约 16 秒。采样记录显示，两次实验的 KV 池占用都达到过 100%，请求在进入执行前经历了很长等待。输入与输出的时段组合改变了何时释放状态、何时接纳新请求，所以即使整批请求的完成时间接近，用户开始收到响应的时间仍可不同。KV 空间不足时，调度器可以暂停某条已开始的请求、释放它占用的 KV 空间，之后再恢复或重算，这种行为称为抢占。它会改变请求的等待和后续执行次序。

请求进入执行还需要足够的状态空间。状态池有余量时，新请求可以较早开始；状态池填满后，即使部分计算单元空闲，也要等待已有请求释放空间。排队因此既可能来自处理速度不足，也可能来自已有请求的状态尚未释放。[^serve-replay]

这个递推还能直接预测新的突发条件。若工作到达速率 $\lambda_w$ 连续 $\tau$ 秒高于处理率 $\mu$，初始队列为空，则积压为 $(\lambda_w-\mu)\tau$；停止到达后的排空时间为 $(\lambda_w-\mu)\tau/\mu$。突发持续时间加倍，积压与排空时间都加倍。平均值相同并不能抵消这段已经发生的等待。

## 3.2 多轮交互与 Agent 任务

### 3.2.1 多轮对话与前缀增长

多轮对话的下一次请求通常带着上下文。第一轮通常输入系统提示和用户问题；第二轮除了新问题，还可能包含上一轮回答；之后每轮继续累积。若只看用户新写了多少字，就会低估送入模型的输入长度。

设第 $i$ 轮输入长度为 $I_i$，可复用的前缀长度为 $K_i$，则本轮需要重新处理的输入为

$$
P_i=I_i-K_i,\qquad S_i=K_i.
$$

将 $P_i$ 与 $S_i$ 代入第二章的公式，投影和前馈网络（FFN，对每个位置分别变换特征）只处理新增位置，注意力仍要让新查询访问完整前缀。缓存复用因而减少重算，并没有把旧上下文从后续计算中删除。

以一次包含四轮模型调用的代码修复任务为例。四轮累计输入 5,297 个 token，其中命中 4,480 个，未命中 817 个。第二轮输入 1,443 个、命中 1,392 个，只需处理 51 个未缓存位置；但后续 decode 仍然要访问其上下文状态。如果每轮都重新计算全部输入，prefill 的矩阵运算共需 76.196 TFLOPs；复用已命中的前缀后，共需 11.976 TFLOPs。缓存省去的是旧位置的投影与前馈重算，新的查询仍要使用这些位置的上下文。因此，缓存命中同时带来“少算旧输入”和“继续保留旧状态”两项结果。[^agent-calc]

修改上下文会改变可复用的前缀长度。末尾追加新内容时，原有前缀保持不变；摘要替换一段旧上下文时，替换位置之后的表示要从新的前缀重新计算；工具定义或模板变化则可能更早改变输入。这些操作决定下一轮有多少位置命中、多少位置重新进入 prefill。

上下文策略还会改变未来负载。把新内容持续追加在上下文末尾，有利于保住旧前缀，却会让陈旧内容继续占据上下文；替换前面的内容可以缩短上下文，但其后的缓存可能需要重建。第八章将根据重建计算量、状态大小与复用间隔，比较保留、淘汰和重算的代价。[^context]

用这一模型比较两种编辑方式：在末尾追加 100 个 token，只增加 100 行新输入；若在已有 2000 个 token 的第 501 个位置改写一个 token，变化会影响其后的表示，最长可直接复用的前缀只剩 500 个位置。缓存收益不仅取决于改了多少字，还取决于改动发生在哪里。

从应用看，上下文是编排任务的接口；从系统看，上下文的组织方式决定了计算量和状态保存时间。追加工具返回、替换早期内容、分出多个候选，分别改变新增计算、可复用前缀和私有状态。把这些关系交给服务系统，就能根据复用情况安排缓存，在分支间共享历史，并利用工具等待时间换出状态。因此，负载记录还应包含稳定前缀、改写位置、分支依赖和复用间隔。第八章将使用这些信息选择上下文与缓存策略，第九章再加入状态位置和传输时间。

### 3.2.2 推理与验证：完成一个任务需要多少成本

前缀缓存减少的是已有输入的重复计算。另一类方法则主动增加生成计算，希望提高答案的正确率。增加推理时的计算量，主要有三种方式：延长一条回答中的思考过程，同时生成多份回答并从中选择，或者根据题目难度分配生成次数和长度。延长思考会增加串行生成时间与上下文状态；生成多份回答会增加计算和验证次数；按难度分配则需要决定每道题何时停止。

是否值得增加生成计算，需要比较每个成功任务的成本。设每次尝试的平均成本为 $c$、成功率为 $p$，相同策略下重复尝试的期望次数为 $1/p$，则

$$
C_{\mathrm{success}}=\frac{c}{p}.
$$

新方法的成本和成功率分别为 $c_2,p_2$，旧方法为 $c_1,p_1$，成本下降要求 $p_2/p_1>c_2/c_1$。因此，延长思考或增加采样的依据，是正确率的相对提升能否超过成本的相对增长。所有生成、验证和失败尝试的成本都计入 $c$。

**例子：通过答案检查评价生成效果。** 生成速度只有与任务正确率一起考察，才能反映系统是否有用。一次数学题实验中，对四道题分别生成多份回答，将输出上限从 1024 提高到 4096 个 token，两轮尝试仍未得到通过评分的最终答案。生成已经消耗资源，任务却没有完成；增加输出长度也没有自动带来有效解答。[^reasoning]

答案检查应区分接口格式和内容正确性。格式正确的回答可能算错，数值正确的回答也可能缺少任务要求的字段。把两类错误分开，才能判断应调整生成方式、输出约束还是解题过程。[^reasoning-off]

token 单价降低后，仍需计算完成任务的总成本。用一个简单假设说明：新系统 token 单价降到原来的 1/10，每任务用量却增加到 20 倍，成功率由 50% 提高到 80%。只计模型成本，并假定重复尝试的分布稳定，每个成功任务的成本比为 $2\times\frac{0.5}{0.8}=1.25$。价格下降、质量提高和成功任务成本上升可以同时发生。对带上下文的 Agent，可以沿实际轨迹累加各次尝试，再以通过检查的任务数作分母。[^cost]

>
> 旧方法每次尝试成本为 1 单位、成功率为 50%；新方法成本为 2 单位、成功率为 80%。计算平均每完成一个成功任务所需的成本，并判断新方法是否更省。若新方法成本降到 1.5 单位，成功率至少应达到多少，才能使每个成功任务的平均成本不高于旧方法？对于需要多次采样的任务，说明如何将生成、验证和失败尝试的开销计入总成本。

### 3.2.3 智能体工作负载

反馈还可以改变后续计算。代码 Agent 先生成修改方案，工具写入代码并运行测试，模型再读取测试结果决定下一步。每个循环既有模型计算，也有工具执行；工具返回的日志又成为下一轮输入。因此，减少无关日志能降低下一轮的 prefill 计算量和上下文状态占用，减少无效修改则能直接减少循环次数。

本章的实测任务是修复一个区间合并函数，检查返回结果是否正确、输入是否保持不变。模型负责决定修改并调用工具，工具负责写入文件和运行测试。下面按四轮成功完成原定检查的轨迹，分开统计模型时间、工具时间和等待期间保存的状态。工具调用明细见章末[代码任务轨迹](#agent-trace-detail)。[^agent]

检索增强问答也包含类似的处理过程：检索器找到文档，再将文档交给语言模型生成答案。在达到同样回答质量的前提下，检索内容越少，后续 prefill、KV 存储和上下文读取的开销就越小。因此，检索器返回的内容会直接影响模型负载。第八章将结合具体任务比较不同检索方案。[^retrieval]

**例题 3-2：加速首轮能节省多少任务时间？** 用第一章的 Amdahl 分析，假设后续行为与质量不变。

解： 保持同一条执行轨迹，只改变一个条件：只把首轮 36.375 秒的模型段缩短一半，其余阶段、输出、工具行为和质量都不变，总时间便从 76.510 秒降到 58.323 秒。此时 $f=36.375/76.510$，$s=2$，总加速比约为 1.31；首轮速度提高到两倍的收益受其原有时间占比限制。首轮占总时间约 47.5%，将这一段减半节省约 23.8% 的总时间；其余阶段继续形成约 40.1 秒的固定部分。优化收益由被缩短阶段的原有占比决定。[^agent-speedup]

设模型先计算 2 秒，随后调用两个工具，耗时分别为 6 秒和 10 秒，最后再计算 3 秒。若第二个工具依赖第一个的结果，总时间为 $2+6+10+3=21$ 秒；若工具相互独立，总时间为 $2+\max(6,10)+3=15$ 秒。并行减少了 6 秒，但两个工具的总执行工作仍为 16 秒。

若分支还要分别生成文本，公共前缀可以共享，分支尾部独立增长。设共享前缀长 $H_0$，第 $i$ 个分支新增 $h_i$ 个位置，每位置状态为 $c_{\mathrm{KV}}$，则总状态为 $c_{\mathrm{KV}}(H_0+\sum_i h_i)$。并行一方面缩短关键路径，另一方面让更多分支同时占用状态，需要同时检查时间和容量。

这条轨迹中的工具调用很短，大部分时间都花在模型计算上。若工具改为 10 秒编译，模型暂停的同时，下一轮所需上下文仍占据容量；若多个任务同时等待，驻留量按任务累加。工具执行时间越长，状态保留得越久，系统能同时处理的请求数也会受到影响，第八、九章将在这条时间线上安排缓存与交接。

>
> 一次任务先由模型计算 2 秒，然后调用两个工具，两个工具分别耗时 6 秒和 10 秒。两个工具都完成后，模型再计算 3 秒，任务结束。分别计算两个工具依次执行和同时执行时的任务总耗时。假设仅在等待工具返回期间保留 1 GiB 状态，求两种执行方式下状态占用量与保留时间的乘积，单位为 GiB·s。
>
> 本节的代码任务实测记录显示，任务总耗时为 76.510 秒，其中首轮模型计算耗时 36.375 秒，所有工具执行合计耗时 0.078 秒。保持其余阶段不变，分别计算两种优化能节省多少任务时间：将首轮模型计算速度提高到原来的四倍；将所有工具的执行速度提高到原来的两倍。根据计算结果，解释为什么局部加速倍数不能单独决定一项优化对完整任务的收益。

把同一条会话换成 V4.1，可以看到负载需求如何推动模型结构的变化。设 Agent 已有一段公共上下文，工具随后返回新材料；如果前缀未命中，服务要重新处理较多输入，而本轮输出可能很短。为这样的输入密集场景降低 Prefill 成本，比只优化单步生成更有价值。V4.1 因而使用 20 层因果编码器和 20 层解码器：大部分输入只执行编码器主体，解码器全局 KV 从编码器末层表示投影得到；解码器局部 SWA 则通过提示末尾最多 128 个 token 的编码器输出进行有界重放，近似构建。输出 token 继续经过全部 40 层。[^v41-case]

先计算专家矩阵这一子项，用各 token 经过的专家层数之和表示工作量。设一次从空状态开始的输入为 $P$ 个 token，则普通 40 层路径为 $40P$，论文 CED 调度为 $20P+20\min(P,128)$。当 $P=8192$ 时，两者为 327,680 与 166,400，后者约为前者的 50.8%；当 $P\leq128$ 时，这个子项没有减少。

已有前缀时，输入工作由追加长度与恢复路径共同决定。编码器 SWA 命中，编码器主体便从追加输入继续；编码器 SWA 缺失，则先重放前缀末尾窗口。两条路径随后都要构建本轮的解码器 SWA。第八章将用 8K 与 128K 上下文的教学算例，比较保存状态和重新执行的成本。

## 3.3 多模态与实时交互

Agent 的工具结果通常以文本进入下一轮输入。若输入换成图片或连续语音，调用模型之前还需要编码输入，输出端也可能需要持续播放。我们先看数据在阶段之间怎样改变形状，再看各阶段必须在何时完成。

### 3.3.1 视觉编码、语言生成与状态

图片进入语言模型之前，还要经过预处理、视觉编码和投影。用 $\mathrm E$ 表示视觉编码， $\mathrm P$ 表示语言 prefill， $\mathrm D$ 表示后续 decode，一次视觉问答便有 $\mathrm E\to\mathrm P\to\mathrm D$ 这条基本依赖。图片大小影响 $\mathrm E$，编码后视觉位置数影响语言部分；这两项工作应分别计算。

先数位置，再数每个位置的特征。设预处理后的图片高、宽为 $H_{\mathrm{img}},W_{\mathrm{img}}$，将图片分成方形图像块（patch），每块边长为 $p_{\mathrm{patch}}$，每边再合并 $r$ 个 patch，则视觉位置数为

$$
n_v=\frac{H_{\mathrm{img}}W_{\mathrm{img}}}{p_{\mathrm{patch}}^2r^2}.
$$

Qwen3-VL-4B 的 $640\times640$ 图片，按 $16\times16$ patch 划分得到 1600 个 patch，再作 $2\times2$ 合并，得到 400 个视觉位置。最终特征宽度为 2560，每元素占两字节的 BF16 张量 $[400,2560]$ 占 $400\times2560\times2=2{,}048{,}000$ 字节。

但编码结果不止这一份。为向语言模型提供不同深度的视觉信息，DeepStack 将视觉编码器中间层的特征送入相应语言层。模型还取三个中间视觉层的这类特征，将它们与最终层特征拼接，完整张量为 $[400,10240]$，占 8,192,000 bytes，即 7.8125 MiB。四组特征对应同一组 400 个位置：特征宽度变为四倍，语言序列仍增加 400 个位置。视觉编码的矩阵运算量约为 1.310 TFLOPs；图片解码与缩放发生在编码之前，语言计算则在编码之后。[^vision]

| 完整编码结果 EC | 7.8125 MiB | 图片、预处理、编码器与输出格式一致 |
| 视觉位置的语言 KV | 56.25 MiB | 还依赖先前上下文、顺序、位置与模型状态 |

同一图片回答不同问题时，EC 可能复用；语言 KV 则还要检查问题放在图片前还是后、此前上下文是否改变。**多模态输入的编码状态与 KV 容量预算。** 下面只累计四张图片与 400 个文本位置的有效张量；特殊 token、生成的新位置、分页未用空间和运行工作区在实例容量预算中分别加入。四张相同规格图片的 EC 为 31.25 MiB，视觉位置 KV 为 225 MiB；再加 400 个文本位置，输入逻辑 KV 为 281.25 MiB。这一容量是输入有效位置的逻辑张量大小。

三种数据表示对应三个不同的交接位置。发送原图，接收端还要执行视觉编码；发送 EC，接收端从语言 prefill 开始；发送 KV，则交接已经完成的语言上下文。第八章安排同卡执行，第九章比较阶段交接，第十二章把相同数据流放到端、边、云链路上。

保持 patch 与合并方式不变，将图片两条边都加倍，位置数变为四倍。因此 EC 和视觉位置的语言 KV 都变为四倍；视觉编码内部的位置交互则还要按注意力结构计算。特征拼接增加的是宽度，图片变大增加的是位置数，二者在语言主干中产生不同后果。

### 3.3.2 音频与图像生成的计算过程

视觉问答仍通过语言模型逐 token 生成文本。若输出本身是声音或图像，一次迭代处理的数据和迭代次数也会改变。下面分别看声音与图像的生成过程。

音频输出还有帧内循环。以 Fish Audio 的语音生成模型 S2 Pro 为例，slow（慢速）路径每次推进一个音频帧，fast（快速）路径在帧内补齐多个码本的编号。码本是离散声音表示的候选向量集合，codec（编解码器）将这些编号还原为波形。每帧先用一次 fast 前向建立状态，再用九次预测补齐码本，因此生成一帧需要十次 fast 前向计算。语言 token/s、声学帧/s 与每秒生成多少秒声音因而是不同指标。[^source-1][^media]

图像生成又换了一种循环。latent 是压缩后的连续图像表示；去噪逐步把含噪表示变为目标图像。扩散 Transformer（DiT）执行每步变换，无分类器引导（CFG）组合带条件与无条件两路预测；变分自编码器（VAE）负责像素与压缩表示之间的转换。以 Qwen-Image-2512 为例，$1024\times1024$ 图像形成 4,096 个 latent 位置，执行 50 个去噪步，true CFG 路径每步有两支 DiT 前向，总共执行 100 次 DiT 前向计算。去噪矩阵运算量约 $7.830\times10^{15}$ FLOPs；文本编码器与 VAE 还有各自的工作。latent 的位置集合在去噪期间保持固定，各步持续更新其内容，累计工作随去噪步数增加。[^image]

把每步去噪的运算量记为 $F_{\mathrm{step}}(n_v)$，去噪步数为 $n_s$，每步引导分支数为 $n_b$，总运算量为 $n_sn_bF_{\mathrm{step}}(n_v)$。步数加倍会重复执行两倍工作；分辨率提高会增加图像潜在表示中的空间位置数，从而增加单步内部的矩阵行数和位置间交互。文本生成不断追加上下文，图像去噪反复更新同一组 latent；要先找出循环中究竟改变了哪个量，再判断总成本。

先数实际调用，再比较资源，是这些模型共同需要的步骤。内部循环数决定累计工作，阶段依赖决定哪些时间可以重叠，输出质量决定比较是否成立。

### 3.3.3 连续感知、首段响应与打断

工作总量决定平均处理需求，实时播放还要求每块数据按时到达。令 $A(t)$ 表示截至时刻 $t$ 已到达的可播放音频时长，$P(t)$ 表示已消费的音频时长，缓冲中剩余音频为

$$
B_{\mathrm{audio}}(t)=A(t)-P(t).
$$

播放开始后，$P(t)$ 按每秒一秒音频增长，$A(t)$ 则随数据块到达跳跃增加。两条曲线之间的距离就是缓冲余量；余量降到零而下一块尚未到达，声音就会中断。预缓冲增加初始余量，同时推迟开始播放。

时间要求同时作用于输入和输出。先看输入端：截图 Agent 如果只在动作结束后观察屏幕，就可能漏掉中途出现又消失的弹窗。AOI 是研究持续观察与交互的工作，它将屏幕观测与动作执行分开：持续收集图像、音频和事件，再筛选出供模型使用的记录。增加观测频率可以发现更多短暂事件，但保存更多关键帧也会占用上下文；过多关键帧还可能挤占重要信息，使任务效果下降。[^aoi] 因此，持续观测还要配合筛选，决定哪些内容值得保留并交给模型处理。

语音的时间约束更直接。用户停止说话后，系统要采集或确认输入，经过识别／编码、推理、语音生成和播放。首块在客户端到达，只说明数据已到；扬声器开始出声还取决于解码、缓冲和设备时钟。开始播放后，后续音频还必须及时到达，才能避免中断。

音频块到达应用之后，还要经过解码、排队和播放。两次语音交互测量中，用户停止说话到首块音频到达的时间分别约为 400 ms、370 ms，后续音频块的到达间隔中位数均约为 94 ms。[^audio-real] 到达时间说明数据何时可用，播放时钟则决定数据何时被消费。下面用一条时间线说明两者之间的缓冲如何避免声音中断。

为了看清缓冲的作用，采用下面这组教学参数安排时间线。输入每 20 ms 形成一块，24 kHz、单声道、每样本 2 bytes，每块数据量为：

$$
24{,}000\times0.020\times1\times2=960\ \mathrm{bytes}.
$$

每块采集结束后，模型处理 12 ms、发送 1 ms，通常再传播 5 ms。第一块在 38 ms 到达，等待 40 ms 抖动缓冲后，于从采集起点算起的 78 ms 开始播放。第三块的传播延迟被设为 50 ms，直到 123 ms 才到，错过 118 ms 的播放计划，造成 5 ms 新增停顿。后续块虽已到达，也要按声音顺序等待。

将缓冲改为 60 ms，这次停顿消失，首播却推迟到 98 ms。增加缓冲可以吸收本次抖动，代价是更晚开始；若音频的平均到达速度长期低于播放速度，有限缓冲终究会耗尽。[^audio]

## 3.4 训练的计算与状态需求

### 3.4.1 前向计算、反向传播与参数更新

推理用权重求输出，训练还需要计算怎样调整权重才能降低损失。对线性层 $Y=XW$，输入 $X$ 为 $[m,k]$，权重 $W$ 为 $[k,n]$。损失 $\mathcal L$ 是衡量模型输出与训练目标差异的数值，训练希望降低它；梯度描述损失对某个输入或参数的小变化有多敏感。反向传播从输出端沿依赖逆向传递这些敏感度。设后一层反向传来 $\partial\mathcal L/\partial Y$，当前层需要计算两种梯度：

$$
\frac{\partial\mathcal L}{\partial X}=\frac{\partial\mathcal L}{\partial Y}W^{\mathsf T},\qquad\frac{\partial\mathcal L}{\partial W}=X^{\mathsf T}\frac{\partial\mathcal L}{\partial Y}.
$$

前向计算输出，反向分别计算输入梯度和权重梯度。三次矩阵乘法的运算量相同，因此这一线性层的训练矩阵运算量约为前向的三倍。下表将一次乘加计为两个 FLOPs。

| 操作 | 要解决的问题 | 左、右输入的形状 | 输出形状 | 矩阵 FLOPs |
|---|---|---|---|---|
| 前向 $Y=XW$ | 根据输入求输出 | $[m,k]$ 与 $[k,n]$ | $[m,n]$ | $2mkn$ |
| 输入梯度 $\mathrm dX=\mathrm dY W^{\mathsf T}$ | 将误差传回前一层 | $[m,n]$ 与 $[n,k]$ | $[m,k]$ | $2mkn$ |
| 权重梯度 $\mathrm dW=X^{\mathsf T}\mathrm dY$ | 求这层权重的调整方向 | $[k,m]$ 与 $[m,n]$ | $[k,n]$ | $2mkn$ |

输入梯度把误差信号传给前一层，权重梯度决定本层参数的调整。观察三组矩阵尺寸：虽然乘法顺序不同，三次运算都含有相同的 $mkn$ 个乘加，因此合计约为 $6mkn$ FLOPs。若所有训练 token 都经过同一组主要参数矩阵，累计便得到常见近似 $F_{\mathrm{train}}\approx6ND$，其中 $D$ 为训练 token 总数。[^training]

这一推导也说明怎样处理结构变化。冻结某个权重矩阵后，可省去它的权重梯度计算；若更早的层仍需要梯度，则仍要计算输入梯度。MoE 按选中专家累计两类梯度，注意力则按位置对累计。沿反向依赖逐项累加，就得到各训练方法需要执行的计算量。

反向需要前向留下的信息。计算 $\mathrm dW$ 要使用 $X$，对非线性运算求梯度时，也需要前向计算留下的中间结果，参数梯度在反向中产生，优化器是根据梯度计算参数更新的方法，其状态记录多次更新积累的信息，因此需要保留到下一次更新。它们的寿命不同：某层激活在该层反向结束后可以释放，优化器动量通常一直留到下一次更新。前向产生的激活要等待相应反向才能释放，因此反向传播把中间数据的寿命从相邻算子之间延长到了前后两次遍历之间。

![一层激活从前向完成后保留到相应反向用完。横轴按事件排列，间距表示过程顺序；反向需要的前向输入决定这段存活区间。](ch03/figure-3-activation-lifetime.svg)

**例题 3-3：训练状态为什么超过推理权重数倍？**

解： 以 Qwen3-8B 的 8,190,735,360 个参数为例，保存 BF16 权重、FP32 梯度、一份独立的 FP32 主权重（master weight），以及 Adam 的两个 FP32 矩估计。Adam 是根据梯度及梯度平方的移动平均调节更新幅度的优化器，两个矩估计分别保存这两种平均量。不做分片时，每参数需要 $2+4+4+4+4=18$ bytes，共 147.433 GB，约 137.308 GiB。BF16 权重用于前向和反向计算，梯度用于计算更新量，FP32 主权重用于高精度更新，Adam 的两个矩估计则累计梯度及其平方的统计量。这些数据合计占用的空间，是推理 BF16 权重的九倍。[^train-matrix]

微批次是一次前向和反向实际处理的数据子集；完整训练批可以由多个微批次组成。一个微批次与一次参数更新也要区分。显存放不下完整训练批时，可以分多个微批次累计梯度，最后再更新一次参数。保持目标、有效标签和归一化一致时，将同一训练批拆成更多微批次，会改变执行顺序与激活寿命，而总训练数据量保持不变。第十章将据此讨论分片和流水。

训练过程中还要不断准备下一批输入。CPU 读取、解码、分词并整理批次，再把张量送到设备。双缓冲可以让当前批计算时准备下一批：一个缓冲供计算读取，另一个接收新数据，交替使用。计算耗尽已准备数据时会等待输入，取回设备结果时又会等待相应计算完成。第五章将结合前向、反向和参数更新的执行顺序，分析数据准备与计算如何重叠。

### 3.4.2 预训练、中期训练与 SFT

把一次参数更新所需的完整批次拆成较小批次、逐次执行并累积梯度，这些较小批次称为微批次。训练阶段的名称不同，系统仍要回答同样的问题：输入有多少位置，哪些位置参与损失，多少个微批次后更新一次参数。预训练通常对连续文本做下一 token 预测；中期训练调整数据组成或上下文长度；监督微调（SFT）使用给定输入与目标回答继续训练模型，常把指令与回答放在一起输入，只对回答计算损失。它们的差异通过输入形状、监督位置和更新频率进入资源模型。

Qwen3 的训练过程体现了这些变化：通用阶段在 4096 长度上训练超过 30 万亿 token，随后增加科学、技术、工程与数学（STEM）、代码、推理与合成数据，再训练约 5 万亿 token；长上下文阶段将长度扩至 32768。[^qwen] 数据组成改变学习内容，序列长度还直接改变每个位置可以访问多少前文，因此需要分别观察。

系统需求随长度改变。假设两组独立文档都含 8,192 个 token：一组为 $4096+4096$，另一组为 $7168+1024$。参数投影的行数相同，因果注意力的有效位置对却分别为 16,781,312 和 26,218,496。在 Qwen3-8B 一层上，$QK^{\mathsf T}$ 与 $AV$ 前向工作约从 0.275 增到 0.430 TFLOPs，增加约 56%。较长文档中的位置可以看到更多前文，所以在总行数不变时，上下文交互增加；投影与 FFN 仍处理同样的 8192 个 token 表示。整层增加量由这笔新增交互占原有工作的比例决定。[^training]

SFT 中，模型读取的位置与参与损失计算的位置往往不同。一条样本可以包含系统提示、用户问题、工具结果和回答，但训练只对回答部分计算损失。其余位置仍要经过主干网络，为回答提供上下文。实现还可以只对受监督位置计算词表投影；如果只是屏蔽这些位置的损失，之前的矩阵乘法仍会照常执行。

部分参数训练减少需要保存梯度与优化器状态的参数集合。冻结模块的权重保持不变，但梯度仍需穿过它们传到较早的可训练模块，因此相应输入梯度继续执行。沿反向图逐层判断是否求输入梯度、是否求权重梯度，就能把训练状态与计算分别算清。

微批次与更新数则控制工作的重复次数。设每微批次有 $B_\mu$ 条长度为 $P$ 的序列，累计 $a$ 个微批次后更新一次，则每次更新读取 $aB_\mu P$ 个输入 token。若每条只有 $P_{\mathrm{label}}$ 个监督位置，损失归一化使用的有效 token 数为 $aB_\mu P_{\mathrm{label}}$。增大累计次数可以扩大更新批次，同时让一次更新分多次前反向执行；参数状态一直保留，每个微批次的激活可以在反向完成后释放。

### 3.4.3 从 $6ND$ 估算到逐项计算训练开销

确定训练数据和有效 token 数之后，就可以累计总运算量。先用线性层“训练约为前向三倍”的关系作粗算，再把注意力、词表头和状态更新逐项补回，便能看清粗算与完整模型之间的差距。

以一次完整训练前向和反向为例：Qwen3-8B，$B=1,\ P=8192$，全参数训练，所有位置执行词表头，没有重计算。逐层累计投影、FFN、$QK^{\mathsf T}$、$AV$ 和输出头，矩阵运算量如下。[^train-matrix]

| 矩阵计算 | TFLOPs |
| --- | ---: |
| 前向矩阵 | 143.789 |
| 反向矩阵 | 287.579 |
| 前向加反向 | 431.368 |
| 其中因果注意力 $QK^{\mathsf T}$ 与 $AV$ 前反向 | 59.381 |

把 402.591 TFLOPs 的粗算修正到 431.368 TFLOPs，需要先解释哪些工作被漏掉、哪些被多算。查询与上下文之间的矩阵乘法不对应一份模型参数，却在前反向中贡献 59.381 TFLOPs；另一方面，词嵌入查行等参数并不对每个 token 执行完整矩阵乘法，不能一律按 $6ND$ 计入。两项修正相抵后，总矩阵量比粗算高约 7.15%。

将有效标签数减到 4096，如果仍对全部位置计算词表投影，矩阵运算量就不变。如果先取出有监督位置的隐藏向量，再只对它们执行词表投影，总量则降到 416.074 TFLOPs。主干网络仍处理全部输入，省下的是无监督位置的词表投影；反向时再把梯度放回对应位置。[^mask]

归一化、激活、损失与优化器也需要计算和读写。以参数更新为例，即使序列很短，仍要读写权重、梯度和优化器状态；序列越短，这部分成本在总量中的占比往往越高。因此，训练预算既要考虑随 token 数增长的矩阵计算，也要考虑按参数量发生的更新开销。[^nonmatrix]

模型新增的前向操作，也会增加对应的反向计算。上下文压缩需要对投影、池化和状态更新求梯度，mHC（流形约束超连接，通过受约束的混合连接多条残差通路）需要向各通路传播梯度，MoE 则要对实际选中的专家求梯度。[^v4-training] 第二章的计算图因而也能帮助我们判断：训练时要保存哪些中间结果，反向又要执行哪些运算。

因此，序列长度变化时可以先判断各项开销的变化趋势：参数投影随输入行数增长，注意力随位置对数增长，优化器更新随参数量和更新次数增长。若通过重计算减少保存的激活，容量下降，但被重做的前向运算还要加回 $F_{\mathrm{train}}$。这些变化都能沿同一张前向—反向图逐项解释。

## 3.5 强化学习（RL）

### 3.5.1 Rollout、奖励与环境验证

前面的推理从外部请求开始，预训练从已有文本开始。强化学习（RL）通过行动得到的反馈改进后续行动。在语言模型中，策略是给定上下文时选择下一个 token 的概率分布。RL 把两条路径接起来：当前策略先生成回答，再由反馈决定怎样更新参数，更新后的策略继续产生下一批数据。生成过程通常称为 rollout。

DeepSeek-R1 提供了从推理任务和可验证奖励出发的训练路线。对代码、数学等容易检查的任务，反馈可以来自规则或测试；对需要实际操作的任务，则要运行工具与环境。奖励是用来评价一次回答或行动效果的数值。奖励若由另一个模型生成，还会产生额外推理。一次“训练迭代”因此可能包含多个模型、CPU 测试、沙箱等待和梯度更新。[^r1]

DeepSeek V4-Flash 先通过 SFT 和 RL 训练领域专家，再以多教师的在策略蒸馏（on-policy distillation，OPD）将能力合入统一模型。蒸馏让学生模型学习教师模型给出的输出信息；在策略蒸馏由当前学生自己生成轨迹，教师在这些位置提供候选输出的概率分布，学生据此学习。教师前向因此成为生成与更新之间的一项模型工作；规则验证则以测试或程序执行提供反馈，需要另一组计算资源。[^v4]

沿这个循环分析资源时，先找数据的生产者和消费者：策略生成 token，奖励函数或教师读取回答，学习器读取训练样本并产生新权重，生成副本再使用新权重。某一角色慢下来，会让后继角色等待；增加教师则新增一段前向计算和模型容量。后续的并行安排都必须建立在这张依赖图上。

### 3.5.2 有效样本、策略更新与权重同步

生成回答和计算奖励之后，还要决定哪些样本用于学习。这里的关键是区分已经生成的样本与最终进入更新的样本：前者决定生成开销，后者决定训练批次，两者的数量未必相同。

设一轮需要保留 $n_{\mathrm{keep}}$ 条样本，生成样本的平均保留比例为 $a$，则所需生成数的期望为

$$
n_{\mathrm{generate}}\approx\frac{n_{\mathrm{keep}}}{a}.
$$

保留 16 条样本，比例为一半时平均需要生成 32 条，降为四分之一时平均需要 64 条。生成和评分处理全部回答，参数更新只处理保留样本；保留比例下降会扩大前两个阶段，而不会按同样比例扩大更新批次。下一节用等长样本的确定数量比较这两种情况。

是否保留一条样本，由训练方法及筛选规则决定。有的方法把失败回答作为负反馈，有的方法排除截断或奖励无效的回答。优势表示某个回答相对于比较基准更好或更差的程度。采用组内相对优势时，还要比较同一道题多份回答的奖励。因此，保留样本数决定更新时处理多少数据，奖励和损失函数则决定这些数据产生怎样的梯度。

**例子：相同奖励怎样消除组内学习信号。** 在使用组内相对奖励的策略更新中，如果同组回答得到相同奖励，减去组内平均奖励后，每条回答的优势都为零，相应的策略梯度也为零。回答全部正确就可能出现这种情况。模型完成了生成、评分和更新流程，却没有从这一组回答中获得区分优劣的信号。只有奖励差异提供了非零优势，策略损失才会推动参数沿相应方向调整。[^verl]

损失的求平均方式也会影响训练。若目标是对整批有效 token 求平均，累计各微批次梯度时就要使用整批的有效 token 总数作为分母。若先分别计算每个微批次的均值，再对这些均值求平均，有效 token 较少的微批次中的 token 就可能获得更大权重。第十章将用具体训练方法解释这种差别。[^verl-loss]

更新后还要把策略权重送给生成端。若生成端继续使用旧版本，下一批数据对应的策略就不同。同步循环可以等权重就绪后再生成；异步方案允许部分阶段重叠，却要处理样本版本与滞后。本章先明确这一依赖关系，第十章再讨论交接、抢占、恢复和资源配比。

### 3.5.3 有效样本数固定时，各阶段需要多少计算

这种区分可以用一个固定目标来量化：每轮都要保留 16 条样本用于更新。如果回答更难通过筛选，就必须先生成更多回答。下面保持更新批次不变，只增加为得到这批样本所需的生成和评分。

## 3.6 从负载需求到训练与服务预算

### 3.6.1 Scaling Law：模型规模与数据量的关系

单次更新的计算已经可以逐项求出，接下来要决定训练多少参数、使用多少数据。设总训练计算预算为 $C$，参数数为 $N$，训练 token 数为 $D$，主要计算近似满足 $C=6ND$。增加 $N$ 就必须减少 $D$。要在两者之间作选择，需要知道它们分别怎样影响质量，Scaling Law（规模规律）用实验拟合模型规模、训练数据和损失之间的关系。下面采用参数与数据两项都为正、训练配置和损失评估方式固定的幂律模型：

$$
L(N,D)=E+\frac{A}{N^{\alpha}}+\frac{B}{D^{\beta}}.
$$

$L$ 是验证损失，$E$ 是模型中的渐近损失，$A/N^\alpha$ 描述参数规模不足的影响，$B/D^\beta$ 描述数据量不足的影响。这里的 $A,B,\alpha,\beta$ 都是拟合系数。单独增加参数或数据会降低对应项；固定计算预算时，两项却向相反方向变化。

用 $D=C/(6N)$ 消去数据量，再对 $N$ 求导。最优点满足

$$
\alpha A N^{-\alpha-1}=\beta B\left(\frac6C\right)^\beta N^{\beta-1}.
$$

左侧是增加参数带来的损失下降，右侧是减少数据造成的损失上升；两者相等时，再小幅改变参数量已经没有净收益。整理得到：

$$
N_{\mathrm{opt}}=\left(\frac{\alpha A}{\beta B}\right)^{1/(\alpha+\beta)}\left(\frac{C}{6}\right)^{\beta/(\alpha+\beta)}.
$$

在 $A,B,\alpha,\beta$ 均为正的拟合模型中，增加参数量会减小 $A/N^\alpha$，降低模型规模不足造成的损失；但总计算量固定时，可用于训练的数据量随之减少，$B/D^\beta$ 又会增大。令导数为零，就是寻找两种影响相抵的位置。由此得到的 $N_{\mathrm{opt}}$ 是连续取值的结果，实际设计时可在它附近选择合适的层数和宽度。

Kaplan 等人的早期研究给出约 $N\propto C^{0.73},\ D\propto C^{0.27}$ 的分配关系；Chinchilla 研究用不同实验和拟合，得到模型规模与数据量应随预算更接近等比例增长的结果。前一种分配更快增加模型参数，后一种把更多新增预算分给训练数据；曲线及其拟合指数因此直接改变参数与数据的选择。[^scaling]

训练本身也存在波动。同样的数据与模型规模，改变随机初始化就可能得到不同的学习曲线；较大模型在训练尚未充分时，也未必优于较小模型。使用多个随机种子重复训练，可以区分规模变化带来的趋势与单次训练的偶然波动。[^local-train]

长期服务会把每次调用的成本累积到训练预算之上。较小模型可以通过更长训练达到目标质量，前期多付成本，之后每次调用读取更少权重、执行更少工作。Beyond Chinchilla-Optimal 将这种推理需求纳入分析，47 个模型覆盖 150M–6B；其中 150M 模型测试到 10,000 token／参数，较大模型测试到 1,000。[^beyond] 训练预算与服务次数共同决定较小模型的额外训练何时收回成本。

### 3.6.2 从 Llama 到 Qwen 的训练投入

从各报告披露的阶段和规模，可以看到一个趋势：相近的 7–8B 参数规模，训练 token 数持续增加。[^history]

| --- | ---: | ---: | ---: |
| Llama 1，6.7B | 1T | 149 | $4.02\times10^{22}$ FLOPs |
| Llama 2，约 7B | 2T | 286 | $8.40\times10^{22}$ FLOPs |
| Llama 3.1，约 8B | 约 15T | 约 1,875 | 约 $7.20\times10^{23}$ FLOPs |

$D/N$ 将数据投入换成“每个参数对应多少训练 token”。表中约 7—8B 的稠密模型，从约 149 增至约 4500，说明参数量相近的模型，训练数据量也可以相差很大。前期训练成本随数据增加，部署后每次调用的权重容量却仍主要由参数数量决定。因此，更充分训练的小模型可能增加一次性投入，同时降低长期服务成本。

更长训练、数据筛选、蒸馏和后训练，把更多前期工作用于提高给定规模模型的任务能力。Llama 3 模型卡的基础模型评测中，Llama 3 8B 与 Llama 2 70B 在覆盖多学科选择题的 MMLU 基准上分别为 66.6／69.7，使用维基百科证据的问答基准 TriviaQA-Wiki 为 78.5／87.5。[^cost] 两项差距不同，说明部署方要按自己的任务选择质量要求；通过门槛的小模型，才有机会把较小权重带来的容量与读取收益转成服务收益。

分析大模型和 MoE 时，则要分别列出总参数量与激活参数量。DeepSeek-V3 报告为总参数 671B、每 token 激活约 37B、预训练 14.8T；DeepSeek V4-Flash 为 284B／约 13B、32T，DeepSeek V4-Pro 为 1.6T／约 49B、33T。总权重影响容量，激活参数只提供计算量的粗略估计。DeepSeek V4-Flash 主干专家的三个投影可单独计算：

$$

$$

$$
T_{\mathrm{calendar}}=\frac{H_{\mathrm{GPU}}}{n_{\mathrm{GPU}}}.
$$

Llama 1 65B 的训练消耗 1,022,362 A100 GPU 小时。持续使用 2048 张卡，对应约 499.2 小时，即 20.80 天；在相同设备效率下只使用一半卡数，则需要约 41.60 天。设备小时体现总投入，卡数决定完成这些工作需要多少实际时间。

### 3.6.3 满足质量要求的全生命周期成本

现在把前三章的分析合在一起。模型结构决定每次调用的容量、运算和读取，负载决定调用次数与等待，训练决定上线前的投入。设模型 $m$ 的前期成本为 $C_0(m)$，未来有 $Q$ 个任务，第 $j$ 类占比为 $w_j$、完成一个任务的平均成本为 $c_j(m)$，则

$$
C_{\mathrm{life}}(m)=C_0(m)+Q\sum_jw_jc_j(m).
$$

比较之前，各模型都要满足相同质量、时限与完成条件。若任务成功率不同，$c_j$ 中还需包含失败和重试；价格变化、模型寿命、维护与贴现等假设也应随预算说明。

考虑都满足任务质量和时限的两个模型。若较小模型需要额外训练成本 $\Delta C_0$，但每个成功任务能节省 $\Delta c>0$，累计成本相等的调用量为

$$
Q_* = \frac{\Delta C_0}{\Delta c}.
$$

额外投入 100 万美元、每任务节省 0.002 美元时，$Q_*=5\times10^8$，即五亿次任务。预期需求低于这个量，额外训练成本尚未收回；高于这个量，较小模型累计节省更多。容量、延迟、质量和调用量共同决定选择，单看模型大小或 token 单价无法完成这一判断。

> **练习 3-10〔延伸〕：训练完成时间与累计服务成本**
>
> 将 1,022,362 GPU 小时分别分配给 2048 与 1024 张同类设备，求训练从开始到完成所需的实际天数。再比较两个满足相同质量与时限的模型：小模型多投入 100 万美元训练，每个成功任务节省 0.002 美元。预计服务两亿次和十亿次时分别选哪个？计算总成本差，并说明若实际任务量发生变化，选择会在何处反转。

后续章节将使用本章整理出的三类负载信息。下表列出各类负载需要记录的内容，以及这些信息将用于哪些系统设计问题。

| 负载 | 必须保留的字段 | 后续使用 |
| --- | --- | --- |
| Chat／Agent | 任务检查、模型与版本、每轮输入／命中／输出、到达、工具依赖、分支与复用间隔 | 第 8 章安排批处理与状态；第 9 章交接与路由；第 11 章管理工具环境 |
| 视觉／实时 | 原图字节、$\mathrm E/\mathrm P/\mathrm D$、EC/KV、帧或块到达、首次响应时间／连续播放要求、打断与过期工作 | 第 8、9 章安排编码和交接；第 12 章加入链路与执行位置 |

这三类例子都说明，描述负载需要记录具体的执行过程。两分钟请求中，各时段的输入输出比例决定积压何时出现；代码 Agent 中，工具依赖决定等待时间和状态保存多久；RL 中，筛选前后的样本数决定生成与更新各处理多少数据。掌握这些信息，才能为各阶段安排资源。

训练预算下的最优规模与长期服务的最优规模，也可能不同。固定训练计算量时，参数与训练 token 之间存在折中；若模型还要服务大量请求，多训练一个较小模型，可能用一次性训练投入换取持续较低的推理成本。Llama 3 报告说明，小模型会通过更长时间的训练提高能力，以满足推理成本要求。计算生命周期成本时，应将训练投入、预期服务量、每次任务成本和模型有效寿命分别列出。专用硬件若需要较长部署周期，模型版本能使用多久也会成为这一选择的条件。

## 谬误与陷阱

**均值相同就是同一负载。** 少量超长请求、输入与输出长度的组合、请求到达顺序，都会影响短时间内的资源需求。例题 3-1 中，处理能力足以应付平均到达量，后一分钟却仍会积压。

**token 更便宜，完成任务也更便宜。** 额外思考、未通过检查的回答、工具与环境都应进入分子，合格任务数进入分母。零成功的批次只能报告消耗与失败，不能估计成功成本。

**训练了相同数量的 token，系统工作就相同。** 序列分布改变注意力位置对，标签与词表头策略改变输出工作，更新次数改变优化器成本；RL 还包含未被采用的回答的生成与反馈。

## 本章小结

持续服务的负载既取决于每次请求要做多少工作，也取决于请求何时到达、各步如何等待。平均速率可以粗略估算所需资源，分析短时间内的积压和状态保存时间，则能发现平均值未体现的资源压力。多轮任务还包含工具等待与失败尝试，实时任务要保证数据及时到达，训练则增加反向、参数更新和权重同步。

比较不同方案的资源与成本时，应采用相同的质量要求和任务完成标准。Scaling Law 为训练分配提供可检验的统计模型，长期服务需求又可能改变前期投入的选择。核心练习 3-2、3-4、3-7 分别把这些方法用于持续请求、交互任务和 RL 循环。
