# 四 · 不足：推理引擎的暗面

## 4.1 首 token 延迟：被平均数掩盖的痛

continuous batching 优化的是吞吐-**平均**延迟，但交互产品的体验由 **TTFT（首 token 时间）** 和 **TPOT（每 token 时间）** 两个分离指标决定。暗面在于：

- 长 prompt 的 prefill 是 compute-bound 大活（02.3 节），塞进 decode 流会卡住所有人的下一步——于是有了 **chunked prefill**（把长 prefill 切片分步执行）；
- 但切片又拉长了自己的 TTFT。**TTFT vs 吞吐是一根新的跷跷板**，vLLM/SGLang 的调度参数（`max_num_batched_tokens` 等）全在这根跷跷板上找座——没有最优解，只有业务定位。

## 4.2 长尾与饥饿：调度器的原罪

03 幕的"练习二"埋了伏笔：任何优先级策略都会制造饥饿面——短请求插队越爽，长请求 P99 越惨。真实引擎的调度器（vLLM 的 `Scheduler`、SGLang 的轮转策略）本质是在**公平性/延迟/吞吐三角**里做仲裁，而仲裁规则越多：

- **复杂度税**：调度器本身变成性能瓶颈（每步的调度决策在 CPU 上做，GPU 在等）——vLLM 后来把调度重叠化（CPU 调度下一步与 GPU 执行当前步并行）就是在还这笔税；
- **可预测性丧失**：同一请求在空载与满载系统的延迟差可达 10 倍，"GPU 分钟"计费模型对延迟敏感业务是错的度量。

## 4.3 KV 碎片与块大小：PagedAttention 的次生问题

PagedAttention 把 KV 切成固定块（vLL默认 16 token/块）解决外部碎片，但引入：

- **内部碎片**：最后一块平均浪费半块（长尾序列下浪费率可观）；
- **块表间接层**：每次 attention 多一次块表查找，kernel 变复杂；
- **块大小的权衡**：大块省元数据但碎片多，小块反之——又是没有解析解的调参。

再往上是 KV 的**复用失效**：RadixAttention 靠前缀树共享 KV，但多轮对话的"滚动窗口+改写历史"（agent 场景常见）会让前缀失效，命中率崩塌——[讲透SGLang](../../02-透/讲透SGLang/README.md) 的精讲里有这类真实语义与缓存假设错位的案例。

## 4.4 引擎战争的真实代价

vLLM/SGLang/TensorRT-LLM 三强并立的另一面：

- **功能赛跑压过正确性**：连续批/分块 prefill/投机解码每个新机制都是新的数值一致性风险面（本仓 [讲透TileKernels](../../02-透/讲透TileKernels/README.md) 精读里的位级断言 `torch.equal` 融合验证——业界对"融合零数值代价"的证明义务正在变严）；
- **结构化输出的暗坑**：JSON mode 依赖约束解码（[讲透XGrammar](../../02-透/讲透XGrammar/README.md)：高效 token 掩码），但语法越严、掩码计算越重，极端 grammar 下吞吐掉数倍；
- **可移植性幻觉**：CUDA graph 重放、P2P、定制 kernel 让"换个 GPU 厂商"变成重构级工程——[讲透TIRx](../../02-透/讲透TIRx/README.md)（沐曦 kernel 库）、[讲透WebLLM](../../02-透/讲透WebLLM/README.md)（WebGPU 端侧）各自重走一遍引擎路，正是这个暗面的产业倒影。

## 4.5 一个元教训：模拟器的边界

03 幕模拟器给出的 1.93x 是**调度粒度的净收益**，真实引擎收益通常更高（还有 PagedAttention 的容量增益）也可能更低（调度开销/同步成本）——**模拟器证明的是机制存在，不是工程数值**。把教学模拟的数字直接当 benchmark 引用，是本仓反幻觉纪律（宣称必须实测+口径声明）明令禁止的行为。
