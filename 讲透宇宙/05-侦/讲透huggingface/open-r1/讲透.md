# 讲透 Hugging Face Open-R1

> 仓库：huggingface/open-r1（本地 `/usr-data/data2/repos/open-r1`，76 文件入库分析）
> 产物：`.understand-anything/intermediate/batch-1..11.json`（184 节点 / 367 边），本文行号全部源码核实。

## 一、定位：R1 复现的「训练脚手架 + 评测基座」

README 自述："A fully open reproduction of DeepSeek-R1"，三步计划（README L30-38）：Step 1 蒸馏 R1-Distill（已收官，产出 Mixture-of-Thoughts 35 万条验证轨迹与 OpenR1-Distill-7B）；Step 2 复现 R1-Zero 纯 RL 管线；Step 3 从基座到 RL 的多阶段训练。

一个常见误读需要钉正：**它不是自研 RL 框架，而是 TRL 的薄壳**。核心训练只有两个入口脚本——`src/open_r1/sft.py` 与 `src/open_r1/grpo.py`，分别把数据/模型/奖励装配好后交给 `trl.SFTTrainer`（sft.py L101-109）与 `trl.GRPOTrainer`（grpo.py L112-121），依赖钉版 `trl[vllm]==0.18.0`（setup.py L72）。同样，数据生成走 distilabel（generate.py L17-20），推理服务走 vLLM/SGLang 双线。**仓库真正的增量价值在三块**：可插拔的奖励函数库、把代码评测搬进沙箱的执行基座、以及 Slurm 大规模编排——这些是 TRL 不管的「RL 管线缺失件」。

## 二、架构总览：五层流水线

```
recipes/*.yaml（配置）
   └─> slurm/train.slurm（grep 解析 YAML → accelerate 多机拉起）
         └─> src/open_r1/{sft,grpo}.py（TRL Trainer 装配）
               ├─ configs.py（参数 dataclass + dataset_mixture）
               ├─ utils/data.py（加权混合采样）
               ├─ rewards.py（12 种奖励注册表）
               │     └─ 沙箱执行层：E2B / Morph / Piston 三 provider
               │           ├ 直连：code_providers.py / piston_client.py / morph_client.py
               │           └ 路由：e2b_router.py / morph_router.py（FastAPI 批量服务）
               └─ callbacks.py（存盘即推 Hub revision → 级联触发评测）
评测线：evaluation.py --sbatch--> slurm/evaluate.slurm（lighteval vllm）
数据线：generate.slurm（Ray+vLLM）→ generate.py（distilabel）
       → compute_pass_rate.py（通过率过滤）→ decontaminate.py（8-gram 去污染）
```

分布式三件套：训练用 accelerate（DDP/ZeRO-2/ZeRO-3/FSDP 四配置，recipes/accelerate_configs/），生成用 Ray 编排 vLLM（generate.slurm L175-186 以 ray job 提交 `vllm serve`），GRPO 的 rollouts 用 `trl vllm-serve` 独占末节点（train.slurm L123-133：检测 `use_vllm: true` 后把最后一台机器从训练世界剥离，注入 `--vllm_server_host`）。

## 三、核心模块

### 1. 奖励函数库 rewards.py（706 行，灵魂文件）

`get_reward_funcs`（L646-706）维护 12 项注册表，按 `script_args.reward_funcs` 名单装配（L704），带参奖励用 `partial+update_wrapper` 压平签名——GRPOConfig 里配字符串，训练时拿到的就是可直接调的函数。四类奖励：

- **数学正确性**：`accuracy_reward`（L40-82）用 math_verify 的 `parse/verify` 对比 gold 与 boxed 答案，不可解析的 gold 返回 None 让样本跳过而非误罚；
- **格式契约**：`format_reward`（L85-90）强制 `<think>...</think>\n<answer>...</answer>` 整体匹配，`tag_count_reward` 部分给分；
- **长度与惩罚**：Kimi 1.5 式 `len_reward`（L132-202）、cosine 缩放（L205-282）、DR-GRPO 的 n-gram 重复惩罚（L285-354，中文走 jieba 延迟 import）、DAPO Eq.13 软超长惩罚（L620-643）；
- **代码执行奖励**：`code_reward`（L511-592）把评测脚本模板注入沙箱跑 `verification_info` 测试；`ioi_code_reward`/`cf_code_reward`（L367-473）对接信息奥赛与 Codeforces 评分器，支持 `test_batch_size` 分批评测「失败即停」省评测机。

### 2. 沙箱执行层（仓库最重的工程投入）

三个 provider 各有直连与路由两形态。抽象基类 `CodeExecutionProvider`（code_providers.py L46-60）只定一个 `execute_scripts` 接口；`E2BProvider`（L63-166）三层超时保险（沙箱 30s/请求 28s/asyncio 32s，L141-144，注释说明 AsyncSandbox 自带超时不可靠）；`get_provider` 工厂（L339-366）按名分发。竞赛题专用的是 `piston_client.py`：`PistonClient`（L36-198）用 asyncio.Queue 令牌做多端点负载均衡+指数退避重试+不健康节点摘除；`get_piston_client_from_env`（L17-33）支持 `PISTON_ENDPOINTS=slurm` 从 squeue 动态发现 worker，多 GPU 训练时按 LOCAL_RANK/WORLD_SIZE 条带划分端点（L26-30）——每个训练进程独占一组评测机。742 行的 `morph_client.py` 则把 Piston 载荷翻译成 CMS 语义，自动从 `manager.cpp` 识别 Communication 型任务（L107-116 附近）。路由形态（e2b_router.py/morph_router.py）是 FastAPI `/execute_batch` 批量服务，配 slurm 常驻。

### 3. 数据管线

`configs.py` 的 `ScriptArguments`（L43-120）支持 `dataset_mixture`：多数据集按 weight 采样拼接（`__post_init__` 归一化并强制列名一致）；`utils/data.py:get_dataset`（L16-65）执行 shuffle+select+concatenate。上游生产链：vLLM 生成 → 奖励打分 → `compute_pass_rate.py` 按通过率区间过滤（L78-89，`filt-0.1-0.6` 这类 config 名落 Hub revision）→ `decontaminate.py` 8-gram 去污染（L51-61 倒排查表）。DAPO-Math 过滤数据集就是这么产出的。

### 4. 训练外围：回调与 Hub 版本化

`PushToHubRevisionCallback`（callbacks.py L43-77）在 on_save 时把 checkpoint 推到 `step-000000123` 式分支（hub.py L39-67 `run_as_future` 异步上传），Slurm 可用时在 future 完成回调里接着提交基准评测——存盘、版本化、评测一条链。两处工程坑值得学：DummyConfig 规避 `dataclasses.replace` 破坏分布式状态（L46 WARNING 注释钉版）；evaluation.py 的 `VLLM_SLURM_PREFIX`（L21-26）用 `env -i` 清环境再 source profile.d 才能在 Slurm 作业里起 vLLM，system_prompt 走 base64 穿引号。

## 四、使用建议

- **想跑 GRPO**：从 `recipes/Qwen2.5-1.5B-Instruct/grpo/config_demo.yaml` 三连（数学/代码/IOI）起步，改数据集与 reward_funcs 即可；上集群抄 `recipes/README.md` 的 sbatch 命令，32B 以上学 OlympicCoder-32B 用 FSDP+paged AdamW 8bit。
- **想加自定义奖励**：在 rewards.py 写函数进注册表即可，签名约定 `completions + **kwargs`（数据集列会透传进来，如 verification_info/id/language）。
- **评测机不够**：本地 Docker 起 Piston（slurm/piston/README.md 有现成命令，注意 sed 放宽 512mb body 限制是硬前提）或自建 router；`piston-worker-<port>` 命名是自动发现契约，别改。
- **别踩**：依赖以 `deps_list` 钉版（setup.py L46 注释明言快变的 trl 必须钉），math-verify==0.5.2（L60）与答案判定语义强耦合，升版本前先跑 tests/test_rewards.py。

## 五、甄别与勘误（源码实证）

1. 任务书预设「rllm 框架」不成立：全仓零 rllm 引用，训练是 TRL、生成是 distilabel（generate.py L17-20 实证）；
2. 「slurm/podman 分布式」中 podman 不存在：容器只有 Piston 的 Docker 部署线，分布式靠 Slurm+accelerate+Ray；
3. `code_reward` 的输出比对是逐行字符串精确匹配，模板里留着 TODO（rewards.py L552）——别当语义评测用；
4. `binary_code_reward` 阈值 0.99（L499）而非字面的 1.0；
5. scanner 对 scripts/ 目录的 open_r1 导入全部漏解析（benchmark_e2b.py L31、compute_pass_rate.py L28-30 等 6 处），本图谱已按 depends_on 0.6 补边——若用此图谱做下游分析，scripts 与主库的耦合比原始 import 数据显示的强；
6. `morph_client.py` 与 `ioi_scoring.py` 大量逻辑藏在字符串内嵌 shell 脚本里（compile/run 脚本），静态分析工具会低估其复杂度。
