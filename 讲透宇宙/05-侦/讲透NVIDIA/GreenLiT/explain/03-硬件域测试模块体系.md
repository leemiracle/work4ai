# 03 · 硬件域测试模块体系：src/modules/ 全景与质量防线

## ① 角色定位

`src/modules/` 是 GreenLiT 的主体资产：20 个域目录、48 个 `glt_test_*.py`、103 个 `@GLTCore.GLTTestAttr()` 装饰测试（实测）。每个目录名即一个 category——CLI 扫目录名生成 flag、`_extract_cat` 从路径推断归属（见篇 1）——**目录即注册**。`tests/` 是框架质量防线：96 个测试类继承 `GLTTestBase`（tests/test_base.py:8）。本篇给 20 域全景+三个典型域+tests 层双导入根。

## ② 内部结构

**域规模三梯队**（文件/行，实测）：重镇 arm64（10 文件 4360 行）、cpu（5/3686）、pci（2/1625）、i2c（2/1412）、cxl（1/1116）、irqchip（1/761）、iommu（2/1001）、mm（4/975）；中坚 acpi（3/494）、gpu（5/546）、hwtracing（2/467）、gpio（1/264）、virt（3/315）、tpm（1/227）、irq（2/123）；轻量 rtc/system/ipmi/power（各 1 文件 38-71 行）。**流水线实证**：mtd 是空壳域——只有 `__init__.py` 零测试。

每域三类资产：纯 Python 测试；Python+C 探针子目录（pci/aspm、mm 的 bingo/contpte/hotplug_tlb/sva、arm64/cppc、i2c/kretprobes、iommu/nested_ste 等，机制见篇 2）；与 00_default.yaml 的配置联动。

tests 层骨架在 `GLTTestBase.setUp`（tests/test_base.py:13-21）：project_root（L15-17 两次 dirname）、test_data_dir（L18）、mock/mock_logger/mock_sd 三个 MagicMock 夹具（L19-21）——96 个测试类经此获得统一 harness。

## ③ 外部连接

模块层对外五条线：**glt_core 协议**——所有测试以 `@GLTCore.GLTTestAttr()`+`@GLTCore.GLTPlan()` 声明，函数签名统一 `def test_x(sd, logger)`；**打包**——pyproject.toml:13-16 把 greenlit/common/modules/scripts 四包从 src/ 平铺安装，运行态 import 根是 `common.*`；**配置**——00_default.yaml:1-25 给 test_all_pmu_events 挂 3 条 allow-failure（Ubuntu 20.04/RHEL 9.5/NFS 脚本）+2 条 conditional-skip；**外部测试**——`external` 虚拟域（glt_ext_launcher.py:12）把 external_tests/ 的 shell 包装成带 attr 的测试；**pytest 单测**——tests/ 下 45 处 `from src.common import` 对 32 处 `from common import` 并存（见⑤）。

## ④ 数据流

典型域一：**arm64 PMU**（glt_test_pmu.py:683 `test_all_pmu_events`）。门禁先行：非 Grace/Vera 直接 skip（L687-688，`NvDev().is_cpu_type`）；`perf_utils.resolve_perf_command()`（L690）解决 perf 不在 PATH；`run_perf_test_candidates`（L694-697）跑 perf 子测试并解析。Grace/Vera 分叉校验 validate_grace/vera_pmus（L670-674）。allow-failure/conditional-skip 全由 00_default.yaml:1-25 运行前注入，配置与代码解耦。

典型域二：**hwtracing CoreSight**（glt_test_coresight.py）。"control/trigger 差一法"样板：glt_test_coresight.py:32-37 注释钉死边界——可用动态 trace ID 仅 1..0x6F（111 个），perf 每 CPU 开一个 cs_etm 事件，超限即 mmap ENOMEM（352-CPU Vera CX 实测：111 CPU 干净、112 失败）；阈值常量 112/111（L37/L43）。测试 `test_perf_cs_etm_multisocket_trace_id_map`（L229，JIRA DGX-10931 在 L231）跑两遍 perf record：control 111 CPU（修复/未修复都必须成功）+trigger 112 CPU（仅未修复失败）——两变量只差一个 CPU，把泛用 ENOMEM 归因到全局 trace ID map（docstring L238-247）。

典型域三：**cpu 门面测试**（glt_test_cpu_info.py:28 `test_vera_lscpu_model_name`）：`EXPECTED_MODEL_NAME="Olympus"`（L22），lscpu 型号不符即 fail 并指路 util-linux commit 9087774——最小可抄样板。

## ⑤ 设计决策

**目录即类别**：零注册、零配置，新域=新目录+architecture.md 更新（CLAUDE.md 明文要求，漏更即违反边界）。代价是空壳域（mtd）无人察觉。

**平台门禁前置**：所有平台相关测试先 `is_cpu_type`/BDF 探测再 skip（glt_test_pmu.py:687-688、glt_test_cpu_info.py:35-36），而非跑一半 fail——skip 语义=「本机不适用」，fail 语义=「适用但坏了」，两者在报告里权重完全不同。

**一个测试一个内核 commit**：docstring 普遍带 JIRA+PATCH（glt_test_coresight.py:231 的 DGX-10931、cpu_info 的 util-linux 9087774、篇 2 的 6d4266675279），测试即补丁回归器。

**流水线实证（甄别三条）**：①nv_device.py:119-120 `has_hopper_gpu` docstring 写反——"Returns True..."与"Returns False if system has hopper GPU"两行都是 True，函数实现正确、文档自相矛盾；②glt_test_tpm.py:42-44 `test_nvidia_tpm` 是 3 行占位——docstring"Run TPM tests"+`logger.info("PASS.")`，恒 PASS 无断言，TPM 域其余真测试在 227 行文件的后半段；③双导入根是历史层积：运行态 `common.*`（pyproject 平铺安装）vs pytest 收集态 `src.common.*`（仓根相对导入），45:32 并存，test_perf_coresight_compat.py:11-21 同文件混用双根且 mock 互证——但 mock 必须写被测模块实际加载路径，最常踩的坑是 patch 错根。

## ⑥ 新人提示

1. 加新城按 CLAUDE.md：同步更新 docs/developer-docs/architecture.md，别忘了；mtd 前车之鉴——建目录不建测试就是死目录。
2. 找样板分级抄：最小门面 cpu/glt_test_cpu_info.py:25-50；配置联动 arm64/glt_test_pmu.py:680-702；探针域看篇 2；差一法看 coresight。
3. 写单测继承 `GLTTestBase`（tests/test_base.py:8）即得 mock_logger 等；mock 路径先看被测模块在 tests 里是 `src.` 还是裸 `common` 导入，patch 跟着走。
4. 报告里的 SKIPPED 多为平台门禁，先看 reason 再怀疑代码。
5. 占位与文档漂移（⑤三条实证）是阅读时的地雷：引用 has_hopper_gpu 行为看代码别看 docstring；见到恒 PASS 的测试先查它是不是没写完。
