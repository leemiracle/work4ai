# 12 基建与协作资产：docker 双轨、GitLab CI 编排、skills 生态与 agent 协作约定

## 一、角色定位

Megatron-LM 罕见地"把 CI 基建当产品经营"：开源面朴素，内里面向 NVIDIA 内部 GitLab（ADLR namespace）跑多集群流水线，加上 14 个带 sigstore 签名与三级评测报告的 agent skills、AGENTS.md/CLAUDE.md 孪生契约。本篇覆盖 docker 双轨镜像、GitLab 七阶段编排、收敛测试 recipes YAML、skills 生态——构成"人类 + AI agent 共同开发巨型训练框架"的底座。

## 二、内部结构

**docker CI 双轨**：`Dockerfile.ci.dev:4` 的 ARG 默认 `nvcr.io/nvidia/pytorch:26.06-py3` 浮动月度 tag；`Dockerfile.ci.lts` 头注释（:6-11）写明意图——LTS 一年 bump 一次、故意落后 dev，依赖**直接钉在 Dockerfile 与 `docker/lts/requirements.txt`** 而非 pyproject.toml（"让 pyproject 承载 inference/RL/MoE extras 而不与 LTS pin 冲突"），FROM 用无默认 ARG 注入。dev 版 uv 0.7.2 连 sha256 钉死（:8、:36-37），含 NCCL 重装开关（:11-13）。**jet-client 双代差**：两 Dockerfile 的 `FROM main AS jet` stage（dev:282/lts:114）在同一镜像装两代工具——`/opt/jet` 独立 venv 装 `jet-api==$JET_API_VERSION`（精确钉版，连带 `setuptools<82.0.0`，dev:288-289），主 venv 用 uv 装 `jet-client~=4.0`（4.x 浮升，同时把 setuptools 升 `>=80`，dev:296-298）。两个 venv 隔离方向相反的 setuptools 约束——同镜像双代并存是刻意兼容层。

**GitLab CI 七阶段编排**：`.gitlab-ci.yml` include 链按序吃进 `.gitlab/stages/00.pre.yml`~`06.triage.yml` 七文件（对应 .pre/build/test/integration_tests/functional_tests/publish/triage）。workflow rules 是策略中枢：fork 不触发（namespace != ADLR）；`ci-` 分支只认 schedule；merge_train 带 fast-track 标签只跑单测；MR 靠 `/Run tests|nightly|weekly/` 等标签路由 suite 与重复次数；另有变量面板（SCOPE 五档、三集群、PUBLISH 开关）。dynamic pipeline 是关键机制：configure 跑 `generate_jet_trigger_job.py` 按 platform×cluster 生成子流水线 YAML 作 artifact，下游 `integration:run_lts_dgx_gb200`（03.integration-tests.yml:157）用 trigger:include:artifact 动态展开（:124-127）。**甄别发现一（gb2100 笔误嫌疑）**：`--platform dgx_gb2100`（03.integration-tests.yml:98）全仓唯一出现，且与其后的 `dgx_gb200` 调用（:106）写**同一输出文件** `functional-test-job-lts-GB200.yaml`——顺序执行下 gb200 必然覆盖 gb2100 产物，该平台 trigger job 永不生效：要么笔误要么未接完的双平台改造。**甄别发现二（artifact 双挂）**：该 yaml 同时被 03（:110-116 清单）与 04.functional-tests.yml（:175、:185）引用。

**CI recipes YAML 体系**：`tests/test_utils/recipes/` 是收敛测试声明式用例库——`h100/` 33 个 + `gb200/` 14 个 + 顶层四个 _build/_cleanup。recipe schema（gb200/moe.yaml:5）：type/format_version/maintainers + spec（name 模板、model、build 镜像、nodes/gpus、n_repeat、platforms、script_setup）。script_setup 是灵魂：**双 checkout**——`/opt/megatron-lm` 取 MR commit、`/opt/megatron-lm-legacy` 取 `MCORE_BACKWARDS_COMMIT` 基线，双侧对比 golden 值。私有部分运行时注入：`local_recipes` 子模块 CI 里动态挂载（02.test.yml:62-64），开源用户看不到。

**skills 生态 14 个**：两档成熟度——9 个"签名+评测"档（mcore-build-and-dependency/bump-base-image/cicd/create-issue/linting-and-formatting/onboard-gb200-1node-tests/run-on-slurm/split-pr/testing，各含 SKILL.md+skill-card.md+BENCHMARK.md+evals+skill.oms.sig 五件套）与 5 个裸 SKILL.md（mcore-migrate-gpt-to-hybrid/nightly-sync/pr-review/respond-to-issue/update-golden-values）。BENCHMARK.md 是 NVSkills-Eval 三级评测报告（mcore-testing/BENCHMARK.md:3-5 自述 safe/discoverable/effective/useful）：Tier1 静态、Tier2 去重、Tier3 live agent（报告普遍 not available）。**甄别发现三（FAIL 与声明矛盾）**：mcore-cicd 与 mcore-bump-base-image 总评 **FAIL**——前者因 HIGH DUPLICATE（"Answer-First CI Facts" SKILL.md:5-25 与 "Triggering Internal CI" :89-105 重复，BENCHMARK.md:57-59），建议 review before publication；但两者 skill-card.md 仍写 "ready for commercial/non-commercial use"（mcore-cicd/skill-card.md:4）——就绪声明与评测结论矛盾。**sigstore 签名**：skill.oms.sig 是 sigstore bundle v0.3，证书链主体 "NVIDIA Agent Skills Signing 0010"——技能以密码学身份发布。

**AGENTS.md≡CLAUDE.md 孪生**：diff 完全一致（各 3468 字节）。三件事：skills 是强制上下文且规定"先读工件→再选 skill→后作答"；PR 必须 draft+个人 fork 发起、commit 双签（`-s` DCO + `-S` GPG，供 copy-pr-bot 与 `/ok to test` 验证）；megatron/core 禁新增对 parallel_state 全局进程组的直接读取（要传 ProcessGroupCollection）。**CI 三角监测**：`.gitlab/cerno.yml` 配 Slack/Linear 集成，06.triage.yml:21 的 `triage:linear_reconcile` 用 `cerno-linear status` 把测试失败与 Linear issue 对账（RUN_LINEAR_STATUS/WRITE 双闸）。

## 三、外部连接

docker 镜像由 01.build.yml 的 `test:build_image`（:92）构建推内部 registry；jet 子流水线跑内部 DGX 集群（dgxa100_dracooci、dgxh100_coreweave/eos、dgxgb200_oci-hsg）。skills 被 CLAUDE.md/AGENTS.md 钦点为强制工作流载体，与 .gitlab/ 同名目录形成"技能描述 CI、CI 又训练技能"闭环；裸技能与 06.triage 的 Linear/Slack 自动化互补；recipes 由 04 的 jet 触发器执行。

## 四、数据流

一次 MR 旅程：fork push→draft PR（双签）→merged_result 流水线→00.pre 起 ci 分支+密钥扫描→01 构建三镜像→02 单测（挂 local_recipes）→03 configure 生成子流水线 YAML（artifact）→dynamic trigger 在集群执行 recipe（双 checkout 对比）→04 功能测试同机制→05 可选 publish→06 cerno 把失败对账 Linear 并 Slack 告警。agent 视角：Claude 处理 CI 失败→CLAUDE.md 强制先读日志→选 mcore-cicd/mcore-testing skill→按 Answer-First 事实表定位→`/ok to test`（GPG 验签通过才跑）。

## 五、设计决策

1. **开源/内网双面一体**：.gitlab/ 公开可见但 workflow rules 挡外部触发——透明式开源（内部基建直接晒），社区能读不能跑。
2. **dev/lts 双轨解耦发布节奏**：dev 追月度容器验证兼容性，LTS 年更钉死依赖；LTS pin 挪进 Dockerfile 是"一个 pyproject 服务两类消费者"的务实解。
3. **技能当供应链管理**：sigstore 签名+三级评测+五件套，FAIL 也如实归档——负结果不隐藏是可信来源（尽管 card 声明与 benchmark 有漂移）。
4. **动态子流水线而非巨型矩阵**：configure 生成 YAML artifact、下游 trigger include——集群/平台组合爆炸压缩成一个生成器脚本+通配消费。
5. **AGENTS/CLAUDE 孪生单源**：一份内容两个入口名，防双文件漂移。
