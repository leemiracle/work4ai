# 07 RL 训练线：megatron/rl 的契约、流水线与持久账本

## 一、角色定位

`megatron/rl` 是 2025 年引入的原生 RL 后训练库（README 自述 08/27/2025 起活跃开发，明言"不面向企业框架用户，那请用 NeMo RL"）。设计哲学一句话：**agent/环境设计与 RL 训练系统解耦**——环境侧只拿一个支持 `.generate()` 的推理接口句柄返回带奖励的 rollout，训练侧负责批调度、推理托管与编排。顶层六个文件即六个层次：`agent/`（环境契约）、`inference/`（推理端点抽象）、`types/`（数据载体）、`rollout_pipeline.py`（生成编排）、`rollout_bank.py`（持久账本）、`rl_utils.py`（3173 行粘合层，接到 Megatron 训练循环）。入口是仓根 `train_rl.py`（435 行）。

## 二、内部结构

**契约层 `agent/api.py`（170 行）**：根抽象 `Agent`（api.py:96）只规定 `get_rollout_response()`；其上**五种生成器协议**：`RolloutGenerator`（:108，字符串轨迹+奖励）、`ContrastiveRolloutGenerator`（:115，chosen/rejected 双轨迹）、`TokenizedRolloutGenerator`（:124，token id+可选掩码/logprobs，训练真正消费的形态）、`GroupedRolloutGenerator`（:143，GRPO 类组采样契约，`prepare_group_rollout` 返回 api.py:39 的 `run_episode`/`build_rollout` 闭包对）、`EvaluationAgent`（:166，benchmark 评测）。数据载体在 `types/rollout.py`：`Rollout`（:21，`is_placeholder` 失败标记）、`TokenRollout`（:38）、`RolloutGroup`（:58，带 batch_id/index_in_batch/uid）。

**注册表 `agent/registry.py`**：`AGENT_REGISTRY`（:10）是"稳定名 → module:ClassName"白名单，`get_agent_class()`（:23）importlib 惰性反射。双动机写在注释里：惰性导入避免拉进可选依赖；**白名单防不可信环境配置执行任意代码**——安全设计。注意 `AceMathAgent` 的目标是 `environments.acemath_agent`（:19），不带 examples.rl 前缀，依赖 PYTHONPATH。

**环境 YAML 配置**：`get_agent()`（rl_utils.py:613）`yaml.safe_load` 列表配置交 `WeightedMultiTask.from_config()`（weighted_multi_task.py:100）。以 `examples/rl/environment_configs/math.yaml` 为例：三段 `agent_type/agent_args/weight`，AIME `weight: 0.0` 加 `evaluation_only: true` 表示纯评测。`AgentConfig`（:29）构造期校验 weight 非负；`WeightedMultiTask`（:43）同时继承四个生成器协议，是唯一顶层 agent，`rollout_allocations()`（:216）按权重切每批组配额。

**RolloutPipeline 五阶段（700 行）**：`run()`（rollout_pipeline.py:284）拉起 `stage_prepare`（:378，按粒度闸门生成工作项、优先复活 bank 恢复组）→ `stage_infer`（:419，常驻 worker 池执行 run_episode）→ `stage_assemble`（:459，凑齐组后 build_rollout；`_decide_drop`（:512）对全占位失败组与零方差组（`np.std ≤ 1e-6`）判弃并 `_regenerate_group`（:544）用负数 group_id 补采）→ `stage_bank`（:622，按消费粒度 G（完成序跨环境轮转）/B（数据集序整批）切批）→ `stage_consume`（:639，产出组并释放闸门）。背压核心 `_SubmissionGate`（:109）：以 R/G/B 三档提交粒度计量的信号量，容量 = `(generation_lag+1) × units_per_batch()`（见 rl_utils.py:716），即 README collection lag 理论的代码落点。`_GranularityConfig`（:27）校验"消费粒度不得细于提交粒度"。

**RolloutBank sidecar 账本（984 行）**：为扛 4 小时 SLURM SIGKILL 限时而生。布局：`MANIFEST.json` 原子选代 + `generations/<uuid>/gen-<iter>/` 下 `ledger.log`（JSONL 索引）+ 三个二进制 sidecar（tokens.bin int32/logprobs.bin fp16/masks.bin uint8，:71-73，`_FORMAT_VERSION=2` :77）。动机写在文件头：TokenRollout 走 JSON 约 28 B/token（logprobs 单独 ~18 B，是二进制的 9 倍），大数组进 sidecar、JSONL 只留 (offset,bytes,lengths) 指针。`append()`（:440）逐组 fsync；`recover()`（:853）按"marker≤T 丢、>T 或无标记恢复"重放；`checkpoint()`（:830）在检查点边界压缩发布新代。恢复组经 `set_restored_groups()`（weighted_multi_task.py:192）按 env_id 入队、`take_restored_group()`（:211）在 stage_prepare 优先顶替。

**粘合层 rl_utils.py**：`colocated_inference()`（:775）是训练↔推理同卡切换枢纽——offload 优化器、双模型配置下 `swap_model_weights`（可用 :208 `verify_model_weights_swap` 核验）、进 `megatron_rl_inference_mode`（:2973）收集 rollout。算法侧有 `calculate_grpo_advantages`（:1252）、`calculate_grpo_loss`（:2878）、`prepare_trajectories`（:2109）、`get_logprobs`（:1146，含 CP scatter）。

## 三、外部连接

向上：`train_rl.py:17` import rl_utils 运行时状态；Megatron 训练循环为 RL 做了小改（README 明言）。向内：依赖 `megatron.core.inference.utils` 的 `asyncio_Queue/QueueShutDown`（rollout_pipeline.py:13）。`inference/` 把端点抽象为 `InferenceInterface`（inference_interface.py:15）加三个能力 mixin `ReturnsRaw`（:45）/`ReturnsTokens`（:51）/`ReturnsLogProbs`（:57）；本地部署 `MegatronLocal`（inference/megatron.py:39），`get_inference_interface()`（rl_utils.py:657）在 0.0.0.0:8294 起 HTTP 服务。环境实现活在 `examples/rl/environments/`，注册表显式指向它们。

## 四、数据流

一步 GRPO：YAML → get_agent 构建 WeightedMultiTask → `get_rollout_generator`（首调创建常驻 Pipeline，`initial_batch_id=current_iteration` 保批号跨步连续）→ 五阶段产出 RolloutGroup 流 → prepare_trajectories 对齐、calculate_grpo_advantages 组内基线 → 前向取训练 logprobs 与推理侧做 IS-correction → calculate_grpo_loss 回传。落账并行：assemble 完成即 `bank.append`（rollout_pipeline.py:497），消费后 mark_consumed 写 marker。崩溃恢复：重启 → `bank.recover(args.iteration)` → 组进 restored 队列 → `can_skip_inference()`（rl_utils.py:763）发现整批已备好即跳过推理切换。

## 五、设计决策

1. **闭包式组参数**：GroupRolloutParams 把"跑一集/成一集"打包成 awaitable，流水线只调度不问语义——多轮对话、工具调用环境无需改管线。
2. **粒度显式化**：提交（R/G/B）与消费（G/B）是请求字段（api.py:28-29），不变量挡在构造期断言。
3. **负 lag 合法**：容量公式允许负值（rl_utils.py:729 的 max(1,round(...)) 兜底），README 解释这是推理资源稀缺到全同步也超订时的诚实表达。
4. **bank 只做 PR#1**：文件头明说只覆盖"已完成未训练"排队路径，decode 中间态与部分组快照（阶段 B/C）故意不做。
5. **白名单反射**：RL 环境配置天然来自数据/用户侧，注册表把 yaml 表达力与代码执行权隔开。
6. **观测性一等公民**：闸门计数器、四级队列 dwell、per-env 产出计数（rollout_pipeline.py:263-281）全内置，供 `_collect_rollout_pipeline_metrics`（rl_utils.py:1846）上报。

## 六、新人提示

- 入口别从 3173 行的 rl_utils 啃起；顺序：README → agent/api.py（170 行契约全景）→ rollout_pipeline.py → 回 rl_utils。
- `assert_no_inflight_rollouts()`（rollout_pipeline.py:349）是 lag=0 守门断言：迭代边界还有缓冲 rollout 说明生成器在旧策略下跑飞——先查 lag 配置再查数据。
- 写新环境：实现协议 → registry.py 注册稳定名 → YAML 引用；跳过注册直接给类路径会吃 ValueError（registry.py:35）。
- `is_placeholder`（rollout.py:43）语义是"空轨迹=失败占位"；自定义 agent 失败时返回非空轨迹会绕过补采。
- README 明言未对外完整发布，external 用户跑 examples 可能缺件——排障前先确认不是缺件。
