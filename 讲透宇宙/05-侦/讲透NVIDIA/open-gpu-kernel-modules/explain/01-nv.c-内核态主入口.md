# 01 · kernel-open/nvidia/nv.c——nvidia.ko 内核态主入口

> 仓库：NVIDIA open-gpu-kernel-modules 615.71.09 · 层：nvidia.ko 内核主模块（图谱第 14 层）
> 本文行号锚全部源码核实（nv.c 6735 行 / nv-pci.c / nv-mmap.c / nv.h）

## ① 角色定位

`kernel-open/nvidia/nv.c` 是整个闭源 RM（Resource Manager，已以二进制 `nvidia.ko` 核心形式存在）与 Linux 内核之间的**主粘合文件**：它实现模块装载/卸载、字符设备注册、`file_operations` 全套入口（open/close/ioctl/mmap/poll）、电源管理与 kthread 队列。用户态 libnvidia-api / CUDA driver 的每一次 `ioctl(/dev/nvidia*)`，最终都由本文件的 `nvidia_ioctl()`（nv.c:2627）接住，再交给 `rm_ioctl()`（src/nvidia/arch/nvalloc/unix/src/osapi.c:3002）进入 RM 核心。

一个必须先钉版的勘误：**本版本不存在 `nvidia.c` 与 `nv-frontend.c`**。早期开源版本（515/525 系列）的前端文件 `nv-frontend.c`（负责 cdev 区域管理与 frontend_probe）与 `nvidia.c` 已在本代被合并重构成 `nv.c` 一个文件（6735 行）；PCI 前端职责则拆到同目录 `nv-pci.c`（`struct pci_driver nv_pci_driver` 在 nv-pci.c:3489）。图谱中 nvidia.ko 内核主模块层（181 节点）以 nv.c 为根。

## ② 内部结构

**全局状态区**（nv.c:153-226）：
- `nv_linux_devices`（nv.c:166）——每 GPU 一节点的核心链表，元素类型 `nv_linux_state_t`，与 `nv_linux_minor_bitmap`（nv.c:167，DECLARE_BITMAP 到 247）一起由 `nv_linux_devices_lock`（nv.c:202）保护；
- `nv_ctl_device`（nv.c:170）——控制设备（/dev/nvidiactl）的静态单例，不挂在链表上；
- 两个静态 cdev：`nv_linux_devices_cdev`（nv.c:173，覆盖 minor 0-247 常规设备区）与 `nv_linux_control_device_cdev`（nv.c:176，仅 minor 255）；
- `nvidia_caps_root`（nv.c:153）——/proc/driver/nvidia/capabilities 能力根；两个全局 kthread 队列 `nv_kthread_q` / `nv_deferred_close_kthread_q`（nv.c:180-181）。

**入口注册区**：`nvidia_fops`（nv.c:259-269）只挂六个入口——`open/release/poll/unlocked_ioctl/compat_ioctl/mmap`，x86_64 与 aarch64 上 compat 与 unlocked 指向同一函数（nv.c:263-265），即 32 位用户态进程无需转换层直接复用。`nv_pm_ops`（nv.c:281-290）覆盖 suspend/resume/freeze/thaw/poweroff/restore 与 runtime_pm 八个回调。

**ioctl 大分发表**：`nvidia_ioctl()` 内 `switch (arg_cmd)`（nv.c:2749）先截留少量"前端自处理"命令——`NV_ESC_QUERY_DEVICE_INTR`（nv.c:2751，直接读寄存器映射）、`NV_ESC_CARD_INFO`（nv.c:2770，遍历链表报告显卡）、`NV_ESC_ATTACH_GPUS_TO_FD`（nv.c:2780，控制 fd 绑定多 GPU）、`NV_ESC_EXPORT_TO_DMABUF_FD`（nv.c:2969）——其余全部落入 `default:` 分支的 `rm_ioctl(sp, nv, &nvlfp->nvfp, arg_cmd, arg_copy, arg_size)`（nv.c:2980）。这是"前端薄壳、RM 厚核"的典型分工。

**后台 open 队列**：`nvidia_open()`（nv.c:2007）遇到首个 open（需要做重量级 GPU attach）时不让调用进程持锁死等，而是 `nv_try_lock_foreground_open()` 失败后把工作项 `nvidia_open_deferred` 挂进 `nvl->open_q`（nv.c:2093-2107），用户态随后用 `NV_ESC_WAIT_OPEN_COMPLETE`（nv.c:2710）轮询完成——这是 GSP 时代 RM 初始化耗时的直接产物。

## ③ 外部连接

- **nv-pci.c**：`nv_pci_driver`（nv-pci.c:3489-3508）挂在 `id_table = nv_pci_table` 上，probe 走 `nv_pci_probe`（实现在 nv-pci.c，body 函数 nv-pci.c:2148）；内核支持时声明 `PROBE_PREFER_ASYNCHRONOUS`（nv-pci.c:3503），注册后用 `wait_for_device_probe()` 收口（nv-pci.c:3519-3524）。
- **nv-mmap.c**：`nvidia_mmap_helper`（nv-mmap.c:522）按 mmap 上下文分发到 peer_io/sysmem/numa 三类映射路径（nv-mmap.c:411/433/491）。
- **osapi.c（RM 侧）**：`rm_ioctl` 是 nv.c 前端通往 RM 的唯一主通道；`nv_module_init/nv_module_exit`（nv.c:703/718）只是包装 RM 入口的栈适配层。
- **兄弟内核模块**：`nvidia_init_module()` 中 `nv_uvm_init()`（nv.c:976，NV_UVM_ENABLE 时）拉起 nvidia-uvm 的全局状态；nvidia-modeset/nvidia-drm 各自独立 .ko，但共享 `nv_linux_devices` 链表视图（通过导出的接口）。
- **设备号契约**：主设备号 195、常规 minor 上限 247、控制设备 minor 255（kernel-open/common/inc/nv-chardev-numbers.h:29/32/40），/dev/nvidiactl 与 /dev/nvidia0..N 由同一套 fops 服务，用 minor 区分。

## ④ 数据流

**装载流**（`nvidia_init_module`，nv.c:958 起）：nv_module_init 分配 RM 栈 → `nvos_count_devices`（nv.c:965）数出 PCI+平台设备 → 无 GPU 且无 NVSwitch 则 -ENODEV 退出（nv.c:966-971）→ `nv_uvm_init` → `nv_drivers_init()`（nv.c:674-695）注册 PCI/platform 驱动，probe 全部跑完后各 nvl 挂入 `nv_linux_devices` → **最后一步**才注册两个字符设备区（nv.c:1059-1067，注释明言 "THIS SHOULD BE DONE LAST"，nv.c:1057）。这个顺序保证用户态看到 /dev/nvidia* 时每块卡已可服务。

**ioctl 流**：`nvidia_unlocked_ioctl`（nv.c:3016）→ `nvidia_ioctl` → `nv_validate_ioctls` 白名单校验 → 非 XFER 命令按 `_IOC_SIZE(cmd)` 取尺寸；若是 `NV_ESC_IOCTL_XFER_CMD`（定义于 kernel-open/common/inc/nv-ioctl-numbers.h:41），则改从 `nv_ioctl_xfer_t` 取出真实 cmd/size/ptr（nv.c:2663-2693），尺寸上限 `NV_ABSOLUTE_MAX_IOCTL_SIZE = 16384`（kernel-open/common/inc/nv.h:70）→ `NV_KMALLOC(arg_copy)` + copy_from_user → 大 switch → 结尾统一 copy_to_user 回写（nv.c:2995-3008）。XFER 机制的存在是因为单个 ioctl 命令码在 compat 场景下尺寸字段受限，需要一条"元 ioctl"转发大 payload。

**open 流**：`nv_alloc_file_private` 分配 `nv_linux_file_private_t` → `nv_kmem_cache_alloc_stack`（nv.c:2038）从 slab cache 取一个 `nvidia_stack_t` —— 这是本文件最特殊的数据结构：一块 12KB（x86_64，`NV_STACK_SIZE = NV_RM_PAGE_SIZE*3`，kernel-open/common/inc/nv.h:329-333）的自备栈，因为 RM 代码调用深度大，不能压在 Linux 默认内核栈上，所有进入 RM 的调用（ioctl/mmap/isr bottom-half）都必须自带这块栈，进出各一次 `nv_kmem_cache_free_stack`。

## ⑤ 设计决策

1. **双 cdev + 静态 minor 布局**：控制设备（minor 255）与常规设备（0-247）共享 fops 但语义分流（`nv_is_control_device` / `NV_CTL_DEVICE_ONLY` / `NV_ACTUAL_DEVICE_ONLY` 宏守卫），避免为 ctl 单写一套 file_operations；minor 由 bitmap 分配、设备链表串接，模式极简且并发面小（一把全局锁）。
2. **async probe + 显式屏障**：优先异步 probe 加快启动，但注册后必须 `wait_for_device_probe()`（nv-pci.c:3524）保证 `num_probed_nv_devices` 定值再做校验（nv.c:991-1047 三层计数核对：count / probed / initialized），对"另一驱动抢占设备"给出分级诊断日志（nv.c:1013-1020）。
3. **RM 私有栈池**：`nvidia_stack_t_cache` slab 化（nv.c:199），把"栈"当稀缺资源管理，是 RM 从闭源单核继承下来的硬约束在开源前端的投影。
4. **失败路径细粒度 goto 链**：init_module 的退出标号 `partial_chrdev_exit → drivers_exit → uvm_exit → module_exit → caps_imex_exit → caps_root_exit → pm_notifier_exit → procfs_exit`（nv.c:1077-1108）严格按注册逆序，是内核模块工程范本。
5. **GPU lost 防御**：ioctl/poll/mmap 入口处统一 `nv_check_gpu_state` 检查（nv.c:2741-2747），热拔/掉卡后所有入口快速失败而不是挂在死硬件上。

## ⑥ 新人提示

- 读码路线：nv.c:958 的 init → nv-pci.c probe → nv.c:2007 的 open → nv.c:2627 的 ioctl，四段读完即掌握 nvidia.ko 骨架；NV_ESC 命令号总表在 `kernel-open/common/inc/nv-ioctl-numbers.h`。
- `nvidia_ioctl` 里几乎所有命令都走 default 进 RM，不要在前端找功能实现——前端只管用户态内存搬运与设备/锁校验。
- 调试装载失败时先看 `num_probed_nv_devices != count` 的三条 NVRM 报错（nv.c:1010-1027），十有八九是 nouveau/vfio 抢占。
- GSP 固件模式下首次 open 慢是设计使然（open_q 后台化），用户态的正确姿势是 WAIT_OPEN_COMPLETE 轮询而非长阻塞 open。
- 勘误备注：任务书原文写 "nvidia.c + nv-frontend.c"，本版本源码实证为 `nv.c`（无 nvidia.c；nv-frontend.c 已于早年版本合并消亡，PCI 前端在 nv-pci.c），本文以源码为准。
