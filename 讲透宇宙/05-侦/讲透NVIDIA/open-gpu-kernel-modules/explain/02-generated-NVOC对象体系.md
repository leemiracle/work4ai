# 02 · src/nvidia/generated/——NVOC 生成物与 RM 对象体系

> 仓库：NVIDIA open-gpu-kernel-modules 615.71.09 · 层：NVOC 生成层与运行时（图谱第 5 层，481 节点）
> 本文行号锚全部源码核实（g_*_nvoc.c/.h、rtti.h、runtime.h、prelude.h、g_gpu_class_list.c、g_allclasses.h）

## ① 角色定位

`src/nvidia/generated/` 是 RM（Resource Manager）对象体系的**代码生成层**：目录下共 533 个文件，其中 NVOC 对（`g_*_nvoc.c` × 209 + `g_*_nvoc.h` × 215 = **424 个 NVOC 生成物**）构成 RM 所有运行时类的"虚表+RTTI+多重继承桥"；另有 64 个 `g_bindata*`（GSP 固件二进制 C 数组）与 46 个表类生成物（g_gpu_class_list.c、g_allclasses.h、g_hal* 等）。NVOC 是 NVIDIA 内部的 C 语言面向对象预处理器（"NV Object Compiler"），它吃进带 `[[nvoc::]]` 属性标注的手写头（如 src/nvidia/src/kernel/gpu/gpu.h），产出本目录的 C 代码；**生成器本身（chip-config、Classes.pm 之外的 NVOC 编译器）不开源，本仓只提交生成结果**——g_allclasses.h 头注释明言 "The class list is generated by chip-config from Classes.pm"。

这一层在图谱中单列一层（481 节点），是因为它是理解 RM 全部对象交互的索引：任何 `objCreateDynamic`/`dynamicCast`/RM ctrl 命令分发最终都会落到这里生成的表上。

## ② 内部结构

**单类生成对的解剖**（以 g_access_cntr_buffer_nvoc.c 为例）：
1. **classId 唯一性链接检查**：`char __nvoc_class_id_uniqueness_check__1f0074 = 1;`（g_access_cntr_buffer_nvoc.c:19）——每个类一个以 classId 命名的全局 char，若两个类撞 ID 则符号重定义、链接期报错，这是零运行时成本的防冲突装置；
2. **RTTI 类定义**：`__nvoc_class_def_AccessCounterBuffer`（g_access_cntr_buffer_nvoc.c:123-135），填 `classInfo.size/classId/visibility/providerId/name`、`objCreatefn`、`pCastInfo`、`pExportInfo`；
3. **up/down thunk**：`__nvoc_up_thunk_GpuResource_accesscntrShareCallback` 等（g_access_cntr_buffer_nvoc.c:95-120），把基类（GpuResource/RmResource/RsResource/Notifier）方法适配到子类 this 指针——C 里手工实现的多重继承 vtable 胶水；本文件含 182 处 thunk 引用；
4. **导出方法蹦床**：`accesscntrCtrlCmdAccessCntrBufferReadGet__EXPORT`（g_access_cntr_buffer_nvoc.c:144）一行转调手写 `..._IMPL`；
5. **导出方法表**：`__nvoc_exported_method_def_AccessCounterBuffer[]`（g_access_cntr_buffer_nvoc.c:204 起），每项是 `NVOC_EXPORTED_METHOD_DEF{pFunc, flags, accessRight, methodId, paramSize, pClassInfo}`（runtime.h:71-83），如 `[0]` 项 methodId=0xc3650101、paramSize=sizeof(NVC365_CTRL_ACCESS_CNTR_BUFFER_READ_GET_PARAMS)（g_access_cntr_buffer_nvoc.c:214-215）。

**运行时结构**（手写部分，src/nvidia/inc/libraries/nvoc/）：
- `NVOC_CLASS_INFO`（prelude.h:253-278）：size + 24 位 classId 位域 + 2 位 visibility（NVOC_EVENT_VISIBILITY 枚举，prelude.h:243-249）+ providerId + 调试名；
- `NVOC_CLASS_DEF`（rtti.h:58-63）= classInfo + objCreatefn + pCastInfo + pExportInfo；
- `NVOC_RTTI`（rtti.h:66-71）：**每条 derived→ancestor 边一个实例**，含 pClassDef、析构指针、子对象偏移 offset（派生类自身为 0）；
- `NVOC_CASTINFO`（rtti.h:49-53）：`numRelatives + relatives[]` 变长数组，是 dynamicCast 的合法转换闭包表。

**全类注册表**：g_allclasses.h 双段结构——头部按 `#include <class/clXXXX.h>` 拉入全部 SDK 类头（NV01_ROOT/NV01_DEVICE_0/NV20_SUBDEVICE_0 等），尾部以 `#ifndef NV_XXX #define NV_XXX (0x...)` 输出外部类号（如 `NV_CONFIDENTIAL_COMPUTE (0x0000cb33)`）。g_gpu_class_list.c（4767 行）则是运行时可分配类清单：`gpuGetGenericClassList_IMPL` 内 `genericClassDescriptorList[]`（g_gpu_class_list.c:34）+ **35 个芯片代际变体**（TU102/104/106/116/117、GA100-107、AD102-107、GH100、GB100/102/10B/10C/110/112、GB202-207/20B/20C、GR100/GR102、Tegra T234D/T239D/T264D），每个变体两个函数：NvU32 classId 列表与 `CLASSDESCRIPTOR{classId, engine}` 对表（如 `gpuGetEngClassDescriptorList_T264D`，g_gpu_class_list.c 尾部）；编译期护栏 `ct_assert(NV0080_CTRL_GPU_CLASSLIST_MAX_SIZE >= (16 + 120 /* GB20B *))` 保证最大代际表不越界。GR100/GR102（Rubin）已出现在 615.71.09 的类清单与 GSP 固件 bindata 中。

## ③ 外部连接

- **上游（手写侧）**：每个 `g_X_nvoc.h` 对应手写 `src/nvidia/src/kernel/**/X.h` 的 NVOC 属性标注；`_IMPL` 实现分布全仓（第 9-12 层）；
- **下游（RM 内核核心）**：`__nvoc_objCreateDynamic`（runtime.h:47-52）变参构造、`__nvoc_dynamicCast/__nvoc_dynamicCastById`（runtime.h:54-55）类型转换、`__nvoc_objDelete`/`__nvoc_destructFromBase`（runtime.h:45/57）析构——resource server（rs_server）的分配/释放全走这组入口；`objFindAncestorOfType` 宏（runtime.h:65）依赖 RTTI 链向上找祖先；
- **RM ctrl 分发**：用户态 ioctl 里的 control 命令（NVOS54_PARAMETERS 等）由 resource server 查 `NVOC_EXPORTED_METHOD_DEF` 表匹配 methodId 后调 pFunc——flags 字段承载 NO_LOCK/PRIVILEGED 等属性校验，accessRight 承载 RS_ACCESS 权限位；
- **GSP 固件线**：64 个 `g_bindata_kgspGetBinArchive*_芯片.c`（AD102/GA100/GA102/TU102/TU116/GB100/GB202/GH100/GR100...）以 C 数组内嵌每代 GSP-RM 固件镜像，被 kgsp（第 12 层 GSP 固件层）消费；
- **HAL 表**：g_hal.h/g_hal_stubs.h/g_chips2halspec.h 与 g_rpc_hal.h 服务第 10-11 层各引擎 HAL 的函数指针矩阵。

## ④ 数据流

**对象创建流**：RM 内核代码调用 `objCreateDynamic(&pObj, pParent, classInfo(Xxx), flags, 构造参数...)` → NVOC 运行时按 `__nvoc_class_def_Xxx.objCreatefn` 进入生成蹦床 → 依继承链自基到派生逐级 `__nvoc_construct_Xxx`（生成代码负责基类子对象偏移对齐与 RTTI 填充，`__nvoc_initRtti`，rtti.h:75）→ 返回 Dynamic* 基指针。

**类型转换流**：`dynamicCast(pObj, Xxx)` → 读对象头 RTTI → 在目标类的 `NVOC_CASTINFO.relatives[]` 中线性查源类 → 命中则 `基指针 + NVOC_RTTI.offset` 得到子对象指针，未命中返回 NULL——等价于 C++ dynamic_cast 的手写实现，且无异常路径。

**ctrl 命令流**：用户态 `rm_control(NVXXXX_CTRL_CMD, params)` → resource server 按 (classId, cmd) 匹配 `__nvoc_exported_method_def_*[]` 中 methodId → flags/accessRight 门禁 → `pFunc` 蹦床 → 手写 `_IMPL`。methodId 编码 = 类号<<16 | 序号（0xc3650101 即类 NVC365 命令 0x0101）。

**类清单查询流**：`gpuGetClassList`（OBJGPU 的 HAL 方法）→ 按芯片代际落到 g_gpu_class_list.c 对应 `hal<CHIP>ClassDescriptorList` → RM 用它校验用户 alloc 请求的类是否被该 GPU 支持。

## ⑤ 设计决策

1. **"生成 C 而非改语言"**：RM 历史上是纯 C 巨石，NVOC 用预处理器补 OO（继承/RTTI/属性/权限元数据），保持工具链兼容与可审查性——代价是生成物体积巨大（g_subdevice_nvoc.c 达 15002 行）且无法用调试器直接对应源级概念；
2. **薄壳分层**：实测 209 个 `g_*_nvoc.c` 中 **149 个不含任何 `_IMPL` 调用**（纯 thunk+RTTI+构造析构壳），只有约 60 个含导出 ctrl 方法表；另有 2 个 0 字节占位（g_kern_hwpm_common_defs_nvoc.c、g_kern_hwpm_power_nvoc.c）。**任务书记"123/200 薄壳"，源码实测为 149/209，本文以源码为准**。薄壳的意义：逻辑留在手写 `_IMPL`，生成层只承载"形状"（可被工具重新生成而不丢逻辑）；
3. **链接期 classId 防撞**（§②.1）：用"同名符号重复定义即链接失败"实现零开销断言，是生成代码里少见的巧思；
4. **visibility 位域进 classInfo**（prelude.h:267）：NONEVENT/PRIVATE/PUBLIC/EXPORT 四档事件可见性，把"该类事件可否被谁观测"做成类型系统一等信息，而非散落的运行时判断；
5. **per-chip 类清单静态化**：35 代 class list 全部 `static const` 数组 + ct_assert 编译期容量校验，运行时零分配； Rubin（GR100/GR102）类表与固件 bindata 在本代驱动中已就位。

## ⑥ 新人提示

- 找一个类的"真身"路线：`g_X_nvoc.h`（对象布局）→ 手写 `X.h/X.c`（逻辑 `_IMPL`）→ `__nvoc_exported_method_def_X[]`（对外 ctrl 面）；不要试图通读生成 .c，只读你关心类的 class_def 与方法表；
- `dynamicCast` 返回 NULL 是常态分支不是错误——RM 用它表达"此对象不是该子类型"；调试时 `objGetClassInfo(pObj)->name`（NV_PRINTF_STRINGS_ALLOWED 时）是确认对象真身的最快手段；
- g_gpu_class_list.c 的芯片命名规律：TU=Turing、GA=Ampere、AD=Ada、GH=Hopper、GB=Blackwell、GR=Rubin、Txxx=Tegra；查某 GPU 支持哪些类直接搜 `hal<CHIP>ClassDescriptorList`；
- 改 RM 行为的正确位置永远在手写 `_IMPL`；生成物改动会在下次生成时被覆盖；
- g_bindata_* 文件是巨型 C 数组，别用编辑器整开，grep 定位即可。
