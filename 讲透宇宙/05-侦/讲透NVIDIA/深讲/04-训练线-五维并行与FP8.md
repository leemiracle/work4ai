# 04 · 训练线：五维并行与 FP8

> 系列第 04 篇。锚版本：Megatron-LM `05fb87b`、TransformerEngine `0838ecb`（2026-10-01，本地源码逐条核实）。

## 一、第一性原理设问：为什么必然是"五个维度 + 一个精度配方"

两堵墙。**显存墙**：Adam 混合精度"模型状态"（参数+梯度+优化器状态）约 `16N` 字节，671B 模型仅此就 >10TB，单卡 H100 只有 80GB。**算力墙**：万亿 token 预训练决定必须万卡并行。问题于是变成：**把模型和负载切开，铺到 K 张卡上**。而 Transformer 的结构自由度只有五个，切分维度也就五个——结构决定的完备集：

矩阵乘法的行/列（头数、FFN 中间维）→**TP**；层堆叠深度 →**PP**；batch 维 →**DP**；MoE 专家列表 →**EP**；序列长度维 →**CP**。

每个维度回答：**切什么、通信什么、显存赚多少、通信付多少**。五维各对应一个 process group，统一在 `megatron/core/parallel_state.py:622` `initialize_model_parallel()` 初始化（TP `:1766`、PP `:1811`、DP `:1820`、CP `:1890`、EP `:2315`）——**五个互不重叠的通信域就是"五维正交"的代码证据**。

FP8 是另一条独立战线：每个数从 2 字节压到 1 字节，存储减半、吞吐翻倍（完整公式见结尾总结）。

## 二、直觉层：一家工厂的五种分法

- **DP（开分厂）**：生产线复制 8 份各接各的订单，月底对账（梯度 all-reduce）。模型不切——唯一"零结构侵入"的维度，也是兜底维度。
- **TP（拆车间）**：设备太宽拆成两个半宽车间，**每道工序都对一次数据**（all-reduce）。协作频率最高、车间必须背靠背——TP 锁死单机 NVLink 域的物理原因。
- **PP（流水线）**：32 道工序 8 个车间，半成品传下家（p2p）。开工下游等、收工上游等——空转即 **bubble**。
- **EP（专家门诊）**：科室（专家）分散各机器，病人（token）按挂号单（router 概率）派去再回来——两次 **all-to-all**，全体互打。
- **CP（分段看长卷）**：长序列切段各算一段，但注意力"人人都要看全文"，QKV 沿环传递（ring）。

FP8 的直觉：给每个数定"换算汇率"（scale），把动态范围压进 4bit 指数+3bit 尾数的窄窗。**权重像厚度均匀的书，好定汇率；激活像混了砖头的书堆，单一汇率要么压没了书（下溢）要么为砖头浪费位**——"FP8 权重易、激活难"正是两代方案的演进动力。

## 三、机制层：源码里的五维与两代 FP8

### 3.1 TP：每层两次 all-reduce，锁死 NVLink 域

TP 把线性层拆成对偶：`ColumnParallelLinear`（`megatron/core/tensor_parallel/layers.py:1044`，按输出维切——head 数、FFN 中间维是天然轴）+ `RowParallelLinear`（`layers.py:1465`，按输入维切）。前层输出分片直喂下层，只在需完整激活处聚合——即 `mappings.py:26` 的 `_reduce()`：

```python
# megatron/core/tensor_parallel/mappings.py:26-39
def _reduce(input_, group): ... torch.distributed.all_reduce(input_.contiguous(), group=group)
```

forward/backward 各一次、每 layer 两次 all-reduce，通信量 ∝ `batch×seq×hidden×2×(TP-1)/TP`——TP 超出单机 NVLink 域后 all-reduce 落到 PCIe/IB，带宽掉一个量级，吞吐崩。伴生优化 sequence parallelism：LayerNorm/dropout 区域按序列维再切，把 all-reduce 换成 reduce-scatter+all-gather（`train_llama3_8b_h100_fp8.sh:120` 无条件开）。

### 3.2 PP：调度器压 bubble

心脏是 `pipeline_parallel/schedules.py:54` 的 `get_forward_backward_func()`，分派三种调度：`:724` 无流水、`:1020` 交错式（VPP，每卡持多个虚拟段）、`:2160` 标准 1F1B。1F1B：先灌 `pp_size-1` 个 microbatch 的 forward，随后"一前一后"稳态，最后排水；bubble 占比近似 `(pp-1)/(mb+pp-1)`，**加大 mb 或 VPP 把分母变大**。通信是 p2p 传 activation/gradient，量小但延迟敏感（反向开关 `arguments.py:3128`）；另有 `combined_1f1b`（`schedules.py:39-41`）。

### 3.3 EP：MoE 的 all-to-all 与 grouped GEMM

`transformer/moe/token_dispatcher.py:375` 的 `MoEAlltoAllTokenDispatcher`：按 router 概率 permute token，`:705`/`:718` 两处 `all_to_all` 发往 expert rank，算完 `:864` 收回。收益是专家参数 ÷EP，代价是全体互打的 all-to-all——跨节点打满 IB，须靠计算通信重叠（DualPipe 类）来"藏"。Mixtral 官方脚本（`train_mixtral_8x7b_distributed.sh:50-58`）：`--num-experts 8 --moe-router-topk 2 --moe-token-dispatcher-type alltoall --moe-grouped-gemm`。

### 3.4 组合是设计空间搜索：为什么 V3 选 EP64/TP1

五维按笛卡尔积组合。V3 选 EP64/TP1 而非 TP8 是通信×GEMM 效率的联合决策：(1) V3 专家细粒度小，TP 再切会把专家 GEMM 切碎（M 维过小）；EP 让专家整卡安放，grouped GEMM 聚合同卡 token 批。(2) TP 的每层两次 all-reduce 锁死 NVLink 域；EP 的 all-to-all 可跨节点且能重叠。(3) attention 独立用小 TP+DP——**注意力与 MoE 分开并行**，与推理侧 `TEP/DEP` 记法同理。

### 3.5 FP8 两代方案：从延迟缩放到分块缩放

单位操作：GEMM 输入（activation/weight/grad）量化成 E4M3/E5M2，算完反量化。TE 的 `Linear`（`transformer_engine/pytorch/module/linear.py:1901`）在 forward（`:2339`）装配六个 quantizer——**秘密全在用什么 recipe**：

**一代 DelayedScaling**（`transformer_engine/common/recipe/__init__.py:173`）：per-tensor 单一 scale，用**上一步 amax 假设本步动态范围不变**——滑窗记 `amax_history_len`（默认 1024 步，`:255`）历史最大值定 scale。统计稳定性换零同步开销；代价：激活突变要等窗口追上，离群通道撑大全 tensor 的 scale，挤压其余通道精度。

**二代 Float8BlockScaling**（`recipe/__init__.py:392`）：划 **128×128 块**（`common/include/transformer_engine/recipe.h:149-156` 把 512×512 张量画成 16 块），每块独立 power-of-2 scale，离群被囚禁在单块内；代价是 scale 元数据变多、GEMM 须 128 对齐，且强制 `use_split_accumulator=True`（分块累加保数值）。

**会师点**：最新 TE 默认 recipe 按硬件分派（`pytorch/quantization.py:241`）：支持 MXFP8 → `MXFP8BlockScaling`（32 元素微块+E8M0 共享指数，Blackwell 原生）；sm12x+ 暂不支 → `Float8CurrentScaling`；老架构 → `DelayedScaling()`。**软件 128×128 分块与硬件 MXFP8 微块是同一路线软硬两代，DeepSeek V3 已规模化验证。**

用户侧 API：`pytorch/quantization.py:941` `fp8_autocast()` / `:972` `class autocast`，上下文一包自动量化。

### 3.6 数据管线与 apex 残值

隐形瓶颈：H100 一个 microbatch 前向仅几毫秒，CPU 供不上，GPU 饿死时 MFU"莫名"低。互补两件：**DALI**（GPU 直接解码/augment，管线即计算图）与 **Megatron-Energon**（异步加载：WebDataset 分片 + `SavableDataLoader` + TaskEncoder 流水）。apex 是历史层：FusedAdam（`apex/optimizers/fused_adam.py:6`）已被上游 PyTorch 与 TE 吸收，残值只在老管线。

## 四、程序员实操：从启动脚本到排坑

`examples/llama/train_llama3_8b_h100_fp8.sh` 是最好模板：Llama3-8B 单机 8×H100 用 `TP=1/CP=1/PP=1`（`:33-35`）——**8B 单卡放得下，切分是纯通信税，DP=8 全复制最优**。FP8 四参数（`:106-113`）↔ TE recipe 同名字段：

```bash
--fp8-format hybrid            # 前向 E4M3 / 反向 E5M2
--fp8-amax-history-len 1024 --fp8-amax-compute-algo max   # ↔ DelayedScaling 同名字段
--fp8-param-gather             # 权重以 FP8 参与参数聚合
```

DP 三件套（`:125-129`）：`--use-distributed-optimizer`（优化器状态也切到 DP 组）+ 两个 overlap 开关。

**TE 裸用法**：

```python
with te.fp8_autocast(enabled=True, recipe=Float8BlockScaling()):
    out = te_linear(x)   # 区域内自动量化，出口统一 amax 归约
```

两条 docstring 硬约束（`pytorch/quantization.py:972`）：输入两维须 **16 整除**；`reduce_amax=True` 时同一模块在一个区域只能调一次，否则 amax 被覆盖。

**排错三板斧**：(1) `--log-throughput` 盯 MFU，低于 40% 先查通信；(2) nsys 看 NCCL 是否与 compute 重叠；(3) bubble 心算 `(pp-1)/(mb+pp-1)`：pp=8/mb=16 ≈ 6.7%，mb=64 → 1.6%。

**常见坑**：TP 超单机 NVLink 卡数（TP=16 跨 2 节点）性能崩——MFU 腰斩、all-reduce 占比暴涨；机理是 all-reduce 落 IB 带宽掉一个量级且每层两次。姿势：TP≤8 锁单机、深度不够上 PP、MoE 上 EP。

## 五、批判边界：每条路都有反面

- **TP 不是免费的**：显存充裕时 TP 是纯通信税——llama3-8b 脚本 TP=1 是无声证词，小模型 TP=1 最优。
- **bubble 公式是理想值**：假设各 stage 均匀，straggler 会拖住流水；VPP 的代价是更多 p2p 与显存峰值前移。
- **DelayedScaling 的 1024 步惯性**：对突变（RL 奖励尖峰、分布切换）反应滞后——一代方案的物理上限，blockwise/MXFP8 才是解。
- **blockwise 对齐税**：hidden/ffn 须 128 对齐（4096/14336 天然安全），否则 padding 可浪费双位数百分比算力。
- **EP 网络账**：跨节点 all-to-all 是 IB 带宽怪兽，V3 用 8×800G 才藏得住；4×200G 强上 EP64 会把 MFU 打到地板。

## 六、费曼检验

1. **为什么 TP 必须锁在单机 NVLink 域内，而 EP 可跨节点？**（答：TP 每 layer 两次 all-reduce 与层数同频，不可让；EP 的 all-to-all 可与计算重叠。）
2. **DelayedScaling 为什么叫"delayed"？牺牲什么换什么？**（答：用上一步 amax 历史窗定本步 scale——牺牲对突变的响应，换零同步开销。）
3. **为什么 blockwise（128×128）比 per-tensor 抗激活离群？代价？**（答：离群囚禁在单块内不污染全局；代价是 scale 元数据膨胀 + 128 对齐/split accumulator 税。）

**一句话总结**：训练 = 沿 Transformer 五个结构自由度做通信代价最小的切分组合，再用 FP8 从每个字节榨出第二份显存与算力——Megatron 管并行，TE 管精度，数据管线别让 GPU 挨饿。
