# 04 · CI 双轨、基线体系与版本工程

## 角色定位

Bobber 有两套并行 CI 与一套"土法"版本工程：GitHub Actions 管**静态正确性**（lint/wheel/镜像可构建），GitLab CI 管**真机功能验收**（cast→run-all→parse 全链真跑），`build-dev-wheel` 管开发版版本号。基线体系（`constants.py` 两套内置基线 + `compare_baseline.py` 判定器 + `docs/sample_baseline.yaml` 样例）是"测试结果"变成"验收结论"的最后一环。这四件东西共同回答一个问题：**怎么保证基准工具自己是可信的**。

## 内部结构

**GitHub 轨**（`.github/workflows/python-package.yml`，38 行）：push/PR 触发（`:6`），Python 3.6-3.9 四版本矩阵（`:14`），四步流水——装依赖（`requirements.txt` 全钉版本，docker==4.3.1/numpy==1.19.5 等）、`pycodestyle bobber` lint（`:29`）、`setup.py bdist_wheel sdist` + 装轮子（`:32-33`）、`bobber build` 验证镜像构建（`:36-37`）。

**GitLab 轨**（`.gitlab-ci.yml`，46 行）：三 stage（`:1-4`）。`pre_clean` 杀掉全部容器/镜像/卷（`:13-15`）清历史残渣；`docker_build` 建 venv→建轮子→安装→`bobber build`，再从 build 输出抓镜像 ID 回查 `docker images`（`:26-33`）；`test` 在真机上 `bobber cast /raid`（`:43`）→ `run-all` 两迭代+显式覆盖线程/batch/GPU 参数跑 localhost（`:44`）→ `parse-results --compare-baseline single-dgx-station-baseline`（`:45`）。`variables: GIT_SUBMODULE_STRATEGY: recursive`（`:7`）。

**基线体系**：`SINGLE_DGX_STATION_BASELINE` 单节点阈值（`constants.py:71-97`：读 1.2GB/s/写 1.0GB/s/10 万 IOPS/NCCL 70GB/s/DALI 四档）；`DGX_A100_POD_BASELINE` 覆盖 1-8 节点（`constants.py:99-286`），存储指标随节点数线性放大（1 节点读 2.25GB/s→8 节点 18GB/s），NCCL 恒 180GB/s（2 节点起从 230 降档）。`BASELINES` 字典注册两个可选值（`constants.py:288-291`）。判定器 `metric_passes(expected, got, tolerance)`（`compare_baseline.py:19-51`）：容差单边——expected 乘 `(1-tolerance/100)` 向下放宽（`:47`），`got > expected` 才 PASS（`:48-51`）；结果着色 PASS 绿/FAIL 红（`result_text`，`compare_baseline.py:54-81`），失败计数驱动退出码。

**版本工程**（`build-dev-wheel`，40 行）：bash `case` 分发三函数 `bump_minor/bump_patch/bump_current`（`:3-25`）——共同套路是先 `echo "# SPDX..." > bobber/__version__.py` **重写**文件（`:31`），再 `echo "__version__ = 'M.m.p.dev<timestamp>' >> ...` **追加**（`:8/16/24`，timestamp 来自 `:29`）。所以版本文件永远 2 行，正式版 `6.3.1`（`__version__.py:2`）与 dev 版路径互不纠缠。

## 外部连接

CI 依赖链：两轨都走 `setup.py`——`setup.py:30-31` 的 console_scripts 决定 `bobber` 命令存在，`setup.py:20-27` 的 `package_data` 决定 Dockerfile 与 7 个 shell 脚本随轮子分发（漏一条脚本=容器内 `tests/` 缺文件）。GitLab test stage 的退出码直接由 `compare_baseline` 的失败计数决定（`compare_baseline.py` 里 `sys.exit(BASELINE_FAILURE)` 模式），CI 绿=真机达到 DGX Station 阈值。基线另一来源是用户自产：`parse_results.save_yaml_baseline` 每次 parse 无条件写 `baseline.yaml`（`parse_results.py:404`），经 `--custom-baseline` 回灌比对（`parse_results.py:407-409`），`docs/sample_baseline.yaml` 给出手写模板。

## 数据流

验收数据流：真机 run-all 产出日志目录 → parse-results 聚合成 `systems` 字典 → `compare_baseline` 按 TEST_MAPPING（`compare_baseline.py:11-16`）把 bandwidth/iops/nccl/dali 四键与基线逐项比对 → 终端着色表 + 退出码。开发版本流：改代码 → `./build-dev-wheel [minor|patch]` → 版本变 `M.m.p.dev<ts>` → wheel 装到测试机 → 镜像 tag 跟版本走（`management.py:77` 的 `nvidia/bobber:{version}`），版本闸门（`management.py:267-286`）保证 CLI 与容器不串版本。

## 设计决策

- **双轨分工而非主从**：GitHub 轨快、免真机，拦语法/打包/镜像构建问题；GitLab 轨慢、要 DGX，拦"能跑但数字不对"。基准框架的 CI 必须包含真机链——否则解析器改动可能悄悄改变数字口径。
- **内置基线进 constants 而非外部文件**：随包分发、随版本演进，`--compare-baseline dgx-a100-pod-baseline` 开箱即用；`docs/baselines.md` 记录官方基线的来源背景。
- **单边容差**：性能验收只罚"低于阈值"（`compare_baseline.py:44-48`），容差语义在 `bobber.py:224-233` 的 help 里写死"不会因高于基线而惩罚"——防止基线过低时全员 FAIL，也接受基线保守。
- **版本闸门三处一致**：轮子版本、镜像 tag、日志文件名 version 段（`common.py:63-67`）三者联动，`check_bobber_version` 拦跨版本混目录（`common.py:105-107`）。

## 新人提示

跑 GitLab 轨前确认 runner 是带 GPU 的 DGX 且 `/raid` 存在——`cast /raid`（`.gitlab-ci.yml:43`）是硬编码路径。`GIT_SUBMODULE_STRATEGY: recursive`（`.gitlab-ci.yml:7`）在本仓**没有对应的 .gitmodules**，nccl-tests 等是 Dockerfile 构建期 clone（`Dockerfile:50/65`），该变量是残留配置，别据此推断"子模块引入测试仓"。改 `__version__.py` 手工编辑会被下次 `build-dev-wheel` 覆盖——dev 版永远走脚本，正式版发版时单独写入。给新硬件加基线：抄 `DGX_A100_POD_BASELINE` 结构进 `constants.py`，注册进 `BASELINES`（`constants.py:288-291`），CLI 侧 `choices=BASELINES`（`bobber.py:219`）自动生效。
