# 02 · 从 SWIG 到 Python 环境的绑定链 —— GymSolver 五层穿透

> 对象：`minisat/minisat/gym/GymSolver.i`（60 行接口定义）、`minisat/minisat/gym/GymSolver_wrap.cxx`（4455 行生成胶水）、`minisat/minisat/gym/GymSolver.cc`（97 行）与 `minisat/minisat/gym/GymSolver.h`、`minisat/minisat/gym/GymSolver.py`（161 行生成代理）、`minisat/minisat/gym/MiniSATEnv.py`、`minisat/__init__.py`、`minisat/Makefile`、`minisat/CMakeLists.txt`
> 一句话：一条五层单向链——C++ `env_state_*` 成员 → `GymSolver` getter 返回裸指针 → 手写 SWIG out-typemap 逐元素转 PyList → 生成的 `_GymSolver.so` C 胶水 → 生成的 Python 代理 → `gym.Env` 语义层；决策走反向下行链，32767 哨兵与 VAR_ID_IDX 常量是贯穿两侧的隐式契约。

## 一、角色定位

第 1 篇里 `Solver::saveState` 把求解器状态线性化成 `env_state_*` 四组 `std::vector`；本篇讲这些数据如何跨越 C++/Python 边界。`GymSolver` 类（`minisat/minisat/gym/GymSolver.h:35-48`）是刻意做薄的门面：内嵌一个 `SimpSolver S`（`minisat/minisat/gym/GymSolver.h:37`），对外只暴露 8 个方法——构造、`step`、`getReward`、`getDone` 和四个状态 getter。它不做任何求解逻辑，只做协议转换。

接口文件 `minisat/minisat/gym/GymSolver.i` 开头的注释交代了这层设计的演化史（`minisat/minisat/gym/GymSolver.i:9-13`）：原实现把状态序列化成**字符串**再在 Python 侧解析；本版改为直接返回 Python list；作者还自评"再进一步返回 numpy 数组应该更快"——即当前实现停留在"正确但非最优"的中间态。这也是本仓从 feiwang3311 fork 演进的代际痕迹之一。

## 二、内部结构

### 2.1 GymSolver.cc：97 行的门面

- **构造**（`minisat/minisat/gym/GymSolver.cc:39-62`）：三个参数 `satProb/with_restarts/max_decision_cap`，后两个直通求解器成员（`minisat/minisat/gym/GymSolver.cc:42-43`）。流程为 gz 流打开 CNF → `parse_DIMACS`（`minisat/minisat/gym/GymSolver.cc:44-50`）→ `S.eliminate(true)` 预处理并拦截"化简即 UNSAT"（`minisat/minisat/gym/GymSolver.cc:52-56`）→ `S.solveLimited(dummy)`。最后一行是点睛之笔：注释（`minisat/minisat/gym/GymSolver.cc:58-59`）说明"现在 solveLimited 只是初始化问题，需要若干 step 才能做完"——因为挂起机制（第 1 篇），首次 `solveLimited` 会在第一个决策点挂起返回，真正求解散布在后续 `step` 里。
- **step**（`minisat/minisat/gym/GymSolver.cc:64-71`）：决策注入的唯一入口。`decision == 32767` 哨兵 → `S.agent_decision = S.default_pickLit()`（回落 VSIDS）；否则 `mkLit(abs(decision)-1, decision < 0)` 把 DIMACS 风格 ±var 码翻成 `Lit`；最后 `S.step()` 驱动求解器跑到下一个决策点或终态。
- **getter 组**（`minisat/minisat/gym/GymSolver.cc:73-96`）：`getReward`/`getDone`（`getDone()` 就是 `!S.env_hold`）+ 四个状态 getter。关键细节：状态 getter 返回的是 `&S.env_state_*` **裸指针**（如 `minisat/minisat/gym/GymSolver.cc:90-92` 的 `getClauses` 返回 `std::vector<std::vector<int>>*`）——零拷贝，数据仍由求解器成员托管，typemap 读取时才逐元素搬进 PyObject。

### 2.2 GymSolver.i：四段手写 out-typemap

SWIG 接口文件是绑定链的真正"源代码"（生成物都由它派生）。`%module GymSolver`（`minisat/minisat/gym/GymSolver.i:15`）之后，为每个返回 `std::vector*` 的 getter 手写了一段 out typemap：

- 标量向量（`minisat/minisat/gym/GymSolver.i:19-24` 的 `getMetadata`、`minisat/minisat/gym/GymSolver.i:26-31` 的 `getAssignments`）：`PyList_New` + 循环 `PyLong_FromLong`；
- 浮点向量（`minisat/minisat/gym/GymSolver.i:33-38`）：同构，换 `PyFloat_FromDouble`；
- 嵌套向量（`minisat/minisat/gym/GymSolver.i:40-52`）：两层循环——外层为每个子句建 `PyList`，内层填文字，最后挂回外层 list。

为什么要手写？SWIG 的 `std_vector.i` 标准支持生成的是带代理类的 SWIG 类型包装而非原生 list，嵌套 `vector<vector<int>>` 更是默认不映射。这四段 typemap 标注着 "Graph-Q-SAT UPD: return vectors to support variable sized lists"（`minisat/minisat/gym/GymSolver.i:18`）——变尺寸问题集正是 NVIDIA 版相对原 fork 的核心增量（对应第 1 篇的 `env_state_*` vector 化）。文件末尾 `%include "GymSolver.h"`（`minisat/minisat/gym/GymSolver.i:54`）让 SWIG 解析类声明，typemap 按方法名精确匹配生效。

### 2.3 生成物：GymSolver_wrap.cxx 与 GymSolver.py

`minisat/minisat/gym/GymSolver_wrap.cxx` 共 4455 行，文件头即声明 "automatically generated by SWIG"（`minisat/minisat/gym/GymSolver_wrap.cxx:2`），宏 `SWIGVERSION 0x030012`（`minisat/minisat/gym/GymSolver_wrap.cxx:3041`）对应 SWIG 3.0.12。业务面其实很小：

- 7 个 `_wrap_GymSolver_*` 方法（`minisat/minisat/gym/GymSolver_wrap.cxx:3478-3633`）：step/getReward/getDone/getMetadata/getAssignments/getActivities/getClauses，各自做参数解包→调 C++→（对四个 getter）执行 typemap 展开的 PyList 循环；
- 模块方法表（`minisat/minisat/gym/GymSolver_wrap.cxx:3698-3704`）把它们注册成 `METH_VARARGS` 函数；另有前缀不同的 `_wrap_new_GymSolver`/`_wrap_delete_GymSolver` 完成构造/析构；
- 模块初始化 `PyInit__GymSolver`（`minisat/minisat/gym/GymSolver_wrap.cxx:3033` 的宏定义点）。

Python 侧的 `minisat/minisat/gym/GymSolver.py`（161 行）同样是生成物（`minisat/minisat/gym/GymSolver.py:1-5` 的 "Do not make changes to this file" 头）。甄别要点：L62-105 的 `_swig_setattr_nondynamic`/`_swig_getattr`/`_swig_repr` 是所有 SWIG 代理共享的纯样板，真正的业务面只有 `class GymSolver`（`minisat/minisat/gym/GymSolver.py:119`）——`__init__` 调 `_GymSolver.new_GymSolver`（`minisat/minisat/gym/GymSolver.py:126-131`），7 个方法各自一行转发到 C 扩展（`minisat/minisat/gym/GymSolver.py:133-152`），`__swig_destroy__` 挂析构（`minisat/minisat/gym/GymSolver.py:154`）。按本图谱规范，这类纯转发样板不建函数节点——语义全部归属 C++ 侧。

### 2.4 两层 __init__.py 与 gym 注册

- `minisat/minisat/gym/MiniSATEnv.py:36` 的 `from .GymSolver import GymSolver` 触发生成代理加载 `.so`；
- `minisat/__init__.py:28` 先 `from .minisat.gym.MiniSATEnv import gym_sat_Env`，再 `minisat/__init__.py:30-33` 调 `gym.envs.registration.register(id="sat-v0", entry_point="minisat.minisat.gym.MiniSATEnv:gym_sat_Env")`。

注意包结构的嵌套：`minisat/`（Python 包层）内套 `minisat/minisat/`（C++ 源码树同名目录），注册字符串因此是四段路径。**import 副作用注册**是这条链的隐式前提——`add_metadata.py:16` 的注释说得最明白："import gym, minisat # you need the latter to run __init__.py and register the environment"。`gqsat/utils.py:432` 的 `import gym, minisat` 同理。谁忘了 import minisat，`gym.make("sat-v0")` 就报未注册。

## 三、外部连接

**上行数据流**（每次决策点后）：`Solver::saveState` 填 `env_state_*` → `GymSolver` getter 返回指针 → typemap 循环产 PyList → `MiniSATEnv.parse_state_as_graph`（`minisat/minisat/gym/MiniSATEnv.py:105`）取用：`getMetadata`（`minisat/minisat/gym/MiniSATEnv.py:121-128`）、`getAssignments`（`minisat/minisat/gym/MiniSATEnv.py:129`）、`getClauses`（`minisat/minisat/gym/MiniSATEnv.py:150`）。`getActivities` 虽有完整通道但 Python 侧零消费（与第 1 篇 `getReward` 同属建好未用的管线）。

**下行数据流**：`MiniSATEnv.step` 把 Q 网络的动作编码为 ±(var+1) 或 32767（`minisat/minisat/gym/MiniSATEnv.py:281-291`）→ `GymSolver.step`（代理转发）→ `mkLit` → `S.step()`。

**两条构建线分管**：`minisat/CMakeLists.txt:68-72` 的 `MINISAT_LIB_SOURCES` 只有 4 个 .cc（Options/System/Solver/SimpSolver），**不含任何 gym/ 文件**——CMake 线只管 CLI 可执行文件与安装库（`minisat/CMakeLists.txt:80-81` 的 `minisat_core`/`minisat_simp`）；Python/SWIG 绑定完全由 `minisat/Makefile:224-227` 的 `python-wrap` 目标承担：先依赖动态库全量编译，再 `g++ -O2 -fPIC -c ...GymSolver_wrap.cxx ... -I/usr/include/python3.6`，最后把全部对象文件链接成 `minisat/gym/_GymSolver.so`。`minisat/Makefile:100` 的 `OBJS = $(filter-out %Main.o, ...)` 把两个 Main 排除在 .so 之外（库不能带 main 符号）。

## 四、数据流：一次观测转换的成本解剖

以 `getClauses()` 为例，单个决策点的完整开销：

1. C++ 侧 `saveState` 全量重建子句向量（第 1 篇第四节）；
2. typemap 外层循环 `PyList_New(子句数)`，每子句 `PyList_New(文字数)`，逐文字 `PyLong_FromLong`——O(总文字数) 次 PyObject 分配；
3. Python 侧 `parse_state_as_graph` 再把嵌套 list 转成 numpy 边张量（`minisat/minisat/gym/MiniSATEnv.py:165-188`）。

即同一份子句数据在每个决策点被搬三次：求解器堆 → C++ vector → PyList → numpy。GymSolver.i 头注释设想的"直接返回 numpy 数组"（`minisat/minisat/gym/GymSolver.i:11-12`）能砍掉第三次搬运。对训练吞吐敏感的复现者，这是最先该优化的位置。

## 五、设计决策

**为什么 getter 返回裸指针而非值拷贝？** `&S.env_state_metadata`（`minisat/minisat/gym/GymSolver.cc:82-84`）指向活成员。收益是 C++ 侧零拷贝；代价是生命期耦合——指针只在 GymSolver 对象存活且 `env_state_*` 未被下一次 `saveState` 重写前有效。当前用法（同步调用、每次 step 后立即取）恰好安全，但如果有人缓存了 getClauses() 的结果再 step 一步，C++ vector 重新分配后 Python list 已然固化旧值——好在 typemap 是即时转换，风险被"读时快照"语义吸收。

**为什么硬编码 python3.6？** `minisat/Makefile:226` 的 `-I/usr/include/python3.6` 是构建环境钉子，且讽刺的是上一行注释（`minisat/Makefile:225`）写着 "Graph-Q-SAT UPD: bump python version"——bump 的动作就是把这行从更老的版本号改到 3.6。配套的 `Dockerfile:23` 里 `apt-get install ... python3.6 ... swig` 钉死了完整环境。要在现代系统重建，改这一行 include 路径（或换成 `python3-config --includes`）是第一步，也是新手最常卡住的地方。

**两侧常量的隐式契约**：绑定的正确性依赖三组"无编译期保障"的跨语言约定——(1) 32767 哨兵：`minisat/minisat/gym/GymSolver.cc:65` vs `minisat/minisat/gym/MiniSATEnv.py:39` 的 `MINISAT_DECISION_CONSTANT`；(2) `toInt` 赋值编码 0/1/2（第 1 篇）；(3) `VAR_ID_IDX=0`：定义在 `minisat/minisat/gym/MiniSATEnv.py:40-42`（"顶点特征第 0 列=是否变量节点"），却被 `gqsat/agents.py:17` 与 `gqsat/learners.py:19` 跨包 import——gqsat 训练栈与 minisat 环境栈之间唯一的程序性接口就是这个 int 常量和动作编码约定，改任何一侧另一侧静默出错。

**为什么不用 pybind11？** 2020 年时点 pybind11 已成熟，但本仓继承自更早的 fork 血统（`minisat/minisat/gym/GymSolver.cc:3` 的拷贝声明），SWIG 方案延续了原实现；且嵌套 vector 的手写 typemap 总量只有 40 行，迁移收益不足以抵消重验证成本。这是典型的"研究代码锁定初始技术栈"现象。

## 六、新人提示

1. **改绑定先改 .i，再重新跑 SWIG**：`GymSolver_wrap.cxx` 与 `GymSolver.py` 都是生成物（两文件头部都有警告），直接改生成物会在下次 `swig -python GymSolver.i` 时全部丢失。仓内没有提交重新生成的 Make 规则（`python-wrap` 目标只编译已存在的 wrap.cxx），意味着改接口后要手动跑 swig 并提交两个生成物。
2. **构建顺序**：`make python-wrap` 依赖动态库目标（`minisat/Makefile:224`），且要求先在仓根把 `minisat/` 放进 `PYTHONPATH`（`minisat/__init__.py` 的注册才能生效）。Docker 路径（`docker_build.sh`）是一等公民，本地裸机重建按 `Dockerfile:23` 对齐依赖版本最省事。
3. **排查"sat-v0 未注册"**：先确认 import 链 `minisat → minisat.minisat.gym.MiniSATEnv → .GymSolver → _GymSolver.so` 的最后一环能加载——`.so` 与 Python 版本不匹配时报错常被误读为 gym 注册问题；`add_metadata.py:16` 的注释是这条链的标准修法。
4. **观测为空图的两种含义**：`getClauses()` 返回空 list（`minisat/minisat/gym/MiniSATEnv.py:152-163`）既可能是"超过 max_decision_cap 后不再建图"（第 1 篇的截断），也可能是求解已完成——区分要靠 `getDone()`。混淆二者会把截断当成终点提前结算奖励。
5. **阅读顺序建议**：`GymSolver.h`（35-48 行的类面）→ `GymSolver.i`（60 行）→ `GymSolver.cc`（97 行）→ `MiniSATEnv.py` 的 `parse_state_as_graph`——四步走完绑定链全程；`GymSolver_wrap.cxx` 只需看 L3698-3704 的方法表确认导出面，不必通读。
