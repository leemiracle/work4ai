# 04 · 行为与完整性分析线：behavioral_ast · behavioral_taint_tracking · artifact_integrity

## 一、角色定位

静态正则抓"写了什么字"，行为线抓"代码在做什么结构"。这条线由三个分析器组成：`behavioral_ast`（733 行）在 Python AST 上识别危险执行形态（exec/eval/反射访问/危险链条）；`behavioral_taint_tracking`（742 行）做单遍污点传播，把"凭据/文件/网络输入 → 外传/执行/写文件/反序列化"的 source→sink 流找出来；`artifact_integrity`（1130 行）不解析代码，专抓制品层的混淆与逃逸——零宽/不可见字符密度、混排文字、字距拉长、误导扩展名。三者共同补上"语义级规避"层：`getattr(os, 'sys'+'tem')` 拼接在正则层看不见，在 AST 层是显式的调用节点+常量参数。

## 二、内部结构

**behavioral_ast.py**：规则表三连——`_RULE_MESSAGES/_RULE_SEVERITIES/_RULE_CONFIDENCES`（behavioral_ast.py:182/195/208）定义 AST1-AST10：exec/eval HIGH 0.85（AST1/2），`__import__`/subprocess 家族 MEDIUM（AST3/4，`_SUBPROCESS_CALLS` :117），os.exec/spawn 家族 HIGH（AST5，`_OS_EXEC_CALLS` :129-152），compile MEDIUM（AST6），getattr 动态属性 LOW 0.50（AST7），危险执行链 CRITICAL 0.95（AST8），getattr 字面量危险名 HIGH（AST9，`_DANGEROUS_GETATTR_NAMES` :68），不安全反序列化 MEDIUM（AST10，`_DESERIALIZATION_SINKS` :160-177 覆盖 pickle/marshal/dill/jsonpickle/joblib.load/yaml.unsafe_load；yaml.load 安全性取决于 Loader 参数，`_SAFE_YAML_LOADERS` :180 放行 SafeLoader/CSafeLoader/BaseLoader）。`_analyze_python`（:417-592）单次 `ast.walk`：先处理 Subscript 反射——`os.__dict__["system"]` 字面量危险名 → AST9、动态键 → AST7（:478-496）；再处理 `__dict__.get/setdefault/pop` 方法型反射（:500-527，注释明言"下标访问的等价拼写，不能逃过 AST7/AST9"）；最后 `resolve_call_name` 解析调用名，失败走 `resolve_dynamic_import_call` 兜动态导入链——`importlib.import_module('os').system(...)` 解析回 'os.system' 重新进 sink 阶梯（:529-533）。`node`（:631-733）：只处理 .py（:642），超 1M 记 PARTIAL/SIZE_LIMIT（:665-675），语法错记 SKIPPED（:702-709），COMPLETED 事件带 emitted_finding_ids（:711-717）；预算耗尽转 terminal_limit 后续路径全记 PARTIAL（:644-655）。

**behavioral_taint_tracking.py**：source 四类——凭据/环境（`_CREDENTIAL_SOURCES` :67）、文件读（:75）、网络输入（:83，requests/httpx/urllib/socket.recv）、用户输入（:102，input/sys.stdin）；sink 四类——网络输出（:114）、代码执行（:131）、文件写（:146）、反序列化（:163）。规则 TT1-TT6（:187-203）：通配流 HIGH/MEDIUM（TT1 直接/TT2 间接），**凭据→网络 CRITICAL 0.90（TT3）**、文件读→网络 HIGH（TT4）、外部输入→执行 CRITICAL 0.90（TT5）、外部输入/文件读→反序列化 HIGH（TT6）；`_pick_rule`（:313-325）按 source×sink 选最specific规则。`_analyze_python`（:454-601）单遍 walk：Assign 记污点名（:526-555）——支持下标源 `os.environ["KEY"]`（含别名）、再赋值/容器构造/f-string 传播（注释示例 :542-543）；Call 处 `_resolve_sink_name`（:288-303，类型/别名感知+动态导入链兜底）判 sink，`open` 仅写模式算（`_is_open_for_write` :334，:565-566）。`node`（:640 起）账本模式与 behavioral_ast 一致。

**artifact_integrity.py**：核心是 `_text_signals`（:850-933）——返回 (format_char_density, mixed_script, first_nul_line, first_obfuscation_line)。不可见字符按 `unicodedata.category` 统计 Cf/Cc（软连字符 U+00AD 单列，:904-908），仅放行 \n\r\t（:59）；混排检测只关心 latin×cyrillic/greek 同 token（:915-928）——西里尔同形字攻击的特征。混淆行探测四信号源取最小行号（:864-899）：字距拉长 run、上下文可忽略行、定向混淆指令、投影提示注入行。`node`（:993-1130）产出 AE2 误导扩展名（:1031-1040）、AE5 指令制品超语义分析上限（:1044-1056）、AE3 NUL 字节（:1064-1074）、AE4 可疑 Unicode/混排（:1075-1084）、AE6 字符间分隔符逃逸（:1085-1095）；AE6 同时追加一条 `artifact_interpretation` PARTIAL 系统事件（:1113-1124），把"此行之后内容解释权存疑"写进账本。Finding 构造器固定 category="analysis-evasion"（:988-989）。

**共享地基 python_ast.py**：`MAX_PYTHON_AST_SOURCE_CHARS = 1M`（python_ast.py:37）单文件上限，`ParsedPythonFile`（:45）封装 tree/lines/import_aliases/源段提取；运行时缓存 32 条 LRU（:156-158），按 python_ast_cache_key 共享——behavioral 两分析器与 static_runner 的 AST 组用同一份解析，一个 skill 只 parse 一次。

## 三、外部连接

三个分析器都从 `nodes/analyzers/common.py` 取 AST 工具（resolve_call_name/apply_import_aliases/build_type_map，common.py:199-362）；taint 直接 import static_runner 的常量与 `analyzer_finding_to_finding`（taint :57-62）；artifact_integrity 消费 build_context 的 `artifact_inventory` 元数据（misleading_extension/content_kind/contains_nul）；账本走 inspection_ledger；三者共享 `transitive_remaining_seconds` 全局时钟。

## 四、数据流

behavioral 线：components 过滤 .py → `get_python_ast(cache_key, content, path)` 取共享解析 → 单遍 walk 产出 AnalyzerFinding（带完整源段、字符列坐标）→ analyzer_finding_to_finding 转图态 → 每路径账本事件。artifact 线：artifact_inventory + local_file_cache → 逐制品元数据检查 + 文本信号单遍扫描 → AE 系 Finding + 账本。两线预算模式相同：`_BehavioralBudget/_ArtifactIntegrityBudget` 在**构造 Finding 过程中**查时限（每次迭代/每 4096 字符），超限抛内部错误携带已产出前缀，node 层转 PARTIAL——绝不在事后批量截断。

## 五、设计决策

1. **等价拼写封堵**：AST7/AST9 同时覆盖 `__dict__[...]` 下标与 `.get()/.setdefault()/.pop()` 方法两种反射拼写；动态导入链兜底保证 `importlib.import_module('subprocess')` 与直接 import 同罪——攻防视角的"形态归一"。
2. **污点分析刻意做浅**：单遍 walk + 赋值传播 + f-string/容器传播，不做过程间分析——skill 代码规模小，浅分析覆盖主要攻击形态且可证有界。
3. **AE6 的"解释权存疑"账本事件**是本仓独创设计：不判定恶意，只声明"此行后的文本我无法可靠解释"，把判定权交给人。
4. **预算内嵌构造期**：三个分析器各自复制了一套 Budget/ResourceLimitError 小类（behavioral_ast.py:224/234、taint :208/218、artifact :381/391），不抽公共基类——隔离优先于复用。

## 六、新人提示（坑与勘误）

- **AE1 不在 artifact_integrity**：grep 全 src，`rule_id="AE1"` 唯一出现在 `nodes/finalize_inspection_ledger.py:643`（"Referenced artifact was not completely inspected"）——AE 系规则的 1 号在账本定稿节点而非分析器，读代码别找错文件。
- `open()` 只有写模式才进 FILE_WRITE_SINKS（taint :565-566）——只读 open 是 source 不是 sink，一函数两身份。
- AST7 置信度仅 0.50：getattr 动态访问大量合法使用，LOW 是刻意校准，meta_analyzer 过滤时别当漏报。
- behavioral 线读 `local_file_cache or file_cache`（behavioral_ast.py:634），与静态线同视图；LLM 线另用 llm_file_cache——同一文件在两条线的可见内容可能不同。
- 反序列化白名单是 Loader 名而非模块名（:180）：`yaml.load(x, Loader=CSafeLoader)` 放行、`yaml.unsafe_load(x)` 无条件危险——新增 sink 时保持"参数决定安全性"与"无条件危险"两类分法。
- `_OS_EXEC_CALLS` 含完整 execv/spawn 家族约 20 名（:129-152）；补 sink 记得 SEVERITIES/CONFIDENCES/MESSAGES 三表同步加。
