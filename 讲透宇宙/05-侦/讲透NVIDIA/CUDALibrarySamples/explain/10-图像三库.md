# 10 · 图像三库：nvJPEG ROI、nvJPEG2000 编码器与 vendored 甄别

## 角色定位

图像编解码域（L14 层，66 节点）三库分工：nvJPEG 六示例（解码/后端+ROI/多实例解码/多实例编码/缩放/缩放+水印）覆盖 JPEG 全生产链；nvJPEG2000 四示例（基础/流水线/瓦片部分解码+编码器）主打码流可控性；nvTIFF 七示例走 TIFF 元数据与区域解码。本篇聚焦两个最重的"支撑头"型示例与一个 README 级勘误。

## 内部结构

nvJPEG ROI 示例是"薄主程序+厚支撑头"的极致：nvJPEGROIDecode.cpp 仅 565 行（parseDecodeCoordinates :22、pick_gpu_backend :79、select_backend :129、write_images :286），真正重量在 **nvJPEGROIDecode.h 693 行**——`decode_per_thread_params`（:73，每线程独立 nvjpeg 流与缓冲）与 `decode_params_t`（:85，全局目录/ROI/后端/缩放）两个参数类 + dev/host_malloc/free 四内存回调 + 14 个工具函数；目录枚举直接用 POSIX `struct dirent`（:319）。threadpool.h 是**自实现** 114 行线程池（`class ThreadPool` :30，任务队列+`wait()` :56 屏障）——注意甄别：它不是 vendored 第三方（图像域无 NPP 那样的 dirent.h 副本），多线程批次调度全靠它。

## 外部连接

nvJPEG ROI 同时创建两个解码器实例对冲（nvJPEGROIDecode.h:116-117：`NVJPEG_BACKEND_HYBRID` CPU 版+`NVJPEG_BACKEND_GPU_HYBRID` GPU 版），按流头探测结果二选一——后端选择逻辑就是示例的灵魂。nvJPEG2000 编码器（nvjpeg2k_encode.cpp 1292 行，本域最大 .cpp）的骨架在 :1252-1254 三连 create（Encoder/EncodeState/EncodeParams）与 :1287-1289 对称 destroy；:732 `populate_encoderconfig` 组装码流参数，:832 `nvjpeg2kEncode` + :835-838 **两遍式** `nvjpeg2kEncodeRetrieveBitstream`（第一遍 NULL 探尺寸、第二遍真取码流）。

## 数据流

ROI 链：目录枚举→分批→线程池并发→逐流选后端→`nvjpegDecodeBatched` 带 ROI 裁剪（越界检查在 nvJPEGROIDecode.h:219-220 注释块）→BMP 落盘。编码器链：PFM/PNM/BMP 三种读入器（浮点 PFM :133 行级实现）→`nvjpeg2kImagePlaceholder`→编码→两遍取流→写 .jp2。缩放+水印示例则演示解码→`NVJPEG_OP_RESIZE+WATERMARK` 融合算子→编码的单遍往返。

## 设计决策

两遍取码流是 GPU 库 API 的通用形态（先 query 后 execute，同 cuTENSOR workspace 模式）；per-thread 参数类让多线程无需锁竞争句柄；编码器把 NLT（非线性传输）参数做成开关（:816-820 SetNLTInfo 带参/NULL 两分支），覆盖 HDR 浮点输入。**README 勘误**：nvJPEG2000/README.md 的 Examples 清单只列三个 Decoder，**Encoder 示例缺席**；且第三条链接写作 `nvjpeg2000-Decoder-Tile-Partial/`，实际目录是 `nvJPEG2000-Decoder-Tile-Partial`——大小写不匹配在 Linux 上是死链。

## 新人提示

读 ROI 示例先看头文件的参数类再看 cpp 主流程（顺序与行数相反）；nvJPEG2000 编码器从 main（:1074）倒着读配置填充最快；nvTIFF 的 README 有 API 矩阵表（0.8 API），是三库中唯一表格化文档。跑编码器需系统有 nvjpeg2k 库（CMake `find_library(NVJPEG2K_LIB)` 强制探测），-lstdc++fs 链接行提示老 GCC 的 filesystem 兼容需求。
