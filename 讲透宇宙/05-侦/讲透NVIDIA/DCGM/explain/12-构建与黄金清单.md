# 12 · 构建与黄金清单：dcgmbuild 三镜像链与包内容守门

## 角色定位

DCGM 发布 deb/rpm 包与官方容器镜像，而生产它们的构建机本身也是被版本化的产物——这是 `dcgmbuild/` 的意义。三条流水线：buildx bake 编排 common-host-software → toolchain → dcgmbuild 镜像链，从源码编译 gcc 14.3 交叉工具链与依赖静态库；`docker/` 的 ubi9 与 ubuntu22.04 运行时镜像从 CUDA 公共仓库装成品包发布；`scripts/verify_package_contents/` 的 54 份黄金清单 .txt 对每个包做文件列表 diff 防漂移。

## 内部结构

编排入口 `dcgmbuild/build.sh:34` 把 `dependency_flags.sh bake` 输出灌进 BAKE_ARGS 后 `docker buildx bake`（`dcgmbuild/build.sh:49`）。拓扑在 `dcgmbuild/docker-bake.hcl`：toolchain 引 `target:common-host-software`（`docker-bake.hcl:59`），dcgmbuild 引 `target:toolchain-${architecture}`（`docker-bake.hcl:73`），matrix 默认双架构（`docker-bake.hcl:23,64`）；`FROM toolchain`/`FROM base_image` 是 BuildKit named contexts 而非 ARG（`docker-bake.hcl:48` 映射 ubuntu:24.04）。

toolchain 镜像（`dcgmbuild/container-images/toolchain/Dockerfile`）的 FROM scratch 下载阶段收 crosstool-ng 全家源码与 9 个 CUDA 安装器 deb（11.8/12.9/13.2 各三架构，行 82-112）。随后编译 crosstool-ng，`COPY crosstool-ng/$ARCHITECTURE.config` 为 ct-ng 配置（`toolchain/Dockerfile:163`），一次 `ct-ng build`（行 168）产出 `/opt/cross` 交叉工具链。最终阶段 `FROM common-host-software`（行 171）生成 CMake gcc/clang 双 toolchain 文件（clang 借 `--gcc-toolchain` 复用 gcc sysroot，行 276）、Meson 交叉文件（行 300），异构挂 `qemu-$ARCHITECTURE` emulator（行 215）；Rust 侧 Corrosion 集成先 unset 工具链文件（`corrosion.sh:23`）。

dcgmbuild 镜像三个 FROM：`FROM scratch AS dcgmbuild-downloads`（`dcgmbuild/Dockerfile:18`）装 tarball；`FROM toolchain AS builder`（行 53）设 `CC=/opt/cross/bin/$TARGET-gcc` 等交叉变量（行 66-70）与 `CMAKE_STAGING_PREFIX`（行 72），`find /tmp/scripts -name '*.sh' | sort` 按序号执行依赖脚本（行 82）；第三个 `FROM toolchain`（行 86）把 staging `COPY --from=builder` 进 sysroot（行 88）。

## 外部连接

`dcgmbuild/dependency_flags.sh` 是依赖版本唯一事实源：`dependencies()` heredoc（`dependency_flags.sh:20`）每行"名称 URL sha256"三列——Boost 1.85.0（行 22）、gcc 14.3.0（行 30）、glibc 2.27（行 33）、Linux 4.20.17（行 37）、CUDA 三代安装器（行 43-51）。唯一特例 TCLAP 走 git URL 加 tag（行 65），对应 `ADD ${TCLAP_URL}#${TCLAP_TAG}`（`dcgmbuild/Dockerfile:49`）；输出双格式 bake/buildkit（行 89/92）；tarball 一律 `ADD --checksum`（`dcgmbuild/Dockerfile:42`）。

运行时侧，`docker/Dockerfile.ubi9` 基于 `nvcr.io/nvidia/cuda:13.0.1-base-ubi9`（`docker/Dockerfile.ubi9:15`），同容器并存 cuda13 与 cuda12 两套引擎包（行 33-34；ubuntu22.04 顺序相反，`docker/Dockerfile.ubuntu22.04:31-32`）。GPU 访问靠 Container Toolkit 识别的 ENV：`NVIDIA_VISIBLE_DEVICES=all`（`Dockerfile.ubi9:38`）、`NVIDIA_DRIVER_CAPABILITIES=compute,utility,compat32`（行 42）。ENTRYPOINT `nv-hostengine` 前台运行（行 49），`EXPOSE 5555` 供 dcgm-exporter 连接（行 48）。`docker/Makefile:23` 硬编码 `DCGM_VERSION := 4.4.1` 对齐公共仓库。

## 数据流

物料流：版本表→bake args→ADD checksum→编号脚本→staging→sysroot→交叉编译→`_out/` 包。守门：`verify_package_contents.sh:71` 读实际版本，`specialize()`（行 30）把清单占位符 `<PACKAGEVERSION>` 等四类替换为真值（行 57-61），与 `dpkg --contents` 排序清单 diff（行 76）；rpm 用 `rpm --query --list` 滤 `.build-id`（行 82）。再生成反向：`generate_package_contents.sh:28` 把实际版本逐字符展开成 `[4].[3]...` 正则类防误替换再回写占位符，soname `.4` 归一为 `.<MAJORVERSION>`（行 43）；`generate_all_package_contents.sh:81` 删 `_out` 双架构重建（行 91-92）后逐包生成（行 95-98）。不在容器内时经 `intodocker.sh` 重跑（`_common.sh:32`），靠镜像预埋 `DCGM_BUILD_INSIDE_DOCKER=1`（`toolchain/Dockerfile:384`）防递归。

## 设计决策

三个决策。第一，glibc 2.27 + Linux 4.20.17 老基线是兼容旧发行版的下限锚（`dependency_flags.sh:33,37`），代价是 Boost 规避 statx：Boost.Filesystem 会探测使用内核头的 statx 系统调用，但 glibc 2.28 才有 `statx()` 包装函数，故 `define=BOOST_FILESYSTEM_DISABLE_STATX` 硬关闭（`0120_boost.sh:40`，注释见行 33）退回 stat 老路径。第二，多版本 LLVM 用 update-alternatives 主/从链接组：`0050_clang.sh:55` 以 clang 为主链接、其余 llvm-* 全 `--slave`（行 62-79），一条 `--install` 原子切换（行 81）。第三，黄金清单把包内容升格为评审对象——新增一个 so 即 diff 失败，占位符让清单跨小版本复用。

## 新人提示

升级依赖先改 `dependency_flags.sh`——Dockerfile 的 ARG 全由它喂入，直接改会被 bake 覆盖。本地验证 `./build.sh x86_64` 单架构起步。改 CPack 安装规则后必须重跑 `generate_all_package_contents.sh` 并把 54 个 .txt 的 diff 一起提 PR，否则校验必红。`docker/Makefile:23` 的 4.4.1 是运行时镜像拉公共仓库的包版本，非源码仓 4.6.1；CLANG URL 是 `apt.llvm.org/llvm.sh` 安装器，校验和锁安装器本身。
