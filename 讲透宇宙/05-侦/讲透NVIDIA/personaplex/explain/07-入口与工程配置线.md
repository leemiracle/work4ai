# 07 · 入口与工程配置线：app.tsx、index.html、env.ts 与 client 工程骨架

## ① 角色定位

`client/` 是 PersonaPlex 的 Web 前端（React 18.3 + Vite 5 + TypeScript strict + Tailwind/daisyUI），从 Kyutai 的 moshi 客户端 fork 而来——`package.json:2` 的包名仍是 `"kyutai-client"`，是血统的直接证据。本篇覆盖入口链（index.html → app.tsx → Queue 页）与工程配置层（vite.config.ts、tsconfig.json、env.ts、样式管线、client/Dockerfile）：这层代码不处理任何音频或协议，但它决定了三件关键事——开发期必须 HTTPS、`/api` 请求代理到哪、启动期环境变量是否齐全（fail-fast）。

## ② 内部结构

**入口链**。`index.html:11` 定义唯一挂载点 `#root`，`index.html:12` 以 module script 加载 `/src/app.tsx`；`index.html:2` 在 `<html>` 上预置 `data-theme="light"` 与 `bg-neutral-50`，与后文 Queue 硬编码浅色主题一致。`app.tsx:9-14` 用 `createBrowserRouter` 注册单一路由 `/` → `<Queue />`，`app.tsx:16-18` 是标准的 `createRoot(...).render(<RouterProvider/>)`；`app.tsx:6` 顺带引入全局样式 `index.css`。整个应用没有第二个路由——会话页切换靠 Queue 内部状态机（见 12 篇），这是刻意的极简。

**环境校验 env.ts**。`env.ts:1-4` 定义 `ENV` 类型（`VITE_QUEUE_API_PATH` + `VITE_ENV`），`env.ts:6-17` 的 `parseEnv` 在 `env.ts:9-11` 对缺失的 `VITE_QUEUE_API_PATH` 直接 throw；`env.ts:19` 在模块顶层执行 `export const env = parseEnv()`——即 import 即校验，配置缺失会在页面加载第一时间白屏报错，而不是等到第一次 fetch 才失败。`env.ts:15` 用 Vite 注入的 `import.meta.env.DEV` 区分 development/production。

**Vite 配置 vite.config.ts**。`vite.config.ts:4` 以函数式 `defineConfig(({mode}) => ...)` 拿到 mode；`vite.config.ts:5` 用 `loadEnv` 读 `.env.local`；`vite.config.ts:6-11` 仅当 `VITE_QUEUE_API_URL` 存在时构造 `/api` 代理（`changeOrigin: true` 在 `vite.config.ts:9`），否则空对象——本地纯前端开发可以完全不配后端。`vite.config.ts:14` `host: "0.0.0.0"` 允许容器/局域网访问；`vite.config.ts:15-18` 强制 HTTPS（`cert.pem`/`key.pem` 需按 client/README 手工生成），因为 getUserMedia 与 AudioWorklet 都要求安全上下文。`vite.config.ts:23-29` 挂 `vite-plugin-top-level-await`（`promiseExportName: "__tla"`），为 target ES2020 下不支持原生 top-level await 的依赖兜底。

**TypeScript 与依赖**。`tsconfig.json:3` target ES2020、`tsconfig.json:10` `moduleResolution: "bundler"`、`tsconfig.json:13` `isolatedModules`、`tsconfig.json:15` `jsx: react-jsx`；`tsconfig.json:18-21` 开满 strict + `noUnusedLocals`/`noUnusedParameters`。`package.json:7-8` 两个核心脚本：`dev` 直接跑 vite，`build` 是 `tsc && vite build`（先类型检查）。运行时依赖（`package.json:38-47`）八个：react 系、`opus-recorder`（麦克风 Opus 编码）、`webm-duration-fix`（录音时长修复）、`eruda`（移动端控制台）、`zod`、`ws`、react-router-dom。`modules.d.ts:1` 一行 `declare module "opus-recorder"` 给无类型的 recorder 补声明；`.nvmrc` 钉住 `v20.12.2`。

**样式管线**。`postcss.config.js` 只有 tailwind + autoprefixer 两插件；`tailwind.config.js:9` 扩展 Inter 字体、`tailwind.config.js:12` 挂 daisyui；`src/index.css:1` 从 Google Fonts 引 Inter，`index.css:2-4` 是三条 tailwind 指令，`index.css:6-28` 自定义 `no-scrollbar`/`scrollbar` 工具类，`index.css:30-39` 起 `.main-grid` 用 grid-template-areas 布置会话页（controls/player/player-text 三区，768px 断点转双列）。

**client/Dockerfile**。`client/Dockerfile:1` 基于 `node:20`；`client/Dockerfile:7-9` 依次 `npm install` 与 `npm run build`；`client/Dockerfile:12-17` 安装 openssl 并自签 365 天证书；`client/Dockerfile:19` EXPOSE 5173；`client/Dockerfile:21` 的 CMD 是 `npm run dev`。

## ③ 外部连接

开发期 `/api/*` 被 vite 代理到 `VITE_QUEUE_API_URL`（`.env.local:2` 指向 `https://moshi.chat`，Kyutai 官方排队服务）；会话 WS 则由 Conversation 直接按 `worker_addr` 拼接（11 篇）。生产部署走另一条路：moshi 服务端在 8998 端口托管预构建前端——`moshi/moshi/server.py:344` 默认从 HuggingFace hub `nvidia/personaplex-7b/v1` 的 `dist.tgz` 下载静态产物（`server.py:341-350`），也可用 `--static` 指本地路径。所以仓库里的 `client/` 主要服务开发与再构建，线上 UI 是 HF 分发的 tarball。

## ④ 数据流

浏览器 GET `/` → index.html → module 加载 app.tsx → import 链触发 `env.ts:19` 立即校验（失败即刻抛错）→ RouterProvider 渲染 Queue → Queue 就绪后条件渲染 Conversation。构建产物有两个消费者：`client/Dockerfile:9` 的 `npm run build`（但镜像实际跑 dev server）与发布到 HF 的 dist.tgz。

## ⑤ 设计决策

单路由 + 页内状态切换，避免路由库参与会话生命周期（音频 refs 不能被路由卸载打断）；环境校验放模块顶层实现 fail-fast；HTTPS 是 Web Audio API 的硬需求而非安全姿态，配置里直接写死证书路径；ES2020 + top-level-await 插件的组合说明依赖里有需要顶层等待的模块，又不肯升 target。

## ⑥ 新人提示（坑与勘误）

- **`.eslinrc.json` 文件名拼写错误**：实际文件名少了字母 t（`.eslin` + `rc.json`），ESLint v8 只认 `.eslintrc.json`——这份 `standard-with-typescript` 配置（`.eslinrc.json:6-11`）从未被 `npm run lint` 加载，lint 实际处于无配置状态。改名即修复。
- `package.json:2` 包名 `kyutai-client` 未改，事故排查时别被误导。
- **`ws` 是死依赖**：全 src 无一处 `from "ws"` import（grep 实证），浏览器端用的是原生 WebSocket；它大概率是 Node 侧调试脚本的遗留。
- `client/Dockerfile:21` 生产镜像 CMD 跑的是 `npm run dev`（vite dev server），build 产物并未被 serve；与根 Dockerfile 的 HF dist.tgz 双轨并存，新人极易混淆"哪条才是真部署"。
- `.env.local` 被提交进了仓库且指向外部服务 `moshi.chat`， fork 使用时记得改。
- 证书文件不在仓库（.gitignore），clone 后不生成 `cert.pem`/`key.pem` 则 `vite.config.ts:15-18` 会让 dev server 起不来。
