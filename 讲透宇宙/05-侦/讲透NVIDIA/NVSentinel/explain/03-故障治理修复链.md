# 03 故障治理修复链：quarantine → remediation → 物理末端

> 锚基座：本地仓 @fbe7ec29，行号实测；图谱 L12 主线 + ADR-003/009/036/019/020。

## 角色定位

这是 NVSentinel 从"看见故障"到"动手修好"的完整链路：fault-quarantine 先把坏节点圈起来（cordon/taint），fault-remediation 编排取证与修复动作，gpu-reset 与 log-collector 在节点上物理执行，fault-remediation 的 CUSTOM 模板让任意 CR 修复零代码接入。它回答："节点坏了，怎么在不伤调度器的情况下安全地修？"

## 内部结构

**fault-quarantine**（`fault-quarantine/main.go:49` 入口）：CEL 规则驱动 cordon/taint/注解，带熔断器（ADR-022：规则反复触发会熔断防抖）与 coldstart（服务重启恢复在途隔离状态）。规则配置是 ConfigMap，E2E 基线夹具 `tests/data/basic-matching-configmap.yaml` 被 6 个测试文件消费（fault_quarantine/gpu_reset/smoke/log_collector/fault_management/scale）。

**fault-remediation**（`fault-remediation/main.go:76` 入口）：核心 `fault-remediation/pkg/reconciler/reconciler.go:88` reconciler；reconciler.go:125 `reconcileEvent` 事件会话三段式（:180 `startOrReuseEventSession` 复用会话防重复修复、:200 `completeEventSession` 收尾）；:225 `shouldSkipEvent` 先查 :319 `nodeHasActiveQuarantine`——没隔离就不修，顺序即安全；:356 `runLogCollector` **先取证再动手**；:389 `performRemediation` 按 RecommendedAction 分派；:461 `handleCancellationEvent` 处理取消（ADR-038 取消规则）；:564 `handlePartialRecoveryEvent` 处理部分恢复（单 GPU 好了不等于节点好了）。ADR-036 CUSTOM 动态 CR 落地在 `fault-remediation/pkg/reconciler/templates/custom-action-template.yaml:15-16`：`apiVersion: {{.ApiGroup}}/{{.Version}}`、`kind: {{.Kind}}` 全由配置注入，模板变量带 NodeName/HealthEventID/TraceID（同目录 gpureset-template.yaml/rebootnode-template.yaml 同构）。

**物理末端**：`gpu-reset/gpu_reset.sh`（242 行）支持三种驱动布局（gpu_reset.sh:20-37 container-toolkit/HostPath driver/GKE 主机驱动），gpu_reset.sh:62-70 `run_in_driver_root` chroot 进驱动根跑 nvidia-smi，做单 GPU 设备级重置+复位后健康检查（ADR-019/020）。`log-collector/entrypoint.sh:19-20` 在节点 nvidia-driver-daemonset pod 内跑 nvidia-bug-report+GPU Operator must-gather（entrypoint.sh:31），entrypoint.sh:39-44 MOCK 模式供 E2E。

## 外部连接

上游消费 health-events-analyzer 的结论与 store-client 事件流；quarantine 写 Node cordon/taint（K8s API 是最终执行器）；remediation 渲染的 CR 交给 janitor 执行（见 explain/02）；CSP 重启/终止经 janitor-provider（`janitor-provider/main.go:85`）。lifecycle-manager 的人工 MaintenanceRequest 也会发事件进这条链（`lifecycle-manager/internal/controller/maintenancerequest_controller.go:384` opening/:401 clearing 事件）——人工维护与自动修复共用同一隔离语义。

## 数据流

analyzer 结论→quarantine CEL 匹配→cordon/taint+熔断计数→remediation 消费：跳过检查（reconciler.go:225 已隔离？）→开事件会话（:180）→log-collector 取证（:356）→按动作分派（:389）：GPUReset/Reboot/Terminate 渲染对应 CR→janitor 执行→部分恢复/取消事件回到 reconciler.go:564/:461 分支→会话完成（:200）→隔离解除（MR 删除时 clearing 事件触发 uncordon）。

## 设计决策

"先隔离后修复"是铁序（reconciler.go:225 的 skip 检查）：防止修复中的节点继续接新负载。取证先于动作（:356）：修复可能抹掉现场，bug-report 先落袋。CUSTOM 模板（ADR-036）把"接入新修复系统"从写代码降级为写配置——ApiGroup/Version/Kind 占位符是唯一接口。会话复用（:180）让同一事件的重试不产生重复修复。

## 新人提示

调规则先看 `docs/fault-quarantine.md` 与 E2E 夹具的 CEL 写法。log-collector 的节点标签曾超 63 字符限制被上游修复（commit 44ed7b5 "keep log collector node label within 63 characters"）——自定义标签注意 K8s label 长度约束。修复链路的取消/部分恢复语义最易踩坑：单 GPU 恢复不清节点级隔离，读 :564 的注释再动手。
