# 06 · 安全防线：SSRF / 原型污染 / 开放重定向双层校验

## 角色定位

四个安全模块（`utils/security/` 三件 + `utils/media/validation.ts`）构成「网关层防外人、前端层防内容」的双层纵深：网关在请求进门前校验路径与目标（CommonJS，供 proxy 直接 require），前端在渲染/导入/跳转前校验数据（TS，供组件调用）。攻击面对应三类——SSRF（代理被当跳板打内网）、原型污染（恶意导入文件改写 Object 原型）、开放重定向（伪造 OAuth URL 钓鱼）。

## 内部结构

**网关 SSRF 三件套**（`utils/security/url-validation.js`）：
- `validateProxyHttpPath`（`url-validation.js:26-79`）：先 URL 构造器归一化（`url-validation.js:37`——percent 编码/重复斜杠/dot-segment 一次清掉）→ 必须 `/api/` 前缀（`url-validation.js:47-52`）→ 归一化后**再查一遍 `..`**（`url-validation.js:58-63`，注释自认 defense in depth）→ ALLOWED_PATHS 白名单前缀匹配（`url-validation.js:66-69`，清单源 `constants/index.js:84-87` 由两条路由表自动汇成）。
- `validateProxyWebSocketPath`（`url-validation.js:90-99`）：只放行唯一路径 `/ws`，枚举拒绝一切变体。
- `validateBackendUrl`（`url-validation.js:110-131`）：服务端 fetch 前校验，仅 http/https 协议。

**媒体 SSRF**（`utils/media/validation.ts`）：`isValidMediaURL` 七道闸——data: 仅放行 `data:image/(png|jpeg);base64,`（`validation.ts:10-14`）、非 data URL 限 2048 字符防 DoS（`validation.ts:17-19`）、控制字符（≤0x1f 与 0x7f）拒绝（`validation.ts:23-28`）、协议白名单 http/https/data（`validation.ts:39-45`）、userinfo 凭据封禁（`validation.ts:48`）、IPv6 私有段 fe80/fc/fd（`validation.ts:54-61`）、IPv4 私有/链路本地/组播/保留段正则群（`validation.ts:65-77`，**刻意保留 127.x 给本地开发**）。

**开放重定向**（`utils/security/oauth-validation.ts`）：`isValidConsentPromptURL` 五步——空白/控制符快速拒绝（`oauth-validation.ts:9`）、绝对 URL 可解析（`oauth-validation.ts:13-17`）、仅 http(s)（`oauth-validation.ts:20`）、无 userinfo（`oauth-validation.ts:23`）、8192 长度上限（`oauth-validation.ts:26`）。调用点在 `Chat.tsx:823-831`：校验失败拒绝打开并 toast 报错——OAuth URL 来自后端推送，是不可尽信的输入。

**原型污染**（`utils/security/import-validation.ts`）：`validateImportData` 限 5MB（`import-validation.ts:20-24`，常量 `constants/index.js:14`）→ JSON.parse（27-33）→ 递归 sanitize 剔除 `__proto__/constructor/prototype` 三键（`import-validation.ts:42-62`，数组与嵌套对象全覆盖）→ v1-v4 四代导出格式结构校验（`import-validation.ts:68-107`）。第二道防线在网关：request-transformers 的 RESERVED_FIELDS 过滤让可选参数无法覆写 messages/stream（`request-transformers.js:77` 与 `request-transformers.js:92-96`）。

## 外部连接

url-validation 被 `proxy/server.js:25-28` require，HTTP 路径校验挂 `proxy/server.js:201`、WS 校验挂 `proxy/server.js:354`；media validation 被 Markdown 的 Image/Video 组件消费；import validation 被 `components/Settings/Import.tsx` 的 FileReader 链调用；settings 另有 `utils/app/settingsValidation.ts` 管设置 JSON 校验。测试三合一：`__tests__/security/url-validation.test.ts` 覆盖危险协议/内嵌凭据/保留 IP 段/**%2E 与 %252E 双重编码穿越**，`__tests__/security/json-import-validation.test.ts` 覆盖污染键剔除。

## 数据流

网关向：request → validateProxyHttpPath → 白名单内才 fetch 后端（403 拒绝响应在 `proxy/server.js:203-209`）。内容向：LLM 输出 markdown → img/video src 过 isValidMediaURL → 通过才渲染。导入向：文件 → 5MB/JSON/格式三闸 → sanitize 递归清洗 → 才进 store。OAuth 向：consent 消息 → extractOAuthUrl → isValidConsentPromptURL → 通过才 window.open/跳转。

## 设计决策

①**归一化先于校验**：先 URL 构造器规范化再比对，杜绝 `%2e%2e/`、`//`、大小写变体绕过；归一化后再查 `..` 是对「归一化实现万一有洞」的保险，冗余是刻意的；②**双层同责**：网关挡请求层（外人），前端挡数据层（被污染的 LLM 输出/导入文件）——单层被绕过时另一层兜底；③**127.x 放行**是工程妥协：本地开发需要 localhost 图片，注释明示保留理由（`validation.ts:64`）；④**误伤即拒绝**（fail-closed）：所有校验器对解析失败一律返回 false，绝不放行看不懂的输入。

## 新人提示

新增后端端点必须同时改 `constants/index.js` 路由表（白名单自动汇入，`constants/index.js:84-87`）——直接在 server.js 加路径会绕过白名单形成安全缺口；加新校验规则先在 `__tests__/security/` 写攻击用例（双重编码/私有段/污染键都有现成范式）；`utils/security/url-validation.js` 是 CommonJS 而 `oauth-validation.ts` 是 ESM，混用是有意为之（网关 vs 前端运行时），别统一「顺手重构」；IP 段正则群覆盖 0./10./169.254./172.16-31./192.168./224-255.，但**不含 DNS 解析到内网 IP 的场景**（域名绕过）——若部署环境敏感需在上游加 DNS pinning。
