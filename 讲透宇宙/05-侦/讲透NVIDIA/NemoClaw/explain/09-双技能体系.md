# 09 · 双技能体系（maintainer 22 + contributor 6 + 双 guide + _shared 8）

## 一、角色定位

`.agents/skills/` 是 NemoClaw 的"组织操作系统"：31 个目录（22 maintainer + 6 contributor + 2 guide + _shared）、合计 150 个文件，把人类维护者的日常流程（晨会分诊、日间循环、晚间收尾、发版、E2E 审计）与外部贡献者的阶段生命周期（环境、规划、实现、发 PR）全部写成 agent 可执行的 SKILL.md 工作流。与很多仓库"几个礼貌性 skill"不同，这套体系是日常发版机器的实际驱动者——maintainer-day 明确为 `/loop` 循环设计。仓库根 `CLAUDE.md -> AGENTS.md` 软链与 `.claude/skills -> .agents/skills` 软链（AGENTS.md:146 钉版"两路径解析到同一内容"）保证多 harness 看到同一份指令源。

## 二、内部结构

**贡献者六阶段**（每阶段唯一 owner，AGENTS.md:24 原文逐技能点名）：`nemoclaw-contributor-onboard`（checkout 修复，dev:setup/dev:doctor）→ `plan-issue` → `implement-issue`（代码+测试）→ `create-pr`（发布与评审跟进），另有 `update-dependencies` 与 `update-docs` 两个专项。阶段边界不要求重新授权——同一任务内 setup→plan→implement→publish 连续执行是默认语义（skills-guide/SKILL.md:13 同款条款）。

**维护者 22 技能按时间轴分层**：日常节律 `morning`（晨会分诊+定目标版本）/`day`（日间单趟循环）/`evening`（累积文档 PR+发版条目+可选切 tag）；评审线 `triage`/`find-review-pr`/`pr-comparator`/`cross-issue-sweep`/`normalize-title-tags`；E2E 线 `e2e`（执行路由）/`audit-e2e-assertions`（断言审计，**E2E 分诊的强制前置**）/`fix-e2e-failures`/`classify-ci-failure`/`analyze-ci-performance`；发版线 `cut-release-tag`/`release-notes`/`validate-launchable`；度量线 `analyze-pr-value-stream`；架构线 `refactor-docs`/`runtime-provider`/`security-code-review`/`policies`/`verify-stale`。`nemoclaw-maintainer-day/SKILL.md:14-17` 的自治条款值得逐字读：小修复可在 CI+自动评审 settles 后推送、全绿门可批 PR、贡献者与批准者重叠仅 advisory、**"Never merge"** ——合并权永远留给人。

**双 guide**：`nemoclaw-skills-guide`（65 行）是选择路由器——目录表用 `<!-- user-skills-table:begin/end -->` 标记对（SKILL.md:23,27）标注生成区，正文直说"已知技能直达，不清楚才查目录；推断受众而非询问"（SKILL.md:13）。`nemoclaw-user-guide`（52 行）面向终端用户的 agent：检索顺序四级降级——docs MCP `searchDocs` → 本地 Markdown 索引 → `https://docs.nvidia.com/nemoclaw/llms.txt`（SKILL.md:16）→ HTML 页手动改 `.md` 后缀（Retrieval Order 节 :12 起）；硬规则"绝不让用户把秘密贴进聊天、示例一律 `<PASTE_YOUR_API_KEY_HERE>` 占位"（SKILL.md:34-35）。

**_shared 八篇横切契约**：`security-rubric.md` 九类安全风险分类法（:6）+ 三段用法——Planning 命名风险（:7）、Implementation 留否定性证据（:8）、Independent review 逐类核验（:9）；`documentation-writing-review.md`（一切解释性文本的写作契约，AGENTS.md 明令 skills 写文本必遵）；`git-github-hard-stop.md`（访问失败处置）、`pr-follow-up.md`（PR 后续协议）、`code-change-considerations.md`、`implementation-discovery.md`、`root-cause-and-state-checks.md`、`controlled-words.md`。共享文件解决的是"22 个 maintainer skill 引用同一套安全/文档标准"的去重问题——条件性程序放 references、完成判据留在入口 SKILL.md，这是全体系统一的编写宪法。

**目录内部形态**以 `nemoclaw-maintainer-policies/references/` 为例：8 个参考文件中 `label-taxonomy.json` 与 `label-taxonomy.md` 是**同一分类法的机器/人类双面**——JSON 顶层 `schema_version:1`（label-taxonomy.json:2）+ `issue_type_source_of_truth`（:5，GitHub 原生 Issue Type 六值）+ `project_fields`（:10，"NVIDIA organization Project 199"字段映射），MD 是给人读的叙事版。`nemoclaw-maintainer-pr-comparator/scripts/` 则带四个 bash 工具合计 498 行：find-candidates.sh:86 依赖 gh 搜索原语、collect-gates.sh:222 顶层管线、parse-supersession.sh:85 输出 TSV 边表、check-coderabbit-threads.sh:105——skill 可以自带可执行脚本。

## 三、外部连接

**发布面**：`skills/`（仓库顶层，仅 14 行 README + 一个拷贝）是 NVSkills CI 的客户面目录——README:5-7 明言"源在 .agents/skills/，可发布的客户技能拷贝到这里，目前仅 nemoclaw-user-guide 一个"，签名流程走 `.github/catalog-skills-signing-flow.md`；`.gitattributes:11` 把 `skills/nemoclaw/**` 标记 `linguist-generated=true` 坐实"拷贝产物"身份。**消费面**：根 AGENTS.md 的路由表（E2E 分诊→audit-e2e-assertions；改 skill 的规则；harness 无关性条款——技能陈述"需要的能力/动作/可观察结果"而非点名工具）。`.dsh/tools/` 的 68 个工具是 maintainer 技能的执行后端，但 .dsh/tools/AGENTS.md:7 划清界限："Agent skills 不依赖 DSH 目录"，工具输出仅承担其契约覆盖的操作。文档侧 user-guide 指向 docs/ 的 Fern 生成体系。

## 四、数据流

用户请求 → skills-guide 路由（或已知直达）→ 入口 SKILL.md 的描述与完成判据决定加载哪些 references（条件加载，禁止预载生命周期栈）→ 需要外部证据时经 gh CLI/.dsh 工具取证 → 输出受 _shared 契约约束（安全九类、文档契约、controlled-words 用词表）。维护者节律流：morning 产日计划 → day 在 `/loop` 中跑 merge/salvage/security/test/conflict 六种工作流之一 → evening 汇总文档 PR 与 release entry → cut-release-tag 凭证据切签名 tag。

## 五、设计决策

1. **单入口多参考**：SKILL.md 保持短而具体（frontmatter description 决定触发），重程序下沉 references——对抗 agent 上下文预算。
2. **阶段唯一 owner**消除生命周期缝隙：一个阶段一个技能负责到底，不存在"两个技能都以为对方做"。
3. **机器/人类双面分类法**（label-taxonomy .json/.md）：机器面给脚本消费、人类面给评审阅读，单一事实源双投影。
4. **目录表生成区标记**让 skills-guide 的表格可被工具自动重生成而不伤手写段。
5. **Never merge 红线**+自治边界写进最常用技能的开头——权限语义放在使用频度最高的地方而非藏进 policies。
6. 客户面与内部面物理分目录（skills/ vs .agents/skills/），发布签名流程只作用于前者。

## 六、新人提示

改任何 skill 前先读根 AGENTS.md 的 "Agent Skills" 节（描述要短、条件程序进 references、完成判据在入口）。找某维护流程的入口按时间轴（morning/day/evening）比按字母序快。`_shared/documentation-writing-review.md` 对 explain 类文本同样适用。注意 `.claude/skills` 与 `.agents/skills` 是同一份内容（软链），别在两处各改一遍；`skills/nemoclaw/` 在 .gitattributes 里标 `linguist-generated=true`（`:11`）说明它是构建产物。技能数口诀：22 maintainer + 6 contributor + 2 guide + 1 _shared = 31 目录 150 文件。
