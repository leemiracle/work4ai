# 08 sample_apps：样例应用群与渐进式教学法

## 一、角色定位

`src/apps/sample_apps/` 是 DeepStream 的"官方教学区"：33 个应用目录 + 2 个 Triton 样例，README.md 按八类组织（Core Tutorial / Inference and Metadata / Video Sources and Demuxing / Analytics and Tracking / 3D Sensing / Networking and Server / OpenCV / Triton）。它既是新手的教材，也是**可复制的工程模板库**——绝大多数二次开发从"拷一个 test app 改改"起步。主角是 deepstream-test1 到 test5 的渐进五部曲（348→528→600→1051→2117 行），从单流解码推理一路教到多流配置化+云上报+OTA；deepstream-app（合计 4840 行）则是"配置驱动"的集大成者，也是 Triton 样例的宿主。README:21-25 明确运行契约：构建后二进制装到 `/opt/nvidia/deepstream/deepstream-9.1/bin/`，但**必须 cd 回源码目录跑**（相对 config/model 路径才解析得了），且新装插件后要清 `~/.cache/gstreamer-1.0/`。

## 二、内部结构

**test1**（deepstream_test1_app.c，348 行）是最小完整管线：filesrc→h264parse→nvv4l2decoder（第 194-201 行）→nvstreammux（第 204 行）→PGIE（第 213-217 行，`pgie_type == NVDS_GIE_PLUGIN_INFER_SERVER` 时选 nvinferserver 否则 nvinfer——同一个 app 教两种推理后端）→nvvideoconvert→nvdsosd（第 220-223 行）→nv3dsink/nveglglessink（第 227-232 行）。streammux 的 1920×1080 分辨率与 batch-size=1 硬编码在宏 MUXER_OUTPUT_WIDTH/HEIGHT（第 33-34 行）+ g_object_set（第 248-251 行）；另藏一手：`yaml_config` 分支可用 nvds_parse_file_source 等函数走 YAML 配置（分支判定第 182-184 行）。**test2**（528 行）在 test1 上加 nvtracker（第 387 行，set_tracker_properties 教 tracker-width/height/gpu_id 三件套，第 235-275 行）与两个 SGIE 级联分类器——dstest2_sgie1/2_config.txt（第 30-31 行），sgiex_unique_id=2/3 硬编码对齐（第 86-87 行），类别表如 sgie2 的 coupe/largevehicle/sedan/suv（第 74 行）。**test3**（600 行）教多流：每路一个 source bin（nvurisrcbin 或 uridecodebin，第 260-264 行两代解复用组件对照），主流水线补 5 个 queue（第 430-434 行，线程边界教学）、nvdslogger（第 437 行，测 FPS/延迟）、nvmultistreamtiler（第 447 行，多流拼贴），fakesink 选项（第 456 行）为性能测试铺路。**test4**（1051 行）教云链路：nvmsgconv+nvmsgbroker（第 809-812 行）+ tee 分流（第 815 行）；核心教学点是 Event Msg 元数据的生命周期——meta_copy_func/meta_free_func（第 150/218 行）演示 user_meta 跨线程拷贝/释放必须成对实现，命令行 --msg2p-meta 0/1 切换 Event Msg meta 与 nvds meta 两种 payload 模式（第 122-123 行），--frame-interval 默认 30 控制上报密度。**test5**（deepstream_test5_app_main.c，2117 行）不再手搓：#include "deepstream_app.h"（第 36 行）直接复用 AppCtx 框架与 create_pipeline（deepstream_app.c:2319 的 create_tiled_display_bin 一族），增量在多实例（`AppCtx *appCtx[MAX_INSTANCES]`，第 140 行）、YAML 配置识别（`IS_YAML(file)` 宏，第 62 行）与 **OTA 热更新**——`apply_ota`（第 239 行）+ ota_handler_thread 监听 ota-override-file 变更（第 243-254 行），运行中重解析 override_config 不停机换配置。

## 三、外部连接

上游是 src/gst-plugins 全体插件（每个 app 就是一份插件组合清单）；test4 连接 adapters 子目录的消息适配器（Kafka/MQTT/AMQP 等经 nvmsgbroker 动态加载）；TritonBackendEnsemble/TritonOnnxYolo 不产二进制，而是编译 nvinferserver 的 custom-process 库（libnvdstriton_custom_impl_{ensemble,yolo}.so），由 deb 安装的 deepstream-app 驱动——样例层与插件层的另一种耦合方式。横向呼应：service-maker（src/service-maker/sources/apps/python/）提供 test1-5 的 **Python 镜像**，且分 flow_api 与 pipeline_api 两套 DSL：flow_api 版 test1 仅 68 行，`Flow(pipeline).batch_capture([...]).infer(CONFIG)`（deepstream_test1.py:52）一行搭管线，再 attach Probe("counter", ObjectCounterMarker()) 挂探针——C 版 348 行的等价表达，示范"service-maker DSL 把样板代码吃掉"的设计意图；pipeline_api 多一个 deepstream_kafka_test_app。3D 系应用（action-recognition/depth-camera/lidar-sensor-fusion/can-orientation）则依赖 ds3d 库与 3D 感知插件族。

## 四、数据流

以 test3 为典型：**控制流**先于数据流——main 解析 uri 数组后逐路 `create_source_bin`（每路一个 GstBin 内含解码链），全部 add_bin 到 pipeline；streammux 的 sink_%u 按流序号请求式对接。**数据流**上：解码帧进 streammux 成批（NvDsBatchMeta 在此诞生）→PGIE 推理贴 obj_meta→queue×5 划线程边界（每个 queue 一条线程，背压靠 queue 上限）→tiler 把 N 路缩放拼成一路→OSD 渲染→sink。test4 的第二条数据流是**元数据流**：probe 里把 NvDsEventMsgMeta 挂到 frame 的 user_meta（generate_event_msg_meta 分派 generate_vehicle_meta/generate_person_meta 生成对象级 payload，第 270/312/323 行，时间戳走 generate_ts_rfc3339 第 133 行），nvmsgconv 周期性（frame-interval）把 batch_meta 序列化为 schema payload，nvmsgbroker 异步走云；关键细节是 tee 之后 display 分支与 broker 分支各自独立 queue，UI 卡顿不影响上报。test5 的数据流与 deepstream-app 相同，但 OTA 线程监听文件变更后经 parse_config_file_yaml（第 1628/1770 行）重建 override 配置并 apply，实现"配置即数据"的第三条流。

## 五、设计决策

①**渐进复杂度是刻意的课程设计**：test1→5 每步只引入 1-2 个新概念（推理→跟踪/级联→多流/线程→云上报→配置化/热更新），行数翻倍节奏与之匹配；写新应用时按需选起点而不是全从 test1 搭。②**硬编码与配置化的边界分层教学**：test1 连分辨率都写宏，test5 全配置化——两头都给样例，让开发者理解"何时该抽配置"。③**C++/Python 双轨靠 service-maker 而非 pyds 绑定**：本仓 sample_apps 下没有 Python 版 test1-5，Python 镜像全部长在 service-maker 的 apps/python 下（flow_api 68 行 vs C 版 348 行的对比即最好的 DSL 广告）。④**样例即集成测试**：README 开篇就写"Make sure deepstream-test1 sample can run successfully to verify your installation"（tao_apps/README.md 同款措辞），test1 承担装机验收职责，故其依赖被压到最少。⑤**平台差异用运行时分支而非 ifdef 硬裁**：sink 选择按平台/无显示环境分派（nv3dsink/nveglglessink/fakesink 三态，test1:225-232），Jetson 专属能力（ipc-test）与 x86 专属（ucx/multigpu-nvlink）在 README 层面标注而非代码层分裂。⑥**每个 app 自带配置与模型清单**：目录内 config 文件与下载脚本共存（download_models.sh 模式），保证"cd 进去就能跑"的可复现性。

## 六、新人提示

学习路径按 README 八类走，但顺序建议 test1→test3→test2→deepstream-app：先懂多流再懂级联更顺（test2 的 SGIE 依赖对 tracker 输出的理解）。三个高频坑：(1) **必须从源码目录启动**，否则 dstest1_pgie_config.txt 找不到直接崩，报错只有一句 parse 失败；(2) 改完插件忘了清 GStreamer 缓存会加载旧 so，症状是"改了没生效"；(3) test2 的 unique_id 对齐是隐式契约——sgiex_unique_id=2/3 硬编码（test2:86-87），改配置里的 gie-unique-id 而不改源码，标签会错位到别的组件上。想跨到 Python：直接读 service-maker flow_api 的 test1（68 行）对照 C 版，DSL 语义一一对应（batch_capture=uridecodebin+streammux、infer=PGIE、render=convert+osd+sink）；注意其 main 用 multiprocessing.Process 包 Flow()() 阻塞调用以正确响应 Ctrl+C（deepstream_test1.py:62-68）。甄别说明：任务书所述"C++/Python 双版本镜像"经核实不在 sample_apps 内，Python 镜像实际位于 src/service-maker/sources/apps/python/{flow_api,pipeline_api}/（本篇据此改写）；test5 的 RTSP 输出能力来自复用的 deepstream-app 框架而非独立实现。
