# 讲透 symphony（OpenAI 工程预览）

## 一、定位：把项目工作变成隔离自主的 Codex 运行

Symphony 是 OpenAI 开源的 "low key engineering preview"（README.md:11），一句话定位在 README.md:3：**把项目工作变成隔离的自主实现运行，让团队管理工作本身，而不是监督编码 agent**。闭环：监控 Linear 看板 → 派生 agent 在隔离 workspace 实现 → 交回"工作证明"（CI 状态、PR review、复杂度分析）→ 通过后安全落 PR。

仓库形态特别：**核心资产是一份语言无关规范 + 一个参考实现**。SPEC.md 共 18 章（含 Appendix A），从领域模型、状态机到参考算法与 Definition of Done 清单（SPEC.md:2204 §18）；README.md:25 的官方用法之一就是"把 SPEC 喂给你喜欢的编码 agent，用你选的语言造一个 Symphony"——规范本身即为 prompt。`elixir/` 是参考实现（125 文件），OTP 天然适合这个长驻轮询、进程监督密集的服务。前置条件：README.md:17 指明最适合已采纳 harness engineering（带 AGENTS.md/WORKFLOW.md 契约）的代码库。

## 二、架构解剖

### 2.1 orchestrator 状态机

`orchestrator.ex` 是 1990 行 GenServer，内部 State（orchestrator.ex:24）驱动 SPEC.md:645 的五态生命周期：`Unclaimed → Claimed → Running → RetryQueued → Released`。SPEC.md:642 强调这与 tracker 业务态（`Todo`/`In Progress`）是两套体系。防御细节：**tick 令牌防陈旧定时器**（orchestrator.ex:83 只接受令牌匹配的 tick，陈旧消息在 :100 丢弃）；**进程监控**（orchestrator.ex:128 `{:DOWN, ref}` 收殓崩溃 worker）；每轮 poll 后 reconcile 对账。可测试性靠大量 `*_for_test` 公开包装（orchestrator.ex:360）。SPEC.md:668 规定多轮续跑：worker 正常退出≠终结，issue 仍 active 就在同一 workspace 同一线程续 turn（上限 `max_turns` 默认 20，SPEC.md:624、WORKFLOW.md:32）；首 turn 用全量 prompt，续轮只发 continuation 指引（agent_runner.ex:142）。

### 2.2 workspace 隔离与安全边界

每 issue 一个 workspace：`agent_runner.ex:41` 的 `Workspace.create_for_issue/2` 建目录（`hooks.after_create` 浅克隆+装依赖，`before_remove` 收尾）。安全三条腿：①`workspace.ex:265-284` workspace_key 对非安全 identifier 追加 sha256 前 16 hex 防碰撞；②`workspace.ex:425` 远程命令经 shell_escape 单引号转义；③`PathSafety.canonicalize`（workspace.ex:252）防路径逃逸。远程执行走 SSH Port（app_server.ex:218，对应 SPEC.md:2252 Appendix A 可选扩展）。

### 2.3 六 tracker 适配器三件套同构

`tracker.ex:13` `@adapters` 编译期 map 分发六个实现：asana/github/gitlab/jira/linear 各为 `adapter.ex + agent_tool.ex + client.ex` 三件套，第六个 `tracker/memory.ex:1` 是测试用内存实现。behaviour 仅六回调（tracker.ex:22-27）。**agent_tool 是点睛之笔**——把 tracker 写操作包装成 Codex 可调的 JSON-RPC 工具，agent 自己回报进度；`secret_environment_names` 支撑 SPEC.md:1756 红线：Codex 子进程环境里的 tracker 凭证一律剥除。

### 2.4 PromptBuilder 与 WORKFLOW.md 模板

`prompt_builder.ex:18` 用 Solid（Liquid 风格）渲染 WORKFLOW.md 正文：`{{ issue.identifier }}`（WORKFLOW.md:42）、`{% if attempt %}`（WORKFLOW.md:44）会话启动时插值；strict_variables/strict_filters（prompt_builder.ex:8）让模板错误当场爆炸。front matter 校验借道 Ecto：`config/schema.ex:50` embedded_schema（无数据库，纯 changeset 校验 YAML）。

### 2.5 观测面

`status_dashboard.ex` 1941 行终端 UI：指纹比对跳过无变化重绘（:56）、flush 定时器合并渲染（:158）、115 列宽度自适应（:27）；`humanize_codex_message`（status_dashboard.ex:1072）把 codex 方法名映射为可读文案。另有 Phoenix LiveView 可选观测 UI，config.exs 用 64 个 s 填充的 secret_key_base 与 `check_origin: false` 表明其开发态定位。

## 三、测试体系：替身哲学与双臂 live E2E

**脚本化 fake codex 二进制**：`app_server_test.exs:89` 的替身是 sh 脚本 fake-codex，按读到的 JSON-RPC 行数回放应答（经 `codex_command` 注入，app_server_test.exs:120）；:1208 构造 110 万字符 padding 行，专测 `app_server.ex:12` 的 1MB 行缓冲边界。`ssh_test.exs` 同思路：fake ssh 是 PATH 前置目录脚本，printf ARGV 落 trace 轮询断言。

**live E2E 双臂**：`live_e2e_test.exs:437` `run_live_issue_flow!` 分 :local/:ssh 两臂（:128 "creates a real Linear project and issue with an ssh worker"）。SSH 臂起**双 worker docker 集群**（live_e2e_test.exs:11 `@docker_worker_count 2`）：compose 经 `SYMPHONY_LIVE_DOCKER_*` 注入端口与凭据路径（docker-compose.yml:7），auth.json 与公钥只读挂载——测试基建零秘密落盘。asana_live_e2e_test.exs 还断言 `asana_pat_present=no`，端到端验证 Codex 侧不持有 tracker 凭证。

**同构 adapter 测试**：五个 `*_adapter_test.exs` 结构同构，对应 SPEC.md:2104 §17.3 测试矩阵。dashboard 快照回归用真实 method 名构造事件（`turn/started`、`tokenUsage/updated`），`snapshot.txt` 与去色 `evidence.md` 双比对。cli_test.exs 把运行时依赖全以 deps map 注入，`send`/`refute_received` 断言副作用。

## 四、工程亮点

1. **产品语义固化为 CI 门禁**：`burrito-release.yml:101` smoke job 对构建产物无参调用，断言输出含 "low key engineering preview" 警告且非零退出（:132-137）。CLI 对应 `--i-understand-that-this-will-be-running-without-the-usual-guardrails` 确认开关（cli.ex:125），不传打印 ANSI 边框横幅拒跑。
2. **action 全 SHA 钉版**：第三方 action 以完整 commit SHA 引用（# vN 仅注释）；`burrito-nightly.yml:14` 16 行壳工作流经 `uses:` 委托复用 release 流水线，双入口 + concurrency 表达式区分 nightly 与 tag 流。
3. **大写 CamelCase 反 underscore 命名三例**：SPEC 状态机全用无下划线 CapWords——①issue 编排五态 `Unclaimed/Claimed/Running/RetryQueued/Released`（SPEC.md:645）；②run attempt 十一阶段 `PreparingWorkspace → StreamingTurn → Succeeded/Failed/TimedOut/Stalled/CanceledByReconciliation`（SPEC.md:680）；③tracker 业务态 `Todo/In Progress`（SPEC.md:642）。刻意为之：状态名是跨语言稳定标识符，不能带 Elixir atom 或 Python snake_case 方言色彩。
4. **OTP 形态红利**：状态机+监控+退避全落在 OTP 原语；`.formatter.exs` 200 字符行宽；Burrito 打包检测用 `__BURRITO` 环境变量。

## 五、使用建议

- **先读 SPEC 再读代码**：§3.1 组件清单与 `elixir/lib/symphony_elixir/` 模块一一对应，§16 参考算法是理解 poll-and-dispatch 的最短路径，§18 checklist 是验收表。
- **信任边界是硬约束**：SPEC.md:1721（§15.1）明示只面向受信环境、Codex 无 guardrails；别当通用多租户服务部署。
- **自己造实现比用参考实现更"官方"**：README Option 1 即让编码 agent 照 SPEC 造；WORKFLOW.md front matter + Liquid 模板契约（§5）是唯一必须精确遵守的仓库侧接口。
- **从 memory tracker 起步**：`tracker/memory.ex` 脱离 SaaS 跑通全链路再换真实 adapter；新增 tracker 只需一个三件套目录。
- **测试基建可直接抄**：fake 二进制替身 + 凭证只读挂载 + 双臂 local/ssh 编排，是长驻 agent 服务的测试设计模板。
