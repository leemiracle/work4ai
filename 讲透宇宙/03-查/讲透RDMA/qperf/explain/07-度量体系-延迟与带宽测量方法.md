# 07 度量体系：延迟与带宽测量方法（rdma.c 测量引擎群 + calc_results）

## 一、角色定位

qperf 的价值最终落在一个问题上：一条网络路径到底有多快。rdma.c 里真正回答这个问题的是七个通用测量引擎——`rd_client_bw`（rdma.c:886，单向带宽）、`rd_server_def`（rdma.c:933，万能收包端）、`rd_bi_bw`（rdma.c:976，双向带宽）、`rd_pp_lat`（rdma.c:1035，乒乓延迟）、`rd_client_rdma_read_lat`（rdma.c:1180，RDMA Read 单边延迟）、`rd_client_rdma_bw`（rdma.c:1220，RDMA Read/Write 单边带宽）、`rd_rdma_write_poll_lat`（rdma.c:1120，写内存轮询延迟）。22 个 RDMA 测试名（rc_bw/uc_lat/ud_bi_bw…）只是给这七个引擎换传输类型（RC/UC/UD）与 IO 模式（Send/Receive 或 RDMA）的薄壳。计时与统计结算则跨文件落在 qperf.c 的 `start_test_timer`（qperf.c:1805）与 `calc_results`（qperf.c:1875）。注意任务书里提到的 `rd_tune` 在本仓库（0.4.11 世代）并不存在，那是上游后续版本引入的函数；本版的参数缺省与协商逻辑全部由 `rd_params`（rdma.c:1426）承担。

## 二、内部结构

**带宽引擎 `rd_client_bw`**（rdma.c:886-931）是"管道保持满"模式：`rd_open`/`rd_prep` 建链后先一口气压入 NCQE（1024，rdma.c:52）个 Send，之后每轮 `rd_poll` 收 n 个完成事件就补发 n 个——发送队列里永远悬浮着约 1024 个未完成 WR，保证链路不空转。每轮统计 `max_cqes`（一次 poll 返回的最大 CQE 数，衡量完成队列的消化速度）。`Req.no_msgs` 给定时走 `left_to_send`（qperf.c:1942）限流：按"已发数"裁剪补发量，达标即退循环——这就是 `-n` 选项按消息数而非按时间结束测试的机制。

**收包端 `rd_server_def`**（rdma.c:933-974）对称：预挂 1024 个 Recv，每轮消化 n 个完成事件（`LStat.r.no_bytes += dev.msg_size`）再补挂 n 个。`Req.access_recv` 置位时每收一包调 `touch_data`（support.c）真读一遍缓冲区——测"接收后立即访问"的代价，否则网卡 DMA 进内存的包可以不被 CPU 碰过。

**双向引擎 `rd_bi_bw`**（rdma.c:976-1032）在同一循环里用 `wr_id` 区分 WRID_SEND（rdma.c:64）/WRID_RECV（rdma.c:65）两类完成事件，分别按 `numSent`/`numRecv` 补发补挂，双方向速率自然拉平。

**乒乓延迟 `rd_pp_lat`**（rdma.c:1035-1052）把队列深度降到 1：每方只挂 1 个 Recv，client 先发；循环里用 `done` 位图（发送完成|=1，收到对端包|=2）等"一去一回"都齐了再发下一个。延迟精度完全取决于单包链路往返，没有流水线重叠。`rd_pp_lat_loop`（rdma.c:1054）同时支持 IO_SR（Send/Receive）与 IO_RDMA（RDMA_WRITE_WITH_IMM 带 immediate 的写）两种乒乓载体——后者免去接收侧 post recv 的开销差，可对照出verbs Send 路径本身的代价。

**单边延迟 `rd_client_rdma_read_lat`**（rdma.c:1180-1217）是纯 client 视角：发一个 RDMA_READ，等完成，再发下一个。妙在统计口径——完成事件到达即 `LStat.r.no_bytes` 与 `LStat.rem_s.no_bytes` 同时累加（rdma.c:1202-1204）：本端"收"了自己的读回数据，对端虽未参与任何verbs动作也计一次"远程发送"，这样 `exchange_results` 后对账时两侧数字天然吻合。

**绕过 CQ 的写轮询 `rd_rdma_write_poll_lat`**（rdma.c:1120-1177）：client 发 RDMA_WRITE 写对端 buffer 的首尾两个字节（标记值 0x55/0xaa），然后**裸轮询 volatile 指针** `*p == remid && *q == remid` 直到对端标记出现——注释明言这是"某些 MPI 的策略"，测的是完全不经完成队列、不通知内核的极限往返。首尾双字节防 DMA 半包可见的伪完成。`*p/*q` 必须在 `sync_test` 之前写好（rdma.c:1117 注释），否则有竞态。

**轮询引擎 `rd_poll`**（rdma.c:2509-2529）双模：`Req.poll_mode` 为 0 时先 `ibv_get_cq_event` 阻塞等通知（再 re-arm + ack），为 1 时直接 `ibv_poll_cq` 自旋——对应 `-cp` 选项测"忙轮询把 CPU 烧给低延迟"的模式。

## 三、外部连接

- **参数缺省与协商 `rd_params`**（rdma.c:1426-1469）：每个 run_client_* 在最前面调用它声明本测试接受哪些参数：RC 才开放 `use_cm`（其余传输强制 `setv_u32(L_USE_CM, 0)`，rdma.c:1431-1432）；`!Req.use_cm`（走传统 IB 路径）才缺省 MTU_SIZE=2048（rdma.c:54）并开放 id/sl/static_rate/src_path_bits 四个 IB 路由参数（rdma.c:1435-1446）；`msg_size`/`poll`/`atomic` 三个开关决定 msg_size、poll_mode、rd_atomic 是否进入本测试的合法参数集，最后 `opt_check()` 把"用户设了但本测试不用"的选项点名为警告。
- **MTU 协商**（rdma.c:2004-2020）：`ib_open` 里把 `Req.mtu_size` 映射为 IBV_MTU_256..4096 五档枚举，非法值直接报错；映射结果经 QP 属性 `.path_mtu`（rdma.c:2158）生效。由于 mtu_size 在 REQ 里随请求发给对端，client 的 `-mt` 选择自动成为双方共同值。
- **rd_atomic 协商**（rdma.c:1629-1641）：未指定时取设备 `max_qp_rd_atom` 上限，指定值不能超设备能力；本端深度进 `.max_dest_rd_atomic`（rdma.c:2162），对端深度经 NODE 结构（rdma.c:113 `rd_atomic` 字段）交换后进 `.max_rd_atomic`（rdma.c:2177）——outstanding read 数是对称协商的典型样本。
- **结算 `calc_results`**（qperf.c:1875-1939）：带宽=（两侧 bytes 之和）/（两侧 time_real 的中点均值 midTime）；单向测试时退化用单侧时间。`Res.latency = Res.l.time_real / no_msgs`（qperf.c:1891-1893），no_msgs 是**两侧收包数之和**——乒乓测试里两侧各收一包算一次往返，除出来即单程平均延迟。
- **时间源**：`start_test_timer`（qperf.c:1805-1826）用 `setitimer(ITIMER_REAL)` 起 SIGALRM，interval 设 10ms（qperf.c:1817-1821 注释解释是 SLES11 高精度定时器下防二次触发过猛的折中）；`set_finished`（qperf.c:1853）只在第一次进入时冻结 `LStat.time_e`，保证被信号打断的系统调用不会污染结束时刻。

## 四、数据流

以 `qperf host rc_bw` 为例：`run_client_rc_bw`（rdma.c:368）先 `par_use` 声明三个参数、`rd_params(RC, K64, 1, 0)` 把 msg_size 缺省成 64KB；`rd_client_bw` → `rd_open`（内部触发 `client_send_request` 把 REQ 推给 server）→ `rd_prep` 交换 NODE → `sync_test` 对齐起跑线并起表 → 灌 1024 个 Send → poll/补发循环直到 SIGALRM 置 Finished → `stop_test_timer` 冻结时间 → `exchange_results` 互发 STAT → `calc_results` 把 no_bytes/midTime 折算成 GB/sec → `show_results(BANDWIDTH)`。server 侧 `run_server_rc_bw`（rdma.c:384）只调 `rd_server_def`，对称地收包计数。rc_lat 则是 msg_size 缺省 1 字节、队列深度 1 的同一骨架。

## 五、设计决策

1. **引擎复用而非每测试一套循环**：22 个测试共享 7 个引擎，行为一致性（错误处理、max_cqes 统计、no_msgs 退出）只需维护一遍。
2. **统计在收发侧各自累加、结算时合并**（add_ustat + rem_s/rem_r 四桶，qperf.h:182-186）：单向 RDMA Read 这类对端"无感"的测试也能凑出对称账目，且 UDP/UD 丢包时两侧差异直接可见。
3. **结束时刻冻结在信号处理器里**（set_finished 只记第一次）：核心考量是"Finished 检查与系统调用发起之间的窗口期"——第二个 SIGALRM 会打断已陷入的系统调用，但计时终点不能因此后移，也不把超时后到达的包计入成绩（qperf.c:1827-1836 注释原话"reject any packets … in order not to cheat"）。
4. **rd_poll 默认阻塞、可选自旋**：默认事件驱动省 CPU，`-cp` 切自旋换延迟——把"轮询代价"本身做成可测变量而不是实现细节。
5. **写轮询延迟绕开整条 verbs 完成路径**：承认 MPI 实现的现实生态，提供一个"理论下界"参照系。

## 六、新人提示

- 读任何带宽引擎先找三件事：队列预灌多少、循环里补多少、退出条件是谁（Finished 还是 no_msgs）；对照 rd_client_bw（rdma.c:886）与 rd_server_def（rdma.c:933）即可建立模板感。
- 延迟数字的口径要会换算：`latency = time_real/(两侧收包和)`，乒乓一往返贡献 2 个收包，所以这就是单程均值；若自己写分析脚本别再除 2。
- `-ar`（access_recv）会显著拉低带宽——它不是 bug，是刻意让 CPU 触碰每个收包；对照组实验必须固定该选项。
- max_cqes 是诊断利器：它长期偏低说明 CQ 消化过快（好），逼近 1024 说明 poll 循环成了瓶颈（坏），输出见 `qperf -vv` 的统计节。
- 本仓库无 rd_tune/rd_show 并非缺页——上游 0.4.9 之后重构才引入，对照源码时注意版本世系（见 12 篇版本考古）。
