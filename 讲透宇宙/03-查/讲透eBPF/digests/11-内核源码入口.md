- **本地状态**：Anubis 壳页，无内容。
- **URL 指向**：`include/uapi/linux/bpf.h`——eBPF **用户态 ABI 的唯一权威定义**。

## [265] linux/include/uapi/linux/filter.h

- **本地状态**：Anubis 壳页，无内容。

## [269] kernel/bpf/verifier.c

- **本地状态**：Anubis 壳页，无内容。
- **URL 指向**：`kernel/bpf/verifier.c`——**静态验证器，eBPF 安全模型的实现核心**，kernel/bpf/ 下体量最大的文件之一。
- **角色**：`bpf_check`→`do_check` 主循环做指令级抽象解释：跟踪每个寄存器的类型/标量区间（tnum 精度）、指针边界与可访问性（map value/packet/ctx）、栈槽生消（`check_mem_access`/`mark_reg_read`，复活读检测）、程序终止性（有界循环检测，loop detection）、helper 调用合法性（对照 prog type 的 func 白名单）、特权性检查；还有 `resolve_pseudo_ldimmq`（map fd 重定位）与 `bpf_patch_insn` 指令改写。它是"BPF 程序加载为什么会报 R1 invalid mem access"这类经典报错的源头。
- **坑**：主线已把 states/fixups/backtrack/liveness/const_fold 拆成独立文件（见 266 清单），读 5.10 时代资料时这些还在 verifier.c 里；且 verifier 报错文案在不同代际变化很大。
- **对学习者价值**：eBPF 与 Lua/JVM 沙箱的本质区别就在这个文件——"允许执行前证明安全"；读懂它等于读懂 BPF 的安全边界论文（如 Elastic Bumps、Bounded Loops patch 的落点）。
- **对 agent 用法**：GitHub 镜像同路径；grep `do_check`、`is_pointer_value`、`check_mem_access`、`R0` 相关报错格式串；配合 `log.c`/`states.c` 读新版本。

## [275] linux/kernel/seccomp.c

- **本地状态**：Anubis 壳页，无内容。
- **URL 指向**：`kernel/seccomp.c`——**seccomp（secure computing mode）实现**，BPF 的第二大经典消费场景。

- **本地状态**：Anubis 壳页，无内容。
- **URL 指向**：`net/core/dev.c`——**网络设备核心**（网络栈最大的中枢文件之一）；对 eBPF 而言是 **XDP 的执行挂载点**。
- **角色**：`netif_receive_xdp`/generic-XDP 路径（`do_xdp_generic`，非 native 驱动 XDP 的软件兜底）、`netif_receive_skb_list` 入口对 `sch_handle_ingress` 的调用（通向 274 clsact）、XDP RX 队列与 `xdp_do_flush` 批量 flush 语义、XDP/frame_mode 事件通知；native XDP 则由各网卡驱动直接调用 `xdp_do_redirect`/`bpf_prog_run_xdp`（定义在 264/270），dev.c 提供 qdisc 与 generic 层的总装。
- **对学习者价值**：追踪"报文从网卡驱动到达 BPF 程序"的完整时序（驱动 XDP→generic XDP→tc ingress→socket filter 四个拦截层的关系在此定序）；理解 XDP redirect/CPUMAP 的 flush 边界。
