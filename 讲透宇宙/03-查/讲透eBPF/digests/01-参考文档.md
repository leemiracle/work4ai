## [11] BPF Design Q&A

- **是什么**：内核官方的 BPF 设计问答（kernel 7.4.0-rc1 快照），Alexei Starovoitov 风格的 blunt QA，逐条钉死"BPF 是什么/不是什么"，全文实抓成功。
- **核心内容**：BPF **不是**通用 ISA 也**不是**通用 VM，而是"**带 C calling convention 的通用指令集**"——与内核 C 调用约定兼容使 helper 调用零开销、JIT 后与原生内核 C 代码无异。硬性设计边界：R1-R5 传参、R0 返回、无多返回值；程序**不能**访问 IP/return address/stack pointer（只可访问 frame pointer R10；LLVM 后端私有定义 R11 为 SP 但保证不使用）；只能调 helper/kfunc 不能调任意内核函数。
- **值得记住的事实**：verifier 对外可见上限 BPF_MAXINSNS=4096（unprivileged），内部路径探索上限 100 万条指令；栈上限 512 字节（大栈架构 x86-64/arm64 JIT 下 2 KiB，含调用链合计）；BPF_JLT/BPF_JLE 是"新增指令必须有 HW 一一对应"的范例；alu32 下 verifier 可插显式 zext 指令减轻 JIT 负担。
- **ABI 边界（对本批最重要的部分）**：指令集/程序参数/helper 集合/返回码=稳定 ABI；tracepoint、kprobe 挂载点、被直接调用的内核函数、BTF_ID 标记函数**都不是** ABI；kfunc 不算稳定 API（有自己的 lifecycle）；map value 里的 bpf_spin_lock/bpf_timer 保持向后兼容，kptr 机制兼容但可用类型可变，**'bpf_' 前缀类型名被内核保留**用户勿用；allocated objects（bpf_obj_new）走 kfunc 生命周期、不保兼容。cBPF 解释器已不存在（一律转译成 eBPF）。
- **对人类学习者**：理解"为什么 eBPF 长成这样"的第一文档，纠正"eBPF=Linux 版 WASM"的常见误解。**对 AI agent**：`web/md/11.md` grep `NO`、`ABI`、`4096`、`bpf_` prefix 可直接引用权威结论做设计决策问答。

## [12] HOWTO interact with BPF subsystem

- **是什么**：内核官方的 BPF 子系统**贡献流程 QA**（bpf_devel_QA，kernel 7.4.0-rc1 快照）——报 bug、提交 patch、进 stable、跑测试、LLVM 协作的全部官方规范。
- **核心内容**：开发一律走 bpf@vger.kernel.org 邮件列表（Cc 维护者 Alexei Starovoitov/Daniel Borkmann），**明令禁止报 bugzilla.kernel.org**（必被忽视）；CI 在 GitHub kernel-patches/bpf（fork+PR 到 bpf-next_base/bpf_base）；patch 状态查 patchwork kernel.org netdevbpf 项目；双树模型=bpf（只收 fix）/bpf-next（feature），汇入 net/net-next 再进 mainline；fix 必须带 `Fixes:` tag；系列 patch 必须带 cover letter；stable 请求**不要**自己加 `Cc: stable` 而是请维护者排队。
- **值得记住的事实**：verifier 行为变更必须配 selftests 用例——"未被 test_verifier.c 跟踪的 verifier 行为视为可变"；新 BPF 指令必须同步 LLVM 后端并 bump 指令集版本（-mcpu=v1/v2/v3，LLVM 20 起默认 v3，`-mcpu=probe` 探测内核能力）；BPF selftests 用 `-mcpu=probe` 跑；pahole≥1.16 是 CONFIG_DEBUG_INFO_BTF=y 的要求；跑 selftests 要用**同版本内核**的测试树，且可用 `BPF_STRICT_BUILD=0` 容忍个别编译失败。
- **clang target 细节**：`--target=bpf` 保证指针/long 为 64 位（SK_MSG 等强依赖），native target 仅在 tracing 走 pt_regs 时需要；默认 target 会生成 switch jump table（BPF 加载必败，需 `-fno-jump-tables`）和 .eh_frame 段。
- **对人类学习者**：想给内核 BPF 提 patch 前的必读手册，能省掉大量社交流程错误。**对 AI agent**：`web/md/12.md` grep `bpf@vger`、`Fixes:`、`-mcpu`、`jump-tables` 拿到可直接执行的贡献流程与编译选项事实。

## [13] bpf(2) man page

- **是什么**：`bpf(2)` 系统调用的权威 man page（Linux man-pages 6.19，2026-02-10 版，man7.org 渲染），eBPF 一切用户态操作的 ABI 入口文档。
- **核心内容**：`bpf(cmd, &attr, size)` 三参数模型，cmd 枚举=MAP_CREATE/MAP_LOOKUP_ELEM/MAP_UPDATE_ELEM/MAP_DELETE_ELEM/MAP_GET_NEXT_KEY/PROG_LOAD（man 页只文档化基础集，注明"完整清单见 /usr/include/linux/bpf.h"）；union bpf_attr 匿名结构体逐字段讲；含可编译的 C wrapper 函数（bpf_create_map/bpf_lookup_elem/...）与一个完整的 SOCKET_FILTER 包计数示例（手工构造 bpf_insn 指令数组）。
- **值得记住的事实**：map 的 key_size/value_size 会被 verifier 用来在加载期拒绝越界访问（fp-4 传 8 字节 key 的例子）；update flags 三态 BPF_ANY/BPF_NOEXIST/BPF_EXIST 与 errno 映射（E2BIG=满、EEXIST/ENOENT）；HASH map 原子替换、ARRAY map 非原子但支持 `__sync_fetch_and_add` 原子计数器（聚合/统计常用套路）、ARRAY 可被 verifier/JIT 内联为常量指针；PROG_ARRAY+bpf_tail_call 跳转表（复用栈、不返回、上限 32 层嵌套、可绕过单程序指令上限、用户态可运行时原子换子程序）；license 字符串必须 GPL 兼容才能调 gpl_only helper；EACCES=verifier 判 unsafe（建议 log_level=1 重试看 log_buf）；Linux 4.4 起非特权用户可加载受限 SOCKET_FILTER（helper 白名单 4 个），可用 unprivileged_bpf_disabled=1 关闭；CONFIG_BPF_JIT_ALWAYS_ON 是 Spectre 缓解；JIT 架构支持表（x86-64/ARM32/ARM64 3.18 起，riscv 5.1 起）。
- **坑**：此 man page 有意只覆盖核心命令与老 map/program 类型（KPROBE/SCHED_CLS/SCHED_ACT 标注 "To be documented"），查全量要走 bpf.h 或 docs.ebpf.io（id 8）。
- **对人类学习者**：理解"eBPF 程序如何从用户态进入内核"的最小完备教材，示例代码可直接改跑。**对 AI agent**：`web/md/13.md` grep `BPF_MAP_TYPE_`、`BPF_PROG_TYPE_`、`EACCES`、`unprivileged` 拿 ABI 事实；完整示例代码在 EXAMPLES 节可复用为模板。

## [14] tc-bpf(8)

- **是什么**：iproute2 的 `tc bpf` 手册页（作者 Daniel Borkmann，上游 iproute2 仓 2026-07-28 快照）——用 eBPF/cBPF 写 tc classifier 与 action 的完整操作文档。
- **核心内容**：参数表（object-file/section/export/verbose/**direct-action(da)**/skip_hw/skip_sw/police/classid/bytecode）；eBPF 指令集设计原则（与 cBPF 同源但更贴近硬件、设计为 JIT 一一映射、LLVM 后端使 restricted C 可编程）；tc 视角的核心卖点=generic framework 避免特性膨胀、非线性分类、用户态经 map 热更新策略不用重载 classifier。
- **值得记住的事实**：**da 模式**让 classifier 直接返回 TC_ACT_*（OK/SHOT/PIPE/RECLASSIFY/UNSPEC）省去外挂 action；classifier 返回码语义=0 不匹配/-1 用默认 classid/其他值覆盖 classid（单程序非线性分类）；ingress qdisc 无排队能力（需 redirect 到 ifb 设备或用 policing）；map fd 可经 Unix domain socket 移交 eBPF agent（`tc exec bpf imp/exp` 把 fd 放进 shell 环境变量 BPF_MAP\<X\>，进程可重启不丢 map）；**最佳实践=只挂一个 classifier 干完所有匹配+改包**；cBPF 旧路可由 tcpdump -ddd/libpcap/bpf_asm 生成 bytecode（但 cBPF action 不支持改包）。
- **亮点**：两个完整 restricted C 示例（mark 统计 classifier + RSS 八端口分发重定向器）含手工函数指针声明 helper 的老式写法（`static int (*bpf_skb_store_bytes)(...) = (void *) BPF_FUNC_...`，早于 BPF helper 宏时代）；JIT 调试三件套 bpf_jit_enable=2/bpf_jit_disasm/modprobe test_bpf。
- **坑**：页脚日期标注 2015，但 COLOPHON 显示内容随 iproute2 仓滚动更新到 2026-07；老式 ELF map 规范（struct bpf_elf_map）与现代 BTF map 定义并存，读代码需分辨时代。
- **对人类学习者**：做流量分类/卸载/负载均衡场景的 eBPF 必读。**对 AI agent**：`web/md/14.md` grep `direct-action`、`TC_ACT_`、`ifb`、`BPF_MAP` 拿 tc 数据面事实与可直接套用的命令行。

## [15] bpf-helpers(7) man page

- **是什么**：eBPF **helper 函数逐条参考**（Linux man-pages 6.19，内核 v7.0 版，2025-10-27）——eBPF 程序可调用内核白名单函数的权威目录，本批最大的工具书（257KB/4985 行）。
- **核心内容**：按**时间顺序**（最老在前）逐条文档化约 190 个 helper，每条含 C 签名/Description/Return 值语义；开头钉死三条机制：helper 上限 5 参数、每个 program type 只能调子集、helper 调用直连编译后的内核函数**零 FFI 开销**。覆盖面从 map 读写（lookup/update/delete）、tracing 读取（probe_read_kernel/user 及 _str 变体）、时间（ktime/jiffies/tai）、printk/snprintf、网络全家桶（skb 改包/redirect/csum/tunnel/syncookie/socket lookup）到 dynptr/spin_lock 等。
- **值得记住的事实（KNOWN ISSUES 节）**：自认"可能滞后于内核"，自查真源=内核树五处——`include/uapi/linux/bpf.h`（helper 全表）、`net/core/filter.c`（网络类+各 program type 可用性）、`kernel/trace/bpf_trace.c`（tracing 类）、`kernel/bpf/verifier.c`（check_map_func_compatibility 查 helper×map 兼容矩阵）、`kernel/bpf/` 其余；**bpftool feature probe**（可加 unprivileged）一键探测本机可用 helper/program/map；helper×program type 兼容看 `struct bpf_func_proto` 的 switch-case（default 标签还会再放行一层）；GPL 要求也编码在 bpf_func_proto；会使 data/data_end 指针失效需重新 pull 的 helper 列在 `bpf_helper_changes_pkt_data()`。
- **对人类学习者**：写任何 eBPF 程序时案头必备——每个 helper 的返回值语义（-ENOENT/-EINVAL 等）只有这里最全。**对 AI agent**：`web/md/15.md` 是本地最大 helper 语义库，直接 grep `bpf_<name>` 拿签名+返回值+版本说明；排 verifier 报错时可 grep `data_end`、`changes_pkt_data` 相关事实。

## [16] RFC 9669 BPF Instruction Set Architecture

- **是什么**：BPF 指令集架构的 **IETF 标准规范**（Standards Track，2024 年 10 月发布，D. Thaler 编），eBPF 从"内核私有实现"升格为"互联网标准 ISA"的里程碑文件，全文实抓。
- **核心内容**：历史注记钉死"**eBPF 不再是缩写**"——BPF 已是独立术语不代表 Berkeley Packet Filter（cBPF=classic BPF 指旧版）。规范主体：两种编码=64 位 basic 指令 + 128 位 wide 指令（ldimm64）；opcode=specific(3bit)+class(3bit)；8 个指令类 LD(0x0 非标准加载)/LDX(0x1)/ST(0x2)/STX(0x3)/ALU(0x4 32 位算术)/JMP(0x5 64 位跳转)/JMP32(0x6)/ALU64(0x7)；算术/字节交换/跳转/加载存储/符号扩展加载/原子操作（5.3）/64 位立即数（5.4，含 map fd 与 platform variable 伪加载）/legacy 包访问指令（5.5，deprecated）。
- **最有工程价值的机制：conformance groups**——base32（实现 MUST 支持）⊂ base64、atomic32 ⊂ atomic64、divmul32 ⊂ divmul64、packet（Historical）；运行时与编译器（如 LLVM -mcpu=v1/v2/v3）靠组名互操作。IANA 建两个注册表（Conformance Groups + Instruction Set），新增指令=Standards Action 或 IESG 批准、废弃走专门流程——指令集演进从此有治理。
- **Security Considerations 亮点**：verifier 的保证（有限时间终止/安全内存交互/遵守 API 契约/无未定义行为）"常能提供比一般软件与 OS 代码更强的安全保证"；**解释器被视为不安全源**（推测执行侧信道 gadget），推荐只用 JIT 编译器——呼应内核 CONFIG_BPF_JIT_ALWAYS_ON 的 Spectre 动机；点名 Linux verifier 与 PREVAIL（eBPF 基金会用户态 verifier）两个参考实现，预告后续 IETF verifier 规范工作。
- **对人类学习者**：想真正理解 eBPF 字节码/写汇编器或 JIT 时的唯一规范源。**对 AI agent**：`web/md/16.md` grep `conformance`、`0x0`、`ldimm64`、`Sign Extend` 拿指令编码权威表；写反汇编/字节码分析工具时此文件是 ground truth。

## [19] bpf.h and you...（xdp-newbies 经典教程 #1）

- **是什么**：David Miller（网络子系统维护者）2017-05-11 发在 xdp-newbies 的 eBPF 入门系列第一篇（spinics 存档 Wayback 快照），讲"写 eBPF 程序需要 include 什么、ELF section 体系如何组织程序"。

## [20] Contextually speaking...（xdp-newbies 经典教程 #2）

- **是什么**：David Miller 2017-05-13 系列第二篇，讲 **context（程序上下文）**——eBPF 程序类型的意义与 direct packet access 的正确写法。
- **核心内容**：program type 在 bpf_load_program() 时指定，**决定三件事**：传入入口函数的 context 类型、可用的 helper 子集、返回值语义。示例：SOCKET_FILTER/SCHED_CLS/SCHED_ACT 三类的 context 都是 `struct __sk_buff *`；SOCK_FILTER 返回值=接受的字节数（0=丢包，非 0=截断到该长度并接受——想全收就 return skb->len）。
- **亮点（本篇精髓）**：LD_ABS/LD_IND 是 cBPF 遗留指令（libpcap 生成的经典代码用它），C 代码不能表达，现代写法一律走 **direct packet access**——`data = skb->data; data_end = skb->data_end;`（"请直接照抄这套转型写法"），然后 **必须先做边界检查 `if (eth + 1 > data_end) return 0;` 才能解引用 eth->h_proto**，否则 verifier 拒载。检查通过后 verifier 记住该指针的合法访问范围，后续整个 struct 都可安全访问。
- **对人类学习者**：这是所有"invalid mem access"类 verifier 报错的解药，读懂这一篇等于掌握 eBPF 包处理第一坑。**对 AI agent**：`web/md/20.md` grep `data_end`、`LD_ABS`、`SOCK_FILTER` 拿 context 类型映射表与边界检查范式代码；排错 prompt 可直接引用此范式。

## [21] BPF Verifier Overview（xdp-newbies 经典教程 #3）

- **是什么**：David Miller 2017-05-18 系列第三篇（被社区引用最广的一篇），讲 **eBPF verifier 内部工作机制**，开场金句："横在我们程序与毁灭深渊之间的唯一东西就是 verifier"。
- **核心内容（五步流水线）**：①map fd 重写——用户态用 ldimm64 加载 map fd（src_reg=1 即 BPF_PSEUDO_MAP_FD），verifier 查 fd 把指令改写成真实 map 指针、验证后清 src_reg；②构建 CFG，强制两条规则=**无后向边（禁循环）+无不可达指令**；③全程序逐指令检查，维护每寄存器类型与取值区间，用"跳转栈"穷举所有控制流路径（遇 BPF_EXIT 后弹栈走对侧分支），复杂度爆炸时靠 **state pruning**（已验证路径的寄存器约束比待查路径更严格则直接剪枝）缓解；④context 访问转换——`struct __sk_buff` 是内核真实 sk_buff 的**固定偏移抽象**（对外 ABI 永不变，内部结构随便改），verifier 把访问改写成真实偏移；⑤helper 调用转换（BPF_CALL 立即数=helper 编号 → 真实函数地址）。
- **亮点**：verifier log 内省机制实演——log level 1 逐指令 dump 寄存器状态（`R1=ctx R3=imm32,min_value=32,max_value=32,min_align=32 R10=fp`），并给出如何用 test_align.c/bpf_verify_program() 捕获 dump。这篇是读得懂 verifier 报错输出的钥匙。
- **坑**：2017 年描述的"无循环"限制后来被 bounded loop（5.3 起）取代，pruning 算法也已演进（等价类+有界循环），但寄存器状态机模型沿用至今。
- **对人类学习者**：从"verifier 是黑盒玄学"到"verifier 是可理解的抽象解释"的分水岭材料。**对 AI agent**：`web/md/21.md` grep `BPF_PSEUDO_MAP_FD`、`state pruning`、`R1=ctx` 拿 verifier 机制事实；解析 verifier log 时此篇的寄存器状态语法说明是对照表。
