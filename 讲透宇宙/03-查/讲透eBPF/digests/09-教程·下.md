## [113] Loops and Iterators in eBPF

- 是什么：eBPFChirp newsletter（Teodor J. Podobnik，2024-09-22）讲 eBPF 里循环的全部方式，配示例仓 github.com/dorkamotorka/ebpf-loops。
- 核心内容：五种循环机制按内核版本演进——①unrolling（v5.3 前）：`#pragma unroll` 把循环展开成直线指令，代价是程序体积膨胀；②bounded loops（v5.3+）：verifier 开始能回溯后向跳转，但受指令数上限约束（v5.4 前仅 4096 条，之后 1M，超限报 "Processed 1000001 insn"）；③bpf_loop helper（v5.17+）：循环体作为回调交给内核管理，verifier 只检查一次回调，上限约 800 万次迭代且不吃指令预算；④open-coded iterators（v6.4+）：bpf_iter_num_new/next/destroy 三件套，libbpf 再封装出 bpf_for 与 bpf_repeat 宏，写法最自然；⑤bonus：bpf_for_each_map_elem（v5.13+）专用于遍历 map。
- 亮点：讲清了"为什么有指令上限"（eBPF 必须及时让出 CPU，否则拖垮网络和整机）以及 verifier 靠 CFG 前后向遍历验证循环终止性的机制。
- 对学习者价值：eBPF 循环选型一页纸：小循环用 bounded loop、大迭代用 bpf_loop、要自然语法用 v6.4 bpf_for、遍历 map 用专用 helper。
- 对 AI agent 用法：本地 113.md 可 grep "bpf_loop"、"bpf_iter_num"、"4096"、"1M" 拿版本号与限制数字；写 eBPF 循环代码时按内核版本选机制可引用此篇结论。

## [114] What Insights Can eBPF Provide into Real-Time SSL/TLS Encrypted Traffic and How?

- 是什么：eBPFChirp newsletter（2024-09-19，赞助文）讲用 uprobe/uretprobe 在加密前/解密后捕获明文流量，示例仓 github.com/dorkamotorka/ssl-ebpf。
- 核心内容：传统 SSL inspection（合法 MiTM）要解密再重加密，需要管理证书且计算昂贵；在应用里埋点又要求改代码+重启。第三条路是 uprobe 挂 OpenSSL 库函数：uprobe 挂 `SSL_write()` 拿加密前的客户端出站明文，uprobe+uretprobe 挂 `SSL_read()` 拿服务端解密后明文及返回码（如 HTTP 200）。限制：只对同节点上的加解密流量有效（不能部署在网络边缘）；换了 BoringSSL/GnuTLS 等其它库就要换挂点。
- 亮点：给了实测性能数据——平均每请求额外延迟仅 ~0.2µs；CPU 开销 uprobe/SSL_write 0.1%、uprobe/SSL_read 0.007%、uretprobe/SSL_read 0.3%。
- 对学习者价值：加密流量观测的三方案对比（MiTM 代理 / 应用埋点 / uprobe）+ 真实开销数字，是 sslsniff 类工具的原理课。
- 对 AI agent 用法：本地 114.md 可 grep "SSL_write"、"SSL_read"、"0.2µs" 取挂点函数名与开销数据；与 eunomia 教程 30 课 sslssniff（web/md/111.md 内有链接）互为印证。

## [115] Can eBPF Detect Redis Message Patterns Before They Become Problems?

- 是什么：eBPFChirp newsletter（2024-09-17，赞助文）讲用 syscall tracepoint 追踪并解码 Redis RESP 协议，示例仓 github.com/dorkamotorka/redis-ebpf。
- 核心内容：Redis 自带指标（如 LATENCY 命令）只有粗粒度平均值，无法定位具体哪条命令引发劣化。方案是挂 4 个 tracepoint：sys_enter_write（捕获客户端命令数据）、sys_exit_write（命令延迟，经 Perf Buffer 送用户态）、sys_enter_read / sys_exit_read（接收数据与读延迟），enter→exit 之间用 active_writes/active_reads 两张 eBPF map 传递参数。由此可拿到连接 fd、socket 地址、完整 Redis 命令（类型/参数）。
- 亮点：手把手解码 RESP 协议示例 `*3 $3 SET $4 name $9 ebpfchirp`（`*`=数组、`$`=bulk string、`+`简单串、`-`错误、`:`整数），并给出万次请求实测：平均开销 ~17µs；各 hook CPU 占用 sys_exit_read 高达 11.69%、sys_enter_read 1.89%、sys_enter_write 4.26%。
- 坑：syscall tracepoint 开销明显高于 uprobe 方案（对比 114 篇的 0.2µs）——解码 RESP 的开销大头在 read 退出路径，生产环境高频 Redis 上要慎重。
- 对学习者价值：L7 协议观测的通用范式（enter/exit tracepoint + map 传参 + perf buffer 出口）+ 一个诚实的开销基准。
- 对 AI agent 用法：本地 115.md 可 grep "sys_enter_read"、"RESP"、"11.69%" 取挂点设计与开销结论；为用户写 Redis/协议级 eBPF 观测方案时的模板引用。

## [116] Transparent Proxy Implementation using eBPF and Go

- 是什么：eBPFChirp newsletter（2024-09-08）讲用 Go + ebpf-go 库实现透明代理，示例仓 github.com/dorkamotorka/transparent-proxy-ebpf。
- 核心内容：三个 eBPF 程序协作完成对客户端完全透明的拦截——①`cgroup/connect4`：挂 connect 系统调用，把目标 IP:port 改写成本地代理 127.0.0.1，同时把原始目的地存入 map_socks；②`sockops`：连接建立后记录源端口与 socket cookie 的映射到 map_ports（源端口只有建连后才知道，cookie 是内核给 socket 的唯一标识）；③`cgroup/getsockopt`：代理检查完包内容后调 getsockopt 查原始目的地，该程序经 map_ports→cookie→map_socks 链路取回原始目的地并与之建连转发。三个程序都绑定特定 cgroup，只对该组进程生效。
- 亮点：把 Istio 类服务网格 sidecar 拦截的核心机制（原目的地还原）拆成 map 链路讲透；实测万次请求平均开销 ~1ms，各 hook CPU：sockops 0.4%、connect4 0.1%、getsockopt 0.09%。
- 对学习者价值：理解 "cgroup/connect4 改目的地 + sockops 记 cookie + getsockopt 还原目的地" 这一透明代理标准三件套的最佳单篇。
- 对 AI agent 用法：本地 116.md 可 grep "connect4"、"sockops"、"map_socks"、"socket cookie" 取机制链与数字；写 Go 透明代理/流量劫持方案时的引用源。

## [119] Accelerating Local Socket Communication using eBPF

- 是什么：eBPFChirp newsletter（2024-08-29）讲 sockops socket splicing 加速本机 socket 通信，示例仓 github.com/dorkamotorka/sockmap-ebpf。
- 核心内容：微服务间走 loopback 的请求要把本地 TCP/IP 栈穿两次（下行+上行），高并发下成为瓶颈（典型场景：同主机两个 Kubernetes pod 互通）。Cilium 的解法是 socket splicing：①`sockops` 程序挂在 cgroup 钩子上，在有 socket 操作（建连、重传超时等）时把 socket 对象插入 Sockmap；②`sk_msg` 程序挂在 Sockmap 的 fd 上，只在命中该 map 的 socket 上触发，拦截 sendmsg()/sendfile() 系统调用，把消息直接重定向到接收端 socket，跳过整个本地网络栈。
- 亮点：讲清了为什么用 cgroup 钩子（cgroup 是进程层级组织，限定作用范围即限定受影响进程）；配图来自 Cloudflare eBPF Day 演讲，是 Cilium 同主机加速的标准原理图。
- 坑：本篇无性能实测数字（作者把测试放到了代码仓）；sk_msg 快捷路径只对同主机且都在 Sockmap 里的 socket 生效。
- 对学习者价值：理解 Cilium/Katran 类 sidecar 加速与 eunomia 教程 29 课 sockops 的原理基础篇。
- 对 AI agent 用法：本地 119.md 可 grep "sk_msg"、"sockops"、"Sockmap"、"sendmsg" 取两程序分工描述；回答"同主机 pod 通信加速怎么做"时的机制引用。

## [120] Writing a basic continuous profiler

- 是什么：Maxgio 博客（2024-08-18，12min）"Unleashing the power of frame pointers pt.2"，从零写一个基于 eBPF 的采样式持续 profiler，完整代码在 github.com/maxgio92/yap（YAP = Yet Another Profiler）。
- 核心内容：内核侧一个 `SEC("perf_event")` 程序负责采样——用 `bpf_get_stackid`（0 取内核栈、BPF_F_USER_STACK 取用户栈）把栈回溯抽象掉，key 为 {pid, kernel_stack_id, user_stack_id} 写入 HASH 直方图 map 计数，栈帧本体（instruction pointers 数组）存 BPF_MAP_TYPE_STACK_TRACE map（value = PERF_MAX_STACK_DEPTH×u64）；同时用 BPF_CORE_READ(task, mm, exe_file, f_path) 取进程可执行文件路径经 binprm_info map 传给用户态。用户态用 libbpfgo：遍历直方图算 residency fraction（nTraceSamples/nTotalSamples）；符号化用 Go 标准库 debug/elf 读未 strip 的 ELF .symtab，按 st_value ≤ ip < st_value+st_size 匹配符号。触发器是 perf 软件事件 PERF_COUNT_SW_CPU_CLOCK，按 CPU 各开一个 fd 定时触发 BPF 程序（sample_period 建议用质数避免与其它周期任务共振）。
- 亮点：把"采样直方图 + 栈表 + 符号表"三张 map 的分工与数据流讲成一堂完整实现课；明确 frame pointer 展开的局限（strip 二进制、无 frame pointer 构建是遗留问题）。
- 对学习者价值：想真正吃透 Parca/Pixie/Pyroscope 这类持续 profiler 内部机制的最好起点——从零复刻最小版本。
- 对 AI agent 用法：本地 120.md 可 grep "bpf_get_stackid"、"PERF_COUNT_SW_CPU_CLOCK"、"symtab"、"libbpfgo" 拿可直接复用的代码片段与 API 序列；写采样 profiler 类方案时的骨架模板。

## [122] Inspektor Gadget - Hello world gadget with Wasm

- 是什么：上一篇的续篇，演示在 gadget 里加 Wasm（Go 编译）模块处理复杂用户态逻辑。
- 核心内容：在 program.bpf.c 旁建 go/program.go，用 `//go:wasmexport` 导出 gadgetInit/gadgetStart/gadgetStop 三个生命周期函数（依赖 inspektor-gadget/wasmapi/go，v0.31.0+），build.yaml 声明 `wasm: go/program.go` 后 ig image build 自动编译为 wasm 模块。三个能力示例：①操作字段——eBPF 里做字符串处理/正则几乎不可能，wasm 侧 GetDataSource("open")→GetField("filename")→Subscribe 回调里用 Go regexp 把 `/home/<user>/` 改写成 `/home/***/`（脱敏）；②加字段——ds.AddField("human", Kind_String) 在回调里拼人类可读描述注入事件；③Dropping events 一节标 TBD 未写。
- 亮点：点破了 eBPF+ wasm 的分工本质——内核侧只管采集原始事件，凡是正则、字符串变换、复杂聚合这类逻辑全放 wasm，且 Go 程序员零新语言成本（与 eunomia 的 wasm-bpf 是同一思想的两家实现）。
- 对学习者价值： gadget 进阶第一课，也是"eBPF 数据面 + Wasm 控制面"架构模式的最短可运行样例。
- 对 AI agent 用法：本地 122.md 可 grep "wasmexport"、"GetDataSource"、"AddField"、"Subscribe" 取 Go wasm API 签名与回调写法；为用户设计"内核采集+用户态富加工"分离架构时引用。

## [123] ebpf.io labs

- 是什么：ebpf.io 官方的交互式实验室（interactive labs）索引页，聚合 7 个可在浏览器里直接动手的 eBPF 教程环境。
- 核心内容：按 Networking/Observability/Programming 三类组织——①Build an eBPF Monitoring Tool for Kubernetes（isovalent labs：补全一个 HTTP 监控 agent，部署为 DaemonSet，导 Prometheus 指标并在 Grafana 里叠加 K8s 元数据可视化）；②Go + eBPF Development（isovalent：用 cilium/ebpf 库，覆盖 maps、ring buffers、XDP 钩子、内核追踪）；③eBPF Networking（isovalent：内核网络与 eBPF 挂载点深潜，讲 Cilium/Hubble/Katran 的生产模式）；④eBPF Beginner Skill Path（iximiuz：从第一个程序到 maps、bpftool/bpftop、verifier，以挑战收尾）；⑤Getting started with eBPF（isovalent 入门）；⑥Getting started with eBPF with Aya（killercoda：Rust 框架 Aya 路线）；⑦Learning eBPF Tutorial（isovalent：Hello World→maps/bytecode/bpftool/xdp/verifier）。
- 亮点：全部免费免安装（浏览器内终端环境），且是官方维护的分类入口，初学路线选型（C/Go/Rust 三语言各有一条路径）一目了然。
- 对学习者价值：比读文章更强的动手起点；配合本批 111 教程（理论+代码）与 121/122（gadget 开发）形成"读—抄—改"完整闭环。
- 对 AI agent 用法：本地 123.md 可 grep "labs.isovalent"、"iximiuz"、"killercoda"、"Aya" 取各 lab 的准确入口 URL；推荐学习路径时按用户语言偏好（C/Go/Rust）定向指路。
