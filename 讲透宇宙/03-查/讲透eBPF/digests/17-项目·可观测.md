# 批次 17-项目·可观测（17 条）

**总评**：本批是 eBPF 可观测生态的完整横切面——从 2016 年 SIGCOMM CCR 的 InKeV 论文（eBPF 内核可编程数据面的早期学术尝试）到 2026 年仍在高频提交的生产级平台（DeepFlow/Coroot/parca-agent/Hubble 全部 11 月初仍有提交），可见这条技术线已从论文走成产业标配。三种技术路线并存：①全栈 APM 平台（DeepFlow/Coroot/SkyWalking Rover/Pixie，零侵扰 auto-instrumentation 为主打）；②聚焦单一痛点做深（kyanos 抓包回放、rbperf Ruby CPU profiling、Caretta eBPF+XDP 服务拓扑、parca 连续 profiling、Hubble 网络流可见性）；③玩具/实验级（kpod-metrics、Kotlin DSL、eTraceGen——同作者 pjs7678 的两个小仓和事件遥测引擎更接近学习样本）。采集点几乎覆盖 eBPF 全部 hook 类型：kprobe（kyanos/DeepFlow/Coroot）、tracepoint（Hubble/Cilium、Caretta）、perf event（rbperf/parca-agent）、tc/XDP（Caretta、InKeV），加上环形缓冲（perf/ringbuf）与 DWARF/帧指针栈回溯两条 profiling 支线。坑：Ingero 上游已删（GitHub 404）；DEEP-mon 的 slideshare 页是 JS 壳页无法抓取正文。

## [200] InKeV: In-Kernel Distributed Network Virtualization for DCN（pdf）

- **是什么**：SIGCOMM CCR 2016 论文（FAST/PLUMgrid/LUMS 合作），基于 eBPF 的多租户数据中心网络虚拟化（NV）**数据面**平台。注意：论文本体是网络虚拟化而非可观测，清单归入 Observability 略有错位，但它正是 eBPF "内核可编程"哲学的奠基文献之一。
- **核心内容**：论点=OVS 式"薄内核+厚用户态"数据面因频繁 user/kernel 上下文切换付出延迟代价；InKeV 用 eBPF 把 VNF 数据面全部塞进内核动态插桩。**stitching（缝合）是关键创新**：用 `BPF_MAP_TYPE_PROG_ARRAY` tail-call 把多个 eBPF VNF 模块串成图，在单 edge 内构建完整虚拟网络拓扑；VID 元数据塞 `sk_buff.cb` 字段传递。
- **架构四组件**：Network Graph Manager（用户态编排：VNF 图的导入/验证/安装，基于 BCC 编译）+ 三个内核 eBPF 模块——PVM（挂 **tc ingress** 抓 sk_buff、`bpf_clone_redirect()` 交付工作负载）、Patch Panel（Graph map + Prog_lookup 两 map 做 VID→VNF 缝合）、Transport Manager（GRE/VXLAN/Geneve 跨 edge 隧道）。
- **实测**：vs OpenStack Neutron（OVS 数据面）——延迟低一个数量级、TCP_CRR 流建立速率高一个数量级、同机吞吐 20Gbps vs 0.6Gbps。结尾展望 P4→eBPF 编译（BCC p4 frontend）承载第三方 VNF。
- **对人类学习者**：理解"为什么 eBPF 会取代内核模块"的最佳一手史料——直接引用 OVS 架构师自述"内核模块难开发难分发"；tail-call 级联 + map 传元数据是至今仍通用的模式（Cilium datapath 同款思想）。
- **对 AI agent**：本地全文 `/usr-data/data2/kylin/network/awesome-ebpf/web/pdf-txt/200.txt`；可 grep `PROG_ARRAY`、`sk_buff.cb`、`bpf_clone_redirect`、`tail call`、`B-R-B` 快速定位架构细节。

## [202] Pixie（repo）

- **是什么**：pixie-io 开源的 Kubernetes 可观测平台（CNCF 项目，px.dev），主打 eBPF **auto-telemetry**——不改动应用代码自动采集 full-body 请求、网络/资源指标、应用 profile。最后提交 2026-10-26，活跃。
- **三大卖点**：①Auto-telemetry（eBPF 自动采集，协议自动解析）；②**In-Cluster Edge Compute**——数据采集、存储、查询全部留在集群内，宣称 <5% 集群 CPU（多数 <2%）；③**PxL**——Pythonic 脚本查询语言，UI/CLI/API 通用。
- **用例**：网络监控（流量图、DNS 全文请求/响应、TCP drop/retransmit 地图）、基础设施健康（Pod/Node 资源 + CPU flame graph）、服务性能（自动 trace 多协议、按 endpoint 的延迟）。
- **架构/语言**：C++ 为主的重型单体仓（bazel 构建）——`src/stirling` 是 eBPF 采集器（335 个 C/C++ 文件，socket tracer 是核心），`src/carnot` 查询引擎（290 .cc），`src/vizier` 集群内数据面，Go 写 operator/CLI，TypeScript 写 UI。
- **采集点**：混合挂载——**uprobe 占大头（88 处，SSL/tls-hook 追踪）+ tracepoint 31 + kprobe 13**，另有 `dynamic_bpftrace` 连接器可直接跑 bpftrace 脚本；基于 BCC。
- **对人类学习者**："eBPF 抓 full-body L7 请求"工程化的标杆实现，stirling 的 socket tracer（协议解析器族）是学习多协议解析的宝库。
- **对 AI agent**：本地 `repos/pixie-io/pixie`；可 grep `stirling/source_connectors/socket_tracer`（协议解析）、`pxl_scripts`（现成 PxL 脚本库）、关键词 `uprobe`、`bpftrace`、`carnot`。

## [206] rbperf（repo）

- **是什么**：javierhonduco 写的 **Ruby (CRuby) 低开销采样 profiler + tracer**，BPF 内运行，Rust 用户态（约 2667 行 .rs + libbpf C 代码）。**最后提交 2024-04-21，已两年半无更新，近乎停滞**。

## [207] rstat（repo）

- **是什么**：overyonder 的 Linux 系统监控守护进程（Rust ~4562 行），给 Waybar 桌面状态栏供 CPU/内存/磁盘/网络/NVIDIA GPU 五个模块。**当前 v2 版零 eBPF**——但 README 专门有一章 "Version 1: the eBPF experiment" 记录弃用 eBPF 的实测过程，**是全批最珍贵的批判性样本**。最后提交 2026-11-04，活跃。
- **v1 实验**：在 `sched_switch` **tracepoint** 挂 eBPF probe 维护 per-task CPU/内存/IO 计数器，userspace 一次 batch lookup——刷新路径 0.13–0.16 ms，比 procfs 进程遍历快约两个数量级。
- **为什么放弃（核心洞察）**：代价没有消失而是转移——poller 按刷新付费，probe 按**每次上下文切换**付费：常规负载 12,454 switches/s 时 handler 花费 8 ms/s；人为切换风暴（240 万/s）时吃掉 **1.8 个 CPU 核**。"always-on probe 在机器最忙时收费最贵——恰恰是监控最该便宜的时候"，还需 root/`CAP_BPF`+`CAP_PERFMON`、启动时 Clang 编译。
- **v2 方案**：持久 fd + `pread` offset 0 重读 /proc、/sys 计数器 + PSI 压力 + NVML，按需采样（section 被订阅才开采集器），五模块全开 ~1.5% 单核。结论："eBPF 仍是内核计数器回答不了的问题（如 per-task 延迟归因）的正确工具，但应只在调查期间运行而非持续运行"。
- **对人类学习者**：全批唯一给出"何时**不**该用 eBPF"定量论证的项目；PSI（some/full）语义讲解也很到位。
- **对 AI agent**：本地 `repos/overyonder/rstat`；grep `Version 1: the eBPF experiment`（完整权衡分析）、`sched_switch`、`PSI`、`pread`。

## [211] kpod-metrics（repo）

- **是什么**：pjs7678 的 eBPF pod 级内核指标采集器（K8s DaemonSet，Prometheus 导出）。**技术栈罕见：Spring Boot（JDK 21 + Virtual Threads）+ JNI 调 libbpf**——不是 Go/Rust/C++ 用户态。最后提交 2026-04-19。
- **架构**：MetricsCollectorService（默认 30s）驱动 **10 个 eBPF collector**（CpuScheduling/Network/Memory/Syscall/Biolatency/Cachestat/Tcpdrop/Hardirqs/Softirqs/Execsnoop + BpfMapStats 自检）+ 4 个 cgroup collector（磁盘 IO/接口网络/文件系统/内存）；PodWatcher（K8s informer）+ **CgroupResolver（cgroup ID → pod 元数据）** 是 per-pod 归因的关键件。
- **采集点**：**tracepoint 为主**（sched_switch、tcp_sendmsg、oom_kill 等，BCC 工具族移植）。
- **本仓最大看点（CLAUDE.md 实证）**：仓库自带 CLAUDE.md 且写明"**所有 eBPF 程序必须用 kotlin-ebpf-dsl（src/bpfGenerator/）实现，禁止手写 .bpf.c**"——它就是 id=212 DSL 的实际宿主项目，构建要求 sibling `kotlin-ebpf-dsl/` 目录；另有 `raw()` 逃生舱机制处理 DSL 表达不了的复杂 C（指针追踪/嵌套循环）。
- **对人类学习者**：Java 生态做 eBPF 的孤例样本（JNI 桥 + codegen）；也展示 "AI 辅助开发规约"如何写进仓库（CLAUDE.md 约束代码生成路径）。
- **对 AI agent**：本地 `repos/pjs7678/kpod-metrics`；grep `CLAUDE.md`、`src/bpfGenerator`、`CgroupResolver`、`jni/`。

## [212] Kotlin DSL（kotlin-ebpf-dsl，repo）

- **是什么**：pjs7678 的 **Kotlin DSL 写 eBPF**——类型安全、**编译期验证**，双代码生成（`.bpf.c` C 源 + Kotlin `MapReader` 类）。最后提交 2026-03-09；与 id=211 kpod-metrics 配套（同作者，宿主关系见上条）。
- **解决什么**：C 写 eBPF 的错误（错 helper 调用、栈溢出、类型不匹配、verifier 拒绝）通常只在 **load time** 暴露；DSL 把它们提前到 **build time** 的 Kotlin 测试里。
- **能力面**：类型安全 struct（自动 C ABI 对齐/padding）、三阶段验证（构造检查→type checker→语义分析）、**31 个 BPF helper（按程序类型的可用性 + GPL 许可强制）**、**14 种程序类型**（tracepoint/kprobe/kretprobe/fentry/fexit/XDP/TC/cgroup/LSM 等）、24 个 BCC 风格内置工具（biolatency/runqlat/execsnoop/tcpconnect...）。
- **用法示例**：`val program = biolatency(); program.validate().throwOnError(); program.emit(...)`——验证过了再生 C，属于"eBPF 的类型安全前端"路线（对比：ppy/nfelf、Bumblebee、aya 同类努力）。
- **对人类学习者**：学"eBPF verifier 错误前置到编译期"的编译器设计样本；struct 布局/padding 自动化是 C/Kotlin 互操作的好教材。
- **对 AI agent**：本地 `repos/pjs7678/kotlin-ebpf-dsl`；grep `BpfStruct`、`generateC`、`preamble()`、`postamble()`、`SEC` 程序类型清单。

## [214] Coroot（repo）

## [215] kyanos（repo）

- **是什么**：hengyoush 的 eBPF 网络问题分析工具，"One command to find slowest requests and identify the reasons"——抓 HTTP/Redis/MySQL/Kafka/MongoDB/RocketMQ/DNS 请求，替代 tcpdump 抓包-下载-分析三步流。Go + libbpf（CO-RE），上过 Hacker News（42154583）+ Trendshift。最后提交 2026-06-16。
- **三大能力**：①流量过滤远超 tcpdump——按 pid/container-id/**Redis key**/响应字节数/延迟/L7 协议字段过滤（`kyanos watch redis --keys my-key1`）；②聚合分析（`kyanos stat http --bigresp` 直接找出哪个 IP 哪个请求吃掉带宽）；③**内核级延迟拆解**——请求/响应从**网卡到 socket buffer 每个内核阶段**的时间可视化，Redis 慢查询能定位到具体慢在哪一段（本工具的招牌）。
- **采集点**：syscall tracepoint（send/recv/write/read 全家族）+ `kprobe/__ip_queue_xmit` + XDP + **uprobe 矩阵**——openssl 从 1.0.2a 到 **3.5.0 逐版本独立 .bpf.c**（十余个）+ `gotls.bpf.c`（Go TLS），是本批 TLS 明文还原覆盖最全的实现；另有 legacy kernel 3.10 适配版（国产旧内核环境友好）。
- **对人类学习者**：网络排障视角的 eBPF 实战教科书；`pktlatency.bpf.c` + `protocol_inference.h`（协议自动推断）是核心学习对象。
- **对 AI agent**：本地 `repos/hengyoush/kyanos`；grep `pktlatency`、`protocol_inference`、`openssl_3_5_0`、`gotls`、`--bigresp`。

## [216] eTraceGen（repo）

- **是什么**：个人项目（bhanuprakasheagala），"Linux Activity Intelligence Platform"——eBPF + **Modern C++20** + libbpf 的模块化内核活动遥测引擎，README 自标 **[IN PROGRESS] / Phase 1**（学习/实验性质）。最后提交 2026-10-24，仍活跃。
- **分层架构设计**：观察层（eBPF→ring buffer→C++ collector）→ 知识层（Canonical Event Model 规范化事件模型 → Entity Registry 进程/文件/socket 实体状态 → Correlation Engine 跨实体跨时间关联）→ 智能层（Semantic Engine 行为推断 → Policy Engine）——只有观察层碰内核，eBPF 保持 verifier 友好轻量。
- **采集点**：纯 **syscall tracepoint**（sys_exit_write/writev/vfork/unlinkat/socketpair/socket/shutdown/setsockopt 等），按 file/network/process/syscall 四个域拆分 .bpf.c；用户态 C++ 按 collector/decoder/enricher/registry/policy/sinks 分模块（13 个 .cpp，早期规模）。
- **对人类学习者**：观测数据"事件→实体→关联→语义"分层提炼的架构思想值得借鉴；C++20 做 eBPF 用户态的少见样例（对比 Pixie 的 C++ 但重量级得多）。
- **对 AI agent**：本地 `repos/bhanuprakasheagala/eTraceGen-eBPFEventTelemetryEngine`；grep `Canonical Event Model`、`Entity Registry`、`event_logger_*.bpf.c`、`policy/`。
