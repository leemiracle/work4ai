# 批次 18：项目·安全与调度器（17 条 = Security 15 + Linux Scheduler 2 + gone 1）

**本批总评**：本批是 eBPF 安全与调度两线的全景切片。防御侧占绝对主体（Falco/SysmonForLinux/Tracee/Tetragon/Red Canary sensor/bpflock/owLSM/BPFJailer/Bombini/Inner Warden 12 项），覆盖从 CNCF 毕业级的云原生运行时检测、微软 Sysinternals 移植、Aqua 开源引擎、Cilium 的 K8s 原生策略执行，到 LSM BPF 强制访问控制（BPFJailer/owLSM/Bombini 一线尤其拥挤）与主机加固锁（bpflock）的全谱；研究/工具侧 harpoon 提供函数级 syscall 细粒度分析，Aya 则是横跨攻防的 Rust eBPF 基础设施。调度器侧 scx（sched-ext，Meta+Google 投入、6.12 主线）与 Gthulhu（K8s 分配→sched_ext 执行面桥接）代表 eBPF 可编程调度的生产与前沿。共同主题：老内核上的 CO-RE/offset 问题有 Red Canary（oxidebpf+LKCCB）与 Sysinternals（BTF autodiscovery）两套解法；而"检测后强制"（detect→enforce in kernel）正成为新一代项目（Tetragon/Bombini/owLSM）对 Falco 世代的核心差异化。数据面注意：本批 4 仓本地克隆损坏已修复（SysinternalsEBPF/owLSM/innerwarden/Gthulhu），Synapse 上游已删，Inner Warden 上游改名并转向 AI agent 护栏（eBPF 部分闭源化）。

- **对 AI agent 的用法**：本地 `/usr-data/data2/kylin/network/awesome-ebpf/web/md/217.md`；可 grep "plugin/CloudTrail/graduated" 快速定位生态位信息。规则细节需另抓 falcosecurity/rules 仓。

## [218] Sysmon for Linux（repo）
- **是什么**：微软 Sysinternals Sysmon 的 Linux 移植【防御】。监控并记录进程生命周期/网络连接/文件写入等系统活动，跨重启 + 高级过滤，事件以 XML 输出到 syslog。
- **核心内容**：C 为主（sysmonforlinux.c + sysmonCommon/ 共享 Windows 版代码 + pugixml），eBPF 程序在 ebpfKern/（GPL2），依赖同目录的 SysinternalsEBPF 库。事件查看器 sysmonLogView；配置与 Windows 版同构（XML，如 FieldSizes 限字段长度）。
- **亮点/坑**：offset 三级策略——BTF 优先（支持 /BTF 开关挂 BTFHub 独立文件）→ autodiscovery（discoverOffsets）→ getOffsets 手工生成覆盖，是"无 BTF 内核上跑 CO-RE"的完整工程示范。坑：syslog 默认 1-8KB 会截断 >64KB 大事件。
- **活跃度**：最后提交 2026-11-04，持续维护中；包已进微软官方 Linux 源。
- **对学习者的价值**：读 ebpfKern/ 可看大厂如何用 C + libbpf 写生产级系统调用追踪探针（execve/proc/create 等 Sysmon 事件映射）。
- **对 AI agent 的用法**：本地 `/usr-data/data2/kylin/network/awesome-ebpf/repos/Sysinternals/SysmonForLinux/`；grep `SEC("tracepoint")` 或 `sysmonevents_defs.c` 看事件定义，vmlinux.h/vmlinux_kern_diffs.h 是内核头处理范例。

## [220] Red Canary: eBPF for security — a beginner's guide（md）
- **是什么**：Red Canary（现 Zscaler 旗下）2022-01 博客，解释为什么 MDR 厂商把 Linux sensor 从 AuditD/LKM 迁到 eBPF【防御·厂商一手资料】。
- **核心内容**：①AuditD 三宗罪：慢（内核外做过滤）、不灵活（只出设计好的事件）、单消费者（事件被读走即消失）；②eBPF 三优势：内核内过滤分析、任意内核观测点、多消费者并存；③自家两件套 redcanary-ebpf-sensor（多探针单 ELF，按内核选载，"Compile-Once, Run-Most-Places"）+ oxidebpf（Rust 管理库，ProgramVersion/optional 探针）；④LKCCB 内核 offset 云构建器计划（"内核 GPS"）。
- **亮点**：实测数据——execve 追踪场景 eBPF 比 auditd 满配高 19% 吞吐（14254 vs 11989 execl/s，基线 19421）；AuditD 在容器场景返回子进程 PID namespace 的 PID 导致进程谱系断裂，eBPF 可在 fork 返回路径读 task_struct 拿 root namespace PID。
- **对学习者的价值**：eBPF 安全遥测的动机论证范本，benchmark 方法（byte-unixbench execl/s）可直接复用。
- **对 AI agent 的用法**：本地 `/usr-data/data2/kylin/network/awesome-ebpf/web/md/220.md`；grep "execl/s/LKCCB/oxidebpf" 取关键数据。

## [223] bpflock（repo）
- **是什么**：eBPF 驱动的 Linux 主机加固/锁工具（linux-lock org）【防御·预防型】，用 LSM+BPF 等钩子收窄攻击面、阻断已知攻击技术——与检测类（Falco/Tracee）互补。
- **核心内容**：Go 控制面 + 多个小 BPF 程序；安全特性分六类：Memory（内核镜像锁定/内核模块保护/BPF 自身保护）、Process（fileless 内存执行拦截、namespace 保护）、Hardware（USB 接入防护）、Tracing（应用执行/特权操作审计）、Filesystem（只读 rootfs/sysfs）、Network（规划中，云原生场景让位 Cilium）。声明式 profile：`restricted/baselice/...` 三档全局语义；只有 host pid/net namespace 的管理者（systemd/容器管理器）保留全功能。
- **亮点/坑**：明确自我定位——不做 MAC 标签、不替代 AppArmor/SELinux、不防 evil root；**坑：experimental 阶段，最后提交 2022-02-16，实质停滞 4 年**，选型须谨慎（同类活项目可看 inner_warden [231]）。
- **对学习者的价值**：docs/ 下每类防护一页（memory-protections.md 等），是"LSM BPF 用于主机加固"的最小可行教材。
- **对 AI agent 的用法**：本地 `/usr-data/data2/kylin/network/awesome-ebpf/repos/linux-lock/bpflock/`；grep `BPF_PROG_TYPE_LSM` 或看 `pkg/` 各守护进程与 `deploy/` 部署单元。

## [224] Tetragon（repo）
- **是什么**：Cilium 家族的实时 eBPF 安全观测与**运行时强制执行**（enforcement）组件【防御】，K8s 原生：事件自动关联 namespace/pod/容器身份。
- **核心内容**：传感器（sensors）挂内核关键钩子：①进程生命周期（process_exec/process_exit 默认开）；②通用追踪（process_kprobe/tracepoint/uprobe），由 TracingPolicy CRD 声明式配置； Enforcement 能力可实时 kill/透传阻断而非仅告警。tetra CLI 独立查询；多许可证（Apache/BSD/GPL 分层）。
- **亮点**：TracingPolicy 是"策略即 K8s 资源"的范式——kprobe/selectors/actions 一体化 YAML；官方 use case 覆盖网络可观测、文件访问、凭证监控、特权执行；与 Cilium 网络层联动是独有生态位。
- **活跃度**：最后提交 2026-11-05（前一天），本批最活跃仓之一。
- **对学习者的价值**：学习"检测+执行闭环"（policy enforcement 而非纯告警）与 K8s 集成的首选大厂实现。
- **对 AI agent 的用法**：本地 `/usr-data/data2/kylin/network/awesome-ebpf/repos/cilium/tetragon/`；bpf/ 与 pkg/sensors/ 是探针体系，`api/` 有 TracingPolicy 的 protobuf 定义，crds 在 `install/`。

## [225] harpoon（repo）
- **是什么**：函数级 syscall 捕获器——"从执行流（河）里钓起单个函数（鱼）的 syscall"【研究/工具·偏防御分析】。作者 alegrey91（意大利安全研究员，GOAL/Fuzzing 项目作者）。
- **核心内容**：Go + libbpfgo（内嵌 libbpf）；用 uprobe/uretprobe 圈定目标函数入口/返回，配合 syscall tracepoint，只输出该函数执行窗口内触发的 syscall——比 strace（全程序全生命周期）精细得多。用法：`objdump --syms` 拿符号 → `harpoon capture -f main.doSomething -- ./binary`。
- **亮点**：用途定位在逆向/攻击面分析（确认某函数是否碰网络/文件），输出 syscall 列表极简；有 docs/commands.md + docs/tutorials.md 教程。
- **活跃度**：最后提交 2025-11-12。
- **对学习者的价值**：uprobe 圈定 + syscall 过滤的组合是 eBPF 用户态细粒度追踪的教学级小样本；libbpfgo 集成范例。
- **对 AI agent 的用法**：本地 `/usr-data/data2/kylin/network/awesome-ebpf/repos/alegrey91/harpoon/`；代码在 ebpf/（探针）+ internal/（Go 侧），grep `uretprobe` 看窗口逻辑。

## [227] BPFJailer（repo）

## [228] Bombini（repo）

- **对学习者的价值**：想用 Rust 写 eBPF 的必经之路；aya-rs.dev book 是体系化教程；对比 libbpfgo（[225] harpoon 用）可见两代语言绑定设计。

## [230] owLSM（repo）
