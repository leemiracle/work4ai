## [186] DPDK PMD for AF_XDP

- **是什么**：DPDK Userspace 2018 会议（2018-09-06，Intel 软件工程师 Xiaoyun Li）的议程页，讲者为 DPDK 实现 AF_XDP Poll Mode Driver 的工作分享；页面含完整 abstract 和幻灯 PDF 直链（hosted-files.sched.co）。
- **核心内容**：AF_XDP 定位为 AF_PACKET 的升级版、宣称 10 倍以上性能提升；能把 XDP pass-through 直连用户态（eBPF 程序处理过的包高效送入应用）。实现要点=把 AF_XDP 概念（XDP socket、eBPF redirect map）翻译成 DPDK 概念（ethdev、queue），以及 rte_mempool 与 XDP umem 之间的 zero-copy；未来方向提到 busy polling。
- **价值**：这是 net_af_xdp PMD 进入 DPDK 主线（DPDK 18.05 起）背后的第一手设计叙述，理解"DPDK 应用如何零成本吃到 XDP 生态"的入口。
- **AI 用法**：本地 `web/md/186.md`；可 grep `umem`、`rte_mempool`、`busy poll`。此 PMD 后续即 DPDK 的 `net_af_xdp` 驱动，与 188（Suricata 文档 DPDK 章节）、196/197（PcapPlusPlus）形成 AF_XDP 三角互证。

## [188] Suricata 官方文档 20.5「eBPF and XDP」章节

- **是什么**：Suricata（OISF 的 IDS/IPS）readthedocs 官方文档的 eBPF/XDP 完整章节，本批信息密度最高的一篇；Suricata 用 eBPF 做三件事：**eBPF filter**（socket filter，如 VLAN/IPv4 黑名单）、**eBPF load balancing**（可编程负载均衡，替代 RSS）、**XDP bypass**（最早阶段丢包/直通）。
- **核心内容**：全流程可操作——编译（`CC=clang ./configure --enable-ebpf --enable-ebpf-build`）、bypass 规则写法（`bypass` 关键字签名 + stream.bypass + TLS encryption-handling bypass）、`cluster_ebpf`/`cluster_qm`/`cluster_cpu` 三种负载均衡模式、XDP cpumap CPU redirect（含 xdp_monitor 输出样例）、pinned maps（/sys/fs/bpf/suricata-<iface>-<map>，配合 bpfctrl 外部管理 IP 黑名单、global_bypass 开关保 IPS 不中断）、Netronome 硬件 offload（xdp-mode: hw，需关 BUILD_CPUMAP/USE_PERCPU_HASH）。

## [190] Suricata bypass feature 博客（Stamus Networks）

- **是什么**：Eric Leblond（Stamus CTO、OISF 董事、Netfilter core team）2016-09-28 博客，宣布 bypass 特性合入 Suricata 3.2——上一代纯 eBPF 版 bypass（先于 XDP 版）的第一手设计说明，188/189 中 XDP bypass 的思想源头。
- **核心内容**：动机=攻击多发生在 TCP 会话开始，到达 stream.reassembly.depth 后 Suricata 不再检测，这些 flow 的包继续送进来纯属浪费；加密流同理。两级实现：**local bypass**（Suricata 内部跳过 streaming/detection/output）与 **capture bypass**（调用采集方法的旁路：NFQ 用 mark、AF_PACKET 用内核里的 eBPF hash table）；capture bypass 失败自动降级 local bypass，被 bypass 的 flow 用短超时（emergency established timeout）清理。规则层加 `bypass` 关键字，可按 flowbits 选择性放行 YouTube/Netflix 类流量。
- **亮点**：iperf/1500MTU 实测数字极具说服力——标准 IPS 669Mbps → local bypass 899Mbps → **NFQ bypass 39 Gbps**（58 倍），这是 eBPF bypass 价值的最常被引用论据。
- **AI 用法**：本地 `web/md/190.md`；grep `capture bypass`、`local bypass`、`39 Gbps`、`bypass; sid`。与 191（netdev 1.2 幻灯）是同一工作的会议/博客双版本。

## [191] The adventures of a Suricate in eBPF land（netdev 1.2 幻灯）

- **是什么**：Eric Leblond 在 netdev 1.2（东京，2016-10-06）的 41 页演讲全文（PDF 已转文本），Suricata×eBPF 的完整技术叙事——从 AF_PACKET fanout 负载均衡讲起，到 eBPF cluster、eBPF bypass 的实现细节，比博客 190 多出内核侧代码与踩坑实录。
- **核心内容**：①eBPF cluster=用户态可编程 hash 替代 RSS（Linux 4.3 起，Willem de Bruijn 实现），用 `setsockopt(PACKET_FANOUT_DATA)` 挂载；②对称哈希血泪史——kernel 4.2 引入非对称 flow hash 导致 TCP 重组乱序、4.6 修复；Intel XL710 硬件能对称但驱动不允许（Victor Julien 提补丁）；③bypass 实现=userspace 建 map + ELF 重定位问题（"Game Over"页）→ 切到 libbpf（当时还需作者自己打补丁才能网络可用）；④给出 kernel 侧 flow_table_v4 hash map 代码（`bpf_map_lookup_elem` + `__sync_fetch_and_add` 统计）与 userspace 超时清理循环；⑤IPv6 支持撞上 libbpf map offset 计算 bug，靠模仿 tc_bpf.c 绕过（Daniel Borkmann 指路）。
- **亮点**：实测 1-2Gbps 真实流量 1 小时，对比 stream depth 1MB/512KB 的 bypass 曲线；作者 fork 链接（regit/suricata ebpf-3.8、regit/linux libbpf-network-v5）是 eBPF 网络早期史的活化石。
- **对学习者的价值**：一份材料同时讲清 socket filter 挂载、map 重定位、libbpf 早期形态三个今日常被忽略的基础问题。
- **AI 用法**：本地 `web/pdf-txt/191.txt`；grep `flow_table_v4`、`bpf_object__open`、`BYPASSED_FLOW_TIMEOUT`、`PACKET_FANOUT`。

## [195] merbridge（repo: merbridge/merbridge）

- **是什么**：「Use eBPF to speed up your Service Mesh like crossing an Einstein-Rosen Bridge」——用 eBPF 加速 Istio/Linkerd/Kuma/OSM 四种 service mesh 的 CNCF landscape 项目（DaoCloud 主导）；Go 控制面（32 个 .go）+ 9 个 C 的 eBPF 程序；要求 kernel >= 5.7；一条 `kubectl apply -f all-in-one.yaml` 即装。最后提交 2025-02-19，**已归档/不活跃**（GitHub 上标注不再维护）。
- **解决什么**：sidecar 模式下 Pod 到 Envoy 走 loopback + iptables REDIRECT，每次进出都有 netfilter 开销和上下文路径拉长；merbridge 用 eBPF 把这条路径短路—— Pod 间通信直接点对点，同节点流量用 sockmap 零拷贝转发。
- **数据面路径**（bpf/ 目录实证）：`cgroup/connect4/6`（mb_connect.c——在 connect 阶段直接改写目的地址到对端 Pod 或本机 Envoy 15001/15006 端口，跳过 iptables）+ `cgroup/sendmsg/recvmsg/getsockopts`（DNS 查询重定向等）+ **sockops/sk_msg sockmap**（mb_sockops.c + mb_redir.c 的 `bpf_msg_redirect_hash` 同节点 socket 直通）+ tc（mb_tc.c）。纯 cgroup/syscall 层，不用 XDP。
- **价值**：是「eBPF 加速 service mesh」这个品类里代码最易读的实现（每个 hook 一个文件、命名清晰），比 Cilium 体积小两个数量级；配合 194（Calico eBPF）可对照两种 K8s 数据面接管思路（Calico=接管 service/kube-proxy，merbridge=只短路 sidecar 路径）。
- **AI 用法**：本地 `repos/merbridge/merbridge/`；grep `cgroup/connect4`、`bpf_msg_redirect_hash`、`15006`、`mb_redir`。README 偏安装说明，原理要看代码与旧版 README-zh/博客。

## [199] ipx_wrap（repo: twisted-pear/ipx_wrap）

- **是什么**：极客玩具兼工程范本——用 **tc eBPF 程序把 IPX（Novell NetWare 古老协议）包封装在 IPv6 里传输**，让现代 Linux 与 NetWare 6.5 主机互通：egress BPF 把设定前缀内的 IPv6 包改写成 IPX 包上线，ingress BPF 反向还原；纯 C（30 余个 .c，含 vmlinux.h 新内核适配），最后提交 2026-04-03，明言"高度实验性、仅零星对 NetWare 6.5 测过"。
- **核心设计**：IPX 无法直接配到接口上，于是发明了**地址编码方案**——IPX 地址 `<4B network>.<6B node=MAC>.<2B socket>` 编进一个特殊 32-bit 前缀的 IPv6 地址（node 部分转 EUI-64 填后 64 位、network 填 byte 5-8、socket 不进地址而用于选程序）；配套完整用户态小生态：`ipx_wrap_mux`（让客户端程序 bind IPX socket 收发包）、`ipx_wrap_ripd`（IPX 路由传播）、`ipx_wrap_sapd`（IPX 服务广播）、ipxping/ipxcat/ipxdiag/ipxtap 诊断工具与 spxtcp（IPX 上跑 TCP）。
- **亮点**：测试环境 Linux 6.18 + libbpf 1.4.6——2026 年还在维护的 BPF 代码（最新 commit 就是适配新 vmlinux.h 的编译 flag）；用 tc 包改写做协议网关是 BPF 包处理能力（bpf_skb_store_bytes 级改写）的极限演示。
- **数据面路径**：**tc hook**（egress+ingress 各一个程序，非 XDP/sockmap）。
- **AI 用法**：本地 `repos/twisted-pear/ipx_wrap/`；grep `ipx_wrap_kern.c`、`tc`、`EUI-64`、`vmlinux.h`。学习者价值：小型、自包含、现代 CO-RE 风格的 tc 包改写参考实现，比大厂代码易读得多。
