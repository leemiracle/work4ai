# 第5章 程序类型与挂载点全景

> 本章导读：本章回答"eBPF 程序到底挂在哪里、怎么被触发、拿到什么、能干什么、返回什么"。前置：第 3 章 Verifier（白名单裁剪的另一半）、第 4 章 Maps。读完你能：①按需求（包处理/追踪/安全策略）选对 program type 与挂载点；②对任何一类程序说出它的 context 类型、helper 白名单入口与返回值语义；③看懂 libbpf SEC 名与 bpf link 两代 attach 方式的演进；④避开选型与版本代差的大坑。

## 5.1 直觉层

**比喻：program type 是"岗位合同"，不是"方言"。** eBPF 指令集只有一套（第 2 章），30 多种 program type 并不是 30 个虚拟机，而是同一批"劳动力"（同一段 BPF 字节码）与内核签订的 30 多种岗位协议。签给网卡收包现场（XDP），拿到的材料是裸包数据（`struct xdp_md`）；签给 kprobe 断点现场，拿到的是 CPU 寄存器现场（`struct pt_regs`）；签给 tc 分类器，拿到的是带完整元数据的包（`struct __sk_buff`）。**岗位合同钉死三件事**——这正是 David Miller 在 xdp-newbies 经典教程里钉版的定义："program type 在 `bpf_load_program()` 时指定，决定：①传入入口函数的 context 类型；②可用的 helper 子集；③返回值语义"（[id=20]）。

**为什么会有 30+ 种？** 因为内核里可编程的现场本来就有 30 多种语义各异的挂载点，而 verifier 必须对每种现场做不同的安全证明。这套绑定在内核侧的实现是 `struct bpf_verifier_ops` 的三个回调——`get_func_proto`（该类型允许调用哪些 helper）、`is_valid_access`（context 结构里哪些字段可读可写）、`convert_ctx_access`（把对公开 context 结构的访问改写成内核真实内部结构的偏移）——定义在 `net/core/filter.c`（[id=39]；digests/11-内核源码入口.md [270]）。换言之：**你选一个 program type，就是在内核里选一套校验器人格**。网络类类型的校验器在 `net/core/filter.c`，tracing 类在 `kernel/trace/bpf_trace.c`（digests/11 [270][271]）。

```mermaid
flowchart TB
    A["C 源码<br/>SEC(\"xdp\") / SEC(\"kprobe/do_unlinkat\")"] --> B["LLVM 编译<br/>按 section 名摆放程序"]
    B --> C["libbpf 扫 ELF section_defs[]<br/>推断 prog_type + expected_attach_type"]
    C --> D["BPF_PROG_LOAD syscall<br/>attr.prog_type 指定类型"]
    D --> E["verifier 按类型查<br/>bpf_verifier_ops 三回调<br/>context 校验 + helper 白名单"]
    E --> F["JIT 编译"]
    F --> G["attach 到挂载点<br/>kprobe 断点 / 驱动 XDP / tc / cgroup"]
    G --> H["事件触发 → 内核现场调用<br/>context 指针作 R1 传入"]
```

图中最容易被初学者忽略的一环是 C→D：**你从不在 C 代码里写 `BPF_PROG_TYPE_XDP` 这个枚举**，是 libbpf 根据 ELF section 名替你填的（`repos/libbpf/libbpf/src/libbpf.c` 的 `section_defs[]` 表，L10840 起）。这也是第 3 章 verifier 与本章的接口：verifier 拒绝你程序的第一行报错，往往就源于类型三绑定里某一条没对上。

## 5.2 原理层

### 5.2.1 两级类型：prog_type 与 attach_type 的拆分

UAPI 里类型其实有两层（`include/uapi/linux/bpf.h`，digests/11 [263]）：`enum bpf_prog_type`（程序类型）+ `enum bpf_attach_type`（挂载类型）。早期一个 prog_type 只有一个挂载语义；后来一个 prog_type 长出多个 attach 点，成了常态。两个极端例子（一手来自 libbpf.c SEC_DEF 表）：

- `BPF_PROG_TYPE_TRACING`（5.5 引入，[id=22] L135）一个类型覆盖 `fentry`/`fexit`/`fmod_ret`/`tp_btf`/`iter` 等 attach 点（libbpf.c L10882-L10897）；
- `BPF_PROG_TYPE_CGROUP_SOCK_ADDR`（4.17 引入时叫 socket binding，[id=22] L127）在 2026 年的 libbpf 里挂了 18 个 attach 点：bind4/6、connect4/6/unix、sendmsg4/6/unix、recvmsg4/6/unix、getpeername4/6/unix、getsockname4/6/unix（libbpf.c L10928-L10949）。

**选型的最小心智模型：先按"挂载域"选定大类（网络/追踪/cgroup/结构体替换），再在大类内按触发时机选 attach 点。**

### 5.2.3 fentry/fexit vs kprobe：BTF 依赖与安全模型差异

两者都能"在内核函数入口执行"，但机制与代价完全不同：

| 维度 | kprobe (KPROBE, 4.1) | fentry/fexit (TRACING, 5.5) |
|---|---|---|
| 挂载机制 | 动态断点（int3 注入），执行绕经 kprobe trampoline | BPF trampoline：把对目标函数的直接调用点改为经 trampoline 跳转（x86 JIT 用 poke descriptor 做 live-patch 式打补丁，digests/11 [272]） |
| BTF 依赖 | 无 | **硬依赖**：SEC 宏带 `SEC_ATTACH_BTF` 标志（libbpf.c L10884），加载时需按函数名解析 BTF_ID 拿到签名；BTF 本身 4.18 引入（[id=22] L83） |
| 参数读取 | 不能直接解引用，必须 `bpf_probe_read_kernel()` 先把内存拷上栈（[id=45] 第 7 节反例：直接解引用 ctx->rdi 会 "R1 invalid mem access"） | 参数即强类型 C 变量，**直接可读**（编译器按 BTF 签名生成取参代码） |
| 返回值 | kretprobe 单独挂出口，读 RAX 同样要 probe_read | fexit 天然拿到出口参数+返回值；fmod_ret 还能改写返回值 |
| 开销 | 断点陷阱 + 上下文保存较重 | 近零开销 trampoline 直跳 |
| 可挂对象 | 几乎任意内核地址（含内联展开后的符号） | 仅 BTF 里登记、被 trampoline 支持的函数集 |
| 稳定性 | **挂载点不是 ABI**（[id=11]：kprobe 挂载点/被直接调用的内核函数/BTF_ID 标记函数都不是稳定 ABI——函数改名/内联/删除即断） | 同样不是 ABI，但 BTF+CO-RE 让"签名漂移"在加载期暴露（重定位失败）而非运行期崩 |

选型口诀：内核有 BTF（现代发行版默认开 `CONFIG_DEBUG_INFO_BTF`，pahole≥1.16，[id=12]）就优先 fentry/fexit；老内核或挂非函数地址才回 kprobe。

### 5.2.4 attach 方式三代演进

**第一代（2014-2019，各挂载点各找各的门）**：socket 用 `setsockopt(SO_ATTACH_BPF)`（[id=38] L187）；tc 用 `tc filter add ... bpf da` 走 iproute2（[id=14]）；kprobe/perf 用 `perf_event_open()`+ioctl 挂 BPF fd。共同痛点：attach 是"一次性动作"，程序生命周期与挂载动作耦合，进程退出程序即卸载（[id=44]），没有原子替换。

**第二代（libbpf SEC 自动推断）**：C 源码里写 `SEC("xdp")`/`SEC("fentry/tcp_connect")`，libbpf 打开 ELF 后按 `section_defs[]` 表推断 prog_type + expected_attach_type + attach 回调（libbpf.c L10840 起，本章 5.2.1/5.2.2 的表就是它的直读）。同一个 section 名带 `+` 后缀表示可附加参数（如 `kprobe/do_unlinkat`）；`.s` 后缀是 sleepable 变体（如 `fentry.s+`、`lsm.s+`，可在可睡眠上下文调用，libbpf.c L10846/L10887-L10893）。这套宏的前身在 2017 年的 xdp-newbies 教程里就是 `SEC()` 宏+三个特殊 section（maps/license/version，[id=19]），语义沿用至今。

**第三代（bpf link）**：`bpf()` syscall 的 `BPF_LINK_CREATE` 子命令（[id=8] syscall 清单；libbpf 封装 `bpf_link_create()`，`repos/libbpf/libbpf/src/bpf.c` L791）把"挂载关系"本身变成一个 fd 对象（link 也是 fd，digests/11 [267]）。收益：①程序生命周期独立于加载进程——link 持有引用，可 pin 到 bpffs 跨进程存续；②`bpf_link__destroy()` 干净卸载（libbpf 加载五步的最后一步，[id=45]）；③原子替换程序不再需要先 detach 再 attach。`xdp`/`tcx`/`lsm`/`fentry` 等主流 attach 点在 libbpf 里都走 link 路径（section_defs[] 中 SEC_ATTACHABLE/SEC_ATTACHABLE_OPT 标志，libbpf.c L10841-L10959）。tcx（`tcx/ingress`、`tc/ingress` 为其别名，libbpf.c L10863-L10866）与 netkit 是 6.x 对 tc 挂载的 link 化重建，旧的 `SEC("tc")`/`SEC("classifier")` 已被 libbpf 源码注释标为 deprecated（L10867-L10868）。

**verifier 视角收尾**：无论哪一代，attach 语义最终都体现在三绑定的校验上——第 3 章 verifier 按你声明的类型裁剪世界，第 6 章 helper 体系则给出每个类型可用的完整函数清单，两章与本章构成"声明—校验—能力"闭环。

## 5.3 实践层

**第一步：摸清本机能力。** 三个命令（[id=15] KNOWN ISSUES 节推荐）：

```bash
bpftool prog                    # 列出本机已加载的全部程序（类型/名称/uid/map ids）
bpftool feature probe           # 一键探测本机内核支持的 prog/map/helper 全集
bpftool feature probe unprivileged   # 同上，但探测非特权用户可用的子集
```

权威枚举底册则是内核 UAPI 头 `include/uapi/linux/bpf.h` 的 `enum bpf_prog_type` / `enum bpf_attach_type`（digests/11 [263]），以及 docs.ebpf.io 的 program-type 逐类型页（[id=8] L55-96）。

**第二步：写一个最小程序，体感三绑定。** 同一个"统计包数"逻辑，换三个类型写一遍（编译命令与 libbpf 五步加载流程见 [id=45]：`bpf_object__open_file` → `bpf_object__find_program_by_name` → `bpf_object__load` → `bpf_program__attach` → `bpf_link__destroy`）：

```c
/* 例 1：XDP——context 无 skb，返回 xdp_action */
SEC("xdp")
int xdp_count(struct xdp_md *ctx) { /* 计数 */ return XDP_PASS; }

/* 例 2：socket filter——context 是 __sk_buff，返回字节数 */
SEC("socket")
int sock_count(struct __sk_buff *skb) { /* 计数 */ return skb->len; }  /* 全收：返回 skb->len（[id=20]） */

/* 例 3：fentry——BTF 签名直读参数，返回 0 */
SEC("fentry/tcp_v4_connect")
int BPF_PROG(tcp_connect, struct sock *sk, struct sockaddr *uaddr) { /* sk 直接可用 */ return 0; }
```

注意例 3 用的 `BPF_PROG` 宏（`repos/libbpf/libbpf/src/bpf_tracing.h`）——它按 BTF 签名把前几个参数展开为强类型形参，这就是 5.2.3 表里"参数直接可读"的落地形态；kprobe 版本则要 `struct pt_regs *ctx` + `PT_REGS_PARM1(ctx)` + `bpf_probe_read_kernel()` 拷贝（[id=45]）。

**第三步：挂载。** 现代 libbpf 程序里 `bpf_program__attach()` 系列自动完成；命令行手工挂载：

```bash
ip link set dev eth0 xdp obj prog.o sec xdp     # XDP
tc filter add dev eth0 ingress bpf da obj prog.o sec cls  # tc（direct-action，[id=14]）
bpftool net attach xdp name xdp_count dev eth0  # link 时代的命令行入口
```

**本地示例仓**：`repos/lizrice/ebpf-beginners/` 三例正好对应三条主干线——`hello.py`（kprobe 挂 execve）、`ebpf.py`（kprobe 挂 clone+BPF_HASH 计数，注意 `get_syscall_fnname()` 处理 `__x64_` 前缀的跨版本写法）、`packet.py`（XDP 挂 eth0 按协议号计数）；该仓是 BCC Python 路线（旧式但最短路径），Go 路线见 `lizrice/libbpfgo-beginners`（[id=48] digest）。

## 5.4 深水区与坑

1. **XDP vs tc 选型不是性能崇拜**。Oracle 实战篇的论证（[id=43] digest）：需要包最终上送协议栈、或需要 ingress/egress 对称处理 → 选 tc；只在最早期丢包/转发才选 XDP。另注意 tc ingress qdisc 本身无排队能力（需 redirect 到 ifb 或用 policing，[id=14]）；tc 侧最佳实践是"只挂一个 classifier 干完所有匹配+改包"（[id=14]）。
2. **generic XDP 不是 XDP**。非 native 驱动时 XDP 走 `net/core/dev.c` 的 generic 路径，**发生在 skb 分配之后**，拿不到"省 sk_buff 分配"这个 XDP 的核心收益（[id=38] digest；digests/11 [276]）。生产选型先 `ethtool -i` 确认驱动支持。
3. **helper 可用性错配是 verifier 拒载高发区**。同一个 helper 在 XDP 里可用、在 socket filter 里未必（例如改包族）；"某类型能调什么"的真源是内核五处（[id=15] KNOWN ISSUES：`net/core/filter.c` 按类型的 `bpf_func_proto` switch-case、`kernel/trace/bpf_trace.c`、`kernel/bpf/verifier.c` 的 check_map_func_compatibility 等），文档可能滞后于内核。
4. **追踪挂载点不是 ABI**（[id=11] Design QA 明文）：kprobe 挂载点、被直接调用的内核函数、BTF_ID 标记函数都不在稳定 ABI 列表内；稳定的是指令集/helper 集/返回码。内核升级函数改名，kprobe 程序就会 attach 失败——这正是 CO-RE/BTF 线存在的理由。
5. **版本表会骗人：两个年代断层**。①bcc kernel-versions 矩阵（[id=22]）停在 6.x 早期，Program types 表止于 SYSCALL（5.15）——**NETFILTER 等 6.x 新类型不在表里**（[id=8] L65 可证其存在），查新类型去 docs.ebpf.io 或 UAPI 头；②`bpf(2)` man page 有意只覆盖基础集，KPROBE/SCHED_CLS/SCHED_ACT 标注 "To be documented"（[id=13]）——man 页查不到不等于不存在。
6. **教材年代口径**。本章主骨架 Oracle 六部曲基于 Linux 4.14（[id=38]）：那时没有 fentry/trampoline（5.5）、没有 bounded loop（5.3）、类型只有约 24 种；kernel 6.2.11 已达 33 种（[id=45] 附录 B），2026 年主线更多。读老教材时用 [id=22] 的版本矩阵校准每个论断。
7. **GPL 分层**：license 字符串必须 GPL 兼容才能调 gpl_only helper（[id=13]）；tracing 类程序整体须 GPL，网络类可专有（[id=45]）——闭源商业程序避开 fentry/kprobe 系。
8. **sleepable 不是免费的**：`.s` 后缀变体（如 `fentry.s+`、`usdt.s+`，libbpf.c L10846/L10862）允许在可睡眠上下文运行，但挂载点本身必须支持 sleepable，乱用照样拒载。
9. **SEC 名代差**：`SEC("tc")`/`SEC("classifier")`/`SEC("action")` 已被 libbpf 注释标 deprecated，改用 `tcx/ingress`/`tc/egress`（libbpf.c L10863-L10868）；老代码迁移时注意 `tc` section 现在是 tcx 语义的别名。
10. **"程序类型数"本身是口径问题**：30（[id=22] 表）/约 33（6.2.11，[id=45] 附录 B）/"约 30"（[id=8]）——按内核版本与是否计入 attach 变体而不同，写文档引用时必须带版本。

## 5.7 AI agent 用法

本章可当"类型速查字典"检索，五条配方：

1. **查某类型的 context/触发/返回值** → grep `BPF_PROG_TYPE_XDP|SCHED_CLS|SOCK_OPS` → 先命中 web/md/22.md 拿版本，再 web/md/38.md 拿四问细节；返回值语义 grep `verdict|xdp_action|TC_ACT_|__SK_PASS`。
2. **查某 SEC 名合法与否/对应什么类型** → grep `SEC_DEF` → `repos/libbpf/libbpf/src/libbpf.c` L10841-10959 一表定论（含 deprecated 标注与 .s 变体）。
3. **查某类型能否用某 helper** → 先 `web/md/15.md` grep `bpf_<name>` 拿语义；可用性存疑时按 [id=15] 指路 grep 真源（filter.c/bpf_trace.c 的 func_proto case 表），或直接给用户 `bpftool feature probe` 命令。
4. **选型问题（XDP vs tc vs cgroup）** → grep `XDP_DROP|direct-action|BPF_CGROUP_INET_INGRESS` → 本章 5.2.2 四域表 + 5.4 坑 1/2；cgroup 侧重定向需求 grep `CGROUP_SOCK_ADDR`。
5. **fentry vs kprobe 决策** → grep `fentry|BPF_PROG|bpf_probe_read_kernel|SEC_ATTACH_BTF` → 本章 5.2.3 对比表 + web/md/45.md 第 7 节反例；BTF 可用性判断 grep `CONFIG_DEBUG_INFO_BTF` → web/md/12.md。
