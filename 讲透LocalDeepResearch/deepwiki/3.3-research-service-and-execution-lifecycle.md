## Research Request Flow

 The research execution process begins when a user submits a query through the web interface or API. The request flows through multiple layers before spawning a background thread.

 
### Entry Point: HTTP Endpoint

 The primary entry points for starting research are the web-based `start_research` route and the `api_start_research` endpoint.

### Parameter Resolution and Settings Snapshot

 The endpoint resolves parameters using a priority hierarchy: request body → database settings → defaults. A complete settings snapshot is captured before thread spawning to ensure thread isolation.

 
| Parameter | Resolution Priority | Default |
|---|---|---|
| model_provider | Request → DB (llm.provider) | "ollama" |
| model | Request → DB (llm.model) | None (resolved via DB) |
| search_engine | Request → DB (search.tool) | "searxng" |
| iterations | Request → DB (search.iterations) | 5 |
| questions_per_iteration | Request → DB (search.questions_per_iteration) | 5 |
| strategy | Request → DB (search.search_strategy) | "source-based" |

 The settings snapshot is created using `SnapshotSettingsContext`. This snapshot is critical because background threads operate in an isolated context where they cannot safely access the main Flask request or session objects.

## Queue vs Direct Execution Modes

 Local Deep Research supports two execution modes to manage concurrent research processes: **direct mode** and **queue mode**. The mode is determined by the `app.queue_mode` setting and per-user concurrency limits.

 
### Mode Selection Logic

 
```

```

 Sources: [src/local_deep_research/web/queue/processor_v2.py145-181](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/queue/processor_v2.py#L145-L181) [src/local_deep_research/web/queue/processor_v2.py297-513](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/queue/processor_v2.py#L297-L513)

 
### Direct Mode Execution

 In direct mode, research starts immediately if slots are available. The decision is made synchronously during request handling:

 
 - **User Critical Lock**: To prevent race conditions during concurrent submissions, a per-user lock is acquired via `_get_user_critical_lock(username)` [src/local_deep_research/web/queue/processor_v2.py95-104](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/queue/processor_v2.py#L95-L104)
 - **Active Count Query**: The system counts `UserActiveResearch` records for the user.
 - **Immediate Start**: If the count is below `app.max_concurrent_researches`, `start_research_process()` is called to spawn the thread [src/local_deep_research/web/services/research_service.py60-61](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/services/research_service.py#L60-L61)
 
 
### Queue Mode Execution

 In queue mode, research is added to a queue and processed by `QueueProcessorV2`:

 
 - **Queue Addition**: Creates a `QueuedResearch` record [src/local_deep_research/web/routes/research_routes.py204-215](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/routes/research_routes.py#L204-L215)
 - **Processor Loop**: The background thread runs `_process_queue_loop()` [src/local_deep_research/web/queue/processor_v2.py297-310](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/queue/processor_v2.py#L297-L310)
 - **Spawn Retries**: If a thread fails to spawn, the system retries up to `SPAWN_RETRY_LIMIT` (3) before marking the research as failed [src/local_deep_research/web/queue/processor_v2.py40-41](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/queue/processor_v2.py#L40-L41)

## Progress Tracking and Callbacks

 Research progress is tracked through a callback mechanism that reports updates from the search system to the web interface via SocketIO.

 
### Progress Callback Implementation

 The progress callback performs several critical functions:

 
 - **Termination Check**: Periodically checks for termination flags using `is_research_active()`. If research was terminated by the user, it raises `ResearchTerminatedException` [src/local_deep_research/web/routes/globals.py68-70](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/routes/globals.py#L68-L70)
 - **Milestone Logging**: Records significant events using `log_for_research()` [src/local_deep_research/utilities/log_utils.py26](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/utilities/log_utils.py#L26-L26)
 - **Throttled SocketIO Emission**: Ensures emissions don't exceed `_EMIT_THROTTLE_SECONDS` (200ms) to prevent UI flooding [src/local_deep_research/web/services/research_service.py43-47](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/services/research_service.py#L43-L47)

## Research Completion and Cleanup

 Research completion involves updating database records and cleaning up tracking structures.

 - **Save Strategy**: The specific strategy used (e.g., `source-based`) is saved via `save_research_strategy()` [src/local_deep_research/web/services/research_service.py131-171](https://github.com/LearningCircuit/local-deep-research/blob/4a6a9088/src/local_deep_research/web/services/research_service.py#L131-L171)
