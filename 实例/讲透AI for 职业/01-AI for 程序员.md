# 01 — AI for 程序员：从码农到架构师

> 程序员是最早被 AI "正面撞击"的职业。GitHub Copilot 2023 调研显示，**88% 的开发者表示效率提升，平均提速 55%**；而 2024 年后 Cursor、Claude Code、aider、Cline 把这个数字继续往上推。但越是深入一线就越清楚——**AI 写 CRUD 像神，搞架构像实习生，调生产 bug 像瞎子**。本篇不是吹 AI 取代程序员，而是诚实地拆解：程序员 6 大任务里哪些交给 AI、哪些必须自己扛，以及怎么把 AI 编进日常 workflow。
>
> **本篇是应用指南**，没有实验脚本——所有 prompt 都可直接复制到 Cursor / Claude Code / ChatGPT 使用。配套总框架见 [`00-AI for 所有职业.md`](00-AI for 所有职业.md)。

---

## 核心论断

$$
\boxed{\text{程序员综合提效 } 2\text{-}3\times\text{，但架构 / 复杂调试 / 跨团队沟通仍需人扛}}
$$

**朴素直觉**：AI 代码生成这么强，程序员要失业了。

**精确视角**：AI 把"**键盘时间**"压缩了一半以上，但软件工程里**真正值钱的是判断、是权衡、是上下文**——这些恰恰是 AI 当前的短板。所以结局不是"失业"，而是**会拆任务、会用 AI、会读代码的程序员，淘汰只会敲 CRUD 的程序员**。提效 2-3× 是真实的，但它落在谁头上、省下的时间拿去做什么，决定了你是被 AI 放大还是被 AI 取代。

---

## 第 1 节：程序员的 6 大任务 + AI 适配度

按 [00 篇的 5 维度评估器](00-AI%20for%20所有职业.md#2-任务自动化评估器5-个维度)（结构化 / 重复性 / 容错率 / 创意 / 模糊），给程序员最核心的 6 个任务打分：

| 任务 | AI 适配度 | 等级 | 为什么 |
|------|:----:|:----:|------|
| **写新代码**（CRUD / 样板 / 单测） | **0.89** | 高 | 输入输出明确，模式重复，容错可改 |
| **代码审查**（风格 / 安全 / 重复） | **0.78** | 中高 | 有明确规则，但需结合上下文权衡 |
| **调试 bug**（单机、可复现） | **0.70** | 中 | 错误堆栈明确时强，根因分析需人 |
| **系统调试**（生产 / 多服务 / 性能） | **0.45** | 低 | 需要真实环境、监控、时序数据 |
| **架构设计**（选型 / 分层 / 演进） | **0.40** | 低 | 需要全局权衡、长期视角、业务理解 |
| **需求沟通**（澄清 / 拉通 / 谈判） | **0.30** | 极低 | 需要人际情商、政治、隐含意图 |

**两个反直觉点**：

1. **"写代码"是程序员最容易被 AI 替代的部分，而它恰恰是入门岗 80% 的工作**。这解释了为什么 junior 岗的冲击最大。
2. **"沟通"得分最低，但它是 senior 以上 50% 的时间消耗**。AI 帮不上忙的部分，才是程序员的真正护城河。

## 第 2 节：高潜力任务详解（AI 主场）

### 2.1 写新代码（0.89）—— AI 最强主场

**推荐工具**：

- **GitHub Copilot**：IDE 内补全，适合样板代码、单测、SQL
- **Cursor**：带 Agent 模式，可跨文件改、自动跑命令、多文件重构
- **Claude Code**：CLI Agent，适合中等复杂度任务、读懂整个 repo
- **aider**：开源终端 Pair，git 友好，每次改动自动 commit
- **Cline**：VS Code 插件，可执行命令、可规划，长任务自动化

**推荐工具栈一句话**：日常补全用 Copilot，中等任务用 Cursor，复杂跨文件用 Claude Code，开源爱好者用 aider。

**Prompt 模板（真实可用）**：

```text
我在一个 FastAPI 项目里，需要加一个「用户收藏文章」的接口。
要求：
1. POST /articles/{article_id}/favorite，需要鉴权（项目用的是 deps.get_current_user）
2. 用 SQLAlchemy 2.0 风格（项目已有 Base、async session）
3. 同一用户对同一文章重复收藏幂等（返回已收藏）
4. 返回 {"favorited": bool, "count": int}
5. 加对应 pytest（用项目里的 conftest.py 里的 async client）

先只给 models/favorite.py、api/favorites.py、tests/test_favorites.py 三个文件，
不要改其他文件。每个文件前用 ```language 标注。
```

> 这个 prompt 好在哪：**给技术栈、给约束、给边界、给验收标准**。AI 不需要猜，直接出可用代码。差的 prompt 是"帮我写个收藏功能"——AI 只能猜你用什么框架。

**实战案例**：写一个 CRUD 接口，手写约 40 分钟（含 model / schema / router / test）。用 Cursor Agent + 上面这个 prompt，5 分钟出第一版，再花 10 分钟 review + 改边界条件。**净提效约 3×**。

---

### 2.2 调试 bug（0.70）—— 错误堆栈是 AI 的燃料

**推荐工具**：

- **Claude（Sonnet/Opus）**：超长上下文，能吃下整个错误链 + 相关代码
- **GPT-4 / o 系列**：推理强，适合复杂逻辑 bug
- **Cursor / Claude Code**：直接在 repo 里调试，可读文件、跑测试

**Prompt 模板**：

```text
我在跑 pytest tests/test_checkout.py::test_apply_coupon 时报错，堆栈如下：

[把完整 Traceback 粘进来，包括最后 10-20 行 frame]

相关代码：
- app/services/coupon.py 的 apply_coupon 函数：
[贴代码]
- app/models/order.py 的 Order 类：
[贴代码]

我的预期：传 coupon_code="SAVE10"，订单满 100 应减 10。
实际：报 KeyError: 'discount_type'。

请按以下顺序回答：
1. 一句话定位根因（哪个文件哪一行）
2. 为什么会出错（数据流追踪）
3. 最小修复 patch（用 diff 格式）
4. 这个 bug 是否暴露了更大的设计问题（如字段缺失校验）
```

> 关键：**给完整 Traceback + 相关代码 + 预期 vs 实际**。AI 调试的准确率，90% 取决于你贴的上下文够不够。

**实战案例**：一个并发场景下的 race condition，报错堆栈 30 行。Claude 在看完堆栈 + 两段相关代码后，第一轮就指出"是 `cache.get` 和 `cache.set` 之间没有锁"，给了 `with cache.lock(...)` 的修复，外加一句"建议把这个模式抽成装饰器，你项目里另外两处也有同样问题"。**省了我两小时**。

---

### 2.3 代码审查（0.78）—— AI 是不知疲倦的 reviewer

**推荐工具**：

- **CodeRabbit**：PR 自动 review，集成 GitHub/GitLab，免费层够用
- **Claude / GPT-4**：贴 diff 人工审查，质量最高
- **Cursor / Copilot**：IDE 内边写边审

**Prompt 模板（PR review）**：

```text
你是资深 code reviewer。下面是一个 PR 的 diff，请审查：

[贴 git diff，建议限制在 500 行以内]

请按以下维度评分（1-5）并给具体修改建议：
1. 正确性：逻辑有没有 bug、边界条件、并发问题
2. 安全性：SQL 注入 / XSS / 鉴权缺失 / 敏感信息泄露
3. 可读性：命名、复杂度、是否过度抽象
4. 测试覆盖：关键路径有没有测，测的是不是行为而非实现
5. 性能：N+1 查询、不必要的循环、内存泄露

输出格式：
- 🔴 Must fix（合并前必须改）
- 🟡 Should fix（建议改，不阻塞）
- 🟢 Nit（可选）
每个问题给：文件:行号 + 问题描述 + 建议改法（代码片段）。
```

> AI review 的甜区：**重复性检查（命名、安全、N+1）远比人稳定**。苦区：业务语义正确性、产品逻辑——它看不懂"这个优惠券叠加规则对不对"。

**实战案例**：团队接 CodeRabbit 后，PR 平均轮次从 3.2 降到 1.8——因为命名、漏测、明显安全问题 AI 第一轮就拦了，人工 review 只剩业务逻辑。**reviewer 时间节省约 50%**。

## 第 3 节：低潜力任务详解（AI 不行的地方）

### 3.1 架构设计（0.40）—— 需要全局视野 + 权衡

AI 能给你 5 种消息队列的对比表，但**回答不了"你这个 50 人团队、三年演进、峰值 QPS 5000 的场景，该选 Kafka 还是 RabbitMQ"**。

为什么？

- **架构是约束下的取舍**：成本、人力、运维能力、未来 2 年路线——这些 AI 看不到。
- **架构是组织问题**：康威定律说"系统结构反映组织结构"，AI 不认识你的团队。
- **架构是演进的艺术**：今天的"正确"决定，三年后可能是技术债。这需要预判，不是查文档。

AI 在架构上的真实价值：**当你的副驾驶**——帮你列选项、画对比、写 ADR 草稿，但**拍板的是你**。

---

### 3.2 系统调试 / 生产排障（0.45）—— 需要真实环境上下文

生产环境的 bug 长这样：

- 错误只在凌晨 3 点高峰期偶现，本地无法复现
- 涉及 5 个微服务 + Redis + MySQL + 一个第三方支付网关
- 监控显示 P99 飙到 8s，但日志被采样丢了关键帧
- 根因可能是上周另一个团队的发布

**AI 在这里几乎帮不上忙**，因为：

1. **它没有你的监控 / 日志 / trace 权限**——除非你把全部贴给它，但那可能违反合规
2. **生产上下文是动态的**：线上正在发生的事，AI 静态的 prompt 接不住
3. **根因常在"两个系统的接缝处"**：AI 对单个系统懂，对"两个系统交互时的 race"无能为力

AI 在这里能做的：**帮你事后复盘**——你贴时间线、贴日志片段、贴变更记录，让它帮你整理 RCA（根因分析）报告。这是有价值的，但**排障本身仍然是人的活**。

---

### 3.3 需求沟通（0.30）—— 需要人际情商

PM 说"这个功能很简单，就加个按钮"。背后的真实意图可能是：

- 老板明天的 demo 要用，必须快
- 这个按钮背后牵涉权限体系重构，PM 不知道
- 客户合同里写了，不做要赔钱
- 另一个团队也想要类似功能，要协调

**这些信息，没有一个会写进 PRD**。能不能问出来、能不能 push back、能不能在 3 个团队之间拉通——这是 senior 工程师的核心能力，**AI 的情商目前是 0**。

AI 能帮的只有**翻译**：把技术方案翻译成 PM 听得懂的话、把 PRD 翻译成技术任务拆解。但**对话本身，必须人去**。

## 第 4 节：实战工作流改造（5 步）

把 AI 编进日常，不是"打开 ChatGPT 问一句"，而是改造**每个环节**。

### 步骤 1：写代码前，先问 AI 拆任务

```text
我要实现 [功能描述]。项目背景：[2-3 句]。
请帮我：
1. 拆成 3-7 个可独立提交的小步骤（每步一个 commit）
2. 标出哪些步骤有依赖、哪些可并行
3. 标出哪些步骤风险高（改共享代码 / 涉及迁移）
4. 给每步一个验收标准（怎么算 done）
```

**收益**：拆解质量直接决定后续 AI 生成代码的质量。**任务定义不清，是 AI 出错的最大来源**。

### 步骤 2：写代码时，AI 生成 + 人审

- 简单部分（model / DTO / 单测）：让 AI 全自动，扫一眼即可
- 中等部分（业务逻辑）：AI 出草稿，人工改边界
- 复杂部分（算法 / 并发）：AI 当顾问，人主写

**原则**：**永远不要把 AI 输出当终点，当成"高级 Stack Overflow 答案"**——读完、理解、改完，才提交。

### 步骤 3：写完后，让 AI 审一遍

提交前，把 diff 喂给 Claude，用 [2.3 的 review prompt](#23-代码审查078--ai-是不知疲倦的-reviewer)。**自己写的代码，自己最看不出问题**——AI 这个"不知疲倦的同事"正好补位。

### 步骤 4：卡住时，AI 当结对伙伴

不要直接问"这 bug 怎么修"。用**橡皮鸭 + AI** 模式：

```text
我遇到一个问题：[现象]。
我目前的假设是 [你的猜测]，理由是 [你的依据]。
我已经试过 [你试过的方案]，结果是 [结果]。
请：
1. 评估我的假设是否合理
2. 列出 3 个其他可能的根因，按概率排序
3. 对每个根因，给一个最小验证步骤（如何确认/排除）
```

> 强迫自己先思考，AI 才能真正帮你。直接要答案，你会变蠢。

### 步骤 5：定期让 AI 审技术债

每周 / 每个 sprint，挑一个模块，让 AI 做一次健康检查：

```text
这是 app/payments/ 目录的全部代码 [贴或让 Agent 自己读]。
请以架构师视角输出一份健康报告：
1. 复杂度热点（哪个文件/函数最该重构）
2. 重复代码（DRY 违规）
3. 耦合问题（哪些模块该解耦）
4. 测试薄弱点（哪些关键路径没测）
5. 给一个"如果只能做 3 件事，先做什么"的优先级清单
```

**收益**：技术债是渐进积累的，AI 帮你**定期 zoom out**，避免"温水煮青蛙"。

## 第 5 节：程序员的新护城河

AI 时代，**会写代码不再是稀缺能力**。稀缺的是这四样：

### 护城河 1：系统思维

AI 能写函数，但**不能设计一个演进 3 年的系统**。能从业务目标倒推技术架构、能预判瓶颈、能在"现在够用"和"未来可扩展"之间找到平衡点的人，价值会**指数级上升**。

### 护城河 2：复杂 bug 调试

生产环境的多服务、多版本、多团队交叉 bug，**没有 AI 能替你扛**。这种能力来自：踩过足够多的坑、对系统行为有肌肉记忆、能在信息不全时做合理猜测。**老医生为什么值钱？因为他们见过太多病例。**

### 护城河 3：跨团队沟通

把技术方案翻译给 PM、把风险讲给老板听、在 3 个团队之间拉通一个标准——这些"软技能"在 AI 时代反而**变硬**了。因为硬技能（写代码）被 AI 平权了，软技能（让事情发生）成了差异化。

### 护城河 4：领域知识

懂金融的程序员、懂医疗的程序员、懂制造的程序员——**AI 懂通用代码，不懂你的业务**。领域知识 + 工程能力，是 AI 最难替代的组合。**深耕一个行业，比追 10 个新框架值钱。**

> 一句话：**从"会写代码的人"，升级成"懂业务、能架构、会沟通、会用 AI 的工程师"**。

## 第 6 节：风险与坑

### 坑 1：AI 代码"看似对，实际错"

AI 写的代码**长得像对的**——命名规范、有注释、能跑通 happy path。但边界条件、并发、异常路径常常是错的。**最危险的 bug，是那种让你产生"这就对了"错觉的代码。**

**对策**：AI 生成的代码，**必须配测试**。测试也是 AI 写的？那更要人读懂每一行。

### 坑 2：安全漏洞

AI 训练数据里有大量**不安全的代码**（Stack Overflow 上的老答案、过时教程）。它会"自信地"写出 SQL 拼接、硬编码密钥、不校验权限的接口。

**对策**：
- 关键路径必须过 SAST 工具（Semgrep / Snyk）
- 安全相关代码（鉴权、加密、支付）**人工逐行审**
- 把"安全检查"写进 [步骤 3 的 review prompt](#步骤-3写完后让-ai-审一遍)

### 坑 3：过度依赖 → 能力退化

长期让 AI 写代码、自己不思考，**调试能力和系统理解会悄悄退化**。等你遇到 AI 搞不定的 bug，会发现自己也搞不定了。

**对策**：
- **核心算法 / 关键路径，坚持手写**（哪怕慢）
- 每周留一段时间**不开 AI**，保持手感
- AI 给的代码，**先读懂再使用**，不懂的不提交

### 坑 4：上下文泄露

把公司代码贴给公网 AI，可能违反保密协议 / 数据合规。**生产数据、客户 PII、核心算法，永远不要出内网。**

**对策**：用企业版（Copilot Business / Cursor Business / Claude Enterprise）或本地模型（DeepSeek / Qwen / Code Llama）。

---

## 第 7 节：一句话总结

> **程序员是 AI 时代受益最大的职业之一，综合提效 2-3×：写 CRUD / 样板 / 单测（0.89）几乎全自动，代码审查（0.78）和单机调试（0.70）AI 当靠谱副驾；但架构设计（0.40）、生产排障（0.45）、需求沟通（0.30）仍是人的主场。GitHub Copilot 2023 调研：88% 开发者提速、平均 55%。新护城河不在"会写代码"，而在系统思维、复杂调试、跨团队沟通、领域知识。最大的风险不是 AI 取代你，而是你停止思考、能力悄悄退化——把 AI 当放大镜，而不是轮椅。**
