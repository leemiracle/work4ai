- **核心数据结构**：`App{opts,ctx,cancel,mu,instance}` 即全部生命周期状态（本地 app.go:L30-36）；中间件两函数类型 `Handler=func(ctx,req)(reply,err)` / `Middleware=func(Handler)Handler`（DW 2.3）。
- **核心算法/协议**：启动舞步（本地 app.go:L100-150）：每 server 双 goroutine——一个 `server.Start(octx)`、一个 `<-ctx.Done()` 后用 `context.WithoutCancel(octx)`+stopTimeout 优雅停（保证取消信号不杀停机流程，L103-112）；**wg.Wait 卡在 Start 与注册之间**（L113-119）确保所有 server 已开跑才向 registrar 注册 ServiceInstance——用 WaitGroup 消灭"已注册但没起来"窗口；`signal.Notify(SIGTERM/SIGQUIT/SIGINT)`（L42）转 `a.Stop()` 走 beforeStop→Deregister→cancel 全链。中间件侧：`selector.Builder` 的 Path/Prefix/Regex/Match 让日志/鉴权按 operation 选择性生效（健康检查免日志），失配直接放行 next handler（selector.go:L76-90, L126-135）。
- **设计模式与工程决策**：① recovery 中间件 defer 捕 panic→slog 栈→Kratos error，并把延迟写进 ctx 的 `Latency{}` key（recovery.go:L61-76）；② logging 支持 `Redacter` 接口做参数脱敏（logging.go:L121-129）；③ `internal/matcher` 用前缀排序+map 查表优化 operation→middleware 映射——热路径不跑正则。

- **一句话本质**：把微服务公约数压进 213 行 app.go 的 Go 骨架。

### ahujasid/blender-mcp
- **DeepWiki**：9 章；深读 2.2 Socket Server and Threading
- **架构模式**：三层桥：AI 平台（stdio 启 `uvx blender-mcp`）→ FastMCP server（`@mcp.tool()` 工具 + lifespan 单例 `BlenderConnection`）→ Blender addon（TCP localhost:9876 监听，DW 1-Overview）；核心工具仅四个：get_scene_info/get_object_info/execute_blender_code/get_viewport_screenshot，可选集成 PolyHaven/Sketchfab/Hyper3D/Hunyuan3D 需在 addon 面板填 key 开关。
- **核心数据结构**：本地 server.py:L31-39 `BlenderConnection` dataclass：host/port/sock + **`_lock: threading.Lock`**，注释直言"序列化 send+receive，否则第二条命令的响应会被读成第一条的，流一直错位直到 180s 超时"——一把锁定义整条协议。
- **核心算法/协议**：addon 三线程模型（DW 2.2）：server thread（socket 1s 超时轮询 running 旗标可优雅停）→ 每连接一个 client thread（8192 字节循环 recv，累加缓冲后 try `json.loads` 判完整，JSONDecodeError 继续等，addon.py:L130-173）→ **`bpy.app.timers.register(execute_wrapper, first_interval=0.0)`** 把命令排进 Blender 主线程下一帧（16-33ms），返回 None 只执行一次（L148-170）；server 侧 receive_full_response 对称地 try-parse 分段 JSON（本地 server.py:L66-120）——两端各自实现"以可解析为完整"的流式 JSON 判定，无长度前缀无分隔符。
- **设计模式与工程决策**：① 超时 180s 双端对齐，超时后置 sock=None 让下次调用重连而非当场重试（L162-167）；错误信息内嵌运维知识："blender -b 下命令永不执行，用 GUI 或 xvfb-run"（L167）；② `@telemetry_tool` 装饰器后台 daemon 线程+非阻塞队列记匿名 uuid 到 Supabase，DISABLE_TELEMETRY 可关（DW 7）；③ `execute_blender_code` 保留任意 Python 逃生舱——工具面小而逃生门大。
- **教学映射**：MCP 工具服务化（跨进程桥接最小可行样本）+ 人机协同（LLM 驾驭 DCC 软件）
- **一句话本质**：用一根带锁的 TCP JSON 管子，把 Blender 主线程按帧租给 LLM。

## 组内横断发现

1. **上下文压缩呈阶梯降级共识**：qwen-code 三级阈值 ladder（0.7 比例+13k 缓冲+20k 预留+3 次断路器）与 kilocode 两级递降（1.25MB 工具输出剪枝→LLM 摘要 CompactionPart）不约而同把压缩做成"先廉价剪枝、后昂贵摘要、失败熔断"的阶梯，而非一次性总结——压缩已是运行时基础设施而非功能。
2. **可恢复执行贯穿五个抽象层**：haystack 用 PipelineSnapshot 让数据流图崩溃可重入，kilocode 用 git Snapshot 让对话与文件系统共回滚，mastra 用 dowhile 持久化工作流+SaveQueueManager，modular 用 MefStore 让"编译"跨机器可复用，blender-mcp 用分段 JSON 判定让流式传输可续——从图引擎到内核编译，"断点"是本批最强母题。
3. **适配器/换壳经济是扩散主路径**：mastra 用 noop model 占位把 Claude/ACP agent 装进统一 SubAgent 接口，kilocode 整仓即 opencode 的品牌适配层（连上游合并流程都文档化），qwen-code 继承 gemini-cli 骨架连类名都懒得改——"下游发行版"已成独立的工程学科。
4. **两端极简与极繁同批共存**：blender-mcp 以一把 threading.Lock 保证单 socket 命令串行（无锁即流错位），haystack 却用 networkx+四级优先级队列做组件并发调度——进程间协议的最小主义与进程内编排的最大主义，是同一条效率光谱的两端。
5. **显式失败优于静默回退**：modular MefStore 拒绝 compile key（跨机器必失配且静默重编译）改为位置+签名校验失配即 raise；agentmemory 把 iii-engine 锁死 0.11.2 并留 11 行注释解释上游架构漂移——两仓都把"上游变了"从隐式运气变成显式契约。
