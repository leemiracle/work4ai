### meilisearch/meilisearch
- **DeepWiki**：Overview、2.2 Index Scheduler
- **架构模式**：actix-web API 层 + IndexScheduler 后台任务线程 + milli(LMDB) 搜索核，Cargo workspace 分 crate
- **核心数据结构**：任务队列是多张 LMDB 表：`all_tasks: BEU32→SerdeJson<Task>`，而 `status/kind/index_tasks` 三张二级索引的值全是 **RoaringBitmap**（DW 2.2 引 queue.rs:34-39）；Task=`{uid,status,kind:KindWithContent,enqueued_at...}`；文档载荷不进 LMDB，由 FileStore 以 UUID 命名落盘（本地 crates__file-store__src__lib.rs:9,41-48 `new_update()` 先写 NamedTempFile 再 persist）
- **核心算法/协议**：tick 循环 8 步（DW 引 scheduler/mod.rs:168-450）：清理旧任务→`create_next_batch` 按 autobatch 规则选批（同 index 同操作可合批、Snapshot 永远单任务，autobatcher.rs:30-150）→process→写回→NDJSON 序列化 + gzip POST webhook
- **设计模式**：1) 位图任务索引（queue.rs:35-39）；2) 载荷外置文件系统（lib.rs:41-48）；3) snapshot=逐文件复制 VERSION+data.mdb+update files（process_snapshot_creation.rs:114-180）；4) feature flag 持久化于 `persisted` 表 `experimental-features` 键（features.rs:12-21）
- **教学映射**：透视Agent系统工程（异步任务队列与自动合批）；上下文缓存（LMDB zero-copy 读路径）
- **一句话本质**：把一切写操作统一成可自动合批的持久任务流，让查询路径只碰只读 LMDB。

## 组内横断发现
1. **同构机制——"快照写入+后台重写"**：meilisearch 任务入队后 autobatch 合并、ClickHouse 插入不可变 part 后 merge、MemPalace verbatim drawer 落库后可再 compress（AAAK）、OpenMontage checkpoint 落盘。LSM 思想跨四个领域复现：前台只管快记，一致性靠异步整理。
2. **对立设计——记"原文"还是记"摘要"**：MemPalace 明确反摘要（verbatim 保 why，README.md:32-34）；private-gpt（TREE_SUMMARIZE/condenser）与 gpt-engineer（collapse 消息）则一切经 LLM 压缩。两条路线在 LongMemEval 上正面竞争。
3. **对立设计——part 不可变 vs 连接长生命周期**：ClickHouse 以不可变换吞吐；dbeaver 全部复杂度在管理可变连接态（connect/invalidate/commit 命令族，plugin.xml:85-107）。
4. **独家发明**：OpenMontage 的"零运行时编排"（agent 即控制平面）；meilisearch 的 RoaringBitmap 任务索引；lencx 的 `webview.eval()` 注入桥；MemPalace 的带 `valid_from/valid_to` 时效三元组；voicebox 的 health-shape 校验防端口误连。
5. **唯一共识——注册表/控制反转**：dbeaver OSGi 扩展点、private-gpt `_PROVIDERS` 策略注册（base_strategy.py:71）、OpenMontage ToolRegistry、ClickHouse Server 启动期工厂注册（Server.cpp:1-140）、meilisearch feature flag 表。十仓殊途同归：新能力一律"注册进来"，核心永不 hardcode。
