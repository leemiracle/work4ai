# TorchScript ONNX Exporter

> 来源: DeepWiki pytorch/pytorch (Last indexed: 2 September 2026, commit 580b06)

Relevant source files: aten/src/ATen/native/{Activation,BinaryOps,TensorCompare,TensorFactories}.cpp, torch/_refs/__init__.py, torch/_refs/nn/functional/__init__.py, test/jit/test_builtins.py, test/export/test_export_opinfo.py 等。

The TorchScript ONNX Exporter is the legacy pathway for converting PyTorch models into the Open Neural Network Exchange (ONNX) format. It operates by tracing a model or script into a `TorchScript` graph and then mapping each ATen operator to its corresponding ONNX operator(s) through a series of symbolic functions. This system supports ONNX opsets 9 through 20.

## Overview of the Export Pipeline

1. **Graph Capture**: The model is captured via `torch.jit.trace` or `torch.jit.script`.
2. **Symbolic Lowering**: The exporter traverses the TorchScript graph and invokes "symbolic" functions for each node.
3. **Opset Dispatch**: Based on the requested `opset_version`, the exporter selects the appropriate mapping from `symbolic_opset<N>.py`.
4. **ONNX Graph Construction**: The symbolic functions use a helper API to build the final ONNX protobuf.

In the context of modern PyTorch, this exporter is often contrasted with the newer `torch.export`-based exporter, though it remains a critical component for models relying on TorchScript features (test/dynamo/test_repros.py:153-162)

## Symbolic Opset Mappings and Dispatch

The mapping logic is partitioned into multiple files, each representing a specific ONNX opset version. Later opsets typically inherit and override implementations from earlier ones.

| Component | Role |
|---|---|
| `symbolic_opset9.py` | The base implementation for most operators. |
| `symbolic_opset10.py` | Overrides/additions for opset 10 (e.g., `Resize`, `Slice`). |
| `_dispatching.py` | Handles routing of `torch.fx.Node` to ONNX functions, including complex-valued input handling. |
| `_registration.py` | Manages the `ONNXRegistry` where decompositions and symbolic mappings are stored. |

The dispatcher specifically checks for complex dtypes to select specialized complex decompositions if available. This is crucial for operators like `add` or `mul` when applied to `complex64` or `complex128` tensors (torch/_refs/__init__.py:163-186)

## Higher-Order Operators (HOPs) and Control Flow

- **Conditional Logic**: Maps `torch.ops.higher_order.cond` to the ONNX `If` operator, constructing `then_branch` and `else_branch` graphs.
- **Looping**: Implements `while_loop` using the ONNX `Loop` operator, managing loop-carried dependencies and iteration counts.
- **Decompositions**: For many operations, the exporter uses decompositions to simplify complex ATen ops into basic ops that map directly to ONNX. For example, `alpha_dropout` is decomposed into a combination of `uniform`, `logical_not`, and basic arithmetic (torch/_refs/nn/functional/__init__.py:106-139)

## Symbolic Helper Utilities and Tensors

The `SymbolicTensor` class enables the use of Python operators (like `+`, `-`, `*`, `/`) during the symbolic conversion process, which are automatically translated into ONNX ops like `Add`, `Sub`, `Mul`, and `Div`.

- **Type Mapping**: The system maps PyTorch types to ONNX IR types, supporting `bfloat16`, `complex64`, and various `float8` formats.
- **Range Factories**: Operations like `arange`, `linspace`, and `logspace` are handled by specialized symbolic logic that accounts for device-specific behavior (e.g., MPS vs CUDA) (aten/src/ATen/native/mps/operations/RangeFactories.mm:28-77, aten/src/ATen/native/cuda/RangeFactories.cu:114-163)

## Data Flow and Node Conversion

The conversion logic relies on an `OpRecorder` and `SymbolicTensor` objects to build the graph. The `OpRecorder` tracks nodes as they are "traced" during the execution of symbolic functions.

**Sources:** aten/src/ATen/native/Activation.cpp:87-112, BinaryOps.cpp:151-182, TensorCompare.cpp:101-135

## Verification and Reporting

- **OpInfo Integration**: The exporter is systematically tested against `OpInfo` definitions (test/export/test_export_opinfo.py:126-136)
- **VerificationInfo**: A dataclass that stores `max_abs_diff` and `max_rel_diff` between expected (PyTorch) and actual (ONNX) values.
- **Failure Handling**: The system tracks known failures using `xfail` and `skip` lists for specific ops (test/export/test_export_opinfo.py:33-59)

Tests for the exporter utilize `TestCase` and often involve `FakeTensorMode` to simulate device execution without requiring physical hardware during the export phase, allowing extensive coverage of operators like `batch_norm`, `conv2d`, and `scaled_dot_product_attention` in CI environments.
