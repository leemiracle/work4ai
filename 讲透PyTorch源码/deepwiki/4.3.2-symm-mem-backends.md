## CUDA Backend (Direct Virtual Memory IPC)

### Implementation Details

- Allocation and Mapping : Using CUDA Driver API calls such as cuMemCreate , cuMemMap , cuMemSetAccess , the backend creates a physical memory allocation and maps it into the virtual address space of each participating GPU. Memory handles are shared via IPC handles exchanged using a rendezvous protocol over a Store torch/csrc/distributed/c10d/symm_mem/CUDASymmetricMemory.cu 36-73
- Multicast Support : For CUDA 12.3+ (or equivalent ROCm support), multicast is implemented using cuMulticastBindMem_ , enabling efficient one-to-many writes executed by hardware torch/csrc/distributed/c10d/symm_mem/CUDASymmetricMemory.cu 59-63
- Synchronization via Signal Pads : The backend implements barrier synchronization and signaling via atomic operations on dedicated "signal pad" memory regions. Kernels wait on and update these pads with put_signal , wait_signal , and barrier operations to coordinate between ranks torch/csrc/distributed/c10d/symm_mem/CUDASymmetricMemory.cu 188-202 The size of the signal pad can be configured at runtime, which affects allocation granularity test/distributed/test_symmetric_memory.py 150-182

## NCCL Backend (Communication Windows)

NCCL Communication Windows
`ncclMemAlloc`
`ncclCommWindowRegister`

### Detailed Behavior

- Allocation: Memory is allocated as a combined region ( ncclMemAlloc ) including signal pads and data buffer. The NCCLAllocation struct manages allocation and deallocation via ncclMemFree torch/csrc/distributed/c10d/symm_mem/NCCLSymmetricMemory.cu 33-74
- Peer Pointers & Device Side Access: During rendezvous, pointers to remote buffers and signal pads are constructed on the device side using device kernels (e.g., build_ptr_dev ), assisted by NCCL device-side APIs such as ncclGetLsaPointer . This enables kernels to perform remote memory reads/writes via known device pointers torch/csrc/distributed/c10d/symm_mem/NCCLSymmetricMemory.cu 136-152
- DevComm Management: NCCLDevCommManager manages the mapping from host-side ncclComm_t to device-side ncclDevComm communicators, which are cached per device and group. This is essential for launching kernels that register with NCCL dev-side API for synchronization and low-level barriers torch/csrc/distributed/c10d/symm_mem/nccl_devcomm_manager.hpp 18-160

## NVSHMEM Backend (One-Sided Communication Library)

### Integration and Usage

- Backend Registration: The NVSHMEM allocator registers itself and can be selected dynamically via the Python API by calling symm_mem.set_backend("NVSHMEM") test/distributed/test_nvshmem.py 70
- Device and Group Initialization: NVSHMEM is integrated with PyTorch process groups and can be used alongside device mesh initializations test/distributed/test_nvshmem.py 12
- Symmetric Memory Management: Allocated symmetric tensors provide remote peer pointers transparently, enabling standard ATen operations such as copy_() from remote peers without explicit communication calls test/distributed/test_nvshmem.py 214-215
- Custom Kernel Support with Triton: Developers can write Triton kernels that directly access NVSHMEM symmetric memory buffers and synchronize using NVSHMEM barriers and signals, facilitating custom fused compute-communication kernels.

### Functional Features

- Support for fine-grained, low-latency collectives such as broadcasts and barriers using NVSHMEM primitives.
- CUDA graph compatibility in capturing sequences that involve NVSHMEM allocations (with caveats about handle creation ordering).

## Backend Comparison Summary

| Feature | CUDA Backend | NCCL Backend | NVSHMEM Backend |
|---|---|---|---|
| Primary API | CUDA Driver Virtual Memory | NCCL ncclCommWindowRegister | NVSHMEM Library |
| Requirements | CUDA or HIP Driver | NCCL 2.27+ | NVSHMEM library installed |
| P2P Memory Mechanism | cuMemMap / hipMemMap | ncclMemAlloc + ncclCommWindowRegister | nvshmem_malloc , PGAS model |
| Multicast Support | cuMulticastBindMem_ (CUDA 12.3+) | ncclGetLsaMultimem | nvshmem_broadcast |
| Synchronization | Signal Pads (atomic polling) | NCCL Device-Side Barriers | NVSHMEM Barriers |
| Memory Allocation | Driver API methods | NCCL P2P memory allocation | NVSHMEM allocation |
| Kernel Integration | Standard CUDA kernels with mapped pointers | NCCL LSA and Device Communicator APIs | Custom kernels with direct NVSHMEM pointers |

# Summary

- The CUDA backend offers direct virtual memory-based P2P access using CUDA or HIP driver APIs, focusing on intra-node communication without requiring NCCL.
- The NCCL backend leverages NCCL communication windows and device communicators for tightly integrated communication with built-in synchronization and P2P memory exposure.
- The NVSHMEM backend provides a one-sided communication layer with RDMA-like semantics suitable for custom high-performance collectives and fused compute/communication kernels, compatible with multi-node deployment.
