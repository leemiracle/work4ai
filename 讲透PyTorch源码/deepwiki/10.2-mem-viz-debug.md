# Memory Visualization and Distributed Debugging

PyTorch provides a suite of tools for inspecting memory allocation patterns and debugging distributed training jobs. These tools bridge the gap between low-level hardware resource utilization and high-level Python execution, offering insights into memory fragmentation, allocation history, and collective communication health.

## 1. Memory Visualization Tools

The memory visualization system is built around the `CUDACachingAllocator`'s ability to capture snapshots of the GPU memory state. These snapshots include information about segments, blocks, and the stack traces that triggered allocations.

### 1.1. Memory Snapshot Generation

The allocator records a ring buffer of `TraceEntry` actions such as `alloc`, `free_requested`, and `free_completed` (torch/utils/viz/process_alloc_data.js:8-21)

- **Trace Actions**: `alloc` represents sub-allocations returned to the user, while `free_completed` marks the actual return of a block to the allocator's free pool
- **Segment Events**: `segment_alloc` and `segment_free` track interactions with the OS (e.g., `cudaMalloc`), while `segment_map` and `segment_unmap` track physical page mapping in expandable segments
- **Private Pools**: The system identifies memory blocks belonging to user-created pools (e.g., FSDP MemPool) via `isPrivatePoolId`, distinguishing them from the default pool `[0, 0]`

### 1.2. MemoryViz frontend and Data Processing

`MemoryViz.js` is a D3.js-based visualization tool that renders captured snapshots (torch/utils/viz/MemoryViz.js:8-10). It provides temporal views of memory allocations, allowing developers to identify leaks and fragmentation.

- **`process_alloc_data`**: The primary entry point for parsing snapshot data into plot-ready structures, handling peak size calculations and timeline reconstruction (torch/utils/viz/process_alloc_data.js:84-118)
- **Interaction Modes**: The tool supports both `hover` and `click` modes for displaying stack traces (torch/utils/viz/MemoryViz.js:71-80)
- **Event Formatting**: `formatEvent` and `formatAddr` convert raw C++ trace metadata into human-readable strings for the UI

**Sources:** torch/utils/viz/MemoryViz.js:1-80, torch/utils/viz/process_alloc_data.js:1-130

## 2. Profiling and Performance Debugging

### 2.1. Kineto and Autograd Profiler

- **`KinetoThreadLocalState`**: A C++ class that manages the lifecycle of a profiling session, including reporting memory usage and finalize traces (torch/csrc/autograd/profiler_kineto.cpp:107-113)
- **Memory Reporting**: `reportMemoryUsage` and `reportOutOfMemory` capture allocation sizes and device info during the trace (torch/csrc/autograd/profiler_kineto.cpp:143-175)
- **Python Frontend**: The `profile` class provides a context manager to enable/disable profiling, with options for `record_shapes`, `profile_memory`, and `with_stack` (torch/autograd/profiler.py:113-162)

### 2.2. Trace Result Analysis

- **`EventList`**: An extension of the Python list providing methods like `table()`, `export_chrome_trace()`, and `key_averages()` (torch/autograd/profiler_util.py:29-57)
- **Tree Building**: The `_build_tree` method populates parent-child relationships between events based on timing intervals (torch/autograd/profiler_util.py:109-113)
- **Data Encoding**: `InputOutputEncoder` handles the serialization of operator input/output metadata (shapes, dtypes) for the profiler trace (torch/csrc/profiler/collection.cpp:182-189)

## 3. Distributed Debugging Infrastructure

- **`CommDebugMode`**: A specialized mode for tracking collective communication calls in distributed tensor operations (torch/profiler/profiler.py:29)
- **Testing Coverage**: The `TestProfilerCUDA` class includes tests for memory leaks during profiling and CUDA graph interactions (test/profiler/test_profiler.py:130-162)

## 4. Execution Trace and Observers

- **Execution Trace Observers**: Functions like `_add_execution_trace_observer` and `_remove_execution_trace_observer` allow external tools to hook into the runtime to capture execution graphs (torch/profiler/profiler.py:19-25)
- **Experimental Config**: `_ExperimentalConfig` allows passing backend-specific configuration strings (e.g., for Kineto) to the profiler (torch/profiler/profiler.py:55-67)
