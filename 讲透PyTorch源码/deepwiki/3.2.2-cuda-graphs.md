- Capture Lifecycle : CUDA graphs are captured on non-default CUDA streams; graph capture begins and ends, producing a graph object that can be replayed.
- Private Memory Pools : Each graph is assigned a dedicated memory pool isolated from the default caching allocator, preventing address reuse conflicts.
- Graph Trees : To support nested or sequential capture on streams, PyTorch manages a tree of CUDA graphs, sharing memory pools safely across replayed graphs.
- Stream/Event Semantics : Synchronization primitives (streams and events) are modeled symbolically in Dynamo and used to generate graph capture-aware FX graphs.
- Allocator Interaction : The caching allocator is integrated with the graph lifecycle, coordinating pool creation, retention, and cleanup.
- User-Stream Support in Inductor : Inductor supports user-assigned CUDA streams with stream context wrappers, generating stream-aware code that cooperates with graph capture.
- Kernel Annotation : During capture, PyTorch can annotate graph nodes (kernels, memcpys, memsets) with metadata to aid in profiling and trace analysis.

### Private Pools and Address Stability

- The default caching allocator manages memory via a global arena and multiple pools.
- CUDA graph capture uses private pools distinct from the default allocator's pools ( aten/src/ATen/cuda/CUDAGraph.cpp 45-49 ), isolating graph allocations.
- Memory allocated during capture is retained until the graph and all its output tensors are destroyed.
- CUDAGraph::retain_pool is used to increment the reference count of a pool to ensure it stays valid across multiple captures or replays aten/src/ATen/cuda/CUDAGraph.cpp 98-110
