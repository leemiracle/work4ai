## 2. Overlap Scheduling System

`torch/_inductor/fx_passes/overlap_scheduling.py`

### Key Concepts and Classes

- Communication Starts and Waits : Collectives are split into "start" nodes (which issue communication) and wait_tensor nodes (which wait for communication to complete). The scheduler reorders these nodes to enhance overlap torch/_inductor/fx_passes/overlap_scheduling.py 22-25
- OverlapScheduler class : The main engine performing the scheduling. It tracks dependencies, estimates operation cost, and reorders nodes by greedily sinking wait nodes and raising communication start nodes near appropriate compute nodes torch/_inductor/fx_passes/overlap_scheduling.py 30-31
- Compute Node Identification : The system uses the flop_registry in torch/utils/flop_counter.py to identify compute-intensive nodes (like aten.mm or aten.bmm ) that are good candidates to hide communication latency torch/_inductor/fx_passes/overlap_scheduling.py 179-184 torch/utils/flop_counter.py 124-181
- Roofline Model : Runtimes are estimated using a roofline model that takes the maximum of compute-bound (FLOPs) and memory-bound (bandwidth) estimates torch/_inductor/fx_passes/overlap_scheduling.py 187-203

## 3. Bucketing Strategies

### Bucketing Modes

`BucketMode`

- "default" : Standard ATen-based bucketing.
- "custom_ops" : Traces bucketing through custom operations to preserve symbolic shapes.
- "custom_ops_multidtype" : Allows bucketing across different dtypes.
- "coalesced" : Uses NCCL coalescing managers.

## 5. Overlap-Preserving Transformations

### Hiding Intervals

`wait_tensor`

- OverlapPreservingBucketer : This class ensures that bucketing two collectives doesn't destroy their ability to overlap with compute. For example, if two collectives have nested hiding intervals, bucketing them might be prohibited test/distributed/test_overlap_bucketing_unit.py 203-206
- _collect_nodes_must_be_after : A BFS-based analysis to find transitive users that must stay after a specific node to maintain correctness torch/_inductor/fx_passes/overlap_manual_scheduling.py 46-59

### Wait Sinking and Comm Raising

- Sink Waits : Move wait_tensor nodes as late as possible in the graph, ideally after compute nodes that don't depend on the collective result test/distributed/test_aten_comm_compute_reordering.py 135-160
- Raise Comms : Move collective start nodes as early as possible to maximize the time available for overlap test/distributed/test_aten_comm_compute_reordering.py 166-185
