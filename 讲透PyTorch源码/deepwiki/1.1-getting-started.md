## 1. Repository Layout and Key Entrypoints

| Directory | Description | Key Contents |
|---|---|---|
| c10/ | Core library module | Basic core abstractions, common utilities, device-agnostic types like SymInt , and dispatcher internals. aten/src/ATen/core/CachingHostAllocator.h 1-20 |
| aten/ | Tensor library implementation | Contains the C++ ATen tensor library and operator implementations under src/ATen/native . aten/src/ATen/native/Repeat.cpp 1-20 |
| torch/ | Python frontend package | Main Python bindings and frontend code, including compiled C++ extensions under csrc/ , and compiler backend components like _inductor/ . CLAUDE.md 47-49 |
| test/ | Python test suites | All unit and integration tests orchestrated primarily by run_test.py . test/run_test.py 1-63 |
| tools/ | Developer utilities | Contains build scripts, code generation tools ( torchgen ), and performance benchmarking tools. pyproject.toml 85-93 |
| docs/ | Documentation sources | Sphinx documentation source files for PyTorch’s public docs. |

## 2. Building from Source

`scikit-build-core`

### Configuring the Build Environment

- Python Dependencies: Required packages include numpy , scikit-build-core , pyyaml , and typing-extensions . pyproject.toml 3-23
- Build Tooling: CI utilizes sccache to speed up C++ and CUDA compilation. .ci/pytorch/build.sh 18-25
- Environment Variables: MAX_JOBS : PyTorch's umbrella parallelism knob for building. pyproject.toml 33-37 DEBUG=1 : Triggers a Debug build type in CMake. pyproject.toml 52-54 REL_WITH_DEB_INFO=1 : Triggers a RelWithDebInfo build. pyproject.toml 56-58 USE_CUDA=0/1 : Explicitly enables or disables CUDA. .ci/pytorch/build.sh 109-110
- ROCm Support: Requires a preprocessing "hipify" step to convert CUDA sources to HIP. .ci/pytorch/build.sh 154-156

## 3. Testing Infrastructure

`test/run_test.py`

### Local Test Execution

- Test Discovery: The runner discovers tests in the test/ directory, including specialized suites like distributed/ and inductor/ . test/run_test.py 57-63 test/run_test.py 119-120
- Device Type Testing: Contributors should use instantiate_device_type_tests to write generic tests that run across CPU, CUDA, and other backends. CLAUDE.md 65-67
- Sharding: CI splits tests into shards using NUM_TEST_SHARDS and SHARD_NUMBER . test/run_test.py 72-76 .ci/pytorch/test.sh 73-74
- Retries: Failing tests are retried in fresh processes to distinguish flaky tests from consistent failures. test/run_test.py 116-118

## 4. CI: The Authoritative Reference

### Key CI Entrypoints

- .ci/pytorch/build.sh : The script that configures environment variables and invokes the build for Linux CI jobs. .ci/pytorch/build.sh 1-10
- .ci/pytorch/test.sh : The script that executes the test suite in CI, handling environment-specific patches (e.g., Numba CUDA 13 crash fixes). .ci/pytorch/test.sh 1-48
- .github/workflows/pull.yml : Defines the PR test matrix, specifying which shards run on which hardware (e.g., linux.g6.4xlarge.experimental.nvidia.gpu ). .github/workflows/pull.yml 113-126

## 5. Developer Workflow and Hygiene

- Linting: Use lintrunner -a before committing. CLAUDE.md 79-80
- AI Policy: AI-generated content must be explicitly marked and reviewed by humans. CLAUDE.md 1-18
- Type Stubs: Edit .pyi.in templates rather than generated .pyi files. CLAUDE.md 68-72
- Asserts: Avoid raw assert statements (which are stripped in optimized runs); use explicit if not cond: raise AssertionError . CLAUDE.md 82-105
