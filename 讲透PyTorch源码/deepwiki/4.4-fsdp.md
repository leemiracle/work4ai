### Core Concepts

- FSDPState : Holds the distributed state for one or more modules managed by FSDP, including parameter groups, communication context, and training state. It registers forward and backward hooks to manage the sharding lifecycle torch/distributed/fsdp/_fully_shard/_fsdp_state.py 59-78
- FSDPParamGroup : Represents a grouping of parameters which share a communication mesh and are all-gathered or reduce-scattered together to improve communication efficiency torch/distributed/fsdp/_fully_shard/_fsdp_param_group.py 151-166
- FSDPParam : Manages the lifecycle of a single parameter, including its sharded and unsharded representations, and transitions during forward/backward passes torch/distributed/fsdp/_fully_shard/_fsdp_param.py 67-83

## Parameter Sharding Lifecycle

`DTensor`
`DeviceMesh`

- Initialization & Sharding Input parameters are sharded along the designated mesh dimension. Users can customize sharding via a shard_placement_fn to specify per-parameter placements torch/distributed/fsdp/_fully_shard/_fully_shard.py 101-103 torch/distributed/fsdp/_fully_shard/_fsdp_param.py 70-72
- Forward Pass – Unsharding via AllGather Prior to computation, each sharded parameter undergoes an all_gather collective to reconstruct the full parameter locally. This happens in the forward pre-hook, invoking foreach_all_gather across parameters in a group torch/distributed/fsdp/_fully_shard/_fsdp_collectives.py 111-124 torch/distributed/fsdp/_fully_shard/_fsdp_state.py 137-154
- Forward Post-hook – Optional Resharding After forward computation, unsharded parameters can be freed to save memory by resharding them. This resharding is configurable via reshard_after_forward torch/distributed/fsdp/_fully_shard/_fully_shard.py 117-119 torch/distributed/fsdp/_fully_shard/_fsdp_param.py 140-144
- Backward Pass – Gradient Reduction via ReduceScatter Gradients computed on the unsharded parameter are reduced and scattered back to the sharded layout via reduce_scatter collectives torch/distributed/fsdp/_fully_shard/_fsdp_collectives.py 175-191

## Collective Communication and Overlap Scheduling

- Dedicated CUDA Streams for Collectives: Separate CUDA streams are allocated for all-gather and reduce-scatter collectives ( all_gather_stream , reduce_scatter_stream ), as well as HSDP all-reduce ( all_reduce_stream ), enabling concurrent progress of communication and computation torch/distributed/fsdp/_fully_shard/_fsdp_param_group.py 76-103
- Prefetching of Parameters: FSDP can prefetch the next parameter group's all-gather in the forward, overlapping communication with computation. This is coordinated by the FSDPCommContext which manages the dedicated streams torch/distributed/fsdp/_fully_shard/_fsdp_param_group.py 62-128
- Symmetric Memory for High-Performance Collectives: When supported by the backend, FSDP uses symmetric memory (e.g., via NCCL with SymmMemAllGather ) to optimize collective communication by enabling zero-copy protocols within intra-node GPU sharing torch/distributed/fsdp/_fully_shard/_fsdp_collectives.py 146-173
