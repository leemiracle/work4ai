# 03 · 可构造与结构——标准文献、合格评定与体系表作为数据对象

> **本章回答五问之 Q4(可构造性与结构)。**
> **本质一句话**:标准科学技术里「可构造」的不是协商
> 过程本身,而是**它的三类产出**——标准文献是把「要求」
> 写成章节-条款-验证成对的结构(GB/T 1.1 骨架),合格
> 评定链是把「谁证明谁」写成检测→认证→认可的金字塔,
> 标准体系表是把「谁管谁、谁代替谁」写成带状态与层级的
> 图(GB/T 13016);把这些结构显式化,标准工作就从文书
> 手艺变成工程:可校验、可对表、可交接(04 章走廊的
> 地基)。

---

## 0. 开篇:一份"标准化任务单"的三件结构化家具

拆开任何一次严肃的标准化工作(立标/采标/合规),都
能拆出三件家具:其一是**标准文献结构**(要写的东西
长什么样——章节骨架、条款效力、附录分层),其二是
**合格评定链**(写了之后谁验——检测、认证、认可三层
各证各的),其三是**标准体系表**(这一份与已有几百份
什么关系——层级、状态、代替关系)。三件家具在手,
「立-验-传」主链(00 章)的每一环就变成**可机检的数据
流水线**;从 Whitworth 的查表螺纹到 AI 标准数据库
(01 章方向四),在数据结构层面是同一套 schema——变的
是标准数量与密度,不变的是结构。

## 1. 什么是"可构造"的:三类结构对象

| 对象 | 数化身 | 可构造性 | 构造中的坑 |
|------|--------|---------|-----------|
| **标准文献** | 章节骨架+条款(效力档+验证对)+附录(规范性/资料性)+版本状态 | ✅ 高度可构造 | 「应」无测试方法(02 章规则一);规范性与资料性混标 |
| **合格评定链** | 检测报告→认证证书→认可资格(对象/颁发方/上游三列) | ✅ 高度可构造 | 认证与认可混称(「认证的认证」被略掉);体系认证冒充产品认证 |
| **标准体系表** | 层级(国/行/地/团/企)+约束力(强制/推荐)+状态(现行/修订/废止)+代替关系 | ✅ 高度可构造 | 状态与日期不钉死(引用作废标准);层级与法律效力混淆 |
| **抽样方案卡** | (n, Ac)+两点风险(p₁,α)/(p₂,β)+OC 曲线 | ✅ 高度可构造 | 只写 AQL 不写 β(02 章规则二) |
| **术语条目** | 术语+定义+同义词+外文对应+概念关系(属分/整体部分) | ✅ 高度可构造 | 同义术语未归一(一物多名);定义含循环(用被定义词定义自己) |

**不可构造的**:协商过程本身(分歧与妥协不入正文,
02 章表达力边界)、条款的「合理裁量」(FRAND 费率个案
裁定)、事实标准的生态边界(装机量统计依赖社区数据,
边界模糊)、以及「这份标准该不该立」(时机决策,00 章
反直觉①)。

### 1.5 最小数据模式(动手者的 schema)

```yaml
# 标准文献结构卡(GB/T 1.1 骨架的机读版)
standard_doc:
  identity: {number: "GB/T XXXXX-YYYY", status: current|revised|withdrawn,
             replaces: [str], superseded_by: [str]}      # 版本与状态必钉死
  sections:
    - {kind: scope, text: str}                            # 范围:划地盘
    - {kind: normative_refs, docs: [str]}                 # 规范性引用文件
    - {kind: terms, entries: [terms_ref]}                 # 术语和定义
    - {kind: requirement,                                  # 要求条款
       clause: str, verb: shall|should|may,               # 效力档(02 章)
       text: str, verification: test_clause|sampling|audit|declaration}  # 验证对(V1-V4)
  annexes:
    - {kind: normative|informative, title: str}           # 附录效力必标

# 认证与认可区分卡(「谁证明谁」的金字塔)
conformity_chain:
  testing:   {subject: product|sample, issuer: lab,          # 检测:对样品
              output: test_report}
  certification: {subject: product|system|person,            # 认证:对产品/体系/人员
              issuer: certification_body,                    # 第三方机构
              output: certificate, accredited_by: str}
  accreditation: {subject: certification_body|lab,           # 认可:对机构能力
              issuer: accreditation_body,                    # 「认证的认证」
              output: accreditation, upstream: IAF|ILAC}     # 国际互认屋顶

# 标准体系表(GB/T 13016 的最小 schema)
standards_system_table:
  nodes:
    - {code: str, level: intl|national|industry|local|group|enterprise,
       binding: mandatory|voluntary, status: current|revised|withdrawn,
       scope: str, review_cycle_years: int}
  edges:
    - {type: replaces|cites|conflicts_with, from: code, to: code}
```

注意 `verification`、`verb`、`status` 三处必填:把 02 章
的证据纪律写进数据结构——**数据层自带校验点,是标准
文献区别于普通文档的第一特征**(与
[工程物理学家族](../讲透工程物理学/03-可构造与结构.md)
schema 同款精神:条款不 naked,效力不缺席)。

## 2. 骨架一:标准文献结构卡(GB/T 1.1 的骨架)

- **范围先行**:第一章永远划地盘——「本文件规定了…
  适用于…」;范围外的内容是越权条款,审查第一刀
- **条款=效力+验证成对**:每条要求由三件构成:助动词
  档位(应/宜/可)、对象、验证方式(V1-V4);「应」找
  不到验证方式即红灯(02 章规则一的 schema 版)
- **附录双层**:规范性附录与正文同效力(合同的一部分),
  资料性附录仅参考;每份附录必须显式标注效力——混标
  是把参考冒充要求(02 章规则三)
- **术语章是私有字典**:标准第三章定义的术语只在本文件
  语境生效;引用他标准术语必须列规范性引用——「同词
  不同义」的隔离墙

## 3. 骨架二:认证与认可区分卡(谁证明谁)

- **三层金字塔**:检测(实验室对样品出报告)→认证
  (第三方机构对产品/体系/人员发证书)→认可(认可
  机构对认证机构/实验室的能力给资格)——**「认证的
  认证」**,最易被日常语言抹掉的一层
- **对象列不可混**:体系认证(ISO 9001/42001 类)证明
  「过程管得好」,不证明「产品好」;拿体系证书宣传
  产品性能是市场话术对结构卡的经典滥用(01 章方向一
  的未决问题)
- **国际互认屋顶**:IAF(认证机构互认)/ILAC(实验室
  互认)把各国认可机构接成网——一张证书全球走的制度
  基础设施(4105050 认证认可方法的核心对象)
- **安全测评样本**:等级保护测评(对信息系统的检测与
  评定)是「标准×合格评定」在安全域的当代演习场,
  本体见[信息安全技术家族](../../讲透信息与系统工程技术/讲透信息安全技术/README.md)

## 4. 骨架三:标准体系表(谁管谁、谁代替谁)

- **层级与效力两列分开**:五级体系(国/行/地/团/企)
  是**制定主体**层级;强制/推荐是**约束力**——两个
  维度,不能合成一列(行业推荐标准不「低于」国家推荐
  标准的法律层级想象)
- **状态与代替关系必钉死**:现行/修订/废止+代替/
  被代替;引用废止标准=引用失效法条,这是体系表维护
  的最高频事故
- **关系边三种以上**:代替(版本链)、引用(依赖链)、
  冲突(待协调)——体系表不是清单,是**图**;复审
  周期字段(通说国标复审一般不超过五年)让维护从
  一次性编表变成闭环(00 章假设三的制度化补救)
- **体系表自指**:GB/T 13016 规定「体系表怎么编」,
  它自己也在国标体系表内——标准体系的图包含「画图
  方法」这个节点(00 章美之时刻③的数据面)

## 5. 从结构到校验:这套骨架买到了什么

- 文献卡带验证对 → 「应」条款可机检(不可判定条款
  自动揪出)
- 区分卡对象列分明 → 体系认证冒充产品认证的话术可
  自动识破
- 体系表带状态与边 → 引用作废标准、依赖冲突可机检
- 抽样方案卡带两点风险 → 单侧验收标准可机检(02 章
  规则二)
- 术语条目带同义词归一 → 一物多名可机检(04 章 C2
  的主战场)

## 6. 构造合法性清单(动手前三问)

把任何标准化构想变成数据结构之前,先过三问——本家族
的「类型检查」:

1. **验证对写全了吗**:每条「应」指向哪种验证(V1-V4)?
   有没有写了效力档却给不出判定程序的裸条款?
2. **效力分层了吗**:规范性/资料性逐件标注了吗?体系
   认证与产品认证、认证与认可,对象列分清了吗?
3. **状态钉死了吗**:版本、日期、代替关系、复审周期
   入表了吗?引用的每份标准都是现行态吗?

三问全过,数据才获得进入 [04 章走廊](04-标准科学技术转代码.md)
的资格。**标准工程的第一特征不是条款多,是账目清楚。**

## 📌 收束

可构造的是**三类数据对象**(文献结构/合格评定链/
体系表),不可构造的是**协商与裁量的过程**;结构化
不是为了替代委员会,是为了让立-验-传的链条可校验、
可交接、可复盘。下一章把骨架接上代码:
[04-标准科学技术转代码](04-标准科学技术转代码.md)。

**🧠 认知升维**:

- **验证眼**:每个条款都要问「怎么判定」——效力档与
  验证方式成对出现,缺一半就是坏条款
- **金字塔眼**:检测→认证→认可三层各证各的——听到
  「认证」先问「谁认证谁,认证的是什么」
- **状态眼**:标准是有时效的文献——引用不带状态与
  日期,等于引用一部可能已废止的法
