# ⚠️ 第 4 幕 · 不足：代码生成的失败模式

## 1. 幻觉 API
LLM 自信调用不存在的函数/过期签名/错误参数名。**这是头号 bug 源**。
**根因**：训练数据里的 API 版本混杂。
**缓解**：约束解码（强制用当前 SDK 的 grammar）、工具检索真实文档、跑编译器/测试即验证。

## 2. 多步错误累积
单步 95% 正确，10 步链 $0.95^{10} \approx 60\%$。长任务必然跑偏。
**缓解**：Agentic 闭环（每步执行反馈）、check-point、人审关键节点。

## 3. 测试通过 ≠ 正确
代码通过了测试，但逻辑错（测试覆盖不全/测试本身错）。
**根因**：SWE-bench 的 30% 失败常是「最难、测试没覆盖的」。
**缓解**：多重测试、property-based testing、代码审查。

## 4. SWE-bench 真实差距
媒体常报「70%+」——但那是 Verified 子集（人工筛过）。全量 SWE-bench 仍低。且**生产任务的复杂度远超 benchmark**。
**判据**：把 benchmark 分数打 5-7 折估真实能力。

## 5. 上下文不够
真实代码库几十万文件，远超 context。Agent 看不全就改，容易破坏全局一致性。
**缓解**：Augment 式大规模索引、分层检索、改前看影响范围。

## 6. 安全：注入
恶意 prompt 藏在代码注释/issue/文档里，诱导 agent 执行危险操作（`rm -rf`、泄漏密钥）。
**根因**：agent 把不可信输入当指令。
**缓解**：指令与数据分离、命令白名单、人审高危操作、sandbox 执行。

## 7. 成本爆炸
Agentic 多轮调用，一个任务可能烧 $10+。长任务成本不可控。
**缓解**：预算上限、prompt caching、小模型先粗筛大模型精修。

## 8. 评估难
通过率、token 成本、人审修改量、用户满意度——多目标难同时优化。
**缓解**：定义清楚北极星指标，做 A/B。

## 9. 「自动化」的过度承诺
Devin 式「全自动工程师 demo」离生产远。**当前主流仍是「AI 写+人审」**。
**判据**：把厂商 demo 的自主度打 3-5 折估真实可用度。

---

## 🎬 收束

> 代码生成的核心张力永在：**统计流畅 ≠ 语义正确**。Agentic 闭环把指数衰减的失败率变成线性可控，但没消除失败。**当前最可靠的用法是「AI 写+人审」，不是「AI 独立交付」**。SWE-bench 70% 不是终点，是「半自动」的起点。
