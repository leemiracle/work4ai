## Overview

 The High Availability (HA) feature in OpenHarmony RDBMS provides durability and resilience through database replication techniques. The system supports real-time data mirroring and backup mechanisms to prevent data loss and minimize service interruptions.

 Key capabilities include:

 
 - Multiple high availability modes
 - Real-time dual-write to replica databases
 - Automated and manual backup/restore functionality
 - Failure detection and recovery mechanisms

## High Availability Architecture

 The HA system implements a primary-replica architecture where operations on the main database can be automatically mirrored to a replica (slave) database. The system supports three operational modes:

 
```

```

 
### HA Modes

 The system supports three high availability modes:

 
| Mode | Enum Value | Description | Implementation |
|---|---|---|---|
| Single | HAMode::SINGLE | Standard single database operation without replication | Default mode with no slave database |
| Main-Replica | HAMode::MAIN_REPLICA | Automatic dual-write to main and slave database | Operations are mirrored in real-time |
| Manual Trigger | HAMode::MANUAL_TRIGGER | Slave database is created/updated only when explicitly triggered | Requires application to initiate replication |

## Double-Write Mechanism

 The double-write mechanism ensures data is written to both the main and slave databases, providing redundancy and protection against data loss.

 
```

```

 
### Implementation Details

 
 - **Statement Preparation**: When a SQL statement is prepared in double-write mode, both main and slave statements are created.
 - **Execution Flow**: Data modification operations (INSERT, UPDATE, DELETE) are executed on both databases.
 - **Error Handling**: If the slave operation fails, the system marks the slave as invalid but allows the main operation to succeed.
 - **Slave Status Tracking**: The system tracks the slave database status and can repair or rebuild it if necessary.

### Slave Creation and Validation

 The slave database is created through the `CreateSlaveConnection` method. Before opening the slave database, the system performs validations:

 
 - Checks if the slave database exists
 - Checks for corruption markers
 - Verifies WAL file size doesn't exceed limits
 - Ensures no synchronization interruption markers exist
 
 If validation fails, depending on the HA mode, the system may rebuild the slave or mark it as invalid.

## Backup and Restore Processes

 The system provides mechanisms for backing up and restoring databases to ensure data can be recovered.

 
```

```

 
### Backup Operation

 The backup process involves:

 
 - **Initiating backup**: Either automatically in `MAIN_REPLICA` mode or manually in `MANUAL_TRIGGER` mode
 - **Status tracking**: The system tracks backup status throughout the process
 - **Page copying**: The database is backed up in chunks of pages (default 12,800 pages)
 - **WAL handling**: Write-Ahead Logging files are properly managed during backup
 
 
### Restore Operation

 The restore process involves:

 
 - **Close connections**: Existing connections to the database are closed
 - **Replace files**: Backup files replace the current database files
 - **Reopen database**: The database is reopened with restored data
 - **Validate integrity**: The restored database is verified for integrity

## Configuration and Implementation

 
### Key Configuration Parameters

 The following configuration parameters control the high-availability behavior:

 
| Parameter | Description | Default Value |
|---|---|---|
| HAMode | Sets the high availability mode | SINGLE |
| SLAVE_WAL_SIZE_LIMIT | Maximum WAL file size for slave | 2GB (2147483647 bytes) |
| BACKUP_PAGES_PRE_STEP | Number of pages per backup step | 12,800 (50MB) |
| BACKUP_PRE_WAIT_TIME | Wait time between backup steps | 10ms |

 
### Implementation Classes

 The high-availability feature is implemented across several key classes:

 
 - **`RdbStoreConfig`**: Defines the HA mode and related configuration
 - **`SqliteConnection`**: Implements the actual double-write mechanism and slave connection management
 - **`ConnectionPool`**: Manages connections to both main and slave databases
 - **`SqliteStatement`**: Handles statement execution on both main and slave databases

## Error Handling and Recovery

 The system incorporates several mechanisms to detect and recover from failures:

 
 - **Slave validation**: Before operations, the slave database is validated
 - **Error markers**: Special files indicate slave corruption or interruption
 - **Automatic rebuild**: In `MAIN_REPLICA` mode, corrupt slaves can be automatically rebuilt
 - **WAL size monitoring**: Oversized WAL files trigger corrective actions
 - **Integrity checks**: Database integrity is verified periodically
 
 When slave operations fail, the system marks the slave as invalid by creating a marker file. This prevents further operations on the corrupt slave until it's repaired or rebuilt.
