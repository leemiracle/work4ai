## Overview

 The encryption subsystem provides transparent SQLite database encryption using industry-standard cryptographic algorithms. When enabled, the entire database file is encrypted, protecting all stored data from unauthorized access if the physical storage is compromised.

## Encryption Algorithms and Parameters

 The system supports several cryptographic algorithms and parameters that can be configured based on security requirements.

 
### Supported Algorithms

 
| Category | Algorithm Options |
|---|---|
| Encryption | AES-256-GCM, AES-256-CBC |
| HMAC | SHA1, SHA256, SHA512 |
| Key Derivation | PBKDF2 with HMAC-SHA1, HMAC-SHA256, HMAC-SHA512 |

### Crypto Parameters

 The `CryptoParam` structure contains all parameters needed for database encryption:

 
| Parameter | Description | Default |
|---|---|---|
| encryptionKey | The raw encryption key | - |
| iterNum | PBKDF2 iteration count | 0 (system-defined) |
| encryptAlgo | Encryption algorithm | AES_256_GCM |
| hmacAlgo | HMAC algorithm | SHA256 |
| kdfAlgo | Key derivation function algorithm | KDF_SHA256 |
| cryptoPageSize | Size of encrypted pages | 1024 bytes |

## Key Management

 The system provides several key management capabilities:

 
 - **System-generated keys**: When no explicit key is provided, the system can generate and manage keys
 - **Key files**: Keys are stored in key files managed by `RdbSecurityManager`
 - **Key rotation**: Support for changing encryption keys

### Key Files

 Encryption keys are stored in key files managed by the `RdbSecurityManager`:

 
```
/path/to/database.db               # Main database file
/path/to/database.db-key           # Current encryption key
/path/to/database.db-newkey        # New key for rotation (if present)
```

 The key files are themselves protected by the system's security mechanisms and accessible only to authorized processes.

## Implementation Details

 
### Encryption Setup in SqliteConnection

 The `SqliteConnection` class handles encryption setup in several key methods:

 
 - `SetEncrypt()` - Main encryption setup function

 
 - Checks encryption configuration
 - Gets/sets encryption key
 - Handles key validation and rotation
 - `SetEncryptKey()` - Sets the encryption key in SQLite

 
 - Calls `sqlite3_key()` to set the key
 - Configures encryption parameters
 - `SetEncryptAgo()` - Configures encryption parameters

 
 - Sets encryption algorithm
 - Sets HMAC algorithm
 - Sets KDF algorithm
 - Sets crypto page size
 - `ReSetKey()` - Handles key rotation

 
 - Calls `sqlite3_rekey()` to change the database encryption key
 - Updates key files

## Security Levels

 The system supports different security levels that can affect encryption requirements:

 
| Security Level | Description |
|---|---|
| S1 | Low security level, for data with low impact if leaked |
| S2 | Medium security level, for data with major impact if leaked |
| S3 | High security level, for data with severe impact if leaked |
| S4 | Critical security level, for data with critical impact if leaked |

 These security levels can be used to determine encryption requirements and key management policies.

## Best Practices

 
 - **Enable encryption for sensitive data**: Always enable encryption for databases containing sensitive information.
 - **Use appropriate security levels**: Choose the security level based on the sensitivity of your data.
 - **Consider custom keys for high-security applications**: For applications with stringent security requirements, provide custom encryption keys rather than relying on system-generated keys.
 - **Validate key strength**: When providing custom keys, ensure they have sufficient entropy.
 - **Secure key storage**: If your application manages its own keys, implement secure key storage mechanisms.
 - **Test encryption overhead**: Database encryption adds processing overhead. Test the performance impact in your application.
 
 
## Limitations and Considerations

 
 - **Performance impact**: Encrypted databases have higher CPU usage and may be slower for read/write operations.
 - **Memory databases**: Encryption is not supported for in-memory databases.
 - **Key loss**: If encryption keys are lost, the database cannot be recovered.
 - **Cross-device compatibility**: When using distributed databases, ensure encryption configurations are compatible across devices.
 - **Backup considerations**: Encrypted databases remain encrypted in backups. Ensure key management supports backup and recovery scenarios.
