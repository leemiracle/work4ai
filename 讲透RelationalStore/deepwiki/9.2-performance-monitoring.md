  This document describes the performance monitoring system implemented in the OpenHarmony Distributed Relational Database Management System. It explains how the system tracks operation execution times, categorizes them based on performance thresholds, and reports statistics for analysis.

 
## Purpose and Scope

 The performance monitoring system provides a mechanism to measure and report the execution time of database operations. It focuses on identifying operations that exceed predefined time thresholds, helping developers identify potential performance bottlenecks in their applications. This system operates with minimal overhead to avoid impacting the actual performance of database operations.

 
## Performance Monitoring Architecture

 The performance monitoring system is implemented primarily through the `RdbStatReporter` class, which works alongside database operations to measure their execution time.

## RdbStatReporter Class

 The `RdbStatReporter` class is the core component of the performance monitoring system. It's designed to be instantiated at the beginning of a database operation and automatically report statistics when the operation completes.

### Usage Pattern

 The `RdbStatReporter` is typically used with RAII (Resource Acquisition Is Initialization) pattern:

 
 - Create an instance at the beginning of an operation
 - When the instance goes out of scope (destructor is called), it calculates the operation's duration and reports if necessary
 
 This pattern ensures that all code paths (including exceptions) are properly monitored without requiring explicit calls to start/stop timing.

## Time Thresholds and Classification

 The system classifies operation durations into different time levels based on predefined thresholds:

 
| Time Level | Duration Range | Classification |
|---|---|---|
| TIME_LEVEL_NONE | < 1500ms | Within expected performance |
| TIME_LEVEL_FIRST | 1500ms to 4999ms | Slow operation (first level) |
| TIME_LEVEL_SECOND | 5000ms to 9999ms | Very slow operation (second level) |
| TIME_LEVEL_THIRD | ≥ 10000ms | Extremely slow (third level) |

 Only operations that exceed the first time level (TIME_LEVEL_NONE) are reported for analysis.

## Reporting Mechanism

 The reporting system has been designed with several important characteristics:

 
 - **Low Overhead**: Reports are submitted asynchronously using a task executor to avoid impacting the database operation's performance.
 - **Rate Limiting**: Reports are rate-limited to prevent flooding the reporting system. A minimum interval of 600 seconds between reports is enforced through the static `reportTime_` variable.
 - **Privacy Considerations**: The store name is anonymized before reporting to protect sensitive information.
 - **Event Information**: Each report includes:

 
 - Operation type (statType)
 - Operation subtype (subType)
 - Bundle name of the application
 - Anonymized store name
 - Performance classification (costTime)

## Integration with Database Operations

 The `RdbStatReporter` is typically integrated into various database operation implementations in the RdbStoreImpl class. When an operation is initiated, an `RdbStatReporter` instance is created with the appropriate operation type. When the operation completes, the reporter automatically calculates and potentially reports the performance statistics.

## Conclusion

 The performance monitoring system provides a lightweight yet effective mechanism for tracking database operation performance. By categorizing operations based on execution time and reporting slow operations, it helps developers identify and address performance bottlenecks in their applications using the relational database management system.

 The system is designed to minimize performance impact while still providing valuable information for analysis, and it includes privacy protections to ensure sensitive data is not exposed in the reports.
