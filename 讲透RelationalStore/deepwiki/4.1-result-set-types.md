  This page documents the different types of result sets in the OpenHarmony Distributed Relational Database Management System and their characteristics. Result sets are data structures that store and provide access to query results from a relational database. For information about navigating and accessing data in result sets, see [Result Set Navigation and Data Access](https://deepwiki.com/openharmony/distributeddatamgr_relational_store/4.2-result-set-navigation-and-data-access).

## Base Result Set Classes

 
### ResultSet Interface

 The `ResultSet` interface defines the core functionality that all result set implementations must provide, including methods to:

 
 - Navigate through the result rows
 - Access data of different types (string, integer, blob, etc.)
 - Get metadata about columns
 - Check the state of the result set
 - Close the result set when done
 
 
### AbsResultSet

 The `AbsResultSet` class provides a base implementation of the `ResultSet` interface that handles common functionality:

 
 - Column name and index mapping
 - Row position tracking
 - Basic navigation operations
 - Data type conversion
 
 Key properties of `AbsResultSet`:

 
| Property | Description |
|---|---|
| rowPos_ | Current row position (-1 means before first row) |
| rowCount_ | Total number of rows in the result set |
| columnCount_ | Number of columns in the result set |
| isClosed_ | Flag indicating if the result set has been closed |
| columnMap_ | Maps column names to their indexes |

### AbsSharedResultSet

 The `AbsSharedResultSet` extends `AbsResultSet` to enable sharing result data through shared memory blocks, which allows for more efficient data access patterns, especially when large amounts of data need to be processed.

 Key features:

 
 - Uses shared memory blocks for data storage
 - Provides methods to manage the shared block
 - Implements optimized navigation methods

## Result Set Data Navigation

 Both result set types share common navigation methods but with different implementation details:

 
| Method | Description | StepResultSet | SqliteSharedResultSet |
|---|---|---|---|
| GoToRow(pos) | Move to specific row | May require reset and iteration | Direct if in current block, or fills block |
| GoToNextRow() | Move to next row | Direct statement step | Updates position in current block |
| GoTo(offset) | Move relative to current position | Multiple steps or reset | May require block refill |
| GoToFirstRow() | Move to first row | Reset and step | Move to position 0 |
| GoToLastRow() | Move to last row | Count rows and go to position | Calculate and go to last position |

## Performance Considerations

 When choosing a result set type, consider the following performance implications:

 
| Aspect | StepResultSet | SqliteSharedResultSet |
|---|---|---|
| Memory Usage | Low (one row at a time) | Higher (block of rows in memory) |
| Sequential Access | Optimized | Good |
| Random Access | Requires reset and re-reading | Optimized with block management |
| Large Result Sets | Better for very large results | Better for medium-sized results |
| Concurrent Access | Limited to originating process | Supports cross-process sharing |
| Access Pattern | Forward-only traversal | Random access and bidirectional |

## Best Practices

 
 - **Choose the Right Implementation**:

 
 - Use `StepResultSet` (QueryByStep) for large result sets with sequential access patterns
 - Use `SqliteSharedResultSet` (QuerySql) for random access patterns or when sharing data between processes
 - **Resource Management**:

 
 - Always call `close()` on result sets when finished to release resources
 - Consider using try-finally blocks to ensure proper closure
 - **Efficient Data Access**:

 
 - Cache column indexes for repeated access
 - Use `getRow()` for retrieving multiple columns at once
 - Consider using `getRows(maxCount)` for bulk retrieval when processing many rows
 - **Column Type Awareness**:

 
 - Check column types when necessary, especially for nullable columns
 - Use the appropriate getter methods to avoid type conversion issues
