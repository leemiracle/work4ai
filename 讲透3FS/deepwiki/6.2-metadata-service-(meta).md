  The Metadata Service (meta) is a critical component of 3FS responsible for implementing file system semantics. It provides a stateless service layer that manages inodes, directory entries, and file sessions, using FoundationDB (FDB) as its transactional persistent back-end.

 
## 1. Overview and Architecture

 The metadata service acts as the bridge between client FUSE/native requests and the persistent metadata stored in FoundationDB. Because all state is persisted in FDB, the metadata service itself is stateless, allowing clients to connect to any available metadata node.

 
### Key Responsibilities

 
 - **Inode Management**: Creation, deletion, and attribute updates for files and directories.
 - **Directory Operations**: Atomic directory manipulation (move, recursive delete) and directory entry (dentry) management.
 - **Session Management**: Tracking open file sessions and handling lease-based cleanups.
 - **Chain Allocation**: Determining which storage chains should host a file's data chunks based on layout policies.
 - **ACL Enforcement**: Validating user permissions (UID/GID) against stored Access Control Lists.

## 2. Inode and File Management

 3FS metadata is organized into Inodes. Files are split into equally sized chunks, which are striped across multiple replication chains.

 
### File Layout and Chaining

 The `Layout` class defines how a file's data is distributed. It includes the `ChainTableId`, `chunkSize`, and `stripeSize` [src/fbs/meta/Schema.cc93-127](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L93-L127)

 
 - **Chunk Identification**: The `getChunkId` function calculates the specific `ChunkId` for a given file offset [src/fbs/meta/Schema.cc62-73](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L62-L73)
 - **Chain Mapping**: The `getChainId` function maps a file offset to a specific `ChainId` by consulting the `RoutingInfo` provided by the Management Service (mgmtd) [src/fbs/meta/Schema.cc75-91](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L75-L91)
 
 
### Chain Allocation

 The `ChainAllocator` is responsible for selecting storage chains for new files. It ensures that data placement follows the cluster's routing logic.

 
| Function | Description |
|---|---|
| checkLayoutValid | Validates that the requested layout (stripe/chunk size) is supported by the current routing table src/meta/components/ChainAllocator.h28-47 |
| allocateChainsForLayout | Performs a round-robin allocation of chains for a new file to balance load across the storage cluster src/meta/components/ChainAllocator.h49-80 |

## 3. File Operations and Storage Interaction

 While the metadata service primarily talks to FDB, it occasionally interacts with the Storage Service to synchronize file states, specifically for determining the actual length of a file.

 
### Querying File Length

 Because writes are handled directly between clients and storage nodes (CRAQ), the metadata service may not always have the most up-to-date file length. The `FileOperation::queryChunks` and `queryChunksByChain` functions are used to query storage nodes for the `lastChunkId` to calculate the current file size [src/fbs/meta/FileOperation.cc45-79](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/FileOperation.cc#L45-L79)

## 4. Session Management

 The `SessionManager` tracks active file sessions to handle multi-client coordination and cleanup.

 
### Session Lifecycle

 
 - **Creation**: When a client opens a file, a session is created and persisted in FDB.
 - **Heartbeats**: Clients must maintain sessions; otherwise, they are considered stale.
 - **Pruning**: The `SessionManager` runs background `ScanTask` workers that identify timed-out sessions [src/meta/components/SessionManager.h91-102](https://github.com/deepseek-ai/3FS/blob/22fca045/src/meta/components/SessionManager.h#L91-L102)
 - **Cleanup**: Stale sessions are processed by `CloseTask` workers, which perform necessary metadata cleanups and synchronization [src/meta/components/SessionManager.h105-113](https://github.com/deepseek-ai/3FS/blob/22fca045/src/meta/components/SessionManager.h#L105-L113)
 
 
### Configuration

 Session behavior is controlled via hot-updatable parameters:

 
 - `scan_interval`: Default 5 minutes [src/meta/components/SessionManager.h48](https://github.com/deepseek-ai/3FS/blob/22fca045/src/meta/components/SessionManager.h#L48-L48)
 - `session_timeout`: Default 5 minutes [src/meta/components/SessionManager.h51](https://github.com/deepseek-ai/3FS/blob/22fca045/src/meta/components/SessionManager.h#L51-L51)

## 5. Security and ACL Enforcement

 3FS implements POSIX-style permissions via the `Acl` class.

 
### Permission Logic

 The `checkPermission` function validates a `UserInfo` object against the Inode's `uid`, `gid`, and `perm` bits:

 
 - **Root**: UID 0 is always granted access [src/fbs/meta/Schema.cc27-28](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L27-L28)
 - **Owner**: If `user.uid == acl.uid`, owner bits are checked [src/fbs/meta/Schema.cc29-30](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L29-L30)
 - **Group**: If the user is in the Inode's group, group bits are checked [src/fbs/meta/Schema.cc31-32](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L31-L32)
 - **Other**: Otherwise, the "other" bits are used [src/fbs/meta/Schema.cc33-34](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L33-L34)
 
 
### Recursive Operations

 For operations like `rm -rf`, the `checkRecursiveRmPerm` function ensures the user has write/execute permissions on the directory and handles the "sticky bit" (S_ISVTX) correctly [src/fbs/meta/Schema.cc48-60](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/Schema.cc#L48-L60)

## 6. Implementation Details

 
### Shuffle Methods

 To ensure uniform data distribution, 3FS uses various shuffle algorithms when selecting chains. The system supports `stdshuffle`, `g++10`, and `g++11` shuffle implementations to maintain compatibility across different compiler versions [CMakeLists.txt30-32](https://github.com/deepseek-ai/3FS/blob/22fca045/CMakeLists.txt#L30-L32)

 The `hf3fs_shuffle` utility wraps these implementations, and the `find_safe_seed` function is used to find seeds that produce consistent results across different GCC versions [src/common/utils/Shuffle.h162-206](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/Shuffle.h#L162-L206)

 
### Performance Instrumentation

 Metadata operations are heavily instrumented using recorders to track latency for:

 
 - `queryLastChunkLatency`
 - `queryTotalChunkLatency`
 - Failed operation counts [src/fbs/meta/FileOperation.cc14-30](https://github.com/deepseek-ai/3FS/blob/22fca045/src/fbs/meta/FileOperation.cc#L14-L30)
