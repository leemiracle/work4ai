  This page documents the core concurrency and coroutine utilities used throughout the 3FS codebase. These primitives provide the foundation for high-performance, non-blocking operations, ranging from specialized thread pool management to sophisticated coroutine-aware synchronization.

 
## Coroutine Execution Framework

 3FS leverages `folly::coro` extensively to handle asynchronous operations without the complexity of manual state machines.

 
### DynamicCoroutinesPool

 The `DynamicCoroutinesPool` provides a managed environment for executing coroutines with a configurable degree of parallelism. Unlike a standard thread pool, it manages a fixed or dynamic number of persistent coroutine "workers" that pull tasks from a shared queue.

 
 - **Task Queueing**: Tasks are enqueued into a `CoroQueue` (an asynchronous producer-consumer queue) [src/common/utils/DynamicCoroutinesPool.h55](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/DynamicCoroutinesPool.h#L55-L55)
 - **Worker Lifecycle**: The `run()` method defines the lifecycle of a worker coroutine. It continuously de-queues tasks and executes them until a `nullptr` is received, signaling shutdown [src/common/utils/DynamicCoroutinesPool.cc67-82](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/DynamicCoroutinesPool.cc#L67-L82)
 - **Dynamic Scaling**: The number of active coroutines can be adjusted at runtime via `setCoroutinesNum`. If the number increases, new `run()` coroutines are scheduled on the underlying `executor_`. If it decreases, `nullptr` tokens are enqueued to gracefully terminate workers [src/common/utils/DynamicCoroutinesPool.cc38-65](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/DynamicCoroutinesPool.cc#L38-L65)
 - **Monitoring**: It tracks the current number of running coroutines using `ValueRecorder` [src/common/utils/DynamicCoroutinesPool.cc11](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/DynamicCoroutinesPool.cc#L11-L11)
 
 
### CPUExecutorGroup

 While 3FS uses standard Folly executors, it often wraps them in a `CPUExecutorGroup` to manage multiple thread pools as a single logical unit, allowing for better isolation of different workload types (e.g., metadata ops vs. data I/O).

 
### Executor Statistics Reporting

 The `ExecutorStatsReporter` template class provides standardized metrics collection for various executor types, including `CPUExecutorGroup`, `folly::CPUThreadPoolExecutor`, and `folly::IOThreadPoolExecutor` [src/common/utils/ExecutorStatsReporter.cc38-40](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/ExecutorStatsReporter.cc#L38-L40)

 **Metrics Captured:**

 
| Metric Name | Description |
|---|---|
| thread_count | Total threads in the pool. |
| idle_thread_count | Threads currently waiting for work. |
| active_thread_count | Threads currently executing tasks. |
| pending_task_count | Tasks in the queue waiting for a thread. |

## Synchronization Primitives

 
### AtomicSharedPtrTable

 The `AtomicSharedPtrTable` is a specialized concurrent data structure designed for high-frequency allocation and retrieval of shared objects (like session handles or connection contexts) using integer indices.

 
 - **Slot Management**: It uses an `AvailSlots` helper to manage a bitset-like pool of available indices [src/common/utils/AtomicSharedPtrTable.h10-49](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/AtomicSharedPtrTable.h#L10-L49)
 - **Atomic Access**: The table itself is a `std::vector` of `folly::atomic_shared_ptr<T>`, ensuring that updates to specific slots are thread-safe and lock-free for readers [src/common/utils/AtomicSharedPtrTable.h74](https://github.com/deepseek-ai/3FS/blob/22fca045/src/common/utils/AtomicSharedPtrTable.h#L74-L74)
 - **Memory Efficiency**: It allows for O(1) access via index while maintaining the safety of `std::shared_ptr`.
 
 
### Coroutine-Aware Locking

 3FS utilizes several primitives that are "coroutine-safe," meaning they suspend the calling coroutine rather than blocking the underlying OS thread when a lock is unavailable.

 
 - **CoLockManager**: (Referenced in system architecture) Manages distributed or local locks specifically for coroutine environments, preventing deadlocks on executor threads.
 - **FairSharedMutex**: A shared-exclusive lock implementation that ensures fairness between readers and writers, preventing writer starvation which is critical in metadata-heavy workloads.
