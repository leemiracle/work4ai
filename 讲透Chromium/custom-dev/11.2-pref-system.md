# 11.2 · 偏好系统 PrefService 与默认值定制

> 改浏览器默认行为（首页/搜索引擎/安全开关/UI 偏好）最正规的路不是改代码分支，而是动 pref：注册表、默认值、策略覆盖三层机制全解。附本库又一重大勘误——pref 服务化已被官方删除。

## ① 角色定位

pref 是 Chromium 的"注册化配置总线"：每个可配置行为一个 key，值经 PrefService 读取，写入 JSON（profile 内 Preferences 或全局 Local State，11.1）。代码面三件套：`components/prefs/`（PrefService/PrefStore 家族库）、`chrome/browser/prefs/browser_prefs.cc`（3050 行注册总枢纽）、策略系统（policy 注入最高优先级）。

## ② 定制切入点全景表

| 想改什么 | 动哪里 | 难度 | 影响面 |
|---|---|---|---|
| 改某 pref 默认值 | 注册处：`browser_prefs.cc` 内 `RegisterBooleanPref(key, false)` 第二参（样例 :1164-1165 指纹防护/IP 保护默认 false）——grep key 找注册点改默认值 | 改配置 | 开箱行为 |
| 加自家 pref | `RegisterProfilePrefs`（:1964，profile 级）或 `RegisterLocalState`（:1630，全局级）里加注册 + 业务代码 `GetBoolean/SetBoolean` | 改逻辑 | 新配置项 |
| profile 级 vs 全局选择 | profile 级进 `Preferences` JSON（随用户走），全局进 `Local State`（随安装走）——两注册函数分野（:1630/:1964） | 设计决策 | 数据归属 |
| 命令行覆盖 pref | `--force-fieldtrials` 类之外的正道：`chrome_command_line_pref_store.cc`（命令行→pref 桥） | 改配置 | 测试/调参 |

## ③ 关键源码走读：一个 pref 的读写全链

**第一站：注册（编译期+启动期）。** `chrome/browser/prefs/browser_prefs.cc` 是总枢纽：`RegisterLocalState(PrefRegistrySimple*)`（:1630）注册全局项，`RegisterProfilePrefs(user_prefs::PrefRegistrySyncable*, locale)`（:1964）注册 profile 项。**每个 RegisterXxxPref 声明 key 的类型与默认值**——默认值改动就在注册现场（grep 你的 key → 改第二参）。

**第二站：值解析栈（运行期）。** PrefService 聚合多个 PrefStore 按优先级取值：命令行 store（`command_line_pref_store.cc`）＞策略 store ＞用户值（Preferences JSON）＞**默认值 store（`default_pref_store.cc`）**。这就是"改默认值只影响未显式设置的用户"的机制根源——**已写 JSON 的老用户不受默认值改动影响**（产品上常见误解：改了默认值以为全体生效）。

**第三站：服务化架构已删（本库勘误）。** `services/preferences/README.md:6-7` 原话："The Preference Service is no longer an independent service. The implementation was deleted"（2019 年 CL 1928248）。**老架构文里"pref 走 mojo 独立服务"的说法已过时**——现行是 browser 进程内 PrefService（跨进程场景由使用方自行经 mojo 同步，如 renderer 侧的 WebView 消息）。查资料遇到 services/preferences 教程一律按历史处理。

## ④ 实操：出厂默认定制三连

1. **改默认搜索引擎**：grep homepage/search 相关 key 的注册点（browser_prefs.cc 或 components/search_engines 侧注册）改默认值；
2. **加自家开关**：RegisterProfilePrefs 加 `registry->RegisterBooleanPref(prefs::kMyAiPanelEnabled, true);`（key 常量放 chrome/common/pref_names.h 一带）+ 业务处 profile->GetPrefs()->GetBoolean 消费 + chrome://settings 加 UI（4.2 的 WebUI 流程）；
3. **首装批量的正确姿势**：改注册默认值（新用户/新 profile）+ master_preferences（首装一次注入）双管齐下，别在运行时代码里 if 首次——那是反模式。

## ⑥ 坑与勘误

- **默认值 ≠ 全体生效**（§3 第二站机制根源）：只对"从未写过该 key 的 profile"生效；改全体要配迁移逻辑（:1237 范式）。
- **pref 服务化已删**（README 实证）——旧教程的 mojo pref service 架构图过时。
- profile 级/全局级放错边：放全局的项在多 profile 间共享（音量类合适、账号类灾难）——先想数据归属再选注册函数（:1630 vs :1964）。
- PrefService 非线程自由：跨线程访问要走 task post 到所属序列（11.1 的 KeyedService 时序坑同类）。
- pref key 是全局字符串命名空间：新 key 先 grep 防撞名；`prefs::` 前缀常量集中在 pref_names.h 系文件。
- 注册了不用的 key 会进"未消费"清理清单（有 lint 跟踪），长期不删被 OWNERS 说。

## ⑦ 验证方法

- chrome://prefs-internals 或 about:settings 搜索 key 看当前值与来源（命令行/策略/用户/默认 四态标注）
- 新 profile 开箱值检查（11.1 §7 的双 profile 法）
- 命令行覆盖验证：对应 switch 起动后 prefs-internals 应显示 command_line 来源
- 策略态：chrome://policy 注入测试值后 pref 值应锁死
