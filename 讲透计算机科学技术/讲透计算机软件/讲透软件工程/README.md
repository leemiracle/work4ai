# 讲透软件工程 · 千人协作的纪律

> 这支负责：**怎么让千百人合写一个还不崩的东西**——过程、需求、架构、
> 测试、度量、维护。软件家族里唯一一支"社会科学含量"最高的分支：
> 它的核心难题是人，不是代码。
>
> GB/T 13745：52040·软件工程。家族：[讲透计算机软件](../README.md)。

## 诞生

1968 NATO Garmisch 会议："软件工程"一词诞生于承认失败——OS/360 的泥潭
（5000 人年，延期交付，永远修不完的 bug）。Brooks 1975《人月神话》
把教训升格为定律：**向进度落后的项目加人只会更落后**（沟通成本按 n² 增长）。
此后五十年：结构化方法→面向对象→敏捷宣言（2001，17 人滑雪场的价值观声明）→
DevOps→平台工程。

## 核心问题（已解决/未解决）

- ✅ 演进式开发（敏捷/持续交付——小步反馈回路的制度化）
- ✅ 测试金字塔与自动化回归（单元/集成/端到端的分层策略）
- ✅ 代码评审制度（社会化缺陷预防的工程化）
- 🔄 生产力度量（DORA 四指标——部署频率/变更前置时间/恢复时间/变更失败率）
- 🔄 供应链安全（SBOM/签名/依赖审计——2021 Log4j 后的制度化）
- ❌ Brooks 定律（1975 年开的药方——"没有银弹"1986 年的预言——至今无根治）
- ❌ 软件估算（"人月"的计量单位本身是错的：人与月不可互换）

## 这支最美的一个事实

**Brooks 定律是一个图论结论**：n 人项目沟通信道数 = n(n-1)/2——
加人=给已经拥堵的网络加节点。软件工程最著名的"经验定律"
其实是组织拓扑的数学。

## 假设与依赖

假设软件的复杂度是**本质的**（Brooks：复杂度/一致性/可变性/不可见性四重本质
——工具只能削"偶然复杂度"）；假设人是理性的且会离开（文档与交接的制度设计）。
上游：全家族（工程纪律约束所有六支）；管理侧：[讲透管理](../../../讲透管理/)。
