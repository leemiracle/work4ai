# 03 · 可构造与结构：软件是构造出来的，还是长出来的

> **本章回答五问之四（家族层）：可构造？结构？**
> 软件家族的可构造性是全部数学家族里最强的——**一切皆可构造，且构造过程就是产品本身**
> （源码=构造步骤的忠实记录）。真正的问题是结构：软件的"刚性"从哪来？
> 为什么有的系统改一处而全身不抖，有的改一行就全线崩溃？

---

## 一、可构造：编译器是一台"构造机器"

直觉图像：编译器是**把描述变成构造物的自动机**——你写下"是什么"（源码），
它产出"怎么造"（目标码）。这个单向自动化的存在，是软件业与一切传统工程的
分水岭（造桥不能"编译"出一座桥）。

| 构造物 | 构造路径 | 可构造性档位 |
|---|---|---|
| 源码 | 人写（或 LLM 生成）+ 编译器检查 | ✅ 完全 |
| 目标码 | 编译器自动 | ✅ 完全（确定性：同源码同产物） |
| 正确性证明 | 程序逻辑 + SMT/证明器 | 🔄 半自动（循环不变式仍靠人） |
| 好架构 | 无自动路径 | ❌ 构造不出——只能"长"（重构/演化） |

**反直觉发现**：**架构不可构造**。五十年软件工程的最大教训是
好结构不能像编译一样一键生成——它是演化 + 选择的结果（Unix 的 pipes、
HTTP 的无状态，都是事后被追认的"好结构"）。这就是为什么 04 章
"自己写玩具"仍然不可替代：你需要亲手感受结构如何从约束中长出来。

## 二、类型即构造性证明（Curry–Howard 的工程面）

类型系统 = 软件家族的"可构造性账本"：

| 命题（类型论） | 构造（程序论） |
|---|---|
| 命题 A | 类型 A |
| A 的证明 | 类型 A 的值 |
| 蕴含 A→B | 函数 A→B |
| 证明 A→B | **写出一个函数** |
| 无证明的命题 | 空类型（如 Void） |

**为什么是这样**：类型检查通过 = 编译器替你验证了一条（弱化版）逻辑证明——
"这个值存在"的构造性证明。这就是 Rust 能宣称"无数据竞争"的底牌：
不是测试出来的，是**类型系统作为证明检查器**逐条检查的。
（数学本体见 [计算机数学 03 章](../../讲透数学/讲透计算机数学/03-可构造与结构.md)。）

✨ **美之时刻：自举（Bootstrapping，1958 起）**
一句话：编译器编译自己——用 C 写的编译器编译出能编译 C 的编译器。
为什么美：**自指而不自毁**（对照停机定理的自指毁灭）：自举成立靠的
是"最小核 + 逐级抬升"——先手写汇编级小编译器，再用它编译更大的自己。
**必然**：这条路线与生物学（DNA→核糖体→DNA）同构，是复杂系统
自我构造的通用模板。
怎么亲历：`experiments/04_toy_interpreter.py` 里用 Python 写 Lisp 解释器——
再想象用这个 Lisp 写出 Lisp 解释器（60 行，网上有现成对照），自举的
最小样本就完成了。

## 三、结构：分层契约 + 不变式 + 一致性边界

软件的结构刚性从三个来源，缺一不可：

### 3.1 分层契约（Layered Contracts）

每层向下只依赖契约（API/ABI/协议），不依赖实现——Unix syscall、SQL、HTTP
都是契约。**刚性来源**：契约稳定，实现可换（Linux 换了三十年实现，
syscall 契约不动）。

### 3.2 不变式（Invariants）

数据结构的"宪法"：红黑树的五条性质、B+ 树的有序性、事务的 ACID。
**刚性来源**：所有操作绕不变式设计——破坏不变式的操作在类型或断言层被拒。

### 3.3 一致性边界（CAP 与事务）

分布式软件的结构难题：网络分区下，一致性与可用性不可兼得（CAP，Brewer 2000）。
**为什么重要**：它划出了软件结构的**物理极限**——不是工程没做好，
是定理不许。各种数据库的"结构个性"（BASE/最终一致/线性一致）都是
在 CAP 边界上的站位选择。

**三者合一的检验**：一个架构能不能讲清楚它的契约在哪、不变式在哪、
一致性边界在哪——讲不清的架构，改一行就崩（"Shotgun Surgery"式脆弱）。

📖 故事框：**Unix 哲学 vs 面向对象**。"小而锐利的工具组合"（McIlroy 1978）
与"一切皆对象"（Smalltalk 系）是两种结构美学。五十年下来管道哲学在
AI 时代回潮（Unix pipe → LLM 工具链编排）——结构的选择是轮回不是进步。

## 四、Python 层

[`experiments/04_toy_interpreter.py`](experiments/04_toy_interpreter.py) 的三个结构观察点：
1. `Environment` 的父指针链 = 作用域的**分层契约**（每层只信父链）
2. `eval` 对特殊形式的分派 = 语言核心的**不变式**（define 必须先于使用）
3. 递归 `fib` 的深度 = 构造性证明的**成本**（证明 fib(15)=610 跑了 1973 次调用——
   Curry–Howard 说"证明=程序"，代价也相等：证明有多长，程序就跑多久）

## 五、不足层

- 架构知识仍是手艺（tacit knowledge）——不可构造部分没有被理论完全覆盖，
  Brooks 的"没有银弹"（1986）四十年后仍成立
- 并发结构（锁/无锁/事务内存）的正确性论证依赖内存模型细节，跨平台不一致
- 本章以系统软件为纲；AI 软件的结构（模型的"不变式"是什么）是开放问题——
  归 52020 人工智能家族与 [`讲透模型`](../../讲透模型/)

## ✍️ 练习

1. 给你手头项目的一个核心数据结构写出不变式（3 条以内）——写不出来的，
   它的每个用户都在赌运气。
2. 在玩具解释器里故意破坏 Environment 父链，观察哪个函数最先暴露错误——
   体会"不变式被破坏时，错误现场离案发现场很远"。
3. 反直觉题：为什么"更严格的类型系统"（更少的合法程序）反而构造出**更多**的
   可能结构？（提示：约束即骨架）

## 📌 收束

软件家族的构造观一句话：**能编译的都好办，长出来的才值钱**——
可构造性解决"有没有"，结构解决"活不活得久"。

**👀 这章给了你什么新眼睛**：看任何系统先找它的三类结构资产
（契约/不变式/一致性边界）——三者齐全的系统才配谈"可维护"。
