# 04 · 计算机基础转代码：从正则引擎到 SAT 求解器

> **本章回答五问之五（本家族：讲透计算机基础）。**
> 本家族是**最不缺代码**的家族——它的定理本来就是程序。
> 真正的问题反过来：**哪些理论保证能原样落进工程，哪些在落地时变形**。

---

## 一、五条走廊总表

| 走廊 | 理论资产 | 工程化身 | 保真度 |
|------|---------|---------|--------|
| ① 正则→引擎 | Kleene 定理/子集构造 | RE2、grep、词法分析器 | ★★★ 完全保真（线性时间保证照搬） |
| ② 复杂度→选型 | 下界/均摊分析 | API 设计时限/容量规划 | ★★ 定性保真（常数与缓存另算） |
| ③ 不可判定→半自动 | Rice/停机 | 静态分析/终止性检查器（sound 不完备） | ★★ 形态改变（保证换成"漏报为零"） |
| ④ 困难性→密码 | 单向函数假设 | TLS/PQC/零知识 | ★★ 假设即地基（FIPS 203/204/205） |
| ⑤ 规范→验证 | Hoare/时序逻辑 | TLA+、验证编译器、SMT | ★★ 证明换人工（不变式要人供） |

**为什么是这样**：本家族的定理形态分两种——**构造性定理**（子集构造、
堆化、Thompson）直接翻译成代码；**不可能性定理**（Rice、下界）翻译成
**工程边界**——它们不产出代码，产出的是"别在这里烧钱"的路标。

## 二、逐条速写

### 走廊① 正则→引擎（完全保真的样板）

正则表达式 `--NFA（Thompson 构造）-->--DFA（子集构造）-->状态机执行`，
每一步都是数学定理的直接实现。RE2/Go regexp 保证**线性时间**——
因为 DFA 匹配是 O(n·m) 上界封死，没有回溯爆炸。反例警示：Perl/Python 的
回溯引擎不是这条走廊（NFA 回溯模拟），所以有 ReDoS（灾难性回滚）——
**2016 年 Stack Overflow 官网宕机 34 分钟，起因一条正则**。
同一定理，走不走走廊，工程命运截然不同。

### 走廊② 复杂度→选型（工程师日用件）

- 比较排序下界 → 大数据不再排序，改基数/外部排序（换模型破墙）
- 均摊 O(1)（动态表倍增）→ vector/Go slice 的扩容策略，云存储容量规划
- NP 完全性识别 → 见到问题先归约试探（"这是不是披着业务皮的 SAT？"），
  是了就上求解器而不是硬写启发式

### 走廊③ 不可判定→半自动（形态改变）

静态分析器（null 检查/资源泄漏）必须 sound 不完备（Rice 墙）——
**告警皆真、漏报未知**，这是推销话术与数学事实的分界线。
终止性检查器（Why3/AproVE）对受限循环类自动证、其余转人工。

### 走廊④ 困难性→密码

加密库是本家族最严格的工程：常数时间实现（分支/访存模式与密钥无关）——
**性能工程的反面战场：为了让"性能"与"秘密"无关，宁可牺牲速度**。
[讲透GPU与系统级](../../讲透GPU与系统级/) 的常规优化（分支消除/预取）在这里
要过安全审查：优化产生的时序差=侧信道。

### 走廊⑤ 规范→验证

TLA+/TLA（AWS：S3 一致性协议、DynamoDB 复制的规范层查错）；
SMT 求解器（Z3）把"找反例"变成解方程——Klee 符号执行、智能合约审计的引擎。

## 三、可机械化边界（三件套之一）

| 任务 | 可机械化程度 | 边界原因 |
|------|------------|---------|
| 正则匹配 | 全自动+最优 | 理论完全闭环 |
| 模型检查（有限状态） | 全自动（状态爆炸是工程墙） | 有限性 |
| 语义 bug 查找 | 半自动（sound 不完备） | Rice 定理 |
| 不变式推断 | 半自动（小循环全自动/大程序人供） | 语义不可判定 |
| 密码安全审计 | 半自动（形式化协议证明可全自动，实现侧信道难全自动） | 物理侧信道 |

## 四、代码走廊清单（三件套之二：问题类→算法→库）

| 问题类 | 算法 | 库/工具 |
|--------|------|--------|
| 文本匹配/词法 | Thompson NFA+子集构造 | re2、ragel、lexer 生成器 |
| 布尔可满足 | DPLL/CDCL | minisat、z3、kissat |

## 五、工程师落点（三件套之三）

1. **正则的安全用法**：对外部输入的正则一律 RE2 系（线性保证）；
   评审见回溯特征（嵌套量词）直接打回
2. **下界是容量规划的地基**：n log n 不是"理论洁癖"，是"为什么这个批处理
   再加机器也只能线性加速"的答案——加速比看并行度，别指望算法 magically 更快
3. **NP 完全问题别硬刚**：SAT/ILP 求解器已经工业级（芯片验证/排班/物流），
   把业务约束编码给求解器，常常赢过手写启发式
4. **安全代码的性能纪律**：密码热路径禁数据依赖分支/表索引（常数时间），
   benchmark 时序方差与吞吐同样重要
5. **复杂度承诺 ≠ 生产延迟**：RAM 模型到真实机器差缓存层级——
   [讲透GPU与系统级](../../讲透GPU与系统级/) 是第二遍校准的地方

## Python 层

[experiments/thompson_regex.py](experiments/thompson_regex.py) 完整走走廊①：
解析正则→Thompson NFA→子集构造 DFA→匹配执行，并在经典指数族
`(a|b)*a(a|b){n}` 上实测"NFA 状态线性 vs DFA 状态 2ⁿ"——
看一眼就知道为什么 RE2 选在 NFA/DFA 之间做权衡（惰性构造+缓存）。

## ✍️ 练习

1. 把你们系统的一条校验规则改写成正则并测量：先跑 Python `re`（回溯），
   再跑 `google-re2`（如果可用）——构造一个让两者差 1000× 的输入
2. 用 z3（pip install z3-solver）解一个 3 变量 SAT，再把一个排班小需求
   编码成 SAT——体会"业务问题=求解器早餐"
3. 解释为什么常数时间比较（`hmac.compare_digest`）比 `==` 慢是**特性**：
   写出时序侧信道如何利用 `==` 的早退行为

## 这章给了你什么新眼睛（认知升维）

1. **走廊眼**：看任何理论定理先分类——它是构造（直接翻译）还是不可能性
   （变成边界/预算/取舍）？决定你在工程上怎么用它
2. **sound 眼**：用静态分析工具先问"sound 还是 complete"——
   告警全真（漏报未知）还是告警可能漏（全真性不保证），误用会出事故
3. **常数时间眼**：安全与性能的冲突点有固定形态（时序=信息），
   认出它就明白为什么有些代码"慢得理直气壮"
