# 讲透计算机科学技术 · 问题转 code 路由表

> **定位**：本表把计算机科学技术学科**真实的典型问题/任务**逐条翻译成 code 任务。
> 分工一句话：家族 04 章管「**边界与走廊**」——哪些问题能转、走哪条走廊、
> 承诺强度多高（可机械化边界/代码走廊/裂缝）；本表管「**具体问题怎么接单**」——
> 一个来路明确的问题，形式化成什么、写成什么代码任务、用什么算法库、坑在哪、归哪个家族管。
> 六家族全景与挂靠成员见 [README.md](README.md)；姊妹表见
> [信息科学与系统科学 · 问题转code路由](../讲透信息科学与系统科学/问题转code路由.md)。

## 使用方法

1. 拿到问题，在「领域问题/任务」列找**最近邻**——现实问题多以口语形态到达，先对上号再谈翻译。
2. 看「形式化后」列：**形式化即定价**——数学对象译错（该是图的问题译成了表），后面全错。
3. 看分层标预定预期：
   - **[A 可直接编码]**：规格明确，天到周级出活；
   - **[B 需先建模]**：必须先补数学模型/规格，建模占一半以上工作量，**规格与代码要一起入档**；
   - **[C 研究级开放]**：无成熟算法或定义仍在竞争，只能出研究原型，**别承诺工期**。
4. 「落点家族」是深钻入口：进该家族 04 章读这条走廊的完整边界分析（承诺强度/裂缝/练习）。
5. C 层问题的正确姿势：把"解决它"改写成"**度量代理指标+诚实标注边界**"——
   本仓库不把研究包装成工程。

口径说明：本表每行给的是**最小可接单形态**——真实工程常是多行组合
（例：#8 推理服务 ≈ #17 的 kernel 视角 + #7 的评估残留问题），
组合时按行分别核对形式化与坑，不要只取并集。

## 分层怎么判（三问）

1. **规格能否今天写出来？** 能——A；要补方程/文法/规格——B；连"对"的定义都还在争——C。
2. **有没有生产级库？** 有且敢背书——A；有但要先建模才能喂——B；只有论文复现——C。
3. **验收断言写得出吗？** 写得出（已知解/参考对照）——A/B；只能"看起来对"——退回，重新定义问题。
4. **谁背书？** 库/标准/契约的承诺——可验收；论文数字——按 C 打折（复现方差常大于报告效应）。

## 三层占比（一句话）

34 题中 **A 13 / B 17 / C 4**——即便在可编码密度最高的学科，"需先建模"仍占半壁：
**计算机科学的难点不在写码，在规格与边界**。分家族看：基础/应用 A 为主
（理论闭环/规格明确），软件/系统结构 B 为主（建模即工程），C 层集中在
"合同外行为"（侧信道/逆向/学习证书/学习引导求解）——合同内全自动，合同外只有攻防与研究。
与姊妹表对照（A/B/C≈14/14/3）：两宇宙合读可见，"需先建模"是跨学科的普遍主旋律。

## 通用工作流（问题→形式化→选走廊→写断言）

1. **问题→形式化**：把口语问题写成数学对象——语言/文法、图、方程、优化问题、
   状态机、契约。判据：这份表述能否交给别人而不产生歧义；不能，回炉。
   例："日志里提取错误码"=正则语言（#1）；"这段代码安不安全"=不可判定，
   要降格成 #3/#4 的有界问题才有 code 任务。
2. **形式化→选走廊**：查落点家族 04 章的走廊表，确认**承诺强度**
   （跑得出/算得准/证得明）——别拿"跑得出"的走廊去承诺"证得明"的结论。
3. **选走廊→写码**：算法照抄走廊清单，**库优先于自写**（自写仅限教学目的或有
   性能/安全证据）；B 层任务先落规格再落码，规格与代码同库入档。
4. **写码→写断言**：开工前先写断言——已知解、不变式、参考实现对照（各家族
   `experiments/` 的断言即范本）。

> **任务完成的定义是断言绿，不是"能跑"**——断言绿之前，一切"跑通了"都只是观察；
> 这条纪律在 CI 文化里叫"红-绿"，在本仓库各家族 `experiments/` 里叫"断言当测试"。
