# 03 — 评估驱动开发：eval 是 AI PM 的 spec

> "没有 eval，你无法知道一个改动让系统变好还是变坏。你是在盲飞。"（techcerted.com, 2026-06）
> "Evals 是 AI PM 的 spec 等价物；它是团队在第一行模型代码写下之前对'成功长什么样'的对齐方式。"（agenticcareers.co, 2026-04）
> 行业共识：**evals 是企业 AI 落地最大的瓶颈**——拥有 evals 的 PM 拥有产品的质量（aiarch.dev, 2026）。

---

## 03.1 为什么 eval 是 AI PM 的核心技艺

回顾 00 章的概率性 spec："拒绝率 ≥99%，有用率 ≥95%，幻觉率 ≤2%"。这些数字从哪来、怎么测、谁判定——**这三个问题就是 eval 设计**。

eval 在 AI 产品里同时扮演四个角色：

1. **Spec**——写下"好"的可测定义，团队开工前对齐
2. **发布门**——达标才上，不达标不上（替代"QA 通过"）
3. **回归网**——换模型/改 prompt/改检索后，确认没把别处改坏
4. **监控源**——上线后的质量漂移信号

## 03.2 eval 的四层栈（从离线到在线）

```
L1 离线 eval 集（静态测试集 + 期望行为）      ← PM 主导设计
L2 人工 rubric 评估（抽检 + 评分标准）         ← PM 拥有 rubric
L3 LLM-as-judge（模型判模型，规模化）          ← PM 验证 judge 一致性
L4 在线信号（thumbs/任务完成/保留/漂移看板）   ← PM 定告警阈值
```

### L1 离线 eval 集：你的单元测试

**构成**：50-500 条精心构造的（输入, 期望行为）对。三个来源：
- **真实用户查询的分层抽样**（最接近生产分布——线上日志是金矿）
- **边界案例**（edge cases：长尾指令、对抗输入、歧义、多语言、超长上下文）
- **金标准集**（golden set：专家确认的标准答案，用于回归）

**PM 的具体工作**：定义覆盖矩阵（场景 × 难度 × 风险等级），保证 eval 集不为"容易的部分"过拟合。**一个只测简单查询的 eval 集会给你虚假的安全感。**

### L2 人工 rubric：质量的ground truth

离线 eval 测不了"语气好不好""结构合不合理"——这些用 rubric：定义维度（有用性/事实性/安全/格式）× 每维 1-5 分锚点描述。**抽检 500 条比全量自动化更可信**（00 章 spec 里"幻觉率 ≤2%（人工 rubric 抽检 500 条）"的由来）。

### L3 LLM-as-judge：规模化的代价与校准

用强模型评判输出。两个必答问题：
1. **Judge 与人的一致性多少？**（用 L2 的人工标定子集测 judge 的准确率，不一致的维度回 L2）
2. **Judge 的偏差谱**：偏好长答案？偏好自家模型家族？位置偏差（对比评估时先看的赢）？

**纪律**：judge 只在"校准报告存在"的前提下可信。PM 要看的不是 judge 分数，是**judge 与人工的一致性报告**。

### L4 在线信号：分布漂移的雷达

上线后质量会漂移（用户人群变了、市场活动引来新用户、模型版本升级）。在线监控的最小集：

| 信号 | 含义 | 典型告警 |
|---|---|---|
| thumbs up/down 率 | 显式满意 | 周环比降 >5pp |
| 任务完成率（funnel） | 真实价值 | 分段下跌 |
| **"答坏用户的 7 日留存"** | 信任损伤（02 章） | 对照组差 >10% |
| 人工介入率（agent 类） | 自治失败 | 升高 = 降档（04 章） |
| 输出长度/延迟分布漂移 | 行为漂移先兆 | 分布形状突变 |

## 03.3 eval 驱动的 PRD 长什么样（模板）

```markdown
## 功能：合同风险扫描（示例）
### 用户价值
律师在 10 分钟内找到 50 页合同里不可接受的条款。
### 成功定义（eval 门槛）
- 高风险条款 recall ≥ 0.95（漏检 = 职业责任，最贵错误）
- 误报率 ≤ 15%（太多误报 → 律师不再看结果）
- 每份合同成本 ≤ ¥0.8，P95 ≤ 60s
### eval 集
- 200 份脱敏合同 × 3 律师标注（kappa ≥ 0.8 才入库）
- 覆盖矩阵：合同类型(5) × 风险等级(4) × 语言(2)
### 失败设计
- recall 不达 → 输出"不确定，请人工复核该节"（降级，见 04 章）
### 上线门槛与监控
- 离线达标 + 灰度 2 周在线任务完成率 ≥ 基线 -2pp → 全量
- 回滚触发：误报率周环比 >8pp
```

注意：**这份 PRD 没有一个字描述界面**——它描述的是质量分布和门槛。界面是 04 章的事。

## 03.4 门槛设定的经济学

阈值不是拍出来的，是**错误成本算出来的**：

```
阈值选择 = argmax_θ [ 正确自动处理的价值 × P(正确|θ) − 错误成本 × P(错误|θ) − 人工复核成本 × P(转人工|θ) ]
```

直觉版（Harvey/客服两类产品对比）：
- **法律（Harvey 类）**：漏检一个条款 = 职业责任 → recall 门槛极高、宁可转人工
- **客服**：错答一条 = 道歉 + 小额补偿 → 门槛可以低、追求自动解决率

**同一个模型，两个产品的正确答案完全不同**——这就是 AI PM 的判断力所在（技术团队给不了这个答案）。

→ `experiments/03_cql_tradeoff.py` 把这个决策做成了可运行模拟（三档模型配置 × 错误成本扫描，输出最优配置切换点）。

## 03.5 eval 的反模式（血泪清单）

1. **静态 eval 集**：三个月不更新 → 团队对它过拟合，生产质量背离。纪律：每双周从线上日志补 10-20 条新案例。
2. **只测平均**：平均分 92% 可能是"简单题 100% + 高风险题 60%"。**永远分片看**（按风险等级/用户段/场景切）。
3. **benchmark 崇拜**：公开 benchmark ≠ 你的产品。MMLU 高分与"你的用户满意度"的相关性可能为零。**自建 eval 是唯一可信的**（这也是 2026 年企业 AI 的最大瓶颈所在）。
4. **judge 未校准**：LLM-as-judge 没有一致性报告 = 装饰品。
5. **eval 无主人**：工程师建了 eval 但没人定义门槛、没人看漂移 → eval 是死文档。**PM 必须拥有门槛和告警语义。**
6. **一次性评估**：上线即停。AI 产品的"done"只是监控的开始（paraform.com, 2026：AI PM 发布后还有再训练/偏差审计/分段行为差异的漫长尾巴）。

## 03.6 A/B 测试的修正（02 章的深化）

输出方差让传统 A/B 难读。修正姿势（institutepm.com, 2026）：
- **核心模型行为**：离线 eval + holdout + 在线质量看板（不是 A/B）
- **shell UX**（界面、入口、文案）：正常 A/B
- **必须 A/B 时**：预计算样本量时把模型输出方差加进方差估计，或用 SxS（side-by-side 人工对比）做离线替代——并诚实知道 **SxS 何时是有效代理、何时不是**

## 03.7 工具地图（2026）

| 层 | 工具 | PM 用法 |
|---|---|---|
| eval 平台 | Braintrust / LangSmith / Patronus / Inspect AI | 建 eval 集、跑回归、看漂移 |
| 模型 playground | OpenAI/Anthropic/DeepSeek console | 手感测试、prompt 迭代 |
| 自建 | Python + pytest + rubric 表（本仓库风格） | 小团队首选，见 experiments |
| 人工评估 | 表格 + kappa 一致性 | 标注团队管理 |

## 核心洞察

1. **eval 四角色**（spec/发布门/回归网/监控源）——只当测试用是最常见的浪费。
2. **门槛是经济学不是工程学**：recall 95% vs 90% 的选择，取决于错误成本结构，这是 PM 独有的决策权。
3. **分片 > 平均**：平均分掩盖的分布问题是 AI 产品最大的隐形风险。
4. **eval 集是活资产**：静态 eval 集的过拟合比没有 eval 更危险（虚假安全感）。
5. **PM 不写 eval 代码但拥有 eval 语义**：覆盖矩阵、门槛、告警语义、rubric——这四样是 AI PM 的签字权。

## ✍️ 自测

1. 为你的核心功能设计覆盖矩阵（场景 × 难度 × 风险），算算现有 eval 集覆盖了几格。
2. 用错误成本公式推一遍你的 threshold：如果错误成本 ×10，你的发布门槛该是多少？
3. 你的产品上一次因为 eval 不达标而推迟发布是什么时候？如果从未发生——eval 可能是装饰品。
