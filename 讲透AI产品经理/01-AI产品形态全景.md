# 01 — AI 产品形态全景：形态决定 PM 的全部工作

> "最贵的架构错误不是选错模型，是选错**交互范式**。该做 agent 的团队花六个月打磨 chatbot，该做 copilot 的团队上了完全自主、然后整个季度都在救火。"（tianpan.co, 2026-04）
>
> AI PM 的第一个决策不是做什么功能，是**产品坐在形态光谱的哪个位置**——它决定信任模型、上下文策略、错误恢复、成本结构、卖法、甚至你的 job description。

---

## 01.1 形态光谱：七类产品（thrumos.com 2026 分类法 + 2026 事实校准）

按 **AI 集成深度**排列——这是最重要的分类维度（买错档位 = 销售对话错配 + 尽调翻车）：

| # | 形态 | 定义 | 例 | PM 工作重心 |
|---|---|---|---|---|
| 1 | **Core AI Infrastructure** | 算力/训练框架 | GPU 云、Ray | 极技术 PM，性能/单位成本 |
| 2 | **AI PaaS / 模型即产品** | 基座模型 API | OpenAI/Anthropic API、DeepSeek | 能力曲线、token 经济、开发者体验 |
| 3 | **Functional AI SaaS** | AI 做核心功能的横向工具 | 编程助手、写作工具 | eval + 工作流嵌入 |
| 4 | **Assistive（Copilot 类）** | 嵌在既有软件里的建议者 | M365 Copilot、Notion AI | 上下文利用、采纳率 |
| 5 | **Autonomous（Agent 类）** | 自主多步执行 | Devin、客服 agent | 权限设计、失败恢复、审计 |
| 6 | **Vertical AI** | 垂直行业的 AI 全栈产品 | Harvey（法律）、医疗 AI | 领域知识、合规、数据壁垒 |
| 7 | **Embedded AI Feature** | 传统产品里的 AI 点缀 | 各种"AI 摘要"按钮 | 价值证明（防"为 AI 而 AI"） |

**2026 动态**：第 5 类（agentic）增长最快、监管审查也最重；第 2 类因模型商品化在洗牌；第 6 类是溢价最高、壁垒最厚的赛道。

## 01.2 四级自主性阶梯：chatbot → copilot → agent → digital employee

2026 年最实用的消费侧分类（Taskade/Presenc AI/Lenny Rachitsky 框架综合）：

| | Chatbot | Copilot | Agent | Digital Employee |
|---|---|---|---|---|
| **一句话** | 回答问题 | 建议下一步 | 规划并执行多步任务 | 持续拥有一个岗位 |
| **谁在掌舵** | AI 掌对话 | 人掌工作（AI 建议，人按 Tab） | AI 掌工作流（里程碑人查） | AI 掌队列 |
| **工具调用** | 0-1 个 | 部分 | 5-20 个（Tier 3）/ 10-50（Tier 4） | 多集成 |
| **记忆** | 会话内 | 部分 | 短期→长期 | **持久身份+KPI+工作队列** |
| **最坏失败** | 回答很烂 | 建议被拒绝（**无害**） | 采取错误行动（**需回滚基建**） | 持续犯错累积损失 |
| **信任模型** | 限流+PII 过滤+转人工 | **继承宿主应用的权限模型** | 必须显式设计：scoped credentials/变更日志/回滚/升级路径 | + 治理面板/审计/kill switch |
| 2026 代表 | FAQ bot | GitHub Copilot、Notion AI | Devin、Operator、Claude Code | Artisan、11x、Decagon、Sierra |

**Copilot 被系统性低估**（tianpan.co 2026-04）：它嵌在宿主应用里能拿到真实上下文（当前文件/活动记录/最近行为），且"人批准"这道闸使错误建议**零伤害**。医疗记录、法律起草、财务报告——**历史上就该人签核的领域，copilot 是终态而非过渡**。选 copilot 不是保守，是决策。

**Digital Employee 的鉴别器**：市面上 2026 年多数"AI 员工"是单任务 agent 换皮——**先查持久记忆**（跨周/月的存在 + 队列 + KPI）再信 label（Taskade, 2026）。

## 01.3 Agent 的五层工程分档（Presenc AI, 2026-05，对齐 BFCL/GAIA/SWE-Bench 基准）

买/造之前先定档——**档位错配是最大浪费**（Tier 1 任务的 FAQ 挡掉买 Tier 4 产品 = 花冤枉钱 + 白添失败面）：

| Tier | 形态 | 记忆 | 规划 | 工具 | 时间域 | 试点停滞率（中位） |
|---|---|---|---|---|---|---|
| 1 | 带工具的 chatbot | 会话 | 无 | 0-1 | 秒-分 | 低 |
| 2 | 工作流自动化（固定分支+LLM 填槽） | 状态机 | 预定义 | 固定管线 | 分 | 低 |
| 3 | **工具编排 agent**（动态选择 5-20 工具） | 短期 | 反应式 | 5-20 | 分 | **~55%** |
| 4 | 自主任务 agent（长程/自纠错） | 长期+情景 | 多步 | 10-50 | 分-时 | **~70%** |
| 5 | 多 agent 系统 | 共享 | 层级 | 每 agent+共享 | 时-天 | 最高 |

**残酷事实**：2026 年多数标"autonomous agent"的商业产品是 Tier 3；多数"multi-agent 系统"是披着营销标签的顺序流水线（Tier 2/3 换皮）。Tier 4 真品屈指可数（Devin、Claude Code 自主模式、Codex agent、Operator）；Tier 5 生产级极稀有——**Tier 5 任务应该 build 而不是 buy**。

> PM 动作：给供应商四个问题——记忆模型（会话内还是跨会话）？工具数？流程动态还是预定义？任务时间域？**答不清楚 = 档位低于营销**。

## 01.4 Microsoft 四态模型：产品自身的 AI 演化阶梯

产品视角（非能力视角）的四态（Microsoft SaaS AI strategy，via framework.ai-native-transformation.com, 2026-06）：

```
Foundational（AI 内部用，产品面不变）
   → Conversational（产品加了 chat/copilot 界面）
      → Agentic（agent 代表用户在产品内行动）
         → Multi-agent（你的产品参与外部 agent 编排的工作流）
```

2026 年现状：多数 B2B SaaS 卡在 Foundational↔Conversational 之间；Stripe、Customer.io 等少数已到 Agentic→Multi-agent 子集。

## 01.5 AI-native 的八层产品表面（2026 年新常识）

当 agent 成为用户，你的产品对外的"表面"从 UI 变成八层（Stripe 是跨品类原型：framework.ai-native-transformation.com, 2026-06）：

| 层 | 是什么 | 状态 |
|---|---|---|
| 1 REST/GraphQL API | 权威 schema 的基底 | 前agent时代已有 |
| 2 SDK | 类型化多语言 | 已有 |
| 3 Function-tool 定义 | JSON-Schema 包装的 API 子集（喂给 agent 框架） | 新增 |
| 4 **MCP server** | 跨宿主协议（tools/resources/prompts），Claude/Cursor/ChatGPT 等 agent 宿主消费 | **承重层** |
| 5 Webhooks/事件流 | 状态回读通道 | 新增 |
| 6 **可查询文档** | schema/错误语义/幂等契约——运行时可得，不只是文档站 | **承重层** |
| 7 Agent 沙箱+eval harness | 非确定性客户端的测试基底 | 差异化 |
| 8 **治理控制台** | 按环境权限/scoped 凭据/审计日志/kill switch | **承重层（信任表面）** |

**MCP 事实线**（本仓库 [MCP 生态全景](../讲透Agent/Agent框架案例/MCP协议生态全景/) 有深读）：Anthropic 2024-11 发布 → Google DeepMind/Microsoft/IBM/Amazon 跟进 → **2025-12 捐给 Linux Foundation 旗下 Agentic AI Foundation**（vendor-neutral）→ 18 个月内 Fortune 500 采用率 ~28%，NSA 2026-05 发布安全设计指引称其为事实标准。

**关键反转**："UI 曾经是产品；现在它只是工具目录的一个渲染子集——**工具目录才是产品的新 spec**。" Customer.io 直接卖"你不需要 GUI"的 Builder Plan（CLI+MCP+webhooks，$0.40/千条消息）。

**薄 MCP 陷阱**：把 REST 端点原样包一层 = agent 被迫做人级编排决策、失败率复利放大。正解是 **capability over endpoint**——工具按工作流造型，内置资格检查/参数校验/审批门。**少而大的工具，不是多而小的端点。**

## 01.6 形态→PM 工作映射表（本章的落点）

| 形态 | PM 的时间花在哪 | 关键指标 | 最难的问题 |
|---|---|---|---|
| 模型即产品 | 能力路线图×客户需求的匹配 | benchmark 转化率、API 用量 | 能力窗口何时开 |
| Copilot | 上下文工程、采纳率优化 | 采纳率、节省时间 | 用户不知道能问什么 |
| Agent | 权限分级、失败恢复、成本控制 | 任务完成率、人工介入率 | 放权到哪一级 |
| Digital Employee | 岗位设计、KPI、与人类团队融合 | 岗位级指标（如线索转化） | 组织信任与责任归属 |
| Vertical AI | 领域数据壁垒、合规 | 领域 eval、每案例价值 | 专家知识的获取成本 |
| Embedded | 价值证明 | 使用率、NPS 增量 | 防"为 AI 而 AI" |

## 核心洞察

1. **形态是第一产品决策**：它先于功能存在，决定信任模型、失败成本、卖法和你作为 PM 的日常。
2. **自主性阶梯不是越高越好**：每上一级，复杂度、失败率、成本都升。**任务匹配档位，不要过度购买**（Presenc AI, 2026）。
3. **Copilot 是终态之一**，不是怯懦的 agent——人签核领域（医/法/财）里它是正确架构。
4. **产品表面正在爆炸**：从 1 层 UI 到 8 层表面，其中 MCP/可查询文档/治理控制台是承重层——这对所有 B2B 产品成立，不只是 AI 公司。
5. **营销标签系统性虚标一档**：自称 autonomous 的多是 Tier 3，自称 multi-agent 的多是流水线。PM 的基本功是**用记忆/工具数/时间域三问揭底**。

2. 八层表面你有几层？MCP 是薄包装还是 capability over endpoint？
