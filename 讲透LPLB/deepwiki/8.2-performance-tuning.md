## Performance Metrics

 LPLB tracks two primary performance metrics: **balance coefficient** and **solver latency**. These metrics help evaluate the quality of load balancing and the computational overhead introduced by the solver.

 
### Balance Coefficient

 The balance coefficient quantifies load imbalance across ranks after LPLB optimization. It is defined as:

 
```
balance_coefficient = max_workload / mean_workload
```

 A coefficient of 1.0 indicates perfect balance (all ranks have equal workload), while higher values indicate imbalance. LPLB aims to minimize this coefficient while respecting expert redundancy constraints.

### Solver Latency

 Solver latency measures the time required for `kernel_solve` to compute the optimal token distribution. This overhead is added to each forward pass and can impact performance, especially for small batches.

 **Typical Latency Values:**

 
 - **Intra-node optimization**: ~100 microseconds
 - **Inter-node optimization**: Higher latency due to NVSHMEM communication
 
 The latency depends on:

 
 - Problem size (number of experts, redundancy configuration)
 - Topology complexity (Cube vs Torus vs Hypercube)
 - Communication patterns (intra-node vs inter-node)
 - Hardware characteristics (GPU architecture, interconnect bandwidth)

## Performance Characteristics

 
### Intra-Node vs Inter-Node Performance

 LPLB's performance varies significantly based on whether optimization occurs within a node or across nodes:

 
| Configuration | Typical Latency | Communication Method | Use Case |
|---|---|---|---|
| Intra-Node | ~100 µs | CUDA IPC | Cube topology, single 8-GPU node |
| Inter-Node | >100 µs | NVSHMEM RDMA | Torus/Hypercube topologies, multi-node |

 **Intra-node optimization** benefits from:

 
 - Fast CUDA IPC memory access between GPUs
 - Minimal communication latency
 - Lower probability of network congestion
 
 **Inter-node optimization** faces:

 
 - Higher NVSHMEM RDMA latency
 - Network bandwidth constraints
 - Potential synchronization overhead
 
 Sources: [README.md70](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L70-L70)

 
### Topology Performance Impact

 
```

```

 **Diagram: Topology Performance Characteristics**

 **Cube (8-GPU):**

 
 - Lowest latency due to intra-node-only communication
 - Best choice for single-node EP groups
 - Limited global balancing capability
 
 **Hypercube (16-GPU):**

 
 - Moderate latency with cross-node communication
 - Balances across two 8-GPU nodes
 - No diagonal edges reduces complexity
 
 **Torus (Flexible):**

 
 - Highest latency due to mixed communication patterns
 - Enables global balancing across all nodes
 - Higher overhead may not justify benefits for localized imbalance

### Batch Size Considerations

 Solver overhead becomes more significant for smaller batches:

 
| Batch Size Range | Overhead Impact | Recommendation |
|---|---|---|
| Large (>10k tokens) | Negligible (<1%) | Use LPLB freely |
| Medium (1k-10k tokens) | Low (1-5%) | Monitor balance coefficient |
| Small (<1k tokens) | High (>5%) | Consider static EPLB only |

 For very small batches, the ~100 µs solver latency may represent a substantial fraction of total computation time. In such cases, static EPLB without dynamic balancing may provide better overall performance.

 Sources: [README.md70](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L70-L70)

### N_SMS Parameter Tuning

 The `N_SMS` parameter passed to `Planner.run()` specifies the number of streaming multiprocessors (SMs) used for workload counting. This affects:

 
 - **Histogram granularity**: More SMs provide finer-grained workload distribution
 - **Memory usage**: Each SM maintains separate counters
 - **Performance**: Higher values may improve parallelism but increase overhead
 
 **Typical Values:**

 
 - **Conservative**: 80-100 SMs (suitable for most GPUs)
 - **Aggressive**: 100-132 SMs (for high-end GPUs like H100)
 - **Auto-detect**: Query `torch.cuda.get_device_properties().multi_processor_count`

## Known Limitations and Considerations

 
### Non-Linear Cost Model

 LPLB's LP solver optimizes for **total token count balance** but does not account for non-linearities in grouped matrix multiplication time costs. This can lead to suboptimal performance when:

 
 - Token distribution within experts varies significantly
 - Hardware execution units have non-linear performance characteristics
 - Memory access patterns differ across workload distributions
 
 **Impact:** In practice, balance coefficient improvements may not translate directly to proportional speedup due to these non-linearities.

 Sources: [README.md69](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L69-L69)

 
### Solver Overhead

 The ~100 µs solver latency is non-negligible for small batches:

 **Break-Even Analysis:**

 
 - For 1ms forward pass: 10% overhead
 - For 10ms forward pass: 1% overhead
 - For 100ms forward pass: 0.1% overhead
 
 **Mitigation:**

 
 - Use larger batch sizes when possible
 - Consider static EPLB for small-batch scenarios
 - Profile end-to-end to measure actual impact
 
 Sources: [README.md70](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L70-L70)

 
### Extreme Global Imbalance

 Under extreme global load imbalance, LPLB may perform worse than static EPLB due to differences in redundant expert assignment:

 **LPLB Constraint:** Avoids assigning multiple replicas to the same original expert within a single batch **EPLB Approach:** May create more replicas without this constraint

 **When This Matters:**

 
 - Very skewed expert selection patterns
 - Small number of highly popular experts
 - Limited redundancy capacity
 
 **Recommendation:** Compare LPLB and static EPLB performance for your specific workload pattern before deploying.

 Sources: [README.md71](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L71-L71)
