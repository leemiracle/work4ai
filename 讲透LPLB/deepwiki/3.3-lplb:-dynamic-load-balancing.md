## Purpose and Scope

 This page explains how LPLB (Linear-Programming-Based Load Balancer) handles **dynamic load imbalance** in Mixture-of-Experts (MoE) models through per-batch token redistribution. Dynamic imbalance refers to workload fluctuations that occur between batches during training, as opposed to static imbalance caused by consistent expert popularity patterns.

 For static load balancing through expert reordering and replication, see [EPLB: Static Load Balancing](https://deepwiki.com/deepseek-ai/LPLB/3.2-eplb:-static-load-balancing). For the detailed implementation of the LP solver and CUDA kernels, see [Linear Programming Solver](https://deepwiki.com/deepseek-ai/LPLB/5.5-linear-programming-solver) and [CUDA Kernel Implementation](https://deepwiki.com/deepseek-ai/LPLB/5.4-cuda-kernel-implementation).

 
## The Dynamic Load Imbalance Problem

 Dynamic load imbalance occurs when token assignments to experts vary significantly across batches, even after static rebalancing has been applied. This happens because:

 
 - **Small-batch randomness**: During training with small batch sizes, the random routing decisions made by the MoE gating network create unpredictable workload distributions
 - **Temporal fluctuations**: Expert selection patterns change as the model learns, causing different experts to be overloaded in different batches
 - **Insufficient static redundancy**: Static replication alone cannot adapt to batch-specific workload spikes
 
 Unlike static imbalance (which EPLB addresses through expert reordering and replication based on historical statistics), dynamic imbalance requires **per-batch optimization** to redistribute tokens in real-time.

## LPLB Solution: Redundant Experts as Flexible Edges

 LPLB treats redundant experts as **edges in a graph** connecting GPUs. Each redundant expert provides a channel for redistributing tokens from one GPU to another:

 
 - **Original expert**: The primary copy of an expert on its home GPU
 - **Redundant expert**: A replica of that expert on a different GPU, forming an edge
 - **Edge capacity**: The number of tokens currently assigned to a redundant expert in the batch, defining the maximum flow for rebalancing
 
 The key insight is that tokens initially routed to a redundant expert can be **flexibly distributed** between the original and redundant copies, enabling load balancing without changing the logical expert assignments.

## Three-Phase Dynamic Balancing Process

 
### Phase 1: Workload Counting (`count_workload`)

 The first phase counts how many tokens are assigned to each logical expert in the current batch. This counting is performed efficiently using per-SM (Streaming Multiprocessor) histograms to avoid global atomic contention.

 **Key method:** `Planner.count_workload(idx, n_sms)`

 
 - **Input**: `idx` - logical expert indices selected by the MoE router, shape `[num_tokens]`, range `[-1, n_logical_routed_experts)` (where `-1` indicates no expert)
 - **Output**: 
 - `workload` - total count per expert, shape `[n_logical_routed_experts]`
 - `local_workload_by_sm` - prefix sum of counts across SMs, shape `[n_sms, n_logical_routed_experts]`
 
 The prefix sum is used in Phase 3 to deterministically distribute tokens across original and redundant experts.

 **Implementation:** `kernel_count_idx` uses shared memory atomics within each SM block, then performs a grid-wide prefix sum.

 **Sources:** [lplb/planner.py184-194](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/planner.py#L184-L194) [lplb/resources/csrc-tmpl/minilp.cu410-443](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/resources/csrc-tmpl/minilp.cu#L410-L443)

 
### Phase 2: LP Solving (`solve_probs`)

 The second phase solves a linear programming problem to compute optimal distribution ratios for tokens assigned to redundant experts. The LP solver determines what fraction of each redundant expert's workload should go to the original vs. the replica.

 **Key method:** `Planner.solve_probs(workload, avail_counter)`

 
 - **Input**: 
 - `workload` - global workload statistics (all-reduced across ranks), shape `[n_experts]`
 - `avail_counter` - counter for tracking feasible solutions, shape `[1]`
 - **Output**: `o_weight` - distribution ratios, shape `[num_redundants, combined_redundant_experts]`
 
 The distribution ratio `o_weight[r, e]` indicates what fraction of tokens for redundant expert `e` should be assigned to its original copy (vs. the replica at redundant index `r`).

 If workload synchronization via DeepEP is enabled (`deep_ep_initialized=True`), the all-reduce is performed using optimized NVLINK/NVSHMEM communication. Otherwise, it falls back to `torch.distributed.all_reduce`.

 **Sources:** [lplb/planner.py196-218](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/planner.py#L196-L218) [lplb/resources/csrc-tmpl/minilp.cu83-402](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/resources/csrc-tmpl/minilp.cu#L83-L402)

 
### Phase 3: Index Mapping (`weighted_select_target`)

 The final phase uses the computed distribution ratios to deterministically map each logical expert index to a physical expert index (either original or redundant).

 **Key method:** `Planner.weighted_select_target(idx, o_weight, local_workload_by_sm, n_sms)`

 
 - **Input**: 
 - `idx` - logical expert indices, shape `[num_tokens]`
 - `o_weight` - distribution ratios from Phase 2
 - `local_workload_by_sm` - prefix sum from Phase 1
 - **Output**: `physical_indices` - mapped indices, shape `[num_tokens]`, range `[-1, n_routed_experts)`
 
 The mapping uses a deterministic pseudo-random function based on token position within the expert's workload to decide whether each token goes to the original or redundant expert, respecting the target distribution ratios.

 **Implementation:** `kernel_map_idx` maintains per-expert counters and uses the formula `(count * 499 + 41) % total_count` to create a uniform distribution without requiring true random number generation.

 **Sources:** [lplb/planner.py219-243](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/planner.py#L219-L243) [lplb/resources/csrc-tmpl/minilp.cu445-515](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/resources/csrc-tmpl/minilp.cu#L445-L515)

 
## LP Problem Formulation

 
```

```

 **Diagram: LP Formulation Structure**

 The linear program solved by `kernel_solve` has the following structure:

 
### Variables

 The solution vector `x` has `NV = GROUP_SIZE * DUP_PER_RANK * 2 + GROUP_SIZE + 2` variables:

 
| Variable Range | Size | Meaning |
|---|---|---|
| x[0 : GS*DPR] | GROUP_SIZE * DUP_PER_RANK | Load fraction for original experts |
| x[GS*DPR : GS*DPR*2] | GROUP_SIZE * DUP_PER_RANK | Load fraction for redundant experts |
| x[... : ...*2+GS] | GROUP_SIZE | Slack variables (load difference from max) |
| x[...*2+GS] | 1 | Max load across all ranks |
| x[...*2+GS+1] | 1 | Big M artificial variable (feasibility) |

 Where `GS = GROUP_SIZE` and `DPR = DUP_PER_RANK` are topology parameters.

 
### Constraints

 The constraint matrix `a` has `NC = GROUP_SIZE + GROUP_SIZE * DUP_PER_RANK` rows:

 
 - **Load Balance Constraints** (first `GROUP_SIZE` rows): Each rank's total load (original + replica + slack) must equal the maximum load:

 
```
Σ(original_loads[i]) + Σ(replica_loads[i]) + slack[i] - max + artificial = -fixed_load[i]
```
 - **Assignment Constraints** (remaining rows): For each redundant expert, the sum of loads for original and replica must equal 1:

 
```
original_load[e] + replica_load[e] + artificial = 1
```
 
 The `phy2log` mapping determines which physical experts correspond to which variables, and the `r2o` (redundant-to-original) matrix defines the expert replication topology.

 
### Objective Function

 Minimize: `c = [0, ..., 0, 1, 1000]` where:

 
 - Coefficient `1` for the max load variable (minimize maximum load)
 - Coefficient `1000` for the artificial variable (Big M method to ensure feasibility)

## Integration with EPLB

 LPLB and EPLB work together in a complementary fashion:

 
```

```

 **Diagram: EPLB and LPLB Integration**

 **EPLB's Role:**

 
 - Performs **offline** expert reordering based on historical workload statistics
 - Selects which experts to replicate and determines replication topology
 - Creates the `r2o` matrix that defines redundancy structure
 
 **LPLB's Role:**

 
 - Performs **online** optimization for each batch
 - Uses EPLB's replication structure (`r2o`) to determine feasible token flows
 - Adapts to per-batch variations without changing the physical expert layout
 
 **Key integration point:** `Planner.update_redundancy_mapping(workload)`

 This method can be called periodically (e.g., every few thousand steps) to refresh the expert ordering based on updated workload statistics. It:

 
 - Calls `rebalance_experts` from EPLB to get a new ordering
 - Selects the top-loaded experts for redundancy
 - Updates `phy2log` mapping to reflect the new physical-to-logical expert assignments

## Convergence and Fallback Behavior

 The LP solver performs 5 iterations of an Interior Point Method (IPM) and validates the solution using three criteria:

 
| Criterion | Threshold | Purpose |
|---|---|---|
| d_max < 0.1 | Descent direction magnitude | Ensure optimization is converging |
| 0 <= x[NV-1] < 0.01 | Artificial variable value | Verify feasibility (Big M method) |
| max_residual < 0.05 | Constraint violation | Check solution accuracy |

 If any criterion fails, the solver **falls back to uniform distribution** (`o_weight = 0.5` for all redundant experts), meaning tokens are split 50/50 between original and redundant experts. This ensures the system remains functional even when the LP solver cannot find an optimal solution.

 The `avail_counter` parameter tracks how many LP groups found feasible solutions, which can be monitored to detect optimization issues.

## Performance Characteristics

 LPLB's dynamic balancing introduces overhead compared to static-only approaches:

 
 - **Solver latency**: ~100 µs for intra-node optimization (8 GPUs in a cube topology), longer for inter-node topologies
 - **Communication overhead**: Requires workload all-reduce across the expert parallel group (optimized via NVSHMEM when using DeepEP)
 - **Memory usage**: Minimal additional memory for workload counters and distribution ratios
 
 The overhead is most significant for **small batch sizes** where the solver latency becomes a larger fraction of total batch time. For large batches with significant load imbalance, the performance gain from better load distribution typically outweighs the overhead.
