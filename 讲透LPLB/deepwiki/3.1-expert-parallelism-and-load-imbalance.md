  This page explains the fundamental problem that LPLB solves: load imbalance in expert-parallel Mixture-of-Experts (MoE) models. It covers what expert parallelism is, why load imbalance occurs, and the critical distinction between static and dynamic imbalance patterns. ## Expert Parallelism in MoE Models

 Expert parallelism is a distributed training strategy for MoE models where different experts are assigned to different GPUs within an expert-parallel (EP) group. Each input token is routed to one or more experts based on a learned routing function, and the selected experts process the token independently.

 
```

```

 **Token Routing Process in Expert Parallelism**

 In this architecture, the routing decision produces **logical expert indices** that identify which expert should process each token. These indices are distributed across the EP group, with each GPU responsible for computing its assigned experts. The system must map these logical indices to **physical expert locations** on specific GPUs.

## The Load Imbalance Problem

 Load imbalance occurs when tokens are not evenly distributed across experts (and therefore GPUs). Since all GPUs must synchronize after the expert computation phase, the total computation time is determined by the slowest GPU—the one with the most tokens to process.

 
```

```

 **Impact of Load Imbalance on GPU Utilization**

 The **balance coefficient** quantifies this imbalance as the ratio of maximum load to mean load:

 
```
balance_coefficient = max_load / mean_load
```

 A perfectly balanced system has a coefficient of 1.0. Higher values indicate worse imbalance. For example, if one GPU processes 200 tokens while others process 100, the coefficient is 2.0, meaning 50% of the available compute capacity is wasted waiting for the slowest GPU.

## Static vs Dynamic Imbalance

 LPLB distinguishes between two types of load imbalance, each requiring different mitigation strategies:

 
### Static Imbalance

 Static imbalance arises from **systematic biases in the data distribution or training dynamics** that cause certain experts to consistently receive more tokens than others across many batches. This pattern is relatively stable over time.

 **Characteristics:**

 
 - Persists across multiple training steps
 - Caused by data distribution, curriculum learning, or routing function convergence
 - Predictable from historical workload statistics
 - Can be mitigated by **expert reordering and replication** before training begins
 
 **Example:** In a language model, experts specializing in common linguistic patterns (e.g., subject-verb agreement) may consistently receive more tokens than experts for rare constructs.

 
### Dynamic Imbalance

 Dynamic imbalance occurs due to **per-batch fluctuations in token routing**, particularly pronounced in small-batch training scenarios. Even if the overall distribution is balanced across many batches, individual batches may exhibit significant imbalance.

 **Characteristics:**

 
 - Varies significantly from batch to batch
 - More severe with smaller batch sizes (fewer tokens to average over)
 - Cannot be predicted from long-term statistics alone
 - Requires **per-batch runtime optimization** to mitigate
 
 **Example:** In a batch of 1024 tokens, random variation might assign 150 tokens to Expert 0 and 50 tokens to Expert 1, even if their long-term averages are equal.

## Workload Representation and Metrics

 LPLB uses specific tensor structures to represent and measure workload:

 
| Tensor | Shape | Purpose | Imbalance Type |
|---|---|---|---|
| weight | [layers, num_logical_experts] | Historical token counts per expert | Static |
| indices | Variable (batch-dependent) | Current batch's expert selections | Dynamic |
| r2o | [group_size, num_redundants] | Maps redundant experts to originals | Both |
| prob | [num_SMs, num_experts] | Computed token distribution ratios | Dynamic |

 The **workload counting** phase (`count_workload()` method in `Planner`) aggregates per-SM histograms of token assignments. These histograms reveal the actual load on each GPU and streaming multiprocessor (SM), enabling fine-grained optimization.

 
```

```

 **Workload Counting and Synchronization Pipeline**

 The counting phase produces detailed workload information that quantifies the dynamic imbalance in the current batch. This data flows into the LP solver to compute optimal token redistribution.

## Why Both Solutions Are Necessary

 Neither static nor dynamic balancing alone is sufficient:

 **Static Balancing Alone:**

 
 - Cannot adapt to per-batch variations
 - Leaves residual imbalance in each batch
 - Particularly ineffective for small batch sizes where randomness dominates
 
 **Dynamic Balancing Alone:**

 
 - Must handle the full range of expert popularity
 - May require excessive redundancy (many replicas per expert)
 - Higher communication overhead if experts are poorly placed initially
 
 **Combined Approach (LPLB's Design):**

 
 - **EPLB** handles static imbalance through expert reordering and strategic replication based on historical data
 - **LPLB** handles dynamic fluctuations by redistributing tokens along pre-established redundancy edges
 - The `r2o` topology matrix connects both phases, defining the solution space for runtime optimization
 
 This two-phase approach minimizes both the number of redundant experts needed (static phase reduces baseline imbalance) and the per-batch optimization overhead (dynamic phase works within a constrained topology).

## Redundant Experts and Edge Capacity

 A key concept in LPLB's dynamic balancing is the **redundant expert**: a replica of an original expert placed on a different GPU. Each redundant expert creates an **edge** between GPUs that can be used for load balancing.

 
```

```

 **Redundant Experts Create Balancing Edges Between GPUs**

 The **edge capacity** is determined by the number of tokens assigned to the redundant expert in the current batch. This defines the maximum amount of workload that can be redistributed along that edge. The LP solver optimizes the flow along these edges to minimize overall imbalance while respecting capacity constraints.

 For example, if 50 tokens are routed to Expert 0 in the current batch, and Expert 0 has a redundant copy on GPU 1, then up to 50 tokens can be redistributed from GPU 0 to GPU 1 by processing some of them on the redundant copy instead of the original.

## Summary

 Expert parallelism distributes MoE computation across GPUs but introduces load imbalance challenges:

 
 - **Static imbalance** arises from consistent patterns in data distribution and routing behavior
 - **Dynamic imbalance** results from per-batch random fluctuations, especially severe in small-batch training
 - LPLB addresses both types: EPLB handles static imbalance through expert replication, while LPLB's LP solver handles dynamic imbalance through per-batch token redistribution
 - Redundant experts create edges between GPUs with capacities determined by current batch workload
 - The balance coefficient (max_load / mean_load) quantifies imbalance severity
