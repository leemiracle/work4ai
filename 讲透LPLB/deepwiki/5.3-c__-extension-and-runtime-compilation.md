## Purpose and Scope

 This page explains the C++ extension layer that bridges LPLB's Python API to CUDA execution. The extension uses a two-stage compilation approach: the C++ plugin is compiled at install time, then dynamically compiles and caches specialized CUDA kernels at runtime using NVRTC. This architecture enables template specialization for specific problem parameters while maintaining a simple Python interface.

 For information about the Python layer that uses this extension, see [Python Layer Implementation](https://deepwiki.com/deepseek-ai/LPLB/5.2-python-layer-implementation). For details on the CUDA kernels themselves, see [CUDA Kernel Implementation](https://deepwiki.com/deepseek-ai/LPLB/5.4-cuda-kernel-implementation).

## Two-Stage Compilation Architecture

 LPLB uses a sophisticated two-stage compilation strategy to balance flexibility with performance:

 
### Stage 1: Build-Time C++ Extension Compilation

 The `setup.py` script uses PyTorch's `CUDAExtension` to compile `plugin.cpp` into a Python-importable shared object (`lplb._cpp.so`). This happens once during installation.

 
```

```

 **Key Build Parameters** (from [setup.py14-50](https://github.com/deepseek-ai/LPLB/blob/0490f794/setup.py#L14-L50)):

 
| Parameter | Purpose |
|---|---|
| libraries=['nvrtc', 'nvJitLink', 'cuda'] | Links CUDA runtime compilation libraries |
| -DDEFAULT_CACHE_DIR | Sets default cache location for compiled kernels |
| -DUSE_NVSHMEM | Conditionally enables NVSHMEM support |
| -DNVSHMEM_DIR | Points to NVSHMEM installation |
| -DDEEP_EP_SO | Path to DeepEP shared object for symbol synchronization |

 The extension conditionally compiles with NVSHMEM support if `deep_ep_cpp` is available at [setup.py9-12](https://github.com/deepseek-ai/LPLB/blob/0490f794/setup.py#L9-L12) This enables advanced distributed communication features.

 **Sources**: [setup.py1-51](https://github.com/deepseek-ai/LPLB/blob/0490f794/setup.py#L1-L51) [csrc/plugin.cpp38-40](https://github.com/deepseek-ai/LPLB/blob/0490f794/csrc/plugin.cpp#L38-L40)

 
### Stage 2: Runtime CUDA Kernel Compilation

 At runtime, when a `compiled_solver` is instantiated with specific parameters, it compiles specialized CUDA kernels using NVRTC. This allows template parameters (`GROUP_SIZE`, `DUP_PER_RANK`, etc.) to be known at compile time, enabling aggressive compiler optimizations.

 
```

```

 **Why Two Stages?**: The C++ plugin provides stable ABI boundaries and manages CUDA context, while runtime compilation allows kernel specialization without requiring users to recompile the entire extension for different problem sizes.

 **Sources**: [csrc/plugin.cpp149-327](https://github.com/deepseek-ai/LPLB/blob/0490f794/csrc/plugin.cpp#L149-L327) [csrc/plugin.cpp459-470](https://github.com/deepseek-ai/LPLB/blob/0490f794/csrc/plugin.cpp#L459-L470)

## Kernel Caching Strategy

 To avoid recompiling identical kernels across runs or processes, LPLB implements a hash-based caching mechanism.

 
### Cache Key Generation

 The cache key is a hash of:

 
 - Kernel name (e.g., `minilp_solve_8x2.cu`)
 - Complete source code
 - All compilation options


```

```

 These buffers are accessible via RDMA from any node in the NVSHMEM team.

 **Intra-Node Buffers** (CUDA IPC) at [csrc/plugin.cpp395-448](https://github.com/deepseek-ai/LPLB/blob/0490f794/csrc/plugin.cpp#L395-L448):

 
 - Each rank allocates local buffers with `cudaMalloc`
 - Each rank creates IPC handles with `cudaIpcGetMemHandle`
 - Handles are exchanged using `ProcessGroup::_allgather_base`

 The result is two arrays of pointers:

 
 - `workload_buf_intranode[i]`: Points to rank `i`'s buffer within the node
 - `workload_sig_intranode[i]`: Points to rank `i`'s signal flag within the node
 
 These arrays are copied to device memory for kernel access at [csrc/plugin.cpp439-448](https://github.com/deepseek-ai/LPLB/blob/0490f794/csrc/plugin.cpp#L439-L448)

## Summary

 The C++ extension provides a high-performance bridge between Python and CUDA through:

 
 - **Two-Stage Compilation**: Build-time C++ compilation for stability, runtime CUDA compilation for specialization
 - **Intelligent Caching**: Hash-based kernel caching with collision detection
 - **Efficient Module Loading**: Direct cubin loading with runtime configuration
 - **Clean Python Interface**: PyBind11 bindings with automatic type conversion
 - **Distributed Infrastructure**: Optional NVSHMEM integration for multi-node optimization
 
 This architecture enables LPLB to achieve near-optimal performance while maintaining ease of use from Python.
