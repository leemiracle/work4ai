## Purpose and Scope

 This document explains LPLB's runtime compilation and caching system, which uses NVIDIA's NVRTC (Runtime Compilation) and NVJitLink to generate specialized CUDA kernels on-demand. Unlike traditional pre-compiled CUDA code, LPLB compiles kernels at runtime with parameters specialized for specific expert configurations, then caches the resulting binaries for reuse.

 For information about the overall build system architecture, see [Build System](https://deepwiki.com/deepseek-ai/LPLB/6-build-system). For details on how the compiled kernels are used, see [CUDA Kernel Implementation](https://deepwiki.com/deepseek-ai/LPLB/5.4-cuda-kernel-implementation).

 
---

 
## Overview

 LPLB employs a **two-stage compilation strategy**:

 
 - **Build-time**: The C++ plugin (`plugin.cpp`) is compiled into `lplb._cpp.so` using PyTorch's extension builder
 - **Runtime**: CUDA kernels are compiled from templates with problem-specific parameters (group size, duplication per rank) using NVRTC, then linked with math libraries using NVJitLink
 
 This approach enables kernel specialization without requiring separate builds for each configuration. The `compiled_solver` class manages the entire compilation, linking, caching, and loading pipeline.

 **Key Components**:

 
 - **NVRTC**: Compiles CUDA C++ source to LTO IR at runtime
 - **NVJitLink**: Links LTO IR modules with pre-compiled libraries
 - **Cache System**: Hash-based storage in `~/.lplb/cache/` to avoid recompilation
 - **Module Loader**: Extracts kernels from compiled cubins for execution

## NVRTC Compilation Process

 
### Source Template Loading

 The compilation process begins by loading the CUDA kernel template from the resources directory:

 
```
resource_path/csrc-tmpl/minilp.cu
```

 This template contains the kernel implementations with preprocessor directives for specialization. The file is read into a string buffer that will be compiled by NVRTC.

 NVRTC compilation is configured with multiple options to ensure proper specialization and library integration:

 
| Option Category | Example | Purpose |
|---|---|---|

| Block Size | -DBLOCK_DIM=128 | Thread block dimension |

### LTO IR Generation

 NVRTC compiles the source to **Link-Time Optimization (LTO) Intermediate Representation** rather than directly to cubin. This allows subsequent linking with pre-compiled libraries:

 
```
nvrtcCreateProgram() → nvrtcCompileProgram() → nvrtcGetLTOIR()
```

 If compilation fails, the error log is extracted via `nvrtcGetProgramLog()` and thrown as an exception.

 Sources: [csrc/plugin.cpp256-275](https://github.com/deepseek-ai/LPLB/blob/0490f794/csrc/plugin.cpp#L256-L275)

### Cache Directory Structure

 Compiled kernels are stored in a hierarchical directory structure:

 
```
~/.lplb/                              (or $LPLB_CACHE_PATH)
├── cache/
│   ├── minilp_solve_8x2_<hash>/
│   │   ├── cubin                     (compiled binary)
│   │   ├── cu                        (source for validation)
│   │   └── options                   (options for validation)
│   ├── minilp_solve_8x4_<hash>/
│   └── ...
└── tmp/
    └── minilp_solve_8x2_<hash>_<hostname>_<pid>/
        └── (temp files during compilation)
```

 The cache path can be customized via the `LPLB_CACHE_PATH` environment variable. The default is defined at compile time as `DEFAULT_CACHE_DIR`.

### Atomic Cache Updates

 To prevent corruption from concurrent builds, LPLB uses a two-stage commit:

 
 - **Temporary Directory**: Create a unique temp directory using hostname and PID:

 
```
tmp/minilp_solve_8x2_<hash>_<hostname>_<pid>
```
 - **Write Files**: Write `cubin`, `cu`, and `options` to temp directory

```

## Specialized Kernel Instances

 The compilation system produces specialized kernel instances for each unique configuration. The key specialization parameters are:

 
| Parameter | Source | Impact |
|---|---|---|
| GROUP_SIZE | Python Planner constructor | Number of ranks per expert group |
| DUP_PER_RANK | Python topology config | Redundancy level per rank |
| BLOCK_DIM | Runtime configuration | CUDA thread block size |
| SM_Ver | Current GPU | Target compute capability |

 Example: A configuration with 8 ranks per group and 2 redundancies per rank produces:

 
```
minilp_solve_8x2_<hash>
```

 Different configurations require separate compilation because matrix dimensions and loop bounds are compile-time constants for performance.

```

### Automatic Invalidation

 Cache entries are automatically invalidated when:

 
 - Source code changes (detected via hash)
 - Compilation options change (detected via hash)
 - Different CUDA architecture is detected (included in hash)
 
 No explicit version tracking is needed because all relevant inputs are hashed.

 
### Cache Size

 Each cache entry contains:

 
 - **cubin**: ~1-5 MB (varies by configuration)
 - **cu**: ~10-50 KB (source text)
 - **options**: <1 KB (text file)
 
 With typical usage, expect ~100 MB cache size across multiple configurations.

## Error Handling

 The compilation and linking system uses exception-based error handling with custom macros:

 
| Macro | Purpose | Behavior |
|---|---|---|
| NVRTC_CHECK(x) | Check NVRTC calls | Throw with nvrtcGetErrorString() |
| NVJITLINK_CHECK(h, x) | Check NVJitLink calls | Throw with error log from handle |
| CUDA_CHECK(x) | Check CUDA runtime calls | Throw with cudaGetErrorName() |
| LPLB_ASSERT(x) | Validate assumptions | Throw with assertion message |

 All errors are propagated as `std::runtime_error` exceptions that can be caught at the Python boundary via pybind11.

 Sources: [csrc/plugin.cpp42-88](https://github.com/deepseek-ai/LPLB/blob/0490f794/csrc/plugin.cpp#L42-L88)

## Performance Considerations

 
### Compilation Cost

 
 - **First compilation**: 5-15 seconds (NVRTC + linking)
 - **Cache hit**: <100 ms (load from disk)
 - **Cache validation**: <10 ms (string comparison)
 
 The compilation cost is amortized across all batches using the same configuration.

 
### Cache Locality

 The cache is stored in the user's home directory (`~/.lplb/`) by default. For multi-user systems or cluster environments, consider setting `LPLB_CACHE_PATH` to a shared location with proper permissions:

 
```

```

 This enables cache sharing across users running identical configurations.
