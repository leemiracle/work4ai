  This page explains the concept of expert topology configurations in LPLB, which define how redundant experts are distributed across GPUs to enable dynamic load balancing. A topology is encoded in the `r2o` (redundant-to-original) matrix that specifies which GPU hosts each redundant expert. Three standard topologies are provided: **Cube** (8-GPU), **Hypercube** (16-GPU), and **Torus** (flexible grid). Understanding these configurations is essential for choosing the right topology for your hardware setup and balancing requirements.

 For information about how LPLB uses these topologies to perform dynamic balancing, see [LPLB: Dynamic Load Balancing](https://deepwiki.com/deepseek-ai/LPLB/3.3-lplb:-dynamic-load-balancing). For details on how EPLB selects which experts to replicate, see [EPLB: Static Load Balancing](https://deepwiki.com/deepseek-ai/LPLB/3.2-eplb:-static-load-balancing).

 
## The r2o Matrix Concept

 The `r2o` (redundant-to-original) matrix is the core data structure that defines an expert topology. This matrix encodes the graph structure of redundant expert connections across GPUs.

 
### Matrix Structure

 The `r2o` matrix has dimensions `[group_size, num_redundants]` where:

 
 - `group_size` is the number of GPUs in the expert parallel group
 - `num_redundants` is the number of redundant experts per GPU (typically 2 for standard topologies)
 
 Each element `r2o[i, j]` specifies the target GPU rank for the `j`-th redundant expert on GPU rank `i`. This creates a directed edge from rank `i` to rank `r2o[i, j]` in the topology graph.

 
```

```

 **Matrix Properties:**

 
 - Each row represents a GPU rank's redundant expert assignments
 - Column `j` across all rows defines a permutation of GPU ranks (each GPU appears exactly once)
 - This ensures uniform redundancy: each GPU hosts exactly one replica of each redundant expert
 
 **Sources:** [README.md34-39](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L34-L39) [tests/utils.py97-113](https://github.com/deepseek-ai/LPLB/blob/0490f794/tests/utils.py#L97-L113)

 
### Inverse Mapping: o2r

 The `o2r` (original-to-redundant) matrix is derived from `r2o` by sorting. For each redundant expert, `o2r` specifies which GPU rank hosts that expert's replica for each original expert position.

 
```

```

 The relationship between `r2o` and `o2r`:

 
 - `r2o[o2r[i, j], j] == i` for all valid `i, j`
 - `o2r` enables efficient lookup during the index mapping phase

## Standard Topology Configurations

 LPLB provides three predefined topologies optimized for common hardware configurations and balancing requirements.

 
### Cube Topology (8-GPU)

 The Cube topology forms a 3D cube graph with diagonal edges, designed for balancing within a single 8-GPU node. Each GPU has two redundant experts connecting to specific neighbors in the cube structure.

 **Characteristics:**

 
 - **Graph Structure:** 8-vertex cube with diagonal edges added
 - **Redundancy:** 2 redundant experts per GPU (`2E` suffix)
 - **Communication Pattern:** All connections stay within a single 8-GPU node
 - **Requirements:** Minimum 2 experts per GPU for effective balancing
 - **Use Case:** Intra-node balancing in systems with 8-GPU nodes, optimized for NVLINK bandwidth

### Torus Topology (Flexible Grid)

 The Torus topology arranges GPUs in a 2D grid with wraparound connections, enabling flexible scaling and global load balancing across arbitrary node configurations.


 **Generation Logic:**

 
 - `m`: number of rows in the grid
 - `n`: number of columns in the grid
 - Total GPUs: `m * n`
 - For GPU at position `(i, j)`: 
 - Redundant 0 connects to `((i+1) % m, j)` (next row, wraps around)
 - Redundant 1 connects to `(i, (j+1) % n)` (next column, wraps around)
 
 **Example for 2x4 Torus:**

 
| GPU | Position | Redundant 0 | Redundant 1 |
|---|---|---|---|
| 0 | (0, 0) | 4 (1,0) | 1 (0,1) |
| 1 | (0, 1) | 5 (1,1) | 2 (0,2) |
| 2 | (0, 2) | 6 (1,2) | 3 (0,3) |
| 3 | (0, 3) | 7 (1,3) | 0 (0,0) |
| 4 | (1, 0) | 0 (0,0) | 5 (1,1) |
| 5 | (1, 1) | 1 (0,1) | 6 (1,2) |
| 6 | (1, 2) | 2 (0,2) | 7 (1,3) |
| 7 | (1, 3) | 3 (0,3) | 4 (1,0) |

 **Characteristics:**

 
 - **Graph Structure:** 2D torus with wraparound in both dimensions
 - **Redundancy:** 2 redundant experts per GPU
 - **Communication Pattern:** Typically one edge within node, one edge across nodes (depending on node assignment)
 - **Requirements:** Minimum 2 experts per GPU, flexible GPU count (`m * n`)
 - **Use Case:** Global load balancing across multiple nodes, scalable to arbitrary configurations

## Custom Topology Definition

 Users can define custom topologies by constructing their own `r2o` matrix, enabling specialized balancing strategies for unique hardware configurations.

 
### Constraints and Requirements

 When defining a custom `r2o` matrix, the following constraints must be satisfied:

 
 - **Permutation Property:** Each column of `r2o` must be a permutation of `[0, 1, ..., group_size-1]`

 
 - This ensures uniform redundancy across all GPUs
 - **Self-Loop Prohibition:** `r2o[i, j] != i` for all valid `i, j`

 
 - A GPU cannot have a redundant expert mapping to itself
 - **Dimensionality:** `r2o.shape == [group_size, num_redundants]`

 
 - `group_size` must match the expert parallel group size
 - `num_redundants` determines the redundancy factor
 - **Data Type:** Must be `torch.int32` or convertible to it

### Custom Topology Considerations

 When designing a custom topology, consider:

 
 - **Communication Locality:** Prioritize connections within the same node over inter-node connections to minimize latency
 - **Redundancy Level:** Higher `num_redundants` provides more balancing flexibility but increases memory overhead
 - **Graph Connectivity:** Ensure the topology graph has sufficient connectivity for effective load distribution
 - **Hardware Topology Alignment:** Match the logical topology to physical GPU interconnects (NVLINK, NVSwitch, InfiniBand)
