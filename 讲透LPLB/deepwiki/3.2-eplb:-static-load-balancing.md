## Purpose and Scope

 EPLB (Expert Parallelism Load Balancer) addresses **static load imbalance** in Mixture-of-Experts models by redistributing experts across GPUs based on historical workload statistics. Unlike LPLB's per-batch dynamic optimization (see [LPLB: Dynamic Load Balancing](https://deepwiki.com/deepseek-ai/LPLB/3.3-lplb:-dynamic-load-balancing)), EPLB performs a one-time rebalancing operation that assigns physical experts to GPUs in a way that minimizes long-term imbalance.

 This document explains EPLB's three-phase algorithm: expert reordering by load, expert replication to create redundancy, and balanced packing onto GPUs. For information about the topology configurations that define redundancy relationships, see [Topology Configurations](https://deepwiki.com/deepseek-ai/LPLB/3.4-topology-configurations). For the complete API reference, see [EPLB Functions](https://deepwiki.com/deepseek-ai/LPLB/4.2-eplb-functions).

## Static vs Dynamic Load Imbalance

 In MoE models, load imbalance occurs when some experts receive significantly more tokens than others. EPLB distinguishes between two types:

 
| Imbalance Type | Characteristics | Solution |
|---|---|---|
| Static Imbalance | Consistent across batches due to data distribution patterns; predictable from historical statistics | EPLB: Redistribute experts based on average workload |
| Dynamic Imbalance | Varies per batch due to random sampling and small batch sizes; unpredictable | LPLB: Per-batch LP optimization |

 EPLB operates on aggregated workload statistics (e.g., token counts averaged over many batches) to make strategic placement decisions that improve long-term balance. This happens infrequently (typically once during initialization or when workload patterns change significantly), whereas LPLB runs on every forward pass.

### Phase 1: Expert Reordering

 **Function:** `balanced_packing(weight, num_packs)`

 The first phase groups logical experts and assigns them to nodes (in hierarchical mode) or prepares them for replication (in global mode). The goal is to pack groups such that each pack has equal item count but weights are as balanced as possible.

 **Algorithm:**

 
 - Sort experts by weight in descending order
 - Greedily assign each expert to the pack with minimum total weight, subject to capacity constraint (each pack must have exactly `n/m` items)
 - Return pack assignments and ranks within packs
 
 
```

```

 **Key Properties:**

 
 - Each pack receives exactly `n/num_packs` items (balanced capacity)
 - Within capacity constraint, minimizes maximum pack weight (greedy approximation)
 - Special case: if `groups_per_pack == 1`, returns identity mapping
 
 **Sources:** [lplb/eplb.py6-46](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/eplb.py#L6-L46)

### Phase 2: Expert Replication

 **Function:** `replicate_experts(weight, num_phy)`

 After reordering, EPLB creates redundant expert copies to enable load balancing. Redundant experts are additional physical instances of logical experts that can process the same workload.

 **Algorithm:**

 
 - Start with `num_log` original experts
 - For each additional slot up to `num_phy`: 
 - Compute load density: `weight / logcnt` (average load per replica)
 - Select the logical expert with maximum load density
 - Create a new replica of that expert
 - Increment replica count
 
 
```

```

 **Output Tensors:**

 
 - `phy2log`: Maps each physical expert index to its logical expert ID
 - `rank`: Indicates which replica (0 = original, 1 = first redundant, etc.)
 - `logcnt`: Number of replicas for each logical expert
 
 **Balancing Strategy:** By always replicating the expert with highest `weight/logcnt` ratio, this greedy algorithm approximates minimizing the maximum load across all physical experts.

 **Sources:** [lplb/eplb.py49-77](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/eplb.py#L49-L77)

### Phase 3: Balanced Packing to GPUs

 **Function:** `balanced_packing(tokens_per_phy, num_gpus // num_nodes)`

 The final phase distributes physical experts across GPUs within each node. This uses the same `balanced_packing` function as Phase 1, but now operates on physical experts rather than logical expert groups.

 **Process:**

 
 - Compute per-replica load: `tokens_per_phy = (tokens_per_mlog / mlogcnt).gather(-1, phy2mlog)`
 - Pack physical experts to GPUs, ensuring each GPU receives equal number of experts
 - Generate final mappings: `pphy2log` (physical expert → logical expert) and `pphyrank` (replica rank)

## Hierarchical vs Global Policies

 EPLB supports two balancing policies based on network topology:

 **Hierarchical Policy** (when `num_groups % num_nodes == 0`):

 
 - Groups experts by locality to minimize inter-node communication
 - Applies three-phase algorithm at node level
 - Preserves expert group structure across node boundaries
 - **Use case:** Multi-node deployments where intra-node bandwidth (NVLink) >> inter-node bandwidth
 
 **Global Policy** (when groups don't align with nodes):

 
 - Treats all GPUs uniformly, ignoring node boundaries
 - Maximizes global load balance at cost of more inter-node traffic
 - Implemented by calling hierarchical policy with `num_groups=1, num_nodes=1`
 - **Use case:** Single-node deployments or when global balance is critical

## Data Structures and Transformations

 
### Input Tensor

 
```

```

 Historical workload statistics (e.g., average token counts per expert over many batches). Each element `weight[layer, expert]` represents the expected load for that expert.

 
### Output Tensors

 
| Tensor | Shape | Description |
|---|---|---|
| phy2log | [layers, num_replicas] | Maps physical expert index → logical expert ID |
| log2phy | [layers, num_logical, X] | Maps logical expert → list of physical replica indices (padded with -1) |
| logcnt | [layers, num_logical] | Number of physical replicas per logical expert |

 where `X = max(logcnt)`.

 
### Example Transformation

 For a system with 4 logical experts and 6 physical experts (2 replicas created):

 
```
Input weight: [10, 5, 8, 3]  # Expert loads

After replication (replicate experts 0 and 2):
phy2log:  [0, 1, 2, 3, 0, 2]  # Physical 0→Logical 0, Physical 1→Logical 1, etc.
rank:     [0, 0, 0, 0, 1, 1]  # Physical 4 is 2nd replica of Logical 0
logcnt:   [2, 1, 2, 1]        # Logical 0 has 2 replicas, Logical 1 has 1, etc.

log2phy (max replicas = 2):
[[0, 4],   # Logical 0 → Physical [0, 4]
 [1, -1],  # Logical 1 → Physical [1] (padded)
 [2, 5],   # Logical 2 → Physical [2, 5]
 [3, -1]]  # Logical 3 → Physical [3] (padded)
```

## Integration with LPLB

 EPLB operates as a preprocessing step for LPLB's dynamic balancing:

 
 - **Initialization Phase:** EPLB uses historical workload to determine:

 
 - Which experts to replicate (heaviest ones)
 - Initial placement of experts on GPUs
 - **Runtime Phase:** LPLB uses EPLB's output mappings:

 
 - `phy2log` defines which logical expert each physical slot represents
 - `log2phy` enables efficient lookup of available replicas
 - These mappings constrain LPLB's LP problem (see [LPLB: Dynamic Load Balancing](https://deepwiki.com/deepseek-ai/LPLB/3.3-lplb:-dynamic-load-balancing))
 - **Topology Integration:** EPLB's placement decisions are further refined by topology constraints (`r2o` matrix) that define redundancy relationships (see [Topology Configurations](https://deepwiki.com/deepseek-ai/LPLB/3.4-topology-configurations))
 
 The separation between static (EPLB) and dynamic (LPLB) balancing allows the system to handle both long-term trends and short-term fluctuations efficiently.
