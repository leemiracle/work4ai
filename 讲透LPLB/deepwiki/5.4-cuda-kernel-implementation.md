# CUDA Kernel Implementation

  Relevant source files 
 - [lplb/resources/csrc-tmpl/minilp.cu](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/resources/csrc-tmpl/minilp.cu)
 
  This page provides detailed documentation of the three specialized CUDA kernels that form the computational core of LPLB's dynamic load balancing system. These kernels are defined in the template file `lplb/resources/csrc-tmpl/minilp.cu`() and are compiled at runtime with problem-specific parameters. For information about the compilation and linking process, see [C++ Extension and Runtime Compilation](https://deepwiki.com/deepseek-ai/LPLB/5.3-c++-extension-and-runtime-compilation). For mathematical details of the LP formulation, see [Linear Programming Solver](https://deepwiki.com/deepseek-ai/LPLB/5.5-linear-programming-solver).

 The three kernels work together in a pipeline:

 
 - **`kernel_count_idx`** - Counts workload distribution across experts
 - **`kernel_solve`** - Solves the LP problem to compute optimal load distribution ratios
 - **`kernel_map_idx`** - Maps logical expert indices to physical indices based on LP solution
 
 
## Kernel Pipeline Architecture

 The three kernels form a sequential pipeline where each kernel's output feeds into the next stage of load balancing computation.

 
```

```

 **Kernel Execution Flow**: Each kernel operates on a grid of CUDA blocks (SMs). `kernel_count_idx` produces per-SM histograms that are aggregated via prefix sum. `kernel_solve` uses this aggregated workload to compute optimal distribution ratios through an Interior Point Method solver. `kernel_map_idx` uses these ratios to deterministically route tokens to physical expert replicas.

## Template Parameters and Memory Layout

 All three kernels are specialized at compile-time with problem-specific dimensions through C preprocessor macros. These parameters determine the sizes of constraint matrices, variable vectors, and shared memory allocations.

 
| Macro | Default | Description |
|---|---|---|
| GROUP_SIZE | 8 | Number of ranks in a balancing group |
| DUP_PER_RANK | 2 | Number of redundant expert copies per rank |
| SM_Ver | 900 | CUDA compute capability (900 = Hopper) |
| BLOCK_DIM | 128 | Number of threads per block |

 These parameters define derived constants used throughout the kernels:

 
 - **`NC`** = `GROUP_SIZE + GROUP_SIZE * DUP_PER_RANK` - Number of constraints (load balance + assignment)
 - **`NV`** = `GROUP_SIZE * DUP_PER_RANK * 2 + GROUP_SIZE + 2` - Number of variables (original loads + replica loads + slack + max + artificial)
 
 Sources: `lplb/resources/csrc-tmpl/minilp.cu:20-26`(), `lplb/resources/csrc-tmpl/minilp.cu:61-62`()

 
### Shared Memory Structure

 The `kernel_solve` kernel uses a large shared memory structure (`smem_variables`) that holds all intermediate computation results. This structure is carefully designed to maximize memory coalescing and minimize global memory access.

 
```

```

 **Memory Access Pattern**: All matrix operations are performed in shared memory to avoid global memory latency. The solver reuses the same shared memory buffers (`ax2c`, `r`, `d`) across iterations to minimize memory footprint. The structure size is queried via `get_solve_smem_size` kernel for dynamic shared memory allocation.

 Sources: `lplb/resources/csrc-tmpl/minilp.cu:64-77`(), `lplb/resources/csrc-tmpl/minilp.cu:79-81`()

 
## kernel_solve: LP Optimization Kernel

 The `kernel_solve` kernel is the computational core of LPLB. It implements a 5-iteration Interior Point Method to solve the load balancing LP problem. Each CUDA block processes one balancing group independently.

 
### Workload Synchronization

 Before solving the LP problem, the kernel synchronizes workload statistics across all ranks using a three-tier communication system. When NVSHMEM is enabled, this occurs in block 0 only to minimize communication overhead.

 
```

```

 **Communication Strategy**: The NVSHMEM path uses RDMA for inter-node communication and CUDA IPC atomic operations for intra-node synchronization. Each rank contributes to a distributed buffer, signals completion, and waits for all peers before proceeding. The fallback path simply normalizes the local workload when distributed synchronization is not available.

 Sources: `lplb/resources/csrc-tmpl/minilp.cu:109-197`()

 
### LP Problem Formulation

 The kernel constructs constraint matrix `a`, RHS vector `b`, and objective vector `c` in shared memory. The constraint system encodes both load balancing requirements (each rank's load equals the maximum) and assignment constraints (original + replica = 1).

 
#### Constraint Matrix Structure

 
```

```

 **Matrix Construction**: Each thread processes multiple elements of the constraint matrix in parallel. The load balance constraints (rows 0 to `GROUP_SIZE-1`) ensure each rank's total workload equals the maximum workload in the group. The assignment constraints (rows `GROUP_SIZE` to `NC-1`) ensure that for each redundant expert pair, the sum of load fractions equals 1. The Big M column ensures feasibility by allowing an initial basic feasible solution.

 Sources: `lplb/resources/csrc-tmpl/minilp.cu:199-293`()

 
### Interior Point Method Loop

 The kernel executes exactly 5 iterations of a primal-dual Interior Point Method with diagonal scaling. Each iteration refines the solution by solving a linearized system using cuSolverDx's Cholesky decomposition.

 
```

```

 **Iteration Details**:

 
 - **Step 1** performs element-wise scaling with `x²` terms for barrier function
 - **Steps 2-3** use cuBLASDx template-based matrix multiplication for compile-time optimization
 - **Step 4** uses cuSolverDx's Cholesky solver (`cusolverdx::function::posv`) which assumes positive-definite `ax2a`
 - **Step 6** uses warp shuffle operations (`__shfl_xor_sync`) for efficient parallel reduction
 - **Step 7** uses a conservative step size (0.999) to ensure interior feasibility
 
 Sources: `lplb/resources/csrc-tmpl/minilp.cu:331-367`()

 
### Convergence Validation

 After 5 iterations, the kernel validates the solution using three criteria. If validation fails, the kernel falls back to uniform distribution (0.5 for each replica).

 
| Criterion | Threshold | Purpose |
|---|---|---|
| d_max < 0.1 | 0.1 | Descent direction magnitude (near optimum) |
| 0 <= x[NV-1] < 1e-4 | 0.0001 | Big M artificial variable near zero (feasibility) |
| max_residual < 0.05 | 0.05 | Constraint satisfaction accuracy |

 
```

```

 **Validation Logic**: Only thread 0 sets the `avail_flag` in shared memory after checking all criteria. All threads synchronize before writing results. The `avail_num` counter tracks how many groups successfully converged, providing a metric for solver reliability.

 Sources: `lplb/resources/csrc-tmpl/minilp.cu:369-402`()

 
## kernel_count_idx: Workload Counting Kernel

 The `kernel_count_idx` kernel produces per-SM histograms of logical expert indices and computes cumulative sums across all SMs. This provides the workload distribution needed for LP formulation.

 
```

```

 **Histogram Algorithm**: Each SM processes a contiguous range of input elements, using shared memory atomics for fast histogram accumulation. The `split_and_align` function ensures block-aligned partitioning for coalesced memory access. After all blocks complete their local histograms, warp 0 of each block performs a sequential prefix sum to convert histograms into cumulative counts.

 **Buffer Offset**: The shared memory buffer includes 16 bytes of padding (`smem_buffer + 16`) to allow safe negative indexing for `idx[i] = -1` cases, which increment `smem_counts[-1]`.

 Sources: `lplb/resources/csrc-tmpl/minilp.cu:404-443`()

 
## kernel_map_idx: Index Remapping Kernel

 The `kernel_map_idx` kernel performs the final stage: deterministically mapping logical expert indices to physical indices based on the LP solution weights. This ensures each token is routed to the optimal replica.

 
### Shared Memory Initialization

 The kernel maintains three key shared memory arrays that encode the mapping logic:

 
```

```

 **Array Semantics**:

 
 - `smem_total_count[i]` holds the final cumulative count from the last SM
 - `smem_expected_count[i]` = `o_weight[...] * smem_total_count[i]` for replicated experts, else equals total count
 - `smem_current_count[i]` starts at the previous SM's cumulative count for this SM's processing range
 - `smem_log2r[i*2]` stores primary physical index, `smem_log2r[i*2+1]` stores alternative physical index
 
 Sources: `lplb/resources/csrc-tmpl/minilp.cu:460-496`()

 
### Weighted Deterministic Selection

 Each thread processes elements in its assigned range, using a pseudo-random but deterministic hash to select between primary and secondary replicas.

 
```

```

 **Deterministic Hashing**: The expression `(computed_count * 499 + 41) % total` provides pseudo-random distribution while maintaining determinism across runs. The constants 499 (prime) and 41 (offset) ensure good mixing. This hash maps the sequential counter to a pseudo-random position, which is then compared against the expected count to decide replica assignment.

 **Replica Selection Logic**: If the hashed position is less than `expected_count`, the token goes to the primary replica (original expert). Otherwise, it goes to the secondary replica (redundant expert). This achieves the exact distribution ratios computed by `kernel_solve`.

 Sources: `lplb/resources/csrc-tmpl/minilp.cu:498-515`()

 
## Helper Functions and NVIDIA Library Integration

 The kernels use template-based wrappers around NVIDIA math libraries for compile-time optimization. These wrappers are instantiated with specific matrix dimensions at compile time.

 
### Linear System Solver

 
```

```

 **Function**: Solves the linear system `a * x = b` in-place using Cholesky decomposition. The matrix `a` is assumed to be symmetric positive-definite (guaranteed by the `ax2a` construction). The solution overwrites vector `b`.

 **Library**: Uses `cusolverdx::function::posv` with row-major layout, configured for the target SM architecture and block dimensions.

### Matrix Multiplication

 
```

```

 **Function**: Performs matrix multiplication with compile-time dimension specialization. `matmulNT` handles transposed second operand (column-major `b`), while `matmulNN` handles both operands in row-major layout.

 **Library**: Uses `cublasdx::function::MM` with template-based configuration for optimal register usage and shared memory layout. The `BlockDim<BLOCK_DIM>()` parameter ensures the thread block size matches the kernel launch configuration.

 Sources: `lplb/resources/csrc-tmpl/minilp.cu:41-59`()

```

```

 **Function**: Computes the start index for a given block in a distributed workload. Ensures each block's range is aligned to a multiple of `align` (typically `block_size`) for coalesced memory access. Returns the minimum of `n` and the computed aligned start position.

 **Usage**: Called by both `kernel_count_idx` and `kernel_map_idx` to partition the input array across CUDA blocks with proper alignment.

## Compilation and Specialization

 The CUDA template file `lplb/resources/csrc-tmpl/minilp.cu`() is not compiled at build time. Instead, it is specialized and compiled at runtime by the C++ plugin using NVRTC with problem-specific macro definitions:

 
```

```

 This approach allows:

 
 - **Compile-time optimization** of matrix dimensions for NVIDIA libraries
 - **Zero runtime overhead** for dimension bounds checking
 - **Cache reuse** of compiled kernels for common configurations
 - **Conditional compilation** of NVSHMEM code paths via `#ifdef USE_NVSHMEM`
 
 The compilation process, kernel caching, and module loading are handled by the `CompiledSolver` class documented in [C++ Extension and Runtime Compilation](https://deepwiki.com/deepseek-ai/LPLB/5.3-c++-extension-and-runtime-compilation).
