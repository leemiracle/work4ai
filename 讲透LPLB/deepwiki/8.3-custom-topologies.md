  This document explains how to define custom expert redundancy topologies for LPLB by constructing the `r2o` (redundant-to-original) matrix. Custom topologies enable fine-tuned control over which experts are replicated and where replicas are placed, allowing optimization for specific hardware configurations, communication patterns, or workload characteristics beyond the standard Cube, Hypercube, and Torus topologies.

 For an introduction to the standard topologies and the basic r2o matrix concept, see [Topology Configurations](https://deepwiki.com/deepseek-ai/LPLB/3.4-topology-configurations). For guidance on evaluating topology performance, see [Performance Tuning](https://deepwiki.com/deepseek-ai/LPLB/8.2-performance-tuning).

## Understanding the r2o Matrix

 
### Matrix Structure

 The `redundant_to_original` matrix (r2o) is a 2D integer tensor with shape `[group_size, num_redundants]` that defines the redundancy topology for expert load balancing.

 
```

```

 **Matrix Semantics:**

 
 - Each row corresponds to one rank in the redundancy group
 - Each column represents one redundant expert slot
 - `r2o[i, j] = k` means: "Rank `i`'s `j`-th redundant expert is a replica of Rank `k`'s original expert"
 
 **Sources:** [lplb/planner.py47-60](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/planner.py#L47-L60) [README.md34-39](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L34-L39)

 
---

 
### Structural Constraints

 LPLB enforces strict constraints on the r2o matrix structure to ensure efficient LP solving and deterministic routing:

 
| Constraint | Description | Rationale |
|---|---|---|
| Uniform Redundancy | Each rank must have exactly num_redundants redundant experts | Ensures balanced replication across ranks |
| Column Uniqueness | Each column must contain each rank index exactly once | Creates pairwise expert sharing between ranks |
| Bijective Mapping | The j-th redundant on any rank is always a copy of the j-th original on some other rank | Simplifies the LP constraint formulation |
| No Self-Loops | r2o[i, j] ≠ i (implicit) | A rank cannot replicate its own experts |

 
```

```

 The **column uniqueness constraint** creates a bipartite graph where each redundant expert slot connects exactly two ranks. This ensures that the LP solver can distribute workload optimally without creating degenerate cases where multiple ranks replicate the same expert in the same redundant slot.

 **Sources:** [lplb/planner.py51-59](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/planner.py#L51-L59) [lplb/planner.py66-68](https://github.com/deepseek-ai/LPLB/blob/0490f794/lplb/planner.py#L66-L68)

## Topology Design Principles

 
### Graph Theory Perspective

 Expert redundancy topologies can be viewed as directed graphs where:

 
 - **Nodes** represent ranks in the redundancy group
 - **Edges** represent redundant expert connections
 - Each redundant slot `j` creates one edge per rank
 
 
```

```

 **Key Design Considerations:**

 
| Property | Impact | Example |
|---|---|---|
| Graph Diameter | Affects maximum token flow distance | Torus has higher diameter than Cube |
| Local Connections | Reduces inter-node communication | Cube prioritizes intra-node edges |
| Symmetry | Simplifies load balancing | Ring is fully symmetric |
| Redundancy Degree | Controls balancing granularity | More redundants = finer-grained control |

 **Sources:** [README.md61-78](https://github.com/deepseek-ai/LPLB/blob/0490f794/README.md?plain=1#L61-L78)

 Different edge types have vastly different latency and bandwidth characteristics:


 - **Prioritize intra-node edges** when workload imbalance is primarily within nodes
 - **Use inter-node edges** when global imbalance dominates
 - **Balance edge types** based on communication cost vs. balancing benefit analysis

## Performance Considerations

 
### Topology Selection Guidelines

 
```

```

 **Performance Factors:**

 
| Factor | Impact on Performance | Optimization Strategy |
|---|---|---|
| Edge Count | More edges = more LP variables = slower solve | Balance against balancing flexibility |
| Inter-node Edges | 10-50× slower than intra-node | Minimize if possible |
| Graph Diameter | Affects token flow distance | Lower diameter = faster convergence |
| Redundancy Degree | Higher = finer control, more memory | Start with 2, increase if needed |

## Summary

 Custom topologies in LPLB provide fine-grained control over expert replication patterns. Key takeaways:

 
 - **r2o Matrix:** The `[group_size, num_redundants]` integer tensor defines which ranks replicate which experts
 - **Constraints:** Column uniqueness and no self-loops are mandatory for correct operation
 - **Design:** Consider communication costs, graph properties, and hardware topology
 - **Validation:** Always validate constraints before deployment
 - **Testing:** Use provided utilities to benchmark and compare topologies
 
 For most use cases, the standard topologies (Cube, Hypercube, Torus) are sufficient. Custom topologies are recommended when:

 
 - Hardware has non-standard connectivity (e.g., partial NVLINK)
 - Workload has known patterns that don't match standard topologies
 - Experimenting with novel load balancing strategies
