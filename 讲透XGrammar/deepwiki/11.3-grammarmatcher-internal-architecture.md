## Purpose and Scope

 This document describes the internal architecture of `GrammarMatcher::Impl`, the core runtime component responsible for validating tokens and strings against compiled grammars. The GrammarMatcher implements an Earley parser to track all valid parser states and generates token bitmasks that constrain LLM output to grammatically valid tokens.

 For information about the Earley parsing algorithm details, see [Earley Parser Implementation](https://deepwiki.com/mlc-ai/xgrammar/8.1-earley-parser-implementation). For token mask precomputation during grammar compilation, see [Adaptive Token Mask Precomputation](https://deepwiki.com/mlc-ai/xgrammar/7.4-adaptive-token-mask-precomputation). For the Python API surface, see [Grammar Matching and Validation](https://deepwiki.com/mlc-ai/xgrammar/3.3-grammar-matching-and-validation).

## Class Hierarchy

 The `GrammarMatcher` uses the PIMPL (Pointer to Implementation) pattern with `GrammarMatcher::Impl` as the concrete implementation. This implementation class inherits from `EarleyParser`, extending it with token-specific functionality.

 **Inheritance Relationship:**

 
 - `EarleyParser` provides the core character-by-character parsing algorithm (Scan/Predict/Complete operations)
 - `GrammarMatcher::Impl` adds token-level operations and adaptive mask integration
 - `BatchGrammarMatcher::Impl` orchestrates parallel processing of multiple matchers

## Core Data Structures

 
### ParserState

 `ParserState` is the fundamental unit representing a position in the grammar during parsing. It encodes where the parser currently is within a specific rule.

 
| Field | Type | Purpose |
|---|---|---|
| rule_id | int32_t | ID of the current rule being matched |
| sequence_id | int32_t | Which choice/sequence within the rule (for choice rules) |
| element_id | int32_t | Position within the sequence or FSM state ID |
| rule_start_pos | int32_t | History index where this rule started (for completion) |
| sub_element_id | int32_t | Byte position within byte strings or UTF-8 continuation bytes remaining |
| repeat_count | int32_t | Current iteration count for repetition constructs |
| partial_codepoint | int32_t | Accumulated UTF-8 codepoint during multi-byte matching |

 Special sentinel values:

 
 - `sequence_id == kUnexpandedRuleStartSequenceId` (128000): Rule hasn't been expanded yet
 - `rule_start_pos == kNoPrevInputPos` (-1): Root of parsing stack (no parent)
 - `sequence_id == kInvalidSequenceId` (-1): Invalid/uninitialized state

## Token Acceptance Flow

 
### AcceptToken Method

 The `AcceptToken` method validates and advances the parser state for a single token ID. The process involves converting the token to its UTF-8 byte sequence and advancing character-by-character.

 
```

```

 **Key behaviors:**

 
 - **Termination check**: Rejects tokens after stop token accepted
 - **Stop token handling**: If token is a stop token, only accept if `IsCompleted()` returns true
 - **Special token rejection**: Special tokens (except stop tokens) are always rejected
 - **Character-by-character advancement**: Token bytes processed sequentially via `EarleyParser::Advance()`
 - **Rollback on failure**: If any character fails, all previously accepted characters in the token are rolled back
 - **History tracking**: Token byte length stored in `token_length_history` for later rollback

## Token Bitmask Generation

 
### FillNextTokenBitmask Algorithm

 The `FillNextTokenBitmask` method is the performance-critical path that determines which tokens are valid at the current parser state. It leverages precomputed `AdaptiveTokenMask` objects from the cache.

 
```

```

 **Key optimizations:**

 
 - **Precomputed masks**: Each `ParserState` has a cached `AdaptiveTokenMask` that categorizes tokens as:

 
 - **Accepted**: Guaranteed valid for this state alone
 - **Rejected**: Guaranteed invalid for this state alone
 - **Uncertain**: Depends on parent/context states (requires testing)
 - **Union of accepted sets**: Accepted tokens across all states are merged (any state accepting makes it valid)
 - **Intersection of rejected sets**: Only tokens rejected by ALL states are truly rejected
 - **Longest common prefix (LCP) optimization**: When testing uncertain tokens, the algorithm maintains `prev_token` and `prev_matched_size`. For each new token, it computes the LCP with the previous token and reuses the already-matched prefix, avoiding redundant `Advance()` calls. If `lcp_len < prev_matched_size`, the parser state is rolled back only the necessary amount.
 - **Sorted vocabulary**: Tokens sorted by decoded string in `sorted_decoded_vocab` allows:

 
 - Prefix reuse: Adjacent tokens often share prefixes
 - Subtree rejection: When a token fails at position `j`, all tokens in its subtree (determined by `subtree_range[cur_token_idx]`) can be rejected without testing
 - Efficient iteration: Process uncertain tokens in lexicographic order
 
 **Sources:** [cpp/grammar_matcher.cc624-777](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_matcher.cc#L624-L777) [cpp/grammar_matcher.cc850-905](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_matcher.cc#L850-L905)

## Stop Token and Termination

 
### Termination Logic

 The matcher has two termination modes controlled by `terminate_without_stop_token_`:

 
| Mode | terminate_without_stop_token_ | Termination Condition |
|---|---|---|
| Standard | false (default) | Must accept stop token AND grammar completed |
| Auto-terminate | true | Grammar completed (no stop token required) |

 
```

```

 **Stop token acceptance rules:**

 
 - Stop tokens can only be accepted when `IsCompleted()` returns true (grammar fully matched)
 - In standard mode, generation continues until stop token explicitly accepted
 - In auto-terminate mode, generation stops immediately when grammar completes

## Temporary Buffer Management

 To minimize allocations during the critical path, `GrammarMatcher::Impl` maintains reusable buffers:

 
| Buffer | Type | Purpose |
|---|---|---|
| tmp_accepted_bitset_ | DynamicBitset | Accumulates accepted tokens across states |
| tmp_rejected_indices_ | vector<int32_t> | Accumulates rejected token indices |
| tmp_rejected_indices_delta_ | vector<int32_t> | Per-state rejected tokens during uncertain testing |

 These are initialized once in the constructor and cleared/reused for each `FillNextTokenBitmask` call, avoiding repeated heap allocations in the hot path.

## RepeatDetector: State Deduplication

 The `RepeatDetector` class prevents the Earley parser from processing duplicate states in the queue, which is essential for preventing exponential blowup during Predict/Complete operations.

 **Adaptive Storage Strategy:**

 
```

```

 **Rationale:**

 
 - Small state sets (< 50): Linear search in vector is faster than hashing
 - Large state sets (≥ 50): Hash set provides O(1) lookup
 - Transition happens once when threshold crossed
 - Typical states per position: 5-20 (vector sufficient)
 - Pathological cases: 100+ states (hash set necessary)
 
 **Sources:** [cpp/earley_parser.h187-217](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.h#L187-L217) [cpp/earley_parser.cc894-926](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L894-L926)

 
---

 This architecture achieves "near-zero overhead" through:

 
 - **Precomputed masks**: Expensive token validation done once during compilation
 - **Efficient cache lookups**: O(1) hash table access per state
 - **Buffer reuse**: No allocations in critical path
 - **Parallel processing**: Thread pool for batch operations
 - **Prefix sharing**: Sorted vocabulary enables LCP optimization for uncertain tokens
