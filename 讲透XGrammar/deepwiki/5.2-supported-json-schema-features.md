## Purpose and Scope

 This page provides a comprehensive reference of JSON Schema keywords and features supported by xgrammar's JSON Schema to EBNF converter. It documents which JSON Schema Draft specifications are implemented, what constraints can be enforced, and known limitations.

 For information about the converter's internal architecture and parsing pipeline, see [Converter Architecture](https://deepwiki.com/mlc-ai/xgrammar/5.1-converter-architecture). For detailed processing of arrays and objects, see [Object and Array Schema Processing](https://deepwiki.com/mlc-ai/xgrammar/5.3-object-and-array-schema-processing). For string format implementations, see [String Formats and Numeric Ranges](https://deepwiki.com/mlc-ai/xgrammar/5.5-string-formats-and-numeric-ranges).

## Core Type Keywords

 
### `type` Keyword

 The `type` keyword specifies the data type. XGrammar supports all JSON Schema primitive types and maps each to a corresponding `SchemaSpec` variant.

 
| JSON Schema Type | SchemaSpec Type | Generated Grammar |
|---|---|---|
| "integer" | IntegerSpec | Integer pattern with optional constraints |
| "number" | NumberSpec | Number pattern with decimals and scientific notation |
| "string" | StringSpec | Quoted string with escape sequences |
| "boolean" | BooleanSpec | "true" \| "false" |
| "null" | NullSpec | "null" |
| "array" | ArraySpec | Bracketed array with item schemas |
| "object" | ObjectSpec | Braced object with property schemas |

 **Type Array Support:** The `type` keyword can be an array to allow multiple types: `{"type": ["string", "integer"]}`. This is converted to `TypeArraySpec` containing multiple schema alternatives.

 **Sources:** [cpp/json_schema_converter.cc315-359](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L315-L359) [cpp/json_schema_converter.cc922-948](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L922-L948)

 
### Boolean Schema

 JSON Schema allows schemas to be boolean values:

 
 - `true`: Accepts any value (maps to `AnySpec`)
 - `false`: Rejects all values (triggers `kUnsatisfiableSchema` error)
 
 **Sources:** [cpp/json_schema_converter.cc269-278](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L269-L278)

## Array Constraints

 
### Array Schema Structure (`ArraySpec`)

 **Diagram: ArraySpec Structure and Processing Flow**

 
```

```

 
| Keyword | Type | Description | Implementation |
|---|---|---|---|
| prefixItems | array | Fixed-position item schemas | Each item gets its own schema in prefix_items vector |
| items | schema/boolean | Schema for all items (or after prefix) | Stored in additional_items if true/schema |
| unevaluatedItems | schema/boolean | Schema for items not covered by other keywords | Fallback to additional_items if items not present |
| minItems | integer | Minimum array length | Enforced via repetition count in grammar |
| maxItems | integer | Maximum array length | Enforced via repetition count in grammar |

 **Prefix vs Additional Items:** `prefixItems` defines schemas for specific array positions (tuple validation). `items` or `unevaluatedItems` defines the schema for remaining items.

 **Strict Mode Behavior:** When `strict_mode=true` (the default), arrays have the following default behaviors:

 
 - If `items` is not specified and no `unevaluatedItems` is present, additional items beyond `prefixItems` are **not allowed** (`allow_additional_items = false`)
 - This is implemented at [cpp/json_schema_converter.cc605-610](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L605-L610)
 
 **Non-Strict Mode Behavior:** When `strict_mode=false`:

 
 - If `items` and `unevaluatedItems` are both absent, additional items are **allowed** and can be any type (`AnySpec`)
 - This is implemented at [cpp/json_schema_converter.cc605-610](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L605-L610)
 
 **Sources:** [cpp/json_schema_converter.cc549-669](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L549-L669) [cpp/json_schema_converter.h73-81](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.h#L73-L81) [cpp/json_schema_converter.cc1425-1525](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L1425-L1525)

## Object Constraints

 
### Object Schema Structure (`ObjectSpec`)

 
```

```

 
| Keyword | Type | Description | Implementation |
|---|---|---|---|
| properties | object | Named property schemas | Each property stored with name and schema |
| required | array | Required property names | Set of required property names |
| patternProperties | object | Regex-matched property schemas | Pattern + schema pairs |
| propertyNames | schema | Schema for all property names | Must validate strings; constrains key patterns |
| additionalProperties | schema/boolean | Schema for properties not in properties | If false, disallows additional properties |
| unevaluatedProperties | schema/boolean | Schema for properties not matched by any keyword | Fallback if additionalProperties not specified |
| minProperties | integer | Minimum number of properties | Enforced in grammar generation |
| maxProperties | integer | Maximum number of properties | Enforced in grammar generation |

 **Property Evaluation Order:** The grammar generation prioritizes required properties first, then optional properties, then additional/unevaluated properties.

 **Strict Mode Behavior:** When `strict_mode=true` (the default), objects have the following default behaviors:

 
 - `additionalProperties` defaults to `false` (no additional properties allowed beyond `properties`)
 - `unevaluatedProperties` defaults to `false` (no unevaluated properties allowed)
 - This is implemented at [cpp/json_schema_converter.cc730](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L730-L730) [cpp/json_schema_converter.cc756-758](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L756-L758)
 
 **Non-Strict Mode Behavior:** When `strict_mode=false`:

 
 - `additionalProperties` defaults to `true` (additional properties of any type allowed)
 - `unevaluatedProperties` defaults to `true` (unevaluated properties allowed)
 - This allows more flexible object structures
 
 **Sources:** [cpp/json_schema_converter.cc671-812](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L671-L812) [cpp/json_schema_converter.h83-108](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.h#L83-L108)

 
### Pattern Properties Processing

 `patternProperties` allows defining schemas for properties matching regex patterns. The converter:

 
 - Stores each pattern-schema pair in `pattern_properties` vector
 - During grammar generation, creates alternations between patterns
 - Property keys are validated against patterns via `RegexToEBNF()`
 
 **Property Names:** When `propertyNames` is specified, it must validate strings. The converter enforces this by passing `"string"` as the default type if no type is specified.

 **Sources:** [cpp/json_schema_converter.cc697-709](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L697-L709) [cpp/json_schema_converter.cc711-728](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L711-L728)

## Composition Keywords

 
### `anyOf` and `oneOf`

 Both keywords create alternatives in the grammar. XGrammar treats them identically since EBNF alternation (`|`) naturally expresses "any of these options."

 **Diagram: anyOf/oneOf Processing**

 
```

```

 **Example:** A schema with `{"anyOf": [{"type": "string"}, {"type": "integer"}]}` generates grammar like:

 
```
root_case_0 ::= basic_string
root_case_1 ::= basic_integer
root ::= root_case_0 | root_case_1
```

 **Sources:** [cpp/json_schema_converter.cc889-905](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L889-L905) [cpp/json_schema_converter.h129-133](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.h#L129-L133) [tests/python/test_json_schema_converter.py609-632](https://github.com/mlc-ai/xgrammar/blob/c30554f7/tests/python/test_json_schema_converter.py#L609-L632)

 
### `allOf`

 Represents the intersection of multiple schemas. XGrammar handles this by:

 
 - Parsing each sub-schema into `AllOfSpec.schemas` vector
 - Attempting to merge constraints from all schemas
 - Generating a single grammar rule that satisfies all constraints
 
 **Limitation:** True intersection of arbitrary schemas is complex. The current implementation handles common cases (e.g., combining type constraints) but may not fully support all `allOf` combinations.

 **Sources:** [cpp/json_schema_converter.cc907-920](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L907-L920) [cpp/json_schema_converter.h135-139](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.h#L135-L139)

 
### Unsupported Composition Keywords

 
 - `not`: Not implemented (warning logged)
 - `if`/`then`/`else`: Conditional schemas not supported (warning logged)

## References (`$ref`)

 The `$ref` keyword enables schema reuse and recursion. XGrammar supports:

 
### Reference Resolution Patterns

 **Diagram: $ref Resolution and Circular Reference Handling**

 
```

```

 
| Reference Pattern | Description | Example |
|---|---|---|
| "#" | Root schema | {"$ref": "#"} |
| "#/$defs/Name" | Definition in $defs | {"$ref": "#/$defs/User"} |
| "#/definitions/Name" | Definition in definitions (older draft) | {"$ref": "#/definitions/User"} |
| "#/path/to/schema" | JSON Pointer path | {"$ref": "#/properties/user"} |

 **Circular Reference Handling:** The converter handles circular references through a two-level caching mechanism:

 
 - **URI-to-Rule Cache (`uri_to_rule_name_`)**: Maps reference URIs to generated EBNF rule names, established during grammar generation at [cpp/json_schema_converter.cc1127-1129](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L1127-L1129)
 - **Reference Spec Cache (`ref_cache_`)**: Maps reference URIs to parsed `SchemaSpecPtr` objects, preventing infinite loops during schema parsing at [cpp/json_schema_converter.cc843-851](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L843-L851)
 
 **Resolution Process:**

 
 - When `"#"` is encountered, it creates a placeholder `AnySpec` in the cache before parsing the root schema
 - This allows recursive schemas like `{"type": "object", "properties": {"child": {"$ref": "#"}}}` to work correctly
 - Subsequent references return the cached `SchemaSpecPtr` without re-parsing

 - Self-referential schemas with `$ref: "#"` - [tests/python/test_json_schema_converter.py553-572](https://github.com/mlc-ai/xgrammar/blob/c30554f7/tests/python/test_json_schema_converter.py#L553-L572)

## Schema Metadata and Ignored Keywords

 The following keywords are recognized but ignored during grammar generation (they don't affect validation). These keywords are excluded from the cache key computation in `SchemaParser::ComputeCacheKey()`:

 
| Keyword | Purpose | JSON Schema Use | Excluded from Cache |
|---|---|---|---|
| title | Human-readable title | Documentation | ✓ |
| description | Schema description | Documentation | ✓ |
| default | Default value | Provides default when value absent | ✓ |
| examples | Example values | Documentation and testing | ✓ |
| deprecated | Deprecation flag | Marks schema as deprecated | ✓ |
| readOnly | Read-only flag | For data validation contexts | ✓ |
| writeOnly | Write-only flag | For data validation contexts | ✓ |
| $comment | Developer comments | Internal documentation | ✓ |
| $schema | Schema version URI | Specifies JSON Schema draft version | ✓ |

 **Cache Key Purpose:** The cache key is used to deduplicate identical schemas during conversion. By excluding metadata keywords, schemas that are semantically identical but have different documentation are recognized as the same schema and share the same generated grammar rule.

 **Implementation:** The exclusion set is defined in `kSkippedKeys` at [cpp/json_schema_converter.cc199-209](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L199-L209) The cache key computation recursively serializes the schema object, skipping these keys at [cpp/json_schema_converter.cc211-244](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L211-L244)

 **Rationale:** These keywords provide documentation, hints, and context for human readers or schema validators but don't affect the structural constraints on valid JSON instances. For grammar-guided generation, only the structural constraints matter.

 **Sources:** [cpp/json_schema_converter.cc199-244](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L199-L244) [cpp/json_schema_converter.cc264-267](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L264-L267)
