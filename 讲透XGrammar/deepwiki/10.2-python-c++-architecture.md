## Purpose and Scope

 This document explains the Python-C++ interoperability architecture in XGrammar, focusing on how the nanobind binding layer enables efficient communication between Python user code and the C++ core. It covers the class wrapper pattern, DLTensor zero-copy tensor sharing, memory management, and thread safety mechanisms.

 For information about the C++ implementation internals, see [C++ Implementation Details](https://deepwiki.com/mlc-ai/xgrammar/11-c++-implementation-details). For the overall system architecture, see [System Architecture](https://deepwiki.com/mlc-ai/xgrammar/10-system-architecture).

 
## Architecture Overview

 XGrammar uses a dual-layer architecture where Python provides the user-facing API while C++ implements all performance-critical logic. The nanobind library serves as the Foreign Function Interface (FFI) boundary, enabling seamless interoperation between the two languages.

 
### Three-Layer Architecture Pattern

 The architecture consists of three distinct layers:

 
 - **Python Layer**: User-facing API classes that inherit from a common base pattern
 - **Nanobind Binding Layer**: FFI boundary implemented in `cpp/nanobind/nanobind.cc`
 - **C++ Core Layer**: Performance-critical implementations using PIMPL pattern

## Memory Management and Ownership

 Memory management across the Python-C++ boundary follows a clear ownership model enforced by nanobind's reference counting system.

 
### Ownership Model and Reference Counting

 
```

```

 **Sources:** [cpp/nanobind/nanobind.cc141-317](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/nanobind/nanobind.cc#L141-L317)

 
### Memory Lifetime Rules

 
| Aspect | Rule | Implementation Detail |
|---|---|---|
| Data ownership | C++ owns all grammar, FSM, and parser state data | Data resides in C++ heap memory managed by smart pointers |
| Reference tracking | nanobind manages reference counts | Automatic reference counting synchronized with Python GC |
| Cleanup | Automatic when Python objects are garbage collected | nanobind decrements refcount and calls C++ destructor at refcount=0 |
| Shared ownership | shared_ptr for shareable objects | Grammar, CompiledGrammar can be shared across multiple Python objects |
| Exclusive ownership | unique_ptr for single-owner objects | GrammarMatcher::Impl, GrammarCompiler::Impl have exclusive ownership |

 **Sources:** [cpp/nanobind/nanobind.cc141-317](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/nanobind/nanobind.cc#L141-L317)

 
### Tensor Memory Model for DLTensor

 
| Aspect | Ownership Rule | Implication |
|---|---|---|
| Buffer allocation | Python (PyTorch) owns the buffer | Memory allocated by PyTorch's allocator |
| Pointer passing | C++ borrows the pointer (does not own) | C++ receives void* data from DLTensor |
| Memory copying | Zero-copy guarantee | No allocation or memcpy during transfer |
| Lifetime requirement | Python tensor must outlive C++ usage | Caller must ensure tensor is not garbage collected during C++ operation |
| Thread safety | Caller's responsibility | Python must not modify tensor while C++ is accessing it |
