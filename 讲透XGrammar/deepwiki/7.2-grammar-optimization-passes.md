  This page documents the individual optimization passes that transform grammar representations to improve efficiency and enable runtime matching. These passes are applied sequentially during grammar compilation to normalize structure, eliminate redundancy, add semantic information, and generate finite state machines.

 For the overall compilation pipeline orchestration, see [Grammar Compiler and Optimization Pipeline](https://deepwiki.com/mlc-ai/xgrammar/5.2-supported-json-schema-features). For FSM construction details, see [Finite State Machine Generation](https://deepwiki.com/mlc-ai/xgrammar/5.4-formatting-and-whitespace-control).

 
## Overview

 Grammar optimization passes transform the internal Grammar representation through a series of functors that visit and mutate the grammar's abstract syntax tree (AST). Each pass is implemented as a `GrammarFunctor` subclass that traverses the grammar rules and their constituent `GrammarExpr` objects, applying specific transformations.

 The optimization pipeline achieves:

 
 - **Structure normalization**: Convert grammars to a canonical form for consistent processing
 - **Redundancy elimination**: Remove unused rules and inline simple references
 - **Semantic enrichment**: Add lookahead assertions and analyze nullable rules
 - **Efficient representation**: Build FSMs for performance-critical patterns

## Structure Normalization

 
### SingleElementExprEliminator

 Removes trivial container expressions that contain only a single element. This simplification reduces AST depth before subsequent transformations.

 **Transformations**:

 
 - `choices("a")` → `"a"` (single-choice becomes the choice itself)
 - `sequence("a")` → `"a"` (single-element sequence becomes the element)
 - `[a-a]` → `"a"` (character class with single codepoint becomes byte string)
 
 **Implementation**: Overrides `VisitSequence()`, `VisitChoices()`, and `VisitCharacterClass()` to detect single-element cases and unwrap them.

 Sources: [cpp/grammar_functor.cc175-215](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_functor.cc#L175-L215)

 
### StructureNormalizer

 Normalizes grammar structure to a canonical form where every rule body follows a strict pattern. This standardization simplifies all downstream processing.

 **Normalized form**:

 
```
rule_name ::= ("" | (element1_1 element1_2 ...) | (element2_1 element2_2 ...) | ...)
```

 Where:

 
 - Each rule body is a `kChoices` expression
 - Each choice is either: 
 - `kEmptyStr` (only as first choice, indicating the rule can be empty)
 - `kSequence` of elements (elements are `kCharacterClass`, `kByteString`, `kRuleRef`, `kRepeat`, `kCharacterClassStar`)
 - Exception: Rules with `kTagDispatch` bodies are preserved as-is
 
 **Lookahead assertions**: Normalized to `kSequence` expressions.

 **Nested structure handling**: When nested sequences or choices are encountered:

 
 - Nested sequences in sequences: Flattened into the parent sequence
 - Nested choices in choices: Flattened into the parent choice list
 - Choices in sequences: Extracted into new helper rules
 - TagDispatch in sequences/choices: Extracted into new helper rules

## Optimization Passes

 
### RuleInliner

 Inlines simple rule references to reduce indirection overhead during matching. Only inlines rules that meet strict criteria to avoid explosion in grammar size.

 **Inlining criteria** (all must be satisfied):

 
 - Rule body is a `kChoices` expression
 - Rule is non-empty (does not have empty string as first choice)
 - Each choice in the rule is a sequence of elements
 - No element in any sequence is a `kRuleRef` (prevents recursive inlining)
 
 **When applied**: Rule references at the **beginning of sequences** are candidates for inlining.

 **Example transformation**:

 
```
A ::= ((B c d) | (e f))
B ::= ((x y) | (z))

# After inlining B into A:
A ::= ((x y c d) | (z c d) | (e f))
```

 **Implementation**:

 
 - `CheckIfRuleCanBeInlined()`: Validates inlining criteria
 - `VisitChoices()`: Detects inlinable rule references and expands them
 
 **Trade-offs**: Inlining increases grammar size but reduces runtime rule dispatch overhead. The restrictive criteria prevent pathological expansion.

 Sources: [cpp/grammar_functor.cc498-579](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_functor.cc#L498-L579) [cpp/grammar_functor.h317-320](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_functor.h#L317-L320)

 
### DeadCodeEliminator

 Removes unreferenced rules from the grammar to reduce memory footprint and compilation time.

 **Algorithm**:

 
 - Use `UsedRulesAnalyzer` to find all reachable rules from the root rule
 - Create mapping from old rule IDs to new rule IDs (only for used rules)
 - Rebuild grammar with only used rules, updating all `kRuleRef` and `kTagDispatch` references
 
 **UsedRulesAnalyzer**:

 
 - Implements breadth-first traversal from root rule
 - Follows `kRuleRef`, `kRepeat`, and `kTagDispatch` edges
 - Returns set of reachable rule IDs
 
 **Rule reference types traversed**:

 
 - `kRuleRef`: Direct rule reference
 - `kRepeat`: Repetition of a rule
 - `kTagDispatch`: Each tag's associated rule
 
 Sources: [cpp/grammar_functor.cc585-679](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_functor.cc#L585-L679) [cpp/grammar_functor.h325-328](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_functor.h#L325-L328)

 
### LookaheadAssertionAnalyzer

 Detects patterns where a rule is always followed by specific tokens and adds lookahead assertions to enable early rejection of invalid tokens.

 **Detection pattern**: Rule R has a lookahead assertion if:

 
 - R appears in the middle of exactly one sequence (not at the end)
 - The elements after R are consistent across all occurrences
 - R does not appear in `kTagDispatch` rules
 - R does not appear as the last element of any sequence (except in its own definition)
 
 **Exact vs. non-exact lookahead**:

 
 - **Exact**: The rule appears only once in the grammar (in the detected position)
 - **Non-exact**: The rule appears multiple times but has a consistent lookahead
 
 **Example**:

 
```
main ::= ((prefix number suffix))
number ::= ((digit+))

# If number always followed by suffix, add lookahead:
number ::= ((digit+)) with lookahead assertion "suffix starts with..."
```

 **Implementation**:

 
 - `DetectLookaheadAssertion()`: Scans all rules for consistent lookahead patterns
 - `IsExactLookaheadAssertion()`: Determines if lookahead is exact
 - Updates `Rule::lookahead_assertion_id` and `Rule::is_exact_lookahead`

## Analysis Passes

 
### AllowEmptyRuleAnalyzer

 Identifies all rules that can match the empty string (ε-rules). This information is crucial for Earley parsing and token mask computation.

 **Algorithm** (two-phase):

 **Phase 1 - Explicit empty rules**:

 
 - Rules with `kEmptyStr` as first choice
 - Rules where all sequences contain only `kCharacterClassStar` elements
 
 **Phase 2 - Indirect empty rules** (Bellman-Ford on rule reference graph):

 
 - Build inverted rule reference graph (referee → referrers)
 - Propagate emptiness: If rule A can be empty and rule B references A in a sequence where all other elements can be empty, then B can be empty
 - Repeat until no new empty rules found
 
 **Emptiness conditions for elements**:

 
 - `kCharacterClassStar`: Always can be empty (matches zero or more)
 - `kRuleRef`: Can be empty if referenced rule can be empty
 - `kRepeat`: Can be empty if `min_repeat_count == 0` or referenced rule can be empty
 - Other elements: Cannot be empty

### RuleRefGraphFinder

 Helper visitor that constructs an inverted rule reference graph showing which rules reference each rule.

 **Output format**: `vector<vector<int32_t>>` where `graph[rule_id]` contains IDs of all rules that reference `rule_id`.

 **Traversed reference types**:

 
 - `kRuleRef`: `graph[referenced_rule].push_back(current_rule)`
 - `kRepeat`: `graph[repeated_rule].push_back(current_rule)`
 - `kTagDispatch`: `graph[tag_rule].push_back(current_rule)` for each tag

## Optimization Pipeline Orchestration

 
### GrammarOptimizer

 Combines all optimization passes in a fixed sequence to produce an optimized grammar ready for FSM construction and compilation.

 **Pass sequence**:

 
 - **GrammarNormalizer**: Structure normalization
 - **ByteStringFuser**: Combine consecutive byte strings (implementation not shown in provided code)
 - **RuleInliner**: Inline simple rules
 - **DeadCodeEliminator**: Remove unreferenced rules
 - **LookaheadAssertionAnalyzer**: Add lookahead constraints
 - **AllowEmptyRuleAnalyzer**: Identify nullable rules
 - **RepetitionNormalizer**: Normalize repetition ranges (implementation not shown)
 - **GrammarFSMBuilder**: Build finite state machines (see [Finite State Machine Generation](https://deepwiki.com/mlc-ai/xgrammar/5.4-formatting-and-whitespace-control))

## Data Structures and Helpers

 
### Grammar::Impl::GrammarExpr

 The core data structure representing grammar expressions. All optimization passes operate on this representation.

 **Structure**:

 
 - `type`: `GrammarExprType` enum (kSequence, kChoices, kRuleRef, etc.)
 - `data`: Variable-length array of `int32_t` values
 - `data_len`: Length of the data array
 
 **Storage**: CSR-style (Compressed Sparse Row):

 
 - All `GrammarExpr` data stored consecutively in `grammar_expr_data_` vector
 - `grammar_expr_indptr_` vector stores starting index of each expression
 - Each expression stored as: `[type, data_len, ...data...]`
 
 **Type-specific data formats**:

 
| Type | Data Format |
|---|---|
| kByteString | [byte0, byte1, ...] |
| kCharacterClass | [is_negative, lower0, upper0, lower1, upper1, ...] |
| kCharacterClassStar | Same as kCharacterClass |
| kEmptyStr | [] |
| kRuleRef | [rule_id] |
| kSequence | [expr_id0, expr_id1, ...] |
| kChoices | [expr_id0, expr_id1, ...] |
| kTagDispatch | [tag_expr0, rule_id0, ..., stop_eos, stop_str_expr_id, loop_after_dispatch, excluded_str_expr_id] |
| kRepeat | [rule_id, min_repeat_count, max_repeat_count] |

## Performance Considerations

 **Pass ordering rationale**:

 
 - **Normalization first**: Ensures all subsequent passes work on consistent structure
 - **Inlining before dead code elimination**: Inlining may make rules unreferenced
 - **Lookahead after inlining**: Inlining may create new lookahead opportunities
 - **Empty analysis late**: Needs final rule structure to be accurate
 - **FSM generation last**: Requires complete semantic information
 
 **Memory impact**:

 
 - **RuleInliner**: Can increase grammar size significantly (multiplicative for each inlined rule)
 - **DeadCodeEliminator**: Reduces memory by removing unreferenced rules
 - **AllowEmptyRuleAnalyzer**: Minimal overhead (just a vector of IDs)
 - **FSM generation**: Largest memory consumer (creates DFA states)
 
 **Compilation time**:

 
 - Normalization and inlining: O(n) in grammar size
 - Dead code elimination: O(n) BFS traversal
 - Lookahead analysis: O(n²) in worst case (scans all rules for each rule)
 - Empty rule analysis: O(n·m) where m is average rule reference graph degree
 - FSM generation: Can be exponential in worst case (DFA construction)
