  Grammar matching is the runtime component of xgrammar that validates whether token sequences conform to a specified grammar. After a grammar is compiled ([2.2](https://deepwiki.com/mlc-ai/xgrammar/2.2-grammar-compilation)), the matching engine uses an Earley parser to incrementally validate tokens as they are generated by an LLM, producing bitmasks that constrain which tokens can be sampled next.

 This page provides a conceptual overview of the matching system. For implementation details of the Earley parser algorithm, see [8.1](https://deepwiki.com/mlc-ai/xgrammar/8.1-earley-parser-implementation). For token acceptance and bitmask generation details, see [8.2](https://deepwiki.com/mlc-ai/xgrammar/8.2-token-acceptance-and-state-management) and [8.3](https://deepwiki.com/mlc-ai/xgrammar/8.3-token-bitmask-generation).

 
## Purpose and Scope

 The grammar matching system serves three primary functions:

 
 - **Token Validation**: Accept or reject individual tokens based on whether they conform to the grammar
 - **Bitmask Generation**: Produce efficient bitmasks indicating which tokens are valid at each generation step
 - **State Management**: Maintain parser state to support rollback, reset, and termination detection
 
 The matching engine operates on `CompiledGrammar` objects and integrates directly with LLM inference loops to constrain generation.

## The Earley Parser Approach

 xgrammar uses an Earley parser for grammar matching. This algorithm is well-suited for constrained generation because it:

 
 - **Supports arbitrary context-free grammars** without requiring grammar transformations
 - **Processes input incrementally**, validating one character at a time
 - **Maintains multiple parallel parsing states**, handling ambiguous grammars efficiently
 - **Allows efficient backtracking** for speculative decoding and rollback scenarios
 
 The Earley parser operates through three fundamental operations:

 
 - **Predict**: When a rule reference is encountered, predict which rules could match next
 - **Scan**: Accept a character if it matches the current position in any active parsing state
 - **Complete**: When a rule finishes, advance parent states that were waiting for it

### ParserState

 The `ParserState` struct represents a position in the parsing process. Each state tracks:

 
| Field | Purpose |
|---|---|
| rule_id | Which grammar rule is being processed |
| sequence_id | Which choice within the rule is active |
| element_id | Position within the sequence or FSM state |
| rule_start_pos | Where this rule started (for completion) |
| sub_element_id | Position within multi-byte elements (strings, UTF-8) |
| repeat_count | Number of times a repeated element has matched |
| partial_codepoint | Accumulated codepoint for UTF-8 character validation |

 The parser maintains multiple `ParserState` objects in parallel to handle grammar ambiguity and choices.

### GrammarMatcher::Impl

 The `GrammarMatcher::Impl` class (C++) extends `EarleyParser` and adds token-specific functionality:

 
 - **Token-to-string conversion**: Uses `TokenizerInfo` to decode token IDs to strings
 - **Stop token handling**: Detects when grammar completion requires accepting stop tokens
 - **Token bitmask caching**: Leverages `AdaptiveTokenMask` from the compiled grammar
 - **History tracking**: Maintains `token_length_history` for rollback support
 
 The class provides three key methods:

 
 - `AcceptToken(token_id)`: Validates a token by matching its decoded string character-by-character
 - `FillNextTokenBitmask(bitmask)`: Generates a bitmask of valid next tokens
 - `Rollback(num_tokens)`: Reverts the parser state by a specified number of tokens

## Token Acceptance Algorithm

 When `accept_token` is called, the following process occurs:

 
 - **Special Token Check**: Stop tokens and special tokens receive special handling
 - **Token Decoding**: The token ID is decoded to a UTF-8 byte string using `TokenizerInfo`
 - **Character-by-Character Matching**: Each byte is validated through `Advance(char)`
 - **State Updates**: If all characters match, the parser advances; otherwise, it rolls back
 - **History Recording**: The token's character count is recorded for potential rollback

## Token Bitmask Generation

 The `fill_next_token_bitmask` method determines which tokens are valid at the current parsing position. The algorithm leverages precomputed `AdaptiveTokenMask` objects stored in the `CompiledGrammar`:

 
 - **Retrieve Current States**: Get all active `ParserState` objects from the parser
 - **Lookup Adaptive Masks**: For each state, find its precomputed `AdaptiveTokenMask`
 - **Merge Accepted Sets**: Union all definitely-accepted token sets across states
 - **Process Uncertain Tokens**: For uncertain tokens, speculatively test them via `Advance` 
 - Use longest common prefix (LCP) optimization to reuse parsing work
 - Leverage the trie structure in `sorted_decoded_vocab`
 - **Intersect Rejected Sets**: Find tokens rejected by all states
 - **Handle Stop Tokens**: Add stop tokens only if `IsCompleted()` returns true
 
 The result is a packed bitset where each bit represents whether a token is valid (1) or invalid (0).

## State Management and Rollback

 The matching system supports several state management operations:

 
### Rollback

 The `rollback(num_tokens)` method allows reverting the parser state by a specified number of tokens. This is essential for:

 
 - **Speculative decoding**: Testing multiple token sequences in parallel
 - **Error recovery**: Backing out of invalid parsing paths
 - **Beam search**: Exploring alternative generation paths
 
 Rollback works by:

 
 - Popping states from `scanable_state_history_` based on `token_length_history`
 - Reverting `rule_id_to_completable_states_` (needed for Earley completion)
 - Clearing the `stop_token_is_accepted_` flag if applicable
 
 With the Earley parser implementation, rollback is unlimited (no max_rollback_tokens constraint).

 **Sources:** [cpp/grammar_matcher.cc838-848](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_matcher.cc#L838-L848)

 
### Reset

 The `reset()` method returns the matcher to its initial state, allowing reuse without reallocating:

 
 - Clears all parser state history
 - Re-initializes with the root grammar rule
 - Runs initial prediction to populate the first set of scanable states
 
 **Sources:** [cpp/earley_parser.cc348-361](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L348-L361)

 
### Termination Detection

 The `is_terminated()` method checks if generation should stop. Termination occurs when:

 
 - **With stop token requirement** (default): Both `IsCompleted()` and `stop_token_is_accepted_` are true
 - **Without stop token** (`terminate_without_stop_token=True`): Only `IsCompleted()` needs to be true
 
 This allows flexible control over when generation ends based on application requirements.

## Performance Optimizations

 The grammar matching implementation includes several optimizations:

 
 - **Adaptive Token Masks**: Precomputed masks categorize tokens as accepted, rejected, or uncertain ([2.2](https://deepwiki.com/mlc-ai/xgrammar/2.2-grammar-compilation))
 - **Longest Common Prefix**: Reuses parsing work when testing similar tokens in the trie
 - **First Character Filtering**: Narrows candidates based on first byte before full validation
 - **Speculative Calculation**: For self-recursive patterns, caches results across iterations
 - **Compact State Representation**: `ParserState` uses primitive types for cache efficiency
 - **RepeatDetector**: Prevents duplicate states in the Earley parser queue using thresholds
 
 These optimizations enable real-time token constraint generation during LLM inference with minimal overhead.
