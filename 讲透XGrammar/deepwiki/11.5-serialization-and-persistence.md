  This page documents the serialization and deserialization capabilities in XGrammar, which enable persistent storage and transfer of `Grammar` and `CompiledGrammar` objects. This functionality allows users to save preprocessed grammars to disk and reload them later, avoiding repeated parsing and compilation overhead.

 For information about grammar compilation and caching during runtime, see [Grammar Compilation](https://deepwiki.com/mlc-ai/xgrammar/2.2-grammar-compilation) and [Multi-Level Caching Strategy](https://deepwiki.com/mlc-ai/xgrammar/9.1-multi-level-caching-strategy).

## Overview of Serializable Objects

 XGrammar provides JSON serialization for two core objects:

 
| Object | Purpose | Serialization Scope |
|---|---|---|
| Grammar | Contains the abstract syntax tree (AST) of parsed grammars | Full grammar structure with rules and expressions |
| CompiledGrammar | Contains preprocessed token masks and FSMs for efficient matching | Token masks, FSMs, and grammar reference (excludes TokenizerInfo object) |

 Both objects support bidirectional conversion to/from JSON strings through dedicated methods.

### Version Checking

 Grammar deserialization includes version validation. The serialized JSON contains a `__VERSION__` field that must match the current XGrammar version. If versions mismatch, a `DeserializeVersionError` is raised.

 **Error Types:**

 
 - `InvalidJSONError`: When the JSON string is malformed
 - `DeserializeFormatError`: When the JSON structure doesn't match the expected format
 - `DeserializeVersionError`: When the `__VERSION__` field doesn't match the current version
 
 **Sources:** [python/xgrammar/grammar.py424-432](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/grammar.py#L424-L432)

## CompiledGrammar Serialization

 
### Design Rationale

 `CompiledGrammar` serialization is more complex because it's associated with a `TokenizerInfo` object. The design separates concerns:

 
 - **TokenizerInfo is NOT serialized** with `CompiledGrammar` - it must be provided during deserialization
 - **Tokenizer metadata IS serialized** - used for validation during deserialization
 - This enables sharing a single `TokenizerInfo` instance across multiple compiled grammars

### Metadata Validation

 During deserialization, XGrammar verifies that the provided `TokenizerInfo` matches the tokenizer metadata stored in the JSON. This prevents mismatches where a compiled grammar is loaded with the wrong tokenizer vocabulary.

 **Validation Failure:** If metadata doesn't match, a `DeserializeFormatError` is raised with details about the mismatch.

## Memory and Performance Considerations

 
### Serialization Overhead

 Both `Grammar` and `CompiledGrammar` serialization involves:

 
 - **Memory allocation** for JSON string construction
 - **Deep traversal** of internal data structures
 - **String encoding** of binary data
 
 The size of serialized output depends on:

 
 - Grammar complexity (number of rules and expressions)
 - Vocabulary size (affects `CompiledGrammar` token mask data)
 - FSM state count (affects `CompiledGrammar` per-rule FSM data)
 
 
### Deserialization Overhead

 Deserialization involves:

 
 - **JSON parsing** of the entire string
 - **Memory allocation** for reconstructed objects
 - **Validation passes** (version, format, metadata)
 
 **Performance Tip:** For frequently used grammars, maintain deserialized objects in memory rather than repeatedly deserializing from JSON.

 **Sources:** [cpp/grammar.cc24-31](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar.cc#L24-L31) [python/xgrammar/compiler.py42-44](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/compiler.py#L42-L44)

## Implementation Details

 
### CSR-Style Storage in Grammar

 The `Grammar` object stores expressions in CSR (Compressed Sparse Row) matrix style:

 
 - `grammar_expr_data_`: Flat array of all expression data
 - `grammar_expr_indptr_`: Index pointers marking expression boundaries
 
 This format is efficiently serialized as two JSON arrays and reconstructed during deserialization.


 **Diagram: Grammar CSR-style data serialization**

 **Sources:** [cpp/grammar.cc24-31](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar.cc#L24-L31)

 
### CompiledGrammar Internal Structure

 The serialized `CompiledGrammar` contains:

 
| Component | Description |
|---|---|
| per_rule_fsms | FSM states and transitions for each grammar rule |
| adaptive_token_masks | Precomputed accepted/rejected token sets per FSM state |
| complete_fsm | Optional complete FSM if applicable |
| allow_empty_rule_ids | Rules that can match empty strings |
| tokenizer_metadata | Hash/signature of the tokenizer for validation |

 **Note:** The actual `TokenizerInfo` object (vocabulary, decoding logic) is NOT included in the serialization to avoid duplication and enable sharing.

 **Sources:** [cpp/grammar.cc24-31](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar.cc#L24-L31) [python/xgrammar/compiler.py31-44](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/compiler.py#L31-L44)

 
### AutoSerializeJSON/AutoDeserializeJSON

 These utility functions (referenced in the implementation) provide:

 
 - **Automatic field serialization** based on object structure
 - **Version field management** (injection and validation)
 - **Error result types** (`std::variant<T, SerializationError>`)
 - **Type-safe reconstruction** during deserialization
 
 The implementation uses introspection or template metaprogramming to serialize object fields without manual JSON construction code.

## Integration with Caching System

 Serialization complements the runtime caching system (see [Multi-Level Caching Strategy](https://deepwiki.com/mlc-ai/xgrammar/9.1-multi-level-caching-strategy)):

 
 - **Runtime cache:** In-memory LRU cache for active `CompiledGrammar` objects during execution
 - **Persistent serialization:** Long-term storage across process restarts
 
 These systems serve different purposes:

 
 - Use runtime cache for repeated grammar usage within a single process
 - Use serialization for persistent storage, distribution, or cross-process communication
