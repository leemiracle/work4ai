  This page documents the grammar compilation system, which transforms `Grammar` objects into optimized `CompiledGrammar` objects ready for runtime matching. The compilation process includes grammar optimization, FSM generation, and token mask precomputation. For information about grammar definition and construction, see [Grammar Definition and Construction](https://deepwiki.com/mlc-ai/xgrammar/2.1-grammar-representation). For runtime matching using compiled grammars, see [Grammar Matching and Validation](https://deepwiki.com/mlc-ai/xgrammar/2.3-grammar-matching).

 
## Overview

 The `GrammarCompiler` class is responsible for compiling `Grammar` objects into `CompiledGrammar` objects. Compilation is a computationally expensive process involving multiple optimization passes and FSM construction, so the compiler implements sophisticated two-tier caching (grammar-level and rule-level) to amortize costs across similar grammars.

## FSM Generation and Hashing

 After optimization passes, the `GrammarFSMBuilder` constructs finite state machines for each rule in the grammar. The FSMs are then hashed by `GrammarFSMHasher` to enable rule-level cache lookups.

 
```

```

 **FSM Generation and Hashing Pipeline**

 The FSM builder creates a finite state machine for each rule, performing DFA conversion and minimization. The FSM hasher then computes a hash for each FSM to enable cross-grammar rule-level cache lookups.

### Token Checking Optimizations

 Several optimizations accelerate token mask generation:

 
 - **Speculative Calculation**: For self-recursive patterns (e.g., string content matching), tokens with all ASCII characters in the first-character mask are accepted without parser simulation
 - **Longest Common Prefix (LCP)**: When checking sorted tokens, the parser state is rolled back only to the common prefix with the previous token
 - **Subtree Pruning**: When a token is rejected, all tokens in its subtree (sharing the same prefix) are also rejected
 - **Tag Dispatch Second Slicing**: For tag dispatch rules, tokens are quickly accepted if their suffix doesn't contain trigger strings
 
 **Sources:** [cpp/grammar_compiler.cc415-496](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_compiler.cc#L415-L496) [cpp/grammar_compiler.cc498-698](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_compiler.cc#L498-L698)

 
### AdaptiveTokenMask Storage

 The `AdaptiveTokenMask` class uses adaptive storage based on the ratio of accepted to rejected tokens:

 
| Storage Type | Condition | Stored Data |
|---|---|---|
| kAccepted | Few accepted tokens | accepted_indices vector |
| kRejected | Few rejected tokens | rejected_indices vector |
| kAcceptedBitset | Many accepted tokens | accepted_bitset (DynamicBitset) |

 All storage types also maintain an `uncertain_indices` vector for tokens that require lookahead checking.

 **Threshold**: The storage switches to bitset when vector size exceeds `AdaptiveTokenMask::USE_BITSET_THRESHOLD`.

 **Sources:** [cpp/compiled_grammar_impl.h](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/compiled_grammar_impl.h) [cpp/grammar_compiler.cc133-294](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_compiler.cc#L133-L294)

 
## Caching System Architecture

 The compiler implements a sophisticated two-tier caching system to avoid redundant compilation:

 
```

```

 **Two-Tier Caching Architecture**

 The grammar-level cache stores entire `CompiledGrammar` objects, while the rule-level cache stores `AdaptiveTokenMask` objects keyed by FSM hash, enabling cache sharing across different grammars with similar rule patterns.

 **Sources:** [cpp/grammar_compiler.cc](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_compiler.cc) [cpp/grammar_functor.h407-440](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_functor.h#L407-L440)

 
### Grammar-Level Cache

 The grammar-level cache is an LRU (Least Recently Used) cache that stores complete `CompiledGrammar` objects:

 **Cache Key Computation**:

 
 - Grammar structure (serialized or hashed)
 - TokenizerInfo identifier
 - Compilation options (indent, separators, strict_mode, etc.)
 
 **Memory Management**:

 
 - Configurable via `cache_limit_bytes` parameter
 - Default: unlimited (`-1`)
 - When limit exceeded: evict least recently used entries

## Performance Characteristics

 
### First Compilation (Cold Cache)

 Compilation time breakdown:

 
 - **Grammar Optimization**: 1-10 ms (depends on grammar complexity)
 - **FSM Generation**: 5-20 ms (depends on number of rules)
 - **Token Mask Precomputation**: 50-500 ms (depends on vocabulary size and grammar complexity)
 
 **Sources:** [tests/python/test_grammar_compiler.py22-25](https://github.com/mlc-ai/xgrammar/blob/c30554f7/tests/python/test_grammar_compiler.py#L22-L25) [tests/python/test_grammar_matcher_json_schema.py90-94](https://github.com/mlc-ai/xgrammar/blob/c30554f7/tests/python/test_grammar_matcher_json_schema.py#L90-L94)

 
### Subsequent Compilations (Warm Cache)

 
 - **Grammar-level cache hit**: < 1 ms (instant return)
 - **Rule-level cache hit**: 20-80% reduction in compilation time
 - **Cross-grammar cache benefit**: Grammars with shared rule patterns benefit significantly
 
 **Sources:** [tests/python/test_grammar_compiler.py62-84](https://github.com/mlc-ai/xgrammar/blob/c30554f7/tests/python/test_grammar_compiler.py#L62-L84) [tests/python/test_grammar_compiler.py349-382](https://github.com/mlc-ai/xgrammar/blob/c30554f7/tests/python/test_grammar_compiler.py#L349-L382)

## Best Practices

 
 - **Reuse Compiler Instances**: Create one `GrammarCompiler` per tokenizer and reuse it to benefit from caching
 - **Set Appropriate Cache Limits**: For memory-constrained environments, set `cache_limit_bytes` to prevent unbounded growth
 - **Use Multi-Threading for Large Vocabularies**: Set `max_threads=8` for vocabularies with >50K tokens
 - **Compile Once, Match Many Times**: Compilation is expensive; create matchers from cached `CompiledGrammar` objects
 - **Monitor Cache Size**: Use `get_cache_size_bytes()` to track memory usage in long-running processes
