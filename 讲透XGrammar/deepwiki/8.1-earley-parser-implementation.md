## Purpose and Scope

 This document describes the Earley parsing algorithm implementation used in xgrammar for context-free grammar recognition during LLM generation. The Earley parser is the core matching engine that validates character sequences against compiled grammars and enables the generation of token bitmasks for constrained decoding.

 For information about how the parser is used to generate token bitmasks and integrate with LLMs, see [Token Acceptance and State Management](https://deepwiki.com/mlc-ai/xgrammar/8.2-token-acceptance-and-state-management) and [Token Bitmask Generation](https://deepwiki.com/mlc-ai/xgrammar/8.3-token-bitmask-generation). For details on the grammar representation that the parser operates on, see [Grammar Representation](https://deepwiki.com/mlc-ai/xgrammar/2.1-grammar-representation).

 
## Overview of the Earley Algorithm

 The Earley parsing algorithm is a chart-based parsing technique that handles arbitrary context-free grammars, including those with left recursion, right recursion, and ambiguity. The algorithm operates by maintaining multiple parse states in parallel and processing input one character at a time through three operations:

 
 - **Scan**: Advance states when the current character matches
 - **Predict**: Expand states when a rule reference is encountered
 - **Complete**: Propagate completed rules back to their parent states
 
 The implementation maintains parse states across input positions, storing scanable states (those ready to match the next character) and completable states (those that can complete their parent rules).

## Core Data Structures

 
### ParserState Structure

 
```

```

 The `ParserState` struct represents a position in the grammar during parsing. Each state tracks:

 
| Field | Type | Purpose |
|---|---|---|
| rule_id | int32_t | ID of the current grammar rule being matched |
| sequence_id | int32_t | Which alternative (choice) in the rule is selected |
| element_id | int32_t | Position within the sequence or FSM node ID |
| rule_start_pos | int32_t | Input position where this rule began (for completion) |
| sub_element_id | int32_t | Position within byte string or UTF-8 continuation bytes remaining |
| repeat_count | int32_t | Current iteration count for repetition elements |
| partial_codepoint | int32_t | Accumulated UTF-8 codepoint during multi-byte matching |

 States with `sequence_id == kUnexpandedRuleStartSequenceId` (128000) indicate a rule that hasn't been expanded into its alternatives yet. States with `rule_start_pos == kNoPrevInputPos` (-1) represent root-level rules.

 Sources: [cpp/earley_parser.h41-130](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.h#L41-L130)

 
### State Tracking and History

 
```

```

 The parser maintains three primary history structures:

 
 - **`scanable_state_history_`**: A `Compact2DArray<ParserState>` where `history[i]` contains all states that can scan the character at position `i`. These are the states ready to match the next input character.
 - **`rule_id_to_completable_states_`**: A `Compact2DArray<std::pair<int32_t, ParserState>>` where `states[i]` maps rule IDs to their parent states at position `i`. When a rule completes, this structure provides the parent states to advance.
 - **`is_completed_`**: A `std::vector<bool>` tracking whether the root rule has completed at each position, indicating whether a stop token can be accepted.
 
 Temporary working structures used during `Advance`:

 
 - **`tmp_process_state_queue_`**: Queue of states awaiting Predict/Complete operations
 - **`tmp_states_visited_in_queue_`**: RepeatDetector preventing duplicate state processing
 - **`tmp_states_to_be_added_`**: Accumulator for new scanable states

### RepeatDetector Optimization

 
```

```

 The `RepeatDetector` class optimizes state duplicate detection by adapting its internal representation:

 
 - **Small state count** (≤50): Uses `std::vector<ParserState>` with linear search
 - **Large state count** (>50): Transitions to `std::unordered_set<ParserState>` with hash-based lookup
 - Avoids hash table overhead for typical parsing scenarios with few parallel states
 - Automatically migrates all states from vector to set when crossing threshold

## Parser Operations

 
### Advance: Main Entry Point

 
```

```

 The `Advance` method is the main entry point that processes one character:

 
 - **Initialize**: Clear temporary structures for this iteration
 - **Scan**: Process all scanable states from the previous position with the current character
 - **Reject early**: If no states can proceed, return false without modifying history
 - **Predict/Complete loop**: Process queued states until exhausted
 - **Update history**: Record new scanable states and completion status
 
 Sources: [cpp/earley_parser.cc211-247](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L211-L247)

 
### Scan Operation

 The Scan operation advances states when the current character matches. It dispatches to specialized handlers based on the grammar element type:

 
```

```

 **AdvanceByteString**: Checks if `ch == sub_rule[sub_element_id]`. If matched:

 
 - Increment `sub_element_id`
 - If byte string complete, increment `element_id` and enqueue for processing
 - Otherwise, add directly to `tmp_states_to_be_added_` (continues matching next byte)
 
 **AdvanceCharacterClass**: Handles UTF-8 character matching:

 
 - If `sub_element_id > 0`: Processing UTF-8 continuation bytes 
 - Accumulate into `partial_codepoint`
 - When complete, check if codepoint in character class ranges
 - If `sub_element_id == 0`: First byte 
 - ASCII: Direct range check against character class
 - Multi-byte: Compute possible codepoint range, filter by potential matches
 
 **AdvanceCharacterClassStar**: Similar to character class but doesn't advance `element_id` after match (enables repetition)

 **AdvanceFsm**: For rules with compiled FSMs:

 
 - Iterate over edges from `state.element_id`
 - Match character against edge ranges
 - Create new state with `element_id = edge.target`
 - Enqueue without processing if state is not at FSM terminals
 
 Sources: [cpp/earley_parser.cc171-198](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L171-L198) [cpp/earley_parser.cc573-871](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L573-L871)

 
### Predict Operation

 
```

```

 The Predict operation determines what can happen next from a state:

 **For FSM-based rules**: Calls `ExpandNextRuleRefElementOnFSM` to:

 
 - Process epsilon edges (add target states to queue)
 - Process rule reference edges (predict referenced rules, manage right recursion)
 - Add parent states to `rule_id_to_completable_states_`
 
 **For sequence-based rules**: Examines the current element:

 
 - **kRuleRef/kRepeat**: Calls `ExpandNextRuleRefElement` to predict the referenced rule
 - **kCharacterClass/kByteString**: Returns `(scanable=true, completable=false)`
 - **kCharacterClassStar**: Also enqueues state with `element_id+1` (zero-match path)
 - End of sequence: Returns `(scanable=false, completable=true)`
 
 **Right recursion optimization**: When a rule reference is at the end of its parent sequence and leads back to ancestors, the implementation adds ancestor states directly to the current completion layer instead of creating redundant parent pointers.

 Sources: [cpp/earley_parser.cc112-169](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L112-L169) [cpp/earley_parser.cc351-571](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L351-L571)

 
### Complete Operation

 
```

```

 The Complete operation propagates a completed rule back to its parent states:

 
 - **Check for root completion**: If `rule_start_pos == kNoPrevInputPos`, this is a root rule completing, so set `tmp_accept_stop_token_ = true`
 - **Find parent states**: Look up all parent states from `rule_id_to_completable_states_[state.rule_start_pos]` where `ref_id == state.rule_id`
 - **Advance each parent**:

 
 - **FSM parent**: Enqueue parent state (FSM edges will be processed in Predict)
 - **kRuleRef element**: Enqueue parent with `element_id + 1`
 - **kRepeat element**: Increment `repeat_count` 
 - If reached `min_repeat_count`: Also enqueue with `element_id + 1` (exit repetition)
 - If not reached `max_repeat_count`: Enqueue for another iteration

## State Management and Control Flow

 
### Parser Initialization

 
```

```

 The parser constructor sets up initial states:

 
 - **Validate grammar**: Ensures the grammar has been optimized (required for FSM availability)
 - **Initialize state**: If no valid initial state provided, creates root state with:

 
 - `rule_id = grammar->GetRootRuleId()`
 - `sequence_id = kUnexpandedRuleStartSequenceId` (128000)
 - `element_id = 0`
 - `rule_start_pos = kNoPrevInputPos` (-1)
 - **Expand or add directly**: If `need_expand == false`, adds initial state to `scanable_state_history_[0]`. Otherwise, expands the state through Predict/Complete to populate position 0.
 
 Sources: [cpp/earley_parser.cc249-282](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L249-L282)

 
### Rollback and Reset

 The parser supports both incremental rollback and full reset:

 **PopLastStates(cnt)**: Removes the last `cnt` accepted characters:

 
 - Removes entries from `rule_id_to_completable_states_`
 - Removes entries from `is_completed_`
 - Removes entries from `scanable_state_history_`
 - Clears `stop_token_is_accepted_` flag
 
 **Reset()**: Returns parser to initial state:

 
 - Calls `PopLastStates` to clear all history
 - Calls `PushStateAndExpand` with fresh root state

### Queue Processing and Deduplication

 
```

```

 The `Enqueue` method prevents duplicate state processing:

 
 - Checks `tmp_states_visited_in_queue_.IsVisited(state)` before adding
 - Uses `RepeatDetector` which adapts between vector and hash set storage
 - Essential for performance with ambiguous grammars that generate many equivalent parse paths
 
 The `EnqueueWithoutProcessing` variant adds states directly to `tmp_states_to_be_added_` for scanable states that don't need Predict/Complete.

## Grammar Element Handling

 
### UTF-8 Character Class Matching

 
```

```

 Character class matching handles UTF-8 properly:

 **Continuation bytes** (`sub_element_id > 0`):

 
 - Verify byte is continuation (0x80-0xBF)
 - Accumulate 6 bits into `partial_codepoint`
 - When complete, check final codepoint against ranges
 - Early reject if intermediate codepoint can't possibly match
 
 **First byte**:

 
 - **ASCII** (0x00-0x7F): Direct comparison against character class ranges
 - **Multi-byte UTF-8**: 
 - Extract byte length (2-4 bytes) and initial bits
 - Compute possible codepoint range for this prefix
 - Continue only if some character class range could overlap
 
 **Negative character classes** (`is_negative`):

 
 - Accept if codepoint is NOT in any range
 - During intermediate bytes, always continue (can't determine until final byte)
 
 Sources: [cpp/earley_parser.cc593-726](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L593-L726)

 
### Byte String Matching

 Byte string matching is straightforward:

 
 - Compare `ch` against `sub_rule[state.sub_element_id]`
 - If match: increment `sub_element_id`
 - When `sub_element_id == sub_rule.size()`: 
 - Increment `element_id` and reset `sub_element_id = 0`
 - Enqueue state for Predict/Complete processing
 - Otherwise: Add to `tmp_states_to_be_added_` to continue matching
 
 Sources: [cpp/earley_parser.cc573-591](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L573-L591)

 
### FSM Traversal

 For rules compiled to FSMs:

 
```

```

 FSM matching:

 
 - Iterate edges from current FSM node (`state.element_id`)
 - Filter to character range edges that match `ch`
 - Create new state with `element_id = edge.target`
 - **Terminal states**: Enqueue for Predict/Complete (may reference rules or be end states)
 - **Scanable states**: Add directly to `tmp_states_to_be_added_` (pure character matching continues)
 
 Sources: [cpp/earley_parser.cc855-871](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L855-L871)

 
### Repetition Handling

 The `kRepeat` grammar expression type handles quantified patterns `{min, max}`:

 **During Predict**:

 
 - If `repeat_count < max`: Call `ExpandNextRuleRefElement` to predict the repeated rule
 - If `repeat_count >= min`: Also enqueue state with `element_id + 1` (exit repetition)
 
 **During Complete**:

 
 - Increment parent state's `repeat_count`
 - If `repeat_count >= min`: Enqueue parent with `element_id + 1` (can exit)
 - If `repeat_count < max`: Enqueue parent with same `element_id` (repeat again)
 
 This allows matching between `min` and `max` repetitions of the referenced rule.

## Integration with GrammarMatcher

 
```

```

 The `GrammarMatcher::Impl` class extends `EarleyParser` to provide token-level operations:

 **AcceptToken(token_id)**:

 
 - Check if token is stop token → call `AcceptStopToken()`
 - Decode token to UTF-8 bytes using `tokenizer_info_.GetDecodedVocab()`
 - Call `Advance(byte)` for each byte in sequence
 - If any byte rejected, call `PopLastStates` to rollback
 - Record token byte length in `token_length_history` for rollback support
 
 **FillNextTokenBitmask()**:

 
 - Get latest scanable states via `GetLatestScanableStates()`
 - For each state, lookup precomputed `AdaptiveTokenMask` from `compiled_grammar_`
 - For uncertain tokens in each mask: 
 - Push state with `PushOneStateToCheck`
 - Call `Advance` repeatedly to test token bytes
 - Use longest-common-prefix optimization across tokens
 - Call `PopLastStates` to restore state
 - Merge results: union accepted, intersection rejected
 - Write final bitmask with stop tokens if `IsCompleted()`
 
 **Rollback(num_tokens)**:

 
 - Uses `token_length_history` to track byte count per token
 - Calls `PopLastStates` with total byte count to rewind

## Performance Optimizations

 
### Right Recursion Optimization

 The parser detects right-recursive patterns (rule reference at end of sequence) and optimizes completion:

 Instead of creating a chain of parent pointers:

 
```
A → B at pos 0
B → C at pos 1  
C → A at pos 2  (right recursion)
```

 It directly adds ancestors to current layer:

 
```
A → B at pos 0
B → C at pos 1
C → A at pos 2 (points back to pos 0 ancestors directly)
```

 This is implemented in `ExpandNextRuleRefElement` and `ExpandNextRuleRefElementOnFSM` by checking if the rule reference is at the end and adding parent states to the current completion layer.

 Sources: [cpp/earley_parser.cc372-405](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L372-L405) [cpp/earley_parser.cc484-520](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L484-L520)

 
### Longest Common Prefix (LCP) Optimization

 During token bitmask generation, testing uncertain tokens can reuse work:

 Tokens `"abc"` and `"abd"` share prefix `"ab"`:

 
 - Advance through `'a'` and `'b'`
 - Test `'c'` for first token
 - Rollback only 1 position (not 2)
 - Test `'d'` for second token
 
 The implementation tracks `prev_matched_size` and `prev_token` to compute longest common prefix and minimize rollback operations.

 Sources: [cpp/grammar_matcher.cc688-755](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_matcher.cc#L688-L755)

 
### FSM State Optimization

 For FSM states that are pure scanable (not terminal, not end, no rule references):

 
 - Call `EnqueueWithoutProcessing` instead of `Enqueue`
 - Skips Predict/Complete operations
 - Directly adds to `tmp_states_to_be_added_`
 - Reduces queue processing overhead
 
 Sources: [cpp/earley_parser.cc862-869](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/earley_parser.cc#L862-L869)

 
### Nullable Rule Handling

 Rules that can match empty strings (`allow_empty_rule_ids`) receive special handling:

 
 - When predicting such a rule, immediately enqueue parent state with `element_id + 1`
 - Allows parser to consider both "match empty" and "continue matching" paths
 - Prevents unnecessary rule prediction overhead

### State Equality and Hashing

 Two hash/equality implementations optimize different use cases:

 **StateHashForCache / operator==**:

 
 - Ignores `rule_start_pos`, `repeat_count`, `partial_codepoint`
 - Used for adaptive token mask cache lookup
 - Multiple parsing states can share same mask
 
 **StateHashForParsing / StateEqualForParsing**:

 
 - Considers all fields including `rule_start_pos`
 - Used for deduplication during parsing
 - Ensures correct completion handling
