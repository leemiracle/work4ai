  This document describes the hardware-accelerated kernel implementations for applying token bitmasks to logits during constrained generation. These kernels are the performance-critical path in the token generation loop, where the bitmask computed by the grammar matcher is applied to LLM logits to enforce grammar constraints.

 For information about how bitmasks are generated from grammar states, see [Token Bitmask Generation](https://deepwiki.com/mlc-ai/xgrammar/8.3-token-bitmask-generation). For the overall runtime matching process, see [Runtime Matching Engine](https://deepwiki.com/mlc-ai/xgrammar/8-runtime-matching-engine).

 
---

 
## Overview

 XGrammar provides five backend implementations of the `apply_token_bitmask_inplace` operation, each optimized for different hardware platforms:

 
| Backend | Target Hardware | Implementation Method | Primary Use Case |
|---|---|---|---|
| CPU | x86/ARM CPUs | Native C++ | CPU-only inference |
| Triton | NVIDIA/AMD GPUs | Triton JIT compilation | Default GPU backend |
| CUDA | NVIDIA GPUs | Native CUDA with JIT | C++-based inference engines |
| Torch Compile | CPU/GPU/TPU/ROCm | PyTorch compiler | Cross-platform fallback |
| Torch Native | Kunlun, etc. | Pure PyTorch ops | Extended hardware support |

 The operation modifies logits in-place by setting masked token logits to `-inf`, preventing the LLM from sampling tokens that would violate the grammar.

 **Sources:** [python/xgrammar/kernels/__init__.py1-9](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/kernels/__init__.py#L1-L9) [python/xgrammar/matcher.py58-189](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/matcher.py#L58-L189)

## Bitmask Format and Operation

 The token bitmask is a compact bit-packed representation stored as an `int32` tensor with shape `(batch_size, ceil(vocab_size / 32))`. Each bit represents whether a token is allowed (1) or masked (0) at the current grammar state.

 
```

```

 **Bit Packing Example:**

 
 - Token 0 → bit 0 of `bitmask[batch_id, 0]`
 - Token 35 → bit 3 of `bitmask[batch_id, 1]` (35 = 32 + 3)
 - Token 127 → bit 31 of `bitmask[batch_id, 3]` (127 = 96 + 31)
 
 **Rationale:** The choice of `int32` over `uint32` is for compatibility with older PyTorch versions that lacked `uint32` support.

 **Sources:** [python/xgrammar/matcher.py15-21](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/matcher.py#L15-L21) [python/xgrammar/matcher.py66-82](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/matcher.py#L66-L82)

## Dispatch Logic

 The `apply_token_bitmask_inplace` function automatically selects the appropriate backend based on the device type and user preference:

 
```

```

 **Key Dispatch Rules:**

 
 - If `backend="auto"` (default): automatically select based on `logits.device.type`
 - CPU tensors → CPU backend
 - CUDA tensors → Triton backend (optimized for NVIDIA/AMD GPUs)
 - Other devices → Torch Compile backend (for TPU, ROCm, etc.)
 - Manual selection overrides auto-detection
 
 **Device Compatibility Check:** The function enforces that `logits.device == bitmask.device` before dispatching.

## CPU Backend

 The CPU backend is implemented in native C++ and provides a straightforward sequential implementation. It is accessed through the Python binding layer.

 **Implementation Characteristics:**

 
 - Direct bit manipulation using bitwise operations
 - No explicit parallelization (relies on compiler auto-vectorization)
 - Minimal memory overhead
 - Suitable for inference engines running on CPU-only systems
 
 **Interface:**

 
```

```

 **Parameters:**

 
 - `logits`: Tensor on CPU with shape `(batch_size, vocab_size)` or larger with padding
 - `bitmask`: int32 tensor on CPU with shape `(batch_size, ceil(vocab_size/32))`
 - `vocab_size`: Optional actual vocabulary size (for handling padding)
 - `indices`: Optional list of batch indices to apply mask to

## Triton Backend (Default GPU)

 The Triton backend provides a high-performance GPU implementation using Triton's Python DSL for kernel authoring. This is the default backend for CUDA tensors.

 
```

```

 **Kernel Implementation:** The Triton kernel at [python/xgrammar/kernels/apply_token_bitmask_inplace_triton.py12-78](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/kernels/apply_token_bitmask_inplace_triton.py#L12-L78) uses a persistent thread block strategy:

 
 - **Grid Configuration:** Launches `NUM_SMS` thread blocks (one per streaming multiprocessor)
 - **Work Distribution:** Each block processes multiple row-block pairs via a loop: `for work_id in tl.range(pid, num_rows * num_blocks, NUM_SMS)`
 - **Bit Unpacking:** Loads packed `int32` bitmask values and unpacks to boolean array: 
```

```
 - **Conditional Store:** Writes `-inf` only to masked positions: `tl.store(..., -float("inf"), vocab_mask & bitmask)`
 
 **AMD GPU Support:** The kernel detects AMD GPUs via `torch.cuda.get_device_properties(0).gcnArchName` and adjusts `WARP_SIZE` to 64 for non-Navi architectures (vs. 32 for NVIDIA).

 **Performance Tuning Parameters:**

 
 - `BLOCK_SIZE = 4096`: Processes 4096 tokens per block
 - `num_warps = BLOCK_SIZE // WARP_SIZE // (16 // logits.element_size())`: Configures warp count
 - `num_stages = 3`: Pipeline depth for load/compute overlap
 
 **Sources:** [python/xgrammar/kernels/apply_token_bitmask_inplace_triton.py12-127](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/kernels/apply_token_bitmask_inplace_triton.py#L12-L127) [python/xgrammar/matcher.py168-171](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/matcher.py#L168-L171)

## CUDA Native Backend

 The CUDA native backend provides a JIT-compiled CUDA kernel for integration with C++-based inference engines. It uses PyTorch's `cpp_extension.load_inline` to compile CUDA source at runtime.

 
```

```

 **Initialization Sequence:**

 
 - **Toolchain Verification** [python/xgrammar/kernels/apply_token_bitmask_inplace_cuda.py24-58](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/kernels/apply_token_bitmask_inplace_cuda.py#L24-L58): Searches for `nvcc` compiler in:

 
 - `which nvcc` output
 - `$CUDA_HOME/bin/nvcc`
 - `C:/Program Files/NVIDIA GPU Computing Toolkit/CUDA/v*.*` (Windows)
 - `/usr/local/cuda/bin/nvcc` (Linux fallback)
 - **Flag Cleanup** [python/xgrammar/kernels/apply_token_bitmask_inplace_cuda.py60-69](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/kernels/apply_token_bitmask_inplace_cuda.py#L60-L69): Removes incompatible NVCC flags:

 
 - `-D__CUDA_NO_HALF_OPERATORS__`
 - `-D__CUDA_NO_HALF_CONVERSIONS__`
 - `-D__CUDA_NO_BFLOAT16_CONVERSIONS__`
 - `-D__CUDA_NO_HALF2_OPERATORS__`
 - **JIT Compilation** [python/xgrammar/kernels/apply_token_bitmask_inplace_cuda.py72-91](https://github.com/mlc-ai/xgrammar/blob/c30554f7/python/xgrammar/kernels/apply_token_bitmask_inplace_cuda.py#L72-L91): Compiles with flags:

 
 - C++ flags: `["-O3", "-Wno-switch-bool"]` (Linux/Mac)
 - CUDA flags: `["-O3", "-std=c++17", "--threads", "4", "-use_fast_math"]`
 
 **Torch Compile Support:** Registers a fake kernel implementation when `torch.library.register_fake` is available, enabling `torch.compile` with `fullgraph=True`.

## Torch Compile Backend

 The Torch Compile backend uses PyTorch's compiler infrastructure to generate optimized kernels for diverse hardware platforms (CPU, GPU, TPU, ROCm).

 **Implementation Strategy:**

 
 - Writes bitmask application using pure PyTorch operations
 - Relies on `torch.compile` to generate optimized code for the target device
 - Supports hardware without specialized kernel implementations
 
 **Advantages:**

 
 - Cross-platform portability (CPU, CUDA, TPU, ROCm, etc.)
 - Automatic optimization via PyTorch's compiler
 - No manual kernel authoring required

## Torch Native Backend

 The Torch Native backend provides a pure PyTorch implementation without compilation, offering broader hardware support at the cost of performance.

 **Use Cases:**

 
 - Hardware platforms not well-supported by other backends (e.g., Kunlun)
 - Development/debugging where kernel inspection is needed
 - Environments where JIT compilation is unavailable
 
 **Performance Note:** This backend may have worse performance than Torch Compile due to lack of optimization. It is primarily provided for compatibility.

## Performance Characteristics

 
### Backend Comparison

 
| Backend | Latency | Throughput | Memory | Portability |
|---|---|---|---|---|
| Triton | Very Low | Very High | Low | NVIDIA/AMD GPU |
| CUDA | Very Low | Very High | Low | NVIDIA GPU |
| CPU | Moderate | Moderate | Very Low | Universal |
| Torch Compile | Low | High | Low | Multi-platform |
| Torch Native | High | Low | Moderate | Universal |

 
### Optimization Strategies

 
 - **Device Co-location:** Keep logits and bitmask on the same device to avoid CPU↔GPU transfers

 
```

```
 - **Pinned Memory:** For CPU↔GPU transfers, use pinned memory for faster data movement (handled automatically by `allocate_token_bitmask`)
 - **Batch Processing:** Use `indices` parameter to skip masking unstructured requests in mixed batches, reducing unnecessary computation
 - **Persistent Thread Blocks:** Triton kernel uses persistent threads (`tl.range` loop) to amortize launch overhead across multiple work items
