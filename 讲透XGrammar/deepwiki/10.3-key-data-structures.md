  This page documents the core data structures used throughout xgrammar's implementation. These structures form the foundation for representing grammars, finite state machines, parser states, and token masks. Understanding these data structures is essential for comprehending the system's internals and contributing to the codebase.

 For information about how these structures are used in the runtime matching process, see [Grammar Matching](https://deepwiki.com/mlc-ai/xgrammar/2.3-grammar-matching). For details on how grammars are compiled and optimized, see [Grammar Compilation](https://deepwiki.com/mlc-ai/xgrammar/2.2-grammar-compilation).

## Overview

 The xgrammar system is built around several categories of data structures:

 
 - **FSM Structures**: Represent finite state machines for efficient pattern matching
 - **Grammar Structures**: Store the abstract syntax tree and rules of grammars
 - **Parser State Structures**: Track the Earley parser's progress during matching
 - **Token Mask Structures**: Efficiently store and manipulate token acceptance information
 - **Support Structures**: Provide memory-efficient containers and utilities
 
 These structures are designed with careful attention to memory efficiency, cache locality, and computational performance. Many use techniques like CSR (Compressed Sparse Row) format, compact storage, and bit-packing to minimize memory footprint while maintaining fast access patterns.

## Memory Management Patterns

 
### Ownership Models

 Different data structures use different ownership and sharing patterns:

 
| Data Structure | Ownership | Sharing | Lifetime |
|---|---|---|---|
| Grammar | Shared (PImpl) | Reference counted | Persistent |
| CompiledGrammar | Shared (PImpl) | Reference counted | Cached |
| GrammarMatcher | Shared (PImpl) | Reference counted | Per-request |
| ParserState | Value | Copied | Transient |
| FSMEdge | Value | Copied | Embedded in FSM |
| DynamicBitset | Value/External | Flexible | Context-dependent |
| Compact2DArray | Value | Copied | Embedded |

 **PImpl Pattern**: Classes like `Grammar`, `CompiledGrammar`, and `GrammarMatcher` use the PImpl (Pointer to Implementation) idiom with `std::shared_ptr<Impl>` for:

 
 - Reference-counted memory management
 - Efficient copying (shallow copy of pointer)
 - ABI stability
 - Python integration
 
 **Value Semantics**: Small structures like `ParserState` and `FSMEdge` use value semantics for:

 
 - Cache locality
 - No allocation overhead
 - Simple semantics

## Size Optimization Techniques

 
### Bit Packing

 Several structures use bit-level packing to reduce memory:

 
 - **FSMEdge**: 8 bytes total (2×int16 + 1×int32)
 - **ParserState**: 28 bytes (7×int32)
 - **DynamicBitset**: 32 tokens per uint32 (3.2% overhead)
 
 
### CSR Format

 The CSR (Compressed Sparse Row) format is used extensively:

 
 - **Grammar expressions**: Eliminates per-expression object overhead
 - **FSM edges**: Eliminates per-state vector overhead
 - **Parser state history**: Eliminates per-position vector overhead
 
 **Memory Savings**: For N elements distributed across M containers:

 
 - Traditional: `M * sizeof(vector) + N * sizeof(element)`
 - CSR: `sizeof(vector) + (M+1) * sizeof(int) + N * sizeof(element)`
 - Savings: `(M-1) * sizeof(vector) - M * sizeof(int)` ≈ 20-32 bytes per container
 
 
### Adaptive Storage

 `AdaptiveTokenMask` adapts storage based on data characteristics:

 
 - Sparse accepted: Store accepted indices only
 - Sparse rejected: Store rejected indices only
 - Dense: Use bitset (1 bit per token)
 
 **Example**: For 128K vocabulary with 100 accepted tokens:

 
 - Bitset: 4K bytes (128K / 8)
 - Index list: 400 bytes (100 * 4)
 - Savings: 90%
