## Purpose and Scope

 This document explains the internal representation of grammars in XGrammar's C++ core, focusing on the `Grammar::Impl` structure, `GrammarExpr` types, CSR-like storage format, and `Rule` structure. This is the foundation that all grammar operations build upon.

 For information about how grammars are constructed from EBNF strings, see [EBNF Parser and Grammar Representation](https://deepwiki.com/mlc-ai/xgrammar/5.1-converter-architecture). For details on grammar optimization transformations, see [Grammar Optimization Passes](https://deepwiki.com/mlc-ai/xgrammar/5.3-object-and-array-schema-processing).

## Grammar and Grammar::Impl Overview

 The `Grammar` class uses the PIMPL (Pointer to Implementation) pattern to separate the public interface from the internal representation. The actual data is stored in `Grammar::Impl`, which is held via `shared_ptr` to enable efficient copying and sharing of grammar objects.

 
```

```

 **Core Components:**

 
 - **`rules_`**: Vector of `Rule` objects, each representing a named production rule
 - **`grammar_expr_data_`**: Flat array storing all expression data in CSR format
 - **`grammar_expr_indptr_`**: Index pointers into `grammar_expr_data_` for random access
 - **`root_rule_id_`**: Integer identifying which rule is the grammar entry point
 
 **Optimization Artifacts** (populated by [Grammar Optimization Passes](https://deepwiki.com/mlc-ai/xgrammar/7.2-grammar-optimization-passes)):

 
 - **`complete_fsm`**: A unified finite state machine built from all rules (see [FSM Implementation](https://deepwiki.com/mlc-ai/xgrammar/11.2-fsm-implementation))
 - **`per_rule_fsms`**: Optional per-rule FSMs for specialized matching scenarios
 - **`allow_empty_rule_ids`**: Set of rule IDs that can match the empty string
 
 **PIMPL Pattern Benefits:**

 
 - Multiple `Grammar` objects can share the same `Grammar::Impl` via `shared_ptr`
 - Copying a `Grammar` only increments reference count (O(1) operation)
 - Internal representation can change without breaking public API
 - Thread-safe sharing of immutable grammar data

## GrammarExpr Types and Encoding

 Each `GrammarExpr` represents a single grammar construct. The `GrammarExpr` structure is a lightweight view into the CSR storage, containing a type tag and a pointer/length pair for associated data.

### Expression Types and Data Layouts

 
| GrammarExprType | Data Format | Description |
|---|---|---|
| kEmptyStr | Empty (0 ints) | Matches empty string ε |
| kByteString | [byte0, byte1, ..., byteN] | Literal string as byte sequence (0-255) |
| kCharacterClass | [is_neg, lo0, hi0, lo1, hi1, ...] | Character ranges; is_neg = 1 for negation |
| kCharacterClassStar | [is_neg, lo0, hi0, lo1, hi1, ...] | Star quantifier [...]*  optimized form |
| kRuleRef | [rule_id] | Reference to another rule by ID |
| kSequence | [expr_id0, expr_id1, ..., expr_idN] | Concatenation of N expressions |
| kChoices | [expr_id0, expr_id1, ..., expr_idN] | Alternation (OR) of N expressions |
| kTagDispatch | [tag_expr0, rule0, tag_expr1, rule1, ..., stop_eos, stop_str_expr, loop, exclude_expr] | Dynamic grammar dispatch by tag |
| kRepeat | [rule_id, min_count, max_count] | Bounded repetition {min, max} |

 **Character Class Encoding:**

 
 - First element: `0` = positive class, `1` = negated class
 - Remaining elements: pairs of `[lower_bound, upper_bound]` (inclusive)
 - Example: `[a-zA-Z]` → `[0, 97, 122, 65, 90]`
 - Example: `[^0-9]` → `[1, 48, 57]`
 
 **Sequence and Choices:**

 
 - Store expression IDs (not direct references)
 - IDs are indices into the `grammar_expr_indptr_` array
 - Allow recursive and mutually recursive structures

## CSR-Like Storage Format

 The grammar uses a Compressed Sparse Row (CSR) inspired storage format to enable:

 
 - **Flat memory layout**: All expressions stored contiguously for cache efficiency
 - **Random access**: O(1) lookup of any expression by ID
 - **Immutability**: Once built, the structure is read-only and thread-safe
 
 
```

```

 
### Storage Algorithm

 **Building phase** (via `GrammarBuilder::AddGrammarExpr`):

 
```
1. Append current data size to grammar_expr_indptr_
2. Append type (int32_t) to grammar_expr_data_
3. Append data_len (int32_t) to grammar_expr_data_
4. Append all data elements to grammar_expr_data_
5. Return new expression ID = indptr.size() - 1
```

 **Access phase** (via `Grammar::Impl::GetGrammarExpr`):

 
```
Given expr_id:
1. offset = grammar_expr_indptr_[expr_id]
2. type = grammar_expr_data_[offset]
3. data_len = grammar_expr_data_[offset + 1]
4. data = &grammar_expr_data_[offset + 2]
5. Return GrammarExpr{type, data, data_len}
```

 **Memory Layout Example:**

 
```
grammar_expr_indptr_:  [0,          3,             8,        10]
                        ^           ^              ^         ^
                        expr 0      expr 1         expr 2    expr 3

grammar_expr_data_:    [kByteString, 1, 97,    kSequence, 3, 0, 1, 2,    kRuleRef, 1, 5,   ...]
                        |___________|  |        |____________|  |           |_________|  |
                        type   len     'a'      type    len     expr refs   type   len  rule 5
```

## Rule Structure

 Rules are named production rules that form the high-level structure of the grammar. Each rule has a unique ID (its index in the `rules_` vector) and references a body expression and optional lookahead assertion.

 
```

```

 
### Rule Fields

 
| Field | Type | Purpose |
|---|---|---|
| name | std::string | Human-readable identifier for debugging and references |
| body_expr_id | int32_t | ID of the expression that defines the rule body |
| lookahead_assertion_id | int32_t | ID of lookahead expression, or -1 if none |
| is_exact_lookahead | bool | If true, lookahead must match exactly; if false, it's a prefix match |

 
### Rule References and Recursion

 Rules can reference each other through `kRuleRef` expressions, enabling:

 
 - **Direct recursion**: `expr ::= expr "+" term`
 - **Mutual recursion**: `rule_a ::= "a" rule_b` and `rule_b ::= "b" rule_a`
 - **Deep nesting**: Complex grammar structures with multiple levels
 
 Example recursive rule encoding:

 
```
Rule ID 0: "expr"
  body_expr_id = 5  (kChoices expression)
  
Expr ID 5: kChoices
  data = [6, 7]  (two alternatives)
  
Expr ID 6: kSequence
  data = [8, 9]  (expr "+" term)
  
Expr ID 8: kRuleRef
  data = [0]  (references rule 0 - direct recursion!)
```

## Memory Layout and Access Patterns

 
### Memory Efficiency Characteristics

 
 - **Contiguous allocation**: All expressions in a single vector for spatial locality
 - **Indirect addressing**: Expression IDs are small integers (4 bytes) rather than pointers (8 bytes)
 - **Cache-friendly**: Sequential access patterns for common operations like rule traversal
 - **Immutable sharing**: Multiple `Grammar` objects can share the same `Impl` via `shared_ptr`
 
 
### Access Pattern Example

 Traversing a sequence expression `"a" "b" rule_c`:

 
```
1. Start with expr_id = 10 (kSequence)
2. GetGrammarExpr(10) → type=kSequence, data=[11, 12, 13], len=3
3. For each child:
   - GetGrammarExpr(11) → type=kByteString, data=[97], len=1 ('a')
   - GetGrammarExpr(12) → type=kByteString, data=[98], len=1 ('b')
   - GetGrammarExpr(13) → type=kRuleRef, data=[2], len=1 (rule_c)
4. GetRule(2) → Rule{name="rule_c", body_expr_id=14, ...}
```

 **Memory access:**

 
 - 4 lookups into `grammar_expr_indptr_` (4 cache lines at most)
 - 1 lookup into `rules_` (1 cache line)
 - All data reads from contiguous `grammar_expr_data_` array

## GrammarBuilder: Constructing Grammars

 The `GrammarBuilder` class provides a mutable interface for constructing `Grammar` objects. It maintains the CSR storage invariants while allowing incremental construction. The builder is used internally by all grammar construction methods (EBNF parser, JSON schema converter, etc.).

 **Construction Flow**

 
```

```

 
### Builder Construction Phases

 **Phase 1: Forward declare rules** (for mutual recursion support)

 
```
builder.AddEmptyRule("expr");    // Returns rule_id 0, body_expr_id = -1
builder.AddEmptyRule("term");    // Returns rule_id 1, body_expr_id = -1
builder.AddEmptyRule("factor");  // Returns rule_id 2, body_expr_id = -1
```

 **Phase 2: Build expression tree bottom-up**

 
```
int32_t digit_expr = builder.AddCharacterClass({{48, 57}});  // [0-9]
int32_t plus_expr = builder.AddByteString("+");
int32_t term_ref = builder.AddRuleRef(1);  // Reference to "term" rule
int32_t add_expr = builder.AddSequence({term_ref, plus_expr, term_ref});
int32_t mult_expr = ...;  // Similar for multiplication
int32_t expr_body = builder.AddChoices({add_expr, mult_expr});
```

 **Phase 3: Populate rule bodies**

 
```
builder.UpdateRuleBody(0, expr_body);  // Fill in "expr" rule
builder.UpdateRuleBody(1, term_body);  // Fill in "term" rule
builder.UpdateRuleBody(2, factor_body);  // Fill in "factor" rule
```

 **Phase 4: Finalize and set root**

 
```
Grammar grammar = builder.Get("expr");  // Set "expr" as root rule
// or
Grammar grammar = builder.Get(0);  // Set rule 0 as root rule
```

 **Sources:** [cpp/grammar_builder.h24-344](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_builder.h#L24-L344)

 
### GrammarBuilder Internal State

 
| Component | Type | Purpose |
|---|---|---|
| grammar_ | shared_ptr<Grammar::Impl> | Mutable pointer to the grammar being built |
| rule_name_to_id_ | unordered_map<string, int32_t> | Maps rule names to rule IDs for lookup |

 The `rule_name_to_id_` map enables:

 
 - O(1) lookup of rule IDs by name during construction
 - Name uniqueness validation when adding new rules
 - Forward reference resolution (rule used before body is defined)
 - `GetNewRuleName()` to generate unique names with numeric suffixes
 
 When `Get()` is called, the builder returns a `Grammar` object that shares the `Grammar::Impl` pointer. The builder itself can be discarded, and the `rule_name_to_id_` map is no longer needed since rule names are stored in each `Rule` object.

 **Sources:** [cpp/grammar_builder.h30-343](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_builder.h#L30-L343) [cpp/grammar_parser.cc518-536](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_parser.cc#L518-L536)

 
### Expression Builder Methods

 The `GrammarBuilder` provides specialized methods for each `GrammarExpr` type:

 
| Method | Returns | Description |
|---|---|---|
| AddByteString(string) | int32_t | Creates literal byte string expression |
| AddByteString(vector<int32_t>) | int32_t | Creates byte string from int array |
| AddCharacterClass(elements, neg) | int32_t | Creates character class [...] or [^...] |
| AddCharacterClassStar(elements, neg) | int32_t | Creates optimized [...]* expression |
| AddEmptyStr() | int32_t | Creates empty string "" expression |
| AddRuleRef(rule_id) | int32_t | Creates reference to another rule |
| AddSequence(expr_ids) | int32_t | Creates concatenation of expressions |
| AddChoices(expr_ids) | int32_t | Creates alternation (OR) of expressions |
| AddTagDispatch(tag_dispatch) | int32_t | Creates tag dispatching expression |
| AddRepeat(rule_id, min, max) | int32_t | Creates bounded repetition {min,max} |

 All methods return the `expr_id` of the newly created expression, which can be used in subsequent calls to build up the expression tree.

 **Sources:** [cpp/grammar_builder.h69-220](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_builder.h#L69-L220)

 
### Rule Builder Methods

 
| Method | Returns | Description |
|---|---|---|
| AddRule(name, body_id) | int32_t | Adds complete rule with body |
| AddEmptyRule(name) | int32_t | Adds rule without body (to be filled later) |
| AddRuleWithHint(hint, body_id) | int32_t | Adds rule with auto-generated unique name |
| UpdateRuleBody(rule_id, body_id) | void | Sets body for rule created with AddEmptyRule |
| UpdateLookaheadAssertion(rule_id, la_id) | void | Adds lookahead assertion to rule |

| GetNewRuleName(hint) | string | Generates unique name (adds _1, _2, etc.) |

 The `AddEmptyRule()` / `UpdateRuleBody()` pattern is essential for handling recursive grammars where a rule needs to reference itself in its body definition.

## Implementation Notes

 
### Type Safety

 
 - All expression IDs and rule IDs are validated at access time with `XGRAMMAR_CHECK`
 - Out-of-bounds access triggers a fatal error with debugging information
 - The CSR format makes it impossible to have dangling pointers within the grammar structure
 
 
### Thread Safety

 
 - `Grammar::Impl` is immutable after construction
 - Multiple threads can safely read the same `Grammar` object concurrently
 - `GrammarBuilder` is not thread-safe (intended for single-threaded construction)
 
 
### Serialization

 The flat CSR layout makes serialization straightforward:

 
 - Serialize `grammar_expr_data_` and `grammar_expr_indptr_` as raw int32 arrays
 - Serialize `rules_` as structured data (name + 2-3 int fields per rule)
 - No pointer fixup required on deserialization
