  This page documents the batch processing capabilities in XGrammar, specifically the `BatchGrammarMatcher` class and its methods for parallel processing of multiple grammar matchers. Batch processing enables efficient handling of multiple concurrent grammar-constrained generation requests by utilizing multi-threading.

 For information about individual matcher operations, see [Grammar Matching and Validation](https://deepwiki.com/mlc-ai/xgrammar/2.3-grammar-matching).

 
## Overview

 XGrammar provides batch processing capabilities to improve throughput when handling multiple grammar matchers simultaneously. This is particularly useful in scenarios where:

 
 - Multiple LLM requests with structured output constraints are processed in parallel
 - A server handles concurrent requests requiring grammar-guided generation
 - Different requests use different grammars or are at different stages of generation
 
 The `BatchGrammarMatcher` class coordinates parallel execution of matcher operations across multiple `GrammarMatcher` instances using a configurable thread pool.

## BatchGrammarMatcher Class

 
### Initialization

 The `BatchGrammarMatcher` class is instantiated with a threading configuration:

 
| Parameter | Type | Description |
|---|---|---|
| max_threads | Union[int, Literal["auto"]] | Maximum threads for parallel processing. Default: "auto" |

 When `max_threads` is set to:

 
 - **Integer (≥ 1)**: Uses exactly that many threads (capped at hardware concurrency)
 - **"auto"**: Uses `std::thread::hardware_concurrency() / 2`
 - **1**: Disables multi-threading (sequential processing)

## Batch Token Mask Generation

 
### batch_fill_next_token_bitmask Method

 The primary use case for batch processing is generating token bitmasks for multiple matchers in parallel:

 
| Parameter | Type | Description |
|---|---|---|
| matchers | List[GrammarMatcher] | List of matcher instances to process |
| bitmask | ArrayLike | 2D int32 tensor with shape (batch_size, bitmask_size) |
| indices | Optional[List[int]] | Optional mapping of matchers to bitmask rows |
| debug_print | bool | Whether to print debug information |

 **Bitmask Shape**: The bitmask must be 2-dimensional with shape `(batch_size, ceil(vocab_size/32))`. The batch_size can be larger than the number of matchers to allow padding.

 **Index Mapping**: When `indices` is provided, `matchers[i]` writes to `bitmask[indices[i]]`. When `indices` is `None`, `matchers[i]` writes to `bitmask[i]`.

## Batch Token and String Acceptance

 
### batch_accept_token Method

 Static method for accepting tokens across multiple matchers:

 
| Parameter | Type | Description |
|---|---|---|
| matchers | List[GrammarMatcher] | List of matcher instances |
| tokens | List[int] | List of token IDs (must match matchers length) |
| debug_print | bool | Whether to print debug information |

 **Returns**: `List[bool]` indicating whether each token was accepted by its corresponding matcher.

 **Execution**: This method always executes sequentially (no parallelism) because accepting tokens modifies matcher state in a way that is typically order-dependent.

### Thread Count Selection

 **Thread Count Decision Logic**: The system validates and caps thread counts to prevent over-subscription of CPU cores.

### Performance Characteristics

 
| Scenario | Recommended max_threads | Rationale |
|---|---|---|
| Small batch (< 4) | 1 (sequential) | Thread overhead exceeds benefit |
| Medium batch (4-16) | "auto" or 2-4 | Balance parallelism and overhead |
| Large batch (> 16) | "auto" or 4-8 | Maximize throughput |
| CPU-limited | hardware_concurrency / 2 | Avoid oversubscription |
| I/O-bound workload | hardware_concurrency | Can utilize full CPU |

 **Threading Overhead**: Each thread incurs context-switching overhead. For small batches, sequential processing may be faster.

 **Thread Safety**: The `GrammarMatcher` instances are accessed independently in parallel, so no locking is required as long as each matcher is only accessed by one thread at a time.

## Performance Considerations

 
### When to Use Batch Processing

 **Use batch processing when**:

 
 - Processing ≥ 4 matchers simultaneously
 - Each matcher operation is relatively expensive (complex grammars)
 - CPU cores are available for parallel work
 - Matchers are at different states (no shared work)
 
 **Avoid batch processing when**:

 
 - Batch size < 4 (thread overhead dominates)
 - Single-threaded environment
 - Matchers share significant computation (better to optimize grammar)
 
 
### Overhead Analysis

 
```

```

 **Overhead Impact**: Parallel execution adds overhead O (thread creation, synchronization). Beneficial when `O < T * (N - N/P)` where N is batch size and P is thread count.
