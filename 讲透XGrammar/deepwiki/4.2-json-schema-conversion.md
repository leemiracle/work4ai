## Overview

 JSON Schema is a widely-used specification for describing JSON data structures. XGrammar converts JSON Schema definitions into EBNF grammars that can constrain LLM token generation to produce valid JSON matching the schema. This enables:

 
 - **Type-safe generation**: Ensure LLM outputs conform to expected data structures
 - **Pydantic integration**: Directly use Python Pydantic models for schema definition
 - **Complex constraints**: Support for numeric ranges, string patterns, array/object constraints
 - **Flexible formatting**: Control JSON output formatting (compact, indented, flexible whitespace)
 
 The conversion process transforms a JSON Schema (as a string or Python dict) into an EBNF grammar that the GrammarMatcher can use during token generation.

## Conversion Process

 
```

```

 **Conversion Flow:**

 
 - **Parsing**: `SchemaParser` parses the JSON schema into an intermediate representation (`SchemaSpec`)
 - **Validation**: Parser validates schema structure and checks for unsatisfiable constraints
 - **Caching**: `SchemaParser` uses `ComputeCacheKey()` to deduplicate identical schema fragments
 - **Generation**: `JSONSchemaConverter` converts each `SchemaSpec` variant to EBNF rules
 - **Formatting**: `IndentManager` applies whitespace and separator formatting

## Supported Features

 
### Basic Types

 
| JSON Schema Type | EBNF Pattern | Constraints Supported |
|---|---|---|
| integer | ("0" \| "-"? [1-9] [0-9]*) | minimum, maximum, exclusiveMinimum, exclusiveMaximum |
| number | "-"? ("0" \| [1-9] [0-9]*) ("." [0-9]+)? ([eE] [+-]? [0-9]+)? | minimum, maximum, exclusiveMinimum, exclusiveMaximum |
| string | "\"" [^"\\]* "\"" | pattern, format, minLength, maxLength |
| boolean | "true" \| "false" | None |
| null | "null" | None |

### String Formats

 XGrammar supports string format validation through regex conversion:

 
 - **email**: RFC 5322-compliant email pattern
 - **date**: ISO 8601 date (YYYY-MM-DD)
 - **time**: ISO 8601 time with timezone
 - **date-time**: ISO 8601 datetime
 - **uri**, **uri-reference**: URI patterns
 - **uuid**: UUID format
 - **duration**: ISO 8601 duration
 
 Format patterns are converted to regex and then to EBNF. See [String Formats and Numeric Ranges](https://deepwiki.com/mlc-ai/xgrammar/5.5-string-formats-and-numeric-ranges) for implementation details.

### Objects

 Object schemas support:

 
 - `properties`: Named properties with schemas
 - `required`: Array of required property names
 - `additionalProperties`: Schema for unspecified properties (boolean or schema)
 - `patternProperties`: Pattern-matched property schemas
 - `propertyNames`: Schema constraining all property names
 - `minProperties`, `maxProperties`: Property count constraints
 
 The converter generates complex EBNF that handles:

 
 - Required vs optional properties
 - Property ordering permutations
 - Additional property validation
 - Property count constraints

### Composition Keywords

 
| Keyword | Meaning | EBNF Strategy |
|---|---|---|
| anyOf | Union (one or more schemas) | OR-separated alternatives |
| oneOf | Exclusive union | Same as anyOf (enforcement at schema level) |
| allOf | Intersection (all schemas) | Merged constraints |
| const | Single literal value | Exact string match |
| enum | Set of allowed values | OR-separated literal matches |

### References ($ref)

 XGrammar supports JSON Schema references including:

 
 - Simple references: `{"$ref": "#/$defs/MyType"}`
 - Nested references: References within referenced schemas
 - Circular references: Self-referential and mutually-referential schemas
 - Root reference: `{"$ref": "#"}` refers to root schema
 
 The converter uses placeholder rules and URI-to-rule-name mapping to handle circular dependencies.

## Configuration Options

 
### Strict Mode

 When `strict_mode=True` (default):

 
 - `additionalProperties` defaults to `false` for objects
 - `items` defaults to `false` (no additional items) for arrays
 - Prevents LLM from generating unexpected fields
 
 When `strict_mode=False`:

 
 - `additionalProperties` defaults to `true` (allows any additional properties)
 - `items` defaults to `true` (allows additional items of any type)
 - More flexible but less constrained generation

## Implementation Notes

 
### Two-Stage Architecture

 The converter uses a two-stage pipeline for maintainability and extensibility:

 
 - **Stage 1 - SchemaParser**: Validates and normalizes JSON Schema → `SchemaSpec` IR

 
 - Handles JSON Schema keywords and validation
 - Resolves references and checks for circular dependencies
 - Computes cache keys for deduplication
 - Type-safe intermediate representation
 - **Stage 2 - JSONSchemaConverter**: Generates EBNF from `SchemaSpec`

 
 - Traverses SchemaSpec tree
 - Generates EBNF rules with proper naming
 - Handles formatting via IndentManager
 - Extensible for different output formats (JSON, XML variants)
 
 This separation allows supporting multiple output formats (e.g., `QwenXMLToolCallingToEBNF`, `MiniMaxXMLToolCallingToEBNF`) by subclassing `JSONSchemaConverter` without modifying the parser.

 **Sources:** [cpp/json_schema_converter.cc132-950](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L132-L950) [cpp/json_schema_converter.cc1091-1323](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/json_schema_converter.cc#L1091-L1323)

 
### Caching and Deduplication

 The converter implements multi-level caching to optimize grammar size:

 
 - **Schema-level cache**: Identical schemas (by cache key) generate one EBNF rule
 - **String spec cache**: Reuses string patterns with same constraints
 - **Basic rules**: Pre-generated `basic_integer`, `basic_string`, etc. are shared
 
 Cache keys are computed by `SchemaParser::ComputeCacheKey()` which:

 
 - Serializes schema to canonical JSON (sorted keys)
 - Excludes non-semantic fields (title, description, etc.)
 - Enables structural sharing across schema fragments
