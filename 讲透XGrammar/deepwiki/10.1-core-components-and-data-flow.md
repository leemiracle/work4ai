## System Overview

 XGrammar processes grammar specifications through four primary stages:

 
 - **Input Parsing**: Convert various input formats (EBNF, JSON Schema, regex, structural tags) into a normalized `Grammar` object
 - **Compilation**: Transform and optimize the grammar, build finite state machines (FSMs), and precompute token masks to create a `CompiledGrammar`
 - **Runtime Matching**: Use `GrammarMatcher` with the Earley parser to validate token sequences and generate acceptance masks
 - **Integration**: Expose functionality to Python and apply masks to LLM logits

## Core Components

 
### Grammar Representation Layer

 
#### Grammar::Impl

 The `Grammar::Impl` class stores the abstract syntax tree (AST) of a BNF grammar using compressed sparse row (CSR) format for memory efficiency.

 **Key Members**:

 
 - `rules_`: Vector of `Rule` objects, each containing a name, body expression ID, and optional lookahead assertion
 - `grammar_expr_data_`: Flat vector storing all grammar expression data consecutively
 - `grammar_expr_indptr_`: Index pointers into `grammar_expr_data_` for each expression
 - `root_rule_id_`: ID of the grammar's root rule
 - `per_rule_fsms`: Optional FSMs for each rule (populated during compilation)
 - `complete_fsm`: Combined FSM containing all rule FSMs
 - `allow_empty_rule_ids`: IDs of rules that can match empty strings
 
 Sources: [cpp/grammar_impl.h70-280](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_impl.h#L70-L280)

 
#### GrammarExpr Types

 Grammar expressions represent components of grammar rules. Each expression has a type and variable-length data array:

 
| Type | Data Format | Description |
|---|---|---|
| kByteString | [byte0, byte1, ...] | Literal byte sequence |
| kCharacterClass | [is_negative, lower0, upper0, ...] | Character range (e.g., [a-z]) |
| kCharacterClassStar | Same as kCharacterClass | Star quantifier [a-z]* |
| kEmptyStr | [] | Empty string |
| kRuleRef | [rule_id] | Reference to another rule |
| kSequence | [expr_id0, expr_id1, ...] | Concatenation of expressions |
| kChoices | [expr_id0, expr_id1, ...] | Alternation (OR) |
| kTagDispatch | [tag0, rule0, ..., loop_flag, excluded_str_id] | Dynamic dispatch based on tags |
| kRepeat | [rule_id, min_count, max_count] | Repetition with bounds |

### Compilation Layer

 
#### GrammarCompiler

 `GrammarCompiler` coordinates the compilation pipeline and manages a two-tier cache to avoid redundant work.

 **Key Responsibilities**:

 
 - Apply normalization and optimization passes
 - Build FSMs for each rule
 - Precompute adaptive token masks
 - Cache compiled grammars (grammar-level LRU cache)
 - Share cached rule-level token masks across grammars
 
 **Main Methods**:

 
 - `CompileGrammar()`: Orchestrates the full compilation pipeline
 - `CompileJSONSchema()`: Converts JSON schema to grammar and compiles
 - `CompileBuiltinJSONGrammar()`: Returns cached standard JSON grammar

#### Optimization Pipeline

 The compilation applies these transformations in sequence:

 
```

```

 **Optimization Passes**:

 
 - **StructureNormalizer**: Ensures each rule body is either:

 
 - `kChoices` of `kSequence` of elements (e.g., `rule ::= (a b c) | (d e)`)
 - `kTagDispatch` for structural tags
 - **ByteStringFuser**: Merges consecutive byte strings in sequences
 - **RuleInliner**: Inlines rules that appear only at sequence beginnings and don't contain rule references
 - **DeadCodeEliminator**: Removes unreferenced rules based on reachability analysis
 - **LookaheadAssertionAnalyzer**: Detects patterns where a rule always follows certain elements and adds lookahead assertions
 - **GrammarFSMBuilder**: Constructs finite state machines for each rule using Thompson's NFA construction, subset construction for DFA conversion, and Hopcroft's algorithm for minimization

### Runtime Layer

 
#### GrammarMatcher::Impl

 The `GrammarMatcher::Impl` class handles token acceptance and mask generation using the Earley parser.

 **Key Members**:

 
 - `compiled_grammar_`: The `CompiledGrammar` to match against
 - `tokenizer_info_`: Vocabulary and token information
 - `stop_token_ids_`: Token IDs that terminate matching
 - `token_length_history`: History for rollback support
 - `tmp_accepted_bitset_`: Temporary storage for building masks
 
 **Main Methods**:

 
 - `AcceptToken(token_id)`: Validates and accepts a token, advancing the parser state
 - `AcceptString(str)`: Accepts a string by processing each character
 - `FillNextTokenBitmask(bitmask, index)`: Generates the bitmask of acceptable next tokens
 - `Rollback(num_tokens)`: Reverts the parser by `num_tokens` steps

#### EarleyParser

 The `EarleyParser` implements the core parsing algorithm that tracks all possible parse states.

## Token Mask Generation Flow

 The `FillNextTokenBitmask()` method generates the bitmask for acceptable tokens:

 
```

```

 **Algorithm Details**:

 
 - **Query Precomputed Masks**: For each scanable parser state, retrieve its `AdaptiveTokenMask` from cache
 - **Union Accepted Tokens**: Combine accepted tokens from all states using bitwise OR
 - **Process Uncertain Tokens**: For uncertain tokens, actually run the parser on each token's string to determine acceptance
 - **Longest Common Prefix (LCP) Optimization**: Reuse parsing work from the previous token when tokens share prefixes
 - **Intersect Rejected Tokens**: Compute the intersection of rejected tokens across all states
 - **Set Stop Tokens**: If parsing is completed, include stop tokens in the accepted set
 - **Write Bitmask**: Pack the final accepted/rejected sets into the int32 bitmask array
