## Overview

 The Structural Tags System is a flexible, JSON-based format specification language for defining structured generation constraints in LLM applications. Unlike fixed JSON schemas or EBNF grammars, structural tags support **dynamic grammar dispatching** where different constraints activate based on trigger strings in the LLM's output.

 This system is designed for advanced LLM use cases that require:

 
 - **Tool calling with multiple functions** - LLM can choose which tool to invoke based on generated text
 - **Mixed free-form and structured output** - Allow natural language explanations alongside structured data
 - **Conditional formatting** - Different validation rules apply depending on context
 - **Complex nested structures** - Combine multiple format types compositionally
 
 **Key Design Principle:** Structural tags enable LLMs to generate text that switches between unconstrained natural language and strictly validated structured content, all within a single generation session.

 For detailed implementation of parsing, analysis, and conversion algorithms, see [Structural Tags Deep Dive](https://deepwiki.com/mlc-ai/xgrammar/6-structural-tags-deep-dive).

## Why Structural Tags?

 Traditional constrained generation systems require choosing a single grammar upfront. Structural tags solve three limitations:

 
| Traditional Approach | Structural Tags Solution | Example |
|---|---|---|
| Fixed schema for entire output | Dynamic schema selection via triggers | LLM chooses which of 10 tools to call based on context |
| No free-form text in structured output | Mix of any_text and structured formats | "Let me analyze this... <tool_call>...</tool_call>" |
| Single format type | Compositional format combinations | Sequence of thinking tag, then tool calls, then summary |

 **Core Innovation:** The `TriggeredTagsFormat` and `TagDispatch` mechanism allow grammars to "wake up" when specific trigger strings are detected, then validate subsequent content against the triggered grammar.

### Basic Formats

 These are atomic building blocks that match specific content types:

 
| Format Type | Purpose | Example |
|---|---|---|
| const_string | Match exact string literal | {"type": "const_string", "value": "Hello"} |
| json_schema | Validate JSON against schema | {"type": "json_schema", "json_schema": {...}, "style": "json"} |
| any_text | Match arbitrary text (optionally with exclusions) | {"type": "any_text", "excludes": ["</think>"]} |
| grammar | Embed EBNF grammar string | {"type": "grammar", "grammar": "root ::= [0-9]+"} |
| regex | Match regex pattern | {"type": "regex", "pattern": "[A-Z][a-z]+"} |

### Dynamic Dispatching Formats

 These are the most powerful formats enabling conditional grammar activation:

 
| Format Type | Purpose | Key Feature |
|---|---|---|
| triggered_tags | Activate different grammars based on trigger strings | Core tool calling mechanism - LLM output triggers appropriate function schema |
| tags_with_separator | Match zero or more tags separated by delimiter | Parallel tool calling with comma-separated calls |

 **The `triggered_tags` format is the foundation of flexible tool calling systems.** When the LLM generates a trigger string (e.g., `"<function="`), the system switches to validating against the corresponding function's schema.

## Tool Calling with Triggered Tags

 The `triggered_tags` format is the primary mechanism for implementing flexible tool calling in LLM applications. It allows the LLM to generate free-form text until a trigger string indicates a function call is starting.

 **Triggered Tags Structure:**

 
```

```

 **Control Parameters:**

 
| Parameter | Effect | Use Case |
|---|---|---|
| at_least_one=false | Allow generation without any tool calls | Optional tool calling |
| at_least_one=true | Require at least one tool call | Forced tool calling |
| stop_after_first=false | Allow multiple tool calls in sequence | Parallel tool calling |
| stop_after_first=true | Stop after first tool call | Single tool calling |

 **How Trigger Matching Works:**

 
 - LLM generates text freely until it produces a string matching one of the `triggers`
 - System switches to validating the next tokens against tags whose `begin` starts with that trigger
 - After completing a tag (reaching `end`), system returns to free-form text (if `stop_after_first=false`)
 - Process repeats until EOS or generation limit
 
 This enables natural interaction patterns like:

 
```
Let me check the weather for you. <function=get_weather>{"location": "NYC"}</function>
Based on the forecast, I recommend...
```

## Performance Considerations

### Grammar Compilation

Structural tags with many triggers and complex schemas can be expensive to compile:

1. **Caching**: Use `GrammarCompiler` with `cache_enabled=True` to avoid recompilation
2. **Thread Safety**: Multiple threads can compile different grammars simultaneously
3. **Optimization**: The grammar normalizer reduces redundant rules after conversion

```python
compiler = xgr.GrammarCompiler(tokenizer_info, max_threads=16, cache_enabled=True)
compiled_grammar = compiler.compile_structural_tag(tags, triggers)
```

 **Sources:** tests/python/test_structural_tag_converter.py:14-21, tests/python/test_grammar_matcher_structural_tag.py:347-375

### TagDispatch Runtime

 The `TagDispatch` mechanism uses Aho-Corasick automaton for efficient multi-pattern matching:

 
 - **Trigger Detection**: O(m) where m is input length, regardless of trigger count
 - **Token Mask Generation**: Only applies mask when inside structured content
 - **Memory**: Scales with number of unique trigger prefixes
 
 Profiling shows mask generation takes microseconds even for complex patterns:

 
```
Time to fill_next_token_bitmask: 10-50 us (inside structured tag)
Time to fill_next_token_bitmask: 1-5 us (free text region, no masking)
```
