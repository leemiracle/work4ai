  This page explains the internal Abstract Syntax Tree (AST) representation of grammars in XGrammar. It covers the `Grammar::Impl` class structure, how rules and expressions are stored, and the CSR-style data format used for efficient storage and traversal.

 For information about parsing EBNF strings into this representation, see [EBNF Parser and Grammar Construction](https://deepwiki.com/mlc-ai/xgrammar/7.1-ebnf-parser-and-grammar-construction). For compilation of grammars into finite state machines, see [Grammar Compilation](https://deepwiki.com/mlc-ai/xgrammar/2.2-grammar-compilation). For lower-level C++ implementation details, see [Grammar Internal Representation](https://deepwiki.com/mlc-ai/xgrammar/11.1-grammar-internal-representation).

 
## Overview

 The `Grammar::Impl` class stores the complete AST of a Backus-Naur Form (BNF) grammar. Each grammar consists of:

 
 - **Rules**: Named production rules, each defined by a `GrammarExpr`
 - **GrammarExprs**: Expression nodes that define rule bodies (strings, character classes, sequences, choices, etc.)
 - **Auxiliary data**: FSMs, lookahead assertions, and optimization metadata
 
 All grammars are internally normalized to a canonical form where rules reference other rules, and expressions are stored in a compact CSR (Compressed Sparse Row) format for efficient traversal.

 **Structure of Grammar::Impl**

 The `Grammar::Impl` class maintains three core data structures:

 
 - **`rules_`**: Vector of `Rule` objects, indexed by `rule_id`
 - **`grammar_expr_data_`**: Flat array storing all expression data
 - **`grammar_expr_indptr_`**: Index pointers into `grammar_expr_data_` for each expression

## Rule Structure

 Each `Rule` represents a production rule in the grammar:

 
| Field | Type | Purpose |
|---|---|---|
| name | std::string | Unique identifier for the rule |
| body_expr_id | int32_t | ID of the GrammarExpr defining the rule body |
| lookahead_assertion_id | int32_t | Optional lookahead assertion expression ID (-1 if none) |
| is_exact_lookahead | bool | Whether the lookahead assertion must match exactly |

 **Example mapping from EBNF to Rule:**

 
```
EBNF: root ::= "hello" "world"
Rule: { name="root", body_expr_id=5, lookahead_assertion_id=-1 }
```

 The `body_expr_id` references a `GrammarExpr` stored in the expression data arrays.

### kByteString

 **Data format:** `[byte0, byte1, byte2, ...]`

 Stores a literal string as a sequence of bytes (0-255). Supports UTF-8 encoding.

 **Example:**

 
 - EBNF: `"hello"`
 - Data: `[104, 101, 108, 108, 111]` (ASCII codes)
 
 Sources: [cpp/grammar_impl.h109-110](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_impl.h#L109-L110) [cpp/grammar_builder.h88-107](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_builder.h#L88-L107)

 
### kCharacterClass

 **Data format:** `[is_negative, lower0, upper0, lower1, upper1, ...]`

 Represents a set of Unicode codepoint ranges. The `is_negative` flag indicates whether the class is negated (e.g., `[^a-z]`).

 **Example:**

 
 - EBNF: `[a-z0-9]`
 - Data: `[0, 97, 122, 48, 57]` (is_negative=0, 'a'-'z', '0'-'9')
 
 Sources: [cpp/grammar_impl.h111-113](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_impl.h#L111-L113) [cpp/grammar_builder.h119-136](https://github.com/mlc-ai/xgrammar/blob/c30554f7/cpp/grammar_builder.h#L119-L136)

 
### kCharacterClassStar

 **Data format:** Same as `kCharacterClass`

 Special optimization for `[a-z]*` patterns to avoid recursive rule expansion during matching.

 **Example:**

 
 - EBNF: `[a-z]*`
 - Data: `[0, 97, 122]` (non-negated, 'a'-'z')

### kRuleRef

 **Data format:** `[rule_id]`

 Reference to another rule by its `rule_id`.

 **Example:**

 
 - EBNF: `root ::= term` (where `term` is defined elsewhere)
 - Data: `[3]` (rule_id of `term`)

### kSequence

 **Data format:** `[expr_id0, expr_id1, expr_id2, ...]`

 Concatenation of multiple expressions. All expressions must match in order.

 **Example:**

 
 - EBNF: `"hello" " " "world"`
 - Data: `[5, 6, 7]` (IDs of the three string expressions)

### kChoices

 **Data format:** `[expr_id0, expr_id1, expr_id2, ...]`

 Alternation between expressions. Any one expression must match.

 **Example:**

 
 - EBNF: `"a" | "b" | "c"`
 - Data: `[8, 9, 10]` (IDs of the three alternatives)

### kTagDispatch

 **Data format:** `[tag_expr0, rule_id0, tag_expr1, rule_id1, ..., stop_eos, stop_str_expr_id, loop_after_dispatch, excluded_str_expr_id]`

 Conditional dispatching based on matching tag strings. Used for tool calling and structured tag systems.

 **CSR Storage Details**

 Each expression in `grammar_expr_data_` is stored as:

 
 - **Type field** (1 int32): `GrammarExprType` enum value
 - **Length field** (1 int32): Number of data elements
 - **Data payload** (variable length): Expression-specific data
 
 The `grammar_expr_indptr_` array stores the starting index of each expression in `grammar_expr_data_`.

## Normalized Grammar Structure

 After parsing and normalization, grammars follow a canonical structure:

 
```

```

 **Normalized Form Properties:**

 
 - Each rule body is either: 
 - A `kChoices` expression containing sequences of elements
 - A `kTagDispatch` macro expression
 - The first choice can be `kEmptyStr` to allow empty matches
 - Elements can be: `kByteString`, `kCharacterClass`, `kCharacterClassStar`, `kRuleRef`, `kRepeat`
 - Nested sequences and choices are flattened

## Auxiliary Data

 Beyond the core AST, `Grammar::Impl` stores optimization metadata:

 
| Field | Type | Purpose |
|---|---|---|
| complete_fsm | CompactFSM | Combined FSM for all rules |
| per_rule_fsms | vector<optional<CompactFSMWithStartEnd>> | Individual rule FSMs (if applicable) |
| per_rule_fsm_hashes | vector<optional<uint64_t>> | Hash values for FSM caching |
| per_rule_fsm_new_state_ids | vector<vector<pair<int32_t, int32_t>>> | Remapped FSM state IDs |
| allow_empty_rule_ids | vector<int32_t> | Rules that can match empty string |
| optimized | bool | Whether grammar has been optimized |

 These fields are populated during compilation (see [Grammar Compilation](https://deepwiki.com/mlc-ai/xgrammar/2.2-grammar-compilation)) and used during matching (see [Grammar Matching](https://deepwiki.com/mlc-ai/xgrammar/2.3-grammar-matching)).
