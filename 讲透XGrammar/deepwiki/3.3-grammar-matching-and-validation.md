  This page documents the `GrammarMatcher` class, which provides runtime validation of token sequences against compiled grammars. The matcher maintains a stateful parser that accepts tokens or strings, generates token bitmasks for LLM sampling, and supports rollback for speculative decoding.

 For batch processing of multiple matchers in parallel, see [Batch Processing](https://deepwiki.com/mlc-ai/xgrammar/3.4-batch-processing). For token bitmask allocation and application functions, see [Token Bitmask Operations](https://deepwiki.com/mlc-ai/xgrammar/3.5-token-bitmask-operations). For information about compiling grammars before matching, see [Grammar Compilation](https://deepwiki.com/mlc-ai/xgrammar/3.2-grammar-compilation).

 
## Overview

 The `GrammarMatcher` class is the core runtime component for grammar-guided generation. It wraps an Earley parser that validates input token sequences against a compiled grammar and efficiently generates token bitmasks to constrain LLM output.

 
```

```

 **Diagram: GrammarMatcher state machine showing method calls and transitions**

 The matcher operates in a loop: at each step, `fill_next_token_bitmask()` generates constraints for the next token, the LLM samples a token respecting those constraints, and `accept_token()` advances the parser state. The matcher terminates after accepting a stop token (or after matching the full grammar if `terminate_without_stop_token=True`).

## Core Validation Methods

 
### `accept_token()`

 
```

```

 Accepts a single token and advances the matcher state. This is the primary method for feeding LLM-generated tokens to the matcher.

 **Parameters:**

 
| Parameter | Type | Description |
|---|---|---|
| token_id | int | The token ID to accept. Must be a valid token from the vocabulary. |
| debug_print | bool | If True, prints internal parser state information for debugging. |

 **Returns:**

 `bool` - `True` if the token was accepted, `False` otherwise.

 **Rejection Cases:**

 The method returns `False` in the following situations:

 
 - Token does not match the grammar at the current position
 - Matcher has already terminated but is trying to accept a new token
 - Token ID is out of the valid range
 - Token is a special token (not in the regular vocabulary)

## Token Bitmask Generation

 
### `fill_next_token_bitmask()`

 
```

```

 Generates a token bitmask indicating which tokens are valid at the current matcher state. This is the key method for grammar-guided generation, producing constraints that are applied to LLM logits.

 **Parameters:**

 
| Parameter | Type | Description |
|---|---|---|
| bitmask | ArrayLike | Pre-allocated bitmask tensor (CPU, int32). Create with allocate_token_bitmask(). Shape: (batch_size, ceil(vocab_size/32)). |
| index | int | Batch index where the bitmask should be written (for batched inference). |
| debug_print | bool | If True, prints information about the generated bitmask. |

 **Returns:**

 `bool` - `True` if the bitmask needs to be applied (contains restrictions), `False` if all tokens are valid (optimization to skip application).

 **Bitmask Format:**

 
 - Each bit represents one token: `1` = valid, `0` = invalid
 - Packed into int32 elements (32 tokens per element)
 - Token `i` is represented by bit `i % 32` in element `i // 32`

## Implementation Details

 
### Internal Architecture

 
```

```

 **Diagram: GrammarMatcher internal architecture mapping Python API to C++ implementation**

 The Python `GrammarMatcher` class is a thin wrapper around C++ implementation via nanobind. The core matching logic uses:

 
 - **EarleyParser**: Implements Earley's algorithm for context-free grammar parsing
 - **ParserState**: Maintains the set of Earley items (dotted rules) at each position
 - **RepeatDetector**: Prevents infinite loops in recursive grammars
 - **AdaptiveTokenMask**: Efficiently stores token acceptance information in 3 modes: 
 - Accepted set (for few valid tokens)
 - Rejected set (for few invalid tokens)
 - Bitset (for mixed cases)
 - **Rule-Level Cache**: Caches token masks by FSM state hash to avoid recomputation
 
 The matcher consults pre-built finite state machines (FSMs) from the `CompiledGrammar` to determine valid tokens at each grammar position.

## Performance Considerations

 
### Caching Strategy

 The matcher employs a two-tier caching system:

 
 - **Grammar-Level Cache**: LRU cache in `GrammarCompiler` that stores entire `CompiledGrammar` objects
 - **Rule-Level Cache**: Hash-based cache in `AdaptiveTokenMask` that stores token masks for specific FSM states
 
 Both caches are automatically managed and transparent to users.

 
### Optimization Techniques

 
| Technique | Description | Benefit |
|---|---|---|
| First character filtering | Quickly eliminates tokens that don't match the first character | Reduces candidate set by ~95% |
| Longest common prefix (LCP) | Reuses parsing work across tokens with shared prefixes | Avoids redundant FSM traversals |
| Speculative calculation | Pre-computes masks for self-recursive patterns | Handles [a-z]+ efficiently |
| Adaptive mask storage | Switches between accepted/rejected/bitset modes | Memory-efficient for different acceptance patterns |
| Early termination | Returns False from fill_next_token_bitmask() when no restrictions | Skips expensive bitmask application |

 
### Best Practices

 
 - **Reuse matchers when possible**: Reset and reuse a matcher instance rather than creating new ones
 - **Use batch processing for multiple sequences**: See [Batch Processing](https://deepwiki.com/mlc-ai/xgrammar/3.4-batch-processing) for parallel mask generation
 - **Enable caching**: Keep `cache_enabled=True` in `GrammarCompiler` (default)
 - **Monitor termination**: Always check `is_terminated()` to avoid accepting tokens after completion
 - **Handle rejection gracefully**: Check return value of `accept_token()` and handle `False` cases
