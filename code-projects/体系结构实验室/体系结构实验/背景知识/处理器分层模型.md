## 1. 故事起点：IBM System/360 与 ISA 的诞生 `[经典理论]`

### 1.1 1964 年的痛苦

1960 年代初，IBM 同时卖着多款完全不兼容的计算机（7090、1401、1620、7070……）。每款机器**指令集都不一样**：

- 用户为 7090 写的程序，**无法**搬到 1401 上跑；
- IBM 每出一个新型号，**所有软件都要重写一遍**；
- 客户被锁死在旧机器上，因为换机器等于换所有软件。

这是软件危机的最早形态之一。

### 1.2 IBM 的解法：把"硬件规格"从"硬件"里抽象出来

1964 年 4 月 7 日，IBM 发布 **System/360** 系列，做了商业史上最大胆的一次豪赌——**让六款完全不同的硬件（不同频率、不同晶体管数、不同内存）共享同一份"程序员看到的机器"规范**。

这份规范被命名为 **Instruction Set Architecture（ISA，指令集体系结构）**，包括：

- 一套统一的**指令集**（指令的二进制编码、汇编助记符、语义）；
- 一组程序员可见的**寄存器**（16 个 GPR + 4 个浮点寄存器）；
- 一套**地址空间与内存模型**（24 位地址、大端）；
- 一套**异常/中断处理模型**（PSW 切换机制）。

**契约**一旦定义下来：
- **软件人员**只面向 ISA 编程，**不必关心**底层用的是什么晶体管、什么流水线；
- **硬件人员**只要保证"按 ISA 规范响应"，**可以自由选择**实现方式（标量、流水线、超标量、微程序控制存储……）。

### 1.3 后果：软硬件解耦，从此可以独立演进

| 在 S/360 之前 | 在 S/360 之后 |
|----------------|-----------------|
| 软件跟着硬件走，每代重写 | 软件面向 ISA，硬件代代演进 |
| 客户被锁死在旧机器 | 客户可以平滑升级（同一个 OS/360 与 COBOL 程序，从 Model 40 一直跑到 Model 195） |
| IBM 内部产品线互为敌人 | IBM 内部产品线共享生态 |

**S/360 的成功确立了"ISA = 软硬件之间的契约"这一范式**，至今未变。x86、ARM、RISC-V、MIPS、POWER、SPARC 全都遵循这个范式。

> 📖 **延伸阅读**：Fred Brooks《人月神话》第 1 章讲述了 S/360 项目（OS/360）的开发故事；Bob Evans、Gene Amdahl、Fred Brooks 三人因此获得 1985 年 ACM 软件系统奖。`[经典理论]`

## 2. 核心矫正：跨 ISA 兼容性的最大误区

> ⚠️ **本文最重要的一节**。这个误区不矫正，后面的所有讨论都会偏。

### 2.1 错误的原话

> "开发出的软件不经过修改就可以应用在其他 ISA 架构的系统上。"

这句话在某些教材/博客里流传甚广，但**严格来说是错的**，会误导初学者。

### 2.2 真相

**跨 ISA 的二进制程序是完全无法直接运行的**——因为不同 ISA 的**指令编码**完全不同。

举例：

| 同一段 C 代码 `int add(int a, int b) { return a + b; }` | 反汇编 |
|---|---|
| x86-64（Intel/AMD） | `lea eax, [rdi + rsi]` → 字节序列 `8D 04 37` |
| ARMv8-A（飞腾/苹果/高通） | `add w0, w0, w1` → 字节序列 `20 00 01 0B` |
| RISC-V RV64I | `add a0, a0, a1` → 字节序列 `33 85 05 00` |

把 `8D 04 37` 当 ARM 指令喂给飞腾，CPU 译码器要么报"未定义指令"异常，要么把它解释成完全无关的指令然后崩溃。

### 2.3 正确的描述

> "开发出的软件，**只要面向同一个 ISA（指令集架构）编程**，那么它**无需修改**（或仅需重编译），就能在**该 ISA 规范下的各种不同微架构、不同工艺、不同厂商**的处理器上跑起来。"

举例（**同 ISA 跨实现**，软件不变）：

| 场景 | ISA | 微架构/工艺 | 软件 |
|------|-----|------------|------|
| 你 2015 年买的 i7-6700K | x86-64 | Intel Skylake / 14nm | 同一份 Windows 程序 |
| 你 2024 年买的 Ryzen 9 7950X | x86-64 | AMD Zen 4 / 5nm | 同一份 Windows 程序 |
| 你 2010 年买的 iPhone 4 | ARMv7-A | Apple A4 / 45nm | 同一份 iOS App |
| 你 2024 年买的 iPhone 16 | ARMv8.6-A | Apple A18 / 3nm | 同一份 iOS App |

→ **性能从 1x 涨到 50x，但软件一份代码不用改**。这就是 ISA 契约的力量。

举例（**跨 ISA**，软件必须重写或翻译）：

| 场景 | 跨 ISA 的方法 | 代价 |
|------|--------------|------|
| 把 x86 程序搬到 Apple M1（ARM）上跑 | 苹果 Rosetta 2 **二进制翻译** | 启动时翻译、运行时仍有 20–80% 性能损失 |
| 把 Android ARM App 跑在 x86 模拟器上 | Android Studio 模拟器 **指令翻译** | 慢得多，仅用于开发 |
| 把 PC 游戏搬到 PS5（x86-64）上 | 巧了，PS5 也是 x86-64，**同 ISA，无需翻译** | 0 代价 |
| 把飞腾服务器上的 ARM Linux 二进制搬到 x86 服务器 | **必须重新编译源码** | 需要 ARM 与 x86 都有的依赖库 |

### 2.4 一句话记忆

> **ISA 是契约，不是实现。同契约可移植，跨契约必须翻译。**

## 3. 五层抽象栈：从应用到硅片

> 初学者常以为只有"3 层（ISA / 微架构 / 物理实现）"。**完整栈其实有 5 层**，
> 软硬件真正的分界线**不在 ISA**，而在 **ABI/OS**。

```
                  ┌──────────────────────────────────────────┐
       Layer 5    │  应用软件（App / 浏览器 / 游戏 / 推理框架）│   面对-API
                  │  e.g. 微信 / Chrome / PyTorch             │
                  └──────────────────────────────────────────┘
                                  ▲ syscall / libc
                  ┌──────────────────────────────────────────┐
       Layer 4    │  操作系统内核 + ABI（应用程序二进制接口）   │   ★ 软硬件真正分界线
                  │  e.g. Linux + ARM64 System V ABI          │
                  └──────────────────────────────────────────┘
                                  ▲ 指令 / 寄存器
                  ┌──────────────────────────────────────────┐
       Layer 3    │  ISA 指令集架构（契约！）                  │   面向-ISA
                  │  e.g. ARMv8.4-A（飞腾 D3000M 用的）        │
                  └──────────────────────────────────────────┘
                                  ▲ 微架构设计师实现
                  ┌──────────────────────────────────────────┐
       Layer 2    │  微架构（Microarchitecture，CPU 设计实现） │
                  │  e.g. FTC663（飞腾自研，4-wide OoO）       │
                  └──────────────────────────────────────────┘
                                  ▲ 物理设计师画版图
                  ┌──────────────────────────────────────────┐
       Layer 1    │  物理实现（硅片 / 工艺 / 封装）            │
                  │  e.g. 14nm FinFET / BGA 封装 / 2.5GHz     │
                  └──────────────────────────────────────────┘
                                  ▼
                              电子 / 量子 / 光子
```

### 3.1 每一层的契约

| 层 | 契约（这层保证什么） | 变化频率 | 谁负责 |
|----|---------------------|---------|--------|
| **L5 应用** | "我调用 `printf`、我用 PyTorch API" → 这是面向**编程语言 + 库 API** | 高（按周迭代） | 应用开发者 |
| **L4 OS + ABI** | "syscall 号、参数寄存器约定、栈帧布局、ELF 格式" → 这是**进程之间、程序与 OS 之间**的契约 | 中（每代 OS 一次大改） | OS 厂商 + 编译器厂商 |
| **L3 ISA** | "指令编码、可见寄存器、异常模型、内存模型" → 这是**软硬件之间的契约** | 低（每 10–15 年加扩展，不重写） | ISA 标准委员会（ARM Holdings / RISC-V International） |
| **L2 微架构** | "我怎么把 ISA 实现得快/省电/小面积" → **无契约**，自由发挥 | 高（每代 CPU 一次） | CPU 设计公司（Intel/AMD/Apple/飞腾/高通） |
| **L1 物理实现** | "工艺节点、频率、电压、面积、封装" → 物理定律 | 中（每 2–3 年一代工艺） | 晶圆厂 + 封测厂（TSMC/Samsung/中芯） |

> 🔑 **关键观察**：契约越靠下层越稳定。**ISA 的稳定性是整个软件生态存在的前提**。
> Intel x86 已经存活 45+ 年（从 1978 的 8086 到 2024 的 Granite Rapids），软件二进制兼容性几乎从未破坏——这就是 ISA 契约的力量。

### 3.2 为什么初学者常漏掉 L4（OS + ABI）

因为很多入门书在讲"CPU 是什么"时只关心 ISA 以下三层。但**真实软件的运行栈**必须经过 L4：

```
你写：printf("hello")                  ← L5 应用
  ↓ libc 把它转成：write(1, "hello", 5)  ← L4 syscall
  ↓ CPU 执行 svc #0（ARM 的 syscall 指令）← L3 ISA
  ↓ 流水线 + 乱序 + 分支预测               ← L2 微架构
  ↓ 电子在 14nm 晶体管里流过              ← L1 物理
```

**ABI** 是 L4 中**程序员可见、但与硬件相关**的部分，包括：

- **调用约定**（Calling Convention）：前 8 个整数参数走 X0–X7，X19–X28 是 callee-saved……见 [`Lab01 §2.2`](../Lab01_ISA与汇编/README.md)；
- **系统调用号与寄存器约定**：Linux ARM64 的 `read` 是 `syscall #63`，参数 X0–X5；
- **可执行文件格式**：ELF 的结构、动态链接 PLT/GOT 的约定；
- **栈帧布局**：FP/LR/SP 的位置；

**ABI 也跨了不能跑**：Linux ARM64 的二进制搬到 Linux x86-64 上，即使 CPU 支持二进制翻译，syscall 号、寄存器、ELF 头都对不上，必须重写。Windows ARM64 与 Linux ARM64 共享 ISA 但 **ABI 不同**，二进制也不能互换。

> 📌 与项目其他文档的关系：
> - [`Lab01 §2.2`](../Lab01_ISA与汇编/README.md) 实际上同时跨了 **L3（ISA）+ L4（ABI）**：寄存器是 ISA 定的，但"哪些是 callee-saved、参数怎么传"是 ABI 定的。
> - [`Expert_04_OS_Kernel`](../Expert_04_OS_Kernel/) 测 syscall 延迟，就完全在 **L4 层**——它假设 ISA 不变，研究 OS 与硬件之间的过渡。

## 4. L3 ISA 内部：契约具体长什么样？

### 4.1 一份 ISA 规范实际包含的内容

以 ARMv8-A 为例（飞腾 D3000M 用），完整规范（`[官方]` ARM ARM DDI 0487）包括：

| 子系统 | 内容 | 飞腾 D3000M 是否实现 |
|--------|------|---------------------|
| **通用指令集**（A64） | ADD / SUB / LDR / STR / B / BL …… 几百条基础指令 | ✅ |
| **整数寄存器** | 31 个通用 X0–X30 + SP + PC | ✅ |
| **浮点/向量**（ASIMD/NEON） | V0–V31，128 位宽，FMLA / LD1 / ST1 | ✅ |
| **向量扩展**（SVE） | 可变长向量（128–2048 bit），LD1W / FMLA | ❌（E02 §4.6 评为"最大战略伤疤"）|
| **原子操作**（LSE） | CAS / LDADD / SWP | ✅（ARMv8.1-A 强制）|
| **密码学扩展** | AES / SHA1 / SHA256 / SM3 / SM4 | ✅（含中国 SM 算法）|
| **虚拟化**（EL2） | HVC 指令、Stage-2 页表 | ✅ |
| **RAS 扩展**（v5.2） | ESB 指令、ERRIDR/ERRSELR 寄存器 | ✅（见 [`Expert_23`](../Expert_23_Server_RAS/)）|
| **内存模型** | Multi-copy atomic、AArch64 的 acquire/release 语义 | ✅（见 [`Lab06`](../Lab06_内存模型与并发/)）|
| **异常等级** | EL0/EL1/EL2/EL3、同步/IRQ/FIQ/SError | ✅ |
| **系统寄存器** | SCTLR_EL1 / TCR_EL1 / MAIR_EL1 …… 几百个 | ✅ |

> 💡 **这就是为什么 ISA 是"契约"**——它规定的是一份**几百页的规范文档**，硬件只要按这份文档实现，软件就能跑。
> 飞腾 D3000M 与高通 Oryon、Apple A18、亚马逊 Graviton4 都实现 ARMv8-A，它们**互相兼容的根**就是这份共同契约。

### 4.2 ISA 演化谱系：CISC / RISC / EPIC / VLIW `[经典理论]`

| 类型 | 时期 | 代表 | 思想 |
|------|------|------|------|
| **CISC**（复杂指令集） | 1970s– | x86、x86-64、z/Architecture | 用复杂指令压缩代码体积，节省内存（内存贵时） |
| **RISC**（精简指令集） | 1980s– | MIPS、SPARC、POWER、**ARM**、**RISC-V** | 指令简单→流水线深→频率高；让编译器做复杂工作 |
| **EPIC**（显式并行） | 1990s–2000s | Intel Itanium（IA-64） | 编译器一次性告诉硬件所有并行性，硬件不用猜——失败了 |
| **VLIW**（超长指令字） | 1980s– | TI C6000 DSP、Intel Larrabee、一些 NPU | 一条"指令"打包多个独立操作，硬件无需依赖检查 |

> 📌 现代 CPU 几乎清一色 RISC 内核 + RISC 暴露的 ISA，CISC 的 x86 实际上是"前端解码为微操作（μops）+ 后端 RISC 流水线"——见 [`Expert_11_Compiler_Research`](../Expert_11_Compiler_Research/)。
> **飞腾 D3000M 是 ARMv8-A，纯 RISC ISA**，所以流水线后端不需要 x86 那种复杂的微码翻译层。

### 4.3 三大主流 ISA 对照（飞腾 / x86 / RISC-V）

| 特性 | ARMv8-A（飞腾）| x86-64 | RISC-V RV64G |
|------|----------------|--------|--------------|
| 指令长度 | 32 位固定 | 1–15 字节变长 | 32 位固定（RVC 压缩可 16 位）|
| 通用寄存器 | 31 | 16 | 31 |
| 内存模型 | Weakly ordered + barriers | TSO（Total Store Order）| RISC-V RVWMO |
| 谁定义 | ARM Holdings（商业授权） | Intel/AMD 事实标准 | RISC-V International（开源）|
| 授权模式 | 商业 IP 授权 | 不授权（Intel/AMD/威盛独占）| 开源，任何人可实现 |
| 典型频率 | 2.0–3.4 GHz（飞腾 2.5 GHz `[实测]`）| 3.0–6.0 GHz | 0.5–3.0 GHz |
| 典型能效 | 高（移动 + 服务器主流） | 中（依赖大功率） | 取决于实现 |
| 项目中相关 Lab | [`Lab01`](../Lab01_ISA与汇编/) / [`Lab02`](../Lab02_流水线与ILP/) / [`Lab04`](../Lab04_超标量乱序/) / [`Lab06`](../Lab06_内存模型与并发/) | [`View_01_Compiler`](../View_01_Compiler/) 对比 | [`Capstone/cpu_simulator`](../Capstone/cpu_simulator/) 用 RV32I |

## 5. L2 微架构：契约的实现自由度

### 5.1 微架构是"自由发挥"的层

ISA 告诉你"必须有 ADD 指令"，但**怎么实现 ADD**，微架构设计师完全自由：

| ISA 要求 | 微架构可自由选择 |
|----------|-----------------|
| 一条 ADD 1 周期完成（语义） | 用**单周期** ALU？还是**3 级流水线**？还是**多簇 ALU**？ |
| 提供 31 个通用寄存器（ISA 可见） | 用 32 端口寄存器堆？还是 **Cluster 化 + 复制**（Apple 风格）？|
| 提供 1 个 ROB（ISA 不知道有 ROB） | 128 项 ROB？256 项？512 项？（[`Lab04`](../Lab04_超标量乱序/) 测的是这个）|
| LDR/STR 完成语义（ISA） | L1 Cache 多大？多少路组相联？是否支持 memory disambiguation？|
| 分支指令正确执行（ISA） | 是否预测？2-bit 饱和？TAGE？2 级自适应？（[`Lab02`](../Lab02_流水线与ILP/) 测的是这个）|

### 5.3 经典案例：Tomasulo 算法（与项目呼应）

Tomasulo 1967 年在 IBM System/360 Model 91 中提出，**是微架构层的算法，不是 ISA 层的规范**。它解决的问题是：

> 顺序程序里有 RAW 依赖（B = A+1; C = B*2;），但下面的指令（D = E+3;）与前面无依赖，能不能提前执行？

- **ISA 视角**：必须保证**最终提交顺序**看起来像顺序执行；
- **微架构视角**：可以在内部乱序执行，只要**提交时按序**；
- **Tomasulo 的方案**：用**保留站（Reservation Station）+ 寄存器状态位**追踪每个操作数"是否 ready"，ready 就发射，不等前面的指令。

> 🔬 **想深挖 Tomasulo？** 项目里直接对应：
> - [`Lab04 §2.1`](../Lab04_超标量乱序/README.md) 讲了**三种寄存器重命名方案**（ROB-based / ARF-based / PRF-based）——这就是 Tomasulo 思想的现代实现。
> - [`Lab04 §2.2`](../Lab04_超标量乱序/README.md) 给出了**乱序执行的关键数据结构**（ROB / Issue Queue / RS / PRF）。
> - [`Capstone/alpha_21264_study`](../Capstone/alpha_21264_study/) 精读 Alpha 21264——历史上第一个**乱序 + 多簇**的商用 CPU，是飞腾 OoO 设计的"远房亲戚"。

### 5.4 同 ISA、不同微架构的对照

**全部是 x86-64，但内部完全不同**：

| 厂商 | 微架构 | Issue Width | ROB | L1 D$ | 重命名表方案 |
|------|--------|-------------|-----|-------|-------------|
| Intel | Skylake（2015）| 6-wide | 224 项 | 32KB/8-way | PRF（物理寄存器堆）|
| Intel | Golden Cove（2021）| 6-wide | 512 项 | 48KB/12-way | PRF |
| AMD | Zen 4（2022）| 6-wide | 320 项 | 32KB/8-way | PRF |
| Zhaoxin | Yongfeng（2020）| 3-wide | ~180 项 | 32KB/8-way | PRF |

**软件层面**：一份 Windows 11 + Chrome 二进制，在这些 CPU 上**一行都不用改就能跑**。
**性能层面**：跑同样的 SPEC CPU 2017，Golden Cove 比 Yongfeng 快约 3–4 倍。

→ **这就是 ISA 与微架构分离的实际意义：性能由微架构决定，兼容性由 ISA 保证**。

### 5.5 同微架构、不同型号

同一种微架构也可以出多种型号的处理器——常见手段：

| 拓扑调整 | 后果 |
|----------|------|
| 砍核数（8 核 → 4 核） | 多线程变慢，单线程不变 |
| 砍 L3（8MB → 4MB） | 数据库/ML 变慢 |
| 降频（2.5GHz → 2.0GHz） | 整体慢，良率上升、成本下降 |
| 关核屏蔽坏核（4 核良率不够时变 2 核卖） | 良率救星（[`Expert_14`](../Expert_14_Process_Manufacturing/) 良率模型相关）|

飞腾 D3000 与 D3000M 就是这种关系——同一微架构（FTC663/FTC862），不同核数、不同频率、不同 TDP。详见 [`战略锚点.md`](../战略锚点.md)。

## 6. L1 物理实现：从版图到硅片

物理实现层负责把微架构设计师的 RTL 代码（Verilog）变成**真正的硅片**：

```
RTL (Verilog)        →  逻辑综合  →  门级网表
                                       ↓
                     →  布局布线   →  GDSII 版图
                                       ↓
                     →  掩膜       →  光刻        →  晶圆
                                       ↓
                     →  封装       →  测试        →  成品 CPU
```

| 子层 | 内容 | 飞腾 D3000M |
|------|------|--------------|
| **工艺节点** | 14nm / 7nm / 5nm / 3nm | `[推测-依据]` 14nm 级（见 [`Expert_14`](../Expert_14_Process_Manufacturing/) 良率模型）|
| **晶体管结构** | FinFET / GAA / BC | `[推测-依据]` FinFET |
| **频率** | 由 FO4 延迟 × 流水级数决定 | `[实测]` 2.5 GHz（[`Expert_02 §3`](../Expert_02_Architect/) 物理墙分析）|
| **面积** | die size 决定成本 | `[推测-依据]` ~120 mm²（[`Expert_14`](../Expert_14_Process_Manufacturing/)）|
| **封装** | BGA / FCBGA / Chiplet | `[推测-依据]` 单 die BGA |
| **电源** | TDP、电压档位 | `[推测-依据]` TDP ~72W（[`Expert_20`](../Expert_20_Green_Compute/)）|

> **物理实现层的独立性**：同一种微架构（RTL）可以用不同工艺流片。
> Apple A 系列芯片同一份 RTL，在 TSMC 5nm 与 3nm 上都流过片——主要差别是性能、能效、成本，**软件二进制完全相同**。

## 7. 工具辨析：QEMU vs Gem5（最常被初学者搞混）

> 这两件事都在"模拟 CPU"，但**模拟的是不同层**，搞混会浪费时间。

| 工具 | 模拟层 | 用途 | 速度 | 精度 |
|------|--------|------|------|------|
| **QEMU** | L3 ISA + 部分 L4 | 跨 ISA 跑别人的二进制（如 Mac 跑 x86）| 极快（TCG JIT）| 功能正确，**不模拟微架构** |
| **Gem5** | L3 + **L2 微架构** | 学术界模拟流水线/Cache/分支预测器 | 慢（比真实慢 100–1000x）| 可模拟 ROB 大小、发射宽度、分支预测 |
| **真实硬件** | L1–L5 全部 | 跑生产负载 | 满速 | 满精度 |

**一句话记忆**：

> QEMU 关心**"这条指令做什么"**（功能），Gem5 关心**"这条指令怎么做的、用了几拍"**（行为）。

| 你想做的事 | 用哪个 |
|-----------|--------|
| 在 Mac M1 上跑 x86 Windows 程序 | QEMU（或苹果 Rosetta，本质也是这类）|
| 在 x86 PC 上调试 ARM Linux 内核 | QEMU system mode |
| 学术研究：把 ROB 从 128 项扩到 512 项，IPC 涨多少？ | Gem5 O3 CPU 模型 |
| 评估新型分支预测器 | Gem5 + 自定义分支预测模块 |
| 在飞腾 D3000M 上**实测**它真实微架构（ROB/重命名/Issue）| 真机 + PMU 计数器（[`Lab04`](../Lab04_超标量乱序/) 就是这么做的）|

> 🔬 **本项目的方法论**：**不靠 Gem5，靠飞腾本机 + perf + PMU 计数器反推**。
> 因为 Gem5 模拟出来的数字是模型预测，**真实硬件才是 ground truth**。每个 Lab 的实测数据都打了 `[实测]` 标记，可由读者重跑。

## 9. 五种"相同 vs 不同"——彻底搞清边界

> 这一节用穷举的方式，把五种常见"看起来一样其实不一样"的情况列清楚。

### 9.1 同 ISA + 同微架构 + 不同物理实现

**例子**：Apple A14 Bionic（TSMC 5nm）vs Apple A14X（TSMC 5nm，但 die 更大）
**软件是否兼容**：✅ 完全兼容
**性能差异**：频率/能效/面积差异，IPC 相同

### 9.2 同 ISA + 不同微架构

**例子**：飞腾 FTC663（4-wide OoO）vs Apple M1（Firestone，8-wide OoO）——都是 ARMv8-A
**软件是否兼容**：✅ 完全兼容
**性能差异**：Apple M1 单核 IPC 是飞腾的 2–3 倍（[`Expert_02`](../Expert_02_Architect/) 对标数据）

### 9.3 不同 ISA + 不同微架构

**例子**：飞腾 D3000M（ARMv8-A）vs AMD EPYC（x86-64）
**软件是否兼容**：❌ 不兼容，必须重新编译
**性能差异**：跑各自原生代码，单核差距 2–3 倍

### 9.4 同 ISA + 不同 ABI

**例子**：Linux ARM64 二进制 vs Windows ARM64 二进制
**软件是否兼容**：❌ 不兼容（syscall 号、ELF/PE 格式都不同）
**性能差异**：N/A（根本不能跑）

### 9.5 同 ISA + 同微架构 + 同物理 + 不同微码

**例子**：Intel 同一批 CPU，加载不同 microcode（修补 Spectre/Meltdown）
**软件是否兼容**：✅ 兼容
**性能差异**：修补后某些 syscall 慢 5–30%（[`Expert_12_Security_CISO`](../Expert_12_Security_CISO/) 相关）

## 11. ✍️ 练习（教学模式）

### 📝 练习 1（基础，§2 矫正检验）

下面三句话，哪些是错的？为什么？

- (a) "x86 程序可以直接搬到 ARM CPU 上跑。"
- (b) "ARM Linux 的二进制可以直接搬到 ARM Windows 上跑。"
- (c) "Intel Skylake CPU 升级到 Intel Golden Cove CPU，软件需要重新编译。"

<details><summary>参考答案</summary>

- (a) ❌ 跨 ISA，指令编码完全不同，无法直接跑（除非 Rosetta 类翻译）。
- (b) ❌ 同 ISA 但 **ABI 不同**（syscall 号、可执行文件格式 ELF vs PE 都不同），不能直接跑。
- (c) ✅ 软件不用重编译——**同 ISA、同 ABI**，软件二进制不变；性能自动提升。

</details>

### 📝 练习 2（中级，§4.2 ISA 分类）

判断下列 ISA 分别属于哪一类（CISC / RISC / EPIC / VLIW）：

- (a) ARMv8-A
- (b) Intel 8086
- (c) Itanium IA-64
- (d) RISC-V
- (e) TI C66xx DSP

<details><summary>参考答案</summary>

- (a) RISC
- (b) CISC
- (c) EPIC（已失败）
- (d) RISC
- (e) VLIW

</details>

### 📝 练习 3（高级，§5 微架构 vs ISA）

判断下列特性属于 **ISA 层**还是 **微架构层**：

- (a) 31 个通用寄存器
- (b) ROB 大小为 256 项
- (c) LDR 指令的语义
- (d) 4-wide Issue
- (e) ARM 的 NZCV 条件码
- (f) TAGE 分支预测器
- (g) L1 D-Cache 64KB

<details><summary>参考答案</summary>

- (a) **ISA**（程序员可见）
- (b) **微架构**（程序员不可见，但 [`Lab04`](../Lab04_超标量乱序/) 能反推）
- (c) **ISA**（指令语义）
- (d) **微架构**（程序员看不见 IPC 是几宽）
- (e) **ISA**（条件码是 ISA 的一部分）
- (f) **微架构**（ISA 只规定"分支指令"，不规定怎么预测）
- (g) **微架构**（ISA 不规定 Cache 大小）

</details>

### 📝 练习 4（实战，§7 工具选择）

对于下列任务，应该用 QEMU、Gem5、还是真机？

- (a) 在 x86 Mac 上运行 ARM Android App
- (b) 评估"把飞腾 ROB 从 128 项扩到 256 项"的 IPC 增益
- (c) 实测飞腾 D3000M 的 L1 D-Cache 容量
- (d) 学术研究：自研新 ISA 跑 SPEC 基准

- (b) **Gem5**（微架构层评估，但本项目方法论是用 PMU 反推——见 [`Lab04`](../Lab04_超标量乱序/)）
- (c) **真机 + perf**（[`Lab03`](../Lab03_存储层次/) 给出的是 `[实测]` 64KB/4-way）
- (d) **Gem5 + 自定义 ISA**（开源工具最适合自研 ISA）

</details>
