# 项目宪法（Kernel-Lab 改造与写作规范 v1.0）

> 本文件是 Kernel-Lab（飞腾 D3000 算子优化实验室）的**最高决策文档**。
> 所有新增算子、视角报告（lens）、实验、文档都必须遵循此处的清单、门槛、模板、纪律。
> 制定于 2026-07-01，借鉴姊妹项目「体系结构实验」的项目宪法，适配算子优化定位。

---

## 0. 一条战略忠告（最高原则）

> **项目护城河 = 对一颗具体芯片（FTC862 / D3000）上算子性能的密集实测剖析 + 可复用的多视角分析方法论，不是通用算子优化教程。**

任何新增内容的入场券 = **必须通过"D3000 特异性测试"**：
> 删掉"飞腾/D3000/FTC862/4 FVU"几个字后，若该文仍读得通 → **判定为通用教科书，失败，重写**。

每个算子/lens 必须有**只有这台芯片才答得出**的具体内容：
- 实测 GFLOPS / 利用率（对标 4 FVU = 40 GFLOPS FP32 峰值）
- PMU 计数证据（L1D refill / branch miss / stall backend）
- Roofline 定位（compute-bound 还是 memory-bound，在哪条线上）
- 反直觉发现（如 FP16 MR=8 反而比 MR=2 慢）

**资源分配**：70% 投在「把现有算子推到理论峰值 + 多视角交叉验证」，30% 才铺算子种类广度。**禁止用算子数量换深度。**

## 1. 项目定位（与姊妹项目的关系）

| 维度 | 本项目 Kernel-Lab | 姊妹项目 体系结构实验 |
|------|-------------------|---------------------|
| **视角** | 自上而下："怎么让算子跑得快" | 自下而上："硬件到底怎么工作" |
| **核心问题** | "GEMM/Conv/Attention 在 D3000 上能到多少 GFLOPS？瓶颈在哪？" | "流水线/Cache/分支预测到底是什么？" |
| **PMU 用法** | 用于**优化决策**（该不该 prefetch、分块多大）| 用于**观测概念**（验证 cache 边界）|
| **关系** | **互补**：硬件理解→优化直觉 | 互补：优化经验→硬件提问 |

两者**不重复**：体系结构实验教你看懂硬件，本项目教你把硬件榨干。

**双重定位**：
- (a) 飞腾"自主可控等级二级"的**软件层实证**（4 FVU 自研差异化）
- (b) **国产边缘/信创算力**场景的算子优化实战

## 2. 质量门槛（每个算子 / lens 强制）

### 2.1 算子实现的硬性下限

| 维度 | 下限 | 说明 |
|------|------|------|
| 正确性 | 必须有数值验证 | 与 naive 参考实现对比，输出 max_abs_err |
| 性能数据 | ≥ 3 次取中位数 | 单次结果不可信（见 §7 实验纪律）|
| 利用率 | 必须对标峰值 | FP32: 40 GFLOPS, INT8: 80 GOPS, FP16: 50 GFLOPS（4 FVU）|
| Roofline 定位 | 必须给出 | compute-bound / memory-bound / 在 roofline 哪条线上 |
| PMU 证据 | 至少 cycles + inst + 1 个 cache 事件 | IPC / L1D miss rate / stall |
| `bin/` 产物 | 必须挂到 Makefile | 反例：`gemm_autotune.c` / `conv_winograd_int8.c` 未挂（技术债）|

### 2.2 Lens 视角报告的硬性下限

| 维度 | 下限 | 说明 |
|------|------|------|
| 字数 | ≥ 3000 字（深度型 ≥ 6000）| 禁止"占位式"短文 |
| 量化对标表 | ≥ 1 张 | 禁止裸断言，所有性能数字必须标来源 |
| 可执行证据 | 技术类 lens 尽量有 | `analysis/lens-*.c` 是范例 |
| **D3000 特异性测试** | ✅ **必过** | 删芯片名后不能读成通用优化教科书 |
| 具体建议 | ≥ 3 条可执行 | "建议加 prefetch" 不算，"GEMM 内核 k 循环加 `__builtin_prefetch(B+jc+kc+8)`" 算 |

### 2.3 三条制度性纪律（强制）

1. **数字来源分级制**：所有数字必须标 `[实测]` / `[推导]` / `[官方文档]` / `[推测-依据]`。
   - `[实测]`：本机跑出来，附命令与日期
   - `[推导]`：基于实测数据算出（如 4 FVU × 2.5GHz × 2×8 lane = 40 GFLOPS）
   - `[推测-依据]`：未实测但有依据，必须写出依据

2. **"盲区/弱点"诚实段强制**：每个 lens 必须有一节"**这一视角的盲区与反方**"——敢说这一视角看不见什么、会误导什么。**杜绝软文。**
   - 范例：[`docs/lenses/02-algorithm-scientist.md`](./docs/lenses/02-algorithm-scientist.md) 指出"FP16 用 MR=8 反直觉地慢"

3. **对偶链接强制**：每个 lens 必须有"与其他视角对偶"段，指明一致/冲突。
   - 范例：OS 专家建议 MC×NC 分块（+52%），性能架构师 lens 确认一致

## 4. 算子实现写作模板（统一结构）

每个新增算子的 README / 报告按此结构：

```markdown
# <算子名> — <一句话定位>

## 1. 算子语义（数学定义 + 维度约定）
## 2. D3000 上的理论峰值（推导：FVU 数 × 频率 × lane）
## 3. 实现演进（v1 naive → v2 ... → vN 最优，每步的 GFLOPS 与改动）
## 4. 最优参数表（MR/NR/KC + 推导理由）
## 5. 实测结果（中位数 + 利用率 + Roofline 定位）

```

## 5. D3000 实测锚点速查（所有报告必须引用的真实数据）

> 这是"特异性"的地基，来自 v0.1→v0.9 沉淀。

### 微架构与峰值
| 维度 | 实测值 | 来源 |
|------|--------|------|
| 核 | 自研 FTC862，**4 FVU**（v0.6 重大校准）| docs/lenses/05 |
| FP32 峰值 | **40 GFLOPS**（4 FVU × 2.5GHz × 4 lane）| v0.6 推导 |
| INT8 峰值 | **80 GOPS**（vdotq，4 FVU）| v0.6 |
| FP16 峰值 | 50 GFLOPS（理论，实际 78% 利用）| v0.8 |
| L3 | 8MB shared，**双段**（核 0-3 / 核 0-7）| docs/lenses/05 |

### 算子最优成绩
| 算子 | 配置 | GFLOPS | 利用率 |
|------|------|--------|--------|
| FP32 GEMM 单核 | v5 MR=8 | **39.45** | 98.6% |
| INT8 GEMM 单核 | v5 MR=8 | **77.74** | 97.2% |
| FP16 GEMM 单核 | v4_dual MR=2 ⚠️ | 39.01 | 78% |
| FP32 GEMM 4 核 | MC×NC=256 tiled | **143** | 92.4% |
| Winograd F(4,4) | 6×6 tile | 26.19 等效 | 21.5× vs Direct |
| NEON Flash Attention 8 核 | N=1024 | — | 16.0× vs Naive |

### 反直觉发现（必读）
1. **FP16 用 MR=8 反而比 MR=2 慢**（35 vs 39 GFLOPS）——单条 `vfmaq_laneq_f16` 吞吐 < 4/cyc
2. **OMP_PROC_BIND=close 在 D3000 上反而慢**——拓扑特殊，通用 OS 调优必须本机验证
3. **多核 flat 只有 57% 效率**，MC×NC 分块才到 92%——分块不是可选项是必选项

## 7. 实验纪律（避免掉坑，数据可信的底线）

借鉴 CAQA Ch1 "Fallacies and Pitfalls" 和 Mytkowicz 2009：

1. **固定频率**：`cpupower frequency-set -g performance`，避免 DVFS 干扰
2. **绑单核**：`taskset -c 0` 或 `pin_to_cpu(0)`，避免调度漂移
3. **跑足够多次取中位数**：单次结果几乎一定有偏差（≥ 20 次）
4. **warmup + measured**：先跑 5 次预热 Cache，再计时
5. **防 DCE**：`escape()` / memory clobber，否则编译器删掉"无副作用"循环
6. **数据对齐**：`posix_memalign` / `aligned_alloc`，64 字节
7. **检查编译器有没有"作弊"**：`objdump -d` 看 hot loop 还在不在
8. **PMU 注意 multiplexing**：6 个硬件计数器不够时会分时
9. **永远先写假设再跑实验**：没有假设的"实验"只是 curiosity
10. **通用 OS 调优建议必须本机验证**：D3000 拓扑特殊（如 OMP_PROC_BIND 反例）

工具支持见 [`common/`](./common/)（`bench.h` / `pmu.h` / `run_template.sh` 已封装 1/2/3/4/5）。
