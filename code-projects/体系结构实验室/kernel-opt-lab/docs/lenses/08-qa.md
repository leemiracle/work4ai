## 1. 视角定位

我设计过 TensorFlow/XLA 的算子正确性框架，专长 property-based testing（PBT）与 metamorphic testing（MT）。算子库的测试核心矛盾是**数值正确性的模糊性**——NEON 向量化引入的再结合误差合法但危险。本报告聚焦：覆盖率、代数不变量、随机化、性能回归、跨平台 oracle。

## 2. 八个盲区（按危害排序）

### 🚨 盲区 1：覆盖率仅 0.006%——8×8 子块采样严重不足
`gemm_f32.c:170-182` 仅校验 `C[0..7][0..7]` 共 64 个元素，而矩阵是 1024×1024（1,048,576 元素）。**覆盖率 = 0.0061%**。MR=8 分块边界、N%4 残列、pack_B_blk 的转置逻辑、cache 边界、M=8 倍数以外的"tail 分支"（`gemm_f32.c:124-141`）**从未被执行**——因为 M=N=K=1024 恰好整除。这段尾代码是死测试（dead test）。

### 🚨 盲区 2：无 randomized testing——输入完全确定性
`A[i]=(i%17)/17.0f`、`B[i]=(i%19)/19.0f` 是固定模式。`srand` 在 `lens-precision.c:175` 才首次出现，且不在回归链路。**NaN / Inf / denormal / 大动态范围 / 全零行 / 符号翻转**全部没覆盖。i%17 模式恰好让 K 维累加的舍入误差高度对称，**掩盖了 FP16 大 K 累加的真实危险**。

### 🚨 盲区 3：零 property-based / metamorphic testing
GEMM 满足的代数不变量**一个都没测**：
- `(AB)C = A(BC)`（结合律——可直接暴露累加顺序 bug）
- `(A+B)C = AC + BC`（分配律）
- `A·B = (Bᵀ·Aᵀ)ᵀ`（转置对称——验证 pack_B_blk 转置正确性的金标准）
- `A·I = A`、`I·A = A`（单位元）
- **Metamorphic**：`scale(A,α)·B = scale(C,α)`；`A·perm(B) = perm(C)`

这些性质**无需 golden reference**，是 NEON 内核自验证的最强武器——尤其当无法移植 x86 BLAS 做交叉验证时。

### 🚨 盲区 4：无跨平台 golden oracle——"scalar" 与被测代码同源
`gemm_f32_scalar`（`gemm_f32.c:143`）和被测 NEON 内核用**同一套 `-O3 -fno-inline-functions`、同一 PhyGCC**编译。若编译器对 `float s += a*b` 做了 FMA 收缩（`-ffast-math` 隐式或/gcc 默认 FP contraction），scalar 与 NEON 都会用 FMA，**相同再结合误差互相抵消，bug 被掩盖**。应引入独立 oracle：离线 NumPy/OpenBLAS dump `golden_<dtype>_<M>x<N>x<K>.bin`，CI 比对。

### 🚨 盲区 5：tolerance 策略错误——绝对阈值而非 ULP/相对
全线 `md<1e-4`（FP32）、`tol=1e-2`（F(4,4) Winograd）。问题：①**大动态范围输入**下 1e-4 太严，合法 FMA 误差被判 FAIL；②**小数值输入**下 1e-4 太松，系统性偏置（如符号 bug 导致 1e-5 量级恒定偏置）逃逸。应改为 **ULP-based tolerance**：`tol = max(rel_eps * |ref|, K * eps_machine)`，FP32 `eps=1.19e-7`、FP16 `eps=9.77e-4`、K=1024 累加误差 ≈ `sqrt(K)*eps`（随机游走）或 `K*eps`（最坏）。

### 🚨 盲区 6：无 perf regression baseline 与 CI gating
`results/baseline.md` 记 39.45 GFLOPS，但 `bench-all.sh` 只生成 markdown、**无自动对比阈值**。一次 `-O3` 退步或 MR 参数误改，GFLOPS 从 39 跌到 35（-10%）也只体现为"数字变化"，CI 不拦。`lens-latency` 测 p99 但**无时间序列**，无法回答"这周回归了吗"。需要：`perf-baseline.json` + `±3%`（或按样本 t-test @95%置信）gate。

### 🚨 盲区 7：无 sanitizer / memory 安全检测
`malloc` 全部未判 NULL（`gemm_f32.c:158`），INT8 pack_B_blk 若 N%4≠0 会越界写。**无 ASan / UBSan / MSan build**。`gemm_s8.c` 的 `vdupq_lane_s32` + `vreinterpretq_s8_s32` 是经典 UB 温床（若 a2 未对齐）。一次 `make test-sanitize` 能在 5 分钟内暴露这些。

### 🚨 盲区 8：CI 矩阵为空——仅本地 pre-commit
`.github/` 目录存在但**无 workflow 文件**（glob 返回空）。pre-commit hook（`setup-hooks.sh`）只在装过的机器跑。无矩阵覆盖：{PhyGCC-12.3.2, gcc-12, gcc-13} × {Release, ASan, UBSan} × {单核, OMP_NUM_THREADS=1/4/8}。PhyGCC 升级一次就无人察觉。

## 4. 关键洞察：算子库测试 vs 普通软件测试的本质差异

普通软件是 **boolean 正确性**（assertEqual）。算子库是 **数值正确性**——NEON 向量化、FMA contraction、reduction 顺序变化，使得"正确答案"本身是**模糊集合**。这导致三个反直觉结论：

1. **PASS 不代表对**：当前 `md<1e-4` 对 K=1024 累加，合法 FMA 误差可达 `1024 × 1.19e-7 ≈ 1.2e-4`，**已贴 tolerance 上限**。一次合法优化（改累加树形结构）可能让 md 从 0.8e-4 升到 1.3e-4 → 误判 FAIL；反之一个符号 bug 若偏置量小，也可能 PASS。**绝对阈值是反模式**。

2. **oracle 不能同源**：用同编译器的 scalar 做 reference 等于**自我证明**。算法 bug（如 INT8 量化 scale 算错）两边都错 → PASS。必须引入独立工具链的 golden（NumPy 用 x86 FMA，误差模型不同，能交叉暴露 ARM 特有问题）。

3. **代数性质是免费 oracle**：`(AB)C=A(BC)` 对任意输入成立，且对累加顺序**不敏感**（只要最终结果数学等价）——这恰好屏蔽了"哪个再结合顺序对"的歧义，专抓"逻辑错"（如 pack_B 转置错位、lane index 写反）。这是 NEON 算子测试**性价比最高**的一招，本项目零使用。

此外，Attention 的 `md<0.01 ? "✅" : "⚠️"`（`attention_neon.c:252`）**输出 ⚠️ 而非 ❌**，而 `test.sh:23` 只 grep `❌|FAIL`——**意味着 Attention 即使完全不正确，CI 也 PASS**。这是测试与判定的语义断裂，P0 必须修。
