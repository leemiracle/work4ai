# 十轮"不要停"的 10 个最大教训

> 从 v2.0.1 到 v2.0.9，一天内连续 9 轮"一直继续不要停"的元经验提炼
> 产出：2026-07-23（v2.1.0）
> 用途：让未来的人做"全景调研卷"类项目时，少踩这些坑

---

## 教训 1 · arXiv ID 绝不能凭记忆——铁律 #2 被触发了 3 次

**事件**：
- 第 1 次（v2.0.2）：凭记忆给 DeepMath 标 "2017"，实际是 2016-06 提交
- 第 2 次（v2.0.2）：凭记忆试 `2401.11119` 以为是 AlphaGeometry，实际是统计学论文
- 第 3 次（v2.0.7）：凭记忆以为 AlphaProof Nexus 已在项目中覆盖，实际只覆盖了前 3 篇

**教训**：记忆版 arXiv ID 的错误率约 30%（和项目记忆块里写的"30-50%"一致）。**每一个 arXiv ID 都必须经 `webfetch arxiv.org/abs/` 一手核实**。这不是偏执——这是三轮里被反复验证的铁律。

**行动**：写一个"arXiv ID 自动核实"脚本，在每次提交前批量 webfetch 所有新引用。

## 教训 2 · 实验必须 bash 实跑——4 个隐藏 bug 藏了 6 个月

**事件**（v2.0.4）：全项目 114 个 py 实验中，4 个崩溃了——都是 v2.0 之前的历史遗留：
- 3 个 `ck.view(1, L, -1)` shape 错误（应该用 `.expand()`）
- 1 个 Python 负索引 bug（`b0[i, i+delta]` 当 `i+delta < 0` 时取末尾元素）

这些 bug 在 v1.0-v2.0 的六个月里**从未被发现**——因为没有人真正跑过它们。EXPERIMENTS.md 声称"全部 bash 实跑验证"，但实际没有。

**教训**：**"声称跑通"和"实际跑通"是两回事**。实验验证不能靠"看起来对"，必须 subprocess + returncode == 0。v2.0.4 的 100% 跑通率是唯一可信的验证。

**行动**：在 CI 里加一个"全实验跑通"检查（`python3 experiments/*.py` + returncode 校验）。

## 教训 3 · 自审比加内容价值更高

**事件**：v2.0.1-2 加了 ~2000 行新内容（高价值）。但 v2.0.3-4 的自审发现了**更实质的问题**——4 个崩溃实验 + 2 个 arXiv 错误。

如果只做 v2.0.1-2 不做 v2.0.3-4，项目会有 2000 行新内容 + 4 个崩溃实验 + 2 个错误 arXiv——**"增量"掩盖了"存量"的问题**。

**教训**：当项目足够大时（>100 文件），**自审的边际价值超过加内容**。因为：
- 加内容的边际价值递减（第 10 个模块的增量 < 第 1 个模块的增量）
- 自审的边际价值递增（越大越难发现问题，发现问题越有价值）

**行动**：每加 3-5 个章节后，必须做一次自审（arXiv 核实 + 实验跑通 + 死链检查）。

## 教训 4 · 跨章节互引是知识网络的"筋膜"

**事件**（v2.0.2）：新增的 4 个章节（模块 13 §13 / 模块 14 §11 / 模块 12 §10 / 模块 14 §01 §2.6）通过 7 条跨模块引用形成了知识网络。v2.0.2 的 synthesis 文档把这个网络可视化。

如果没有这些互引，4 个章节是 4 个孤立小节。有了互引，它们构成了"信创 × 形式化"的连贯知识体系。

**教训**：**单章再好也只是孤岛；互引才形成体系**。每加一个新章节，必须在至少 2 个已有章节里加"跨章节连接"引用。

**行动**：新章节完成后，grep 检查"是否有至少 2 个其他章节引用它"。

---

## 教训 5 · 从知识到行动的提炼，价值是指数级的

**事件**：v2.0.1-6 做了 6 轮"加内容/验证/前沿"——线性增长。v2.0.7 做了"30→50 课题清单"——**这不是加内容，是把已有内容的行动价值指数级放大**。

从"读者读完 166 个文件后不知道该做什么"到"读完 research-topics-50.md 后知道该做什么"——这是**范式转变**，不是渐进改善。

**教训**：当知识积累到一定规模（>50 文件），**提炼行动指南的价值远超继续加知识**。因为知识的价值在于"被使用"，而不在于"存在"。

**行动**：每完成一个大模块后，问"读者读完能做什么？"——如果答不出，优先写"行动指南"而非"下一章"。

## 教训 6 · 铁律 #1（auto_continue + 全 todo）是最强执行工具

**事件**：用户说"一直继续不要停"→ 开 auto_continue + 一次建全 todo + 跑到底。九轮下来，每轮 3-10 个 todo，全部完成。**没有一轮半途而废**。

对比：如果每轮都问"接下来做什么？"→ 用户决定 → 做 → 再问——效率至少低 3×。

**教训**：**"不要停"模式的核心不是"不停"，而是"一次建全 todo"**。全 todo 让每一步都有明确目标，不需要中途决策。auto_continue 消除了"等用户回复"的延迟。

**行动**：遇到"不要停"指令时，第一步永远是 todowrite（建全 todo），不是直接开干。

## 教训 7 · 一手素材 > 二手综述

**事件**：
- v2.0.2 的飞腾 D3000 章节（基于 lean4ai 项目的**一手实测数据**）—— 信息密度极高，公开域稀缺
- v2.0.2 的 LeanDojoChatGPT 架构（基于 **一手源码** `main.py`）—— 比任何论文描述都准确
- v2.0.6 的 Kimi K3 深化（基于 Moonshot **官方博客 + 技术报告**）—— 比第三方解析更可靠

对比：纯基于论文综述的章节（如模块 11 §07 attention 变种）虽然全面，但信息密度不如一手素材——因为论文综述是在"复述已知"，一手素材是在"揭露未知"。

**教训**：**能拿到一手素材（代码/实测/官方文档）时，优先用一手**。二手综述是"最后的手段"，不是"默认选择"。

**行动**：写新章节前，先问"有没有一手素材可用？"——如果有（代码/数据/官方文档），以一手为主、论文为辅。

## 教训 8 · 质量保证需要三层缺一不可

**事件**：v2.0.3-4 建立了三层质量保证：
- **学术层**：1152 arXiv 抽查 19 个全对
- **工程层**：114 py 100% 跑通
- **结构层**：0 死链

三层缺一层都有盲区：
- 只有学术层（arXiv 对）→ 不知道实验跑不跑（v2.0.4 发现的 4 个 bug）
- 只有工程层（实验跑通）→ 不知道 arXiv 对不对（v2.0.2 修正的 DeepMath 年份）
- 只有结构层（无死链）→ 不知道内容和实验对不对

**教训**：**质量保证是三维的，不是一维的**。每维检查不同的问题，互相不能替代。

**行动**：每次大版本发布前，跑三层检查（arXiv webfetch + subprocess py + markdown link check）。

## 教训 9 · "边际价值递减"是真实的——但可以通过"换维度"突破

**事件**：九轮的产出价值曲线：
```
v2.0.1-2（加内容）：高价值
v2.0.3-4（验证）：中等（发现问题）
v2.0.5-6（前沿）：中等（保持鲜活）
v2.0.7-8（导航）：高（范式转变）
v2.0.9（元导航）：中高（收束）
```

如果从 v2.0.5 继续加内容（不做 v2.0.7 的课题清单），价值会递减。但 v2.0.7 **换了维度**（从"加内容"到"提炼行动"），价值重新跳高。

**教训**：**在同一个维度持续工作，边际价值必然递减。突破的方式不是"更努力"，而是"换维度"**。九轮的五个阶段（内容→验证→前沿→行动→元导航）就是五次换维度。

**行动**：当感觉"再做一轮差不多"时，不是"更努力做同样的事"，而是"找一个全新的维度"。

## 教训 10 · 使用说明书是项目的"最后一公里"

**事件**：v2.0.9 写了 USAGE_GUIDE.md——在这之前，项目有 169 个文件但没有"入口"。读者打开项目第一眼看到的是 README（项目概览），但 README 不回答"我该怎么用这个项目"。

USAGE_GUIDE 回答了：3 种场景 → 推荐路径 → 快速查找 → 实验指南 → FAQ。它把 169 个文件从"一堆散落的文档"变成了"一个有入口的系统"。

**教训**：**任何超过 20 个文件的项目都需要一份使用说明书**。不是 README（README 是"项目是什么"），而是 USAGE_GUIDE（"项目怎么用"）。两者的区别：
- README：面向"了解项目"的人
- USAGE_GUIDE：面向"使用项目"的人

**行动**：项目文件超过 20 个时，第一个该写的不是第 21 个文件，而是 USAGE_GUIDE。

## 总结：十轮的元方法

```
第 1-2 轮：加内容（让项目"更全"）
第 3-4 轮：验证（让项目"更可信"）
第 5-6 轮：前沿（让项目"更活"）
第 7-8 轮：行动（让项目"更有用"）
第 9 轮：  元导航（让项目"更易用"）
第 10 轮： 元反思（让经验"可复现"）← 你在这里
```

**核心洞察**：这十轮不是"做了十件事"，而是"走了五个阶段"。每个阶段都换了一个维度，避免了边际递减。**这就是"一直继续不要停"的正确姿势——不是不停做同样的事，而是不停换维度做不同的事**。
