# 06 · 模型差异矩阵：Claude / GPT / Gemini / Llama / Qwen / GLM / Kimi

> **核心论点**：同一个 prompt 在不同模型上**真的**表现不同。这不是玄学，是**训练数据 + 对齐方式 + 架构**的真实差异。
> **本文是什么**：2026-08 一手核实的 7 大主流模型 prompt 偏好对比（v1.1 补齐 GLM / Kimi 两个国产系列）。

## 🔍 Claude（Anthropic）详细偏好

### 核心特性
- **XML 标签是 native**：训练时大量用了 XML
- **长上下文（200K-1M）**：long document 是强项
- **Constitutional AI**：内置对齐价值观

### Claude 专属技巧

#### 1. XML 标签（最重要）
```xml
<context>You are helping debug Python code.</context>

<instructions>
1. Identify the bug
2. Suggest a fix with code
3. Explain why the fix works
</instructions>

<code>
{{user_code}}
</code>

<output_format>
Return JSON: {"bug": "...", "fix": "...", "explanation": "..."}
</output_format>
```

#### 2. 长文档：数据在前，查询在后（30% 改进）
```
<documents>
  <document index="1">
    <source>file1.pdf</source>
    <content>{{doc1}}</content>
  </document>
</documents>

<query>
分析以上文档，提取关键事实。
</query>
```

#### 3. Prefill 强制格式
```python
response = claude.messages.create(
    messages=[
        {"role": "user", "content": "Extract facts..."},
        {"role": "assistant", "content": "{"}  # 强制以 { 开始
    ]
)
```

#### 4. Extended Thinking（Opus 4 / Sonnet 4）
```
不需要手动 CoT。直接问：
"分析这段代码的安全问题。输出 JSON。"
模型自己 thinking。
```

#### 5. 正面表述（Constitutional AI 偏好）
- ❌ "不要用 markdown"
- ✅ "用流畅散文"

## 🔍 GPT（OpenAI）详细偏好

### 核心特性
- **Markdown 友好**：训练数据中 markdown 占比高
- **JSON mode 最可靠**：schema 强制
- **System prompt + User + Assistant 分离**

### GPT 专属技巧

#### 1. Markdown 结构
```markdown
# Context
You are debugging Python code.

# Task
1. Identify the bug
2. Suggest a fix

# Code
```python
{{user_code}}
```

# Output Format
JSON: {"bug": "...", "fix": "..."}
```

#### 2. JSON Mode（最强）
```python
response = openai.chat.completions.create(
    model="gpt-5",
    response_format={"type": "json_object"},  # 强制 JSON
    messages=[...]
)

# 或用 Structured Output（schema 强制）
from pydantic import BaseModel
class BugReport(BaseModel):
    bug: str
    fix: str

response = openai.chat.completions.create(
    model="gpt-5",
    response_format=BugReport,  # schema 强制
    messages=[...]
)
```

#### 3. Bookend 结构（指令在前 + 后）
```
[System] You are a code reviewer. Focus on bugs and security.

[User]
Review this code:
{{code}}

Remember: only return JSON.
```

#### 4. Reasoning Effort（o1 / o3）
```python
response = openai.chat.completions.create(
    model="o1",
    reasoning_effort="high",  # low / medium / high
    messages=[...]
)
```

## 🔍 Gemini（Google）详细偏好

### 核心特性
- **超长上下文**（2M token）
- **多模态优先**（图 / 视频 / 音频原生）
- **temperature 必须 1.0**（低会循环）

### Gemini 专属技巧

#### 1. 编号步骤（最爱）
```
Task:
1. Read the input carefully
2. Identify the main entity
3. Extract facts about that entity
4. Return as JSON

Input: {{input}}
```

#### 2. 多模态
```python
response = gemini.generate_content([
    "What's in this image?",
    PIL.Image.open('photo.jpg')
])
```

#### 3. Thinking Budget
```python
response = gemini.generate_content(
    "...",
    generation_config=GenerationConfig(
        thinkingBudget=8000  # token budget for thinking
    )
)
```

#### 4. Google Search grounding
```python
response = gemini.generate_content(
    "What's the latest news on X?",
    tools=[google_search_tool]
)
```

## 🔍 Llama（Meta）详细偏好

### 核心特性
- **开源**：preference 不强
- **prompt 要更具体**
- **few-shot 重要**

### Llama 专属技巧

#### 1. 必加 few-shot
```
Llama 对 zero-shot 不如 GPT/Claude。加 3-5 个例子。

Examples:
Input: ...
Output: ...

Input: ...
Output: ...

Now:
Input: {{real}}
Output:
```

#### 2. 明确格式 + retry
```python
for attempt in range(3):
    response = llama.invoke(prompt)
    try:
        return json.loads(response)
    except json.JSONDecodeError:
        prompt += "\nReturn ONLY valid JSON, no other text."
```

#### 3. 系统提示前置
```python
# Llama 系统提示权重弱，重要约束两边都写
system = "You are X. Always return JSON."
user = f"Do Y. Return JSON only. {input}"
```

## 🔍 Qwen / DeepSeek（中文友好）详细偏好

### 核心特性
- **中文 prompt 最自然**
- **DeepSeek R1 推理强**（GRPO + RLVR）
- **价格便宜**

### Qwen/DeepSeek 专属技巧

#### 1. 中文任务用中文 prompt
```
# 比 GPT/Claude，Qwen 处理中文 prompt 更稳
你是一个 Python 代码审查专家。
任务：找出代码中的 bug。
输出 JSON: {"bug": "...", "fix": "..."}
```

#### 2. DeepSeek R1 thinking

## 🔍 GLM（智谱 / Z.ai）详细偏好

### 核心特性
- **型号线（2026-08）**：GLM-4.5（355B-A32B，agent 基座）→ 4.6（200K 窗口 + 推理中调工具）→ 4.7（2025-12，SWE-bench 73.8%、HLE 42.8%）→ **GLM-5**（2026-02，744B-A40B，MIT 开源，对标 Opus 4.5）→ 5-Turbo（OpenClaw 场景特化）→ 5.1（对齐 Opus 4.6，单任务自治 8 小时）→ 5.2（1M 无损上下文）→ **5.3**（2026-08-14，同 5.2 基座、纯后训练 scaling：长程任务环境×数十倍；Terminal Bench 3.0 / Agents' Last Exam 开源 SOTA，Z.ai Code Bench 较 5.2 +50%，编程接近 Claude Fable 5；权重两周后开源，最敏感 cyber 能力走受信访问计划）
- **全系原生支持**：深度思考 / 流式 / Function Calling / 上下文缓存 / MCP 协议；200K 窗口 + 128K 最大输出（5.2 = 1M）
- **轻量/免费**：GLM-4.7-Flash（30B-A3B 免费）、glm-4-flash（免费 API）；GLM Coding Plan 兼容 Claude Code / OpenCode / OpenClaw
- 端侧生态：GLM-4.5V/4.6V（128K 视觉，"截图即代码"）、GLM-OCR、AutoGLM-Phone

### GLM 专属技巧

#### 1. thinking 参数三态控制（与别家最大的不同）
```python
response = client.chat.completions.create(
    model="glm-4.6",
    messages=[...],
    thinking={"type": "enabled"}   # enabled / disabled
)
# 注意：GLM-5/5.1/5.2/5-Turbo/4.6/4.5 = 模型自动判断是否思考；
#      GLM-4.7 / 4.5V = 强制思考，disabled 无效
#      ⚠️ GLM-5.3 破坏性变更：thinking.type "disabled" 取消，
#      改用 reasoning_effort: low / high / max（思考不可关，默认行为）
# 思维链返回在 reasoning_content 字段（streaming 时在 delta.reasoning_content）
# 实测（2026-08-17 coding 端点）：glm-5.3 默认输出 reasoning_content
```

#### 2. Preserved Thinking（跨轮保留思维链）
```python
# 默认 clear_thinking=True：历史轮 reasoning_content 被清除（省 token）
# 长程 agent 任务开启保留：
thinking={"type": "enabled", "clear_thinking": False}
# ⚠️ 必须"完整、未修改、按原顺序"透传历史 reasoning_content，
#    缺失/裁剪/改写会导致效果下降——与 Kimi k2.7-code 同款铁律
```

#### 3. JSON mode（原生，接近 GPT 可靠性）
```python
response = client.chat.completions.create(
    model="glm-5",
    messages=[
        {"role": "system", "content": "以 JSON 格式返回：{\"bug\": \"...\", \"fix\": \"...\"}"},
        {"role": "user", "content": user_code}
    ],
    response_format={"type": "json_object"}  # glm-5/4.7/4.6/4.5 均支持
)
# 无 schema 强制（弱于 GPT Structured Output），结构仍要在 prompt 里写清楚
```

#### 4. 工具调用流式 + 免费档 + coding 端点
```python
response = client.chat.completions.create(
    model="glm-4.6", messages=[...], tools=tools,
    stream=True, tool_stream=True   # 工具参数实时流出（4.6+ 独有）
)
# 开发/调试用 glm-4-flash（免费，普通端点）；生产按 4.6/4.7/5 梯度选
# ⚠️ GLM-5.3 实测路由（2026-08-17，coding-plan key）：
#   普通端点 api/paas/v4 + glm-5.3 → err 1220 无权限（独立 API 尚未开放）
#   coding 端点 api/coding/paas/v4 + glm-5.3 → ✅（GLM Coding Plan 积分计费：
#   input 6.9 / cached 1.7 / output 24，非高峰 50%——工作日 14-18 点外）
# temperature 范围 [0,1]，5.x/4.7/4.6 默认 1.0
```

#### 5. 中文任务直接中文 prompt
与 Qwen/DeepSeek 同类：中文指令更稳。注意 `finish_reason="sensitive"` 表示内容被安全审核拦截（不是模型拒绝），需在上层做处理分支。

## 🔍 Kimi（月之暗面 / Moonshot）详细偏好

### 核心特性
- **型号线（2026-08）**：K2（2025-07，1T-A32B MoE，首个开源万亿 agentic 基座）→ K2 Thinking（2025-11，HLE 44.9% w/tools、SWE-bench Verified 71.3%，**200-300 次序贯工具调用不漂移**，原生 INT4）→ **K2.5**（2026-01，开源多模态 + **Agent Swarm**：最多 100 并行子代理 / 1500 步，BrowseComp 78.4%）→ K2.6（thinking 参数化）→ kimi-k2.7-code（思考常开）→ k3（reasoning_effort，已上平台文档）
- **256K 上下文**；API **OpenAI / Anthropic 双兼容**
- 官方 prompt 哲学：**给目标，不给步骤**——模型自己规划（agentic 训练的产物）

### Kimi 专属技巧

#### 1. 系统提示保持极简（官方明确建议）
```python
messages = [
    {"role": "system", "content": "You are Kimi, an AI assistant created by Moonshot AI."},
    {"role": "user", "content": "分析这份数据并写一份完整报告：..."}
]
# 与 Claude 相反：不要往 system 里塞长指令。
# 复杂约束放 user 消息；给高层目标而非分步指令（"Think in goals, not steps"）
```

#### 2. 超长输入：末条消息给 executive summary
```
256K 虽大，但 >100K 输入响应明显变慢。
技巧：长文档正常放入后，在最后一条 user 消息末尾附一段
"执行摘要/聚焦指令"——引导模型注意力落在关键处。
（Kimi 官方上下文工程：Map-Reduce 分段摘要、滚动摘要保留
最新 ~20 条、路由分类——详见本手册第 12 章）
```

#### 3. thinking 参数 + Preserved Thinking（k2.5/k2.6）
```python
response = client.chat.completions.create(
    model="kimi-k2.6",
    messages=[...],           # 开 keep 时必须原样回传历史 reasoning_content
    extra_body={"thinking": {"type": "enabled", "keep": "all"}},
    stream=True,              # 官方建议开流式（reasoning+content 双流较大）
    # 不要传 temperature！k2.6/k2.7-code 不可修改，传了报错
    # max_tokens >= 16000，防止思维链截断
)
# kimi-k2.7-code：thinking 永远开 + keep 永远 "all"，无需（也不许）传 thinking
# kimi-k3：改用 reasoning_effort: "low"/"high"/"max"（默认 max）
```

#### 4. 工具调用的 ID 格式坑（自部署/手解析时）
```
K2 系工具调用 ID 必须是 functions.{函数名}:{序号} 格式
（如 functions.get_weather:0），序号全局递增。
ID 不对 → tool-call crash：content 里吐出 <|tool_call_begin|> 裸 token。
vLLM/SGLang 旧版会生成随机 ID——升级或客户端改写。
```

#### 5. 长程 agent 场景选型
- 连续深度研究/多步执行：K2 Thinking（200-300 步稳定）
- 并行大规模任务（调研/长文/批量）：K2.5 Agent Swarm（最高 4.5× 提速）
- 终端编码：Kimi Code CLI + kimi-k2.7-code（Preserved Thinking 常开，多轮不断链）

## ⚠️ 跨模型的 6 个真实陷阱

### 1. JSON 不可靠（除 GPT 外）
**问题**：除 GPT 外，"输出 JSON" 没强制。
**对策**：用 schema enforcement（OpenAI structured output / Claude prefill / Gemini schema）。

### 2. 温度不一致
**问题**：GPT-5 temp=0.7 ≠ Claude temp=0.7。
**对策**：各自标定。生产推荐 temp=0.0-0.3。

### 3. few-shot 顺序敏感
**问题**：Llama 对顺序敏感（recency bias），GPT 不敏感。
**对策**：随机化 + 跑多次。

### 4. 指令位置
**问题**：Claude 指令放后，GPT 放前。
**对策**：**不要直接复制 prompt**，按模型调整。

### 5. system prompt 优先级
**问题**：Claude 系统 prompt > 用户；GPT 用户 > 系统。
**对策**：安全约束两边都写。

### 6. thinking / 推理参数跨家不兼容（2026 新坑）
**问题**：同为"开思考"，三家 API 完全不同——GPT 是 `reasoning_effort`，GLM 是 `thinking.type`（且 4.7 强制开），Kimi 是 `thinking.type + keep`（k2.6/k2.7-code **禁止设 temperature**）；开启跨轮保留后（GLM `clear_thinking=False` / Kimi `keep="all"`），**历史 `reasoning_content` 必须原样、完整、按序透传**，裁剪即失效。
**对策**：适配层为每家单独映射 thinking 参数；多轮 agent 会话保存原始 assistant 消息（含 reasoning_content）整条回传，不要手工重组。
