# 04 · 上下文管理参数表：趋同解，可直接抄

> **核心论点**：上下文管理是经典系统问题——固定尺寸工作集管理。四大 harness 独立收敛到同一套参数。
> **本文是什么**：全部数值经 Arize 2026-04-28 一手分析核实，抄完即用。

---

## 📐 参数速查表（Python 常量版）

```python
# ===== 文件读取（趋同解）=====
FILE_MAX_LINES = 2000            # 四大 harness 一致（Pi/OpenClaw/Claude Code/Letta）
FILE_MAX_BYTES = 50_000          # Pi/OpenClaw 50KB
LINE_MAX_CHARS = 2000            # Claude Code 超长行截断

# ===== 双层防御（token 密集文件会漏过 byte 门）=====
PRE_READ_BYTE_GATE = 262_144     # stat 预检 256KB（Claude Code，拒读并教模型用 offset/grep）
POST_READ_TOKEN_GATE = 25_000    # 读后 token 计数（Claude Code）

# ===== 工具结果预算 =====
TOOL_RESULT_CAP = 50_000         # chars/工具（Claude Code）
MESSAGE_AGGREGATE_CAP = 200_000  # chars/消息（Claude Code，每次 API 调用前预防性落盘+2KB 预览）
OPENCLAW_TOOL_CAP = 16_000       # 或 30% 窗口，取小（OpenClaw）

# ===== 压缩触发（四档任选其一）=====
PI:      trigger = context_window - 16_384;  keep_recent = 20_000   # 摘要为合成 user 消息
OPENCLAW: trigger = 0.5 * context_window     # token 均衡分块丢最旧 + 多阶段摘要；压缩前 flush 状态到内存文件
CLAUDE:  trigger = context_window - 13_000   # ~167K/200K；9 部结构化摘要；压缩后回挂最近 5 个文件
LETTA:   trigger = 0.9 * context_window      # 滑动窗 30% 起 +10% 步进；溢出两级回退（工具结果截 5K → 30%头+30%尾）

# ===== token 估算启发式 =====
ESTIMATED_TOKENS = total_chars // 4          # Alyx char/4

# ===== 系统提示词预算 =====
INSTRUCTION_BUDGET = 150_200 条指令   # 前沿模型可靠遵循上限；系统自身已占 ~50
CLAUDE_MD_ADVICE = "<200 行 / 40KB"
```

## 🧱 七个趋同机制（不只参数，是模式）

| 机制 | 趋同解 | 为什么 |
|---|---|---|
| 文件读取上限 | 硬 cap + offset/limit 分页 + 续读提示 | `2000 lines or 50KB, whichever first` + "[Showing lines 1-2000. Use offset=2001]" |
| 双层防御 | byte 预检 + token 后检 | token 密集文件（minified code）会漏过 byte 门 |
| 工具结果预算 | 超限**落盘 + 2KB 预览** | 不丢信息，只移出窗口（Claude Code/OpenClaw/Alyx 三家同款）|
| LLM 压缩 | 阈值触发 + 保留最近 N token + 摘要回注 | 摘要插为**合成 user 消息**，绝不切断 tool_call/result 配对 |
| 重复读取去重 | 同文件重复读返回 stub | 省 token（Claude Code read deduplication）|
| 子代理隔离 | 默认只传任务字符串 | 干净窗口；fork 是显式选项（07 章）|
| bootstrap 预算 | 启动文件 12K/文件、60K 总量（OpenClaw）| 防会话开始就把窗口吃掉一半 |

**趋同的深层原因**：把"窗口太小"重构为**固定尺寸工作集管理**——让 200K token 用起来像 200T。Alyx（数据探索产品，非编码域）独立收敛到同款（10K token 工具上限、幂等去重、char/4 估算、50K checkpoint），证明这是任务无关的结构解。

## 🏗️ 三层渐进披露（上下文的架构模式）

```
Tier 1  常驻层    身份+核心指令+状态      几百~几千 token，每轮都付，必须小
Tier 2  指针层    "去哪找"：文件路径/查询钩子/命名空间     不放内容放地址
Tier 3  按需层    全文/全表，任务相关时才加载             just-in-time
```

两条硬约束（缓存经济学 × 注意力经济学）：
1. **稳定前缀放最前且永不修改**（live 时间戳/每会话插值都会炸掉下游缓存）
2. **易变状态放最后**（recency bias 让最靠近生成的内容获得最多注意力——Manus 的"复述"技巧就吃这个红利）

**Claude Code 自己的数字**：CLAUDE.md 建议 <200 行/40KB，理由写在明面上——"前沿模型可靠遵循约 150-200 条指令，系统提示词已用掉约 50 条"。**指令跟随是有预算的，超了就被静默忽略**。

## ⚠️ 四个真实陷阱

1. **压缩丢细节**：摘要必然有损，"compressed summaries can still lose local in-situ detail"——对策：压缩前状态 flush（OpenClaw）+ 摘要/工件双轨（细节在外存可回查）
2. **超长文件 needle 在 cap 外**：答案恰好在 2000 行之后——对策：grep-first 定向读 + 元数据优先（先 ls/stat 再读）
3. **bootstrap 膨胀→过早压缩**：常驻层太大导致用户还没说话就触发压缩——对策：机械上限（byte 数）而非"请写短点"
4. **STALE**：注入的状态与真实状态矛盾，agent 自信地按旧状态行动——对策：状态写入前验证（06 章）
