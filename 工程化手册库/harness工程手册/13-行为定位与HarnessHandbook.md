# 13 · 行为定位与 Harness Handbook：给 harness 画一张"行为地图"

> **建立日期**：2026-08-20 · **素材**：arXiv:2607.13285（2026-07-14，腾讯混元前沿 + IU/UMD/UGA/NUS；abs 页 webfetch 一手核实 2026-08-20）
> **本文是什么**：harness 演进的第三个瓶颈——不是"怎么改"（11 章进化闭环）、不是"改得对不对"（06 章验证），而是**"该去哪里改"**。
> **一句话**：六组件（03 章）按*结构*解剖 harness；Handbook 按*行为*解剖——同一个仓库的第二张地图。

---

## 1. 问题：行为定位（Behavior Localization）

一条自然语言变更请求（"删除文件前必须询问用户"）的实现，往往散布在 **5+ 个实现点**：prompt 指令、工具拦截器、权限配置、状态记录、沙箱执行、回退路径——不同文件、不同执行阶段。

- 代码搜索/仓库索引/长上下文只能让代码*更容易看*，**"行为描述 → 代码位置"的映射仍靠人脑恢复**
- 这正是 agent 改 harness 时"改漏一处"的结构性根源——不是模型蠢，是地图缺了一层

> **定义**：Behavior Localization = 找到实现某行为变更所需的**全部**代码位置。它是规划完整编辑方案的前提。

## 2. 方案：三层递进手册（L1→L2→L3）

| 层 | 回答 | 内容 |
|---|---|---|
| **L1 系统概览** | 整体怎么跑？ | 追一个请求如何流经系统：入口→执行阶段→状态流转→输出变动作 |
| **L2 行为单元概览** | 有哪些行为单元？ | 系统分解为 Behavior Unit：职责/输入输出/依赖/关键状态 |
| **L3 行为单元详情** | 这个单元怎么执行？ | 触发条件 / 权限规则 / 状态变化 / 执行路径 / 边界情况（headless、自动审批回退） |

**宪法原则：Prose explains; facts anchor.**——每条自然语言声明必须锚定 `file:line` 级代码证据，可逐条验证。这与本手册 06 章"验证即证据"、用例库"文件:行号"铁律同源。

### 生成管线（三阶段，全自动）

```
静态分析（文件/函数/调用/状态读写/配置边界 → 程序图 Program Graph）
  → 按行为组织（执行骨架 + Proposer-Reviewer 循环，映射收敛为止 → 行为图）
    → 合成渲染（L1/L2/L3 手册；所有链接必须来自程序事实，不许 LLM 编造）
```

开源三模块：`handbook_generate_large`（大库，自底向上文件为叶，支持 Python/Rust/TS/Go）、`handbook_generate_small`（小库，骨架驱动 skeleton.yaml）、`handbook_as_helper`（**Planner**：手册转 Agent SKILL 挂到规划器；**Resync**：代码变更后前滚派生层——过期问题的官方解）。

## 3. 使用范式：BGPD（Behavior-Guided Progressive Disclosure）

```
行为问题 → L1 定位阶段 → L2 定位单元 → L3 定位实现点 → 代码证据
```

三种用途：**理解**（Understand，从 L1/L2 建系统模型）、**审计**（Audit，L3 逐条核对触发器/权限/回退）、**适配**（Adapt，定位变更边界→生成带证据的编辑计划）。这和 04 章"三层渐进披露"是同一思想在*仓库知识*维度的应用。

## 4. 实测数字（为什么值得信）

| 被测 Harness | Planner 胜率 | Token 消耗 |
|---|---|---|
| Codex（2,267 文件 / 34K+ 函数 / ~160K 代码连接）| **+10.0pp** | **−12.7%** |
| Terminus-2 | **+18.9pp** | **−8.6%** |

- 文件级/符号级 Recall/Precision/F1 几乎全线提升；"完全定位错子系统"的 Wrong 案例大降
- 增益最大处：**实现点分散 / 很少执行的代码路径 / 跨模块交互**（Search-hostile 类请求）
- 评判：三独立 Judge（GPT-5.5 / Opus 4.8 / DeepSeek-V4-Pro）

## 5. 与本手册的接口（关键：互补，不是重复）

| 已有章 | Handbook 补什么 | 关系 |
|---|---|---|
| 03 六组件（结构解剖）| 行为解剖（第二坐标系）| 结构=名词视图，行为=动词视图，**双图对照** |
| 04 上下文管理（三层披露）| BGPD 是同一原则用于*仓库知识*而非*任务上下文* | 原则复用 |
| 06 验证即证据 | facts anchor 是它在"读路径"的镜像 | 同一宪法 |
| 11 自动进化闭环（AHE）| **AHE 管"怎么改"，Handbook 管"去哪改"**——进化 agent 的动作空间定位器 | 读路径 × 写路径 |
| 12 最小实现 | mini-handbook 可作 12 章骨架的标配输出物 | 落地形态 |

**推理链**：AHE 的组件可观测性（每个可编辑组件=文件）解决"改哪个*组件*"；Handbook 解决"这个行为散布在哪些*代码位置*"——前者按组件分类，后者按行为聚合，进化 agent 两者都要。

## 6. 落地：给你的 harness 造 mini-handbook（半天量级）

1. **抽事实**：`grep`/tree-sitter 扫你的 agent 目录——入口函数、工具注册表、每工具的 schema/handler、中间件链、状态文件读写点
2. **列行为单元**：典型 10-30 个（每个工具调用一个 + 生命周期各阶段一个）
3. **每单元填 L3 表**：触发/权限/状态读写/正常路径/异常路径/**每行带 file:line**
4. **挂进 agent**：作为 SKILL.md 或 docs/ai/skills/ 一员（x-kernel 已有此结构，直接加 `behavior-map.md`）
5. **Resync 纪律**：每次 harness 变更后前滚受影响单元——或最低限度，CI 里加"手册行号失配检查"

> ⚠️ 诚实边界：手工维护的 handbook 会腐烂——官方 Resync 是 LLM 辅助前滚，尚无强保证；小团队先覆盖 Top-10 高频变更行为即可，别追求全量。
