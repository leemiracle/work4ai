  The Hugging Face Transformers library provides native integrations for high-performance distributed training and inference through DeepSpeed and PyTorch Fully Sharded Data Parallel (FSDP). These integrations are primarily orchestrated via the `Trainer` class and specialized configuration utilities in the `distributed` and `integrations` subpackages.

 
## DeepSpeed Integration

 DeepSpeed integration allows for Zero Redundancy Optimizer (ZeRO) stages 1, 2, and 3, enabling the training of models that exceed the memory capacity of a single GPU by sharding optimizer states, gradients, and parameters [src/transformers/integrations/deepspeed.py57-86](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/integrations/deepspeed.py#L57-L86)

 
### Configuration and HfDeepSpeedConfig

 The integration uses `HfDeepSpeedConfig` and its subclass `HfTrainerDeepSpeedConfig` to manage the bridge between Transformers' `TrainingArguments` and DeepSpeed's JSON configuration [src/transformers/integrations/deepspeed.py57-86](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/integrations/deepspeed.py#L57-L86)

 Key behaviors include:

 
 - **Auto-filling**: Users can set values to `"auto"` in the DeepSpeed JSON config. The `Trainer` then populates these fields using values from `TrainingArguments` (e.g., `learning_rate`, `per_device_train_batch_size`) [src/transformers/integrations/deepspeed.py105-132](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/integrations/deepspeed.py#L105-L132)
 - **Global State**: A weak reference to the active configuration is stored globally via `set_hf_deepspeed_config` to allow `from_pretrained` to detect if ZeRO-3 parameter sharding is active during model instantiation [src/transformers/integrations/deepspeed.py61-67](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/integrations/deepspeed.py#L61-L67) [src/transformers/integrations/deepspeed.py228-232](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/integrations/deepspeed.py#L228-L232)
 - **ZeRO-3 Loading**: When ZeRO-3 is enabled, `_load_state_dict_into_zero3_model` is used to partition and inject weights directly into the partitioned parameters [src/transformers/integrations/deepspeed.py235-260](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/integrations/deepspeed.py#L235-L260)

## PyTorch FSDP 2.0 Integration

 Transformers supports PyTorch FSDP 2.0 (also known as `fully_shard`), which provides a more modular approach to sharding compared to FSDP 1.0. The implementation leverages `src/transformers/distributed/fsdp.py`.

 
### Key Components

 
 - **DistributedConfig**: A centralized dataclass used to define `fsdp_size`, `tp_size`, and other parallelization degrees [src/transformers/modeling_utils.py57-58](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/modeling_utils.py#L57-L58)
 - **Initialization**: `initialize_fully_sharded_data_parallelism` sets up the `device_mesh` and binds the process to the correct local rank accelerator [src/transformers/trainer.py58-59](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/trainer.py#L58-L59)
 - **Detection**: The utility `is_fsdp_enabled` checks if FSDP environment variables are set or if the FSDP state is active in `TrainingArguments` [src/transformers/modeling_utils.py68-69](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/modeling_utils.py#L68-L69)
 
 
### Requirements

 FSDP 2.0 integration on XLA backends requires `torch_xla>=2.2.0` to utilize the `XLA_FSDPV2` infrastructure [src/transformers/trainer.py200-204](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/trainer.py#L200-L204)

## Multi-GPU Training Configuration

 The library uses a unified set of utilities to initialize distributed backends across different hardware (CUDA, XPU, HPU, etc.) [src/transformers/training_args.py42-55](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/training_args.py#L42-L55)

 
### Initialization Sequence

 
 - **Accelerator Detection**: The system identifies the available device type via utilities like `is_torch_cuda_available` or `is_torch_npu_available` [src/transformers/training_args.py43-50](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/training_args.py#L43-L50)
 - **Process Group Setup**: `TrainingArguments` orchestrates the initialization of the `Accelerator` and the underlying torch distributed process group [src/transformers/trainer.py217-219](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/trainer.py#L217-L219)
 - **Parallel Mode**: The `ParallelMode` enum defines the distributed strategy, including `DISTRIBUTED`, `DEEPSPEED`, and `FSDP` [src/transformers/trainer.py151](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/trainer.py#L151-L151)
 
 
### Sharding and Conversion Logic

 During model loading, `ConversionOps` classes handle the transformation of tensors, which is critical when loading standard checkpoints into sharded distributed environments [src/transformers/core_model_loading.py81-174](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/core_model_loading.py#L81-L174)

 
 - **Chunk**: Splits a tensor along a dimension into equally sized chunks for sharding [src/transformers/core_model_loading.py112-148](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/core_model_loading.py#L112-L148)
 - **Concatenate**: Recombines tensors, often used in reverse operations during checkpoint saving [src/transformers/core_model_loading.py150-174](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/core_model_loading.py#L150-L174)

## Weight Loading in Distributed Environments

 Loading models into DeepSpeed ZeRO-3 or FSDP requires special handling to avoid OOM (Out of Memory) on the primary rank.

 
 - **Sharding on Read**: `DtensorShardOperation` allows for sharding weights as they are read from the checkpoint using `torch.distributed.tensor`, rather than loading the full weight into CPU memory first [src/transformers/core_model_loading.py33-34](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/core_model_loading.py#L33-L34)
 - **Glob Matching**: The `build_glob_alternation` function creates regex patterns to match state dict keys against sharding plans (e.g., matching `model.layers.*.self_attn.q_proj.weight`) [src/transformers/core_model_loading.py49-78](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/core_model_loading.py#L49-L78)
 - **Renaming**: `WeightRenaming` and `WeightConverter` handle architecture-specific mapping during the load process, such as converting `to_q` to `q_proj` for specific model families [src/transformers/conversion_mapping.py152-157](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/conversion_mapping.py#L152-L157)
 - **Lazy Loading**: `LoadStateDictConfig` bundles parameters like `device_map` and `disk_offload_folder` to orchestrate how weights are materialized in distributed setups [src/transformers/modeling_utils.py171-184](https://github.com/huggingface/transformers/blob/8f542025/src/transformers/modeling_utils.py#L171-L184)
