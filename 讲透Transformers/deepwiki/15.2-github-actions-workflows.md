  The `.github/workflows/` directory contains the automation logic for the Hugging Face Transformers library. While CircleCI handles the primary continuous integration for CPU and standard GPU tests, GitHub Actions (GHA) manages Docker image orchestration, documentation testing, specialized hardware CI (AMD, Intel Gaudi, NVIDIA A10/H100), Slack reporting, and PR management utilities.

 
## Infrastructure & Workflow Orchestration

 The workflow system is designed to handle heterogeneous hardware and complex reporting requirements. It uses `workflow_call` patterns to reuse logic across different triggers (push, schedule, and PR comments).

 
### Docker Image Build System

 The library maintains several specialized Docker images to ensure consistent test environments across different hardware backends. The `build-docker-images.yml` workflow orchestrates these builds.

 
| Image Name | Purpose | Base |
|---|---|---|
| transformers-all-latest-gpu | Main CI image for model testing, including FA2 and quantization. | nvidia/cuda:13.0.3 |
| transformers-quantization-latest-gpu | Specialized for quantization backends (BNB, AWQ, GPTQ, HQQ). | nvidia/cuda:12.6.0 |
| transformers-pytorch-amd-gpu | Optimized for ROCm/AMD hardware. | rocm/pytorch:rocm7.2.2 |
| transformers-doc-builder | Environment for building and validating documentation. | Custom |

 The `transformers-all-latest-gpu` Dockerfile includes complex logic to pin PyTorch, TorchAudio, and TorchCodec versions to ensure ABI compatibility, which is verified by a smoke test at the end of the build.

### Slack Reporting Service

 The `slack-report.yml` workflow serves as a centralized reporting hub. It processes test artifacts and uses `utils/notification_service.py` to post detailed summaries to Slack. It maps job identifiers (e.g., `run_models_gpu`) to human-readable categories like "Models" [utils/notification_service.py36-44](https://github.com/huggingface/transformers/blob/8f542025/utils/notification_service.py#L36-L44)

 
#### Notification Logic Flow

 The `Message` class in `notification_service.py` aggregates results from different test suites (Models, Trainer, Pipelines, etc.) and formats them for Slack blocks. It distinguishes between modeling failures (single vs multi-GPU) and additional suite failures [utils/notification_service.py152-183](https://github.com/huggingface/transformers/blob/8f542025/utils/notification_service.py#L152-L183) It handles raw pytest output to extract failure counts, errors, and time spent [utils/notification_service.py74-102](https://github.com/huggingface/transformers/blob/8f542025/utils/notification_service.py#L74-L102)

## Specialized CI Callers

 Transformers utilizes self-hosted runners for hardware that requires specific drivers or accelerators.

 
### Hardware-Specific CI

 Workflows like `self-scheduled-amd-mi300-caller.yml`, `self-scheduled-intel-gaudi.yml`, and `self-scheduled-caller.yml` (Nvidia) trigger tests on specialized hardware. These callers use `daily-ci_reusable.yml` to run standardized jobs like `run_models_gpu`, `run_pipelines_torch_gpu`, and `run_quantization_torch_gpu` [.github/workflows/self-scheduled-caller.yml53-138](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/self-scheduled-caller.yml#L53-L138) The `get_previous_daily_ci.py` utility is used to fetch history for comparison, including logic to handle stale GitHub API responses by checking if the current `GITHUB_RUN_ID` is present in the results [utils/get_previous_daily_ci.py29-58](https://github.com/huggingface/transformers/blob/8f542025/utils/get_previous_daily_ci.py#L29-L58)

 
### PR Slow CI

 For large models or slow tests that cannot run on every PR commit, the `self-comment-ci.yml` workflow allows maintainers to trigger comprehensive tests via PR comments (e.g., `run-slow`).

 
 - **Security Check**: It verifies that the `merge_commit` timestamp is older than the triggering comment to prevent malicious code execution [.github/workflows/self-comment-ci.yml50-61](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/self-comment-ci.yml#L50-L61)
 - **Model Selection**: It uses `utils/pr_slow_ci_models.py` to parse the comment and determine which specific models or quantization suites to test [.github/workflows/self-comment-ci.yml90-95](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/self-comment-ci.yml#L90-L95)
 - **Status Updates**: It creates and updates GitHub Commit Statuses to reflect the progress of these external runs [.github/workflows/self-comment-ci.yml153-160](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/self-comment-ci.yml#L153-L160)

## PR Management & Repository Consistency

 
### PR Dashboard & Recap

 The `pr-ci-post-dashboard-link.yml` workflow runs after the "PR CI" completes. It executes `utils/update_pr_ci_dashboard_recap.py` to post a comment on the PR containing a consolidated view of all CI results across CircleCI and GHA [.github/workflows/pr-ci-post-dashboard-link.yml33-36](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/pr-ci-post-dashboard-link.yml#L33-L36)

 
### Repository Consistency Bot

 The `pr-repo-consistency-bot.yml` workflow allows maintainers to trigger style and repository consistency fixes via comments like `@bot /repo` or `@bot /style` [.github/workflows/pr-repo-consistency-bot.yml19-20](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/pr-repo-consistency-bot.yml#L19-L20) It checks out the trusted `main` branch to install dependencies before applying changes to the PR branch to ensure security [.github/workflows/pr-repo-consistency-bot.yml128-143](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/pr-repo-consistency-bot.yml#L128-L143)

 
### Automated Regression Bisection

 The `check_failed_tests.yml` workflow automates the identification of the specific commit that introduced a test failure. It uses `utils/check_bad_commit.py` to perform a `git bisect` run.

 
 - **Flakiness Detection**: `check_bad_commit.py` creates a `target_script.py` that runs `pytest` with `--flake-finder` to distinguish between genuine regressions and flaky tests [utils/check_bad_commit.py28-80](https://github.com/huggingface/transformers/blob/8f542025/utils/check_bad_commit.py#L28-L80)
 - **Backward Search**: The `find_bad_commit` function searches backward from the current failure (`start_commit`) to a known good state (`end_commit`) [utils/check_bad_commit.py120-137](https://github.com/huggingface/transformers/blob/8f542025/utils/check_bad_commit.py#L120-L137)

## Documentation Building

 Transformers uses GHA to build and preview documentation for every PR and push to `main`.

 
 - **PR Previews**: `build_pr_documentation.yml` uses the `huggingface/doc-builder` action to generate a preview for contributors [.github/workflows/build_pr_documentation.yml15-22](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/build_pr_documentation.yml#L15-L22)
 - **Main Build**: `build_documentation.yml` builds the production documentation for multiple languages including English, Arabic, German, Spanish, French, etc.

## SSH Access for Debugging

 The `ssh-runner.yml` workflow provides a secure way to debug failing CI jobs on self-hosted runners using Tailscale SSH. Maintaining security, it uses `huggingface/tailscale-action` to establish a connection [.github/workflows/ssh-runner.yml163-170](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/ssh-runner.yml#L163-L170) It also includes a `memory_monitor.py` script to track RAM usage during debugging sessions [.github/workflows/ssh-runner.yml109-128](https://github.com/huggingface/transformers/blob/8f542025/.github/workflows/ssh-runner.yml#L109-L128)
