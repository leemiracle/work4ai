## 一、csdiy 到底是什么？（重新定义）

**v1.0 的定义**：csdiy 是一个**程序员能力转化管道**——把 15GB 原始 CS 课程资料，加工成能直接救线上命的实战知识。

**v2.0 的修正定义**：csdiy 是一个**多层金字塔**：
- **L0 原始层**（15GB）：cs-self-learning + website + books + 102 github-repos
- **L1 课程解析层**（13 篇 / ~5,200 行）：6 篇 csdiy-*-complete.md 把 csdiy.wiki 全课程地图逐 session 解析
- **L2 程序员视角层**（7 篇 / ~4,050 行）：从 bug/事故反推原理，落到命令
- **L3 源码精读层**（59 篇 / ~14,400 行）：从 5 篇经典系统源码扩展到 22 篇 LLM 全栈
- **L4 毕业项目层**（68 个 / 14,681 行 py）：每个参照世界级开源，CSAPP 9/9 覆盖
- **L5 工具/检索层**（10 个工具 + 28k FTS 索引）：daily/review/ask/by_topic/index_append

**关键洞察**：v1.0 时 csdiy 是"输入强、输出弱"。v2.0 时，**L4 毕业项目层（14,681 行可运行代码）已经是最大的产出**——比所有精加工笔记加起来还多。

**它不是什么**：
- ❌ 不是网课列表（cs-self-learning 在做）
- ❌ 不是百科（维基在做）
- ❌ 不是面试题库（LeetCode/牛客在做）
- ✅ 是"**从真实 bug/代码出发，反推原理，落到可粘贴命令/可运行项目**"的工程师实战体系

## 五、v1.0 的 3 个怀疑，现在如何？

### 怀疑 1：资料堆积 ≠ 能力增长
**v1.0 状态**：精读从 7→20，debug 能力没同步增长 3 倍。
**v2.0 现状**：精读从 7→59，但**有了 68 个能跑的项目**做对照。读 micrograd → 跑 tinytorch；读 nanoGPT → 跑 tinyllm。读+做配对，能力有锚。
**仍未解决**：68 个项目都是玩具，离生产级还远。需要至少 1 个真实开源项目验证。
**对策**：开源 tinyproxy / tinydb / tinyllm 中的一个，接受真实用户反馈。

### 怀疑 2：csdiy 变成了"拖延真实项目的借口"
**v1.0 状态**：花 3 个月完善 csdiy，没花 3 个月造真实东西。
**v2.0 现状**：csdiy 自身已经造出了 14,681 行"真实东西"。但它们仍然是 csdiy 内部的，没有面对真实用户。
**仍未解决**：csdiy 内的项目 ≠ 真实开源项目。前者是"练手"，后者是"产品"。
**对策**：选 1 个 tiny* 项目，做 GitHub 开源 + 文档 + CI + 接 issue。这是从练手到产品的关键一跃。

### 怀疑 3：单人项目缺少 Socialization
**v1.0 状态**：读再多 before/after，不如和高手一起 review 一次。
**v2.0 现状**：仍然单人。68 个项目的代码风格、权衡决策都没有外部反馈。
**仍未解决**：socialization 必须靠真实协作。
**对策**：给开源项目提 PR（见 v2.0 输出指标 #8）；找 mentor；参与 code review。

## 六、v2.0 的两个新怀疑

### 新怀疑 A：内容覆盖已经超过个人消化能力
**症状**：59 篇源码精读 + 68 个项目 + 13 篇 notes + 6 篇课程解析 = ~30,000 行精加工。
我自己读完了多少？**保守估计 < 30%**。
**根因**：v2.0 是"建仓库"驱动的，不是"消化"驱动的。建得越快，消化滞后越严重。
**对策**：
1. **冻结扩张**：明确停止新增 tiny* 项目和 source-reading（除非配套费曼挑战）
2. **强制消化**：daily.py 每天抽 1 篇精读 + 1 个项目，强制阅读 + 跑代码
3. **进度跟踪**：用 feynman.py 完成度作为消化指标

### 新怀疑 B：从"基础设施"到"产品"的鸿沟
**症状**：csdiy 是完美的脚手架，但**没有用 csdiy 造出任何真实产品**。
**根因**：csdiy 的全部激励都是"建好基础设施"，没有"用基础设施造产品"的机制。
**对策**：
1. 用 tinyllm + tinyrag + tinyvector + csdiy 自己的 28k 索引，造一个**csdiy 学习助手 App**（自己用的）
2. 这一个产品就能验证：tinyllm 是否真的能跑 / RAG 是否真的有用 / 我是否真的能 ship 一个东西

## 八、机会成本思考（v2.0 重审）

**问题**：花在 csdiy 的时间，如果花在别处，会怎样？

| 如果花在... | 可能的收益 | 比较（v2.0 视角） |
|------------|-----------|------|
| 造一个真实开源项目 | GitHub stars / 简历 / 真实用户反馈 | **> csdiy 扩张**（v1.0 结论仍成立）|
| 参与开源 contribution | 真实协作 / Socialization | **> csdiy 扩张** |
| 写博客 / 技术分享 | 影响力 / 反馈 / 费曼输出 | **≈ csdiy**（csdiy 本身已是费曼输出）|
| 做自由职业项目 | 钱 / 真实问题 / 经验 | **> csdiy（经济上）** |
| csdiy 内部深化（不扩张） | 把现有 30k 行精加工真正消化 | **v2.0 首要任务** |
| csdiy | 系统化知识 / 个人参考库 | **基础设施已完成** |

**v2.0 结论**：csdiy 的**建设阶段已完成**（v2.0 = 基础设施 95% 完成 + 产出 30%）。**下一步必须切换模式**：
- 不再扩张（停止新增 tiny* / source-reading）
- 转向**消化**（用 feynman.py + daily.py 把 30k 行精加工吃透）
- 同时**产出**（开源 1 个 tiny* + 给上游提 1 个 PR + 用 tinyllm 造 1 个真实工具）
