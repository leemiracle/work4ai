> 每张卡：**正面**=真实问题/场景，**背面**=一句话本质 + 关键命令/公式 + 易记例子。

---

## 一、系统 / 底层

### 1. 进程 vs 线程 vs 协程，到底差在哪？

**本质**：谁调度它 + 是否共享地址空间。
- 进程：内核调度，独立地址空间（独立页表），切换要换页表+flush TLB，最重。
- 线程：内核调度，共享进程地址空间，切换不换地址空间，中等。
- 协程：**用户态**调度（不进内核），只保存寄存器+栈指针，纳秒级，最轻。

**例子**：Go 的 goroutine 就是 M:N 协程，一个 OS 线程上跑几万个；pthread_create 创建的是内核线程。

---

### 2. 虚拟内存：每个进程都用 0x7fff… 地址，为什么不会撞？

**本质**：虚拟地址经 **MMU + 页表** 映射到不同物理页，每个进程有独立页表。
- 进程 A 的 0x400000 → 物理 0x1000
- 进程 B 的 0x400000 → 物理 0x5000

**关键**：隔离靠的是「每进程一套页表」，不是地址不重叠。

---

### 3. fork 之后子进程有哪些隐藏的坑？

**本质**：fork 只复制调用线程，共享已打开的 fd 偏移量。
- 坑1：子进程不继承其他线程（多线程 fork 后只剩调用线程）。
- 坑2：父子共享文件描述符的**文件偏移量**，互相干扰写入位置。
- 坑3：子进程继承了父进程的 malloc 锁状态，**只能调 async-signal-safe 函数**，否则可能死锁。

**类比**：fork 不是「复制整个房子」，是「复制一张地图，房子里的东西还是共享的」。

---

### 4. 僵尸进程（Zombie）怎么来的？怎么清？

**本质**：子进程退出后父进程**没调 wait/waitpid**，内核保留进程表项（PID + 退出状态）等父回收。
- 现象：`ps` 看到 `<defunct>`，kill 不掉（已经死了，只是没收尸）。
- 危害：耗尽 PID（系统 PID 有限，默认 32768）。
- 清理：`kill -9 父进程` 或让父进程 `signal(SIGCHLD, SIG_IGN)`。

**类比**：孩子死了但家属不肯签死亡证明，户籍上还占着名额。

---

### 5. 缺页中断（Page Fault）到底有多贵？

**本质**：访问的虚拟页不在物理内存 → 陷入内核 → 分配物理页（可能触发磁盘 IO）。
- 软缺页（页在内存只是没建立映射）：~1-2 μs
- 硬缺页（要从磁盘/swap 读）：~10-100 μs，比内存访问（~100ns）**慢 100-1000 倍**。

**实测**：程序顺序扫描大数据比随机访问快几倍，就是缺页率差异。

---

### 6. 为什么总说「CPU 缓存友好性」？顺序 vs 随机访问差多少？

**本质**：缓存行（cache line）64 字节，预取和局部性让顺序访问命中率高。
- L1 命中 ~1ns，L3 ~10ns，内存 ~100ns。
- 随机访问链表：每次都可能 cache miss，比连续数组慢 **10-50 倍**。

**例子**：遍历 `int[1000][1000]`，按行遍历比按列遍历快几倍（列遍历每次跨 4KB 缓存行）。

---

### 7. 大端小端（Endianness）什么时候会咬人？

**本质**：多字节类型（int/float）在内存中的字节序。x86/ARM **小端**（低字节在低地址），网络字节序/Java/**大端**。
- 咬人场景：跨机器传二进制结构体、解析网络协议、读文件二进制头。
- 必须用 `htonl/ntohl`（C）或 `ByteBuffer.order(BIG_ENDIAN)`（Java）。

**例子**：`0x01020304` 小端存为 `04 03 02 01`，大端机器直接读会变成 `0x04030201`。

---

### 8. 结构体对齐（padding）：为什么 sizeof 比字段总和大？

**本质**：CPU 要求访问对齐地址（如 int 必须 4 字节对齐），编译器在字段间插入 padding。
```c
struct { char a; int b; }  // sizeof = 8 不是 5（a 后补 3 字节）
```
- 危害：跨平台二进制协议对齐不一致 → 数据错位；ARM 上未对齐访问可能直接 segfault。
- 手段：`#pragma pack(1)` 强制紧凑（牺牲性能），或手动重排字段（大字段在前）。

---

### 9. 系统调用（syscall）为什么那么贵？

**本质**：用户态→内核态切换成本：保存用户寄存器、切换内核栈、权限检查、返回时恢复。
- 一次 syscall ~1-2 μs，而普通函数调用 ~1ns，**慢 1000 倍**。
- 罪魁：`gettimeofday`、频繁 `read` 小数据、`printf` 频繁 flush。

**优化**：批量（readv/writev）、缓冲（stdio）、vDSO（时间相关调用不真切换）。

---

### 10. 零拷贝（zero-copy）到底省了什么？

**本质**：传统 `read + write` = 4 次上下文切换 + 4 次拷贝（2 次 CPU 拷贝 + 2 次 DMA）。
- `sendfile()`：数据全程在内核态，**0 次 CPU 拷贝 + 2 次上下文切换**。
- `mmap`：省掉 read 的一次 CPU 拷贝。

**例子**：Kafka、Nginx 用 sendfile 传文件，吞吐量提升数倍。

---

## 二、网络

### 11. TCP 三次握手为什么不是两次？

**本质**：两次握手无法防止**历史重复连接**（已失效的旧 SYN）被当成新连接；也无法让双方都确认「对方的收发能力正常」。
- 第三次 ACK 证明：客户端确实收到了服务端的 SYN+ACK（确认服务端能收）。
- 类比：A 打电话给 B：「你能听到吗？」B：「能，你呢？」A：「能。」——少了最后一句 B 不知道 A 是否真听到。

---

### 12. TIME_WAIT 堆积怎么办？

**本质**：主动关闭方进入 TIME_WAIT 等 **2MSL**（确保最后 ACK 到达 + 旧报文消亡），高并发短连接服务端会堆积。
- 解决：
  - `SO_REUSEADDR`（复用 TIME_WAIT 端口）
  - 让**客户端**主动关闭（服务端少堆积）
  - 调 `net.ipv4.tcp_max_tw_buckets` / 用长连接池
- **不要**盲目 `tcp_tw_reuse=1`（NAT 环境有风险）。

---

### 13. 为什么要用 Nagle 算法？什么时候要关？

**本质**：Nagle 把小包攒成大包发，减少网络包数量；但和**延迟 ACK** 叠加会导致 ~40ms 延迟。
- 该开：大文件传输、telnet（省包）。
- 该关（`TCP_NODELAY`）：Redis/MySQL 请求-响应、交互式游戏——小包延迟敏感。
- Redis 官方客户端默认 `TCP_NODELAY`。

---

### 14. HTTP/2 多路复用解决了什么问题？

**本质**：HTTP/1.1 一个连接一次只能处理一个请求（队头阻塞），HTTP/2 在**一个 TCP 连接**上用二进制帧交错多个 stream，并行不阻塞。
- 解决了 HTTP 级队头阻塞（但 TCP 层丢包仍会阻塞所有 stream）。
- 省去了「为了并发开 6-8 个 TCP 连接」的握手开销。

**HTTP/3 (QUIC)** 进一步把多路复用做到 UDP 层，彻底消灭 TCP 队头阻塞。

---

### 15. 为什么用 epoll 不用 select？

**本质**：
- `select`：每次调用要把所有 fd 拷贝到内核 + 内核 O(n) 轮询所有 fd + 有 **1024 个 fd 上限**。
- `epoll`：内核维护就绪链表，`epoll_wait` 只返回**就绪的 fd**，O(1)；用红黑树管理 fd 无上限。

**例子**：10 万连接只有 100 个活跃，select 要轮询 10 万次，epoll 只返回 100 个。

---

### 16. CLOSE_WAIT 堆积是谁的锅？

**本质**：**应用层 bug**——收到对方的 FIN 后，自己没调 `close()`（连接泄漏）。
- 对比：TIME_WAIT 是主动关闭方的正常状态，CLOSE_WAIT 是被动方**该关没关**。
- 排查：`netstat -an | grep CLOSE_WAIT`，找代码里哪个连接没释放（finally 漏 close、异常未处理）。

---

### 17. MTU 和 MSS 有什么区别？

**本质**：
- **MTU**（链路层）：一个以太网帧最大多少字节，默认 **1500**。
- **MSS**（TCP 层）：一个 TCP 报文段最多携带多少**数据**，= MTU − IP头(20) − TCP头(20) = **1460**。
- 意义：MSS 协商让 TCP 不超过 MTU，**避免 IP 分片**（分片丢一片全丢，效率低）。
- 巨帧（Jumbo Frame）MTU=9000，用于数据中心内部。

---

### 18. 长连接为什么还需要心跳？

**本质**：NAT 网关/防火墙会清理**空闲**连接表项（通常 5 分钟），断了你不知道，下次写就失败。
- TCP KeepAlive 默认 2 小时太长，**应用层自己发心跳**（如 30s 一次 ping）。
- 双重作用：保活 + 检测对端是否真死了（半开连接）。

---

### 19. TCP 粘包/拆包怎么拆？

**本质**：TCP 是**字节流**，没有「消息边界」，应用层必须自己定义边界。
- 方案1：**定长消息**（每条固定 N 字节）。
- 方案2：**长度前缀**（先读 4 字节长度，再读对应数据）——最常用。
- 方案3：**分隔符**（如 HTTP 的 `\r\n`，有问题：数据含分隔符要转义）。

**例子**：大多数 RPC 协议用「magic + 长度 + body」。

---

### 20. TLS 握手到底有多贵？

**本质**：
- TLS 1.2：**2-RTT** 握手 + 非对称加密计算（RSA/ECDHE），首次连接延迟高。
- TLS 1.3：**1-RTT**，甚至 0-RTT（Session Resumption，有重放风险）。
- 优化：Session Ticket 复用、HTTP/2 多路复用省连接、OCSP Stapling。

**实测**：一个 HTTPS 请求比 HTTP 多 ~100-300ms（冷启动），复用后几乎无差。

---

## 三、数据库

### 21. MySQL 为什么用 B+ 树而不是 B 树/红黑树？

**本质**：磁盘 IO 是瓶颈，B+ 树**非叶节点不存数据**（只存索引），扇出极大 → 树更矮 → IO 次数少。
- B+ 树 3-4 层就能存千万级数据（每层可上千指针）。
- 红黑树二叉，存千万数据要 ~23 层 = 23 次磁盘 IO。
- B 树非叶节点也存数据，扇出小，树更高。
- 额外：B+ 树叶子**链表相连**，范围查询高效。

---

### 22. 索引为什么突然失效了？（索引失效八大场景）

**本质**：优化器决定不用索引，通常是写法让它**没法走索引**或**估算全表扫更快**：
1. 函数操作列：`WHERE YEAR(date)=2024`（→ 改 `date >= '2024-01-01'`）
2. 隐式类型转换：列是 varchar 但 `WHERE phone = 13800138000`（数字）
3. 最左前缀不满足：联合索引 `(a,b,c)` 查 `WHERE b=1`
4. `LIKE '%xxx'` 前缀模糊
5. `OR` 连接非索引列
6. `!=` / `NOT IN` / `IS NOT NULL`
7. 联合索引中间列用了范围
8. 优化器估算全表扫成本更低（数据量小或统计信息过期）

---

### 23. 事务隔离级别：幻读到底怎么解决？

**本质**：
| 级别 | 脏读 | 不可重复读 | 幻读 |
|------|------|-----------|------|
| RU | ✓ 有 | 有 | 有 |
| RC | ✗ | 有 | 有 |
| RR（MySQL 默认） | ✗ | ✗ | MVCC+**间隙锁**解决 |
| Serializable | ✗ | ✗ | ✗ |

- MySQL InnoDB 在 **RR** 级别用 MVCC（快照读）+ 间隙锁（当前读 `SELECT ... FOR UPDATE`）解决幻读。
- 幻读 = 同一事务内两次查询，**行数**变了（别人 INSERT 了新行）。

---

### 24. MVCC 一句话怎么说？

**本质**：每行数据带**版本号/事务ID**，读事务只看自己**开始时的快照**（不改不加锁），写才加行锁 → **读不阻塞写，写不阻塞读**。
- InnoDB：每行有 `trx_id`（最近修改它的事务），undo log 链存历史版本。
- 快照读（普通 SELECT）走 MVCC，当前读（UPDATE/FOR UPDATE）读最新+加锁。

---

### 25. SELECT 为什么慢？EXPLAIN 怎么读？

**本质**：看 EXPLAIN 关键列：
- `type`：访问类型，**ALL = 全表扫**（最差），`ref/eq_ref` 才算走索引，`const` 最优。
- `key`：实际用的索引（≠ `possible_keys`，可能是 NULL 没用）。
- `rows`：估算扫描行数（越小越好）。
- `Extra`：`Using filesort`（额外排序）、`Using temporary`（临时表）都是坏信号；`Using index`（覆盖索引）是好信号。

**口诀**：type 看有没有 ALL，rows 越小越好，Extra 别有 filesort/temporary。

---

### 26. 主从延迟（replication lag）怎么来的？怎么治？

**本质**：
- 5.7 之前从库**单线程**回放 binlog，主库多线程写，从库追不上。
- 大事务（一次删百万行）回放慢。
- 网络瓶颈 / 从库机器差。

**治法**：MySQL 5.7+ **并行复制**（基于组提交/写集合）、拆大事务、从库用更好的硬件。监控 `Seconds_Behind_Master`。

---

### 27. 死锁怎么排查？

**本质**：两个事务互相等对方的锁。
- 排查：`SHOW ENGINE INNODB STATUS` → 看 `LATEST DETECTED DEADLOCK`，能看到两个事务各持有/等待哪个锁。
- 预防：**固定加锁顺序**（如都按主键升序）、**小事务快提交**、降低隔离级别。
- InnoDB 默认自动检测死锁并**回滚代价小的事务**（不会一直卡死）。

---

### 28. 数据库连接池开多大才对？（反直觉）

**本质**：**不是越大越好**，连接太多反而因上下文切换变慢。
- 公式（HikariCP 官方）：`pool_size = (核心数 × 2) + 磁盘数`
- 原理：CPU 密集时线程多了反而争抢；IO 等待时才需要多一点。
- 实测：PostgreSQL 文档实验，50 连接比 100 连接吞吐高 30%。

---

### 29. redo log 和 undo log 分别干嘛？

**本质**：
- **redo log**（重做日志）：记录「数据页**修改后**的值」→ 保证**持久性**（crash 后能恢复）。WAL（先写日志再改数据页）。
- **undo log**（回滚日志）：记录「修改**前**的值」→ 保证**原子性**（回滚）+ 支撑 **MVCC**（历史版本）。

**口诀**：redo 保持久（崩了能恢复），undo 保回滚 + MVCC。

---

### 30. 什么时候该分库分表？

**本质**：单表/单库撑不住时，**不要过早**。
- 触发点（经验值，非绝对）：
  - 单表数据量 **> 1000 万**且 B+ 树变 4 层、查询变慢。
  - 单库**写 QPS** 到瓶颈（MySQL 单机 ~几千-1万写）。
  - 单机磁盘/内存到瓶颈。
- 代价：跨库 JOIN 难、分布式事务难、全局唯一 ID 要单独方案。
- 先尝试：**垂直拆分**（按业务）→ **读写分离** → **水平分表**（按 hash/range）。

## 四、并发 / 分布式

### 31. 互斥锁 vs 信号量 vs 条件变量，什么时候用哪个？

**本质**：
- **互斥锁（mutex）**：保护临界区，**同一时刻只允许 1 个**进入。场景：修改共享变量。
- **信号量（semaphore）**：计数器，允许 **N 个**并发。场景：限流 N 个连接、生产者-消费者空位。
- **条件变量（condvar）**：等待「**条件成立**」，必须配合 mutex。场景：队列非空才消费。

**类比**：mutex=单人厕所门锁；信号量=停车场剩余车位；条件变量=取号排队等叫号。

---

### 32. CAS 是什么？ABA 问题怎么破？

**本质**：`Compare-And-Swap(addr, expected, new)` 原子操作——值==expected 才改成 new，否则失败重试。
- ABA 问题：值 A→B→A，CAS 以为没变过，实际变过两次。
- 破法：加**版本号**（`CAS(addr, expected, version, new, version+1)`），Java 用 `AtomicStampedReference`。

**例子**：转账，余额 100→扣 50（变 50）→存 50（变 100），另个线程 CAS 看到还是 100 会误判。

---

### 33. Raft 选举一句话？

**本质**：节点随机超时（150-300ms）**先变成 Candidate**，给自己投票并向其他节点要票，**获得多数票**就当 Leader。
- 防脑裂：必须**多数派**同意才能当选，分区时少数派那侧选不出 leader。
- Leader 心跳：周期发 AppendEntries 续约，follower 超时就重新选举。
- 一句话：**随机超时触发选举 + 多数票当选 + 心跳续约**。

---

### 34. CAP 三选二，到底选 CP 还是 AP？

**本质**：分区（P）必然存在，只能在 **C（一致性）** 和 **A（可用性）** 间选：
- **CP**（如 ZooKeeper、etcd、HBase）：分区时**拒绝写**保证强一致。适合配置中心、选主、金融账务。
- **AP**（如 Cassandra、DynamoDB、Eureka）：分区时**各自接受写**，事后异步修复。适合社交、购物车、点赞计数。
- 没有完美的 CA 分布式系统（除非单机）。

---

### 35. 幂等怎么做？（重复请求结果不变）

**本质**：让重复执行产生相同结果。四种手段：
1. **唯一键约束**（数据库层兜底，重复插入报错）。
2. **Token 机制**（请求前先领 token，用一次作废）。
3. **状态机**（只允许合法状态流转，重复请求到同一状态被拒）。
4. **乐观锁版本号**（`UPDATE ... WHERE version=x`）。

**例子**：支付接口，订单号做唯一键，重复点支付第二次直接返回「已支付」。

---

### 36. 分布式锁有哪些坑？

**本质**：要同时满足**互斥 + 不会死锁 + 容错**，三个全满足很难。
- Redis `SETNX + 过期`：坑=锁过期但业务没完（别人拿到锁）→ 用看门狗续期（Redisson）。
- Redlock（多节点多数派）：Martin Kleppmann 质疑其正确性（GC 停顿/时钟漂移）。
- ZooKeeper 临时顺序节点：最可靠，但性能低。
- 终极坑：客户端 GC Stop-the-World 停了几秒，锁早过期了，醒来还以为持锁 → **fencing token**（每次锁带递增序号，旧 leader 写被拒）。

---

### 37. 消息队列：至少一次 / 最多一次 / 恰好一次？

**本质**：
- **至少一次**（at-least-once）：可能重复（消费者 ack 丢失会重投），**必须幂等**。
- **最多一次**（at-most-once）：可能丢（发完不等确认），允许丢的场景用（如日志）。
- **恰好一次**（exactly-once）：极难，靠「幂等生产 + 幂等消费 + 事务消息」**模拟**（Kafka 0.11+ 事务、RocketMQ）。

**实践**：大多数系统是至少一次 + 业务幂等，而不是真恰好一次。

---

### 38. 限流算法：令牌桶 / 漏桶 / 滑动窗口怎么选？

**本质**：
- **令牌桶**：匀速发令牌，桶可累积 → **允许突发**（攒满桶一次用光）。适合允许偶尔高并发（API）。
- **漏桶**：请求匀速漏出 → **严格匀速**，不允许突发。适合保护下游（如调第三方）。
- **滑动窗口**：精确统计窗口内请求数，无临界突刺（固定窗口在窗口边界有双倍流量突刺）。

**例子**：Sentinel 用滑动窗口，Guava RateLimiter 用令牌桶，Nginx limit_req 用漏桶。

---

### 39. 一致性哈希解决了什么？为什么要虚拟节点？

**本质**：把节点和 key 都映射到哈希环上，key 顺时针找最近的节点。
- 优势：**增删节点只迁移相邻段数据**（普通取模 hash 会全量迁移）。
- 问题：节点少时数据**倾斜**（某节点分到一大段）。
- 解决：**虚拟节点**（一个物理节点对应 150+ 虚拟节点），数据均匀分布。

---

### 40. 分布式脑裂（Split-Brain）是什么？怎么防？

**本质**：网络分区把集群分成两半，**各自选出 leader**，双方都接收写 → 数据不一致。
- 防法1：**多数派（Quorum）**——写必须过半节点确认（Raft/Paxos），少数派侧选不出 leader 无法写。
- 防法2：**Fencing Token**——每次新 leader 拿到更高序号，旧 leader 的写被存储层拒绝（租约过期）。
- 防法3：**Witness/Stonith**——专门节点仲裁，或直接「射击」故障节点（强制隔离）。

---

## 五、算法 / 数据结构

### 41. 哈希表冲突攻击是什么？怎么防？

**本质**：攻击者构造大量**哈希冲突**的 key，让所有 key 落同一个桶，哈希表退化成链表，查询 O(n) → DoS。
- 经典：2011 年 PHP/Java/ASP 都中招，POST 一堆冲突参数把 CPU 打满。
- 防御：
  - **随机化哈希种子**（Python 3.3+ 默认随机，防预计算）。
  - 冲突链超过阈值**树化**（Java 8 HashMap 链表>8 转红黑树，O(logn)）。

---

### 42. 为什么 Java/C++ 标准库用红黑树而不是 AVL 树？

**本质**：红黑树是**近似平衡**，插入/删除旋转次数 ≤3（AVL 严格平衡旋转更多），适合**频繁增删**场景。
- AVL 树更严格平衡 → 查询略快（高度更低），但增删旋转多。
- 红黑树增删性能更好 → 适合动态数据（HashMap 桶树化、Linux CFS 调度器、epoll）。

**一句话**：AVL 查多写少，红黑树读写均衡。

---

### 43. 跳表（Skip List）vs B+ 树，Redis 为什么用跳表？

**本质**：
- **跳表**：多层概率链表，O(logn) 查询，**实现简单 + 并发友好**（只锁局部节点）。
- **B+ 树**：磁盘友好（扇出大、树矮、IO 少），但并发控制复杂（锁粒度大）。
- Redis ZSET 用跳表：纯内存（不需要磁盘优化）、跳表实现简单、范围操作天然支持、并发不是主要矛盾。

---

### 44. 布隆过滤器（Bloom Filter）什么时候用？

**本质**：空间极省地判断「**可能存在**」或「**绝对不存在**」，有**假阳性**（说有其实没有）无假阴性（说没有就真没有）。
- 适合：缓存穿透防护（先挡掉一定不存在的 key）、海量去重（爬虫 URL）、黑名单初筛。
- 一个误判率 1% 的 BF，1 亿 key 只需 ~120MB。

**注意**：标准 BF 不支持删除（要 Counting BF）；元素越多误判率越高（需预估容量）。

---

### 45. LRU 缓存怎么做到 O(1)？

**本质**：**哈希表 + 双向链表**组合。
- 哈希表：O(1) 查到节点。
- 双向链表：O(1) 把节点移到头部 / 删除尾部（淘汰最久没用）。
- `get(key)`：查哈希表 → 移到头部 → 返回值。
- `put(key)`：更新/插入 → 移到头部 → 超容量则删尾部。

**Java**：`LinkedHashMap` 重写 `removeEldestEntry` 即可；**面试手写**要双向链表+HashMap。

---

### 46. Top-K 问题：用堆还是全排序？

**本质**：
- 全排序取前 K：O(n logn)，浪费（排了后面 n-K 个没用的）。
- **小顶堆（容量 K）**：O(n logK)，遍历一遍，比堆顶大就替换——只维护前 K 大。
- K << n 时，O(n logK) << O(n logn)。

**例子**：10 亿数据找 top 100，堆法 O(n log100)，快排分区法（QuickSelect）平均 O(n) 但不是流式。

---

### 47. 二分查找最常见的边界 Bug？

**本质**：三个坑点：
1. `mid = (left+right)/2` 溢出 → 用 `mid = left + (right-left)/2`。
2. 死循环：`left = mid`（而非 `mid+1`）+ `while(left<=right)` 会卡死 → 找确切值用 `mid±1`。
3. 找「第一个 ≥ target」vs「最后一个 ≤ target」边界条件不同——用 `left < right` + 缩进后检查。

**LeetCode 34**（找第一个和最后一个位置）就是经典边界题，先写对再背模板。

---

### 48. 图的 BFS 和 DFS 什么时候选哪个？

**本质**：
- **BFS**（队列）：找**无权图最短路径**、层序遍历、社交网络「度数」、最近匹配。空间 O(宽度)。
- **DFS**（栈/递归）：**连通性**、拓扑排序、环检测、回溯（全排列/迷宫）。空间 O(深度)。
- 选型：要最短/最近 → BFS；要遍历所有/回溯 → DFS；树深 >> 宽 → BFS 省内存，树宽 >> 深 → DFS 省内存。

---

### 49. Trie（字典树）什么时候才值得用？

**本质**：把字符串按**公共前缀**组织成树，查询 O(L)（L=字符串长度），适合**前缀匹配**场景。
- 值得用：自动补全、拼写检查、IP 路由（最长前缀匹配）、敏感词过滤。
- 不值得：精确查找（哈希表 O(1) 更快）、数据量小（哈希表更省内存）。
- 空间代价：公共前缀少时内存膨胀（每个节点多指针）。

---

### 50. 概率算法：哪些场景可以「跳过」精确？

**本质**：用「**大概对**」换「快/省」，适合海量数据实时场景：
- **蓄水池抽样**：流式数据中等概率抽 K 个（不知总数），O(n) O(K) 内存。
- **HyperLogLog**：基数计数（UV），12KB 估 10 亿级基数，误差 0.81%。
- **Count-Min Sketch**：频率统计，省内存，只多不少（高估）。
- **跳表**：概率层级代替平衡树旋转。

**原则**：能容忍误差 + 数据量大 + 要实时 → 用概率结构。

## 六、调试 / 工程

### 51. segfault 排查三步走？

**本质**：
1. **拿 core + backtrace**：`ulimit -c unlimited` 开 core，`gdb ./程序 core`，`bt full` 看栈。
2. **定位非法地址**：看崩溃行，查空指针 / 数组越界 / use-after-free / 栈溢出。
3. **工具兜底**：`valgrind` 查内存错误，或编译加 `-fsanitize=address`（ASan，比 valgrind 快）。

**常见根因**：90% 是空指针解引用、写越界、释放后使用。

---

### 52. 内存泄漏怎么定位？

**本质**：分配了没释放，长跑程序内存只涨不降。
- C/C++：`valgrind --leak-check=full` 看 `Definitely lost`，或 `AddressSanitizer`。
- Java：`jmap -dump` 导 heap → MAT/VisualVM 看「支配树」找最大对象 → 查 GC Root 引用链。
- Go：`pprof` 的 heap profile，对比两次快照看增长。
- 容器：`top`/`docker stats` 看常驻内存（RSS）持续涨。

---

### 53. 性能优化的正确方法论？（别瞎猜）

**本质**：**先测量再优化**，用 USE/RED 框架定位瓶颈，火焰图找热点。
1. **USE 模型**（资源层）：每个资源看 Utilization（利用率）/ Saturation（饱和度）/ Errors（错误）。
2. **RED 模型**（服务层）：Rate（请求量）/ Errors（错误率）/ Duration（延迟）。
3. **火焰图**：CPU 时间花在哪，找最宽的「平台」。
4. 优化**最热**的那一个瓶颈，再测量验证（Amdahl 定律：优化非瓶颈没用）。

**反例**：「我觉得这里慢」→ 改了 → 没快 → 因为瓶颈在别处。

---

### 54. 日志到底该记什么？不该记什么？

**本质**：日志是为了**事后排查**，要能还原「谁在什么时间做了什么，结果如何」。
- **该记**：`trace_id`（串联一次请求）、关键参数、返回结果、异常堆栈（带上下文）、耗时。
- **不该记**：密码/Token/身份证（脱敏或打码）、大对象全文、高频无价值信息。
- 级别：ERROR（出错了要告警）/ WARN（可恢复异常）/ INFO（关键业务节点）/ DEBUG（排查用）。
- 结构化：JSON 格式方便 ELK 查询，别用 `printf` 拼字符串。

---

### 55. Code Review 重点抓什么？（别抠风格）

**本质**：抓**人容易犯且 lint 抓不到**的错：
1. **边界条件**：空值、负数、越界、并发竞态。
2. **错误处理**：异常被吞了？返回值没检查？资源没释放（try-with-resources）？
3. **安全**：SQL 注入、XSS、权限校验、敏感信息泄漏。
4. **设计**：是否过度设计、是否符合现有模式、是否有测试。
- **别抓**：格式（lint 管）、命名风格（团队规范管）、个人偏好。

---

### 56. 单元测试 vs 集成测试，边界在哪？

**本质**：
- **单元测试**：测**单个函数/类**，mock 掉外部依赖，快（毫秒级），覆盖各种分支。
- **集成测试**：测**多个组件协作**（如 service + 数据库），慢（秒级），验证「连起来能跑」。
- 金字塔：**大量单测（70%）+ 适中集成测（20%）+ 少量 E2E（10%）**。
- 反模式：只有 E2E（又慢又脆，挂了不知道哪坏）；只测 happy path（不测边界/异常）。

---

### 57. panic 还是 error？什么时候让程序崩？

**本质**：
- **error（预期错误）**：业务上的正常失败（文件不存在、网络超时）→ 必须处理/返回，**不该崩**。
- **panic（不可恢复）**：程序逻辑错误（不变量被破坏、空指针该不可能）→ 崩了让上层 recover 或重启。
- Go：`error` 是值必须检查；`panic` 像 exception 但只用于真异常。
- Rust：`Result<T,E>` 处理预期错误；`panic!` 用于「这绝不该发生」。
- **原则**：能恢复的错误用 error，编程 bug 用 panic（fail fast）。

---

### 58. 灰度发布怎么做？

**本质**：先让**一小部分流量**用新版本，验证没问题再放量，**降低爆炸半径**。
- 流量切分：按用户 ID hash（5%→10%→50%→100%）、按地域、按机型。
- 金丝雀发布：先放 1 台机器（最危险的一台先上）。
- 蓝绿/红黑：两套环境一键切换，出问题秒级回滚。
- 关键：**可观测**（灰度期间监控核心指标）+ **可回滚**（10 分钟内能退回旧版）。

---

### 59. 为什么说「回滚比修复更重要」？

**本质**：线上故障的**第一目标是恢复服务**，不是找 bug。边查边修会让你越改越乱。
- 黄金法则：**先止血（回滚）→ 再诊断 → 再修复**。
- 前提：每次发布**必须可回滚**——代码回滚 + 数据库变更可逆（删列前先改名、加列设默认值、不在线上做破坏性 DDL）。
- 反例：发了个带 bug 的版本，不回滚非要 hotfix，结果 fix 引入新 bug，雪上加霜。

---

### 60. 监控三件套是什么？（Metrics / Logging / Tracing）

**本质**：三件套互补，缺一不可：
- **Metrics（指标）**：聚合数字（QPS、延迟 P99、错误率），**发现异常**，用 Prometheus + Grafana。
- **Logging（日志）**：离散事件记录，**定位具体问题**，用 ELK/Loki。
- **Tracing（链路追踪）**：一次请求跨服务的调用链，**找慢在哪一环**，用 Jaeger/Zipkin。

**口诀**：Metrics 告诉你「**坏了**」，Logging 告诉你「**哪坏了**」，Tracing 告诉你「**为什么坏**」。
