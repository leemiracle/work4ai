# 抽象

> 抽象是「主动忽略细节以保留可迁移结构」的过程——它不是终点，而是数学赖以攀爬的阶梯。

## 出现在哪些教材/阶段

| 教材 / 来源 | 阶段 | 抽象的脸孔 |
| --- | --- | --- |
| LADR《Linear Algebra Done Right》| 阶段 1（本科核心） | 向量空间公理：把 $\mathbb{R}^n$ 抽象成满足 8 条公理的任意集合 |
| Dummit & Foote《Abstract Algebra》| 阶段 2（研究生基础） | 群/环/域/模：把数与运算抽离成「结构 + 公理」 |
| 01-Grothendieck（rising sea）| 阶段 3（研究方向） | 范畴与函子：对象本身不重要，对象之间的关系才重要 |
| Curry-Howard（类型论）| 跨阶段工具 | 命题即类型，证明即程序——抽象在逻辑与计算之间架桥 |
| 软件工程实践 | 从业者透镜 | 接口 / 抽象类 / 设计模式：隐藏实现，暴露契约 |

## 多重表征并列对照

| 视角 | 抽象掉什么 | 保留什么 | 核心产物 |
| --- | --- | --- | --- |
| 1. 代数结构抽象 | 具体元素的含义 | 运算满足的公理 | 群、环、域、模 |
| 2. 范畴抽象 | 对象内部构造 | 对象之间的态射 | 函子、自然变换、Yoneda 引理 |
| 3. 类型抽象 | 数据的具体取值 | 类型构造与组合规则 | 依赖类型、参数化多态 `List<T>` |
| 4. 软件接口抽象 | 实现细节 | 行为契约 | 接口、抽象类、设计模式 |

### 1. 代数结构抽象（抽象代数）

把「整数加法」「矩阵乘法」「几何旋转」统统抽象成「群」——只要满足封闭、结合、有单位元、有逆元四条公理，就享有同一套定理（Lagrange 定理、同构定理……）。

一个具体例子：研究 $\mathbb{Z}$ 的加法和研究 $n \times n$ 可逆矩阵的乘法看似无关，但都是「群」。同构定理告诉我们：任何群 $G$ 与其正规子群 $N$ 都能生成商群 $G/N$——这条定理对整数模 $n$、对矩阵的相似关系、对几何对称性都同时成立。

LADR 的向量空间公理是同一类抽象：函数、多项式、矩阵看似风马牛不相及，但都满足那 8 条公理，于是线性无关、基、维数等概念一齐成立。**抽象的真正收益：证一次，处处适用。**

### 2. 范畴抽象

更进一步：连「对象是什么」都不关心，只关心「对象之间的关系」即态射（morphism）。
- **函子（functor）**：在范畴之间搬运结构（例如把每个群映成一个集合，同时把群同态映成函数）；
- **自然变换（natural transformation）**：函子之间的态射——两个函子之间的「一致变形」；
- **Yoneda 引理**：一个对象由它与其他对象的关系完全决定，而非由它自身的内部构造决定。

常见的范畴有 $\mathbf{Set}$（集合）、$\mathbf{Grp}$（群）、$\mathbf{Top}$（拓扑空间）——同一个「函子」概念在它们之间自由穿梭。

Grothendieck 的「rising sea（涨潮）」隐喻——不要硬凿问题，而要把周围的数学海面整体抬升，让问题自然浮出解。Eugenia Cheng 一句话概括：「范畴论是数学的数学」。

### 3. 类型抽象（类型论）

依赖类型（dependent type）、参数化多态（parametric polymorphism）、抽象类型——把「值的抽象」升级为「类型的抽象」。

`List<T>` 不关心 `T` 是 int 还是 string，只关心「列表」这一结构本身。一个更深刻的例子：恒等函数 `id : ∀T. T → T`，凭参数化多态对**所有**类型 $T$ 都成立——这本身就是一条关于类型的「定理」（「free theorem」）。

Curry-Howard 同构告诉我们：**类型 = 命题，程序 = 证明**，于是类型系统成为「轻量级形式证明」——编译器每通过一次类型检查，就相当于完成了一次小规模的形式化验证。

### 4. 软件接口抽象（工程实践）

接口（interface）、抽象类（abstract class）、设计模式（design pattern）——工程师每天都在做抽象：API 隐藏实现，只暴露契约。

例如 Python 的 `collections.abc.Sequence`：它不关心底层是 list、tuple 还是自定义类，只要求实现 `__getitem__` 与 `__len__` 两个方法，于是所有序列自动享有 `index`、`count` 等默认实现——这与「满足群公理就享有同构定理」是同构的思维。

作为从业者透镜下的「架构师」角色，可建立两层直觉类比：
- **公理 ≈ 接口契约**：定义「可被合法调用」的最小规则；
- **范畴论 ≈ 设计模式**：跨具体场景的、可复用的结构模板。

## 它们的统一与差异

**统一**：四种视角都是「忽略细节、保留结构」。代数忽略元素含义、范畴忽略对象内部、类型忽略取值、接口忽略实现——四者本质上是同一种思维操作在不同领域的投影。这就是为什么一个训练有素的数学家转行做软件架构会格外顺手：他已经在用同一套抽象工具。

**差异**：抽象的对象层级不同，可排成一条「抽象阶梯」：

$$
\text{具体对象} \;\to\; \text{共性} \;\to\; \text{模式} \;\to\; \text{结构} \;\to\; \text{元结构}
$$

- 代数结构抽象：停留在「结构」层；
- 范畴抽象：进入「元结构」层（研究结构本身的结构）；
- 类型抽象与软件接口：可停留在任一层，是工程中最常被实践的两层。

> 阶梯越往上，「证一次，处处适用」的红利越大，但「与直觉的距离」也越远——这正是初学范畴论时普遍感到抽象空洞的根源。

Eugenia Cheng 提醒：**「抽象不是目的，而是过程」**——抽象化的价值在于让原本看不见的相似性显形，而非建造一座离地越来越远的空中楼阁。

## 跨学科这张面孔

| 学科 / 角色 | 抽象扮演的角色 | 直觉锚点 |
| --- | --- | --- |
| 软件架构师 | 公理 ≈ 接口契约 | 把「正确性约束」写成可被编译器/团队遵守的规则 |
| 编译器 / 类型系统 | 类型系统 = 轻量级证明 | 用类型在编译期消灭整类 bug |
| 人工智能 / 机器学习 | 抽象 = 泛化（generalization） | 模型在训练分布之外的迁移能力，本质是抓住了抽象结构 |
| 物理学 | 对称性抽象成守恒律（Noether） | 抽象的群作用对应具体的守恒量 |

抽象因此不是某一门学科的专利，而是**所有理性学科共用的一把钥匙**。

值得注意的是：跨学科的抽象类比也会**失真**——例如把「公理」直接等同于「接口」会忽略公理的「无矛盾性/完备性」这种逻辑约束，而接口通常只关心语法层面。**好的类比是脚手架，而非真理。**
