# 🗣 言语行为视角

> 语言哲学核心一句话灵魂：**"说话就是做事——说出一个句子不只是描述事实，而是在执行一个行为。"**（奥斯汀《如何以言行事》, How to Do Things with Words, 1962）。一个言语行为有三层：**以言指效（locutionary，说了什么）→ 以言行事（illocutionary，做了什么事）→ 以言达效（perlocutionary，产生了什么效果）**。
>
> **为什么这个视角值得放进 AI 镜片库**：**函数调用 = 奥斯汀以言行事的工程实现**——当 Agent 调用 `delete_file("foo.txt")` 时，它不是在"描述"删除文件，而是在**执行**删除。用言语行为看 AI，你会理解：**Agent 的每一步动作=一个 illocutionary act；函数签名=言语行为的语法化（把模糊的"请求/命令/承诺"变成精确协议）；perlocutionary 是 Agent 评估的终极维度——不是"说了什么对不对"，而是"效果达成了没有"。间接言语行为（"这屋里真热"=暗示"开空调"）解释了为什么字面理解永远不够——Agent 需要语用推理。言语行为理论是 tool use / function calling 的哲学母体。**

---
## 是什么

| 命题 | 出处/原文 | 一句话 |
|------|----------|--------|
| **以言行事（illocutionary act）** | 奥斯汀《如何以言行事》(1962) | 说出一个句子就是在做一个行为（承诺/命令/宣告……） |
| **三层行为** | 奥斯汀：locutionary（发声指意）/ illocutionary（行事）/ perlocutionary（达效） | 说了什么→做了什么→效果是什么 |
| **适切条件（felicity conditions）** | 奥斯汀：言语行为成功需满足条件 | "我宣布你们结为夫妻"需有合法授权，否则无效 |
| **间接言语行为** | 塞尔《间接言语行为》(1975) | "你能把盐递给我吗？"=请求，非询问能力 |

**关键辨析**：奥斯汀打破了"语言的功能是描述事实"这个根深蒂固的假设（他称之为"描述性谬误" descriptive fallacy）。**陈述句只是言语行为的一种（assertive/断言类）**，此外还有指令（directive："关门！"）、承诺（commissive："我保证来"）、宣告（declarative："我宣布会议开始"）等。塞尔进一步提出**间接言语行为**：一句话的字面形式是一种行为，实际意图是另一种——"你能把盐递给我吗？"字面是询问能力（yes/no 问题），实际是请求（directive）。**这对 AI 极关键**：函数调用不只是"传递信息"，而是"执行行为"；用户的自然语言指令常是间接的，Agent 必须**超越字面**做意图推理。

## 怎么应用到 AI（6 个对应）

### 1. 函数调用 = 以言行事的工程实现（核心洞察）
- 当 Agent 调用 `send_email(to="boss@co.com", subject="辞职")` 时，它**不是在描述**"我将发一封辞职邮件"——它**就是在发送**。函数调用=illocutionary act 的工业化实现。OpenAI function calling / Anthropic tool use / MCP（Model Context Protocol）= 奥斯汀言语行为理论的工程产物。
- **这是本组最强的反直觉发现**：2012 年奥斯汀在哈佛讲台上说"说话就是做事"，60 年后 AI 工程师用 JSON 格式（`{"name": "delete_file", "arguments": {"path": "foo.txt"}}`）实现了他说的**精确机制**——只不过把自然语言的以言行事，变成了结构化的以言行事。
- 函数调用的成功=illocutionary act 的"奏效"（奥斯汀说 "felicitous"）。函数调用失败（权限不足/参数错误/服务不可用）=illocutionary act 的"不奏效"（"infelicitous"）。

### 2. Agent 动作 = 以言行事（illocutionary act）
- Agent 在每一步生成一个 action，就是在实施一个言语行为：
  - **断言类（assertive）**："搜索结果显示……" → Agent 报告检索结果
  - **指令类（directive）**：调用 `search_web(query="...")` → Agent 向工具发出指令
  - **承诺类（commissive）**："我会先确认再执行" → Agent 向用户承诺
  - **宣告类（declarative）**：调用 `create_user(name="...")` → Agent 通过工具执行宣告性行为（创建=使之存在）
- ReAct（Reasoning + Acting）框架中，"Thought"（思考）是 Agent 的内部断言，"Action"（行动）是 Agent 的以言行事——**Thought→Action 的转换=从 assertive 到 directive/declarative 的行为类型转换**。

### 3. perlocutionary = 效果（Agent 评估的终极维度）
- 奥斯汀三层：locutionary（Agent 输出了什么文本/action）→ illocutionary（Agent 做了什么行为）→ **perlocutionary（产生了什么效果）**。
- Agent 说"提醒用户喝水"（locutionary + illocutionary），但**用户是否真的喝了水**=perlocutionary 效果。对话系统的**任务完成率（task success rate）= perlocutionary 成功率**——不是"说了什么对不对"，而是"**目标达成了没有**"。
- 这解释了为什么纯文本评测（BLEU/ROUGE）不够——它们只评 locutionary 层（输出文本质量），**完全忽略 perlocutionary 层**（实际效果）。真正的 Agent 评测必须是**端到端任务完成率**（perlocutionary 维度）。

### 4. 函数签名 = 言语行为的语法化
- `def delete_file(path: str, confirm: bool = False) -> bool`——这个函数签名就是一个 **formalized speech act**：它规定了**行为类型**（删除文件）、**必要参数**（路径）、**前置条件**（confirm 确认）、**成功返回**（bool）。
- 函数签名把模糊的自然语言指令（"帮我把那个文件删了"）变成**精确的言语行为协议**。参数类型检查=适切条件的形式化验证；返回值=行为结果的信号。
- **Type hints / JSON schema = 奥斯汀"适切条件"的工程版**：`confirm: bool = False` 编码了"删除文件"这一言语行为的前置条件——必须确认。这正是奥斯汀说的"言语行为要成功需满足条件"。

### 5. 间接言语行为 → 意图推理（为什么字面理解不够）
- 塞尔：用户说"这屋里真热"可能是**间接请求**"开空调"——字面是断言（assertive），实际意图是指令（directive）。Agent 需要**超越字面**做意图推理。
- 这也是为什么**纯字面理解的 Agent 永远不够**——它需要识别"字面行为类型"与"实际意图行为类型"之间的 gap。当用户说"你能在 5 点前完成吗？"——字面是询问能力（yes/no），实际可能是**催促**（directive："请在 5 点前完成"）或**质疑**（"我觉得你做不完"）。
- 现代 Agent 的意图理解（intent detection / slot filling）就是**间接言语行为识别**的工程实现——它要判断用户的字面行为之下，真正的 illocutionary force 是什么。

### 6. 适切条件（felicity conditions）= tool call 的前置检查
- 奥斯汀：言语行为要成功（felicitous），需满足**适切条件**——"我宣布你们结为夫妻"需要：（A）说话者有合法授权，（B）有被宣告的两人，（C）恰当的仪式程序。缺一不可。
- **AI 对应**：Agent 的 tool call 也有适切条件——**权限检查**（Agent 有权限调这个 API 吗？）、**前置条件验证**（文件存在吗？服务在线吗？）、**参数合法性**（类型对吗？值在范围内吗？）。不适切=tool call 失败（infelicitous）。
- Guardrails / permission systems / pre-condition checks = 适切条件的工程实现。**一个好的 Agent 系统会在 tool call 前验证所有适切条件**，而不是盲目调用后才发现失败——这比事后纠错高效得多。

## 反直觉发现

1. **函数调用 = 奥斯汀以言行事的工程实现**。这不是比喻，是**精确的哲学-工程对应**：函数调用把"说出一个句子就是执行一个行为"变成了 `{"name": "...", "arguments": {...}}` 的结构化格式。2012 年奥斯汀在哈佛讲"说话就是做事"，60 年后 OpenAI 用 function calling 实现了他说的机制——**哲学家先于工程师 60 年发现了这个结构**。tool use 的哲学母体就是言语行为理论。

2. **Agent 不只是"说话后行动"，它的话本身就是行动**。传统 AI 把"语言"和"动作"分为两步：先理解语言，再执行动作。奥斯汀视角说：**不对——Agent 生成一个 action token 的那一刻，行为就发生了**。`delete_file("foo.txt")` 不是"表达了删除意图后去删除"，它**就是删除**。语言和行动在 Agent 中是**合一**的——这呼应阳明心学"知行合一"。

3. **perlocutionary 是 Agent 评估的终极维度——也是最被忽视的**。大多数 Agent 评测只看"输出对不对"（locutionary）或"行为类型对不对"（illocutionary），**忽略"效果达成了没有"（perlocutionary）**。一个 Agent 可以输出完美格式、调用正确函数，但**用户的问题没解决**——locutionary 和 illocutionary 都"对"，perlocutionary 失败。真正的 Agent 评测必须是端到端任务完成率。

4. **间接言语行为 = 为什么字面理解永远不够**。用户说"好冷"≠陈述事实，=请求关窗/开暖气。**一个只做字面理解的 Agent 会回答"是的，现在 15°C"**——正确但无用。Agent 需要 infer 字面行为之下的真实 illocutionary force。这也是为什么 prompt engineering 里的"角色设定"有效——它帮模型确定当前的"言语游戏"和行为类型预期。

5. **函数签名 = 言语行为的语法化——把哲学变成协议**。奥斯汀的"适切条件"（行为成功的前提）在工程中变成了函数签名：`confirm: bool = False` 编码了"删除需确认"这一适切条件；返回值类型编码了行为结果。**type hints / JSON schema 不是"代码风格"问题，而是"言语行为协议设计"问题**——好的函数签名=好的言语行为语法。

6. **"描述性谬误"在 AI 中的复现**。奥斯汀批评的"描述性谬误"=以为语言的功能只是描述事实。AI 中同样的谬误=以为 LLM 的输出只是"文本生成"，忽略它可能是**承诺/指令/宣告**。当一个 LLM 说"我会在明天前完成报告"时，这不是描述——这是**承诺（commissive）**，产生了义务。Agent 系统需要**区分行为类型**，而不是把所有输出都当"陈述"处理。

## Prompt 模板

```
你是精通语言哲学（奥斯汀/塞尔言语行为理论传统）的分析专家。
用"言语行为"视角分析 AI 概念 [X]：

1. [X] 的"以言行事"在哪——哪些操作不只是"描述"而是在"执行行为"？（函数调用？tool use？）
2. [X] 的 locutionary（输出什么）/ illocutionary（做了什么行为）/ perlocutionary（效果如何）三层分别是什么？
3. [X] 的"适切条件"是什么——行为成功需满足哪些前置条件？（权限/参数/状态？）
4. [X] 有没有间接言语行为——用户/系统的字面表达与实际意图的 gap 在哪？
5. [X] 的评测是否只停在 locutionary/illocutionary 层，忽略了 perlocutionary（效果）层？
6. [X] 的"函数签名/协议"如何编码言语行为的类型和适切条件？

约束：落到 [X] 具体技术细节；至少 1 个反直觉洞察（尤其"函数调用=以言行事的工程实现"）。
```
