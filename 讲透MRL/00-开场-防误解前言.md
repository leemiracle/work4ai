# 00 · 开场：防误解前言 + MRL 是什么

> **本章不教任何数学**。本章只回答四个问题：①MRL 是什么？②MRL **不是**什么？③为什么需要 MRL？④学完本系列你能做什么？

---

## 1. 一个真实场景

假设你在做端侧 RAG（手机本地知识库）：
- 文档库：10 万条
- 嵌入模型：embeddinggemma-300m，每条文档 → **768 维 float32 向量 = 3072 字节**
- 数据库体积：10 万 × 3072 = **307 MB**
- 每次检索：query 向量与 10 万个 768 维向量算余弦 → **150M FLOPs**

这手机塞得下吗？
- 307 MB 库 + 1.2 GB 模型权重 = 不行，太大了
- 150M FLOPs / 检索 → 中端手机约 100 ms，还行

**怎么缩小库**？三个老办法都有问题：
- **PCA**：要训练投影矩阵，且对非线性结构损失大
- **PQ（乘积量化）**：训练复杂，且召回率掉 10-20%
- **直接砍维度**：768→128 = **断崖式掉点**（标准嵌入模型前 128 维没有特殊意义）

**MRL 的承诺**：如果模型用 MRL 训练过，**直接砍维度前 N 维**，精度几乎不变。

## 2. MRL 是什么——一句话

> **MRL（Matryoshka Representation Learning）是一种训练时损失函数的改造**：让模型在多个嵌套的输出维度上同时学习（如 768/512/256/128/64/32），使得部署时**只取前 N 维**就是有用的嵌入。

**关键词**：
- "训练时"：MRL **不改变模型架构**，不改变推理过程
- "嵌套"：前 32 维 ⊂ 前 64 维 ⊂ ... ⊂ 前 768 维
- "部署时按需截断"：一次训练，部署灵活选维度

## 3. MRL **不是**什么（防误解清单）

### 3.1 MRL **不**让模型变小

```
                模型权重        推理 FLOPs       RAM 占用        输出向量大小
MRL 截断 768→128   完全不变        完全不变         完全不变         ↓ 6×
```

> **铁证**（[04 章实验](04-反直觉实验.md)）：embeddinggemma-300m 在 768 维和 128 维下，**模型文件、加载时间、推理延迟完全相同**。只有输出的向量从 768 个数字变成 128 个。

### 3.2 MRL **不**让推理更快

主干的矩阵乘法还是要算完，**前向 FLOPs 一字节不变**。Sentence Transformers 原话：

> *"training and inference of a Matryoshka model is **not faster**, not more memory-efficient, and not smaller."*

加速只发生在**下游**：
- 检索（点积）：768→128 = 6× 加速
- sqlite-vec 距离计算：6× 加速
- 分类器特征：6× 加速

### 3.3 MRL **不**是量化

| | MRL | 量化 |
|---|---|---|
| 改什么 | 输出向量的**维度** | 输出向量或权重的**精度** |
| 怎么改 | 训练时加 loss | 训练后或训练中映射到低 bit |
| 例子 | 768 维 → 128 维 | float32 → int8 / 1-bit binary |
| 兼容性 | **正交可叠加**（详见 [04 章](04-反直觉实验.md)）| 同 |

### 3.4 MRL **不**是黑科技

实现只需要**几行代码**（详见 [02 章](02-MRL数学.md)、[03 章](03-从零实现.md)）：

```python
# 标准 contrastive loss
loss_full = contrastive(emb[:, :768])

# MRL: 加几个截断维度的 loss 项
loss_mrl = (contrastive(emb[:, :768]) +
            contrastive(emb[:, :512]) +
            contrastive(emb[:, :256]) +
            contrastive(emb[:, :128])) / 4
```

就这么简单。

### 3.5 MRL **不**让所有模型都能截断

只有**用 MRL loss 训练过**的模型才能截断。直接截断非 MRL 模型（如 `bge-small-zh-v1.5`）会**真的损失精度**——除非：
- 用 Matryoshka-Adaptor 后接 MLP 升级（[03 章](03-从零实现.md)）
- 或换用原生 MRL 模型（如 `jina-v5-text-nano` / `embeddinggemma-300m`）

### 3.6 MRL **不**万能——有理论上限

Google DeepMind LIMIT 论文（[arXiv:2508.21038](https://arxiv.org/abs/2508.21038)）证明：**对固定维度 $d$，存在数据集使 embedding 模型无法正确返回所有 top-k 子集**。

| $d$ | 文档数上限（自由优化） |
|---|---|
| 32 | ~500 |
| 128 | ~5,000 |
| 256 | ~30,000 |
| 768 | 170 万 |

**端侧启示**：1 万文档以下，128 维够；10 万文档要 256 维；百万文档必须 512+ 维。

## 4. 为什么需要 MRL——四个真实痛点

### 痛点 1：存储成本

云端 RAG 系统，1 亿文档 × 768 维 × 4 字节 = **300 GB**。MRL 截断到 128 维 → 50 GB，**省 83%**。

### 痛点 2：检索延迟

HNSW 索引下，距离计算是 O(d log N)。768→128 维 → 6× 加速。在 p99 100ms SLA 下，这是"达标"和"不达标"的区别。

### 痛点 3：端侧 RAM

手机 RAG：1 万文档 × 768 维 × 4 字节 = 30 MB（库） + 1.2 GB（模型） = **塞不下**。
MRL 截断到 128 维 + Q4 量化：5 MB（库）+ 300 MB（模型）= **塞下了**。

### 痛点 4：模型选型灵活度

没有 MRL 时，要支持多个维度就要训多个模型（如 768d 一个、128d 一个）。MRL 让**一个模型服务多个用例**：
- 粗排：用 32d 快速过一遍
- 精排：用 768d 精排 top-K
- 不需要两个模型

## 5. MRL 的真实代价

天下没有免费的午餐。MRL 的代价：

| 代价 | 量化 |
|---|---|
| 训练时间增加 | 多个 loss 项 → 训练时间 +10-30% |
| 全维精度轻微下降 | MRL 模型在 768d 通常比纯 768d 训练的模型低 0.5-1 pp |
| 训练复杂度 | 需要选择 matryoshka_dims 和权重 $c_j$ |
| 调试难度 | 截断维度的 loss 曲线更多 |
| 工程惯例改变 | 截断后**必须**重新归一化（[01 章](01-直觉与几何.md)） |

## 7. 本系列的来源

本系列源自一份**用户报告**：

> *"维度压缩黑科技 MRL（俄罗斯套娃表示学习）：embeddinggemma-300m、jina-embeddings-v5-text-small 以及近期的 nomic-embed-text-v2，将核心语义权重集中在前面的维度中，可以毫无心理负担地截断向量..."*

追问这条报告，发现：
- 报告大体正确，但细节有出入（embeddinggemma 不支持截到 64，只能到 128）
- 模型大小不变这一点报告没说，是关键误解
- 2025-2026 有大量 follow-up 论文，没有中文系统综述
- 端侧 RAG 工程师需要的是**实证 + 决策树**，不是论文宣读

所以这个系列诞生了。

## 费曼回炉记录（L2 自检 · 已迭代）

- **F2 卡壳点**：早期被"MRL 截断后精度几乎不掉"的营销话术唬住，以为这是免费午餐。重读原始论文 + Sentence Transformers 官方说明才看清**模型权重、推理 FLOPs、RAM 一字节都没省**——省的只是下游"输出向量"的存储和距离计算。第二个误区是把 MRL 当成量化的一种，重读后才明白两者**正交**：MRL 砍维度、量化砍精度，可以叠加。第三个坑是以为所有嵌入模型都能截断用，重读才意识到**必须用 MRL loss 训练过**，否则前 N 维没有特殊含义，直接截断会断崖式掉点。最后还有一个被忽视的事实：MRL 模型在 768 全维通常比纯 768d 训练的模型低 0.5-1pp——天下没有免费的午餐。
- **F3 术语翻译**：
  - "Matryoshka（俄罗斯套娃）" → 大套娃里装小套娃，前 32 维 ⊂ 前 64 维 ⊂ ... ⊂ 前 768 维，外面那层永远包含里面那层，所以截到任意维度都还"是个完整的套娃"
  - "嵌套损失" → 训练时让模型同时学习"前 32 维够用"、"前 128 维够用"、"前 768 维够用"——逼它把最重要的语义塞进前面几维，重要度从前往后排
  - "理论维度上限（LIMIT）" → 不是无穷缩，32 维最多能精确区分约 500 个文档，128 维约 5000 个，文档数超过这个上限必然撞墙——这是数学定理不是经验值
- **F4 回炉**：v1 罗列"MRL 能省存储/省延迟/省 RAM"的好处清单，听起来像营销；v2 改成"MRL 是什么 + 不是什么 + 真实代价"三段对照，把"不改变模型大小、不加速推理、有精度代价、有理论上限"全摆出来。diff 是从"卖点宣传"升级为"防误解清单"，让读者既知道用在哪、也知道局限在哪。
