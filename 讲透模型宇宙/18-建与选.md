# 18 · 建与选：从工作问题到模型方案

> 工作里来一个需求——"自动给工单分类""把会议录音变成纪要""判断这封邮件是不是钓鱼"。你会本能想"上个模型"。但**90% 的人在这一步就走错了**：要么过度上模型（规则就够）、要么选错方法（该 RAG 却微调）、要么过早优化（先想 70B 不想 7B）。本章给你一套**从工作问题到模型方案的决策链**，让你第一遍就选对。

## 18.1 第一个问题：真的需要模型吗？

拿到需求，**先别想模型**。先问：

> **这个问题，几行 if-else + 一个查表能解决吗？**

大量"AI 需求"其实是**规则问题**。例：
- "判断金额是否超阈值" → 一个 `if`，不需要模型。
- "把邮箱按域名分类" → 一个查表，不需要模型。
- "提取发票里的金额" → 正则 + 少量规则，可能够用。

**判断标准**：如果一个新员工**不需要任何"学习"**，看一份操作手册就能做对——那它就是规则问题，**不要上模型**。模型的价值在"**无法用有限规则穷举的模式**"（如语义、图像、长尾）。

> 研究者/工程师的纪律：**最简单的能解决问题的方案，就是最好的方案。** 上模型前，先证明规则不够。

## 18.2 建 vs 选：四象限决策

确定要上模型后，第二个问题是**自己建还是用现成**。用两个轴画四象限：

```
                    任务的定制化程度
              低（通用）              高（领域特殊）
         ┌─────────────────────┬─────────────────────┐
   高    │  ① 调 API           │  ③ 微调开源模型       │
(够用)   │  GPT/Claude API     │  开源基座 + LoRA      │
数据/    │  零成本起步           │  RAG 也常落这格       │
质量     ├─────────────────────┼─────────────────────┤
   低    │  ② 换任务或补数据     │  ④ 先补数据, 别建     │
         │  模型救不了坏数据     │  无数据=无模型        │
         └─────────────────────┴─────────────────────┘
```

- **① 调 API**：任务通用（摘要、翻译、问答）、数据少 → 直接用闭源 API，**零成本验证可行性**。永远从这里开始（MVP）。
- **② 换任务或补数据**：数据质量差 → 模型再强也救不了。**先修数据，别碰模型**。
- **③ 微调开源**：任务特殊 + 有数据 → 开源基座 + LoRA/RAG。这是多数真实工作落点。
- **④ 先补数据**：任务特殊但没数据 → **别建**。没有领域数据，模型一定差。先攒数据。

> **核心原则**：**先 ① 验证可行，再 ③ 降本/提精**。永远不要一上来就 ③/④——你还没证明问题可解。

## 18.3 模型方案的决策链：问题→数据→方法→评估

一个完整的模型方案，按这四步走，**顺序不能乱**：

### 步骤 1：把问题问清楚（最重要，最常被跳过）
- **输入是什么？输出是什么？**（具体到格式）
- **成功的标准是什么？**（可量化的指标，不是"好用"）
- **错误的代价是什么？**（误判的后果，决定精度要求）
- **延迟/成本约束？**（实时？离线？预算？）

> 80% 的模型项目失败，是因为**问题没问清楚**就开始建。先把这四问写在文档里，让需求方确认。

### 步骤 2：盘点数据
- **有多少标注数据？**（< 100 条 → 只能 few-shot/API；> 1万条 → 可微调）
- **数据质量？**（噪声、标注不一致 → 先清洗）
- **数据覆盖了真实分布吗？**（训练集和线上分布漂移 = 灾难）

### 步骤 3：选方法（见 §18.4 决策树）

### 步骤 4：定评估
- **离线指标**（准确率/F1/...）+ **在线指标**（业务效果）；
- **必须有 hold-out 测试集**（不能边训边看 test）；
- **错误分析**：不只看总分，看错在哪类样本（见 Ch14 批判）。

## 18.4 方法选择决策树

确定有数据、问题清楚后，按这棵树选方法：

```
任务需要"知识"吗(文档/数据库)?
├─ 是 → RAG (检索增强)        ← 讲透RAG
│       (知识常变? 必须 RAG; 微调记不住新知识)
└─ 否 → 任务需要"风格/领域适配"吗?
        ├─ 是, 有>1万标注 → 微调 (LoRA 优先)   ← 讲透微调
        ├─ 是, 标注少 → few-shot prompt (API)  ← 讲透Prompt
        └─ 否 → 通用能力够 → 直接调 API

任务需要"多步推理/工具"吗?
└─ 是 → Agent 框架                          ← 讲透Agent

输出需要极低延迟(端侧)?
└─ 是 → 蒸馏/量化小模型                     ← Ch20 + 讲透端侧AI压缩
```

**关键洞见**：
- **知识用 RAG，能力用微调，推理用 Agent**——三者解决不同问题，经常**组合**用。
- **优先 RAG > 微调**：RAG 改知识库即时生效，微调改一次要重训。除非要改"风格/能力"，否则 RAG 更划算。
- **LoRA > 全量微调**：90% 的领域适配，LoRA 够用且省 10-100 倍算力。

## 18.5 最小可行方案（MVP）原则

**永远从最小方案开始**，迭代加深：

1. **MVP-0**：调一次 API + 一个 prompt，看能不能解决。（1 小时）
2. **MVP-1**：加 few-shot examples + 简单后处理。（1 天）
3. **MVP-2**：加 RAG（如果需要知识）。（1 周）
4. **MVP-3**：微调（如果 MVP-2 不够）。（2-4 周）

**每一步都要验证"够不够"**——多数需求在 MVP-1/2 就够了，**不需要走到微调**。

> 反面教材：很多团队一上来就微调 70B，花几周——结果发现 prompt 调一下 + RAG 就解决。**过早优化是万恶之源**。

## 18.6 工作场景的三个真实决策

**场景 A：工单自动分类**（500 类，有 5 万标注）
→ 任务特殊 + 有数据 → **微调一个 7B 开源模型 + LoRA**。规则不够（语义），API 不够（领域术语）。

**场景 B：内部知识库问答**（公司文档，常更新）
→ 需要知识 + 知识常变 → **RAG**。微调记不住新文档，RAG 改库即时生效。

**场景 C：实时语音转写 + 摘要**（端侧，低延迟）
→ 延迟约束 → **蒸馏/量化小模型 + 流式**。大模型太慢。

## 18.7 批判：建与选的常见坑

- **过度工程**：能用 API 解决的，非要自训模型。**先证明 API 不够**。
- **过早优化**：MVP 没验证，就上 70B + 复杂架构。**先跑通再优化**。
- **数据忽视**：疯狂调模型，不修数据。**坏数据 + 好模型 = 坏结果**。
- **评估缺失**：只看 demo 效果，没有 hold-out 测试集。**上线必翻车**。
- **方法崇拜**：听说 Agent 火，什么都套 Agent。**方法服务问题，不是问题服务方法**。
