## Overview

 Collectors and Evaluators are two crucial components in the DI-engine reinforcement learning (RL) framework. They serve as the interface between policies (agents) and environments, with distinct but complementary roles in the training pipeline. This document explains their architecture, functionality, and integration within the framework.

 
 - **Collectors** gather experience data by having policies interact with environments. They organize and process transitions for training.
 - **Evaluators** assess policy performance by measuring metrics like average episode return during periodic evaluation episodes.
 
 For information about the training process that uses the collected data, see Learners. For the data storage components, see Replay Buffer.

 
## Role in RL Pipeline

 In the reinforcement learning loop, Collectors and Evaluators serve different purposes:

 
 - **Collectors** execute the policy in the environment to gather experience data. They:

 
 - Take policy outputs (actions) and apply them to environments
 - Process resulting transitions (state, action, reward, next state, done)
 - Organize transitions into trajectories or episodes
 - Deliver processed data for training
 - **Evaluators** measure policy performance periodically. They:

 
 - Run the policy for complete episodes without collecting data for training
 - Calculate metrics like average episode return
 - Determine when to save checkpoints based on performance
 - Provide stopping conditions when performance reaches target values
 
 
## Collector System

 
### Collector Architecture

 
```

```

 Sources: [ding/worker/collector/sample_serial_collector.py15-200](https://github.com/opendilab/DI-engine/blob/c290a673/ding/worker/collector/sample_serial_collector.py#L15-L200) [ding/worker/collector/battle_sample_serial_collector.py13-100](https://github.com/opendilab/DI-engine/blob/c290a673/ding/worker/collector/battle_sample_serial_collector.py#L13-L100) [ding/framework/middleware/collector.py14-165](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/middleware/collector.py#L14-L165)

 The collector system in DI-engine has two main implementations:

 
 - **Worker-based Collectors** (`ISerialCollector` and its implementations):

 
 - Object-oriented implementation used in the serial pipeline
 - Manages environment and policy interactions directly
 - Maintains internal buffers and data structures
 - Used in traditional entry points like `serial_pipeline`
 - **Middleware-based Collectors** (`StepCollector`, `EpisodeCollector`):

 
 - Functional implementation used in the task framework
 - Uses context objects to pass data between pipeline components
 - More lightweight and composable
 - Used in newer, more modular pipeline implementations
 
 
### Collecting Process

 
```

```

 Sources: [ding/worker/collector/sample_serial_collector.py224-378](https://github.com/opendilab/DI-engine/blob/c290a673/ding/worker/collector/sample_serial_collector.py#L224-L378) [ding/framework/middleware/functional/collector.py50-166](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/middleware/functional/collector.py#L50-L166)

 The collection process involves the following steps:

 
 - **Preparation**: The collector retrieves ready observations from the environment
 - **Policy Forward**: The observations are sent to the policy to get actions
 - **Environment Step**: Actions are applied to the environment to get new timesteps
 - **Transition Processing**: Each timestep is processed with the policy to create transitions
 - **Storage**: Transitions are stored in trajectory buffers
 - **Completion Check**: When trajectories are complete (episode done or buffer full): 
 - Transitions are converted to training samples
 - Buffers are cleared for new data
 - **Logging**: Collection statistics are logged periodically

 Similar to collectors, evaluators in DI-engine have two main implementations:

 
 - **Worker-based Evaluators** (`ISerialEvaluator` and its implementations):

 
 - Traditional object-oriented implementation
 - Manages complete evaluation cycles
 - Used in serial pipeline entry points
 - **Middleware-based Evaluators** (`interaction_evaluator` function):

 
 - Functional implementation for task framework
 - Uses context objects to pass data between pipeline components
 - More modular and composable
 
 Both systems use `VectorEvalMonitor` to track evaluation metrics across multiple environments.

 
### Evaluation Process

 
```

```

 Sources: [ding/worker/collector/interaction_serial_evaluator.py184-326](https://github.com/opendilab/DI-engine/blob/c290a673/ding/worker/collector/interaction_serial_evaluator.py#L184-L326) [ding/framework/middleware/functional/evaluator.py213-328](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/middleware/functional/evaluator.py#L213-L328)

 The evaluation process follows these steps:

 
 - **Initialization**: Reset environments and policy, create evaluation monitor
 - **Interaction Loop**: Run policy in environments until sufficient episodes are completed 
 - Get observations and compute actions
 - Step environments with actions
 - When episodes complete, update metrics
 - **Performance Analysis**: 
 - Calculate episode statistics (mean, std, min, max rewards)
 - Check if performance exceeds previous best
 - Save checkpoint if performance improved
 - Check if performance meets stopping criterion

## Integration into Training Pipeline

 DI-engine provides two main ways to integrate collectors and evaluators into training pipelines:

 
### 1. Serial Pipeline Integration

 In the traditional serial pipeline, collectors and evaluators are constructed as part of the pipeline initialization:

 
```

```

 Sources: [ding/entry/serial_entry.py18-147](https://github.com/opendilab/DI-engine/blob/c290a673/ding/entry/serial_entry.py#L18-L147) [ding/entry/serial_entry_onpolicy.py18-127](https://github.com/opendilab/DI-engine/blob/c290a673/ding/entry/serial_entry_onpolicy.py#L18-L127)

 
 - **Collector Creation**: Using `create_serial_collector` factory function that:

 
 - Instantiates the appropriate collector type (sample, episode, etc.)
 - Links collector to environment manager and policy
 - Configures collection parameters
 - **Evaluator Creation**: Using `create_serial_evaluator` or direct instantiation that:

 
 - Creates the evaluator with configured parameters
 - Links to environment manager and policy
 - **Main Loop**: Orchestrates the interaction:

 
 - Evaluator runs periodically (`evaluator.should_eval()`)
 - Collector provides data for each training iteration
 - Learner uses collected data to update policy
 
 
### 2. Task Framework Integration

 In the newer task framework, collectors and evaluators are middleware components:

 
```

```

 Sources: [ding/example/ppo.py34-74](https://github.com/opendilab/DI-engine/blob/c290a673/ding/example/ppo.py#L34-L74) [ding/example/dqn.py54-97](https://github.com/opendilab/DI-engine/blob/c290a673/ding/example/dqn.py#L54-L97)

 
 - **Component Registration**: Use `task.use()` to register middleware:

 
 - `interaction_evaluator()` for evaluation
 - `StepCollector`/`EpisodeCollector` for data collection
 - **Context Flow**: Data flows between components through context object:

 
 - Collectors update `ctx.trajectories`/`ctx.episodes`
 - Advantage estimators create `ctx.train_data`
 - Evaluators update `ctx.eval_value`
 - **Distributed Integration**: Additional middleware for distributed operation:

 
 - `ContextExchanger` for sharing context between processes
 - `ModelExchanger` for sharing policy models

## Performance and Implementation Considerations

 When using collectors and evaluators, consider the following:

 
 - **Environment Vectorization**: Both collectors and evaluators work with vectorized environments to parallelize data collection:

 
 - `collector_env_num` determines collection parallelism
 - `evaluator_env_num` determines evaluation parallelism
 - **Collection Efficiency**:

 
 - Using `n_sample` with values divisible by `env_num` improves efficiency
 - `deepcopy_obs=False` reduces memory usage but requires careful handling
 - **Evaluation Scheduling**:

 
 - `eval_freq` controls the frequency of evaluation
 - Too frequent evaluation slows training
 - Too infrequent evaluation might miss optimal policy checkpoints
 - **Distributed Collection**:

 
 - Multiple collectors can run on different machines
 - `allreduce_data()` synchronizes statistics across distributed collectors

## Conclusion

 Collectors and Evaluators are essential components in DI-engine that bridge policies and environments. They handle the data flow for both training and assessment, supporting various RL algorithms and training pipelines.

 
 - **Collectors** manage the experience gathering process, providing structured data for learning algorithms
 - **Evaluators** assess policy performance and help determine when training should stop
 - Both components support various configurations to adapt to different algorithms and environments
 
 Understanding how to properly configure and integrate these components is crucial for effective reinforcement learning with DI-engine.
