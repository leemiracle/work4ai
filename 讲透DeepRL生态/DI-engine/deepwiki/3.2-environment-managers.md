  Environment managers in DI-engine provide a system for efficiently managing multiple reinforcement learning environments. These managers offer a unified interface for running environments in different execution modes (synchronous, asynchronous) and provide essential features like parallel execution, automatic environment reset, and error handling. For information about environment wrappers, see [Environment Wrappers](https://deepwiki.com/opendilab/DI-engine/3.1-environment-wrappers).

 
## Overview

 Environment managers control the lifecycle of multiple environments, handling their creation, execution, and termination. They serve as a bridge between policies and environments, facilitating efficient data collection by running multiple environments simultaneously.

## Environment Manager Types

 DI-engine provides several types of environment managers for different use cases:

 
 - **BaseEnvManager**: A basic environment manager that runs environments sequentially in the main process. Used for simple scenarios and debugging.
 - **AsyncSubprocessEnvManager**: Runs environments in separate subprocesses asynchronously. Ideal for compute-intensive environments.
 - **SyncSubprocessEnvManager**: Similar to AsyncSubprocessEnvManager but ensures environments step in sync. Good for deterministic behavior.
 - **GymVectorEnvManager**: Adapts Gym's vectorized environments to DI-engine's interface.

## Key Concepts

 
### Environment States

 Environment managers use an internal state model to track the status of each managed environment:

 
| State | Description |
|---|---|
| VOID | Environment not initialized or closed |
| INIT | Environment initialized but not reset |
| RUN | Environment running and ready for stepping |
| RESET | Environment in the process of resetting |
| DONE | Environment finished all episodes |
| ERROR | Environment encountered an error |
| NEED_RESET | Environment done and needs manual reset |

 Sources: [ding/envs/env_manager/base_env_manager.py20-27](https://github.com/opendilab/DI-engine/blob/c290a673/ding/envs/env_manager/base_env_manager.py#L20-L27)

 
### Ready Observations

 Environment managers provide a special mechanism called "ready observations" to unify both synchronous and asynchronous execution patterns:

 
```
1. Get ready observations with env_manager.ready_obs
2. Compute actions for these observations
3. Step the environments with these actions
4. Repeat
```

 This design allows algorithms to interact with environments in a consistent way regardless of the underlying execution mode.

### Error Handling

 Environment managers implement several error handling mechanisms:

 
 - **Automatic Retries**: Retry environment operations when errors occur
 - **Timeouts**: Detect and handle hanging environments
 - **Error States**: Track environments in error state
 - **Environment Recreation**: Recreate environments when necessary

## Common Configuration

 Environment managers share a set of common configuration parameters:

 
| Parameter | Description | Default |
|---|---|---|
| episode_num | Maximum number of episodes to run | float("inf") |
| max_retry | Maximum retry attempts when errors occur | 1 |
| retry_type | Strategy for retries ('reset' or 'renew') | 'reset' |
| auto_reset | Automatically reset environments when done | True |
| step_timeout | Timeout for step operations | None |
| reset_timeout | Timeout for reset operations | None |
| retry_waiting_time | Wait time between retries | 0.1 |

 Additional configuration for subprocess environment managers:

 
| Parameter | Description | Default |
|---|---|---|
| shared_memory | Use shared memory for observations | True |
| copy_on_get | Copy data when retrieving from shared memory | True |
| context | Multiprocessing context ('spawn' or 'fork') | Platform-dependent |
| wait_num | Minimum number of environments to wait for | 2 |
| step_wait_timeout | Timeout for waiting on environment steps | 0.01 |
| connect_timeout | Timeout for subprocess connections | 60 |
| reset_inplace | Reset in subprocess immediately when done | False |

## Implementation Details

 
### BaseEnvManager

 The `BaseEnvManager` class provides the foundational implementation for environment management:

 
 - Manages environments in the main process
 - Handles environment states and transitions
 - Implements core methods (reset, step, seed, close)
 - Provides the ready observation mechanism
 - Includes error handling and retry logic
 
 BaseEnvManager is best suited for small-scale experiments and debugging since it runs environments sequentially.

 Sources: [ding/envs/env_manager/base_env_manager.py63-566](https://github.com/opendilab/DI-engine/blob/c290a673/ding/envs/env_manager/base_env_manager.py#L63-L566)

 
### AsyncSubprocessEnvManager

 The `AsyncSubprocessEnvManager` extends BaseEnvManager to run environments in separate subprocesses:

 
 - Creates subprocesses for each environment
 - Uses pipes for inter-process communication
 - Supports shared memory for observation transfer
 - Implements asynchronous environment execution
 - Provides worker functions for subprocess execution
 
 Key components:

 
 - **Subprocess Creation**: Each environment runs in a separate subprocess.
 - **Pipe Communication**: Uses pipes to send commands to subprocesses and receive results.
 - **Shared Memory**: Optionally uses shared memory to efficiently transfer observations.
 - **Worker Function**: Executes environment operations in the subprocess.
 - **Wait Mechanism**: Implements a wait method to collect results from multiple subprocesses.
 
 AsyncSubprocessEnvManager is ideal for compute-intensive environments and when gathering experience from multiple environments in parallel.

 Sources: [ding/envs/env_manager/subprocess_env_manager.py34-650](https://github.com/opendilab/DI-engine/blob/c290a673/ding/envs/env_manager/subprocess_env_manager.py#L34-L650)

 
### SyncSubprocessEnvManager

 The `SyncSubprocessEnvManager` extends AsyncSubprocessEnvManager but overrides the step method to provide synchronous execution:

 
 - Ensures all environments step together
 - Simplifies the step implementation to wait for all environments
 - Provides better reproducibility at the cost of efficiency
 
 SyncSubprocessEnvManager is useful when deterministic behavior is important and when all environments need to stay in sync.

 Sources: [ding/envs/env_manager/subprocess_env_manager.py677-775](https://github.com/opendilab/DI-engine/blob/c290a673/ding/envs/env_manager/subprocess_env_manager.py#L677-L775)

 
### GymVectorEnvManager

 The `GymVectorEnvManager` adapts Gym's vectorized environments to DI-engine's interface:

 
 - Wraps Gym's AsyncVectorEnv
 - Converts Gym's interface to DI-engine's interface
 - Provides compatibility with Gym's vectorized environments
 
 GymVectorEnvManager allows leveraging Gym's vectorized implementation while maintaining compatibility with DI-engine's systems.

 Sources: [ding/envs/env_manager/gym_vector_env_manager.py16-138](https://github.com/opendilab/DI-engine/blob/c290a673/ding/envs/env_manager/gym_vector_env_manager.py#L16-L138)

## Conclusion

 Environment managers are a critical component of DI-engine, enabling efficient management of multiple environments for reinforcement learning. The modular design allows selecting the appropriate manager based on the specific use case, from simple sequential execution to highly parallelized asynchronous environments.

 The environment manager system provides:

 
 - Unified interface for environment interaction
 - Parallel execution of environments
 - Error handling and recovery
 - Flexible configuration options
 - Compatible implementations for different scenarios
 
 By abstracting the environment management details, DI-engine allows algorithm implementations to focus on the learning logic rather than environment execution specifics.
