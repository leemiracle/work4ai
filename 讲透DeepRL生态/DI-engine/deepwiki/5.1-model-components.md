## Introduction

 This page documents the model components in DI-engine's neural network system. DI-engine provides a modular architecture for building reinforcement learning models, where components can be mixed and matched to create complex architectures. The two primary types of model components are **encoders** and **heads**.

 For information about how these components are assembled into complete models, see [Model Templates](https://deepwiki.com/opendilab/DI-engine/5.2-model-templates). For information about model wrappers that extend component functionality, see [Model Wrappers](https://deepwiki.com/opendilab/DI-engine/5.3-model-wrappers).

## Architecture Overview

 Model components in DI-engine follow a modular design that allows for flexible composition of neural network architectures. The general structure involves encoders that process input observations into latent representations, followed by heads that transform these representations into actionable outputs (e.g., action values, action probabilities, etc.).

## Encoders

 Encoders transform input observations (like images or feature vectors) into latent representations that capture relevant information for decision-making. These latent representations are then fed to heads that produce action values or probabilities.

 
### Encoder Types

 
```

```

 Sources: [ding/model/common/encoder.py14-516](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/encoder.py#L14-L516)

 
#### ConvEncoder

 The `ConvEncoder` is designed for encoding 2D image observations. It processes input images through a series of convolutional layers, optionally followed by residual blocks, and outputs a flattened feature vector.

 Key characteristics:

 
 - Input: 2D images with shape `(batch_size, channels, height, width)`
 - Architecture: Convolutional layers followed by optional residual blocks
 - Output: 1D feature vector with shape `(batch_size, hidden_size)`
 
 
```

```

 Sources: [ding/model/common/encoder.py24-155](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/encoder.py#L24-L155)

 
#### FCEncoder

 The `FCEncoder` processes 1D vector inputs through fully connected layers. It's suitable for environments with structured or vectorized observations (like sensor readings or state vectors).

 Key characteristics:

 
 - Input: 1D vectors with shape `(batch_size, obs_shape)`
 - Architecture: Fully connected layers, optionally with residual connections
 - Output: 1D feature vector with shape `(batch_size, hidden_size)`
 
 
```

```

 Sources: [ding/model/common/encoder.py158-236](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/encoder.py#L158-L236)

 
#### IMPALAConvEncoder

 The `IMPALAConvEncoder` is a specialized encoder based on the IMPALA paper architecture. It's designed for processing image observations in IMPALA algorithm implementations.

 Key characteristics:

 
 - Input: 2D images with shape `(batch_size, channels, height, width)`
 - Architecture: Series of downsampling stacks with residual connections
 - Output: 1D feature vector with shape `(batch_size, outsize)`
 
 Sources: [ding/model/common/encoder.py390-473](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/encoder.py#L390-L473)

 
#### GaussianFourierProjectionTimeEncoder

 This encoder is used for encoding time steps in generative models like diffusion models. It uses Gaussian random features to encode time steps.

 Key characteristics:

 
 - Input: 1D time step tensor with shape `(batch_size,)`
 - Output: Embedded time representation with shape `(batch_size, embed_dim)`

## Heads

 Heads are components that transform encoded representations into outputs directly related to agent decision-making, such as action values, action probabilities, or value distributions.

 
### Head Types

 
```

```

 Sources: [ding/model/common/head.py14-790](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L14-L790)

 
#### DiscreteHead

 The most basic head, which generates discrete action logits or Q-values for discrete action spaces. Used in standard Q-learning and actor-critic algorithms.

 Key characteristics:

 
 - Input: Encoded features with shape `(batch_size, hidden_size)`
 - Output: Action logits with shape `(batch_size, output_size)`
 
 
```

```

 Sources: [ding/model/common/head.py14-83](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L14-L83)

 
#### DuelingHead

 Implements the dueling architecture, which decomposes Q-values into state value and advantage functions. Used in Dueling DQN and related algorithms.

 Key characteristics:

 
 - Separate value and advantage streams
 - Combines value and advantage to produce Q-values
 - Helps in better state value estimation
 
 
```

```

 Sources: [ding/model/common/head.py791-870](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L791-L870)

 
#### DistributionHead

 Used to generate distributions for Q-values rather than point estimates. This head is used in C51 (Categorical DQN) algorithm.

 Key characteristics:

 
 - Outputs a categorical distribution over atom values
 - Supports distributional reinforcement learning
 - Uses softmax to convert logits to probabilities
 
 Sources: [ding/model/common/head.py86-173](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L86-L173)

 
#### RainbowHead

 Specialized head for Rainbow DQN, which combines several improvements to DQN including distributional RL and dueling networks.

 Key characteristics:

 
 - Combines features of DistributionHead and DuelingHead
 - Outputs distributional Q-values with dueling architecture
 
 Sources: [ding/model/common/head.py289-390](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L289-L390)

 
#### QRDQNHead

 Used in Quantile Regression DQN (QR-DQN) to output quantile values for distributional RL.

 Key characteristics:

 
 - Outputs quantile values instead of a categorical distribution
 - Supports more flexible distributional representation
 
 Sources: [ding/model/common/head.py393-473](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L393-L473)

 
#### QuantileHead

 Used in Implicit Quantile Networks (IQN) to model the state-action quantile function.

 Key characteristics:

 
 - Maps from state-actions and samples from base distributions
 - More sample-efficient than QR-DQN for distributional RL
 
 Sources: [ding/model/common/head.py476-609](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L476-L609)

 
#### FQFHead

 Used in Fully parameterized Quantile Function (FQF) to estimate adjustable quantile values for approximating return distributions.

 Key characteristics:

 
 - Learns the quantile fractions (unlike IQN which samples them)
 - More expressive representation of return distributions
 
 Sources: [ding/model/common/head.py612-787](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L612-L787)

 
#### BranchingHead

 Used for high-dimensional action spaces. Allows for a level of independence for each individual action dimension, making it suitable for environments with many degrees of freedom.

 Key characteristics:

 
 - Independently computes action-values for each action dimension
 - Linear scaling with action dimensions instead of exponential
 
 Sources: [ding/model/common/head.py176-286](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/common/head.py#L176-L286)

## Component Factory and Registration

 DI-engine provides a factory pattern for creating model components. The `create_model` function allows for dynamic component instantiation based on configuration.

 
```

```

 The model registration system works as follows:

 
 - Model classes are registered with `MODEL_REGISTRY` using the `@MODEL_REGISTRY.register()` decorator
 - The `create_model` function takes a configuration dictionary and dynamically creates the appropriate model
 - The configuration specifies the model type, which determines which registered model to instantiate

## Integration with Policy System

 Model components are heavily used by the Policy System (see [Policy System](https://deepwiki.com/opendilab/DI-engine/4-policy-system)) to implement various reinforcement learning algorithms.

 
```

```

 Different policies use different combinations of encoders and heads:

 
 - DQN-based policies typically use a combination of ConvEncoder/FCEncoder with DiscreteHead or DuelingHead
 - Distributional RL policies use specialized heads like DistributionHead or QRDQNHead
 - Actor-critic policies may use shared encoders with separate heads for actor and critic
 
 Sources: [ding/model/template/maqac.py12-478](https://github.com/opendilab/DI-engine/blob/c290a673/ding/model/template/maqac.py#L12-L478)

 
## Summary

 Model components in DI-engine provide a flexible foundation for building various reinforcement learning algorithms. By combining different encoders and heads, users can implement classic algorithms like DQN, advanced methods like Rainbow or SAC, and even custom models tailored to specific needs.

 The modularity of these components enables experimentation with novel architectural variations without rewriting the entire learning framework. Components can be mixed and matched to create hybrid models or to adapt existing algorithms to new environments.

 For information on how these components are assembled into complete models, see [Model Templates](https://deepwiki.com/opendilab/DI-engine/5.2-model-templates).
