  The Task and Context Framework is a core component of DI-engine that orchestrates reinforcement learning (RL) workflows. It provides a flexible, composable approach to building RL pipelines using a middleware pattern. This framework enables developers to create modular, reusable components that can be combined to form complete RL algorithms.

 For information about the specific middleware implementations that work within this framework, see [Middleware System](https://deepwiki.com/opendilab/DI-engine/2.3-middleware-system).

 
## Core Components and Architecture

 The Task and Context Framework consists of three main components:

 
 - **Task**: Manages workflow execution, middleware registration, and control flow
 - **Context**: Provides shared state between middleware components
 - **Middleware**: Functions that perform specific operations within the RL pipeline

### Context

 The Context is a dataclass that serves as a shared state container, passing information between middlewares. It maintains a lifecycle tied to a training iteration, with mechanisms to preserve specific data across iterations.

 
```

```

 Sources: [ding/framework/context.py7-105](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/context.py#L7-L105)

 The base `Context` class provides these key methods:

 
 - **renew()**: Creates a new context for the next iteration, carrying over only "kept" properties
 - **keep(*keys)**: Marks properties to be preserved across context renewals
 - **has_attr(key)**: Checks if a specific attribute exists in the context
 
 The framework provides two specialized context classes:

 
 - **OnlineRLContext**: For online RL algorithms that interact with environments in real-time
 - **OfflineRLContext**: For offline RL algorithms that learn from static datasets
 
 Each context type defines fields appropriate for its use case. For example, `OnlineRLContext` includes environment-related fields (`env_step`, `env_episode`), while both include training-related fields (`train_iter`, `train_data`).

 
### Task

 The `Task` class manages the execution pipeline, middleware registration, and workflow control. It's responsible for orchestrating the entire RL process.

 
```

```

 Key methods of the `Task` class include:

 
| Method | Purpose |
|---|---|
| use(fn) | Register a middleware function |
| use_wrapper(fn) | Register a wrapper to be applied to all middlewares |
| run(max_step) | Execute the pipeline for a specified number of iterations |
| forward(fn, ctx) | Execute a middleware until a yield statement or completion |
| backward(backward_stack) | Execute the remaining portion of middlewares (after yield) |
| serial(*fns) | Wrap functions to run in serial |
| parallel(*fns) | Wrap functions to run in parallel |
| renew() | Create a new context for the next iteration |

 The `Task` class implements a singleton pattern through the module-level instance `task`.

### Execution Flow

 The Task and Context Framework uses a unique forward-backward execution pattern that allows for complex middleware interactions:

 
```

```

 Sources: [ding/framework/task.py194-217](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/task.py#L194-L217)

 The execution flow consists of these key steps:

 
 - **Forward Phase**: Execute each middleware until a `yield` statement or completion
 - **Sync Phase**: Wait for any asynchronous tasks to complete
 - **Backward Phase**: Resume execution of middlewares that used `yield`
 - **Renew Context**: Create a new context for the next iteration
 
 This pattern allows middlewares to pause execution at strategic points (using `yield`) and resume after other middlewares have executed, enabling complex dependencies and data flows.

 
## Understanding Middleware

 Middlewares are functions that take a context object as input, perform operations, and potentially modify the context. They can be simple functions or generated by factory functions that provide additional configuration.

 
```

```

 Sources: [ding/framework/middleware/functional/advantage_estimator.py18-105](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/middleware/functional/advantage_estimator.py#L18-L105) [ding/framework/middleware/functional/collector.py50-86](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/middleware/functional/collector.py#L50-L86) [ding/framework/middleware/functional/trainer.py10-54](https://github.com/opendilab/DI-engine/blob/c290a673/ding/framework/middleware/functional/trainer.py#L10-L54)

 Common middleware types include:

 
 - **Collector**: Gathers experiences from environments (e.g., `StepCollector`, `EpisodeCollector`)
 - **Advantage Estimator**: Calculates advantage estimates for policy gradient methods (e.g., `gae_estimator`)
 - **Trainer**: Updates the policy based on collected data (e.g., `trainer`, `multistep_trainer`)
 - **Evaluator**: Evaluates policy performance (e.g., `interaction_evaluator`)
 
 Middlewares can yield control back to the task at key points, allowing for complex execution patterns. For example, a data collection middleware might yield after gathering experiences, allowing an advantage calculation middleware to process that data before training continues.

## Best Practices

 When working with the Task and Context Framework, consider these best practices:

 
 - **Design focused middlewares**: Each middleware should have a clear, single responsibility
 - **Use `yield` strategically**: Place `yield` statements at points where you want to pause execution and allow other middlewares to process the intermediate data
 - **Manage context fields carefully**: Use `ctx.keep()` for properties that should persist across iterations
 - **Check roles in distributed execution**: Use `task.has_role()` to ensure middlewares only execute on appropriate processes
 - **Use appropriate context type**: Choose `OnlineRLContext` for interactive RL and `OfflineRLContext` for offline RL
