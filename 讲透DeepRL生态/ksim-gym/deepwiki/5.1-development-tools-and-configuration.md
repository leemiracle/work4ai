### Linting

 Linting is handled by ruff with rules configured to enforce coding standards:

 
 - Import sorting (`I`)
 - Error checking (`E`, `F`)
 - Naming conventions (`N`)
 - Style guidelines (`PL*`)
 
 The project specifically ignores certain rules for pragmatic development, such as some documentation requirements and complexity metrics.

 Sources: [pyproject.toml58-79](https://github.com/kscalelabs/ksim-gym/blob/3e92db5c/pyproject.toml#L58-L79)

 
### Type Checking

 Static type checking is performed with mypy, configured to:

 
 - Disallow untyped function definitions
 - Enforce strict equality
 - Show detailed error context and codes
 - Track incremental builds for performance
 
 Third-party libraries without type annotations are explicitly allowed.

 Sources: [pyproject.toml10-42](https://github.com/kscalelabs/ksim-gym/blob/3e92db5c/pyproject.toml#L10-L42)

### File Exclusions

 The `.gitignore` file specifies patterns for files that should not be tracked by Git:

 
 - Python bytecode and cache files (`*.py[oc]`, `__pycache__/`)
 - Type checking cache (`.mypy_cache/`, `.ruff_cache/`)
 - Jupyter notebook checkpoints (`.ipynb_checkpoints/`)
 - Build artifacts (`build/`, `dist/`, `*.so`)
 - Logs and rollout data (`rollouts/`)

## Best Practices

 When contributing to K-Sim Gym, follow these best practices:

 
 - Run `make format` before committing changes to ensure consistent code style
 - Validate code with `make static-checks` to catch issues early
 - Use type annotations for all function definitions
 - Follow Google-style docstrings for documentation
 - Keep the CI pipeline green by addressing all static check issues
 - Use Jupyter notebooks for exploration but move production code to proper Python modules
 
 This approach ensures that code contributions maintain the project's quality standards and remain maintainable.
