  This page documents the value-based algorithm implementations in SLM Lab: `SARSA`, `VanillaDQN`, `DQNBase`, `DQN`, and `DoubleDQN`.  For the abstract base class that all these algorithms extend, see [Algorithm Base Class and Action Selection](https://deepwiki.com/kengz/SLM-Lab/5.2.1-algorithm-base-class-and-action-selection). For memory types used by these algorithms (`Replay`, `OnPolicyBatchReplay`, `PrioritizedReplay`), see [Replay and On-Policy Memory](https://deepwiki.com/kengz/SLM-Lab/5.3.1-replay-and-on-policy-memory) and [Prioritized Experience Replay](https://deepwiki.com/kengz/SLM-Lab/5.3.2-prioritized-experience-replay).

## SARSA

 **File:** [slm_lab/agent/algorithm/sarsa.py](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/sarsa.py)

 `SARSA` implements on-policy TD control. It learns a Q-function using the *actual* next action taken in the environment (rather than the greedy action), satisfying the SARSA update rule:

 
```
y_t = r_t + γ · Q(s_t', a_t')
```

 where `a_t'` is the action actually taken in state `s_t'`.

 
### `init_algorithm_params`

 [slm_lab/agent/algorithm/sarsa.py44-64](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/sarsa.py#L44-L64)

 Reads the following fields from `algorithm_spec` and sets them as instance attributes:

 
| Field | Type | Description |
|---|---|---|
| action_pdtype | str | Probability distribution type (e.g. "Argmax", "default") |
| action_policy | str | Policy function name from policy_util (e.g. "epsilon_greedy", "boltzmann") |
| explore_var_spec | dict or null | Decay schedule for exploration variable (ε or τ) |
| gamma | float | Discount factor |
| training_frequency | int | How many timesteps between training calls |

 After setting these attributes, it calls `super().init_algorithm_params()` to initialize the `explore_var_scheduler` from `explore_var_spec` via the base class.

 
### `init_nets`

 [slm_lab/agent/algorithm/sarsa.py67-82](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/sarsa.py#L67-L82)

 Instantiates a single `net` of the type named in `net_spec['type']` (e.g. `MLPNet`, `RecurrentNet`). Sets `self.net_names = ['net']`. Creates `self.optim` and `self.lr_scheduler` from the net's `optim_spec` and `lr_scheduler_spec`. Calls `net_util.set_global_nets` and `end_init_nets`.

 
### `calc_q_loss`

 [slm_lab/agent/algorithm/sarsa.py110-128](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/sarsa.py#L110-L128)

 This is the on-policy TD loss:

 
 - Forward-pass `states` through `self.net` → `q_preds`
 - Forward-pass `next_states` through `self.net` (no grad) → `next_q_preds`
 - Extract `act_q_preds = q_preds[actions]` and `act_next_q_preds = next_q_preds[next_actions]`
 - Compute targets: `act_q_targets = rewards + γ · (1 - terminateds) · act_next_q_preds`
 - Return `self.net.loss_fn(act_q_preds, act_q_targets)`
 
 The `next_actions` field is constructed in `sample()` by shifting the actions array by one position [slm_lab/agent/algorithm/sarsa.py101-108](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/sarsa.py#L101-L108) which is valid because SARSA uses the on-policy memory where the next action is already recorded in the same buffer.

 
### `train`

 [slm_lab/agent/algorithm/sarsa.py131-150](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/sarsa.py#L131-L150)

 Called every step; only executes when `self.to_train == 1`. Performs a single gradient update:

 
 - `batch = self.sample()`
 - `loss = self.calc_q_loss(batch)`
 - `self.net.train_step(loss, self.optim, self.lr_scheduler, global_net=self.global_net)`
 - Steps `lr_scheduler` and resets `to_train = 0`
 
 
### `update`

 [slm_lab/agent/algorithm/sarsa.py152-156](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/sarsa.py#L152-L156)

 Calls `explore_var_scheduler.update(self, self.agent.env)` to advance the exploration variable (ε or τ) according to its decay schedule.

## VanillaDQN

 **File:** [slm_lab/agent/algorithm/dqn.py12-159](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L12-L159)

 `VanillaDQN` extends `SARSA`. The key algorithmic change is using the **max over next-state Q-values** (off-policy Bellman target) rather than the on-policy next action's value:

 
```
y_t = r_t + γ · max_a Q(s_t', a)
```

 It also adds a **replay memory** (`Replay`) and a `training_start_step` delay before training begins.

 
### Additional `init_algorithm_params` Fields

 [slm_lab/agent/algorithm/dqn.py51-73](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L51-L73)

 
| Field | Type | Description |
|---|---|---|
| training_batch_iter | int | Gradient updates per sampled batch |
| training_iter | int | Batches to sample per training call |
| training_start_step | int | Minimum experiences before training starts (default: batch_size) |

 
### `calc_q_loss`

 [slm_lab/agent/algorithm/dqn.py93-112](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L93-L112)

 
 - Forward `states` → `q_preds`
 - Forward `next_states` (no grad) → `next_q_preds`
 - `act_q_preds = q_preds.gather(-1, actions)`
 - `max_next_q_preds = next_q_preds.max(dim=-1)` — greedy max
 - `max_q_targets = rewards + γ · (1 - terminateds) · max_next_q_preds`
 - Compute `q_loss = self.net.loss_fn(act_q_preds, max_q_targets)`
 - If memory is `PrioritizedReplay`, compute TD errors and call `self.agent.memory.update_priorities(errors)` [slm_lab/agent/algorithm/dqn.py108-111](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L108-L111)
 
 
### `train` Loop

 [slm_lab/agent/algorithm/dqn.py127-154](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L127-L154)

 More complex than SARSA — supports multiple batch iterations:

 
```
for _ in range(training_iter):
    batch = self.sample()
    for _ in range(training_batch_iter):
        loss = self.calc_q_loss(batch)
        self.net.train_step(loss, ...)
```

 `lr_scheduler.step()` is called once per full training call (not per inner loop iteration).

 
### `training_start_step` and `to_train`

 The `to_train` flag is set by the `Replay` memory's `add_experience` method [slm_lab/agent/memory/replay.py169-173](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/replay.py#L169-L173) only when:

 
 - `seen_size > algorithm.training_start_step`
 - `head % algorithm.training_frequency == 0`

## DQNBase

 **File:** [slm_lab/agent/algorithm/dqn.py162-228](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L162-L228)

 `DQNBase` extends `VanillaDQN` by introducing a **target network** (`self.target_net`) to stabilize training. It also exposes `online_net` and `eval_net` references to support the Double DQN action-selection/value-evaluation split.

 
### Two-Network Setup

 [slm_lab/agent/algorithm/dqn.py179-198](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L179-L198)

 `init_nets` creates both `self.net` and `self.target_net` from the same `net_spec`. After initialization:

 
 - `self.online_net = self.net` — used for action selection in next state
 - `self.eval_net = self.target_net` — used for value evaluation of selected action
 
 Setting `online_net = eval_net = self.net` reduces to the VanillaDQN case.

 
### `calc_q_loss`

 [slm_lab/agent/algorithm/dqn.py200-222](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L200-L222)

 
 - Forward `states` through `self.net` → `q_preds`
 - Forward `next_states` through `self.online_net` (no grad) → `online_next_q_preds`
 - Forward `next_states` through `self.eval_net` (no grad) → `next_q_preds`
 - Select actions greedily from `online_next_q_preds`: `online_actions = online_next_q_preds.argmax()`
 - Evaluate those actions with `eval_net`: `max_next_q_preds = next_q_preds.gather(-1, online_actions)`
 - Compute targets and loss as before
 
 When `online_net = eval_net = target_net`, this is standard DQN. When `online_net = self.net` and `eval_net = self.target_net`, it becomes Double DQN.

 
### `update` — Target Network Refresh

 [slm_lab/agent/algorithm/dqn.py224-228](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L224-L228)

 Calls `net_util.update_target_net(self.net, self.target_net, frame, num_envs)`, which uses `update_type` and `update_frequency` from `net_spec` to decide whether to do a hard replace or Polyak (exponential moving average) update. See [Network Utilities](https://deepwiki.com/kengz/SLM-Lab/5.4.2-network-utilities) for details.

 Sources: [slm_lab/agent/algorithm/dqn.py162-228](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L162-L228)

## Algorithm Comparison

 The following table summarizes how each algorithm differs from the one above it in the hierarchy.

 
| Class | Q-target formula | Networks | Memory | training_start_step |
|---|---|---|---|---|
| SARSA | r + γ·Q(s', a') (on-policy) | net only | OnPolicyBatchReplay | — |
| VanillaDQN | r + γ·max_a Q(s', a) | net only | Replay | Yes |
| DQNBase | Parametric via online_net/eval_net | net + target_net | Replay | Yes |
| DQN | r + γ·target_net(s', argmax_a net(s', a)) | net + target_net | Replay | Yes |
| DoubleDQN | Same as DQN — explicit wiring | net + target_net | Replay | Yes |

## Target Network Updates

 Target network updates are controlled by three `net_spec` fields:

 
| Field | Description |
|---|---|
| update_type | "replace" for hard copy, "polyak" for exponential moving average |
| update_frequency | How often (in frames) to apply the update |
| polyak_coef | Weight for old network in Polyak: θ_target ← τ·θ_target + (1-τ)·θ; 0 means full replace each time |

 These are read by `net_util.update_target_net`, called from `DQNBase.update` [slm_lab/agent/algorithm/dqn.py224-228](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L224-L228)

 `VanillaDQN` and `DQNBase` assert at `init_nets` time that these fields are absent from the spec, enforcing that only `DQN` and its subclasses use target network updates [slm_lab/agent/algorithm/dqn.py78-79](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L78-L79) [slm_lab/agent/algorithm/dqn.py181-182](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/algorithm/dqn.py#L181-L182)

## Exploration: `explore_var_spec`

 All value-based algorithms use a scheduled exploration variable (ε for epsilon-greedy, τ for Boltzmann temperature). The variable is controlled by a `VarScheduler` initialized from `explore_var_spec`.

 **Decay schedule structure:**

 
```

```

 The `name` field maps to a decay function in `policy_util` (e.g. `linear_decay`, `rate_decay`, `no_decay`). Each call to `algorithm.update()` calls `explore_var_scheduler.update(self, self.agent.env)`, which returns the current value and advances the schedule. The value is stored on `self.agent.explore_var` for use by the action policy function.

 For full documentation of `VarScheduler` and the decay functions, see [Algorithm Base Class and Action Selection](https://deepwiki.com/kengz/SLM-Lab/5.2.1-algorithm-base-class-and-action-selection).
