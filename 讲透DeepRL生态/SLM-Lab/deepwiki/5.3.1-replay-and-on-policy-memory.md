  This page documents the concrete memory implementations used by agents in SLM Lab: `Replay`, `OnPolicyReplay`, `OnPolicyBatchReplay`, and `OnPolicyCrossEntropy`. These classes reside in `slm_lab/agent/memory/` and are responsible for storing, managing, and sampling agent experiences during training. For the abstract `Memory` base class interface that all of these implement, and for a module-level overview of the memory system, see [Memory (5.3)](https://deepwiki.com/kengz/SLM-Lab/5.3-memory). For `PrioritizedReplay`, which extends `Replay` with priority-based sampling, see [Prioritized Experience Replay (5.3.2)](https://deepwiki.com/kengz/SLM-Lab/5.3.2-prioritized-experience-replay).

## Abstract Base Class: `Memory`

 [slm_lab/agent/memory/base.py7-33](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/base.py#L7-L33)

 All memory classes inherit from `Memory`. The constructor stores `memory_spec` and a back-reference to the owning `agent`. Three abstract methods define the interface every concrete class must implement:

 
| Method | Signature | Purpose |
|---|---|---|
| reset | reset() | Fully reinitialize memory storage and all tracking variables. |
| update | update(state, action, reward, next_state, done, terminated, truncated) | Accept one timestep of experience. Guards for np.nan values from vectorized env resets. |
| sample | sample() | Return a batch of experiences for algorithm training. |

 The `data_keys` list declared in the base class (`['states', 'actions', 'rewards', 'next_states', 'dones', 'priorities']`) is overridden by subclasses to match what they actually store.

 Sources: [slm_lab/agent/memory/base.py1-33](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/base.py#L1-L33)

## `Replay`

 **File:** [slm_lab/agent/memory/replay.py40-228](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/replay.py#L40-L228)

 `Replay` implements an off-policy circular buffer for use with value-based and off-policy algorithms such as DQN, DoubleDQN, and SAC. Experiences are stored in fixed-size arrays and sampled uniformly at random.

 
### Internal State

 
| Attribute | Type | Description |
|---|---|---|
| batch_size | int | Number of experiences returned per sample() call. |
| max_size | int | Maximum buffer capacity. Oldest entries are overwritten once full. |
| use_cer | bool | Enable Combined Experience Replay. Default False. |
| head | int | Index of the most recently written experience. Starts at -1. |
| size | int | Number of valid entries currently in the buffer (≤ max_size). |
| seen_size | int | Cumulative total experiences ever added (never reset). |
| ns_idx_offset | int | Offset used to locate next_state entries. Equals num_envs for vectorized envs, else 1. |
| ns_buffer | deque | Sliding window holding the most recent ns_idx_offset next-states. Used for boundary-crossing lookups. |
| is_episodic | bool | Always False for Replay. |
| data_keys | list | ['states', 'actions', 'rewards', 'next_states', 'dones', 'terminateds', 'truncateds'] |

 Each data key except `next_states` is stored as a plain Python list of `max_size` slots (pre-allocated as `[None] * max_size`). `next_states` is not stored directly; it is derived on-demand at sample time (see [Next-State Sampling](https://github.com/kengz/SLM-Lab/blob/d3128a8a/Next-State Sampling) below).

 
### `reset()`

 [slm_lab/agent/memory/replay.py110-120](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/replay.py#L110-L120)

 Reinitializes all storage lists to `[None] * max_size`, resets `size` and `head` to their starting values, and clears `ns_buffer`. `seen_size` is **not** reset here because it lives on the object and survives across resets.

 
### `update()` and `add_experience()`

 [slm_lab/agent/memory/replay.py122-173](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/replay.py#L122-L173)

 `update()` is the public interface called by the agent at each timestep. For vectorized environments (`agent.env.is_venv == True`), it unpacks the per-environment tuples and calls `add_experience` once per environment. For single environments, it delegates directly.

 `add_experience()` performs the actual write:

 
 - Advances `head` by one, wrapping modulo `max_size`.
 - Stores `state` and `next_state` as `uint8` if the input dtype is `uint8` (Atari image frames), otherwise as `float16` to save memory.
 - Appends `next_state` to `ns_buffer` (a deque; old entries fall off automatically).
 - Increments `size` (up to `max_size`) and `seen_size`.
 - Sets `algorithm.to_train` if the training conditions are met:
 
 
```
algorithm.to_train = algorithm.to_train or (
    seen_size > training_start_step
    and head % training_frequency == 0
)
```

 The modulo on `head` (not on the clock tick) is used because the clock advances by `num_envs` each step in vectorized mode, which would cause misalignment if used directly.

 
### Next-State Sampling

 [slm_lab/agent/memory/replay.py10-37](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/replay.py#L10-L37)

 `next_states` are not stored as a separate array. Instead, the next state for the experience at index `i` is the state at index `(i + ns_idx_offset) % max_size`. The module-level function `sample_next_states` implements this with a boundary guard:

 When the computed next-state index falls between `head+1` and `head + ns_idx_offset` (i.e., the index has already been overwritten by the circular buffer's advance), the correct value is fetched from `ns_buffer` instead. This ensures that recently-collected next-states remain accessible even after the write head has moved past them.

### `sample()`

 [slm_lab/agent/memory/replay.py175-202](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/replay.py#L175-L202)

 `sample()` draws `batch_size` indices via `sample_idxs()`, then assembles a dict keyed by `data_keys`. `next_states` are computed via `sample_next_states`. All other keys use `util.batch_get` to extract values at the sampled indices.

 
### Combined Experience Replay (CER)

 [slm_lab/agent/memory/replay.py204-227](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/replay.py#L204-L227)

 When `use_cer=True`, `apply_cer()` is called inside `sample_idxs()`. It replaces a trailing subset of the randomly drawn indices with the indices of the most recent experiences (those added since the last call to `sample`). The number of injected recent experiences is `min(new_experiences_since_last_sample, batch_size, size)`. The pointer `last_sample_head` is advanced to track this.

 CER ensures that the latest transition is always included in each training batch, which can help stabilize learning in DQN-family algorithms.

| use_cer | No | false | Enable Combined Experience Replay. |

## `OnPolicyReplay`

 **File:** [slm_lab/agent/memory/onpolicy.py9-99](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L9-L99)

 `OnPolicyReplay` stores complete episodes and returns them all at once for training. The memory is cleared immediately after `sample()` is called to prevent the algorithm from reusing stale, off-policy data. It is designed for algorithms that require full episode trajectories (e.g., REINFORCE with `training_frequency=1`).

 
### Internal State

 
| Attribute | Description |
|---|---|
| is_episodic | Always True. |
| cur_epi_data | Dict of lists accumulating the in-progress episode. Flushed to main storage when episode ends. |
| most_recent | Tuple of the last added (state, action, reward, next_state, done, terminated, truncated). |
| states, actions, ... | Lists of complete episodes; each element is itself a list of per-step values. |
| size | Running count of individual experiences stored. |
| seen_size | Cumulative individual experiences ever seen. |

 
### `add_experience()` and Episode Boundary

 [slm_lab/agent/memory/onpolicy.py68-83](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L68-L83)

 Each call appends all fields to `cur_epi_data`. When `util.epi_done(done)` returns `True` (indicating end of episode):

 
 - The current episode data is appended to each of the top-level lists (`self.states`, etc.).
 - `cur_epi_data` is re-initialized to empty lists.
 - If the number of stored episodes equals `algorithm.training_frequency`, `algorithm.to_train` is set to `1`.
 
 
### `sample()`

 [slm_lab/agent/memory/onpolicy.py85-99](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L85-L99)

 Returns `{k: getattr(self, k) for k in data_keys}` — the entire nested episode store — then immediately calls `reset()`. The returned batch has a nested structure:

 
```
batch = {
    'states':  [[s_epi1_t0, s_epi1_t1, ...], [s_epi2_t0, ...], ...],
    'actions': [[a_epi1_t0, ...], ...],
    ...
}
```

 The algorithm is responsible for flattening or otherwise processing this nested structure.

 
### Spec Reference

 
```

```

 No memory-level parameters are needed. `training_frequency` (number of episodes before training) is set in the `algorithm` spec block.

## `OnPolicyBatchReplay`

 **File:** [slm_lab/agent/memory/onpolicy.py102-145](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L102-L145)

 `OnPolicyBatchReplay` is a subclass of `OnPolicyReplay` with `is_episodic = False`. It stores experiences in **flat lists** rather than nesting them by episode. Training is triggered when the number of accumulated experiences (not episodes) reaches `algorithm.training_frequency`.

 
### Differences from `OnPolicyReplay`

 
| Property | OnPolicyReplay | OnPolicyBatchReplay |
|---|---|---|
| is_episodic | True | False |
| Storage structure | Nested by episode | Flat list |
| to_train trigger | len(self.states) == training_frequency (episode count) | len(self.states) == training_frequency (experience count) |
| Episode tracking | Yes (cur_epi_data) | No |
| Typical use | REINFORCE (1 episode) | SARSA, REINFORCE batch, PPO, A2C |

 
### `add_experience()`

 [slm_lab/agent/memory/onpolicy.py121-131](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L121-L131)

 Appends each field directly to `getattr(self, k)` without any episode nesting. Sets `algorithm.to_train = 1` as soon as `len(self.states) == training_frequency`.

 
### `sample()`

 [slm_lab/agent/memory/onpolicy.py133-145](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L133-L145)

 Delegates to `super().sample()`, which returns all stored data and then calls `reset()`. The returned batch is a flat dict:

 
```
batch = {
    'states':  [s0, s1, s2, ...],
    'actions': [a0, a1, a2, ...],
    ...
}
```

## `OnPolicyCrossEntropy`

 **File:** [slm_lab/agent/memory/onpolicy.py148-200](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L148-L200)

 `OnPolicyCrossEntropy` extends `OnPolicyReplay` to implement the Cross-Entropy Method for episode selection. After collecting a batch of episodes, only those with total rewards at or above the `cross_entropy`-th percentile are returned to the algorithm for training. This focuses updates on the higher-performing rollouts.

 
### `filter_episodes()`

 [slm_lab/agent/memory/onpolicy.py175-188](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L175-L188)

 
 - Computes `accumulated_reward[i] = sum(batch['rewards'][i])` for each episode.
 - Computes `reward_bound = np.percentile(accumulated_reward, cross_entropy * 100)`.
 - Returns only episodes where `accumulated_reward[i] >= reward_bound`.
 
 With `cross_entropy = 0.5`, the bound is the 50th-percentile reward value, so approximately the top half of episodes are retained.

 
### `sample()`

 [slm_lab/agent/memory/onpolicy.py190-200](https://github.com/kengz/SLM-Lab/blob/d3128a8a/slm_lab/agent/memory/onpolicy.py#L190-L200)

 Collects the full batch dict, calls `reset()`, then conditionally calls `filter_episodes` when `cross_entropy < 1.0`. When `cross_entropy == 1.0` (default), no filtering occurs.

```

```

|---|---|---|---|
| cross_entropy | No | 1.0 | Percentile threshold (0–1). Episodes below this reward percentile are discarded. 1.0 disables filtering. |

## Vectorized Environment Handling

 `Replay.update()` explicitly handles the case where `agent.env.is_venv == True` by iterating over the per-environment tuples and calling `add_experience` once per sub-environment per step. `OnPolicyReplay.update()` does not have this loop; it delegates to `add_experience` directly and expects single-environment inputs. The `ns_idx_offset` for `Replay` is set to `num_envs` for vectorized environments so that the next-state offset window correctly spans all environments' contributions within one clock step.

## Algorithm-to-Memory Mapping

 
| Memory Class | is_episodic | Algorithms That Use It | Training Trigger |
|---|---|---|---|
| Replay | False | VanillaDQN, DQN, DoubleDQN, SAC | head % training_frequency == 0 after training_start_step |
| OnPolicyReplay | True | REINFORCE (training_frequency=1) | Episode count == training_frequency |
| OnPolicyBatchReplay | False | REINFORCE (batch), SARSA, ActorCritic, PPO | Experience count == training_frequency |
| OnPolicyCrossEntropy | True | REINFORCE with CE filtering | Episode count == training_frequency |
| PrioritizedReplay | False | DQN variants (with PER) | Same as Replay |
