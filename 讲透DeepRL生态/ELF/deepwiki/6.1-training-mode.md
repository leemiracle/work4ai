## Purpose and Scope

 This document explains the Training Mode of ELF OpenGo, which implements a complete AlphaZero-style reinforcement learning pipeline for training Go AI models. Training Mode coordinates distributed self-play game generation with neural network training in a server-client architecture. This page focuses on how to set up and run the training system, the components involved, and the overall workflow.

 For information about running self-play independently, see [Self-Play Mode](https://deepwiki.com/pytorch/ELF/6.2-self-play-mode). For details about the underlying model training mechanism, see [Model Training](https://deepwiki.com/pytorch/ELF/5.2-model-training). For execution infrastructure, see [Execution Runners](https://deepwiki.com/pytorch/ELF/5.3-execution-runners).

 The Training Mode in ELF OpenGo follows a distributed server-client architecture where a central server manages neural network training while multiple clients generate self-play games.

## Server-Client Setup

 Training Mode uses a distributed setup with:

 
 - **Training Server**: Runs on a machine with GPU(s), loads game data, performs neural network training, and saves model checkpoints
 - **Training Clients**: Run on separate machines, use the latest model to play games against themselves, and send game data back to the server

## Setting Up Training Mode

 
### Prerequisites

 Before starting training, ensure:

 
 - ELF is built following the installation instructions
 - Python path is set using `source scripts/devmode_set_pythonpath.sh`
 - Server and client machines have access to a shared directory (via NFS or similar)
 
 
### Starting the Server

 To start the training server:

 
 - Change to the Go game scripts directory:

 
```
cd scripts/elfgames/go/
```
 - Edit `server_addrs.py` to specify your server's IP address
 - Create a directory for model storage (default is `myserver`)
 - Start the server:

 
```
./start_server.sh
```
 
 The server has been tested on machines with 8 GPUs.

 
### Starting Clients

 To start training clients:

 
 - On each client machine, ensure the shared directory is mounted
 - Run: 
```
./start_client.sh
```
 
 The clients have been tested with up to 2000 clients, each running on a dedicated GPU.

## Training Workflow

 Training in ELF OpenGo follows this workflow:

 
```

```

 
 - **Model Initialization**: The server initializes neural network weights either randomly or from a checkpoint
 - **Self-Play Generation**: Clients load the current model and generate games through MCTS-based self-play
 - **Data Collection**: Game results, moves, and board states are collected and stored in the shared storage
 - **Neural Network Training**: The server samples from collected games and trains the policy and value networks
 - **Model Publication**: Updated models are saved to the shared storage for clients to use

## Component Details

 
### Training Server Components

 The training server consists of several key components:

 
| Component | Purpose |
|---|---|
| Parameter Server | Manages model weights and synchronization |
| Training Loop | Handles the neural network training process |
| Model Updater | Updates models based on training results |
| Model Storage | Saves model checkpoints to shared storage |

 
### Training Client Components

 Each client runs:

 
| Component | Purpose |
|---|---|
| MCTS Engine | Performs Monte Carlo Tree Search to find moves |
| Game Context | Manages the state of Go games |
| Feature Extractor | Converts board positions to neural network inputs |
| Model Interface | Interfaces with the neural network for predictions |

## Monitoring and Debugging

 
### Training Progress

 The training server logs key metrics including:

 
 - Loss values for policy and value networks
 - Gradient norms
 - Model performance metrics
 - Game statistics from self-play
 
 
### Common Issues

 Some common issues when running in Training Mode:

 
 - **Communication failures**: Ensure server IP is correctly set in `server_addrs.py`
 - **Storage access issues**: Verify shared storage is properly mounted on all machines
 - **GPU memory errors**: Adjust batch sizes based on available GPU memory
 - **Training instability**: Check learning rates and model hyperparameters
