  Execution Runners are core components in the ELF OpenGo platform that orchestrate the execution of training and self-play workloads. They provide standardized interfaces for running both single-process and multi-process training sessions, managing the lifecycle of these sessions, and coordinating interactions between game logic and model training.

 The Execution Runners serve as the bridge between high-level training logic and the underlying GameContext interface. For information about the overall training system, see [Training System](https://deepwiki.com/pytorch/ELF/5-training-system), and for model training details, see [Model Training](https://deepwiki.com/pytorch/ELF/5.2-model-training).

 
## Overview

 ELF OpenGo provides two primary execution runners:

 
 - **SingleProcessRun**: A simpler execution runner that operates within a single process, suitable for smaller experiments or environments with limited resources.
 - **MultiProcessRun**: A more complex runner designed for distributed processing across multiple processes, ideal for large-scale training with substantial computational resources.
 
 Both runners handle similar responsibilities but differ in their execution approach and scalability characteristics.

## SingleProcessRun

 The `SingleProcessRun` class manages training execution in a single process, coordinating between the game environment and training callbacks.

 
### Options and Configuration

 `SingleProcessRun` provides several configurable options through the `PyOptionSpec` mechanism:

 
| Option | Description | Default Value |
|---|---|---|
| num_minibatch | Number of minibatches per episode | 5000 |
| num_cooldown | Number of cooldown batches for refreshing batch normalization stats | 0 |
| num_episode | Total number of episodes to run | 10000 |
| tqdm | Toggle progress bar visualization | False |

 These options control the execution flow and can be customized based on specific training requirements.

### Multithreaded Execution

 In addition to the standard execution mode, `SingleProcessRun` also provides a multithreaded execution mode through the `run_multithread()` method. This creates separate threads for training and actor operations:

 
 - **Train Thread**: Executes training operations using `GC.runGroup("train")`
 - **Actor Thread**: Continuously executes actor operations using `GC.runGroup("actor")`
 
 This approach allows for concurrent execution of training and acting steps, potentially improving throughput.

## MultiProcessRun

 The `MultiProcessRun` class implements a more sophisticated execution model that distributes training across multiple processes.

 
### Options and Configuration

 Similar to `SingleProcessRun`, `MultiProcessRun` provides configurable options:

 
| Option | Description | Default Value |
|---|---|---|
| num_minibatch | Number of minibatches per episode | 5000 |
| num_episode | Total number of episodes to run | 10000 |
| num_process | Number of processes to use | 2 |
| tqdm | Toggle progress bar visualization | False |

 The key difference is the `num_process` option, which specifies the number of processes to utilize.

## Common Usage Patterns

 
### Single-Process Training

 The single-process runner is typically used for:

 
 - Development and debugging
 - Small-scale experiments
 - Environments with limited computational resources
 
 Example usage pattern:

 
 - Create a GameContext
 - Configure a SingleProcessRun instance with desired options
 - Set up callbacks for episode management
 - Call run() to start training
 
 
### Multi-Process Training

 The multi-process runner is better suited for:

 
 - Large-scale training
 - Production environments
 - Distributed computing setups
 
 Example usage pattern:

 
 - Create a GameContext and ModelInterface
 - Configure a MultiProcessRun instance with desired options
 - Set up callbacks for remote initialization and processing
 - Call run() to start distributed training
 
 
## Conclusion

 The Execution Runners in ELF OpenGo provide flexible and powerful mechanisms for executing training workloads. By separating the execution logic from the game implementation and model training, they enable a clean architecture that can scale from single-process development to large-scale distributed training.

 The choice between SingleProcessRun and MultiProcessRun depends on the scale of training and available computational resources, but both provide a consistent interface for orchestrating the interactions between game simulation and model training.
