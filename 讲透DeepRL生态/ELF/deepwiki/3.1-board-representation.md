## Overview

 The board representation is the foundation of the game logic in ELF OpenGo. It efficiently encodes the state of a Go game, including stone positions, groups of connected stones, their liberties, game history, and ko situations. The implementation is optimized for performance, using compact data structures and efficient algorithms to support the MCTS search process.

## Coordinate System

 The board uses a 1D coordinate system to represent the 2D grid. This flattens the 2D coordinates into a single value, making array access more efficient.

 
```

```

 A few important coordinate-related macros:

 
 - `OFFSETXY(x, y)`: Converts 2D coordinates to a 1D coordinate
 - `X(c)`: Extracts the x-coordinate from a 1D coordinate
 - `Y(c)`: Extracts the y-coordinate from a 1D coordinate
 - `BOARD_SIZE`: The size of the Go board (typically 19)
 - `BOARD_EXPAND_SIZE`: The expanded board size, including margins
 
 The board also defines special coordinate values:

 
 - `M_PASS`: Represents a pass move
 - `M_RESIGN`: Represents resignation
 - `M_INVALID`: Represents an invalid move

## Core Data Types

 
### Stone

 The `Stone` type (unsigned char) represents the state of an intersection on the board:

 
| Value | Constant | Meaning |
|---|---|---|
| 0 | S_EMPTY | Empty intersection |
| 1 | S_BLACK | Black stone |
| 2 | S_WHITE | White stone |
| 3 | S_OFF_BOARD | Off-board area (margin) |
| 4+ | S_UNKNOWN+ | Special states (rarely used) |

 There are also macros to check stone states:

 
 - `EMPTY(s)`: Checks if a stone is empty
 - `HAS_STONE(s)`: Checks if an intersection has a stone
 - `OPPONENT(s)`: Returns the opponent's stone color

### Info Structure

 Each intersection on the board has an associated `Info` structure containing:

 
```
struct Info {
    Stone color;       // The stone color at this point
    unsigned short id; // The group ID this stone belongs to
    Coord next;        // The next stone in the same group (linked list)
    int last_placed;   // The move number when this stone was placed
};
```

 The `Info` structure allows stones to be linked together in groups and provides historical information.

### Group Structure

 The `Group` structure represents a connected group of stones of the same color:

 
```
struct Group {
    Stone color;        // The color of stones in this group
    Coord start;        // Starting point of the stone linked list
    unsigned char liberties; // Number of liberties (empty adjacent points)
    unsigned short stones;   // Number of stones in this group
};
```

 Groups are key to implementing Go rules efficiently, as they allow fast calculation of liberties and captures.

## The Board Structure

 The `Board` structure is the central data structure that represents the entire Go board:

 
```
struct Board {
    Info infos[BOARD_EXPAND_SIZE * BOARD_EXPAND_SIZE]; // Information for each point
    Group _groups[MAX_GROUP];                         // All stone groups
    Stone _next_player;                               // Next player to move
    int _ply;                                         // Current move number
    Coord _last_move, _last_move2, _last_move3, _last_move4; // Recent moves
    Coord _simple_ko;                                 // Ko point if any
    Stone _simple_ko_color;                           // Player affected by ko
    int _ko_age;                                      // How old the ko is
    short _num_groups;                                // Number of groups on board
    short _w_cap, _b_cap;                             // Captured stones count
    uint64_t _hash;                                   // Board position hash
    unsigned char _removed_group_ids[4];              // Groups removed in last move
    short _num_group_removed;                         // Number of groups removed
    // Other fields for board state and optimization
};
```

 The board is represented as a 1D array of `Info` structures, with dimensions `BOARD_EXPAND_SIZE × BOARD_EXPAND_SIZE` to include margins around the playable area.

## Making Moves

 The process of making a move involves several steps:

 
 - Check if the move is valid with `TryPlay()`
 - If valid, update the board with `Play()`
 
 
```

```

 `TryPlay()` checks if a move is valid by:

 
 - Verifying the move is on the board
 - Checking if the target point is empty
 - Ensuring the move doesn't violate the ko rule
 - Analyzing the liberties to prevent suicide moves
 
 `Play()` updates the board state by:

 
 - Placing the stone
 - Updating affected groups (merging connected groups)
 - Removing captured stones
 - Updating ko status
 - Updating the move history

## Liberty Analysis

 A key part of the board representation is tracking liberties (empty adjacent points) for each group of stones. This is essential for implementing the rules of Go such as captures and preventing suicide moves.

 The `StoneLibertyAnalysis()` function examines the surroundings of a potential move to:

 
 - Count the direct liberties of the stone being placed
 - Identify adjacent groups (both friendly and enemy)
 - Track the liberties of these adjacent groups
 
 This analysis is used by:

 
 - `isSuicideMove()`: Determines if a move would result in the capturing of its own group
 - `isSimpleKoViolation()`: Checks for ko rule violations
 - `isSelfAtari()`: Identifies moves that would put a group in atari (one liberty remaining)
 - `checkLadder()`: Analyzes if a group is caught in a ladder sequence

## Board Features

 The board representation also supports feature extraction for neural network processing via the `BoardFeature` class. This class:

 
 - Extracts features from the current board state
 - Applies transformations like rotations and reflections for data augmentation
 - Produces feature planes that serve as input to the neural network
 
 The features extracted include:

 
 - Liberty maps (tracking liberties for each group)
 - Stone positions (black, white, and empty)
 - Ko positions
 - Move history
 - Distance maps

## Board Analysis Functions

 The board representation includes numerous analysis functions to evaluate game positions:

 
| Function | Purpose |
|---|---|
| isEye() | Checks if a point is completely surrounded by one player's stones |
| isTrueEye() | Checks if a point is a true eye that's safe from capture |
| isSemiEye() | Identifies eyes that could be turned into false eyes |
| isFakeEye() | Detects false eyes that don't count as territory |
| getEyeColor() | Determines which player controls an eye |
| getFastScore() | Provides a quick estimate of the game score |
| getTrompTaylorScore() | Calculates the precise score according to Tromp-Taylor rules |
| isGameEnd() | Checks if the game has ended (two consecutive passes or resignation) |

 These functions are essential for evaluating positions during MCTS search.

## Performance Considerations

 The board representation is designed for performance, with several optimizations:

 
 - Use of compact data types (unsigned short for coordinates, unsigned char for stones)
 - 1D array representation instead of 2D to reduce memory access overhead
 - Linked list representation of groups for efficient traversal
 - Hashing of board positions to detect repeated states
 - Efficient liberty counting and group merging algorithms
 
 These optimizations are crucial for the MCTS algorithm, which needs to simulate thousands of games per second.
