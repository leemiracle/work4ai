## Purpose and Scope

 Self-Play Mode in ELF OpenGo enables AI agents to play against themselves to generate training data for reinforcement learning. This mode is a critical component of the AlphaGo Zero-style training methodology, where the system learns entirely through self-play without human game data. This page explains how to configure and run the self-play client, how game data is generated, and how the system manages model versions.

 For details about using the generated data to train models, see [Training Mode](https://deepwiki.com/pytorch/ELF/6.1-training-mode). For information about playing against external opponents using GTP, see [GTP Mode](https://deepwiki.com/pytorch/ELF/6.3-gtp-mode).

 
## System Architecture

 Self-Play Mode functions as a client in ELF OpenGo's distributed training architecture. Multiple self-play clients can run in parallel, each generating game data by having neural network models play against themselves. The generated data is then used by the training server to improve the models.

## Integration with Training System

 
### Model Version Management

 Self-play mode works with versioned models, where each model is saved with a numeric version identifier. This allows tracking of which model version generated which game data and enables systematic evaluation of model improvements over time.

 
### Data Flow to Training

 The game data generated by self-play clients is sent to the training server, which uses it to improve the neural network model. The updated models are then saved to a shared file system, where they can be loaded by self-play clients.

### Coordination with Training Server

 Self-play clients and the training server coordinate through:

 
 - **Shared File System**: Models are saved by the training server and loaded by self-play clients.
 - **Version Control**: Each model has a version number embedded in its filename.
 - **Game Data Transfer**: Game data generated by self-play is sent to the training server.
 
 This coordination ensures that:

 
 - Self-play clients use up-to-date models
 - The training server receives diverse and relevant game data
 - The overall system continually improves through iterative self-play and training

## Best Practices and Troubleshooting

 
### Performance Considerations

 
 - **GPU Usage**: Self-play is compute-intensive. For best performance, each self-play client should run on a dedicated GPU.
 - **Batch Size**: Larger batch sizes generally improve throughput but require more memory.
 - **Multiple Clients**: For large-scale training, run many self-play clients in parallel (the paper mentions testing with up to 2000 clients).
 
 
### Common Issues

 
 - **Model Loading Errors**: The system will retry loading models if it encounters errors (with a 10-second delay between attempts).
 - **Version Mismatch**: Ensure that the model versions specified exist in the shared file system.
 - **Resource Contention**: If running multiple clients on the same machine, ensure they use different GPUs or have sufficient resources.
