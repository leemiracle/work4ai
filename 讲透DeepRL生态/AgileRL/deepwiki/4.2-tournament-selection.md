# Tournament Selection

  Relevant source files 
 - [agilerl/hpo/tournament.py](https://github.com/AgileRL/AgileRL/blob/03307c7b/agilerl/hpo/tournament.py)
 
  The Tournament Selection system implements the selection mechanism for evolutionary hyperparameter optimization in AgileRL. This component determines which agents from the current population become parents for the next generation, balancing exploration and exploitation through competitive selection and optional elitism.

 For information about the mutation operators applied after selection, see [Mutation System](https://deepwiki.com/AgileRL/AgileRL/4.1-mutation-system). For the broader evolutionary optimization framework, see [Evolutionary Hyperparameter Optimization](https://deepwiki.com/AgileRL/AgileRL/4-evolutionary-hyperparameter-optimization).

 
## Purpose and Core Functionality

 The `TournamentSelection` class manages the selection process that drives evolutionary optimization of RL agents. It implements tournament-based selection where agents compete based on their fitness scores, with special handling for Large Language Model (LLM) agents that require careful memory management.

 The system supports two main selection strategies:

 
 - **Standard Selection**: For traditional RL algorithms with lightweight agent cloning
 - **LLM Selection**: For GRPO agents with memory-efficient distributed processing

## Elitism and Fitness Evaluation

 The elitism mechanism preserves the best-performing agent across generations. The system calculates fitness by averaging the most recent `eval_loop` fitness scores for each agent, then ranks the population accordingly.

 
| Parameter | Purpose | Impact |
|---|---|---|
| tournament_size | Number of agents competing in each tournament | Higher values increase selection pressure |
| elitism | Whether to preserve the best agent | Ensures best solutions aren't lost |
| eval_loop | Number of recent fitness scores to average | Smooths fitness evaluation over time |
| population_size | Total number of agents in population | Balances diversity vs computational cost |

 The elitism function returns three key components:

 
 - **Elite agent**: Best performing agent (or its index for LLMs)
 - **Rank array**: Sorted rankings of all agents
 - **Max ID**: Highest agent index for generating new IDs

## LLM Agent Selection with Memory Management

 LLM agents require special handling due to their large memory footprint and distributed training requirements. The selection process includes explicit memory cleanup and accelerator synchronization.

 
```

```

 Key differences in LLM selection:

 
 - **Index-based tracking**: Uses agent indices instead of direct references
 - **Memory cleanup**: Explicit `clean_up()` calls with synchronization
 - **Distributed coordination**: Broadcast operations across processes
 - **Reference management**: Careful null assignment to free memory
