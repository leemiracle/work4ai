Callbacks are a powerful mechanism for customizing and extending the training process without modifying the core training loop. For information about built-in callbacks, see [Built-in Callbacks](https://deepwiki.com/catalyst-team/catalyst/3.1-built-in-callbacks).

 
## Understanding the Callback System

 The callback system is a core component of Catalyst that enables customization of the training process at specific points. Callbacks work with the Runner system to implement event-driven behavior during training.

 Catalyst organizes callbacks in a clear hierarchy, making it easy to create specialized callbacks for specific purposes.

 All callbacks in Catalyst inherit from the `ICallback` interface, which defines the event methods. The `Callback` abstract class adds the concept of execution order, which is determined by the `CallbackOrder` enumeration. Specialized callback interfaces like `IMetricCallback` and `IOptimizerCallback` provide more specific functionality.

 
## Creating a Basic Custom Callback

 To create a custom callback, you need to inherit from the `Callback` class and implement the event methods you want to use.

 Here's the basic structure of a custom callback:

 
 - Inherit from `Callback` class
 - Initialize with an appropriate order
 - Override the event methods you want to customize

### Accessing Runner State

 The runner object is passed to every callback method, providing access to:

 
 - Model, criterion, optimizer, and scheduler
 - Current batch data and metrics
 - Training state (epoch, batch step, loader information)
 - Experiment metrics across epochs and loaders
 
 All of these elements can be accessed and modified by callbacks to implement custom behavior.

 
## Callback Order and Execution Flow

 Callbacks are executed in a specific order defined by the `CallbackOrder` enumeration. This ensures that dependent operations (like backward pass after loss calculation) happen in the correct sequence.

 
| Order Value | Callback Type | Purpose |
|---|---|---|
| 0 | Internal | Catalyst internal operations |
| 10 | Metric | Metrics and losses computation |
| 20 | MetricAggregation | Aggregating metrics (e.g., summing losses) |
| 30 | Backward | Backward pass for gradient computation |
| 40 | Optimizer | Optimizer step, updating model parameters |
| 50 | Scheduler | Learning rate scheduling |
| 50 | Checkpoint | Model checkpointing |
| 100 | External | Custom user logic |

 Sources: [catalyst/core/callback.py48-88](https://github.com/catalyst-team/catalyst/blob/e99f9065/catalyst/core/callback.py#L48-L88)

 When multiple callbacks with the same order are registered, their relative execution order is determined by their registration order in the Runner.

## Conclusion

 Creating custom callbacks in Catalyst is a powerful way to extend the framework's functionality without modifying its core components. By understanding the callback lifecycle and correctly implementing event handlers, you can add custom behavior to any part of the training process.

 Remember these key points when creating custom callbacks:

 
 - Choose the appropriate base class (`Callback` or a specialized interface)
 - Set the correct order to ensure proper execution sequence
 - Implement only the event methods you need
 - Use the runner object to access and modify training state
 
 Custom callbacks allow you to implement sophisticated training techniques, custom metrics, visualizations, and integrations with external systems, making Catalyst a highly flexible framework for deep learning research and development.
