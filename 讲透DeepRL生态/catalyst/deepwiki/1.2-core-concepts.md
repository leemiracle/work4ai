  This page explains the fundamental concepts and architecture of the Catalyst framework. Catalyst is a PyTorch framework for Deep Learning Research and Development that focuses on reproducibility, rapid experimentation, and codebase reuse. The core concepts described here form the foundation upon which the rest of the framework is built.

 For specific implementation details of the Runner system, see [Runner System](https://deepwiki.com/catalyst-team/catalyst/2-runner-system). For callbacks, see [Callback System](https://deepwiki.com/catalyst-team/catalyst/3-callback-system).

## The Runner

 The Runner is the central component of Catalyst that orchestrates the entire training process. It manages the model, data loaders, criterion, optimizer, scheduler, and callbacks.

 
### Runner Interface and Implementations

 
```

```

 Sources: [catalyst/core/runner.py:40-426], [catalyst/runners/runner.py:34-503], [catalyst/runners/supervised.py:24-261]

 
### Key Runner Components

 The Runner manages the following components:

 
 - **Model**: The neural network to be trained
 - **Engine**: Abstracts hardware details (CPU, GPU, multi-GPU, TPU)
 - **Data Loaders**: Provide data for training, validation, and inference
 - **Criterion**: Loss function for computing the training objective
 - **Optimizer**: Algorithm for updating model parameters
 - **Scheduler**: Adjusts optimizer parameters (like learning rate) during training
 - **Callbacks**: Custom logic executed at different points in the training loop
 - **Loggers**: Log metrics, hyperparameters, images, and artifacts
 
 Sources: [catalyst/core/runner.py:68-86]

 
### Data Flow in Runner

 The Runner manages three key data containers:

 
 - **batch**: Contains model inputs, outputs, and targets
 - **batch_metrics**: Metrics computed for the current batch
 - **loader_metrics**: Aggregated metrics for the current loader
 - **epoch_metrics**: Aggregated metrics for the current epoch
 
 Sources: [catalyst/core/runner.py:79-85]

 Callbacks are the primary mechanism for customizing the training process in Catalyst. They are executed at specific points in the training loop and can modify the runner's state.

### Specialized Callbacks

 Catalyst provides several specialized callback interfaces for common tasks:

 
 - **IMetricCallback**: For computing metrics
 - **ICriterionCallback**: For computing losses
 - **IBackwardCallback**: For backward pass
 - **IOptimizerCallback**: For optimization steps
 - **ISchedulerCallback**: For scheduling learning rates
 - **ICheckpointCallback**: For model checkpointing

### Common Callback Implementations

 Catalyst provides many built-in callback implementations for common tasks:

 
 - **CriterionCallback**: Computes loss using model outputs and targets
 - **BackwardCallback**: Performs backward pass based on loss
 - **OptimizerCallback**: Updates model parameters based on gradients
 - **SchedulerCallback**: Adjusts learning rate based on scheduler
 - **CheckpointCallback**: Saves model checkpoints based on metrics
 - **MetricCallbacks**: Compute various metrics (accuracy, precision, recall, etc.)

## SupervisedRunner: A Key Concept

 The `SupervisedRunner` is a specialized implementation of `Runner` for supervised learning tasks. It handles the forward and backward pass, loss computation, and optimization automatically.

 
```

```

 Sources: [catalyst/runners/supervised.py:24-261]

 
### SupervisedRunner Components

 The `SupervisedRunner` manages the following keys:

 
 - **input_key**: Key in the batch for model input (default: "features")
 - **output_key**: Key in the batch for model output (default: "logits")
 - **target_key**: Key in the batch for targets (default: "targets")
 - **loss_key**: Key in batch_metrics for loss (default: "loss")
 
 The typical data flow in `SupervisedRunner` is:

 
 - Get input from batch using `input_key`
 - Pass input to model to get output
 - Store output in batch using `output_key`
 - Compute loss using output and target
 - Store loss in batch_metrics using `loss_key`
 - (If training) Perform backward pass and optimization
 
 Sources: [catalyst/runners/supervised.py:60-74], [catalyst/runners/supervised.py:152-161]

 
## Putting It All Together

 When using Catalyst, the typical workflow involves:

 
 - Define your model, criterion, optimizer, and data loaders
 - Choose a Runner (usually `SupervisedRunner`)
 - Configure callbacks for metrics, checkpointing, etc.
 - Call `runner.train()` to start training

## Conclusion

 Catalyst's core concepts revolve around an event-driven architecture that provides flexibility and extensibility for deep learning research and development. The Runner orchestrates the training process, while Callbacks enable customization at specific points in the training loop. The Engine system abstracts hardware details, and the Logger system provides unified logging across different backends.

 Understanding these core concepts is essential for effectively using Catalyst and leveraging its full potential for your deep learning projects.
