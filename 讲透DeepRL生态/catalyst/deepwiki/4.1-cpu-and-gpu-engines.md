  This document explains Catalyst's CPU and GPU engine implementations, which provide hardware abstraction for training models on different computing devices. These engines are part of Catalyst's hardware abstraction system that allows seamless switching between different hardware configurations. For distributed training options, see [Distributed Training](https://deepwiki.com/catalyst-team/catalyst/4.2-distributed-training), and for TPU and specialized engines, see [XLA and Special Engines](https://deepwiki.com/catalyst-team/catalyst/4.3-xla-and-special-engines).

 Catalyst uses an engine-based architecture to abstract away hardware-specific details from the training code. This allows users to write device-agnostic code and easily switch between different hardware configurations by simply changing the engine parameter.

## Engine Functionality

 When an engine is initialized, it sets up the appropriate device configurations. During training, it provides several key functionalities:

 
 - **Device Management:** The engine handles moving tensors to the right device (CPU or GPU)
 - **Memory Management:** The engine optimizes memory usage for the selected device
 - **Backward Operation:** The engine provides a standardized way to perform the backward pass
 - **Metric Reduction:** In distributed settings, the engine handles metric synchronization

## Performance Considerations

 When choosing between CPU and GPU engines, consider:

 
 - **Dataset Size:** For small datasets, the overhead of transferring data to GPU might outweigh the benefits
 - **Model Size:** Small models might not benefit significantly from GPU acceleration
 - **Memory Usage:** GPUs have limited memory compared to system RAM
 - **Development Workflow:** CPU mode is often more convenient for debugging and initial development
 
 Catalyst's benchmarking tools can help compare performance between CPU and GPU engines for your specific use case.
