  This page documents the `IRunner` interface, the core abstraction in Catalyst that orchestrates deep learning experiment execution. It defines how to run experiments, epochs, data loaders, and process individual batches. For implementations of this interface, see [Supervised and Custom Runners](https://deepwiki.com/catalyst-team/catalyst/2.2-supervised-and-custom-runners).

 
## Introduction

 `IRunner` serves as the central coordinator in the Catalyst framework, connecting models, data, callbacks, and infrastructure. It provides a standardized way to execute training loops while allowing flexibility in how specific components are implemented.

## Interface Definition

 The `IRunner` interface inherits from both `ICallback` and `ILogger`, allowing it to both process events during training and log metrics and artifacts.

 
### Core Properties

 
| Property | Type | Description |
|---|---|---|
| seed | int | Experiment's seed for reproducibility |
| hparams | OrderedDict | Hyperparameters for the current run |
| num_epochs | int | Number of epochs in the experiment |
| model | RunnerModel | The model being trained |
| criterion | RunnerCriterion | Loss function used for training |
| optimizer | RunnerOptimizer | Optimizer for updating model parameters |
| scheduler | RunnerScheduler | Learning rate scheduler |
| engine | Engine | Hardware abstraction layer |
| loaders | Dict[str, DataLoader] | Data loaders for training/validation |
| callbacks | Dict[str, Callback] | Callbacks for customizing training flow |
| loggers | Dict[str, ILogger] | Loggers for tracking metrics and artifacts |

## Experiment Lifecycle

 The `IRunner` interface defines a complete event flow for deep learning experiments, with clearly defined stages that callbacks can hook into.

 
```

```

 The lifecycle methods correspond to these stages:

 
 - `on_experiment_start/end`: Setup/teardown for the entire experiment
 - `on_epoch_start/end`: Preparation/finalization for each epoch
 - `on_loader_start/end`: Initialization/cleanup for each data loader
 - `on_batch_start/end`: Processing before/after each batch
 - `on_exception`: Handling of any exceptions during execution

## Metrics Tracking System

 `IRunner` maintains a hierarchical metrics tracking system that operates at multiple levels of granularity:

 
```

```

 
### Metrics Structure

 
 - `batch_metrics`: Metrics for the current batch (e.g., loss value)
 - `loader_metrics`: Aggregated metrics across all batches in a loader
 - `epoch_metrics`: A dictionary mapping loader keys to their metrics for the current epoch
 - `experiment_metrics`: A dictionary mapping epoch numbers to all metrics from that epoch
 
 The `IRunner` also implements logging methods to record these metrics through attached loggers:

 
 - `log_metrics()`: Logs batch, loader, or epoch metrics
 - `log_image()`: Logs images to available loggers
 - `log_artifact()`: Logs arbitrary artifacts (files)
 - `log_hparams()`: Logs hyperparameters

## Runner Execution Flow

 The main execution flow of the `IRunner` is managed by a set of nested methods:

 
 - `run()`: The public API method called by users
 - `_run()`: Sets up the engine and spawns the local run
 - `_run_local()`: Executes the experiment on a specific device
 - `_run_experiment()`: Loops through epochs
 - `_run_epoch()`: Loops through loaders
 - `_run_loader()`: Loops through batches
 - `handle_batch()`: Processes individual batches (to be implemented)
 
 This hierarchical structure allows for clean separation of concerns and makes it easier to implement custom runners that modify only specific parts of the execution flow.

## Implementing a Custom Runner

 To create a custom runner, you need to implement the required abstract methods and customize the experiment flow as needed. At minimum, you must implement:

 
 - `get_engine()`: Return the hardware acceleration engine
 - `get_loaders()`: Return data loaders
 - `get_model()`: Return the model to train
 - `handle_batch(batch)`: Process a single batch of data

## Relationship with Other Components

 The `IRunner` interface interacts with several other core components of Catalyst:

 
```

```

 
 - **Engine**: Abstracts hardware details (CPU, GPU, multi-GPU, TPU) and provides methods for device placement, forward/backward passes, etc.
 - **Callbacks**: Extend the runner's functionality at specific points in the experiment lifecycle
 - **Loggers**: Record metrics, images, and artifacts during training
 - **Metrics**: Track and compute performance metrics
 
 This architecture follows a composition-based design, where the runner orchestrates the interaction between components rather than implementing all functionality itself.

## Summary

 The `IRunner` interface is the backbone of the Catalyst framework, providing a structured yet flexible way to implement deep learning training loops. By separating the experiment execution logic from the specific implementation details, it enables:

 
 - Clean abstraction of hardware acceleration details
 - Event-driven architecture for customizing behavior
 - Hierarchical metrics tracking and logging
 - Modular composition of training components
 
 The interface is designed to be extensible, allowing users to create custom runners for specific use cases while maintaining a consistent structure and API.
