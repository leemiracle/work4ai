## Purpose and Scope

 This page documents the experience buffer system used to store and manage agent trajectories during training in MAgent. It covers the `EpisodesBuffer` and `EpisodesBufferEntry` classes, their data structures, and how they integrate with the training workflow to accumulate transitions for batch learning.

 For information about how these buffers are used within the broader training loop, see [Training Workflow](https://deepwiki.com/geek-ai/MAgent/4.1-training-workflow). For details on how different RL algorithms consume sampled data, see [RL Algorithms](https://deepwiki.com/geek-ai/MAgent/4.3-rl-algorithms). For parallel training that uses these buffers across multiple processes, see [ProcessingModel and Parallelism](https://deepwiki.com/geek-ai/MAgent/4.2-processingmodel-and-parallelism).

## Overview of Experience Storage

 MAgent uses an episode-based replay buffer system designed for multi-agent environments where:

 
 - Each agent has its own trajectory (episode) that may terminate at different times
 - Thousands of agents can be active simultaneously
 - Off-policy algorithms (DQN, DRQN) require storing complete episodes for batch training
 - On-policy algorithms (A2C) may use buffers for advantage estimation
 
 The buffer system consists of two main classes:

 
| Class | Purpose | Key Responsibility |
|---|---|---|
| EpisodesBufferEntry | Single agent episode | Stores views, features, actions, rewards for one agent |
| EpisodesBuffer | Multi-agent buffer | Manages dictionary of entries, capacity control, sampling |

 **Key Design Decisions**:

 
 - **Agent-centric storage**: Each agent ID maps to its own episode entry
 - **Capacity limiting**: Buffer stops accepting new agents once capacity is reached
 - **Random insertion order**: When buffer is not full, agents are added in random order to avoid bias
 - **No eviction**: Once full, existing entries persist until reset

### Implementation Details

 The method has two paths depending on whether the buffer is full:

 **When buffer is not full** [python/magent/utility.py54-66](https://github.com/geek-ai/MAgent/blob/2144dbd4/python/magent/utility.py#L54-L66):

 
 - Processes agents in **random order** using `np.random.permutation(len(ids))`
 - Creates new entries for unseen agent IDs
 - Once capacity is reached, sets `is_full = True`
 - Randomization prevents bias toward agents that appear early in simulation
 
 **When buffer is full** [python/magent/utility.py47-52](https://github.com/geek-ai/MAgent/blob/2144dbd4/python/magent/utility.py#L47-L52):

 
 - Processes agents in **sequential order** (faster, no need to randomize)
 - Only updates existing entries
 - Ignores new agent IDs (no new entries created)
 
 This optimization avoids the cost of random permutation when the buffer is already at capacity.

## Capacity Management

 The buffer capacity is a critical hyperparameter that affects:

 
| Aspect | Impact |
|---|---|
| Memory usage | Each entry stores multiple timesteps of observations (can be large for vision) |
| Training batch diversity | Higher capacity = more diverse agents in training batch |
| Sampling bias | Once full, only existing agents are updated (recent agents may be underrepresented) |

### Memory Efficiency Considerations

 **Storage per entry**:

 
 - Views: `(num_steps, view_height, view_width, channels)` - typically `(T, 13, 13, 5)` = ~8KB per step
 - Features: `(num_steps, feature_dim)` - typically `(T, 9)` = ~72 bytes per step
 - Actions/rewards: Minimal overhead
 
 **For 5,000 agents over 100 steps**: ~4GB of view data alone

 **Mitigation strategies**:

 
 - Use lower capacity for large view spaces
 - Reset buffer more frequently
 - Consider frame stacking or compression for vision-based observations

## Parallel Buffer Management

 When using `ProcessingModel` for parallel training, each model process maintains its own buffer:

 
```

```

 **Diagram: Parallel Buffer Architecture**

 
### Key Points

 
 - **Process Isolation**: Each model has its own buffer in its own process
 - **Independent Training**: Models train on their own collected experiences
 - **No Sharing**: Buffers are not shared between processes (no synchronization overhead)
 - **Group-Specific**: Each buffer only stores experiences for its assigned group
 
 This design enables true parallelism where multiple models can simultaneously record experiences and train without contention.

## Best Practices

 
### Buffer Capacity Sizing

 
| Scenario | Recommended Capacity | Rationale |
|---|---|---|
| DQN with small observations | 1M transitions | Standard replay buffer size |
| DRQN with sequences | 5K-10K episodes | Need complete episodes for RNN training |
| A2C (on-policy) | 1-2K episodes | Only need current rollout data |
| Large-scale (1000+ agents) | 5K-20K agents | Balance diversity with memory |

 
### When to Reset Buffer

 **Never reset** (accumulate across episodes):

 
 - Off-policy algorithms (DQN, DRQN) with replay memory
 - When using experience replay for sample efficiency
 
 **Reset after each episode**:

 
 - On-policy algorithms (A2C, PPO)
 - When episode-level statistics are needed
 
 **Reset periodically**:

 
 - To prevent old, suboptimal trajectories from dominating training
 - When memory is constrained
 
 
### Recording Efficiency

 **Do**:

 
 - Use `block=False` for `sample_step()` to avoid blocking main loop
 - Process multiple models in parallel
 - Preallocate buffer capacity appropriately
 
 **Don't**:

 
 - Call `reset()` unnecessarily (it's a full dictionary clear)
 - Store raw observations if you can compress them
 - Create new buffers frequently (reuse existing ones)

## Summary

 The MAgent experience buffer system provides:

 
 - **EpisodesBufferEntry**: Agent-level episode storage with views, features, actions, rewards
 - **EpisodesBuffer**: Multi-agent buffer with capacity management and random insertion
 - **Efficient recording**: Optimized paths for full vs. non-full buffers
 - **Batch retrieval**: Simple `episodes()` method for training
 - **Evaluation sampling**: `sample_observation()` for generating fixed test sets
 - **Parallel support**: Per-process buffers for independent model training
 
 The buffer design balances **simplicity** (dictionary-based storage), **efficiency** (random insertion only when needed), and **scalability** (capacity-limited to prevent memory overflow) for large-scale multi-agent reinforcement learning.
