## Purpose and Scope

 This document explains how to train a single reinforcement learning model against copies of itself using self-play. In self-play, the same model instance controls agents on both sides of a competitive or cooperative scenario, learning from the interactions between its own policies at different stages of training.

 This page focuses specifically on the single-model self-play implementation pattern. For training multiple distinct models competitively, see [Multi-Agent Training Strategies](https://deepwiki.com/geek-ai/MAgent/4.4-multi-agent-training-strategies). For general training workflow concepts, see [Training Workflow](https://deepwiki.com/geek-ai/MAgent/4.1-training-workflow). For parallel training with multiple models, see [ProcessingModel and Parallelism](https://deepwiki.com/geek-ai/MAgent/4.2-processingmodel-and-parallelism).

## What is Self-Play

 Self-play is a training paradigm where a single model plays against itself, acting as both protagonist and antagonist in competitive scenarios or as multiple cooperating agents in collaborative tasks. The model improves iteratively by learning from games played against progressively stronger versions of itself.

 
### Key Characteristics

 
| Aspect | Self-Play | Multi-Model Training |
|---|---|---|
| Model Instances | Single shared model | Separate model per group |
| Memory Usage | Shared replay buffer | Independent buffers |
| Learning Dynamics | Co-evolution with self | Competition between distinct policies |
| Convergence | Can reach Nash equilibrium | May exhibit cyclical dynamics |
| Implementation | Simpler, less overhead | More complex, parallelizable |

 
### When to Use Self-Play

 **Recommended for:**

 
 - Initial policy bootstrapping before competitive training
 - Symmetric scenarios where both sides have identical capabilities
 - Memory-constrained environments
 - Exploring basic strategy development
 
 **Not recommended for:**

 
 - Asymmetric scenarios (predator-prey with different capabilities)
 - When you need diverse opponent strategies
 - Large-scale parallelism requirements

## Training Considerations

 
### Exploration Strategy

 Self-play requires careful exploration management to avoid converging to suboptimal strategies:

 
```

```

 This creates an epsilon-greedy schedule:

 
 - **Rounds 0-700**: ε = 1.0 → 0.2 (high exploration, discovering basic strategies)
 - **Rounds 700-1400**: ε = 0.2 → 0.05 (exploitation with some exploration)
 - **Rounds 1400+**: ε = 0.05 (mostly exploitation, fine-tuning)
 
 **Rationale**: Early high exploration prevents the model from converging to trivial strategies (e.g., "always move forward"). Later reduction allows exploitation of learned strategies.

 
### Convergence Dynamics

 
| Phase | Epsilon | Behavior | Purpose |
|---|---|---|---|
| Early (0-700) | 1.0 → 0.2 | Random to semi-random | Strategy discovery |
| Middle (700-1400) | 0.2 → 0.05 | Mostly exploitation | Strategy refinement |
| Late (1400+) | 0.05 | Near-greedy | Policy stabilization |

 
### Symmetry Breaking

 In symmetric scenarios, self-play can get stuck in symmetric strategies. Consider:

 
 - **Initial randomness**: High epsilon early on
 - **Map generation variation**: Alternate agent placement between rounds
 - **Curriculum learning**: Gradually increase scenario complexity

 This ensures the model experiences both spatial positions equally.

 
### Memory Efficiency

 Self-play is more memory-efficient than multi-model training:

 
 - **Single model**: ~1x parameter memory
 - **Single buffer**: ~1x replay memory
 - **No IPC overhead**: No inter-process communication

## Advantages and Limitations

 
### Advantages of Self-Play

 **Memory Efficiency**:

 
 - Single model parameter set (typically 1-10 MB)
 - Single replay buffer (configurable, but can be larger than multi-model)
 - No inter-process communication overhead
 
 **Simplicity**:

 
 - Simpler code structure
 - Easier debugging (single model state)
 - No process synchronization complexity
 
 **Curriculum Generation**:

 
 - Automatically generates increasingly difficult opponents
 - Avoids manual opponent design
 - Can discover novel strategies
 
 
### Limitations of Self-Play

 **Convergence Issues**:

 
 - May converge to weak Nash equilibria
 - Can get stuck in cyclic strategies (rock-paper-scissors dynamics)
 - Symmetry can lead to uninteresting policies
 
 **Lack of Diversity**:

 
 - Only learns to counter its own strategies
 - May not generalize to different opponents
 - Limited exploration of strategy space
 
 **No Parallelism**:

 
 - Cannot leverage multi-process parallelism
 - Inference is sequential across groups
 - Training is single-threaded
 
 **When to Transition**:

 Consider switching from self-play to multi-model training when:

 
 - Self-play converges to suboptimal behavior
 - You need to train against diverse opponent strategies
 - Computational resources allow parallel training
 - You want to maintain historical opponent snapshots

 - **Q-values**: Should stabilize

 When ready to move beyond self-play:

 
 - Save the self-play checkpoint
 - Load it as initial weights for multi-model training
 - Use self-play model as frozen opponent while training new model
 - Gradually increase opponent diversity
