## Purpose and Scope

 This page describes the action space in MAgent: the discrete actions available to agents, how they are structured and indexed, and how to set and execute actions during simulation. For information about how agents observe the environment, see [Observation Spaces](https://deepwiki.com/geek-ai/MAgent/2.3-observation-spaces). For details on how different agent types are configured with different action capabilities, see [Agent Types and Groups](https://deepwiki.com/geek-ai/MAgent/2.2-agent-types-and-groups).

 
---

 
## Overview

 MAgent uses **discrete action spaces**. Each agent selects one action per simulation step from a predefined set of valid actions. Actions fall into three categories:

 
 - **Move actions**: Move to an adjacent grid cell within the agent's movement range
 - **Turn actions**: Rotate the agent's facing direction (only if `turn_mode` is enabled)
 - **Attack actions**: Attack a target cell within the agent's attack range
 
 The total action space size for a given agent type equals the sum of valid actions across all three categories. For example, an agent with 13 move positions, 2 turn options, and 8 attack positions has 23 total actions.

## Action Space Composition

 
### Action Indexing Scheme

 Actions are indexed sequentially across the three action types, with specific base indices separating each category:

 
```
[0 ... move_base)          → Move actions
[move_base ... turn_base)  → Turn actions (if turn_mode enabled)
[turn_base ... attack_base) → (no actions in this range)
[attack_base ... total)    → Attack actions
```

 The boundaries are stored in the `AgentType` structure as `move_base` (always 0), `turn_base`, and `attack_base`.

## Action Types

 
### Move Actions

 Move actions allow agents to move to adjacent grid cells. The set of valid move positions is determined by the agent's `move_range` (a `Range` object, typically `CircleRange`).

 **Key Characteristics:**

 
 - **Index range**: `[0, turn_base)` where `turn_base` equals the number of valid move positions
 - **Direction-relative**: Move deltas are relative to the agent's current facing direction
 - **Collision handling**: If a move would place the agent on an occupied cell, the move is blocked
 
 **Direction Transformation:**

 The move range defines deltas in the agent's local coordinate system. These are transformed based on the agent's facing direction before execution:

 
| Agent Direction | Delta Transformation |
|---|---|
| NORTH | (dx, dy) |
| SOUTH | (-dx, -dy) |
| WEST | (dy, -dx) |
| EAST | (-dy, dx) |

### Turn Actions

 Turn actions rotate the agent's facing direction. This action type is only available when `turn_mode` is enabled in the environment configuration.

 **Key Characteristics:**

 
 - **Index range**: `[turn_base, attack_base)`
 - **Typically 2 actions**: Turn left (counterclockwise) and turn right (clockwise)
 - **Action encoding**: `act - turn_base` yields 0 (turn right) or 1 (turn left)
 - **Direction delta**: `dir = (act - turn_base) * 2 - 1` gives -1 (right) or +1 (left)
 
 **Turn Direction Mapping:**

 
```
Action Index (relative to turn_base) → Direction Delta
0 → -1 (turn right/clockwise)
1 → +1 (turn left/counterclockwise)
```

 Turn actions modify the agent's direction without changing position. The new direction is computed modulo the number of valid directions (typically 4: NORTH, SOUTH, EAST, WEST).

### Attack Actions

 Attack actions allow agents to attack a target cell within their attack range. The set of valid attack positions is determined by the agent's `attack_range`.

 **Key Characteristics:**

 
 - **Index range**: `[attack_base, action_space_size)`
 - **Action encoding**: `act - attack_base` gives the attack position index
 - **Target determination**: The attack range maps action indices to relative positions
 - **Rewards**: Agents receive rewards based on what they hit (other agents, walls, empty cells)
 
 **Attack Resolution:**

 
 - **Target Identification**: `map.get_attack_obj()` determines what occupies the target cell
 - **Damage Application**: If an agent is hit, `map.do_attack()` reduces its HP
 - **Reward Calculation**: 
 - Hit an enemy agent: Receive `attack_in_range_reward` (typically positive)
 - Kill an enemy agent: Receive `kill_reward` (typically large positive)
 - Hit nothing: Receive `attack_penalty` (typically negative)
 - Agent dies: Receives `dead_penalty`

### Large Map Optimization

 For large maps (> 99x99 cells), MAgent uses spatial partitioning to enable parallel action execution:

 
 - **Spatial buffers**: Move and turn actions are partitioned into `NUM_SEP_BUFFER` separate buffers based on agent x-coordinate
 - **Boundary buffer**: Actions near partition boundaries use a separate `move_buffer_bound` or `turn_buffer_bound`
 - **Parallel processing**: Each spatial partition can be processed in parallel during `step()`
 
 The partitioning strategy:

 
 - Map is divided into vertical strips of width `bandwidth = (width + NUM_SEP_BUFFER - 1) / NUM_SEP_BUFFER`
 - Agents with `x % bandwidth ∈ [4, bandwidth-4]` go to spatial buffer `x / bandwidth`
 - Agents with `x % bandwidth ∈ [0, 4) ∪ [bandwidth-4, bandwidth)` go to boundary buffer
 
 **Sources:** [src/gridworld/GridWorld.cc407-454](https://github.com/geek-ai/MAgent/blob/2144dbd4/src/gridworld/GridWorld.cc#L407-L454)

## Action Execution Order

 During `env.step()`, actions are executed in a specific order:

 
 - **Attack actions** (parallel execution with shuffling)
 - **Turn actions** (parallel execution by spatial region)
 - **Move actions** (parallel execution by spatial region)
 
 This ordering ensures that:

 
 - Attacks resolve before agents move away
 - Turning happens before movement, so new direction affects move delta transformation
 - Dead agents are filtered out before movement

## Action Constraints and Validation

 
### Invalid Actions

 MAgent does not perform explicit validation of action indices in `set_action()`. It is the user's responsibility to ensure:

 
 - Action indices are in range `[0, action_space_size)`
 - Actions array length equals number of agents in the group
 
 Providing invalid actions can lead to undefined behavior or segmentation faults.

 
### Dead Agents

 Dead agents' actions are ignored during execution. The action execution loops check `agent->is_dead()` before processing each action.

## Summary

 **Action Space Structure:**

 
| Component | Index Range | Description |
|---|---|---|
| Move Actions | [0, turn_base) | Move to adjacent cells based on move_range |
| Turn Actions | [turn_base, attack_base) | Rotate facing direction (if turn_mode enabled) |
| Attack Actions | [attack_base, total) | Attack cells within attack_range |

 **Key API Methods:**

 
| Method | Purpose |
|---|---|
| env.set_action(handle, actions) | Set actions for all agents in a group |
| env.get_info(handle, 'action_space') | Query action space size |
| env.get_info(handle, 'attack_base') | Query attack action boundary |
| env.get_info(handle, 'view2attack') | Map view cells to attack actions |

 **Execution Order:** Attack → Turn → Move
