## Spatial Partitioning

 Spatial partitioning divides the map into vertical strips to enable parallel action processing. Each strip is processed by a separate thread, eliminating race conditions for agents in non-overlapping regions.

 
### Partition Strategy

 The map is divided along the x-axis with a computed bandwidth:

 
```
bandwidth = (width + NUM_SEP_BUFFER - 1) / NUM_SEP_BUFFER
```

 Each agent's actions are assigned to a buffer based on its x-coordinate:

 
```

```

 **Boundary Region Definition:** Agents within 4 cells of a partition boundary are processed serially to prevent race conditions when agents from different partitions interact.

## Memory Management

 Efficient memory management is crucial for million-agent simulations. MAgent uses several strategies to minimize allocation overhead and cache misses.

 
### Agent Memory Layout

 
```

```

 
### Buffer Organization for Large Maps

 
| Buffer Type | Count | Purpose | Allocation Timing |
|---|---|---|---|
| move_buffers | NUM_SEP_BUFFER | Spatial move action partitioning | reset() if large_map_mode |
| turn_buffers | NUM_SEP_BUFFER | Spatial turn action partitioning | reset() if large_map_mode |
| move_buffer_bound | 1 | Boundary region moves | Always allocated |
| turn_buffer_bound | 1 | Boundary region turns | Always allocated |
| attack_buffer | 1 | All attacks (not spatially partitioned) | Always allocated |

 **Rationale for Attack Buffer:** Attacks have potentially long range and can target agents in different spatial partitions, so they cannot be safely partitioned without complex dependency analysis.

 **Sources:** [src/gridworld/GridWorld.cc66-69](https://github.com/geek-ai/MAgent/blob/2144dbd4/src/gridworld/GridWorld.cc#L66-L69) [src/gridworld/GridWorld.cc82-83](https://github.com/geek-ai/MAgent/blob/2144dbd4/src/gridworld/GridWorld.cc#L82-L83) [src/gridworld/GridWorld.cc411-437](https://github.com/geek-ai/MAgent/blob/2144dbd4/src/gridworld/GridWorld.cc#L411-L437)

## OpenMP Thread Configuration

 The number of OpenMP threads significantly impacts performance. MAgent's testing scripts configure `OMP_NUM_THREADS` based on agent count.

```

```

 **Default Behavior:** MAgent automatically sets `OMP_NUM_THREADS` to `CPU_COUNT / 2` when loading the C++ library, balancing parallelism with system responsiveness.

 **Testing Configuration:**

 
 - For agent counts < 1M: `OMP_NUM_THREADS=8`
 - For agent counts ≥ 1M: `OMP_NUM_THREADS=16`

| Thread Count | Agent Count | Typical Behavior |
|---|---|---|
| 1 | Any | Serial execution, minimal overhead |

## Practical Scaling Limits

 
### Computational Limits

 
```

```

 
### Memory Requirements

 **Per-Agent Memory (Approximate):**

 
 - Agent object: ~200 bytes
 - Observation buffer: `view_height × view_width × n_channel × 4` bytes (float32)
 - Feature buffer: `feature_size × 4` bytes
 
 **Example:** For 1M agents with 13×13 view, 10 channels, 50 feature size:

 
 - Agent objects: 200 MB
 - Observations (if all extracted): ~67 GB
 - Features: ~200 MB
 
 **Optimization:** Observations are extracted per-group in batches, not all at once, significantly reducing memory footprint.

 
### Performance Bottlenecks

 
| Bottleneck | Typical Cause | Mitigation |
|---|---|---|
| Observation extraction | Large view ranges | Reduce view range, use smaller maps |
| Step time | High agent density | Increase map size, reduce interactions |
| Memory bandwidth | Massive agent counts | Optimize cache locality, use larger batch sizes |
| Thread contention | Too many threads | Reduce OMP_NUM_THREADS |
| Attack processing | Many simultaneous attacks | Already optimized with critical sections |

## Scaling Checklist

 When designing experiments with large agent populations:

 
 - **Map Size:** Ensure map size > 99×99 to enable large_map_mode
 - **Agent Density:** Target ~1 agent per 10-20 cells to prevent excessive crowding
 - **View Range:** Keep view ranges ≤10 cells for performance
 - **Thread Count:** Set `OMP_NUM_THREADS` appropriately (8-16 for massive simulations)
 - **Memory:** Estimate memory needs: ~200-500 bytes per agent minimum
 - **Batch Inference:** Use large `infer_batch_size` for GPU models (100K+)
 - **Group Organization:** Split agents into multiple groups to enable parallel processing
 - **Testing:** Use `test_1m.py` to benchmark before full training runs

## Summary

 MAgent's scaling capabilities stem from:

 
 - **Automatic Mode Switching:** Detects map size and agent count to enable optimizations
 - **Spatial Partitioning:** Divides the map into parallel-processable regions
 - **Thread-Level Parallelism:** Extensive OpenMP usage for CPU-bound operations
 - **Efficient Memory Management:** In-place compaction, buffer reuse, minimal allocations
 - **Boundary Handling:** Careful synchronization where necessary to prevent race conditions
 - **Testing Infrastructure:** Built-in benchmarks to validate performance
 
 These techniques combine to enable simulations with up to 1 million agents at interactive frame rates on modern multi-core systems.
