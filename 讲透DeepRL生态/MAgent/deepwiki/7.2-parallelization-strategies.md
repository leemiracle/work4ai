  This document describes how MAgent achieves high performance through parallelization at multiple levels: OpenMP-based parallelism in the C++ simulation engine, multi-process model execution in Python, and GPU utilization for neural network inference. These strategies enable MAgent to efficiently simulate and train millions of agents.

 For information about the overall training workflow, see [Training Workflow](https://deepwiki.com/geek-ai/MAgent/4.1-training-workflow). For details on model training interfaces, see [ProcessingModel and Parallelism](https://deepwiki.com/geek-ai/MAgent/4.2-processingmodel-and-parallelism).

## Overview of Parallelization Levels

 MAgent implements a three-tier parallelization strategy:

 
| Level | Technology | Purpose | Scope |
|---|---|---|---|
| C++ Engine | OpenMP | Parallel agent processing during simulation | Within single environment step |
| Python Process | multiprocessing | Parallel model inference and training | Across multiple models/groups |
| GPU | TensorFlow/MXNet | Accelerated neural network operations | Within model computation |

 These levels operate independently and can be combined for maximum throughput.

## C++ Engine Parallelization with OpenMP

 
### Large Map Mode and Spatial Partitioning

 The GridWorld engine automatically enables spatial partitioning for large maps to enable efficient parallelization:

 
```

```

 **Map Size Thresholds:**

 
 - Maps ≤ 99×99: Single-threaded action processing (`NUM_SEP_BUFFER = 1`)
 - Maps 99×99 to 1000×1000: 8 spatial partitions (`NUM_SEP_BUFFER = 8`)
 - Maps > 1000×1000: 16 spatial partitions (`NUM_SEP_BUFFER = 16`)
 
 The bandwidth parameter defines the width of each partition. Agents within 4 cells of a partition boundary are placed in a separate boundary buffer to avoid race conditions during parallel processing.

 **Sources:** [src/gridworld/GridWorld.cc72-86](https://github.com/geek-ai/MAgent/blob/2144dbd4/src/gridworld/GridWorld.cc#L72-L86) [src/gridworld/GridWorld.cc407-453](https://github.com/geek-ai/MAgent/blob/2144dbd4/src/gridworld/GridWorld.cc#L407-L453)

### Synchronization and Critical Sections

 The engine uses minimal synchronization to maximize parallel efficiency:

 **Critical Sections:**

 
 - `do_attack()` at [src/gridworld/GridWorld.cc498-504](https://github.com/geek-ai/MAgent/blob/2144dbd4/src/gridworld/GridWorld.cc#L498-L504): Multiple agents may attack the same target, requiring atomic HP updates

 - Map operations that modify agent positions use internal locking
 
 **Reduction Operations:**

 
 - Attack render events: `reduction(merge: render_attack_buffer)` merges per-thread attack events
 - Starve count: `reduction(+: starve_ct)` sums dead agents across threads
 - Mean position calculation: `reduction(+: sum_x)` and `reduction(+: sum_y)` for statistics

## Python Multi-Process Parallelism

 
### ProcessingModel Architecture

 The `ProcessingModel` class enables parallel execution of multiple RL models by hosting each in a separate process:

 
```

```

 Each `ProcessingModel` instance:

 
 - Spawns a subprocess running `model_client()` function
 - Establishes a named pipe connection (or socket)
 - Sends observations and receives actions via the pipe
 - Maintains an independent replay buffer
 - Trains the model asynchronously

### NDArrayPackage: Efficient Array Transfer

 The `NDArrayPackage` class handles serialization of large NumPy arrays across process boundaries:

 
```

```

 **Key Features:**

 
 - **Segmentation:** Arrays exceeding `max_len = (1 << 30) / 4` (256M elements) are split into segments to avoid memory issues
 - **Zero-Copy Receive:** Uses `recv_bytes_into()` to receive directly into pre-allocated NumPy buffers
 - **Optional Threading:** The `use_thread=True` parameter spawns a thread for sending, allowing the caller to continue immediately

## Configuration and Tuning

 
### OpenMP Thread Control

 The number of OpenMP threads is controlled via the `OMP_NUM_THREADS` environment variable:

 
```

```

 **Best Practices:**

 
 - Default: Half of CPU cores (set automatically by MAgent)
 - Small maps (<1000 agents): 4-8 threads
 - Medium maps (1K-100K agents): 8-16 threads
 - Large maps (>100K agents): 16-32 threads
 
 Over-subscription (threads > cores) typically degrades performance due to context switching overhead.

## Performance Characteristics

 
### Scaling with Agent Count

 
| Agent Count | Map Size | OMP Threads | FPS (CPU) | Bottleneck |
|---|---|---|---|---|
| 1,000 | 140×140 | 8 | ~500 | Overhead dominates |
| 10,000 | 450×450 | 8 | ~200 | Balanced |
| 100,000 | 1,400×1,400 | 16 | ~50 | Observation extraction |
| 1,000,000 | 4,500×4,500 | 16 | ~5 | Large map operations |

 Performance scales sub-linearly with agent count due to:

 
 - Increased observation computation (O(N))
 - Map access contention in critical sections
 - Memory bandwidth limitations

### Memory Considerations

 Parallel processing increases memory requirements:

 
 - **OpenMP threads:** Share process memory, minimal overhead
 - **ProcessingModel:** Each subprocess duplicates model parameters and buffers
 - **NDArrayPackage:** Temporarily doubles array memory during transfer
 
 For 2 models with 100K agents each:

 
 - Main process: ~2GB (environment state)
 - Model process 1: ~1.5GB (model + buffer)
 - Model process 2: ~1.5GB (model + buffer)
 - **Total:** ~5GB

## Summary

 MAgent's parallelization strategy combines:

 
 - **OpenMP in C++ engine:** Fine-grained parallelism for agent processing, automatically enabled for large maps with spatial partitioning
 - **Python multiprocessing:** Process-level parallelism for multiple models, enabled via `ProcessingModel` wrapper
 - **GPU acceleration:** Neural network operations within each model, configured via `num_gpu` parameter
 
 These layers work together to scale from thousands to millions of agents while maintaining interactive frame rates. Proper configuration of thread counts, process counts, and batch sizes is essential for optimal performance.
