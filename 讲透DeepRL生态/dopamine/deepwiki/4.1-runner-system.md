  The Runner System is the central orchestration component in Dopamine that controls the execution of reinforcement learning experiments. It manages the interactions between agents and environments, handles training and evaluation phases, collects statistics, and coordinates checkpointing and logging. This document explains the design and usage of the Runner System in Dopamine.

 For information about the Experiment Configuration system with Gin, see [Configuration with Gin](https://deepwiki.com/google/dopamine/4.2-configuration-with-gin). For details about checkpointing and logging mechanisms, see [Checkpointing and Logging](https://deepwiki.com/google/dopamine/4.3-checkpointing-and-logging). For information about the Replay Memory System, see [Replay Memory System](https://deepwiki.com/google/dopamine/4.4-replay-memory-system).

 
## 1. Core Runner Architecture

 The Runner System is built around the `Runner` class which provides the foundation for executing reinforcement learning experiments. It handles all aspects of experiment execution, from initialization to completion, including the training and evaluation loop, checkpoint management, and statistics collection.

### 1.1 Core Components

 The Runner System consists of the following key components:

 
 - **Runner Class**: The base runner class that manages the full experiment lifecycle.
 - **TrainRunner Class**: A specialized runner that only performs training without evaluation.
 - **DataEfficientAtariRunner**: A specialized runner for data-efficient RL research with the Atari 100k benchmark.
 - **Factory Functions**: Helper functions like `create_runner()` and `create_agent()` that facilitate creating instances.
 
 The Runner class is designed to be configurable via Gin, allowing for easy parameter adjustment without code changes.

## 2. Execution Flow

 The Runner System follows a structured execution flow that alternates between training and evaluation phases across multiple iterations.

### 2.1 Training and Evaluation Cycle

 The Runner alternates between training and evaluation phases:

 
 - **Training Phase**: The agent learns from interactions with the environment, with the `eval_mode` flag set to `False`. This phase runs for a fixed number of steps defined by `training_steps`.
 - **Evaluation Phase**: The agent is evaluated without learning (exploration is still possible but at a lower rate), with the `eval_mode` flag set to `True`. This phase runs for a fixed number of steps defined by `evaluation_steps`.
 
 The following table shows the main differences between training and evaluation phases:

 
| Phase | Learning | Agent Mode | Steps Parameter | Purpose |
|---|---|---|---|---|
| Training | Enabled | eval_mode = False | training_steps | Agent learns from experiences |
| Evaluation | Disabled | eval_mode = True | evaluation_steps | Performance assessment |

### 2.3 Statistics Collection

 The Runner collects various statistics during execution:

 
 - **Episode Statistics**:

 
 - Episode lengths
 - Episode returns (total rewards)
 - **Phase Statistics**:

 
 - Average return per episode
 - Number of episodes
 - Average steps per second (training performance)
 
 These statistics are stored in the `IterationStatistics` object and are used for logging, visualization, and as return values for the experiment.

### 3.1 TrainRunner

 The `TrainRunner` is a variant that only performs the training phase without evaluation. It inherits from the base `Runner` class but overrides the `_run_one_iteration` method to skip the evaluation phase. This is useful for scenarios where:

 
 - You only need to train an agent without regular evaluation
 - You want to perform evaluation externally or less frequently
 - You want to maximize training throughput
 
 Sources: [dopamine/discrete_domains/run_experiment.py742-845](https://github.com/google/dopamine/blob/bec5f4e1/dopamine/discrete_domains/run_experiment.py#L742-L845)

 
### 3.2 DataEfficientAtariRunner

 The `DataEfficientAtariRunner` is designed specifically for data-efficient reinforcement learning research with the Atari 100k benchmark. Key differences include:

 
 - Runs a fixed number of episodes rather than steps during evaluation
 - Supports parallel evaluation across multiple environments
 - Enforces strict data collection caps
 - Tracks and reports normalized scores
 - Provides mechanisms for handling agent state with multiple environments
 
 This runner is used in research that focuses on sample efficiency, where agents must learn with limited environment interactions.

 Sources: [dopamine/labs/atari_100k/atari_100k_runner.py46-590](https://github.com/google/dopamine/blob/bec5f4e1/dopamine/labs/atari_100k/atari_100k_runner.py#L46-L590)

 
### 3.3 LoggedDataEfficientAtariRunner

 The `LoggedDataEfficientAtariRunner` extends the `DataEfficientAtariRunner` with capabilities for loading and saving replay buffer data. This enables:

 
 - Running experiments with pre-recorded experiences
 - Saving agent experiences for later use
 - Supporting offline RL research

## 4. Configuration

 The Runner System is highly configurable through Gin, allowing users to adjust parameters without modifying code.

 
### 4.1 Common Configuration Parameters

 Here are the main configuration parameters for the base `Runner`:

 
| Parameter | Default | Description |
|---|---|---|
| base_dir | (required) | Base directory for all output files |
| create_agent_fn | (required) | Function to create the agent |
| create_environment_fn | atari_lib.create_atari_environment | Function to create the environment |
| checkpoint_file_prefix | 'ckpt' | Prefix for checkpoint files |
| logging_file_prefix | 'log' | Prefix for log files |
| log_every_n | 1 | Frequency of writing logs |
| num_iterations | 200 | Number of iterations to run |
| training_steps | 250000 | Number of training steps per iteration |
| evaluation_steps | 125000 | Number of evaluation steps per iteration |
| max_steps_per_episode | 27000 | Maximum steps per episode |
| clip_rewards | True | Whether to clip rewards to [-1, 1] |

 For the `DataEfficientAtariRunner`, additional parameters include:

 
| Parameter | Default | Description |
|---|---|---|
| num_eval_episodes | 100 | Number of episodes for evaluation |
| max_noops | 30 | Maximum number of no-ops at episode start |
| parallel_eval | True | Whether to use parallel evaluation |
| num_eval_envs | 100 | Number of environments for evaluation |
| num_train_envs | 1 | Number of environments for training |

### 5.1 Agent Integration

 The Runner interacts with agents through a defined interface:

 
 - `begin_episode(observation)`: Starts a new episode with an initial observation
 - `step(reward, observation)`: Processes a step and returns the next action
 - `end_episode(reward)`: Finalizes an episode with the last reward
 - `bundle_and_checkpoint()`: Saves the agent's state during checkpointing
 
 This interface allows the Runner to be agent-agnostic, supporting any agent implementation that follows this protocol.

 Sources: [dopamine/discrete_domains/run_experiment.py355-362](https://github.com/google/dopamine/blob/bec5f4e1/dopamine/discrete_domains/run_experiment.py#L355-L362) [dopamine/discrete_domains/run_experiment.py377-388](https://github.com/google/dopamine/blob/bec5f4e1/dopamine/discrete_domains/run_experiment.py#L377-L388) [dopamine/discrete_domains/run_experiment.py705-707](https://github.com/google/dopamine/blob/bec5f4e1/dopamine/discrete_domains/run_experiment.py#L705-L707)

 
### 5.2 Environment Integration

 The Runner interacts with environments through the standard Gym interface:

 
 - `reset()`: Resets the environment to start a new episode
 - `step(action)`: Executes an action and returns observation, reward, done, info
 
 Additionally, the Runner applies preprocessing through environment wrappers and handles environment variations like life loss in Atari games.

### 5.3 Metrics and Logging Integration

 The Runner collects and reports metrics through two systems:

 
 - **Legacy Logger System**: Writes logs to files with experiment statistics
 - **CollectorDispatcher System**: A newer system that collects metrics and sends them to various destinations
 
 The Runner also supports TensorBoard integration for visualizing metrics during and after experiments.
