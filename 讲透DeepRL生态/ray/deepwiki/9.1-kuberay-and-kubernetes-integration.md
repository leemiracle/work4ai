  The KubeRay operator is the standard way to deploy and manage Ray on Kubernetes. It provides a Kubernetes-native control plane to manage the lifecycle of Ray clusters, jobs, and services through Custom Resource Definitions (CRDs).

 
## KubeRay Custom Resources

 KubeRay defines three primary custom resources to manage different Ray workloads:

 
| Resource | Purpose | Key Components |
|---|---|---|
| RayCluster | Manages the lifecycle of a single Ray cluster. | Head Pod, Worker PodGroups, Autoscaler sidecar. |
| RayJob | Manages a Ray application execution by creating a RayCluster and submitting a job. | RayCluster spec, Job submitter (K8s Job or HTTP). |
| RayService | Manages high-availability Ray Serve applications. | Multi-cluster rollout, Health checking, Dashboard proxy. |

 
### RayJob Lifecycle

 A `RayJob` automates the process of cluster creation and application submission. It supports multiple `submissionMode` types, including `K8sJobMode` (default), `HTTPMode`, `SidecarMode`, and `InteractiveMode` [doc/source/cluster/kubernetes/getting-started/rayjob-quick-start.md53-57](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/getting-started/rayjob-quick-start.md?plain=1#L53-L57) In `K8sJobMode`, KubeRay creates a submitter Kubernetes Job that runs `ray job submit` against the RayCluster [doc/source/cluster/kubernetes/getting-started/rayjob-quick-start.md15-16](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/getting-started/rayjob-quick-start.md?plain=1#L15-L16) Starting in version 1.2.0, users can configure `deletionStrategy` (rules-based) to automate the cleanup of workers or the entire cluster after a job succeeds or fails [doc/source/cluster/kubernetes/getting-started/rayjob-quick-start.md73-77](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/getting-started/rayjob-quick-start.md?plain=1#L73-L77)

 
### RayService and High Availability

 `RayService` provides zero-downtime upgrades and high availability for Ray Serve. It manages two `RayCluster` resources during an upgrade (Blue-Green deployment) and ensures traffic is only routed to the "Ready" cluster [doc/source/cluster/kubernetes/user-guides/rayservice.md20-21](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/user-guides/rayservice.md?plain=1#L20-L21) It monitors `Application Statuses` and `Serve Deployment Statuses` to ensure the health of the serving layer [doc/source/cluster/kubernetes/user-guides/rayservice.md140-146](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/user-guides/rayservice.md?plain=1#L140-L146)

## Autoscaling Configuration

 Autoscaling in KubeRay is implemented as a sidecar container within the Ray head Pod [doc/source/cluster/kubernetes/user-guides/configuring-autoscaling.md24-26](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/user-guides/configuring-autoscaling.md?plain=1#L24-L26) The `Autoscaler` monitors logical resource demands (tasks, actors, placement groups) and updates the `RayCluster` CR to scale worker pods.

 
### Implementation Architecture

 The `AutoscalingConfigProducer` fetches the `RayCluster` CR via the `KubernetesHttpApiClient` and derives an internal `autoscaling_config` used by the Ray Autoscaler [python/ray/autoscaler/_private/kuberay/autoscaling_config.py43-67](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/_private/kuberay/autoscaling_config.py#L43-L67) This config includes `available_node_types` mapped from `headGroupSpec` and `workerGroupSpecs` [python/ray/autoscaler/_private/kuberay/autoscaling_config.py176-191](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/_private/kuberay/autoscaling_config.py#L176-L191)

## GCS Fault Tolerance

 The Global Control Service (GCS) is the metadata hub of a Ray cluster. On Kubernetes, GCS fault tolerance is achieved by persisting state to an external store or using persistent volumes.

 
 - **GCS Storage**: KubeRay supports GCS fault tolerance (GCS FT) to recover cluster metadata if the head Pod restarts [doc/source/cluster/kubernetes/user-guides.md61-62](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/user-guides.md?plain=1#L61-L62)
 - **Persistent Storage**: State can be persisted to external databases or cloud storage (e.g., GKE GCS buckets) [doc/source/cluster/kubernetes/user-guides.md68](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/user-guides.md?plain=1#L68-L68)
 - **Head Pod Recovery**: When the head Pod is recreated, the GCS server recovers the state of actors and nodes, ensuring the cluster remains functional without losing active workloads.
 
 Sources: [doc/source/cluster/kubernetes/user-guides.md61-68](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/user-guides.md?plain=1#L61-L68)

## Observability and Ecosystem Integration

 KubeRay clusters integrate with Prometheus via `PodMonitor` and `ServiceMonitor` resources. KubeRay exposes a Prometheus metrics endpoint on port `8080` by default [doc/source/cluster/kubernetes/k8s-ecosystem/prometheus-grafana.md101](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/k8s-ecosystem/prometheus-grafana.md?plain=1#L101-L101)

 - **PodMonitor**: Recommended for head Pods to avoid double-counting metrics when multiple services target the same Pod [doc/source/cluster/kubernetes/k8s-ecosystem/prometheus-grafana.md125-126](https://github.com/ray-project/ray/blob/bf129559/doc/source/cluster/kubernetes/k8s-ecosystem/prometheus-grafana.md?plain=1#L125-L126)
