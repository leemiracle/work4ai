  This page explains the fundamental architecture of Ray and its core concepts including tasks, actors, objects, and the key components (CoreWorker, Raylet, GCS) that enable distributed execution. For details on higher-level libraries built on Ray Core (Data, Serve, RLlib), see their respective sections ([Ray Data](https://deepwiki.com/ray-project/ray/3-ray-data), [Ray Serve](https://deepwiki.com/ray-project/ray/4-ray-serve), [Ray RLlib](https://deepwiki.com/ray-project/ray/5-ray-rllib)).

 
## Overview

 Ray is a distributed computing framework with a three-tier architecture:

 
 - **Application Layer**: User code written in Python, Java, or C++.
 - **Core Runtime Layer**: Distributed task execution, object management, and scheduling.
 - **Infrastructure Layer**: Cluster management and resource coordination.
 
 The core runtime provides abstractions for distributed computing (tasks and actors) while managing object storage, reference counting, and fault tolerance transparently.

## Core Concepts

 
### Tasks

 Tasks are the fundamental unit of computation in Ray. A task is a stateless function decorated with `@ray.remote` that executes asynchronously and returns an `ObjectRef`.

 **Task Types**:

 
 - **Normal tasks**: Stateless functions executed by worker processes.
 - **Actor creation tasks**: Special tasks that instantiate an actor process.
 - **Actor tasks**: Methods executed on stateful actor instances.
 - **Driver tasks**: The main script that orchestrates execution.

### Actors

 Actors are stateful workers that execute methods sequentially. Each actor is a long-running Ray worker process that maintains state across method invocations.

 
```

```

 **Key Properties**:

 
 - **Statefulness**: Instance variables persist across method calls.
 - **Sequential execution**: Methods execute one at a time by default.
 - **Concurrency control**: Configurable with `max_concurrency` parameter [python/ray/actor.py29-32](https://github.com/ray-project/ray/blob/bf129559/python/ray/actor.py#L29-L32)
 - **Async actors**: Support for `async def` methods with higher concurrency [python/ray/actor.py31-32](https://github.com/ray-project/ray/blob/bf129559/python/ray/actor.py#L31-L32)
 
 **Implementation**:

### Objects and ObjectRefs

 Ray objects are immutable data stored in the distributed object store. An `ObjectRef` is a reference to an object that may not yet exist (future).

 
```

```

 **Object Lifecycle**:

 
 - **Creation**: Objects created via `ray.put()` or task returns.
 - **Storage**: Small objects stored in-process `MemoryStore`, large objects in `Plasma`.
 - **Reference tracking**: `ReferenceCounter` tracks local and borrowed references [src/ray/core_worker/core_worker.h44-48](https://github.com/ray-project/ray/blob/bf129559/src/ray/core_worker/core_worker.h#L44-L48)
 - **Retrieval**: `ray.get()` fetches object data, potentially from remote nodes.
 - **Garbage collection**: Objects deleted when all references go out of scope.
 
 **Implementation Details**:

 
 - Object IDs are 28 bytes fixed size [python/ray/_private/ray_constants.py37-38](https://github.com/ray-project/ray/blob/bf129559/python/ray/_private/ray_constants.py#L37-L38)

 - `MemoryStore` provides in-process storage [src/ray/core_worker/core_worker.h47](https://github.com/ray-project/ray/blob/bf129559/src/ray/core_worker/core_worker.h#L47-L47) and `PlasmaStoreProvider` handles shared memory for large objects.
 - Object location information is encapsulated in `ObjectLocation` struct [src/ray/core_worker/core_worker.cc95-111](https://github.com/ray-project/ray/blob/bf129559/src/ray/core_worker/core_worker.cc#L95-L111)

### Raylet

 The Raylet is a per-node daemon that handles local scheduling, resource management, and object transfer. Each node runs exactly one Raylet process.

 **Raylet Components**:

 
 - **NodeManager**: Manages workers, resource scheduling, and node-level lifecycle [src/ray/raylet/node_manager.h138-142](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/node_manager.h#L138-L142)
 - **WorkerPool**: Manages a pool of worker processes for task execution [src/ray/raylet/node_manager.h55](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/node_manager.h#L55-L55) (relevant implementation in node_manager.cc and worker_pool.cc).
 - **ClusterResourceScheduler**: Makes local scheduling decisions based on cluster resources [src/ray/raylet/node_manager.h50](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/node_manager.h#L50-L50)
 - **ObjectManager**: Manages object transfers and shared memory (Plasma) [src/ray/raylet/node_manager.h40](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/node_manager.h#L40-L40)
 
 **Worker-Raylet Communication**:

 
 - Uses IPC (Unix domain sockets) for local communication.
 - Raylet assigns tasks to workers by leasing them to the `CoreWorker`.
 - Raylet starts and manages worker processes, enforcing resource isolation with cgroups v2 if enabled.
 - Raylet is started using command line flags (node IP, ports, paths) as seen in [src/ray/raylet/main.cc70-150](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/main.cc#L70-L150)

## Node Lifecycle and Process Management

 
### ray start CLI

 The `ray start` command (implemented in `python/ray/scripts/scripts.py`) initializes a Ray node process [python/ray/scripts/scripts.py70-140](https://github.com/ray-project/ray/blob/bf129559/python/ray/scripts/scripts.py#L70-L140)

 
 - **Head Node**: Starts GCS, Raylet, Plasma Store, and Dashboard processes.
 - **Worker Node**: Starts Raylet and Plasma Store, connecting to the head node's GCS.
 
 `ray start` sets configuration flags such as resource info, port ranges, paths, and enables authentication tokens if configured.

 
### Process Management

 Ray manages several types of processes:

 
 - **Raylet**: Starts the local node manager daemon (`RAYLET_EXECUTABLE`) which handles scheduling and worker pool management [python/ray/_private/services.py55-75](https://github.com/ray-project/ray/blob/bf129559/python/ray/_private/services.py#L55-L75)
 - **GCS Server**: A standalone metadata service process (`GCS_SERVER_EXECUTABLE`).
 - **Workers**: Task execution processes started by the Raylet’s `WorkerPool`. Python workers use the Python interpreter (`sys.executable`) with specific environment variables [python/ray/_private/services.py150-170](https://github.com/ray-project/ray/blob/bf129559/python/ray/_private/services.py#L150-L170)
 
 
### Resource Isolation and Worker Lifecycle

 Ray supports resource isolation via **cgroups v2** configured in the node manager (`enable_resource_isolation` flag in `NodeManagerConfig`) [src/ray/raylet/node_manager.h133](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/node_manager.h#L133-L133) The Raylet creates cgroup hierarchies separating system and user processes, enforcing CPU and memory constraints [src/ray/common/ray_config_def.h85-128](https://github.com/ray-project/ray/blob/bf129559/src/ray/common/ray_config_def.h#L85-L128)

 Worker process management ensures:

 
 - Safe process group signaling and termination [src/ray/raylet/node_manager.cc106-132](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/node_manager.cc#L106-L132)
 - Port allocation for workers within specified ranges or explicit lists.
 - Pre-started Python workers to minimize startup latency [src/ray/raylet/node_manager.cc90-105](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/node_manager.cc#L90-L105)
