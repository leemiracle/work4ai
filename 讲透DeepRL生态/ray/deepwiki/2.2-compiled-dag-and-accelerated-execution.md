## Purpose and Scope

 This document describes the Compiled DAG system, an experimental feature in Ray that provides accelerated execution for task graphs through channel-based communication and optimized scheduling. Compiled DAGs eliminate overhead from traditional Ray task submission by pre-allocating communication channels, reusing actors, and enabling zero-copy data transfer through shared memory and GPU-direct communication.

 For general DAG concepts and the standard execution model, see [Architecture and Core Concepts (1.1)](https://github.com/ray-project/ray/blob/bf129559/Architecture and Core Concepts (1.1)) For information about other Ray libraries that build on top of this infrastructure, see [Ray Data (3)](https://github.com/ray-project/ray/blob/bf129559/Ray Data (3)) [Ray Serve (4)](https://github.com/ray-project/ray/blob/bf129559/Ray Serve (4)) and [RLlib (5)](https://github.com/ray-project/ray/blob/bf129559/RLlib (5))

 
## Overview and Motivation

 Traditional Ray DAGs create new tasks and `ObjectRef`s for each execution, incurring serialization and scheduling overhead. Compiled DAGs (also known as Ray Compiled Graphs) optimize this by:

 
 - **Reducing system overhead** to less than 50µs per task launch [doc/source/ray-core/compiled-graph/ray-compiled-graph.rst19](https://github.com/ray-project/ray/blob/bf129559/doc/source/ray-core/compiled-graph/ray-compiled-graph.rst#L19-L19)
 - **Native GPU-to-GPU communication** via NCCL, bypassing CPU host memory [doc/source/ray-core/compiled-graph/ray-compiled-graph.rst20](https://github.com/ray-project/ray/blob/bf129559/doc/source/ray-core/compiled-graph/ray-compiled-graph.rst#L20-L20)
 - **Static execution model** that allows for pre-allocation of resources and deadlock-free scheduling [doc/source/ray-core/compiled-graph/ray-compiled-graph.rst48-52](https://github.com/ray-project/ray/blob/bf129559/doc/source/ray-core/compiled-graph/ray-compiled-graph.rst#L48-L52)
 - **Overlapping GPU compute and communication** to improve hardware utilization [doc/source/ray-core/compiled-graph/ray-compiled-graph.rst53](https://github.com/ray-project/ray/blob/bf129559/doc/source/ray-core/compiled-graph/ray-compiled-graph.rst#L53-L53)
 
 A DAG is compiled by calling `experimental_compile()` on a `DAGNode`, which triggers the transformation of a logical Ray DAG into an executable physical plan [python/ray/dag/dag_node.py279-363](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/dag_node.py#L279-L363)

## ExecutableTask and Operations

 In a Compiled DAG, actor methods are not invoked via the standard Ray scheduler. Instead, they are wrapped in `ExecutableTask` objects and executed in a dedicated loop.

 
### Operation Types

 Each task is decomposed into three distinct operation types [python/ray/dag/dag_node_operation.py14-24](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/dag_node_operation.py#L14-L24):

 
 - **READ:** Pulls data from input channels.
 - **COMPUTE:** Executes the actual Python method on the actor.
 - **WRITE:** Pushes the result to output channels.
 
 
### Execution Loop

 The `do_exec_tasks` method runs an infinite loop on each participant actor, executing the operations defined in its local `schedule` [python/ray/dag/compiled_dag_node.py186-210](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/compiled_dag_node.py#L186-L210)

 - **WriteRelease:** Signals readers by releasing the `header_sem` and increments the version number [src/ray/core_worker/experimental_mutable_object_manager.cc280-303](https://github.com/ray-project/ray/blob/bf129559/src/ray/core_worker/experimental_mutable_object_manager.cc#L280-L303)
 - **ReadAcquire:** Blocks on `header_sem` until the writer has finished. It ensures the reader sees the latest version [src/ray/core_worker/experimental_mutable_object_manager.cc305-366](https://github.com/ray-project/ray/blob/bf129559/src/ray/core_worker/experimental_mutable_object_manager.cc#L305-L366)
 - **ReadRelease:** Decrements the remaining reader count. The last reader releases the `object_sem`, allowing the writer to start the next cycle [src/ray/core_worker/experimental_mutable_object_manager.cc368-403](https://github.com/ray-project/ray/blob/bf129559/src/ray/core_worker/experimental_mutable_object_manager.cc#L368-L403)

## GPU Tensor Transport and NCCL

 For GPU-heavy workloads, Ray Compiled DAGs support direct GPU-to-GPU communication via NCCL.

 
### Communicators

 The `Communicator` abstract class defines the interface for collective and point-to-point operations [python/ray/experimental/channel/communicator.py18-145](https://github.com/ray-project/ray/blob/bf129559/python/ray/experimental/channel/communicator.py#L18-L145) The primary implementation is `_NcclGroup`.

 
 - **_NcclGroup:** Wraps a NCCL communicator ID. It handles `send`, `recv`, and collective operations like `allreduce` [python/ray/experimental/channel/nccl_group.py21-269](https://github.com/ray-project/ray/blob/bf129559/python/ray/experimental/channel/nccl_group.py#L21-L269)
 - **Initialization:** Actors join a NCCL group by sharing a unique ID (from `nccl.get_unique_id()`) during the compilation phase [python/ray/experimental/channel/nccl_group.py29-90](https://github.com/ray-project/ray/blob/bf129559/python/ray/experimental/channel/nccl_group.py#L29-L90)
 
 
### Overlapped Execution

 The system can overlap GPU communication with computation using multiple CUDA streams [python/ray/dag/compiled_dag_node.py575-618](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/compiled_dag_node.py#L575-L618):

 
 - **Computation Stream:** The default stream for actor method execution.
 - **Communication Streams:** Dedicated `_send_stream` and `_recv_stream` in `_NcclGroup` [python/ray/experimental/channel/nccl_group.py102-113](https://github.com/ray-project/ray/blob/bf129559/python/ray/experimental/channel/nccl_group.py#L102-L113)
 
 The `GPUFuture` class facilitates this by recording CUDA events to synchronize between these streams without blocking the CPU thread [python/ray/dag/dag_operation_future.py57-123](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/dag_operation_future.py#L57-L123)

## Compilation and Execution Flow

 
 - **Logical Graph Construction:** User binds actor methods using `DAGNode` [python/ray/dag/dag_node.py41-65](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/dag_node.py#L41-L65)
 - **Compilation:** `experimental_compile()` calls `build_compiled_dag_from_ray_dag()` [python/ray/dag/dag_node.py350](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/dag_node.py#L350-L350) 
 - It performs topological sorting of the graph [python/ray/dag/dag_node_operation.py29-37](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/dag_node_operation.py#L29-L37)
 - It allocates physical channels between actors using `do_allocate_channel` [python/ray/dag/compiled_dag_node.py151-182](https://github.com/ray-project/ray/blob/bf129559/python/ray/dag/compiled_dag_node.py#L151-L182)

 - **Execution:** `CompiledDAG.execute()` writes the input data to the root channel. 
 - Data flows through the pre-allocated channels.
