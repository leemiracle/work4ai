  This page documents the core execution engine of Ray Tune, focusing on the `TuneController` event loop, the lifecycle of `Trial` objects, and how experiment state is persisted and restored. It also covers the integration between high-level configurations (`RunConfig`, `TuneConfig`) and the underlying Ray Train trainables.

 
## TuneController Execution Loop

 The `TuneController` (formerly `TrialRunner`) is the central orchestration component of a Tune experiment. It manages the interaction between the `SearchAlgorithm`, the `TrialScheduler`, and the Ray cluster.

 
### Core Event Loop

 The execution loop is primarily driven by the `TuneController` which monitors the state of all active trials. It performs the following high-level steps:

 
 - **Trial Generation**: Requests new hyperparameter configurations from the `SearchAlgorithm`.
 - **Resource Allocation**: Uses `PlacementGroupFactory` to request resources for pending trials [python/ray/tests/test_placement_group_5.py1-20](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_placement_group_5.py#L1-L20)
 - **Task Dispatch**: Launches `Trainable` actors via Ray Core when resources become available.
 - **Result Processing**: Collects results reported by `Trainable.report()`, updates trial metadata, and passes results to the `TrialScheduler` to decide on pausing, stopping, or continuing.

## Trial Lifecycle Management

 A `Trial` object represents a single instance of a hyperparameter evaluation. It tracks the state, configuration, and results of the run.

 
### Trial States

 Trials transition through a specific state machine managed by the `TuneController`:

 
 - **PENDING**: The trial is created but waiting for resources or searcher concurrency limits.
 - **RUNNING**: A Ray actor has been started and is executing the `Trainable`.
 - **PAUSED**: The trial is stopped but its state is preserved (e.g., for PBT or ASHA).
 - **TERMINATED**: The trial completed successfully.
 - **ERROR**: The trial failed due to an exception or node failure.
 
 
### Result Reporting

 When a `Trainable` calls `report()`, the result is sent back to the `TuneController`. The `Trial` object updates its `last_result` and increments its training iteration. In the dashboard context, this status is tracked via `JobInfo` [python/ray/dashboard/modules/job/common.py1-50](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/common.py#L1-L50)

 
### Resource Management

 Resources are defined via `PlacementGroupFactory`. This allows Tune to reserve specific bundles of CPUs and GPUs across the cluster before starting the actor [src/ray/raylet/placement_group_resource_manager.cc1-50](https://github.com/ray-project/ray/blob/bf129559/src/ray/raylet/placement_group_resource_manager.cc#L1-L50)

## Experiment State and Persistence

 Tune ensures fault tolerance by persisting the experiment state. This allows resuming experiments after a driver failure or cluster preemption.

 
### State Persistence

 The experiment state is periodically saved into an `experiment_state.json` file. In the modern Ray Job submission framework, this persistence is handled by the `JobInfoStorageClient` which interacts with the GCS [python/ray/dashboard/modules/job/job_manager.py73-78](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/job_manager.py#L73-L78)

 
### Restoration Logic

 When a user restores an experiment, the following sequence occurs:

 
 - **Load State**: The `TuneController` (or `JobManager` in the dashboard context) reads the persisted state [python/ray/dashboard/modules/job/job_manager.py107-118](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/job_manager.py#L107-L118)
 - **Rehydrate Trials**: `Trial` objects are reconstructed from the metadata stored in GCS [python/ray/tests/test_gcs_utils.py139-160](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_gcs_utils.py#L139-L160)
 - **Resume Policy**: Tune decides whether to skip finished trials, restart errored ones, or resume from the last checkpoint.

## Configuration: RunConfig and TuneConfig

 Tune uses configuration objects to separate experiment execution from hyperparameter tuning logic.

 
### RunConfig

 Defines the "how" of execution, shared with Ray Train:

 
 - **Storage**: Where to save results (local or cloud URI).
 - **Checkpoints**: Managed via `JobLogStorageClient` and `JobInfoStorageClient` [python/ray/dashboard/modules/job/job_manager.py75-78](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/job_manager.py#L75-L78)
 
 
### TuneConfig

 Defines the "what" of hyperparameter optimization:

 
 - **Metric/Mode**: The objective to optimize.
 - **Search Algorithm**: The `Searcher` instance.
 - **Concurrency**: Number of trials to run in parallel.

## Integration with Ray Train

 Ray Tune often wraps Ray Train trainers. In this mode, each `Trial` managed by Tune becomes a coordinator for a `WorkerGroup` in Ray Train.

 
### Data Integration

 When running a trainer inside Tune, Ray Data ensures that resources are properly partitioned to prevent the data ingest from starving training workers [doc/source/train/user-guides/data-loading-preprocessing.rst6-12](https://github.com/ray-project/ray/blob/bf129559/doc/source/train/user-guides/data-loading-preprocessing.rst#L6-L12)

 
### Execution Flow with Train

 
 - `TuneController` starts a `Trainer` actor (often a `JobSupervisor` in job submission mode) [python/ray/dashboard/modules/job/job_supervisor.py57-65](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/job_supervisor.py#L57-L65)
 - The `Trainer` actor launches a `WorkerGroup` for distributed training [doc/source/train/user-guides/data-loading-preprocessing.rst97-105](https://github.com/ray-project/ray/blob/bf129559/doc/source/train/user-guides/data-loading-preprocessing.rst#L97-L105)
 - Workers consume data shards via `get_dataset_shard` [doc/source/train/user-guides/data-loading-preprocessing.rst76-78](https://github.com/ray-project/ray/blob/bf129559/doc/source/train/user-guides/data-loading-preprocessing.rst#L76-L78)
