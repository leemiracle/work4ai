  Ray Tune separates the **generation** of hyperparameters from the **scheduling** of trials. This separation allows users to combine any search algorithm (e.g., Bayesian Optimization) with any scheduling strategy (e.g., Early Stopping or Population Based Training).

 
## Search Algorithms

 Search algorithms in Tune are responsible for suggesting hyperparameter configurations. They implement the `Searcher` or `SearchAlgorithm` interface to provide logic for exploring the parameter space.

 
### Implementation and Data Flow

 The `Searcher` interface provides the core logic for suggesting new trials and processing results to update underlying models (such as Gaussian Processes in Bayesian Optimization).

 
 - **Suggestion**: The `TuneController` requests a new configuration via `Searcher.suggest()`. [python/ray/tune/search/searcher.py20-50](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/search/searcher.py#L20-L50)
 - **Feedback**: When a trial reports results or completes, the execution loop calls `Searcher.on_trial_result()` and `Searcher.on_trial_complete()` to provide feedback to the algorithm. [python/ray/tune/tune.py197-201](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/tune.py#L197-L201)
 - **Concurrency Limiting**: The `ConcurrencyLimiter` wrapper is used to restrict the number of trials initiated by a searcher. This is critical for sequential algorithms like those found in Optuna or BayesOpt that require feedback before making the next optimal suggestion. [python/ray/tune/search/concurrency_limiter.py15-40](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/search/concurrency_limiter.py#L15-L40)

## Trial Schedulers

 Schedulers manage the lifecycle of running trials. Unlike Searchers, which pick *what* to run, Schedulers decide *when* to stop, pause, or mutate trials based on intermediate performance metrics.

 
### Key Schedulers

 
 - **ASHA (Asynchronous Successive Halving)**: An aggressive early-stopping scheduler that promotes well-performing trials to higher "rungs" of resource allocation while terminating underperformers. [python/ray/tune/schedulers/async_hyperband.py10-50](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/schedulers/async_hyperband.py#L10-L50)
 - **PBT (Population Based Training)**: Periodically replaces underperforming trials with clones of top performers and "mutates" their hyperparameters in-flight, creating a dynamic schedule. [python/ray/tune/schedulers/pbt.py20-100](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/schedulers/pbt.py#L20-L100)
 - **HyperBand**: A multi-fidelity bandit-based approach that allocates more resources to promising configurations. [python/ray/tune/schedulers/hyperband.py5-40](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/schedulers/hyperband.py#L5-L40)
 - **MedianStoppingRule**: Stops trials whose performance is below the median of previous trials at similar time points.

## Search Space API

 The search space defines the domain and distribution of hyperparameters. Tune provides a domain-specific language (DSL) to define these distributions, which are resolved during experiment execution.

 
### Common Distributions

 
 - `tune.grid_search([values])`: Iterates through every value in the provided list. [python/ray/tune/search/variant_generator.py68-70](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/search/variant_generator.py#L68-L70)
 - `tune.uniform(low, high)`: Samples uniformly between low and high.
 - `tune.loguniform(low, high)`: Samples from a logarithmic uniform distribution, ideal for parameters like learning rates. [python/ray/tune/tests/test_tuner.py130-132](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/tests/test_tuner.py#L130-L132)
 - `tune.randint(low, high)`: Samples random integers. [python/ray/tune/tests/test_tuner.py132-133](https://github.com/ray-project/ray/blob/bf129559/python/ray/tune/tests/test_tuner.py#L132-L133)

## Concurrency Management

 In distributed environments, it is vital to control the number of simultaneous trials to prevent resource contention or to satisfy the requirements of sequential search algorithms.

 
### ConcurrencyLimiter Pattern

 The `ConcurrencyLimiter` is a wrapper class that intercepts `suggest()` calls. If the number of active trials meets the `max_concurrent` threshold, it returns `None`, signaling the controller to wait.

## Resource Schedulers and Data Integration

 Tune trials often integrate with Ray Train and Ray Data. The `DataConfig` class ensures that resources (CPUs/GPUs) are correctly partitioned between the training logic and the data preprocessing/ingestion logic.

 
 - **Resource Exclusion**: When using `DataParallelTrainer` within Tune, `DataConfig` can exclude training-reserved resources from the `StreamingExecutor` to ensure the data pipeline does not starve the model training. [python/ray/train/_internal/data_config.py127-141](https://github.com/ray-project/ray/blob/bf129559/python/ray/train/_internal/data_config.py#L127-L141)
 - **Execution Resources**: The `ExecutionResources` class in Ray Data tracks limits for CPU, GPU, and Object Store memory used by operators within a Tune trial. [python/ray/data/_internal/execution/interfaces/execution_options.py11-39](https://github.com/ray-project/ray/blob/bf129559/python/ray/data/_internal/execution/interfaces/execution_options.py#L11-L39)
