## Purpose and Scope

 This document explains Ray Serve's architecture, separating the control plane (orchestration and state management) from the data plane (request routing and execution). It covers how the `ServeController`, `ApplicationStateManager`, and `DeploymentStateManager` orchestrate deployments, how HTTP/gRPC proxies route requests to replica actors via deployment handles, how metrics drive autoscaling decisions, and how state is persisted for fault tolerance.

 For information about specific replica lifecycle states and transitions, see the deployment state management documentation. For protocol-specific proxy implementations, see page 4.2. For the overall Ray distributed systems architecture, see page 1.1.

### Fault Tolerance Guarantees

 Ray Serve provides the following guarantees:

 
| Scenario | Behavior | Recovery Time |
|---|---|---|
| Controller crash | Applications continue serving; state recovered from checkpoint and running actors | Seconds (controller restart time) |
| Replica crash | Request fails; router retries on different replica; controller starts new replica | Immediate retry; new replica in ~10-30s |
| Proxy crash | New proxy started automatically; inherits route table from LongPoll | Seconds (proxy restart time) |
| Node failure | All actors on node marked dead; controller starts replacements | 1-2 minutes (node detection + actor restart) |

### Request Router Load Balancing

 The default `PowerOfTwoChoicesRequestRouter` implements load balancing using the "power of two choices" algorithm:

 **Power-of-Two Load Balancing**

 
```

```

 The algorithm:

 
 - Randomly sample two replicas from available replicas [python/ray/serve/_private/request_router/pow_2_router.py](https://github.com/ray-project/ray/blob/bf129559/python/ray/serve/_private/request_router/pow_2_router.py)

 - If cache is stale, probe replicas for current queue length
 - Select replica with lower queue length
 - Fallback to random selection if queue data unavailable
