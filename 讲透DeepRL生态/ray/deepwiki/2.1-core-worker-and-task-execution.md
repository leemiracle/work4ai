## Purpose and Scope

 The `CoreWorker` is the fundamental runtime component that powers distributed task execution in Ray. Every worker process (including drivers) contains a `CoreWorker` instance that handles:

 
 - **Task submission**: Submitting tasks and actor methods to the distributed system.
 - **Task execution**: Receiving and executing tasks on worker processes.
 - **Object management**: Storing, retrieving, and tracking distributed objects through reference counting.
 - **Actor lifecycle**: Managing actor creation, method invocation, and state.
 
 This document details the `CoreWorker` implementation, its internal pipeline (including `NormalTaskSubmitter` and `ActorTaskSubmitter`), and its role in the task/actor execution lifecycle.

## Task Execution and Lifecycle

 When a worker receives a task, it enters the execution loop managed by `TaskReceiver`.

 
### Execution Flow

 
 - **Dependency Resolution**: The `TaskReceiver` ensures all `ObjectRef` arguments are available locally (fetching from Plasma if necessary).
 - **Execution Callback**: The `CoreWorker` invokes the `task_execution_callback_` (provided during initialization). In Python, this triggers `python/ray/_private/worker.py:execute_task`.
 - **Metric Tracking**: `TaskCounter` updates the task status (e.g., `MovePendingToRunning`, `MoveRunningToFinished`).
 - **Return Object Allocation**: The worker calls `AllocateReturnObject` to reserve space in the Object Store (Plasma) or Memory Store for the results.
 
 **Task Status Transitions in CoreWorker**

 
| Status | Method | Description |
|---|---|---|
| kPending | IncPending | Task is submitted but not yet running. |
| kRunning | MovePendingToRunning | Worker has started executing the task logic. |
| kFinished | MoveRunningToFinished | Task logic completed; results are being sealed. |

## Object Lifecycle and Reference Counting

 Ray uses a distributed reference counting mechanism implemented in `ReferenceCounter`.

 
### Reference Types

 The `ReferenceCounter` tracks three types of references to an `ObjectID`:

 
 - **Local References**: Held by the language runtime (e.g., a Python `ObjectRef` object).
 - **Submitted Task References**: Objects passed as arguments to pending tasks.
 - **Contained References**: Objects nested inside other objects (e.g., a list of `ObjectRefs` stored as a single Ray object).
 
 
### Reference Counting Logic

 
 - **Ownership**: The worker that creates an object (via `ray.put` or as a task return) is the **owner**.
 - **Borrowing**: Workers that receive an `ObjectRef` are **borrowers**. Borrowers report their local reference counts back to the owner.
 - **Fate Sharing**: If an owner dies, all objects it owned become unreachable (Error: `OWNER_DIED`).

## Actor Management and Fault Tolerance

 
### Actor Lifecycle

 Actors are created via `ACTOR_CREATION_TASK`. The `ActorManager` tracks the state of all actor handles visible to the worker.

 
 - **Creation**: Handled by GCS; the `CoreWorker` submits the creation task and waits for the actor to be instantiated.
 - **Death Detection**: The `CoreWorker` subscribes to actor state changes from the GCS. If an actor dies, the `ActorManager` marks the handle as dead, and subsequent tasks fail with `RayActorError`.
 
 
### Fault Tolerance Mechanisms

 
 - **Task Retries**: Controlled by `max_retries` in `TaskSpecification`. If a worker or actor dies, the `TaskManager` triggers a retry using exponential backoff via `GetTaskRetryDelayMs`.
 - **Lineage Reconstruction**: If an object is lost and was created by a task, Ray can re-execute the task lineage to recover the object.
 - **Object Recovery**: Managed by `ObjectRecoveryManager`, which coordinates with the `ReferenceCounter` and `GCS` to find or recreate lost objects.

## Generator Tasks and Streaming Returns

 For tasks returning multiple values (Generators), Ray uses the `ObjectRefStream` to manage dynamic returns.

 
 - **`ObjectRefStream`**: Manages a sequence of `ObjectIDs` associated with a single generator task.
 - **Backpressure**: The `GeneratorBackpressureWaiter` prevents a generator from producing objects faster than the consumer can process them, preventing OOM.
 - **EndOfStream**: The stream is closed when the task finishes or explicitly signals EOF via `MarkEndOfStream`.

## Worker Initialization and Shutdown

 
### Initialization

 The `CoreWorkerProcess` initializes the singleton `CoreWorker` instance.

 
 - **IO Service**: Starts a background `io_service_` thread for RPC and GCS communication.
 - **GCS Registration**: Registers the worker with the GCS to receive a `WorkerID`.
 - **Signal Handling**: Sets up signal handlers (e.g., `SIGTERM`) to trigger graceful shutdown.
 
 
### Shutdown

 Shutdown is coordinated by the `ShutdownCoordinator` and `CoreWorkerShutdownExecutor`.

 
 - **Graceful Shutdown**: The worker stops accepting new tasks, flushes pending task events via `TaskEventBuffer`, and notifies the Raylet.
 - **Exit Types**: Workers exit with specific types like `INTENDED_USER_EXIT`, `SYSTEM_ERROR`, or `NODE_OUT_OF_MEMORY`, which are mapped to `ShutdownReason`.
