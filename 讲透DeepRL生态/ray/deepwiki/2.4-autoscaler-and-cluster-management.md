  Ray's autoscaling system is responsible for dynamically adjusting the cluster size to meet resource demands while minimizing costs. The system has evolved into the **Autoscaler v2** architecture, which provides a more robust, state-machine-driven approach to node lifecycle management, integration with Kubernetes via KubeRay, and support for various cloud providers.

 
## Autoscaler v2 Architecture

 The v2 autoscaler is built around a reconciliation loop that synchronizes the desired cluster state (based on resource demands) with the actual state of the cloud provider and the Ray cluster.

 
### Key Components

 
| Component | Role | Code Entity |
|---|---|---|
| InstanceManager | Tracks the state of all instances (nodes) in the cluster and persists them to storage. | InstanceManager python/ray/autoscaler/v2/instance_manager/instance_manager.py15 |
| Reconciler | The central logic engine that computes state transitions and triggers actions. | Reconciler python/ray/autoscaler/v2/instance_manager/reconciler.py56 |
| ResourceDemandScheduler | Calculates the target cluster shape based on pending tasks, actors, and placement groups. | ResourceDemandScheduler python/ray/autoscaler/v2/scheduler.py216 |
| NodeProvider | Interface for interacting with cloud/infrastructure backends (AWS, GCP, KubeRay). | ICloudInstanceProvider python/ray/autoscaler/v2/instance_manager/node_provider.py20 |

## Resource Scheduling and Demand Calculation

 The `ResourceDemandScheduler` is responsible for mapping resource requests (e.g., "I need 2 CPUs and 1 GPU") to specific node types defined in the `AutoscalingConfig`.

 
### Scheduling Logic

 
 - **Request Grouping**: Resource requests are grouped by count to optimize scheduling calculations [python/ray/autoscaler/v2/utils.py22](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/utils.py#L22-L22)
 - **Bin Packing**: The scheduler attempts to fit pending `ResourceRequest` bundles into existing `SCHEDULABLE` nodes [python/ray/autoscaler/v2/scheduler.py188](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/scheduler.py#L188-L188)
 - **Upscaling**: If existing nodes cannot satisfy demand, the scheduler selects the cheapest/best-fit `NodeType` to launch [python/ray/autoscaler/v2/scheduler.py216](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/scheduler.py#L216-L216) [python/ray/autoscaler/v2/scheduler.py300](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/scheduler.py#L300-L300)
 - **Constraints**: It respects `ClusterResourceConstraint` (minimum cluster size) and `GangResourceRequest` (atomic allocation of multiple bundles) [python/ray/autoscaler/v2/scheduler.py59-65](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/scheduler.py#L59-L65)

## Node Lifecycle Management

 The `Reconciler` manages nodes through a series of states defined in `instance_manager_pb2`.

 
### State Transitions

 The `Reconciler._sync_from` method performs "passive" transitions based on external observations, while `_step_next` performs "active" transitions.

 
| Initial Status | Condition | Target Status | Action |
|---|---|---|---|
| QUEUED | Instance assigned by scheduler | REQUESTED | Call CloudProvider.launch_node |
| REQUESTED | Cloud instance ID becomes available | ALLOCATED | Node is provisioning in cloud |
| ALLOCATED | Ray process starts and registers | RAY_RUNNING | Node is ready for tasks |
| RAY_RUNNING | Idle timeout or scale-down | TERMINATING | Call CloudProvider.terminate_node |

 **Sources:** [python/ray/autoscaler/v2/instance_manager/reconciler.py147-167](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/instance_manager/reconciler.py#L147-L167) [python/ray/autoscaler/v2/instance_manager/reconciler.py291-320](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/instance_manager/reconciler.py#L291-L320)

 
## Cloud Provider Integration

 Ray uses adapters to support various environments. Each provider implements the `NodeProvider` interface.

 
### KubeRay (Kubernetes)

 KubeRay integrates Ray with Kubernetes using Custom Resource Definitions (CRDs) like `RayCluster`.

 
 - **Config Production**: The `AutoscalingConfigProducer` fetches the `RayCluster` CR and derives the autoscaling configuration [python/ray/autoscaler/_private/kuberay/autoscaling_config.py42](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/_private/kuberay/autoscaling_config.py#L42-L42)
 - **Node Management**: The `KubeRayNodeProvider` communicates with the Kubernetes API server to adjust the `replicas` field of `workerGroupSpecs` or to delete specific pods via `scaleStrategy` [python/ray/autoscaler/_private/kuberay/node_provider.py69-80](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/_private/kuberay/node_provider.py#L69-L80)
 - **TPU Support**: KubeRay supports Google Cloud TPUs, including multi-host TPU slices. The `AutoscalingConfigProducer` extracts TPU-specific labels (`cloud.google.com/gke-tpu-topology`, `cloud.google.com/gke-tpu-accelerator`) from the `RayCluster` CR to correctly configure TPU resources for autoscaling [python/ray/autoscaler/_private/kuberay/autoscaling_config.py35-36](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/_private/kuberay/autoscaling_config.py#L35-L36) It also infers the number of TPUs from the `rayStartParams` or container resource limits [python/ray/autoscaler/_private/kuberay/autoscaling_config.py20-21](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/_private/kuberay/autoscaling_config.py#L20-L21)
 
 
### Ray on Spark

 Ray can run inside a Spark cluster, utilizing Spark executors as Ray nodes.

 
 - **Cluster Initialization**: `RayClusterOnSpark` manages the lifecycle of Ray processes on Spark [python/ray/util/spark/cluster_init.py72](https://github.com/ray-project/ray/blob/bf129559/python/ray/util/spark/cluster_init.py#L72-L72)
 - **Resource Mapping**: It maps Spark executor cores and memory to Ray resources [python/ray/util/spark/cluster_init.py24-33](https://github.com/ray-project/ray/blob/bf129559/python/ray/util/spark/cluster_init.py#L24-L33)
 
 
### Cloud Adapters (AWS, GCP, Azure)

 These providers use SDKs (boto3, google-cloud-sdk) to manage VM instances.

## Failure Handling and Timeouts

 The autoscaler includes robust error handling for common cloud issues:

 
 - **Launch Failures**: If `CloudInstanceProviderError` occurs, the reconciler marks the request as failed and allows the scheduler to retry [python/ray/autoscaler/v2/instance_manager/reconciler.py151](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/instance_manager/reconciler.py#L151-L151)
 - **Timeouts**: `InstanceReconcileConfig` defines timeouts for each state (e.g., `allocate_status_timeout_s`). If an instance hangs in `ALLOCATED` but never reaches `RAY_RUNNING`, it is terminated [python/ray/autoscaler/v2/instance_manager/config.py83-113](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/instance_manager/config.py#L83-L113)
 - **Resource Availability**: The `CloudResourceMonitor` tracks if specific node types are currently unavailable in the cloud (e.g., Spot instance preemption or stock-out) to avoid repeated failed launch attempts [python/ray/autoscaler/v2/instance_manager/reconciler.py24-26](https://github.com/ray-project/ray/blob/bf129559/python/ray/autoscaler/v2/instance_manager/reconciler.py#L24-L26)
