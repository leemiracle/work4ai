  Ray provides a comprehensive observability stack designed to monitor distributed applications, query cluster-wide state, and collect performance metrics. The architecture is split into a centralized control plane (Dashboard Head) and distributed agents (Dashboard Agents) running on every node.

 
## 1. Dashboard Architecture

 The Ray Dashboard is a multi-process system that provides a GUI and REST APIs for cluster monitoring. It consists of a `DashboardHead` process (usually on the head node) and a `DashboardAgent` on every node.

 
### 1.1 Dashboard Head

 The `DashboardHead` is responsible for aggregating data from agents, serving the frontend, and providing REST endpoints. It loads modular components (e.g., `NodeHead`, `StateHead`, `JobHead`) to handle specific domains [python/ray/dashboard/head.py49-70](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/head.py#L49-L70)

 
 - **Process Management**: It uses `SubprocessModule` to run heavy modules in separate processes to avoid Global Interpreter Lock (GIL) contention. This is controlled by `RAY_DASHBOARD_DASHBOARD_HEAD_TPE_MAX_WORKERS` [python/ray/dashboard/head.py41-46](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/head.py#L41-L46)
 - **Data Aggregation**: The `NodeHead` subscribes to GCS updates for node information, actor states, and resource usage using `GcsAioNodeInfoSubscriber` and `GcsAioActorSubscriber` [python/ray/dashboard/modules/node/node_head.py189-201](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/node/node_head.py#L189-L201)
 - **HTTP Server**: The `HttpServerDashboardHead` manages the aiohttp-based REST API and static asset serving [python/ray/dashboard/http_server_head.py35-50](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/http_server_head.py#L35-L50)
 
 
### 1.2 Dashboard Agent

 The `DashboardAgent` runs on every node in the cluster. Its primary role is to collect local node-level metrics and relay them to the head or export them to external systems [python/ray/dashboard/agent.py35-56](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/agent.py#L35-L56)

 
 - **Reporter Module**: The `ReporterAgent` module within the agent uses `psutil` to gather CPU, memory, disk, and network statistics [python/ray/dashboard/modules/reporter/reporter_agent.py80-82](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/reporter/reporter_agent.py#L80-L82)
 - **Hardware Monitoring**: It includes specialized managers like `GpuProfilingManager`, `CpuProfilingManager`, and `MemoryProfilingManager` to capture deep performance profiles [python/ray/dashboard/modules/reporter/reporter_agent.py62-73](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/reporter/reporter_agent.py#L62-L73)
 - **Metric Export**: It supports exporting metrics via Prometheus and OpenTelemetry. It persists ports for service discovery using `persist_port` [python/ray/dashboard/modules/reporter/reporter_agent.py48-49](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/reporter/reporter_agent.py#L48-L49)

## 2. State API

 The State API provides a unified interface to query the current state of Ray resources (Tasks, Actors, Objects, Nodes, Placement Groups) across the entire cluster.

 
### 2.1 State Aggregation

 The `StateAPIManager` acts as the core backend for the State API, utilizing a `StateDataSourceClient` to fetch data from distributed sources [python/ray/dashboard/state_aggregator.py57-60](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/state_aggregator.py#L57-L60) It aggregates data from:

 
 - **GCS**: For persistent metadata like Nodes (`GcsNodeInfo`), Actors (`ActorTableData`), and Placement Groups [python/ray/tests/test_state_api.py119-124](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_state_api.py#L119-L124)
 - **Raylets**: For real-time resource usage and local task information via `node_manager_pb2`.
 - **Core Workers**: For object metadata (`ObjectRefInfo`) and reference counting [python/ray/tests/test_state_api.py256-261](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_state_api.py#L256-L261)
 
 
### 2.2 Query Execution

 Queries are initiated via the `StateApiClient` or the `ray list/get/summarize` CLI [python/ray/util/state/state_cli.py92-95](https://github.com/ray-project/ray/blob/bf129559/python/ray/util/state/state_cli.py#L92-L95)

 
 - **Filtering/Sorting**: The API supports server-side filtering using `convert_filters_type` to minimize data transfer [python/ray/dashboard/state_api_utils.py58-60](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/state_api_utils.py#L58-L60)
 - **Summarization**: Functions like `summarize_tasks`, `summarize_actors`, and `summarize_objects` provide rolled-up views of resource states [python/ray/util/state/__init__.py74-76](https://github.com/ray-project/ray/blob/bf129559/python/ray/util/state/__init__.py#L74-L76)

## 3. Metrics and Monitoring

 Ray's metrics system is built on OpenTelemetry (OTLP) and Prometheus.

 
### 3.1 Metrics Collection

 Metrics are produced by various Ray components and captured by `METRICS_GAUGES` [python/ray/dashboard/modules/reporter/reporter_agent.py132-140](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/reporter/reporter_agent.py#L132-L140):

 
 - **Node Metrics**: `ray_node_cpu_utilization`, `ray_node_mem_used`, and `ray_node_disk_usage` [python/ray/tests/test_metrics_agent.py67-72](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_metrics_agent.py#L67-L72)
 - **Raylet/GCS**: Reports scheduling stats (`ray_scheduler_tasks`) and actor counts (`ray_gcs_actors_count`) [python/ray/tests/test_metrics_agent.py104-114](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_metrics_agent.py#L104-L114)
 - **Core Worker**: Reports object store memory (`ray_object_store_memory`) and gRPC server latencies [python/ray/tests/test_metrics_agent.py78-90](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_metrics_agent.py#L78-L90)
 
 
### 3.2 Export Mechanisms

 
 - **Prometheus**: The `PrometheusServiceDiscoveryWriter` writes a service discovery file (`prom_discovery.json`) so Prometheus can automatically find all nodes in the cluster [python/ray/_private/metrics_agent.py28-34](https://github.com/ray-project/ray/blob/bf129559/python/ray/_private/metrics_agent.py#L28-L34)
 - **OpenTelemetry**: If `RAY_ENABLE_OPEN_TELEMETRY` is set, the `OpenTelemetryMetricRecorder` exports metrics via OTLP [python/ray/dashboard/modules/reporter/reporter_agent.py39-41](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/reporter/reporter_agent.py#L39-L41)

 Ray provides pre-configured Grafana panels defined in Python and JSON:

 
 - **Default Dashboard**: Includes "Node Count", "Cluster Utilization", and "Ray OOM Kills" [python/ray/dashboard/modules/metrics/dashboards/default_dashboard_panels.py42-114](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/metrics/dashboards/default_dashboard_panels.py#L42-L114)

## 4. Job Submission API

 The Job Submission API allows users to submit, monitor, and manage Ray jobs asynchronously via a REST interface.

 
 - **JobHead**: The dashboard module that exposes the `/v1/jobs/` REST endpoints [python/ray/dashboard/modules/job/job_head.py](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/job_head.py)
 - **JobManager**: Manages the lifecycle of a job, including environment setup and process supervision [python/ray/dashboard/modules/job/job_manager.py](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/job_manager.py)
 - **JobSubmissionClient**: The Python SDK for interacting with the `JobHead` REST endpoints [python/ray/dashboard/modules/job/sdk.py](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/modules/job/sdk.py)
