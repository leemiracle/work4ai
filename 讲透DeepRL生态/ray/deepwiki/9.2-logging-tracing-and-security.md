  This page documents Ray's observability and security infrastructure, including the unified logging system, distributed tracing support, and the security model governing cluster access and inter-process communication.

 
## Logging Infrastructure

 Ray provides a distributed logging system that captures output from various system components (GCS, Raylet) and user-defined tasks and actors.

 
### Log Redirection and Rotation

 Ray processes redirect `stdout` and `stderr` to log files located in the session directory. To prevent disk exhaustion, Ray implements log rotation controlled by environment variables:

 
 - `RAY_ROTATION_MAX_BYTES`: Maximum size of a log file before rotation (defaults to 512MB) [python/ray/serve/_private/logging_utils.py11](https://github.com/ray-project/ray/blob/bf129559/python/ray/serve/_private/logging_utils.py#L11-L11)
 - `RAY_ROTATION_BACKUP_COUNT`: Number of historical log files to retain [python/ray/serve/_private/logging_utils.py11](https://github.com/ray-project/ray/blob/bf129559/python/ray/serve/_private/logging_utils.py#L11-L11)
 
 The `LogMonitor` process tracks these files and handles scenarios where inodes change due to rotation, ensuring it resumes reading from the correct position or the beginning of a new file [python/ray/tests/test_logging.py61-154](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_logging.py#L61-L154)

 
### Structured Logging

 Ray supports structured logging in both C++ and Python. The C++ logging layer uses `spdlog` as the backend [src/ray/util/logging.cc53](https://github.com/ray-project/ray/blob/bf129559/src/ray/util/logging.cc#L53-L53)

 
 - **Log Formats**: Supports `TEXT` and `JSON` encodings. The JSON format includes standard fields like `asctime`, `levelname`, and `message` [src/ray/util/logging.cc60-61](https://github.com/ray-project/ray/blob/bf129559/src/ray/util/logging.cc#L60-L61)
 - **Python Configuration**: The `LoggingConfig` class allows users to specify encoding and additional standard attributes (e.g., `task_id`, `job_id`) to be included in every log record [python/ray/_private/ray_logging/logging_config.py68-73](https://github.com/ray-project/ray/blob/bf129559/python/ray/_private/ray_logging/logging_config.py#L68-L73)
 - **Contextual Metadata**: Log records are enriched with Ray-specific IDs using keys defined in `kLogKeyJobID`, `kLogKeyWorkerID`, etc. [src/ray/util/logging.h93-107](https://github.com/ray-project/ray/blob/bf129559/src/ray/util/logging.h#L93-L107)
 
 
### Ray Serve Logging

 Serve extends the base logging with specialized filters and formatters to track requests across replicas:

 
 - `ServeComponentFilter`: Adds `component_name`, `component_id`, and `component_type` (e.g., REPLICA, PROXY) to records [python/ray/serve/_private/logging_utils.py49-63](https://github.com/ray-project/ray/blob/bf129559/python/ray/serve/_private/logging_utils.py#L49-L63)
 - `ServeContextFilter`: Injects `route`, `request_id`, and `app_name` from the active request context [python/ray/serve/_private/logging_utils.py84-104](https://github.com/ray-project/ray/blob/bf129559/python/ray/serve/_private/logging_utils.py#L84-L104)
 - `ServeFormatter`: A high-performance formatter that pre-computes format strings for common request patterns [python/ray/serve/_private/logging_utils.py124-166](https://github.com/ray-project/ray/blob/bf129559/python/ray/serve/_private/logging_utils.py#L124-L166)
 
 
### Event Logging

 Ray includes an event reporting system for high-level system events (e.g., task state changes).

 
 - **LogEventReporter**: Uses `spdlog::rotating_logger_mt` to write events to specific files like `event_GCS.log` or `event_RAYLET.log` [src/ray/util/event.cc36-85](https://github.com/ray-project/ray/blob/bf129559/src/ray/util/event.cc#L36-L85)
 - **Serialization**: Events are serialized to JSON, including standard fields and `custom_fields` for specific metadata [src/ray/util/event.cc106-129](https://github.com/ray-project/ray/blob/bf129559/src/ray/util/event.cc#L106-L129)

## Distributed Tracing

 Ray integrates with OpenTelemetry to provide distributed tracing across tasks and actors. When enabled, Ray propagates trace contexts across RPC boundaries, allowing developers to visualize the execution flow of a distributed application.

 
### Implementation Details

 
 - **Context Propagation**: Ray's C++ RPC layer handles the injection and extraction of trace headers.
 - **Task Spans**: A span is automatically created for every task execution and actor method call.
 - **Integration**: Traces can be exported to backends like Jaeger or Honeycomb via the OpenTelemetry collector.
 
 
## Security Model

 Ray's security model focuses on authentication and isolation within the cluster.

 
### Token-Based Authentication

 Ray implements token-based authentication for all internal RPC calls (GCS, Raylet, Worker). This prevents unauthorized processes from joining the cluster or submitting tasks.

 
 - **Token Generation**: By default, `ray.init()` or `ray start` generates a 64-character hex token if `auth_mode="token"` is enabled [python/ray/tests/test_token_auth_integration.py113-137](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_token_auth_integration.py#L113-L137)
 - **Storage**: The token is typically stored in `~/.ray/auth_token` [python/ray/tests/test_token_auth_integration.py116](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_token_auth_integration.py#L116-L116)
 - **Verification**: The `AuthenticationTokenLoader` class in the C++ core is responsible for loading and validating tokens during RPC handshakes [python/ray/tests/test_token_auth_integration.py18-24](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_token_auth_integration.py#L18-L24)
 - **Dashboard Security**: The `DashboardAgent` uses an `AsyncAuthenticationServerInterceptor` to enforce token checks on gRPC calls [python/ray/dashboard/agent.py120-142](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/agent.py#L120-L142)
 - **State API Security**: Access to the Dashboard and State APIs (e.g., `/api/v0/actors`) requires a valid `Authorization: Bearer <token>` header when auth is enabled [python/ray/tests/test_token_auth_integration.py174-191](https://github.com/ray-project/ray/blob/bf129559/python/ray/tests/test_token_auth_integration.py#L174-L191)
 
 
### Kubernetes RBAC Integration

 When running on Kubernetes via KubeRay, Ray leverages Kubernetes Native security:

 
 - **Service Accounts**: Ray pods run with specific ServiceAccounts.
 - **RBAC**: Role-Based Access Control limits the Ray operator's ability to manage resources within specific namespaces.
 
 
### TLS Encryption

 Ray supports TLS for all internal communication channels.

 
 - **Certificates**: Users can provide their own CA, server, and client certificates.
 - **Dashboard Integration**: The `add_port_to_grpc_server` utility is used to bind the Dashboard Agent's gRPC server with TLS credentials if configured [python/ray/dashboard/agent.py116-163](https://github.com/ray-project/ray/blob/bf129559/python/ray/dashboard/agent.py#L116-L163)

## Exception Handling and Observability

 Ray provides specialized exception types to distinguish between system failures and application-level errors.

 
 - **RayTaskError**: Indicates a task threw an exception. It wraps the original traceback and cause.
 - **C++ Terminate Handler**: A global handler `TerminateHandler` captures unhandled exceptions in the C++ core, logging the exception type and a full stack trace before aborting [src/ray/util/logging.cc112-128](https://github.com/ray-project/ray/blob/bf129559/src/ray/util/logging.cc#L112-L128)
 - **Stack Traces**: The `StackTrace` class provides a unified way to dump frames in both Windows and Linux environments [src/ray/util/logging.cc73-110](https://github.com/ray-project/ray/blob/bf129559/src/ray/util/logging.cc#L73-L110)
