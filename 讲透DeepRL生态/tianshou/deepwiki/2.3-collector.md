  The Collector component is a core part of Tianshou's data handling system, responsible for mediating interactions between policies and environments to gather experiences for reinforcement learning. It efficiently collects transitions from environments and adds them to replay buffers for training algorithms to use.

 
## Purpose and Scope

 This document covers the Collector system in Tianshou, including:

 
 - The role of collectors in the reinforcement learning workflow
 - The collector architecture and implementation details
 - How to use collectors for gathering experience data
 - Collector features such as hooks, vectorized environments, and various collection modes
 
 For information about the replay buffer system that works alongside the Collector, see [ReplayBuffer](https://deepwiki.com/thu-ml/tianshou/2.2-replaybuffer).

## Collection Modes

 The Collector supports two primary collection modes:

 
 - **Step-based collection** (`n_step`): Collect a specified number of environment steps

 
 - Good for fixed-size batch updates
 - More consistent update timing
 - **Episode-based collection** (`n_episode`): Collect a specified number of complete episodes

 
 - Better for algorithms that need complete trajectories
 - Variable collection time depending on episode lengths

## Hooks for Customizing Collection Behavior

 Tianshou's Collector supports two types of hooks for customizing collection behavior:

 
 - **Episode Rollout Hook** (`on_episode_done_hook`): Executed when an episode is completed

 
 - Receives a batch containing the entire episode data
 - Can return a dictionary with additional data to be added to the buffer
 - Example: `EpisodeRolloutHookMCReturn` which adds Monte Carlo returns to episodes
 - **Step Hook** (`on_step_hook`): Executed after each environment step

 
 - Can modify the rollout batch before it's added to the buffer
 - Useful for implementing custom rewards or observations

 - Using a wait_num parameter to specify how many environments must be ready before processing actions

## Tips and Best Practices

 
 - **Choose the right collection mode**:

 
 - Use `n_step` for stable batch sizes and consistent update timing
 - Use `n_episode` when you need complete trajectories or working with episode hooks
 - **Vectorized environments**:

 
 - For best performance, match the number of environments to your hardware capabilities
 - Use `DummyVectorEnv` for CPU-bound environments and `SubprocVectorEnv` for I/O-bound environments
 - **Buffer management**:

 
 - Size your buffer appropriately for your algorithm (larger for off-policy methods)
 - Consider using `reset_buffer(keep_statistics=True)` to clear the buffer while preserving metrics
 - **Handling NaN values**:

 
 - The default `raise_on_nan_in_buffer=True` helps catch numerical issues early
 - If using episode hooks that may produce NaNs (like in unfinished episodes), use `buffer.dropnull()` after collection
 - **Custom statistics**:

 
 - Extend `CollectStats` to track additional metrics relevant to your specific environment or algorithm

## Implementation Details and Naming Conventions

 The Collector uses consistent naming conventions for variables:

 
| Suffix | Meaning |
|---|---|
| _N | Array with size equal to number of environments |
| _R | Array with size equal to number of ready environments |
| _O | Dimensions of observations |
| _A | Dimensions of actions |
| _H | Dimensions of hidden state |
| _D | Number of envs reaching done state in current iteration |

 For example:

 
 - `ready_env_ids_R`: Array of environment indices that are ready for processing
 - `last_obs_RO`: Last observations from ready environments
 - `act_RA`: Actions for ready environments
