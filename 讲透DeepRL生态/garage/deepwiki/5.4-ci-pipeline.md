  This document provides a detailed explanation of Garage's Continuous Integration (CI) pipeline, which automates testing, validation, and deployment processes. The CI pipeline ensures code quality, compatibility, and functionality across the codebase. For information about the testing system itself, see [Testing System](https://deepwiki.com/rlworkgroup/garage/5.3-testing-system).

 
## Overview

 The Garage CI pipeline is built using GitHub Actions and is responsible for validating all contributions to the codebase. It runs a series of automated checks and tests whenever code changes are pushed, ensuring that new contributions maintain the project's quality standards before being merged.

## Workflow Triggers

 The CI pipeline can be triggered by several events:

 
 - **Push to master branch**: Runs when code is pushed directly to master
 - **Pull requests to master**: Runs when a PR is opened or updated
 - **Daily scheduled run**: Automatic daily execution at 9:00 UTC
 - **Release candidate tags**: Runs for tags matching `v20[2-9][0-9].[0-9][0-9].[0-9]+rc[0-9]`
 - **Repository dispatch events**: For fork PRs with the "ok-to-test-command"
 
 Special handling is implemented for pull requests from forks due to security constraints with GitHub Actions.

## Docker-Based Execution Environment

 The Garage CI pipeline uses Docker to create a consistent environment for all tests, ensuring reproducibility across different environments.


 The Docker container:

 
 - Is built from the `garage-dev` target in `docker/Dockerfile`
 - Is cached in GitHub Package Registry to speed up subsequent runs
 - Contains all dependencies needed for testing
 - Is used consistently across all test jobs

### Test Suite Jobs

 The CI pipeline includes several test suite jobs, each focusing on different aspects of the codebase:

 
| Test Job | Description | Test Selection |
|---|---|---|
| Normal Tests | Basic functionality tests | Not GPU, nightly, huge, flaky, large, mujoco, or mujoco_long |
| Large Tests | Larger, more time-consuming tests | Tests marked as "large" |
| MuJoCo Tests | Tests requiring MuJoCo simulator | Tests marked as "mujoco" |
| Large MuJoCo Tests | Longer tests requiring MuJoCo | Tests marked as "mujoco_long" |
| Doctest | Validates code examples in documentation | Runs through Sphinx doctest |
| Nightly Tests | Long-running tests (scheduled only) | Tests marked as "nightly" |

 All test jobs:

 
 - Use the same Docker container
 - Report code coverage to Codecov
 - Run with pytest and have automatic retry for flaky tests

### Environment Verification Jobs

 These jobs verify that Garage can be properly installed in different environments:

 
 - **Conda Environment**: Verifies installation in a fresh Conda environment
 - **Pipenv Environment**: Verifies installation using Pipenv (currently disabled due to performance issues)
 
 These tests run only during scheduled builds to avoid slowing down regular PR checks.

## Special Handling for Fork PRs

 Pull requests from forks require special handling due to GitHub Actions security restrictions:

 
 - Fork PRs don't have access to repository secrets
 - A repository dispatch event with "ok-to-test-command" is needed to run CI
 - A comment with a link to CI output is posted on the fork PR
 - Check results are updated on the original PR using GitHub Checks API
 
 This ensures security while still providing CI feedback for external contributors.

## Scheduled Maintenance Tasks

 The daily scheduled CI run includes additional maintenance tasks:

 
 - **Nightly Tests**: Runs longer tests marked as "nightly"
 - **Environment Verification**: Tests installation in fresh environments
 - **Dependency Compatibility Checks**: Verifies compatibility with latest dependencies
 
 These tasks help catch issues that might not be apparent during regular PR testing.
