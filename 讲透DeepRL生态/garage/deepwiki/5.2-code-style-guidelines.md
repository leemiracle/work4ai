## Python Code Style

 
### PEP8 Compliance

 All Python code in Garage must conform to the [PEP8](https://www.python.org/dev/peps/pep-0008/) standard. Please read and understand it in detail.

 
### Garage-specific Python Style Rules

 Beyond standard PEP8, Garage enforces several project-specific style rules:

 
#### Import Sorting

 Python package imports should be sorted alphabetically within their PEP8 groupings. The sorting is alphabetical from left to right, ignoring case and Python keywords (`import`, `from`, `as`).

 
#### String Quotation

 Prefer single-quoted strings (`'foo'`) over double-quoted strings (`"foo"`). Use double quotes only when there's a compelling reason (e.g., a single quote appears inside the string).

## Documentation Standards

 
### Docstrings

 Python files should provide docstrings for all public methods following [PEP257](https://www.python.org/dev/peps/pep-0257/) conventions and [Google](http://google.github.io/styleguide/pyguide.html#38-comments-and-docstrings) docstring formatting.

 Key docstring requirements:

 
 - Docstrings for `__init__` should be included in the class docstring
 - Provide full type information for all arguments, return values, and exceptions
 - When documenting fields that are numpy arrays or tensor types, document the expected input shape
 - Use the Sphinx `:math:` directive for shapes and equations

### Tensor Shape Documentation

 When documenting tensor shapes, follow these conventions:

 
| Symbol | Description |
|---|---|
| (...) | Tensor shapes are enclosed in parentheses |
| N | Batch dimension |
| T | Time dimension |
| .^* | Variadic parts of a tensor shape |
| [.] | Variable-length dimensions are enclosed in square brackets |
| \bullet | Flattening operator |

### pylint

 - Main code uses [.pylintrc1-54](https://github.com/rlworkgroup/garage/blob/2d594803/.pylintrc#L1-L54)

### isort

 isort automatically sorts imports according to PEP8 and Garage's alphabetical ordering rules.

 
### yapf

 yapf (Yet Another Python Formatter) ensures consistent code formatting across the codebase.

 
### flake8

 flake8 checks code for PEP8 compliance and includes additional plugins for docstring checking:

 
 - flake8-docstrings
 - pycodestyle
 - pydocstyle

## Style for Other Languages

 Non-Python files should follow the [Google Style Guide](https://github.com/rlworkgroup/garage/blob/2d594803/Google Style Guide) for that language:

 
 - XML, HTML, CSS, JavaScript, and Shell Scripts
 
 YAML files should use 2 spaces for indentation.

 
## Whitespace Conventions

 All files must follow these whitespace conventions:

 
 - Use Unix-style line endings (`\n`)
 - Trim trailing whitespace from all lines
 - All files should end in a single newline
 
 These rules are enforced by pre-commit hooks.

## Commit Message Format

 Garage follows strict git commit message guidelines to maintain a clean and informative commit history.

 **Commit Message Structure**

 
```

```

 The commit message checker enforces:

 
 - Subject line is capitalized
 - Subject line is 50 characters or less
 - No period at the end of the subject line
 - Blank line between subject and body
 - Body paragraphs wrapped to 72 characters
 
 The commit message format is verified by the `check_commit_message` script that runs as a pre-commit hook.
