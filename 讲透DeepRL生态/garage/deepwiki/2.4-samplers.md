  Samplers are a core component of the Garage reinforcement learning framework that collect experiences from environments by executing policies (agents). They form a critical link in the RL training loop by providing the data that algorithms use for learning. This document explains the sampler subsystem in Garage, including the base architecture, different implementations, and their usage patterns.

 
## Overview

 In reinforcement learning, collecting experience through interactions with environments is often computationally intensive. The sampler subsystem in Garage provides different implementations to efficiently collect these experiences, including options for multi-processing and distributed data collection.

## Core Components

 
### Base Sampler Class

 The `Sampler` abstract base class defines the interface that all sampler implementations must follow. It specifies methods for collecting samples and managing workers but does not implement the actual sampling logic.

 Key methods in the interface include:

 
 - `obtain_samples()`: Collects at least a specified number of transitions
 - `obtain_exact_episodes()`: Collects exactly n episodes per worker
 - `shutdown_worker()`: Properly terminates workers

## Sampler Implementations

 
### LocalSampler

 `LocalSampler` is the simplest implementation that runs workers in the main process. Key characteristics:

 
 - Creates workers directly in the main process
 - Synchronous operation - one worker completes before the next begins
 - Simplest to debug but lacks parallelism

## Worker Updates and Communication

 
### Agent and Environment Updates

 Samplers handle updating agents and environments through:

 
 - `WorkerFactory.prepare_worker_messages()`: Handles distribution of updates to workers
 - Sampler-specific update methods: 
 - `LocalSampler._update_workers()`
 - `RaySampler._update_workers()`
 - `MultiprocessingSampler._push_updates()`
 
 This enables:

 
 - Updating all workers with the same policy parameters
 - Using different policies for different workers
 - Changing environment parameters during training

### Parallel Execution Patterns

 The different samplers use different patterns for parallel execution:

 
 - **LocalSampler**: Simple sequential execution
 - **RaySampler**: 
 - Uses Ray's remote function calls
 - Monitors completion with `ray.wait()`
 - Retrieves results with `ray.get()`
 - **MultiprocessingSampler**: 
 - Uses queues for communication
 - Workers run a state machine with states like 'start', 'continue', 'stop', 'exit'
 - Parent process monitors queue for completed episodes

## Usage Guidelines

 
### Choosing a Sampler

 Select the appropriate sampler based on your needs:

 
| Sampler | Best For | Advantages | Limitations |
|---|---|---|---|
| LocalSampler | Debugging, simple use cases | Simplest to understand, no parallel overhead | Sequential execution is slow |
| RaySampler | Distributed setups, large-scale training | Highly scalable, can use multiple machines | Requires Ray setup |
| MultiprocessingSampler | Mid-scale training on single machine | Parallel without Ray dependency | Limited to one machine |
