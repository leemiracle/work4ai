  This document describes the Continuous Integration and Continuous Deployment (CI/CD) workflows implemented in the KSIM framework. These workflows automate testing, validation, and publishing processes to ensure code quality and streamline the release process. For information about setting up the project and its dependencies, see [Project Setup and Dependencies](https://deepwiki.com/kscalelabs/ksim/6.1-project-setup-and-dependencies).

 
## 1. Overview of CI/CD in KSIM

 KSIM employs GitHub Actions for its CI/CD pipelines, with two main workflows:

 
 - **Test Workflow**: Runs automated tests and static code analysis on all code changes
 - **Publish Workflow**: Handles package building and publication to PyPI when releases are created
 
 These workflows ensure that code quality is maintained throughout development and simplify the process of releasing new versions of the library.

### 2.2 Jobs and Steps

 The test workflow consists of a single job named `run-base-tests` that performs all necessary testing and validation:

 
| Step | Description | Command/Action |
|---|---|---|
| 1 | Check out repository | Uses actions/checkout@v3 |
| 2 | Set up Python | Uses actions/setup-python@v4 with Python 3.12 |
| 3 | Restore cached dependencies | Uses actions/cache/restore@v3 |
| 4 | Install package | pip install --upgrade --upgrade-strategy eager -e '.[dev]' |
| 5 | Run static checks | make static-checks |
| 6 | Run unit tests | make test |
| 7 | Save cache | Uses actions/cache/save@v3 (only on master branch) |

### 3.2 Build Matrix

 The `build-wheels` job uses a build matrix to create platform-specific wheels:

 
| Platform | Operating System |
|---|---|
| Linux | ubuntu-latest |
| macOS | macos-latest |

 The job can be skipped for pure Python packages by setting the `build_wheels` input parameter to `false`.

 Sources: [.github/workflows/publish.yml23-68](https://github.com/kscalelabs/ksim/blob/9d26400d/.github/workflows/publish.yml#L23-L68)

 
### 3.3 Package Building

 The workflow builds two types of distributions:

 
 - **Wheel distributions** (.whl files):

 
 - Built using `cibuildwheel`
 - Platform-specific binaries for Linux and macOS
 - Skips PyPy and musllinux builds
 - **Source distribution** (.tar.gz files):

 
 - Built using Python's `build` module
 - Contains source code only

### 4.1 Pull Request Validation

 When a developer creates or updates a pull request:

 
 - The test workflow automatically runs
 - Static checks (typing, linting, etc.) are performed
 - Unit tests verify functionality
 - Results are reported back to the pull request
 
 Sources: [.github/workflows/test.yml3-14](https://github.com/kscalelabs/ksim/blob/9d26400d/.github/workflows/test.yml#L3-L14)

 
### 4.2 Release Process

 When a new release is created:

 
 - The publish workflow is triggered
 - Platform-specific wheels are built (if configured)
 - Source distribution is created
 - All packages are published to PyPI
 
 Sources: [.github/workflows/publish.yml3-5](https://github.com/kscalelabs/ksim/blob/9d26400d/.github/workflows/publish.yml#L3-L5)

 
## 5. Manual Workflow Triggering

 Both workflows can be triggered manually:

 
 - The test workflow runs automatically on PRs and pushes to master
 - The publish workflow can be manually triggered through GitHub's interface with the option to build platform-specific wheels
 
 Sources: [.github/workflows/publish.yml6-12](https://github.com/kscalelabs/ksim/blob/9d26400d/.github/workflows/publish.yml#L6-L12)

 
## 6. Permissions and Security

 The publish workflow uses minimal permissions following the principle of least privilege:

 
| Permission | Level | Purpose |
|---|---|---|
| contents | read | Access repository contents |
| id-token | write | Generate OIDC tokens for PyPI publishing |

 This secure approach avoids the need to store PyPI API tokens in GitHub secrets.
