## Purpose and Scope

 This page explains how RL Tools supports both **static** (stack-based) and **dynamic** (heap-based) memory allocation modes, controlled at compile time. This capability is essential for deploying trained policies on embedded systems with limited or no heap allocation support. For information about backend-specific device configuration, see [Backend Configuration](https://deepwiki.com/rl-tools/rl-tools/6.2-backend-configuration). For deployment to specific embedded platforms, see [Embedded Platforms](https://deepwiki.com/rl-tools/rl-tools/8.1-embedded-platforms).

 
---

 
## Allocation Modes Overview

 RL Tools provides two memory allocation strategies that can be selected at compile time:

 
| Mode | Memory Location | Controlled By | Primary Use Case |
|---|---|---|---|
| Dynamic Allocation | Heap (via malloc/new) | Default behavior | General training on CPU/CUDA with ample memory |
| Static Allocation | Stack (compile-time sized arrays) | RL_TOOLS_STATIC_MEM flag | Embedded deployment (PX4, Crazyflie, ESP32, iOS) |

 When **static allocation** is enabled, all containers (matrices, tensors, buffers) are allocated on the stack with sizes determined at compile time. This eliminates runtime heap allocations entirely, making the code suitable for resource-constrained embedded systems.

 **Sources:** [src/rl/environments/pendulum/ppo/cpu/training.cpp2-4](https://github.com/rl-tools/rl-tools/blob/a0aef476/src/rl/environments/pendulum/ppo/cpu/training.cpp#L2-L4) [src/rl/environments/pendulum/ppo/cpu/training.cpp43-47](https://github.com/rl-tools/rl-tools/blob/a0aef476/src/rl/environments/pendulum/ppo/cpu/training.cpp#L43-L47)

## Trade-offs

 
| Aspect | Dynamic Allocation | Static Allocation |
|---|---|---|
| Memory Location | Heap | Stack |
| Allocation Time | Runtime | Compile time |
| Size Flexibility | Can vary at runtime | Fixed at compile time |
| Memory Fragmentation | Possible | None |
| Allocation Overhead | malloc/free calls | Zero runtime overhead |
| Maximum Size | Limited by heap size | Limited by stack size |
| Embedded Compatibility | Requires heap support | Works on bare metal |
| Determinism | Potential allocation failures | Fully deterministic |
| Binary Size | Smaller | Larger (includes all data) |

 **Sources:** [src/rl/environments/pendulum/ppo/cpu/training.cpp43-47](https://github.com/rl-tools/rl-tools/blob/a0aef476/src/rl/environments/pendulum/ppo/cpu/training.cpp#L43-L47) [src/rl/environments/pendulum/ppo/cpu/CMakeLists.txt1-6](https://github.com/rl-tools/rl-tools/blob/a0aef476/src/rl/environments/pendulum/ppo/cpu/CMakeLists.txt#L1-L6)

## Implementation Details

 
### No-Op Operations

 For CPU devices, the `malloc` and `free` operations for containers become no-ops when static allocation is used. The operations exist but perform no runtime work:

 
```

```

 This pattern applies to all RL Tools containers and allows the same code to work in both allocation modes.

 **Sources:** [include/rl_tools/random/operations_cpu.h16-18](https://github.com/rl-tools/rl-tools/blob/a0aef476/include/rl_tools/random/operations_cpu.h#L16-L18)

 
### Recursive Allocation

 The `malloc` and `free` operations recursively traverse the component hierarchy:

 
```

```

 Each level allocates its own members and recursively calls `malloc` on nested components. In static mode, all these calls are no-ops.

 **Sources:** [include/rl_tools/rl/algorithms/ppo/loop/core/operations_generic.h20-42](https://github.com/rl-tools/rl-tools/blob/a0aef476/include/rl_tools/rl/algorithms/ppo/loop/core/operations_generic.h#L20-L42) [include/rl_tools/rl/algorithms/ppo/operations_generic.h29-37](https://github.com/rl-tools/rl-tools/blob/a0aef476/include/rl_tools/rl/algorithms/ppo/operations_generic.h#L29-L37)
