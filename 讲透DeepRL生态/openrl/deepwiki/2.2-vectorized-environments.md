  Vectorized environments in OpenRL provide an efficient mechanism for running multiple environment instances in parallel. This parallelization significantly speeds up data collection during training by simultaneously executing multiple environment copies, which is critical for sample-efficient reinforcement learning. This page documents the architecture, implementation, and usage of vectorized environments in OpenRL.

 For information about creating custom environments, see [Custom Environments](https://deepwiki.com/OpenRL-Lab/openrl/2.3-custom-environments).

 
## 1. Architecture Overview

 Vectorized environments in OpenRL are designed around a base abstract class (`BaseVecEnv`) with two concrete implementations: synchronous (`SyncVectorEnv`) and asynchronous (`AsyncVectorEnv`). These implementations allow running multiple copies of an environment either sequentially in a single process or in parallel across multiple processes.

## 3. Types of Vectorized Environments

 
### 3.1 Synchronous Vector Environment (SyncVectorEnv)

 SyncVectorEnv runs multiple environments sequentially in a single process. It's simpler but doesn't leverage parallel processing capabilities.

 **Key characteristics:**

 
 - All environments run in the same process
 - No interprocess communication overhead
 - Simpler implementation with fewer failure modes
 - Blocking operation (the next environment doesn't start until the current one completes)
 
 
### 3.2 Asynchronous Vector Environment (AsyncVectorEnv)

 AsyncVectorEnv runs multiple environments in parallel using Python's multiprocessing. It's more efficient for compute-heavy environments but introduces complexity with interprocess communication.

 **Key characteristics:**

 
 - Environments run in separate processes
 - Non-blocking operation for improved throughput
 - Uses pipes for interprocess communication
 - Supports shared memory for efficient observation handling
 - More complex error handling due to distributed execution

## 4. Implementation Details

 
### 4.1 Asynchronous Communication Protocol

 The AsyncVectorEnv uses a command-based protocol for communication between the main process and worker processes:

 
| Command | Purpose | Data Format |
|---|---|---|
| reset | Reset environments | kwargs for reset |
| step | Step environments with actions | action array |
| seed | Set environment seeds | Seed value |
| close | Close environments | None |
| _check_spaces | Verify observation/action spaces | Spaces tuple |
| _call | Call arbitrary environment methods | Method name and arguments |
| _setattr | Set environment attributes | Attribute name and value |
| _func_exec | Execute arbitrary functions | Function and arguments |

 The communication flow for a step operation follows this pattern:

 
 - **Main process sends command**: `pipe.send(("step", action))`
 - **Worker executes command**: Runs `env.step(action)`
 - **Worker sends result**: `pipe.send(((observation, reward, terminated, info), True))`
 - **Main process processes result**: Aggregates results across all environments

### 4.2 Shared Memory Support

 For environments with large observation spaces (like images), AsyncVectorEnv offers shared memory support to avoid copying large data between processes:

 Shared memory usage is controlled by the `shared_memory` parameter when creating the AsyncVectorEnv:

 
 - When enabled (`shared_memory=True`), observation data is written directly to shared memory buffers
 - The main process reads observations directly from shared memory without copying data
 - This is especially beneficial for large observations (like images)

### 4.3 Error Handling

 AsyncVectorEnv includes robust error handling for worker process failures:

 
 - **Error detection**: Workers catch exceptions and send them through a dedicated error queue
 - **Error propagation**: The main process checks for errors after each operation
 - **Graceful failure**: When a worker fails, the main process shuts it down and raises the exception
 
 This ensures that failures in individual environments don't silently corrupt the training process.

## 6. Performance Considerations

 
### 6.1 Synchronous vs. Asynchronous

 Choose between synchronous and asynchronous environments based on:

 
 - **Environment complexity**: For compute-intensive environments, asynchronous is generally better
 - **Number of environments**: With more environments, asynchronous provides better parallelism
 - **System resources**: Asynchronous requires more CPU cores to be effective
 - **Debugging needs**: Synchronous environments are easier to debug
 
 
### 6.2 Shared Memory Optimization

 For environments with large observation spaces:

 
 - Enable shared memory (`shared_memory=True`) to avoid copying large data between processes
 - Shared memory works with standard Gymnasium spaces (Box, Discrete, Dict, etc.) but not custom spaces
 - For custom observation spaces, you'll need to use `shared_memory=False`

### 6.3 Error Handling Considerations

 AsyncVectorEnv includes robust error handling, but there are some best practices:

 
 - Always call `env.close()` when done to clean up worker processes
 - Be aware that errors in worker processes are propagated to the main process
 - Consider using timeouts (`timeout` parameter in fetch methods) to avoid hanging due to worker process issues

## 7. Integration with Training

 Vectorized environments are central to efficient training in OpenRL. The training infrastructure uses them to:

 
 - **Collect experiences in parallel**: Multiple environments generate training data simultaneously
 - **Evaluate policies**: Test policy performance across multiple environments for more robust evaluation
 - **Support self-play**: In multi-agent settings, vectorized environments can run multiple instances of agents competing/cooperating
 
 The framework is designed to seamlessly work with vectorized environments at all stages of the RL pipeline.
