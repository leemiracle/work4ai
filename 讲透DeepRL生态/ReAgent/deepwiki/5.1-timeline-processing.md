## Introduction and Purpose

 Timeline Processing is a critical data preprocessing component in ReAgent that prepares sequential decision-making data for reinforcement learning algorithms. It transforms raw interaction logs (states, actions, rewards) into properly structured temporal sequences with aligned features, actions, and rewards—a format required by reinforcement learning models.

 This document covers the implementation of timeline processing in ReAgent, which is primarily written in Scala and uses Apache Spark SQL for efficient data manipulation. Timeline processing bridges the gap between raw data collection and model training pipelines discussed in [Training Workflows](https://deepwiki.com/facebookresearch/ReAgent/4.2-training-workflows) and [Data Preprocessing](https://deepwiki.com/facebookresearch/ReAgent/5-data-preprocessing).

## Key Concepts

 Timeline processing in ReAgent revolves around transforming raw decision data into Markov Decision Process (MDP) format suitable for reinforcement learning. Key concepts include:

 
 - **MDP ID**: A unique identifier for a sequence of related decisions
 - **State Features**: Feature values representing the state
 - **Action**: The decision taken (can be discrete or parametric)
 - **Reward**: The feedback signal received after taking an action
 - **Sequence Numbers**: Ordering of states within an MDP
 - **Time Difference**: Gap between consecutive states (useful for irregular timelines)
 - **Possible Actions**: Set of actions that were available at each state

## Single-Step vs. Multi-Step Timeline Processing

 ReAgent supports both single-step and multi-step reinforcement learning through two different implementations:

 
### Single-Step Timeline Processing

 The standard `Timeline` processor creates pairs of (state, action, reward, next_state, next_action) suitable for traditional RL algorithms like DQN, SARSA, and Actor-Critic methods.

 
### Multi-Step Timeline Processing

 The `MultiStepTimeline` processor creates sequences of multiple future states, actions, and rewards. This is useful for:

 
 - Multi-step TD learning
 - N-step returns
 - Sequence modeling approaches

## Handling Different Action Types

 Timeline processing supports two types of action representations:

 
 - **Discrete Actions**: Represented as strings (e.g., "action1", "action2")
 - **Parametric Actions**: Represented as feature maps (`Map<Long, Double>`)
 
 The system automatically detects the action type from the input data schema and applies the appropriate transformations. It handles different user-defined functions (UDFs) for sorting and processing based on the action type.

## Input and Output Schema

 
### Input Schema

 The input table must contain the following fields:

 
 - `mdp_id` (STRING): Unique identifier for the MDP sequence
 - `state_features` (MAP<BIGINT,DOUBLE>): Features representing the state
 - `action` (STRING or MAP<BIGINT,DOUBLE>): Action taken
 - `action_probability` (DOUBLE): Probability of selecting the action
 - `reward` (DOUBLE): Reward received
 - `sequence_number` (BIGINT): Position within the MDP
 - `possible_actions` (ARRAY  or ARRAY<MAP<BIGINT,DOUBLE>>): Optional available actions
 
 
### Output Schema

 The output table contains the following fields:

 
 - `mdp_id` (STRING): Preserved from input
 - `state_features` (MAP<BIGINT,DOUBLE>): Current state features
 - `action` (STRING or MAP<BIGINT,DOUBLE>): Current action
 - `action_probability` (DOUBLE): Probability of the action
 - `reward` (DOUBLE or ARRAY ): Reward(s)
 - `next_state_features` (MAP<BIGINT,DOUBLE> or ARRAY<MAP<BIGINT,DOUBLE>>): Features of next state(s)
 - `next_action` (Same type as action): Action(s) taken in next state(s)
 - `sequence_number` (BIGINT): Original sequence number
 - `sequence_number_ordinal` (BIGINT): Ordinal position (1-based, no gaps)
 - `time_diff` (BIGINT or ARRAY ): Time steps between consecutive states
 - `time_since_first` (BIGINT): Time since the first state in the MDP
 - `possible_actions`: Available actions at the current state
 - `possible_next_actions`: Available actions at the next state(s)

## Handling Terminal States and Edge Cases

 The timeline processor includes special handling for:

 
 - **Terminal states**: Can be included or excluded based on the `addTerminalStateRow` configuration
 - **Empty sequences**: Appropriate empty placeholders are provided for nulls
 - **Outlier episodes**: Can filter out unusually long episodes using percentile thresholds
 - **Time window limits**: Can constrain the timeline to a maximum time window

## Common Issues and Troubleshooting

 When using timeline processing, be aware of these common issues:

 
 - **Memory pressure with large datasets**: The window functions and joins can be memory-intensive
 - **Terminal state handling**: Incorrect configuration can lead to missing or unexpected terminal states
 - **Action type mismatches**: Ensure consistent action representation (discrete or parametric)
 - **Data validation failures**: Use the validation SQL option to catch data issues early
