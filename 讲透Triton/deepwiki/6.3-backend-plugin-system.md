## Purpose and Scope

 This page documents Triton's plugin system for integrating GPU backends and custom MLIR passes. The architecture allows third-party backends and out-of-tree passes to be dynamically discovered, built, and registered. Plugins provide backend-specific compilation pipelines, hardware-specific dialects, and optimization passes while leveraging Triton's core infrastructure (e.g., `BaseBackend`).

 This page covers:

 
 - Plugin discovery and registration via CMake and environment variables.
 - The implementation of `BaseBackend` and `CUDAOptions` for the NVIDIA plugin.
 - The out-of-tree MLIR pass plugin system for inserting custom passes into `mlir::PassManager`.

## Backend Registration and Options

 Each backend defines a set of unique compilation options and a backend class. For instance, the NVIDIA backend defines `CUDAOptions` to configure hardware-specific parameters such as `num_warps`, `num_stages`, and `maxnreg` [third_party/nvidia/backend/compiler.py109-124](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L109-L124)

 
### NVIDIA Backend Implementation Example

 The `CUDABackend` class identifies its compatibility via `supports_target` by checking if `target.backend == 'cuda'` [third_party/nvidia/backend/compiler.py170-171](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L170-L171) It translates high-level targets into specific compute capabilities, e.g., `sm_80` [third_party/nvidia/backend/compiler.py102-105](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L102-L105)

## Out-of-Tree Pass Plugin System

 Triton supports an extensible pass system that allows users to load external C++ libraries containing MLIR passes and expose them to the Python compilation pipeline.

 
### Registration Mechanism (`extend_with`)

 The function `init_plugin_passes` in the C++ bindings defines `extend_with(path)`, which uses `mlir::triton::plugin::TritonPlugin::load(path)` to dynamically load a shared library [python/src/passes.cc120-131](https://github.com/triton-lang/triton/blob/f893845b/python/src/passes.cc#L120-L131)

 **Pass Discovery Flow:**

 
 - **Load Library**: The plugin library is opened, and the system retrieves a list of available passes via `plugin.listPasses()` [python/src/passes.cc135](https://github.com/triton-lang/triton/blob/f893845b/python/src/passes.cc#L135-L135)
 - **Generate Python Bindings**: For each pass found in the plugin, a new function named `add_<pass_name>` is added to the Triton Python module [python/src/passes.cc136-137](https://github.com/triton-lang/triton/blob/f893845b/python/src/passes.cc#L136-L137)
 - **Pipeline Integration**: These functions take an `mlir::PassManager` and a vector of arguments, allowing custom passes to be inserted into any stage of the backend pipeline [python/src/passes.cc138-143](https://github.com/triton-lang/triton/blob/f893845b/python/src/passes.cc#L138-L143)

## Backend Internal Tooling and Knobs

 Backends often require external toolchains (e.g., `ptxas` for NVIDIA). The plugin system leverages `triton.knobs` to discover these tools and manage environmental overrides.

 
 - **Tool Discovery**: Tools like `ptxas` are located via `env_nvidia_tool`, which searches paths like `TRITON_PTXAS_PATH` [python/triton/knobs.py194-201](https://github.com/triton-lang/triton/blob/f893845b/python/triton/knobs.py#L194-L201)
 - **Version Management**: The NVIDIA backend includes logic to select the correct `ptxas` binary (e.g., `ptxas_blackwell` for arch >= 100) [third_party/nvidia/backend/compiler.py38-39](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L38-L39)
 - **Feature Detection**: `get_features` calculates the `+ptx` feature string based on the current LLVM support and driver capabilities [third_party/nvidia/backend/compiler.py82-93](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L82-L93)

## Testing and Debugging Plugins

 Plugins can be tested by injecting them into the compilation lifecycle or using specialized debug modes.

 
 - **IR Overrides**: The `CUDAOptions` class supports `ir_override`, allowing developers to bypass the standard pipeline and inject user-defined `.ttir`, `.ttgir`, `.llir`, or `.ptx` files [third_party/nvidia/backend/compiler.py119](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L119-L119)
 - **Instrumentation**: Backends can enable sanitizers like `gsan` (Global Sanitizer) or `iisan` by modifying the `instrumentation_mode` in the backend options [third_party/nvidia/backend/compiler.py135-150](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L135-L150) [third_party/nvidia/backend/compiler.py162-164](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L162-L164)
 - **LLVM Options**: The system provides RAII guards like `ScopedLLVMOption` in `python/src/llvm.cc` to safely set and restore global LLVM flags during backend compilation stages [python/src/llvm.cc175-188](https://github.com/triton-lang/triton/blob/f893845b/python/src/llvm.cc#L175-L188)
