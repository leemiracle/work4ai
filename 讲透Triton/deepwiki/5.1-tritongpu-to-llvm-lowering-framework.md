## Purpose and Scope

 This document describes the infrastructure for converting TritonGPU IR (TTGIR) operations to LLVM IR. This lowering framework provides the core abstractions, utility classes, and pattern-based rewriting system used across all backends (NVIDIA, AMD) to transform GPU-specific operations into LLVM IR that can be compiled to machine code.

 The framework provides the `TargetInfoBase` abstraction to encapsulate hardware-specific details, allowing common lowering logic for memory operations, layout conversions, and reductions to be shared across different GPU architectures.

 
---

 
## Architecture Overview

 The conversion framework is built on MLIR's pattern rewriting infrastructure and provides common abstractions that all backends share. The architecture separates backend-agnostic conversion logic from hardware-specific code generation using a target info abstraction.

### LinearLayout Application

 A key part of the lowering is applying `LinearLayout` to map logical coordinates (register, lane, warp, block) to physical memory offsets or register indices. The framework uses `matrixVectorProd` to efficiently compute these mappings in the generated LLVM IR using bitwise operations.

## Common Lowering Patterns

 
### Layout Conversion (ConvertLayoutOp)

 `ConvertLayoutOpConversion` handles the movement of data between different layouts. It categorizes conversions based on the dimension names in the `LinearLayout`:

 
 - **Transfer Within Thread (`kRegister`):** Simply reorders the elements of the source values [lib/Conversion/TritonGPUToLLVM/ConvertLayoutOpToLLVM.cpp79-82](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ConvertLayoutOpToLLVM.cpp#L79-L82)
 - **Transfer Within Warp (`kLane`):** Uses warp shuffles (via `TargetInfo::shuffleXor`) if profitable, otherwise falls back to shared memory [lib/Conversion/TritonGPUToLLVM/ConvertLayoutOpToLLVM.cpp69-78](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ConvertLayoutOpToLLVM.cpp#L69-L78)
 - **Transfer Within CTA (`kBlock` or `kWarp`):** Moves values through shared memory using swizzling to avoid bank conflicts [lib/Conversion/TritonGPUToLLVM/ConvertLayoutOpToLLVM.cpp63-68](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ConvertLayoutOpToLLVM.cpp#L63-L68)

### Memory Operation Lowering

 Memory operations are lowered by calculating the hardware-specific vector sizes and cache policies.

 
 - **Vectorization:** The framework determines the maximum possible vector size based on pointer contiguity and hardware limits (e.g., 128-bit or 256-bit on Blackwell) [third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/LoadStoreOpToLLVM.cpp91-106](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/LoadStoreOpToLLVM.cpp#L91-L106)
 - **Cache Policies:** NVIDIA uses `createpolicy.fractional.L2` for eviction hints [third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/LoadStoreOpToLLVM.cpp46-79](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/LoadStoreOpToLLVM.cpp#L46-L79) AMD uses `LLVM::FenceOp` and specific cache modifier flags for buffer operations [third_party/amd/lib/TritonAMDGPUToLLVM/LoadStoreOpToLLVM.cpp49-71](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/lib/TritonAMDGPUToLLVM/LoadStoreOpToLLVM.cpp#L49-L71)
 - **Shared Memory:** `getSrcDstTiles` provides the tiles for `ld.shared`, `st.shared`, `ldmatrix`, and `stmatrix` based on the target capabilities [lib/Conversion/TritonGPUToLLVM/Utility.cpp43-81](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/Utility.cpp#L43-L81)

## Utility Functions

 
### External Function Management

 The `appendOrGetExternFuncOp` utility ensures that external device functions (like `vprintf`, `__assertfail`, or math library calls) are declared only once at the module level before being called [lib/Conversion/TritonGPUToLLVM/Utility.cpp88-109](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/Utility.cpp#L88-L109)

 
### Masking and Fallbacks

 For predicated loads, the framework handles constant fallbacks by emitting inline assembly that initializes registers before the conditional load (e.g., `mov.u32 $0, 0x0; @$2 ld.global.b32 { $0 }, [ $1 + 0 ];`) [test/Conversion/tritongpu_to_llvm.mlir34-45](https://github.com/triton-lang/triton/blob/f893845b/test/Conversion/tritongpu_to_llvm.mlir#L34-L45)
