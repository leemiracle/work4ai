  This document describes the **OptimizeDotOperands** pass, which optimizes memory layouts and data movement for operands of matrix multiplication (dot) operations. This pass operates at the TritonGPU dialect level and focuses on improving shared memory usage, eliminating redundant layout conversions, and enabling hardware-specific optimizations for tensor core instructions.

 For information about how dot operations are initially accelerated with MMA encodings, see [Matrix Multiplication Acceleration](https://deepwiki.com/triton-lang/triton/4.2-matrix-multiplication-acceleration). For details on how these optimizations integrate with software pipelining, see [Loop Pipelining and Software Pipelining](https://deepwiki.com/triton-lang/triton/4.4-loop-pipelining-and-software-pipelining).

## Overview and Purpose

 The `OptimizeDotOperands` pass applies a set of rewrite patterns to optimize the operands of dot operations before they are lowered to hardware instructions. The primary goals are:

 
 - **Shared Memory Swizzling**: Insert swizzled shared memory layouts to improve bank conflict avoidance.
 - **Transpose Fusion**: Fuse transpose operations into memory descriptors for MMAv3+ to avoid explicit register transposes.
 - **Memory Descriptor Reshaping**: Convert tensor reshapes into memory descriptor reshapes to eliminate data movement.
 - **Scale Optimization**: Optimize scale operand handling for scaled dot products (MMAv5).
 
 The pass runs after the `AccelerateMatmul` pass has assigned MMA encodings but before the actual lowering to LLVM IR.

 **Sources:** [lib/Dialect/TritonGPU/Transforms/OptimizeDotOperands.cpp325-334](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/OptimizeDotOperands.cpp#L325-L334)

## Pass Structure and Patterns

 
### Pass Entry Point

 
```
TritonGPUOptimizeDotOperandsPass::runOnOperation()
  ├─> Canonicalization (pre-pass)
  ├─> SwizzleShmemConvert
  ├─> FuseTransMMAV3Plus
  ├─> ReshapeMemDesc
  ├─> UseShmemForScales
  └─> ConvertLayoutOp canonicalization patterns
```

 The pass applies patterns greedily using MLIR's `applyPatternsGreedily` framework. It first runs a canonicalization pass to simplify the IR, then applies the optimization patterns.

## Shared Memory Swizzling

 
### SwizzleShmemConvert Pattern

 The `SwizzleShmemConvert` pattern identifies opportunities to use swizzled shared memory layouts, which reduce bank conflicts and improve memory bandwidth utilization.

 **Pattern Matching:**

 
```
Input:  dot(convert(trans(src)))
         where convert produces DotOperandEncoding
         
Output: dot(convert(local_load(trans(alloc(src)))))
         where alloc uses SwizzledSharedEncodingAttr
```

## Transpose Fusion for MMAv3+

 
### FuseTransMMAV3Plus Pattern

 For MMAv3 and MMAv5 (Hopper and Blackwell), transpose operations can be fused directly into the memory descriptor, avoiding the need to transpose data in registers before storing to shared memory.

 **Pattern Matching:**

 
```
Input:  dot(alloc(trans(src)))
         where dot is WarpGroupDotOp or MMAv5OpInterface
         
Output: dot(trans(alloc(src)))
         where trans is MemDescTransOp
```

 
### Implementation Details

 
 - **User Validation** [lib/Dialect/TritonGPU/Transforms/OptimizeDotOperands.cpp98-102](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/OptimizeDotOperands.cpp#L98-L102): Ensures the alloc has exactly one use and it's an MMAv3/v5 operation (e.g., `WarpGroupDotOp` or `tc_gen5_mma`).

## Memory Descriptor Reshaping

 
### ReshapeMemDesc Pattern

 Similar to transpose fusion, this pattern converts tensor reshapes into memory descriptor reshapes, avoiding data movement.

 **Pattern Matching:**

 
```
Input:  alloc(reshape(src))
         
Output: memdesc_reshape(alloc(src))
```

### NVIDIA Architectures

 
| Architecture | Capability | Dot Operand Optimizations |
|---|---|---|

| Hopper | SM90 | Transpose/Reshape fusion for MMAv3 test/TritonGPU/dot-operands.mlir35-52 |
| Blackwell | SM100 | Scale loading optimizations for MMAv5 test/Conversion/tritongpu_to_llvm_sm120.mlir1-30 |

 
### MMA Version Support

 The compiler selects the highest preferred version based on compute capability [lib/Dialect/TritonGPU/Transforms/AccelerateMatmul.cpp43-83](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/AccelerateMatmul.cpp#L43-L83):

 
 - **MMA v5**: SM100-119 (Blackwell)
 - **MMA v3**: SM90-99 (Hopper)
 - **MMA v2**: SM75-89 (Turing, Ampere, Ada)
