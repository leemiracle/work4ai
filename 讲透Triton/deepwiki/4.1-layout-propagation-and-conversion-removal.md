## Purpose and Scope

 This document describes the layout propagation and conversion removal optimization passes in the TritonGPU compiler. These passes work together to minimize expensive `ttg.convert_layout` operations by intelligently choosing and propagating tensor layouts throughout the program. The goal is to reduce layout conversions while respecting the layout requirements of anchor operations like loads, stores, and matrix multiplications.

 For information about the layout encoding system itself, see [3.3. Layout Encoding Attributes](https://github.com/triton-lang/triton/blob/f893845b/3.3. Layout Encoding Attributes) For details on the LinearLayout abstraction used during layout conversions, see [3.4. LinearLayout System](https://github.com/triton-lang/triton/blob/f893845b/3.4. LinearLayout System)

 
## System Overview

 The layout optimization system consists of two main components that run as part of the TritonGPU compilation pipeline:

 
 - **Layout Propagation** (`LayoutPropagation` class): Analyzes the IR to determine optimal layouts for all tensor values based on anchor operations [lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp60-68](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L60-L68)
 - **Layout Rematerialization** (`LayoutRematerialization` class): Reduces conversion overhead by hoisting conversions and rematerializing operations in different layouts [lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp113-115](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L113-L115)
 
 These passes transform the intermediate representation to minimize the number and cost of layout conversion operations, which can be expensive on GPUs due to register shuffling or shared memory round-trips.

## Layout Propagation Algorithm

 The layout propagation algorithm works in four distinct phases:

 
### Phase 1: Anchor Initialization

 The function `initAnchorLayout()` identifies anchor operations and initializes their layouts in the `layouts` data structure [lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp70](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L70-L70) Anchor operations are those with a layout that should be preserved for performance reasons [lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp45-46](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L45-L46)

 
| Operation Type | Condition | Reason |
|---|---|---|
| tt.load, tt.store | isExpensiveLoadOrStore() | Coalesced memory access is critical lib/Dialect/TritonGPU/Transforms/Utility.cpp1001-1012 |
| tt.dot | Always | Requires specific operand encodings for MMA lib/Dialect/TritonGPU/Transforms/TritonGPUConversion.cpp81-90 |
| AtomicRMWOp, AtomicCASOp | Always | Hardware atomics often require specific layouts lib/Dialect/TritonGPU/Transforms/Utility.cpp101-112 |
| DescriptorOpInterface | Always | TMA operations have fixed layout requirements lib/Dialect/TritonGPU/Transforms/Coalesce.cpp58-69 |

 
### Phase 2: Layout Propagation

 The algorithm recursively propagates layouts to all users of anchor ops until a fix point is reached [lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp71-72](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L71-L72)

 
 - **Forward Propagation**: Layouts are pushed from operands to results using `inferDstEncoding` [lib/Dialect/TritonGPU/Transforms/Utility.cpp558-590](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Utility.cpp#L558-L590)
 - **Backward Propagation**: In rematerialization, layouts are pushed from results to operands using `inferSrcEncoding` [lib/Dialect/TritonGPU/Transforms/Utility.cpp520-556](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Utility.cpp#L520-L556)
 
 
### Phase 3: Conflict Resolution

 If a value has multiple candidate layouts, `resolveConflicts()` decides which layout the op should keep and inserts `ttg.convert_layout` ops where necessary [lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp52-54](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L52-L54)

 
### Phase 4: IR Rewriting

 The IR is rewritten by walking the function in dominance order. Each op is rewritten using the layout decided during the analysis phase [lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp55-59](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/RemoveLayoutConversions.cpp#L55-L59)
