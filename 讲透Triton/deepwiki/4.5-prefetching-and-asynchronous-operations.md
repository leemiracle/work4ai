## Purpose and Scope

 This document describes the prefetching and asynchronous operation mechanisms in Triton's compiler optimization pipeline. These transformations overlap computation with memory transfers to hide memory latency and improve GPU utilization. The two main components are:

 
 - **Prefetching**: A transformation that splits dot operation operands into smaller chunks and pulls the "head" of the load out of the loop.
 - **Asynchronous Operations**: Hardware-accelerated memory copy and wait operations that run concurrently with computation.
 
 For information about the broader loop pipelining framework, see [Loop Pipelining and Software Pipelining](https://github.com/triton-lang/triton/blob/f893845b/Loop Pipelining and Software Pipelining) For details on memory layout conversions, see [Layout Conversion Lowering](https://github.com/triton-lang/triton/blob/f893845b/Layout Conversion Lowering)

 
---

 
## Overview

 Prefetching and asynchronous operations work together to maximize GPU throughput. The key insight is that while matrix multiplication (`tt.dot`) operations execute, the GPU can simultaneously load data for the next iteration from global memory into shared memory, or from shared memory into registers.

## The Prefetch Pass

 The Prefetch Pass (`tritongpu-prefetch`) rewrites `tt.dot` loops to pull the prefetched head out of the loop and prefetch the next iteration's operands at the end of the loop body. This is primarily used for `ttg.local_load` operations.

## Asynchronous Operations

 Triton uses specialized IR operations to represent hardware-accelerated asynchronous memory transfers, particularly for moving data from Global Memory to Local (Shared) Memory.

 
### Key Dialect Operations

 
| Operation | Dialect | Purpose |
|---|---|---|
| ttg.async_copy_global_to_local | TritonGPU | Initiates an asynchronous copy. |
| ttg.async_wait | TritonGPU | Waits for a specific number of async groups to complete. |
| ttg.async_commit_group | TritonGPU | Marks the end of a group of async operations. |
| amdg.buffer_load_to_local | TritonAMDGPU | AMD-specific asynchronous buffer load to LDS. |

### AMD-Specific Asynchronous Coalescing

 The `CoalesceAsyncCopy` pass in the AMD backend ensures that asynchronous copies are optimized for the hardware's Load-to-LDS (Shared Memory) capabilities.

 The pass checks `canLoadDirectToLDS` and adjusts the `BlockedEncodingAttr` (specifically `sizePerThread`) to match the hardware's supported vector sizes (e.g., 32-bit, 64-bit, or 128-bit loads). If the blocked and shared encoding orders disagree, the pass distributes lanes/warps following the shared order to map consecutive lanes to consecutive LDS offsets.

## Lowering to LLVM

 Asynchronous operations are lowered to target-specific intrinsics to utilize hardware features like NVIDIA's `cp.async` or AMD's `global_load_lds`.

 
### AMD Lowering Example

 On AMD CDNA3/CDNA4 architectures (e.g., `gfx942`, `gfx950`), asynchronous operations map to specific `rocdl` intrinsics:

 
 - **Async Copy**: Lowered to `rocdl.global.load.async.lds` or `rocdl.raw.ptr.buffer.load.async.lds`.
 - **Wait**: Lowered to `rocdl.wait.asyncmark`. The commit group count is passed through directly as LLVM handles the final `waitcnt` logic.
 - **Commit**: Lowered to `rocdl.asyncmark`.
 
 **Sources:** [test/Conversion/amd/async_ops_to_llvm.mlir16-114](https://github.com/triton-lang/triton/blob/f893845b/test/Conversion/amd/async_ops_to_llvm.mlir#L16-L114) [test/Conversion/amd/buffer_load_to_local_to_llvm.mlir16-44](https://github.com/triton-lang/triton/blob/f893845b/test/Conversion/amd/buffer_load_to_local_to_llvm.mlir#L16-L44) [test/Conversion/amd/async_ops_to_llvm.mlir79-97](https://github.com/triton-lang/triton/blob/f893845b/test/Conversion/amd/async_ops_to_llvm.mlir#L79-L97)

 
### Alias Analysis for Async Ops

 To help LLVM optimize around asynchronous transfers, Triton attaches `alias_scopes` and `noalias_scopes` to these operations. This informs the LLVM optimizer that memory being written by an async copy does not conflict with other local loads until a wait occurs. The scopes are typically identified as `amdg.AsyncCopies` and `amdg.LocalLoads`.

 **Sources:** [test/Conversion/amd/async-ops-alias-scopes.mlir4-22](https://github.com/triton-lang/triton/blob/f893845b/test/Conversion/amd/async-ops-alias-scopes.mlir#L4-L22) [test/Conversion/amd/async-ops-alias-scopes.mlir73-79](https://github.com/triton-lang/triton/blob/f893845b/test/Conversion/amd/async-ops-alias-scopes.mlir#L73-L79)

 
### Hardware-Specific ID Retrieval

 Asynchronous coordination often depends on knowing the current warp or wave ID.

 
 - On `gfx12`, Triton uses the `rocdl.wave.id` instruction.
 - On `gfx9` (CDNA3/4), there is no dedicated hardware instruction for `wave_id`. It is computed from `rocdl.workitem.id.x` divided by the warp size, followed by a `rocdl.readfirstlane` instruction to ensure the value is scalarized and stored in a scalar register (e.g., initializing `$m0`).
