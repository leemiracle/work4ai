## Purpose and Scope

 This page documents Triton's GitHub Actions-based CI/CD infrastructure, covering LLVM compilation, Python wheel distribution, documentation generation, and test execution. The CI/CD system manages dependencies across multiple platforms, automates binary artifact generation, and validates compiler correctness through integration testing on NVIDIA and AMD hardware.

 For information about local test execution and test structure, see page 7.1. For debugging environment variables and profiling utilities, see page 7.3 and 7.4.

 
## CI/CD Infrastructure Overview

 Triton's CI/CD consists of several primary workflows implemented as GitHub Actions YAML files:

 **Main CI/CD Workflows**

 
| Workflow File | Primary Purpose | Trigger Conditions |
|---|---|---|
| llvm-build.yml | Build LLVM/MLIR binaries for multiple platforms | Push to main with changes to cmake/llvm-build-info.json |
| wheels.yml | Build Python wheels with manylinux compatibility | Daily at 08:00 UTC, manual dispatch, or PRs affecting the workflow |
| ci.yml | Main integration test driver | Pull requests, pushes to main |

 The workflows execute on a variety of runners: GitHub-hosted Ubuntu/macOS/Windows, and self-hosted GPU nodes (NVIDIA A100, H100, GB200; AMD gfx90a, gfx942, gfx950).

## Integration Testing Pipeline

 Triton uses a multi-stage integration testing pipeline triggered on pull requests and post-submit.

 
### Runner Preparation

 The `runner-preparation.yml` workflow determines whether to run integration tests based on the event type and file changes.

 
 - **Pre-submit**: Always enabled for PRs [.github/workflows/runner-preparation.yml23-25](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/runner-preparation.yml#L23-L25)
 - **Post-submit**: Enabled if `cmake/` files changed or if >=4 hours have passed since the last successful run [.github/workflows/runner-preparation.yml92-98](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/runner-preparation.yml#L92-L98)
 - **Matrix Generation**: It outputs matrices for NVIDIA, AMD, and MacOS runners based on the repository path [.github/workflows/runner-preparation.yml103-111](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/runner-preparation.yml#L103-L111)
 
 Sources: [.github/workflows/runner-preparation.yml21-111](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/runner-preparation.yml#L21-L111)

### Build Process and cibuildwheel

 Triton uses `cibuildwheel` to generate manylinux-compatible wheels:

 
 - **Environment**: `MAX_JOBS=4` is used to prevent OOM during compilation [.github/workflows/wheels.yml81](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/wheels.yml#L81-L81)
 - **Stable ABI**: Builds a single abi3 wheel on Python 3.12+ using `TRITON_STABLE_ABI=ON` [.github/workflows/wheels.yml110-113](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/wheels.yml#L110-L113)
 - **Toolchain**: Uses `dnf install clang lld -y` inside the `manylinux_2_28` image [.github/workflows/wheels.yml91](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/wheels.yml#L91-L91)
 - **Repair**: `auditwheel repair` is configured to exclude `libtriton.so` to keep wheel size manageable [.github/workflows/wheels.yml97](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/wheels.yml#L97-L97)

## Caching Strategy

 To maintain fast CI cycles, Triton utilizes several caching mechanisms:

 
 - **Dependency Cache**: Build dependencies (LLVM, NVIDIA toolchain, JSON) are cached based on SHA256 hashes of configuration files like `cmake/llvm-info.json` [.github/workflows/integration-tests-nvidia.yml37-65](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/integration-tests-nvidia.yml#L37-L65)
 - **ccache**: Enabled via `TRITON_BUILD_WITH_CCACHE: "true"` to speed up C++ compilation across workflow runs [.github/workflows/integration-tests-nvidia.yml24](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/integration-tests-nvidia.yml#L24-L24)
 - **sccache**: Specifically used during the LLVM build pipeline for distributed compilation caching [.github/workflows/llvm-build.yml141](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/llvm-build.yml#L141-L141)
 - **Compile Trace Cache**: The `TRITON_CI_COMPILE_TRACE_DIR` is used during warmup to track and report on compile cache completeness [.github/workflows/integration-tests-nvidia.yml97-104](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/integration-tests-nvidia.yml#L97-L104)
