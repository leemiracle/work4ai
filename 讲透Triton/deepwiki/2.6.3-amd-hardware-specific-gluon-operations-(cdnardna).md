  This page documents the hardware-specific APIs and IR components within the Gluon frontend targeted at AMD's CDNA (Matrix Core) and RDNA (Graphics/WMMA) architectures. These operations provide explicit control over scaled matrix multiplication, asynchronous memory movement, and architecture-specific synchronization primitives.

 
## Matrix Multiplication Acceleration (MFMA and WMMA)

 Triton supports two primary hardware accelerators on AMD GPUs: **MFMA** (Matrix Fused Multiply-Add) for CDNA architectures and **WMMA** (Wavefront Matrix Multiply-Add) for RDNA and GFX1250 architectures.

 
### MFMA Layouts and Scaled Operations (CDNA)

 The `AMDMFMALayout` class represents the distribution of matrix elements across registers for CDNA hardware `[python/triton/experimental/gluon/language/amd/_layouts.py:16-37]`. It supports versions 1 through 4 (targeting GFX908 to GFX950).

 On CDNA4 (GFX950), Gluon introduces `mfma_scaled` to support OCP Microscaling Formats (MX) `[python/triton/experimental/gluon/language/amd/cdna4/__init__.py:28-51]`. This allows multiplying tensors of types such as `e2m1` (FP4), `e4m3` (FP8), and `e5m2` (BF8) with associated scale factors.

 Key scaling utilities include:

 
 - **`get_mfma_scale_layout`**: Computes the required register distribution for scale tensors to match the dot operand layout `[python/triton/experimental/gluon/language/amd/cdna4/__init__.py:110-128]`.
 - **`scaled_upcast`**: Folds raw E8M0 scale payloads into an upcast operation, converting them to the internal format expected by CDNA4 hardware `[python/triton/experimental/gluon/language/amd/cdna4/__init__.py:70-86]`.
 
 
### WMMA Operations (RDNA/GFX1250)

 The `AMDWMMALayout` targets RDNA3, RDNA4, and the GFX1250 architecture `[python/triton/experimental/gluon/language/amd/_layouts.py:110-128]`. GFX1250 specifically introduces version 3 WMMA, which supports larger instruction shapes like 16x16x128 for packed 4-bit types `[test/TritonGPU/amd/accelerate-amd-matmul-wmma-gfx1250.mlir:9-10]`.

 
### Hardware Intrinsic Selection

 The compiler maps high-level `tt.dot` or `tt.dot_scaled` operations to specific hardware intrinsics based on the target ISA and operand types:

 
 - **MFMA Selection**: `chooseMfmaInstruction` selects the appropriate `MfmaIntrinsic` based on the CDNA version and tensor shapes (e.g., 32x32, 16x16, or asymmetric 64x4) `[third_party/amd/lib/TritonAMDGPUTransforms/AccelerateAMDMatmul.cpp:173-196]`.
 - **WMMA Selection**: The `WmmaDatabase` maintains a mapping of architecture versions to LLVM intrinsics (e.g., `llvm.amdgcn.wmma.f32.16x16x16.f16`) `[third_party/amd/lib/TritonAMDGPUTransforms/WmmaGroup.cpp:34-106]`.

## Memory Operations and Buffer APIs

 AMD-specific memory operations in Gluon optimize for GCN/CDNA's buffer resource model and Local Data Share (LDS).

 
### Buffer Load/Store and Atomics

 Gluon provides `buffer_load`, `buffer_store`, and various `buffer_atomic_*` operations `[python/triton/experimental/gluon/language/amd/cdna3/__init__.py:98-161]`. Unlike standard pointer-based loads, these use a **base pointer + offset tensor** model.

 
 - They map directly to `buffer_load`/`buffer_store` in the Triton Dialect `[python/triton/experimental/gluon/language/amd/cdna3/__init__.py:130-161]`.
 - Supports cache modifiers and specialized atomic operations (e.g., `fadd` on `bf16` specifically for CDNA4) `[python/triton/experimental/gluon/language/amd/cdna3/__init__.py:64-70]`.
 
 
### Shared Memory Optimization

 For CDNA4, Triton includes logic to compute bank-conflict-free shared memory layouts:

 
 - **`compute_efficient_padded_shared_layout`**: Generates a `PartitionedSharedLayout` that avoids LDS bank conflicts for dot operands by applying specific padding patterns based on the MFMA instruction shape and data type `[python/triton/experimental/gluon/language/amd/cdna4/__init__.py:138-158]`.
 - **`load_shared_fp4_repacked`**: A specialized operation to load M/N-packed FP4 bytes from shared memory into the K-packed register layout required for matrix cores `[python/triton/experimental/gluon/language/amd/cdna4/__init__.py:90-99]`.
 
 
### LDS Transpose (ds_read_tr)

 On GFX1250 and CDNA4, the hardware supports `ds_read_tr`, which can perform a transpose while loading from LDS to registers. The compiler uses `lowerDsReadTr` to emit these intrinsics (e.g., `llvm.amdgcn.ds.load.tr16.b128`) when the `LinearLayout` conversion matches the hardware's transpose pattern `[third_party/amd/lib/TritonAMDGPUToLLVM/MemoryOpToLLVM.cpp:48-80, 114-150]`.

## Synchronization and Warp Patterns

 
### PartitionedSharedLayout and Warp Pipelines

 The `PartitionedSharedLayout` (often referenced in warp-pipeline patterns) allows splitting shared memory access between different groups of warps. This is used to implement producer-consumer loops where some warps perform global-to-shared copies while others perform shared-to-register MFMA operations.

 
### CDNA5/GFX1250 Advanced Features

 Experimental support for the latest AMD architectures includes:

 
 - **TDM (Tensor Data Movement)**: Specialized hardware for moving matrix data.
 - **mbarrier**: Hardware-accelerated barriers for asynchronous synchronization across the thread block or clusters.
 - **Cluster Support**: APIs to manage groups of Compute Units (CUs) for multi-CU collaborative kernels.

### Summary of Supported ISA Features

 
| Feature | Architecture | Gluon API / IR Attribute |
|---|---|---|
| MFMA v1-v4 | CDNA 1/2/3/4 | AMDMFMALayout |
| MX Scaled Dot | CDNA 4 (GFX950) | mfma_scaled, scaled_upcast |
| WMMA v1-v3 | RDNA 3/4, GFX1250 | AMDWMMALayout |
| LDS Transpose | CDNA 4, GFX1250 | ds_read_tr (via ttg.local_load) |
| Buffer Ops | All AMD GCN/CDNA | buffer_load, buffer_store, buffer_atomic |
| Async Copy | CDNA 4/5 | amd.async_copy |
