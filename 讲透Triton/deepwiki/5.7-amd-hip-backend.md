## Purpose and Scope

 The AMD HIP Backend is the compilation pipeline component responsible for translating Triton kernels into executable code for AMD GPUs. This backend handles the complete transformation from Triton's intermediate representations (TTIR and TTGIR) through LLVM IR to AMDGCN assembly and finally to HSACO (Heterogeneous-System Architecture Code Object) binaries that execute on AMD hardware via the ROCm runtime.

 This page covers the AMD-specific compilation stages, optimization passes, code generation, and target features.

## Architecture Support and Target Features

 The AMD backend supports multiple GPU architectures across the CDNA (data center) and RDNA (gaming/consumer) product lines.

 
### Supported Architectures

 
| Architecture | Example GPUs | Warp Size | Key Features |
|---|---|---|---|
| gfx942 (CDNA3) | MI300A/X | 64 | MFMA, XF32/TF32, Block Pingpong |
| gfx950 (CDNA4) | MI350 | 64 | MFMA, MXFP (FP4/FP8), Improved AsyncCopy |
| gfx110x/115x (RDNA3) | RX 7000 series | 32 | WMMA, In-thread Transpose |
| gfx1200/1250 (RDNA4) | RX 8000 series | 32 | WMMA, Enhanced async, Coexec Scheduler |

 **Architecture Detection and Configuration**:

 The backend determines architecture capabilities at initialization via `HIPOptions` ([third_party/amd/backend/compiler.py69-105](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/backend/compiler.py#L69-L105)) and the `HIPBackend` class ([third_party/amd/backend/compiler.py131-139](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/backend/compiler.py#L131-L139)). It uses specific predicates like `is_async_copy_enabled` ([third_party/amd/backend/compiler.py32-33](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/backend/compiler.py#L32-L33)) and `is_pingpong_schedule_enabled` ([third_party/amd/backend/compiler.py22-24](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/backend/compiler.py#L22-L24)) to toggle features.

## Key AMD-Specific Optimization Passes

 For deep technical details on these passes, see the child pages.

 
### [AMD-Specific Optimizations and Passes](https://deepwiki.com/triton-lang/triton/5.7.1-amd-specific-optimizations-and-passes)

 
 - **AccelerateMatmul**: Selects optimal matrix multiplication instructions (MFMA for CDNA, WMMA for RDNA) based on target architecture ([third_party/amd/include/TritonAMDGPUTransforms/Passes.td41-62](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/include/TritonAMDGPUTransforms/Passes.td#L41-L62)).
 - **Pipelining**: Overlaps computation with memory transfers using `TritonAMDGPUPipeline` and `TritonAMDGPUScheduleLoops` ([third_party/amd/include/TritonAMDGPUTransforms/Passes.td6-39](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/include/TritonAMDGPUTransforms/Passes.td#L6-L39)).
 - **Block Pingpong**: Interleaves instructions from multiple warps to maximize matrix core utilization on CDNA3/4 ([third_party/amd/include/TritonAMDGPUTransforms/Passes.td223-228](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/include/TritonAMDGPUTransforms/Passes.td#L223-L228)).
 - **LDS Optimization**: Manages Local Data Share (shared memory) allocation and access via `AllocateAMDGPUSharedMemoryPass` ([third_party/amd/python/triton_amd.cc67-69](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/python/triton_amd.cc#L67-L69)).
 
 
### [AMD Load/Store and Memory Operations](https://deepwiki.com/triton-lang/triton/5.7.2-amd-loadstore-and-memory-operations)

 
 - **Buffer Operations**: Converts `tt.load/store` to AMD-specific buffer intrinsics using `TritonAMDGPUConvertToBufferOps` ([third_party/amd/include/TritonAMDGPUTransforms/Passes.td169-185](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/include/TritonAMDGPUTransforms/Passes.td#L169-L185)).
 - **Direct-to-LDS**: Implements async copies that bypass registers to load data directly into shared memory ([third_party/amd/include/TritonAMDGPUTransforms/Passes.td23-39](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/include/TritonAMDGPUTransforms/Passes.td#L23-L39)).
 - **Resource Descriptors**: Manages the 128-bit TDM and buffer descriptors used by hardware ([third_party/amd/backend/driver.c115-212](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/backend/driver.c#L115-L212)).
 
 
### [Shuffle and Warp Reduction on AMD](https://deepwiki.com/triton-lang/triton/5.7.3-shuffle-and-warp-reduction-on-amd)

 
 - **DPP and Permlane**: Uses Data Parallel Primitives and permlane instructions for efficient cross-lane data exchange.
 - **In-Thread Transpose**: Optimizes register layouts for matrix operations without using shared memory ([third_party/amd/include/TritonAMDGPUTransforms/Passes.td214-221](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/include/TritonAMDGPUTransforms/Passes.td#L214-L221)).

## LLVM IR Lowering and Binary Generation

 The final stages of the pipeline involve lowering to LLVM IR and assembling the binary.

 
### TritonAMDGPUToLLVM Lowering

 The `ConvertTritonAMDGPUToLLVM` pass ([third_party/amd/lib/TritonAMDGPUToLLVM/TritonGPUToLLVM.cpp74-80](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/lib/TritonAMDGPUToLLVM/TritonGPUToLLVM.cpp#L74-L80)) handles the conversion of TritonGPU operations to the LLVM dialect, incorporating `ROCDL` intrinsics for hardware-specific functionality. It also manages shared memory allocation and synchronization via `ModuleAllocation` and `ModuleMembarAnalysis` ([third_party/amd/lib/TritonAMDGPUToLLVM/TritonGPUToLLVM.cpp104-116](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/lib/TritonAMDGPUToLLVM/TritonGPUToLLVM.cpp#L104-L116)).

 **Sources**: [third_party/amd/lib/TritonAMDGPUToLLVM/TritonGPUToLLVM.cpp74-180](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/lib/TritonAMDGPUToLLVM/TritonGPUToLLVM.cpp#L74-L180) [third_party/amd/lib/TritonAMDGPUToLLVM/CMakeLists.txt1-48](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/lib/TritonAMDGPUToLLVM/CMakeLists.txt#L1-L48)

 
### Binary Production (HSACO)

 The backend produces `hsaco` (HIP Shared Assembly Code Object) files ([third_party/amd/backend/compiler.py149](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/backend/compiler.py#L149-L149)). The driver utility in `third_party/amd/backend/driver.py` and `third_party/amd/backend/driver.c` provides the low-level interface to the ROCm runtime for loading these binaries and launching kernels.
