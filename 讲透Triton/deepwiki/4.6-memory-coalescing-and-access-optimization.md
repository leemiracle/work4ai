## Purpose and Scope

 This page explains how Triton optimizes memory access patterns to maximize GPU memory bandwidth through coalescing. Memory coalescing refers to combining multiple memory accesses from different threads into fewer, wider transactions that can be serviced more efficiently by the memory system. The compiler analyzes tensor layouts, access patterns, and thread mappings to determine optimal vectorization strategies for load and store operations.

 For information about shared memory layout optimization and swizzling, see [Memory Descriptors and Shared Memory Layouts](https://deepwiki.com/triton-lang/triton/3.5-memory-descriptors-and-shared-memory-layouts). For information about prefetching and asynchronous memory operations in the context of pipelining, see [Prefetching and Asynchronous Operations](https://deepwiki.com/triton-lang/triton/4.5-prefetching-and-asynchronous-operations). For the actual lowering of memory operations to LLVM IR, see [Memory Operations Lowering](https://deepwiki.com/triton-lang/triton/5.2-memory-operations-lowering).

## Memory Access Pattern Analysis

 The compiler performs contiguity and alignment analysis to determine vectorization opportunities for memory operations. The analysis is performed by `ModuleAxisInfoAnalysis` which tracks properties of tensor values through the computation graph.

 
### Axis Information Lattice

 The `AxisInfo` class represents known properties of a value's axes in a dataflow lattice [include/triton/Analysis/AxisInfo.h23-175](https://github.com/triton-lang/triton/blob/f893845b/include/triton/Analysis/AxisInfo.h#L23-L175) It tracks three primary vectors:

 
 - **Contiguity**: The length of the shortest sequence of contiguous integers along a dimension [include/triton/Analysis/AxisInfo.h45-67](https://github.com/triton-lang/triton/blob/f893845b/include/triton/Analysis/AxisInfo.h#L45-L67)
 - **Divisibility**: The largest power of two that divides the first element of all groups of length contiguity along a dimension [include/triton/Analysis/AxisInfo.h70-93](https://github.com/triton-lang/triton/blob/f893845b/include/triton/Analysis/AxisInfo.h#L70-L93)
 - **Constancy**: The length of the shortest sequence of repeating values along a dimension [include/triton/Analysis/AxisInfo.h105-121](https://github.com/triton-lang/triton/blob/f893845b/include/triton/Analysis/AxisInfo.h#L105-L121)
 - **Constant Value**: The exact fixed-width integer scalar or splat bits, if known [include/triton/Analysis/AxisInfo.h174-175](https://github.com/triton-lang/triton/blob/f893845b/include/triton/Analysis/AxisInfo.h#L174-L175)

### Contiguity and Vectorization Detection

 The compiler uses `AxisInfo` to determine how many consecutive elements each thread accesses. The `ConstantEvaluator` within the axis analysis helps refine these bounds for arithmetic operations [lib/Analysis/AxisInfo.cpp39-63](https://github.com/triton-lang/triton/blob/f893845b/lib/Analysis/AxisInfo.cpp#L39-L63)

 The `TritonGPUCoalesce` pass uses this analysis to determine the best layout for memory accesses. ## The Coalescing Pass

 The `CoalescePass` is a `ModulePass` that transforms memory operations to use layouts optimized for coalesced access [lib/Dialect/TritonGPU/Transforms/Coalesce.cpp71-121](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Coalesce.cpp#L71-L121)

 "Coalescing Transformation Pipeline"

 The pass follows these steps:

 
 - Runs `ModuleAxisInfoAnalysis` to gather `AxisInfo` for all values [lib/Dialect/TritonGPU/Transforms/Coalesce.cpp80](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Coalesce.cpp#L80-L80)
 - Walks the module to find memory access operations (Load, Store, Atomic) [lib/Dialect/TritonGPU/Transforms/Coalesce.cpp86-89](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Coalesce.cpp#L86-L89)
 - For each operation, determines a "coalesced" layout where the fastest-varying dimension in memory matches the fastest-varying dimension in the thread mapping [lib/Dialect/TritonGPU/Transforms/Coalesce.cpp101-104](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Coalesce.cpp#L101-L104)
 - Replaces the original operation with one using the new layout, inserting `ttg.convert_layout` ops via `convertDistributedOpEncoding` [lib/Dialect/TritonGPU/Transforms/Coalesce.cpp117-120](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Coalesce.cpp#L117-L120)

## Instruction Reordering for Access Optimization

 The `TritonGPUReorderInstructions` pass further optimizes memory performance by moving operations to reduce register pressure and improve scheduling [lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp73-174](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp#L73-L174)

 Key reordering strategies include:

 
 - **Sinking Conversions**: Moving `ttg.convert_layout` after the last `ttg.local_dealloc` in its block to free up registers earlier [lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp97-103](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp#L97-L103)
 - **Hoisting Allocations**: Moving `ttg.local_alloc` immediately after its source definition (unless it's a scalar/splat) to minimize the lifetime of the source tensor in registers [lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp125-136](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp#L125-L136)
 - **Dot Operand Ordering**: Moving `dot` operand conversions so that operand 1 (B) is processed after operand 0 (A) if it helps avoid write-after-read hazards or improves dominance [lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp147-171](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/ReorderInstructions.cpp#L147-L171)

## Layout-Driven Vectorization

 Vectorization in Triton is heavily dependent on the `BlockedEncodingAttr`. The compiler selects `sizePerThread` and `order` to ensure that consecutive threads in the same warp access consecutive memory locations.

 
### Vectorization for Descriptor Operations

 For hardware features like NVIDIA TMA (Tensor Memory Accelerator), the compiler picks layouts that support up to 16-byte vectorization even when L1 coalescing is handled by hardware [lib/Dialect/TritonGPU/Transforms/Coalesce.cpp26-29](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Coalesce.cpp#L26-L29)

## Test Verification of Alignment and Coalescing

 Triton uses specialized test passes to verify that axis information and alignment are correctly inferred.

 
### Alignment Inference Examples

 The `test-print-alignment` pass verifies `AxisInfo` properties [test/Analysis/test-alignment.mlir1-15](https://github.com/triton-lang/triton/blob/f893845b/test/Analysis/test-alignment.mlir#L1-L15)

 
 - `arith.constant 1`: Results in `contiguity = [1], divisibility = [1], constancy = [1], constant_value = 1`.
 - `arith.extui %minus_one : i8 to i32`: Results in `constant_value = 255` [test/Analysis/test-alignment.mlir22](https://github.com/triton-lang/triton/blob/f893845b/test/Analysis/test-alignment.mlir#L22-L22)

## Alias Analysis in Shared Memory

 The `SharedMemoryAliasAnalysis` is used during memory optimization to determine if different memory descriptors point to the same physical shared memory buffer [lib/Analysis/Alias.cpp23-64](https://github.com/triton-lang/triton/blob/f893845b/lib/Analysis/Alias.cpp#L23-L64)

 
 - `LocalAllocOp` creates a new buffer [lib/Analysis/Alias.cpp37-39](https://github.com/triton-lang/triton/blob/f893845b/lib/Analysis/Alias.cpp#L37-L39)
 - `MemDescViewTrait` operations (like `memdesc_trans` or `memdesc_index`) create aliases to existing buffers [lib/Analysis/Alias.cpp40-42](https://github.com/triton-lang/triton/blob/f893845b/lib/Analysis/Alias.cpp#L40-L42)
