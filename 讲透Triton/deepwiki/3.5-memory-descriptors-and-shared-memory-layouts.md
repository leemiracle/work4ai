## Purpose and Scope

 This page documents the memory descriptor system and shared memory layouts in Triton. Memory descriptors represent handles to GPU memory allocations (shared memory or tensor memory) with associated layout information, enabling explicit control over data placement and access patterns in Triton kernels. This page covers:

 
 - Memory descriptor types (`MemDescType`) and their associated memory spaces.
 - Shared memory layout encodings (`SwizzledSharedEncodingAttr`, `NVMMASharedEncodingAttr`, etc.).
 - Tensor memory layouts for NVIDIA Blackwell architecture.
 - Operations on memory descriptors (allocation, load, store, slicing, reshaping).
 - The use of `LinearLayout` for canonical representation of memory mappings.

## Memory Descriptor System Overview

 Memory descriptors are first-class values in TritonGPU IR that represent handles to memory regions with associated layout metadata. Unlike distributed tensors (which represent values distributed across threads), memory descriptors represent shared memory or device-specific memory allocations that can be accessed by multiple threads. The C++ type is `mlir::triton::gpu::MemDescType`, and the memory space is defined via attributes like `SharedMemorySpaceAttr`.

 The memory descriptor system supports two primary memory spaces:

 
 - **Shared Memory**: GPU-shared memory accessible by all threads in a CTA. Created via `ttg.local_alloc` [lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp37-38](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp#L37-L38)

## Shared Memory Layout Encodings

 Shared memory layouts describe how tensor elements are mapped to shared memory addresses. Different layouts optimize for hardware constraints like bank conflicts.

 
### SwizzledSharedEncodingAttr

 `SwizzledSharedEncodingAttr` applies XOR-based swizzling to shared memory addresses. The swizzling pattern is controlled by:

 
| Parameter | Description |
|---|---|
| vec | Number of elements swizzled together as a unit include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td95 |
| perPhase | Number of rows per swizzling phase include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td96 |
| maxPhase | Maximum phase value for XOR swizzling include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td97 |
| order | The fastest-changing axis first include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td98 |

 The conversion to `LinearLayout` for this attribute uses a 2D basis construction where the row dimension is XORed with the column dimension based on `vec`, `perPhase`, and `maxPhase` [lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp75-86](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp#L75-L86)

 **Sources:** [include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td10-100](https://github.com/triton-lang/triton/blob/f893845b/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td#L10-L100) [lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp50-96](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp#L50-L96)

 
### NVMMASharedEncodingAttr

 `NVMMASharedEncodingAttr` represents the shared memory layout required for NVIDIA MMAv3 (Hopper) and MMAv5 (Blackwell) matrix operations. It handles specific hardware requirements like `swizzlingByteWidth` and `fp4Padded` for Blackwell FP4 operations [lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp154-166](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp#L154-L166)

## Tensor Memory Accelerator (TMA) and Descriptors

 In modern NVIDIA architectures, Triton uses **Tensor Descriptors** (`!tt.tensordesc`) to interface with the TMA hardware.

 
### TMA Lowering Flow

 The `TMALowering` pass transforms high-level descriptor operations into architecture-specific asynchronous copies:

 
 - **Descriptor Extraction**: The pass calls `getEncodingFromDescriptor` to determine the shared memory layout needed for the destination buffer [lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp33](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp#L33-L33)
 - **Buffer Allocation**: It creates a `ttg.local_alloc` with the inferred encoding [lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp37-38](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp#L37-L38)
 - **Barrier Initialization**: TMA requires hardware barriers. The pass inserts `ttng.init_barrier` and `ttng.barrier_expect` [lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp49-55](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp#L49-L55)
 - **Async Copy**: The operation is lowered to `ttng.async_tma_copy_global_to_local` [lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp72-74](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp#L72-L74)
 - **Synchronization**: `ttng.wait_barrier` ensures data is ready before consumption [lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp58](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp#L58-L58)

## Memory Descriptor Operations

 Memory descriptors support several IR operations for manipulation:

 
| Operation | Purpose | Implementation Location |
|---|---|---|
| ttg.local_alloc | Allocates shared memory or TMEM with a specific layout. | lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp37 |
| ttg.local_load | Loads data from a memory descriptor into a distributed register tensor. | lib/Dialect/TritonNvidiaGPU/Transforms/TMALowering.cpp60 |
| ttg.local_store | Stores a register tensor into a memory descriptor. | lib/Dialect/TritonGPU/Transforms/Pipeliner/TMAStoresPipeline.cpp80 |
| ttg.memdesc_reshape | Reshapes a memory descriptor without changing the underlying allocation. | lib/Dialect/TritonGPU/IR/Dialect.cpp91-104 |

 
### Pipelining with Descriptors

 The `TMAStoresPipeline` pass optimizes memory descriptors by reusing allocations for stores of the same shape and type, which saves shared memory [lib/Dialect/TritonGPU/Transforms/Pipeliner/TMAStoresPipeline.cpp115-127](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/TMAStoresPipeline.cpp#L115-L127) It inserts `ttng.fence_async_shared` to ensure memory consistency during asynchronous TMA transfers [lib/Dialect/TritonGPU/Transforms/Pipeliner/TMAStoresPipeline.cpp81](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/TMAStoresPipeline.cpp#L81-L81)

## Layout Conversion to LinearLayout

 All layouts, including shared memory encodings, can be converted to a `LinearLayout` for canonical analysis. The `TritonGPUDialect::toLinearEncoding` function manages this conversion and uses a `LinearEncodingCache` to avoid redundant computations [lib/Dialect/TritonGPU/IR/Dialect.cpp46-59](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/IR/Dialect.cpp#L46-L59)

 
### Swizzling and Bank Mapping

 The `chooseShemLayoutForRegToRegConversion` function determines the optimal shared memory layout for register-to-register conversions, ensuring that vectorization is maintained while minimizing bank conflicts [include/triton/Dialect/TritonGPU/IR/LinearLayoutConversions.h132-134](https://github.com/triton-lang/triton/blob/f893845b/include/triton/Dialect/TritonGPU/IR/LinearLayoutConversions.h#L132-L134) For AMD architectures, `AMDRotatingSharedEncodingAttr` provides a specialized rotating swizzle pattern to optimize LDS access [lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp99-149](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp#L99-L149)
