## Purpose and Scope

 This page documents the lowering of reduction and scan operations from TritonGPU IR to LLVM IR. Reduction operations aggregate tensor values along specified dimensions using associative operations (sum, max, etc.), while scan operations compute prefix or suffix operations. The lowering process involves multi-level strategies that exploit GPU hardware hierarchy: within-thread aggregation, within-warp communication via shuffles, and cross-warp coordination via shared memory.

 For general TritonGPU to LLVM lowering infrastructure, see [TritonGPU to LLVM Lowering Framework](https://deepwiki.com/triton-lang/triton/5.1-tritongpu-to-llvm-lowering-framework). For memory operation lowering, see [Memory Operations Lowering](https://deepwiki.com/triton-lang/triton/5.2-memory-operations-lowering).

### Within-Thread Reduction

 Each thread first reduces values it owns along the reduction axis. This stage leverages the `LinearLayout` of the source tensor to identify register indices that belong to the same logical reduction group.

 **Implementation Details:**

 
 - **Register Packing:** The implementation can detect vectorized patterns (e.g., F16x2) to use hardware-accelerated instructions via `getInThreadVectorizeOpKind`.
 - **Layout Mapping:** It uses `removeZeroBasesAlongDim` to simplify the `LinearLayout` before reduction [lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp46-47](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp#L46-L47)

### Within-Warp Reduction

 After within-thread reduction, threads in the same warp exchange partial results using warp shuffle operations. This is a lock-free, low-latency communication mechanism.

 **Implementation:**

 
 - **Shuffle Primitives:** The `TargetInfoBase` provides architecture-specific implementations for `shuffleUp`, `shuffleDown`, and `shuffleXor`.
 - **Iteration:** The process iterates until the `regLl` (register layout) shows a size of 1 for the reduction axis dimension [lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp53-54](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp#L53-L54)

### Cross-Warp Reduction via Shared Memory

 When the reduction spans multiple warps, shared memory is used as a communication medium. This involves moving data from registers to shared memory, synchronizing, and then performing another round of reduction.

 **Lowering Logic:**

 
 - **Inter-Layout Calculation:** `ReduceOpHelper::getInterLayout` determines the intermediate layout for the transfer [lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp73](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp#L73-L73)
 - **Synchronization:** `sync()` is called, which translates to a `barrier` or `clusterBarrier` depending on whether the reduction crosses CTA boundaries [lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp161-168](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp#L161-L168)
 - **Layout Conversion:** `convertLayoutValues` moves data through shared memory to the new layout [lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp79](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp#L79-L79)
 - **Iterative Reduction:** The loop continues until the axis dimension is fully reduced [lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp72-85](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ReduceOpToLLVM.cpp#L72-L85)

### Scan Lowering Strategy

 Scan operations are lowered in `ScanOpToLLVM.cpp` using a multi-pass approach:

 
 - **Thread-Contiguous Scan:** `scanThreadContiguousElements` performs a scan on elements held by a single thread [lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp29-49](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp#L29-L49)
 - **Warp-Level Scan:** `warpScan` uses `targetInfo.shuffleUp` to propagate prefix values across lanes [lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp53-84](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp#L53-L84)
 - **Cross-Warp Propagation:** 
 - `storeWarpAccumulator` writes the final value of each warp to shared memory [lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp92-126](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp#L92-L126)
 - `AddPartialReduce` reads these values and adds them as offsets to subsequent warps [lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp133-146](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/ScanOpToLLVM.cpp#L133-L146)

## Memory and Layout Considerations

 
### Shared Memory Allocation

 Scratch memory for reductions and scans is calculated based on the `LinearLayout` and bitwidth of the operands. The `getScratchSizeInBytes` method in `ReduceOpHelper` iterates through intermediate layouts to find the maximum required buffer size [lib/Analysis/Utility.cpp109-142](https://github.com/triton-lang/triton/blob/f893845b/lib/Analysis/Utility.cpp#L109-L142)

 
### Histogram and Gather Lowering

 
 - **Histogram:** Lowered using atomic operations in shared memory. Threads initialize a shared memory buffer, perform `atomicAdd`, and then load the results back into registers [lib/Conversion/TritonGPUToLLVM/HistogramOpToLLVM.cpp17-65](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/HistogramOpToLLVM.cpp#L17-L65)
 - **Gather:** Can be lowered either via shared memory (storing the source and gathering using indices) or via `warp-local` shuffles if the layout analysis permits [lib/Conversion/TritonGPUToLLVM/GatherOpToLLVM.cpp34-49](https://github.com/triton-lang/triton/blob/f893845b/lib/Conversion/TritonGPUToLLVM/GatherOpToLLVM.cpp#L34-L49)
