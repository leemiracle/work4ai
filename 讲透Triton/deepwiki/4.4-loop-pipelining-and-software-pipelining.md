## Purpose and Scope

 Loop pipelining is a compiler transformation in Triton that restructures loops to overlap memory operations with computation, thereby hiding memory latency and improving GPU kernel performance. This page covers the software pipelining infrastructure, stage assignment, prologue/epilogue generation, and specialized pipelining for matrix multiplication operations.

 For general optimization passes, see [Compiler Transformations and Optimization Passes](https://deepwiki.com/triton-lang/triton/4-compiler-transformations-and-optimization-passes). For memory-specific optimizations, see [Memory Coalescing and Access Optimization](https://deepwiki.com/triton-lang/triton/4.6-memory-coalescing-and-access-optimization). For asynchronous operations in general, see [Prefetching and Asynchronous Operations](https://deepwiki.com/triton-lang/triton/4.5-prefetching-and-asynchronous-operations).

## Overview of Software Pipelining

 Software pipelining transforms a loop by scheduling operations from different iterations to execute concurrently. The key idea is to start loading data for iteration `i+1` while computing on data from iteration `i`, effectively overlapping memory access latency with computation.

 The transformation converts a standard loop into three parts:

 
 - **Prologue**: Pre-loads data for the first `N-1` stages before entering the main loop.
 - **Kernel**: The pipelined loop body where operations from multiple logical iterations execute together.
 - **Epilogue**: Completes the final `N-1` iterations after the main loop.

## Pipeline Stages and Scheduling

 Operations within the loop are assigned to **stages** (numbered 0, 1, 2, ..., maxStage), where stage 0 executes first and higher stages execute later. The scheduler determines which stage each operation belongs to, typically based on operation latency and dependencies.

 
### Latency Assignment

 Before expansion, the `tritongpu-assign-latencies` pass assigns latency attributes to operations.

 
 - `AssignLoadLatencies` calculates the stage distance between applicable loads based on indirection levels [lib/Dialect/TritonGPU/Transforms/Pipeliner/AssignLatencies.cpp106-132](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/AssignLatencies.cpp#L106-L132)
 - Latencies can also be user-provided via attributes [lib/Dialect/TritonGPU/Transforms/Pipeliner/AssignLatencies.cpp96-104](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/AssignLatencies.cpp#L96-L104)
 - `hasLoopCarriedAccumulatorCycle` checks for dependencies in `MMAv5` operations to avoid invalid schedules [lib/Dialect/TritonGPU/Transforms/Pipeliner/AssignLatencies.cpp28-73](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/AssignLatencies.cpp#L28-L73)
 
 
### Scheduling Constraints

 The `verifySchedule()` function ensures that all definitions are scheduled before uses within the generated pipeline [lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp90](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp#L90-L90) The `CoarseSchedule` class handles the mapping of operations to (stage, cluster) pairs [lib/Dialect/TritonGPU/Transforms/Pipeliner/LowerLoops.cpp77-80](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/LowerLoops.cpp#L77-L80)

## Prologue, Kernel, and Epilogue

 
### Prologue Generation

 The prologue executes `maxStage` partial iterations before the main loop. For stage `i`, it executes all operations from stages `0` to `i`.

 
 - For dynamic loops, the prologue uses predicates generated via `emitPredicateStageFn` to guard operations [lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp179-183](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp#L179-L183)
 - `valueMapping` tracks the version of values peeled from the loop [lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp77-81](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp#L77-L81)
 
 Sources: [lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp296-380](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp#L296-L380)

 
### Kernel Loop Creation

 The kernel is a new `scf::ForOp` that takes additional loop arguments for cross-stage values and buffer indices [lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp416-478](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp#L416-L478)

 
 - Circular buffer indexing is managed via `loopArgMap` which maps a `(Value, stage)` pair to a specific loop argument index [lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp104-105](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp#L104-L105)
 
 
### Epilogue Generation

 The epilogue completes the final `maxStage - 1` iterations. If `peelEpilogue` is false, the epilogue is integrated into the kernel using predicates [lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp642-743](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/PipelineExpander.cpp#L642-L743) Triton also supports custom epilogue peeling for `MMAv5` loops with waits in the last stage [lib/Dialect/TritonGPU/Transforms/Pipeliner/SoftwarePipeliner.cpp119-123](https://github.com/triton-lang/triton/blob/f893845b/lib/Dialect/TritonGPU/Transforms/Pipeliner/SoftwarePipeliner.cpp#L119-L123)
