## Overall System Architecture

 The Triton compiler follows a multi-layered architecture that progressively transforms Python kernel code into hardware-specific GPU binaries. The `JITFunction` acts as the entry point, which leverages `ASTSource` to represent the kernel's metadata and source before invoking the backend-specific compiler.

## Compilation Pipeline Stages

 The compilation process orchestrated by the `compile()` function in `compiler.py` proceeds through distinct stages. Each backend implements the `BaseBackend` interface to handle target-specific IR generation.

 **Stage Pipeline with Function Names**

 
```

```

 **Key Compilation Functions:**

 
| Stage | Primary Function | Module | Description |
|---|---|---|---|
| Source → TTIR | ast_to_ttir() | code_generator.py | Converts Python AST to Triton MLIR (TTIR) |
| TTIR → TTGIR | make_ttgir() | BaseBackend subclasses | Applies GPU-specific transformations and layout assignment |
| TTGIR → LLIR | make_llir() | BaseBackend subclasses | Lowers to LLVM IR with target-specific dialects |
| LLIR → ASM | make_ptx() / make_amdgcn() | CUDABackend / HIPBackend | Translates LLVM IR to target-specific assembly |
| ASM → Binary | ptxas / llvm-mc | External / Subprocess | Assembles assembly to final executable binaries |

## IR Transformation Details

 Triton utilizes MLIR dialects to represent code at varying levels of abstraction.

 
### TTIR: Triton IR Stage

 Hardware-agnostic tensor operations. Generated by the `CodeGenerator` class using `TritonSemantic` to map Python calls to IR.

 
 - **Key operations**: `tt.load`, `tt.store`, `tt.dot`, `tt.reduce`. [python/triton/language/semantic.py39-48](https://github.com/triton-lang/triton/blob/f893845b/python/triton/language/semantic.py#L39-L48)
 - **Functionality**: Handles SSA construction, local variable scoping, and constant folding. [python/triton/compiler/code_generator.py129-149](https://github.com/triton-lang/triton/blob/f893845b/python/triton/compiler/code_generator.py#L129-L149)
 
 **Sources:** [python/triton/compiler/code_generator.py144-194](https://github.com/triton-lang/triton/blob/f893845b/python/triton/compiler/code_generator.py#L144-L194) [python/triton/language/semantic.py39-48](https://github.com/triton-lang/triton/blob/f893845b/python/triton/language/semantic.py#L39-L48)

 
### TTGIR: TritonGPU IR Stage

 Introduces the concept of layouts and GPU-specific memory hierarchy.

 
 - **Layouts**: Tensors are annotated with attributes like `BlockedEncodingAttr` or `MmaEncodingAttr`.
 - **Shared Memory**: Managed through `ttg.local_alloc` and `ttg.local_load`.
 - **Passes**: Includes `coalesce` to optimize global memory access and `accelerate_matmul` to target hardware tensor cores. [third_party/amd/python/triton_amd.cc70-72](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/python/triton_amd.cc#L70-L72)
 
 **Sources:** [python/src/ir.cc187-200](https://github.com/triton-lang/triton/blob/f893845b/python/src/ir.cc#L187-L200) [third_party/nvidia/backend/compiler.py109-135](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L109-L135)

 
### LLIR: LLVM IR Stage

 The final IR stage before machine code generation.

 
 - **Dialects**: Uses `nvvm` for NVIDIA-specific intrinsics and `rocdl` for AMD. [third_party/amd/python/triton_amd.cc9-10](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/python/triton_amd.cc#L9-L10)
 - **Lowering**: Structured control flow (`scf`) is lowered to standard control flow (`cf`) before translation. [python/src/ir.cc15-16](https://github.com/triton-lang/triton/blob/f893845b/python/src/ir.cc#L15-L16)
 
 **Sources:** [python/src/llvm.cc1-50](https://github.com/triton-lang/triton/blob/f893845b/python/src/llvm.cc#L1-L50) [third_party/nvidia/backend/compiler.py84-94](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L84-L94)

 The `CUDABackend` handles compilation for NVIDIA GPUs. It manages `CUDAOptions` such as `num_warps`, `num_stages`, and `ptx_version`. ## Caching and Dependency Tracking

 Triton employs a robust caching mechanism to avoid re-compiling kernels. The cache key is a SHA-256 hash derived from the kernel source, constants, and transitively called functions. [python/triton/runtime/jit.py54-55](https://github.com/triton-lang/triton/blob/f893845b/python/triton/runtime/jit.py#L54-L55)

 
### Dependency Tracking

 The `DependenciesFinder` class (an `ast.NodeVisitor`) traverses the kernel's AST to identify:

 
 - **Global Variables**: Captured in `used_global_vals`. [python/triton/runtime/jit.py90-91](https://github.com/triton-lang/triton/blob/f893845b/python/triton/runtime/jit.py#L90-L91)
 - **Called JIT Functions**: Their cache keys are incorporated into the parent's hash. [python/triton/runtime/jit.py99-113](https://github.com/triton-lang/triton/blob/f893845b/python/triton/runtime/jit.py#L99-L113)
 - **Builtins**: Verified against `supported_python_builtins`. [python/triton/runtime/jit.py61-72](https://github.com/triton-lang/triton/blob/f893845b/python/triton/runtime/jit.py#L61-L72)
 
 **Sources:** [python/triton/runtime/jit.py39-93](https://github.com/triton-lang/triton/blob/f893845b/python/triton/runtime/jit.py#L39-L93) [python/triton/runtime/jit.py156-178](https://github.com/triton-lang/triton/blob/f893845b/python/triton/runtime/jit.py#L156-L178)

 
### Cache Management

 The `FileCacheManager` and `RemoteCacheManager` handle the persistence of compiled artifacts (e.g., `.cubin`, `.hsaco`, `.json` metadata). [python/test/unit/runtime/test_cache.py18-19](https://github.com/triton-lang/triton/blob/f893845b/python/test/unit/runtime/test_cache.py#L18-L19)

## Debugging and Instrumentation

 The compiler provides specialized modes for debugging and profiling:

 
 - **Interpreter Mode**: Executes kernels on CPU using NumPy via the `TritonSemantic` implementation in `interpreter.py`. [python/triton/runtime/interpreter.py15-20](https://github.com/triton-lang/triton/blob/f893845b/python/triton/runtime/interpreter.py#L15-L20)
 - **Diagnostics**: The `TritonSourceMgrDiagnosticHandler` in `ir.cc` maps MLIR errors back to Python source lines. [python/src/ir.cc80-107](https://github.com/triton-lang/triton/blob/f893845b/python/src/ir.cc#L80-L107)
 - **Sanitizers**: Hardware-specific sanitizers like `GSan` (Global Memory Sanitizer) or `FpSan` (Floating Point Sanitizer) can be enabled via `instrumentation_mode`. [third_party/nvidia/backend/compiler.py144-150](https://github.com/triton-lang/triton/blob/f893845b/third_party/nvidia/backend/compiler.py#L144-L150) [third_party/amd/backend/compiler.py48-50](https://github.com/triton-lang/triton/blob/f893845b/third_party/amd/backend/compiler.py#L48-L50)
