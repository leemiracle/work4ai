## Overview

 The Triton repository follows a layered architecture where Python frontend code, C++ compiler infrastructure, MLIR dialects, backend-specific implementations, and build/test systems are organized into distinct directory hierarchies. The structure separates:

 
 - **Python package code** in `python/` (user-facing API, JIT compilation, language definitions)
 - **C++ compiler infrastructure** in `lib/` and `include/` (MLIR dialects, optimization passes, lowering)
 - **Backend implementations** in `third_party/` (NVIDIA, AMD, and plugin backends)
 - **Build configuration** in root `CMakeLists.txt` and `cmake/` (LLVM integration, toolchain versions)
 - **Testing and CI/CD** in `test/`, `python/test/`, and `.github/workflows/`

## Backend Plugin Architecture

 Backend implementations are located in `third_party/` as semi-independent modules that register themselves with the core compiler via `setup.py` and the `BackendInstaller` class.

 
```

```

 **Backend Structure**

 Each backend follows a standard directory layout as defined in `BackendInstaller`:

 
 - `backend/`: Contains `compiler.py` and `driver.py` [setup.py89-101](https://github.com/triton-lang/triton/blob/f893845b/setup.py#L89-L101)
 - `language/`: Optional backend-specific language extensions [setup.py92-94](https://github.com/triton-lang/triton/blob/f893845b/setup.py#L92-L94)
 - `tools/`: Optional backend-specific tools [setup.py96-98](https://github.com/triton-lang/triton/blob/f893845b/setup.py#L96-L98)
 
 **Backend Registration**

 Backends are registered during build by setting `TRITON_CODEGEN_BACKENDS` or `TRITON_PLUGIN_DIRS` [CMakeLists.txt27](https://github.com/triton-lang/triton/blob/f893845b/CMakeLists.txt#L27-L27)

 
 - `BackendInstaller.copy` initializes submodules for in-tree backends in `third_party/` [setup.py110-112](https://github.com/triton-lang/triton/blob/f893845b/setup.py#L110-L112)
 - `BackendInstaller.copy_externals` searches `TRITON_PLUGIN_DIRS` for `backend/name.conf` to identify external plugins [setup.py117-126](https://github.com/triton-lang/triton/blob/f893845b/setup.py#L117-L126)
 - All identified backends are installed into `python/triton/backends/{name}` [setup.py103](https://github.com/triton-lang/triton/blob/f893845b/setup.py#L103-L103)
 
 Sources: [setup.py57-127](https://github.com/triton-lang/triton/blob/f893845b/setup.py#L57-L127) [CMakeLists.txt27-28](https://github.com/triton-lang/triton/blob/f893845b/CMakeLists.txt#L27-L28) [.gitignore24-29](https://github.com/triton-lang/triton/blob/f893845b/.gitignore#L24-L29)

## Build System Structure

 The build system uses CMake to orchestrate compilation of C++ components, LLVM/MLIR integration, and Python extension module creation.

 
```

```

 **Key Build System Components**

 
| Component | Purpose |
|---|---|
| CMakeLists.txt | Root build configuration, handles LLVM linking and backend registration CMakeLists.txt1-173 |
| cmake/llvm-build-info.json | Contains the llvm_hash and repository for the pinned LLVM version .github/workflows/llvm-build.yml62-68 cmake/llvm-build-info.json1-5 |
| python/build_helpers.py | Utility for downloading dependencies and generating CMake variables CMakeLists.txt123-134 |
| Makefile | Developer helper for common tasks like dev-install and test Makefile1-142 |

 **LLVM Integration**

 Triton depends on a specific LLVM/MLIR version. The build system can:

 
 - Download a prebuilt LLVM based on the hash in `llvm-build-info.json` [.github/workflows/llvm-build.yml84-89](https://github.com/triton-lang/triton/blob/f893845b/.github/workflows/llvm-build.yml#L84-L89)
 - Use a custom LLVM specified via `LLVM_SYSPATH` [CMakeLists.txt32](https://github.com/triton-lang/triton/blob/f893845b/CMakeLists.txt#L32-L32)
 - Build LLVM from source using the `make dev-install-llvm` helper [Makefile110-117](https://github.com/triton-lang/triton/blob/f893845b/Makefile#L110-L117)
