# Device Configuration and SM Management

  Relevant source files 
 - [tile_kernels/__init__.py](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/__init__.py)
 - [tile_kernels/config.py](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py)
 
  This page documents the global configuration utilities in `TileKernels` that interface with NVIDIA GPU hardware properties. These utilities are critical for the library's performance, as they provide the hardware constraints used by kernels to determine grid sizes for persistent-block scheduling and to calculate shared memory (smem) allocation limits.

 
## Overview of Configuration Management

 The `tile_kernels/config.py` module serves as a centralized registry for GPU device properties. It abstracts the underlying `torch.cuda` calls and provides a mechanism to override the number of Streaming Multiprocessors (SMs) used by the library. This is particularly useful for profiling, simulating smaller hardware, or partitioning resources.

 
### Hardware Discovery and State

 The module maintains a global state for the number of SMs and uses caching to minimize the overhead of querying hardware properties through the CUDA driver.

 
| Function | Role | File Reference |
|---|---|---|
| get_device_num_sms() | Queries the physical hardware for the total SM count. | tile_kernels/config.py7-10 |
| get_num_sms() | Returns the active SM count (either hardware default or user override). | tile_kernels/config.py19-23 |
| set_num_sms() | Manually overrides the SM count used for grid calculations. | tile_kernels/config.py13-16 |
| get_max_smem_per_sm() | Returns the maximum shared memory available per SM. | tile_kernels/config.py26-29 |

## SM Management API

 
### SM Count Resolution

 The library distinguishes between the physical SM count and the logical SM count used for kernel dispatch.

 
 - **`get_device_num_sms()`**: This function uses `torch.cuda.get_device_properties` to fetch the `multi_processor_count` [tile_kernels/config.py9-10](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py#L9-L10) It is decorated with `@functools.lru_cache` to ensure the property is only queried once per process [tile_kernels/config.py7](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py#L7-L7)
 - **`get_num_sms()`**: This is the primary getter used by kernel developers. If the global `_num_sms` variable is `0` (default), it returns the result of `get_device_num_sms()` [tile_kernels/config.py21-22](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py#L21-L22) Otherwise, it returns the overridden value [tile_kernels/config.py23](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py#L23-L23)
 
 
### Overriding SM Count

 Users can restrict the library to a subset of SMs using `set_num_sms(num_sms: int)`. This function includes an assertion to ensure the requested count is positive and does not exceed the physical hardware capacity [tile_kernels/config.py15](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py#L15-L15)

## Shared Memory Configuration

 The `get_max_smem_per_sm()` function retrieves the `shared_memory_per_multiprocessor` attribute from the current CUDA device [tile_kernels/config.py28-29](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py#L28-L29)

 In TileKernels, this value is critical for:

 
 - **Tiling Constraints**: Ensuring that `T.alloc_shared` blocks in TileLang do not exceed the physical capacity of a single SM.
 - **Occupancy Tuning**: Helping the compiler or the developer decide how many blocks can reside on a single SM simultaneously based on the required shared memory.
 
 **Sources:** [tile_kernels/config.py26-30](https://github.com/deepseek-ai/TileKernels/blob/36d9e45d/tile_kernels/config.py#L26-L30)

## Integration with Kernel Grids

 TileKernels frequently utilizes **persistent-block grids**. Unlike standard grids where the grid size matches the total number of work units, persistent grids are often sized exactly to the number of available SMs (or a small multiple thereof).

### Usage Pattern in Kernels

 When a kernel is launched, the `grid` parameter in the `T.Kernel` call (within a `@tilelang.jit` decorated function) typically references `get_num_sms()`. This ensures that:

 
 - The GPU is fully utilized (one or more blocks per SM).
 - The kernel can implement a "while" loop internally to process all data tiles, effectively "persisting" on the SM until the entire workload is complete.
