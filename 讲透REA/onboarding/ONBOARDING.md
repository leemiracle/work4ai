## 1. 项目定位与核心概念

REA（morluto/rea，npm 包名 `rea-agents`，当前 v6.5.0，MIT 协议）是一个统一的逆向工程 **MCP server + CLI**：让终端用户和 AI agent 在**没有源码**的前提下，检查原生二进制（Hopper/Ghidra/IDA/Kuna）、JavaScript/Electron 应用、.NET 程序集、网站、EVM 字节码、Android APK 与固件，并给出带证据的结论。**v6.2-v6.5 把能力面扩到几乎全部逆向对象**：GDB/Rizin 持久调试会话与 Cutter GUI 桥、Frida 动态插桩、SQLite 数据库、pcap/pcapng 网络捕获、sigrok 信号录制、WASM 产物、Go/Rust 二进制内嵌元数据、Flutter 构建识别、Electron fuse 位、JEB 反编译器——src/ 顶层子系统从 20 个涨到 43 个（新 19 个实质子系统约 120 文件/3.3 万行）。README.md（19 种语言镜像在 `docs/readme/`）开篇的场景就是典型用法——"看到某个 App 里喜欢的功能，让 agent 调查它如何工作、展示证据，再为你的项目实现一个版本"。它解决的真实痛点是：逆向工程工具链（反汇编器、调试器、CDP、字节码分析器）各自为战、学习曲线陡峭，agent 直接驱动它们极易产生幻觉；REA 把这些引擎统一成一组语义稳定的工具，并把"结论可信"做成了结构属性。

双形态是刻意设计而非附带品：MCP 工具与 CLI 命令走**同一套**应用层 workflow，AGENTS.md 明文要求 "equivalent behavior through the CLI and MCP"——任何新能力都必须两端同时落地，避免出现"只有 agent 能用"或"只有脚本能用"的分裂。`src/cliCommandNames.ts` 维护全部 CLI 命令名与 MCP 工具名的对照表（`CLI_COMMAND_TOOL_ALIASES`），保证两个入口暴露一致的能力面。生产入口是 `scripts/rea.mjs`——`package.json` 定义 `rea` 与 `rea-agents` 双 bin 都指向它，它按参数三分派：MCP stdio 服务（`--mcp`/`mcp`）、`mcp doctor` 诊断、默认 CLI，进入前先校验 `dist/` 编译产物齐全，缺失时提示先构建。

核心理念可以概括为**"分析本地运行 + 结论带证据与局限"**。一切分析在本地执行、默认不触网；每个结论必须携带可验证的 Evidence——观察位置、canonical digest、来源 provider、可追溯的 artifact 身份（v6.5 起每条 Evidence 还必填 `analysis_profile`，它参与 Evidence 身份计算，见 `docs/migration-6.2.md`）；工具结果显式区分 observation（观察）/ derivation（推导）/ inference（推断）/ unknown（未知）四类事实（AGENTS.md 现行措辞 "observations, derivations, inferences, unknowns"，比 v6.1 的三分多了显式 derivation）。unknown 在这里不是失败，而是被登记进账本、可后续追问的一等公民：比对工作流没匹配上的条目会自动生成 residual unknown（`src/domain/residualUnknown.ts`，414 行），`audit_residual_unknowns` 之类的 prompt 甚至专门用于盘点它们。错误同样是契约：27 个稳定错误 tag + remediation 建议，响应超预算时不静默截断，而是转为带恢复指引的资源约束错误。这套"证据先行"的设计是 REA 对抗 agent 幻觉的核心机制，也是全仓架构分层的出发点。

## 2. 环境搭建与快速上手

**使用者路径**：Node.js `^22.19 || ^24.11 || >=26` 下执行 `npx rea-agents setup`。setup 是 plan/approve 两段式——先渲染计划变更、批准后才写文件，且对既有配置做备份（AGENTS.md 钉死的红线：安装器不得顺手装 Homebrew/Node/Java 等无关软件）。setup 把 REA 的 MCP server 与匹配的 workflow skill（` .agents/skills/reverse-engineer-anything/` 是随包分发的 agent 指令源；v6.1 时代的 `skill-src/` 已在 2026-10-10 整体迁移至此，`scripts/verify-repository-skill.mjs` 守卫其结构）一并注册进你选的 agent。受支持客户端注册表在 `src/application/SupportedClients.ts`（v6.1 的 14 个→**25 个**）：Claude Code/Desktop、Codex、Cursor、Gemini CLI、Windsurf、Devin、OpenCode、Antigravity、Copilot CLI、Grok 等 + v6.5 新增 Qwen Code、Kimi Code、Trae、WorkBuddy、OMP、Pi、Hermes、Qoder、Factory Droid、ZCode、DeepSeek Harness（`:486-700`），各家的平台配置路径与格式（json/toml/grok/opencode/omp/pi/kimi/hermes/zcode/dsh）都有专门解析——`src/application/ClientConfigurationDocument.ts` 能编辑 JSON/JSONC/TOML（含 OpenCode V2 方言）且保留注释与无关设置。交互层在 `src/cli/interactiveSetup.ts`（@clack/prompts，非 TTY 场景自动降级为 accessible 串行模式）。装好后 `rea doctor`（编排器 `src/application/Doctor.ts`，生产宿主 `src/application/SetupHost.ts`）逐项报告 Hopper/Ghidra/技能安装/客户端注册的就绪状态与恢复建议；`rea mcp doctor`（`src/mcpDoctor.ts`）则拉起真实 stdio 子进程，对照契约清单核对 tools/prompts 的 missing/unexpected。

**引擎是可选 provider 而非前置依赖**：原生二进制深度分析需要 Hopper、Ghidra、IDA 或 Kuna 之一（v6.5 起四选）。Ghidra、IDA 与 Kuna 是 bring-your-own——Ghidra 安装巡检在 `src/ghidra/GhidraInstallation.ts`（解析安装坐标、校验版本/JDK/原生反编译器），IDA 接入见 `docs/ida-provider.md`，Kuna（Noelo-Lab 开源反编译器）经 `REA_KUNA_COMMAND` 自备；Hopper 在 v6.1 只能装 Linux 官方包（`src/application/LinuxHopper.ts` 按 `/etc/os-release` 识别发行版家族，sha1/长度预登记校验，`scripts/hopper-demo-x11.py` 在私有 Xvfb 上自动处理 demo 授权对话框），**v6.5 起 setup 可直接下载安装**（`HopperDownload.ts` 100MB 上限 + `HopperReleaseFeed.ts` 发布源，双平台 Publisher 落地）。**JavaScript 与 .NET 静态分析完全不需要任何引擎**，纯 Node 即可跑：`npx -y rea-agents@latest analyze-javascript-application /absolute/path --json`，结果含模块、import、Electron 边界及各自的证据；v6.5 又把 **go/rust/flutter/electron/sqlite 五族做成零引擎纯解析**（Go/Rust 内嵌元数据、Flutter 构建识别、Electron fuse 位、Node 24.15+ 原生 node:sqlite），Frida 动态插桩则作为 optionalDependencies（frida@17.23.2）随包可选安装。gdb/rizin/cutter/objdump/tshark/sigrok/WABT/JEB 等属 caller-supplied（`docs/reverse-engineering-tools.md`：REA 不装不更新它们）。更新走 `rea update` 或 `npx rea-agents@latest setup` 刷新注册。

**贡献者路径**（CONTRIBUTING.md，v6.5 已重构为 Choosing a contribution / Contribution scope / PR ownership and readiness / Maintainer release checklist 的新结构）：开发环境钉版 Node 24.18.x + npm 11.16.x（`.nvmrc` + packageManager 字段，CONTRIBUTING.md 不再写死数字、直接引用这两处），然后 `npm ci` → `npm run build:cached` → `npm run check:fast`（缓存类型检查 + lint 的 pre-push 门）。日常迭代用 `npm run test:local`（只跑变更相关源码测试）与 `npm run check:changed`（自 merge-base 起的增量检查），完整门 `check:pr` 留给大改动——CI 才拥有全量覆盖，本地不必每次跑全量。`package.json` 里 **209 个 scripts**（v6.1 约 138 个）基本都围绕这三层组织，其中 **99 个 `verify:*`** 是真引擎验证入口（见第 7 节）。

依赖方向由 AGENTS.md 钉死："dependencies flow inward from pure domain logic through contracts, providers, application workflows, and CLI/MCP adapters"。用度数统计可以实证 domain 是被依赖最深的地基：`src/domain/evidence.ts` 与 `src/domain/result.ts` 度数并列全仓第一（各 270），`src/domain/jsonValue.ts`（253）、`src/domain/analysisErrorCore.ts`（218）紧随其后——也就是说，上层几乎所有文件都在用同一套 Evidence 词汇表与 Result 错误通道。反方向看枢纽：契约层是 `src/contracts/toolContracts.ts`（度数 112），适配层是 `src/server/createServer.ts`（158），应用层是 `src/application/AnalysisProvider.ts`（185）。实测 `src/application/` 下 75 个文件直接 import `../domain`——application→domain 是最粗的依赖主干，而 domain 不依赖任何人（纯函数、无 I/O，这是它 409 个节点能稳坐塔基的原因）。

两个小层常被低估但不可或缺。**composition（26 节点）** 是 CLI 与 MCP 共享的唯一生产装配点：`src/composition/binary.ts` 的 `createBinarySession` 组装**深度 provider 注册表 `[hopper, ghidra, ida, kuna]`**（kuna 为 v6.5 新增，`binary.ts:32`）与辅助 provider 注册表；v6.5 起新子系统各有 6-58 行的薄装配 `src/composition/<area>.ts`（reverseEngineering/adb/pcap/sqlite/wasm…），`optionalObservationProviders.ts` 逐端口容错加载可选观测 provider（健康者保留、失败者精确记录原因）；配置侧 `src/config/` 汇聚全部 `REA_*`/`GHIDRA_*`/`HOPPER_*` 环境变量的 zod schema（`src/config/environment.ts`）与解析管道（`src/config/parseConfig.ts`）——新引擎族统一走 `REA_<TOOL>_COMMAND` env 门面（ADB/APKTOOL/TSHARK/CAPINFOS/SIGROK/KUNA/WABT_BIN_DIRECTORY/JEB_MCP_URL）。**bridge（29 节点@基线，现 32 文件）** 是跨语言世界：`bridge/ghidra/ReaGhidraBridge.java`（度数 89，bridge 层最高；v6.1 3404 行→**4892 行**，能力 case 26→28）、`bridge/hopper_bridge.py`（1181 行）、`bridge/native/rea_lldb_tracer.py`（917 行）、`bridge/process/ProcessRunTokenReader.swift`（339 行）、`native/windows/src/addon.cc`，v6.5 新增 `bridge/cutter/rea_bridge.py`（816 行，Cutter/Rizin GUI 桥）与 `bridge/nativeaot/`（4 个 Java 文件 361 行：NativeAotExtension/Directory/TypeMetadata/MethodConventions，.NET NativeAOT 的 Ghidra 扩展，自 bridge/ghidra/extensions/ 平移）——它们运行在 REA 沙箱里，语言栈与主仓完全不同，因此被单独成层隔离演进。测试层是全仓最大层，这个比例本身就是项目价值观的声明：验证面比功能面更大。

## 4. 核心子系统走读

**domain（基线 409 节点，现 608 文件）——全仓词汇表**。`src/domain/evidence.ts`（451 行）定义 provider/evidenceLocation/evidenceRecord schema，`parseEvidence` 校验语义 ID 防篡改、`immutableEvidence` 冻结密封快照；**v6.2 起 evidenceEnvelope（`{result, evidence_id, evidence}` 包装）已废除**——Evidence-producing 工具把完整 Evidence 直接放进 `structuredContent`，取值用 `evidence.normalized_result`（`docs/migration-6.2.md:7-24`）；每条 Evidence 必填 `analysis_profile`（observed profile 对象或 null）且参与身份计算；evidenceAuthoritySchema 五枚举 shipped-artifact/controlled-replay/historical-reference/external-service/analyst-inference（`evidence.ts:108-114`）。`src/domain/result.ts` 的 `Result<T,E>` 判别联合是期望式错误通道的最小基建；错误体系分三级——`src/domain/analysisErrorBase.ts` 定义 27 个稳定 tag 与抽象基类（tag 列表 v6.1→v6.5 一字未改；本体新增 `diagnostics` 字段与 `cleanupIncomplete`/`cleanupResources`，配套新文件 `analysisErrorCleanup.ts`），`src/domain/analysisErrorCore.ts` 展开十个核心错误类（不支持目标/资源约束/协议/取消/超时/访问拒绝……，各类已补 diagnostics/cleanup 支持），`src/domain/analysisErrorProjection.ts` 把失败投影为秘密安全的调用方字段（code/category/retryable/remediation）。`src/domain/binaryTarget.ts` 无 I/O 地按 magic 解析 ELF/Mach-O(fat/thin)/PE 文件头，连 managed 判定（PE 的 CLI header）都在这里做完——目标分类因此是 provider 中立的。JS 子树（`src/domain/javascript/`，基线 126 文件→**214 文件**，单子域扩张冠军）是个独立小宇宙：`javascriptApplicationGraph.ts`（499→**656 行**，度数 83@基线）定义应用图节点/边的 semantic-content-sha256 确定性 ID 策略与十余项全图不变量校验，`javascriptSemanticAnalysis.ts` 构建作用域/绑定状态机输出语义 IR，`javascriptStaticAnalysisHelpers.ts`（38 个函数）是静态侧共用底座，v6.5 新增 electronStaticAnalysis* 8 文件、electronActiveObservation、javascriptApplicationChangeGraph 等。**v6.5 最大新子域是 `src/domain/analysisView/`（31 文件）**：统一"分析视图"投影层（androidPackageView/binaryLayoutView/machoView/dartAotView/evmInterfaceView/javascriptApplicationView 等），供 `inspect_analysis_view` 类工具按需发现保留字段。此外 `src/domain/digests.ts` 统一 SHA-256 digest 形状（收敛了此前散落约 30 个模块的手抄正则），`src/domain/canonicalOrdering.ts` 提供与 locale 无关的 Unicode 码点序——确定性是这个层的审美。

## 5. 分析 Provider 体系

**反汇编四巨头（Hopper/Ghidra/IDA/Kuna），四种接入姿势、同一个 AnalysisProvider 接口**——这个对照是理解 provider 设计的最佳教材：

- **Ghidra（REA 打包桥，最重）**：`src/ghidra/GhidraLauncher.ts` 创建隔离运行时目录树（home/temp/cache/config/data 分离）后 spawn analyzeHeadless，Windows 专门处理 cmd.exe 批处理引号与进程树清理；`src/ghidra/GhidraClient.ts` 拥有经认证的私有 headless 会话——私有 Unix socket 传输、请求队列、行式响应路由、鉴权 token 保留与诊断脱敏；进程外对手是 `bridge/ghidra/ReaGhidraBridge.java`——只读 Ghidra 桥，v6.1 3404 行→**v6.5 4892 行**，服务 28 项能力（内存读取/反编译/pcode 值流/跳转表与 API 边界推断/注释回写/交叉引用；switch case 由 26 涨到 28）；旁边新增 6 个 Java sidecar：BundleActivator/AnalysisOptions/**ApplySeeds**（配 `GhidraAnalysisSeeds.ts` 285 行种子库）/NoReturnFix/MipsSoftFloat/PrepareRaw，以及新语言与架构 profile 族（`GhidraLanguageCatalog.ts` 209 行 + Mips/Psp/Riscv/PowerPc/RawBinary/Pe Profile，对应新文档 ghidra-mips/ppc/psp/riscv/raw-binary）。还有扩展机制：`src/ghidra/extensions/GhidraExtensions.ts` 定义 JAR 白名单加载（绝对路径+sha256+entry_class 校验），当前注册 nativeaot 扩展用于 .NET NativeAOT 镜像分析（v6.5 已整体平移到 `bridge/nativeaot/`，4 个 Java 文件 361 行）。

## 6. 关键数据流

一次 MCP 工具调用的完整旅程（以 `analyze_function` 为例）：

1. **入口**：agent 经 MCP stdio 发起调用；handler 由 `src/server/registerOfficialTools.ts`/`registerEnhancedTools.ts`/`registerSessionTools.ts` 等注册器挂到 `src/server/createServer.ts` 组装的服务器上。CLI 侧等价命令从 `src/cli.ts` 进入（输入解析 `src/cliJsonInput.ts` 支持内联 JSON 与文件路径），殊途同归于同一个组合根。
2. **契约校验**：输入先过 `src/contracts/` 目录树中该工具所属 group 的 strict zod schema（v6.1 的单文件总账已拆为 35+ 模块，`toolContracts.ts` 仍做聚合）；注册时 schema 已经 `src/server/toolRegistrationOptions.ts` 投影为 SDK registerTool 的 inputSchema/outputSchema/annotations，因此校验规则与广告给 agent 的 schema 严格同源。
3. **应用编排**：`src/application/DirectAnalysis.ts` 按工具名路由到对应操作族，驱动 `src/application/binary/BinarySession.ts`；session 委托 `src/application/binary/SessionProviderRouter.ts` 按目标选择 provider（目标由 `src/application/BinaryTargetResolver.ts` 解析——魔数与扩展名双通道检测格式，读可执行元数据并算 sha256）。已分析过的调用命中 `src/domain/analysisSnapshot.ts` 的快照缓存（provider/profile 精确绑定；**v6.2 起快照要求 workflow_entries + 每个 cached query 的 profile-bound Evidence，import 拒绝不完整绑定**，`docs/migration-6.2.md:68-82`）可直接重放。
4. **provider 执行**：以 Ghidra 为例——`GhidraLauncher.ts` spawn 受管进程，`GhidraClient.ts` 经认证 socket 发请求，`ReaGhidraBridge.java` 在 headless 会话里执行反编译并返回带位置定位的结果。子进程全部经 `src/process/ProviderProcess.ts` 生成并注入 run token；取消信号（AbortSignal）沿 CDP 连接与进程监督链一路贯通。
5. **Evidence 沉淀**：结果观察值经 `src/domain/evidence.ts` 的 `createEvidence` 逐 provider 归一化并计算 digest（v6.2 起必填 `analysis_profile`，参与身份计算），`immutableEvidence` 冻结；多条证据由 `src/domain/evidenceBundle.ts` 组成确定性排序的密封 bundle（`evidenceBundleForTarget` 可按目标投影）；比对类工作流（如 `src/server/registerFunctionComparisonTool.ts` 的 compare_functions、`registerArtifactComparisonTool.ts` 的 compare_artifacts）为未匹配项生成 residual unknown 登记进账本（函数比较维度状态 v6.2 收敛为 unchanged/changed/unknown，truncated 移除），沿 evidence_links 的闭包遍历在 `src/server/registerInvestigationTools/helpers.ts` 里完成。`src/domain/digests.ts` 与 `src/domain/canonicalOrdering.ts` 保证这些 digest 与排序跨平台确定；"Preserve Evidence provenance" 是 AGENTS.md 钉死的横向原则（落点散布 artifactGraph/hopperValues/browserNetworkEvidence/artifactInventorySnapshot 等）。
6. **结果序列化**：`src/server/toolResult.ts` 把应用结果序列化为 CallToolResult、确认 Evidence 记录；**v6.2 起 Evidence-producing 工具把完整 Evidence 直接放进 `structuredContent`（evidenceEnvelope 包装已废除，取值用 `evidence.normalized_result`；错误结果 `isError:true` + text diagnostic，不再带 structuredContent）**；响应超出 MCP 预算时，`src/server/EvidenceMcpServer.ts` 的 ErrorEvidenceTransport 把原始错误转存为 Evidence 台账条目（可携带 `details.reported_limits.evidence_reference`，同连接用 `inspect_analysis_view`/`export_evidence_bundle` 取回完整 Evidence）、回投带 remediation 的资源约束错误并保持连接存活——agent 拿到的是"如何取回完整结果"的指引而非截断的垃圾。

度数统计（@图谱基线）印证了这条链的枢纽位置：`src/domain/result.ts` 与 `src/domain/evidence.ts`（各 270）是全仓被引用最多的两个文件，几乎所有边界都在用同一套 Result 错误通道与 Evidence 词汇表说话。浏览器线是另一条平行流：`CdpBrowserProvider.ts` 经 `src/browser/CdpConnection.ts`（WebSocket 命令收发 + pending promise 管理）做被动观察，`src/browser/CdpCaptureEvents.ts` 持全部捕获状态、`src/browser/WebSourceMapFetcher.ts` 在 64MiB/30s 预算内抓取并解码 source map、`src/browser/CdpCaptureStorageFingerprints.ts` 对 cookies/IndexedDB 只留指纹不落敏感值；v6.5 新增三个网络捕获契约族 webScript/webRuntime/webNetworkCapture（mitmproxy 桥 `bridge/mitmproxy/capture.py` 384 行与 http3-capture-lab 实验配套）；静态侧 `JavaScriptApplicationService.ts` 重建的应用图与之在 `reconcile_javascript_runtime` 工具上汇合——运行时观察与静态恢复在同一张图上对账（JS presence 三态 present/absent/unknown-coverage 为 v6.2 新契约）。

## 8. 扩展指南与常见陷阱

**加一个 provider**：先选轨道。**深度 provider 轨**（要被 open_binary 选中、参与确定性选择）：实现 `src/application/AnalysisProvider.ts` 的接口（identity/capabilities/createClient，v6.5 起还含 hasPendingOwnedResources/closeOwnedResources 清理所有权义务），引擎专属代码放 `src/<engine>/` 新目录，**绝不进 domain/application**（oxlint 的 no-restricted-imports 分层规则在 lint 层强制），在 `src/composition/binary.ts` 的注册表注册——v6.5 的样板是 kuna（`src/kuna/KunaProvider.ts`）。**领域 Port 轨**（v6.5 主流，artifact/observation 型能力）：定义 `src/application/<area>/<Area>Port.ts` 端口 + `src/contracts/<area>/` 契约族 + `src/composition/<area>.ts` 薄装配，不进 AnalysisProviderRegistry。**RE 工具直通轨**（caller-supplied 调试器/命令行工具）：只有工具契约与命令构造，参考 gdb/rizin/cutter。深度/辅助的分界原则（不相交操作族走组合、重叠的深度静态分析族走确定性选择、一次绑定会话内禁止漂移）原写在 `docs/adr/0001`，**v6.5 已废弃 ADR 机制**——决策记录改为 `docs/specs/` 的 spec/plan/tasks/verification 四件套（现有 2356-wasm-interface-comparison、solidity/cbor-metadata 两组）。进程外引擎先读 `src/process/`——复用 supervision 与身份原语（AGENTS.md："a PID and executable pathname alone do not establish ownership"），别写 provider 私有生命周期代码。

**加一个 MCP 工具**：先过 `docs/tool-design.md` 检查清单——从分析师问题出发而非引擎 API；命名遵循语义动词（inspect/search 查事实、trace 查关系、compare 显式配对、observe/capture 仅在需要运行时时使用且契约里声明 authority 与 lifecycle effects；v6.5 新红线：外码执行与设备变更要在 10 维副作用里显式声明 executesForeignCode/mutatesDevice）。然后在 `src/contracts/` 对应 group 目录加 `ToolContract`，在 `toolEffects.ts` 声明 10 维副作用，`toolOutputSchemaGroups.ts` 登记输出 schema；在 `src/server/` 加/扩展注册器（现有 36 个 register*Tools.ts）；CLI 等价命令同步进 `src/cliCommandNames.ts` 与对应 `src/cli/*Commands.ts`（v6.1 的 `toolContracts.test.ts`/FLOOR 下限已删，防漂移靠 `tests/boundary/mcp/serverIdentity.test.ts` 的 CATALOG_IDENTITY.counts 行为断言 + `docs:check:built` 的 product-catalog/completion-ledger/error-schema/licenses 四重 --check），最后 `npm run build:cached` 重新生成 product-catalog 与文档事实。

**常见陷阱**：

1. **NodeNext `.js` specifier**：tsconfig 是 ESM NodeNext，TS 源码互相 import 必须写 `.js` 后缀——`src/domain/evidence.ts` 里就是 `import { digestCanonicalValue } from "./canonicalDigest.js"`。写 `.ts` 或省扩展名直接编译失败，新来者最容易踩。
2. **dist 构建产物依赖**：`scripts/rea.mjs` 动态 import 前先校验 `dist/` 齐全，缺失时提示 `npm ci && npm run build:cached`；`src/generatedMcpToolCatalog.ts` 与 `docs/public/product-catalog.json` 是构建生成物且 gitignored，**绝不提交**，merge 里撞见它就删掉重跑 build。
3. **fixture 体系**：不提交编译二进制——`scripts/fixtures/managed/pe.mjs` 用纯 Buffer 手工构造 .NET 程序集（CLI header、metadata 五流、IL method body），测试用 `tests/fixtures/` 生产接缝而非 vi.mock 模块。
4. **release-please 流程**：提交信息必须 Conventional Commits（`feat:`/`fix(process):`/`docs:`），PR 标题即 squash 后的 release commit；`release-please-config.json` 的 `always-bump-minor` 意味着 breaking change 也只升 minor 版本（**minor 不等于向后兼容**——6.2 就是 breaking 版，`docs/migration-*.md` 是升级必读）；发布走 `.github/workflows/release.yml` 的 prepare/publish 双相，merge 发布 PR 前有 `scripts/verify-release-checkpoint.mjs` 校验版本与祖先链（v6.5 另有 release-recovery workflow 兜底）。
5. **风格与红线**：oxlint 限文件 500 行/函数 100 行/复杂度 20；禁 `any`、非空断言、import 时 I/O、floating promises；期望失败用 tagged error + Result 而非宽泛异常包装；边界测试要覆盖畸形输入、取消、生命周期清理（AGENTS.md 测试指南的强制项；`docs/tool-design.md:116` 链到 lifecycle regression 场景）。
6. **v6.5 新红线——资源所有权与性能次序**：AGENTS.md 新增 Architecture and Cleanup 段（每个 interpretation/resource 必须有明确 owner；清理失败的资源保留所有权而非泄漏）与 Performance 段（优化次序：① agent tokens/context ② 分析时间 ③ CPU/内存，且要实测报告）；合规三件套 `licenses/`（19 项第三方许可证，Ghidra/frida 等）+ `THIRD_PARTY_NOTICES.md` + `DISCLAIMER.md` 由 `licenses:check` 守卫（挂在 `docs:check:built`，改依赖必须重生成）；逆向工具线改动要过 reverse-tools 覆盖率与双份 Stryker 突变配置（CI reverse-tools-quality lane）。
