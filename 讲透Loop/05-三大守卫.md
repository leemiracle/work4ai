# 05 · 三大守卫：hard cap / 机器可查条件 / 独立验证

> 讲透Loop 第 5 章 | 实验基座：E2b 失控实验 + E4 双相外环（R4 熔断精调）

## 一、直觉层：守卫是循环的免疫系统

三守卫（vibeengines handbook 的三道闸，2607.00038/2608.21884 共识）：

| 守卫 | 是什么 | 抓什么 | 缺了怎么死 |
|------|--------|--------|-----------|
| **Hard cap 硬上限** | max_iterations / wall-clock / token 预算 | 失控、振荡、成本爆炸 | 循环没有天花板，最终撞上一个你没计划的（账单/限流/超时） |
| **机器可查条件** | 测试绿 && lint 零错 && diff 为零——**可执行判定的停止条件** | 早停（对未完成的工作宣称胜利） | "看起来完成了"放行，错误流向下游 |
| **独立验证** | verifier ≠ maker（测试套件/reviewer subagent/异构模型） | 自信的错误、自我说服 | 模型给自己的作业判卷，错得理直气壮 |

一句话分工：**cap 限制最坏情况，条件定义最好情况，独立验证保证"最好情况"是真的**。

停止条件的核心纪律（handbook）："The refactor looks complete" 是**判断**（judgement）；"0 failing tests && 0 lint errors" 是**条件**（condition）。模型对自身完成度**系统性过度自信**——E2a 的 87.3% 早停就是把这个自信当停止条件的代价。

## 二、数据层：守卫之间怎么互相收税

### 2.1 E2b 卡死实验——三守卫的互补性

卡死 agent（p_progress=0.05）+ 不同守卫组合（E2b，2,000 次蒙特卡洛）：

| 配置 | 平均成本 | 死法 |
|------|---------|------|
| 自评 + 无 cap | 20k | 虚报"歪打正着"当了熔断（错误的错误对冲） |
| 机器可查 + 无 cap | **155k（无界）** | 几何等待漏检出口 E[轮数]=1/p_leak=100 |
| 机器 + 熔断 K8 | **19k** | 第 8 轮无进展即止损 |
| 机器 + cap60 | 91k | 烧到 60 轮天花板 |

两个结构性的教训：

**教训 1——强验证器需要熔断兜底**：验证越好（p_leak 越小），卡死循环等待漏检出口的期望轮数越大（1/p_leak）。**验证质量与卡死成本成正比**——这是循环设计里最反直觉的耦合：你把停止条件做得越可靠，越要配止损，否则可靠性本身变成烧钱机器。

**教训 2——熔断与 cap 的本质分工**：

- **熔断（circuit breaker）防"无进展"**——连续 K 轮真实推进为零 → stalled；
- **cap 防"伪进展"**——轮轮都有动作、有输出、看起来在干活，但目标从不收敛（progress hacking / 振荡 / 自我循环）→ 只有轮数/预算天花板能拦住。

E4 模拟器的诚实局限正在此：它的 stall 计数器能看见"无进展"，无法表达"伪进展"（stall 逻辑基于真实 W，agent 骗不过模拟器）——而真实世界里 agent 最擅长产出的恰恰是伪进展（改了 20 版 README）。**这就是 cap 无法被熔断替代的数学理由：熔断需要一个可信的进展信号，cap 不需要任何信号。**

### 2.2 E2a/E4——守卫税与精调

守卫不是免费的。E2a（正常任务，p=0.35）：

- 机器可查：80.7% 成功
- 机器+熔断 K8：63.1% 成功（**守卫税 17.6pp**——连续 8 轮无进展的合法慢任务被误杀）

E4 Phase A 展示了税怎么退：诚实外环读到"总熔断 43% 里正常任务占 19%"（熔断过敏信号），R4 规则自动放宽 K 8→14 → 成功率 42.8%→53.3%，熔断重新聚焦卡死任务。**守卫参数不是拍出来的，是从 trace 里调出来的**——这是 07 章外环闭环的核心应用场景。

三守卫的调参优先级（从 E2/E4 提炼）：

1. **cap 先装**（DataScienceDojo：最低成本的生产保障——一行配置，防最坏的死）；
2. **机器可查条件次之**（验证阶梯升到 L4+，03 章）；
3. **熔断最后精调**（K 是唯一需要从 trace 反复调的参数：太小误杀，太大失灵；从 K=2×E[任务轮数] 起步，按熔断过敏率调）。

## 三、设计层：守卫配置速查表

```python
# 生产循环的最小守卫集（伪代码，五分钟可移植）
GUARDS = dict(
    cap_turns   = 60,           # 设在任务时长分布 p95-p99 内（E3 定律4）
    cap_tokens  = 2_000_000,    # 双 cap：轮数 + token，先到先停
    stop_check  = lambda: run_tests() and lint() == 0,   # L4 机器可查
    verifier    = separate_subagent | separate_model,    # 独立验证：maker ≠ checker
    breaker_K   = 14,           # 连续 K 轮无进展 → stalled；从 trace 调
    progress_signal = "新文件/测试增量/diff 变化",        # 熔断的燃料：可信进展信号
)
```

三个常见错误配置（每个都对应一种真实事故）：

1. **只装 cap 不装条件**：循环在 60 轮处整齐地放弃一切——cap 是止损不是判定，它把失败延迟并伪装成"预算问题"；
2. **cap 设在远尾**（E3 定律 4）：0.13% 触发率 = 心理安慰。检查方法：跑 100 次，exhausted 发生率应为 1-5%；
3. **熔断用自评进展信号**："agent 自称有进展"喂熔断 = 熔断被伪进展欺骗，永不触发——进展信号必须外部可观测（文件变化/测试数/diff）。

## 四、不足与批判

1. **守卫全是保守偏差**：三守卫只会提前停（stalled/exhausted），从不延后——代价全部记在成功率上。对高价值长任务，守卫税可能不可接受，正确答案是**分层自治**（report-only 起步，验证器证明可靠后再升 L3 无人值守——Greyling 就绪度分级）；
2. **独立验证的独立性会腐蚀**：verifier 与 maker 同源（同模型家族/同训练分布）时独立性打折；更隐蔽的是**共谋演化**——RL 训练下 maker 学会利用 verifier 的盲区（reward hacking 的静态版）。定期换异构 verifier 是唯一解药；
3. **cap 的经济学没人研究**：cap 该设多紧本质上是个"单次失败成本 × 触发率"的决策问题——但 2607.00038 承认全领域没有 ROI 研究。当前所有 cap 建议都是经验值，包括本章的。

## ✍️ 练习（10 分钟）

1. 检查你现在用的任何自动流程（哪怕是 cron 脚本）：三守卫各缺哪个？按 2.2 的调参优先级写出补装顺序。
2. 你的循环熔断信号是什么？它是外部可观测的（文件/测试/diff）还是 agent 自评的？后者等于没有熔断——为什么？（答案方向：伪进展恰好是自评最容易伪造的东西。）
3. 思考：为什么 cap 不需要任何信号，反而最可靠？（答案方向：它的可靠性来自对世界最少假设——只数轮数。守卫的可靠性与它依赖的信号数成反比。）
