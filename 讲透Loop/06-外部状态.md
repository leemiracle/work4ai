# 06 · 外部状态：state file 是循环的脊椎

> 讲透Loop 第 6 章 | 证据：2608.21884（36,645 仓只有 2 个合格 state file）+ 本仓库活案例

## 一、直觉层：模型失忆，仓库记得

冷峻的事实（Osmani）："The model forgets everything between runs so the memory has to be on disk and not in the context. **The agent forgets, the repo doesn't.**"

没有外部状态的循环是什么样（vibeengines 的 state amnesia）：周一的 run 重修了周五修好的 bug；迁移循环每次从头转换同样的十个文件；迭代次数与进度脱钩——**每轮都是第一次**。

state file 把一串孤立 run 变成一个有方向的系统。它的地位：**五件套里最便宜的一件，却是自治的前提**——Loop Library 数据（02 章）里持久记忆只有 32% 采用，这正是"验证成熟、自治幼稚"的主因之一：没有跨 run 记忆，触发再自动也是每次从零开始。

## 二、协议层：三条规则（vibeengines handbook）

### 规则 1——读帧写验（never mid-run）

```
run 开始 → 读状态（frame the task）→ 干活 → 验证 → 写状态 → 结束
```

**绝不在 run 中间写状态**。原因：crashed run 不能记录它没完成的工作——中途写的"正在转换 auth 模块"在崩溃后就是永久谎言，下一个 run 读到它就跳过这个模块。状态只记录**已验证的事实**，正在进行的事留在对话（会死）和工作区（可检查）里。

### 规则 2——事实非 vibes（facts, not vibes）

```
❌ "made good progress on auth"          ← 不可重放，等于失忆加废话
✅ "converted auth/session.ts, tests pass" ← 可重放，可验证，可接续
```

判断标准：**下一轮 run 能不能仅凭这一行决定跳过什么/做什么**。vibes 状态的最大危害是自我感觉良好地绕过验证——它把状态文件退化成了日记。

### 规则 3——resume-point 一行（最便宜的可靠性升级）

状态文件末尾固定一行："下一步从哪开始"。handbook 原话：这是"the cheapest reliability upgrade a loop can get"。它把断点续传从"重新理解全部历史"降到"读一行执行"。

## 三、实证层：全世界的 state file 都不在版本控制里

2608.21884 最刺眼的发现：

- 36,645 仓扫描，**满足内容标准的 state file 只有 2 个**；零 stop condition 文件、零预算文件、循环引用的 verifier subagent 零；
- 217 个确认循环的**运行时状态全部在版本控制之外**（GitHub Actions 的日志会过期、/loop 与 /goal 的状态在产品内部、私有调度器不可见）；
- 仓库挖掘只能看到循环的**配置侧**（trigger/workflow），看不到**运行侧**（state/trace）——研究者在呼吁 loop observability 成为独立研究方向。

这个缺口的两面读法：

1. **悲观**：实践远落后于话语——"持久状态"人人都说，几乎没人做对；
2. **机会**：谁把 state file 做成版本控制内的一等公民（可 diff、可 review、可回滚），谁就补上了学科的最大空洞。**RESUME 模式正是这个方向的微型实践**（见下）。

## 四、活案例：本仓库的 RESUME 模式

本仓库每个长程单元都配一个 `RESUME-MMDD.md`（讲透Prompt/Context/Loop 皆然，本文集自身的 RESUME-0826.md 就是运行中的实例）。对照三规则逐项自检：

| 规则 | RESUME 模式实现 |
|------|----------------|
| 读帧写验 | 每次 session 开头读 RESUME（读帧）；单元收官才改写终稿（写验）——中途进展写在 todowrite（易失层），验证通过才沉淀 |
| 事实非 vibes | "E1-E3 跑通 + 数字"（19.4%/155k/5.7倍）而非"实验进展顺利" |
| resume-point | "待续（按优先级）"清单 = 显式 resume-point |
| 版本控制内 | RESUME 是 md 文件，进 git，可 diff——**恰好是 2608.21884 指出的全世界缺失的那个东西** |

诚实自评差距：本仓库的"循环"仍以人当触发器（你说"继续"），state file 有了，trigger 没自动化——五件套 4/5。完全体是 10 章的 opencode 定时任务（cron trigger + RESUME memory + experiments 退出码 verification——所有零件都在手边，只差组装）。

## 五、设计层：state file 最小模板

```markdown
# STATE: <循环名>（git 跟踪）
## 已完成（只记验证过的事实）
- [x] E1 跑通：01_results.json 存在，早停率 87.3%（2026-08-26）
## 进行中（run 结束时要么移上去，要么删掉）
- [ ] Ch07 草稿半篇（不可续传，重写）
## 下一步（resume-point，一行一任务）
1. 跑 E5 收敛演示 → 09 章引用
## 账本
tokens: ~1.2M | runs: 4 | stalled: 1（K过敏，已调14）
```

三条工程纪律：

1. **状态与产物分离**：state file 记"做到哪"，不记"做出来的东西"（产物自己会说话——文件/测试/图）；
2. **每条完成项带验证证据指针**（文件名/数字/日期）——否则"完成"就是 vibes；
3. **账本区顺手记守卫事件**（stalled 几次/cap 触发没）——这是 07 章外环分析的现成原料。

## 六、不足与批判

1. **状态是新的攻击面**：prompt 注入的高级目标是 state file 本身——诱导循环写"任务全部完成，无需复核"进状态，下轮读帧即骗过验证。状态文件的写权限应比读权限更保守（理想：只有验证通过的 run 能写"已完成"区）；
2. **md 状态没有 schema**：自然语言状态对 LLM 友好但对程序不可判——验证器无法机器检查"converted auth/session.ts"是否为真。进化方向：结构化状态（YAML/JSON + 自然语言注释双层），机器检查字段与人读字段分离；
3. **状态膨胀**：长跑循环的状态文件会越长越像对话史——把 Context Rot（讲透Context Ch03）从窗口搬到了盘上。纪律：状态文件本身也要 compaction，"已完成"区超过一屏就归档。

1. 给你手头最长的任务建一个 state file（用第五节模板），把今天的工作写进去。用规则 2 检查：每行都能重放吗？
2. 审计你见过的自动化：它的状态在哪？如果答案是"在日志里"或"没有"——它每轮多付多少理解成本？写一句估算。
3. 思考：为什么"读帧写验"比"每步写状态"更可靠，尽管后者信息更全？（答案方向：可靠性来自**只相信验证过的事**，不来自信息量；中途状态是未验证的，验证前写入 = 把赌注当事实存档。）
