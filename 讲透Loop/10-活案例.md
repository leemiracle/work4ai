# 10 · 活案例：本仓库就是 Loop Engineering 现场

> 讲透Loop 第 10 章 | 方法：用 02 章五件套 × 03 章验证阶梯 × 04 章形状学，逐项解剖三个活体
> 本章是讲透系列的"镜子章"——研究对象是读者自己的工作流

## 一、活体 1：MATH_LOOP_ENGINE——goal loop 的标准标本

`top-math-courses/MATH_LOOP_ENGINE.md`（2026-08-25 落盘）+ `loops/ANCHOR_CARDS_30.md` + skill `math-loop-driver`。五件套逐项对号：

| 五件套 | MATH_LOOP_ENGINE 实现 | 评价 |
|--------|----------------------|------|
| **Trigger** | 人说"开跑 Wave N" + skill 触发条件（锚点卡启动/卡壳时） | 半自动（22% 俱乐部的实践水准） |
| **Goal** | "点亮 30 锚点卡 / MSC 63 类，Wave N 完成 80% 才开 N+1" | **可验证 + 波次纪律 = 收敛保证**（09 章 $q$ 的控制） |
| **Verification** | 五类 reward：Lean 0-sorry / SymPy 恒等 / 数值阈值 / OEIS 命中 / 超 dummy；**≥2 类非零才 verified** | **L4-L5 交叉验证**——阶梯顶层 + 信号独立性，比单信号再稳一档（03 章练习 3 的答案） |
| **Stopping** | 五终态映射：verified=success / 卡壳降档=blocked / 15 分钟规则=止损 / Wave 80%=批完成 | 命名终态完备（74% 俱乐部之上） |
| **Memory** | ANCHOR_CARDS_30.md（状态）+ MATH_LOOP_ENGINE 仪表盘（22/30 卡，24/63 MSC）+ skill 红线（禁"读了=会了"） | **盘上 + 机器可查进度 + 反 vibes 条款**——06 章三规则全中 |

结构判词：**七阶段循环（理论→计划→实践→观察→反思→理论'→深挖）= 内循环的周期化**，外面包着 Wave BFS（调度）+ 五 reward（验证）+ 仪表盘（state）。它是 2607.00038 循环规格的教科书式实现——**比 Loop Library 50-loop 语料的平均水平（验证 70%/记忆 32%/触发 22%）高出一档**，尤其"≥2 类 reward"的交叉验证设计超出了语料中的常见做法。

唯一的天花板（也是 08 章结论的体现）：⑤反思的 R1-R5 生成规则产出的**新锚点方向**无法机器验证——OEIS 能验证"这个数列对不对"，不能验证"这个方向值不值得深挖"。方向归人，执行归机器——双人舞结构不是缺陷，是验证层级的结构性安排。

## 二、活体 2：Prover harness——AlphaProof 同构的最小实现

`讲透Agent/实战案例-Prover数学Agent/`：DeepSeek-Prover-V2-7B 提议 → 子目标分解 → Lean `lake build` 验证 → 专家迭代。对号：

- **内循环**：proposer-decomposer-verifier 三角（01 章五阶段的 LLM 版）；
- **验证**：Lean 0 sorry = L5 顶格——08 章表格里 AlphaProof 同款信号。**这就是为什么 24 题的蒸馏可以无人值守跑**：卡住的任务会失败得很诚实（build 不过），不会早停也不会烧穿（每题有超时 cap）；
- **外环**：24 题完成后人工读轨迹蒸馏十条规律（e1-e6 的分解失败案例是金子）——这是**人肉 L4 外环**（07 章 hill climbing 的手工版）；
- **已知弱点**：progress 由人判（e1 failed@decompose 是人标的）——若全自动需要 03 章阶梯补位（如"连续 N 次 decompose 失败 → blocked 终态"的机器判定）。

结构判词：bounded self-refinement 的干净标本（08 章判词）——收敛（每题有界）、可评估（build 二值）、改进对象是 $\Sigma$（prompt 策展/分解策略）不是 $\theta$。它和 MATH_LOOP_ENGINE 分工：Prover 闭环验证**命题**，LOOP 引擎闭环点亮**领域**——前者是后者的 L4 层实例（MATH_LOOP_ENGINE §〇 原话）。

## 三、活体 3：opencode 本身——你天天在用的 loop primitives

把 opencode 的功能读成循环零件（这是本单元最实用的视角转换）：

| opencode 功能 | 循环零件 | 对应章 |
|--------------|---------|--------|
| `auto_continue` | **自动触发器**（todo 未清→继续）——把"你说继续"换成系统说继续 | 04 章形状（半 goal） |
| `todowrite` | **stopping 的可视化**（任务清单 = success 终态清单）| 05 章 |
| `delegation`（subagent） | **maker ≠ checker** 的原生实现（verifier 用独立上下文/独立模型）| 03 章公理 1 |
| `schedule_job`（cron） | **Heartbeat/Cron 形状**的成品触发器 | 04 章 |
| memory blocks | **跨 session 的 state**（06 章：只是它在内存配置里不在 git 里——2608.21884 批评的那种"状态在版本控制外"）| 06 章 |
| skills | 循环的**具名可复用构建块**（Loop Library 里只有 20% 用了——你已经在这 20% 里）| 02 章 |
| RESUME-*.md | **读帧写验 state file**（本仓库模式，见 06 章四节自检表）| 06 章 |

**完全体组装示范**（所有零件都买了，只差上螺丝）：MATH_LOOP_ENGINE Wave 4 的全自动版 = `schedule_job`（cron 每天触发）+ RESUME/ANCHOR_CARDS（state）+ Lean build 退出码（L5 验证）+ `delegation`（verifier subagent）+ token 预算（cap）+ 卡壳两轮 → stalled 升级人类（熔断）。五件套全齐，零件零新开发。**没组装的原因不是技术是经济学**：每天一次的人肉触发成本 < 配置+信任自动化验证的成本——这个判断本身符合 11 章的成本理性（循环的采用是选择，不是义务）。

## 五、方法论收网：镜子章的用法

本章的真正交付不是三个案例的描述，是**这套解剖刀**：五件套（结构完整性）→ 阶梯（验证强度）→ 形状（触发-停止匹配）→ 守卫（失效安全）→ 状态（跨 run 连续性）→ 外环（改进回路）。拿去切你自己的任何自动化流程，切出来的缺口清单就是你的 Loop Engineering 待办。

一个诚实的提醒：三活体都是**结构标本**（配置正确），不是**效果证据**（没有对照实验证明"这样更快"）——2608.21884 指出的全学科证据真空，本仓库也在真空里。结构对了效果才可能对；结构对了效果未必对。前者是我们能做到的，后者是 2026-2027 的研究机会。
