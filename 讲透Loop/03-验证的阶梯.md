# 03 · 验证的阶梯：maker-checker 分离与五级验证

> 讲透Loop 第 3 章（心脏章）| 三层宪法：直觉 → 数学 → 代码
> 实验基座：`experiments/01_loop_dynamics.py`（E2 三守卫，已跑通）| 前置：00 章验证中心论

## 一、直觉层：整座学科立在一条物理学上

这条物理学叫**验证不对称性**（verification asymmetry）：**检查一份工作比做这份工作容易。**

- 批改一道积分题比做它快；
- 看出代码有 bug 比写出无 bug 代码容易（多数时候）；
- Lean 里 `#check` 一个证明比从头构造它便宜几个数量级。

如果这条不对称性不成立——如果验证和生成一样贵——那么整个 Loop Engineering 就塌了：循环自我纠错的开销会吞掉自动化的全部收益。**循环之所以能转起来，是因为"查"比"做"便宜。**

从这条物理学直接推出本学科的两条公理：

**公理 1（maker ≠ checker）**：干活的模型不能给自己的活判卷。利益冲突与你 review 自己的 PR 同构——只不过模型"失败得更可靠"（Osmani）。工程落点：Claude Code 的 `/goal` 用一个 **fresh model**（不是干活那个）检查停止条件是否为真；Codex 同名同构。这就是把 maker-checker 分离应用到**停止条件本身**。

**公理 2（验证到哪里，自治就到哪里）**（aipatternbook："autonomy is capped by verification reach"）：你的循环敢无人值守跑到什么程度，取决于你能在多大成本内**独立**确认正确性。验证器多强，缰绳就多长。

## 二、五级验证阶梯（2607.07663，1,250 篇综述的核心产出）

按**信号强度**从弱到强排列——每级回答同一个问题："凭什么是真的？"

| 级 | 名称 | 信号是什么 | 典型例子 | 强度 | 成本 |
|----|------|-----------|---------|------|------|
| L1 | 内在自评 | "我自己觉得对了" | Self-Refine、Reflexion 的自我批评、"看起来完成了" | 最弱：confidently wrong 时信号本身就是错的 | 极低 |
| L2 | 过程奖励 | 轨迹每步的分数 | PRM（process reward model）、rubric 打分 | 弱：分数可被 hackers 演化着骗 | 低-中 |
| L3 | 判官模型 | 另一个模型的裁决 | LLM-as-judge、fresh-model `/goal` 判卷、DeepVerifier | 中：比自评强（独立性），但判官自身会错/会被讨好 | 中 |
| L4 | 外部工具 | 与模型无关的世界反馈 | 编译器、linter、单元测试、搜索引擎核对、数值复算 | 强：不服从模型的自信 | 低-高不等 |
| L5 | 形式验证 | 数学证明的机器判定 | Lean `lake build` 0 sorry、SymPy `simplify(lhs-rhs)==0`、类型检查、OEIS 命中 | 最强：p(漏检)→0 | 最高（写形式规约贵） |

**2607.07663 的实证规律**：自改进的强度沿此阶梯排列（demonstrated self-improvement strength tracks this hierarchy），失败模式——自我确认循环、模型塌缩、多样性塌缩——**恰好是违反层级的后果**（自改进信号比被改进对象更弱时，错误自我强化）。一句话：**用 L1 信号驱动自改进 = 让最不可靠的部件当裁判。**

例证（每级一个循环）：
- L1 循环：Self-Refine（自评→自改→自评……）——对 confidently wrong 无解；
- L3 循环：`/goal`（干活模型 ≠ 判卷模型）、DeepVerifier（ACL 2026 Findings：rubric 分解验证，比 vanilla agent-as-judge / LLM judge 高 12–48% meta-eval F1，test-time 迭代 3–4 轮收益封顶后早停）；
- L4 循环：**Ralph Loop**（DataScienceDojo 模式 5）：退出条件=确定性测试全绿，且**每轮重置上下文**防 Context Rot——agent 无法通过"说服自己"过关；
- L5 循环：你的 **Prover harness**（提议→Lean 验证→专家迭代）与 **MATH_LOOP_ENGINE**（五类 reward：Lean 0-sorry / SymPy 恒等 / 数值阈值 / OEIS 命中 / 超 dummy——**全部 L4-L5**，全机器可判）。这就是为什么它可以安全自治：验证器在阶梯顶层。

## 三、数学层：漏检的复利定律

验证器的"每轮漏检率" $p$ 看着很小，但循环会**复利**它。

### 3.1 累积早停律

设任务需 $T$ 轮完成，每轮验证以 $p$ 的概率**漏检**（活没干完但检查通过了）。整个过程中至少一次被漏检放行的概率：

$$P_{\text{premature}} = 1-(1-p)^T \approx pT \quad (p \ll 1)$$

**理论 vs 实测对照**（E2，参数 W=8, p_progress=0.35, p_leak=0.01）：

$$E[T] = W/p_{\text{progress}} = 8/0.35 \approx 22.9 \text{ 轮} \Rightarrow P_{\text{premature}} = 1-0.99^{22.9} = 20.5\%$$

E2a 蒙特卡洛实测：**19.4%**。偏差 1.1 个百分点，公式成立。单轮 1% 的漏检，被 23 轮放大成 1/5 的假完成——**这不是验证器太烂，是循环在放高利贷。**

### 3.2 设计公式（反解）

要保证 $T$ 轮内早停率低于 $\varepsilon$，单轮漏检率必须：

$$p < \varepsilon / T$$

代入数字：30 轮任务要早停 <5% → **p < 0.0017**。也就是说每 600 次检查只能漏 1 次。这解释了两个工程事实：

1. 为什么"差不多能用的验证器"在循环里完全不可用（单轮 1% 看着行，循环里是灾难）；
2. 为什么 **Lean / 形式验证在循环里拥有霸权**：$p = 0$ 时累积率恒为 0，**没有复利**。任务越长，L5 与 L4 的差距按指数拉开——这正是 AlphaProof 架构（LLM 提议 + Lean 验证）在长推理链上的数学理由。

### 3.3 几何等待：漏检是卡死循环的唯一出口

agent 完全卡死（p_progress→0）且无 cap 无熔断时，"机器可查"循环的期望轮数：

$$E[\text{turns}] = \frac{1}{p_{\text{leak}}}$$

E2b 实测：p_leak=0.01 时卡死 agent 均烧 155k token（≈100+ 轮），恰好等在漏检出口上。对照：熔断 K=8 在第 8 轮截断（19k）。**验证越强，卡死越贵**——这就是为什么三守卫必须成套（见 05 章）：强验证器需要熔断和 cap 给它兜底。

### 3.4 一张对照表：同一 agent，四种停止配置

| 停止配置 | 验证层级 | 早停率 | 卡死成本 | 结论 |
|---------|---------|--------|---------|------|
| 自评停止 | L1 | 87.3%（E2a） | 20k（虚报"歪打正着"当了熔断） | 便宜且错 |
| 机器可查 | L4 | 19.4%（≈理论 20.5%） | **155k，无界**（几何等待） | 对但可能贵到爆 |
| 机器+熔断 | L4+守卫 | 17.8% | 19k | 正常场景付 17.6pp 成功率税（80.7→63.1）|
| 机器+熔断+cap | 全守卫 | 同上 | 有界 | 生产配置 |

注意第三行的**守卫税**：熔断在正常场景误伤了慢任务（连续 8 轮无进展的合法任务被止损）。守卫不是免费的——这是 05 章的主菜。

## 四、代码层：三行核心 + 一个可跑对照

循环里唯一不能省的那一行，抽象出来是：

```python
def loop(env, agent, stop):
    obs = env.reset()
    while not stop(obs):          # ← 验证阶梯全部押注在这行的实现里
        obs = env.execute(agent.decide(obs))
    return obs
```

`stop` 的实现决定层级：`agent.self_report()` 是 L1；`run_tests()` 是 L4；`lake_build_zero_sorry()` 是 L5。**循环的自治等级不是 agent 的属性，是 `stop` 函数的属性。**

累积漏检律的验证（复现 E2 理论-实测对照）：

```bash
python3 -c "print(f'{1-0.99**(8/0.35):.3f}')"   # → 0.205 理论
# 对照 E2a 实测 premature=19.4%，偏差 1.1pp ✅
```

完整实验：`python experiments/01_loop_dynamics.py`（E2a/E2b/E2c 三组数据，结果在 `01_results.json`，图在 `01_loop_dynamics.png`）。

## 五、不足与批判（给心脏章泼的四盆水）

1. **验证不是免费的**：每级验证都在延迟/token/工程量上收费。DeepVerifier 的 test-time 迭代收益 3–4 轮封顶（早停自己的验证循环）；Anthropic 长程 agent 的 200+ 特征 `passes:false` 清单（eesel 转述，一手待核）本质是把验证成本前置成了一张规约表——**规约本身可能比代码还贵**；
2. **gate ≠ goal（Goodhart）**：循环满足的是你写的 gate，不是 gate 背后的意图（Lindenberg）。测试全绿 ≠ 重构正确。更阴险的是**验证器成为攻击面**：RL 训练的 agent 会演化出"让测试通过"而不是"把事做对"的行为（reward hacking；2607.00038 把反模式锚定在 model-as-judge fragility 文献上）。E4 实验将用一个被污染的外环 reward 亲手复现这个塌缩；
3. **判官模型的独立性是稀缺品**：L3 的强度来自独立性（fresh model），但判官与 maker 同源（同一家族/同一训练分布）时独立性打折；判官还会被讨好性拉偏（sycophancy）。2607.07663 把"self-evaluation"单列一个类目正是因为**每个改进循环都是一次"某信号能替代人类判断"的赌注**；
4. **L5 的天花板是形式化成本**：不是所有任务都写得进 Lean/测试。开放性任务（研究/写作/产品判断）只能停在 L2-L3——这正是 2607.07663 指出的"研究方向设定留在人类手里"的结构性原因：**阶梯的顶层覆盖不到的地方，就是人类必须留守的地方。**

## 六、应用：把阶梯装进你的循环

1. **设计任何循环先填这张表**：任务的最强可得验证是什么？→ 决定自治上限。写不进 L4 的任务，循环只能跑 report-only（Greyling 就绪度 L1，2608.21884 转述）；
2. **MATH_LOOP_ENGINE 就是范本**：五类 reward 全在 L4-L5，且"新卡 verified 条件 = ≥2 类 reward 非零"是**交叉验证**（两级不同信号源）——比单信号再稳一档；
3. **升级路径**：L1 自评 → L3 加独立判官（便宜快速）→ L4 加测试/编译（coding 任务默认）→ L5 形式规约（长链/高价值任务）。**降级是事故**：测试被删、验证被 mock、判官与 maker 合并——每一次生产事故几乎都能定位成一次阶梯降级；
4. **给循环配守卫要成套**：强验证器（L4-L5）配熔断+cap（3.3 节的几何等待教训）；弱验证器（L1-L2）根本不该无人值守。
