# 04 · 四种循环形状：Heartbeat / Cron / Hook / Goal

> 讲透Loop 第 4 章 | 实验基座：E3（`experiments/03_loop_shapes.py`，2,000 天蒙特卡洛）

## 一、直觉层：形状 = 触发 × 停止

vibeengines handbook 的四形状分类——**外循环按"怎么点燃 × 怎么熄灭"分型**，这是循环设计的第一决策（多数坏循环 = 把 goal 问题硬塞进 heartbeat 形状，或反之）：

| 形状 | 触发 | 停止 | 天职 | 天敌 |
|------|------|------|------|------|
| **Heartbeat 心跳** | 短间隔连续轮询（秒-分） | 从不（被杀/暂停/预算耗尽） | 监控日志、值守队列、健康分诊 | 空转成本 + 重叠事故 |
| **Cron 定时** | 时刻表（每日 7 点/每周一） | 每批完成即止 | 夜间审查、依赖审计、晨报 | 延迟（最坏等一天） |
| **Hook 钩子** | 事件（PR push/CI 失败/消息） | 一次一事件 | 响应式：修挂的构建、审新 PR | 事件风暴成本线性爆炸 |
| **Goal 目标** | 反复迭代直到条件为真 | **条件验证为真**——或 cap 熔断 | 迁移、重构、"让测试全绿"（范围未知） | 无进展时无限烧钱 |

关键句（handbook 原文意译）：**Goal 循环是唯一天然处于"继续"状态的形状**——其他三个的默认态是"停"，goal 的默认态是"跑"。所以它最强也最危险，独享 hard cap 强制令（E3 数据将量化这个"危险"）。

**形状可组合**（成熟形态通常是三件套）：cron 巡逻发现工作 → hook 响应事件 → 每个工作项 spawn 一个 goal 循环——各自带各自的停止规则。Osmani 描述的 Codex/Claude Code 内部自动化就是这个组合。

## 二、数据层：E3 的 24 小时账本

模拟设定：24h 窗口，泊松到达（日均 ~77 件，白天峰值 λ≈6/h，夜间低谷），2,000 天蒙特卡洛。结果（日均 token）：

| 形状 | 日均 | p95 | 完成 | 备注 |
|------|------|-----|------|------|
| Heartbeat（有锁） | 374k | 450k | 77.5 | 144 次检查/天是固定开销 |
| Heartbeat（无锁） | 513k | 630k | 77.5 | 日均 13.9 次重叠事故 × 15k 修复费 |
| Cron 日批 | **233k** | 277k | 77.5 | 最便宜，但最坏延迟 24h |
| Hook 事件驱动 | 271k | 322k | 77.5 | 延迟≈0，性价比最优 |
| Goal 无上限 | **1,550k** | 1,860k | 77.5 | **Hook 的 5.7 倍** |
| Goal cap=25 | 1,545k | 1,868k | 76.6 | cap 形同虚设 |

四个可复用的形状学定律：

**定律 1——心跳的固定税**：检查费是心跳的下限，与你有没有活无关（xpk 的 6,290 次零命中运行是极端版）。周期越短税越重：10 分钟周期 = 144 次/天 × c_check。**心跳只配监控类任务**——它的价值在"永远在场"，不在"干活"。

**定律 2——无锁心跳 = 事故制造机**：上一 tick 没干完下一 tick 又开，两个 agent 改同一状态。E3 里事故率×3 的无锁版日均贵 37%（+139k tok）。**每个心跳实现必须有"cycle in progress"锁**（DataScienceDojo 模式 9 原文要求）——这本质是给 heartbeat 加一个迷你 stopping rule。

**定律 3——Cron 买便宜牺牲延迟，Hook 买速度付出线性**：Cron 比 Hook 便宜 14%（省掉逐事件检查），但最坏延迟一整个周期；Hook 成本随事件率线性（风暴天没有上限）。两者之间没有免费的形状——只有任务对延迟的容忍度。

**定律 4——Goal 的危险 + cap 的失准**：goal 无上限是 hook 的 5.7 倍成本，因为它把"每事件一次"变成"每事件迭代到完成"。而 cap=25 形同虚设的原因值得背下来：W=3、p=0.3 的任务 P(超25轮) = 0.7^25 ≈ **0.13%**——cap 设在任务时长分布的远尾之外，等于没设。**cap 必须设在尾部之内**（让 exhausted 有实际发生率，比如 1-5%），否则它只是心理安慰。

## 三、设计层：形状选择决策树

```
任务有明确"完成"判据吗？
├─ 没有（持续监控/值守）──────────→ Heartbeat（加锁 + 预算上限）
├─ 有，但批量够大且不急 ──────────→ Cron（接受延迟，成本最低）
├─ 有，且必须即时响应 ────────────→ Hook（每事件 spawn）
└─ 有，但单件工作量大/范围未知 ───→ Goal（每件 spawn，强制 cap + 熔断）
                                        └─ cap 设在时长分布 p95-p99 内，不设远尾
```

三个组合件（成熟配置）：
1. **cron 巡逻 + goal 工人**：每天早上 cron 扫 issue/CI，每项 spawn goal（Osmani 的 triage 自动化）；
2. **hook 门卫 + 独立 verifier**：PR push 触发 hook，verifier subagent 审查（2608.21884 里 205/253 的真实循环就是这个形状——**事件触发的 PR 审查是当前最普遍的生产循环**）；
3. **heartbeat 哨兵 + hook 执行**：心跳只做检测（便宜模型），异常才触发 hook 干活（贵模型）——检查与执行分级是成本设计的通用手法。

## 四、不足与批判

1. **E3 是排队近似**：每 tick 处理一件、goal 任务 W=3 固定——真实负载的相关性（bug 成簇来）与任务时长分布的重尾会被低估，goal 无上限的真实尾部比模拟更毒；
2. **四形状不是封闭分类**：数据流（streaming）、自适应频率（负载高时心跳加速）等变体在 handbook 分类之外——形状学是起手式，不是终局；
3. **"形状选错"的诊断很难**：一个烧钱的系统可能同时有形状错（goal 干心跳的活）与守卫缺（无 cap 无熔断）——先修哪个？经验法则：**先修停止（守卫），再修形状**——停止错了会流血，形状错了只是低效。
