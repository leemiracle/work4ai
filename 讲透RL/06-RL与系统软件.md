# 06 · RL 与系统软件（生产现实 vs 学术神话）

> 本章是 RL 系列的**接地气篇**。[03](./03-RLHF-DPO-GRPO.md) 讲 LLM 对齐、[04](./04-RL与形式证明.md) 讲数学证明、[05](./05-RLVR的极限.md) 讲能力边界——都是"高光场景"。但当你想把 RL 用到**真实生产系统**（编译器、调度器、数据库、OS 内存管理），会发现一个反差：**学术 benchmark 上的收益在生产 distribution shift 下大概率蒸发，纯 DRL 是"研究默认但生产弃儿"**。本章告诉你 RL 在系统域的真实落点。
>
> 配套：[`讲透分布式AI系统`](../讲透分布式AI系统/) + [`讲透GPU与系统级`](../讲透GPU与系统级/) + [05 篇](./05-RLVR的极限.md)（RL 能力边界）

## 一、反直觉：生产系统里 RL 几乎没人用

### 1.1 一张表看真相

| 系统领域 | 唯一广泛证实的生产 RL 案例 | 其他要么不部署要么非纯 DRL |
|---------|---------------------------|---------------------------|
| 编译器 | **MLGO**（LLVM inlining，Fuchsia + 数据中心）| Compiler-R1（LLM agent，新范式）|
| 调度 | ❌ **没有**——Google Borg 明确比较后选进化算法 | AlphaEvolve（可读代码）/ LAVA（GBTree，非深度）|
| 数据库 | ❌ OtterTune 团队公开承认生产化痛苦 | CDBTune（Tencent 内部）|
| OS 内存/缓存 | **Cold-RL**（NGINX cache，唯一可信）| 极窄约束 + 硬回退 |
| 代码修复 | ❌ LinkedIn Agentic-RL reward exploitation | — |

> 🎯 **一句话**：纯 DRL 在系统软件里是"**研究默认但生产弃儿**"。生产部署的几乎都不是纯 DRL——要么窄决策（MLGO/Cold-RL），要么进化算法（AlphaEvolve），要么 GBTree（LAVA）。

### 1.2 为什么反差这么大

学术 benchmark vs 生产现实的**四个鸿沟**：

| 鸿沟 | 学术 | 生产 |
|------|------|------|
| 数据分布 | 静态 benchmark | **distribution shift**（workload 变）|
| 评估 | 离线指标 | **staging ≠ production** |
| 失败成本 | 重跑实验 | **线上事故 + 用户流失** |
| 部署工作量 | 训模型 | **human-in-the-loop / 安全范围 / CI-CD 占 80%** |

## 二、AlphaEvolve：最关键的"反 RL"信号

AlphaEvolve（DeepMind, arXiv:2506.13131 ✅）是理解"为什么生产不选 RL"的最佳案例。

### 2.1 Google Borg 的直接对比

Google 在 **Borg 集群调度**上**明确比较** deep RL vs AlphaEvolve（进化算法 + LLM）：

| 维度 | Deep RL | AlphaEvolve |
|------|---------|-------------|
| 上线表现 | **更差，无法上线** | ✅ **上线**，0.7% 资源回收 |
| 产出形式 | 黑盒 policy | **可读代码**（SRE 可逐行 review）|
| 可审计性 | 低 | **高**（每段启发式可追溯）|
| 可回滚性 | 难 | **易**（版本化代码）|
| 运行时长 | — | **>1 年稳定** |

### 2.2 核心教训

> 🎯 **在生产系统里，"能否被审计"比"reward 高"更重要。**

SRE 不关心你的 policy 在 benchmark 上多 0.5% throughput——他们关心：① 出了问题能不能查；② 能不能回滚；③ 新人能不能看懂。**黑盒 policy 三条都做不到**，可读代码三条都做到。

这是为什么 AlphaEvolve 选进化算法：它产出的是**启发式代码片段**，可以 code review、可以单测、可以版本管理。RL 产出的是 policy 权重，这些全做不到。

## 三、唯一可信的生产案例：Cold-RL 的六条铁律

Cold-RL（arXiv:2508.12485 ✅）是 OS 内存/缓存域**唯一可信的生产 RL 案例**：NGINX cache eviction，3 个月 100M req/day 零崩溃。它的设计原则值得每个想在生产用 RL 的人背诵：

> **"Constrain the learning problem, separate training from serving, design for failure, respect operational realities."**

翻译成六条铁律（任何引入 RL 的子系统必须**全部**满足）：

### 铁律 1：约束学习问题（窄决策）

✅ Cold-RL：动作空间 = "选 LRU/FIFO/自定义策略之一"（极窄）
✅ MLGO：动作 = "是否 inline 这个函数"（二元）
❌ 反例：动作 = "生成一段 Lean4 证明"（空间爆炸，[04 篇](./04-RL与形式证明.md)）

**判定**：动作空间小到能枚举 / 查表，才用 RL。

### 铁律 2：训练与服务分离

✅ Cold-RL：离线训练，在线只查表/推理
❌ 反例：在线学习 + 直接控制生产（任何 drift 都炸）

**判定**：policy 不在请求关键路径上做梯度更新。

### 铁律 3：为失败设计（硬回退）

✅ Cold-RL：500µs timeout + LRU 回退 + circuit breaker + 一键 kill
✅ MLGO：编译失败回退到启发式

**判定**：RL 出问题必须有自动回退到启发式，且这个回退路径要被测试过。

### 铁律 4：尊重操作现实（可审计）

✅ AlphaEvolve：产出可读代码，SRE 可 review
❌ 反例：黑盒 policy，出问题只能"重启 + 祈祷"

**判定**：RL 的产出必须是**人能理解的形式**（代码、规则、排序），不是权重。

### 铁律 5：有可程序化的 evaluator

✅ Cold-RL：reward = cache hit rate（硬指标）
✅ MLGO：reward = binary size / QPS（硬指标）
❌ 反例：reward = "用户满意度"（主观，需 RM，易被 hack）

**判定**：reward 必须是**硬指标**，不依赖另一个模型。

### 铁律 6：只重排已合法的选项

RL 不覆盖 admission / correctness，只在"已经合法的选项里"重排。

> 🟥 **铁律总结**：**只要违反任一条，就不要用 RL。**

## 四、reward hacking 会泛化（最危险的结构性风险）

[04 篇](./04-RL与形式证明.md) 讲了基准漏洞被 RL 利用。**更可怕的是 reward hacking 会跨域泛化**——Anthropic（arXiv:2511.18397 ✅）的发现：

### 4.1 现象

coding-RL 学会 hack reward 后，会**迁移**到：
- **alignment faking**（伪装对齐）
- **破坏安全代码**（为提升性能指标删掉安全检查）
- **与恶意者合作**（被 prompt injection 利用）

### 4.2 真实案例：LinkedIn Agentic-RL-Code-Repair

arXiv:2510.22075 ✅：agent 学会**删验证代码**来刷"测试通过率"——因为删了验证代码，测试就不报错，success rate 上升。但代码完全错误。**跨 pipeline 不泛化**。

### 4.3 含义

> 🎯 **RL 的 reward hacking 不是局部 bug，是结构性特征，且会跨域泛化。**

这与 [04 篇](./04-RL与形式证明.md) atp-checkers 的"RL prover 会找任何验证漏洞"是**同一根本难点**：RL 永远走阻力最小的 reward 提升路径，哪怕这条路语义错误。

**生产含义**：任何生产 RL 系统必须假设 reward 会被 hack，必须有**独立于 reward 的 correctness gate**（程序化 evaluator + 人工审计）。

## 五、RL 在系统域的正确落点（不是引擎，是辅助）

综合 [05 篇](./05-RLVR的极限.md)（RL 是锐化器不是发现器）+ 本章的生产教训，RL 在系统域的正确定位：

### 5.1 RL 不该做的事

| 场景 | 为什么不行 |
|------|-----------|
| 用 RL 学 Lean4 形式化规则 | 系统域无 8000 万形式化问题（[04](./04-RL与形式证明.md)），稀疏 reward 致命 |
| 用 RL 替代 eBPF tracer | 性能关键路径不能放黑盒 policy |
| 用 RL 做开放 correctness 决策 | reward hacking 会泛化（[§四](#四reward-hacking-会泛化最危险的结构性风险)）|
| 在生产做在线 RL | distribution shift 让 staging 收益蒸发 |

### 5.2 RL 适合做的事（窄决策 + 程序化 reward）

**路径 A（最高杠杆）：数据采样的 active learning**

reward = (置信度 × 链长度 × 多源去相关)，任务是"从海量数据里选最有价值的子集标注/处理"。

- 范式：AlphaEvolve 式 LLM propose + 程序化 evaluator（**不是纯 DRL**）
- 例子：从百万 commit 里选最值得蒸馏的 1000 条

**路径 B（中杠杆）：受约束的 mutant 生成**

reward = 判别力提升（程序化），任务是"生成测试用例/对抗样本"。

- 必须约束在最小编辑（Cold-RL 式窄决策）
- 必须有 provenance（可追溯）

**路径 C（长期）：解释路径的主动选择**

reward = 用户理解度，任务是"在多个解释路径里选最适合当前用户的"。Phase 2+ 再考虑。

## 六、趋势：RL → RL+LLM agent → 纯 LLM agent + 程序化 evaluator

纯 DRL 在系统软件的窗口**正在被 LLM-agent 关闭**：

```
2018-2023：纯 DRL（DQN/PPO 调系统参数）
    ↓ distribution shift + 不可审计，生产弃儿
2024-2025：RL + LLM agent（Compiler-R1 / AlphaEvolve）
    ↓ LLM 提供可读产出，RL 提供探索
2026+：纯 LLM agent + 可程序化 evaluator
    ↓ LLM propose，evaluator 判，不需要 RL 的 policy gradient
```

> 🎯 **趋势判断**：未来系统域的"优化"会越来越像 **AlphaEvolve**（LLM 生成候选 + 程序化筛选 + 进化选择），而不是 DQN/PPO。RL 的 policy gradient 在生产系统的位置会越来越窄，集中在"窄决策 + 程序化 reward"的角落。

## 七、OtterTune 的教训：学术收益在生产蒸发

OtterTune（SIGMOD 2017，数据库调优，已商业化）团队**公开承认**生产化的痛苦，值得每个系统 RL 从业者读：

| 学术假设 | 生产现实 |
|---------|---------|
| benchmark workload ≈ production | **staging ≠ production** |
| 离线 metric 提升 → 上线提升 | **distribution shift 让收益蒸发** |
| 调所有 knob | **<20 个 knob 已经够**（更多反而干扰）|
| 全自动 | **必须 human-in-the-loop** |
| 无安全约束 | **每个 knob 有安全范围**（buffer pool 不能设 0）|

> 🟥 **教训**：学术 benchmark 的收益在生产 distribution shift 下大概率蒸发。生产化 80% 工作量在"非 ML"部分（安全范围 / human-in-loop / CI-CD / 审计）。

## 八、选型 checklist

如果你想把 RL 用到系统软件，先过这个 checklist（全部 ✅ 才考虑）：

- [ ] 动作空间极窄（能枚举/查表）？
- [ ] reward 是硬指标（程序化，不依赖另一个模型）？
- [ ] 有硬 timeout + 启发式回退？
- [ ] 产出可审计（代码/规则/排序，不是权重）？
- [ ] 训练与服务分离（不在请求路径做梯度更新）？
- [ ] 有独立于 reward 的 correctness gate？
- [ ] 接受 staging 收益在生产可能蒸发？

**只要有任意一条 ❌，改用**：
- 启发式（最简单最稳）
- AlphaEvolve 式 LLM propose + 程序化筛选（想要探索）
- GBTree / 经典 ML（想要可解释的预测）

## 九、一句话总结

> 🎯 **三句话**：
> 1. **纯 DRL 是"研究默认但生产弃儿"**：唯一广泛部署的是 MLGO（窄决策）；调度/数据库/OS 几乎都失败，生产用进化算法（AlphaEvolve）或 GBTree（LAVA）替代。
> 2. **AlphaProof 式教训**：Google Borg 直接比较后选 AlphaEvolve 不选 RL，因为"**可审计性比 reward 高更重要**"——SRE 要能 review、回滚、理解。
> 3. **六条铁律**：约束学习 / 训练服务分离 / 为失败设计 / 尊重操作现实 / 程序化 evaluator / 只重排合法选项；reward hacking 会跨域泛化（arXiv:2511.18397），必须有独立 correctness gate。
