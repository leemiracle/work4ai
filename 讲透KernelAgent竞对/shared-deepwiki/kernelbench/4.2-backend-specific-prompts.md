## Purpose and Scope

This document describes how KernelBench customizes prompts for each of the five supported GPU kernel DSLs (Domain-Specific Languages): CUDA, Triton, CuTe, TileLang, and ThunderKittens. Each backend requires different syntax, programming patterns, and compilation toolchains, necessitating tailored prompt templates and examples. This page covers the backend configuration system, example file organization, and backend-specific constraints.

For general prompt construction mechanics and template assembly, see Prompt Construction System [/ScalingIntelligence/KernelBench/4.1-prompt-construction-system]. For prompting strategies (zero-shot, one-shot, few-shot), see Prompting Options [/ScalingIntelligence/KernelBench/4.4-prompting-options]. For hardware-specific prompt augmentation, see Hardware-Aware Prompting [/ScalingIntelligence/KernelBench/4.3-hardware-aware-prompting].

## Supported Backend DSLs

KernelBench supports five GPU kernel programming languages, each with distinct characteristics:

| | Backend | Display Name | Default Precision | Primary Use Case | Compilation Method
| `cuda` | CUDA operators | FP32 | Low-level kernel optimization | `nvcc` via `torch.utils.cpp_extension`
| `triton` | Triton kernels | FP32 | High-level kernel DSL with Python syntax | `@triton.jit` decorator
| `cute` | CuTe (CUTLASS) kernels | FP32 | Template metaprogramming for tensor ops | CUTLASS header-only library
| `tilelang` | TileLang kernels | FP16 (required) | Tile-based abstractions | TileLang compiler
| `thunderkittens` | ThunderKittens kernels | BF16 (required) | Warp-level primitives for Hopper+ GPUs | `kittens::` namespace with CUDA

## Example File Organization

### Example File Types

Each backend uses three types of example files:

- Shared input architecture (`few_shot_example_arch`): PyTorch reference code, shared across all backends

- One-shot optimized implementation (`one_shot_new_arch`): Single example of optimized kernel

- Few-shot examples (`few_shot_examples`): Multiple input/output pairs (CUDA only currently)

Pattern 1: CUDA with Few-Shot Examples

When `backend="cuda"` and `prompt_option="few_shot"`, the system:

- Loads `backend_display = "CUDA operators"` from TOML

- Reads all three example pairs from `few_shot_examples` array prompts.toml31-35 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/prompts.toml#L31-L35]

- Formats each pair using `example_entry_template` prompts.toml108-118 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/prompts.toml#L108-L118]

- Injects into `examples_block` component prompts.toml90-94 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/prompts.toml#L90-L94]

Pattern 2: Triton with One-Shot Example

When `backend="triton"` and `prompt_option="few_shot"`:

- Loads `backend_display = "Triton kernels"` prompts.toml38 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/prompts.toml#L38-L38]

## Summary

Backend-specific prompts enable KernelBench to guide LLMs toward generating syntactically correct kernels for five different GPU DSLs. The TOML-based configuration system provides:

- Declarative backend definitions: Each backend specifies display names and example file paths

- Flexible example systems: CUDA supports three few-shot examples; other backends use one-shot

- Automatic constraint enforcement: Precision requirements (FP16 for TileLang, BF16 for ThunderKittens) are set programmatically

- Shared template infrastructure: Common components like `problem_statement` and `instruction` use `{backend_display}` placeholders

The system achieves backend portability by separating what varies (backend-specific examples and display names) from what's shared (template structure and assembly logic), enabling consistent prompt generation across diverse compilation toolchains.
