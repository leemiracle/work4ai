## Local vs Modal Compilation Workflows

KernelBench's compilation strategies differ fundamentally between local GPU execution and Modal cloud execution due to infrastructure constraints and optimization trade-offs.

### Compilation Strategy Comparison

| | Aspect | Local Execution | Modal Execution
| Build Cache | Optional (`build_cache=True/False`) | Not available (always JIT)
| Build Directory | `cache/{run}/{problem}/{sample}` | `None` (in-memory only)
| Compilation Phase | Pre-compile on CPU (optional) or JIT on GPU | Always JIT per container
| Cache Sharing | Shared across all GPU workers | Isolated per container
| GPU Arch Config | Single `set_gpu_arch()` call | Per-container via `gpu_arch_mapping`
| Persistence | Survives evaluation runs | Discarded on container exit
| Parallelization | N GPUs share cache directory | N containers with independent compilation

### Local Evaluation Compilation Flow

```

Local compilation code path:

- Optional: `set_gpu_arch(config.gpu_arch)` sets environment variable

- Optional: `compile.batch_compile()` pre-compiles all kernels on CPU

- Each GPU worker calls `evaluate_single_sample()` with `build_dir` pointing to cache

- If build exists, `torch.utils.cpp_extension.load_inline()` loads cached binary

- If build doesn't exist, JIT compilation occurs and writes to cache

### Modal Evaluation Compilation Flow

```

Modal compilation code path:

- `ModalEvaluator.with_options(gpu=config.gpu)` configures container GPU type

- Each spawned container calls `evaluate_single_sample_modal.remote()`

- Inside container: `set_gpu_arch(gpu_arch_mapping[gpu_type])`

- `eval_kernel_against_ref(..., build_dir=None)` forces JIT compilation

- Compilation artifacts stored in container's temporary filesystem

- Container exits after returning `KernelExecResult`, discarding all builds

### Why Modal Doesn't Use Build Cache

Modal's architecture makes build caching impractical:

- Ephemeral containers: Containers are created per-evaluation and destroyed immediately after

- No shared filesystem: Each container has isolated storage; no way to share cache between containers

- GPU attachment latency: Container startup time dominates; compilation overhead is acceptable

- Parallelization model: Massive parallelization (hundreds of containers) makes per-sample JIT acceptable

## Best Practices

### When to Enable Build Cache

Enable build cache (`build_cache=True`) when:

- Evaluating 100+ samples where GPU evaluation time dominates

- Running multiple evaluation passes on the same kernel set

- Using local execution mode with multiple GPUs

- Compilation overhead is measurable in overall runtime

Disable build cache when:

- Evaluating <10 samples (overhead outweighs benefit)

- One-off kernel testing or debugging

- Using Modal execution (cache not supported)

- Disk space is constrained or cache directory is on slow storage

### GPU Architecture Selection

- Match target hardware: Set `gpu_arch` to match your evaluation GPU's architecture to enable architecture-specific optimizations

- Multi-architecture support: Include multiple architectures when evaluating across heterogeneous GPU fleet

- Forward compatibility: Newer architectures (e.g., Hopper) can execute binaries compiled for older architectures (e.g., Ampere), but not vice versa

- Modal automatic mapping: Modal handles architecture selection via `gpu_arch_mapping`; users specify GPU type, not architecture

### Cache Management Strategies

- Monitor cache growth: Build cache can consume significant disk space with many problems/samples

- Periodic cleanup: Remove `cache/` directory between major evaluation campaigns

- Clear on kernel modification: Use `clear_cache=True` when iterating on kernel code

- Automatic cleanup on failures: Failed builds are automatically removed; no manual intervention needed

- Timeout adjustment: Increase `config.timeout` if legitimate kernels are timing out during compilation

### Compilation Parallelization Tuning

For CPU pre-compilation (`build_cache=True`):

- `num_cpu_workers=20` (default): Good balance for most systems

- Higher values: If you have many CPU cores and fast storage (NVMe SSD)

- Lower values: If experiencing memory pressure or slow disk I/O

- Formula: `min(cpu_count, num_samples / 10)` provides reasonable heuristic
