This page documents KernelBench's profiling and debugging infrastructure for analyzing kernel performance and behavior. It covers the four available timing methods, PyTorch Profiler integration for inspecting torch.compile output, NVIDIA Nsight Compute integration for hardware-level metrics, and debugging strategies for generated kernels.

For information about evaluation metrics and correctness checking, see Evaluation Metrics [/ScalingIntelligence/KernelBench/7.1-evaluation-metrics]. For information about static validation of generated code, see Static Validation [/ScalingIntelligence/KernelBench/8.2-static-validation].

## Overview

KernelBench provides multiple profiling approaches to understand kernel performance at different levels of granularity:

| | Tool | Granularity | Use Case | Hardware Access Required
| CUDA Event Timing | Device time | Cold cache performance measurement | No
| Triton do_bench | Device time | Adaptive benchmarking | No
| Host Time | Wall-clock | End-to-end latency including overhead | No
| Nsight Python | Hardware counters | SM cycles, tensor ops, memory metrics | Yes (sudo)
| PyTorch Profiler | Operator trace | torch.compile inspection, flamegraphs | No

## CUDA Event Timing

The default timing method used by KernelBench evaluation. Measures device-side execution time using CUDA event markers.

### Key Characteristics

- Cold cache performance: Clears L2 cache before each trial using a 256MB thrash tensor

- Device-side measurement: Records time between CUDA events on the current stream

- Explicit trial control: User specifies exact number of warmup and timing trials

- Stream isolation caveat: Assumes computation occurs on current stream (does not guard against adversarial multi-stream hacks)

### Implementation Details

```

CUDA Event Timing Pipeline: Each trial synchronizes all GPU streams, creates timing events, clears L2 cache, records start event, executes kernel, records end event, synchronizes again, and computes elapsed time in milliseconds.

## Triton do_bench

Adaptive benchmarking using Triton's testing utilities. Automatically determines the number of trials based on time budgets.

### Two Interfaces Available

Interface Version (src/kernelbench/timing.py174-220 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L174-L220]):

- Calls `triton.testing.do_bench()` directly

- Uses fixed time budgets: 25ms warmup, 100ms repetition

- Number of trials computed adaptively based on kernel runtime

- Returns all measured times in a list

- `num_warmup` and `num_trials` parameters ignored (kept for API compatibility)

Implementation Version (src/kernelbench/timing.py223-320 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L223-L320]):

- Reimplements do_bench logic for explicit control

- User specifies exact `num_warmup` and `num_trials`

- Uses Triton's cache clearing mechanism: `triton_runtime.driver.active.clear_cache(cache)`

- Returns list of exactly `num_trials` measurements

### Implementation Details

```

Triton do_bench Variants: The interface version delegates to Triton's do_bench with time budgets, while the implementation version mirrors Triton's logic but gives explicit trial control. Both use Triton's cache clearing which thrashes L2 cache before each measurement.

## Host Time Measurement

Measures wall-clock time from the CPU perspective, capturing end-to-end latency including all overhead.

### Measured Overhead Sources

- Python function call overhead

- CUDA kernel launch latency

- CUDA runtime API overhead

- GPU work across all streams on the device

- OS scheduling and context switching

### Implementation

Uses `time.perf_counter()` for high-resolution CPU timing:

```

The `torch.cuda.synchronize()` call blocks the CPU thread until all kernels on all streams of the device have completed, ensuring the measurement captures all GPU work.

Sources: src/kernelbench/timing.py323-390 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L323-L390]

### When to Use Host Time

- Measuring production deployment latency where host-GPU round-trip matters

- Debugging cases where device time and wall-clock time diverge significantly

- Detecting overhead from Python wrappers or memory transfers

Host time will typically be longer than CUDA event time due to the additional overhead sources.

## Best Practices

### Timing Method Selection

Use this decision matrix:

| | Scenario | Recommended Method | Rationale
| KernelBench evaluation | `cuda_event` | Consistent cold cache measurement, explicit trial control
| Quick benchmarking | `do_bench` | Adaptive trials, no manual tuning needed
| Production latency | `host_time` | Captures real-world E2E overhead
| Detailed analysis | `nsight_python_time` | Hardware counters, root cause analysis
| torch.compile debugging | PyTorch Profiler | Operator-level trace, kernel inspection

### Profiling Workflow

Recommended analysis sequence:

- Initial timing: Use `cuda_event` to establish baseline performance

- Verify consistency: Run `host_time` to check for launch overhead anomalies

- Hardware analysis: Profile with Nsight to identify bottlenecks (memory-bound vs compute-bound)

- Optimization: Based on Nsight metrics, apply targeted optimizations

- Validation: Re-run timing suite to measure improvement

### Common Pitfalls

Insufficient warmup: GPU kernels need warmup for JIT compilation and persistent L2 cache setup. Use at least 3 warmup iterations.

Ignoring variance: Always collect multiple trials (≥10) and report statistics. High variance indicates unstable performance.

Wrong device: Ensure timing functions use the correct GPU device parameter, especially in multi-GPU systems.

Cache effects: Understand whether you're measuring cold cache (realistic for batch processing) or hot cache (optimistic) performance.
