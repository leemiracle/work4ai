## Overview

KernelBench evaluates generated kernels along two orthogonal dimensions: correctness (functional equivalence to PyTorch reference) and performance (wall-clock execution time). The primary benchmark metric, `fast_p`, combines both dimensions to measure the fraction of problems solved with both correctness and speedup exceeding threshold `p`.

All metrics are computed from `KernelExecResult` objects stored in `eval_results.json` files and baseline timing data stored in `results/timing/<hardware>/<baseline>.json`.

## Correctness Metrics

### Compilation Rate

The fraction of kernels that compiled without errors:

```
`compilation_rate = Σ(compiled) / total_problems
`

A kernel is marked `compiled=True` if it successfully loads and executes on the GPU. Compilation failures are captured in `metadata` with error types like `CompileError`, `CudaError`, or `ImportError`.

### Correctness Rate

The fraction of kernels that produce functionally correct outputs, equivalent to `fast_0`:

```
`correctness_rate = Σ(correctness AND compiled) / total_problems
`

Correctness is determined by running `num_correct_trials` (default: 5) with randomized inputs and verifying outputs match the PyTorch reference using `torch.allclose` with precision-dependent tolerances.

| | Precision | rtol | atol
| fp32 | 1e-5 | 1e-5
| fp16 | 1e-3 | 1e-3
| bf16 | 1e-2 | 1e-2

### Runtime Measurement

Execution times are measured using CUDA events for GPU-accurate timing:

```

The system performs:

- Warmup: 3 initial executions (discarded)

- Timing trials: `num_perf_trials` (default: 100) measurements

- Statistical aggregation: mean, std, min, max computed

### Speedup Calculation

Speedup is the ratio of baseline execution time to custom kernel time:

```
`speedup = baseline_time / custom_kernel_time
`

Where:

- `baseline_time` comes from `results/timing/<hardware>/<baseline>.json`

- `custom_kernel_time` is the mean from `runtime_stats`

- Values > 1.0 indicate the custom kernel is faster

- Values < 1.0 indicate slowdown relative to baseline

Example:

- Baseline (PyTorch Eager): 10.5ms

- Custom CUDA kernel: 2.1ms

- Speedup: 10.5 / 2.1 = 5.0x

## Primary Benchmark Metric: fast_p

The `fast_p` metric captures both correctness and performance by computing the fraction of problems that are both correct and have speedup > p:

```

### Common Thresholds

| | Metric | Threshold `p` | Interpretation
| `fast_0` | 0.0 | Correctness rate (any speed)
| `fast_1` | 1.0 | Correct and faster than baseline
| `fast_2` | 2.0 | Correct and at least 2x faster

Higher thresholds make the benchmark more challenging by requiring greater speedups.

## Statistical Metrics

### pass@k

For problems with multiple generated samples, `pass@k` estimates the probability that at least one of `k` samples is correct:

```

This formula is an unbiased estimator derived from HumanEval and accounts for sampling without replacement.

Example:

- Generated 10 samples for a problem

- 3 samples are correct (c=3)

- pass@1 = 0.30 (30% chance random sample is correct)

- pass@5 = 0.83 (83% chance at least 1 of 5 random samples is correct)

### Geometric Mean Speedup

The geometric mean of speedup ratios for correct samples:

```

Geometric mean is preferred over arithmetic mean for speedup ratios because:

- It's symmetric: geomean(2x, 0.5x) = 1.0

- It's not dominated by outliers

- It has clearer physical interpretation for multiplicative quantities

## Interpreting Evaluation Results

### Compilation Failures

When `compiled=False`, the `metadata` field contains diagnostic information:

```

Common error types:

- `SyntaxError`: Python syntax errors in generated code

- `CompileError`: CUDA compilation errors (nvcc)

- `ImportError`: Missing dependencies or CUDA toolkit issues

- `CudaError`: Runtime GPU errors (illegal memory access, etc.)

### Performance Analysis

The `runtime_stats` field provides detailed timing distribution:

```

High standard deviation (>10% of mean) may indicate:

- GPU clock throttling

- Competing GPU workloads

- Non-deterministic kernel behavior

- Insufficient warmup

## Metric Dependencies and Relationships

```

Figure 5: Metric Dependency Graph

Key relationships:

- `fast_0 ≡ correctness_rate` (speedup threshold of 0)

- `fast_1 ≤ fast_0` (stricter threshold reduces score)

- `fast_2 ≤ fast_1 ≤ fast_0` (monotonic in threshold)

- Geometric mean uses only correct samples (`correctness=True`)

## Example: Full Metric Computation

Given evaluation results for 3 problems:

| | Problem | compiled | correctness | runtime (ms) | baseline (ms) | speedup
| 1 | True | True | 2.1 | 10.5 | 5.0x
| 2 | True | False | 8.3 | 5.2 | 0.63x
| 3 | False | False | -1.0 | 8.1 | -0.12x

Computed metrics:

- Compilation rate: 2/3 = 66.7%

- Correctness rate: 1/3 = 33.3%

- fast_0: 1/3 = 33.3% (same as correctness)

- fast_1: 1/3 = 33.3% (problem 1 is correct and >1x)

- fast_2: 1/3 = 33.3% (problem 1 is correct and >2x)

- Geometric mean speedup: 5.0 (only problem 1 is correct)
