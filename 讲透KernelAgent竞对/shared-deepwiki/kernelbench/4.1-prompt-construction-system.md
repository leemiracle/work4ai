This document explains KernelBench's TOML-based prompt construction system, which provides a declarative approach to building prompts for LLM-based kernel generation. The system uses modular template components that can be composed into different prompt strategies (zero-shot, one-shot, few-shot) across multiple kernel backends (CUDA, Triton, CuTe, TileLang).

## System Overview

The prompt construction system separates prompt content from code through a declarative TOML configuration file. This design enables:

- Modular composition: Prompts are assembled from reusable template blocks

- Backend flexibility: Different kernel backends (CUDA, Triton, etc.) share common templates with backend-specific variations

- Learning strategies: Support for zero-shot, one-shot, and few-shot prompting

- Hardware awareness: Optional injection of GPU architecture specifications

- Custom configurations: User-defined prompt compositions for experimentation

The core workflow loads templates from TOML, substitutes context variables (reference code, backend name, etc.), and assembles the final prompt string.

## TOML Configuration Structure

The prompt system is configured in src/prompts/prompts.toml1-214 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/prompts/prompts.toml#L1-L214] The TOML file uses a hierarchical structure with the following top-level sections:

| | Section | Purpose | Example Keys
| `[meta]` | Global configuration | `version`, `default_backend`, `default_precision`
| `[shared]` | Cross-backend templates | `problem_statement`, `instruction`
| `[backends.<name>]` | Backend-specific config | `backends.cuda`, `backends.triton`, `backends.cute`, `backends.tilelang`
| `[options.<name>]` | Prompting strategies | `options.zero_shot`, `options.one_shot`, `options.few_shot`
| `[templates.common]` | Reusable template blocks | `arch_block`, `examples_block`, `precision_note`
| `[templates.hardware]` | GPU-specific templates | `hardware_specs`, `hardware_definitions`, `hardware_best_practices`
| `[precision.<name>]` | Precision configurations | `precision.fp32`, `precision.fp16`, `precision.bf16`
| `[custom_prompts.<key>]` | User-defined compositions | `custom_prompts.custom`

### Prompting Options

Options define prompt composition strategies:

| | Option | Purpose | Components | Example Requirement
| `zero_shot` | No examples, model infers from description | `["problem_statement", "arch_block", "precision_note", "instruction"]` | None
| `one_shot` | Single example demonstration | `["problem_statement", "examples_block", "arch_block", "precision_note", "instruction"]` | `requires_example = "one_shot"`
| `few_shot` | Multiple examples (fallback to one-shot if unavailable) | `["problem_statement", "examples_block", "arch_block", "precision_note", "instruction"]` | `requires_example = "few_shot"`

## Hardware-Aware Prompting

Hardware-aware prompting injects GPU architecture information into prompts. When `include_hardware=True`, the system loads specifications from src/prompts/hardware/gpu_specs.py1-NaN [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/prompts/hardware/gpu_specs.py#L1-LNaN]

### Hardware Template Components

Hardware information is injected through four template blocks:

| | Template | Purpose | Context Variables
| `hardware_header` | Introduction to hardware section | None
| `hardware_specs` | GPU specifications | `gpu_name`, `gpu_architecture`, `gpu_specs_bullets`
| `hardware_definitions` | Architecture concept definitions | `gpu_definitions_bullets`
| `hardware_best_practices` | Optimization guidelines | `gpu_best_practices_bullets`

Insertion Logic

When `include_hardware=True`:

- If `components_override` is None: Hardware blocks are inserted before `arch_block`

- If `components_override` is provided: User must explicitly include hardware components in their custom sequence

## Conclusion

Chain of Thought prompting is a valuable technique in KernelBench for guiding LLMs through the process of generating optimized CUDA kernels. By encouraging step-by-step reasoning, CoT prompting helps models understand the original PyTorch implementation, plan an efficient CUDA implementation strategy, and generate correct, high-performance kernel code. The system supports various CoT examples tailored to different types of neural network operations and can be used with specialized reasoning models from different LLM providers.
