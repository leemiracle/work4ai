## Purpose and Scope

This document details KernelBench's parallel execution infrastructure for scaling workloads across CPU threads, GPU processes, and cloud containers. It covers the implementation of multithreading for LLM API calls, multiprocessing for GPU kernel evaluation, Modal cloud distribution, rate limiting mechanisms, timeout handling, and performance tuning parameters.

For configuration of execution modes (local vs Modal), see Local vs Modal Execution [/ScalingIntelligence/KernelBench/6.2-local-vs-modal-execution]. For the overall configuration system, see Configuration System [/ScalingIntelligence/KernelBench/6.1-configuration-system].

## Multiprocessing for GPU Tasks

### `maybe_multiprocess_cuda` Function

GPU kernel evaluation requires process-level isolation to prevent CUDA state corruption and memory conflicts between concurrent evaluations. The `maybe_multiprocess_cuda` function uses `ProcessPoolExecutor` with the `spawn` start method.

```

Why `spawn` Start Method is Required:

The code explicitly forces `spawn` mode for CUDA compatibility:

```

| | Start Method | Description | CUDA Compatibility
| `fork` | Copies parent process memory (Linux default) | ❌ Causes CUDA state corruption
| `spawn` | Starts fresh Python interpreter | ✅ Clean CUDA context per process
| `forkserver` | Hybrid approach | ⚠️ Not widely tested with CUDA

## Performance Tuning Guidelines

### Parameter Selection Matrix

| | Workload | Parallelism Strategy | Key Parameters | Typical Values
| LLM API Calls | `maybe_multithread` | `num_workers`, `time_interval` | 10-20 workers, 0.1-0.5s interval
| Local GPU Eval | `maybe_multiprocess_cuda` | `num_gpu_devices`, `batch_size` | 1-8 GPUs, batch_size = GPU count

| Modal Cloud Eval | `batch_eval_modal` | `batch_size`, `gpu` type | 10-50 containers, match GPU to workload

### GPU Memory and Batch Sizing

Local Multi-GPU Configuration:

```

Guidelines:

- Start conservatively: Begin with `num_gpu_devices=1` to verify correctness

- Monitor GPU memory: Use `nvidia-smi` to check memory usage per GPU

- Adjust batch size: Increase `num_gpu_devices` if memory utilization < 80%

- Watch for OOM errors: If frequent, reduce batch size or use smaller problems first

Modal Cloud Scaling:

Modal automatically manages container lifecycle, but batch sizing affects cost and throughput:

```

| | Batch Size | Parallel Containers | Throughput | Cost per Hour
| 5 | 5 | ~50 evals/batch | $5-10
| 10 | 10 | ~100 evals/batch | $10-20
| 20 | 20 | ~200 evals/batch | $20-40
| 50 | 50 | ~500 evals/batch | $50-100

Optimal batch size depends on:

- Dataset size: Larger datasets benefit from bigger batches

- GPU availability: Modal queues requests if capacity is reached

- Budget constraints: Larger batches increase concurrent charges
