## Purpose and Scope

The Configuration System provides a structured approach for managing all execution parameters in KernelBench workflows. Built on the `pydra` library, it uses type-safe configuration classes to control dataset access, LLM inference, kernel evaluation, execution environments, and performance measurement. This page documents the configuration classes, their parameters, and lifecycle management.

For information about using configurations in specific workflows, see Generating Kernels with LLMs [/ScalingIntelligence/KernelBench/3.1-generating-kernels-with-llms], Batch Evaluation [/ScalingIntelligence/KernelBench/3.2-batch-evaluation], and Local vs Modal Execution [/ScalingIntelligence/KernelBench/6.2-local-vs-modal-execution].

## Core Configuration Classes

### EvalConfig (Batch Evaluation)

`EvalConfig` controls batch evaluation of pre-generated kernels. It manages dataset access, evaluation parameters, execution environment, and parallelization settings.

Key Fields:

| | Field | Type | Default | Description
| `run_name` | str | REQUIRED | Name of run directory containing generated kernels
| `dataset_src` | str | REQUIRED | `"huggingface"` or `"local"`
| `level` | int | REQUIRED | Problem level (1, 2, or 3)
| `eval_mode` | str | `"local"` | `"local"` or `"modal"` execution
| `gpu` | str | `"A10G"` | GPU type for Modal (`L40S`, `H100`, `A100`, etc.)
| `gpu_arch` | list[str] | `["Ada"]` | CUDA architecture list for compilation
| `num_correct_trials` | int | 5 | Correctness validation trials
| `num_perf_trials` | int | 100 | Performance measurement trials
| `timeout` | int | 180 | Per-sample timeout (seconds)
| `num_gpu_devices` | int | 1 | Number of parallel GPUs
| `backend` | str | `"cuda"` | Kernel DSL: `cuda`, `triton`, `cute`, `tilelang`, `thunderkittens`
| `precision` | str | `"fp32"` | Data type: `fp32`, `fp16`, `bf16`
| `build_cache` | bool | False | Pre-compile kernels on CPU
| `num_cpu_workers` | int | 20 | CPU workers for cache building

### GenerationConfig (Batch Generation)

`GenerationConfig` controls batch kernel generation via LLM APIs. It specifies inference parameters, prompt construction, and parallelization.

Key Fields:

| | Field | Type | Default | Description
| `run_name` | str | REQUIRED | Output directory name
| `dataset_src` | str | REQUIRED | `"huggingface"` or `"local"`
| `level` | int | REQUIRED | Problem level
| `server_type` | str | None | LLM provider (`deepseek`, `google`, etc.)
| `model_name` | str | None | Model identifier
| `temperature` | float | 0.0 | Sampling temperature
| `max_tokens` | int | None | Maximum output tokens
| `num_samples` | int | 1 | Samples per problem for pass@k
| `num_workers` | int | 64 | Parallel API query threads
| `backend` | str | `"cuda"` | Target kernel DSL
| `precision` | str | `"fp32"` | Data type
| `prompt_option` | str | `"one_shot"` | `zero_shot`, `one_shot`, `few_shot`
| `include_hardware_info` | bool | False | Inject GPU specs into prompt
| `check_kernel` | bool | True | Enable static validation

## Summary

The KernelBench configuration system provides:

- Type-safe configuration classes for each workflow type

- Automatic validation of required fields and backend constraints

- Command-line argument parsing via `@pydra.main` decorator

- YAML persistence for reproducibility

- Backend-specific auto-configuration (precision, GPU requirements)

- Flexible execution modes (local GPU, Modal cloud)

All scripts share a consistent configuration pattern, making it easy to understand and modify evaluation parameters across the entire benchmark suite.
