## Purpose and Scope

This page documents how to use scripts/benchmark_eval_analysis.py [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/scripts/benchmark_eval_analysis.py] to analyze evaluation results from KernelBench runs. The analysis script computes aggregate statistics across all evaluated problems, including success rates, speedup metrics, and pass@k scores. This enables comparing the performance of different LLMs, prompting strategies, or configurations on the benchmark.

For information about the evaluation metrics themselves, see page 7.1. For baseline performance data, see page 7.2. For the evaluation pipeline that generates the results, see page 3.2.

## Computed Metrics

The analysis script computes several key metrics to characterize kernel performance:

### Success Rates

Compilation Rate: Percentage of kernels that successfully compile without errors.

```

Correctness Rate: Percentage of kernels that compile and produce correct results across all correctness trials.

```

### Geometric Mean Speed Ratio (GMSR)

Measures average speedup of correct kernels against baseline. Only includes samples that are both compiled and correct.

```

Values > 1.0 indicate the generated kernel is faster than baseline. GMSR is robust to outliers compared to arithmetic mean.

### Fast_p Score

Percentage of problems where the correct kernel achieves at least `p`x speedup over baseline. This metric emphasizes practical speedup thresholds.

```

Standard thresholds: `[0.0, 0.5, 0.8, 1.0, 1.5, 2.0]`

- `fast_0.0`: All correct kernels (equivalent to correctness rate)

- `fast_1.0`: Kernels at least as fast as baseline

- `fast_1.5`: Kernels at least 1.5x faster than baseline

### Pass@k Metrics

When multiple samples per problem are evaluated, pass@k measures the probability that at least one of k samples is correct:

```

This formula provides an unbiased estimate and is numerically stable.

| | Metric | Description | Interpretation
| `pass@1` | Probability first sample is correct | Greedy sampling success rate
| `pass@5` | Probability at least 1 of 5 samples correct | Benefit of sampling multiple solutions
| `pass@10` | Probability at least 1 of 10 samples correct | Upper bound with more samples
```

## Output Format and Interpretation

### Console Output Structure

The analysis script produces formatted output with several sections:

Section 1: Evaluation Summary

```
`------------------------------------------------------------------------
Eval Summary for {run_name}
------------------------------------------------------------------------
Total test cases with Eval Results: 95 out of 100
Successfully compiled: 82
Functionally correct: 68
`

- Shows which problems were evaluated

- Raw counts for compilation and correctness

Section 2: Success Rates

```
`Success rates:
Compilation rate: 82.0%
Correctness rate: 68.0%
`

- Percentages normalized to total problem count

- Correctness rate is the key metric for functional quality

Section 3: Speedup Metrics

```
`Speedup Metrics:
Geometric mean of speedup for correct samples: 1.38
`

- GMSR > 1.0: Average correct kernel is faster than baseline

- GMSR < 1.0: Average correct kernel is slower than baseline

- Computed only over correct samples to avoid skew from failures

Section 4: Fast_p Results

```
`╒════════════════════════╤═════════════════╕
│ Speedup Threshold (p)│ Fast_p Score │
╞════════════════════════╪═════════════════╡
│ 0.0 │ 0.68 │
│ 0.5 │ 0.64 │
│ 0.8 │ 0.61 │
│ 1.0 │ 0.55 │
│ 1.5 │ 0.38 │
│ 2.0 │ 0.22 │
╘════════════════════════╧═════════════════╛
`

- Each row shows fraction of problems achieving >= p speedup

- `fast_1.0` is the most important: fraction matching/beating baseline

- Monotonically decreasing as threshold increases

Section 5: Pass@k Metrics (if available)
Only present when multiple samples per problem were evaluated. Shows metadata and average pass@k values.

### Interpretation Guidelines

Strong Performance Profile:

- Correctness rate: > 70%

- GMSR: > 1.2x

- fast_1.0: > 50% (majority beat baseline)

- fast_1.5: > 30% (substantial speedups common)

Weak Performance Profile:

- Correctness rate: < 40%

- GMSR: < 0.9x (slower on average)

- fast_1.0: < 30% (minority beat baseline)

- fast_1.5: < 10% (few substantial speedups)

Trade-off Analysis:

- High correctness + low GMSR: Generates correct but slow kernels

- Low correctness + high GMSR: Generates fast but unreliable kernels

- Ideal: High correctness (>70%) AND high GMSR (>1.2x)

## Best Practices for Using Optimization Methods

When working with KernelBench and evaluating generated kernels:

- 
For comprehensive evaluation: Compare against multiple optimization strategies to understand performance across different scenarios.

- 
For fair comparisons: Use the most optimized baseline (typically Max Autotune) to ensure generated kernels truly improve upon PyTorch's built-in optimizations.

- 
For development and debugging: Use the No CUDA Graphs variant or Eager mode for more straightforward execution traces and error messages.

- 
For production deployment: Consider the compilation overhead vs. runtime performance trade-off based on your deployment scenario (batch inference vs. online serving).

- 
For hardware-specific optimizations: Use baseline timings specific to your target hardware architecture.

## Common Optimization Patterns

Different optimization strategies excel at different types of operations:

| | Optimization Pattern | Best Optimization Method | Example Operations
| Operation Fusion | Max Autotune | Conv + Bias + Activation
| Memory Layout Optimization | Reduced Overhead | Transposed operations
| Kernel Specialization | Max Autotune | Matrix multiplications
| Parallel Reduction | Max Autotune | Sum, Mean, Max reductions
| Dynamic Shape Handling | No CUDA Graphs | Variable batch size operations
