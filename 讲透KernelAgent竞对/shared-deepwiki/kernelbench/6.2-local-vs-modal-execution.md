## Purpose and Scope

KernelBench supports two execution environments for kernel evaluation: local GPU execution and Modal cloud execution. This page explains the architecture, configuration, and tradeoffs of each approach. For information about the evaluation methodology itself, see Kernel Evaluation System [/ScalingIntelligence/KernelBench/2.1-kernel-evaluation-system]. For parallel execution strategies within each environment, see Parallel Execution Strategies [/ScalingIntelligence/KernelBench/6.3-parallel-execution-strategies].

Local execution runs kernels directly on GPUs attached to the host machine using Python's multiprocessing. Modal execution runs kernels on cloud GPUs via Modal [https://modal.com/]'s serverless infrastructure with container orchestration. The choice between these modes is controlled by the `eval_mode` configuration parameter.

## Configuration Parameters

Both execution modes are configured through the `EvalConfig` class, which uses the `pydra` configuration system. The key parameters are:

| | Parameter | Local Mode | Modal Mode | Description
| `eval_mode` | `"local"` | `"modal"` | Execution environment selector
| `gpu_arch` | Required | Derived from `gpu` | List of CUDA architectures (e.g., `["Ada"]`, `["Hopper"]`)
| `gpu` | Not used | Required | Modal GPU type (e.g., `"L40S"`, `"H100"`, `"A100"`)
| `num_gpu_devices` | Max = `torch.cuda.device_count()` | Max = parallel containers | Number of parallel workers
| `kernel_eval_build_dir` | Build cache directory | Not used (ephemeral) | Kernel compilation cache location
| `timeout` | Per-batch timeout | Per-batch timeout | Maximum evaluation time (seconds)

### Two-Layer Error Handling

Modal execution implements error handling at two levels:

- 
Outer Catch (Infrastructure Level): Lines 525-550 handle Modal infrastructure failures (GPU attachment failures after retries, network issues, container crashes). These create a `KernelExecResult` with `compiled=False` and error metadata.

- 
Inner Catch (Kernel Execution Level): Lines 234-248 handle GPU errors during evaluation. CUDA errors trigger container retirement via `stop_fetching_inputs()`.

This dual approach ensures that infrastructure failures don't block the evaluation pipeline while properly handling GPU-level issues.

## Execution Mode Comparison

| | Aspect | Local Execution | Modal Execution
| Setup | Requires local GPU(s) | Requires Modal account and API token
| GPU Access | Direct via CUDA | Remote via container
| Parallelization | `multiprocessing.Pool` | `spawn()` futures + container pool
| GPU Selection | Uses available `cuda:0`, `cuda:1`, ... | Specify type: `"L40S"`, `"H100"`, etc.
| Build Caching | Persistent in `cache/` directory | Ephemeral (no shared cache)
| Timeout Handling | `apply_async().get(timeout=...)` | Future timeout + retry logic
| Error Recovery | Remove cache, retry manually | Automatic retry (3x) with backoff
| GPU Corruption | Terminate pool, restart | Container retirement via `stop_fetching_inputs()`
| Cost | Free (local hardware) | Pay-per-use GPU time
| Scalability | Limited to local GPU count | Unlimited (cloud pool)
| Hardware Variety | Single architecture | Heterogeneous (Ada, Hopper, Ampere, Turing)
| Network Dependency | None | Requires internet
| State Isolation | Process isolation | Container isolation

### When to Use Local Execution

- You have sufficient local GPU resources

- You want persistent build caching for faster iterations

- You need to avoid cloud costs

- You're debugging compilation issues and want direct access to build artifacts

- Network latency is a concern

### When to Use Modal Execution

- You need specific GPU architectures (H100, L40S) not available locally

- You want massive parallelization across heterogeneous GPUs

- You need to run evaluations without local GPU setup

- You want automatic retry and error handling

- You need isolation from local environment contamination
