This document describes the timing and profiling infrastructure in KernelBench. The system provides multiple timing methodologies for measuring kernel performance and profiling tools for analyzing GPU execution characteristics. These tools are essential for evaluating generated kernels against baseline implementations and detecting performance anomalies.

For information about the evaluation pipeline that uses these timing methods, see Kernel Evaluation System [/ScalingIntelligence/KernelBench/2.1-kernel-evaluation-system]. For details about baseline generation, see Generating Baseline Timings [/ScalingIntelligence/KernelBench/3.4-generating-baseline-timings]. For metrics computed from timing data, see Evaluation Metrics [/ScalingIntelligence/KernelBench/7.1-evaluation-metrics].

## Timing Method Comparison

Each timing method has distinct characteristics that make it suitable for different evaluation scenarios:

| | Method | Precision | Trial Control | Cache | Overhead | Use Case
| `cuda_event` | Device-side | Explicit | Cold | Low | Default evaluation
| `do_bench` | Device-side | Adaptive | Cold | Low | Quick benchmarking
| `do_bench_impl` | Device-side | Explicit | Cold | Low | Reproducible timing
| `host_time` | Host-side | Explicit | Cold | Higher | E2E latency
| `nsight_python_time` | Hardware | Explicit | Cold | Highest | Profiling

Key Differences:

- 
`cuda_event` src/kernelbench/timing.py91-171 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L91-L171]: Uses `torch.cuda.Event` for device-side timing with explicit control over trial count. This is the default method for KernelBench evaluation.

- 
`do_bench` src/kernelbench/timing.py174-221 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L174-L221]: Wraps Triton's `do_bench` with adaptive trial count based on time budgets (warmup=25ms, rep=100ms). Trial count is determined automatically.

- 
`do_bench_impl` src/kernelbench/timing.py223-321 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L223-L321]: Custom implementation mirroring Triton's approach but with explicit trial control for reproducibility.

- 
`host_time` src/kernelbench/timing.py323-390 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L323-L390]: Measures wall-clock time including Python overhead, CUDA launch costs, and synchronization. Captures end-to-end latency.

## Host-Side Timing

The `host_time` method measures wall-clock time from the CPU perspective, capturing end-to-end latency including all overhead.

```

Comparison with cuda_event:

| | Aspect | cuda_event | host_time

| Includes Python overhead | No | Yes
| Includes CUDA launch | No | Yes
| Stream coverage | Current stream only | All streams
| OS scheduling | Not included | Included
| Precision | Higher | Lower

Use Cases:

- Measuring end-to-end latency for production scenarios

- Detecting overhead from Python/CUDA runtime

- Comparing against real-world deployment timing

## Known Limitations and Considerations

### CUDA Stream Assumptions

Current timing methods assume computation occurs on the current stream for the current device. CUDA events only record time between markers on the same stream src/kernelbench/timing.py105-107 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L105-L107]:

```

Adversarial Scenario: A generated kernel could launch work on a separate stream that completes outside the measured window, producing artificially fast times.

Mitigation: Future versions will implement multi-stream detection. See test_eval_adversarial.py [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/test_eval_adversarial.py] for examples of reward hacking patterns.

### Precision Considerations

- All timing methods return times in milliseconds as floating point src/kernelbench/timing.py139 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L139-L139]

- Times are formatted to 3 significant figures in statistics src/kernelbench/timing.py499-502 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/timing.py#L499-L502]

- Hardware counter metrics from Nsight are in native units (nanoseconds for time, cycles for cycles) src/kernelbench/profile.py444-450 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/profile.py#L444-L450]

### Hardware Counter Access

Nsight profiling requires:

- Root/admin privileges for some hardware counters src/kernelbench/profile.py9 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/profile.py#L9-L9]

- NVIDIA Nsight Compute installed src/kernelbench/profile.py49-59 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/profile.py#L49-L59]
