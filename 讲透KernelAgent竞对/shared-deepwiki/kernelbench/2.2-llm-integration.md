## Purpose and Scope

This document describes KernelBench's integration with Large Language Model (LLM) APIs for kernel code generation. It covers the infrastructure for querying various LLM providers, processing responses, and handling provider-specific features. For information about how prompts are constructed before being sent to LLMs, see Prompt Engineering [/ScalingIntelligence/KernelBench/4-prompt-engineering]. For details on how generated kernels are evaluated, see Kernel Evaluation System [/ScalingIntelligence/KernelBench/2.1-kernel-evaluation-system].

## Overview

KernelBench uses the `litellm` library to provide a unified interface to multiple LLM providers (DeepSeek, OpenAI, Anthropic, Google, etc.). The system abstracts LLM interaction into three key stages:

- Inference Server Creation: Configure and instantiate a callable function with provider-specific settings

- Query Execution: Send prompts to the LLM and receive raw responses

- Response Processing: Extract executable code from the LLM's text response

## litellm Foundation

KernelBench uses litellm [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/litellm] as its LLM interface library. This provides:

- Unified API: Single `litellm.completion()` interface for all providers

- Automatic Translation: Maps provider-specific parameter names to a common format

- Error Handling: Standardized error types across providers

- Streaming Support: Optional streaming for long responses

The library is configured via environment variables in a `.env` file. Users must set their API keys following the pattern in `.env.example`.

## Server Presets

The `SERVER_PRESETS` dictionary in `kernelbench.utils` defines default configurations for common LLM providers. Each preset specifies the model name, maximum token limit, and default temperature.

| | Preset Key | Model Name | Max Tokens | Temperature | Use Case
| `deepseek` | `deepseek-chat` | 8192 | 0.0 | General-purpose kernel generation
| `google` | `gemini/gemini-2.5-flash` | 8192 | 0.0 | Fast generation with Google's API
| `openai` | `gpt-4` | 4096 | 0.0 | High-quality generation
| `anthropic` | `claude-3-opus` | 4096 | 0.0 | Complex reasoning tasks

Presets can be overridden by passing explicit values to `create_inference_server_from_presets()`. The system applies presets in this order:

- User-provided explicit values (highest priority)

- Values from `SERVER_PRESETS[server_type]`

- Default values in the Config class (lowest priority)

## Response Processing

The `extract_first_code()` function in `kernelbench.utils` extracts executable code from LLM responses by detecting code blocks. This is necessary because LLMs often wrap code in markdown formatting or include explanatory text.

Detection Strategy:

The function searches for code blocks in this priority order:

- Python code blocks: ````python ... ````

- C++ code blocks: ````cpp ... ````

- Generic code blocks: ```` ... ````

```

The function returns:

- The first matching code block if found

- `None` if no code blocks are detected

This extraction is critical because:

- CUDA kernels are embedded in Python modules using `torch.utils.cpp_extension.load_inline()`

- Triton kernels are Python functions with `@triton.jit` decorators

- Other backends (CuTe, TileLang, ThunderKittens) have similar embedding patterns

## Error Handling

The LLM integration includes several layers of error handling:

### API Call Failures

When `litellm.completion()` fails, the error is caught and logged. Users should check:

- API keys are set correctly in `.env`

- The model name is spelled correctly

- The provider's API is operational

- Rate limits are not exceeded

### Code Extraction Failures

When `extract_first_code()` returns `None`, the system raises an assertion:

```

This indicates the LLM response did not contain any code blocks. Common causes:

- The model refused the request

- The response was truncated due to `max_tokens`

- The prompt was unclear

### Debugging with Verbose Logging

Enable verbose output to see full LLM responses:

```

This logs:

- The full prompt sent to the LLM

- The raw LLM response

- The extracted code (if successful)

- Generation timing information
