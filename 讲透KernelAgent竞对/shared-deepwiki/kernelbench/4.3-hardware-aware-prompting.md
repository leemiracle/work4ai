## Purpose and Scope

Hardware-aware prompting is a technique for injecting GPU-specific specifications and optimization best practices into LLM prompts to guide kernel generation toward hardware-appropriate optimizations. This page explains the hardware template system, available placeholders, and how to construct prompts that leverage hardware context.

For information about the overall prompt construction system, see Prompt Construction System [/ScalingIntelligence/KernelBench/4.1-prompt-construction-system]. For backend-specific prompt customization, see Backend-Specific Prompts [/ScalingIntelligence/KernelBench/4.2-backend-specific-prompts]. For different prompting strategies (zero-shot, one-shot, few-shot), see Prompting Options [/ScalingIntelligence/KernelBench/4.4-prompting-options].

## Hardware Template System

KernelBench provides a modular template system for injecting hardware information into prompts. These templates are defined in the `[templates.hardware]` section of `prompts.toml` and can be selectively included in any prompt configuration.

### Hardware Template Blocks

The system provides four distinct hardware information blocks:

Hardware Header Template

```

This introductory text prepares the LLM to receive hardware-specific context. It signals that optimization decisions should consider the hardware constraints and capabilities that follow.

Hardware Specifications Template

```

This template communicates concrete hardware specifications such as compute capability, memory bandwidth, L2 cache size, shared memory per block, and maximum threads per block. The `{gpu_specs_bullets}` placeholder is populated with bulleted hardware facts.

Hardware Definitions Template

```

This block provides architectural concept definitions (e.g., what warps are, memory hierarchy explanation, compute vs memory bound operations). The `{gpu_definitions_bullets}` placeholder contains educational context about GPU architecture fundamentals.

Hardware Best Practices Template

```

This section offers concrete optimization guidelines such as maximizing occupancy, coalescing memory accesses, avoiding bank conflicts, minimizing warp divergence, and exploiting tensor cores. The `{gpu_best_practices_bullets}` placeholder is filled with actionable optimization advice.

## Template Placeholders

Hardware templates use placeholder syntax for runtime substitution:

| | Placeholder | Description | Example Value
| `{gpu_name}` | GPU model name | "H100", "A100", "L40S"
| `{gpu_architecture}` | NVIDIA architecture generation | "Hopper", "Ampere", "Ada Lovelace"
| `{gpu_specs_bullets}` | Bulleted list of hardware specifications | "• Compute Capability: 9.0
• Memory Bandwidth: 3.35 TB/s
• L2 Cache: 50 MB"
| `{gpu_definitions_bullets}` | Bulleted list of architectural concept definitions | "• Warp: group of 32 threads executing in SIMT
• Shared memory: fast on-chip memory shared by thread block"
| `{gpu_best_practices_bullets}` | Bulleted list of optimization recommendations | "• Maximize occupancy by tuning block size
• Coalesce memory accesses for bandwidth efficiency"

These placeholders are populated based on the `gpu_arch` parameter and any additional hardware information provided at runtime.

## GPU Architecture Targeting

Hardware-aware prompting works in conjunction with the `gpu_arch` parameter, which controls both prompt content and kernel compilation:

### Supported Architectures

| | Architecture | Value | Representative GPUs | CUDA Arch
| Ada Lovelace | `ada` | L40S, L4, RTX 4090 | `sm_89`
| Hopper | `hopper` | H100, H200 | `sm_90a`
| Ampere | `ampere` | A100, A10G | `sm_80`
| Turing | `turing` | T4 | `sm_75`

### Architecture-Specific Optimizations

When hardware information is injected with a specific `gpu_arch`, the prompt can guide the LLM toward architecture-appropriate optimizations:

Hopper-specific (sm_90a):

- Wgmma (Warp Group Matrix Multiply-Accumulate) instructions

- Thread Block Clusters

- Tensor Memory Accelerator (TMA)

- Distributed shared memory

Ampere-specific (sm_80):

- MMA (Matrix Multiply-Accumulate) instructions

- Asynchronous copy from global to shared memory

- L2 cache residency controls

Ada Lovelace-specific (sm_89):

- Enhanced tensor core throughput

- Improved memory compression

## Example: ThunderKittens Hardware Context

For ThunderKittens backend targeting Hopper architecture, hardware-aware prompting might inject:

Hardware Specifications:

- "The GPU is NVIDIA H100, Hopper architecture"

- "Compute Capability: 9.0"

- "Memory Bandwidth: 3.35 TB/s"

- "L2 Cache: 50 MB"

- "Shared Memory per Block: 227 KB (with opt-in)"

Best Practices for ThunderKittens:

- "Use 16x16 tiles (st_bf<16, 16>) for optimal tensor core utilization"

- "Leverage wgmma instructions via kittens::mma operations"

- "Stage data through shared memory for complex layouts"

- "Ensure bf16 dtype for native tensor core support"

This context guides the LLM to generate code compatible with ThunderKittens' tile-based API and Hopper's hardware capabilities, as demonstrated in the example kernel.

## Comparison: Standard vs Hardware-Aware Prompts

| | Aspect | Standard Prompt | Hardware-Aware Prompt
| GPU context | None | Explicit specifications (compute capability, bandwidth, cache)
| Optimization guidance | General best practices | Architecture-specific techniques
| Use case | Baseline evaluation | Maximizing performance on target hardware
| Prompt length | Shorter | Longer (additional hardware context)
| LLM token cost | Lower | Higher
| Generated code specificity | Generic optimizations | Hardware-tuned optimizations

Hardware-aware prompting trades increased prompt length for potentially better-optimized kernel generation, especially when targeting specific GPU architectures with unique features (e.g., Hopper's TMA, Ampere's async copies).

## Usage Guidelines

### When to Use Hardware-Aware Prompting

Recommended:

- When targeting specific GPU architectures in production

- When evaluating LLM's ability to leverage hardware-specific features

- When generating kernels for heterogeneous GPU clusters

- When exploring architecture-specific optimization strategies

Not Recommended:

- For baseline model evaluation (use standard zero/one/few-shot instead)

- When comparing across different hardware without normalization

- When hardware specifications are unknown or variable

### Configuration Best Practices

- 
Consistency: Use the same hardware context for all samples in a benchmark run to ensure fair comparison.

- 
Granularity: Choose the appropriate level of detail:

- `hardware_specs` alone for basic hardware awareness

- Add `hardware_best_practices` for optimization guidance

- Include `hardware_definitions` for educational context (may help smaller models)

- 
Validation: Verify that generated kernels actually exploit the hardware features mentioned in the prompt by profiling with tools like NCU (see Profiling and Debugging [/ScalingIntelligence/KernelBench/8.3-profiling-and-debugging]).

- 
Versioning: Document which hardware context was used when reporting results, as different GPU specifications may lead to different generated code.
