This document explains how KernelBench problems are organized, loaded, and accessed through a unified dataset abstraction layer. It covers the `Problem` dataclass, `BaseDataset` interface, local and HuggingFace implementations, and subset selection mechanisms.

For detailed information about individual problem specifications and difficulty levels, see Dataset Organization [/ScalingIntelligence/KernelBench/5.1-dataset-organization]. For generation workflows that consume these datasets, see Generating Kernels with LLMs [/ScalingIntelligence/KernelBench/3.1-generating-kernels-with-llms]. For evaluation workflows that execute problems, see Kernel Evaluation System [/ScalingIntelligence/KernelBench/2.1-kernel-evaluation-system].

## Dataset Storage Structure

KernelBench problems are stored as individual Python files organized into three difficulty levels. The dataset can be accessed from either local filesystem or HuggingFace through a unified interface.

### File Organization

Directory Structure

```

The `KERNEL_BENCH_PATH` constant in src/kernelbench/dataset.py16-22 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/dataset.py#L16-L22] points to the top-level directory containing all problems. Each problem file follows the naming convention: `{problem_id}_{description}.py`, where `problem_id` is a 1-indexed integer determining the sort order within each level.
```

## Problem Dataclass and Interface

### Problem Dataclass

The `Problem` dataclass at src/kernelbench/dataset.py29-64 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/kernelbench/dataset.py#L29-L64] provides a unified representation of KernelBench problems:

Problem Dataclass Structure

```

| | Attribute | Type | Description
| `problem_id` | `int` | 1-indexed logical ID matching filename prefix
| `name` | `str` | Filename (e.g., `"1_Square_matrix_multiplication_.py"`)
| `code` | `str` | Complete source code of the problem
| `level` | `int` | KernelBench level (1, 2, 3, or custom)
| `path` | `Optional[str]` | Local filesystem path (None for HuggingFace)
| `metadata` | `Optional[dict]` | Reserved for future extensions
| `hash` | `str` (property) | MD5 hash of normalized code
```

```
Hash Properties:

- Functional equivalence: Comments and whitespace don't affect the hash

- Change detection: Any code modification produces a different hash

- Reproducibility: Same code always produces the same hash

- Uniqueness: Different implementations have different hashes

Use Cases:

- Evaluation caching: Detect when problem code has changed

- Result tracking: Ensure consistency across evaluation runs

- Version control: Compare local vs HuggingFace versions

- Deduplication: Identify duplicate problems across datasets
```

```
## Random Input Generation

While problem files define `get_inputs()` functions, the system also provides utilities for generating diverse test inputs during evaluation.

### Distribution Sampling

```

The `rand_mix()` function at src/utils.py489-518 [https://github.com/ScalingIntelligence/KernelBench/blob/2f65279d/src/utils.py#L489-L518] extends PyTorch's random generation capabilities:

| | Mode | Behavior
| `"random"` | Cycles through 5 distributions (normal, uniform, laplace, exponential, lognormal)
| `"normal"`, `"uniform"`, etc. | Samples from specified distribution

This diversity helps test kernel correctness across different input patterns, catching edge cases that uniform random sampling might miss.
