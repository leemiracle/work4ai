# 04 · 量化中的激活函数

> 对应原对话 **Q4：变体和 ReLU 在量化上会有问题吗？** / **Q5：量化时变体如何被 PyTorch / ONNX Runtime 处理？** / **Q6：这些变化是不是量化误差的主要来源？**
>
> 本章是**工程师视角**。把激活函数放回真实部署场景，你会看到：ReLU 是量化优等生，GELU 是噩梦，Leaky ReLU 会偷偷退化。而且——激活函数的妥协**根本不是**量化误差的主因。

---

## 第 0 节：先讲透「量化」到底是什么（数学零基础补课）

### 直觉

量化 = **用更少的比特去近似同一个数**。好比把一张高清照片压成低分辨率缩略图：大体轮廓还在，但细节糊了。

### 数学

浮点数 $x_{\text{float}}$ 与整数 $x_{\text{int}}$ 之间的**线性仿射映射**：

$$
x_{\text{float}} = S \cdot (x_{\text{int}} - Z)
$$

- $S$（**scale，缩放因子**）：一个浮点的「步长」，决定每个整数刻度代表多大。
- $Z$（**zero-point，零点**）：浮点 0 对应的整数值（对齐用）。

**对称量化**（最常用）：$Z=0$，整数范围 $[-127, 127]$（INT8），$S = \frac{\max|x|}{127}$。

**量化**（float → int）：$x_{\text{int}} = \text{round}(x_{\text{float}}/S)$，再 clamp 到范围。
**反量化**（int → float）：$x_{\text{float}} = x_{\text{int}} \cdot S$。

> 关键洞察：$S$ 由**张量里的最大绝对值**决定。这正是后面「离群点」致命的根源。

---

## 第一部分：各激活函数在量化下的处境（Q4）

### ReLU：量化优等生

$$
\text{ReLU}(x)=\max(0,x)
$$

为什么对量化极其友好：

1. **截断负数 → 省动态范围**。ReLU 把负数全砍成 0，非对称量化下宝贵的整数刻度可以**全部分给正半轴**，数值分辨率翻倍。
2. **算子融合几乎免费**。量化后 ReLU 变成一个整数比较 $Y_{\text{int}} = \max(Z, X_{\text{int}})$，通常直接融合进上一层 GEMM/Conv 的 bias-add + requantize 步骤，几乎不占额外时间。
3. **唯一隐患**：正轴**无界**。若出现个别超大正激活（outlier），会拉大 $S$，压垮正常值精度——这正是 ReLU6 存在的理由。

### ReLU6：移动端的量化神器

$$
\text{ReLU6}(x) = \min(\max(0,x),6)
$$

给 ReLU 加上限 6，激活值被锁在 $[0,6]$。99% 的正常激活都在这个范围内，物理上几乎不改变前向结果，却**彻底消灭了离群点对 scale 的污染**——低比特量化的最佳搭档。MobileNet 标配。

### Leaky ReLU：动态范围与精度的拉扯

$$
f(x) = \max(\alpha x, x), \quad \alpha \approx 0.01
$$

痛点：**单一 scale 无法兼顾两端**。

- 正轴保留大数值，负轴乘了 $\alpha=0.01$ 后变成极小数值。
- 为了覆盖正轴大数，$S$ 被拉大，于是那些微小的负数 $\alpha x$ 除以大 $S$ 后四舍五入 → **全部下溢成 0**。
- 结果：**INT8 下 Leaky ReLU 经常事实性退化为普通 ReLU**，丧失「防死神经元」的设计初衷。

### GELU：量化工程师的噩梦

$$
\text{GELU}(x) = x\cdot\Phi(x)
$$

痛点：**高度非线性的超越函数，无法用整数乘加精确求解**。量化是线性仿射变换，而 GELU 包含 $\Phi$（累积分布，含指数积分），两者水火不容。两种妥协方案都很痛（见第二部分）。

## 第二部分：PyTorch / ONNX Runtime 怎么处理这些变体（Q5）

> 核心：如何在**没有浮点单元**的纯整数（INT8/INT4）流水线里，计算非线性甚至含指数的超越函数？框架用三种策略。

### 策略一：图级降级（Dequantize-Compute-Quantize）

**最基础、最安全、也是最慢的兜底方案**。当框架遇到无法整数化的激活函数（早期 GELU、Swish），保持激活函数在**浮点**下执行：

```
前置算子(QLinearConv) --输出INT--> Dequantize(转FP16) --> GELU(浮点) --> Quantize(转回INT) --> 下游
```

- **代价**：打断算子融合，数据在 SRAM/DRAM 间频繁搬运，memory-bound，推理极慢。
- **何时用**：目标硬件 EP 不支持该量化激活算子时的默认回退。

### 策略二：查表法（Look-Up Table, LUT）

**INT8 量化下处理复杂变体最高效的手段**（CPU/NPU/DSP 常用）。

原理：INT8 输入只有 256 种取值（$-128\ldots127$）。**预先**把每个输入对应的 GELU 浮点结果算好、量化成 INT8，存成一张 256 字节的表。运行时只需一次查表（ARM NEON 的 `tbl` 指令、x86 的 `pshufb`），$O(1)$ 完成。

- PyTorch 的 FX 量化、ONNX Runtime 的 `QLinearSigmoid` / 部分后端 `QLinearGelu` 内部就用 LUT。

### 策略三：定点数 + 多项式近似

无法建小 LUT 的场景（INT16 激活、GPU 上追求吞吐），用**纯整数移位与定点运算**逼近。

- **Leaky ReLU**：$x<0$ 时不用浮点 $\alpha$ 乘，而是预计算整数乘子与移位量：$y_{\text{int}} = (x_{\text{int}} \cdot \text{fixed\_multiplier}) \gg \text{shift}$。
- **GELU**：用泰勒展开或切比雪夫多项式，几次纯整数乘加逼近曲线。

### ONNX Runtime Execution Provider 视角（你的工程主场）

鉴于你排查过 `MyProviderExecutionProvider`（EP），这是更底层的视角：

1. **图划分**：图优化器把 `DequantizeLinear → GELU → QuantizeLinear` 序列尝试融合成单个 `QLinearGelu`。
2. **EP 认领（`GetCapability`）**：各 EP 报告自己能否处理 `QLinearGelu`。若 TensorRT 或你的自定义 EP 有对应的整数 LUT kernel 实现 → 认领；否则拒绝。
3. **拒绝则降级**：ORT 退回 CPU EP，或打散融合、用策略一在你的 EP 跑完卷积后倒腾回 CPU 跑浮点 GELU，再量化传回。

> 😤 **开发痛点**：自定义硬件或写 CUTLASS 4-bit GPTQ/W8A8 kernel 时，**算子断图常常出现在复杂激活函数处**——你必须为每个用到的变体手写整数处理逻辑或集成 LUT。这是部署团队的日常噩梦。

## 第三部分：这些变化是量化误差的主要来源吗？（Q6）

**严格说：不是。** 它们是**误差放大器**，不是**源头**。真正的两大主因，在数据进入激活函数**之前**就已注定。

### 主因一：舍入误差 / 离散化信息丢失（绝对主因）

量化的本质是用低比特离散网格去拟合高精度连续空间。把 FP32 压到 INT8（256 态）或 INT4（16 态），大量细微特征被「抹平」，**不可逆**。这种基础舍入误差在每层 GEMM 中累积。

### 主因二：激活值离群点（致命杀手，Transformer 头号痛点）

网络中绝大多数激活分布在 $[-1,1]$，但总有极少数「离群点」（比如突然一个 100）。由于 $S$ 由最大绝对值决定，为了装下 100，$S$ 被迫拉大 → 99% 的正常值除以大 $S$ 取整后**全部变成 0**（underflow）。

> 这就是为什么 **GPTQ / AWQ / SmoothQuant** 等前沿量化算法，核心都在处理权重和激活的**离群点**，而不是优化激活函数本身。

### 那激活函数的近似扮演什么角色？

- **误差放大器**：输入 $x$ 已带量化舍入误差 $\epsilon$，再喂给定点多项式拟合的 GELU，非线性会把 $\epsilon$ 扭曲放大。
- **逻辑断裂发生器**：Leaky ReLU 负半轴下溢成 0，相当于量化**物理性地把网络拓扑改了**（Leaky → ReLU）。在依赖负特征传递的网络（某些 GAN、检测）里，精度会断崖下跌。

### 实验验证（Q4 + Q6 全打包）

```bash
cd experiments && python3 05_quantization_demo.py
```

**① 舍入误差（即使没有激活函数也丢信息）：**

```
1000 个 N(0,1) 样本, INT8 对称量化后
  平均绝对量化误差 = 0.008115
  相对原始标准差比 = 0.79%
```

**② 离群点拉大 scale（头号杀手）：**

```
1000 个样本里塞入 1 个 =100 的离群点
  无离群点时 scale = 0.0323
  有离群点时 scale = 0.7874  (被放大 ~100 倍!)
  有离群点后, 量化为 0 的元素数 = 327/1000  (正常值大批 underflow)
```

**③ Leaky ReLU 退化（激活函数的逻辑断裂）：**

```
LeakyReLU (α=0.01), 输入含离群点 (scale 被拉大到 0.6299):
  浮点结果中 <0 的点数: 972/2000  (负半轴保留微小负值)
  INT8 统一scale后 <0 的点数: 1/2000   (微小负值全四舍五入成 0!)
  负信息存活率: 972 -> 1 (0.1%)
  ==> LeakyReLU 在负半轴事实性退化为普通 ReLU, 丧失设计初衷!
```

> 这组数字极有说服力：**972 个负值，量化后只剩 1 个存活**。Leaky ReLU 防死神经元的设计，在 INT8 下几乎完全失效。

## 总结表：量化友好度速查

| 激活函数 | 量化处理方式 | 主要风险 | 友好度 |
|----------|-------------|---------|--------|
| ReLU | 整数比较，融合进 GEMM epilogue | 正轴无界离群 | ⭐⭐⭐⭐⭐ |
| ReLU6 | 同上 + 有界 | 几乎无 | ⭐⭐⭐⭐⭐+ |
| Leaky/PReLU | 定点乘子 or 退化 | 负轴下溢→退化成 ReLU | ⭐⭐ |
| GELU | LUT / 反量化 / 多项式 | 精度损失 or 带宽浪费 | ⭐⭐ |
| SiLU/Swish | 同 GELU | 同上 | ⭐⭐ |
| SwiGLU | 多重 GEMM + 激活离群 | 融合复杂 | ⭐⭐⭐ |

## 批判性视角

- **不要把锅甩给激活函数**。模型量化掉点时，先查权重/激活的**离群点分布**和**基础舍入误差**，再看激活函数近似。前者是病根，后者是并发症。
- **精度 vs 性能永恒权衡**。极致推理系统里，工程师有时**宁可切回浮点算 GELU**（牺牲带宽），也不愿让非线性算子破坏整体数值稳定性——因为一次精度崩溃比慢 10% 更致命。
- **量化感知训练（QAT）能救一部分**。但那是第 05 章的话题。
