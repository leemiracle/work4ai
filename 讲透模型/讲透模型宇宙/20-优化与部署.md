# 20 · 优化与部署：让模型跑得快又省

> 模型训好了，但一上线：延迟太高用户骂、显存爆了跑不起、成本烧不起。**优化不是可选项，是模型能否真正落地的决定因素。** 本章给你推理优化的决策框架——量化、KV cache、服务化怎么选。深细节指向 `讲透KV Cache`/`讲透GPU与系统级`，本章讲**何时用、为什么、怎么决策**。

## 20.1 优化的不可能三角：成本 · 延迟 · 精度

推理优化永远在三个目标间权衡，**三者不可同时最优化**：

```
           精度(准)
             △
            / \
           /   \
          /     \
         /  你   \
        /  只能   \
       /   选两角  \
      /___________\
  成本(省)──────延迟(快)
```

- 要**快又准** → 成本高（大 GPU、低 batch）；
- 要**省又准** → 延迟高（小 GPU、排队）；
- 要**快又省** → 精度降（量化/小模型）。

**优化的本质**：明确你的场景**最在乎哪个角**，然后牺牲另外两个中较不重要的那个。

| 场景 | 最在乎 | 牺牲 | 典型方案 |
|------|--------|------|---------|
| 实时对话 | 延迟 | 成本/部分精度 | 小模型 + 量化 + 流式 |
| 离线批处理 | 成本 | 延迟 | 大模型 + 高 batch + 量化 |
| 医疗/法律 | 精度 | 成本/延迟 | 大模型 FP16，不量化 |
| 端侧 | 成本+延迟 | 精度 | 极端量化 INT4 + 小模型 |

## 20.2 量化决策

量化（降低权重/激活的数值精度）是**最常用、性价比最高**的优化：

| 精度 | 显存 | 速度 | 精度损失 | 何时用 |
|------|------|------|---------|--------|
| FP16/BF16 | 基准 | 基准 | 0 | 默认，精度优先 |
| INT8 | 1/2 | +30-50% | <1% | 通用场景，性价比之王 |
| INT4 | 1/4 | +50-100% | 1-5% | 显存极紧/端侧 |

**关键认识**（呼应项目铁律）：
- **量化损失在玩具模型上看不出**——必须用真实大模型测。
- **激活量化比权重量化难**：权重静态（可离线量化），激活动态（需校准）。
- **AWQ/GPTQ** 是当前主流权重量化算法；**GGUF** 是 llama.cpp 的端侧格式。

**决策**：
- 上线服务、显存够 → **INT8**（几乎无损）。
- 端侧/消费级 GPU → **INT4**（AWQ/GGUF）。
- 精度敏感（医疗/金融）→ **不量化，FP16**。

## 20.3 KV Cache：长上下文的瓶颈

自回归生成时，每生成一个 token，要重新算所有历史 token 的 attention。**KV cache** 把历史的 Key/Value 存起来复用，避免重算——这是长上下文推理的核心优化。

但 KV cache **随序列长度线性增长显存**：128K 上下文的 KV cache 能吃掉几十 GB。

优化手段（深细节见 `讲透KV Cache`）：
- **PagedAttention**（vLLM）：把 KV cache 像虚拟内存分页管理，碎片降到最低，吞吐翻倍。
- **KV 压缩/剪枝**：丢掉不重要的 KV（如 StreamingLLM 保留首尾）。
- **多查询/分组查询注意力**（MQA/GQA）：共享 KV，从架构层减 KV 量。

**决策**：服务化长上下文 → **必上 vLLM（PagedAttention）**；超长上下文（>32K）→ 考虑 KV 压缩。

## 20.4 服务化选型

模型怎么跑成可调用的服务？三个主流选择：

| 工具 | 定位 | 何时选 |
|------|------|--------|
| **vLLM** | 高吞吐服务 | 生产服务、并发高、要 PagedAttention |
| **SGLang** | 复杂推理/结构化输出 | 需要程序化控制生成、多轮复杂 prompt |
| **Ollama** | 本地最简 | 个人/开发/单机，一键跑 |
| **llama.cpp** | 极致省内存 | CPU/端侧/极端量化 |
| **TGI**（HF）| HF 生态服务 | 和 HF 无缝集成 |

**经验法则**：
- **生产服务 → vLLM**（吞吐/PagedAttention 最强）。
- **本地实验 → Ollama**（一行命令）。
- **CPU/端侧 → llama.cpp**。

## 20.5 部署决策树

```
要在哪跑?
├─ 云端服务 (并发)
│   ├─ 长上下文/高并发 → vLLM + PagedAttention
│   └─ 一般并发 → vLLM/TGI + INT8 量化
├─ 单机/开发
│   └─ Ollama (一行命令跑起来)
└─ 端侧/CPU/无网
    └─ llama.cpp + GGUF INT4 量化
```

**显存不够怎么办**（按代价递增）：
1. 量化（INT8→INT4）；
2. 减小上下文长度；
3. 用更小的模型（70B→14B→7B）；
4. 多卡张量并行（vLLM `--tensor-parallel-size`）；
5. 卸载到 CPU（llama.cpp，慢但能跑）。

## 20.6 成本估算（必须会）

部署前**必须算成本**，否则烧钱：
- **显存** ≈ 参数量 × 精度字节 + KV cache。7B FP16 ≈ 14GB 权重 + KV。
- **单次推理成本** ≈ (输入token + 输出token) × 单价。API 按此计费。
- **吞吐** = 并发 / 平均延迟。决定单卡能服务多少用户。

> 工程纪律：**上线前算清"每用户每次调用的成本"**，对照预算。很多人模型上线才发现"每用户亏钱"。

## 20.7 批判

- **优化有风险**：量化/剪枝会引入隐蔽的精度损失，**必须在真实数据上 benchmark**，不能只看通用 benchmark。
- **延迟不止模型**：网络、序列化、前处理都是瓶颈。模型快但 pipeline 慢，等于没优化。
- **过早优化**：MVP 阶段别优化——**先跑通验证可行，再优化**（呼应 Ch18）。优化是"已验证可行后的降本"，不是"还没跑通就调"。
- **监控缺失**：上线后不监控延迟/错误率/成本，等于裸奔。
