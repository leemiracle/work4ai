# Tile Scheduler and Split-KV Strategy

  This page explains the tile scheduling mechanism and the split-KV approach used in FlashMLA to distribute attention computation across GPU Streaming Multiprocessors (SMs). It details how the library handles long sequences by partitioning them into splits and combining them with numerical stability.

 
## Overview

 FlashMLA uses a two-stage approach for decoding attention when sequences are long or when high SM utilization is required. First, a lightweight metadata kernel calculates the optimal work distribution. Second, the main attention kernels execute either in a single pass or via a split-combine pattern.

## Tile Scheduler Metadata

 The scheduler partitions the total KV cache blocks across `num_sm_parts`. This ensures that even with a small batch size, the workload can be distributed across all available SMs on the GPU.

 
### Metadata Structure

 The scheduling metadata is stored in a `torch.Tensor` of shape `(num_sm_parts, 5)` with `int32` elements [flash_mla/flash_mla_interface.py33-34](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/flash_mla/flash_mla_interface.py#L33-L34) Each entry for an SM part contains:

 
 - **Start Batch Index**: The index of the first request in the batch this SM part handles.
 - **Start Block Index**: The starting tile offset within that request's KV cache.
 - **End Batch Index**: The index of the last request handled.
 - **End Block Index**: The ending tile offset.
 - **Split Index**: The sequence number of the split for the current request.
 
 
### Workload Distribution Logic

 The scheduler attempts to balance the number of KV blocks processed by each SM. If a single request's sequence length $s_k$ is large, it is divided into multiple "splits." Each split is processed by a different SM part, and their results are later merged by the `combine` kernel.

## Split-KV Strategy

 When a sequence is split, the attention kernel cannot compute the final softmax normalization because it only sees a fraction of the KV tokens. FlashMLA uses the "Online Softmax" algorithm extension to handle this.

 
### Stage 1: Partial Computation

 The `flash_fwd_splitkv_mla_kernel` (or architecture-specific variants like those in `csrc/sm90/decode/`) computes partial attention results.

 
 - **Output Accumulator (`o_accum`)**: Stores the weighted sum of values $\sum P_i V_i$ in `float32`.
 - **LSE Accumulator (`lse_accum`)**: Stores the Log-Sum-Exp of the scores for that split.
 
 
### Stage 2: Combine Kernel

 The `flash_fwd_mla_combine_kernel` is responsible for merging the partials. It performs a global reduction across all splits for each query head.

### Numerical Stability in Combination

 The kernel calculates a `global_lse` to normalize the partial sums [csrc/smxx/decode/combine/combine.cu98-100](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/csrc/smxx/decode/combine/combine.cu#L98-L100) It also supports an `attn_sink` parameter. If provided, the final output is scaled by $\frac{\exp(lse)}{\exp(lse) + \exp(attn_sink)}$, which is useful for models utilizing "sink tokens" to prevent attention score explosion [csrc/smxx/decode/combine/combine.cu102-113](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/csrc/smxx/decode/combine/combine.cu#L102-L113)

 
## Seesaw Scheduling (SM90/Hopper)

 For SM90 (Hopper) architectures, FlashMLA implements a "seesaw" scheduling technique to maximize Tensor Core utilization. This is a specialized form of tile scheduling that overlaps CUDA Core operations (like softmax and scaling) with Tensor Core WGMMA instructions.

 
### Register Management

 Because the MLA output matrix ($64 \times 512$) is large, it occupies 32,768 registers. Since an SM has 65,536 registers, only one output matrix can be stored per SM while maintaining high occupancy [docs/20250422-new-kernel-deep-dive.md21-22](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L21-L22)

 The seesaw schedule splits the output matrix into $O_L$ and $O_R$ ($64 \times 256$ each) and interleaves two warpgroups:

 
 - **Warpgroup 0** computes $P_0 = Q K_0^T$ and updates $O_L$.
 - **Warpgroup 1** computes $P_1 = Q K_1^T$ and updates $O_R$.
 - The warpgroups then exchange partial data to update the opposite halves ($O_R$ and $O_L$) using the "seesaw" pattern [docs/20250422-new-kernel-deep-dive.md25-42](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L25-L42)
 
 
### TMA and GEMM Pipelining

 To hide memory latency, the scheduler uses fine-grained TMA copies. For a $64 \times 576$ K-block, it launches 9 separate TMA copies of $64 \times 64$ tiles. GEMM operations begin as soon as the first tile arrives, rather than waiting for the entire block [docs/20250422-new-kernel-deep-dive.md54-55](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L54-L55)
