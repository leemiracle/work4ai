## Purpose and Scope

 This page documents the core performance optimization techniques employed across FlashMLA's CUDA kernels to achieve high utilization of GPU resources. These optimizations enable FlashMLA to reach up to 660 TFlops for dense decoding, 410 TFlops for FP8 sparse decoding, and 640 TFlops for sparse prefill on Hopper architecture GPUs.

 The techniques described here are implemented across multiple kernel variants. For architecture-specific kernel implementations, see [SM90 Kernels (Hopper)](https://deepwiki.com/deepseek-ai/FlashMLA/5.1-sm90-kernels-(hopper)) and [SM100 Kernels (Blackwell)](https://deepwiki.com/deepseek-ai/FlashMLA/5.2-sm100-kernels-(blackwell)). For details on the FP8 KV cache format that motivates some optimizations, see [FP8 KV Cache Format and Quantization](https://deepwiki.com/deepseek-ai/FlashMLA/4.2-fp8-kv-cache-format-and-quantization). For the tile scheduling mechanism that distributes work, see [Tile Scheduler and Split-KV Strategy](https://deepwiki.com/deepseek-ai/FlashMLA/4.3-tile-scheduler-and-split-kv-strategy).

## Compute-Bound vs Memory-Bound Classification

 FlashMLA kernels are designed to handle both compute-bound and memory-bound scenarios, with optimization strategies varying based on the workload characteristics.

 
### Theoretical Analysis

 The kernel performance bottleneck depends on the ratio of floating-point operations (FLOPs) to memory access volume. For a decoding kernel with:

 
 - `h_q`: number of query heads
 - `s_q`: number of query tokens per sequence (1 for standard decoding, >1 for speculative decoding)
 - `s_k`: number of KV tokens per sequence
 - `d_k`: key head dimension (576 for MLA)
 - `d_v`: value head dimension (512 for MLA)
 
 The compute-to-memory ratio is approximately `2 * h_q * s_q`.

 On NVIDIA H800 SXM5:

 
 - Peak memory bandwidth: 3.35 TB/s
 - Practical peak FLOPs (with throttling to ~1600 MHz): 865 TFlops
 - Critical threshold: `h_q * s_q >= 128`
 
 When `h_q = 128` (full query heads without tensor parallelism), the kernel is **compute-bound**, requiring optimization for maximum tensor core utilization. When `h_q * s_q < 128`, the kernel is **memory-bound**, requiring optimization for memory bandwidth. [docs/20250422-new-kernel-deep-dive.md7-16](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L7-L16)

 
### Performance Targets

 
| Configuration | Bottleneck | Optimization Focus | Achieved Performance |
|---|---|---|---|
| h_q=128, s_q=1 | Compute-bound | Tensor Core utilization | 660 TFlops (dense), 410 TFlops (FP8 sparse) |
| h_q=16, s_q=1 | Memory-bound | Memory bandwidth | 3000 GB/s |
| h_q=128, s_q≥2 | Compute-bound | Tensor Core + memory latency | Up to 640 TFlops (sparse prefill) |

## Seesaw Scheduling for Compute-Bound Workloads

 Seesaw scheduling is a warp-level execution strategy that overlaps Tensor Core (MMA) operations with CUDA Core (softmax) operations to maximize hardware utilization in compute-bound scenarios.

 
### The Register Constraint Problem

 The primary challenge is register scarcity. The output matrix from WGMMA (Warp Group Matrix Multiply-Accumulate) operations must remain in registers throughout the mainloop. For a single 64×512 output matrix:

 
 - Register usage: 32,768 32-bit registers
 - Available registers per SM: 65,536 32-bit registers
 - Constraint: Only **one** output matrix can fit per SM [docs/20250422-new-kernel-deep-dive.md21](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L21-L21)
 
 This eliminates traditional ping-pong buffering approaches used in FlashAttention-3, where two complete output matrices alternate between compute and accumulate phases.

 
### Seesaw Schedule Design

 The solution splits the output matrix vertically into two halves (`O_L` and `O_R`, each 64×256) and assigns them to two warpgroups. Each iteration processes **two** KV blocks simultaneously using an interleaved schedule:

## TMA-GEMM Pipelining

 TMA (Tensor Memory Accelerator) - GEMM pipelining addresses memory latency in compute-bound kernels.

 
### Fine-Grained TMA Copy Strategy

 For a 64×576 K block, the kernel launches **9 separate TMA copies**, each transferring a 64×64 sub-block. GEMM operations begin as soon as each individual sub-block arrives in shared memory. ## Crossover Technique with Distributed Shared Memory

 The crossover technique solves the dequantization bottleneck in FP8 sparse decoding kernels.

 
### The Dequantization Bottleneck

 Dequantizing a token's FP8 cache (512 elements) requires ~50 cycles on CUDA cores, while the corresponding MMA operations only take ~34 cycles. This makes the kernel **dequantization-bound**. [docs/20250929-hopper-fp8-sparse-deep-dive.md17-25](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250929-hopper-fp8-sparse-deep-dive.md?plain=1#L17-L25)

 
### Crossover Implementation

 Using **Distributed Shared Memory (DSM)** and CTA clusters of size 2, each CTA dequantizes only **half** of the KV cache and shares it with the other CTA. [docs/20250929-hopper-fp8-sparse-deep-dive.md33-45](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250929-hopper-fp8-sparse-deep-dive.md?plain=1#L33-L45)

## Warp Specialization and Programmatic Launch

 
### Warp Roles

 FlashMLA uses warp specialization to partition tasks within a CTA:

 
 - **Load Warp**: Manages TMA copies and asynchronous barriers. [docs/20250422-new-kernel-deep-dive.md42-46](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L42-L46)
 - **MMA Warpgroups**: Execute WGMMA instructions using seesaw scheduling. [docs/20250422-new-kernel-deep-dive.md40](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L40-L40)
 - **Compute Warps**: Perform softmax and LSE reductions on CUDA cores. [docs/20250422-new-kernel-deep-dive.md42](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L42-L42)
 
 
### Programmatic Dependent Launch

 FlashMLA uses `cudaLaunchDeviceV2` to overlap the `splitkv_mla` and `combine` kernels, eliminating CPU-GPU round-trip latency. [docs/20250422-new-kernel-deep-dive.md60](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250422-new-kernel-deep-dive.md?plain=1#L60-L60)
