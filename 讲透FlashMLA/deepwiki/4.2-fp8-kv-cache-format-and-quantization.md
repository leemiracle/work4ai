## Purpose and Scope

 This document describes the FP8 KV cache memory format used by FlashMLA for efficient storage and computation during the decode phase. It covers the memory layout, quantization scheme, tile-based scaling strategy, and the dequantization process performed inside CUDA kernels. For information about how the FP8 cache is used during sparse decoding operations, see [Sparse Attention Implementation](https://deepwiki.com/deepseek-ai/FlashMLA/4.5-sparse-attention-implementation). For SM90-specific kernel implementation details, see [SM90 Kernels (Hopper)](https://deepwiki.com/deepseek-ai/FlashMLA/5.1-sm90-kernels-(hopper)).

## Overview

 FlashMLA uses FP8 quantization for KV cache storage to reduce memory footprint while maintaining accuracy. The system supports two primary cache layouts optimized for different model configurations:

 
 - **V32_FP8Sparse**: For DeepSeek-V3.2 models with `head_dim_k=576`, `head_dim_v=512`.
 - **MODEL1_FP8Sparse**: For alternative configurations with `head_dim_k=512`.
 
 Both layouts use **tile-level quantization** with fine-grained scale factors to preserve numerical accuracy while achieving significant memory savings. The quantization is applied only to the NoPE (non-positional encoding) components, while RoPE (rotary positional encoding) components remain in higher precision (bfloat16) to avoid accuracy degradation.

 **Sources:** [README.md115-124](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/README.md?plain=1#L115-L124) [tests/quant.py6-15](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/tests/quant.py#L6-L15) [docs/20250929-hopper-fp8-sparse-deep-dive.md7-11](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250929-hopper-fp8-sparse-deep-dive.md?plain=1#L7-L11)

## Memory Layout per Token

 
### V32_FP8Sparse Layout (656 Bytes per Token)

 This layout is used for DeepSeek-V3.2 models and stores each token's KV cache in exactly 656 bytes:

 
```

```

 
| Component | Offset | Size | Data Type | Description |
|---|---|---|---|---|
| Quantized NoPE | 0 | 512 bytes | float8_e4m3fn | Quantized non-positional values (4 tiles of 128 elements each) |
| Scale Factors | 512 | 16 bytes | float32[4] | One scale factor per 128-element tile |
| RoPE Part | 528 | 128 bytes | bfloat16[64] | Unquantized rotary positional encoding values |

### MODEL1_FP8Sparse Layout (576 Bytes per Token)

 This layout is used for models with `head_dim_k=512` and features a different memory arrangement:

 
```

```

 
| Component | Byte Range | Size | Data Type | Description |
|---|---|---|---|---|
| Quantized NoPE | 0 to 448×block_size | 448 bytes/token | float8_e4m3fn | 7 tiles of 64 elements each |
| RoPE Part | 448×block_size to 576×block_size | 128 bytes/token | bfloat16[64] | Unquantized RoPE values |
| Scale Factors | End of block | 7 bytes/token | float8_e8m0fnu[7] | Compact power-of-2 scales |

 **Note:** MODEL1 layout pads each block to a 576-byte boundary for alignment optimization.

## Hardware Dequantization Bottleneck

 On H800 GPUs, the multi-step type conversion process creates a performance bottleneck because the architecture cannot directly cast `float8_e4m3` to `bfloat16` [docs/20250929-hopper-fp8-sparse-deep-dive.md19-23](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250929-hopper-fp8-sparse-deep-dive.md?plain=1#L19-L23)

 
### Cycle Analysis for H800

 
| Operation | Cycles per 512 elements | Calculation |
|---|---|---|
| float8_e4m3 → half | ~8 | (1/64) × 512 |
| half → float32 | ~8 | (1/64) × 512 |
| float32 → bfloat16 | ~32 | (1/16) × 512 |
| Scale multiplication | ~2 | (1/256) × 512 |
| Total Dequantization | ~50 | - |
| MMA operations | ~34 | 64×(576+512)×2 / 4096 |

 This analysis reveals that without optimization, the kernel would be **dequantization-bound** rather than compute-bound. The crossover technique (see [Kernel Performance Optimizations](https://deepwiki.com/deepseek-ai/FlashMLA/4.4-kernel-performance-optimizations)) addresses this by using Distributed Shared Memory (DSM) to share dequantized data between CTAs [docs/20250929-hopper-fp8-sparse-deep-dive.md27-46](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250929-hopper-fp8-sparse-deep-dive.md?plain=1#L27-L46)

## Conversion Utilities

 The `tests/quant.py` module provides utility functions for converting between formats:

 **`quantize_k_cache`** [tests/quant.py20-78](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/tests/quant.py#L20-L78):

 
 - Input: `(num_blocks, block_size, h_k, d)` tensor in original dtype (bfloat16/float16).
 - Output: `(num_blocks, block_size, 1, bytes_per_token)` tensor as float8_e4m3fn view.
 - Handles both `V32_FP8Sparse` and `MODEL1_FP8Sparse` layouts.
 
 **`dequantize_k_cache`** [tests/quant.py81-123](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/tests/quant.py#L81-L123):

 
 - Reconstructs original values by applying scales per tile.
 - Used primarily for correctness validation in tests.

## Memory Savings Analysis

 
### Storage Comparison (DeepSeek-V3.2)

 
| Configuration | Original (BF16) | FP8 (V32) | Compression Ratio | Memory Saved |
|---|---|---|---|---|
| Per token | 1152 bytes | 656 bytes | 1.76× | 496 bytes (43%) |
| 128K context | ~8.7 GiB | ~4.9 GiB | 1.76× | ~3.8 GiB |

 The FP8 format enables a **43% reduction** in KV cache memory footprint, which is critical for 128K context lengths where a single request otherwise requires 8.72 GiB of VRAM [docs/20250929-hopper-fp8-sparse-deep-dive.md3](https://github.com/deepseek-ai/FlashMLA/blob/15f13e50/docs/20250929-hopper-fp8-sparse-deep-dive.md?plain=1#L3-L3)
