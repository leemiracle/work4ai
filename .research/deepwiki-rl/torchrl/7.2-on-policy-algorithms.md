This document covers on-policy reinforcement learning algorithms in TorchRL: PPO (Proximal Policy Optimization), A2C (Advantage Actor-Critic), and REINFORCE. These algorithms update policies using trajectories collected from the current policy, distinguishing them from off-policy methods that can use historical data.

On-policy algorithms share common features: advantage computation (typically GAE), entropy bonuses for exploration, and actor-critic architectures. TorchRL's implementation provides configurable clipping mechanisms, flexible value estimation, and efficient functional programming support.

For off-policy algorithms, see Off-Policy Algorithms. For base loss module features, see Loss Module Architecture. For value estimation details, see Value Estimators.

On-policy algorithms in TorchRL follow the `LossModule` base class pattern and integrate with the value estimation system for advantage computation. The primary distinction is the use of current policy data for updates.

#### ClipPPO vs KLPENPPO

TorchRL provides two PPO variants:

ClipPPOLoss torchrl/objectives/ppo.py703-850:

  - Clips importance sampling ratio: clip(ratio, 1-ε, 1+ε)

  - Default clip_epsilon=0.2

  - More stable, easier to tune

  - Most commonly used in practice

KLPENPPOLoss torchrl/objectives/ppo.py853-1047:

  - Adds adaptive KL penalty: loss + β * KL(π_old || π_new)

  - Dynamically adjusts β based on observed KL divergence

  - Target KL can be specified via dtarg

  - Better theoretical properties but more hyperparameters

#### A2C vs PPO

Key Differences:

| Feature | A2C | PPO |
| Policy Update | Direct gradient | Clipped importance sampling |
| Update Stability | Less stable | More stable |
| Sample Efficiency | Lower | Higher (multiple epochs) |
| Hyperparameters | Fewer | More (clip_epsilon, epochs) |
| Theoretical Guarantee | Policy improvement | Conservative policy improvement |

A2C is simpler and faster per update but requires more samples. PPO's clipping mechanism provides better stability and enables multiple optimization passes over the same data.

#### REINFORCE Characteristics

Advantages:

  - Simple implementation

  - Unbiased gradient estimates

  - Works with any differentiable policy

  - No bootstrapping required

Limitations:

  - High variance (Monte Carlo estimates)

  - Sample inefficient

  - Requires full episode trajectories

  - Slow learning without variance reduction

The value function baseline (critic) is crucial for reducing variance. Without it, REINFORCE has impractically high gradient variance.

Sources: torchrl/objectives/reinforce.py40-380

#### GAE (Generalized Advantage Estimation)

GAE is the standard advantage estimator for on-policy algorithms. It exponentially weights TD errors to balance bias and variance:

```
A_t^GAE = Σ(γλ)^l * δ_{t+l}
where δ_t = r_t + γV(s_{t+1}) - V(s_t)
```

GAE Parameters:

  - gamma : Discount factor (typically 0.99)

  - lmbda : GAE parameter λ (typically 0.95) λ=0: TD(0), high bias, low variance λ=1: Monte Carlo, low bias, high variance

Code Entity: `GAE` class in torchrl/objectives/value/advantages.py685-875

The `GAE` estimator:

  - Computes TD errors: δ_t = r_t + γV(s_{t+1}) - V(s_t)

  - Exponentially weights them: (γλ)^l

  - Outputs both advantage and value_target keys

#### Entropy Decay Strategies

Common practices for entropy coefficient scheduling:

  - Fixed: Constant coefficient throughout training

  - Linear decay: Reduce from initial to final value

  - Exponential decay: Geometric reduction over time

TorchRL doesn't enforce a specific schedule; users can modify `loss_module.entropy_coeff` during training as needed.

### Key Features and Utilities

#### Reduction and Output Management

Loss modules support configurable output reduction (`"none"`, `"mean"`, `"sum"`) and selective output key filtering through `select_out_keys()`. This enables flexible integration with different training frameworks and logging systems.

#### Compatibility Modes

Loss modules can operate in two modes:

  - TensorDict Mode : Full integration with TorchRL's tensordict ecosystem

  - Non-TensorDict Mode : Direct tensor input/output for compatibility with existing codebases

The non-tensordict mode automatically handles input key mapping and returns tuples of tensors in a predictable order.

#### Performance Optimizations

The system includes several performance optimizations:

  - vmap support for vectorized operations across ensemble members

  - Functional programming to enable meta-learning and parameter sharing

  - Efficient target network updates with minimal memory overhead

  - Lazy parameter initialization for memory efficiency
