### Purpose and Scope

This document covers exploration modules in TorchRL that add stochastic behavior to deterministic policies for improved learning in reinforcement learning environments. Exploration strategies modify action selection during training to encourage discovery of better policies while maintaining the ability to switch to deterministic evaluation mode.

For policy network architectures themselves, see Actors, Critics, and Value Networks. For probability distributions used in stochastic policies, see Probability Distributions.

Sources: torchrl/modules/tensordict_module/exploration.py1-608 torchrl/modules/models/exploration.py1-500

### Architecture Overview

Exploration modules in TorchRL follow a modular design pattern where exploration behavior is added as a composable layer that wraps or follows a base policy. All exploration modules inherit from `TensorDictModuleBase` and operate on `TensorDict` inputs, allowing them to be seamlessly integrated into policy chains using `TensorDictSequential`.

```

```

Exploration Module Taxonomy:

| Type | Modules | Modifies | Use Case |
| Action-Space | EGreedyModule , OrnsteinUhlenbeckProcessModule , AdditiveGaussianModule | Actions after policy | Post-processing continuous/discrete actions |
| Parameter-Space | NoisyLinear , NoisyLazyLinear | Network weights | Built into network architecture |
| State-Dependent | gSDEModule , LazygSDEModule | Actions based on state | Smooth, structured exploration |
| Dropout-Based | ConsistentDropoutModule | Network activations | Ensemble-like exploration |

### Action-Space Exploration: Epsilon-Greedy

#### EGreedyModule

`EGreedyModule` implements epsilon-greedy exploration for discrete and continuous action spaces. With probability `eps`, it replaces the policy's action with a random sample from the action spec. The epsilon value anneals from `eps_init` to `eps_end` over `annealing_num_steps`.

```

```

Key Implementation Details:

  - Action Masking Support : When action_mask_key is provided, random actions respect the mask by calling spec.update_mask(action_mask) before sampling

  - Spec Expansion : Automatically expands unbatched specs to match batched action shapes for parallel environments

  - Exploration Type Gating : Only applies randomization when exploration_type() returns ExplorationType.RANDOM

### Action-Space Exploration: Ornstein-Uhlenbeck Process

#### OrnsteinUhlenbeckProcessModule

`OrnsteinUhlenbeckProcessModule` adds temporally-correlated noise to continuous actions using the Ornstein-Uhlenbeck process. This creates "structured" exploration where actions are smoothly varying rather than independently noisy at each timestep.

OU Process Equation:

The noise evolves according to:

```
noise_t = noise_{t-1} + θ(μ - noise_{t-1})dt + σ_t√(dt)W
```

where:

  - θ (theta): mean reversion rate (default: 0.15)

  - μ (mu): long-term mean (default: 0.0)

  - σ_t : time-varying standard deviation

  - W : Gaussian white noise

```

```

State Tracking: OU requires maintaining noise state across timesteps. The module reads and writes:

  - _ou_prev_noise : previous noise value (shape: [batch, action_dim] )

  - _ou_steps : step counter for sigma annealing

  - is_init : reset flag indicating trajectory start

Critical Usage Requirement: The environment must be wrapped with `InitTracker` to provide the `is_init` key:

```

```

Factorized Noise: The implementation uses factorized Gaussian noise for computational efficiency, computing outer products of two noise vectors rather than sampling the full noise matrix.

Sources: torchrl/modules/tensordict_module/exploration.py405-608 torchrl/modules/tensordict_module/exploration.py611-695 test/test_exploration.py213-425

### Parameter-Space Exploration: Noisy Networks

#### NoisyLinear and NoisyLazyLinear

Noisy networks add learnable parametric noise directly to network weights, enabling the policy to learn both the mean parameters and the exploration strategy. Presented in "Noisy Networks for Exploration" (Fortunato et al., 2017).

```

```

Key Properties:

  - Learnable Exploration : Both weight_sigma and bias_sigma are learned via gradient descent, allowing the network to adapt exploration magnitude during training

  - Factorized Noise : Uses outer product of two noise vectors ( ε_out and ε_in ) rather than sampling the full weight matrix, reducing computational cost from O(in × out) to O(in + out)

  - Training/Eval Behavior : Training mode : Returns μ + σ ⊙ ε (noisy weights) Eval mode : Returns μ (mean weights only)

  - Noise Reset : Call reset_noise() to resample epsilon values:

```

```

Initialization: Standard deviation initialized as `std_init / sqrt(fan_in)` where `std_init` defaults to 0.1.

Use Case: Ideal for value-based methods (DQN, Rainbow) where the network itself learns when and how much to explore, eliminating the need for separate epsilon schedules.

Sources: torchrl/modules/models/exploration.py29-240 test/test_modules.py346-365

### State-Dependent Exploration: gSDE

#### gSDEModule and LazygSDEModule

Generalized State-Dependent Exploration (gSDE) adds exploration noise that depends on the current state, creating smooth, structured exploration suitable for continuous control. Presented in "Smooth Exploration for Robotic Reinforcement Learning" (Raffin et al., 2020).

```

```

Mathematical Formulation:

Given state `s` and action mean `μ`:

  - Sample noise matrix: ε ~ N(0, I) with shape [action_dim, state_dim]

  - Compute state-dependent noise: noise = (σ ⊙ ε) · s

  - Output action: a = μ + noise

  - Output scale: scale = sqrt(Σ_j (σ_ij · s_j)²) for each action dimension i

Sigma Learning: The `sigma` parameter can be learned (`learn_sigma=True`) or fixed:

```

```


Environment Setup: Must use `gSDENoise` transform to initialize `_eps_gSDE`:

```

```

Advantages:

  - State-dependent noise adapts to different regions of state space

  - Single noise sample per trajectory reduces variance compared to per-step sampling

  - Smooth exploration trajectories better suited for physical systems

### Consistent Dropout for Exploration

#### ConsistentDropoutModule

`ConsistentDropoutModule` applies consistent dropout masks across a trajectory, creating ensemble-like exploration behavior. The same dropout mask is reused until the episode resets, ensuring that the policy remains consistent within an episode while varying between episodes.

```

```

Key Implementation Details:

  - Mask Identification : Each dropout layer gets a unique mask key based on id(self) : f"mask_{id(self)}"

  - Mask Storage : The dropout mask is stored in the TensorDict and automatically propagated through the collector, ensuring consistency

  - Scaling : Masks are pre-scaled by 1/(1-p) during generation, matching PyTorch's dropout convention

  - Initialization Tracking : Requires is_init key in the tensordict (provided by InitTracker transform)

Usage Pattern:

```

```

Monte Carlo Verification: The test suite verifies consistency by:

  - Running the policy on the same input multiple times within an episode

  - Asserting that outputs match (same mask)

  - Resetting and verifying that outputs differ (new mask)

Use Case: Useful for creating diverse policies during exploration while maintaining coherent behavior within each episode. Can be seen as a form of parameter-space exploration where different subnetworks are activated for different episodes.

Sources: torchrl/modules/models/exploration.py428-631 test/test_exploration.py741-869

### Annealing Schedules and Step Management

#### Annealing Implementation

Most exploration modules support linear annealing of their exploration parameter:

```

```

Implementation Detail:

The `step()` method updates exploration parameters in-place:

```

```

Common Pitfall: Forgetting to call `step()` results in constant exploration:

```

```

Frame Counting: The `frames` argument should match the number of environment steps:

  - For unbatched collectors: frames=data.numel()

  - For batched collectors with parallel envs: frames=batch_size * num_envs

  - This ensures annealing rate is consistent regardless of parallelization

#### Module-Specific Annealing

Different modules anneal different parameters:

| Module | Annealed Parameter | Range |
| EGreedyModule | eps (epsilon) | [eps_init → eps_end] (e.g., 1.0 → 0.1) |
| AdditiveGaussianModule | sigma (noise std) | [sigma_init → sigma_end] (e.g., 1.0 → 0.1) |
| OrnsteinUhlenbeckProcessModule | eps (noise scale) | [eps_init → eps_end] (e.g., 1.0 → 0.1) |
|  | sigma (OU process σ) | [sigma → sigma_min] (separate schedule) |

OU Double Annealing: `OrnsteinUhlenbeckProcessModule` has two annealing schedules:

  - eps annealing (controlled by step() )

  - sigma annealing (internal, controlled by n_steps_annealing )
