### Purpose and Scope

This document describes the architecture of TorchRL's replay buffer system, which provides composable, efficient storage and retrieval of experience data for reinforcement learning algorithms. The replay buffer system consists of three primary components—Storage, Sampler, and Writer—that can be mixed and matched to create customized replay buffers for different use cases.

This page focuses on the architectural design and component interactions. For details on specific storage backends, see Advanced Replay Buffer Features. For information on using replay buffers with collectors, see Collector Architecture.

Sources: torchrl/data/replay_buffers/replay_buffers.py92-247 docs/source/reference/data.rst1-59

### Core Design Principle: Composability

The replay buffer system is built on a composable architecture where three independent components work together:

```

```

Composability Design: Each component can be independently selected and configured. For example, you can combine `LazyMemmapStorage` with `PrioritizedSampler` and `RoundRobinWriter`, or use `TensorStorage` with `RandomSampler` and `TensorDictMaxValueWriter`.

#### Storage Backend Comparison

| Storage Type | Use Case | Memory Location | Data Types |
| ListStorage | Arbitrary data, dynamic size | RAM (Python list) | Any Python object |

### Advanced Features

#### Transform Support

Transforms can be applied during sampling:

```

```

Transform Registration: Pass `transform` or `transform_factory` to ReplayBuffer constructor. Transforms are applied in `_sample()` after data retrieval.

Sources: torchrl/data/replay_buffers/replay_buffers.py249-270 torchrl/data/replay_buffers/replay_buffers.py472-500

#### Prefetching

Multi-threaded prefetching improves sampling throughput:

```

```

Configuration: Set `prefetch=N` in constructor to prefetch N batches in background threads.

Sources: torchrl/data/replay_buffers/replay_buffers.py301-320 torchrl/data/replay_buffers/replay_buffers.py1017-1054

#### Dimension Extension

The `dim_extend` parameter controls which dimension is extended when calling `extend()`:

| dim_extend | Interpretation | Use Case |
| 0 (default) | Extend along batch dimension | Individual transitions |
| 1 | Extend along time dimension | Trajectory segments |

Example: With `dim_extend=1` and data of shape `[batch, time]`, each batch element is treated as a separate trajectory.

Sources: torchrl/data/replay_buffers/replay_buffers.py140-160 torchrl/data/replay_buffers/replay_buffers.py517-550

#### Compilability

Setting `compilable=True` makes the replay buffer compatible with `torch.compile()`:

Trade-offs:

  - Enabled : Compatible with compilation, but writer/storage cannot be shared across processes

  - Disabled : Uses multiprocessing-safe primitives (e.g., mp.Value ), but not compilable

Sources: torchrl/data/replay_buffers/replay_buffers.py170-172 torchrl/data/replay_buffers/storages.py617-637 torchrl/data/replay_buffers/writers.py236-278

### Summary

The TorchRL replay buffer architecture provides:

  - Composability : Mix-and-match Storage, Sampler, and Writer components

  - Flexibility : Support for tensors, TensorDicts, and arbitrary Python objects

  - Efficiency : Memory-mapped storage, prefetching, and lazy initialization

  - Persistence : Comprehensive checkpointing with compression and format conversion

  - Extensibility : Clear interfaces for implementing custom components
