## Batched and Parallel Environments

This document describes TorchRL's system for running multiple environment instances simultaneously, either in parallel across processes or serially on a single process. These batched environments enable efficient data collection by executing multiple rollouts concurrently.

Scope: This page covers `BatchedEnvBase`, `ParallelEnv`, `SerialEnv`, and the supporting infrastructure (`EnvCreator`, `EnvMetaData`, buffer management). For information about single environment instances, see EnvBase and Environment Specifications. For environment transforms applied to batched environments, see Environment Transforms. For data collection using batched environments, see Collector Architecture.

### Overview

Batched environments run multiple copies of an environment simultaneously. The key benefit is vectorization: instead of collecting experiences one step at a time from a single environment, you can collect `N` experiences in parallel, dramatically improving data collection throughput.

TorchRL provides two main implementations:

  - ParallelEnv : Runs environments in separate processes with inter-process communication

  - SerialEnv : Runs environments sequentially in a single process (useful for debugging or when multiprocessing overhead is undesirable)

Both inherit from `BatchedEnvBase` and present identical APIs, allowing you to switch between them without code changes.

### BatchedEnvBase Architecture

`BatchedEnvBase` is the abstract base class that defines the interface for batched environments. It handles:

  - Environment Creation : Accepts callables that create environment instances

  - Metadata Management : Collects specs and properties from environments via EnvMetaData

  - Batch Size Management : The environment's batch_size includes the number of workers

  - Memory Strategy : Determines whether to use shared memory, memmap, or standard tensors

  - Buffer Management : Optionally uses pre-allocated buffers for zero-copy communication

#### Key Constructor Parameters

| Parameter | Type | Description |
| num_workers | int | Number of environment instances to run |
| create_env_fn | Callable or list[Callable] | Function(s) to create environments |
| create_env_kwargs | dict or list[dict] | Keyword arguments for environment creation |
| share_individual_td | bool | Whether to return LazyStackedTensorDict (True) or stacked TD (False) |
| shared_memory | bool | Whether to use shared memory for communication |
| use_buffers | bool | Whether to use pre-allocated circular buffers (incompatible with dynamic specs) |
| device | torch.device | Device for the batched environment (can differ from worker devices) |

#### Process Start Methods

`ParallelEnv` supports different multiprocessing start methods via the `mp_start_method` parameter:

  - "spawn" (default on Windows): Most compatible, starts fresh Python interpreter

  - "fork" (default on Unix): Faster startup, copies parent memory

  - "forkserver" : Hybrid approach for safety

### SerialEnv: Sequential Execution

`SerialEnv` runs all environments sequentially in the main process. Despite running serially, it maintains the same API as `ParallelEnv`, making it useful for:

  - Debugging : No multiprocessing complexity

  - Low Worker Counts : When overhead exceeds parallelism benefits

  - Gradient Tracking : Supports backpropagation through environment dynamics

#### Execution Flow

```

```

`SerialEnv` iterates through environments and calls their methods sequentially. Results are collected and stacked into a batched tensordict.

Sources: torchrl/envs/batched_envs.py1874-2119

#### SerialEnv vs ParallelEnv Trade-offs

| Aspect | SerialEnv | ParallelEnv |
| Execution | Sequential, single process | Parallel, multi-process |
| Overhead | Minimal | Process creation, IPC |
| Debugging | Easy (standard debugger) | Hard (multiprocessing) |
| Gradients | Supported | Not supported |
| Throughput | Lower (1 env at a time) | Higher (N envs simultaneously) |
| Memory | Single process memory | N × process memory |

### Memory Management Strategies

`BatchedEnvBase` supports three memory strategies for inter-process communication:

#### 1. Shared Memory ( shared_memory=True )

Tensors are placed in shared memory using `tensor.share_memory_()`. Multiple processes can read/write the same memory without copying.

  - Pros : Zero-copy communication, fastest

  - Cons : Limited to CPU tensors, requires process safety

  - Use case : CPU-based environments with frequent communication

#### 2. Memory-Mapped Storage ( memmap=True )

Tensors are backed by memory-mapped files on disk.

  - Pros : Persists across runs, handles large data

  - Cons : Slower than shared memory, disk I/O overhead

  - Use case : Very large environments, persistent storage needed

#### 3. Standard Memory ( shared_memory=False, memmap=False )

Tensors are copied between processes via pickling.

  - Pros : Most compatible, works with any data

  - Cons : Copying overhead, slower

  - Use case : Environments with complex non-tensor data

### Buffer Management and Dynamic Specs

#### Pre-Allocated Buffers ( use_buffers=True )

When specs are static, TorchRL pre-allocates circular buffers for zero-copy communication:

```

```

The main process allocates a buffer that workers write to directly. This eliminates serialization overhead.

Key Variables:

  - shared_tensordict_parent torchrl/envs/batched_envs.py 746 : Parent's view of shared buffers

  - shared_tensordicts torchrl/envs/batched_envs.py 917 : Per-worker views of their buffer slice

#### Dynamic Specs ( use_buffers=False )

Environments with variable output shapes (e.g., variable-length trajectories) cannot use pre-allocated buffers. In this case:

  - Worker creates a new tensordict for each output

  - Data is serialized and sent via pipe

  - Main process deserializes the data

This is slower but supports arbitrary output shapes.
