This page documents the distributed data collection strategies in TorchRL, specifically the multi-worker collector implementations that enable parallel environment execution across multiple processes. For information about the base collector architecture and single-process collection, see Collector Architecture. For replay buffer coordination with collectors, see ReplayBuffer Architecture.

### Overview

TorchRL provides three main strategies for distributed data collection:

| Collector Class | Collection Mode | Use Case | Result Structure |
| MultiSyncCollector | Synchronous | Deterministic ordering, batch consistency | Stacked or concatenated batches |
| MultiAsyncCollector | Asynchronous | Maximum throughput, independent workers | Concatenated batches |
| Collector (single) | Single process | Simple cases, debugging | Single batch |

All multi-worker collectors inherit from `MultiCollector` base class and coordinate multiple environment instances running in separate processes.

### MultiSyncCollector: Synchronous Collection

`MultiSyncCollector` runs multiple environments in parallel and waits for all workers to complete their collection step before aggregating results. This ensures deterministic batch ordering and consistent timing across workers.

#### Key Parameters

The `MultiSyncCollector` constructor accepts:

  - create_env_fn : List of callable environment factories (one per worker)

  - policy : Policy module to execute in each environment

  - cat_results : "stack" or None - how to aggregate worker outputs "stack" : Creates LazyStackedTensorDict with shape [num_workers, frames_per_worker, ...] None : Concatenates along batch dimension

### Advanced Features

#### Use Buffers Flag

The `use_buffers` parameter controls whether collectors use pre-allocated circular buffers for communication:

  - True (default for static specs): Pre-allocate shared memory tensordicts for efficient communication

  - False (required for dynamic specs): Create new tensordicts for each batch

Dynamic specs (e.g., variable-length observations) require `use_buffers=False` because buffer sizes cannot be predetermined.

Sources: torchrl/envs/batched_envs.py196-199 torchrl/envs/batched_envs.py502-505

#### Split Trajectories

When `split_trajs=True`, collectors track trajectory boundaries and add `("collector", "traj_ids")` and `("collector", "mask")` keys to distinguish complete episodes. This is essential for algorithms that need full trajectories (e.g., Monte Carlo methods).

Sources: test/test_collector.py503-588

#### Seed Management

Multi-worker collectors support two seeding modes via `set_seed(seed, static_seed=...)`:

  - static_seed=True : All workers get the same seed (deterministic across workers)

  - static_seed=False : Each worker gets a derived seed using seed_generator()

Sources: test/test_collector.py674-688

### Comparison Table

| Feature | MultiSyncCollector | MultiAsyncCollector | Collector |
| Parallelism | Multi-process workers | Multi-process workers | Single process |
| Synchronization | Wait for all workers | Asynchronous queue | N/A |
| Batch order | Deterministic | Non-deterministic | Deterministic |
| Throughput | Medium | Highest | Lowest |
| Memory | Shared memory buffers | Queued batches | Single buffer |
| Weight updates | Between batches | Asynchronous | Direct |
| Result structure | Stacked or concat | Concatenated | Single batch |
| Use case | Reproducible training | Maximum throughput | Debugging, simple cases |
