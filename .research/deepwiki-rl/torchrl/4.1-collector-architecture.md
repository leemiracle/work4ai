### Purpose and Scope

This document describes the collector system in TorchRL, which is responsible for gathering environment interactions during reinforcement learning training. Collectors orchestrate the interaction loop between policies and environments, producing batches of experience data (observations, actions, rewards, done flags) in the form of `TensorDict` objects.

For information about environments themselves, see Environments. For replay buffer integration, see Replay Buffers. For the high-level training orchestration that uses collectors, see Trainer System.

### Core Components

#### BaseCollector

`BaseCollector` is the abstract base class that defines the collector interface. All collectors inherit from this class and must implement its core methods.

Key Responsibilities:

  - Define the collection iteration protocol ( __iter__ , __next__ )

  - Manage collector state (frames collected, iteration count)

  - Handle seeding for reproducibility

  - Provide state dict interface for checkpointing

  - Register with environments for bidirectional communication

Essential Attributes:

  - frames_per_batch : Number of frames to collect in each batch

  - total_frames : Total frames to collect before stopping

  - policy : The policy module used to select actions

  - env or create_env_fn : The environment(s) to interact with

  - _frames : Current count of frames collected

  - _iter : Current iteration number

Core Methods:

  - iterator() : Returns an iterator over collected batches

  - set_seed(seed) : Sets the random seed for reproducibility

  - state_dict() / load_state_dict() : Checkpointing interface

  - shutdown() : Cleanup resources (especially for parallel collectors)

Sources: torchrl/collectors/collectors.py8-60 test/test_collector.py598-637

### Single-Environment Collectors

#### Collector (SyncDataCollector)

The `Collector` class handles data collection from a single environment in a synchronous manner. This is the simplest and most commonly used collector.

```

```

Execution Model:

  - Environment runs in the main process/thread

  - Policy is called synchronously to get actions

  - Steps are executed sequentially

  - Batches are accumulated until frames_per_batch is reached

  - Returns control to caller after each batch

Constructor Parameters:

  - create_env_fn : Callable that creates the environment

  - policy : Policy module (can be None for random actions)

  - frames_per_batch : Frames per collection batch

  - total_frames : Total frames to collect

  - device : Device for the collector's operations

  - storing_device : Device where collected data is stored

  - max_frames_per_traj : Maximum frames per trajectory before reset

  - init_random_frames : Number of initial random frames

  - split_trajs : Whether to split trajectories at done flags

Use Cases:

  - Single environment training

  - Debugging and development

  - Environments where parallelization overhead exceeds benefits

  - When gradient computation through collection is needed

Sources: torchrl/collectors/collectors.py30 test/test_collector.py374-398

#### AsyncCollector (aSyncDataCollector)

The `AsyncCollector` executes the collection loop in a background process while the main process can perform other operations (like training).

```

```

Execution Model:

  - Environment runs in a separate process

  - Policy is executed in the worker process

  - Collected data is written to shared memory

  - Main process reads from shared memory asynchronously

  - Enables overlap between data collection and training

Key Differences from Collector:

  - Non-blocking: collection happens in background

  - Shared memory communication between processes

  - Cannot backpropagate through collection

  - Better throughput when training time ≈ collection time

Use Cases:

  - When training and collection times are balanced

  - CPU-bound environments that benefit from dedicated process

  - When maximizing hardware utilization is critical

Sources: torchrl/collectors/collectors.py31 test/test_collector.py776-803

### Multi-Environment Collectors

Multi-environment collectors manage multiple environment instances simultaneously, distributing the `frames_per_batch` across workers.

#### MultiSyncCollector

`MultiSyncCollector` runs multiple environments in parallel and collects data synchronously from all of them.

```

```

Architecture:

  - Each environment runs in its own process

  - Main process coordinates all workers

  - Waits for all workers to complete their batch

  - Results are stacked or concatenated based on cat_results parameter

Constructor Parameters:

  - create_env_fn : List of environment creation functions (one per worker)

  - policy : Shared policy (parameters synchronized across workers)

  - frames_per_batch : Total frames across all workers

  - cat_results : How to combine results ( "stack" or None )

Batch Size Distribution:
With `num_workers=N` and `frames_per_batch=F`:

  - Each worker collects approximately F // N frames

  - Actual distribution: ceil(F / N) per worker to ensure at least F total frames

  - Output shape: [num_workers, frames_per_worker, ...] if stacked

Use Cases:

  - Multiple homogeneous or heterogeneous environments

  - When environments can run independently

  - CPU-bound environments benefiting from parallelization

  - When deterministic synchronization is required

Sources: torchrl/collectors/collectors.py28 test/test_collector.py308-330

#### MultiAsyncCollector

`MultiAsyncCollector` runs multiple environments asynchronously, allowing workers to operate at different speeds.

```

```

Architecture:

  - Workers operate independently without waiting for each other

  - Results are aggregated as they become available

  - Faster workers contribute more to each batch

  - Uses circular buffers for efficient memory usage

Key Differences from MultiSyncCollector:

  - No synchronization barriers between workers

  - Variable contribution per worker based on speed

  - Lower latency for fast environments

  - More complex state management

Use Cases:

  - Heterogeneous environments with different speeds

  - Maximizing throughput when environment speeds vary

  - Large-scale parallel collection

  - When some environments may block or hang

Sources: torchrl/collectors/collectors.py23 test/test_collector.py291-306

### Collector Lifecycle and Operation

#### Initialization and Setup

```

```

Initialization Steps:

  - Environment Creation : The create_env_fn is called to instantiate the environment

  - Collector Registration : env.register_collector(self) establishes bidirectional link

  - Initial Reset : Environment is reset to obtain initial observations

  - Policy Setup : Policy is prepared (moved to device, initialized)

  - Buffer Allocation : If use_buffers=True , preallocated memory buffers are created

  - Seed Setting : If provided, seeds are set for reproducibility

Dynamic Specs and Buffers:

  - If environment has dynamic specs (variable-size tensors), use_buffers defaults to False

  - Static specs enable circular buffer optimization for memory efficiency

  - Dynamic specs require flexible allocation on each step

### Data Flow Through Collectors

#### TensorDict Pipeline

Collectors act as the bridge between environments and training, transforming raw environment interactions into structured batches:

```

```

Data Transformations:

  - Environment Reset : Initial TensorDict with observations and done states

  - Policy Application : Policy adds actions to the TensorDict

  - Environment Step : Returns TensorDict with "next" sub-dictionary

  - MDP Step : step_mdp() promotes "next" data to root for next iteration

  - Batch Accumulation : Multiple steps stacked along time dimension

  - Metadata Addition : Trajectory IDs, step counts added under "collector" key

Key Data Operations:

  - step_mdp() : Transforms tensordict["next"] → next tensordict root

  - Trajectory tracking: Assigns unique IDs to maintain trajectory boundaries

  - Device management: Automatic casting between worker and storage devices

Sources: torchrl/envs/utils.py327-500 test/test_collector.py412-454

#### Frame Accounting

Collectors carefully track frame counts to ensure correct batch sizes:

| Collector Type | Frame Distribution | Batch Size |
| Collector | All frames from single env | frames_per_batch |
| AsyncCollector | All frames from single env (async) | frames_per_batch |
| MultiSyncCollector | ceil(frames_per_batch / num_workers) per worker | ceil(frames_per_batch / num_workers) × num_workers |
| MultiAsyncCollector | Variable per worker (async) | ≥ frames_per_batch |

Handling Episode Boundaries:

  - max_frames_per_traj : Forces reset after N frames in trajectory

  - Automatic reset on done: Environments reset when done=True

  - Partial resets: In batched envs, only done environments reset

  - split_trajs : Optionally marks trajectory boundaries in batch

Sources: test/test_collector.py262-330

#### Policy Integration

Collectors treat policies as black-box `TensorDict` transformers:

```

```

Policy Requirements:

  - Input: TensorDict with observation keys

  - Output: Same TensorDict updated with action keys

  - Can be None : collector uses random actions from env.action_spec

  - Supports stateful policies: Hidden states tracked in TensorDict

Policy Types Supported:

  - Stateless policies: MLP , ConvNet wrapped in Actor

  - Recurrent policies: LSTMModule with hidden state keys

### Advanced Features

#### Split Trajectories

The `split_trajs` parameter enables trajectory-aware batch processing:

Without split_trajs:

```
Batch: [t0, t1, t2, t3, t4, t5, ...]  # Mixed trajectories
```

With split_trajs:

```
Batch: [traj1: [t0, t1, t2], traj2: [t3, t4], traj3: [t5, ...]]
Mask:  [     True,  True,  True,      True,  True,       True, ...]
```

Implementation:

  - Adds ("collector", "mask") key indicating valid steps

  - Pads shorter trajectories to align batch dimensions

  - Essential for algorithms requiring complete episodes (REINFORCE, PPO)

Sources: test/test_collector.py405-454

#### Init Random Frames

The `init_random_frames` parameter enables initial exploration:

Behavior:

  - First N frames collected with random actions (ignoring policy)

  - Useful for pre-filling replay buffers with diverse data

  - After N frames, switches to policy-driven collection

#### Device Management

Collectors support sophisticated device placement strategies:

Three Device Levels:

  - Environment Device : Where env computations occur

  - Policy Device : Where policy computations occur

  - Storage Device : Where collected data is stored

Configuration:

```

```

Automatic Casting:

  - auto_cast_to_device=True : Automatically moves data between devices

  - Non-blocking transfers: Uses non_blocking=True for async GPU transfers

  - Sync primitives: Ensures data consistency across devices

Sources: test/test_env.py586-618 torchrl/envs/batched_envs.py388-494

#### Circular Buffers

When `use_buffers=True` and environments have static specs:

Memory Optimization:

  - Preallocated circular buffers avoid repeated allocation

  - Reduces memory fragmentation and GC pressure

  - Enables zero-copy data transfer in some cases

Trade-offs:

  - Only works with static specs (fixed tensor shapes)

  - Increased memory upfront

  - Complexity in managing buffer indices

Sources: torchrl/envs/batched_envs.py406-494 test/test_collector.py646-726

### Summary

The collector architecture in TorchRL provides a flexible, performant system for gathering environment interactions:

Key Design Principles:

  - Composability : Collectors work with any EnvBase and policy following TensorDict protocol

  - Scalability : From single environments to massive parallel collection

  - Flexibility : Synchronous, asynchronous, single, multi-environment modes

  - Efficiency : Circular buffers, device management, and memory optimization

  - Reproducibility : Full checkpointing and seeding support

Collector Selection Guide:

| Use Case | Recommended Collector |
| Single environment, simple training | Collector |
| Single environment, maximize throughput | AsyncCollector |
| Multiple environments, deterministic sync | MultiSyncCollector |
| Multiple environments, maximize throughput | MultiAsyncCollector |
| Heterogeneous environment speeds | MultiAsyncCollector |
| Need gradients through collection | Collector (only) |
