This document explains the development workflow, project structure, dependency management, code quality tools, and shared utilities for CleanRL. It covers the technical setup required for contributing to the codebase, running tests locally, and understanding the CI/CD pipeline.

### Project Structure

CleanRL follows a flat, single-file implementation philosophy where each algorithm is self-contained. The project structure is organized to minimize abstraction layers while maintaining clear separation between algorithms, utilities, and infrastructure.

```

```

Directory and File Organization:

| Directory/File | Purpose | Key Contents |
| cleanrl/ | Algorithm implementations | Single-file RL algorithms (PPO, DQN, SAC, etc.) |
| cleanrl_utils/ | Shared utilities | buffers.py , tuner.py , resume.py , reproduce.py |
| requirements/ | Exported dependencies | Autogenerated .txt files for various extras |
| pyproject.toml | Package configuration | Dependencies, metadata, and optional extras |
| uv.lock | Dependency lock file | Exact versions for reproducibility |

### Dependency Management with uv

CleanRL uses `uv` as its primary package manager. `uv` provides significantly faster installation times and robust environment management.

### Code Quality and Pre-commit Hooks

To maintain high standards across single-file implementations, CleanRL uses `pre-commit` hooks. These are configured in `.pre-commit-config.yaml` to run formatting, linting, and dependency export checks.

#### Pre-commit Workflow

  - Formatting : Uses black with a line length of 127 .pre-commit-config.yaml 16-22

  - Import Sorting : Uses isort with the black profile .pre-commit-config.yaml 8-15

  - Upgrade : Uses pyupgrade to ensure modern Python syntax .pre-commit-config.yaml 2-7

  - Dependency Sync : Automatically exports requirements/*.txt files using uv-export to ensure they match pyproject.toml .pre-commit-config.yaml 30-76

Sources: .pre-commit-config.yaml1-80 pyproject.toml77-78

### Shared Utilities (cleanrl_utils)

While CleanRL emphasizes single-file algorithms, certain complex or boilerplate components are centralized in `cleanrl_utils` to improve maintainability.

#### Buffers ( buffers.py )

Provides `ReplayBuffer` and `RolloutBuffer` classes adapted from Stable Baselines3.

  - ReplayBuffer : Used for off-policy algorithms like DQN and SAC. It handles sampling transitions (s, a, s', r, d) cleanrl_utils/buffers.py 56-62

  - RolloutBuffer : Used for on-policy algorithms like PPO. It stores additional metadata like advantages and log_probs cleanrl_utils/buffers.py 47-53

#### Hyperparameter Tuning ( tuner.py )

The `Tuner` class integrates with Optuna to automate hyperparameter search.

  - Metric Aggregation : Supports average , median , max , and min across multiple seeds cleanrl_utils/tuner.py 51-61

  - Weights & Biases Integration : Logs tuning progress and best trials directly to W&B cleanrl_utils/tuner.py 75-83

### Development Workflow

#### Coding Conventions

  - Args Dataclass : Every algorithm must use a dataclass for arguments, parsed via tyro cleanrl/sac_atari.py 27-75

  - Layer Initialization : Standardized layer_init function for consistent weight initialization cleanrl/sac_atari.py 102-106

  - Seeding : Manual seeding of random , numpy , and torch is mandatory at the start of the script cleanrl/sac_atari.py 195-199

#### Reproducibility and Resuming

  - Resume : cleanrl_utils/resume.py provides utilities to restart training from checkpoints.

  - Reproduce : cleanrl_utils/reproduce.py helps in re-running experiments with identical seeds and configurations.
