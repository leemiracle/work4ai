# 分词器创新 × 硬件特性 × 端侧 CPU：2024–2026 思考笔记

> **落盘日期**：2026-08-07
> **触发问题**：大语言模型分词器的创新、最新研究、如何结合已有大模型；分词器能否结合硬件特性让向量与后续计算更适合硬件；嵌入式设备/纯端侧 CPU 是怎么做的。
> **信息时效**：2024-01 至 2026-08，所有 arXiv ID 已通过 abs 页或 ACL Anthology 一手核实。
> **元结论**：
> 1. 分词器进入"后 subword 时代"——主流创新分四派：byte-patching（BLT/MegaByte）、tokenizer-free（T-FREE）、tokenizer transfer（ZeTT/MATT/ReTok）、dynamic vocab（VocabTailor）。
> 2. **"硬件感知 tokenization"作为独立研究方向几乎是空白**，但相关工程实践很丰富：vocab 对齐硬件宽度、embedding 量化、pretokenizer 去 regex、embedding table 分层存储。
> 3. **端侧 CPU 的真正瓶颈不是 tokenizer 本身，而是 embedding + LM head 的 memory-bandwidth**。VocabTailor / Liquid AI / FP8 Embedding / Peek2 / NoMAD-Attention 各打一个角度。
> 4. 结合已有大模型有 6 条路径，从 0 训练成本的 ZeTT 到彻底改架构的 "BLT from Llama 3"。

## 一、分词器创新主线（2022→2026 时间轴）

### 1.1 四大流派对照

| 流派 | 代表作 | 核心思想 | 局限 |
|------|--------|---------|------|
| **Subword 增强/迁移** | BPE-continue / ZeTT / MATT / ReTok / Trans-Tok | 保留 subword 范式，但让 vocab 可"换皮/扩展" | 仍是离散 vocab |
| **Byte-level patching** | MegaByte / MambaByte / **BLT** | 不分词，把字节聚合成 patch，主 Transformer 只跑 patch | 训练贵、长 tail 难 |
| **Tokenizer-free（hash/稀疏）** | **T-FREE** / ADE | 不固定 vocab，用 hash 函数把 trigram 映到稀疏激活 | 训练目标改 BCE，需要重训 |
| **Dynamic vocab** | VocabTailor / Vocabulary Reduction | runtime 动态选 vocab 子集 | 任务相关 |

### 1.2 必读里程碑论文（已核实）

| 论文 | 时间 | arXiv | 一句话 |
|------|------|-------|------|
| **MegaByte** (Meta) | NeurIPS 2023 | `2305.07185` | 固定 patch 长度的 byte-level 多尺度 Transformer，sub-quadratic attention，patch=8 |
| **MambaByte** (Cornell) | COLM 2024 | `2401.13660` | 用 SSM 的固定大小 hidden state 处理 byte 序列；speculative decoding with subword drafter 加速 2.6× |
| **T-FREE** (Aleph Alpha) | EMNLP 2024 | `2406.19223` | 用 trigram hash 稀疏激活替代 vocab，**embedding 层压缩 85%**，cross-lingual transfer SOTA |
| **ZeTT** | 2024-05 | `2405.07883` | **超网**输入新 tokenizer 输出对应 embedding，零训练给 LLM 换 tokenizer |
| **Trans-Tokenization "Tweety"** | 2024-08 | `2408.04303` | 跨语言 token 翻译字典（SMT 对齐），低成本迁移 Mistral-7B |
| **ReTok** | 2024-10 | `2410.04335` | 替换输入输出层 + 用原模型均值初始化 + 冻主干微调 |
| **BLT** (Meta) | ACL 2025 | `2412.09871` | **entropy patching**：用小 byte-LM 的熵动态切 patch；8B byte-level 与 Llama 3 持平，**inference FLOPs 减 50%** |
| **VocabTailor** | 2025-08 | `2508.15229` | embedding offload 到 CPU/disk，LM head hybrid 静态+动态选择；vocab 相关内存最多减 99% |
| **MATT** | 2025-10 | `2510.21954` | **Attention Influence Modeling**——用注意力图蒸馏做 tokenizer 迁移，几 GPU 小时恢复大模型性能 |
| **Liquid AI Tokenizer Expansion** | 2026-07 | blog + tech report | In-place BPE 扩 vocab 65K→128K；LFM2.5-8B-A1B 端侧 Hindi/Viet/Thai **per-char 快 2.2–3.7×** |
| **Peek2** | ACL 2026 SRW | anthology `2026.acl-srw.10` | Regex-free 的 cl100k pretokenizer，CPU 微基准 **2.48×**，整体 **1.14×** |
| **Teaching Old Tokenizers New Words** | 2025-12 | `2512.03989` | "continued BPE training"——直接接着原 tokenizer 的 merge 序列继续训；leaf-based 剪枝 |

### 1.3 BLT 为什么是分水岭（核心洞察）

BLT 解决了一个困扰 byte-level 模型 5 年的核心矛盾：

> **传统 BPE**：每个 token 算同样多 FLOPs——但 "th" 和 "xDiffEq)" 显然不应该花一样多算力。
> **MegaByte 固定 patch=8**：粗暴均分，对熵不敏感。
> **BLT 的 entropy patching**：训一个 100M 的小 byte-LM，它对下个 byte 的预测熵 H(xᵢ) 超过阈值就开新 patch。这样**可预测的内容（重复模板、常见词）压成长 patch，不确定内容（数学符号、稀有字符）切成短 patch**。

实测在 Llama 3 同等训练 FLOPs 下，BLT 推理用 **少 50% FLOPs** 拿到持平精度，且对噪声/拼写/低资源语言鲁棒性显著提升。

## 二、如何"结合已有大模型"（6 条路径，按成本递增）

| 路径 | 代表方法 | 训练成本 | 改 vocab 大小 | 适用 |
|------|---------|---------|--------------|------|
| **0 训练：超网预测 embedding** | ZeTT (`2405.07883`) | 0（一次性训超网后任意复用） | 任意 | 想试不同 tokenizer、跨语言 |
| **0 训练：均值初始化** | FVT / ReTok | 微调 ~1B token | 扩或缩 | 加 domain token、补语言 |
| **轻量：in-place BPE 扩展** | Liquid AI Expansion + Continued BPE (`2512.03989`) | Stage1 600B + Stage2 400B（只动新 token 行） | 仅扩 | 已有昂贵 checkpoint，想保留 |
| **中量：embedding relearning** | Embedding Relearning for decoder-only (EACL 2026 `2026.eacl-long.357`) | 冻主干只训 embedding | 扩或缩 | 跨 100 语言同时适配 |
| **重量：attention 蒸馏** | MATT (`2510.21954`) | 几 GPU 小时（warm-up） | 任意 | 想"接近原模型"性能 |
| **彻底：架构迁移** | **"BLT from Llama 3"** (BLT 论文 §6.2) | 全量继续预训练 | 移除 vocab | 想升级到 byte-level |

**BLT 这条路径最值得展开**：Meta 在论文里展示了**把 Llama 3.1 的 global Transformer 权重直接搬进 BLT 架构**，然后用 1/10 学习率继续训。结果在新 tokenizer + byte-level 表征下还能接近原模型 MMLU。这是目前唯一从 token-based 到 byte-based 的"翻新"路径。

**实用建议**：
- 大多数场景，**Continued BPE + FVT 初始化**就够（成本低、bug 少）。
- 想做零样本换 tokenizer 实验 → 用 [`bminixhofer/tokenkit`](https://github.com/bminixhofer/tokenkit)，它把 ZeTT/FVT/cross-tokenizer distill 全打包了。
- **铁律**：所有这些方法都假设"知识主要在 FFN 层"——所以**新 vocab 必须能被旧 embedding 空间线性表达**。否则只能全量重训。

## 三、分词器 + 硬件特性（关键洞察）

**直接说结论**：把"分词器创新"和"硬件特性"显式绑定的论文非常少。这是个**有蓝海的研究方向**。但工程实践中已经在四个层面"隐式地"考虑硬件：

### 3.1 Vocab size 对齐硬件宽度（最关键）

**为什么**：LM head 在 decode 阶段是 `hidden @ W_outᵀ`，每生成一个 token 都要把整个 `[V, d]` 矩阵从内存读到算力单元。如果 V 不是硬件友好值，会有：
- **INT4 packed LM head**：要求 `group_size=128`，所以 `V` 必须是 128 倍数（见 NVIDIA TensorRT-Edge-LLM Vocabulary Reduction 文档）。
- **FP8 Embedding**：per-row block-wise 量化，block size = 128，`scale_shape = [V, d/128]`。
- **SIMD/GEMM tile**：GPU tensor core / CPU AMX 的 tile 通常是 16/32/64，V 是这些数的倍数时 tail 浪费最少。

**实测数据（来自 Liquid AI 2026-07 blog）**：

| Vocab size | M4 Max CPU | M4 Max GPU | Snapdragon 8 Elite |
|-----------|-----------|-----------|---------------------|
| 65K → 128K | per-token 慢 7–10% | 同 | 同 |
| 65K → 256K | — | — | **throughput 掉 37%** |

**关键洞察**：vocab 不是越大越好。**端侧 batch=1 时，decode 是 memory-bandwidth bound**，更大的 vocab 让每步多读一个超大矩阵——**只有当压缩率（每词更少 token）的收益 > per-token 变慢的代价**，才值得扩。

### 3.2 Embedding table 分层存储

**VocabTailor 的核心不对称观察**（这是硬件感知的精华）：
- **Input embedding**：只是查表（lookup，O(1) 计算），**memory-bound 但 compute 几乎为 0** → 可以放 CPU 甚至 disk（LMDB）
- **LM head**：是 `hidden @ Wᵀ` 矩阵乘，**compute-bound** → 必须留 GPU/算力单元

把这两件事解耦：embedding 全量保留只是 offload，LM head 用 hybrid 静态（任务常见 token）+ 动态（runtime 输入相关 token）。**vocab 相关内存最多减 99%**，M1 Pro/Jetson Orin Nano/A100 全部实测 VRAM -22~23%。

### 3.3 Pretokenizer 硬件友好

**Peek2（ACL 2026 SRW）**：cl100k/Llama-3/Qwen-2.5 用的 regex pretokenizer 在端侧 CPU 是隐藏开销。Peek2 用 7×7 查表（Hopcroft DFA 最小化启发）替代 NFA regex，**O(n) 时间、O(1) 空间**，bug-for-bug 兼容，微基准 2.48× 提速。这是少数直接把"tokenizer 实现"和"CPU 指令集"绑定的论文。

### 3.4 算子级硬件感知（虽不直接改 tokenizer 但同思路）

| 工作 | arXiv | 改了什么 | 收益 |
|------|-------|---------|------|
| **NoMAD-Attention** | `2403.01273` | attention score 从 MAD 改为 SIMD register LUT，重排 key cache 为 transposed+blocked 32-key | 长 context **8.3×** |
| **FP8 Embedding (NVIDIA)** | TRT-Edge 文档 | per-row block=128 FP8 E4M3 量化 embedding | embedding 内存 **-50%** |
| **IsoQuant** | `2603.28430` | 把 KV cache 旋转从 3D Clifford 改 4D quaternion，对齐 SIMD float4 | 4.49–4.66× |

**蓝海方向**：让"token embedding 的统计分布"在训练时就适配 INT4/FP8 量化的精度范围（目前都是事后量化，损失大）；或者让 vocab 学习时直接输出"硬件宽度对齐"的稀疏激活模式（T-FREE 已接近，但没考虑硬件）。

## 四、嵌入式 / 端侧 CPU-only

### 4.1 为什么端侧 CPU 是 tokenizer 的"放大镜"

| 模型 | Vocab | Embedding+LM head 占比 |
|------|-------|----------------------|
| Llama 3.2-1B (128K vocab) | 128K | **>20%** 总内存 |
| BLOOM-560M (250K vocab) | 250K | 接近 **50%** |
| Phi-4-mini (200K vocab) | 200K | 比 LLaMA-7B 占比还高 |

模型越小、vocab 越大，比例越惨。1B 模型带 128K vocab ≈ 256MB 仅 embedding+head，4-bit 量化后这部分**通常不量化**（保表征质量），所以可能占总内存 40%。

### 4.2 端侧方案选择矩阵

| 场景 | 推荐方案 | 关键收益 | 实测 |
|------|---------|---------|------|
| **通用 1–3B 部署** | llama.cpp GGUF Q4_K | INT4 weight + 紧凑 vocab | 7B ≈ 4GB RAM，30–40 tok/s（笔记本）|
| **单语言部署** | Vocabulary Trimming (`2024.insights-1.17`) | Unicode script 过滤掉无关语言 token | BLOOM-560M 内存 **-50%** |
| **任务固定输出** | Vocabulary Reduction (TRT-Edge) | logits 只算子集；reduced_vocab 必须 128 倍数 | Qwen3-0.6B 16K 子集 |
| **任务特定 + 内存极紧** | **VocabTailor** (`2508.15229`) | embedding offload CPU/disk + LM head hybrid | M1 Pro **VRAM -22%**, TPOT **+17%** |
| **多语言端侧** | **Liquid AI In-place Expansion** | 65K→128K，新 token embedding 用子 token 均值初始化 | Hindi/Viet/Thai **per-char +2.2–3.7×** |
| **大 vocab 优化** | FP8 Embedding (NVIDIA TRT) | per-row block128 FP8 | embedding 内存 **-50%** |
| **高吞吐 tokenization** | Peek2 pretokenizer | regex-free, O(1) 内存 | 1.14–2.48× |
| **长 context CPU** | NoMAD-Attention (`2403.01273`) | SIMD register LUT 替代 MAD | attention **8.3×** |
| **CPU + 少量 NPU/GPU** | Intel Extension for Transformers | AVX512/VNNI/AMX kernel 自动选 | 比 llama.cpp int4 **1.3–1.6×** |

### 4.3 纯 CPU 推理栈现状（2026）

```
┌─────────────────────────────────────────────────────┐
│ 应用层: MedLocalGPT / Ollama / GPT4All / LM Studio  │
├─────────────────────────────────────────────────────┤
│ 推理引擎: llama.cpp(GGML) | Intel-Transformers |    │
│           MLC-LLM | PowerInfer-2(CPU+少量GPU混合)    │
├─────────────────────────────────────────────────────┤
│ 算子优化: NoMAD-Attention(长ctx) | AVX512/VNNI/AMX  │
│           | int4 GEMM | KV cache 量化                │
├─────────────────────────────────────────────────────┤
│ 模型格式: GGUF(Q4_K等) | SafeTensors | MLX(Apple)   │
├─────────────────────────────────────────────────────┤
│ 硬件: x86(AVX512/VNNI/AMX) | Apple Silicon(NE+GPU) │
│       | ARM NEON | Snapdragon Hexon NPU             │
└─────────────────────────────────────────────────────┘
```

**核心瓶颈**（很重要，决定你怎么优化）：
- **Decode 阶段**（batch=1）是 **memory-bandwidth bound**——CPU 每秒能算的 FLOPs 远多于能从 RAM 搬的字节数。
- 所以优化方向是：**减小模型/激活/KV cache 的字节**，而不是堆 FLOPs。
- **Token 数量直接决定 decode 步数**——这就是为什么 tokenizer 压缩率在端侧是头等大事（每少 10% token ≈ 10% decode 加速）。

### 4.4 实操建议（纯 CPU 端侧部署 checklist）

1. **模型选型**：
   - 1B 级 → Qwen3-0.6B / Gemma-3-1B-it（Q4 ≈ 0.6GB，100 tok/s 笔记本）
   - 3B 级 → Phi-4-mini / Llama-3.2-3B（Q4 ≈ 1.9GB，15–40 tok/s）
   - 7B 级 → Qwen2.5-7B / Mistral-7B（Q4 ≈ 4GB，需要 8GB+ RAM）

2. **Vocab 策略**（按场景）：
   - 英文单语 + 任务固定输出 → **Vocabulary Reduction**（128K → 16K 子集，TRT-Edge 一行命令）
   - 多语言但偏向某几种 → **Vocabulary Trimming**（按 Unicode script 过滤）
   - 内存极紧且任务特定 → **VocabTailor**（embedding offload + 动态 LM head）
   - 多语言全覆盖 → **Liquid AI Expansion**（但要付 600B+400B token 的 fine-tune）

3. **算子优化**：
   - 长 context（>8K）→ 上 NoMAD-Attention（attention 是瓶颈时）
   - 短 context 高并发 → 多进程 + CPU affinity + NUMA pin（MedLocalGPT 的实践）

4. **量化**：
   - 默认 Q4_K_M（4-bit 主权重 + 高精度 outlier）
   - 大 vocab 模型额外开 **FP8 Embedding**（如果用 TensorRT-Edge-LLM）
   - **不要量化 embedding/LM head**——除非用 FP8/VocabTailor 这种专门方案

## 五、关键风险与未解决问题

### 5.1 各方案的失败模式

| 方案 | 主要风险 |
|------|---------|
| ZeTT/FVT 均值初始化 | 对"全新语言/全新字符集"接近随机（chance level） |
| Continued BPE | 必须有原 merge 规则；第三方 tokenizer 不适用 |
| Vocabulary Trimming | 任务泛化性差，换任务得重训 vocab |
| VocabTailor | TTFT 增加（动态加载有 prefill 开销） |
| BLT / byte-level | 训练 FLOPs 仍贵；端侧 CPU 实测几乎没有 |
| T-FREE | 7B 还没释出；目标函数改 BCE 要全量重训 |
| Liquid AI Expansion | fine-tune 成本（600B+400B token）= 几百 GPU 小时 |

### 5.2 学术蓝海（潜在研究方向）

1. **Hardware-aware tokenizer learning**：让 BPE merges 直接学习"产生 SIMD/AMX 友好宽度的 vocab"——目前没人系统做。
2. **Quantization-aware token embedding training**：让 token embedding 训练时就适配 INT4 精度（现在都是事后量化）。
3. **BLT on edge CPU**：BLT 的 entropy patcher 在端侧 CPU 实测完全空白——entropy model 100M 太大？patch 长度分布对 cache 友好？都是好问题。
4. **Cross-tokenizer 知识蒸馏 + 硬件感知 vocab 选择联合优化**：现有 cross-tokenizer distill 不考虑硬件，现有 hardware-aware 不考虑 vocab——结合两者是空白。

## 六、思考延伸（落盘时的二次反思）

### 6.1 这套素材与 work4ai 项目的关系
- work4ai 当前有"讲透基础模型 / 讲透 Transformer / 讲透Prompt / 讲透RAG"等系列，但**没有"分词器"专门系列**——这是讲透承诺的缺口之一。
- 这篇笔记最值得展开成正式章节的部分：
  - **BLT 的 entropy patching 三层讲透**（直觉：熵=不确定→切 patch；数学：H(xᵢ)=−Σp log p；代码：100M byte-LM 跑一遍）
  - **端侧 vocab tradeoff 的实测对比**（用 Liquid AI 的 M4 Max/Snapdragon 数据 + VocabTailor 的 M1 Pro/Jetson 数据做一组可视化）
  - **6 条 tokenizer transfer 路径的统一框架**（按"训练成本 × 是否动 vocab 大小 × 是否动 embedding 空间"三维分类）

### 6.2 与"讲透复用权重"系列的串联潜力
- "讲透复用权重"已经讲了 LoRA/PEFT/继续预训练，但**没讲 tokenizer 层面的复用**——ZeTT/MATT/Continued BPE 正好补这一块。
- 可以在"讲透复用权重"里加一章"tokenizer 也复用：从 ZeTT 到 BLT-from-Llama3"，与现有 PEFT 内容形成"权重复用 ↔ vocab 复用"对照。

### 6.3 与 neo-os / ai-os-dd 项目的潜在交叉
- neo-os 的"事件本体 + commit 蒸馏 world model"如果用 byte-level 表征，BLT 的 entropy patcher 天然适合——entropy 高的 commit 段落正好是"行为变化点"。
- ai-os-dd 的 PagedAttentionCache 与 VocabTailor 的 embedding offload 思路同构（都是分层存储 + 按需加载）。

### 6.4 个人判断
- **3–5 年内主流仍然是 BPE + subword**——BLT/T-FREE 还没成熟到工业替换。
- 但**端侧 CPU/嵌入式场景会率先采用 byte-level 或 tokenizer-free**——因为 vocab 内存占比在那里最痛，而 byte-level 模型在端侧反而有 KV cache 小的优势（如果用 Mamba 风格 SSM）。
- "硬件感知 tokenization" 是**值得关注的论文选题**——目前是真空地带，先到者可以先定义问题。
