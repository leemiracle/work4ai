  The Mega MoE subsystem is a specialized, high-performance architecture within DeepGEMM designed to handle the massive computational and communication demands of Mixture-of-Experts (MoE) models. It focuses on fusing and overlapping multiple operations—Expert Parallel (EP) dispatch, dual linear layers (Linear1 and Linear2), SwiGLU activation, and EP combine—into a single execution pipeline to maximize hardware utilization and minimize latency on Blackwell (SM100) architectures.

 
## 1. Fused Execution Model

 The Mega MoE kernel (`sm100_fp8_fp4_mega_moe_impl`) implements a unified pipeline that avoids intermediate global memory round-trips between the two linear layers of an MoE block.

 
### 1.1 Pipeline Stages

 The kernel fuses the following logical operations:

 
 - **EP-Dispatch**: Pulling tokens assigned to local experts from remote GPUs using one-sided NVLink transfers via `SymBuffer`.
 - **Linear 1**: FP8/FP4 mixed-precision GEMM ($X \times W_1$) where $W_1$ contains both gated and up projections ($2 \times$ `intermediate_hidden`).
 - **Activation**: SwiGLU activation function applied to the output of Linear 1, followed by requantization to FP8.
 - **Linear 2**: FP8/FP4 mixed-precision GEMM ($Activated(X \times W_1) \times W_2$).
 - **EP-Combine**: Gathering and summing expert outputs back to the original token distribution using BF16 precision.
 
 
### 1.2 Warp Specialization

 To achieve high efficiency on the SM100 architecture, the kernel utilizes a three-role warp specialization strategy:

 
 - **Dispatch Warps**: Handle incoming token data pulling and metadata management. The number of threads is defined by `num_dispatch_threads`. [csrc/jit_kernels/heuristics/mega_moe.hpp38](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L38-L38)
 - **MMA Non-Epilogue Warps**: Execute the core matrix multiplication instructions (UMMA) for both Linear 1 and Linear 2. The number of threads is defined by `num_non_epilogue_threads`. [csrc/jit_kernels/heuristics/mega_moe.hpp38](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L38-L38)
 - **Epilogue Warp Groups**: Manage the SwiGLU activation, FP8 requantization, and the final output accumulation/combine. The number of threads is defined by `num_epilogue_threads`. [csrc/jit_kernels/heuristics/mega_moe.hpp38](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L38-L38)

## 2. Symmetric Memory Layout (SymBuffer)

 Mega MoE relies on a symmetric memory abstraction to facilitate efficient cross-GPU communication over NVLink.

 
### 2.1 SymmBuffer and Workspace

 The `SymBuffer` struct provides a unified view of memory across all participating GPUs in an EP group by storing a `base` address and `offsets` for all ranks. [deep_gemm/include/deep_gemm/layout/sym_buffer.cuh10-14](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/layout/sym_buffer.cuh#L10-L14) The `Workspace` struct defines the layout of metadata within this buffer, including grid sync counters, expert send/recv counts, and arrival counts for L1/L2 stages. [deep_gemm/include/deep_gemm/layout/mega_moe.cuh46-64](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/layout/mega_moe.cuh#L46-L64)

 
### 2.2 Data Layout and Pool Management

 
 - **Token Pool**: All local experts share a contiguous token pool to maximize memory efficiency, sized to handle worst-case routing plus alignment padding using `get_num_max_pool_tokens`. [deep_gemm/include/deep_gemm/layout/mega_moe.cuh17-25](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/layout/mega_moe.cuh#L17-L25)
 - **SF Pool**: Scaling factors are stored in a contiguous region. Because SM100 requires 128-element alignment for UTCCP scaling factor operations, the pool is sized using `get_num_sf_ring_tokens`. [deep_gemm/include/deep_gemm/layout/mega_moe.cuh28-31](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/layout/mega_moe.cuh#L28-L31)
 - **Workspace Offsets**: The `Workspace` class provides `get_*_ptr` methods to calculate specific offsets for L1/L2 full/empty counts and source token metadata (`TokenSrcMetadata`) used during combine. [deep_gemm/include/deep_gemm/layout/mega_moe.cuh140-186](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/layout/mega_moe.cuh#L140-L186)

## 3. MegaMoEScheduler and NVLink Overlap

 The `MegaMoEScheduler` coordinates block distribution across SMs and manages the state machine for fused execution. [deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh152-162](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh#L152-L162)

 
### 3.1 Communication Overlap Strategy

 The scheduler manages the arrival of token data via EP-dispatch. It uses counters like `l1_full_count` and `l2_full_count` within the symmetric workspace to track when specific token blocks are ready for computation. [deep_gemm/include/deep_gemm/layout/mega_moe.cuh98-108](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/layout/mega_moe.cuh#L98-L108) This allows the kernel to overlap the NVLink transfer of later tokens with the GEMM computation of tokens that have already arrived.

 
### 3.2 Block Distribution and Warmup

 The scheduler calculates `num_l1_warmup_waves` to ensure no L1 -> L2 deadlock occurs by issuing necessary L1 tasks before starting L2 tasks. [deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh18-45](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh#L18-L45) It tracks tasks using the `TaskInfo` struct, which contains metadata like `BlockPhase` (Linear1, Linear2, etc.), `m_block_idx`, and `pool_block_idx`. [deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh92-134](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/deep_gemm/include/deep_gemm/scheduler/mega_moe.cuh#L92-L134)

## 4. FP8/FP4 Mixed-Precision Pipeline

 Mega MoE implements a compute pipeline optimized for the SM100 architecture's Tensor Memory (TMEM) and UMMA instructions.

 
### 4.1 Compute Flow

 The data flow within a single SM for Mega MoE is as follows:

 
 - **Load A (Tokens)**: FP8 tokens loaded into Shared Memory (Smem) via TMA.
 - **Load B (Weights)**: FP4 weights loaded into Smem.
 - **MMA (Linear 1)**: UMMA instructions compute the product, utilizing scaling factors (SF) for both activations and weights. The configuration `sf_block_m` and `sf_block_n` define the granularity. [csrc/jit_kernels/heuristics/mega_moe.hpp24-25](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L24-L25)
 - **SwiGLU & Requant**: Results in TMEM are processed by epilogue warps to apply SwiGLU and are requantized back to FP8 for the next stage. `smem_amax_reduction` is used for cross-warp amax exchange during requantization. [csrc/jit_kernels/heuristics/mega_moe.hpp153-155](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L153-L155)
 - **MMA (Linear 2)**: The output of the activation serves as the LHS for the second GEMM, producing results for the final EP-combine.

## 5. Parameter Selection and Heuristics

 The `MegaMoEConfig` struct encapsulates all parameters required to tune the kernel for specific MoE shapes. [csrc/jit_kernels/heuristics/mega_moe.hpp18-59](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L18-L59)

 
### 5.1 Heuristic Logic

 DeepGEMM employs a heuristic system to select optimal parameters:

 
 - **Block Size Selection**: `get_block_config_for_mega_moe` selects `block_m` (ranging from 16 to 192) based on `num_expected_tokens_per_expert`. Smaller blocks (e.g., 16 or 32) are used for decoding or small batch sizes, while larger blocks (up to 192) are used for prefill. [csrc/jit_kernels/heuristics/mega_moe.hpp81-102](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L81-L102)
 - **Pipeline Staging**: `get_pipeline_config_for_mega_moe` calculates shared memory requirements for `smem_dispatch_size`, `smem_cd` (C/D output region), and `smem_barriers`. [csrc/jit_kernels/heuristics/mega_moe.hpp131-151](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L131-L151)
 - **SF Block Alignment**: `sf_block_m` and `sf_block_n` are used to manage scaling factor block sizes, which must be 128-aligned for SM100. [csrc/jit_kernels/heuristics/mega_moe.hpp24-25](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit_kernels/heuristics/mega_moe.hpp#L24-L25)
