  The JIT compilation pipeline dynamically generates, compiles, and loads optimized CUDA kernels at runtime. This system allows DeepGEMM to specialize kernels for specific matrix dimensions, data types (FP8/BF16/FP4), and hardware architectures (SM90/SM100) without the overhead of a massive pre-compiled library.

 
## Architecture Overview

 The JIT system is implemented in C++ and follows a layered design that separates code generation, compilation backends, caching, and runtime execution. It supports both the CUDA Driver API and the newer CUDA Runtime API (for CUDA 12.8+) for kernel loading and launching [csrc/jit/handle.hpp48-114](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/handle.hpp#L48-L114)

### Base Compiler Logic

 The `Compiler` base class initializes global state such as the library paths and default compilation flags.

 
 - **Initialization**: Paths for `library_root_path`, `cuda_home`, and `cuobjdump` are set via `prepare_init` [csrc/jit/compiler.hpp30-36](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L30-L36)
 - **Default Flags**: Includes C++ standard (defaulting to C++20 via `DG_JIT_CPP_STANDARD`), register usage levels (`--register-usage-level=10`), and diagnostic suppressions [csrc/jit/compiler.hpp53-57](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L53-L57)

### NVCC vs NVRTC Backends

 DeepGEMM supports two primary backends:

 
 - **NVCCCompiler**: Invokes the `nvcc` binary as an external process. It is used when `DG_JIT_USE_NVRTC` is not set [csrc/jit/compiler.hpp166-185](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L166-L185)
 - **NVRTCCompiler**: Uses the NVRTC library for in-memory compilation. It supports **Precompiled Headers (PCH)** for significantly faster compilation on CUDA 12.8+ by pre-loading standard headers like `cuda_fp8.h` [csrc/jit/compiler.hpp203-215](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L203-L215)

## Caching Strategy

 The system employs a two-tier caching mechanism to minimize startup latency and ensure atomic updates on distributed filesystems.

 
| Cache Tier | Implementation | Key | Storage |
|---|---|---|---|
| L1: Memory | KernelRuntimeCache | dir_path (string) | std::unordered_map csrc/jit/cache.hpp12 |
| L2: Disk | Filesystem | Hash of (Code + Flags + Signature) | ~/.deep_gemm/cache/ csrc/jit/compiler.hpp49-51 |

 
### Atomic Cache Updates

 To avoid race conditions in multi-GPU or multi-node environments, DeepGEMM uses an atomic rename strategy:

 
 - Compile into a unique temporary directory under `tmp/` generated via `get_uuid()` [csrc/jit/compiler.hpp111-112](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L111-L112) [csrc/utils/system.hpp84-98](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/utils/system.hpp#L84-L98)
 - Perform `fsync_dir` to ensure data and directory entries are visible on other nodes in distributed filesystems [csrc/jit/compiler.hpp130](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L130-L130) [csrc/jit/compiler.hpp80-88](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L80-L88)
 - Atomically `rename` the temporary directory to the final cache path. If another process wins the race, the local temporary directory is safely removed [csrc/jit/compiler.hpp135-143](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L135-L143)

## Kernel Runtime and Loading

 Once a `.cubin` file is available, the `KernelRuntime` class handles the transition from a file on disk to an executable kernel handle.

 
### Symbol Discovery

 Because generated kernels may have mangled names or include helper functions, `KernelRuntime` identifies the correct entry point:

 
 - **Library Enumeration**: On CUDA 12.4+, it uses `cuLibraryEnumerateKernels` to find the kernel [csrc/jit/handle.hpp123-153](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/handle.hpp#L123-L153)
 - **Legacy Symbol Parsing**: For older drivers, it parses the output of `cuobjdump -symbols`, filtering out internal symbols like `vprintf`, `__instantiate_kernel`, or `__assertfail` to find the unique entry point [csrc/jit/kernel_runtime.hpp56-79](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/kernel_runtime.hpp#L56-L79)

## SASS Disassembly and Inspection

 DeepGEMM provides built-in support for inspecting the low-level machine code (SASS) generated by the compiler. This is critical for performance tuning.

 
 - **`Compiler::disassemble`**: Invokes `cuobjdump --dump-sass` on a `.cubin` file to produce a `.sass` text file [csrc/jit/compiler.hpp151-161](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L151-L161)
 - **Environment Controls**: 
 - `DG_JIT_DUMP_SASS`: Triggers disassembly after compilation [csrc/jit/compiler.hpp124-127](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L124-L127)
 - `DG_JIT_DUMP_ASM` or `DG_JIT_DUMP_PTX`: Triggers PTX generation during the compilation phase [csrc/jit/compiler.hpp116-118](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/compiler.hpp#L116-L118)

## Device Runtime Context

 The `DeviceRuntime` class provides the JIT pipeline with hardware-specific information and manages shared resources like the cuBLASLt handle.

 
 - **Architecture Detection**: Detects compute capability (e.g., SM90, SM100) via `cudaGetDeviceProperties` [csrc/jit/device_runtime.hpp72-81](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/device_runtime.hpp#L72-L81)
 - **SM and L2 Info**: Tracks the number of multiprocessors (`num_sms`) and L2 cache size to inform kernel heuristics [csrc/jit/device_runtime.hpp108-116](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/device_runtime.hpp#L108-L116)
 - **Programmatic Dependent Launch (PDL)**: Manages the `enable_pdl` state, which allows kernels to launch with `cudaLaunchAttributeProgrammaticStreamSerialization` (on Driver API) or `cudaLaunchAttributeProgrammaticStreamSerializationAllowed` (on Runtime API) for optimized scheduling [csrc/jit/device_runtime.hpp127-133](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/device_runtime.hpp#L127-L133) [csrc/jit/handle.hpp101-106](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/handle.hpp#L101-L106)
 - **cuBLASLt Management**: Maintains a `cublasLtHandle_t` and a 32MB workspace tensor, with options to use PyTorch-managed handles via `DG_USE_PYTORCH_CUBLASLT_HANDLE` [csrc/jit/device_runtime.hpp20-49](https://github.com/deepseek-ai/DeepGEMM/blob/559d79fb/csrc/jit/device_runtime.hpp#L20-L49)
