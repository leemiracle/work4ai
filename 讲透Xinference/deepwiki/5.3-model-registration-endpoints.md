## Purpose and Scope

 This page documents the RESTful API endpoints for registering custom models in Xinference. These endpoints allow users to dynamically add new model definitions without modifying source code or restarting the server. Custom models are validated, stored, and automatically integrated with the appropriate backend engines.

 For information about launching registered models, see [Model Management Endpoints](https://deepwiki.com/xorbitsai/inference/5.1-model-management-endpoints). For details on model specification schemas, see [Model Specifications and Schemas](https://deepwiki.com/xorbitsai/inference/8.2-model-specifications-and-schemas). For custom model registration via Python client, see [Client Interfaces](https://deepwiki.com/xorbitsai/inference/6-client-interfaces).

 
## Overview

 The model registration system enables users to extend Xinference's model catalog at runtime. Registration endpoints support all model types (LLM, embedding, image, audio, rerank, video) and validate custom models against compatibility requirements before storing them in memory or persisting them to disk.

 Starting from `v0.14.0`, users can also directly launch existing models by passing a `model_path` to the launch interface if the `model_family` is already built-in, eliminating the need for manual registration [doc/source/models/custom.rst9-13](https://github.com/xorbitsai/inference/blob/d97e0970/doc/source/models/custom.rst#L9-L13)

## API Endpoints

 
### Endpoint Summary

 
| Endpoint | Method | Purpose |
|---|---|---|
| /v1/model_registrations/{type} | POST | Register a new custom model |
| /v1/model_registrations/{type} | GET | List all model registrations of a type |
| /v1/model_registrations/{type}/{model_name} | GET | Get details of a specific registration |
| /v1/model_registrations/{type}/{model_name} | DELETE | Unregister a custom model |

 The `{type}` parameter accepts: `LLM`, `embedding`, `image`, `audio`, `rerank`, `video`, `flexible` [doc/source/models/custom.rst84-290](https://github.com/xorbitsai/inference/blob/d97e0970/doc/source/models/custom.rst#L84-L290)

 
### POST /v1/model_registrations/{type}

 Registers a new custom model. The model definition is validated and stored either in memory only or persisted to disk.

 **Request Body Schema:** `RegisterModelRequest` [xinference/api/schemas/requests.py121-124](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/api/schemas/requests.py#L121-L124)

 
```

```

 **Parameters:**

 
 - `model` (string, required): JSON-serialized model family definition.
 - `persist` (boolean, optional): If `true`, saves the model to `XINFERENCE_MODEL_DIR/v2/{type}/` for automatic loading on restart [xinference/model/llm/__init__.py111-129](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/__init__.py#L111-L129)
 
 
### GET /v1/model_registrations/{type}

 Lists all model registrations of the specified type. For example, for embedding models, it calls `get_user_defined_embeddings()` which interacts with the `RegistryManager` [xinference/model/embedding/custom.py72-76](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/custom.py#L72-L76)

 
### DELETE /v1/model_registrations/{type}/{model_name}

 Unregisters a custom model. For embedding models, this calls `unregister_embedding()`, which removes the model from the `RegistryManager` and deletes the engine configurations from `EMBEDDING_ENGINES` [xinference/model/embedding/custom.py86-91](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/custom.py#L86-L91)

## Validation and Persistence

 
### Registry Manager and Persistence

 Xinference uses a `ModelRegistry` base class for each model type to manage custom definitions. For example, `EmbeddingModelRegistry` manages `UD_EMBEDDINGS` [xinference/model/embedding/custom.py32-41](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/custom.py#L32-L41)

 When Xinference starts, it performs a migration and loads persisted models from the file system:

 
 - Calls `migrate_from_v1_to_v2()` [xinference/model/embedding/__init__.py52-55](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/__init__.py#L52-L55)
 - Iterates through `XINFERENCE_MODEL_DIR/v2/{type}/` [xinference/model/embedding/__init__.py57-60](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/__init__.py#L57-L60)
 - Parses JSON files into the appropriate `Custom...ModelFamilyV2` class [xinference/model/embedding/__init__.py64-66](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/__init__.py#L64-L66)
 - Registers the model with `persist=False` (since it is already on disk) [xinference/model/embedding/__init__.py67](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/__init__.py#L67-L67)
 
 
### Model Virtual Environments

 Starting from `v2.0`, virtual environments are enabled by default (`XINFERENCE_ENABLE_VIRTUAL_ENV=1`) [doc/source/models/virtualenv.rst61-66](https://github.com/xorbitsai/inference/blob/d97e0970/doc/source/models/virtualenv.rst#L61-L66) When a custom model is registered, the system can define a `virtualenv` configuration to isolate dependencies like specific versions of `transformers` [doc/source/models/virtualenv.rst13-21](https://github.com/xorbitsai/inference/blob/d97e0970/doc/source/models/virtualenv.rst#L13-L21)

 **Storage Path for Virtual Envs (v2.0+):** `XINFERENCE_HOME/virtualenv/v4/{model_name}/{model_engine}/{python_version}` [doc/source/models/virtualenv.rst124](https://github.com/xorbitsai/inference/blob/d97e0970/doc/source/models/virtualenv.rst#L124-L124)

### Engine Matching Logic

 For each registered model, the system iterates through `SUPPORTED_ENGINES` to find a match. For embedding models, it checks:

 
 - `check_format_with_engine()`: Validates if the format (e.g., `ggufv2`) is compatible with the engine (e.g., `llama.cpp`) [xinference/model/embedding/__init__.py72-77](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/__init__.py#L72-L77)
 - `cls.match()` or `cls.match_json()`: Performs deep matching of the model family, spec, and quantization [xinference/model/embedding/__init__.py96-99](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/embedding/__init__.py#L96-L99)

## Distributed Considerations

 In a distributed environment, if a custom model file exists on a specific worker node, it can be launched directly using the `worker_ip` and `model_path` parameters in the launch interface [doc/source/models/custom.rst49-51](https://github.com/xorbitsai/inference/blob/d97e0970/doc/source/models/custom.rst#L49-L51) For models that are too large for a single machine (e.g., DeepSeek V3), Xinference supports distributed inference across multiple workers using engines like `vLLM` or `SGLang` [doc/source/user_guide/distributed_inference.rst6-18](https://github.com/xorbitsai/inference/blob/d97e0970/doc/source/user_guide/distributed_inference.rst#L6-L18)
