## Purpose and Scope

 This document describes the complete lifecycle of requests in Xinference, from initial client submission through model inference and response delivery. It covers both model launch requests and inference requests (chat/completion), detailing how requests flow through the API layer, supervisor coordination, worker execution, and model processing layers.

 For information about the actor framework and cluster coordination, see [Supervisor and Worker System](https://deepwiki.com/xorbitsai/inference/2.1-supervisor-and-worker-system). For details about the ModelActor pattern and concurrency management, see [Model Actor Framework](https://deepwiki.com/xorbitsai/inference/2.2-model-actor-framework). For model registry and caching details, see [Model Registry and Cache Management](https://deepwiki.com/xorbitsai/inference/2.4-model-registry-and-cache-management).

## Request Lifecycle Overview

 Xinference processes two primary types of requests:

 
 - **Model Management Requests**: Launch, terminate, and query model instances.
 - **Inference Requests**: Chat completions, text completions, embeddings, and other model operations.
 
 All requests follow a multi-layered architecture:

## Inference Request Lifecycle

 
### Request Reception

 Inference requests are received by `RESTfulAPI` endpoints like `/v1/chat/completions` or `/v1/completions` [xinference/api/restful_api.py1649-1826](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/api/restful_api.py#L1649-L1826) The API layer parses the request into types defined in `xinference/types.py`, such as `CreateChatCompletion` [xinference/types.py210-217](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/types.py#L210-L217)

 
### Concurrency Control

 Requests are governed by the `@request_limit` decorator in `ModelActor`. This decorator tracks `_serve_count` against `_request_limits` [xinference/core/model.py88-119](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L88-L119)

 
 - **Success**: `_serve_count` is incremented, and the request proceeds.
 - **Failure**: If the limit is reached, a `RuntimeError` is raised, and `model_request_errors_total` metrics are recorded [xinference/core/model.py107-114](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L107-L114)

## Streaming vs. Non-Streaming Paths

 
### Non-Streaming Path

 The request is processed fully by the engine, and a single response object (e.g., `ChatCompletion`) is returned to the client [xinference/types.py210-217](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/types.py#L210-L217)

 
### Streaming Path

 
 - The `ModelActor` returns an `AsyncGenerator` or `IteratorWrapper` [xinference/core/model.py130-134](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L130-L134)
 - The `RESTfulAPI` uses `EventSourceResponse` to stream Server-Sent Events (SSE) to the client [xinference/api/restful_api.py45](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/api/restful_api.py#L45-L45)
 - The `streaming_response_iterator` in the client handles the consumption of these chunks [xinference/client/restful/restful_client.py20](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/client/restful/restful_client.py#L20-L20)

## Error Handling and Cancellation

 
### OOM Handling

 The `@oom_check` decorator wraps model methods to catch `OutOfMemoryError` [xinference/core/model.py173-202](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L173-L202) When an OOM occurs, the actor calls `_handle_oom_error()` to report the event and potentially trigger recovery [xinference/core/model.py180-193](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L180-L193)

 
### Request Cancellation

 Xinference supports request cancellation via `CancelMixin` [xinference/core/utils.py71](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/utils.py#L71-L71)

 
 - **Client Side**: The `RESTfulClient` can close sessions to stop receiving streams [xinference/client/restful/restful_client.py60-66](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/client/restful/restful_client.py#L60-L66)
 - **Server Side**: The `RESTfulAPI` inherits from `CancelMixin` to manage request blocking and timeouts during cancellation [xinference/api/restful_api.py160](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/api/restful_api.py#L160-L160)
