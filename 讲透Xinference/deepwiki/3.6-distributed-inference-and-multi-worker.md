## Purpose and Scope

 This page documents Xinference's distributed inference system, which enables large language models to be served across multiple GPUs and multiple worker nodes. This includes tensor parallelism (splitting a model across GPUs within a single node), pipeline parallelism (splitting model layers across multiple workers/nodes), and the coordination mechanisms that enable distributed execution.

 For information about GPU resource allocation and device management, see [GPU Resource Management](https://deepwiki.com/xorbitsai/inference/2.5-gpu-resource-management). For details about the supervisor-worker architecture that manages the cluster, see [Supervisor and Worker System](https://deepwiki.com/xorbitsai/inference/2.1-supervisor-and-worker-system). For specific inference engine features like continuous batching, see [Continuous Batching and Scheduling](https://deepwiki.com/xorbitsai/inference/3.4-continuous-batching-and-scheduling).

 
## Overview of Distributed Inference

 Xinference supports distributed model serving through two primary parallelization strategies:

 
 - **Tensor Parallelism (TP)**: Splits individual model layers across multiple GPUs within a single node or across nodes.
 - **Pipeline Parallelism (PP)**: Distributes different layers of the model across multiple worker processes/nodes.
 
 These strategies are primarily implemented in the `vLLM` and `SGLang` backend engines, which provide the infrastructure for distributed execution.

 **Model Distributed Capabilities:**

 
| Engine | TP Support | PP Support | Multi-Worker Coordination |
|---|---|---|---|
| vLLM | Yes | Yes | XinferenceDistributedExecutor |
| SGLang | Yes | Yes | dist_init_addr orchestration |

 **Sources:** [xinference/model/llm/vllm/core.py332-342](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L332-L342) [xinference/model/llm/sglang/core.py152-158](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/sglang/core.py#L152-L158)

 
## Tensor Parallelism

 Tensor parallelism splits the weight matrices of individual model layers across multiple GPUs. This allows models that don't fit on a single GPU to be served efficiently.

 
### Configuration

 The `tensor_parallel_size` parameter controls the number of GPUs used for tensor parallelism:

 
| Parameter | Description | Default | Used By |
|---|---|---|---|
| tensor_parallel_size | Number of GPUs for TP | Auto-detected GPU count | vLLM |
| tp_size | Number of GPUs for TP | Auto-detected GPU count | SGLang |

 In vLLM, the tensor parallel size is automatically set based on the available GPU count within a worker: [xinference/model/llm/vllm/core.py740](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L740-L740)

 
### GPU Layer Distribution

 For models with automatic GPU layer offloading (`n_gpu_layers = -1`), the system calculates optimal layer distribution. In the `vLLM` engine, this is handled by passing the `tensor_parallel_size` to the `AsyncEngineArgs`.

 **Sources:** [xinference/model/llm/vllm/core.py732-745](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L732-L745) [xinference/model/llm/sglang/core.py278-296](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/sglang/core.py#L278-L296)

 
## Pipeline Parallelism and Multi-Worker

 Pipeline parallelism distributes different layers of a model across multiple worker processes, potentially on different physical nodes. This is configured using the `n_worker` parameter during model launch.

### Worker Initialization Flow

 The initialization process differs based on whether a worker is the driver (shard 0) or a follower (shard > 0):

 **Driver (Shard 0):** [xinference/model/llm/vllm/core.py493-510](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L493-L510)

 
 - Sets `driver_info` with its own address.
 - Waits for all workers to register their pool addresses via the `_all_worker_ready` event.
 - Gathers all worker addresses across shards.
 - Creates the distributed executor with the complete worker address list.
 
 **Follower Workers (Shard > 0):** [xinference/model/llm/vllm/core.py481-492](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L481-L492)

 
 - Receives `driver_info` from the supervisor.
 - Uses an actor reference to communicate with the driver.
 - Registers its pool addresses with the driver using `set_worker_addresses`.
 - Initializes its portion of the model.
 
 **Sources:** [xinference/model/llm/vllm/core.py460-560](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L460-L560) [xinference/model/llm/sglang/core.py206-245](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/sglang/core.py#L206-L245)

## NCCL Backend and Communication

 NCCL (NVIDIA Collective Communications Library) provides the low-level communication primitives for distributed GPU execution. Xinference uses NCCL through the underlying inference engines.

 
### NCCL Initialization Considerations

 The vLLM backend has special handling for NCCL initialization across different versions. For versions 0.3.1 to 0.3.3, Xinference forces the multiprocessing start method to `fork` to accommodate the `cupy` NCCL backend: [xinference/model/llm/vllm/core.py396-402](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L396-L402)

 For SGLang, distributed initialization requires setting up the NCCL communication address (`dist_init_addr`): [xinference/model/llm/sglang/core.py210-222](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/sglang/core.py#L210-L222)

 SGLang also enforces the `spawn` multiprocessing method to avoid NCCL hangs: [xinference/model/llm/sglang/core.py204](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/sglang/core.py#L204-L204)

## Engine-Specific Implementations

 
### vLLM Distributed Executor

 vLLM provides two distributed executor implementations depending on the version and environment settings.

 **vLLM v0 (XinferenceDistributedExecutor):** The v0 executor is created by patching the `AsyncLLMEngine` class to return a `XinferenceDistributedExecutor` which coordinates across the provided `pool_addresses`. [xinference/model/llm/vllm/core.py514-534](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L514-L534)

 **vLLM v1 (XinferenceDistributedExecutorV1):** When `VLLM_USE_V1` is enabled, Xinference patches `Executor.get_class` to return `XinferenceDistributedExecutorV1`. In v1, a new process called `EngineCore` is created via fork, and the loop management differs. [xinference/model/llm/vllm/core.py536-554](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/vllm/core.py#L536-L554)

 
### SGLang Distributed Setup

 SGLang uses a setup based on PyTorch distributed variables:

 
| Parameter | Description |
|---|---|
| nnodes | Number of worker nodes (set to n_worker) |
| node_rank | Rank of current node (set to shard) |
| dist_init_addr | NCCL initialization address |

 [xinference/model/llm/sglang/core.py206-222](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/model/llm/sglang/core.py#L206-L222)
