  The Model Actor Framework is the core architectural component of Xinference that enables distributed model serving by wrapping machine learning models in actors. This framework uses the **xoscar** actor system to create an efficient, scalable, and fault-tolerant infrastructure for deploying and serving various types of models, particularly Large Language Models (LLMs).

 This page explains how models are encapsulated within actors and how the actor framework facilitates distributed model serving. For details on the supervisor and worker components that orchestrate these model actors, see **2.1 Supervisor and Worker System**.

 
## Actor-based Architecture Overview

 
### Core Actor System Integration

 Xinference utilizes a hierarchical actor structure where specialized actors manage different aspects of the system's lifecycle.

 Title: Xinference Actor Hierarchy and Relationships


 The Model Actor Framework is built on the xoscar distributed actor system, using `xo.StatelessActor` as the base class for all actors [xinference/core/model.py204](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L204-L204) Each model instance is wrapped in a `ModelActor` that runs in an isolated actor subpool with dedicated GPU resources.

 **Key architectural patterns:**

 
 - **Actor Isolation**: Each `ModelActor` runs in its own subpool with isolated memory and GPU allocation [xinference/core/worker.py782-790](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/worker.py#L782-L790)
 - **Reference Management**: Actors communicate through `xo.ActorRefType` references maintained by supervisors and workers [xinference/core/supervisor.py130-141](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/supervisor.py#L130-L141)
 - **Fault Recovery**: Failed actors are automatically recreated using `recover_sub_pool` mechanisms triggered by the actor system [xinference/core/worker.py179-232](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/worker.py#L179-L232)

### Request Limits

 The `@request_limit` decorator [xinference/core/model.py88-170](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L88-L170) enforces concurrent request limits. It increments `_serve_count` before execution and decrements it after completion, unless the response is a stream. For streaming, the client must explicitly call `decrease_serve_count()` [xinference/core/model.py260](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L260-L260) to release the slot.

 
### Concurrency Models: Batching vs. Locking

 
 - **Sequential (allow_batch=False)**: Models like basic Transformers use an `asyncio.Lock` [xinference/core/model.py220-223](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L220-L223) to ensure only one request is processed at a time.
 - **Batch-capable (allow_batch=True)**: Models like vLLM or llama.cpp allow multiple concurrent requests. These may use the `_pending_requests` queue [xinference/core/model.py245-252](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L245-L252) to feed a continuous batching engine.

## Metrics Tracking

 Model Actors track performance and utilization metrics, which are reported back to the worker's metrics server.

 
### Tracked Metrics

 The `_record_completion_metrics` method [xinference/core/model.py286-321](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L286-L321) records:

 
 - `input_tokens_total_counter`: Total prompt tokens [xinference/core/metrics.py49](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/metrics.py#L49-L49)

 Metrics are initialized with labels including `type`, `model`, `node`, `format`, and `quantization` [xinference/core/model.py227-233](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L227-L233)

## Fault Tolerance and Recovery

 
### Out-of-Memory (OOM) Recovery

 The `@oom_check` decorator [xinference/core/model.py173-202](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L173-L202) catches `OutOfMemoryError`. When triggered, it calls `_handle_oom_error` [xinference/core/model.py323](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/model.py#L323-L323) which:

 
 - Logs the error.
 - Reports the OOM event to the `EventCollectorActor`.
 - Allows the worker to take recovery actions, such as restarting the subpool.
 
 
### Process Crash Recovery

 If a `ModelActor` subpool process crashes, the `WorkerActor` receives a `recover_sub_pool` callback [xinference/core/worker.py179](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/worker.py#L179-L179)

 
 - It checks the `MODEL_ACTOR_AUTO_RECOVER_LIMIT` [xinference/core/worker.py80](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/worker.py#L80-L80)
 - If within limits, it recreates the actor using the original launch arguments stored in `_model_uid_to_launch_args` [xinference/core/worker.py199](https://github.com/xorbitsai/inference/blob/d97e0970/xinference/core/worker.py#L199-L199)
