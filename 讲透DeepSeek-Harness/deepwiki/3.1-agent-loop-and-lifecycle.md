  This page provides an in-depth technical examination of the `ReactLoopAgent` implementation within DeepSeek Harness (dsh). It covers the internal turn/step state machine, inbox management for different types of messages, mechanisms for cancellation and maintenance, epoch header handling for consistent model requests, and the publication transaction pattern for agent lifecycle management.

## Overview of ReactLoopAgent

 The `ReactLoopAgent` class is the default, concrete agent driver in dsh, implementing the public `Agent` interface. It manages the full lifecycle of a session from message intake to turn and step execution. It uses an internal state machine to manage active vs idle phases, processes user requests, orchestrates LLM calls and tool executions, and emits events both for live observers and persistent session logging [packages/core/agent-loop/src/agent.ts68-170](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/agent.ts#L68-L170)

 Key aspects:

 
 - Reads input messages from its durable, append-only `Inbox`.
 - Advances through `turn` and `step` boundaries, processing input batches.
 - Leverages Cordis event taxonomies to orchestrate model requests and tool calls.
 - Supports cancellation via cooperative AbortController signals.
 - Supports maintenance mode for background work without breaking ongoing turns.
 
 The agent also owns its own scoped `Context` for registrations and emits fused `agent/*` events through a dispatcher bound on construction [packages/core/agent-loop/src/agent.ts69-104](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/agent.ts#L69-L104)

## Turn/Step State Machine

 
### Concepts

 
 - **Turn:** A logical conversation segment consisting of zero or more steps. A turn opens when the first input message is claimed and closes once no further work remains owed (e.g., no more tool calls or pending input).
 - **Step:** A unit representing a single request-response cycle with the LLM plus any associated tool calls and results.
 
 
### Internal State Phases

 The agent maintains a `phase` typed as one of:

 
 - `idle` — waiting for input; not actively driving.
 - `maintenance` — running a background job that temporarily blocks active work; any wakeups during this phase get latched for replay.
 - `running` — actively driving a turn and/or step.
 
 
```

```

 
### State Transition Highlights

 
 - When idle, the agent waits. A call to `send` with wakeup starts the driver by transitioning it to `running`.
 - Maintenance jobs can run only when idle, and block new input processing. Wake requests during maintenance are latched.
 - Active steps can abort, finish, or spawn new steps depending on tool call outcomes.
 - The agent signals status changes on every phase transition for external observers [packages/core/agent-loop/src/agent.ts111-179](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/agent.ts#L111-L179)

## Inbox Management: Followup, Steer, Inject

 The `Inbox` maintains ordered queues of pending user messages for the agent to consume. It supports two primary queues indexed by `InboxTarget`:

 
 - `next-turn`: messages queued to kick off a new turn.
 - `next-step`: messages queued for the current turn's next step.
 
 
### Message Management Methods

 The agent exposes these methods on its handle to route input messages accordingly:

 
| Method | Inbox Target | Wake Agent? | Description |
|---|---|---|---|
| followup | next-turn | Yes | Queue message for a new conversation turn. |
| steer | next-step | Yes | Queue message for the current turn's next step. |
| inject | next-step | No | Add context to the next model request without waking. |

 All methods use `Inbox.splice` to insert messages durably, triggering `agent/inbox/*` events on insertion, claim, or discard. Wakes are passed along the pipeline to start or continue work [packages/core/agent-loop/src/agent.ts120-139](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/agent.ts#L120-L139) [packages/core/agent/src/types.ts25-43](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent/src/types.ts#L25-L43)

 The `Inbox` preserves unprocessed input durably until claimed by a step, ensuring resilience in case of cancellations or crashes.

## Execution Lifecycle (Turn Flow)

 The agent orchestrates turns and steps according to a strict sequence of claims, prompt assembly, model request, and tool execution phases integrated with event waterfalls.

 
### Detailed Turn Flow

 
```

```

 
 - Each step begins by *claiming* input from the inbox.
 - The system prompt context service assembles prompt fragments and tool schemas scoped to the agent.
 - `agent/pre-step` listeners may rewrite or reject the step input batch.
 - The model is requested in the `agent/request` waterfall; tokens stream back via `llm/stream`.
 - Tool calls invoked by the model are run in the guarded pipeline.
 - Steps may chain sequentially if tools request follow-up calls.
 - When no further work remains, the turn closes by emitting `agent/turn-stopping` before emitting `turn/end`.

## Cancellation & Maintenance Mechanics

 
### Cancellation Through `cancel()`

 The agent supports cooperative cancellation of active and queued work via `cancel(cause, options)`:

 
 - Default behavior clears the inbox and aborts the running `AbortController`, terminating active steps promptly.
 - Optionally, `keepInbox: true` preserves messages queued in the inbox, allowing them to be replayed later.
 - Disposing the agent triggers a cancellation with a `disposed` cause that also prevents latching subsequent wakes.
 - The cancel method immediately aborts the current activity controller and potentially drops queued messages [packages/core/agent-loop/src/agent.ts141-147](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/agent.ts#L141-L147) [packages/core/agent-loop/tests/cancel.spec.ts](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/tests/cancel.spec.ts)
 
 
### Maintenance Mode with `runMaintenance()`

 
 - Maintenance allows running background async jobs while the agent is idle.
 - While maintenance is active, any wake requests caused by incoming messages are *latched*: they do not immediately trigger active execution but are replayed once maintenance completes.
 - This pattern prevents overlap and ensures single-threaded sequential delivery of work.
 - The method maintains the last turn count for proper idle transition tracking and emits state updates accordingly [packages/core/agent-loop/src/agent.ts148-169](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/agent.ts#L148-L169) [packages/core/agent-loop/tests/loop.spec.ts108-139](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/tests/loop.spec.ts#L108-L139)

## Epoch Headers & Publication Transaction Pattern

 
### Epoch Headers: Anchoring Model Requests

 Each model request is prefixed by an `EpochHeader` describing the effective LLM configuration and request parameters. These headers are persisted in the session log as durable events and allow the loop to:

 
 - Record the exact adapter-configured defaults in use.
 - Ensure request consistency and enable debug/replay fidelity.
 - Strip adapter-derived defaults before the next pipeline proposals to allow plugins to override or fill missing config while preserving immutable defaults [packages/core/agent-loop/src/agent.ts30-65](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/agent.ts#L30-L65)
 
 
### Publication Transaction for Agent Creation and Teardown

 The lifecycle entity management relies on a transactional style:

 
 - **Preparation Phase:** 
 - Construct the private session and `ReactLoopAgent` instance.
 - The agent is created but not yet published in registries.
 - **Setup Phase:** 
 - Run any agent-scoped setup logic (plugin registrations, event listeners).
 - **Publication Phase:** 
 - Enter both the `ctx.sessions` and `ctx.agents` registries.
 - Detect identity collisions, and if so, rollback the transaction.
 - Announce the agent via `agent/created` event and start the agent driver.
 - **Teardown Phase:** 
 - On dispose, stop the agent driver, unwind the scope, unregister from registries, and clean up the inbox and session.
 
 This pattern ensures atomic startup and prevents stale duplicate agents from coexisting [packages/core/agent-loop/README.md85-135](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/README.md?plain=1#L85-L135) [packages/core/agent-loop/src/index.ts40-90](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/core/agent-loop/src/index.ts#L40-L90)

# Summary

 The `ReactLoopAgent` is the heart of DeepSeek Harness's agent orchestration, providing a robust state machine managing every conversational turn and step. Through durable inbox splices, event waterfalls, cancellation and maintenance orchestration, and transactional agent lifecycle management, it underpins the entire user-model-tool interaction fabric. Observers and plugins extend its behavior via the rich `agent/*` event taxonomy without coupling to this concrete driver. The modular design allows the agent loop to be replaced while maintaining consistent interfaces and execution semantics.
