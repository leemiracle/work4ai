  The DeepSeek Harness (dsh) execution environment employs a multi-layered sandboxing strategy to confine subprocesses (primarily `bash` and `pwsh` executors) while providing a controlled escalation path for user-approved operations. The system is built around a unified capability seam that abstracts platform-specific enforcement mechanisms like Landlock on Linux and Restricted Tokens on Windows.

 
## Overview & Capability Seam

 Sandboxing in dsh is not a hardcoded feature of any single executor but a **capability** composed via the Cordis plugin framework. The core abstraction is `ctx.sandbox`, provided by `SandboxProvider` `.agents/notes/implemented/feature/2026-07-06-sandbox.md:51-53`.

 
### Key Vocabulary

 
 - **SandboxMode**: Defines the file-effect boundary. Supported modes are:

 
 - `read-only`: FILE effects restricted.
 - `workspace-write`: Allows writes to the workspace root and a backend-defined private temp area.
 - `danger-full-access`: No file effect restrictions.
 `.agents/notes/implemented/feature/2026-07-06-sandbox.md:53-54`
 - **SandboxEnforcement**: Indicates the backend’s enforcement completeness:

 
 - `full` or `partial` confinement reported by providers.
 `.agents/notes/implemented/feature/2026-07-06-sandbox.md:53-54`
 - **Denial Signatures**: Stderr substrings utilized to detect kernel or launcher denial of file operations.
 `.agents/notes/implemented/feature/2026-07-06-sandbox.md:53-54`
 - **Runner Failure Rules**: Rules for identifying sandbox launcher failures (e.g., missing runner binary) versus child command failures.
 `.agents/notes/implemented/feature/2026-07-06-sandbox.md:53-54`

## Linux Sandboxing: Landlock & Bubblewrap

 On Linux, `dsh-sandbox-local` implements a runner chain that first attempts to confine subprocesses with `bwrap` (Bubblewrap). If unavailable—common in minimal container environments where unprivileged user namespaces are disabled—it falls back to the native `landlock-run` binary. This fallback is crucial for environments lacking `bwrap` or where kernel Landlock support exists `.agents/notes/implemented/feature/2026-07-06-sandbox.md:11-12`.

 
### `landlock-run` Native Binary

 
 - **Location & Language**: The `landlock-run` launcher is a ~300-line pure C11 program located in `native/landlock-run`. It uses Linux Landlock UAPI syscalls directly, without external dependencies, minimizing audit surface and binaries.
 - **Functionality**: The launcher installs Landlock rulesets — (`--ro <path>`, `--rw <path>`) flags confer read-only or workspace-write permissions. The rulesets are inherited through `execve`, so child processes remain confined.
 - **Probing**: It supports a `--probe` mode that creates a maximum rule set to verify kernel support and exits 0 only if fully enforced.
 - **Failure Semantics**: All launcher failures print a fatal line prefixed with `landlock-run:` and exit with code 125 to distinguish launcher errors from child process errors.
 - **Enforcement Reporting**: Landlock signals partial enforcement if kernel ABI is old and certain operations cannot be controlled, otherwise full enforcement is reported.

## Windows Sandboxing: Restricted Tokens

 Windows sandboxing is implemented within the `@deepseek-ai/dsh-sandbox-windows-acl` package using **Restricted Tokens** configured with `WRITE_RESTRICTED`. This approach preserves ambient read and network capabilities but enforces a strict intersection check on write permissions, limiting writes to the workspace and a private temporary directory [packages/sandbox/sandbox-windows-acl/src/index.ts2-20](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/sandbox/sandbox-windows-acl/src/index.ts#L2-L20)

 
### Implementation Details

 
 - **Token Derivation**
 The sandbox duplicates the caller’s token with `CreateRestrictedToken`, applying flags: `WRITE_RESTRICTED`, `DISABLE_MAX_PRIVILEGE`, and `LUA_TOKEN`. This creates a token that restricts write-access to specified SIDs but otherwise retains read and network rights.
 [.agents/notes/implemented/feature/2026-08-08-windows-acl-restricted-token-sandbox.md13-17](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/.agents/notes/implemented/feature/2026-08-08-windows-acl-restricted-token-sandbox.md?plain=1#L13-L17)
 - **Capability SIDs**

 
 - **Workspace SID**: Derived deterministically from the canonical workspace path using `workspaceWriteSid(path)`.
 This SID’s ACE is materialized once per workspace per machine lifetime, serving as a standing cache to avoid expensive tree propagation on every session start.
 - **Temp SID**: A distinct SID generated per live session for a private temporary directory using `tempWriteSid(path)`. This SID’s ACE is revocable upon session end to ensure proper isolation of temporary data between sibling sessions.
 Both SIDs are passed to the restricted token as part of its restricting SIDs list.
 [packages/sandbox/sandbox-windows-acl/src/index.ts8-14](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/sandbox/sandbox-windows-acl/src/index.ts#L8-L14)
 - **Partial Enforcement**
 Enforcement is reported as `partial` by design because:

 
 - The restricted token must keep the `Everyone` SID for proper process initialization, which grants some ambient write permission.
 - NTFS hard links can cause a file object to be written via alternate paths bypassing some checks.
 This is documented behavior acknowledged in the package README.
 [packages/sandbox/sandbox-windows-acl/README.zh.md77-79](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/sandbox/sandbox-windows-acl/README.zh.md?plain=1#L77-L79)
 - **Runner Operation**
 The runner process (in `runner.ts`) is spawned under these restricted tokens, wraps the child process' stdio (pipe or inherit), and creates a **Job Object** configured with `KILL_ON_JOB_CLOSE` so that all descendant processes die if the parent is killed.
 On disposal, revocable ACEs for the temporary directories are removed.
 [packages/sandbox/sandbox-windows-acl/src/runner.ts47-51](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/sandbox/sandbox-windows-acl/src/runner.ts#L47-L51)
 - **Fail-Closed Guarantees**
 Every Win32 API interaction is checked for failure; any failure causes an immediate exception (`Win32Error`), ensuring no subprocess can be spawned unrestricted to avoid silent escapes.
 [packages/sandbox/sandbox-windows-acl/src/index.ts1-41](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/sandbox/sandbox-windows-acl/src/index.ts#L1-L41)

## Approval Seam & Escalation

 DeepSeek Harness integrates an **Escalation Path** enabling an agent to retry an operation with widened permissions upon user approval after an initial denial by the sandbox `.agents/notes/implemented/feature/2026-07-06-sandbox.md:9-10`.

 
### Escalation Logic

 
 - **Denial Detection**:
 The runtime (e.g., `dsh-bash-sandbox`) inspects stderr output for known `denialSignatures` that indicate sandbox file-access restrictions triggered the error. The `SandboxProvider` supplies these signatures matching the underlying backend.
 `.agents/notes/implemented/feature/2026-07-06-sandbox.zh.md:73-75`
 - **User Approval Flow**:
 If elevated permissions are required, the system pauses the agent loop awaiting user consent via the `approval` seam (`ctx.approval`). The user may allow or deny the escalation `.agents/notes/implemented/feature/2026-07-06-sandbox.md:31-34`.
 - **Retry on Approval**:
 If approved, the command is retried once with a new `SandboxExecutionPolicy` specifying a wider sandbox mode than the session default.
 `.agents/notes/implemented/feature/2026-07-06-sandbox.zh.md:81-83`.

## Security Boundaries & Limitations

 
| Feature | Linux (Landlock/bwrap) | Windows (Restricted Token) |
|---|---|---|
| Write Restriction | Full (or Partial on old kernels) | Partial (due to Everyone SID and hard-link behavior) |
| Read Restriction | Supported (enforced by Landlock rulesets) | Not supported (ambient access through normal SIDs) |
| Network Restriction | Not claimed in this seam | Not supported |
| Process Visibility | Not claimed in this seam | Not supported |
| Console Isolation | Supported (creates isolated consoles) | Unavailable (children share host console; restricted tokens die if console creation flags used) |

 **Notes on Windows partial enforcement:**

 
 - The `Everyone` SID must remain in the restricting list for proper process initialization (early DLL init, CNG cryptographic DLLs).
 - NTFS hard links alias the same file object across multiple paths. Since ACLs attach to file objects, writes through hard links bypass path-based ACL restrictions.
 - These side effects are recorded and reported; defenders requiring absolute boundaries should employ additional mechanisms or higher-level policy.
