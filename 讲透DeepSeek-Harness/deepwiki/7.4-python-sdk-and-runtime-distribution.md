  The DeepSeek Harness (DSH) Python ecosystem provides a high-level interface for driving agentic workflows from Python. It consists primarily of two components:

 
 - **`deepseek-harness-sdk`**: The Python SDK client library for spawning and interacting with the DSH runtime via JSON-RPC.
 - **`deepseek-harness-runtime-bin`**: The platform-specific runtime distribution, delivered as native single-file executables (SEA) bundled into Python wheels.
 
 This architecture enables Python users to leverage the Node.js-based DSH agent system without separately installing Node.js, facilitating seamless Python integration with the full agentic capabilities of DeepSeek Harness.

 
---

 
## Architecture & Data Flow

 The Python SDK operates as a thin interface that launches the DSH runtime as a child process and communicates over a JSON-RPC protocol tunneled on the child process's standard IO streams. This subprocess runtime is a Node.js closure embedding the Cordis plugin framework with agent orchestration, LLM adapters, and tool runtimes.

## The Runtime Distribution (`deepseek-harness-runtime-bin`)

 `deepseek-harness-runtime-bin` delivers the DSH runtime environment for Python via Python wheels containing platform-specific native executables and necessary assets. This runtime bundle encapsulates the entire Node.js closure needed for agent execution, plugin composition, and tool management.

 
### Runtime Carriers

 
 - **Single-File Executable (SEA - Production)**
 A native single-file Node.js executable built with `@yao-pkg/pkg`. The executable includes an embedded virtual filesystem snapshot of ESM modules, Cordis plugins, and runtime dependencies. It exposes the JSON-RPC API over stdio for the Python SDK to communicate.
 Supported platforms currently include Linux x64/arm64, macOS arm64, and Windows x64, matching the target Python wheel platform tags.
 - **Node.js Closure (Development Only)**
 An unpackaged Node closure deployed under `runtime/node/` used for local development and debugging. It requires Node.js ≥22 installed on the system and is activated by the environment variable `DSH_RUNTIME_MODE=node`. It runs the same runtime logic but without the SEA packaging.
 
 
### Zero Configuration Design

 
 - If the user does not provide a custom `cordis.yml` configuration, the SDK injects a default profile and configuration upon runtime launch.
 - This default configuration includes essential plugins and tools like: 
 - `@deepseek-ai/dsh-sdk-jsonrpc-server` — Standalone JSON-RPC server for runtime control.
 - `llm-deepseek` — Official DeepSeek LLM adapter.
 - `tool-bash-persistent` and `tool-str-replace-editor` — Persistent shell state and string replacement tools for editing files efficiently.
 
 This design ensures out-of-the-box operation without requiring manual Cordis plugin configuration.

## Internal Python Protocol (`code-runtime-python`)

 When the agent runtime executes Python code (e.g., via the `run_code` tool), it spawns a CPython subprocess. The runtime and the Python subprocess communicate using a specialized versionless JSON-lines protocol over file descriptor 3 (`PROTOCOL_FD`).

 
### Protocol Overview

 The protocol permits multiplexing JSON-RPC frames separated by newlines, using a dedicated pipe (fd 3) apart from stdout and stderr, which remain free for the program’s own output.

 Key frame types include:

 
 - **BootMessage**: Sent by the host immediately after spawning the Python subprocess. It contains resource limits (CPU time and address space) and a list of namespaces to materialize inside the child's Python environment.
 - **BootAckMessage**: Acknowledgment sent by Python after bootstrapping and resource limit enforcement is complete.
 - **CallMessage**: Python issues calls to host-side bindings, e.g., invoking a tool’s method with arguments.
 - **LogMessage**: Streamed logs or output text from the Python child, including markers indicating truncation if the logging budget is exceeded.
 - **DoneMessage**: Sent by Python when the execution completes, optionally with a final JSON value or an error descriptor.

 The build and release process coordinates packaging the SDK and runtime into versioned Python wheels while building native single-file executables for supported platforms.

### Build Implementation Details

 
 - Target platforms are parsed from CLI arguments or environment inputs and include Linux (x64/arm64), macOS arm64, and Windows x64.
 - The build script validates targets rigorously and selects matching build runners.
 - Native plugins like `node-pty` are rebuilt for Linux with `manylinux_2_28` to maximize compatibility.
 - The deployment closure is constructed without symlinks (`pnpm deploy --legacy`) to enable `pkg` bundling into a single executable binary.
 - Python wheels are built with `uv build` packaging the SDK and runtime modules and including the platform native executable.

# Summary

 
 - The `deepseek-harness-sdk` Python package provides a simple client API built on a JSON-RPC protocol.
 - Communication with the runtime occurs via stdio using a carefully designed protocol including bootstrapping, calls, logs, and done messages.
 - The `deepseek-harness-runtime-bin` wheel delivers a native platform-specific runtime executable bundling Node.js and the Cordis plugin closure.
 - Build and release tooling ensures consistent versioning and artifact generation, supporting multi-platform distribution.
 - Together, these components allow Python developers to leverage the full DSH agent ecosystem in pure Python environments without requiring Node.js installation.
