  The DeepSeek Harness (dsh) testing infrastructure relies on Vitest to ensure high-quality code across a large, multi-package monorepo. It enforces stringent quality gates such as 100% per-file coverage and employs a project-level split between thread-safe suites and those requiring serial, process-bound isolation. This structure maintains deterministic test outcomes in concurrent CI environments and supports complex snapshot-driven validation of protocols like ACP (Agent Client Protocol). The system is further enhanced by specialized test-support packages enabling hermetic LLM mocking, replay, and session snapshot management.

 
---

 
## Vitest Configuration & Project Split

 
### Test Runner Setup

 The `vitest.config.ts` configures test suites with:

 
 - A **thread-safe** project that runs most stateless or pure logic packages under parallel forked workers.
 - A **process-bound** project isolating tests with global process state dependencies or timing-sensitive I/O via dedicated forks.
 
 This split balances parallelism with the need for serialized, uncontended environments where global or external side effects would otherwise cause flaky tests [vitest.config.ts114-160](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/vitest.config.ts#L114-L160)

 
### Thread-Safe vs. Process-Bound distinction

 
 - **Thread-safe:** Used for isolated logic and Cordis plugin lifecycle tests, where concurrency is safe.
 - **Process-bound:** Used when tests interact with process-global modules like `session-persistence-jsonl`, ACP orchestration, or require real timing, e.g., `time-context`, or specific LLM adapter backends [vitest.config.ts114-156](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/vitest.config.ts#L114-L156)
 
 
### Platform-Specific Filtering

 To maintain reliable coverage and prevent false failures:

 
 - Tests requiring Bash (e.g., `bash-local`) are excluded on Windows.
 - Windows-specific packages (e.g., `sandbox-windows-acl`) are excluded from Linux-based runs, removing them from coverage denominator computations for the 100% coverage gate [vitest.config.ts22-65](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/vitest.config.ts#L22-L65)

## Quality Gates & Coverage Requirements

 
### Per-File 100% Coverage Policy

 DSH mandates that every source file within `packages/*/*/src` achieves **100% code coverage** for statements, branches, functions, and lines [vitest.config.ts10-13](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/vitest.config.ts#L10-L13) This provides a robust guard against dead or untested code.

 
 - **Uncovered Locations Reporter**: The custom reporter in `scripts/coverage-uncovered-locations.cjs` outputs precise `path:line:col` locations for missing branches or statements, facilitating prompt fixes [vitest.config.ts14](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/vitest.config.ts#L14-L14)
 - **Coverage Exemptions**: Heavy or special-case test suites that do not contribute to coverage thresholds (e.g., generators or long-running compiler specs) are excluded from instrumentation to reduce CI runtime without weakening coverage guarantees. This is controlled via `DSH_COVERAGE_EXEMPT_HEAVY` and configured in `scripts/coverage-exempt.ts` [scripts/coverage-exempt.ts1-59](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/scripts/coverage-exempt.ts#L1-L59)
 - **In-Job Partitioned Coverage**: On Linux and native Windows, test coverage is partitioned into shards (typically 4 child Vitest processes, each with a single worker); shard reports are merged post-run to maintain global per-file thresholds without increasing wall-clock time [2026-08-18-in-job-partitioned-coverage.md5-49](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/2026-08-18-in-job-partitioned-coverage.md?plain=1#L5-L49)
 - **Windows-Specific Coverage Jobs**: The `windows-native` GitHub Actions job independently enforces coverage for Windows-only packages that Linux jobs skip, ensuring full platform coverage [2026-08-08-native-windows-pull-request-ci.md8-23](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/2026-08-08-native-windows-pull-request-ci.md?plain=1#L8-L23)
 
 
| Coverage Attribute | Description |
|---|---|
| Required Coverage | 100% per source file for statements, branches, functions, and lines |
| Heavy Suite Exclusion | Heavy suites run without instrumentation but preserve correctness signal |
| Sharded Coverage | Parallel Vitest shards merge coverage reports to respect per-file thresholds |
| Platform Denominator Exclusion | Non-native package tests excluded from coverage denominator to avoid false errors |

## Snapshot Testing & Session Logs

 
### Session Event Snapshots

 Many integration tests in DeepSeek Harness validate the runtime by comparing agent-generated session event logs (`SessionEvent` append-only JSONL streams) against previously recorded golden snapshots [examples/headless-agent/tests/snapshots/advanced-toolchain/session.jsonl1-10](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/examples/headless-agent/tests/snapshots/advanced-toolchain/session.jsonl#L1-L10)

 
 - Snapshots contain events like `turn/start`, `step/start`, and `user/message` with pseudo-deterministic timestamps and unique IDs to stabilize comparison.
 - This proves that sequences of agent interactions, tool calls, and LLM messages remain unchanged as code evolves, providing confidence in architecture and business logic.
 
 
### ACP Snapshot Harness

 The `@deepseek-ai/dsh-acp-snapshot` package provides a test suite factory to run the Agent Client Protocol agent through multiple snapshot modes:

 
 - **Replay**: Runs agents against pre-recorded transcripts, feeding LLM and protocol inputs from snapshots via `llm-replay` [examples/acp-agent/tests/acp.snapshot.ts27](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/examples/acp-agent/tests/acp.snapshot.ts#L27-L27)
 - **Record**: Executes agents connecting to real LLM APIs, recording fresh transcripts [examples/acp-agent/tests/acp.snapshot.ts25-26](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/examples/acp-agent/tests/acp.snapshot.ts#L25-L26)
 - **Refresh**: Rewrites expected outputs without triggering new model calls, useful for formatting or policy update changes [examples/acp-agent/tests/acp.snapshot.ts27](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/examples/acp-agent/tests/acp.snapshot.ts#L27-L27)
 
 This mode-aware testing approach ensures agents remain consistent, and changes are explicitly reviewed.

## Test Support Packages

 DeepSeek includes dedicated packages to improve test determinism and ease integration testing:

 
| Package | Purpose |
|---|---|
| llm-mock-server | Provides a local server implementing LLM provider APIs for unit tests and controlled LLM interaction simulations. |
| llm-replay | Acts as a proxy to intercept LLM requests and respond deterministically from recorded snapshots, enabling playback of dialogs. |
| acp-snapshot | Factory package that orchestrates snapshots, temp directory management, fixture seeding, and test lifecycle for ACP compliance. |

 
### Workspace Fixtures

 Testing often requires deterministic filesystem states for tools like `ripgrep` which sort search results by file modified times. The snapshot tests use seed functions such as `prepareFsSearchWorkspace` that create temp directories with fixed `mtime`s ensuring consistent output [examples/acp-agent/tests/acp.snapshot.ts113-124](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/examples/acp-agent/tests/acp.snapshot.ts#L113-L124)

## CI Infrastructure & Failover

 The GitHub Actions-based CI integrates with the test infrastructure as follows:

 
 - Uses a mix of hosted enterprise runners and self-hosted pools for different platforms.
 - Supports failover variables (`DSH_CI_FAILOVER_LINUX`, `DSH_CI_FAILOVER_WINDOWS`) to redirect jobs to in-house runners on degraded hosted pools without code merges or config changes [2026-07-26-ci-failover-runbook.md8-33](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/2026-07-26-ci-failover-runbook.md?plain=1#L8-L33)
 
 
### Platform-Specific Jobs

 
| Job Name | Description |
|---|---|
| windows | Runs Linux-based jobs using Wine on Ubuntu to provide minimal Windows API signals without full Windows runner usage 2026-08-08-native-windows-pull-request-ci.md9-15 |
| windows-native | Runs full Windows tests on a 16-core self-hosted Windows pool to verify NTFS, DACL, and ConPTY behaviors that Wine cannot simulate 2026-08-08-native-windows-pull-request-ci.md9-17 |

 This tiered strategy ensures stable Windows coverage while minimizing resource costs.

# Summary

 The DeepSeek Harness adopts a comprehensive strategy for unit and integration testing aimed at:

 
 - **Stable, parallel execution** enabled by a Vitest multi-project split.
 - **Full per-file coverage enforcement** alongside selective exemptions to optimize CI runtime.
 - **Snapshot-based validation** of protocol interactions and complex agent behaviors.
 - **Dedicated test-support packages** promoting hermetic, reproducible LLM and protocol tests.
 - **Robust CI failover** infrastructure catering to platform-specific needs.
 
 Together, these form a rigorous framework guaranteeing high confidence in the correctness and stability of the highly concurrent, distributed DeepSeek system.
