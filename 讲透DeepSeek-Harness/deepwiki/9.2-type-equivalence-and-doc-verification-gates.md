  The documentation system within DeepSeek Harness (DSH) incorporates rigorous verification gates to maintain synchronization between the codebase and its human-facing Markdown documentation. This serves to prevent documentation drift and ensure high-quality, precise technical content throughout the monorepo.

 This page describes the key mechanisms, scripts, data flows, and standards for:

 
 - The **verify-type-equiv** gate, verifying TypeScript code snippets in Markdown against source code.
 - Documentation budgets and formatting constraints.
 - The **Model Experience** documentation standard for package READMEs.
 - The **VitePress documentation site build** driven by a manifest projection system.
 - Ancillary verification like markdown link checks and package integrity using **publint-all**.
 
 
---

 
## 1. Type Equivalence Gate (`verify-type-equiv`)

 Ensuring that pasted TypeScript declarations in documentation match the real source code is fundamental to avoiding stale or incorrect references. DeepSeek Harness employs a custom gate, `verify-type-equiv`, that checks type equivalence between snippets in Markdown and the actual TypeScript source.

 
### 1.1 Description

 
 - Markdown fenced code blocks annotated with special info strings — `ts type-equiv` or `ts public-api` — mark snippets expected to be **byte-identical** or semantically equivalent to live code [docs/AGENTS.md41-43](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/AGENTS.md?plain=1#L41-L43)
 - `ts type-equiv` is used for verbatim pastes of full type declarations with JSDoc.
 - `ts public-api` holds body-stripped class/interface public declarations.
 - These snippets must be registered in manifests to enable monitoring and tracking [docs/AGENTS.md41-42](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/AGENTS.md?plain=1#L41-L42)
 - The gate fails on mismatch, prompting documentation authors to update the content to match current source.
 
 
### 1.2 Technical Implementation

 
 - The verification logic lives in `scripts/verify-type-equiv.ts`, which:

 
 - Parses Markdown files to extract fenced code blocks annotated with relevant info strings.
 - Resolves these snippets against TypeScript declarations found in the workspace, leveraging the coordinated build outputs for accurate symbol resolution.
 - Reports mismatches with line and file references to aid correction.
 - Complementing this is `scripts/doc-typecheck.ts`, which compiles all Markdown `ts` fences (including `type-equiv`) against the workspace API declarations to confirm valid TypeScript fragments, avoiding stale or invalid code blocks [scripts/doc-typecheck.ts1-126](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/scripts/doc-typecheck.ts#L1-L126)
 - A manifest file enumerates the source-code snippets covered, forbidding drift outside gate control.

## 2. Documentation Budgets & Formatting

 To enforce concise, readable documentation, DSH applies strict limits and style gates.

 
### 2.1 `doc-budgets.manifest.json`

 
 - Located at `scripts/doc-budgets.manifest.json`.
 - Specifies character or word count limits on key docs to prevent bloat [scripts/doc-budgets.manifest.json1-10](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/scripts/doc-budgets.manifest.json#L1-L10)
 
 
| Document | Limit |
|---|---|
| AGENTS.md | 1950 |
| docs/architecture.md | 2400 |
| docs/testing.md | 1150 |
| packages/README.md | 994 |

 
### 2.2 Formatting Gates

 
 - **`verify-md-wrap`** enforces "one physical line per paragraph" to facilitate clean diffs and editing [docs/AGENTS.md40](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/AGENTS.md?plain=1#L40-L40)
 - **`verify-md-links`** scans and validates all Markdown links for validity and correctness.
 - **`verify-mermaid`** checks embedded Mermaid diagrams for syntactical correctness before publishing.

## 3. Model Experience Documentation Standard

 Every DSH package README documents the "Model Experience" — the exact LLM-visible API contract, token usage, and KV cache effects — serving as a binding contract for model-aware behaviors.

 
### 3.1 Standard Description

 
 - The README is a **per-package contract** describing configuration, semantic impact, limitations, and how the package affects model experience [docs/AGENTS.md29](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/AGENTS.md?plain=1#L29-L29)
 - Required sections include:

 
 - A top-level `## Model Experience` heading.
 - Subsections like `#### Token effect` outlining token usage profiles.
 - Packages that are model-agnostic document their exemption decisions.
 
 
### 3.2 Verification

 
 - Automated scripts parse README Markdown to verify presence and correctness of these sections.
 - This guards against omissions and enforces uniform documentation across packages.

## 4. VitePress Documentation Site Build

 The official documentation website is deployed using VitePress, generating a structured, bilingual site from scattered Markdown sources.

 
### 4.1 Manifest Projection with `website/docs.ts`

 
 - The file `website/docs.ts` provides a **canonical manifest** that maps repository-relative source Markdown files to VitePress route trees for multiple locales (Chinese "root" and English "en") [website/docs.ts1-141](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/website/docs.ts#L1-L141)
 - This manifest supports:

 
 - Locale-specific routing and sidebar placement.
 - Bilingual pairing: `.md` and `.zh.md` files are associated to project the right content for each locale, projecting raw originals if a translation is missing to avoid broken links.
 - Source aliases and section ordering.
 - Functions like `pairedPages` automate pairing and locale resolution.
 
 
### 4.2 Site Build Pipeline (`scripts/project-doc-site.ts`)

 
 - The build script executes during site generation to assemble pages:

 
 - **Inject VitePress Frontmatter**: Adds metadata such as `editSource` with GitHub edit links.
 - **Rewrite Cross-References**: Converts repository-relative Markdown/TS source links to stable GitHub blob URLs or site-internal references.
 - **Image Handling**: Validates and relocates images ensuring they are projectable and publishable within the site.
 - This ensures a harmonized user experience and up-to-date, browsable documentation.
 
 
### 4.3 VitePress Dev Server Hooks (`website/.vitepress/config.ts`)

 
 - Extends default theme behavior, builds sidebar navigation from the manifest.
 - Watches source files to trigger rebuilds on changes.
 - Serves raw Markdown content for certain requests during development.
 - Integrates Mermaid diagram rendering via the `vitepress-plugin-mermaid` plugin.

## 5. Ancillary Doc Verification Tools

 
### 5.1 Markdown Link Validation

 
 - The `verify-md-links` gate scans all Markdown files for valid internal and external links, preventing dead references.
 
 
### 5.2 Mermaid Diagram Validation

 
 - Embedded Mermaid diagrams are parsed and syntax-checked via the `verify-mermaid` gate.
 
 
### 5.3 Package Integrity Verification (`publint-all`)

 
 - Not strictly documentation but relevant: `publint-all` validates package-level configurations (`package.json` export fields and TypeScript type entrypoints) to ensure published API contracts align with documentation.
