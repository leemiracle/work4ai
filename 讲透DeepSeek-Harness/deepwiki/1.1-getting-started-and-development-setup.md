  This page provides the technical foundation for setting up and developing DeepSeek Harness (dsh) locally. It covers the monorepo environment, the build system's dual-aggregate architecture, the dual-channel CI topology, and the quality gate infrastructure.

 
## 1. Environment Prerequisites

 The repository requires specific engine versions and tools to ensure stability across the plugin-based architecture.

 
 - **Node.js**: Supports versions `^22.19.0` or `>=24.0.0` [package.json:8-10]. CI covers 22.19, 24, and 26 [docs/development.md:11].
 - **pnpm**: Version `11.7.0` is pinned via `package.json` [package.json:7]. Run `corepack enable` if `pnpm --version` does not resolve [docs/development.md:12].
 - **Git**: Version `2.26+` is required for worktree-specific configuration extensions [docs/development.md:13].
 - **API Key**: A `DEEPSEEK_API_KEY` in a root `.env` file is required for real-API tests, demos, and headless execution [AGENTS.md:98-100], [docs/development.md:14].
 
 **Sources:** [package.json:7-10], [docs/development.md:9-15], [AGENTS.md:98-100]

## 3. The dsh CLI & Profile Booting

 The `dsh` command (defined in `apps/cli`) is the primary product launcher. It manages **Profiles**, which are assembled from ordered patch layers [AGENTS.md:9].

 
### Command Modes

 
| Command | Purpose |
|---|---|
| pnpm dsh --profile web | Starts the Web UI host [AGENTS.md:82]. |
| pnpm dsh --profile headless "task" | Runs a single task from source and exits [AGENTS.md:82]. |
| pnpm run demo:ptc -- "task" | Runs the headless PTC (Plain Text Chat) mode [AGENTS.md:83]. |

 
### Profile Composition

 Profile booting logic is centralized in `apps/cli/src/profile-boot.ts`. The `dsh` CLI launch runs through `node --import tsx/esm`; modules it reaches must stay ESM [AGENTS.md:105]. Raw/Web `cordis.yml` bare plugins must appear in their resolver manifest's `dependencies` [AGENTS.md:105].

 **Sources:** [AGENTS.md:82-83], [AGENTS.md:105], [apps/cli/src/profile-boot.ts:1-20]

 
## 4. Dual-Aggregate Build System

 DSH uses two isolated TypeScript aggregates—**Host** and **Client**—to avoid `Context` declaration-merge collisions in the Cordis framework [docs/development.md:45-56].

 
### Aggregate Architecture

 The repository splits logic into two programs because both sides merge different services into the same Cordis `Context` keys [docs/development.md:56-60].

 
| Aggregate | Config | Scope |
|---|---|---|
| Host | tsconfig.host.json | Node.js runtime, agents, tools, scripts, and api/remotes (Host side) [docs/development.md:51]. |
| Client | tsconfig.client.json | Browser runtime, UI packages, apps/web, and api/remotes (Client side) [docs/development.md:52]. |

 
### Build Data Flow

 The build process follows a strict order to satisfy Typert RPC requirements [docs/development.md:67-74]:

 
 - **Host Emit**: `tsc -b tsconfig.host.json` generates JS/Types for the host.
 - **Host Bundle & Typert**: `tsdown` (Host face) analyzes types and generates RPC contracts.
 - **Client Emit**: `tsc -b tsconfig.client.json` consumes generated RPC types.
 - **Client Bundle**: `tsdown` (Client face) bundles browser artifacts.

## 5. Quality Gate System

 The repository enforces code quality through a "Quality Gate" system managed by `scripts/run-gates.ts` [scripts/run-gates.ts:1-7].

 
### Key Gates

 
 - **`ci-static`**: Runs static analysis including `oxlint`, `knip`, and documentation gates [scripts/run-gates.ts:26].
 - **`ci-coverage`**: Enforces **100% per-file coverage** for all packages [AGENTS.md:68], [scripts/run-gates.ts:28].
 - **`ci-snapshot`**: Headless replay tests against expected outputs [AGENTS.md:71], [scripts/run-gates.ts:29].
 - **`ci-windows-blocking`**: Required win32 toolchain signal, often running via Wine on Linux runners [scripts/run-gates.ts:32], [.github/workflows/ci.yml:95-99].
 
 
### Gate Execution Model

 Gates are executed with bounded parallelism. Local modes (like `check-all` or `doc-sync`) cap workers to 4 to prevent memory blowups during documentation builds [scripts/run-gates.ts:157-161].

## 6. Windows CI & Failover Strategy

 DSH employs a dual-channel CI for Windows:

 
 - **Wine Channel**: A blocking `windows` job on `ubuntu-latest` for fast toolchain signals [.github/workflows/ci.yml:95-99].
 - **Native Channel**: Four independent native jobs (`windows-build`, `windows-coverage`, `windows-native-tests`, `windows-observational`) running on `dsh-windows-2025-16core` runners [.agents/notes/implemented/process/2026-08-08-native-windows-pull-request-ci.md:17].
 
 If the hosted runners fail, the `DSH_CI_FAILOVER_LINUX` and `DSH_CI_FAILOVER_WINDOWS` variables retarget jobs to in-house pools [.github/workflows/ci.yml:27-38].

 **Sources:** [.github/workflows/ci.yml:21-45], [.agents/notes/implemented/process/2026-08-08-native-windows-pull-request-ci.md:1-23]

 
## 7. Local Development Workflow

 
 - **Relevant Checks**: CI owns exhaustive coverage. Locally, use `test:snapshot` for model/user-output verification and `doc-sync` for documentation changes [AGENTS.md:92-95].
 - **Vitest Partitioning**: Coverage is partitioned into shards to handle large suites [vitest.config.ts:8], [.github/workflows/ci.yml:103].
 - **Bilingual Docs**: Documentation is paired. Use `pnpm run verify-translation-pairing --write <path>` after editing `.md` or `.zh.md` files [.agents/notes/implemented/process/2026-08-08-native-windows-pull-request-ci.i18n.yaml:1-5].
 - **Cleaning**: Use `pnpm run clean` to remove build outputs and safe residue from deleted packages [AGENTS.md:66].
