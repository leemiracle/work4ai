  DeepSeek Harness (dsh) employs an event-driven architecture built upon the Cordis plugin framework. Communication between decoupled subsystems is mediated by a central **Event Bus**, while external interactions (I/O, LLM calls, filesystem access) are abstracted through **Capability Seams**. This design allows the core agent logic to remain agnostic of specific implementations, such as whether a shell command runs locally or in an E2B sandbox [docs/architecture.md9-13](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L9-L13)

 
## 1. Event-Driven Communication

 The system uses three primary event patterns: `emit` (one-to-many notification), `parallel` (concurrent execution), and `waterfall` (sequential data transformation) [docs/event-producer-consumer.md8-9](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/event-producer-consumer.md?plain=1#L8-L9)

 
### 1.1 Session & Agent Events

 The lifecycle of an agent and its interactions are broadcast via the event bus. The `sessions` service acts as the primary coordinator for these events [docs/architecture.md53-55](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L53-L55)

 
 - **`agent/created`**: Dispatched when a new agent instance is initialized [docs/event-producer-consumer.md12](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/event-producer-consumer.md?plain=1#L12-L12)
 - **`agent/pre-step`**: A critical `waterfall` event where plugins (like `agent-instructions` or `time-context`) inject information into the agent's context before the LLM is called [docs/event-producer-consumer.md18](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/event-producer-consumer.md?plain=1#L18-L18)
 - **`agent/status`**: Signals state changes in the agent loop (e.g., `idle`, `running`) [docs/event-producer-consumer.md22](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/event-producer-consumer.md?plain=1#L22-L22)
 - **`agent/inbox/claimed`**: Dispatched when the driver picks up a message from the inbox to start a turn [docs/event-producer-consumer.md15](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/event-producer-consumer.md?plain=1#L15-L15)
 
 
### 1.2 LLM & Stream Waterfalls

 LLM interactions are handled via the `llm` service, which manages a registry of adapters [docs/architecture.md61](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L61-L61) Streaming responses use a waterfall pattern to allow middleware to process chunks (e.g., token metering or reasoning extraction) before they reach the UI or session log [docs/architecture.md87](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L87-L87)

## 2. Capability Seams

 Capability Seams are Cordis services that define a standard interface for sensitive or environment-dependent operations. By injecting these seams, the `agent-loop` and `tools` remain portable across different host environments [docs/architecture.md64-71](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L64-L71)

 
### 2.1 Key Capability Seams

 The following table maps the capability seams to their primary implementations and consumers.

 
| Seam (Service Key) | Purpose | Primary Implementation | Key Consumers |
|---|---|---|---|
| ctx.llm | LLM Provider Abstraction | llm-deepseek, llm-pi-ai | agent-loop, compaction-basic |
| ctx.fs | Filesystem Access | fs-local | tool-fs, agent-instructions |
| ctx.tools | Tool Registry | tools | agent-loop, subagent |
| ctx.agents | Agent Registry | agent | apiproxy, acp |
| ctx.systemPrompt | Prompt Assembly | system-prompt | agent-loop |

### 2.2 The Seam Pattern Implementation

 Seams are defined as services that contribute to a shared context. A **Service Definition** declares the interface, a **Service Provider** implements it, and a **Consumer** uses it [docs/architecture.md11-13](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L11-L13)

## 3. Event Producer-Consumer Map

 The interaction between packages is strictly governed by the event bus. Below is a subset of the high-traffic events within the harness.

 
| Event | Mode | Dispatcher (Producer) | Listeners (Consumers) |
|---|---|---|---|
| agent/inbox/inserted | emit | agent-loop | goal-round-driver |
| agent/request | waterfall | agent-loop | agent, webhook |
| agent/pre-step | waterfall | agent-loop | agent-instructions, time-context, plan-mode, tool-skill |
| agent/status | emit | agent-loop | agent, goal-round-driver, session-controller |
| approval/request | waterfall | user-approval | acp, remotes |
| session/event | emit | sessions | persistence, session-query |

### 3.1 Data Flow: Tool Execution Seam

 When an agent decides to use a tool, it goes through the `tools` capability seam, which triggers a series of events to ensure safety and logging [docs/architecture.md88-89](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L88-L89)

 
 - **`agent-loop`** identifies tool calls in the LLM response.
 - **`tools/pre-execute`** waterfall allows hooks (like `hooks-codex`) to intercept the call [docs/event-producer-consumer.md33](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/event-producer-consumer.md?plain=1#L33-L33)
 - The tool implementation executes (potentially using `ctx.fs` or `ctx.shell`).
 - **`tools/post-execute`** waterfall allows for result pruning or metadata attachment [docs/event-producer-consumer.md32](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/event-producer-consumer.md?plain=1#L32-L32)
 - The result is returned to the `agent-loop` and appended to the session log as a `tool/result` event [docs/architecture.md88-89](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/architecture.md?plain=1#L88-L89)
