  DeepSeek Harness (dsh) is assembled as a layered composition of Cordis plugins. A running instance is not a monolithic application but a dynamic tree of services and events defined by ordered configuration patches. This architecture allows the same codebase to run in diverse environments—from a local CLI to a web-hosted application or a headless agent—by swapping "bundles" and "profiles."

 
## Composition Layers: Profiles & Bundles

 A dsh instance is booted by selecting a **Profile**, which specifies the entry point and the initial set of plugins. The composition is further organized into **Bundles**, which are packages that group related plugins and provide base configurations via `cordis.patch.yml` files.

 
### 1. Profiles

 Profiles are the primary entry point for the application. They determine which environment is initialized (e.g., CLI, Web).

 
 - **CLI Profile**: Managed via `apps/cli/src/profile-boot.ts` [apps/cli/src/profile-boot.ts1-50](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/apps/cli/src/profile-boot.ts#L1-L50) it handles local execution and command-line argument parsing.
 - **Agent Presets**: Specific configurations like `standard`, `code`, or `cordis` (for meta-programming dsh itself) are defined as presets [apps/cli/tests/web-agent-presets.e2e.ts106](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/apps/cli/tests/web-agent-presets.e2e.ts#L106-L106)
 
 
### 2. Bundles

 Bundles provide the structural foundation of the harness.

 
 - **dsh-base**: The minimal set of plugins required for any harness instance, including core agent logic and basic filesystem access [packages/bundle/base/package.json1-20](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/bundle/base/package.json#L1-L20)
 - **dsh-headless**: Extends base for non-interactive automation [packages/bundle/headless/package.json1-20](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/bundle/headless/package.json#L1-L20)
 - **dsh-web-app**: Adds the API gateway, web server, and browser-side client modules [packages/bundle/web-app/package.json1-20](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/bundle/web-app/package.json#L1-L20)

## Configuration Mechanism

 The harness uses `cordis.yml` and `cordis.patch.yml` files to define the plugin tree. The `cordis-plugin-loader` (a vendored dependency) processes these files to instantiate plugins and inject services.

 
### The Config Catalog

 Every loadable harness package defines a `Config` interface in its entry point. These interfaces are extracted by `scripts/gen-config-catalog.ts` into a centralized reference document: `docs/config-catalog.md` [docs/config-catalog.md1-10](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/config-catalog.md?plain=1#L1-L10)

 Key characteristics of the configuration system:

 
 - **Service Injection**: Plugins declare dependencies via `Requires:` lines in the catalog, mapping to Cordis `inject` properties [docs/config-catalog.md10](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/config-catalog.md?plain=1#L10-L10)
 - **Type Safety**: Config blocks are validated against Zod schemas generated from the TypeScript interfaces [docs/config-catalog.md8-9](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/config-catalog.md?plain=1#L8-L9)
 - **Deployment Axis**: Settings like `provider`, `model`, and `persistenceRoot` are swappable per deployment [docs/config-catalog.md40-47](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/docs/config-catalog.md?plain=1#L40-L47)

## Inspection & Debugging Tools

 To manage complex, multi-layered configurations, dsh provides tools to inspect the active state of the harness.

 
### dump-config

 The `dump-config` utility (often used during development or CI) outputs the fully resolved plugin tree after all patches and environment variables have been applied [apps/cli/src/args.ts31-37](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/apps/cli/src/args.ts#L31-L37) This is critical for debugging why a specific service failed to load or which plugin is providing a shared capability.

 The `dsh` CLI offers two commands for inspecting the configuration:

 
 - `dsh --profile <name> --dump-default-config`: Prints only the bundle layers, excluding user-defined patches and `--patch` overlays [apps/cli/reference/README.md41](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/apps/cli/reference/README.md?plain=1#L41-L41)
 - `dsh --profile <name> --dump-config`: Prints the full composed tree, including bundle layers, the profile's `cordis.patch.yml`, the home-level `$DSH_HOME/cordis.patch.yml`, and any `--patch` overlays [apps/cli/reference/README.md39](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/apps/cli/reference/README.md?plain=1#L39-L39)
 
 Both commands print comments indicating the source file for each configuration row and any overlays that modified it. `!!js` expressions remain unevaluated, and relative plugin names are resolved based on their patch file's directory [apps/cli/reference/README.md42-43](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/apps/cli/reference/README.md?plain=1#L42-L43)

## Service Roles & Implementations

 The composition process determines which "Seam" implementations are active. A seam is a service key that can be fulfilled by different plugins depending on the bundle or profile [scripts/gen-doc-graphs.ts99-100](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/scripts/gen-doc-graphs.ts#L99-L100)

| sessions | In-memory session store | session apps/cli/composition.md19-20 |
| sessionPersistence | Durable storage seam | session-persistence-jsonl, session-persistence-sqlite apps/cli/composition.md51-52 packages/bundle/web-app/cordis.patch.yml26-29 |
