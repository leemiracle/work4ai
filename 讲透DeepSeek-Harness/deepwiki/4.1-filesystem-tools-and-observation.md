  The DeepSeek Harness (DSH) filesystem architecture provides a unified, capability-based interface for interacting with the host filesystem. It separates low-level I/O mechanics from model-facing tools and security policies. The system is built around the `ctx.fs` capability seam, allowing for interchangeable backends (e.g., local, remote, or sandboxed) while maintaining a consistent toolset for agents.

 
## 1. Filesystem Capability Seam (`ctx.fs`)

 The core of the filesystem subsystem is the `FileSystem` abstract class, which defines the primitive operations required by the harness [packages/fs/fs/src/index.ts15-20](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs/src/index.ts#L15-L20)

 
### Key Primitives

 
 - **`resolve(path, opts)`**: Converts a relative or absolute path into a `FsTarget`, which contains a stable `targetKey` (the realpath) and a `displayPath` [packages/fs/fs-local/src/fsio.ts146-151](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/fsio.ts#L146-L151)
 - **`stat` / `lstat`**: Returns metadata including an opaque `FsVersion` token derived from high-resolution identity and freshness metadata (`dev:ino:size:mtimeNs:ctimeNs`) [packages/fs/fs-local/src/fsio.ts74-76](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/fsio.ts#L74-L76)
 - **`readText` / `streamText`**: Reads UTF-8 text. Large files are streamed to avoid memory exhaustion, rejecting binary data via NUL-byte sampling [packages/fs/fs-local/src/fsio.ts17-22](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/fsio.ts#L17-L22)
 - **`writeText` / `editText`**: Atomic mutation operations that support optional "intents" (optimistic locking guards) [packages/fs/fs-local/src/index.ts170-176](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/index.ts#L170-L176)

## 2. Local Filesystem Implementation (`fs-local`)

 The `LocalFileSystem` class implements the `FileSystem` seam for the host machine [packages/fs/fs-local/src/index.ts64-68](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/index.ts#L64-L68)

 
### Atomic Writes and Windows Safety

 To ensure data integrity, writes are atomic:

 
 - A temporary file is created in a private staging directory sibling to the target [packages/fs/fs-local/src/fsio.ts4-5](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/fsio.ts#L4-L5)
 - On Windows, the target's DACL (security descriptor) is copied to the temp file to preserve permissions using `copyFileDaclWin32` [packages/fs/fs-local/src/fsio.ts15](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/fsio.ts#L15-L15)
 - The file is `fsync`'d and then atomically renamed (using `replaceFileWin32` on Windows) to the target path [packages/fs/fs-local/src/fsio.ts15](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/fsio.ts#L15-L15) [packages/fs/fs-local/README.md72-73](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/README.md?plain=1#L72-L73)
 
 
### Concurrency Control

 The backend maintains a `locks` Map of `targetKey` to `Promise<unknown>`. All mutating operations (`writeText`, `editText`) for a specific file are queued to ensure that the read-guard-write cycle is never interleaved [packages/fs/fs-local/src/index.ts74-77](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/fs-local/src/index.ts#L74-L77)

### Read Tool & Windowing

 The `read` tool handles line-numbered output and pagination.

 
 - **Line Windowing**: It caps output at `READ_LIMIT` (default 2000 lines) and `readMaxBytes` (default 51,200 bytes) [packages/fs/tool-fs/src/read.ts15-34](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/tool-fs/src/read.ts#L15-L34)

## 5. Observation & Freshness Policy

 The `fs-observation-policy` plugin implements optimistic concurrency control for the filesystem.

 
### The "Read-Before-Write" Invariant

 By default, the harness enforces a policy where an agent must have "observed" (read) a file version before it is allowed to modify it [packages/fs/tool-fs/README.md40-41](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/tool-fs/README.md?plain=1#L40-L41)

 
 - **Observation**: When `read` succeeds, the tool emits a `fs/observed` event [packages/fs/tool-fs/src/read.ts162](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/tool-fs/src/read.ts#L162-L162)
 - **Intent**: When `write` or `edit` is called, the tool requests an "intent" via `ctx.waterfall('fs/write-intent', ...)` [packages/fs/tool-fs/src/write.ts111](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/tool-fs/src/write.ts#L111-L111)
 - **Validation**: The policy plugin checks its internal cache. If the file has changed since the last observation, it returns a `replaceIfVersion` guard or throws `FS_NOT_OBSERVED` [packages/fs/tool-fs/README.md52](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/tool-fs/README.md?plain=1#L52-L52)
 
 
### Error Remediation

 If a mutation fails due to a stale version, the system catches the `FsError` and provides a model-facing remedy, instructing the agent to "read the file again to see the latest changes" [packages/fs/tool-fs/src/edit.ts134-139](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef814/packages/fs/tool-fs/src/edit.ts#L134-L139)
