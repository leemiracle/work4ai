  The Client Runtime provides the browser-side orchestration layer of DeepSeek Harness (dsh). It manages sessions and workspaces on the client, dispatches multiplexed host streams to the appropriate session instances, assembles raw event logs into conversation snapshots for UI consumption, and handles history pagination and gap repair. This module integrates closely with the Cordis framework for service injection and lifecycle management.

 
---

 
## Overview & Service Architecture

 The client runtime is constructed atop the Cordis service framework and exposes core services into the browser context via `ctx.sessions` and `ctx.workspaces` [packages/client/runtime/src/client/index.ts:1-13]. It provides a React-independent object hierarchy that reflects the host state, enabling efficient snapshot-based UI updates [packages/client/runtime/README.md:5-5].

 
### Primary Runtime Services

 
 - **SessionRuntime**: The root service that manages the session list mirror, `SessionManager`, and a client-side mirror of the Agent scope tree from dsh-scope [packages/client/runtime/src/client/sessions/service.ts:1-40].
 - **WorkspaceRuntime**: Manages workspace states, the workspace list, and the logic for connecting workspaces to new or existing sessions, forming a binding between file system contexts and conversation threads [packages/client/runtime/src/client/workspaces/service.ts:51-55].
 - **SlotRegistry**: Provides extensibility points to the UI by acting as a registry for named slots, enabling injection of data sources or components into UI slots [packages/client/runtime/README.md:11-13].
 
 
---

 
## Session Management

 A **Session** represents a conversation thread. Sessions continue to reside and manage state in memory after creation to continuously consume and process live multiplexed frames from the host, even if off-screen [packages/client/runtime/src/client/sessions/session.ts:1-126].

 
### Session Lifecycle

 
 - **Creation**: Sessions are born on the Host through `session.create`. The client receives a `SessionId` and tracks the session in a local list mirror [packages/client/runtime/src/client/sessions/service.ts:107-120].
 - **Opening**: When a session is staged for viewing, it opens a history window and begins consuming live `mux` (multiplexed) frames from the shared host stream [packages/client/runtime/src/client/sessions/service.ts:8-15].
 - **Mux Frame Dispatch**: Incoming `MuxFrame` packets from the host are dispatched by `SessionManager` to the appropriate `Session` instance based on session ID [packages/client/runtime/src/client/sessions/manager.ts:106-130].
 - **Pruning**: When sessions are removed from the client-side list, their associated agent scopes and subordinate resources are cleaned up to avoid leaks [packages/client/runtime/README.md:5-5].
 
 
---

 
### History Paging and Gap Repair

 Sessions internally manage windows into their event logs for efficient memory and UI synchronization.

 
 - **Paging**: History is fetched page-by-page (defaulting to 50 messages per page) on demand [packages/client/runtime/src/client/sessions/session.ts:32-80].
 - **Loading State**: `loadingOlder` tracks if a previous history page RPC is outstanding, preventing concurrent requests [packages/client/runtime/src/client/sessions/session.ts:80-80].
 - **Gap Detection & Stitching**: If a gap is detected between the oldest live event and the newest loaded history event (e.g., disconnect or packet loss), the session enters a `stitching` state. Incoming live events are buffered until the missing history page arrives, after which the events are merged in sequence order [packages/client/runtime/src/client/sessions/session.ts:104-107].
 - **Queue Mirroring**: `SessionQueueMirror` maintains the authoritative inbox snapshot as streamed from the host for message delivery and ordering [packages/client/runtime/src/client/sessions/session.ts:85-85].

## Conversation Assembly

 The `ConversationNodeAssembler` is the core subsystem for folding raw `SessionEvent` logs into UI-ready conversation snapshots.

 
### Assembly Pipeline

 
 - **Node Definitions**: Plugins register `ConversationNodeDefinition` objects that map specific event types into business domain nodes like User Message, Assistant Message or Tool Call [packages/client/runtime/README.zh.md:47-49].
 - **State Folding**: Streaming updates (e.g., assistant chunk deltas) fold into existing nodes by stable identity for incremental UI updates [packages/client/runtime/README.zh.md:47-49].
 - **Location Indexing**: A `ConversationLocationIndex` holds stable references to turns and steps in the conversation to support precise UI highlighting and navigation [packages/client/runtime/src/client/index.ts:24-25].
 - **Snapshot Publication**: The assembler produces `ConversationSnapshot` objects that the UI consumes, containing `nodes`, partially streaming content (`partial`), and list of `runningCalls` for interactive elements [packages/client/runtime/src/client/sessions/conversation.ts:211-224].

## Workspace & Session Interaction

 `WorkspaceRuntime` governs the relationship between file system directories (Workspaces) and conversation threads (Sessions).

 
### Workspace-Session Binding Logic

 
 - **`connectWorkspace(workspaceId)`**: When a "New Session" flow starts, the runtime tries to find a blank session targeting the same workspace and path before creating a new one [packages/client/runtime/src/client/workspaces/service.ts:89-116].
 - **Blank Session Reuse**: A session is considered blank if its conversation log is empty (`SessionSummary.blank`). Once input is accepted or a tool runs, the blank flag switches off permanently [packages/client/runtime/README.zh.md:37-39].
 - **Archiving**: Sessions can be archived, removing them from visual grouping surfaces but retaining their full event logs and accounting slots for historical or audit purposes [packages/client/runtime/src/client/contract/workspaces.ts:88-93].
 
 
---

 
## Projection Management

 The client runtime includes a **Push-Model Projection** subsystem to manage special domain-specific views like TODOs, titles, and other host-computed metadata.

 
 - **ProjectionValueStore**: Owned per session, this store keeps values calculated on the host and seeded by the most recent projections tail block [packages/client/runtime/src/client/sessions/session.ts:112-123].
 - **Higher-Seq-Wins Policy**: When frames arrive out-of-order or after reconnects, the projection applies updates only if their sequence number is higher, ensuring convergent consistency [packages/client/runtime/README.md:5-5].
 - **UI Access**: Domain UI packages consume projection values via a hook `useProjection(key)`, avoiding scanning or refolding entire conversation history on the client [packages/client/runtime/src/client/sessions/session.ts:116-118].
