# 10 · 攻黑盒五步法与案例索引 ⭐

> 这一章把前面 9 章的方法论**收敛成一个流程**：观察 → 假设 → 反推 → 实测 → 验证。然后给出一个**完整案例的脱敏索引**，让你看到这套方法学在真实项目里如何串联。
>
> 这是本教程的收尾章——读完这章你应该能独立对一个全新的闭源 AI 系统开始逆向。

---

## 一、五步法总览

```
┌──────────────────────────────────────────────────────┐
│  Step 1. 观察（Observe）— 看清楚现场有什么          │
│     ↓                                                │
│  Step 2. 假设（Hypothesize）— 给每个黑盒起假设       │
│     ↓                                                │
│  Step 3. 反推（Reverse）— 用工具验证假设             │
│     ↓                                                │
│  Step 4. 实测（Experiment）— 写脚本跑通              │
│     ↓                                                │
│  Step 5. 验证（Verify）— 与原系统对拍                │
└──────────────────────────────────────────────────────┘
```

每一步都有具体的工具、产物、和"什么时候进入下一步"的标准。

---

## 二、Step 1：观察（Observe）

**目标**：把目标系统的所有"可观察表面"扫一遍，建立**全局清单**。

**工具**：
- `unzip -l target.apk` — APK 文件清单
- `aapt dump badging target.apk` — APK 元信息（包名、权限、入口 Activity）
- `strings lib*.so | sort -u` — 所有 .so 的字符串
- `for db in assets/*.db; do sqlite3 "$db" ".tables"; done` — 所有 SQLite 表
- `xxd assets/*.model | head -100` — 模型/资产文件头

**产物**：
```markdown
# 观察 Checklist
## APK 结构
- classes*.dex 个数 + 总大小
- lib/<abi>/*.so 个数 + 名字（暴露功能模块）
- assets/ 下所有文件名 + 大小 + 类型线索

## 权限
- 网络权限、存储权限、特殊权限（如 accessibility）

## 入口
- Application 类
- 主 Activity
- Services（暴露的 SDK 接口）

## 字符串（金矿）
- 文件名/路径常量
- API URL
- 模型/词典文件名
- 日志 tag（暴露类名）

## SQLite 表
- 每张表的 schema + 行数
```

**完成标准**：你能用一句话回答"这个 APK 用了什么模型、什么 NLU 库、什么 SDK、什么推理引擎"。

> 📌 **铁律**：**这一步绝对不要急着反编译**。先用 `strings` + `unzip -l` + `aapt` 把"不用动脑"的信息拿全。这 30 分钟会决定后面 30 小时的方向。

---

## 三、Step 2：假设（Hypothesize）

**目标**：基于 Step 1 的观察，给每个黑盒组件**起假设**——它可能是什么、对应哪个开源等价物。

**工具**：
- 你的 AI 知识库（你看过哪些开源 AI 系统？哪些和这个像？）
- GitHub / HuggingFace / PapersWithCode 搜索
- 厂商开发者平台（公开文档）

**产物**：
```markdown
# 假设表
| 组件 | 观察 | 假设 | 置信度 | 验证方法 |
|------|------|------|--------|---------|
| .model 文件 | head 是 FlatBuffer offset | FlatBuffer + TFLite 变种 | 🟢 高 | vtable walker |
| nlu.db | 89K 行 tag_pattern 表 | 中文 NLU 意图库 | 🟢 高 | 表结构对照 |
| libfoo.so | strings 有 "faiss" | FAISS fork 向量库 | 🟡 中 | 符号对照 |
| 混淆类 dd.a | 调用 vectordb_write | 持久化层 | 🟠 低 | 数据流分析 |
```

**完成标准**：每个黑盒至少有 1 个假设 + 验证方法。

> 📌 **铁律**：**置信度 < 🟡 的假设不要先验证**——先把 🟢 假设全验证完，拿到 80% 信息再回头收拾 🟡/🟠。

---

## 四、Step 3：反推（Reverse）

**目标**：用具体工具**验证或推翻** Step 2 的每个假设。

**工具按假设类型选**：

| 假设类型 | 工具 | 章节 |
|---------|------|------|
| FlatBuffer schema | vtable walker | [03](03-二进制格式逆向.md) |
| marisa-trie 词典 | `marisa_trie` Python 库 | [03](03-二进制格式逆向.md) |
| SQLite 内容 | `sqlite3` 直接 dump | [05](05-数据反推-SQLite与NLU.md) |
| Java 业务逻辑 | JADX + JADX-GPT | [02](02-静态分析-DEX反编译.md) |
| Native 算法 | Frida hook + LLM4Decompile | [04](04-动态插桩-Frida.md) [08](08-LLM辅助逆向.md) |
| 模型结构 | vtable walker + 开源等价物 | [03](03-二进制格式逆向.md) [06](06-模型恢复.md) [07](07-同构对比与文档考古.md) |

**产物**：每个黑盒的**详细规格**（schema / 字段语义 / 算法 / 配置）。

**完成标准**：所有 🟢 假设验证完毕，置信度提升到 🟢 或被推翻。剩下的 🟡/🟠 进入 Step 4。

> 📌 **铁律**：**反推失败也是信息**。如果"看起来是 FAISS fork"但符号对不上，那它可能是个**全新实现**或**别的开源 fork**——这就是个**新假设**。

---

## 五、Step 4：实测（Experiment）

**目标**：把反推出来的规格**实现成可跑的代码**（PyTorch / SQLite / 向量库等），用真实数据跑一遍。

**工具**：
- PyTorch（模型）
- sqlite3（数据）
- `marisa_trie`（词典）
- 自造 mock 数据 + Frida 真机数据

**产物**：
```python
# 1. 装载模型
model = ReconstructModel()
model.load_state_dict(weights_dict)

# 2. 用真实输入推理
real_input = load_real_input()  # 从 APK 抽的真实场景
output = model(real_input)
print(output)
```

**完成标准**：能跑通端到端，**输出看起来合理**（在合理范围、对相似输入有相似输出）。

> 📌 **铁律**：**第一次跑出来的输出几乎一定有问题**——BN 顺序错、归一化缺失、dtype 不对。这是正常的，进入 Step 5 验证修复。

---

## 六、Step 5：验证（Verify）

**目标**：与原系统**对拍**——给定相同输入，你的复刻和原系统输出是否一致？

**工具**：
- Frida 真机收集 (in, out) 对
- 横向对照（同一输入跑原系统 + 你的复刻，diff）

**对拍标准**：

| 一致度 | 状态 | 含义 |
|--------|------|------|
| ≥99% | 🟢 攻下 | 可以认为 1:1 复刻 |
| 95-99% | 🟡 半攻 | 主要逻辑对了，有细节差异（如 BN epsilon） |
| 90-95% | 🟠 部分 | 大致对，但某些路径错（如降级 fallback 不全）|
| <90% | 🔴 还有黑盒 | 反推有根本性错误，回到 Step 2 |

**产物**：
```markdown
# 验证报告
## 对拍结果
- 测试输入数: 1000
- 一致输出: 952 (95.2%)
- 不一致输出: 48 (4.8%)
  - 其中 30 个是 BN epsilon 差异（已知，可修复）
  - 其中 18 个是未见过的输入分支（待研究）

## 攻下的黑盒
✅ #1: ...
✅ #2: ...
🟡 #3: ... (95% 还原)
🔴 #4: ... (待研究)

## 整体还原度
≈ 95%
```

**完成标准**：还原度 ≥95%，或者你已经识别出剩余 5% 的具体原因（且不再值得投入）。

> 📌 **铁律**：**永远要给原系统和你的复刻同一份输入，diff 输出**。这一步省了，前面 4 步都是空中楼阁。


## 八、方法论延伸

本教程的方法论综合了业界公开的逆向工程实践（Black Hat / DEFCON 议题、学术论文、开源工具文档、安全研究博客）。读者可基于任何**合法授权**的端侧 AI 系统做练习。

### 8.1 案例的攻黑盒全景

| 黑盒 | 目标 | 走的路线 | 耗时 | 还原度 |
|------|------|---------|------|--------|
| **#1 向量库持久化格式** | 还原自定义二进制格式 | 路线 2（同构装载）+ Step 3 vtable walker | 1 天 | 🟢 100% |
| **#2 多模态实体持久化** | 搞懂混淆类的持久化策略 | 路线 2（同构对比 SQLite） + Step 4 实测 | 半天 | 🟢 100% |
| **#3 真实文本编码器** | 还原 libTextEnc-like.so | 路线 1（开源 CLIP 等价物）+ 三级降级设计 | 半天 | 🟢 95% |
| **#4 NLU subIntentInverse 反推** | tagId → intentName 完整映射 | 路线 2（数据反推 SQLite）+ Step 3 SQL dump | 1 小时 | 🟢 90% |
| **#5 模型格式与端到端推理** | 从 .vndl 跑通 PyTorch | 路线 1+2（FlatBuffer walker + 权重切分）| 1 天 | 🟡 85% |

### 8.2 案例索引链接

> 📌 **本教程只讲方法论，不复述任何具体案例的内部细节**。读者可以拿任何公开已授权的端侧 AI 系统（或自己有合法访问权限的系统）作为练习对象，套用上面的五步法。

**推荐练习对象**（公开可访问）：
- 开源移动端 AI 助手（Apache/MIT LICENSE 的项目）
- 自己开发的、有完整源码的系统
- 公开学术数据集配套的系统

> ⚠️ **法律边界**：未经授权对商业闭源系统做逆向并公开传播产物，可能违反 DMCA / 中国《计算机软件保护条例》。本教程的方法论用于**学习目的 + 合法授权场景**。

### 8.3 案例的关键学习点

**学方法论**：读案例时关注**每个还原点走的哪条路线**、**为什么选这条路**、**ROI 评估**。

**学陷阱**：读案例的"证据溯源"和"反逆向手段"章节，看厂商用了哪些防御、研究者用了哪些对策。

**学心态**：看研究者在反推失败时如何**记录失败原因**、**调整假设**、**横向找对照**。

**不学具体内部细节**：案例里的具体类名、API URL、字段数字都已经过时（厂商会更新版本），照搬没意义。**方法论不会过时**。

## 九、本教程的局限

诚实标注本教程**不覆盖**的内容：

1. **iOS 逆向**：本教程主要讲 Android。iOS 需要 class-dump / Frida-iOS / Theos，是另一个生态。
2. **车机 / IoT 逆向**：本教程主要讲手机端侧。车机 / IoT 的硬件攻击面（JTAG / UART / side-channel）未覆盖。
3. **大模型服务端逆向**：本教程只讲端侧 AI。云端 LLM 服务的逆向（如 OpenAI API 逆向）涉及完全不同的技术栈（网络协议、tokenizer 推断、对齐策略）。
4. **AI 模型版权检测**：本教程不教"如何判断模型 A 是否是模型 B 的 fine-tune"——这是另一个研究主题。
5. **法律细节**：本教程只讲"合法边界"的大原则，**不能替代律师意见**。
