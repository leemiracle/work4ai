# 09 · 反逆向手段与对策 ⭐

> 这一章站在**厂商角度**——他们用什么手段阻止你逆向？以及**对策**——遇到这些手段怎么办？
>
> 核心洞察：**没有不可逆的系统，只有"逆向成本 > 收益"的系统**。厂商的目标不是绝对防御，而是把成本推高到让 95% 的逆向者放弃。你的目标是降本增效——找到那条还活得动的缝隙。

---

## 一、分层反逆向模型

商业 AI 系统的反逆向通常是**多层防御**，每层防御的目标不同：

| 层 | 防御目标 | 典型手段 | 你看到的现象 |
|---|---------|---------|------------|
| **L1 APK 加固** | 防 unpack | 加固壳（如腾讯乐固、360 加固、爱加密） | APK 解压后 dex 全是壳代码 |
| **L2 代码混淆** | 防读 Java 逻辑 | ProGuard / R8 + 类名方法名混淆 | 看到大量 `a.b.c` `dd.a` |
| **L3 注解混淆** ★ | 防读泛型 / 类型信息 | 故意破坏 `@Signature` value | 字段名明文，但泛型 `List<Foo>` 看不出来 |
| **L4 native 加固** | 防读核心算法 | stripped so、OLLVM 混淆、控制流平坦化 | IDA / Ghidra 反编译出花指令 |
| **L5 资产加密** | 防读模型 / 词典 | 自定义加密 + key 放 native | assets/ 下的文件 hexdump 看不出结构 |
| **L6 反调试 / 反 hook** | 防动态分析 | 检测 Frida / ptrace / Magisk | Frida 一挂上 app 就崩 |
| **L7 完整性校验** | 防修改 | 签名校验 + SafetyNet + 文件 hash 检查 | 改一个字节就闪退 |
| **L8 法律层** | 防发布 | ToS 禁止逆向 + DMCA + 反不正当竞争 | （本章不管这层）|

> 📌 **铁律**：永远先**探测**当前系统在哪几层做了防御，再选对策。**不要试图同时攻所有层**——成本极高。

## 二、L1 APK 加固对策

### 2.1 识别

```bash
# 看原 APK 解压后的 dex
unzip -l target.apk | grep classes
# 如果 classes.dex 很小（<100KB），classes2.dex/3.dex 都是壳 → 已加固
# 如果 classes.dex 是 1-10MB 正常 dex，且类名是 com.xxx → 未加固
```

### 2.2 对策

| 加固类型 | 对策 | 难度 |
|---------|------|------|
| **腾讯乐固 / 360 / 爱加密** | 商业脱壳服务 / BlackDex / FRIDA-DEXDump | 🟠 中 |
| **DexProtector** | 难，需 root + 内存 dump | 🔴 难 |
| **自研壳** | 具体分析（找 OEP） | 🔴 难 |

**通用对策（动态脱壳）**：用 Frida hook `DexFile.openDexFile` 或 `ClassLoader.loadClass`，让 app 自己把脱壳后的 dex 加载到内存，然后 dump。

```javascript
// FRIDA-DEXDump 思路（简化版）
Java.perform(function() {
    var DexFile = Java.use('dalvik.system.DexFile');
    DexFile.openDexFile.overload('java.lang.String').implementation = function(path) {
        console.log('Dex loaded:', path);
        // 这里把 path 对应的 dex 文件 dump 出来
        return this.openDexFile(path);
    };
});
```

### 2.3 法律/道德提示

⚠️ **脱壳商业 APK 用于发布盗版是违法的**。脱壳用于学习/互操作/审计（不发布）多数情况下可接受，但请咨询法律意见。

## 三、L2 代码混淆对策

### 3.1 识别

```bash
# 反编译后看到大量短类名
jadx-gui target.apk
# 类名: a.b.c / com.xxx.dd.a / lll.lll.lll
```

### 3.2 对策

| 工具 | 用途 | 效果 |
|------|------|------|
| **JADX-GPT** | LLM 自动重命名 | 把 `dd.a` 改成 `PersistenceImpl` |
| **GhidraGPT / GhidraNLP** | native LLM 重命名 | 给 `sub_4821A` 一个语义名 |
| **Soot / SootUp** | 数据流分析 | 自动找 getter/setter 关系 |
| **OPG 图数据库** | 把 DEX 类建成图 | Cypher 查找中心类 |

> 📌 **铁律**：**不要试图读懂所有混淆类**——只要找到**主入口**（`Application.onCreate` / `Activity.onCreate`）和**核心 SDK 接口**（`IMemory` `IVector` 这类），顺着调用链读即可。其他类是 noise。

### 3.3 `@Keep` 注解是金矿

很多厂商对**对外 API** 用 `@androidx/annotation/Keep` 防混淆（否则反射调用会断）：

```python
# 用 androguard 找所有 @Keep 注解的类
from androguard.core.bytecodes.apk import APK
from androguard.core.bytecodes.dvm import DalvikVMFormat

a = APK('target.apk')
for dex_bytes in a.get_all_dex():
    d = DalvikVMFormat(dex_bytes)
    for cls in d.get_classes():
        for ann in cls.get_annotations():
            if 'Keep' in str(ann):
                print(f'Keep 类: {cls.get_name()}')
```

**找到所有 @Keep 类** = 拿到厂商公开 API 表。

## 四、L3 注解混淆 ★（最有意思的一层）

### 4.1 什么是注解混淆

Dalvik 字节码里有两个特殊注解：
- `@dalvik/annotation/Signature`：存泛型信息（如 `List<NoteSlot>`）
- `@dalvik/annotation/Throws`：存 throws 声明

**正常情况下**，ProGuard 不破坏这些注解——因为反射 API 需要它们。

**但厂商可以做自定义 pass 故意破坏**：把 Signature 的 value string_idx 指向**无关字符串**（如 `"\nStack Trace: "`），让 `getGenericType()` 返回错误结果。

### 4.2 识别

```python
from androguard.core.bytecodes.dvm import DalvikVMFormat

a = APK('target.apk')
for dex_bytes in a.get_all_dex():
    d = DalvikVMFormat(dex_bytes)
    for cls in d.get_classes():
        for field in cls.get_fields():
            for ann in field.get_annotations():
                if 'Signature' in str(ann):
                    sig_value = ann.get_value()
                    # 如果 sig_value 是 "\nStack Trace: " 这种无关字符串 → 已被混淆
                    if not sig_value.startswith('Ljava/util/') and not sig_value.startswith('Lcom/'):
                        print(f'疑似混淆: {cls.get_name()}.{field.get_name()} → sig={sig_value!r}')
```

### 4.3 对策：运行时反射 ★

Signature 注解被混淆了，但**运行时类型信息还在**（JVM 必须知道真实泛型才能正确调用）。

```javascript
// Frida hook 反射 dump 真实泛型
Java.perform(function() {
    var targetClass = Java.use('com.xxx.NoteBean');
    var fields = targetClass.class.getDeclaredFields();
    fields.forEach(function(field) {
        var type = field.getGenericType();
        console.log(field.getName() + ': ' + type.toString());  // ParameterizedType 完整泛型
    });
});
```

> 📌 **铁律**：**注解可以骗你，但反射骗不了你**。Signature 混淆只在静态分析层有效；动态反射一定拿到真实类型。

### 4.4 案例（脱敏）

某厂商系统的 11 个数据模型类（如 `NoteBean` / `PersonBean`）有 27 个 `List` / `Map` 字段。其中：
- ✅ 字段名明文（`noteSlots` / `slotIdToImageVectorsMap`）—— 因为有 `@Keep`
- ❌ Signature value 全被混淆 —— 静态看不出 `List` 的元素类型
- ✅ 运行时反射立刻拿到 `java.util.List<com.xxx.NoteSlot>` —— 真实泛型

这是典型的"分层反逆向"——表面透明，深层模糊。

## 五、L4 native 加固对策

### 5.1 识别

```bash
# 看 .so 文件
readelf -h libtarget.so
# 如果 .symtab 不存在（stripped）→ 无符号
# 如果 .text 段有大量 .byte 而非合法指令 → OLLVM 控制流平坦化
```

### 5.2 对策

| 加固类型 | 对策 | 工具 |
|---------|------|------|
| **stripped** | 字符串扫描 + LLM 反编译 | `strings` + LLM4Decompile |
| **OLLVM 控制流平坦化** | deflattener 工具 | D810 / Tuple / OLLVM-deflat |
| **字符串加密** | 找解密函数 + Frida hook | 看 init_array |
| **VMP（虚拟机保护）** | 极难，先放着 | （没有通用工具）|

### 5.3 LLM4Decompile 路线

```bash
# 1. 从 so 中导出函数 pseudo-code
ghidra_headless analyzeHeadless ./tmp_proj proj \
    -import libtarget.so \
    -postScript ExportDecompilation.java \
    -deleteProject

# 2. 喂给 LLM4Decompile
python -m llm4decompile.run \
    --model albertan017/LLM4Decompile-9B-v2 \
    --input libtarget.c \
    --output libtarget_refactored.c
```

LLM4Decompile 9B-v2 在 OSS-Fuzz 23,400 真实函数上达到 64.9% re-executability——不是 100%，但已经能给你 80% 的语义信息。

## 六、L5 资产加密对策

### 6.1 识别

```bash
# 用 hexdump 看模型/词典文件头
xxd -l 64 target.model
# 如果看到 FlatBuffer 标准 header (4 字节 offset) → 未加密
# 如果看到随机字节 → 加密了
```

### 6.2 找 key

加密 key 几乎一定在 native so 里（不会在 Java 层，否则 ProGuard 一开就泄露）。**找 key 三种方法**：

#### 方法 1：strings + 熵分析

```bash
strings libtarget.so | awk 'length == 16 || length == 32 {print}' | head -50
# AES key 通常是 16 / 32 字节字符串
# 然后逐个试（解密 head 几字节，看是否合理）
```

#### 方法 2：Frida hook 加密 API

```javascript
// hook AES_init / EVP_DecryptInit
Interceptor.attach(Module.findExportByName(null, 'EVP_DecryptInit_ex'), {
    onEnter: function(args) {
        var key = Memory.readBytes(args[3], 32);  // 第 4 个参数通常是 key
        console.log('AES key:', hexdump(key));
    }
});
```

#### 方法 3：反编译 init_array

加密 key 通常在 `.init_array` 段初始化时被解密/拼装。反汇编 init_array 找 key。

### 6.3 解密

拿到 key 后用标准 AES / RC4 / XOR 解密：

```python
from Crypto.Cipher import AES

with open('target.model', 'rb') as f:
    encrypted = f.read()

key = bytes.fromhex('...')  # 从 native 拿到的 key
cipher = AES.new(key, AES.MODE_CBC, iv=bytes(16))
decrypted = cipher.decrypt(encrypted)

# 检查解密结果
print(decrypted[:4].hex())  # 如果是 FlatBuffer，应该是合理的 offset
```

## 七、L6 反调试 / 反 hook 对策

### 7.1 识别

```javascript
// Frida 一挂上 app 就闪退
frida -U -l hook.js -f com.xxx.target
# app 启动后立即 crash 或退出
```

### 7.2 反 Frida 检测常见手段

| 检测 | 原理 | 对策 |
|------|------|------|
| `/proc/self/maps` 扫描 | 找 frida-agent.so | frida-gadget 重命名 |
| `tcp` 端口扫描 | 找 frida 默认端口 27042 | frida 改 port |
| `frida-server` 进程名 | ps 找 frida | 改 frida-server 名字 |
| `pthread_create` 检测 | frida 注入会创建线程 | hook pthread 隐藏 |
| `is_debugger_attached` | ptrace 检测 | hook ptrace 返回 0 |

### 7.3 通用对策：Frida Anti-Detect

```bash
# 用 frida-gadget 重打包（不是 attach）
# 1. 把 libfrida-gadget.so 改名（如 libtarget_helper.so）
mv libfrida-gadget.so libtarget_helper.so

# 2. 注入到 APK 的 lib/arm64-v8a/
# 3. 修改 smali 让 Application.onCreate 加载 libtarget_helper.so
# 4. 重新签名 APK
```

工具：`objection patchapk` 自动化这一步。

### 7.4 Magisk + Zygisk + LSPosed

root 设备 + Magisk + Zygisk 模块（如 Shamiko）可以隐藏 root，绕过 SafetyNet。LSPosed 持久 hook 不需要每次启动 Frida。

## 八、L7 完整性校验对策

### 8.1 识别

```bash
# 改 APK 一个字节后重新签名安装，启动就闪退
# 典型: SafetyNet attestation / 自有签名校验
```

### 8.2 对策

| 校验类型 | 对策 |
|---------|------|
| **APK 签名校验** | hook `PackageManager.getPackageInfo` 返回原签名 |
| **文件 hash 校验** | hook `MessageDigest.digest` 返回原 hash |
| **SafetyNet attestation** | 难，需 Magisk + SafetyNet-fix 模块 |
| **Play Integrity API** | 难，2024+ 替代 SafetyNet |

⚠️ 这一层的对策已接近"破解"边界，请确保你有合法授权。

## 九、心理战：故意让你以为攻下了

最有趣的反逆向是**心理战**——厂商故意让你看到一些"合理的"信息，让你以为攻下了，实际上你被诱导走了错路。

### 9.1 字段名透明但泛型模糊

如 §四 所述。你看到 `List` 字段名 `noteSlots`，会自然以为里面是 `NoteSlot`——但如果实际是 `LegacyNoteSlot`，你的复刻就错了。

**对策**：永远做**端到端对拍**——用真实数据跑原系统和你的复刻，diff 输出。<95% 一致就还有黑盒。

### 9.2 假默认值

某些字段有**看似合理的默认值**（如 `0` `false` `null`），让你以为不需要再深挖。

**对策**：对所有"看起来 OK"的字段，用 Frida 跑一次真实场景，看运行时值——往往跟"默认"不一样。

### 9.3 字符串蜜罐

厂商故意在二进制里留一些"明显"的字符串（如类名 `MockBackend`），让你以为是测试代码不重要。实际是生产路径。

**对策**：所有字符串都验证一遍——`xxd` + `strings` + 在 dex/so 里 grep 引用次数。

## 十、什么时候放弃

逆向的成本曲线是**指数增长**——前 80% 信息成本线性，最后 20% 成本指数。

### 10.1 该停的信号

- ⚠️ 单个字段/方法反推花了**超过半天**还没结果
- ⚠️ 必须 root 真机才能继续，但你**没有合法授权**
- ⚠️ 攻下的部分**还原度 <80%**，但继续投入成本极高
- ⚠️ 你在做的是**绕过 DRM / 窃取商业秘密**，法律风险大

### 10.2 放弃后的退路

1. **开源等价物**：找一个类似的开源系统替代（[07 章](07-同构对比与文档考古.md)）
2. **黑盒 API 封装**：不逆向，直接调用厂商 API（如果有）
3. **公开论文 + 专利**：很多厂商在论文/专利里**主动披露**核心算法
4. **联系厂商**：直接问（学术合作、商业授权）
