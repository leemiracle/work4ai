# 07 · 同构对比与文档考古

> 99% 的端侧 AI 系统都能在开源世界找到**等价物**——同样的算法、同样的架构、甚至同样的代码。这一章讲透如何"找开源对照"和"挖官方文档"，**让你不用从头反推**。
>
> 核心思路：**站在巨人肩膀上**。厂商的工程师也是从开源起步的，他们没发明任何东西——你只要找到他们借鉴的开源项目，就拿到了 80% 的复刻。

---

## 一、同构对比的四种类型

| 类型 | 找什么 | ROI |
|------|--------|-----|
| **1. 同名开源模型** | 模型文件名 → GitHub 搜 | ⭐⭐⭐⭐⭐ |
| **2. 同架构开源推理引擎** | 推理引擎 → TFLite / MNN / NCNN 对比 | ⭐⭐⭐⭐⭐ |
| **3. 官方 SDK 文档** | 厂商开发者平台的公开文档 | ⭐⭐⭐⭐⭐ |
| **4. APK 历史版本** | APKMirror 早版本（可能少混淆） | ⭐⭐⭐⭐ |

## 二、类型 1：开源等价模型

### 2.1 模型文件名是金矿

```bash
# 从 .so / dex 里 dump 所有 strings,找 .tflite / .onnx / .pt 后缀
strings libtarget.so | grep -iE '\.(tflite|onnx|pb|pt|caffemodel)$'
# 典型输出:
#   mobilenet_v3_small.tflite
#   squeezenet_v1.1.onnx
#   bert_base_uncased.pt
#   chinese-clip-vit-base-patch16.pt
```

**这些文件名直接告诉你厂商用了哪个开源模型。**

### 2.2 GitHub 检索

把文件名拆解成关键词，在 GitHub 检索：

```bash
# 文件名: mobilenet_v3_0905_sim.tflite
# 拆解: mobilenet + v3 + 0905(版本) + sim(可能 simplify)

# GitHub search:
# https://github.com/search?q=mobilenet_v3+tflite&type=repositories
```

### 2.3 HuggingFace 检索

```bash
# 文件名: chinese-clip-vit-base-patch16.pt
# 拆解: chinese + clip + vit + base + patch16

# HuggingFace search:
# https://huggingface.co/models?search=chinese-clip
```

找到等价模型后：
- 下载它的 PyTorch 版本
- 对比层图（应该一致）
- 直接用它的权重（如果 license 允许）

### 2.4 实例（脱敏）

某厂商的 `*_encoder_128d_Nc_v1.tflite` 文件名告诉我们：
- `128d` — 128 维 embedding
- `Nc` — N 个类别（App 推荐场景的 App 总数）
- `v1` — 版本号

立刻能搜：
- GitHub App 推荐开源项目
- PapersWithCode 的 "app recommendation" 论文
- 论文里大概率是 ResidualMLP / Wide&Deep / DCN 架构

## 三、类型 2：开源推理引擎对比

### 3.1 推理引擎开源等价物

| 厂商引擎 | 开源对照 |
|---------|---------|
| TFLite | TensorFlow Lite（直接开源）|
| PyTorch Mobile | PyTorch（直接开源）|
| NCNN | 腾讯 NCNN（开源）|
| MNN | 阿里 MNN（开源）|
| TNN | 腾讯 TNN（开源）|
| ONNX Runtime | 微软 ONNX Runtime（开源）|
| TensorRT | NVIDIA TensorRT（部分文档公开）|
| 自研引擎 | 大概率借鉴上述之一 |

### 3.2 推理引擎对比策略

```python
# 假设厂商格式是 .vndl,反汇编暴露 vndllite::Params 类层级
# 对照 MNN 的 Tensor 相关类:
# vndllite::Conv2DParams    ↔ MNN::ConvolutionCommon
# vndllite::BatchNormParams ↔ MNN::BatchNorm
# vndllite::AddParams       ↔ MNN::Eltwise
# ...
```

如果类层级相似，**模型文件格式也大概率相似**——可以用 MNN 的 schema parser 直接试解析。

### 3.3 调用约定对比

```c
// 厂商 SDK 暴露的 C API:
VndlInstance* createNetWithPath(const char* path, ...);
void setInput(VndlInstance*, const char* name, float* data, ...);
void forward(VndlInstance*);
void getOutput(VndlInstance*, const char* name, float* out);

// 对比 TFLite C API:
TfLiteModel* TfLiteModelCreateFromFile(const char* path);
TfLiteInterpreter* TfLiteInterpreterCreate(TfLiteModel*, ...);
TfLiteInterpreterAllocateTensors(TfLiteInterpreter*);
TfLiteInterpreterInvoke(TfLiteInterpreter*);
TfLiteTensor* TfLiteInterpreterGetOutputTensor(...);
```

如果 API 形状高度相似，**厂商就是套壳 TFLite**——可以直接用 TFLite 解析。

## 四、类型 3：官方 SDK 文档（蓝海信息源）⭐

### 4.1 为什么官方文档是蓝海

很多厂商为了吸引开发者，会公开：
- 推理引擎 API 文档
- 模型格式白皮书
- 集成指南

**但逆向工程师很少去看这些文档**——他们默认"厂商不会公开任何东西"。这是认知盲区。

### 4.2 找官方文档

```bash
# 厂商开发者平台 URL 模式（举例）:
# - 某厂商: vendor-api.example.com / vendor.example.com/developer
# - oppo: developer.coloros.com
# - xiaomi: dev.mi.com
# - huawei: developer.huawei.com
# - samsung: developer.samsung.com

# 在开发者平台搜:
# "VNDL API reference" / "VNDL 快速入门" / "AI inference SDK"
```

### 4.3 PDF 文档结构解析

```bash
# 下载 PDF 后
pip install pdfplumber

python -c "
import pdfplumber
with pdfplumber.open('VNDL_API_reference.pdf') as pdf:
    for i, page in enumerate(pdf.pages):
        text = page.extract_text()
        if 'VndlInstance' in text or 'nativeForward' in text:
            print(f'=== Page {i+1} ===')
            print(text)
"
```

PDF 里通常有：
- 完整 Java API 签名（不用反编译就能拿）
- 模型文件格式规范（不用 vtable walker 反推）
- 集成示例代码

## 五、类型 4：APK 历史版本

### 5.1 为什么历史版本有用

厂商的反逆向手段是**逐步加强**的：
- v1.0 可能没加固
- v2.0 加了 ProGuard
- v3.0 加了 native 混淆
- v4.0 加了 Signature 混淆

**早期版本**通常反推更容易。

### 5.2 找历史版本

| 平台 | 说明 |
|------|------|
| **APKMirror** | 最大 APK 历史仓库（国外为主）|
| **APKPure** | 国际版 APK |
| **国内应用市场历史** | 应用宝 / 360 / 华为（国内厂商）|

### 5.3 diff 历史版本

```bash
# 用 apktool 解开 v1.0 和 v4.0
apktool d target_v1.apk -o v1
apktool d target_v4.apk -o v4

# diff smali
diff -r v1/smali v4/smali | head -100

# diff assets
diff -r v1/assets v4/assets | head -100
```

新版本里**新增**的类/字段，往往是厂商升级时加的（可能更容易看懂，因为离最新业务近）；**删除**的类，往往是被重构的（找替代品）。

## 六、字符串反查：网络检索

从二进制 dump 出的字符串（如 `vendor_encoder_128d_v1.tflite`）能做**全网检索**——可能在某个论坛、博客、研究论文里有人提到过：

```
Google 搜索:
"vendor_encoder_128d" → 可能在 某厂商工程师的招聘 JD / 学术合作论文里

GitHub 搜索:
filename:*.tflite vendor_encoder_128d → 可能有 某厂商员工泄露

学术论文:
site:arxiv.org "某厂商" "recommendation" → 可能有合作论文
```

> 📌 **铁律**：每个 dump 出的字符串都做一次全网搜索——成本极低，偶尔有意外收获。
