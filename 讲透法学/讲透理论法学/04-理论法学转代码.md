# 04 · 理论法学转代码:规范的可计算走廊与不可编译的价值

> **本章回答五问之五(家族层):这个分支的问题怎么变成 code 问题?**
> **本质一句话**:法律的可计算核心很小但很硬——**"要件→效果"的
> 演绎骨架可以命题化、可机检**(一致性/蕴含/漏洞);但解释的选择、
> 原则的重量、类比的相似性住在代码外面。三件套:可机械化边界 /
> 六条代码走廊 / 工程师落点,外加裂缝清单。

📖 **开篇故事**:2021 年,法国计算机科研机构 Inria 的团队发布
Catala——一门为法律而造的编程语言。起因:他们把法国社会保障法典
的育儿津贴条款逐条写成程序,发现起草者自己都没意识到的歧义
(同一条款两种读法、默认值没有说清)。Catala 的设计对应法条结构:
每条规则=**默认值+范围+例外**,层层覆盖,编译成可执行代码。
这场"规则即代码"(Rule as Code,新西兰政府 2018 年前后在
立法试点中提出)运动的宣言只有一句:**如果一条法律不能被机器
解释,也许它本来就没写清楚**——富勒"清晰"原则的编译器版。

---

## 一、可机械化边界(三件套之一)

| 任务 | 可机械化? | 说明 |
|------|-----------|------|
| 法条一致性检查(命题级) | ✅ 全自动 | 命题化+穷举/SAT——家族实验即样本(走廊①) |
| 规范蕴含与漏洞检测 | ✅ 全自动 | ⊨ 查询:"红绿灯漏洞"可机检(实验场景 A) |
| 规则文本→形式规则 | 🟡 半自动 | LLM 起草+人审(01 章方向一/三);本体骨架可复用 |
| 事实认定(证据→小前提) | ❌ 为主不可 | 归纳+经验+证明标准,司法认知的核心 |
| 类比/相似性判断 | ❌ 原则上不可完全 | 相似性是价值判断(Levi 三步的第二步) |
| 原则权衡(重量) | ❌ | 无刻度(Dworkin:weight 不是 arithmetic) |
| 解释方法选择 | ❌ | 四要素给出论辩空间,不给出裁决 |
| 恶法/正当性判断 | ❌ | 价值问题;代码只能执行预设,不能生成预设 |

## 二、代码走廊总表(三件套之二)

| 走廊 | 问题类型→形态→栈 | 承诺强度 |
|------|-----------------|---------|
| ① 命题一致性 | "这组条款矛盾吗" → 命题化+穷举赋值 → 纯 python(家族实验) | 算得准(命题逻辑可判定) |
| ② 道义/可废止推理 | "例外压得过一般规则吗" → 道义算子+可废止规则(Prakken/Sartor 谱系)/ASP → 自写/ASP 求解器 | 算得对(给定规则序) |
| ③ 规则即代码 | "津贴/税率/抚养费条款无歧义执行" → 默认值+例外结构 → Catala(DSL) | 条款级等价(法学家可读源码) |
| ④ 法律本体 | "概念的机器骨架" → Hohfeld 原子/LegalRuleML → RDF/OWL 图谱 | 结构等价(语义约束) |
| ⑤ LLM 法律推理评测 | "模型会不会 IRAC" → 分阶段基准+引证约束 → python+LLM API | 统计可信(非演绎保证) |
| ⑥ 合规即代码 | "机构守没守规" → 义务/许可映射的规则引擎(RegTech) | 场景级(规则子集) |

### 走廊①:法条一致性检查器(本章主样本)

**命题化三步**:找变元(事实原子:红灯/紧急任务/已交货……)→
写约束(每条法条=一个蕴含式:要件→效果)→ 问可满足性。
家族实验 [experiments/legal_rule_consistency.py](experiments/legal_rule_consistency.py)
用交通与合同两组条款走完全程,核心不到二十行:

```python
# 法条命题化:每条规则=蕴含式;一致性=规则+事实的合取可满足
R1 = IMP(AND(v("red"), NOT(v("emergency"))), NOT(v("pass")))  # 红灯禁行(特种车除外)
R2 = IMP(v("emergency"),  v("pass"))                          # 紧急任务车辆可通行
model = satisfiable([R1, R2] + facts)  # 有模型=一致;无模型=冲突
core = minimal_core(rules, facts)      # 最小冲突核:哪几条顶牛
entails(rules, facts, query)           # 蕴含查询;不蕴含=规范漏洞
```

**三个法理学现场**(实验专门演示):

1. **冲突是情形相对的**:规则集自身可满足≠无冲突——冲突在
   具体事实加入时才显形(实验场景 B:红灯∧紧急任务,禁行与放行
   同时点火)
2. **直接冲突可定位**:两条规则前件联合可满足、后件矛盾——
   命题化让"自相矛盾"从修辞变成 witness(反例赋值)
3. **漏洞可检出**:某情形所有规则沉默(实验场景 A:黄灯没有规则)
   ——富勒"清晰"与"不矛盾"原则的机器版

02 章"一般而言……除非"的每一步都能落到这条骨架上;
道义算子(O/P/F)在此之上再加一层:击败的是**适用**,

### 走廊③④⑤:三条工程化走廊

- **Catala 走廊**:法学家读 DSL 源码如同读条文(默认值/例外/
  范围三件套对应法条的"原则规定+但书+适用范围")——
  形式化不再是程序员对法条的转译,而是**起草行为本身**
- **本体走廊**:Hohfeld 八原子做类设计,LegalRuleML 做交换格式
  ——01 章"数据集/基准/本体"三层基建的中层
- **评测走廊**:IRAC 分阶段出题+引证命中率硬指标——01 章方向一
  的工程形态;法律长文档超出上下文窗口,**检索优先于生成**

## 三、工程师落点(三件套之三;性能工程视角)

1. **穷举 2ⁿ 的悬崖**:20 个事实原子=100 万赋值(毫秒级),
   40 个=一万亿(不可行)——真实法规是千原子级,必须按调整对象
   切片,或上 SAT 求解器(CDCL 把指数平均压平)。
   小条款用穷举(可读、可教学),大法典用 SAT——**可判定性
   是免费的,复杂度不是**
2. **一致性检查进 CI**:法规修订像代码提交——每次改动对全量
   条款跑一致性+蕴含回归,冲突在合并前暴露;
   "立法后评估"的自动化雏形(立法学支的接口)
3. **本体图谱的规模**:百万级法条-判例节点,图数据库+向量检索
   与 LLM 的 RAG 组合是当前默认栈;引证幻觉=不可采信证据
   (01 章证据门)
4. **规则即代码的双态维护**:条文改一版、Catala 源码要同步改
   ——版本对齐成为新工艺问题(02 章"版本冻结"的工程版)

## 四、裂缝清单(原则上/工程上的不可转)

1. **开放结构不可枚举**:"车辆"的外圈半透明(02 章)——
   形式化必须先做语义决策,而那正是解释学的领地;
   每一次命题化都是一次隐性的解释选择
2. **原则的重量不可编译**:权衡无算术(Dworkin);Alexy 的
   重量公式是启发式排序不是演算法——把权衡写死在代码里,
   等于让程序员替共同体做价值决断
3. **意图要件的空位**:AI 无意图(Ayres,01 章方向四)——
   "应当"对无心智者退化为"被迫",00 章枪手情境在机器身上重演:
   命令+制裁≠义务,那么规则+执行器=守法吗?
4. **正当性不可编译**:为何守法/恶法是否法的答案住在政治哲学里
   (法哲学支);代码只能预设其一,不能裁决——
   **预设写在需求文档里,不在代码里,这是最后的诚实**

## ✍️ 练习

1. **造冲突**:在家族实验场景 A 里删掉 R1 的例外条件
   (`NOT(emergency)`),重跑——观察最小冲突核怎么变化,
   并写出"修复"的两种方案(改一般规则 vs 加更高优先级例外)
2. **黄灯条款**:给场景 A 补一条"黄灯亮时应停车,已越线者除外"
   ——命题化时你必须决定几个语义问题(黄=非红非绿?
   "越线"要不要变元?),记录每一个决策,数一数:你做了几次
   "解释"
3. **Hohfeld 对偶机检**:把 claim-duty 对偶写成约束
   (`a_claim_b ↔ b_duty_a`),加进实验,构造一个"有请求权却无
   相应义务"的病态规则集让检查器报警——03 章✨④的亲手复现

**🧠 认知升维**:
- **可判定眼**:命题层的"矛盾/漏洞"是免费的,一阶以上与
  权衡层不是——先问自己站在这条线的哪一边
- **情形相对眼**:规则"没冲突"永远只是"尚未在此情形下冲突"
  ——一致性是相对于事实集的性质
- **预设眼**:每个形式化系统背后都站着一个没写进代码的
  解释者——找出它,是审查任何"法律 AI"的第一动作
