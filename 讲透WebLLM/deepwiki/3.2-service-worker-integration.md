  This page documents the Service Worker integration in WebLLM, which enables running Large Language Models in a persistent background context. Unlike Web Workers (covered in [Web Worker Integration](https://deepwiki.com/mlc-ai/web-llm/3.1-web-worker-integration)), Service Workers can persist across page reloads and continue running even when a user navigates away from the page, making them ideal for long-running inference tasks or applications that benefit from keeping models loaded.

 
## Purpose and Benefits

 Service Workers in WebLLM enable several key capabilities:

 
 - **Persistence**: Models remain loaded in the background even when users navigate away from the page
 - **Offline capabilities**: Cached models can be used without network connection
 - **Performance**: Reduced startup time for returning users as models stay loaded
 - **Chrome Extensions**: Essential for running WebLLM in browser extensions
 
 The primary use cases include web applications that need to maintain model state across page refreshes, Progressive Web Apps (PWAs), and Chrome extensions that provide AI capabilities.

### Message Types

 Communication between client and Service Worker uses standardized message formats:

 
| Message Type | Direction | Purpose |
|---|---|---|
| WorkerRequest | Client → Service Worker | Request operations like model loading, inference |
| WorkerResponse | Service Worker → Client | Return results or errors |
| keepAlive | Client → Service Worker | Prevent Service Worker termination |
| heartbeat | Service Worker → Client | Confirm Service Worker is active |
| initProgressCallback | Service Worker → Client | Report model loading progress |

 Key fields in messages:

 
 - `kind`: Type of message (e.g., "reload", "runtimeStatsText")
 - `uuid`: Unique identifier to match requests with responses
 - `content`: The payload containing request parameters or response data

## Keep-Alive Mechanism

 Service Workers are designed to be terminated when idle. WebLLM prevents this with a keep-alive mechanism:

 
 - `ServiceWorkerMLCEngine` periodically sends `keepAlive` messages (default: every 10 seconds)
 - `ServiceWorkerMLCEngineHandler` responds with `heartbeat` messages
 - `ServiceWorkerMLCEngine` tracks missed heartbeats to detect if the Service Worker was terminated
 
 This mechanism prevents the browser from terminating the Service Worker while models are loaded, which would require re-loading them when the user interacts again.

## Error Handling

 Several error types are defined for Service Worker integration:

 
| Error Type | Description |
|---|---|
| NoServiceWorkerAPIError | Thrown when Service Worker API is not available in the browser |
| NonWorkerEnvironmentError | Thrown when trying to create handler outside a worker context |
| ServiceWorkerInitializationError | Thrown when Service Worker initialization fails |

 Proper error handling should include:

 
 - Checking if Service Worker API is available
 - Fallback mechanism when Service Workers aren't supported
 - Handling missed heartbeats that indicate Service Worker termination

## Best Practices

 
 - **Model Loading Strategy**: Load smaller models when using Service Workers to reduce memory pressure
 - **Error Handling**: Implement fallback to standard WebWorkers when Service Workers aren't available
 - **Service Worker Updates**: Implement proper update mechanism for Service Worker code
 - **Keep-Alive Tuning**: Adjust the keep-alive interval based on your application's needs
 - **Memory Management**: Be aware that Service Workers can be terminated if system memory is low
 - **Feature Detection**: Always check for Service Worker support before attempting to use it
