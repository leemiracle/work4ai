# 01 · LLM 完整生命周期 — pretrain → SFT → RL → deploy → eval

> **本篇是讲透LLM 的核心整合章**。把 LLM 从"一堆代码"到"上线服务"的完整链路串成一条线，每个阶段**指向项目内的专题深挖目录**——避免重造内容，只做整合叙事。
>
> 与 [`讲透RL/09 §1 工程化 SOP`](../讲透RL/09-工业实践与能力建设.md) 的区别：09 讲 RL 系统全链路，本篇讲 **LLM 全生命周期**（预训练是 LLM 特有的最大工程，RL 只是其中一环）。

## §0 一张图：LLM 完整生命周期

```
┌─────────────────────────────────────────────────────────────────┐
│                   LLM 完整生命周期（5 阶段）                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ① 数据          ② 预训练       ③ 后训练        ④ 部署    ⑤ 评估  │
│  ────────       ────────       ────────       ────────  ──────  │
│  万亿token      next-token     SFT→RLHF       vLLM       bench   │
│  清洗/去重      Scaling Laws   DPO/GRPO       SGLang     human   │
│  配比/质量      FSDP/ZeRO      RLVR/reason    蒸馏/量化  LLM-judge│
│  (讲透数据)     (讲透Transformer)(讲透RL)    (KV Cache) (前沿与媒体)│
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

**成本分布**（粗估，7B 模型为例）：
| 阶段 | GPU 时 | 占比 |
|------|-------|------|
| ① 数据 | 处理 ~千 GPU 时 | 5% |
| ② 预训练 | ~万 GPU 时 | **80%** |
| ③ 后训练（SFT+RL）| ~千 GPU 时 | 10% |
| ④ 部署 | 一次性 | <5% |
| ⑤ 评估 | 持续 | — |

→ **预训练是大头**。这是为什么 LLM 门槛高——预训练 infra 是核心壁垒。

## §1 ① 数据阶段：万物之源

### 1.1 预训练数据（详见 [04 训练数据全景](./04-训练数据全景.md) + [`讲透数据/`](../讲透数据/)）

**规模**：GPT-4 ~13T token，Llama 3 ~15T token，DeepSeek V3 ~14.8T token。

**配比**（Llama 3 公开数据，近似）：
| 类型 | 占比 | 作用 |
|------|------|------|
| 网页文本（Common Crawl）| ~50% | 广度知识 |
| 代码（GitHub）| ~30% | 推理能力 |
| 书籍（Books）| ~10% | 深度知识 |
| 学术（arXiv）| ~5% | 专业知识 |
| 数学 | ~5% | 推理强化 |

**工程关键**：
- **去重**（MinHash / SimHash）—— 数据多份等于浪费算力
- **质量过滤**（fasttext 分类器 / 启发式规则）—— 去垃圾
- **去有害内容**（safety classifier）—— 合规
- **配比调优**—— 代码/数学比例直接影响推理能力

### 1.2 SFT 数据

**规模**：万级 ~ 百万级 (instruction, response) 对。
**质量 >>> 数量**：LIMA 论文证明 1000 条高质量 > 5 万条低质量。
**来源**：人工编写 / 强模型蒸馏（GPT-4 生成）/ 公开数据集（Alpaca/WizardLM/UltraChat）。

### 1.3 RLHF 偏好数据

**规模**：万级 ~ 十万级 preference pair $(y_w, y_l)$。
**成本**：~$20/对（人工标注）。
**挑战**：标注者一致性（inter-annotator agreement）、偏见。
**替代**：AI judge（用 GPT-4 标注，便宜 100×）/ 隐式偏好（点赞/分享）。

## §2 ② 预训练阶段：最大工程

### 2.1 训练目标（详见 [00 §2.1](./00-LLM是什么.md)）

next-token prediction：
$$\mathcal{L} = -\sum_t \log P(x_t | x_{<t}; \theta)$$

### 2.2 Scaling Laws（详见 [`讲透Transformer/07`](../讲透Transformer/07-预训练与ScalingLaws.md)）

**Chinchilla 最优配比**：模型参数 $N$ 和训练 token $D$ 应满足 $D \approx 20N$。

例：训 70B 模型，最优是 ~1.4T token。早期 GPT-3（175B，300B token）**严重欠训练**，Chinchilla（70B，1.4T token）用更少算力超过它。

### 2.3 分布式训练 infra（详见 [`讲透分布式AI系统/`](../讲透分布式AI系统/)）

| 并行策略 | 切什么 | 适用 |
|---------|-------|------|
| **数据并行（DP）**| 数据 | 模型放得下单卡 |
| **ZeRO / FSDP** | 优化器状态/梯度/参数 | 模型放不下但能切 |
| **张量并行（TP）**| 矩阵 | 单层放不下 |
| **流水线并行（PP）**| 层 | 超大模型（千亿）|
| **序列并行（SP）**| 序列 | 长上下文 |

**DeepSeek V3 的 MTP（Multi-Token Prediction）**：一次预测多个 token，训练效率提升 ~15%。

### 2.4 预训练的稳定性（坑最多）

| 现象 | 根因 | 解法 |
|------|------|------|
| loss spike | 学习率过大 / 数据异常 | 学习率 warmup + cosine decay |
| 发散 | 梯度爆炸 | 梯度裁剪 / QK-norm |
| 慢 | 通信瓶颈 | overlap 计算/通信 / 选好 all-reduce 拓扑 |
| loss 不降 | 数据问题 / 架构 bug | sanity check（overfit 小数据集）|

## §3 ③ 后训练阶段：从 base 到 aligned

### 3.1 SFT（监督微调）

**目标**：让 base model 学会"遵循指令"。
**方法**：监督学习 $\max \log P(\text{response} | \text{instruction})$。
**效率**：用 LoRA/QLoRA（[`讲透微调/`](../讲透微调/)）只训 <1% 参数，省显存。

### 3.2 对齐 RL（详见 [`讲透RL/03`](../讲透RL/03-RLHF-DPO-GRPO.md)）

| 算法 | 核心 | 何时用 |
|------|------|--------|
| **RLHF (PPO)** | RM + PPO 在线优化 | 资源充足，要最强 |
| **DPO** | 跳过 RM，闭式解 | 资源紧，要稳定 |
| **GRPO** | 群组相对优势，省 critic | reasoning 强化（DeepSeek-R1）|

### 3.3 RLVR：reasoning 的突破（详见 [`讲透RL/05`](../讲透RL/05-RLVR的极限.md)）

**DeepSeek-R1 的启示**：当 reward 可验证（数学有答案/代码能跑/证明能 Lean 验证），RL 极其有效。

**但 RLVR 有天花板**（[`讲透RL/05`](../讲透RL/05-RLVR的极限.md) pass@k 反转）：RLVR 是**锐化器不是发现器**——它放大模型已有的能力，但不创造全新能力。

### 3.4 后训练框架（详见 [`讲透RL/07 §4`](../讲透RL/07-2026最新研究全景.md) + [`前沿与媒体/02`](../前沿与媒体/02-后训练信息源专题.md)）

| 框架 | 特点 |
|------|------|
| **verl**（字节，22.8k⭐）| Full-stack，PPO/GRPO/RLOO |
| **OpenRLHF**（地平线）| 模块化 |
| **TRL**（HuggingFace）| 与 transformers 集成 |
| **AReaL**（蚂蚁，待核）| 异步 + 长上下文 |

## §4 ④ 部署阶段：把模型推上线

### 4.1 推理优化（详见 [`讲透Transformer/09`](../讲透Transformer/09-推理优化.md) + [`讲透KV Cache/`](../讲透KV Cache/)）

| 技术 | 加速点 |
|------|-------|
| **KV Cache** | 避免重算历史 key/value |
| **PagedAttention**（vLLM）| 高效显存管理，支持并发 |
| **量化**（INT8/INT4）| 减显存 + 提速 |
| **蒸馏** | 大模型 → 小模型 |
| **投机解码**（Speculative Decoding）| 小模型起草 + 大模型校验 |

### 4.2 Serving 框架（详见 [03 工程全栈](./03-工程全栈.md)）

| 框架 | 特点 |
|------|------|
| **vLLM**（UC Berkeley）| PagedAttention，吞吐最高 |
| **SGLang** | RadixAttention，结构化生成强 |
| **TensorRT-LLM**（NVIDIA）| 极致延迟 |
| **llama.cpp** | CPU/边缘部署 |

### 4.3 部署的工程要求（呼应 [`讲透RL/09 §1④`](../讲透RL/09-工业实践与能力建设.md)）

| 要求 | 指标 |
|------|------|
| 首 token 延迟（TTFT）| <500ms |
| 每 token 延迟 | <50ms |
| 吞吐量 | tokens/s/GPU |
| 并发 | sessions/GPU |
| 显存 | model + KV cache |

## §5 ⑤ 评估阶段：怎么知道模型好不好

### 5.1 评估栈（详见 [`前沿与媒体/`](../前沿与媒体/) + [`高效AI前沿`](../高效AI前沿-全行业热点地图.md)）

| 层级 | 方法 | 成本 |
|------|------|------|
| **自动 benchmark** | MMLU/HumanEval/GSM8K | 低 |
| **动态 benchmark** | LiveBench（防污染）| 低 |
| **RM 评分** | reward model 打分 | 低（但有偏）|
| **LLM-as-judge** | GPT-4 当裁判 | 中 |
| **Human eval** | 盲测对比 | 高（金标准）|

### 5.2 评估的坑（呼应 [`讲透RL/09 §2.4`](../讲透RL/09-工业实践与能力建设.md)）

- **benchmark 污染**：测试题泄露进训练数据 → 用 LiveBench/动态题
- **过拟合 benchmark**：刷 MMLU 但真实能力没涨 → 多 benchmark 交叉验证
- **采样敏感**：同一模型不同温度差很多 → 报告方差

## §6 全生命周期的迭代闭环

```
上线后收集 bad case
        │
        ▼
人工标注 / AI judge
        │
        ▼
进 SFT/RLHF 数据 ──→ 重训 ──→ 新模型
        │                          │
        └──── shadow mode 对比 ────┘
                    │
                    ▼
              A/B 测试 → 全量切流
                    │
                    ▼
              监控 + 回滚预案
```

**这是 LLM 产品的数据飞轮**——上线不是终点，而是下一轮训练的起点。

---

## §7 一句话总结

> 🎯 **5 句话**：
> 1. **LLM 生命周期 5 阶段**：数据 → 预训练（成本 80%）→ 后训练（SFT+RL）→ 部署 → 评估。
> 2. **预训练是最大工程**：万亿 token + Scaling Laws + 分布式 infra（FSDP/ZeRO/TP/PP）。
> 3. **后训练三层**：SFT（指令）→ RLHF/DPO（对齐）→ RLVR（reasoning 强化）。
> 4. **部署三件套**：vLLM（吞吐）+ 量化（省显存）+ KV Cache（避免重算）。
> 5. **评估要隔离训练 reward**：benchmark 会污染/过拟合，必须动态 benchmark + human eval 交叉。
