## §1 ① 训练 infra：怎么训大模型

### 1.1 分布式并行策略（详见 [`讲透分布式AI系统/`](../讲透分布式AI系统/)）

LLM 训练的核心挑战：**模型放不下一张卡**。

| 策略 | 切什么 | 适用规模 | 工具 |
|------|-------|---------|------|
| **数据并行（DP）**| 数据分批 | <单卡显存 | torch DDP |
| **ZeRO / FSDP** | 优化器状态/梯度/参数切片 | 单机多卡 | DeepSpeed / PyTorch FSDP |
| **张量并行（TP）**| 矩阵内切 | 单层放不下 | Megatron-LM |
| **流水线并行（PP）**| 按层切 | 千亿模型 | Megatron / DeepSpeed |
| **序列并行（SP）**| 序列切 | 长上下文 | Ring Attention |

**实战组合**（7B-70B 常用）：
- 7B：FSDP（单机 8 卡）
- 70B：FSDP + TP（多机）
- 405B（Llama 3.1 规模）：3D 并行（DP + TP + PP）

### 1.2 训练框架对比

| 框架 | 特点 | 适用 |
|------|------|------|
| **HuggingFace Accelerate** | 轻量封装，易用 | 入门 / 中小模型 |
| **DeepSpeed** | ZeRO 鼻祖，配置驱动 | 中大模型 |
| **Megatron-LM**（NVIDIA）| TP/PP 强 | 超大模型 |
| **PyTorch FSDP** | 原生 FSDP | 现代默认 |
| **TorchTitan** | PyTorch 官方全栈 | 2025+ 推荐 |
| **MaxText**（Google）| TPU/JAX | Google 生态 |

### 1.3 训练稳定性（坑最多）

| 现象 | 根因 | 解法 |
|------|------|------|
| **loss spike** | 学习率 / 数据 batch 异常 | warmup + gradient clipping |
| **OOM** | 激活值过大 | gradient checkpointing / 减 batch |
| **通信瓶颈** | all-reduce 慢 | overlap 计算/通信 / NCCL 调优 |
| **节点故障** | 大集群硬件故障率高 | checkpoint 频率 / 自动恢复 |

**关键工程实践**：
- **梯度裁剪**（max_grad_norm=1.0）：防梯度爆炸
- **gradient checkpointing**：用计算换显存（省 30%+ 显存，慢 20%）
- **混合精度**（bf16）：省显存 + 提速，bf16 比 fp16 稳定
- **频繁 checkpoint**：万卡集群几小时就有一个节点挂

## §2 ② 推理 serving：怎么把模型上线

### 2.1 推理优化的核心：KV Cache（详见 [`讲透KV Cache/`](../讲透KV Cache/)）

**自回归生成的瓶颈**：每生成一个 token，要重算所有历史 token 的 attention。

**KV Cache**：把历史 token 的 key/value 缓存，避免重算。

```
无 KV Cache: 每步 O(n²) → 慢
有 KV Cache: 每步 O(n)  → 快，但显存占用大
```

**KV Cache 的显存账**（7B 模型，1K 上下文）：
- 每层 KV：2 × 4096 × 1024 × 2 byte（fp16）≈ 16 MB
- 32 层：~500 MB / 请求
- 1000 并发：500 GB！

→ **这就是 PagedAttention 要解决的问题**。

### 2.2 推理引擎对比（详见 [`讲透Transformer/09`](../讲透Transformer/09-推理优化.md)）

| 引擎 | 核心创新 | 优势 |
|------|---------|------|
| **vLLM**（UC Berkeley）| **PagedAttention**（操作系统式显存管理）| 吞吐量最高 |
| **SGLang** | **RadixAttention**（前缀复用）| 结构化生成强 |
| **TensorRT-LLM**（NVIDIA）| TensorRT 编译优化 | 延迟最低 |
| **llama.cpp** | GGUF 量化格式 | CPU/边缘 |
| **MLC-LLM** | 编译到各平台 | 移动端 |

### 2.3 量化：让大模型跑在消费级硬件（详见 [`讲透Transformer/09`](../讲透Transformer/09-推理优化.md)）

| 量化 | 精度损失 | 显存（7B）|
|------|---------|----------|
| FP16（基线）| 0 | 14 GB |
| INT8 | <1% | 7 GB |
| INT4（AWQ/GPTQ）| 1-3% | 4 GB |
| 2-bit（极致）| 5%+ | 2 GB |

### 2.4 投机解码（Speculative Decoding）：用小模型加速大模型

```
小模型（draft）快速生成 N 个 token
    ↓
大模型（target）一次性验证这 N 个 token
    ↓
接受的 token 直接用，拒绝的用大模型的
    ↓
加速 2-3×（无损精度）
```

## §3 ③ 监控：上线后怎么保证质量

### 3.1 监控的四类信号

| 类型 | 指标 | 工具 |
|------|------|------|
| **性能** | TTFT / TPOT / 吞吐 / 并发 | Prometheus + Grafana |
| **资源** | GPU 利用率 / 显存 / 网络 | nvidia-smi / DCGM |
| **质量** | 用户反馈 / bad case 率 | 自建 pipeline |
| **成本** | $/token / $/request | 云账单 |

### 3.2 质量监控（最难）

**痛点**：LLM 输出是开放式文本，没有标准答案，怎么知道质量在降？

**方法**：
- **用户反馈**：点赞/点踩/重生成率（隐式质量信号）
- **LLM-as-judge**：用另一个模型给输出打分（成本可控）
- **bad case 采样**：人工抽检 1% 流量
- **回归测试集**：固定的 golden set，每次发版跑一遍

### 3.3 分布漂移（呼应 [`讲透RL/09 §2.3`](../讲透RL/09-工业实践与能力建设.md)）

LLM 部署后的分布漂移：
- **输入分布**：用户问的题目类型变了（如考试季数学题多）
- **对抗输入**：用户尝试越狱（prompt injection）
- **数据污染**：模型输出被复用为下一版训练数据（递归污染）

**防御**：输入监控（embeddings 漂移检测）+ 对抗测试 + 数据来源审计。

## §5 一句话总结

> 🎯 **5 句话**：
> 1. **训练 infra 核心**：分布式并行（FSDP/ZeRO/TP/PP）+ 混合精度 + 频繁 checkpoint。
> 2. **推理 serving 核心**：KV Cache（避免重算）+ PagedAttention（显存管理）+ 量化（省显存）。
> 3. **vLLM 是吞吐之王**（PagedAttention），TensorRT-LLM 是延迟之王，llama.cpp 是边缘之王。
> 4. **量化让大模型上消费级硬件**：INT4 几乎无损，4-bit 的 70B 能跑单卡。
> 5. **监控四类信号**：性能 + 资源 + 质量 + 成本，质量监控（LLM-as-judge）最难也最关键。
