# 01 · VERISPECGEN：从需求到 spec

> 承接 [00-神经符号循环为什么是新范式](./00-神经符号循环为什么是新范式.md)。00 证明了"LLM 生成 + 符号验证"闭环能创造奇迹（AlphaProof IMO 银牌、Delta-Prover 95.9%）。但留了一个根本问题：**验证的前提是有 spec**——如果连 spec 都没有，验证个什么？

本章讲 VERISPECGEN：如何让 LLM 自己把自然语言需求**合成为** Lean4 形式化规格（spec），打通神经符号闭环最难的"第一公里"。

---

## 直觉层

### 一个具体时刻

> 想象你是 2024 年 DeepMind 的工程师。AlphaProof 拿了 IMO 银牌，团队欢呼。但你翻开源码发现：每道题的 Lean4 形式化命题**是 PhD 数学家手写的**。也就是说，"AI 解奥数题"的真相是"AI 在人类已经翻译好的形式化语言里搜索证明"。你心里一凉——这不可扩展。

**角色**：你（AI 系统设计师）。**冲突**：神经符号闭环很强，但它依赖一个 bottleneck——人类手写 spec。**时刻**：你看着 IMO 那块银牌，意识到"瓶颈不在解，在题"。

这就是 VERISPECGEN 要解决的问题：**让 LLM 自己从自然语言需求生成 Lean4 spec**，把闭环的第一公里也自动化。

### 为什么这是真问题

软件工程里 70% 的 bug 不是"实现错了"，是"需求根本没说清"。形式化验证社区一直默认 spec 由人类写——但人类写 spec 的成本是写代码的 5-10 倍。**没有自动 spec 合成，神经符号永远停留在 demo 阶段**。

---

## 数学层

### spec 合成的形式化定义

给定自然语言需求 $NL$（一段英文描述），目标是在形式语言 $\mathcal{L}$（如 Lean4）中找到 spec $S$，使得：

$$S = \arg\min_{s \in \mathcal{L}} \; \text{KL}(P_{\text{意图}} \;\|\; P_s)$$

其中 $P_{\text{意图}}$ 是需求方心里的真实意图分布，$P_s$ 是 spec $s$ 在 Lean4 解释器下蕴含的程序行为分布。**好 spec = KL 散度接近 0**——这正是元理论里"故事与数据脱节即 KL>0"的工程化版本。

### 原子分解的关键不等式

VERISPECGEN 不直接合成大 spec，而是**原子分解**：

$$\text{KL}(P_{\text{意图}} \| P_S) \;\le\; \sum_{i=1}^{n} \text{KL}(P_{\text{意图}_i} \| P_{s_i})$$

把大需求拆成 $n$ 个原子断言（前置条件、后置条件、不变量），每个原子的 KL 更容易压低。**这是熵治理在 spec 合成上的直接体现**——用正交分解降描述熵。

**适用边界**：原子之间必须真正独立。如果原子间有隐含耦合（如"列表非空" + "首元素为 0"实际依赖），分解反而放大 KL。

## 代码层

VERISPECGEN 的核心 pipeline（伪代码，完整实现见论文 [arXiv:2412.17125]）：

```python
def verispecgen(natural_language_req: str) -> Lean4Spec:
    # 步骤 1：LLM 做原子分解（降熵）
    atoms = llm_decompose(natural_language_req)
    # 例：「栈的 push 后 size+1，pop 后 size-1，空栈 pop 报错」
    # → [precondition: ..., postcondition_push: ..., ...]

    # 步骤 2：每个原子单独翻译成 Lean4（正交合成）
    lean4_atoms = [nl_to_lean4(atom) for atom in atoms]

    # 步骤 3：可溯性标注（每个 Lean4 token 追溯到原 NL 片段）
    traced = add_provenance(lean4_atoms, atoms)

    # 步骤 4：Lean4 类型检查器拒绝错误 spec（硬门）
    for spec in candidate_combinations(traced):
        if lean4_type_check(spec).ok:
            return spec  # 第一个能通过类型检查的组合
    raise SpecSynthesisFailed
```

**反直觉数字**：VERISPECGEN 在真实 Rust crate benchmark 上，**87% 的 spec 能被自动合成并通过类型检查**，其中 62% 与人类专家手写的 spec 语义等价。剩余 25% 是"语法正确但语义偏移"——这正是下一步（对抗层）要查的。

## 不足层

诚实标注 VERISPECGEN 的边界：

- **已证明的**：原子分解的 KL 上界不等式（数学层公式 2）。
- **经验但未证**：87% 通过率——这是 benchmark 经验数，无理论保证。换领域（如并发程序）可能骤降。
- **未解**：
  1. **隐含耦合检测**：原子间耦合如何自动发现？目前靠人类 review。
  2. **意图漂移**：LLM 在翻译时可能"自作主张"修正需求方的措辞，引入 25% 的语义偏移。
  3. **spec 完备性**：合成的 spec 可能**遗漏**需求方没说但心里有的约束（未言明的假设）。

## 费曼回炉记录（L2 自检）

- **F2 卡壳点**：我最初把 KL 散度公式写成 $\text{KL}(P_s \| P_{\text{意图}})$（方向反了）。重读后发现，spec 是"近似意图"的一方，应该是 $P_{\text{意图}}$ 作为 reference，spec 分布作为近似——方向必须是 $\text{KL}(P_{\text{意图}} \| P_s)$。
- **F3 术语翻译**：
  - "Lean4 spec" → 用 Lean4 语言写的一句话：什么样的程序算对。
  - "原子分解" → 把"栈操作正确"拆成"push 后 size+1""pop 后 size-1""空栈 pop 报错"三个独立小断言。
  - "可溯性" → 每个 Lean4 token 都能指回原文哪句话，方便 review。
- **F4 回炉**：v1 把 pipeline 写成单步 LLM 调用；v2 改成"分解→翻译→溯回→类型检查"四步，因为单步生成没有硬门（类型检查），KL 压不下去。
