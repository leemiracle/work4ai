# Communication Modes and Topology

  DeepEP V2 introduces a unified communication model that replaces the V1 distinction between "normal" and "low-latency" modes with a more flexible **Elastic** architecture. This page explains the topology modeling, the hybrid communication mode for hierarchical RDMA and NVLink transfers, and how physical hardware domains map to logical expert domains.

 
## Overview of V2 Architectural Shift

 In DeepEP V2, the architectural shift from NVSHMEM to the **NCCL Gin** backend [README.md9-11](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L9-L11) allows for a more integrated approach to topology. V2 unifies high-throughput and low-latency paths into the `ElasticBuffer` interface [README.md17-18](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L17-L18)

 
| Feature | DeepEP V1 | DeepEP V2 (Elastic) |
|---|---|---|
| Backend | NVSHMEM README.md39 | NCCL Gin README.md9 |
| Topology | Flat RDMA or NVLink | Hierarchical Scale-up + Scale-out README.md19 |
| SM Allocation | Manual via set_num_sms | Analytical via get_theoretical_num_sms README.md158-160 |
| Hybrid Mode | Supported via separate kernels | Integrated via allow_hybrid_mode flag csrc/kernels/backend/nccl.cu65-66 |
| Low-Latency | Pure RDMA (IBGDA) | Integrated into Elastic kernels (low SM usage) README.md22 |

## Topology Model: Scale-up vs. Scale-out

 DeepEP V2 models the cluster as a two-dimensional grid of GPUs. This allows the library to optimize data movement based on the available interconnects (NVLink for high-bandwidth local transfers and RDMA for cross-node transfers).

 
### Physical vs. Logical Domains

 DeepEP distinguishes between the physical hardware layout and the logical expert parallelism layout:

 
 - **Physical Domain**: 
 - **RDMA Ranks (`num_rdma_ranks`)**: The number of nodes or independent network planes in the cluster. Calculated as total ranks divided by local NVLink ranks [csrc/kernels/backend/nccl.cu51-113](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L51-L113)
 - **NVLink Ranks (`num_nvl_ranks`)**: The number of GPUs within a single node or LSA (Local Shared Area) domain, retrieved via `ncclTeamLsa` [csrc/kernels/backend/nccl.cu51-112](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L51-L112)
 - **Logical Domain**: 
 - **Scale-out Ranks (`num_scaleout_ranks`)**: The number of expert-parallel groups across nodes [csrc/kernels/backend/nccl.cu59-123](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L59-L123)
 - **Scale-up Ranks (`num_scaleup_ranks`)**: The number of expert-parallel ranks within the local communication domain [csrc/kernels/backend/nccl.cu59-123](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L59-L123)
 
 The mapping depends on the `allow_hybrid_mode` flag. If hybrid mode is disabled, the logical scale-up domain encompasses the entire world (all ranks), and scale-out is effectively bypassed [csrc/kernels/backend/nccl.cu58-124](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L58-L124)

## Communication Modes

 DeepEP V2 supports two primary operational modes controlled by the `allow_hybrid_mode` flag during `ElasticBuffer` initialization [csrc/kernels/backend/nccl.cu65-85](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L65-L85)

 
### 1. Direct (Non-Hybrid) Mode

 In direct mode (`allow_hybrid_mode=False`), tokens are sent directly from the source GPU to the destination GPU across the entire world.

 
 - **When to use**: Intranode-only training, small scale-out domains, or when RDMA bandwidth is not the primary bottleneck.
 - **Mechanism**: Logical scale-up domain is set to the total number of ranks [csrc/kernels/backend/nccl.cu58-123](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L58-L123) The backend uses `NCCL_GIN_CONNECTION_FULL` for the device communicator [csrc/kernels/backend/nccl.cu98-99](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L98-L99)
 
 
### 2. Hybrid Mode

 Hybrid mode implements hierarchical communication. It is specifically designed to optimize the DeepSeek-V3/R1 "Group-Limited Gating" algorithm by utilizing RDMA for inter-node and NVLink for intra-node transfers.

 
 - **When to use**: Large-scale training (e.g., EP256+) where RDMA resources are precious and tokens are grouped by node.
 - **Mechanism**: 
 - **Scale-out Phase**: Tokens are sent via RDMA to the target node using `NCCL_GIN_CONNECTION_RAIL` [csrc/kernels/backend/nccl.cu98-99](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L98-L99)
 - **Scale-up Phase**: Intra-node distribution is handled via NVLink within the LSA domain [csrc/kernels/backend/nccl.cu111-112](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L111-L112)

## Implementation Detail: NCCL Gin Backend

 V2 replaces the NVSHMEM-based transport with **NCCL Gin** [README.md9](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L9-L9) This backend provides lightweight `put`/`get` primitives and supports multiple "teams" to handle the topology described above.

 
### Team Tags and Connections

 The backend uses different connection types based on the mode [csrc/kernels/backend/nccl.cu98-99](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L98-L99):

 
 - **`NCCL_GIN_CONNECTION_FULL`**: Used for direct mode to allow any-to-any communication across all ranks.
 - **`NCCL_GIN_CONNECTION_RAIL`**: Used for hybrid mode to optimize RDMA rails between nodes.
 
 In the kernel, these are mapped to team tags such as `ncclTeamTagWorld` or `ncclTeamTagRail` [deep_ep/include/deep_ep/common/comm.cuh137-162](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L137-L162)

 
### Symmetric Memory and Windows

 The `NCCLSymmetricMemoryContext` manages the registration of memory windows across the communicator [csrc/kernels/backend/nccl.cu129-140](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L129-L140) It allows GPUs to access remote memory via `ncclGetLsaDevicePointer` for local NVLink peers [csrc/kernels/backend/nccl.cu141-147](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L141-L147)

## Comparison with V1 Modes

 The V2 `ElasticBuffer` provides a superior replacement for V1's manual mode selection.

 
| Metric | V1 Normal | V1 Low-Latency | V2 Elastic |
|---|---|---|---|
| SM Usage | High (fixed) | Near-zero | Analytical (4-12 typical) README.md22-51 |
| Throughput | Baseline | Lower | Up to 1.3x higher README.md55 |
| Complexity | Two APIs | Two APIs | Single API README.md18 |
| Tuning | Manual Config | Manual Config | Analytical (No tuning) README.md20 |

 
### Resource Sharing and QPs

 DeepEP V2 kernels dynamically allocate Queue Pairs (QPs) based on the SM count. The function `get_qp_mode` determines if a QP is shared at the CTA or GPU level [deep_ep/include/deep_ep/common/comm.cuh56-64](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L56-L64) If the number of SMs is less than or equal to available QPs, each SM gets a dedicated QP with `NCCL_GIN_RESOURCE_SHARING_CTA` [deep_ep/include/deep_ep/common/comm.cuh73-80](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L73-L80) Otherwise, QPs are shared across the grid using `NCCL_GIN_RESOURCE_SHARING_GPU` [deep_ep/include/deep_ep/common/comm.cuh81-85](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L81-L85)
