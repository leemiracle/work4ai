# Pipeline Parallelism and AGRS

  Relevant source files 
 - [csrc/kernels/elastic/pp_send_recv.hpp](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/elastic/pp_send_recv.hpp)
 - [deep_ep/include/deep_ep/impls/pp_send_recv.cuh](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh)
 - [tests/elastic/test_agrs.py](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_agrs.py)
 
  This page documents the experimental high-performance communication primitives in DeepEP V2 beyond Expert Parallelism: **Pipeline Parallelism (PP)** and **All-Gather Reduce-Scatter (AGRS)**. Both features leverage the **NCCL Gin backend** to achieve near-zero SM occupation during communication by offloading RDMA operations.

 
### 1. Pipeline Parallelism (PP)

 DeepEP provides an experimental 0-SM Pipeline Parallelism API designed for high-throughput point-to-point communication between adjacent ranks in a ring topology. Unlike standard NCCL point-to-point calls, these primitives are optimized for RDMA-based transfers that minimize CPU and GPU SM involvement by utilizing NVLink and InfiniBand hardware offloads via the Gin backend.

 
#### 1.1 Topology Constraints and Configuration

 The PP implementation in DeepEP is currently restricted to a ring topology where a rank can only communicate with its immediate `prev` and `next` neighbors. The `get_buffer_offset` helper function determines the internal buffer index based on whether the destination is the `next_rank_idx` or `prev_rank_idx` [deep_ep/include/deep_ep/impls/pp_send_recv.cuh12-16](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L12-L16)

 The configuration is managed via `pp_set_config`, which establishes the peer relationships and buffer allocations for the pipeline [csrc/elastic/buffer.hpp66](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L66-L66) Users must also calculate the required workspace using `get_pp_buffer_size_hint` to ensure the `ElasticBuffer` has sufficient memory for the P2P windows [csrc/elastic/buffer.hpp67-68](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L67-L68)

 
#### 1.2 PP Implementation (pp_send_impl)

 The underlying kernel implementation `pp_send_impl` uses a combination of **TMA (Tensor Memory Accelerator)** for local data movement and **NCCL Gin** for remote RDMA `put` operations [deep_ep/include/deep_ep/impls/pp_send_recv.cuh119-130](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L119-L130)

 
 - **TMA Copy**: The kernel uses `tma_copy` to pipeline data from local source tensors into the Gin-registered symmetric buffer. It utilizes `ptx::mbarrier` to synchronize TMA loads and stores across multiple stages [deep_ep/include/deep_ep/impls/pp_send_recv.cuh44-112](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L44-L112)
 - **Signal Synchronization**: It implements a timeout-aware signal check (`check_signal`) using `ptx::ld_acquire_sys` to ensure the destination buffer slot is released by the receiver before initiating the next send [deep_ep/include/deep_ep/impls/pp_send_recv.cuh19-36](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L19-L36)
 - **RDMA Put**: Once data is staged locally, the first SM issues a `gin.put<ncclTeamTagWorld>` to transfer data to the remote peer's `recv_buffer_ptr` [deep_ep/include/deep_ep/impls/pp_send_recv.cuh155-161](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L155-L161)

### 2. All-Gather Reduce-Scatter (AGRS)

 The AGRS API is an experimental feature designed to provide efficient All-Gather and Reduce-Scatter operations, typically used for Data Parallelism (DP) or Tensor Parallelism (TP) weight/gradient synchronization. It introduces a "Session" abstraction to manage the state and temporary buffers required for these collective operations.

 
#### 2.1 AGRS Session Management

 DeepEP uses a session-based approach to minimize allocation overhead and manage concurrent AGRS operations.

 
 - **`create_agrs_session`**: Allocates the necessary resources for AGRS operations within an `ElasticBuffer` [csrc/elastic/buffer.hpp73](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L73-L73)
 - **`destroy_agrs_session`**: Releases session-specific resources [csrc/elastic/buffer.hpp74](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L74-L74)
 - **`agrs_new_session`**: A Python context manager used in tests and production to ensure sessions are properly scoped via `create_agrs_session` and `destroy_agrs_session` calls [tests/elastic/test_agrs.py170-174](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_agrs.py#L170-L174)
 - **`agrs_set_config`**: Tunes the session parameters, such as `num_max_agrs_session_bytes` and `num_max_agrs_per_session` [csrc/elastic/buffer.hpp71-72](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L71-L72)
 
 
#### 2.2 Communication Primitives

 
 - **`all_gather`**: Collects tensors from all ranks in the group. It supports both single-tensor and batched modes [tests/elastic/test_agrs.py75-84](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_agrs.py#L75-L84)
 - **`agrs_get_inplace_tensor`**: Returns a view into the symmetric buffer to allow zero-copy (in-place) All-Gather operations [tests/elastic/test_agrs.py63-65](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_agrs.py#L63-L65)
 - **`get_agrs_buffer_size_hint`**: Calculates the total memory required for the AGRS workspace based on the expected session size [tests/elastic/test_agrs.py100-101](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_agrs.py#L100-L101)

### 3. Implementation Details

 
#### 3.1 Zero-SM Communication

 Both PP and AGRS aim for minimized SM occupation. This is achieved by using the `ncclGin` backend to issue RDMA `put`/`get` commands directly from the GPU's copy engines or specialized hardware units. In the `pp_send_impl`, only a single warp (or even a single thread via `elect_one_sync`) is responsible for issuing the RDMA command [deep_ep/include/deep_ep/impls/pp_send_recv.cuh155-156](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L155-L156)

 
#### 3.2 Memory Layout and Symmetric Windows

 For these operations to work across nodes, the `ElasticBuffer` must register its memory with the NCCL Gin backend as a symmetric window.

 
 - **Allocation**: `ElasticBuffer` allocates a contiguous block of memory, partitioning it into Workspace, GPU buffer, and CPU buffer [csrc/elastic/buffer.hpp20-25](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L20-L25)
 - **Registration**: The `NCCLSymmetricMemoryContext` registers this block across all ranks, providing the `ncclWindow_t` used by Gin [csrc/elastic/buffer.hpp111-114](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L111-L114)
 - **Buffer Slots**: For PP, the buffer is partitioned into slots based on `num_max_inflight_tensors` to allow pipelined transfers without overwriting data. Offsets are calculated using `num_max_tensor_bytes` [deep_ep/include/deep_ep/impls/pp_send_recv.cuh135-140](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L135-L140)
