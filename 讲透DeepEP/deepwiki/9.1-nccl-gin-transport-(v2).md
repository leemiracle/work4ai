# NCCL Gin Transport (V2)

  Relevant source files 
 - [csrc/kernels/backend/nccl.cu](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu)
 - [deep_ep/include/deep_ep/common/comm.cuh](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh)
 
  The NCCL Gin backend is the primary communication transport for DeepEP V2, replacing the NVSHMEM-based backend used in V1. It is a header-only, lightweight transport layer designed to provide high-performance RDMA and NVLink primitives (`put`, `get`, and atomic operations) while maintaining a minimal SM footprint. NCCL Gin allows DeepEP to reuse existing NCCL communicators and windows, simplifying deployment in standard distributed training environments.

 
---

 
## Architecture and Key Entities

 The NCCL Gin transport is built around the `ncclGin` handle and the concept of symmetric memory windows. It abstracts hardware-specific RDMA and NVLink operations into a unified device-side API.

 
### Core Components

 
| Entity | Description |
|---|---|
| ncclGin | The primary device-side handle used to perform remote memory operations (put, get, signal). |
| ncclWindow | A symmetric memory registration across a group of GPUs, enabling direct peer access csrc/kernels/backend/nccl.cu140 |
| ncclGinRequest_t | A handle used for tracking the status of non-blocking operations, such as get. |
| ncclTeamTagWorld | Defines the scope of communication for all ranks in the communicator csrc/kernels/backend/nccl.cu51 |
| ncclTeamTagLsa | Defines the scope for Local SM Area (Intranode/NVLink) ranks csrc/kernels/backend/nccl.cu51 |
| ncclTeamTagRail | Defines the scope for ranks in the scale-out domain (RDMA rail) deep_ep/include/deep_ep/common/comm.cuh161 |

 
### Resource Sharing Modes

 NCCL Gin supports modes for managing device-side resources (like Queue Pairs or internal state) via `ncclDevCommRequirements_t` [csrc/kernels/backend/nccl.cu85-99](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L85-L99):

 
 - **`NCCL_GIN_RESOURCE_SHARING_CTA`**: Resources are shared among threads within a single CTA (thread block). This is the default for most DeepEP kernels to maximize concurrency [deep_ep/include/deep_ep/common/comm.cuh59](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L59-L59)
 - **`NCCL_GIN_RESOURCE_SHARING_GPU`**: Resources are shared globally across the entire GPU, typically used when the number of SMs exceeds the available QPs [deep_ep/include/deep_ep/common/comm.cuh60-85](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L60-L85)

## Device-Side API (Device Handle)

 The `ncclGin` handle provides the low-level primitives used by DeepEP's elastic kernels (dispatch, combine, and Engram).

 
### Key Functions

 
| Function | Description |
|---|---|
| put<T>(dst_ptr, src_ptr, size, rank) | Performs a remote write (RDMA Write or NVLink Write) to the target rank. |
| get<T>(dst_ptr, src_ptr, size, rank) | Performs a remote read. Returns a ncclGinRequest_t. |
| signal(team, rank, op) | Performs a remote atomic operation (e.g., ncclGin_SignalInc) for synchronization deep_ep/include/deep_ep/common/comm.cuh164 |
| flush(scope) | Ensures all previous operations on a specific QP are globally visible deep_ep/include/deep_ep/common/comm.cuh146 |
| quiet() | A global synchronization primitive to ensure all previous put operations are completed. |

 
### QP Selection Logic

 DeepEP uses a specialized function `get_qp_mode` to map SMs and warps to specific NCCL Gin Queue Pairs (QPs) [deep_ep/include/deep_ep/common/comm.cuh57-86](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L57-L86) If the number of SMs is less than or equal to available QPs, each SM gets an exclusive QP (`NCCL_GIN_RESOURCE_SHARING_CTA`). Otherwise, QPs are shared across the GPU grid (`NCCL_GIN_RESOURCE_SHARING_GPU`).

## Backend Integration and Configuration

 The NCCL Gin backend is initialized via the `NCCLSymmetricMemoryContext` in the C++ layer [csrc/kernels/backend/nccl.cu62-67](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L62-L67) It handles the allocation of symmetric windows and the setup of communication channels.

 
### Environment Variables and Tuning

 
| Variable | Description |
|---|---|
| EP_DISABLE_GIN | If set to 1, DeepEP falls back to standard NCCL collectives or legacy paths csrc/kernels/backend/nccl.cu86 |
| EP_REUSE_NCCL_COMM | Although DeepEP creates a ncclComm_t, it can reuse properties from existing communicators csrc/kernels/backend/nccl.cu76 |
| EP_NIC_NAME | Specifies the network interface name to use for RDMA operations. |
| EP_OVERRIDE_RDMA_SL | Overrides the RDMA Service Level (SL) via reqs.ginTrafficClass csrc/kernels/backend/nccl.cu95 |
| PCI_ATOMIC_MODE=4 | Required for certain hardware configurations to support RDMA atomics used by Gin. |

 
### Team Tags and Domains

 DeepEP V2 uses logical and physical domains to optimize traffic. NCCL Gin uses tags to route these:

 
 - **`ncclTeamLsa`**: Used for Local SM Area (intranode/NVLink) communication [csrc/kernels/backend/nccl.cu51](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L51-L51)
 - **`ncclTeamWorld`**: Used for the global communication group [csrc/kernels/backend/nccl.cu51](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L51-L51)
 - **`ncclTeamRail`**: Used for railed (scale-out) communication when `allow_hybrid_mode` is enabled [csrc/kernels/backend/nccl.cu98](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L98-L98)

## Hardware and Networking Recommendations

 To achieve peak performance with the NCCL Gin transport, the following hardware configurations are recommended:

 
 - **Adaptive Routing**: Highly recommended for InfiniBand networks to prevent congestion during the heavy all-to-all traffic patterns typical of MoE dispatch.
 - **PCI Atomics**: Ensure `PCI_ATOMIC_MODE=4` is set in the environment or driver configuration, as RDMA atomics are critical for low-latency signaling.
 - **Service Levels**: Use `EP_OVERRIDE_RDMA_SL` to isolate DeepEP traffic from other network traffic if necessary to maintain consistent latency [csrc/kernels/backend/nccl.cu95](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/nccl.cu#L95-L95)
 
 
### Synchronization and Barriers

 DeepEP V2 implements custom barriers using NCCL Gin primitives to minimize overhead:

 
 - **`nvlink_barrier_wo_local_sync`**: A low-latency barrier for NVLink domains using `ptx::red_add_rel_sys` [deep_ep/include/deep_ep/common/comm.cuh89-129](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L89-L129)
 - **`gin_barrier_wo_local_sync`**: A global barrier using `gin.signal` and `ncclTeamRail` or `ncclTeamWorld` [deep_ep/include/deep_ep/common/comm.cuh135-165](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/comm.cuh#L135-L165)
