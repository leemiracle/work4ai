  Engram is an experimental feature in DeepEP V2 designed for high-performance remote memory access, primarily targeting KV cache fetching in inference scenarios. It allows ranks to directly read from or write to the memory of other ranks with near-zero SM (Streaming Multiprocessor) overhead by leveraging RDMA (Remote Direct Memory Access) via the NCCL Gin backend.

 Unlike the primary Expert Parallelism (EP) dispatch and combine operations which involve complex routing and data shuffling, Engram provides a more direct interface for point-to-point remote memory operations.

 
---

 
## Architecture and Data Flow

 Engram operations are built upon the `ncclGin` transport layer. It uses a "get" model where the requesting rank fetches data from a remote rank's symmetric memory.

## Key Functions and Implementation

 
### Python API

 The Engram feature is exposed through the `ElasticBuffer` class:

 
 - **`engram_write`**: Writes local data to the symmetric memory window so it can be accessed by other ranks. It also handles scaling factor (SF) replication for FP8 support. [tests/elastic/test_engram.py53](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_engram.py#L53-L53)
 - **`engram_fetch`**: Initiates a remote read. It returns a **hook callable**. This design allows for asynchronous execution where the user can trigger the fetch and later invoke the hook to ensure the data has arrived. [tests/elastic/test_engram.py67-68](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_engram.py#L67-L68)
 - **`get_engram_storage_size_hint`**: A static method to calculate the required buffer size for storing Engram-related data, considering entries, hidden dimension, and data type. [tests/elastic/test_engram.py17-18](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/tests/elastic/test_engram.py#L17-L18)

### CUDA Kernels: Fetch and Wait

 The core logic resides in two specialized kernels defined in the `deep_ep::elastic` namespace:

 
#### 1. `engram_fetch_impl`

 This kernel issues the RDMA requests. It is designed to be extremely lightweight:

 
 - **Warp-level RDMA**: Each warp fetches one token cooperatively using `gin.get`. [deep_ep/include/deep_ep/impls/engram_fetch.cuh51-55](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/engram_fetch.cuh#L51-L55)
 - **`ncclGinRequest_t`**: The kernel uses `gin.get` with `ncclGinOptFlagsAggregateRequests` to issue RDMA read requests without immediate blocking. [deep_ep/include/deep_ep/impls/engram_fetch.cuh70-74](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/engram_fetch.cuh#L70-L74)
 - **Aggregated Requests**: It issues a `flush_async` per peer to commit all aggregated gets on the same QP. [deep_ep/include/deep_ep/impls/engram_fetch.cuh95-105](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/engram_fetch.cuh#L95-L105)
 - **FP8 Scaling Factors**: If `kNumSFPacks > 0`, the kernel also fetches scaling factors from a local table. [deep_ep/include/deep_ep/impls/engram_fetch.cuh78-88](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/engram_fetch.cuh#L78-L88)
 
 
#### 2. `engram_fetch_wait_impl`

 This kernel handles the synchronization. It is invoked when the Python hook is called:

 
 - **Non-blocking Wait**: It iterates through the `last_gin_requests` (stored as `int4` for atomic loading) and calls `gin.wait(last_gin_req)` for any non-zero request handles. [deep_ep/include/deep_ep/impls/engram_fetch_wait.cuh20-28](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/engram_fetch_wait.cuh#L20-L28)

## Use Cases: KV Cache in Inference

 In Large Language Model (LLM) inference, particularly with Mixture-of-Experts (MoE), KV caches may be distributed across different ranks. When a token is routed to an expert on a remote rank, the model may need to fetch the corresponding KV cache history.

 Engram enables this by:

 
 - **Efficient Retrieval**: Fetching specific slices of remote memory (KV heads) without requiring the remote CPU or a heavy-weight collective operation.
 - **Overlapping**: Because `engram_fetch` returns a hook, the system can issue KV cache fetches while simultaneously performing other computations.

## SM Resource Management

 A key claim of DeepEP V2's Engram feature is **near-zero SM overhead**.

 
| Feature | Mechanism | SM Impact |
|---|---|---|
| Engram Fetch | RDMA get via Gin | Only requires SM for instruction issue; hardware handles transfer. deep_ep/include/deep_ep/impls/engram_fetch.cuh53-89 |
| Engram Wait | Gin wait | Minimal polling until NIC reports completion. deep_ep/include/deep_ep/impls/engram_fetch_wait.cuh20-28 |
| Resource Tuning | num_allocated_qps | Users can specify exactly how many QPs (and thus SMs) to dedicate to Engram. tests/elastic/test_engram.py21-36 |

 In typical configurations, Engram can operate with a limited number of SMs, as the bottleneck is usually the network interface (NIC) rather than GPU compute resources. The implementation uses `kNumEngramFetchThreads = 1024` and `kNumEngramFetchWaitThreads = 1024` to maximize issue throughput within the launched blocks.
