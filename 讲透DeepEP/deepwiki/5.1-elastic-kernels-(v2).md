## Purpose and Scope

 This page documents the V2 elastic kernel implementations located in `deep_ep/include/deep_ep/impls/`. These kernels represent the architectural shift from the V1 NVSHMEM-based backend to the **NCCL Gin backend**, providing a header-only, JIT-compiled communication layer.

 The V2 kernels are designed for high-throughput and low-latency Expert Parallelism (EP) with significantly reduced SM occupation. They support larger scale-up (NVLink) and scale-out (RDMA) domains and utilize an analytical resource allocation model.

 
---

 
## JIT Template Instantiation Pattern

 DeepEP V2 uses a Just-In-Time (JIT) compilation system where kernels are instantiated from templates at runtime. This allows the compiler to optimize for specific hardware and problem dimensions (e.g., hidden size, expert count) without requiring a heavy pre-compiled library.

 Key template parameters used across the implementations include:

 
 - `kNumSMs`: The number of Streaming Multiprocessors allocated to the kernel. [csrc/kernels/elastic/dispatch.hpp59](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/elastic/dispatch.hpp#L59-L59)
 - `kNumQPs`: The number of InfiniBand Queue Pairs used for RDMA. [csrc/kernels/elastic/dispatch.hpp65](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/elastic/dispatch.hpp#L65-L65)
 - `kNumExperts`: The total number of experts in the MoE layer. [csrc/kernels/elastic/dispatch.hpp64](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/elastic/dispatch.hpp#L64-L64)
 - `kNumTopk`: The number of experts selected per token. [csrc/kernels/elastic/dispatch.hpp64](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/elastic/dispatch.hpp#L64-L64)
 - `kHidden`: The hidden dimension size of the tokens. [deep_ep/include/deep_ep/impls/hybrid_combine.cuh15](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/hybrid_combine.cuh#L15-L15)
 - `kAllowMultipleReduction`: Boolean flag to enable/disable summation of tokens from different experts. [deep_ep/include/deep_ep/impls/hybrid_combine.cuh11](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/hybrid_combine.cuh#L11-L11)
 - `kNumTimeoutCycles`: GPU clock cycles before a kernel-side synchronization timeout occurs. [csrc/kernels/elastic/dispatch.hpp65](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/elastic/dispatch.hpp#L65-L65)

## Dispatch Kernels

 The dispatch operation routes tokens from ranks to their assigned experts. V2 provides two primary implementations: `dispatch_impl` (direct) and `hybrid_dispatch_impl` (hierarchical).

 
### Warp Roles

 Within a dispatch kernel, warps are assigned specific roles to maximize overlapping of communication and data movement:

 
| Role | Responsibility |
|---|---|
| Notify | Handles synchronization and metadata exchange (token counts) between ranks using atomic operations. deep_ep/include/deep_ep/impls/dispatch.cuh79-115 |
| Dispatch / Scaleout | Manages RDMA data movement to remote nodes via the Gin backend. deep_ep/include/deep_ep/impls/hybrid_dispatch.cuh30 |
| Forward | Moves data within the local scale-up (NVLink) domain, often using TMA (Tensor Memory Accelerator). deep_ep/include/deep_ep/impls/hybrid_dispatch.cuh31 |

 
### Hybrid Dispatch Flow

 The `hybrid_dispatch_impl` is used for hierarchical communication where data moves across the scale-out domain (RDMA) and the scale-up domain (NVLink) simultaneously or in sequence.

## Combine Kernels

 The combine operation gathers processed tokens from experts back to their original ranks. It includes `combine_impl` and `hybrid_combine_impl`.

 
### Implementation and Reduction

 
 - **Reduction Logic**: The `combine_reduce` utility handles the summation of tokens. It uses `nv_bfloat162` for vectorized addition and supports adding bias tensors during the process. [deep_ep/include/deep_ep/impls/combine_utils.cuh8-39](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine_utils.cuh#L8-L39)
 - **Layout Optimization**: The kernels use `use_rank_layout` to determine if tokens should be organized by rank or by top-k slot, optimizing memory access patterns based on `kNumRanks` and `kNumTopk`. [deep_ep/include/deep_ep/impls/combine.cuh25-26](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine.cuh#L25-L26)
 - **Vectorization**: `CombineVecTraits` selects the optimal vector type (e.g., `int4` or `longlong4_t`) based on hidden size alignment. [deep_ep/include/deep_ep/impls/hybrid_combine.cuh51-52](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/hybrid_combine.cuh#L51-L52)
 - **Copy Epilogue**: The `dispatch_copy_epilogue_impl` is used to move received tokens from the communication buffer into the target tensor, supporting both expand and non-expand layouts. [deep_ep/include/deep_ep/impls/dispatch_copy_epilogue.cuh22-33](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/dispatch_copy_epilogue.cuh#L22-L33)

## Specialized Kernels

 
### Engram Fetch

 The `engram_fetch_impl` (implemented in `engram.hpp` runtime) allows for remote memory access (RMA) of KV caches. It leverages `ncclGin.get` primitives to fetch data from remote ranks with minimal SM overhead.

 
### Pipeline Parallelism (`pp_send_recv`)

 The `pp_send_recv.cuh` implementation provides point-to-point communication for PP stages. It utilizes the NCCL Gin backend for zero-copy transfers between adjacent ranks.

 
 - **Buffer Management**: Uses `get_buffer_offset` to determine the correct slot for next/previous rank communication. [deep_ep/include/deep_ep/impls/pp_send_recv.cuh12-16](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L12-L16)
 - **Pipelined TMA**: Implements `tma_copy` with multi-stage pipelining to overlap TMA loads and stores. [deep_ep/include/deep_ep/impls/pp_send_recv.cuh38-46](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L38-L46)
 
 Sources: [deep_ep/include/deep_ep/impls/pp_send_recv.cuh118-161](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/pp_send_recv.cuh#L118-L161)

 
### Barrier Implementation

 The V2 `barrier_impl` coordinates ranks across both scale-up and scale-out domains.

 
 - **GPU Barrier**: Calls `comm::gpu_barrier` with specific tags like `kKernelBarrierTag`. [deep_ep/include/deep_ep/impls/barrier.cuh24-39](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/barrier.cuh#L24-L39)
 - **Synchronization**: Uses `ptx::mbarrier` and `ptx::named_barrier` for intra-CTA and inter-CTA coordination. [deep_ep/include/deep_ep/common/ptx.cuh56-90](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/ptx.cuh#L56-L90)

## NCCL Gin Backend Integration

 The `ncclGin` handle is the core device-side interface for V2 kernels, replacing NVSHMEM.

 
### Primitives and Team Tags

 The backend uses **Team Tags** to identify logical communication groups:

 
 - `ncclTeamTagWorld`: All ranks in the communicator. [deep_ep/include/deep_ep/impls/combine.cuh27](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine.cuh#L27-L27)
 - `ncclTeamTagLsa` (Local Scale-up Area): Ranks within the same NVLink domain. [deep_ep/include/deep_ep/impls/hybrid_combine.cuh140](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/hybrid_combine.cuh#L140-L140)
 - `ncclTeamTagRail`: Ranks across nodes that share the same local NVLink index (Rail-optimized RDMA).
