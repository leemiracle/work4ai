# Asynchronous Execution and Overlapping

  Relevant source files 
 - [deep_ep/buffers/elastic.py](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py)
 - [deep_ep/utils/event.py](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/utils/event.py)
 
  This page describes DeepEP V2's asynchronous execution mechanisms that enable overlapping communication with computation. These features are essential for achieving high performance in MoE workloads by allowing GPU computation to proceed concurrently with data transfers.

 DeepEP V2 introduces a hook-based communication model that replaces the V1 `return_recv_hook` pattern with a more flexible `async_with_compute_stream` and `previous_event` architecture, fully compatible with the new `ElasticBuffer` and `NCCL Gin` backend.

 
---

 
## Overview

 DeepEP provides asynchronous execution through:

 
 - **Dual-stream architecture**: Separate communication and compute streams.
 - **Event-based synchronization**: `EventOverlap` and `EventHandle` objects for dependency tracking.
 - **Hook-based execution**: `dispatch` and `combine` can return a callable hook to trigger the receive/finish phase.
 - **Analytical Overlap**: `prefer_overlap_with_compute` flag to adjust SM allocation for concurrent execution.
 - **CUDA Graph compatibility**: Via `extra_tensors` and `EventHandle` to avoid CPU-side synchronization.
 
 
### V1 vs V2 Comparison

 
| Feature | V1 (Legacy) | V2 (Elastic) |
|---|---|---|
| Primary Flag | async_finish | async_with_compute_stream |
| Hook Pattern | return_recv_hook=True returns callable | async_with_compute_stream=True returns hook |
| Stream Control | Manual comm_stream management | Automatic via get_comm_stream() and capture() |
| Backend | NVSHMEM | NCCL Gin |
| Memory | Fixed NVLink/RDMA buffers | Unified ElasticBuffer |

## Communication Stream Architecture

 DeepEP creates a dedicated high-priority communication stream during `ElasticBuffer` initialization. All communication kernels execute on this stream, isolated from user computation on the default compute stream.

 
### Stream Management

 The communication stream is managed as an `at::cuda::CUDAStream` in the C++ layer. In Python, it can be retrieved to record events or manage manual dependencies.

### Resource Allocation for Overlapping

 V2 uses analytical modeling to determine SM counts. When overlapping is intended, the `prefer_overlap_with_compute` flag should be set to `True` during buffer creation. This informs the analytical formula to favor configurations that leave more SMs available for computation, potentially using more channels or different kernel configurations to minimize SM occupancy.

## CUDA Graph Compatibility

 DeepEP V2 is designed for CUDA graph compatibility by avoiding CPU-side synchronization during the critical path and providing mechanisms to manage tensor lifetimes within the graph.

 
### Key Mechanisms

 
 - **`extra_tensors`**: Used in `EventOverlap` to keep tensors alive without explicit `record_stream` calls that might break graph capture.
 - **`EventHandle` Capture**: The `capture()` method provides a graph-safe way to record the state of the compute stream.
 - **Hook-based Wait**: The returned hook performs a `current_stream_wait()` on the `EventHandle`, which is a recordable operation in CUDA graphs.
 
 [deep_ep/utils/event.py25-30](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/utils/event.py#L25-L30) [deep_ep/utils/event.py39-45](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/utils/event.py#L39-L45)

 
### Deterministic Hooks

 For deterministic execution, `EventOverlap` supports a `hook_after_wait`. This is used during deterministic dispatch to trigger the sorting of received tokens immediately after the communication stream syncs but before the compute stream proceeds.

## Implementation Details

 The `ElasticBuffer` implementation handles the stream switching and barrier logic to support overlapping.

 
### Stream Synchronization Logic

 In the communication methods (dispatch, combine), the following logic is applied:

 
 - **`async_with_compute_stream`**: If enabled, the kernel launch is dispatched to the `comm_stream`.
 - **`previous_event`**: If provided, the `comm_stream` waits for this event before executing the kernel.
 - **Hook Return**: A closure is returned that performs `EventHandle.current_stream_wait()` on the compute stream.
 
 
### Memory Allocation

 The `allocate_on_comm_stream` pattern ensures that internal buffer management respects the asynchronous execution flow, preventing the allocator from reusing memory while a communication kernel is still inflight on the `comm_stream`.
