  DeepEP V2 introduces a unified memory model based on the `ElasticBuffer`. Unlike V1, which managed separate NVLink and NVSHMEM regions, V2 utilizes a single contiguous GPU buffer managed via the **NCCL Gin backend**. This architecture enables elastic scaling of resources, analytical SM allocation, and simplified buffer management for both high-throughput and low-latency communication.

 
---

 
## ElasticBuffer Memory Model

 The `ElasticBuffer` is the primary interface for memory management in DeepEP V2. It allocates a single, large block of GPU memory that is registered with NCCL for symmetric access across all ranks in a process group.

 
### Single Contiguous Buffer

 A single allocation covers all communication needs, including token data, metadata, and workspace requirements. The buffer is divided into sub-regions at runtime. In V2, the memory layout is strictly defined as `[[[Workspace] GPU buffer] CPU buffer]` [csrc/elastic/buffer.hpp20-21](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L20-L21)

 **Key properties:**

 
 - **Symmetric Registration**: The buffer is registered as a NCCL symmetric memory window, allowing remote ranks to perform `put` and `get` operations directly into the memory space [csrc/elastic/buffer.hpp111-115](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L111-L115)
 - **Unified Interface**: Both high-throughput and low-latency operations share this buffer, eliminating the need for separate NVSHMEM heaps.
 - **Alignment**: All buffer allocations and the workspace are aligned to 2 MB (`kNumAlignmentBytes`) to ensure compatibility with CUDA VMM and high-performance transport [csrc/kernels/backend/symmetric.hpp16](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/symmetric.hpp#L16-L16) [csrc/elastic/buffer.hpp104-105](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L104-L105)
 
 
### CPU+GPU Hybrid Support

 The `ElasticBuffer` supports a hybrid memory model where the tail of the buffer can reside in CPU RAM (NUMA-local) while maintaining a contiguous virtual address (VA) space [csrc/kernels/backend/symmetric.hpp145-161](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/symmetric.hpp#L145-L161) This is managed via `ElasticSymmetricMemory`, which uses `cuMemAddressReserve` and `cuMemMap` to stitch physical GPU VRAM and CPU RAM into a single VA range [csrc/kernels/backend/symmetric.hpp163-173](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/symmetric.hpp#L163-L173)

## NCCLSymmetricMemoryContext and Windows

 DeepEP V2 replaces NVSHMEM with a custom NCCL-based transport layer. The core of this system is the `NCCLSymmetricMemoryContext`, which manages the lifecycle of symmetric memory windows.

 
### NCCL Windows

 A NCCL window provides a way for a rank to expose a local memory region to remote ranks within a NCCL communicator.

 
 - **Creation**: During `ElasticBuffer` initialization, the `nccl_context` is instantiated, which handles the symmetric memory registration [csrc/elastic/buffer.hpp111-114](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L111-L114)
 - **Registration**: The context uses either `GPUSymmetricMemory` (pure GPU) or `ElasticSymmetricMemory` (hybrid) to allocate and register memory [csrc/kernels/backend/symmetric.hpp124-145](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/symmetric.hpp#L124-L145)
 - **Symmetric Access**: `set_access` is called to grant read/write permissions for all peer GPUs and optionally the local NUMA node [csrc/kernels/backend/symmetric.hpp90-111](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/symmetric.hpp#L90-L111)

## Workspace Layout and Buffer Sizing

 The size of an `ElasticBuffer` is determined by the number of tokens, hidden dimension, number of experts, and specialized features like Engram or PP.

 
### Workspace Components

 The `WorkspaceLayout` defines how the front of the contiguous buffer is partitioned for internal metadata and synchronization signals [deep_ep/include/deep_ep/common/layout.cuh10-41](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/layout.cuh#L10-L41)

 
| Component | Purpose |
|---|---|
| NVL Barrier Signals | 16 bytes for pure NVLink scaleup barrier counters deep_ep/include/deep_ep/common/layout.cuh44-46 |
| Notify Reduction | Workspace for rank and expert notification reduction deep_ep/include/deep_ep/common/layout.cuh48-49 |
| Scaleup/Scaleout Counts | Storage for send/recv counts per rank and per expert deep_ep/include/deep_ep/common/layout.cuh51-64 |
| Channel Metadata | Finish flags and linked-list tails for scaleout channels deep_ep/include/deep_ep/common/layout.cuh66-71 |
| PP & AGRS Signals | Synchronization signals for Pipeline Parallelism and All-Gather Reduce-Scatter deep_ep/include/deep_ep/common/layout.cuh73-77 |

 
### Buffer Size Calculation

 DeepEP provides methods to calculate the required buffer size before allocation.

 
 - **C++**: `layout::WorkspaceLayout::get_num_bytes()` calculates the fixed-size workspace overhead [deep_ep/include/deep_ep/common/layout.cuh43-80](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/common/layout.cuh#L43-L80)
 - **Python**: Static methods like `calculate_elastic_buffer_size` and `get_buffer_size_hint` (and specific hints for Engram, PP, and AGRS) allow users to calculate total bytes needed for a specific MoE configuration.

## Roadmap: Elastic CPU+GPU Hybrid Buffers

 DeepEP is moving toward a **Fully Elastic Memory** model to handle MoE scaling challenges.

 
 - **Contiguous Virtual Address Space**: V2 already implements the foundation for this via `ElasticSymmetricMemory`, allowing a single pointer to span both VRAM and NUMA RAM [csrc/kernels/backend/symmetric.hpp145-175](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/symmetric.hpp#L145-L175)
 - **Dynamic Offloading**: The architecture is designed to support offloading of less-frequently accessed data (like parts of a massive KV cache or expert weights) to CPU memory while maintaining high-speed RDMA access to the GPU portion.
 - **Engram Integration**: The `Engram` feature leverages this buffer architecture to perform remote KV cache fetches with near-zero SM overhead by using the Gin backend's asynchronous RMA capabilities [csrc/elastic/buffer.hpp61-64](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L61-L64)
