  This page documents the metadata and configuration objects used in DeepEP V2 to manage expert parallelism (EP) communication. The primary interface for these operations is the `ElasticBuffer`, which produces and consumes `EPHandle` objects to coordinate the two-phase dispatch and combine process.

 
## Overview

 In DeepEP V2, communication is managed through three core entities:

 
 - **`EPHandle`**: A metadata container that stores the routing information (layout) generated during a `dispatch` operation. It is required to execute the corresponding `combine` operation or to replay cached communication patterns. [deep_ep/buffers/elastic.py:25-29]
 - **`Config` and `topk_idx_t`**: C++ types that define the execution parameters and data types for routing. [deep_ep/**init**.py:95-95]
 - **`EventOverlap` and `EventHandle`**: Utilities for managing asynchronous execution and stream synchronization to enable communication-computation overlapping. [deep_ep/utils/event.py:8-15]

## EPHandle

 The `EPHandle` is the central metadata object in the V2 `ElasticBuffer` API. When a `dispatch` is performed, the kernel calculates the layout (which tokens go to which experts on which ranks) and stores this in an `EPHandle`.

 
### Attributes and Metadata

 The `EPHandle` stores several attributes that describe the communication layout:

 
| Attribute | Type | Description |
|---|---|---|
| do_expand | bool | Whether the expanding (one-token-per-expert-slot) layout is used. [deep_ep/buffers/elastic.py:32] |
| num_experts | int | The total number of all experts. [deep_ep/buffers/elastic.py:33] |
| expert_alignment | int | Align the number of tokens received by each local expert to this variable. [deep_ep/buffers/elastic.py:34] |
| num_max_tokens_per_rank | int | The maximum number of tokens per rank across all ranks. [deep_ep/buffers/elastic.py:35] |
| num_sms | int | The SM count used during dispatch (reused in combine). [deep_ep/buffers/elastic.py:36] |
| topk_idx | torch.Tensor | Cloned top-k expert indices from dispatch, [num_tokens, num_topk]. [deep_ep/buffers/elastic.py:37] |
| psum_num_recv_tokens_per_scaleup_rank | torch.Tensor | Inclusive prefix sum of deduplicated received token counts per scaleup rank. [deep_ep/buffers/elastic.py:38-41] |
| psum_num_recv_tokens_per_expert | torch.Tensor | Prefix sum of alignment-padded received token counts per local expert. [deep_ep/buffers/elastic.py:42-48] |

### Handle Caching Semantics

 For inference (decoding) or fixed-routing scenarios, DeepEP supports **Handle Caching**. If the routing (`topk_idx`) does not change between iterations, the `EPHandle` can be reused to skip the layout recomputation overhead. This is triggered by passing a previously generated `EPHandle` to the `handle` argument of `ElasticBuffer.dispatch`.

## Configuration and Types

 
### Config (C++)

 The `deep_ep::Config` struct is a configuration object used to tune kernel behavior. In DeepEP V2, while many parameters are determined analytically via `get_theoretical_num_sms`, `Config` provides a way to pass structured settings into the JIT-compiled kernels. It is exposed to Python via `deep_ep._C`. [deep_ep/**init**.py:95-95]

 
### topk_idx_t (C++)

 The `topk_idx_t` type represents the data type used for expert indices in the routing logic. [deep_ep/**init**.py:95-95]

 
 - **Width**: The bit-width of this type is controlled by environment variables like `EP_NUM_TOPK_IDX_BITS` or `TOPK_IDX_BITS` during the JIT compilation or build process.
 - **Usage**: It is used to store the `topk_idx` tensor which directs tokens to their respective experts.

## Event and Overlap Management

 DeepEP V2 provides utilities to overlap communication with computation (e.g., running the EP dispatch while the previous layer's attention is still computing).

 
### EventHandle

 A low-level wrapper around a CUDA event, bound from C++. It is returned by `ElasticBuffer` operations when `async_with_compute_stream=True`. [deep_ep/utils/event.py:5-5]

 
### EventOverlap

 A utility class that manages `EventHandle` objects to simplify synchronization. [deep_ep/utils/event.py:8-15] It provides:

 
 - **`current_stream_wait()`**: Forces the current PyTorch stream to wait for the communication event to complete. [deep_ep/utils/event.py:39-44]
 - **`hook_after_wait`**: A hook triggered after `current_stream_wait()`, useful for deterministic dispatch which requires a sort on the current stream after communication finishes. [deep_ep/utils/event.py:35-37]
 - **Context Manager**: Using `with event_overlap:` ensures that all operations within the block wait for the associated communication upon exit. [deep_ep/utils/event.py:74-97]

## Implementation Details

 
### Deterministic Sorting

 The `EPHandle` includes logic to guarantee deterministic output. In non-expand mode, it sorts `recv_x`, `recv_sf`, and `recv_topk_idx` based on the original source token indices. In expand mode, it sorts expanded arrays while updating slot pointers in `recv_src_metadata`. [deep_ep/buffers/elastic.py:100-116]

 
### NCCLGin Device Handle

 At the C++ level, communication is powered by the `NCCLGin` handle defined in `deep_ep/include/deep_ep/common/handle.cuh`. [deep_ep/include/deep_ep/common/handle.cuh:11]

 Key components include:

 
 - **`ncclGin`**: The backend primitive for RDMA/NVLink operations. [deep_ep/include/deep_ep/common/handle.cuh:21]
 - **`ncclWindow`**: The symmetric memory window for remote access. [deep_ep/include/deep_ep/common/handle.cuh:20]
 - **Team Tags**: Supports `ncclTeamTagWorld`, `ncclTeamTagLsa` (Local Share Area/NVLink), and `ncclTeamTagRail` (RDMA) for topology-aware routing. [deep_ep/include/deep_ep/common/handle.cuh:12-16]
 - **`is_nvlink_accessible`**: A helper to determine if a destination rank is reachable via NVLink symmetric memory. [deep_ep/include/deep_ep/common/handle.cuh:38-54]
 - **`red_add_rel`**: Atomic reduction operation that uses symmetric pointers for NVLink and `gin.signal` for RDMA. [deep_ep/include/deep_ep/common/handle.cuh:98-120]
