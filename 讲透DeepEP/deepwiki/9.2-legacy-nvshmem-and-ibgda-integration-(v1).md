# Legacy NVSHMEM and IBGDA Integration (V1)

  Relevant source files 
 - [csrc/kernels/backend/api.cuh](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh)
 
  This page describes the V1 NVSHMEM integration in DeepEP. While DeepEP V2 has transitioned to the **NCCL Gin backend** for its primary communication path, the V1 architecture remains available for legacy support and specific low-latency RDMA use cases. The V1 system relies on a patched version of NVSHMEM 3.3.9+ and the IBGDA (InfiniBand GPUDirect Async) transport to enable GPU-side InfiniBand operations.

 
---

 
## Overview and Hardware Requirements

 The V1 integration is designed for high-performance Mixture-of-Experts (MoE) communication using NVSHMEM's Partitioned Global Address Space (PGAS) model. It requires specific hardware and driver configurations to enable GPU-native networking.

 
| Requirement | Details |
|---|---|
| NVSHMEM Version | 3.3.9 or later setup.py94-95 |
| Intranode | NVLink between all GPUs within a node setup.py100 |
| Internode | RDMA-capable InfiniBand with GPUDirect RDMA setup.py112 |
| IBGDA Transport | InfiniBand GPUDirect Async support for GPU-side networking csrc/kernels/legacy/internode_ll.cu2 |

 If NVSHMEM is absent at build time or manually disabled, the internode and low-latency kernels are excluded from the compilation [setup.py112-117](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/setup.py#L112-L117)

## IBGDA Transport Configuration

 NVSHMEM's IBGDA transport enables GPUs to post InfiniBand work requests directly. This requires either specific NVIDIA driver registry keys or the GDRCopy kernel module to manage memory mappings and doorbell ringing.

 
### Enablement Methods

 
 - **NVIDIA Driver Registry Keys (Method 1):** Configuring the driver with `NVreg_EnableStreamMemOPs=1` and `PeerMappingOverride=1` allows the GPU to perform direct memory operations for networking.
 - **GDRCopy (Method 2):** Provides CPU-assisted post-send operations. The build system dynamically links the host library to ensure compatibility with pip-installed NVSHMEM wheels [setup.py26-44](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/setup.py#L26-L44)

## IBGDA Device Primitives

 The device-side communication in V1 kernels is handled by primitives that wrap internal NVSHMEM calls to perform RDMA and AMO (Atomic Memory Operations) directly from GPU warps. These are defined and utilized in the legacy internode implementations.

 
| Primitive | Role |
|---|---|
| nvshmemi_ibgda_put_nbi_warp | Performs a non-blocking RDMA Put operation from a warp. |
| nvshmemi_ibgda_rma_p | Issues a single-element Remote Memory Access (RMA) Put csrc/kernels/legacy/internode_ll.cu48 |
| nvshmemi_ibgda_amo_nonfetch_add | Performs a remote atomic addition without fetching the previous value. |
| nvshmemi_ibgda_quiet | Ensures all previously issued RDMA/AMO operations are completed csrc/kernels/legacy/internode_ll.cu31 |

 These primitives are used extensively in `csrc/kernels/legacy/internode.cu` and `internode_ll.cu` to manage the dispatch and combine phases of MoE. For example, `nvshmemi_ibgda_quiet` is used within the legacy barrier implementation to flush all QPs per rank [csrc/kernels/legacy/internode_ll.cu25-32](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/legacy/internode_ll.cu#L25-L32)

## Runtime Lifecycle and `nvshmem` Backend

 The NVSHMEM runtime is managed through a lifecycle wrapper defined in the `deep_ep::nvshmem` namespace [csrc/kernels/backend/api.cuh14](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh#L14-L14) This layer abstracts the initialization and memory management of the NVSHMEM heap for the legacy V1 path.

 
### Lifecycle Functions

 
 - **`get_unique_id`**: Generates an NVSHMEM unique ID for bootstrap [csrc/kernels/backend/api.cuh16](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh#L16-L16)
 - **`init`**: Initializes the NVSHMEM environment with a rank, total ranks, and team split configuration [csrc/kernels/backend/api.cuh18-21](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh#L18-L21)
 - **`alloc`**: Manages symmetric memory allocation on the NVSHMEM heap with specific alignment [csrc/kernels/backend/api.cuh23](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh#L23-L23)
 - **`free`**: Releases memory allocated on the NVSHMEM heap [csrc/kernels/backend/api.cuh25](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh#L25-L25)
 - **`barrier`**: Synchronizes all PEs (Processing Elements) in the NVSHMEM world, supporting optional CPU synchronization and CUDA streams [csrc/kernels/backend/api.cuh27](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh#L27-L27)
 - **`finalize`**: Tears down the NVSHMEM environment [csrc/kernels/backend/api.cuh29](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/backend/api.cuh#L29-L29)
 
 The build system ensures these backend sources are included when NVSHMEM is detected [setup.py112](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/setup.py#L112-L112)

## Low-Latency Synchronization

 In V1 low-latency mode, DeepEP uses a custom `barrier` implementation in `internode_ll.cu` that bypasses standard NVSHMEM barriers for lower overhead. It uses `nvshmemi_ibgda_quiet` to ensure memory consistency across all QPs before updating a local synchronization counter [csrc/kernels/legacy/internode_ll.cu21-36](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/legacy/internode_ll.cu#L21-L36)

 
### Timeout and Masking

 If a destination rank fails to respond within a predefined cycle count, the system can optionally mask the rank using the `mask_buffer_ptr` to prevent the entire collective from hanging [csrc/kernels/legacy/internode_ll.cu53-66](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/kernels/legacy/internode_ll.cu#L53-L66)

## Build System and Integration

 The build system in `setup.py` automatically detects the NVSHMEM installation and configures the compilation flags.

 
 - **Discovery:** It searches for NVSHMEM roots and resolves versioned shared objects (e.g., `libnvshmem_host.so.3`) to support pip-installed NVIDIA wheels [setup.py26-44](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/setup.py#L26-L44)
 - **Linking:** It links against `libnvshmem_host` and `libnvshmem_device.a`. The static device library is required for the `-rdc=true` (Relocatable Device Code) step [setup.py115-117](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/setup.py#L115-L117)
 - **Source Selection:** When NVSHMEM is enabled, the build includes `internode.cu`, `internode_ll.cu`, and `backend/nvshmem.cu` [setup.py112](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/setup.py#L112-L112)
