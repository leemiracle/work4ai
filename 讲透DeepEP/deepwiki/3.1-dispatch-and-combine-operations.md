## Purpose and Scope

 This page describes the core expert-parallel (EP) communication operations in DeepEP V2. Dispatch routes tokens from source ranks to destination experts across the cluster, while combine reverses this routing to gather processed expert outputs back to their original ranks with weighted aggregation. In V2, these operations are unified under the `ElasticBuffer` interface, leveraging the **NCCL Gin** backend for high-throughput and low-latency all-to-all communication [README.md9-18](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L9-L18)

 Key improvements in V2 include the `EPHandle` metadata abstraction, analytical resource allocation, and optimized layout options such as `do_expand` and `expert_alignment` [README.md115-162](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L115-L162)

 
## Token Routing and Layout

 The dispatch operation routes tokens based on a `topk_idx` tensor. Unlike V1, which required a separate `get_dispatch_layout` call, V2's `ElasticBuffer.dispatch` handles metadata generation internally or reuses a cached `EPHandle` [deep_ep/buffers/elastic.py252-257](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L252-L257)

### Layout Options

 V2 introduces several layout options to optimize the expert computation phase following dispatch:

 
 - **`do_expand`**: Whether the expanding (one-token-per-expert-slot) layout is used. If `True`, one token slot is allocated per expert assignment. If a token is routed to multiple experts on the same rank, it will occupy multiple slots in the received buffer [deep_ep/buffers/elastic.py32](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L32-L32) [deep_ep/buffers/elastic.py78](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L78-L78)
 - **`expert_alignment`**: Aligns the number of tokens received by each local expert to this variable. This is critical for performance in GEMM-based expert implementations that require specific alignment (e.g., 8 or 16) [deep_ep/buffers/elastic.py34](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L34-L34) [deep_ep/buffers/elastic.py80](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L80-L80)
 - **`psum_num_recv_tokens_per_expert`**: Prefix sum of alignment-padded received token counts per local expert. In non-expand mode, this is an inclusive prefix sum. In expand mode, `psum[i]` equals the aligned cumulative count of experts before `i` plus the actual (unaligned) token count of expert `i` [deep_ep/buffers/elastic.py42-48](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L42-L48) [deep_ep/buffers/elastic.py85](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L85-L85)
 - **`psum_num_recv_tokens_per_scaleup_rank`**: Inclusive prefix sum of deduplicated received token counts per scaleup rank. A token is counted once per rank even if multiple of its top-k experts land on the same rank [deep_ep/buffers/elastic.py38-41](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L38-L41) [deep_ep/buffers/elastic.py84](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L84-L84)

## The Dispatch Operation

 The `ElasticBuffer.dispatch` method performs the all-to-all send. It supports both standard BF16 and FP8 quantized formats [deep_ep/buffers/elastic.py252-257](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L252-L257)

 
### Implementation Detail: JIT Kernel Execution

 When `dispatch` is called, DeepEP launches a JIT-compiled kernel (`dispatch_impl` in `deep_ep/include/deep_ep/impls/dispatch.cuh` or `hybrid_dispatch_impl`). These kernels use a multi-role warp architecture:

 
 - **Notify Warps**: Ranks exchange counts to determine how many tokens each will receive. They perform atomic additions on shared memory (`expert_count` and `rank_count`) and then do a full-grid reduction using `ptx::red_add` [deep_ep/include/deep_ep/impls/dispatch.cuh79-115](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/dispatch.cuh#L79-L115)
 - **Dispatch/Forward Warps**: Tokens are copied into the `ElasticBuffer` and sent via NCCL Gin primitives. The kernel treats each warp as a "channel" using `comm::get_qp_mode` [deep_ep/include/deep_ep/impls/dispatch.cuh69-71](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/dispatch.cuh#L69-L71)
 - **Hybrid Mode**: If `allow_hybrid_mode` is enabled, tokens may be routed hierarchically using RDMA and NVLink to optimize bandwidth [csrc/elastic/buffer.hpp40-41](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L40-L41) [csrc/elastic/buffer.hpp111-114](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/csrc/elastic/buffer.hpp#L111-L114)

### EPHandle Metadata and Epilogue

 The `EPHandle` is the primary metadata carrier in V2. It is produced during the first dispatch and contains:

 
 - `recv_src_metadata`: Source token indices and buffer slot indices [deep_ep/buffers/elastic.py52](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L52-L52) [deep_ep/buffers/elastic.py88](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L88-L88)
 - `dst_buffer_slot_idx`: Destination buffer slot indices from dispatch [deep_ep/buffers/elastic.py53](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L53-L53) [deep_ep/buffers/elastic.py89](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L89-L89)
 - `num_recv_tokens`: The total number of received tokens [deep_ep/buffers/elastic.py56](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L56-L56) [deep_ep/buffers/elastic.py94](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L94-L94)
 
 After the main dispatch kernel, a `dispatch_copy_epilogue_impl` kernel is executed on the receiver side to finalize the layout. This kernel performs TMA loads from the scaleup buffer and places tokens into the final expanded or non-expanded tensor [deep_ep/include/deep_ep/impls/dispatch_copy_epilogue.cuh23-143](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/dispatch_copy_epilogue.cuh#L23-L143)

## The Combine Operation

 Combine reverses the dispatch routing. It gathers the outputs from experts and performs a weighted summation to produce the final hidden states.

 
### Weighted Aggregation and Kernel Implementation

 The combine operation is implemented in `combine_impl`. It uses `topk_weights` and the `src_metadata` from the `EPHandle` to map expert outputs back to their original token indices [deep_ep/include/deep_ep/impls/combine.cuh89-93](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine.cuh#L89-L93)

 
 - **TMA Transfers**: The kernel uses Tensor Memory Accelerator (TMA) for efficient data movement [deep_ep/include/deep_ep/impls/combine.cuh50-65](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine.cuh#L50-L65)
 - **Remote Access**: It checks for NVLink accessibility using `gin.is_nvlink_accessible`. If accessible, it bypasses RDMA and uses direct symmetric memory pointers via `gin.get_sym_ptr` [deep_ep/include/deep_ep/impls/combine.cuh95-101](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine.cuh#L95-L101)
 - **Reduction**: If `kAllowMultipleReduction` is enabled, the kernel performs local reduction of multiple expert outputs for the same token before sending [deep_ep/include/deep_ep/impls/combine.cuh144-150](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine.cuh#L144-L150)
 
 
### Reversing the Layout

 Combine handles the `do_expand` and `expert_alignment` padding automatically by using the metadata stored in the `EPHandle`. It ensures that only valid token data (and not padding) is aggregated back to the source [deep_ep/include/deep_ep/impls/combine.cuh13-150](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/include/deep_ep/impls/combine.cuh#L13-L150) [deep_ep/buffers/elastic.py324-370](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L324-L370)

## Handle Caching for Inference

 In inference decoding, the routing pattern (which tokens go to which experts) may remain static for multiple steps or across different layers. V2 allows **EPHandle caching** to eliminate the overhead of metadata computation [README.md178-193](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L178-L193)

 
### Caching Semantics

 
 - **First Iteration**: Call `dispatch` with `topk_idx`. It returns `recv_x` and an `EPHandle`.
 - **Subsequent Iterations**: Pass the cached `EPHandle` back into `dispatch` using the `handle` argument [deep_ep/buffers/elastic.py254-255](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L254-L255)
 - **Benefit**: The kernel skips the layout recomputation phases (Notify and metadata generation), directly moving to data transfer. This significantly reduces latency in decoding [README.md191-193](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L191-L193)
