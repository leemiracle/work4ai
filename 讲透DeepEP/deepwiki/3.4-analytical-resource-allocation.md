## Purpose and Scope

 DeepEP V2 introduces a significant architectural shift by replacing the manual auto-tuning required in V1 with an **analytical resource allocation** model. In V1, users typically had to manually sweep parameters like `num_sms` or use the `Config` object to find optimal performance for a specific topology.

 In V2, the `ElasticBuffer` interface leverages hardware bandwidth modeling to automatically calculate the optimal number of Streaming Multiprocessors (SMs) and Queue Pairs (QPs) required to saturate the physical interconnects (NVLink and RDMA). This approach ensures that communication kernels consume the minimum necessary GPU resources while maintaining peak throughput, effectively moving from an empirical tuning model to a predictive one [README.md17-22](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L17-L22)

 
---

 
## The Shift from V1 to V2

 The transition from V1's `Buffer` to V2's `ElasticBuffer` eliminates the need for manual tuning loops. In V2, high-throughput and low-latency APIs are unified into a single interface where resource counts are determined by the problem geometry (tokens, hidden size, experts) and hardware limits [README.md113-116](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L113-L116)

 
| Feature | V1 (Legacy) | V2 (Elastic) |
|---|---|---|
| SM Allocation | Manual via set_num_sms or Config | Analytical via get_theoretical_num_sms |
| QP Allocation | Manual num_qps_per_rank | Analytical via get_theoretical_num_qps |
| Tuning Method | Empirical sweep (grid search) | Hardware bandwidth modeling |
| Resource Efficiency | Often over-allocated (e.g., 24 SMs) | Optimized (e.g., 4-12 SMs for same perf) |

## Analytical Bandwidth Modeling

 The core of V2's resource allocation is the ability to model the relationship between SM count and achieved bandwidth. The library determines the bottleneck (memory, NVLink, or RDMA) and allocates just enough SMs to saturate that bottleneck.

## Overlap and Debugging

 
### `prefer_overlap_with_compute`

 A key flag in the `ElasticBuffer` constructor is `prefer_overlap_with_compute`.

 
 - **When `True`**: The analytical formula adjusts its resource estimates to be more conservative, using fewer SMs and channels to leave more headroom for concurrent compute kernels (GEMMs).
 - **When `False`**: The system may use more SMs and channels to minimize communication latency at the cost of compute resources.
 
 Sources: [deep_ep/buffers/elastic.py22](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L22-L22)

 
### `EP_BUFFER_DEBUG` for SM Approximation

 The `ElasticBuffer` implementation uses environment variables and internal logic to provide feedback on buffer allocation. Users can inspect the calculated requirements to verify if the analytical model is correctly identifying the system bottleneck.

 Sources: [deep_ep/buffers/elastic.py1-3](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/elastic.py#L1-L3)

## Performance Comparison

 The analytical model demonstrates superior efficiency compared to the manual tuning of V1.

 
| Architecture | Topology | V2 SM Count | V2 Bandwidth (Logical) | V1 Comparison |
|---|---|---|---|---|
| SM90 | EP 8 x 2 | 12 | 90 GB/s (RDMA) | ~24 SMs in V1 |
| SM90 | EP 8 x 4 | 6 | 61 GB/s (RDMA) | ~24 SMs in V1 |
| SM100 | EP 8 (NVLink) | 24 (Min) | 643 GB/s | N/A |
| SM100 | EP 8 (NVLink) | 64 (Max) | 726 GB/s | N/A |

 **Key takeaway**: V2 achieves up to **1.3x peak performance** while saving up to **4x SM count** by using precise analytical allocation rather than static over-provisioning [README.md45-55](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/README.md?plain=1#L45-L55)
