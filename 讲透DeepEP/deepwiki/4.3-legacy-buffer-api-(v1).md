# Legacy Buffer API (V1)

## Purpose and Scope

 The **Legacy Buffer API (V1)** refers to the `Buffer` class located in `deep_ep.buffers.legacy`. This API was the primary interface for DeepEP V1, utilizing **NVSHMEM** as the communication backend and **IBGDA** for low-latency RDMA operations.

 **Note: V1 is archived.** Users are strongly encouraged to migrate to the `ElasticBuffer` (V2) API, which offers superior performance, lower SM occupation, and a unified interface using the NCCL Gin backend. V1 remains in the codebase to support legacy training and inference pipelines.

 For the modern API, see [4.1. ElasticBuffer Class](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/4.1. ElasticBuffer Class) For V1 kernel implementation details, see [5.4. Legacy Kernels (V1)](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/5.4. Legacy Kernels (V1))

## Class Structure and Initialization

 
### Buffer Class Overview

 The `Buffer` class (defined in `deep_ep.buffers.legacy.Buffer`) manages expert-parallel communication across single-node (NVLink) and multi-node (RDMA) topologies. It supports a specialized "low-latency mode" for inference.

 **Key Parameters for `__init__`**:

 
 - `group`: The `torch.distributed` process group [deep_ep/buffers/legacy.py34](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L34-L34)
 - `num_nvl_bytes`: Size of the buffer allocated for intranode NVLink communication [deep_ep/buffers/legacy.py49](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L49-L49)
 - `num_rdma_bytes`: Size of the buffer allocated for internode (or intranode low-latency) RDMA communication [deep_ep/buffers/legacy.py50](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L50-L50)
 - `low_latency_mode`: Boolean. If enabled, uses IBGDA-based RDMA for zero-SM/low-latency transfers [deep_ep/buffers/legacy.py51](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L51-L51)
 - `num_qps_per_rank`: Number of InfiniBand Queue Pairs per rank (default 24). In low-latency mode, this must equal the number of local experts [deep_ep/buffers/legacy.py52-53](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L52-L53)
 - `enable_shrink`: Boolean. If enabled, allocates a mask buffer to support masking ranks dynamically for fault tolerance [deep_ep/buffers/legacy.py60](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L60-L60)

## Core Operations

 
### Dispatch and Combine

 V1 uses a two-phase approach where layout metadata is explicitly managed.

 
 - **`get_dispatch_layout`**: Computes routing metadata. It takes `topk_idx` and `num_experts` and returns a tuple containing `num_tokens_per_rank`, `is_token_in_rank`, and other routing tensors [deep_ep/buffers/legacy.py173-183](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L173-L183)
 - **`dispatch`**: Routes tokens to experts. Unlike V2, V1 requires explicit configuration (`Config` objects) or defaults to hardcoded tuning maps based on rank count. It returns `recv_x`, `recv_topk_idx`, `recv_topk_weights`, and a communication `handle` [deep_ep/buffers/legacy.py227-252](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L227-L252)
 - **`combine`**: Reverses the dispatch. It uses the `handle` (metadata) returned by `dispatch` to aggregate tokens back to their original ranks using `topk_weights` [deep_ep/buffers/legacy.py291-309](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L291-L309)
 
 
### Low-Latency Operations

 The low-latency path is specialized for pure RDMA environments and utilizes double-buffering.

 
 - **`low_latency_dispatch`**: 
 - Uses IBGDA for RDMA sends without SM involvement.
 - Supports FP8, BF16, and specialized formats like **UE8M0** (for scales) [deep_ep/buffers/legacy.py341-356](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L341-L356)
 - Provides a `return_recv_hook` parameter. If `True`, the call returns a hook that the user calls to wait for data completion, allowing communication-computation overlap [deep_ep/buffers/legacy.py349-350](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L349-L350)
 - **`low_latency_combine`**: 
 - Supports **LogFMT** (10-bit compression) to reduce bandwidth [deep_ep/buffers/legacy.py397](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L397-L397)
 - Features a `zero_copy` mode where data is processed directly in the RDMA-registered buffer [deep_ep/buffers/legacy.py401](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L401-L401)

## Mask Buffer and Shrink Mode

 When `enable_shrink=True` is passed to the constructor, the buffer supports dynamic rank exclusion. This is primarily used in inference clusters to handle transient node failures.

 
 - **`low_latency_update_mask_buffer(rank_to_mask, mask)`**: Updates the status of a specific rank in the internal mask buffer [deep_ep/buffers/legacy.py441-446](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L441-L446)
 - **`low_latency_query_mask_buffer(mask_status)`**: Copies the current mask state into a user-provided tensor [deep_ep/buffers/legacy.py452-455](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L452-L455)
 - **`low_latency_clean_mask_buffer()`**: Resets all masks, enabling communication with all ranks [deep_ep/buffers/legacy.py460-462](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L460-L462)

 V1 relies on manual tuning and static configuration, which is a major point of divergence from the V2 `ElasticBuffer`.

 **Key Differences Summary**:

 
 - **Backend**: V1 uses NVSHMEM [deep_ep/buffers/legacy.py105-108](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L105-L108); V2 uses NCCL Gin.
 - **Tuning**: V1 requires manual `Config` tuning [deep_ep/buffers/legacy.py465-477](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L465-L477); V2 uses analytical SM/QP calculation.
 - **Efficiency**: V2 is designed to save SM count while achieving higher performance compared to V1.
 - **Low Latency**: V1 has separate `low_latency_dispatch` APIs [deep_ep/buffers/legacy.py341](https://github.com/deepseek-ai/DeepEP/blob/01dc3aaa/deep_ep/buffers/legacy.py#L341-L341); V2 unifies communication into a single interface.
