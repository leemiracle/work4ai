# 06 · 推理服务栈——Quart 动态服务器、双服务器栈与解析器家族

> 主战场：`megatron/core/inference/text_generation_server/`（新旧双栈并存）+ `megatron/core/tokenizers/text/parsers/`（5 文件 628 行）。图谱批注：chat_completions.py 有 1586 行且以嵌套在工厂函数里的 async 端点为组织方式——这类"函数内定义+装饰器路由"形态正是静态分析器（含 tree-sitter 提取）的盲区，本篇以源码核实为准。

## ① 角色定位：这个子系统解决什么问题

引擎内核（第 05 篇）只会 `step()`，用户要的是 HTTP。服务栈要补齐三块：**OpenAI 兼容 API**（/v1/chat/completions、SSE 流式、logprobs、多模态）、**多进程前端部署**（每个 DP rank 一个 HTTP 副本、SO_REUSEPORT 分流）、以及**输出后处理**——推理模型的 `<think>` 段拆分、工具调用模型的 XML 解析，这些"模型格式方言"必须在服务端翻译成标准 API 字段（reasoning_content/tool_calls）。mcore 当前有**两代服务器栈并存**：Flask 同步栈（老，tools/run_text_generation_server.py 路径）与 Quart 异步栈（新，动态引擎配套），加上一组可插拔的文本解析器。

## ② 内部结构：关键类/函数与行号锚

**新栈：Quart 动态服务器（`text_generation_server/dynamic_text_gen_server/`）**。入口 `text_generation_server.py`：quart/hypercorn 在 try/except 里导入（:13-19，`HAS_BACKEND` 缺依赖时 RuntimeError :74）；`_run_text_gen_server`（:58）搭 `Quart(__name__)`（:101），`MAX_CONTENT_LENGTH=2**30`（:103-104，注释：1GB 上限为长 prompt）。三条工程细节值得精读：①**tokenize 线程池**（:120-128）——chat template 应用是同步 O(prompt)，直接跑在事件循环上会"卡住本副本所有其它请求（包括已完成的响应回投）"，所以单 worker ThreadPoolExecutor + `copy.deepcopy(tokenizer)`（注释：HF tokenizers 非线程安全）；②**SO_REUSEPORT 绑定**（:150 `_bind_reuseport_socket`，hypercorn 以 `fd://` 接管socket）——多副本同端口内核级分流；③**spawn 上下文**（:36-40）——注释解释为何前端进程必须 spawn：policy worker 是"带后台线程的活 Ray/CUDA 进程"，fork 会复制锁却不复制持锁线程，"child alive but unable to make progress"。端点按 Blueprint 注册：`endpoints/__init__.py` 的 `__all__ = [Completions, ChatCompletions, Health, Profile]`（try/except 包裹，缺 quart 时静默空表），服务器端循环 `app.register_blueprint`（:134-135）。

**端点（`endpoints/`）**：`chat_completions.py`（1586 行，最大）组织方式特殊——Blueprint 在模块级建（completions.py:33 同款），但 `chat_completions()` 等 **async 端点函数定义在工厂函数内部**，`:884-885` 双路由 `@bp.route('/chat/completions')` + `/v1/chat/completions`；请求处理链含 offload_params 校验、tool_calls 规范化（:198 `_normalize_tool_calls`，arguments 字符串↔dict 双向兼容 :433-439）、`_maybe_filter_parallel_tool_calls`（:240，"Matches vLLM's maybe_filter_parallel_tool_calls behavior"）。解析器消费在 :842-870：遍历 `parsers` 列表逐个调 `PARSER_MAPPING[parser].parse(text, ...)`，结果合并带断言 `"Multiple parsers found the same information."`（:873-875）；流式路径还读各 parser 的 `streaming_markers`（:1272）。配套件：`incremental_detokenizer.py`（97 行，`update`/`_decode_next` 增量解码）、`openai_streaming.py`（479 行，`_finish_reason`/`_safe_content_prefix` 等 SSE 装配）、`chat_templates/pretraining.jinja`。

**老栈：Flask 同步服务器（`text_generation_server/text_generation_server.py`）**：`Flask+flask_restful`（:9-10 try/except），`MegatronGenerate(Resource)`（:27）用 **PUT** 收生成请求（:35），还保留 API 演进化石——`max_len`/`sentences`/`beam_width` 参数直接 400 并提示替代（:37-48）；`Api` 挂载与静态目录在 :195-204。同目录 `run_mcore_engine.py` 提供"server-compatible version of the MCore Engine"：参数经 `broadcast_float_list` 从 rank0 广播（含 random_seed 时 `sampling_rng.manual_seed`），服务于 tools/run_text_generation_server.py 的静态批离线生成。

**解析器家族（`tokenizers/text/parsers/`）**：契约极简——`BaseParser.parse(text, **kwargs) -> (content, info)`（base_parser.py:5-19）。注册表 `PARSER_MAPPING`（__init__.py:13-18）四个键：
- `"deepseek-r1-reasoning"`：`DeepSeekR1ReasoningParser.parse`（deepseek_r1_reasoning_parser.py:29-46）——`partition("<think>")` 丢弃首标签前文本；`</think>` 定位 reasoning 边界；**无闭合标签时整段视为未结束的推理**（:40-42）；还支持 `implicit_reasoning_end_markers`（:33-37，把隐式结束标记位置当边界但保留标记给下游工具 parser）。
- `"nemotron-v3-reasoning"`：`NemotronV3ReasoningParser`（62 行）委托 DeepSeek 的 think 切分再补 Nemotron 语义，`_should_force_content`（:29-40）镜像 vLLM `SuperV3ReasoningParser`——`enable_thinking=False` 或 `force_nonempty_content=True` 时把空 content 用 reasoning 回填。
- `"qwen3-coder-tool"` / `"-combined"`：`Qwen3CoderToolParser`（qwen3_coder_tool_parser.py:442）/`Qwen3CoderToolCombinedParser`（:470，工具+推理组合）。标记语法：`<tool_call>`…`</tool_call>` 包 `<function=名>…<parameter=名>值` 的 XML（:178-186 一组预编译正则）。**全文件最硬核的是 `_find_tool_call_end`（:301-360）**：docstring 完整记录了一次**灾难性回溯事故**——用单条交替正则匹配"参数块或普通字符"在没有 `</tool_call>` 时指数级分裂文本；重写为只前进的有限窗口扫描（pos 单调推进，每次 search 限制在下一参数边界内），总工作量线性。还带 RL 反馈闭环的注释（:256-258）：残留在 content 里的 `<tool_call>` 会被 NeMo-Gym 判 `is_invalid_tool_call` 打 -5.0 advantage。

## ③ 外部连接：与哪些子系统互依

新栈垂直串起整个推理线：端点的 `client` 是 `InferenceClient`（inference_client.py，682 行）→ 连第 05 篇 `DynamicInferenceEngine`/coordinator；`MegatronAsyncLLM.serve`（apis/async_llm.py:185）内部就调本栈启动 HTTP。解析器虽住在 `tokenizers/text/parsers/`（层级上属于 tokenizer 子系统），但唯一消费方是 chat_completions 端点——**按消费者而非按出身聚类**的依赖形态（推断：放 tokenizers 下是因为它与 detokenize 同属"文本→结构"后处理）。与 vLLM 的关系在这层最显性：async 端点行为、tool_calls 规范化、Nemotron parser 语义都显式标注 "Matches vLLM's..."——新栈的目标就是让 mcore 服务能无缝替换 vLLM 前端。老栈则连 `tools/run_text_generation_server.py` 与静态引擎，是训练仓自带离线评测路径。图谱侧：chat_completions.py 作为 1586 行大文件其端点函数全部内嵌于工厂——静态调用图看不见它们，这是"tree-sitter 盲区"的实证（推断依据：端点无模块级符号，只能从 Blueprint 路由表反查）。

## ④ 数据流：一次典型调用的路径

Qwen3-Coder 工具调用请求的流式响应：

1. 客户端 POST /v1/chat/completions（tools 数组带 schema）→ SO_REUSEPORT 分到某个 rank 副本 → `chat_completions()`（:884）await 解析 JSON。
2. chat template 应用+tokenize 走单 worker 线程池（让出事件循环）；请求经 InferenceClient 进引擎 → context 组 batch → 第 05 篇 step 循环。
3. 生成期间 `IncrementalDetokenizer.update` 逐 token 增量解码；SSE chunk 由 openai_streaming 装配。
4. 完成时依次跑 parsers 列表：Qwen3CoderToolCombinedParser 先做 think 切分（reasoning 进 info），再扫 `<tool_call>` 块——`_find_tool_call_end` 线性扫描找闭合、`tool_call_function_regex`/`tool_call_parameter_regex` 抽函数名与参数、`_coerce_to_schema_type`（:106）按调用方 schema 强转类型、`_generate_tool_call_id`（:206）造 id；产出 content=""+info={"reasoning":…, "tool_calls":[…]}。
5. 端点把 info 映射进 OpenAI 响应字段（message.reasoning_content / message.tool_calls[0].function.{name,arguments}）；`_finish_reason`（openai_streaming.py:117）判 "tool_calls" 结束因；断言防多 parser 重复产出。
6. 老栈同请求走 `MegatronGenerate.put()`：收 prompts JSON → 同步引擎 forward → 整段 JSON 返回，无流式无解析器。

## ⑤ 设计决策：为什么这么设计

**为什么是 Quart 而不是 Flask/aiohttp？** 动态引擎全链路 asyncio（AsyncStream/事件循环回投），前端必须是 ASGI 原生（:158-160 注释"Quart is natively ASGI, so we can serve the app directly"）且 API 兼容 Flask 习惯（Blueprint/request/jsonify 同名）以降低迁移成本。老 Flask 栈保留是因为 tools 脚本与评测管线还依赖 PUT 接口（推断：两代并存是迁移期常态，老栈的 400 消息在主动引导用户迁移）。

**为什么端点函数定义在工厂内部？**（推断）Blueprint 需要在 quart 可选导入失败时整体退化（`__all__=[]`），工厂模式把模块级副作用收到调用时；同时嵌套闭包能捕获每副本配置。代价是静态分析盲区——这正是本篇开头标注的 tree-sitter 现象，人类读者应从 `@bp.route` 装饰器入手而非从类/函数索引入手。

**为什么解析器是纯函数式 `(content, info)` 管道？** 组合需求决定的：Qwen3-Coder = 推理拆分 + 工具解析两个关注点，管道化后 `parsers=["nemotron-v3-reasoning","qwen3-coder-tool"]` 可以自由叠放（合并断言保证幂等）；`implicit_reasoning_end_markers` 把标记保留给下游的设计（deepseek parser :36-37）证明作者按"管线"而非"单件"建模。

**为什么 _find_tool_call_end 要手写扫描器？** docstring 自述这是生产事故驱动的重写：正则交替分支在病态输入上指数回溯（服务可用性问题），且"参数值里嵌 `</tool_call>` 字样"是真实攻击面——截断错判会直接产生半截工具调用进 RL 奖励回路。**输出解析器是安全边界**，这个意识贯穿注释。

## ⑥ 新人提示：坑/入口/阅读顺序

- **阅读顺序**：`parsers/base_parser.py`（21 行）+ `__init__.py`（PARSER_MAPPING）→ `deepseek_r1_reasoning_parser.py`（46 行）→ `endpoints/completions.py`（最短端点样例）→ `chat_completions.py` 从 :884 路由处向上读工厂签名 → `text_generation_server.py:95-160`（Quart 装配）→ `qwen3_coder_tool_parser.py:301-360`（回溯事故文档）。
- **调试端点别 grep 类名**：端点全是闭包函数，从 `@bp.route` 与 Blueprint 名字（completions_api 等）反查；graph/IDE 的函数索引在这两个文件上不可靠。
- **解析器列表是有序的**：reasoning parser 需在 tool parser 前（工具解析要消费去 think 后的 content）；`implicit_reasoning_end_markers` 是两者的交接协议。
- **HF tokenizer 非线程安全**：并发路径必须用 `tokenizer_copy`（:127）；新加同步重活（模板/长文本处理）一律进 tokenize_executor，否则事件循环卡顿会表现为"已完成的请求也不吐字"。
- **多副本部署靠 SO_REUSEPORT**，排查连接分配问题先看 `_bind_reuseport_socket`；hypercorn `backlog=2**14`/`h2_max_concurrent_streams=2**14` 是高并发预设，反向代理时注意对齐。
- 老栈 MegatronGenerate 只认 PUT 且拒绝 max_len/sentences/beam_width——迁移脚本时按 400 消息提示替换参数名。
- 新增模型方言的正确姿势：实现 `parse` 静态方法（返回 (content, info)）+ 注册 PARSER_MAPPING + 需要流式时补 `streaming_markers` 类属性（chat_completions.py:1272 消费点）。
