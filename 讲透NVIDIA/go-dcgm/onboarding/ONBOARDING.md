## 1. 项目定位与 C 头契约双镜像

go-dcgm 是 NVIDIA DCGM（Data Center GPU Manager）的 **Go 语言绑定**：把 `libdcgm.so.4` 的 C API 包装成 Go 包 `pkg/dcgm`，供 dcgm-exporter、GPU Operator 等 Go 云原生组件消费。整个仓的骨架是"**契约镜像 + 单层包装**"——绑定逻辑只有一层，真正的复杂性在契约本身：

- **主契约两件套**：`pkg/dcgm/dcgm_agent.h`（全部 `dcgm*` 函数原型，vendor 镜像不随仓修改）与 `pkg/dcgm/dcgm_structs.h`（结构体+version 宏做 ABI 演进，如 :557 `#define dcgmLink_version1 MAKE_DCGM_VERSION(dcgm_link_t, 1)`、:578 `dcgmConnectV2Params_version1`）。每个结构体首字段是 `version`（dcgm_structs.h:566/585/616），Go 侧用 `pkg/dcgm/utils.go:87-112` 的 `makeVersion1`~`makeVersion5`/`makeVersion12` 工具族在调用前构造版本号——这是 DCGM ABI 的核心约定。
- **辅助契约**：`dcgm_errors.h` 错误码、`dcgm_api_export.h` 导出宏、`dcgm_fields.h`（4381 行，字段 ID/类型/单位/别名枚举，是代码生成器的唯一直接输入，:79/:157-166 带 `Deprecated` 标记）。
- **NVML 双镜像**：仓内有两份不同来源的 NVML 头——`pkg/dcgm/nvml.h`（12600 行完整版）与 `pkg/dcgm/dcgm_nvml.h`（12790 行 DCGM 内嵌裁剪版），版本代际可能不同步。**排障 NVML 符号问题第一步是确认看的是哪份**。
- **测试契约三头**：`dcgm_test_apis.h`/`dcgm_test_structs.h`/`dcgm_structs_internal.h`——无 GPU 环境的注入通路在 C 头层面就已预留（`dcgm_structs_internal.h` 条件包含 nvml_injection.h）。

Go 侧类型底座极薄：`pkg/dcgm/const.go:9` 的 `type Short C.ushort` 这类 `C.xxx` 类型别名直接映射头文件枚举（NOTES batch-1 钉版）。图谱把这 10 个头文件列为最底层（L01 c-contract-mirrors），全仓 3001 条边中引用这些契约的占了相当比例。

## 2. 会话生命周期：dlopen 三模式与引用计数门面

**库加载（admin.go，360 行）**：go-dcgm 不链接 libdcgm，而是 `dlopen` 动态加载——`pkg/dcgm/admin.go:84-91` `loadLibrary` 打开 `libdcgm.so.4`（admin.go:86）并保存句柄；LDFLAGS 声明在 admin.go:20-21（`-ldl -Wl,--unresolved-symbols=ignore-in-object-files`，符号延迟解析）。三种宿主引擎模式定义于 admin.go:43-47：`Embedded`（进程内嵌）/ `Standalone`（连接远端 hostengine）/ `StartHostengine`（自行拉起）。Standalone 连接串按 V3 符号可用性自动降级：admin.go:155-160 构造 `standaloneConnection{useV3:true}`，:190-191 在 `dcgmConnect_v3` 符号缺失时回退 V2，:226-227 探测符号名，:229 明确报错"DCGM 4.5.0 or newer"——**新版连接协议对旧 DCGM 是优雅降级而非硬失败**。可测试性的关键是 admin.go:65 `initDCGMWithCalls(api sessionCalls, m mode, ...)` 依赖注入 calls 接口，admin.go:60 生产路径注入 `cgoAdapter{}`，测试注入 mock。

**公共门面（api.go，239 行）**：26 个导出函数（实测 `grep -c`）全部是一行委托，真实逻辑在同包小写函数。`Init`（api.go:23）用包级 `dcgmInitCounter`（api.go:13）+ mutex 做引用计数：计数为负报"shutdown called before init"（api.go:27-28），为零才真正初始化（api.go:31），递增后返回 cleanup 闭包（api.go:40-45，闭包里调 Shutdown）——**多个模块共享一个 DCGM 会话时，谁 Init 谁清理，最后一人才真正关停**（Shutdown 逻辑 api.go:49-61）。注意：**全库没有 `Client` 结构体**，一切 API 是包级函数（图谱若干 summary 写的 `(c *Client)` 方法不存在，见 README 勘误 5）。

## 3. cgo 原生调用与三回调跳板

**12 个 ops 接口（native_calls.go）**：`pkg/dcgm/native_calls.go:5-6` 定义 `cgoAdapter struct{}` 聚合全部原生实现，随后切成 12 个细分接口（实测 12 个，非图谱所称 15）：sessionCalls(:19)/watchGroupOps(:31)/pidWatchOps(:40)/deviceStatusOps(:50)/healthGroupOps(:59)/policyRegistrationCalls(:68)/fieldPolicyListCalls(:74)/fieldPolicyEventCalls(:80)/multiNodeDiagnosticCalls(:86)/deviceInfoOps(:92)/policyReadOps(:102)/topologyOps(:108)。细粒度切分的目的是**让各子系统能独立注入 mock**——device_info 只需要 deviceInfoOps，不需要整个 adapter。

**三个 C 跳板**：cgo 的经典限制是 C 函数指针不能直接绑定 Go 闭包，仓里用"薄 C 函数声明+转发"解决：

- `pkg/dcgm/callback.c:5-8` `violationNotify` → 转发给 Go 侧 `//export ViolationRegistration`（policy.go:662-665）；
- `pkg/dcgm/field_policy_callback.c:18-21` `fieldPolicyViolationNotify` → `FieldPolicyViolationRegistration`（field_policy.go:694-697）；
- `pkg/dcgm/field_values_cb.c:25-26`（原型 field_values_cb.h:27）→ `go_dcgmFieldValueEntityEnumeration`（field_values.go:124-125 `//export`，extern 声明在 field_values.go:23）。

跳板全部只做声明+转发，Go 侧接收后再进分发器（见第 6 节），保证 DCGM 回调线程不被 Go 逻辑阻塞。

## 4. 字段体系与池化：gen-fields 生成链 + 对象池

字段（field）是 DCGM 数据面的统一词汇，本仓对其做了三层加工：

**生成链（cmd/gen-fields）**：`main.go`（549 行）手写 C 头解析状态机——`parseHeader`（cmd/gen-fields/main.go:161）识别块注释/ifdef 嵌套/deprecated 标记（dcgm_fields.h:157-166 的 `Deprecated:` 注释即其输入），`resolveDeprecatedFieldAliases`（cmd/gen-fields/main.go:377，调用点 :96）把废弃名解析到目标字段 ID，`TemplateData`（cmd/gen-fields/main.go:55）汇聚字段与别名交 template.go（108 行）渲染。`--legacy-fields` flag（cmd/gen-fields/main.go:68-71）读取 `pkg/dcgm/legacy_fields.csv`（44 行含表头，即 43 个数据行，:2 起如 `DCGM_FI_DEV_GPU_UTIL,203`）合并保底兼容名。产物是 `pkg/dcgm/const_fields.go`——3301 行，:17 自带 `// Code generated by gen-fields; DO NOT EDIT.`，尾部手写别名解析函数 `GetFieldID`(:3267)/`GetFieldIDOrPanic`(:3283)/`IsLegacyField`(:3292)。main_test.go 902 行守护解析边界。**这是 CONTRIBUTING.md 字段更新五步流程（改 dcgm_fields.h→gen-fields 生成→验证→评审→测试）的工具核心**。

**采集与池化（fields.go，701 行）**：`WatchFields`（fields.go:141）/`WatchFieldsWithGroupEx`（:186）/`WatchFieldsWithGroup`（:210）建立字段监控；`GetLatestValuesForFields`（:390）、`LinkGetLatestValues`（:420）、`EntityGetLatestValues`（:435）、`EntitiesGetLatestValues`（:459）是四类拉取入口。高频采集的分配开销用手写泛型对象池削减：`pooledSlice[T]`（fields.go:329）+ `acquirePooledSlice`（:334）/`releasePooledSlice`（:349），v1/v2 各一个池（fieldValuePool :358-363、fieldValueV2Pool :366-371），GetLatestValues 路径 acquire/release 成对使用（:289-290）。**v1→v2 转换器**（field_values.go:83 `appendConvertedValues`）保证旧数据源兼容——v2 结构每条自带 4096 字节 payload（field_values.go:49 注释），转换按需扩容（:95）。

**回调桥（field_values.go）**：`GetValuesSince`（field_values.go:176）时间点拉取；回调侧有背压熔断 `callbackLimitExceeded`（field_values.go:63，使用点 :72）——回调带入的值数超限直接拒绝，防止 DCGM 线程被打爆。字段-实体组适用矩阵在 field_scope.go，字段元数据在 field_summary.go，实体组管理在 gpu_group.go（`CreateGroup` :52、`NewDefaultGroup` 快捷全 GPU 组 :57、`AddToGroup` :79、`GetGroupInfo` :152）——**group 是 watch/policy 的组织单位**。

## 5. 设备·拓扑·进程子系统

观测面的第一层业务（图谱 L04 设备·拓扑·进程，7 文件）：

- **device_info.go**：设备枚举/属性/PCI 带宽/CPU 亲和/NvLink P2P。分层手法是 `get*WithOps`——`getPciBandwidthWithOps`（device_info.go:147，生产入口 :143 注入 cgoAdapter）、`getCPUAffinityWithOps`（:209，入口 :206），原生路径可整体替换。防御点是 `validateNativeCount`（:133-134 定义；:66/:90/:122 三处调用）——C 侧返回的数量先校验再切片，防越界 panic。
- **device_status.go**：把字段值聚合为 DeviceStatus（利用率/ECC/显存/时钟）。核心是纯函数 `deviceStatusFromValues`（device_status.go:156）——不碰 cgo，单测直接喂字段值数组；可注入入口 `latestValuesForDeviceWithOps`（:206，生产入口 :203 注入 cgoAdapter，:247 调纯函数收尾）。
- **topology.go**：GPU 间 P2P/NVLink 链路与 PCI 路径（`P2PLink` topology.go:95，链路类型 :21）。
- **cpu.go**（CPU 层级 v1/v2 双版）、**mig.go**（MIG 实例层级）、**process_info.go**（`ProcessInfo` 模型 :70、`WatchPidFieldsEx` 监控进程字段 :95，含 XID 错误模型）、**profile.go**（度量组 `MetricGroup` :15，`metricGroupsFromResponse` :44）。

## 6. 策略七类分发器·健康·诊断

**policy.go（1166 行，全仓最大单文件）**：七类策略条件以强类型 Go 结构表达——`DbePolicyCondition`(:146)/`Pci`(:154)/`RetiredPages`(:160)/`Thermal`(:168)/`Power`(:174)/`Nvlink`(:180)/`Xid`(:188)，统一入口类型 `PolicyCondition`(:26)；`translateConditions`（:486）把 Go 友好条件翻译为 C 位掩码参数（如 DefaultMaxRetiredPages=10 对齐 dcgmi 默认，:58）。事件面是手写 `policyDispatcher`（:219）：多订阅者注册 `addSubscription`(:250)、退订 `removeSubscription`(:293)、分发 `deliver`(:426)、丢弃计数 `dropped`(:454)——**丢弃计数器是"channel 满了扔事件"的显式化，监控侧可直接读 `PolicyViolationDropCount()`（api.go:237）**。可靠性设计是 `rollbackSubscription`（:361-362，调用点 :1095）：DCGM 侧注册失败时回滚本地状态，避免注册表与引擎脱钩。回调解码分支按 condition 类型切 C 结构（policy.go:674 dbe/:682 pci/:697 thermal/:711 nvlink/:719 xid）。

**field_policy.go**：字段策略独立成套——CRUD+订阅注册表 `fieldPolicySubscriptionRegistry`（:546，手写支持并发订阅/退订）；`requireFieldPolicySymbol`（:148，使用点 :218/:255/:276/:290/:299）运行时符号探测，旧 DCGM 缺符号时优雅报错而非崩溃。

**health/diag/mndiag/error**：health.go 提供 `HealthSet`(:54)/`HealthSetWithParams`(:71)/`HealthGet`(:95)/`HealthCheck`(:138)，模型 `DeviceHealth`(:43)/`Incident`(:114)；diag.go 四层诊断结果（`DiagResult` :36/`DiagEntityResult` :54/`DiagResults` :88，legacy/新版双解析）；mndiag.go 多节点诊断用同样的符号探测（`requireMultiNodeDiagnosticSymbol` :127，使用点 :194/:258）+ 异步 stop+wait 收尾防句柄泄漏；error.go:84 `getErrorMeta` 查错误码元数据（导出 api.go:192）。`Introspect`（api.go:174，Status 定义 hostengine_status.go:15）可查会话状态。

## 7. 可测试性设计：mockgen + 生产编译 helpers + 注入 + REST 范式

这是本仓最有特色的工程面（图谱 L07，15 文件）——**在无 GPU 的 CI 里测一个 GPU 绑定库**：

- **注入 API 进生产包（internal.go）**：`CreateFakeEntities`（internal.go:56，内部构造 `dcgmCreateFakeEntities_v2` :62-63，调 C API :82）创建假 GPU 实体（带 MIG 层级）；`InjectFieldValue`（:114）直接往字段管理器注入值——单测可以"无中生有"造出设备与遥测。
- **mockgen 全家桶**：`native_calls_generate_test.go:4` 是 `//go:generate` 指令载体；产物 `native_calls_mock_test.go`（986 行，:1 `DO NOT EDIT`，:4 完整 mockgen 命令含 12 个 `-mock_names`）为 12 个 ops 接口各生成 Mock+MockRecorder（24 个 type Mock）。
- **`*_test_helpers.go` 物料下沉**：9 个文件（cpu/device_info/diag/field_policy/field_values/health/mndiag/process_info/profile_test_helpers.go）以**非 `_test.go` 编译单元进入生产构建**——文件名后缀 `_helpers.go` 骗过 go test 的排除规则，小写 `test` 前缀符号又保证仅包内可见。这是把 cgo 测试物料（需要 C 编译期存在的桩）沉到包内的组织手法。

## 8. 集成测试真值对照与构建 CI 闭环

**tests/ 独立集成包（实机 GPU）**：12 个 Go 文件与 CLI 样例一一对应（deviceinfo/diag/dmon/health/hostengine/policy/processinfo/restapi/topology + preflight/dcgm_test 底座）；bazel 标签 `manual`+`requires-dcgm`（tests/BUILD.bazel:27-30）保证只在有 GPU 的 runner 跑。**真值对照是亮点**：`tests/nvsmi.go:11` 用子进程 `nvidia-smi`（:33 `exec.Command`）而非 NVML 绑定做 A/B 交叉验证——**DCGM 报的值必须和 nvidia-smi 一致，且走的是完全独立的通道**，绑定库自身的 bug 会被对照暴露。

**构建体系（go-task + bazel 双轨）**：`Taskfile.yml:5` dotenv 直接复用 `hack/versions.env`（:1 GO_VERSION=1.27.2，含 TASK/BAZEL/GOLANGCI 等全套工具版本钉）作为**工具版本单一事实源**；GitHub Actions（.github/workflows/go.yml:16/:20 两个 action 均 SHA 钉版本防 tag 重指向，:27 source versions.env，:37-43 跑 task build/test:unit/fmt:check/lint）与本地共用同一套 task 目标。bazel 侧 MODULE.bazel + pkg/dcgm/BUILD.bazel（244 行，cgo 库需声明 C 头/源与链接关系）。devcontainer（Dockerfile:3 `cuda:13.4.3-base-ubuntu26.04` 按摘要钉、:5 DCGM_VERSION=4.7.0-2、:20-22 apt Pin-Priority 1000 钉 DCGM 包、:31-33 装 datacenter-gpu-manager-4 三件套、Go 工具链按 amd64/arm64 双 sha256 校验）。

**代际漂移警示**：`.gitlab-ci.yml:14/16/17` 声明 CUDA 13.3.1/Go 1.26.7/DCGM 4.6.1-1，且 :38-41 引用 `--target samples` 构建阶段——与当前 Dockerfile（13.4.3/1.27.2/4.7.0-2，且无 samples target）**不同代**，是旧版多阶段构建残留（详见 README 勘误 6）。
