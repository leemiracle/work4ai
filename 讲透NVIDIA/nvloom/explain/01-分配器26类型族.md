# 讲透 nvloom 之一：分配器 26 类型族（MNNVL 显存数据面）

## 一、角色定位

`library/allocators.h`（511 行）+ `allocators.cpp`（962 行 53 方法）是 nvloom 的**显存数据面**：它回答"跨节点 GPU 互访的字节到底放在哪、怎么映射、怎么复用"。nvloom 测的每一种 CopyType（`library/enums.h:25` 的 18 形态）都要求源/目的两侧有正确类型的分配——单播拷贝要 fabric 可映射的 unicast 显存，组播要 multicast 对象，CFT 要 logical endpoint。官方设计文档 `library/README.md:24` 钦定根类 MemoryAllocation "meant to be a base for inheritance of your custom allocators"——**这个族同时也是自定义分配器的继承指南**，是仓内文档最厚的一层。

## 二、内部结构

26 个类型（25 class + 1 struct）按四支展开：

- **根与单节点支**：MemoryAllocation（`allocators.h:46-89`，ptr/allocationSize/MPIrank + 静态 uniqueIdCounter）→ DeviceMemoryAllocation（`:91`）/ HostMemoryAllocation（`:102`）；MemoryChunk（`:40`，struct，chunk 元数据）与 MemoryChunkAllocation（`:162`）；
- **多节点 VMM 支**：MultinodeMemoryAllocationBase（`:112-124`，fabric 句柄交换与跨节点映射的公共骨架）→ MultinodeMemoryAllocationUnicast（`:126`）、LocalizedMultinodeMemoryAllocationUnicast（`:136`，配 LOCALIZED_CE，v2.2 新增）、MultinodeMemoryAllocationEGM（`:172`）；
- **组播/CFT 支**：MultinodeMemoryAllocationMulticastRef（`:334-359`，组播绑定/解绑/批量映射的引用语义基类）→ Multicast（`:386`）、MulticastCudaPool（`:410`）；CFT 侧 MemoryAllocationCFT（`:266`）→ UnicastCFT（`:296`）、MulticastCFT（`:312`）与 MulticastCFTRef（`:361`，前向声明 `:310`）；
- **池化支**：UnicastLogicalEndpoint（`:204`）与 EndpointPool（`:233`）、RangeAllocator（`:185`）、MultinodeMemoryPoolAllocationBase（`:416`）→ PoolUnicast/PoolEGM（`:423/:433`）、AllocationPool（`:444`）与 MulticastPool（`:474`）。

注意"26 类继承树"的说法要精确化：Pools（`:31`）、RangeAllocator、UnicastLogicalEndpoint、AllocationPool/MulticastPool 等是**组合器/池**而非 MemoryAllocation 的后代（AllocationPool/MulticastPool 各自继承 MemoryAllocation 但扮演包裹器），真正的继承树以 MemoryAllocation 为单一根。

实现侧 `allocators.cpp` 的 53 个方法覆盖完整生命周期：构造（cuMemCreate 物理分配 + cuMemExportToShareableHandle）→ fabric 句柄经 MPI 播散交换 → 各 rank cuMemMap + cuMemSetAccess 建立远端映射 → 组播对象创建与 bind（cuMulticastCreate/cuMulticastBindMem）→ 析构按逆序拆解。这是 **CUmemAllocation 系列 VMM API 的系统应用**。

## 三、外部连接

- **向上**：Copy 描述直接持有 `shared_ptr<MemoryAllocation>`（`library/nvloom.h:84` 的构造器签名），Benchmark 引擎按分配器的 MPIrank/uniqueId 调度 kernel；
- **向左（CLI）**：`cli/testcases.cpp:735` 的 buildTestcasesLower 把分配器类型作为模板参数（unicast/egm/multicast/cft/cftMulticast/localized 六参，`cli/csv_testcase.cpp:36` 的模板实参列表可见）织进每个用例；三分配策略（unique/reuse/cudapool，`README.md:174-180`）在工厂层选择"裸分配器"还是"池包裹"；
- **向下**：CUDA Driver API（VMM/cudaMallocAsync/cuMulticast*/CFT endpoint）与 NVML（error.h 的 NVML_ASSERT 检查路径）；
- **横向**：kernels.cu 的 kernel 只吃 `CUdeviceptr`/`CUlogicalEndpointId`——分配器把类型信息留在 host 侧，device 侧接口保持扁平。

## 四、数据流

一次 unicast 跨节点读测量的分配-使用-释放：

1. 工厂按 AllocatorStrategy 选型：unique 直接 new 分配器；reuse 用 AllocationPool（`:444`）按尺寸复用；cudapool 走 stream-ordered（组播例外回 unique）；
2. 目标 rank 构造 MultinodeMemoryAllocationUnicast：本地 cuMemCreate + 导出 shareable handle（fabric 句柄）；
3. 句柄经 MPIWrapper 播散，所有参与的 rank 走 Base 类骨架（`:112-124`）做 cuMemMap/cuMemSetAccess——**每个 rank 的地址空间里都出现这块远端显存**；
4. 组播路径额外走 MulticastRef（`:334`）：一次 cuMulticast 组绑定多份物理显存，kernel 里 multimem.ld/st/red 一条指令触达全体；
5. CFT 路径不走 VA 映射而拿 CUlogicalEndpointId（`kernels.cuh:40-44` 的 kernel 签名）——endpoint 由 CFT 分配器族（`:266-312`）创建并池化（v2.2 起按 testcase 池化，CHANGELOG）；
6. 测量结束后按策略决定 free 或归还池；uniqueId 全局计数保证跨 rank 的对象身份可追踪。

## 五、设计决策

1. **类型即文档**：18 种 CopyType 各自要求特定分配语义，用类型系统把"组播 kernel 配 unicast 显存"这类错误在编译期挡掉——代价是 26 个类型的认知负担与 6 模板参数的编译开销；
2. **池化做成包裹器而非侵入**：AllocationPool/MulticastPool（`:444/:474`）以 has-a 复用底层分配器，策略切换不动分配器本体——工厂层三策略（`testcases.cpp:929`）因此只是不同的模板实例化组合；
3. **句柄交换显式走 MPI**：fabric 句柄的播散复用测试自己的 MPI 环境，不引入额外通信依赖，也天然与"每 GPU 一进程"模型对齐；
4. **引用语义分离**：MulticastRef 把"绑定/解绑"从"显存拥有"中拆出来（`:334-359`），让 CFT 组播（MulticastCFTRef 继承它，`:361`）复用组播生命周期语义而替换底层传输。

## 六、新人提示

- 读代码从 `library/README.md`（118 行）开始——它就是为这个族写的，含继承指南与字段语义；
- 抓主线先读 Unicast 一条线：`allocators.h:126` 声明 → 在 `allocators.cpp` 找对应构造/析构 → 对照 `kernels.cu:64` 的 kernel 怎么消费它的 ptr；组播/CFT 线随后；
- `MemoryChunk`（`:40`）是 struct 不是 class——数"26 类"时别漏它也别把它算进继承树；
- 自定义分配器时记住契约：uniqueId 唯一、MPIrank 正确、析构幂等（池化路径下析构≠释放）；
- 想理解 EGM（`:172`）：它是扩展 GPU 显存（extended GPU memory）语义，路径解析与 unicast 不同，配 egm 套件使用——先把 unicast 线吃透再碰它。
