# 11 · 二进制种子与构建资产（npm-cache-seed / reviewed-runtime-bundle / 32 阶段 Dockerfile）

## 一、角色定位

NemoClaw 把"可复现构建"做成了仓内一等资产：npm 依赖 tarball 以 gzip 二进制**直接入库**（`tools/mcp-tool-discovery-runtime/npm-cache-seed/`），使沙箱镜像能在 `--network=none` 下离线组装；构建产物（esbuild bundle）作为"已评审 runtime"冻结入库并受 CI 校验；主 `Dockerfile`（216KB）以 32 个 FROM 阶段、430 处 `ADD --checksum=sha256:` 把每一个外部字节都钉死。这是把供应链信任从"注册表此刻返回什么"迁移到"仓库里躺着什么"的完整实验。

## 二、内部结构

**npm-cache-seed**：目录内 78 个完整 `.tgz` + 24 个 `.part-000..N` 分片（分片属于 7 个超大包：三版 `binding-linux-x64-gnu`、`lightningcss-linux-x64-gnu`、`linux-x64`、`oxfmt`、`typescript-6.0.3`），78+7=85 恰等于 `manifest.json:2` 的 `"archiveCount": 85`——清单按"归档"计数而磁盘按"文件"计数，这是对账时最容易踩的口径差。manifest 逐条记录 archive/integrity(sha512)/resolved/size 四元组，尾部 `lockSha256`（`:516`）把整个种子绑到特定 lock 文件。`.gitattributes:8` 注释解释了为什么 tgz 能安全入库：`text=auto` 保留 Git 二进制检测，二进制不被转换；同文件 `:13` 把 `reviewed-runtime-bundle/**/*.bundle` 标记 `linguist-generated -diff`。分片消费方 `npm-ci-locked.sh:21-27` 显式拒绝"完整 tgz 与分片并存"的重复种子（duplicate complete and chunked），防止半刷新状态。

**reviewed-runtime-bundle**：三个 `.bundle` 文件经 `file` 命令实测均为 **ASCII text（esbuild CJS 打包文本）而非二进制**——`managed-startup-direct-image-runtime.bundle` 开头即是 esbuild 运行时前导（`__create/__defProp/__export` 系列）。批阶段甄别笔记曾按"生成物结构提取为空属实"处理，文本甄别的意义在于：diff/审计/grep 都对人类可用。`build-reviewed-runtime.ts` 的自举手法值得细读：`:13-15` 先把冻结的 `managed-startup-image-runtime.bundle` 读进内存，`:30-33` 才 `rmSync` 清空输出目录重建——冻结产物穿越重建周期靠的是内存暂存；`:36-46` esbuild 配置（entry `managed-startup-direct-entry.ts`、target node22、format cjs、`legalComments:"eof"`、minifyWhitespace）；`:60-66` 对三个 bundle 统一去除行尾空白后回写，`:59-77` 的 `--check` 模式在临时目录重建并与入库文件**逐字节比对文件清单**——"可复现"是被 CI 强制的属性而非愿望。`install-reviewed-runtime.sh:19-27` 给自建 GPU 机器限流：`NPM_CONFIG_MAXSOCKETS=4`、fetch 重试 5 次、`--dns-result-order=ipv4first` 规避双栈 DNS 第二失败路径；`:29` 起支持 `NEMOCLAW_CORPORATE_CA_B64` 注入企业 CA。

**Dockerfile（32 阶段）**：`:15` 第一条 checksummed ADD 拉 npm-12.0.2.tgz，`:16` `FROM node:24.18.1-trixie-slim@sha256:ac39e4b5… AS npm12`——基础镜像双钉（版本 tag+digest）；`:608` 同一 digest 再现于 `openclaw-managed-messaging-npm-cache-0` 阶段。外部 tarball 全部 `ADD --chmod=0444 --checksum=sha256:…`（`:600-603` 的 sharp/sqlite-vec arm64 亦是），主 Dockerfile 合计 430 处。最有代表性的是 `:617-636` 的离线组装：先 `COPY` 种子与 `seed-reviewed-npm-cache.mts` 脚本，`RUN --network=none` 内用脚本把种子铺进 `/out/npm-cache`，再 `NPM_CONFIG_OFFLINE=true npm ci … --cache /out/npm-cache`，随后 `verify-managed-messaging-offline-install.mts` 验证、`npm cache verify`、再跑一次 `--packuments-only` 铺元数据——零网络的 npm ci 全链路在构建期就完成验证。`Dockerfile.base`（3 阶段）延续同模式（SHELL 设 pipefail 防 bash 静默吞错）；`agents/hermes/Dockerfile.base` 更进一步 ARG 级钉扎：`HERMES_VERSION=v2026.9.14`（`:77`）+ `HERMES_NPM_INTEGRITY=sha512-…`（`:80`），`:17` 注释连"node digest 轮换时该跑什么命令"都写好了。

## 三、外部连接

`.dsh/tools/refresh_locked_npm_cache_seed/index.ts` 是种子的运维入口：inspect/plan/regenerate 三模式 + `dryRun/apply` 显式变更 + "原子替换与回滚"承诺（JSDoc `:1-19`）。CI 侧 `trusted reviewed-npm-audit` 门在 main/tag 镜像发布前对同一 lock 校验注册表签名（install 脚本 `:14-19` 注释）。`scripts/checks/materialize-locked-npm-cache-seed.mts` 与 `verify-managed-messaging-offline-install.mts` 在 Dockerfile 内被逐段 COPY 使用；`ci/dockerfile-growth-exceptions.json` 以"PR 号+精确上限+审批链接+移除条件"四元组管理 32 阶段的增长例外。图谱侧这批资产多为 config/service 节点：tgz 分片被诚实标注"gzip 二进制分片，结构提取为空属实"。

## 四、数据流

lock 变更 → dsh 工具 dryRun 出计划 → apply 原子重写种子目录与 manifest → 提交入仓。镜像构建：checksummed ADD 取外部 tarball → 种子 COPY 进构建器 → `--network=none` 铺缓存 → 离线 `npm ci` → 装机验证 → bundle 由 build-reviewed-runtime 重建比对 → `--check` 失败即阻断发布。

## 五、设计决策

1. **二进制入库换确定性**：接受仓体积代价，换取构建不依赖注册表可用性与内容漂移；gzip 实证（file 命令）与 .gitattributes 注释钉版了可行性边界。
2. **归档数≠文件数**：manifest 按 85 归档计，分片让 7 个巨包可入库——对账脚本必须按 manifest 语义而非 `ls | wc`。
3. **冻结产物 + check 重建**：bundle 是"评审快照"，重建漂移被 CI 当场抓住，而不是等运行期诡异行为。
4. **网络预算显式化**：MAXSOCKETS=4 与 ipv4first 把"弱网 GPU 机器"写成代码假设。
5. **digest 双写约束**：blueprint.yaml 的 digest 与 components.sandbox.image 必须同步更新（AGENTS.md 钉版，校验测试拒绝 mutable tag）。

## 六、新人提示

刷新依赖永远走 `.dsh` 工具而非手删目录；先 dryRun 看将产生的分片计划。数种子用 manifest 的 archiveCount，数磁盘文件会得到 103（含 manifest 与分片）。`--check` 失败时先看是不是行尾空白差异（`:60-66` 的归一化是约定的一部分）。改 Dockerfile 阶段数前查 growth-exceptions 是否需要新条目。图谱消费提示：这批节点没有可提取结构，理解它们要读 manifest 与脚本，不要期望函数级节点。
