# NVSHMEM ONBOARDING——OpenSHMEM 的 GPU 延伸，通信即访存

> 基于知识图谱 1458 节点/3529 边/16 层/16 步导览（commit `7bb2e99c`，指纹基线 1043 文件）。
> 全部行号锚经源码独立核实（2026-11-09）。字数口径：不计空格字符。

NVSHMEM 是 NVIDIA 开源的 OpenSHMEM 并行编程接口实现（Apache-2.0，README.md:127）：把 PGAS（分区全局地址空间）模型扩展到 GPU 集群——对称堆内存让每个 PE（处理元素）能直接寻址远端 GPU 显存，宿主线程、CUDA kernel 内线程、CUDA stream 三种身份都可发起通信（README.md:7-10）。它解决的核心问题是：让多 GPU 训练/推理中的通信不再绕回 CPU——GPU kernel 在计算中间直接 put/get/归约，即"通信即访存"。本仓四大板块：`src` 核心库（宿主+设备双码）、`test`/`perftest` 验证与基准、`nvshmem4py`+`contrib/nvshmem4rust` 多语言绑定、`externals/gpunetio` vendored 依赖。设备库走 bitcode→LTOIR→fatbin 三段管线（`src/CMakeLists.txt`），是全仓最深的一条构建链。

## 1. 公开 API 层：一个伞头的双编译模式

用户侧契约全部收在 `src/include`：`nvshmem.h` 是唯一入口伞头，但它只有 22 行（src/include/nvshmem.h:1-22）——价值不在行数而在条件编译的分流：`__CUDACC_RTC__`（NVRTC 运行时编译）等宏隔离下只展开设备 API 定义（nvshmem_defines.h 的 38 个 static inline 设备函数），宿主编译时才引入 `nvshmem_host.h`；`NVSHMEM_HOSTLIB_ONLY` 又把设备头留给 hostlib 场景（nvshmem.h:13-21）。一次 include、三种身份，是理解全仓"同一 API 三处实现"的钥匙。`nvshmemx.h` 聚合 NVIDIA 扩展（tile API、collective launch），`src/include/host/nvshmem_api.h`（511 行）是宿主实现的声明总清单。设备-宿主共用类型在 `device_host/`：`nvshmem_proxy_channel.h` 的 8 字节 packed 命令结构（见第 4 节）、`nvshmem_api_macros.h` 的 RTC 双路径宏。内部中枢则是 `src/include/internal/host/nvshmem_internal.h`（276 行，`nvshmemi_state_t` 全局状态结构：transport/heap/team/bootstrap 全在此声明，被 include 45 次）与 `nvshmemi_types.h`；环境变量的单一事实源在 `env_defs_internal.h`（385 行，`NVSHMEM_ENV` 宏登记全部 NVSHMEM_* 变量的默认值与文档串；src/include/bootstrap_host_transport/env_defs_internal.h:24-31 的 7 类 env 分类枚举可见治理粒度：OPENSHMEM/COLLECTIVES/TRANSPORT/HIDDEN/NVTX/BOOTSTRAP/OTHER）。

## 2. 启动链：init.cu 总导演 + bootstrap 婚介所

`src/host/init/init.cu`（2482 行）是库的心脏：`nvshmem_init` 起点在 init.cu:1425 附近的 API 检查（"nvshmem API called before nvshmem_init"提示锚 init.cu:1425）；多 GPU 设备库用 `registered_device_states` map 管理（init.cu:66），`nvshmemi_init_counter` 支持嵌套 init（init.cu:95 声明、:236 与 :1488 递增、:1585-1586 递减判断）。CUDA/NVML 符号不硬链接，由 `cudawrap/nvmlwrap` 运行期 dlopen 解析——这也是 wheel 可在无 GPU 机器安装的原因。启动的第一步是找到"彼此"：bootstrap 是并行作业的婚介所。`src/host/bootstrap/bootstrap.cpp`（265 行）定义插件接口（bootstrap_preinit 于 bootstrap.cpp:118、bootstrap_init 于 :145），`bootstrap_loader.cpp` 用 GET_SYMBOL 取插件的两个入口符号（bootstrap_loader.cpp:82、:100），ABI 由 `nvshmem_bootstrap.sym` 钉死（仅导出 `nvshmemi_bootstrap_plugin_init` 与 `_pre_init` 两个符号）。插件族在 `src/modules/bootstrap/` 下：**mpi/pmi/pmix/shmem 四主族 + uid socket 直连族，另有 common 共用握手工具**（注意目录是 5+1，常被误称"四插件"）。pmi 族内嵌 vendored MPICH pmi-2 源码（pmi2_api.c 2187 行：PMI2_Init 起于 :183 长 171 行、最长函数 PMIi_ReadCommand 起于 :1447 长 187 行、create_keyval 起于 :1411 仅 33 行）；uid 族的 `ncclSocket/` 是从 NCCL 拷贝改造的 socket 库（ncclsocket_* 前缀保留，bootstrap_uid_remap.h 做符号重映射隔离）。引导完成 rank/size 协商与端点信息交换后即退场——通信建立后 bootstrap 不再参与。

## 3. 对称堆：PGAS 的地基

对称堆保证所有 PE 以相同布局映射堆，使"对称地址"直接可寻址。分配器是 `src/host/mem/dlmalloc.cpp`——Doug Lea dlmalloc 2.8.6 公有领域代码（出处注释在 dlmalloc.cpp:6-11），6419 行全仓第二大单文件；`custom_malloc.cpp`（296 行）在其上适配跨 PE 地址对称约束。周边家族：`mem_heap.cpp` 管堆布局（SYMMETRIC_SIZE 默认 1GB 见 env_defs_internal.h:37）、`heap_registration.cpp` 把堆注册进各传输（ibv_reg_mr）、`mem_transport.cpp` 抽象堆-传输视图、`handle_table.cpp` 维护堆句柄、`nvls_observer.cpp` 监听堆变化驱动 NVLS 多播对象生命周期。堆的测试可以无 GPU：`test/unit/mem/heap/dynamic_unit_tests.cpp` 用链接期符号替换法（重定义 cudaMalloc/ipcSendFd 为本地桩）单测分配逻辑——这是本仓工程化的代表作。

## 4. proxy：设备命令的宿主代理循环

当设备发起的通信无法直达（无 IBGDA、非本节点），命令落入 proxy。协议是 `nvshmem_proxy_channel.h` 的 8 字节 packed 请求族：`base_request_t`（nvshmem_proxy_channel.h:26-33，static_assert 钉死 8 字节）+ DMA/inline/AMO/put_signal 各自的续接槽位；put_signal 需 6×8=48 字节编码，内存布局图就画在注释里（nvshmem_proxy_channel.h:171-187）。文件头注释明示"单系统同 GPU 字节序假设，此结构不可移植"（nvshmem_proxy_channel.h:15-17）——工程上的诚实边界。宿主侧 `src/host/proxy/proxy.cpp`（1787 行）跑 per-PE 通道循环：`nvshmemi_proxy_progress`（proxy.cpp:1667）与 minimal 版（:1695，仅 DMA progress，由 :418/:492 两处 pthread_create 按模式选择）轮询环形队列，主 switch 在 proxy.cpp:1469-1531 分派命令族——DMA（PUT/GET 批量）、inline P、AMO、PUT_SIGNAL，外加 FENCE/QUIET/REGION_END 控制命令，每种还有 _QP 批量变体。宿主 RMA 入口的 2×2 组合在 `src/host/comm/rma.cu:10-23`（nvshmemi_proxy_rma_launcher 按 is_signal×is_nbi 选四个 entrypoint kernel 之一）；`putget.cpp:171` 的 cuMemcpyAsync 是节点内 P2P 优化路径。

## 5. 传输插件六族：ops 表挂接的数据面

远程数据面全部插件化：`src/host/transport/transport.cpp:31` 硬编码 `NVSHMEM_TRANSPORT_COUNT 6`，运行期按 `NVSHMEM_TRANSPORT` 解析→dlopen→调用插件导出的 `nvshmemt_init`（transport.cpp:229；ABI 见 nvshmem_transport.sym）。六族在 `src/modules/transport/`：**ibgda**（GPU 直接发起 IB，ibgda.cpp 5348 行全仓最大 .cpp）、**ucx**、**libfabric**（Slingshot/CXI 路线）、**gpunetio**（DOCA，配 vendored 库）、**ibrc**（IB RC）、**ibdevx**（DEVX 直造 QP）。插件 ABI 是 `transport.h`（258 行）的函数指针表：rma/amo/fence/quiet/put_signal 等 typedef 集中在 transport.h:153-167，`nvshmem_transport_host_ops` 结构在 :174，`nvshmem_transport` 结构在 :208（host_ops 成员挂 :236）。节点内路径不走插件而是内置的 `src/host/transport/p2p/p2p.cpp`（NVLink/PCIe cuMemcpy）。**ibgda 最能体现设计哲学**：宿主侧 nvshmemt_init 在 ibgda.cpp:4911，而 host_ops.rma 与 host_ops.amo 显式置 NULL（ibgda.cpp:5310-5311）——宿主不做 RMA，全部由设备头 `ibgda_device.cuh`（3823 行全仓最大实现头）在 kernel 里直接构造 IB WQE：`ibgda_store_wqe_segment`（:309）写 WQE 段、`ibgda_get_wqe_ptr`（:459）按 wqe_idx 环形取槽、从 CQE 的 wqe_counter 回收完成（:482-491）。六族共享的底座：`transport_gdr_common.cpp` 的 gdrcopy_function_table 显式声明全部符号、可选符号（如 map_v2，:34 声明、:151 版本容忍、:274 LOAD_SYM）按版本缺失容忍；`transport_ib_common.cpp` 几乎所有入口都接收 ftable/mlx5dv_ftable 函数指针表——dlopen 解耦贯穿传输层。`mlx5_ifc.h` 是 ConnectX 固件命令的数据字典（src/modules/transport/common/ 下 5542 行纯布局映射）。

## 6. 集合通信：宿主宏生成器 + 设备 NVLS 归约 + team

集合 API 的三级展开。第一级：宿主宏生成器——`src/host/coll/rdxn/rdxn.cpp` 全文件仅 37 行，用 `DEFN_NVSHMEM_TYPENAME_OP_REDUCE` 宏（rdxn.cpp:16）+ 三族类型表宏（BITWISE 在 rdxn.cpp:29-31 对 and/or/xor、STANDARD 在 :33-34、ARITH 在 :36-37）全组合展开出上百个 `nvshmem_<type>_<op>_reduce` 符号；reducescatter.cpp 同构。第二级：on-stream 变体（`src/host/stream/`）把集合挂 CUDA 流异步执行，`fcollect_on_stream.h` 甚至 include test/ 目录的头共享算法（生产↔测试反向依赖的少数案例）。第三级：设备真身 `src/include/non_abi/device/coll/reduce.cuh`（2739 行）——NVLS 归约以 `mcast ldreduce+multimem.st` 的 PTX 多播指令实现（reduce.cuh:148/180 的 8B/16B 变体宏），tile 版 allreduce 有 v1/v2/v4 三代模板（:478/:361/:237）由 :553-555 静态分派，全部 `__device__ ALWAYS_INLINE` 内联进用户 kernel。通信域由 team 子系统管理：`team_internal.cpp:1478` 的 init_team_pool_and_psync（121 行长函数，调用点 :1744）决定对称堆 pSync 布局，v1/v2 双代际 team_idx 设置对应 libnvshmem 与新 runtime 两种 API；`team_internal_nvls.cpp` 把 team 绑到 NVLS 多播对象，与 `nvshmemi_nvls_rsc.hpp`、内存层 nvls_observer、`topo.cpp` 的 PE-GPU-NIC 拓扑共同构成硬件组播资源管理。

## 8. 生态外延：Python 三后端、Rust、vendored 与构建骨架

**nvshmem4py**（151 节点）是 Python 全栈：bindings 层用 CyBind/Cython 函数指针表让 wheel 运行时才绑定 libnvshmem（`nvshmem4py/nvshmem/bindings/_internal/nvshmem.pyx` 7859 行；注意 `nvshmem_linux.pyx` 与其逐字节相同，是平台别名拷贝非独立实现）。设备 API 三后端：numba（`core/device/numba/amo.py:27-339` 每个原子操作一对函数——裸函数+@overload 实现；collective.py 的 _ol 按逐 dtype×op 组合展开成 489 行/算法的模板）、numba_cuda_mlir（与 numba 后端逐函数同构的平行实现）、CuTe DSL（`core/device/cute/direct.py:204` 的 fence 是三后端中唯一的设备级 fence/quiet 拥有者；`core/interop/cute.py:16` 的 _mr_references 注册表+DLPack v0.9 协议桥接 cuda.core Buffer）。**两枚 LFS 指针勿当源码读**：`bindings/device/numba/_numbast.py`（oid 53ed32a2，size 3.9MB）与 `numba_cuda_mlir/_numbast.py`（oid a82143e2，size 4.3MB）是安装期生成的巨型桥接模块（.gitattributes 钉版）。**nvshmem4rust**（contrib/，25 节点）：generator 从 host_api_surface.py 白名单生成 sys/bindings/api 三层，runtime 用 OnceLock+Arc+Weak 管进程单例与引用计数 finalization。**externals/gpunetio**（66 节点）是 vendored DOCA 库：high_level.cpp 不走 ibv_create_qp 而手工填 mlx5ifc PRM 命令块自造 GPU 可见 doorbell 的 QP/CQ（create_qp 于 doca_gpunetio_high_level.cpp:302、create_cq 于 :246）；其 `include/gpunetio/host/mlx5_ifc.h`（5699 行）与 src/modules/transport/common 版（5542 行）同源但已漂移。**构建骨架**（30 节点）：三个 .sym 符号表钉死 ABI 导出面；`cmake_config/NVSHMEMCUDAArchitectures.cmake` 的 120 档是 Blackwell Ultra 虚拟架构；`NVSHMEMVersioning.cmake` 同一 dev/rc 状态在 artifact/distro/RPM 三生态三种编码；`scripts/bitcode_lib_cleanup.sh` 保持 nvvm-reflect-ftz 运行时反射不被编译期固化；`skills/` 9 张技能卡（select-remote-transport 19 文件含决策表）把调优知识固化成可执行资产；`src/include/internal/host/nvshmem_nvtx.hpp` 基于 vendored nvtx3 单头库做 NVTX 覆盖。
