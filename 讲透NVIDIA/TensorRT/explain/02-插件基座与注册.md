# 02 · 插件基座与注册：单 .so 收编 37 插件 + dlopen 五路 wrapper

## 角色定位

`plugin/` 是官方插件库 `libnvinfer_plugin.so` 的全部源码：37 个算子目录 + 三块公共基座（`api/` 注册入口、`common/` 共享设施、`exports/` 符号导出表）+ `vc/` 版本兼容变体。它回答两个问题：三十几个插件如何编进同一个 `.so` 并按名寻回；插件如何不链接 CUDA 库而按需调用 cuBLAS/cuDNN/cuFFT。目录刻意「去中心化」——每个插件子目录的 CMakeLists.txt 只调一行 `add_plugin_source()`，真正编译目标在父级 `plugin/CMakeLists.txt:24-26`（`target_sources(trt_plugins PRIVATE ${ARGN})`），`:30-33` 再定义 VC 侧孪生 `add_vc_plugin_source`（喂 `trt_vc_plugins` OBJECT 库）。`TRT_PLUGIN_NAMES` 清单（:34 起）+ `foreach` 装配（:78-80）是全仓插件收编名册。

## 内部结构

注册面：`plugin/api/inferPlugin.cpp` 仅 212 行，却是静态注册表本体。模板 `initializePlugin<CreatorType>`（:160-167）把 37 个 Creator 逐个塞进 `PluginCreatorRegistry::getInstance()`，全部集中在 `extern "C" bool initLibNvInferPlugins`（:170-212）——最老的 GridAnchor/GridAnchorRect 在 :188-189，V3 新贵（ROIAlignV3/CropAndResize/InstanceNormalizationV3 等）排 :174-178。共享基类在 `plugin/common/plugin.h`：`nvinfer1::pluginInternal` 命名空间（:50）内 `BasePlugin`（:53）与 `BaseCreator`（:69，只提供 namespace 存取的极简基类——efficientNMS Creator 的 mNamespace 成员即继承自此）。

dlopen 基座五件（图谱批次称「四件套」，cudnnWrapper 后到）：cublasLt/cublas/cufft/cudnn 同构——双平台宏 `#define dllOpen(name) LoadLibraryA(name)`（Windows）/`dlopen(name, RTLD_LAZY)`（POSIX），如 `cublasLtWrapper.cpp:27/34`、`cufftWrapper.cpp:30/35`、`cudnnWrapper.cpp:29/35`；driver 侧第五件 `cudaDriverWrapper.cpp:24/29` 另做名字装饰（`"lib"+name+".so.1"`）。SONAME 拼接依赖 `cudaDriverWrapper.h:142-144` 的 `constexpr getCudaLibVersionMaj()`（`CUDA_VERSION/1000`），如 `cublasLtWrapper.cpp:31/37`；cuFFT 例外——SONAME major 与 CUDA major 独立，`cufftWrapper.cpp:44-51` 的 `cufftLibCandidates()` 生成候选链（版本匹配→裸名回退），`:81` 的 `CloseLibrary` functor+`unique_ptr` 句柄管理最现代。

## 外部连接

ABI 隔离三招值得抄：① `cublasLtWrapper.h:39-56` 不 include 官方头，以 `uint64_t data[8]`/`data[32]` 复刻不透明结构体对齐布局；② `cublasWrapper.h` 把 `cublasHandle_t` 定义为 `struct cublasContext*` 前向声明指针；③ 混合符号版本——`cublasWrapper.cpp:56` 取 `cublasCreate_v2` 而 :61 取无后缀 `cublasGetMathMode`（后者历史无版本别名）。CUDA 新接口按 toolkit 条件暴露：`cudaDriverWrapper.h:77-78`（CUDA_VERSION≥11060 才有 `cuLaunchKernelEx`）、:81-82（≥12000 才有 `cuTensorMapEncodeTiled`）。句柄复用层 `plugin/common/plugin.cpp`（185 行）：按 `executionContextIdentifier` 建 observer map（:53-63），deleter 反向擦除（:78），工厂注册（:104-118）后 `createPluginCudnnWrapper/createPluginCublasWrapper`（声明 `plugin.h:86-88`，实现 :120 起）让多插件共享同上下文库句柄。共享 kernel 库 `plugin/common/kernels/`（19 个 .cu，maskRCNNKernels.cu 3101 行最大）：detectionLayerPlugin.cpp:304 的 `RefineBatchClassNMS`、proposalLayerPlugin.cpp:343 的 `proposalRefineBatchClassNMS` 都出自这里（topkLastDimPlugin.cpp:31 注释所写 topkLastDim.cu 亦在此，非本插件目录）。

## 数据流

构建期：解析器遇未知算子 → 查 `IPluginRegistry` → 命中 Creator；用户也可显式 `initLibNvInferPlugins(logger, ns)` 拉起静态注册（namespace 隔离让同库多版本插件共存）。推理期：插件 `enqueue` 需要矩阵乘/归一化时经 `createPluginCublasWrapper(execCtxId)` 取缓存句柄——wrapper 内函数指针已 `load_sym` 完毕（如 `cublasWrapper.cpp:56`），直接调用，全程无官方 SDK 头参与。点云例：`decodeBbox3DKernels.cu:45` 定义 kernel **`postprocess_kernal`**（源码原拼写，kernal 历史笔误原样保留），:164 以 `<<<blocks, threads, 0, stream>>>` 发射。导出面：`exports/nvinfer_plugin.map`+`.def` 控制可见符号，VC 版另有 `nvinfer_vc_plugin.*` 一对，与 `add_vc_plugin_source` 双轨对应。

## 设计决策

①**单 .so 静态注册表而非每插件一库**：37 个 Creator 显式列名注册（inferPlugin.cpp:174-210），一次 dlopen 全量可用；代价是新增插件要同改三处（TRT_PLUGIN_NAMES、目录 CMakeLists、initLibNvInferPlugins）。②**dlopen 而非链接**：插件 .so 不硬依赖 cuBLAS/cuDNN/cuFFT，只在用到时才要求目标机有对应库，规避 CUDA 组件版本矩阵（cufft 候选链是明证）。③**符号层 ABI 拷贝而非头重包含**：data[N] 复刻与前向声明指针把编译期依赖降到零。④**句柄按 executionContext 缓存**而非全局单例：多上下文互不污染，销毁自动回收。

## 新人提示

找注册入口先 grep `initLibNvInferPlugins`——仓内两套注册并存：多数插件靠 `REGISTER_TENSORRT_PLUGIN` 宏自动注册，inferPlugin.cpp 的显式 initializePlugin 给 def/visibility 构建形态兜底。写新插件拷 V3 四重继承模板（见 03 篇），BaseCreator 只给 namespace 存取，其余自己写。dlopen 失败参照 `cufftWrapper.cpp` 候选链模式——CUDA 组件 SONAME 漂移是部署高频事故。最后，`postprocess_kernal` 拼写是仓内真实考古层：别「好心」纠正，下游 golden 测试按原拼写对账。
