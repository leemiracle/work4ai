# 10 · API 契约层、CRD 生成物链与 tests/uat 验收体系

> 行号锚均经 grep 实测。

## 一、角色定位

NVSentinel 是 Go module monorepo，二十余组件各有独立 `go.mod`，协作靠三类契约钉住：

1. **RPC 契约** `api/proto/`：`csp/v1alpha1/provider.proto:20` 定义 `service CSPProviderService`（SendRebootSignal/IsNodeReady/SendTerminateSignal）；`device/v1alpha1/gpu.proto:96` 定义 `service GpuService`（Get/List/流式 Watch，`gpu.proto:104`）。
2. **数据模型契约** `data-models/`：health_event 等 3 个 proto；`health_event.pb.go` 是全图谱最高扇入枢纽（fan-in 246），`HealthEvent` 即全仓公共语言。
3. **文档契约** `fern/`：发布到 docs.nvidia.com/nvsentinel。

CRD 生成物链是契约的 Kubernetes 投影；`tests/uat/` 验证整机在真云能否工作。

## 二、内部结构

**api/**：`api/Makefile` 的 `protos-generate` 对 device、csp 分别调 protoc，`--go_opt=paths=source_relative`，插件版本由 yq 读根 `.versions.yaml`。细节：`provider.proto:18` 的 `go_package` 指向 `janitor/api/csp/v1alpha1`，生成物却落 `api/gen/go/csp/v1alpha1/`——source_relative 下落盘由 proto 相对路径决定，go_package 只管 import 名（`janitor-provider/main.go:47` 印证）。

**data-models/** 三层：`protobufs/`（源）→ `pkg/protos/`（935 行 `health_event.pb.go` + grpc 桩，注册 `PlatformConnector/HealthEventOccurredV1`，`health_event_grpc.pb.go:37`）→ `pkg/model/` 手写扩展（`health_event_extentions.go`：Status 常量、bson 包装、`GetEffectiveActionName` 摊平 CUSTOM 动作；文件名 "extentions" 是仓库原样拼写）。CRD 入口在 `health_event.proto:22`——import yandex protoc-gen-crd 的 crd.proto，`HealthEventResource` 挂 `k8s_crd` option 声明 api_group（`health_event.proto:126`）。

**CRD 双轨生成链**（核心甄别）：任务书说"根 Makefile 无 controller-gen"，实测是双轨并存——
- **proto 轨**（data-models/Makefile）：yandex `protoc-gen-crd`（`.versions.yaml:75` 锁 v1.1.0）从 proto 注解生成 3 个 CRD，**按 reconciler 归属分 chart 落盘**（health_event→k8s-datastore、external_remediation→janitor、maintenance_request→lifecycle-manager）。生成后 yq 删空 map——空 annotations 会被 K8s apply 剥掉，造成 **ArgoCD 永久 OutOfSync 漂移**。
- **controller-gen 轨**（组件 Makefile）：`janitor/Makefile:62` 从 Go types 的 kubebuilder marker（如 `gpureset_types.go:93` 的 GPU UUID Pattern 正则）生成再 mv 进 chart。工具定义在 `make/common.mk:73`：`go run controller-gen@v0.23.0 --load-build-tags=ignore_autogenerated,controllergen`——@version 形式杜绝误用 PATH 旧版。

两轨在同一 crds/ 目录相遇的缝合：① `lifecycle-manager/Makefile` 生成前只删 `nvsentinel.nvidia.com_*.yaml`，保留 proto 轨产物；② `external_remediation_register.go:17` 的 `//go:build !controllergen`——注释写明"CRD 来自 protoc-gen-crd，controller-gen 无法从 protobuf struct 构建 schema"。

**fern/**：`docs.yml:12` 配 custom-domain docs.nvidia.com/nvsentinel，挂 v1.27-v1.29 三档；`convert_callouts.py` 把 GitHub `> [!NOTE]` admonition 转 Fern 格式；CI 先 diff 检测 `docs/|fern/` 变更才跑校验。

**tests/uat/**：`common.sh`（仅 log/error）+ `run.sh`（编排）+ `install-apps.sh`（装栈）+ `tests.sh`（真测试）+ `junit.sh`（JUnit XML 报告器）。五环境：aws（eksctl 脚本+nodegroup 模板）、gcp（cluster/project 两组 terraform）、kind（本地 KWOK）、azure 与 oci（**仅 .gitkeep 占位**）；`.tf` 共 13 个。每环境配四个 values 文件按 `VALUES_DIR` 拼路径（`install-apps.sh:42`）。

## 三、外部连接

- **CSPProviderService 两端**：`janitor-provider/main.go:275` 实现 CSP 侧（重启/终止裸金属节点），对端 janitor 调用——"K8s 组件 ↔ 云控制面"边界契约。
- **health_event.pb.go 扇入 246**：消费方横跨 store-client、commons、janitor、tilt。
- **PlatformConnector gRPC**：platform-connectors 推入外部平台健康事件的入口。
- **chart 消费**：`charts/{janitor,lifecycle-manager,k8s-datastore,preflight}/crds/` 共 8 个自家 CRD（4/2/1/1）。
- **UAT 依赖**：helm 三 repo、KWOK chart、GCP COS GPU driver（`install-apps.sh:49` 直拉 raw URL）。

## 四、数据流

**契约生成流**：proto/types 修改 → 各自 `make generate` → 生成物随 git 提交入库（不靠 CI 现场生成）→ chart crds/ 由 Helm 原样 apply。

**UAT 执行流**：`run.sh:254` main() 依序 check_prerequisites → create_cluster → install_apps → run_tests。`get_cluster_script`（`run.sh:156`）按 CSP 分派：kind 分支不建集群，只验证 context 存在（`run.sh:190`）；azure/gcp/oci 报"not yet implemented"——自动化闭环当前只有 aws+kind 两路。install-apps.sh 依序装 prometheus → cert-manager → KWOK → 假 GPU 节点（`install-apps.sh:164`，sed 替换模板量产 10 个）→ kind 分支假 GPU 栈（`install-apps.sh:236` 注入 NVML 规格与 tilt 共享）→ nvsentinel chart。`tests.sh:1065` main() 先查 circuit-breaker 是否 TRIPPED（`tests.sh:1069`），再逐个 `junit_test`：DCGM、syslog XID、XID+GPU reset 在线，**SXID 测试整行被注释禁用**（`tests.sh:1092`；函数本体在 `tests.sh:974`）。每测试独立子 shell，失败不阻断，`junit_finish` 汇总。

**压测流**：`tests/scale-tests/` 的 event-generator 对 1500+ 节点灌事件，覆盖 API server 负载、并发 drain、混合驱逐等五问。

## 五、设计决策

1. **CRD 双轨的根因**：HealthEvent 的 schema 要跨 gRPC/Mongo/CRD 复用，源头必须是 proto；而 controller-gen 只认 Go struct 反射，读不了 protobuf 生成的 struct。于是 proto 源类型走 protoc-gen-crd、K8s 原生类型走 controller-gen，用 build tag+精确 rm 缝合。代价：改 CRD 前必须知道"哪个文件归哪条链"。
2. **CRD 跟着 reconciler 走**：proto 轨三个 CRD 落各自 reconciler 的 chart 而非集中一处，chart 自洽可独立安装。
3. **版本单源 + UAT 诚实分层**：工具版本集中 `.versions.yaml`+renovate 自动 PR；UAT 同理——kind/KWOK/假 DCGM 让本地无 GPU 跑通大部分测试，真云只实现 aws，azure/oci 占位即路线图。
4. **JUnit 子 shell 隔离与熔断礼让**：每测试独立 errexit 子 shell、每测后重写 XML（被杀不丢已完结果，面向 Prow/TestGrid）；破坏性 UAT 连续失败后人工置 TRIPPED，套件启动时主动礼让。

## 六、新人提示

- **改 CRD 字段先查归属地图**：health_event/external_remediation/maintenance_request → 改 `data-models/protobufs/*.proto`；GPUReset/RebootNode/TerminateNode/ValidationRequest → 改组件 `api/v1alpha1/*_types.go` 的 marker。改错链路不报错，只在再生成时被覆盖。
- **本地跑 UAT**：先 `kind create cluster --name nvsentinel-uat`，再 `CSP=kind ./tests/uat/run.sh`；run.sh 不替你建/删 kind 集群。
- **SXID 测试当前禁用**（`tests.sh:1092`）；lifecycle-manager 的 `validationconfigurations` 是 config-only 类型，生成后被主动删除（`lifecycle-manager/Makefile:39`），chart 里没有它的 CRD 是设计使然。
- **api/gen/go/device 零消费者**：GpuService（含 WatchGpus 流）目前全仓无 Go 消费者——前向契约，为未来 GPU inventory/watch 预留，评审别急着删。
- **坑**：绕过 make 手跑 protoc-gen-crd 会输出空 map，复发 ArgoCD OutOfSync；fern 新版本要在 `fern/versions/` 建档并注册进 docs.yml。
