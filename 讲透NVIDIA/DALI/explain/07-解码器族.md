# 07 · 解码器族：imgcodec、解码缓存、inflate 与旁路解码器

## 一、角色定位

L09 是管线入口层：把压缩字节流变成 L10 图像算子可消费的 HWC 张量。核心是 `dali/operators/imgcodec/` 基于 nvImageCodec 的统一解码器，外围是 GPU 解码缓存、LZ4 批量解压、音频/NumPy 旁路解码与 `nvcvop` CV-CUDA 桥，外加 `nvimgcodec_wrap.cc`/`npp_wrap.cc` 两个 dlopen 适配层。边界：视频 NVDEC 解码不在本层（属 `operators/video/`，见篇 10）。

## 二、内部结构

**imgcodec 主模板**：`dali/operators/imgcodec/image_decoder.h:130` 的 `template <typename Backend> class ImageDecoder` 以后端为类型参数派生两种形态。甄别修正：批阶段笔记称"CRTP 式"，实为普通后端参数模板；真正分派靠 `image_decoder.h:49` 的 `OutBackend<Backend>` trait——CPUBackend 出 CPU，其余（含 MixedBackend）一律出 GPU。逐样本状态收在 `image_decoder.h:153` 的 `SampleState` 跨 batch 复用。两种执行形态是薄壳：`host_decoder.cc:21` 的 `HostDecoder` 与 `mixed_decoder.cc:21` 的 `MixedDecoder` 仅转发共享 `RunImplImpl`，再以新旧算子名注册（`host_decoder.cc:35`）。ROI 由 `roi_image_decoder.h:44` 的 `WithCropAttr/WithSliceAttr/WithRandomCropAttr` mixin 注入，裁剪窗译成 nvImageCodec 子码流实现"只解 ROI"。

**缓存体系**：`cached_decoder_impl.cc:29` 在 cache_size>0 且达 `cache_threshold` 时经工厂取缓存；命中样本不走解码，`DeferCacheLoad`（`cached_decoder_impl.cc:58`）把拷贝挂进 ScatterGather 批量回放。工厂只认两种策略：`image_cache_factory.cc:32` 把 `cache_type="threshold"` 映到 `ImageCacheBlob`、`image_cache_factory.cc:34` 把 `"largest"` 映到 `ImageCacheLargest`——甄别修正："blob/largest/threshold 三种"不成立，且类名 Blob 对应策略名 threshold，命名陷阱。Blob 是一次性 bump allocator：整块设备内存只增不减（`image_cache_blob.cc:34`）、`tail_` 顺序推进（`:121`），放不下丢新图（`:112`）。Largest 首 epoch 只记账，min-heap（`image_cache_largest.h:39`）维护"最大能装下的图集合"，第二次见到同一图（`image_cache_largest.cc:32`）才写入——warm-up 需 2 epoch。缓存只收非 ROI、RGB、HWC、UINT8 样本（`image_decoder.h:874`）。

**inflate**：甄别修正——非"gzip/zlib 双实现"：算法枚举只有 LZ4（`inflate_params.h:41`），且全仓仅注册 GPU 后端（`inflate_gpu.cc:177`）、无 CPU 实现，走 nvCOMP 批量接口；`inflate_gpu.cu:22` 的 `FillTheTails` 核把"实际解出尺寸小于申报"的尾部补零，防未初始化内存外泄。

**旁路**：音频 `decoders__Audio` 仅 CPU（`audio_decoder_op.cc:22`），libsndfile 以 `sf_open_virtual` 内存流解码（`generic_decoder.cc:206`）；NumPy 解码器纯头解析（magic `\x93NUMPY`、仅主版本 1，`dali/operators/decoder/numpy.cc:37`）；`nvcvop` 把 DALI GPU 张量零拷贝包成 `nvcv::Tensor`（`nvcvop.h:105`）并喂 `cvcuda::Workspace`（`nvcvop.cc:309`）。

## 三、外部连接

上游是 reader/external_source 的编码字节，下游是 L10 的 crop/resize/color 族。nvImageCodec 本体由 `nvimgcodec_wrap.cc:56` 按 6 条候选路径 dlopen 弱链接，与 `dali/util/nvml_wrap.h` 同范式。向左依赖 `dali/core/mm`（`image_decoder.h:63` 的 `static_dali_device_malloc` 把 nvImageCodec 分配接到 DALI memory resource）、`dali/core/dynlink_nvcomp.h`，以及静态链接时手动装载的 opencv/libjpeg-turbo/libtiff/nvjpeg/nvjpeg2k 五扩展；`nvcvop` 与 `image/remap/cvcuda/`、`resize/experimental/` 共享 CV-CUDA 桥。

## 四、数据流

`RunImplImpl`（`image_decoder.h:613`）五段：setup 并行解析头（16 样本/块、最多 8 任务原子领块，`image_decoder.h:724`）→ 查缓存，未命中者格式协商（Mixed 走 STRIDED_DEVICE、CPU 走 STRIDED_HOST，需转换置 `need_processing`）→ `nvimgcodecDecoderDecode` 批量解码 + `FutureWaitForAll`，随后强制 `tp_->WaitForWork()`——`image_decoder.h:818` 注释明言 nvImageCodec 存在"promise 先于流同步置位"竞态 → `need_processing` 样本用 ConvertGPU/ConvertCPU 做布局/格式/动态范围三合一转换 → CacheStore 回填。后端选择上构造器注册 HW_GPU_ONLY→GPU_ONLY→HYBRID_CPU_GPU→CPU_ONLY 优先级链（`image_decoder.h:341` 起），nvImageCodec 按逐样本能力挑第一个可用者；其任务调度又经 `executor_` 回调（`image_decoder.h:383`）注入 DALI 自己的线程池——外库借用宿主调度器，避免双线程池超卖。

## 五、设计决策与取舍

混合解码本质是"CPU 出参数、GPU 出像素"：Mixed 让 nvImageCodec 在四档后端间逐样本路由，DALI 不写格式 if-else，格式矩阵外包给扩展装载（`decoder_schema.cc:30` 的 `hybrid_huffman_threshold` 默认 1M 像素即混合 Huffman 分界）；代价是同步复杂，竞态规避与手动 stream sync 都是外包的补丁。缓存设计务实：bump allocator 换零碎片、拒绝置换，押注"epoch 内热点集稳定"；Largest 用两 epoch warm-up 换最优解。反直觉：`ImageDecoder::SetupImpl` 恒返回 false（`image_decoder.h:505`）——解码器是少数输出形状只能在 Run 期确定的算子。

## 六、新人提示

改解码行为先读 `image_decoder.h`（构造器约 170 行覆盖参数映射、内存、后端链）；排查"偶发花屏"优先看 `:818` 竞态注释与线程生命周期；调缓存别被类名骗——`ImageCacheBlob` 由 `cache_type="threshold"` 激活；加新压缩格式别改 inflate（枚举写死 LZ4），它定位是视频序列帧 LZ4 分块解压；音频/NumPy 解码无 GPU 计划。诊断用 `DALI_NVIMGCODEC_LOG_LEVEL`（1-5）与 `cache_debug=True`。
