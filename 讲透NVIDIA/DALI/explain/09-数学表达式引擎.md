# 09 · 数学表达式引擎（arithmetic expressions）

## 一、角色定位

DALI 里 `images * 0.5 + 1` 这类元素级算术全部落在一个 C++ 算子上：`ArithmeticGenericOp`（dali/operators/math/expressions/arithmetic.h:313），Python 侧每个运算符重载都生成它的一个实例。目录 128 个文件（图谱 L11 层）几乎全是"一算子一文件"的工厂实例化矩阵。甄别勘误：任务书所述 `expression.cc` 不存在，解析器在 `expression_tree.cc`；`tiles` 不是目录，是头文件 `expression_tile.h`。同层 `math/normalize/`（dali/operators/math/normalize/normalize.h:40）是独立统计归一化算子，不经表达式引擎。

## 二、内部结构

**解析器**：手写递归下降。表达式语言是带括号波兰表示法：`ParseExpr`（dali/operators/math/expressions/expression_tree.cc:175）三分派——`&N` 为 tensor 输入、`$N:type` 为常量、裸名字进 `ParseCall` 递归收集子表达式。AST 三类节点（dali/operators/math/expressions/expression_tree.h:54）：`ExprFunc` 内节点与 `ExprTensor`/`ExprConstant` 叶子。BNF 与示例 `add(&0 mul(&1 $0:int8))` 写在算子 schema 文档（dali/operators/math/expressions/arithmetic.cc:122、dali/operators/math/expressions/arithmetic.cc:142）。

**语义阶段**：`PropagateTypes`（dali/operators/math/expressions/arithmetic.cc:58）自底向上类型提升；形状递归到 `BroadcastShape`；layout 走后缀匹配（HWC+WC 合法）。

**工厂三层**：运行时 op 枚举经 `VALUE_SWITCH` 转静态模板参数（dali/operators/math/expressions/expression_impl_factory_cpu.cc:45），调用宏 `IMPLEMENT_OP_FACTORY_CPU_BINARY`（dali/operators/math/expressions/expression_factory_instances/expression_impl_factory.h:166）生成的重载 `OpFactory`；宏展开体落在每算子一个的实例文件——dali/operators/math/expressions/expression_factory_instances/expression_factory_add.cc:22 整文件只有一条宏调用。executor 以节点描述字符串为 key 缓存于 `ExprImplCache`（dali/operators/math/expressions/expression_impl_factory.h:265）。

**执行描述**：`TileDesc`（dali/operators/math/expressions/expression_tile.h:33）描述线性片段，`SampleDesc` 聚合输出/操作数指针与 shape/strides；`ExtractSampleDescs` 用 `StridesForBroadcasting`（dali/operators/math/expressions/expression_impl_factory.h:225）把广播语义烧进输入 strides。

## 三、外部连接

上游是 Python 薄封装（`math.py` 共享 `_arithm_op` 单实现，篇 11 详述）；真正拼装 `expression_desc` 的是 dali/python/nvidia/dali/ops/_operators/math.py:264——`&{idx}`/`${idx}:{dtype}` 编码与"任一输入在 GPU 则选 gpu 设备"规则都在这里。下游依赖 ThreadPool 与 broadcasting 形状化简。算子注册名 `_ArithmeticGenericOp`（下划线前缀=隐藏），schema 的 `OutputDType`（dali/operators/math/expressions/arithmetic.cc:161）在图构建期就调解析+提升做静态类型推断。

## 四、数据流

构造时解析一次字符串（dali/operators/math/expressions/arithmetic.h:316）。`SetupImpl` 首轮完成形状/类型/layout 推断、常量收集（integer/real 两表进 `ConstantStorage`）、合法性检查（bitwise 禁浮点、算术禁纯 bool）。`RunImpl`（dali/operators/math/expressions/arithmetic.cc:79）先重建 SampleDescs，再按维度分岔：1D 输出用 `GetTiledCover`（dali/operators/math/expressions/arithmetic.cc:91）切均匀 tile，多维张量退化为每样本一个 tile——tile 调度实际只对 1D 生效。CPU 每 task 一个线程池工作项；GPU 全部 tile 打包单 task、每算子一次 kernel。`kTileSize` CPU=4096/GPU=65536（dali/operators/math/expressions/arithmetic.h:392），`kTaskSize` CPU=64/GPU=INT_MAX（dali/operators/math/expressions/arithmetic.h:395）。

## 五、设计决策与取舍

**嵌套树是半成品**：解析器与 BNF 都支持任意嵌套，但 `AllocateIntermediateNodes` 硬性拒绝超过一层的函数节点——dali/operators/math/expressions/arithmetic.h:374 报错原文"Complex expression trees are not yet supported"。`images * 0.5 + 1` 因此在 Python 侧被拆成两个链式算子：两次 kernel、中间结果落显存，并非融合树。schema 里的嵌套示例已超前于实现，引用需谨慎。

**一型一文件工厂**：每 TU 只实例化一个 op×11 类型×TT/TC/CT 组合，产物可控、增量编译快；代价是 100 个小文件的结构噪音，且 tree-sitter 类静态分析全盲（批阶段笔记：宏生成结构提取为空，图谱节点靠人工补扫）。

**类型提升表**（dali/operators/math/expressions/arithmetic_meta.h:284）：浮点吞噬整数、intX+uintY=int2Y；`uint64+int64=int64`（dali/operators/math/expressions/arithmetic_meta.h:389）是有损规则。`ARITHMETIC_ALLOWED_TYPES`（dali/operators/math/expressions/arithmetic_meta.h:275）不含 float16（源码 TODO 注明），float16 输入会在类型 switch 处失败，提升表条目只服务输出推断。1 元素 1D 张量视作标量是向后兼容口径（dali/operators/math/expressions/arithmetic_meta.h:1102）。

## 六、新人提示

改表达式语法要动两处：解析器与 schema 内 BNF 文档。新增算子三步：arithm_meta 特化+工厂头声明 `OpFactory`+新建 `expression_factory_X.cc/.cu` 挂进 CMake。调试打印 `GetNodeDesc()` 即对上 `ExprImplCache` 的 key。bool 只能进 `*` 与位运算。normalize 走自己的 kernel 路径，别往表达式引擎里找。
