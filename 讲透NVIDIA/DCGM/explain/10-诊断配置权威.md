# 10 · diag-skus.yaml.in：NVVS 诊断参数的单一事实源与三层兜底

## 角色定位

`nvvs/diag-skus.yaml.in`（实测 4711 行）是 DCGM 诊断（NVVS）的参数权威：按 GPU SKU（PCI device id）给出每项测试的默认参数——target_power 目标功耗、sm_stress 矩阵维度、memory_bandwidth 最低带宽等。文件头第 15 行即 "DO NOT MODIFY"，第 19 行指明用户覆盖通道是 `dcgmi diag -c <config_file>`。它是 CMake 模板而非直接运行的 YAML：`.in` 后缀经 configure_file 替换变量后生成真正的 diag-skus.yaml 装进包，运行期被 ConfigFileParser 解析、Allowlist 转成 TestParameters、TestFramework 传给各诊断 plugin，另有一份完整内容在编译期烤进二进制当兜底——一条从构建到运行的单向数据链。

## 内部结构

文件顶层三键：version（`nvvs/diag-skus.yaml.in:22`，值是模板变量 @CMAKE_PROJECT_VERSION@）、`spec: dcgm-diag-v1`（23 行）与 `skus:`（24 行）。skus 序列共 138 条，从 Kepler 时代的首条 "Tesla K8"（`nvvs/diag-skus.yaml.in:25`，id '1194'）到 Blackwell 的 B300(4199)、GB300 NVL Bianca(4246)、HGX B200(4524)、Galaxy TS2 即 RTX PRO 6000 Blackwell(4614)。每条 SKU 是 name + id + 若干测试块：Tesla K8 的 targeted_power 块（27 行）只有 is_allowed/target_power 75.0/use_dgemm 三键；H100 80GB HBM3（`nvvs/diag-skus.yaml.in:139`，id '2330'）则细到 pcie 子测试的 min_pci_generation 3.0、memory_bandwidth 的 minimum_bandwidth 1905000（注释注明由 dcgmproftester 实测乘 0.75 得出）。参数消费端的类型系统在 `nvvs/include/TestParameters.h`：`TestParameterValue`（43 行）持 string/double 双态，`TestParameters`（79 行）提供 Add*（插件桩注册默认值，89 行）与 Set*（配置解析器覆写，98 行）两套写入口，SubTest 层级与 YAML 两级 map 精确对应。

## 外部连接

构建期：`nvvs/CMakeLists.txt:24` 的 `configure_file(diag-skus.yaml.in diag-skus.yaml @ONLY)` 生成文件，`nvvs/CMakeLists.txt:34` 装进 share 目录；同时 `nvvs/src/CMakeLists.txt:17` 用 file(READ) 读回生成物，19-21 行把换行转义成 `\n`，23 行再 configure 出 FallbackDiagConfig.cpp——整份 YAML 变成 `nvvs/src/FallbackDiagConfig.cpp.in:18` 的 C 字符串常量 c_fallbackBakedDiagYaml。运行期三路入口：①包内文件优先，`nvvs/src/ConfigFileParser_v2.cpp:228` 按 c_configFileName（42 行定义）从 libexec 旁的 share 路径加载；②读不到包文件时 `nvvs/src/ConfigFileParser_v2.cpp:236` 退到烤进二进制的兜底串，242-243 行强校验 spec/version 必须存在；③用户提供 `-c` 配置时 261 行加载 m_userYaml。下游把 SKU YAML 变成可查数据库：`Allowlist::FillMap`（`nvvs/src/Allowlist.cpp:185`）遍历 GetSkus()（190 行）为每个 SKU×plugin 建 TestParameters 存入 m_featureDb（`nvvs/include/Allowlist.h:68`，按 deviceId 再按 plugin 名两级 map）；`NvidiaValidationSuite` 按 GPU 的 PCI device id 查 IsAllowlisted（`nvvs/src/NvidiaValidationSuite.cpp:745`）与 GetDefaultsByDeviceId（1065 行）取参数。诊断执行器 `TestFramework`（模板类，`nvvs/include/TestFramework.h:57` 四个模板参数 PluginLib/Loader/SoftwarePluginFramework/FileSystemOperator）经 loadPlugins（`nvvs/include/TestFramework.inl:677`）动态加载 .so 插件，GetSubtestParameters（TestFramework.inl:1087）汇总各插件声明的合法参数表——正是 ParameterValidator 校验用户配置的依据。

## 数据流

启动序列把三层配置压成一份：`ParseYaml`（`nvvs/src/ConfigFileParser_v2.cpp:336`）按 `{ m_fallbackYaml, m_userYaml }` 顺序迭代（338 行）——fallback 先写、用户配置后写，同名键覆盖，天然实现"默认值+用户覆盖"合并；每条 SKU 以 id 为键 GetOrAddSku（374 行）合入 m_skus（383 行暴露）。诊断跑起来后：NvidiaValidationSuite 拿 GPU 实际 PCI id 查 Allowlist → TestParameters → 经 TestFramework 传给 plugin（sm_stress、memory、pcie 等独立 .so）执行；plugin 侧的 PluginTest（`nvvs/include/PluginTest.h:33`）收集结果与统计。用户自定义文件样例在 `nvvs/configfile_examples/`（Tesla_K80_long.conf 等 37 个，按 "pci ID 102d" 式 device id 组织 quick/long 两档）。两道独立校验：运行期 ParameterValidator（`nvvs/src/ParameterValidator.cpp:58` 的 TransformTestName 把空格/下划线归一，72 行 IsValidTestName 对 m_possiblePlugins 白名单查表）；提交期 `nvvs/verify_allowlist_parameter_range.py:18` 用正则抓取 allowlist.txt 的 "value, min, max" 三元组，值出界即报错退出。

## 设计决策

①单一事实源三副本（.in 模板/包内 .yaml/二进制内嵌串）由同一 CMake 变量链生成，永不漂移；兜底串多花一份二进制体积，换来"包文件被删也能跑诊断"的韧性。②合并语义用迭代顺序而非深拷贝 patch 表达，fallback 与 user 同构，解析代码只写一份。③模板四参数是彻底依赖注入：`nvvs/src/TestFramework.cpp:26` 用真实实现显式实例化，测试用 Mock 四件套实例化另一份，插件加载与文件系统全可 mock。④`GetCompatibleCudaMajorVersion`（`nvvs/include/TestFramework.h:134`）硬编码"CUDA 13.0 弃用 Maxwell/Pascal/Volta"的架构断代逻辑，老卡自动降回 CUDA 12。⑤H100 条目里"dcgmproftester 实测×0.75"式注释把阈值来龙去脉写进数据文件，是数据文件承载工程决策的范本。

## 新人提示

想给新 GPU 加诊断参数，改的是 diag-skus.yaml.in 而非生成物（15 行的 DO NOT MODIFY 是认真的），且需同步补 configfile_examples 与 allowlist.txt 三元组，否则 verify 脚本过不了。查"我的阈值从哪来"按 id（PCI device id）而非 name——Allowlist 全程以 id 为键，name 只是展示。调试合并问题记住用户配置只做键级覆盖，新 id 会 GetOrAddSku 新建而非继承 fallback 同名条目。TestFramework 报错先看 explicit instantiation 是否覆盖你的新模板组合；.inl 只有被实例化点 include 才生成代码。行数口径钉版：diag-skus.yaml.in 4711、TestFramework.inl 1186，均与任务口径一致。
