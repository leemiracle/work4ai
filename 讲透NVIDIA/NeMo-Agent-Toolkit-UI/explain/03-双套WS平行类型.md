# 03 · types/chat.ts vs types/websocket.ts：平行双套 WS 类型的成因与风险

## 角色定位

本仓有一处容易让新人困惑的结构：WebSocket 消息类型定义存在**两套同名平行类型**。`types/websocket.ts`（249 行）是协议中枢——五类入站消息接口、联合类型、运行时类型守卫、结构校验器一应俱全；`types/chat.ts`（72 行）是 UI 域模型文件，末尾却也带了一组同名的简化 WS 接口（`types/chat.ts:29-72`）。两套都活着，都有消费者。

## 内部结构

**types/websocket.ts（权威套）**：`WebSocketMessageBase` 五可选字段（`types/websocket.ts:7-13`）；五类消息——SystemResponse 带 in_progress/complete 状态（`types/websocket.ts:16-24`）、SystemIntermediate 带 index 与嵌套 steps（`types/websocket.ts:27-35`）、SystemInteraction 带 oauth_url/timeout/thread_id（`types/websocket.ts:38-49`）、ObservabilityTrace（`types/websocket.ts:52-57`）、Error（`types/websocket.ts:60-67`）；联合类型 `WebSocketInbound`（`types/websocket.ts:70-75`）；出站 OAuth 偏好帧（`types/websocket.ts:78-84`）；递归结构 `IntermediateStep`（`types/websocket.ts:87-94`）。运行时层：is* 守卫族一行判 type 字段（`types/websocket.ts:97-135`）、`isOAuthConsentMessage` 复合判 input_type==='oauth_consent'（`types/websocket.ts:137-144`）、`isUserAuthErrorMessage` 兜住无 type 的裸 Error 载荷（`types/websocket.ts:152-154`）、conversation_id 校验（`types/websocket.ts:159-169`）、五值枚举结构校验（`types/websocket.ts:174-191`）、**抛含原始 JSON 错误信息**的组合校验器（`types/websocket.ts:197-219`）、`extractOAuthUrl` 三级回退 oauth_url→redirect_url→text（`types/websocket.ts:224-237`）。

**types/chat.ts（简化套）**：`Message` 含 UI 扩展字段 intermediateSteps/errorMessages/observabilityTraceId（`types/chat.ts:1-11`）、四值 Role（`types/chat.ts:13`）、`Conversation` 带 isHomepageConversation/selectedStream 标记（`types/chat.ts:20-27`）；平行 WS 接口差异——SystemIntermediate 无 status 约束 content:any（`types/chat.ts:46-51`）、SystemInteraction 无 timeout/error/thread_id（`types/chat.ts:53-61`）、**Error 的 type 字面量是 'error' 而非 'error_message'**（`types/chat.ts:63-66`）、联合少一类成员（`types/chat.ts:68-72`）。

## 外部连接

Chat.tsx 两套都 import：协议处理用 websocket.ts 守卫族（`Chat.tsx:38-50`），域模型用 chat.ts 的 Conversation/Message（`Chat.tsx:37`）；`utils/app/const.ts:3-10` 的消息类型表（userMessage/userInteractionMessage 等）是出站帧字符串的单一来源，与两套接口的 type 字面量必须人工保持一致。配套测试 `__tests__/types/websocket.test.ts` 逐守卫验证并覆盖 extractOAuthUrl 三级回退。

## 数据流

入站帧 → `JSON.parse` → websocket.ts 守卫族判型 → 命中后转换进 chat.ts 的 Message 域模型（步骤挂 intermediateSteps、错误挂 errorMessages、trace 挂 observabilityTraceId，见 `Chat.tsx:935-941`）→ 渲染层只认 chat.ts。出站帧 → const.ts 类型表拼 type 字符串 → send。

## 设计决策与风险

**成因推断**：chat.ts 的简化套是从上游 chatbot-ui 模板继承的「UI 视图模型」，websocket.ts 是 NAT 接入后为真实后端协议补的「线协议模型」——两者职责本应分离，但 chat.ts 没删旧接口，于是平行共存。

**三处实险**：①字面量漂移——Error 的 `'error'` vs `'error_message'`（`types/chat.ts:64` 对 `types/websocket.ts:61`），若有人按 chat.ts 写判型会永远匹配不上；②结构漂移——websocket.ts 给 SystemInteraction 加了 timeout/thread_id（`types/websocket.ts:45-48`），chat.ts 版没有，按后者取值会 undefined；③守卫只护权威套——运行时校验（`Chat.tsx:852`）用 websocket.ts 的校验器，chart.ts 套完全无运行时保护，错误只能在 TS 编译期暴露，而 `next.config.js` 的 `ignoreBuildErrors:true` 意味着 **next build 连编译期门禁也关了**，漂移只能靠 CI 的显式 typecheck/lint 兜住。

## 新人提示

新消息类型一律加在 websocket.ts（含守卫+校验器枚举 `types/websocket.ts:183-189` 双处），chat.ts 只补 UI 域字段；见到 `SystemResponseMessage` import 先确认来自哪个文件（两个文件同名导出）；改协议后跑 `npm run typecheck` 而非指望 build 报错；理想重构是删掉 chat.ts:29-72 的整套旧接口，但须先 grep 确认无残余消费者再动刀。
