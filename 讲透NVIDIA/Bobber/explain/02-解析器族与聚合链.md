# 02 · 解析器族：parse_results 的 calls 链与 125K 复用

## 角色定位

`bobber/lib/analysis/` 目录 13 个 py 里，`parse_results.py` 是解析器族的**编排总线**：它不解析任何日志行，只负责"找文件→分桶→调对解析器→聚合→输出"。真正干活的五个解析器各管一种日志格式：`fio.py`（bw+125k+iops 三种）、`nccl.py`、`dali.py`、`meta.py`；`common.py` 提供文件名协议工具；`aggregate_results.py`/`table.py`/`compare_baseline.py` 是聚合与出口。同目录的 `parse-mlperf.py` 是**编外独立工具**——自带 `parse_args/main`（`parse-mlperf.py:55-68`），全仓无人 import 它。

## 内部结构

`parse_results.main()`（`parse_results.py:307-411`）七个关键字参数（directory/baseline/custom_baseline/tolerance/verbose/override_version_check/json_filename）编排流水线：

1. `get_files()` glob `*.log`（`parse_results.py:39`），空目录 `sys.exit(MISSING_LOG_FILES)`（`parse_results.py:349-353`）。
2. 版本闸门 `check_bobber_version()`（`common.py:70-109`）：从文件名 `version_x_y_z` 段（`common.py:63-67`）核对全目录同版本，混版本即 `ValueError`。
3. 六个 parse 调用（`parse_results.py:356-365`）：`parse_fio_bw`/`parse_fio_125k_bw`/`parse_fio_iops`/`parse_meta`/`parse_nccl`/`parse_dali`——每个内部都先 `divide_logs_by_systems(log_files, 前缀)` 分桶再逐桶调文件级解析器。
4. 系统数集合从六个结果字典的键里**探测**（`parse_results.py:369-377`，try/max/ValueError 链），逐系统数构造 `AggregateResults` 并塞进 `final_dictionary_output['systems']`（`parse_results.py:379-397`）。
5. 出口：`display_table`（`parse_results.py:403`）→ `save_yaml_baseline` 无条件写 `baseline.yaml`（`parse_results.py:404`，模板见 `parse_results.py:273-304`）→ 可选 JSON（`parse_results.py:236-254`）→ 可选基线比对（`parse_results.py:407-411`）。

**125K 的复用秘密**：`parse_fio_125k_bw()`（`parse_results.py:113-146`）与 `parse_fio_bw()`（`parse_results.py:42-74`）逐行同构，唯一差异是分桶前缀 `'stg_125k_iteration'` vs `'stg_bw_iteration'`，两者都调同一个 `parse_fio_bw_file`（`fio.py:170-211`）。125K 不是新解析器，是 fio 解析器的第二实例。

## 外部连接

上游：`bobber.py:375-378` 把 CLI 参数直传进来。平行：`fio.py:3` 反向 import `common.fio_command_details`（common 既是工具箱也承载 fio 参数解析）。下游：`AggregateResults` 吃 17 个字典（`aggregate_results.py:99-116`），`json` property 生成结构化结果（`aggregate_results.py:269-323`）；`table.py:9-31` 的表头常量与 `compare_baseline.py:11-16` 的 TEST_MAPPING 把内部键映射为人类可读名。

## 数据流

日志文件名是全链协议：`stg_bw_iteration_2_threads_16_direct_1_depth_16_..._systems_4_version_6_3_1.log` 中，`systems_` 段供分桶（`common.py:35-37` 正则），`version_` 段供闸门。fio 行级解析抓 `READ: bw=`/`WRITE: bw=`（`fio.py:205-208`），命中数≠系统数则整文件跳过告警（`fio.py:100-103`）；IOPS 多机场景 fio 多打一行半聚合结果、显式丢弃（`fio.py:151-166`）；NCCL 只看 `float sum` 行、取每日志最大 busbw 与对应字节数（`nccl.py:35-41`）；DALI 丢 warmup（`dali.py:210`）后 ×系统数外推（`dali.py:272-275`）；mdtest 抓 `---------...-- finished` 之间的摘要表（`meta.py:87-95`）转 CSV 式解析（`meta.py:50-63`）。

## 设计决策

- **文件名当协议**：零元数据文件、零数据库，目录即数据库。代价是改名=断链，`run_tests.py` 的模板与 `common.py` 的正则必须同步演化。
- **容错均值装饰器**：`average_decorator`（`aggregate_results.py:6-31`）+ 每个取值方法自带 `try/KeyError: return 0.0`（如 `aggregate_results.py:331-334`），缺失测试静默归零而不是崩——表格永远出得来，代价是错数据也可能被 0 掩盖。
- **基线单边容差**：`metric_passes()` 只把 expected 乘 `(1-tolerance/100)` 向下放宽（`compare_baseline.py:44-48`），高于基线不罚——验收语义是"别太差"而非"精确匹配"。
- **max_bus_bytes 用众数**：多迭代取出现次数最多的字节数（`aggregate_results.py:458-459`），而非均值——离散的尺寸档位取均值无意义。

## 新人提示

调试解析问题第一现场是 `divide_logs_by_systems` 的分桶结果——打印 `num_systems_dict` 就知道文件名协议断在哪。加新测试类型时照抄 125K 的三步：新前缀函数 + main 里新调用 + `save_yaml_baseline` 模板新块（`parse_results.py:290-293`）。别忘 `parse-results` 每跑一次都会覆盖目录里的 `baseline.yaml`。
