## 1. 直觉：依存树——最简洁的句法表示

### 1.1 什么是依存关系

看一句话：

```
The  cat  ate  a  fish.
```

作为人类，你立刻知道：

- **ate** 是句子的核心（动词 = root）
- **cat** 是 ate 的主语（cat 依赖于 ate）
- **The** 是 cat 的限定词（The 依赖于 cat）
- **fish** 是 ate 的宾语（fish 依赖于 ate）
- **a** 是 fish 的限定词（a 依赖于 fish）

这些"依赖于"的关系就是**依存关系（dependency relation）**。画成树：

```
      ate (root)
     ╱    ╲
  cat     fish
  │        │
 The       a
```

每条箭头从 **head（中心词）** 指向 **dependent（修饰词）**：

```
ate ──nsubj──→ cat ──det──→ The
 └──obj──→ fish ──det──→ a
```

**关键性质**：除了 root，每个词有且仅有**一个 head**。这是一棵树（准确地说是"投影树"或"有向生成树"）。

### 1.2 依存树 vs 成分树：一张图说清

成分句法（constituency parsing，SLP3 Ch17-18）用短语嵌套表示句法：

```
成分树 (CFG):                    依存树:
                                   
  S                                ate ──root──→ ROOT
  ├─ NP                            ├─ nsubj ──→ cat ── det ──→ The
  │  ├─ Det (The)                  └─ obj ────→ fish ── det ──→ a
  │  └─ N   (cat)
  ├─ VP                            
  │  ├─ V   (ate)                 依存树：只有词，没有短语节点
  │  └─ NP                         成分树：有 NP/VP 等短语节点
  │     ├─ Det (a)
  │     └─ N   (fish)
```

| 对比维度 | 成分树 (Constituency) | 依存树 (Dependency) |
|---------|----------------------|-------------------|
| 基本单位 | 短语（NP, VP, PP…） | 词与词的关系 |
| 节点 | 非终结符 + 词 | 只有词 |
| 边的含义 | 父节点"包含"子节点 | head"支配"dependent |
| 标注难度 | 高（需要标注短语边界） | 低（只需标 head-dep） |
| 对下游任务的友好度 | 间接（要提取短语） | 直接（直接拿到 head-modifier） |
| 代表系统 | BerkeleyParser, Stanza-constituency | spaCy, Stanza, UDPipe |
| 当前地位 | 退居二线 | **主流** |

> **为什么依存赢了？** 三个原因：(1) 标注快——标注依存树比标注 Penn Treebank 快 2-3 倍；(2) 下游任务直接可用——"找动词的主语"在依存树里就是一条 `nsubj` 弧，在成分树里要先找到 VP→NP 再提取 NP head；(3) 跨语言更自然——不是所有语言都有清晰的 NP/VP 划分（如日语、土耳其语的 SOV 语序），但"谁修饰谁"是普世的。

### 1.3 依存类型（Universal Dependencies）

依存关系是有标签的。Universal Dependencies（UD）项目定义了一套跨语言的通用标签集（2026 年覆盖 200+ 语言，300+ 树库）：

| 标签 | 含义 | 英文例 | 中文例 |
|------|------|--------|--------|
| `nsubj` | 名词主语 | cat → ate (The cat **ate**) | 猫 → 吃 (猫**吃**) |
| `obj` | 直接宾语 | fish → ate (ate a **fish**) | 鱼 → 吃 (吃**鱼**) |
| `det` | 限定词 | The → cat (**The** cat) | — (中文无数词) |
| `amod` | 形容词修饰 | small → cat (a **small** cat) | 小 → 猫 (**小**猫) |
| `aux` | 助动词/助词 | is → eating (cat **is** eating) | 了 → 吃 (吃**了**) |
| `root` | 句子根节点 | ate → ROOT | 吃 → ROOT |
| `case` | 格标记/介词 | of → the (the **head of** dept) | 的 → (修饰) |
| `advmod` | 副词修饰 | very → good (**very** good) | 很 → 好 (**很**好) |
| `compound` | 复合词 | coffee → shop (**coffee shop**) | 咖啡 → 店 (**咖啡**店) |
| `acl` | 从句修饰 | reading → book (book **reading**) | (见下文) |

> 🔑 **中文的特殊标签**：`compound` 极高频（因为中文"复合词"没有空格分隔，如"咖啡店""信息工程部"），`case:dec`（"的"字结构），`discourse`（语气词"啊""吧"），`advmod`（副词如"也""还""都"）。

## 2. 数学：四大核心

依存句法分析的数学骨架有四块：**什么是合法的依存树**（投影性）、**怎么用动作序列构建**（transition-based）、**怎么用全局打分搜索**（graph-based）、**怎么用神经网络打分**（biaffine）。

### 2.1 形式定义与投影性

**依存树**：给定句子 $w_1, w_2, \ldots, w_n$，加一个虚拟 ROOT 节点 $w_0$。一个依存树是一组弧 $(h, m, l)$ 的集合，其中 $h$ 是 head 的索引，$m$ 是 dependent 的索引，$l$ 是标签。满足：

1. **每个词（除 ROOT）恰好有一个 head**：$\forall m \in \{1,\ldots,n\}$，存在唯一的 $(h, m, l)$
2. **ROOT 没有入弧**：不存在 $(h, 0, l)$
3. **连通无环**：从 ROOT 出发能到达所有词，且没有环（即构成一棵以 ROOT 为根的有向生成树）

**投影性（Projectivity）**——本章最关键的数学概念。一条弧 $(h \to m)$ 是**投影的（projective）**，当且仅当 $h$ 和 $m$ 之间的所有词都是 $h$ 的后代（在依存树中从 $h$ 可达）：

$$
\forall k \in (\min(h,m),\, \max(h,m)), \quad k \text{ 是 } h \text{ 的后代}
$$

如果树中**所有弧**都投影，则整棵树是投影树。否则就是**非投影（non-projective）**——存在**交叉弧（crossing arcs）**。

```
投影树：                      非投影树：
                                    
  ate(3)                        w₃(3)
  ├── cat(2)                    └── w₁(1)
  │    └── The(1)                   ├── w₂(2)     ← 弧不交叉
  └── fish(5)                       └── w₄(4)     ← 但弧 w₁→w₄ 跨越了 w₃！
       └── a(4)                                    
                                                w₃ 不是 w₁ 的后代
弧全嵌套，不交叉                                → 非投影！
```

> **投影性有多重要？** 英文中约 **92%** 的句子是完全投影的。但荷兰语、德语（动词提升 verb-raising）、捷克语/俄语（自由语序）、土耳其语（SOV + 后缀）中，非投影结构很常见。能否处理非投影树，是 parser 架构的分水岭。

### 2.2 Transition-Based Parsing：用动作序列构建树

核心思想：**把"解析"变成一个状态机**——维护一个栈（stack）和一个缓冲区（buffer），通过一系列**动作（transition）**逐步构建依存弧。

#### Arc-Standard 系统（Nivre 2004）

**状态** $= (\sigma, \beta, A)$：
- $\sigma$：栈，底部恒为 ROOT
- $\beta$：缓冲区，存放尚未处理的词
- $A$：已建立的弧集合

**三个动作**（只看栈顶两个元素 $s_0, s_1$）：

| 动作 | 前提 | 效果 |
|------|------|------|
| **LEFT-ARC($l$)** | 栈 $\geq 2$ 且 $s_1 \neq$ ROOT | 建立 $s_0 \xrightarrow{l} s_1$，弹出 $s_1$ |
| **RIGHT-ARC($l$)** | 栈 $\geq 2$ | 建立 $s_1 \xrightarrow{l} s_0$，弹出 $s_0$ |
| **SHIFT** | 缓冲区非空 | 把 $\beta[0]$ 压入栈顶 |

**解析过程**（以 "The cat ate a fish" 为例）：

```
步骤  动作              栈              缓冲区         已建弧
────  ────────────────  ──────────────  ────────────   ──────────
 1    SHIFT             [0, 1]          [2,3,4,5]      
 2    SHIFT             [0, 1, 2]       [3,4,5]        
 3    LEFT-ARC(det)     [0, 2]          [3,4,5]        2→1 (cat→The)
 4    SHIFT             [0, 2, 3]       [4,5]          
 5    LEFT-ARC(nsubj)   [0, 3]          [4,5]          3→2 (ate→cat)
 6    SHIFT             [0, 3, 4]       [5]            ← 不能 RIGHT-ARC！
                                                       ate(3) 还有 child fish(5) 在 buffer
 7    SHIFT             [0, 3, 4, 5]    []             
 8    LEFT-ARC(det)     [0, 3, 5]       []             5→4 (fish→a)
 9    RIGHT-ARC(obj)    [0, 3]          []             3→5 (ate→fish)
10    RIGHT-ARC(root)   [0]             []             0→3 (ROOT→ate)
                                            → 完成！
```

> **注意第 6 步**：此时栈顶是 `[0, 3]`（ROOT, ate），$s_1$=ROOT 是 $s_0$=ate 的正确 head，本可以 RIGHT-ARC。但 oracle **不执行**——因为 ate(3) 还有一个未处理的 child fish(5) 在 buffer 里。如果现在弹出 ate，fish 就永远找不到 head 了。这就是 RIGHT-ARC 需要"确认没有剩余 child"的原因。

#### Arc-Eager 系统（Nivre 2003）

Arc-eager 是 arc-standard 的"急切版"——**能尽早建弧就尽早建**，不等所有 child 处理完：

| 动作 | 前提 | 效果 |
|------|------|------|
| **LEFT-ARC($l$)** | 栈 $\geq 1$ 且 $\beta$ 非空 | 建立 $s_0 \xrightarrow{l} \beta[0]$，不弹出 |
| **RIGHT-ARC($l$)** | 栈 $\geq 1$ 且 $\beta$ 非空 | 建立 $\beta[0] \xrightarrow{l} s_0$，SHIFT $\beta[0]$ |
| **REDUCE** | 栈 $\geq 1$ 且 $s_0$ 已有 head | 弹出 $s_0$ |
| **SHIFT** | $\beta$ 非空 | 把 $\beta[0]$ 压入栈 |

> **arc-standard vs arc-eager 的核心区别**：
> - **arc-standard**：每一步要么建一条弧并弹出一个元素，要么 SHIFT。建弧和弹栈绑定，简洁但有时必须等。
> - **arc-eager**：建弧后不弹栈（LEFT-ARC）或仅 SHIFT（RIGHT-ARC），需要一个额外的 REDUCE 动作来弹栈。但建弧更早，对错误传播更鲁棒。

#### Oracle（训练时知道正确动作）

训练时，给定 gold 依存树，**oracle** 函数告诉 parser 每一步该做什么动作：

$$
\text{oracle}(\sigma, \beta) \to a \in \{\text{LEFT-ARC}, \text{RIGHT-ARC}, \text{SHIFT}\}
$$

Arc-standard oracle 的判定规则（见配套实验代码）：

1. 若 $\text{gold\_head}(s_1) = s_0$ 且 $s_1 \neq$ ROOT $\Rightarrow$ **LEFT-ARC**
2. 若 $\text{gold\_head}(s_0) = s_1$ 且 $s_0$ 在 $\beta$ 中无剩余 child $\Rightarrow$ **RIGHT-ARC**
3. 否则 $\Rightarrow$ **SHIFT**

**推理时没有 oracle**——用一个**分类器**预测每一步的动作。分类器的输入是栈/缓冲区的特征（词、POS、已有弧），输出是动作分布。

#### 特征工程（第一代）与神经化（第二代）

- **第一代（2006-2014）**：手工特征模板——栈顶/缓冲区前几个词的 word/POS/deprel，以及已建弧的信息。代表系统 **MaltParser**（Hall et al. 2006），用 SVM 或在线感知机分类。准确率 UAS ≈ 89-90%（英文）。
- **第二代（2015-）**：Chen & Manning (2014) 首次用神经网络替代手工特征——把 word/POS 嵌入，用前馈网络分类。Kiperwasser & Goldberg (2016) 用 **BiLSTM** 编码整个句子，取栈/缓冲区对应位置的隐藏状态输入分类器。准确率跳到 UAS ≈ 93-94%。

### 2.3 Graph-Based Parsing：全局最优的弧集合

Transition-based 是"贪心走一步看一步"——每一步的动作只依赖局部信息。Graph-based 换了个思路：**给所有可能的弧打分，然后找全局最优的树**。

#### 最大生成树（MST）公式

给定句子 $w_1, \ldots, w_n$，定义弧分数 $s(h, m)$——head $h$ 管辖 dependent $m$ 的"好坏程度"。目标：在所有合法依存树 $\mathcal{T}$ 中，找**弧分数之和最大**的那棵：

$$
\hat{T} = \mathop{\arg\max}_{T \in \mathcal{T}} \sum_{(h,m) \in T} s(h, m)
$$

这是一个**最大生成树（Maximum Spanning Tree, MST）**问题。

#### 两种解码算法

| 属性 | Projective | Non-projective |
|------|-----------|----------------|
| 约束 | 弧不能交叉 | 无约束 |
| 算法 | **Eisner 算法**（动态规划）| **Chu-Liu-Edmonds** |
| 复杂度 | $O(n^3)$ | $O(n^3)$（高效实现 $O(n^2)$）|
| 对比 transition-based | 全局最优，但更慢 | 能处理非投影树 |

**Eisner 算法**的核心：用动态规划，把"从 head 向左/右延伸的不完全/完全 span"作为子问题，逐步合并。因为是 DP，保证找到**全局最优的投影树**——不像 transition-based 可能因为一步走错而步步错（error propagation）。

**Chu-Liu-Edmonds**：经典的图论算法——每个词选分数最高的入弧，形成一组连通分量，收缩每个环为超级节点，递归求解，最后展开。能处理任意非投影结构。

> **Transition-based vs Graph-based 的取舍**：
> - **Transition-based**：$O(n)$ 极快，但贪心、有错误传播、只能投影（arc-standard）。
> - **Graph-based**：$O(n^3)$ 较慢，但全局最优、能处理非投影（Chu-Liu-Edmonds）。
> - **实践中**：神经化后两者差距缩小，但 transition-based 仍是工业界首选（速度优势巨大）。

### 2.4 Neural Parsing：Dozat 的 Biaffine Attention

Dozat & Manning (2017) 提出的 **biaffine attention** 是当前依存分析的事实标准。核心改进：不再分类"下一步做什么动作"，而是**直接预测每个词的 head**。

#### 架构

```
词序列 → BiLSTM（或 Transformer）编码 → 两个 MLP（head / dep）→ Biaffine 打分
```

1. **编码**：BiLSTM（后来也用 BERT/Transformer）得到每个词的上下文表示 $\mathbf{r}_i$。

2. **双 MLP**：分别为"当 head"和"当 dependent"的角色投影：

$$
\mathbf{h}_i^{(\text{arc-head})} = \text{MLP}_{\text{head}}(\mathbf{r}_i), \qquad \mathbf{h}_j^{(\text{arc-dep})} = \text{MLP}_{\text{dep}}(\mathbf{r}_j)
$$

3. **Biaffine 打分**：对每个候选 dependent $j$，遍历所有可能的 head $i$，计算弧分数：

$$
s_i(j) = \mathbf{h}_i^{(\text{arc-head})\top} \cdot \mathbf{U} \cdot \mathbf{h}_j^{(\text{arc-dep})} + \mathbf{w}^\top \mathbf{h}_j^{(\text{arc-dep})} + b
$$

其中 $\mathbf{U} \in \mathbb{R}^{d \times d}$ 是双线性矩阵，$\mathbf{w}$ 和 $b$ 是线性项。

4. **预测 head**：softmax + argmax：

$$
P(\text{head of } j = i) = \frac{\exp(s_i(j))}{\sum_{i'} \exp(s_{i'}(j))}
$$

5. **解码**：每个词独立取 argmax head，得到一组弧。这组弧不一定是合法树（可能有环），所以最后用 **Chu-Liu-Edmonds** 或 **Eisner** 修正为合法 MST。

6. **标签分类**：确定 head 后，再用一个 biaffine 分类器预测弧标签（nsubj / obj / det…）。

> **为什么 biaffine 比 transition-based 神经版好？**
> 1. **全局信息**：BiLSTM/Transformer 让每个词的表示包含全句上下文，不受栈顶窗口限制。
> 2. **端到端**：不需要 beam search 或动作序列，直接回归到"head 选择"。
> 3. **label 解耦**：先选 head 再选 label，解耦了两个子任务，各自更准。
>
> 在 PTG（英文宾州树库转依存）上，biaffine 达到 **UAS 96.0%, LAS 94.3%**，接近人工标注一致性上限。

### 2.5 评测：UAS 与 LAS

| 指标 | 全称 | 计算方式 |
|------|------|---------|
| **UAS** | Unlabeled Attachment Score | $\dfrac{\text{head 预测正确的词数}}{\text{总词数}}$ |
| **LAS** | Labeled Attachment Score | $\dfrac{\text{head 和标签都正确的词数}}{\text{总词数}}$ |

- UAS 只看结构（谁连谁），LAS 还看标签（怎么连）。
- 标点符号通常**不计入**评测（因为标点的依存分析没有语言学意义）。
- 英文 PTG 上人工标注一致性约 UAS ≈ 97%，所以 UAS 96% 已经接近天花板。

## 3. 代码：Arc-Standard Parser

配套脚本 `experiments/19_dep_parser.py`（纯 Python 标准库，几秒跑完）。它做三件事：

### 3.1 实验设置

实现了完整的 arc-standard 状态机（`ArcStandardParser` 类），包含 LEFT-ARC / RIGHT-ARC / SHIFT 三个动作。一个规则 oracle 函数 `make_oracle(gold_heads)` 知道正确的依存树，在每一步返回正确动作。用三个例子测试：英文投影句、中文投影句、非投影句。

### 3.2 投影句：完美解析

**例 1：The cat ate a fish**（英文，5 词，投影）

```
  1. SHIFT          : push The(1)
  2. SHIFT          : push cat(2)
  3. LEFT-ARC (det) : cat(2) → The(1)
  4. SHIFT          : push ate(3)
  5. LEFT-ARC (nsubj): ate(3) → cat(2)
  6. SHIFT          : push a(4)       ← 不能 RIGHT-ARC：ate 还有 child fish 在 buffer
  7. SHIFT          : push fish(5)
  8. LEFT-ARC (det) : fish(5) → a(4)
  9. RIGHT-ARC(obj) : ate(3) → fish(5)
 10. RIGHT-ARC(root): ROOT(0) → ate(3)
  >>> 解析完成（10 步）

依存树:
  └─ ate(3)  [root]
     ├─ cat(2)  [nsubj]
     │  └─ The(1)  [det]
     └─ fish(5)  [obj]
        └─ a(4)  [det]

UAS = 5/5 = 100%
```

**例 2：猫 吃 了 鱼**（中文，4 词，投影）

```
  依存树:
  └─ 吃(2)  [root]
     ├─ 猫(1)  [nsubj]
     ├─ 了(3)  [aux]
     └─ 鱼(4)  [obj]

UAS = 4/4 = 100%
```

两个投影句都 100% 完美——arc-standard 在投影树上表现优异。

### 3.3 ★ 反直觉发现：非投影句直接卡死

**例 3：w₁ w₂ w₃ w₄**（4 词，弧交叉——模拟荷兰语 verb-raising）

正确依存树（gold）的弧：

```
  w₃(3) → w₁(1)   [w₃ 是 w₁ 的 head]
  w₁(1) → w₂(2)   [w₁ 是 w₂ 的 head]
  ROOT   → w₃(3)   [w₃ 是 root]
  w₁(1) → w₄(4)   [w₁ 是 w₄ 的 head]  ← 非投影！
```

投影性检测发现：弧 `w₁(1) → w₄(4)` 跨越了词 `w₃(3)`，而 `w₃(3)` 不是 `w₁(1)` 的后代（恰恰相反，`w₁` 是 `w₃` 的后代）。弧交叉了。

让 arc-standard parser 尝试解析：

```
  1. SHIFT          : push w₁(1)
  2. SHIFT          : push w₂(2)
  3. RIGHT-ARC(dep) : w₁(1) → w₂(2)
  4. SHIFT          : push w₃(3)
  5. LEFT-ARC (dep) : w₃(3) → w₁(1)     ← w₁ 被弹出栈！
  6. RIGHT-ARC(root): ROOT(0) → w₃(3)
  7. SHIFT          : push w₄(4)
  >>> ⚠ 卡死！栈=[0, 4]  缓冲区=[]

UAS = 3/4 = 75%  ← 词 w₄(4) 没有被分配 head！
```

**为什么卡死？**

```
  1. w₄(4) 的正确 head 是 w₁(1)
  2. 但 w₁(1) 在 Step 5 的 LEFT-ARC 中已被弹出栈
     （当 w₃(3) 入栈后，oracle 判定 w₃ 是 w₁ 的 head，
      于是建立 w₃→w₁ 并弹出 w₁）
  3. arc-standard 只能在【栈顶两个元素之间】建弧
  4. w₁ 已不在栈上 → w₄ 永远找不到正确 head → 卡死
```

> 👉 **铁证结论**：arc-standard 的三个动作（SHIFT / LEFT-ARC / RIGHT-ARC）**只能产生投影树**。这不是 bug，是**数学定理**——因为栈的 LIFO 结构决定了弧只能嵌套，不能交叉。非投影弧（如荷兰语的 `w₁→w₄`）要求"先建 w₁→w₄，再建 w₃→w₁"，但 arc-standard 要求"先处理完 w₁ 的左邻居才能接触右邻居"——这两个操作顺序互斥。
>
> **解法**：
> - (a) **arc-eager + SWAP**（Nivre 2009）：增加一个 SWAP 动作，允许把栈顶元素放回缓冲区末尾，从而打破 LIFO 约束，实现非投影解析。
> - (b) **graph-based MST**（Chu-Liu-Edmonds）：直接在全弧集上找最优生成树，天然支持非投影。
> - (c) **pseudo-projective**（Nivre & Nilsson 2005）：解析时把非投影树转成投影树（给交叉弧编码额外信息），解析后恢复。

### 3.4 总结

| 句子 | 投影? | arc-standard | UAS |
|------|-------|-------------|-----|
| The cat ate a fish | ✓ | ✅ 完美 | 100% |
| 猫 吃 了 鱼 | ✓ | ✅ 完美 | 100% |
| w₁ w₂ w₃ w₄ (交叉) | ✗ | ❌ 卡死 | 75% |

transition-based parser 是**线性时间 $O(n)$** 的，极快；但代价是**只能产生投影树**——这是数学定理，不是 bug。

## 4. 中文依存分析的特殊挑战

中文的依存分析比英文难，原因有三：

### 4.1 Pro-drop（主语省略）

中文是 **pro-drop 语言**——主语可以自由省略：

```
英文：  (I) ate the fish.        ← 语法不完整，必须补主语
中文：  吃了鱼。                  ← 完全合法！"谁吃"靠上下文推断
```

pro-drop 带来的问题：依存树里找不到 `nsubj`（主语）弧，但语义上主语隐含存在。解析器要么在 root 附近"虚构"一个空主语（empty node），要么忽略。两种处理方式都让下游任务（如语义角色标注）变复杂。

> UD 标准（Universal Dependencies）对此的处理：不插入空节点，而是通过 **enhanced dependencies**（增强依存）在注释中标注隐含主语。

### 4.2 主题突出（Topic-prominent）

中文是**主题突出语言**（Li & Thompson 1981），句子常以"主题—评论"结构组织：

```
那本书，我已经读完了。
  ↑          ↑
  主题      评论（"那本书"是"读"的逻辑宾语，但被提到句首做主题）
```

英文分析："那本书"应该是"读完"的 `obj`。但它的位置在主语之前，依存弧跨越了整个主谓结构——容易产生非投影弧，让 arc-standard parser 为难。

### 4.3 分词的连锁问题

中文没有空格，必须先分词。分词错误会**级联**到依存分析：

```
正确分词：南京市 / 长江大桥    → "南京市" 是 "长江大桥" 的定语
错误分词：南京 / 市长 / 江大桥  → "江大桥"（人名）是 "南京" 的...
```

一个分词错误，整棵依存树的结构全变。这也是为什么中文 NLP 流水线中，分词质量是地基。

> **LLM 时代的解法**：现代 LLM（GPT-4、Claude）用 subword tokenization 绕过了分词问题——不需要显式分词，直接在 character/subword 层面理解。但专门的依存分析器（Stanza、HanLP、LTP）仍需要先分词。

## 5. 批判：依存分析已经"赢了"，但被 LLM 吞噬

### 5.1 依存 vs 成分：依存赢了

到 2026 年，成分句法分析在工业界几乎消失。原因：

1. **spaCy / Stanza / UDPipe 默认输出依存树**——开发者拿到的就是依存树。
2. **Universal Dependencies 统一了标注标准**——200+ 语言共用一套标签，成分树库（如 Penn Treebank）只在英文学术中存活。
3. **下游任务不需要成分树**——信息抽取（Ch20）、语义角色标注（Ch20）、情感分析（Ch22）都直接消费依存弧。
4. **成分树的信息可以近似从依存树恢复**—— constituent → dependency 是简单映射，反过来需要启发式。

### 5.2 但专门的依存分析器正在被 LLM 替代

| 方法 | 代表 | UAS (英文) | 速度 | 状态 |
|------|------|-----------|------|------|
| 规则 oracle | 本实验 | 100% (有 gold) | 极快 | 教学用 |
| MaltParser (SVM) | Hall 2006 | ~89% | 快 | 淘汰 |
| Stanford NN | Chen & Manning 2014 | ~92% | 中 | 淘汰 |
| BiLSTM-biaffine | Dozat & Manning 2017 | **~96%** | 中 | **当前专门 SOTA** |
| BERT-biaffine | — | **~97%** | 慢 | 学术 SOTA |
| GPT-4 / Claude | LLM | ~95%（零样本）| 慢/贵 | 实用但浪费 |

> **LLM 能做依存分析吗？** 能。你给 GPT-4 一句话，让它输出 CoNLL-U 格式的依存树，它做得相当好。但：
> - **太贵**：用 100B 参数的 LLM 做句法分析，像用大炮打蚊子。Stanza 的 biaffine parser 只有几 MB，速度快 1000 倍。
> - **不稳定**：LLM 输出的依存树偶尔不合法（比如一个词有两个 head，或有环），需要后处理。
> - **不可控**：LLM 可能用不同的标签集（不严格遵循 UD），且无法保证一致性。
>
> **结论**：专门 parser（biaffine）仍是生产首选；LLM 用于零样本场景（没有树库的低资源语言）或需要语言推理的复杂句法。

### 5.3 一个更深的批判：句法分析本身是否还需要？

2020 年代 NLP 的一个趋势：**不再显式做句法分析**。LLM 的 self-attention 隐式地编码了句法信息（attention head 对应依存关系的现象被广泛研究，Clark et al. 2019）。那么，显式的依存分析还有用吗？

- **有用的场景**：语言学研究、树库构建、低资源语言标注、可解释性分析、语法纠错（GEC）。
- **不需要的场景**：大多数下游任务（情感、摘要、翻译、问答）在 LLM 时代直接端到端，不需要中间的依存树。

> 这和成分分析（Ch17-18）的命运一样——**从"NLP 的地基"退化为"可选的分析工具"**。但作为学习者，理解依存分析是理解句法的最佳入口，也是理解 self-attention "隐式句法"的前提。
