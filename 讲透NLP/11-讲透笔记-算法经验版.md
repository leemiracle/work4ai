## §0 全局视角：RAG 不是"让 LLM 查资料"，是"重新定义知识存储"

很多人对 RAG 的印象是"给 LLM 加个搜索引擎"。这只是表面。**RAG 真正的概念贡献**：

| | **参数化记忆 (parametric)** | **非参数化记忆 (non-parametric / RAG)** |
|---|---|---|
| 知识存哪 | 模型权重 | 外部向量库 / 文档库 |
| 更新成本 | 重新训练（极贵）| 重建索引（中）|
| 单次查询成本 | 1 次前向传播 | 1 次检索 + 1 次前向 |
| 是否幻觉 | 高（参数化"猜"）| 低（基于证据）|
| 可解释性 | 差（"权重里学到的"）| 好（可指出来源文档）|
| 私有数据 | 几乎不可能（训练数据不可控）| 天然支持 |
| 时效性 | 训练截止日期 | 实时（取决于索引更新频率）|

> **一句话**：LLM 权重是"压缩过的世界知识"，RAG 是"外部记忆"。两者**互补而非替代**——就像人脑（参数化）和图书馆（非参数化）的关系。

### 算法经验 R1：参数化 vs 非参数化的根本权衡

> 这条经验贯穿整个 ML：
> - **kNN（非参数） vs 线性模型（参数化）**
> - **数据库（非参数） vs 神经网络（参数化）**
> - **fine-tuning（参数化） vs in-context learning（半参数化）**
> - **RAG（半参数化） vs 长上下文 LLM（半参数化）**

可迁移：**任何"知识存储"设计都要回答：把知识压进参数，还是放在外部？**——前者更新慢但查询快、后者更新快但每次查询都要算。

## §1 三层讲透 BM25

### 1.1 直觉层

> **TF-IDF 像"数共享词"，BM25 像"数共享词 + 防止关键词堆砌 + 文档长度归一化"**。

### 1.2 数学层

BM25 公式看起来吓人，其实是 TF-IDF 加两个修正：

$$\text{score}_{\text{BM25}}(d, q) = \sum_{t \in q} \text{idf}(t)\cdot \underbrace{\frac{\text{tf}(t,d)\cdot(k_1+1)}{\text{tf}(t,d) + k_1(1 - b + b\cdot\frac{|d|}{\text{avgdl}})}}_{\text{饱和 tf 项 + 长度归一化}}$$

两个修正的算法本质：

**(a) tf 饱和**：分子分母都含 tf，渐近于 $k_1+1$：

| tf | 原始（线性）| BM25 饱和项（k_1=1.5）|
|---|---|---|
| 1 | 1 | 1.00 |
| 2 | 2 | 1.43 |
| 4 | 4 | 1.82 |
| 6 | 6 | 2.00 |
| 16 | 16 | 2.29 |

→ tf 涨 16 倍，BM25 项只涨 2.29 倍。

**(b) 文档长度归一化**：长文档天然更容易碰巧包含查询词，要打折：

$$\text{norm}(|d|) = 1 - b + b \cdot \frac{|d|}{\text{avgdl}}$$

### 1.3 算法经验 R2：饱和作为通用非线性技巧

> BM25 的 tf 饱和、ReLU 的"防线性叠加"、softmax 的温度、dropout 的"防过拟合"、tanh 的"防发散"——都是**同款机制：把线性输入压缩到一个有界的非线性响应**。

**为什么需要饱和？** 任何线性评分系统都可以被"堆砌"作弊：
- TF-IDF 被 SEO 关键词堆砌
- 线性推荐被刷量作弊
- 线性评分被"刷好评/差评"操纵

**解法谱系**：
- $\frac{x(k+1)}{x+k}$（BM25 饱和）
- $\log(1+x)$（logarithmic damping）
- $\tanh(x)$（神经饱和）
- $\min(x, c)$（截断）

可迁移：**任何"防作弊/防堆砌"的评分系统都该用某种饱和函数**。

### 算法经验 R3：文档长度归一化是普遍需求

> 长文本天然更容易"碰巧匹配"，所以在所有"长度可变"的匹配任务里，都要做某种长度归一化。
> - IR：BM25 的 $b$
> - 推荐：序列长度归一化
> - 检测：候选框面积归一化
> - 比较：用 ratio 而非绝对差

可迁移：**只要比较的"对象大小可变"，就要做某种 normalization**。

## §2 双塔架构：大规模检索的工程基础

### 2.1 双塔（bi-encoder）的核心思想

```
        ┌────────────┐
查询 ─→ │ Query 塔   │ ─→ v_q ┐
        └────────────┘        ├→ cos(v_q, v_d) → score
        ┌────────────┐        │
文档 ─→ │ Doc 塔     │ ─→ v_d ┘
        └────────────┘
        (可预计算,
         存进向量库)
```

**关键**：查询和文档**各自独立**过一个 encoder，输出向量算余弦。这意味着：
- **文档向量可预计算**——1M 文档建一次索引
- **查询只需 1 次前向** + 1M 次余弦（可 ANN 加速到 10ms）

### 2.2 算法经验 R4：双塔是大规模检索的核心架构

> 任何需要"在百万级候选中找最相关"的场景，**几乎都用双塔**：
> - **搜索**：query-doc 双塔（DPR, Sentence-BERT, BGE）
> - **推荐**：user-item 双塔（YouTube DNN, DSSM）
> - **广告**：query-ad 双塔
> - **协同过滤**：user-user / item-item 双塔

**为什么必须双塔？** 因为单塔（cross-encoder）必须把查询和候选拼一起算，**1M 候选 = 1M 次前向**——查一次要几百秒，工业上不可接受。双塔把 1M 次前向降到 1 次（查询）+ 预计算的余弦。

可迁移：**当候选规模 > 10K 时，必须用双塔或类似可预计算架构**。

### 2.3 双塔的代价：失去交互

双塔的弱点：查询和文档**没有交互**——查询塔不知道文档长啥样，反之亦然。这导致：
- 同义词匹配精度不如 cross-encoder
- 需要专门训练（contrastive learning，让正例向量近、负例远）

这是为什么需要 **rerank 阶段**——见下节。

## §3 两阶段检索：召回-排序的漏斗范式

### 3.1 标准两阶段架构

```
查询 → [Stage 1: bi-encoder 召回]
         ↓ 取 top-K (K=50~100)
       [Stage 2: cross-encoder rerank]
         ↓ 取 top-k (k=5~10)
       最终结果 → 喂给 LLM
```

### 3.2 算法经验 R5：两阶段 = 漏斗式精度-速度权衡

> **任何"候选规模大、精度要求高"的系统，都该用两阶段（甚至多阶段）漏斗**：
> - **召回 (粗, 快)**：可预计算架构（双塔），取大集合 top-K
> - **精排 (细, 慢)**：高精度架构（cross-encoder），取小集合 top-k

可迁移场景：
- **推荐系统**：召回（双塔）→ 粗排（轻量模型）→ 精排（重模型）→ 重排（多样性）
- **广告投放**：召回 → CTR 预估 → 出价
- **CV 检测**：region proposal（Fast R-CNN 的 RPN）→ classification
- **欺诈检测**：规则召回 → ML 精排
- **搜索引擎**：BM25 召回 → Learning-to-Rank 精排

### 3.3 cross-encoder 的算法本质

cross-encoder 不是简单算相似度，而是让查询和文档**深度交互**：

```
bi-encoder:        v_q · v_d                    (1 次点积)
cross-encoder:     BERT([CLS] q [SEP] d [SEP])  (深度 attention)
```

在 cross-encoder 里，q 的每个 token 都能 attend 到 d 的每个 token——所以能捕捉"fast ↔ high speed"这种细粒度语义对齐。

**算法经验 R6**：交互式模型精度高但慢，独立式模型快但精度低——这是 ML 系统的基本权衡。

可迁移：
- **NLI**：bi-encoder（句对相似度）vs cross-encoder（拼接分类）
- **QA**：bi-encoder（检索段落）vs cross-encoder（reader 读段落）
- **多模态**：CLIP（双塔）vs ViLT（cross-attention）

### 3.4 实验数据对比（toy essence）

| 查询 | bi-encoder 召回 (top-1) | cross-encoder rerank (top-1) | 正解 |
|------|------------------------|----------------------------|------|
| Q1 "cats hunt" | D0 (cos=0.975) | D0 (score=3.6) | D0 ✅ |
| Q2 "vehicle move" | D4 (cos=0.982) | D4 (score=3.9) | D4/D5 ✅ |
| Q3 "top speed of car" | D5 (cos=1.000) | D5 (score=4.8) | D5 ✅ |

注意 cross-encoder 把分数差距拉大（D5=4.8 vs D4=3.3，bi-encoder 是 D5=1.0 vs D4=0.93）——**精排阶段让正确答案更"突出"，降低 LLM 被无关片段污染的概率**。

## §4 混合检索与 RRF：多信号融合的通用套路

### 4.1 为什么混合？

BM25 和稠密检索**各有盲区**：
- BM25 怕转述（词汇鸿沟）
- 稠密怕罕见精确串（专有名词、ID、代码）

**单一信号必然有盲区，混合信号常胜**。

### 4.2 RRF 的算法美

$$\text{score}_{\text{RRF}}(d) = \sum_{r} \frac{1}{k + \text{rank}_r(d)}$$

**为什么用排名而非分数？** 因为不同检索器的分数量纲不同：
- BM25 分数可能 0~20
- 余弦分数 -1~1
- 神经分数可能任意

直接加会被某一路"主导"。**用排名（rank）做融合 = 自带归一化**。

### 4.3 算法经验 R7：用排名做融合 = 无参鲁棒

> RRF 的设计哲学：**不知道各路信号的可信度时，用排名（而非分数）做融合**。这是集成学习的通用套路。

可迁移场景：
- **集成学习**：多模型预测，按预测排名而非概率融合
- **A/B 测试**：多版本排名融合
- **多专家系统**：多专家投票按排名而非置信度
- **元学习**：多 base learner 排名融合

### 4.4 算法经验 R8：稀疏 vs 稠密的对偶

> BM25（稀疏）和 BERT（稠密）是表示学习的两端：
> - **稀疏**：精确匹配、可解释、快、不需训练
> - **稠密**：模糊匹配、不可解释、需训练、能跨语义鸿沟

可迁移：
- **协同过滤（稀疏 user-item 矩阵）vs 内容检索（稠密 embedding）**
- **规则系统（稀疏 if-then）vs ML（稠密模型）**
- **符号 AI（稀疏逻辑）vs 神经网络（稠密参数）**

**经验**：**任何"精确性"和"泛化性"的权衡，都可以用稀疏-稠密视角看**。生产系统几乎总是混合的。

## §5 三大反直觉发现（实验数据存档）

### 5.1 发现 1：关键词堆砌骗过 TF，骗不过 BM25

| 检索器 | top-1 | 关键观察 |
|---|---|---|
| 原始 TF×IDF | D7（垃圾页）❌ | 6 次 cat → 7.69 分 |
| **BM25** | D0（正解）✅ | tf 饱和：6 次 cat 只贡献 2.0 分 |

**算法经验**：饱和函数是反作弊的通用工具（见 R2）。

### 5.2 发现 2：词汇鸿沟让 BM25 直接归零

| 检索器 | 8 篇文档得分 | top-1 |
|---|---|---|
| BM25 | **全部 0.0** | 瞎选 ❌ |
| 稠密（概念向量）| D5=0.962 | D5 ✅ |

**算法经验**：所有基于表面特征的方法都有词汇鸿沟——这是表示学习的根本动力（见 R8）。

### 5.3 发现 3：RAG 的天花板是检索器

|  | Q1 关键词 | Q2 转述 |
|---|---|---|
| BM25 | ✅ D0 | ❌ D0 |
| 稠密 | ✅ D0 | ✅ D5 |
| RRF 混合 | ✅ D0 | ✅ D5 |

### 算法经验 R9：天花板思维（端到端瓶颈分析）

> **多组件系统中，整体上限 = 最弱组件的上限**。
> - RAG：检索器是天花板（再强的 LLM 也救不回错资料）
> - CV 检测+识别：检测框质量是天花板
> - 推荐召回+排序：召回 recall 是天花板
> - 任何 pipeline：第一阶段的错误传播到后面

可迁移：**调试任何多组件系统，先找瓶颈组件**。RAG 系统效果差，**90% 是检索问题，不是生成问题**。

## §6 实战：RAG 系统设计的决策树

```
1. 数据规模?
   ├── < 100 文档 → 直接塞 LLM 上下文 (long-context LLM)
   └── > 1000 文档 → 需要 RAG

2. 查询类型?
   ├── 精确关键词 / 专有名词 / 代码 → 偏 BM25
   ├── 自然语言转述 → 偏稠密
   └── 混合 → 用 RRF 混合 (推荐默认)

3. 精度要求?
   ├── 低 → 单阶段 bi-encoder
   ├── 中 → 两阶段 (bi-encoder + cross-encoder rerank)
   └── 高 → 多阶段 + LLM rerank

4. 文档类型?
   ├── 短文本 → 直接 chunk
   ├── 长文档 → 分段 + overlap
   ├── 结构化 (表格) → Text-to-SQL 或专用
   └── 多模态 (图/视频) → CLIP-style embedding

5. 是否需要多跳推理?
   ├── 否 → 单次 RAG
   └── 是 → GraphRAG / Agentic RAG / 多步检索

6. 评估?
   ├── 检索评估: Recall@k, MRR, NDCG
   ├── 生成评估: faithfulness (RAGAS), answer relevance
   └── 端到端: 人工评估 + LLM-as-judge
```

### 算法经验 R10：chunking 决定上限

> **任何 RAG 系统，chunking 策略决定了检索的天花板**：
> - chunk 太大 → 噪声多，检索精度低
> - chunk 太小 → 信息不全，丢失上下文
> - chunk 切错位置（切断句子）→ 语义破碎

可迁移：**所有 ML 系统都遵循"数据预处理决定上限，模型决定达到上限的速度"**。RAG 的 chunking 就是这个范本。

## §7 批判性：RAG 的边界 + 2024–2026 前沿

### 7.1 RAG 不是万能的

| 问题 | 朴素 RAG 不行 | 解决方案 |
|------|--------------|---------|
| **多跳推理** | "A 的作者的导师" 需要多步检索 | GraphRAG, Agentic RAG |
| **全局综合** | "总结这本 500 页报告" 需要看全文 | Map-reduce RAG, 长上下文 |
| **数值精确** | "我们公司 Q3 营收" 需要精确查询 | Text-to-SQL, 结构化检索 |
| **时序推理** | "上次更新后发生了什么" | 时间索引 + 时序 RAG |

### 7.2 长上下文会替代 RAG 吗？

Gemini 1.5 (2024) 支持百万 token，有人质疑"直接塞全文还要 RAG 干吗"。

**答案：不会替代，会共存。** 原因：

| 维度 | 长上下文 LLM | RAG |
|------|-------------|-----|
| 适合规模 | < 1M token | > 1M token |
| 单次查询成本 | 高（每次都处理全部）| 低（只处理 top-k）|
| 精度 | 高（看全文）| 受检索器限制 |
| 可更新性 | 慢（重训或重新塞）| 快（重建索引）|
| 可解释性 | 差 | 好（可指出处）|

**经验**：**长上下文适合"一次性看完全部"，RAG 适合"反复查询大规模库"**。

### 7.3 2024–2026 RAG 演化趋势

| 方法 | 核心思想 | 适用场景 |
|------|---------|---------|
| **朴素 RAG** | 检索 + 拼接 + 生成 | 简单 QA |
| **HyDE** | LLM 先生成假设答案再检索 | 复杂查询 |
| **Self-RAG** | LLM 自己决定何时检索、检索什么 | 自适应 |
| **Corrective RAG (CRAG)** | 检索结果质量评估 + 纠错 | 高可靠场景 |
| **GraphRAG** | 把文档建成知识图谱 + 图检索 | 多跳推理 |
| **Agentic RAG** | LLM 作为 agent，多步检索+推理 | 复杂任务 |
| **Multimodal RAG** | 跨文本/图/视频/音频 | 多模态问答 |
| **RAPTOR** | 树状摘要，多层级检索 | 长文档综合 |

### 7.4 我对 2025–2026 的判断

- **RAG 不会消失，会变得更"智能"**：从单次检索 → agentic 多步
- **长上下文 + RAG 是互补**：长上下文处理"小而精"，RAG 处理"大而广"
- **检索器仍是中国产优势**：BGE, M3E, Conan-embedding 在 MTEB 上常年霸榜
- **评估方法成熟**：RAGAS, ARES, TruLens 让 RAG 评估更系统化
- **多模态 RAG 是新增长点**：图文混合文档（PDF、PPT）的检索

## §8 算法经验库（R1–R10）

## §9 实验数据存档

### 9.1 原实验（`11_bm25_rag.py`，纯标准库）

**发现 1**：tf 饱和铁证——tf 1→16 倍，BM25 项只涨 2.29 倍。

**发现 2**：BM25 在词汇鸿沟下全零，稠密检索 0.962。

**发现 3**：RAG 三种检索器对照——RRF 融合全对。

### 9.2 essence 补充（`11_essence_rerank.py`，两阶段检索）

**bi-encoder 召回**：3 个查询都把正解放进 top-2

**cross-encoder rerank**：分数差拉大，正解稳定 top-1

| 查询 | bi-encoder top-1 (cos) | rerank top-1 (score) |
|------|----------------------|---------------------|
| Q1 "cats hunt" | D0 (0.975) | D0 (3.6) |
| Q2 "vehicle move" | D4 (0.982) | D4 (3.9) |
| Q3 "top speed car" | D5 (1.000) | D5 (4.8) |

> **算法经验**：rerank 阶段让正确答案"更突出"，降低 LLM 被无关片段污染的概率。

## ✍️ 练习（算法经验导向）

**练习 A**（饱和函数 R2）：在 essence rerank 脚本里，把 cross-encoder 的"维度级精细匹配"分数也加上一个饱和函数（防止某一项过高主导）。观察效果。

**练习 B**（双塔 R4）：用 HuggingFace 加载 `BAAI/bge-small-zh`，把 1000 条中文文档编码成向量存入 FAISS。测量：建索引时间、单次查询时间、暴力余弦时间。体会双塔的速度优势。

**练习 D**（RRF R7）：在 BM25 + 稠密双路检索中，比较 RRF 融合 vs 加权分数融合 vs 学习权重融合（如 LambdaMART）。哪个最简单？哪个最准？
