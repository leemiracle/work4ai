# ⚡ 第 1 幕 · 直觉：缓存即预计算的回忆

## 从一个让你肉疼的账单开始

你做了一个客服 bot，每次请求都把同一份 10 万 token 的产品手册塞进 context。你用 Claude，按官方定价 input $3/M token。

算一笔账：每个请求 10 万 token × $3/M = **$0.30/请求**。一天 1 万请求 = **$3000/天** = **$9 万/月**。

然后 Anthropic 2024 年推出 Prompt Caching：**重复的 prefix 只算一次（贵 25%），之后命中只要原来的 10%**。你把手册标成 cache。

新账单：首次 $0.375（贵 25%）+ 之后每请求 $0.03（省 90%）= **$300/天** vs $3000/天。**省 90%**。

**这就是缓存的魔力——也是本宇宙的全部动机**。

---

## Transformer 的 O(n²) 诅咒

要懂 LLM 缓存，先回到 Transformer 为什么慢为什么贵。

self-attention 的核心操作：每个 token 要「看到」之前所有 token。如果有 n 个 token，注意力计算是 **O(n²)**——序列翻倍，计算量 4 倍。

更狠的是**生成时**：生成第 t 个 token 时，要计算它和前 t-1 个 token 的注意力。但前 t-1 个 token 的 K（键）和 V（值）**之前已经算过了，没变**。

**朴素实现**：每个新 token 都重算所有历史 → 每步 O(t²)，总 O(n³)。
**聪明实现**：把算过的 K/V 存起来复用 → 首次 O(n²)，之后每 token O(n)。

这个「存起来复用」就是 **KV Cache**。它是 Transformer 推理优化最基础、最重要的一招。

---

## KV Cache：把 O(n²) 摊销成 O(n)

用一个比喻：

> **没有 KV Cache**：每次你说话，朋友都从头回想你们整个对话——每句话都要重算一遍关系。
>
> **有 KV Cache**：朋友把之前每句话的「印象」（K/V）记在小本子上，新来一句话只算它和小本子上所有印象的关系——**已经算过的永远不重算**。

数学上：

```
朴素生成第 t 个 token:  对所有 j < t 重新算 K_j, V_j → O(t²) per step
有 KV Cache 生成第 t 个: 只算 K_t, V_t（新 token），历史从 cache 读 → O(t) per step
```

**节省是巨大的**。但 cache 本身要占**显存**：

$$\text{KV cache 显存} = 2 \times L \times n \times d \times \text{precision}$$

（2 = K 和 V；L = 层数；n = 序列长度；d = 隐藏维度）

一个 70B 模型，4K context 的 KV cache ≈ **几 GB**。这就是为什么长 context 又贵又占显存——**不是计算贵，是 KV cache 占地方**。

---

## Prompt Caching：把 KV Cache 商品化

KV Cache 是底层推理优化（vLLM/TGI 这种推理引擎在做）。**Prompt Caching 是把它商品化到 API 层**。

机制：
1. 你在请求里标记一段 prefix 为 cacheable
2. 厂商把这段 prefix 的 KV 算一次，存起来（5 分钟 TTL）
3. 你后续请求里 prefix 相同 → 厂商直接读已算好的 KV，跳过前向传播

**关键限制**：**前缀必须严格相同**。改一个字，整个 cache 失效。这叫 **prefix-aware caching**。

为什么是「前缀」而不是「任意子串」？因为 Transformer 的因果注意力决定了：**第 t 个 token 的 K/V 只依赖它之前的 token**。所以 prefix 共享 = KV 共享。中间改一个字，后面全失效。

---

## vLLM 的 PagedAttention：把 KV Cache 当虚拟内存管

开源推理引擎 vLLM（Kwon et al., SOSP 2023）做了一个 OS 级的突破：**把 KV Cache 当虚拟内存管理**。

类比 OS 的分页机制：
- OS 把物理内存分成固定大小的页（4KB），用页表映射虚拟地址
- vLLM 把 KV cache 空间分成固定大小的 block（如 16 token），用 block table 映射逻辑序列

**好处**：
1. **消除显存碎片**：不同长度序列共享显存池，不浪费
2. **共享 prefix**：多个请求有公共 prefix → 物理上共享同一块 KV（copy-on-write）

结果：vLLM 比 HuggingFace 朴素实现**吞吐量提升 2-4 倍**。这是开源 LLM 服务的基础设施。

---

## SGLang RadixAttention：用基数树共享前缀

SGLang（2024）更进一步：用**基数树**（radix tree）管理所有请求的 KV。

所有活跃请求的前缀组成一棵树，**公共前缀自动共享 KV**。当你有大量用户问相似问题（共享 system prompt / few-shot / 知识库）时，命中率极高。

适用场景：**多请求共享前缀**的服务（API gateway、客服、文档问答）。

---

## Augment 的 60 万 token 魔法

2025 年 coding agent 公司 Augment 推出 Context Engine，号称**真实可用 60 万 token**——这远超一般模型的有效范围。

它的秘密不是「窗口大」，而是**大规模语义索引 + 智能检索 + 缓存**：
1. 把整个代码库语义索引
2. 用户提问时，实时检索最相关的代码片段塞进 context
3. 配合缓存，让常用 prefix 不重算

**这其实是 RAG + 缓存的组合**，但工程做到极致，让「60 万可用」不是营销词。这预示着：**未来长 context 的竞争力，不在窗口大小，在 context 管理**。

---

## 语义缓存：比 prefix 缓存更激进

prompt caching 只认**字面相同的前缀**。更激进的是**语义缓存**：

> **用户问「怎么退款」和「如何申请退钱」——字面不同，语义相同。把它们映射到同一个 embedding，缓存答案。**

机制：
1. 把 query 转成 embedding
2. 在缓存库里找 cosine 相似度 > 阈值的历史 query
3. 命中 → 直接返回缓存的答案

**但这里有个陷阱**：**语义相似 ≠ 语义相同**。「退款金额」和「退款流程」embedding 接近，但答案完全不同。语义缓存的精度比 prefix 缓存低得多，需要谨慎设阈值。

这就是「缓存 = 用空间换时间换正确性」的「换正确性」部分——**激进缓存省更多钱，但风险是返回错答案**。

## 三层缓存的认知复杂度阶梯

把本节所有方案沿「认知复杂度」排成阶梯：

```
                    认知复杂度 ↑
                          │
   语义缓存 ─────────────  │  "理解"相关性（会出错）
                          │
   prompt caching ──────  │  只认字面前缀（安全）
                          │
   PagedAttention ──────  │  显存管理（OS 级）
                          │
   KV Cache ────────────  │  算过的不再算（最基础）
                          │
   无缓存 ──────────────  │  每次从零算（O(n²)）
                          ▼
```

**越往上越「智能」也越「危险」**。KV Cache 是纯确定性优化（绝不影响结果），语义缓存可能改变答案。**这就是为什么 Anthropic 在 prompt caching（中间层）停下了——再往上就要赌正确性**。

---

## 三角权衡：RAG vs 长上下文 vs 缓存

现在能看到 LLM context 管理的三个角的权衡：

```
            RAG（外部检索）
             /  低成本
            /   高延迟（检索）
           /
           ⊙──── 长上下文（全塞进去）
            \   高成本
             \  低延迟
              \
        缓存（复用）
          命中省 90%
          未命中亏
```

**三者不是替代，是组合**：
- 长上下文 = 不动脑子全塞（最贵最准）
- 缓存 = 重复 prefix 不重算（省 prefix）
- RAG = 只塞相关的（省 token，加检索延迟）

**生产系统通常是三者的组合**：长 context 当舞台 + 缓存省固定成本 + RAG 塞动态相关。

## 与其他宇宙的连接

- **`讲透记忆/`**：缓存是「无思考的复用」（前缀相同），记忆是「有语义的复用」（理解相关性）。**语义缓存是两者的模糊地带**。
- **`讲透代码生成/`**：coding agent 的瓶颈就是 context 管理。Augment 的 60 万 token 之所以有意义，是因为 coding 需要看整个代码库。
- **`故事原语/02-熵论辩证`**：缓存是「把已算好的有序状态保留下来」= 典型的负熵注入。每次缓存命中，都是一次熵减。

---

## 🎬 本幕收束

> **缓存是「无思考的负熵」——它不理解语义，只认字面相同。** 这让它在确定性 prefix（system prompt / few-shot / 代码库）上极强，但在语义相似但字面不同的场景失效。
>
> 所以三层方案分工：**prompt caching 解决「重复」，语义缓存试图解决「相似」，长期记忆（`讲透记忆/`）才解决「理解」**。三者是认知复杂度的递进。
