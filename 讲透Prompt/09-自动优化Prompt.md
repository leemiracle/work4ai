# 09 - ★ 自动优化 Prompt：OPRO / APE / DSPy

> 讲透Prompt 第 09 章（重点章）| 实验：E10（`experiments/e10_opro.py`，results/e10_opro.json/png，含 DSPy 安装探测 + 手写 BootstrapFewShot 等价）| 素材：`_source/optimization.opro.en.mdx`（据指南）；论文：Yang et al. 2309.03409（OPRO）、Zhou et al. 2211.01910（APE）、Khattab et al. DSPy（据指南）

## 一、直觉：prompt 是超参，那就用调参的方法调它

深度学习工程师不手写学习率，用网格/贝叶斯搜。Prompt 同理：**它是决定系统行为的可学习参数，只是它住在自然语言空间里**。OPRO 的天才一步：优化器也是一个 LLM——把"指令 → 得分"的历史轨迹喂给一个强模型，让它提出下一条候选指令。黑箱优化器不需要梯度，只需要"轨迹 + 想象力"。

APE（Automatic Prompt Engineer）是它的先驱（用模型生成候选再筛），DSPy 是它的工程化终点（把"提示词"变成"程序"，编译器自动选指令+示例+链拓扑）。

## 二、数学：LLM-as-Optimizer 的黑箱优化视角

设指令空间为自然语言 $\mathcal{I}$，执行器 $f$（固定模型）在任务集 $D$ 上的得分 $S: \mathcal{I} \to [0,1]$。OPRO 迭代：

$$I_{t+1} \sim \pi_{\text{opt}}\left(\cdot \mid \text{meta}, \{(I_j, S(I_j))\}_{j \le t}\right)$$

即优化器 $\pi_{\text{opt}}$（另一个 LLM）以轨迹为条件生成新指令。与贝叶斯优化的结构同构（代理模型→候选→评估→入轨迹），两点不同：①搜索空间无度量（自然语言没有自然的"距离"）；②优化器的归纳偏置是"语言的先验"而不是"平滑性假设"——所以它擅长**语义级跳变**（从朴素描述跳到"注意否定词"），不擅长**数值级微调**（把阈值 0.7 调到 0.72）。

关键洞察（与 MATH_DISCOVERY_ENGINE 同构）：这套循环成立的前提是**评估便宜且可靠**——$S(I)$ 就是验证器。验证器脏，优化器就在拟合你的标注噪声。

## 三、代码：E10 最小 OPRO

```bash
cd 讲透Prompt/experiments && python3 -u e10_opro.py   # ~8 min（含 pip 装 dspy 探测）
```

配置：执行器 glm-4-flash（情感二分类），优化器 glm-4.7，8 轮，12 训练 + 8 留出。初始指令（朴素）："判断这条评论是正面还是负面，只输出一个字：正 或 负。"

**实测（训练集准确率轨迹）**：基线 92% → iter2 **100%**（优化器产出："判断评论情感，注意否定词（如没失望是正，一点也不好是负），只输出：正或负。"）→ 但 iter1/3/4/6/7 全是 **0%**。

三个教训，一个比一个深：

1. **天花板效应**：留出集上基线已 100%——OPRO 最优指令同样 100%。**自动优化需要提升空间；没有 headroom 的任务，优化器只能给你过拟合**（训练集那 8% 的提升里，至少有一半是"不算难吃，但也就那样"这条标注歧义样本——优化器学会了猜我的标注口味，这不是泛化）。FAR 引擎的"问题选择是第一瓶颈"在 prompt 优化域原样重演。
2. **解析器也是 harness**：8 轮里 5 轮 0% 不是优化器笨，是**我们的指令解析太脆**（取首行，被"好的，以下是优化后的指令："这类前缀话打爆）。优化循环的可靠性 = 生成质量 × 解析质量 × 评估质量，三者任一为零全链为零——与 讲透Harness E3 的 SELECT 教训完全同构。工程修复：剥前缀、取代码块、失败重采样。
3. **方向对了，幅度存疑**：iter2 的指令确实抓到了任务本质（否定词），元提示里我们显式提示了这一点——所以这是"人机协同优化"，不是全自动。诚实的 OPRO 复现要控制变量：把元提示里的领域提示删掉再跑（见练习）。

**控制变量复查（E10-R，0826 补）**：解析器加固（剥前缀话/引号/重采样）+ 元提示删掉"注意否定词"领域提示重跑：解析失败 **5/8 轮 → 0 轮**，iter1 即到 100% 训练——工程修复立竿见影。但真正的发现在别处：纯轨迹驱动下，优化器找到的 100% 指令是 **"判断评论的整体情感倾向，非负面即视为正面"**——一条**先验捷径**（默认正类），而不是人机协同版找到的"注意否定词"（预期语义）。两个解在训练/测试集上都拿满分，**但语义完全不同**。这是 reward hacking 的 prompt 版最小实证：**优化器最小化的是你的评分函数，不是你的意图**——评分子集上等价的解，在分布外会分道扬镳（想象一个负类占 80% 的测试集）。自动优化的验收标准不能只有分数，还要人审指令语义。

**DSPy 探测**：`pip install dspy-ai` 成功（网络通）。但 dspy 的 LM 适配层要配 openai 兼容端点，为省时间我们实现了 **BootstrapFewShot 的手写等价**（从训练集挑 3 条正确示例做 few-shot）：留出集 **100%**——在这个简单任务上，"挑对示例"和"优化指令"殊途同归，都到了天花板。DSPy 的真正价值在复杂多级程序（检索-抽取-生成链的联合编译），那是 `讲透Agent` 单元的实验田。

## 四、三种自动优化方法的家谱

| 方法 | 搜什么 | 评估器 | 适用 |
|------|--------|--------|------|
| OPRO | 指令文本（整段重写） | 任务得分函数 | 指令有语义改进空间 |
| APE | 指令候选池（生成→筛选） | 少样本评分器 | 冷启动找指令 |
| BootstrapFewShot (DSPy) | 示例子集（挑对的） | 执行正确性 | 任务有可判定对错 |
| （本单元 06 章链式） | 链拓扑 | 各站合同 | 约束叠加任务 |

组合技（生产常用）：Bootstrap 挑示例 + OPRO 磨指令 + 链式拆约束——三层各管一层，别指望一个优化器包打天下。

## 五、不足与批判

- **优化的是你的验证集**：验证集偏差（标注歧义、分布偏移）会被优化器放大。自动优化前先审验证集，这是 2026 年 prompt 工程的第一美德。
- 成本账没人算：E10 一轮 = 1 优化调用 + 12 评估调用，8 轮 ≈ 100 次调用。生产上值得，玩具上肉疼。**只有任务会长期复用时才值得自动优化**（一次性任务，手写 15 分钟更快）。
- OPRO 论文报 GSM8K +8pp、BIG-Bench 提升；我们 0pp（天花板）——差异全部来自任务选择，再次证明**优化器不生产水，只是headroom的搬运工**。
- 指令漂移风险：优化出的指令在边界 case 上的行为不可解释（"注意否定词"对三重否定怎么办？）——自动优化的可审计性税，合规场景要交。
