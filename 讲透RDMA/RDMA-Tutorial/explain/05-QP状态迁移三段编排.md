# 05 · QP 状态迁移三段编排：connect_qp_server / connect_qp_client

## ① 角色定位

建连编排是 TCP 线（03 篇）与 QP 状态机（ib.c）的汇合点，在图谱"QP 连接编排"（第 10 层），tour 第 11 步。两个对称函数各管一侧：connect_qp_server（setup_ib.c:13-127）守株待兔——bind/listen/accept 收齐所有 client 的 QPInfo 再回发；connect_qp_client（setup_ib.c:129-237）主动出击——连上每个 server、先发本端信息再收对端。两者共同完成同一件事：**把 04 篇创建的 RESET 状态 QP，推到 RTS**，让数据面可以开工。

核心是 ib.c:7-74 的 modify_qp_to_rts：RC QP 的状态机 RESET→INIT→RTR→RTS 三段迁移被打包进一个函数，每段一次 ibv_modify_qp 调用。这是 RDMA 编程里"连接"的真正含义——没有连接握手报文，所谓建连就是**双方交换坐标 + 各自改自己的状态机**。

## ② 内部结构

**三段迁移的字段语义**（ib.c:7-74，每段 attr_mask 与所赋字段严格一一对应——verbs 的 mask 是白名单，没列的字段赋了也被忽略）：

- **INIT**（ib.c:12-27）：声明端口与权限——pkey_index=0、port_num=IB_PORT、qp_access_flags 四权限（ib.c:17-20，含 REMOTE_ATOMIC）。此刻 QP 还不能收发，只是"亮出访问政策"。
- **RTR**（Ready To Receive，ib.c:30-51）：填**对端坐标**——path_mtu=IB_MTU 4096（ib.h:11）、dest_qp_num=target_qp_num、dlid=target_lid、rq_psn=0、max_dest_rd_atomic=1、min_rnr_timer=12（ib.c:33-42）。到 RTR 后 QP 可接收：入包能放进 RQ/SRQ 并产生完成事件。
- **RTS**（Ready To Send，ib.c:54-69）：武装**发送侧**——timeout=14、retry_cnt=7、rnr_retry=7、sq_psn=0、max_rd_atomic=1（ib.c:56-62）。三个重试参数都取宽裕值，保证基准测试不因瞬态丢包误报。RTS 后 SQ 可投递。

**connect_qp_server 九步**（setup_ib.c:13-127）：sock_create_bind（L25）→ listen(sockfd, 5)（L27）→ calloc peer_sockfd（L29）→ 循环 accept 收齐 num_peers=num_clients 个连接（L32-36）→ 填 local_qp_info[i]（lid=port_attr.lid、qp_num=qp[i]->qp_num、rank=本端 rank，L43-47）→ 逐 socket 收 remote_qp_info[i]（L54-57）→ **配对回发**（L62-72）→ **配对迁 RTS**（L76-91）→ sync 握手（L95-103）→ close 全部 fd 并 free peer_sockfd（L105-109）。

**connect_qp_client 镜像八步**（setup_ib.c:129-237）：对 config_info.servers[i] **按列表顺序**逐个 sock_create_connect（L142-146，num_peers=ib_res.num_qps，L132）→ 填 local_qp_info（L153-157）→ **先发**本端信息（L160-163）→ **后收**对端信息（L170-173）→ 配对迁 RTS（L180-195）→ sync 握手（写先读后，L199-207）→ 关 fd 并 free（L209-215）。

配对逻辑两侧同构：双重循环找 `remote_qp_info[j].rank == i` 得 peer_ind（server 侧 L64-69，client 侧 L182-187），用 qp[peer_ind] 对接 remote_qp_info[i]。

## ③ 外部连接

向上：唯一调用方是 setup_ib 的分发分支（setup_ib.c:325-329），按 config_info.is_server 二选一。向下：消费 sock.c 六原语（建连、QPInfo 收发、sync 收发全走 03 篇的线）与 ib.c 的 modify_qp_to_rts；读取 ib_res 的 qp 数组与 port_attr.lid、config_info 的角色与 servers 列表。产出：迁到 RTS 的 QP 集合——server 侧 qp[k] 连 client k、client 侧 qp[s] 连 server s，这个**下标即对端 rank** 的配对约定是第 06 篇 imm_data 路由的前提。图谱上它是资源层（04 篇）与数据面（06 篇）之间唯一的桥。

## ④ 数据流

以 2×2 拓扑的 server 视角走一遍：

1. **上行**：client k 在自己的 socket 上发来 {lid_k, qp_num_k, rank=k}（10 字节 packed，经 sock.c:149-153 转网络序）→ server 存进 remote_qp_info[accept 槽位]（setup_ib.c:54-57）。注意存储下标是 **accept 到达顺序**，不是 rank。
2. **配对换算**：回发循环要给 client i 发信息时，先在 remote_qp_info 里搜 rank==i 的槽位 peer_ind（L64-69），把 local_qp_info[peer_ind]（即 qp[peer_ind] 的地址）从 peer_sockfd[i] 发出（L70）。
3. **下行**：client k 收到 server 侧 qp[k] 的 qp_num/lid，存为对 server 的 remote 信息（client 侧 L170-173）。
4. **状态迁移**：server 对每个 i 执行 modify_qp_to_rts(qp[peer_ind], remote_qp_info[i].qp_num, remote_qp_info[i].lid)（L84-86）——qp[peer_ind] 的 RTR 坐标指向 client i 的 QP；client 侧对称（L188-190）。两侧都到 RTS 后，qp_num 互指的 RC 信道贯通。
5. **屏障**：server 先读后写 sync、client 先写后读（L95-103 vs L199-207）——双向各 5 字节，保证**双方全部 QP 都到 RTS 之后**才允许任何一侧投递数据，消灭竞态。

日志锚点：L89-90/L193-194 打印 `qp[本端] <-> qp[对端]` 配对表，是排查建连问题的第一入口。

## ⑤ 设计决策

**① accept 顺序假设（隐性契约）**：server 侧编排在**两套索引**间转换——accept 槽位与 client rank。peer_ind 查找只修正了"用哪条本地 QP 回发/迁移"（L64-69），但**回发用的 socket 仍是 peer_sockfd[i]（L70，按槽位）**、**RTR 坐标仍取 remote_qp_info[i]（L84-86，按槽位）**。只有 accept 到达顺序恰好等于 rank 顺序（client k 第 k 个连入）时，槽位==rank，一切正确；否则回发与迁移会交叉配对。TCP accept 顺序并无此保证，多 client 并发起连时这是真实风险——教学代码把隐含假设留给了环境。client 侧无此问题：它按 servers 列表顺序主动连接（L142-146），槽位天然等于 server rank，双重循环是恒等变换。

**② QPInfo 泄漏（实证）**：server 侧 local_qp_info（L39 calloc）与 remote_qp_info（L50 calloc）**成功路径不 free**（L111 直接 return），**error 路径也不 free**（L113-126 只清理 fd 与 peer_sockfd）；client 侧两条路径都规范释放（L214-215/L228-234）。每 QP 10 字节×2×num_peers 的小泄漏，但不对称性证明 server 侧是漏写而非风格。

**③ rank 字段专为配对而生**：QPInfo 的 rank（ib.h:32）在 RTR 里完全用不到——它的唯一使命就是让 server 能在 accept 乱序时反查"这条连接是谁"。没有 rank，槽位就是唯一信息，配对彻底不可修复。

**④ 先发后收 vs 先收后发**：client 先发本端再收对端（L160-173），server 先收齐再回发（L54-72)——死锁free的请求-响应模式：client 的 send 不会阻塞等 server 回包，server 收齐 num_peers 条才动。若 client 改成"先收后发"则双方互等，立刻死锁——顺序在此协议里是正确性问题，不是风格问题。

**⑤ 三段合一而非三次调用**：把三段迁移封进 modify_qp_to_rts 一个函数（ib.c:7），调用方只关心"给我一条能用的 QP"——INIT/RTR/RTS 的字段清单差异被封装在函数内部的三对 struct+mask 里，降低了两处调用点的重复。

## ⑥ 新人提示

读法：先 ib.c:7-74 把三段 mask 与字段对齐抄一遍（这是 verbs 面试高频题），再对读 connect_qp_server/client——注意"server 收齐再回发、client 发完再收"的镜像关系与 sync 的读写顺序反转。三个调试锚点：① 建连卡死先看 sync 阶段——server 的 read 阻塞说明某个 client 没到 RTS；② 配对表日志（L89-90）确认 qp 两两互指；③ modify_qp 返回非零最常见原因是 path_mtu 超端口能力与 dest_qp_num 错——前者查 ibv_query_port 的 active_mtu，后者回查 QPInfo 交换字节序。

实验建议：把 min_rnr_timer（ib.c:37）调小观察接收侧缺 pre-post 时的 RNR 行为；把 retry_cnt（ib.c:58）调 0 观察丢包直接暴露为 completion 错误。扩展多 client 时**必须**处理本篇 ⑤① 的槽位/rank 换算——把 L70 改成 peer_sockfd[peer_ind]、L84-86 的 remote_qp_info[i] 改成 [peer_ind] 即可闭合假设。
