# 08 · 完成队列 CQ 与通知：软件世界里没有中断，只有共享内存里的一次握手

> 仓库 zrlio/softiwarp @ 5d8a418 · 本文行号锚全部经源码核实

## 一、角色定位

RDMA 编程模型里，应用把工作交给 QP，然后在 CQ 上等结果——要么轮询（ibv_poll_cq），要么 arm 通知后等完成事件（completion channel）。硬件 RNIC 上这两条路都由 MSI-X 中断支撑；siw 没有中断线，**完成通知被重写成一段共享内存上的标志位握手**：用户态把"我想要通知"写进 mmap 映射的 CQ 控制字，内核在写完 CQE 时读到它、清掉它、调用用户注册的回调。本篇串起 CQ 的全部生命周期：创建（siw_verbs.c:1330）、写入（siw_qp.c:941/siw_qp.c:996）、收割（siw_cq.c:97 的 siw_reap_cqe 与 siw_verbs.c:1437 的 siw_poll_cq）、arm（siw_verbs.c:1466）与事件层（siw_ae.c:73）。siw_cq.c 本身只有 137 行——CQ 的"队列"部分确实简单，复杂性全在软件语义的补偿上。

## 二、内部结构

**对象与存储**：`struct siw_cq`（siw.h:293-304）= ib_cq 壳 + 环形队列指针 `queue` + 生产游标 `cq_put`/消费游标 `cq_get` + `notify` 指针。创建路径 `siw_create_cq`（siw_verbs.c:1330-1425）：容量钳制在 1..SIW_MAX_CQE（:1353-1357），**roundup_pow_of_two 上取整**（:1369）让取模变成掩码；存储是 `vmalloc`——kernel 客户端普通分配，用户客户端 `vmalloc_user`（:1373-1376，页可映射给用户）；队列尾部多分配一个 `struct siw_cq_ctrl`，`cq->notify` 指向它的 notify 字段（:1392）——**控制块与 CQE 数组同一段内存**，用户一次 mmap 全拿到（cq_key 由 siw_insert_uobj :1401 发放）。CQE 格式在 common/siw_user.h（id/opcode/status/bytes/qp_id/flags），flags 的 SIW_WQE_VALID 位是生产者—消费者协议的全部状态。

**写入侧**（siw_qp.c）：`siw_sqe_complete`（:941-990）与 `siw_rqe_complete`（:996-1053）是双胞胎——SQ 完成走前者（cq=qp->scq），RQ 完成走后者（cq=qp->rcq）。核心序列（:959-982）：锁 `lock_cq_rxsave`（irqsave，因 RX 路径在 softirq 上下文写入）→ `idx = cq_put % num_cqe` → **检查槽位空闲**（`if (!cqe->flags)`）→ 填五元组（id/opcode/status/imm_data/bytes）→ kernel_verbs 客户端额外 `siw_qp_get(qp)` 且 cqe->qp 存指针，用户客户端只存 qp_id（:970-974——内核消费者要拿 QP 引用，用户态消费者经 ibv_wc 拿 id 即可）→ `smp_store_mb(cqe->flags, SIW_WQE_VALID)` 发布（store+内存屏障一条指令，x86 上是带 lock 前缀的 mov）→ cq_put++ → 解锁 → **锁外**调 siw_cq_notify（:984）。槽位非空即 CQ 满报 IB_EVENT_CQ_ERR（:985-987）——硬件会覆盖或链式 CQ，siw 直接亮红牌，**CQ 容量欠配是硬错误**。

**通知握手 `siw_cq_notify`（siw_qp.c:924-939）**：读 `cq_notify = _load_shared(*cq->notify)`（共享内存读），命中两条件之一——NEXT_COMPLETION（任何完成都通知）或 SOLICITED 且本 WQE 带 SIW_WQE_SOLICITED——则 `smp_store_mb(*cq->notify, SIW_NOTIFY_NOT)` 清标志（**保证 arm 一次只触发一次回调**）后调 `cq->ofa_cq.comp_handler`（:938，这是 uverbs 核心注入的函数，最终 wake 用户 completion channel 的 fd）。comp_handler 未注册则直接返回（:928-930）——内核消费者（无 channel）天然走纯轮询。

**收割侧**：`siw_reap_cqe`（siw_cq.c:97-125）单条收割：锁 → 看队头 `cq->cq_get % num_cqe` 是否 VALID → 翻译成 ib_wc（siw_wc_siw2ofa :67-88，opcode 经查表 siw_wc_op_siw2ofa :52-62，SIW_OP_READ_RESPONSE 映射 -1 占位 :61）→ **kernel_verbs 时 siw_qp_put 释放写入侧的 QP 引用**（:112-113）→ cqe->flags=0 归还槽位 → cq_get++ → `smp_wmb()` 让"清标志"对生产者可见。`siw_poll_cq`（siw_verbs.c:1437-1448）就是把它循环 num_cqe 次直到空。**注意 siw_cq.c:95 的 TODO："Provide routine which can read more than one CQE"——单条收割在锁上往返，是已知性能欠账**。`siw_cq_flush`（siw_cq.c:132-137）destroy 时 memset 整环，注释明言"no CQ lock is taken"——隐含约定：destroy 时已无并发生产者。

**arm 侧**：`siw_req_notify_cq`（siw_verbs.c:1466-1483）按 flags 写共享 notify：SOLICITED 掩码匹配写 SIW_NOTIFY_SOLICITED、否则 SIW_NOTIFY_ALL（:1472-1476），仍是 smp_store_mb。**IB_CQ_REPORT_MISSED_EVENTS 分支整段被注释**（:1477-1481 的 TODO）——arm 与收割之间的竞态窗口里新到的完成可能丢通知，本版返回值恒 0，应用需要靠额外一轮 poll 兜底。

## 三、外部连接

上游生产者：TX 引擎（05 篇，SIGNALED WQE 完成时）、RX 引擎（06 篇，siw_rqe_complete 出 RQ 完成、siw_sqe_complete 出 READ 响应完成）、错误路径 siw_sq_flush/siw_rq_flush（siw_qp.c:1049/:1128，错误完成洗出队列）。下游消费者：内核 verbs（siw_poll_cq 经 ib_poll_cq）；用户态 OFED 模式走同一 uverbs 入口，mapped 模式则**完全绕开内核**——用户库直接读 mmap 环（10 篇 siw_uverbs.c 的 poll_cq_mapped 自管 cq_get，notify 写 `_store_shared(cq->ctrl->notify, ...)` :71-73）。事件线：siw_cq_event（siw_ae.c:73-86）发的是 ib_event（CQ ERR 类异步事件），与完成通知（comp_handler）是两条通道——前者走 async event fd，后者走 completion channel fd，新手常混为一谈。

## 四、数据流

事件式收成全链：`应用 ibv_get_cq_event 前调 ibv_req_notify_cq → uverbs → siw_req_notify_cq 写共享 notify=SOLICITED/ALL →（内核继续跑数据面）→ siw_sqe_complete 写 CQE+置 VALID → siw_cq_notify 读到 notify 命中 → 清 notify=NOT → comp_handler → 内核 wake completion channel → 应用 ibv_get_cq_event 拿到 cq → ibv_poll_cq 循环 → siw_poll_cq → siw_reap_cqe 逐条翻译清槽`。轮询式则把 arm 一步去掉，应用死循环 poll 直接消化共享环（mapped 模式连 poll syscall 都免）。写入永远持 irqsave 锁，收割持同锁，notify 读写靠原子屏障不靠锁——**锁保护环游标，屏障保护标志位**，两层并发原语各管一段。

## 五、设计决策

1. **共享内存替代中断**：通知的全部成本 = 一次 store_mb + 一次函数调用，无中断、无上下文切换；代价是 arm-then-poll 竞态无硬件事件可补（missed events TODO 未竟），语义上弱于 RNIC。
2. **控制块嵌在队列尾部**（:1392）：省第二次 mmap，代价是 `&cq->queue[size]` 的地址算术侵入两处代码（内核 :1392/用户 siw.h:117 的 ctrl 指针注释），布局契约靠 common/siw_user.h 单点维护。
3. **one-shot notify**（清了才再触发）：与 ibv_req_notify_cq 的语义约定一致——应用想再收事件必须重新 arm，内核侧不必维护"已通知"状态机。
4. **CQ 满即错误事件**：软件环小而快，作者选择把欠配暴露成 IB_EVENT_CQ_ERR 而非静默覆盖——宁可惊叫不可说谎。
5. **kernel_verbs 分叉存指针 vs 存 id**：内核消费者生命周期需要 QP 引用计数护送（put 在 reap 时），用户消费者天然有 mmap 视图、id 就够——同一 CQE 按客户端类型装不同载荷，是 siw 双模式设计的微观体现。

## 六、新人提示

1. CQE 永不覆盖：perftest 报 CQ ERR 事件时先怀疑 CQE 深度——send 队列深度 × 平均在途 WQE 数必须 ≤ CQ 容量，且 sq/rq 共用 CQ 时要双倍。
2. 调通知丢失问题盯三处：siw_req_notify_cq 写入的字节（mapped 模式在用户库 :71-73 写）、siw_cq_notify 的命中分支、comp_handler 是否注册——mapped 模式 arm 完全不进内核，内核侧断点抓不到属正常。
3. ib_wc->opcode 可能是 -1（SIW_OP_READ_RESPONSE 占位，siw_cq.c:61）——poll 到野值先查这张翻译表。
4. siw_wc_siw2ofa 把 imm_data/wc_flags 等全注释置零（siw_cq.c:77-87）：本版不支持 SEND WITH IMMEDIATE 的立即数据上抛——用 imm_data 的程序在此版本必坏。
5. 动手：在 siw_cq_notify 命中分支加计数器，对比 perftest 事件通知模式与轮询模式的吞吐差——量化"软件中断"这条路径的真实代价。
