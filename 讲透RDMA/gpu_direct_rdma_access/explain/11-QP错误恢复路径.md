# 11 QP 错误恢复路径：rdma_reset_device 的排干与重建

> 对应 tour 第 13 步「出错怎么办：server 侧 QP 恢复与统一关闭」。源码锚均对 HEAD `a99d506` 核实。

## 一、角色定位

`rdma_reset_device`（gpu_direct_rdma_access.c:1009-1075，67 行）是全仓唯一的错误恢复路径，头的注释只有一句 "Reset device from failed state back to an operations state"（gpu_direct_rdma_access.h:93-96）。它的真实语义比名字窄、比注释精：**只重建 QP 状态机，不动任何其他资源**——PD/CQ/SRQ/AH 缓存/已注册 MR 全部存活。而且它被硬性限定在 server 侧：入口第一件事就是 `if (!is_server(device)) return EOPNOTSUPP`（gpu_direct_rdma_access.c:1011-1014）——client 的 DCT 没有恢复通道，进 ERR 只能销毁重建（仓内未实现）。为什么只有 server：发起方（DCI）的 QP 错误是本地可修复的（队列脏了排干重来）；目标方（DCT）的错误往往牵连对端行为，单侧复位无意义。

触发点在 server main 的完成校验处：任一 CQE 状态非 IBV_WC_SUCCESS 且 persistent 模式存活时调用（server.c:385-393），**返回值被忽略**——复位失败与成功走同一条去路（clean_socket→sock_listen 等下一个 client）。恢复不是"与老 client 续会话"：失败迭代的 ack 永远不会发出，老 client 的 recv 必然失败退出（client.c:425-430）。复位买到的是"干净的房间迎接下一位客人"。

## 二、内部结构

函数体五段顺序执行，顺序本身是语义的一部分：

| 段 | 行锚 | 动作 |
|---|---|---|
| 守门 | gpu_direct_rdma_access.c:1011-1014 | 非 server 拒绝（EOPNOTSUPP） |
| 进 ERR | :1019-1027 | ibv_modify_qp(IBV_QPS_ERR)，mask 仅 STATE |
| 哨兵排干 | :1029-1056 | 取一枚 AH→投递 flush marker→轮询直到它的 CQE 出现 |
| 账本清零 | :1058-1061 | memset app_wr_id、idx=0、信用恢复 SEND_Q_DEPTH |
| 复位重建 | :1062-1074 | QP→RESET→modify_source_qp_rst2rts（INIT→RTR→RTS） |

哨兵段是全函数的巧思所在：遍历 AH 哈希表任取一枚现成 AH（:1032-1037，循环保留最后一个非空值——具体哪枚无所谓，marker 只需要被投出去）；构造一个**全零的 exec_params** 打上 `wr_id = WR_ID_FLUSH_MARKER`（UINT64_MAX，:72、1039）调 rdma_exec_task（:1043）。零参数意味着：flags=0（WRITE）、无 gather list（走单段路径）、rkey/addr/dctn/长度全 0——一个事实上的 NOP。然后 do-while 轮询收割，直到某条完成事件的 wr_id 等于哨兵值（:1046-1054）。

## 三、外部连接

恢复路径把前几篇的部件全部串了一遍：AH 缓存（第 6 篇的 khash 在这里被当"任意可用 AH"的来源）、exec_task 的单段提交（第 10 篇——marker 也占一个槽、记一笔账）、poll_completions 的翻译（第 10 篇——CQE 的槽位号被还原成应用 wr_id 才能比对哨兵）、modify_source_qp_rst2rts 的三连跳（第 9 篇，open 时与恢复时复用同一函数）。与 rdma_close_device 的分工也清楚：close 是资源终结者且拒绝在 `rdma_buff_cnt > 0` 时执行（gpu_direct_rdma_access.c:1083-1087），reset 是状态维修工且完全不碰资源——一个设备可以无限次 reset，但 close 只能一次。

verbs 层面它依赖两条规范行为：其一，QP 进 ERR 后，硬件把所有在飞 WR（含非信令的，第 10 篇提过）以错误状态冲刷成 CQE；其二，ERR→RESET→INIT 的迁移路径合法。第 9 篇画的状态图里，恢复边 `RTS/ERR→ERR→RESET→INIT→…→RTS` 只在 server 侧存在。

## 四、数据流

marker 的账本之旅：exec_task 给它分配一个新槽（正常占槽流程，gpu_direct_rdma_access.c:920-934），槽内记 `{UINT64_MAX, num_wrs=1, ACTIVE}`。QP 已在 ERR 态，这个 WR 不执行、立即被冲刷——但**排在所有先前在飞 WR 的 CQE 之后**。排干循环每轮收一批事件，逐个比对 wr_id：老任务的失败 CQE（账本翻译出来的原应用号）全部被无视丢弃，直到哨兵号出现——它的出现证明它前面的所有 CQE 都已出手，队列排干（:1051-1053）。

排干**之后**才清账本（:1059-1061）——这个顺序是承重墙：若先清零，哨兵槽的 ACTIVE 位消失，它的 CQE 会在 poll_completions 的 :1538 处被当重复事件静默丢弃，`flushed` 永远不置位，do-while 死循环。同样，老任务槽位的 ACTIVE 位在排干期间仍有效，恰保证它们的失败 CQE 能被正常翻译出来（翻译后被 reset 循环丢弃）——账本的生命周期刚好覆盖整个排干窗口。

清零后的 RESET→rst2rts 与开机路径完全相同（第 9 篇），链尾恢复 `wr_flags = IBV_SEND_SIGNALED`（:520）。回到 RTS 的 DCI 对下一个 client 而言与全新设备无异——DC 模型无连接状态，"复位完成"即刻可用。

## 五、设计决策

- **为什么必须先进 ERR**：verbs 不允许带着在飞 WR 的 QP 直接 RESET（会泄漏 CQE 与硬件资源）。ERR 态强制硬件结算所有未决操作，给软件一个可观测的排干点。marker 技巧把"排干到哪算完"这个模糊问题变成一个精确的序号比对——比"轮询到 CQ 空再 sleep 一下"的朴素做法有正确性保证。
- **为什么复用 exec_task 而不直接 post**：投 marker 也走信用检查、占槽、记账的完整流程，保证它与普通任务在同一排序域（SQ 尾部）——哨兵语义（"我之后没有更早的任务"）因此成立。绕过账本直接 ibv_post_send 反而破坏这个保证。
- **为什么无视 AH 具体身份**：marker 不需要真正到达任何目的地（QP 已 ERR，它只会被冲刷），AH 只是为了满足 mlx5dv_wr_set_dc_addr 的非空参数签名（gpu_direct_rdma_access.c:969）。哈希表空（从没跟任何人说过话）则整段跳过（:1038）——没说过话就没有在飞任务，排干是空集。
- **样例级的诚实边界**：三处容错留白值得点名——server.c:392 忽略返回值；若复位时信用耗尽（qp_available_wr < 1），exec_task 拒绝 marker（gpu_direct_rdma_access.c:894-898）而 :1043 同样忽略返回值，排干循环将等一个永不出现的哨兵 CQE，**死循环**；另外 client 侧无任何对应机制，DCT 出错即整段会话报废。这是"演示恢复概念"与"生产级恢复"的距离清单。
- **恢复与关闭的正交性**：reset 后设备仍持有全部 MR 注册（rdma_buff_cnt 不减），server 的 sock_listen 外循环正是依赖这一点——新连接进来时缓冲已注册、可直接干活（server.c:414-415 跳回标签后不再重新 reg）。

## 六、新人提示

1. **读这个函数先备好第 10 篇**：不懂账本就看不懂"为什么排干之后才清零"，不懂信令优化就看不懂"为什么哨兵 CQE 可能不是最后一个到达的"。它是全仓对前文依赖最重的 67 行。
2. **L1071 有个无害的格式串笔误**：`DEBUG_LOG("...state %d completed.\n", qp_attr.qp_state, device->qp->qp_num)` 两个实参对一个 %d——多余实参不破坏输出，但 -Wformat 类告警会点名，别在 code review 时误判成逻辑错误。
3. **EOPNOTSUPP 是 errno 而非私有错误码**：返回值语义混着"errno 风格"（EOPNOTSUPP=95）与"布尔风格"（其余路径 0/1），调用方 server.c 又不看返回值——复用这个 API 时先统一错误约定。
4. **实验恢复路径的最低配置**：`./server -P -a <ip>` 起 persistent 模式，再用一个中途 kill 掉的 client 触发半途失败；配合 `-D 3`（两档调试全开）能看到 ERR→marker→排干→RESET→RTS 每一步的 DEBUG_LOG。没有 -P 时任何完成错误直接走退出，reset 根本不会被调用。
5. **对比 perftest 等成熟工具的同类逻辑**：ib_send_bw 等用 ibv_modify_qp(RESET) + 重建握手实现"session 级"重试；本仓的 reset 是"设备级"自愈——概念分层不同，移植时别照搬语义。
