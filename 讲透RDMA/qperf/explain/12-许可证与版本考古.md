# 12 许可证与版本考古：双许可证据链、版本宏漂移与死代码化石

## 一、角色定位

这是一篇"法务+考古"收尾篇。qperf 采用 GPLv2 与 OpenIB BSD 双许可"二选一"结构，证据链分布在每个文件头、COPYING、spec 与生成器模板里，且**存在一处自相矛盾**（spec 标签写 BSD 3-Clause 而内嵌 BSD 实为两条款）。版本层面有三个真相：源码宏 0.4.11、configure 0.4.10、检入的 spec 0.4.10——README 自己规定的"四处同步"协议被执行了一半。此外 qperf.h 里躺着三个死原型、一对死存储，rdma.c 里有一行被注释的化石代码，它们共同拼出这个 2002 年起源项目的演进轨迹。读懂这些"不对劲"比读懂正常代码更能建立对仓库的信任边界。

## 二、内部结构

**双许可的文件头证据链**。五个 .c/.h 源文件（qperf.c/socket.c/rdma.c/support.c/qperf.h）头部完全同构：版权行 `Copyright (c) 2002-2009 Johann George` + `Copyright (c) 2006-2009 QLogic Corporation`，正文声明"choice of one of two licenses"——GPL Version 2（指向 COPYING 文件）或随文给出的"OpenIB.org BSD license"。这个内嵌 BSD 只有**两个再分发条件**（源码保留版权声明+免责声明；二进制在文档中重现之），没有"不得用作者名义背书"条款——按 SPDX 分类是 BSD-2-Clause。rds.c 是唯一例外：多一行 `Copyright (c) 2012 Intel Corporation`（rds.c:5），说明 RDS 支持是 2012 年由 Intel 嫁接进来的，也是全仓最新的版权年份——比其他文件的 2009 晚三年，仓库的"世代断代"直接写在文件头里。help.txt 与两个 Perl 脚本无许可证头（数据/构建文件），但 mkhelp 的 $top 模板（src/mkhelp:12-42）把同款双许可头**写入生成的 help.c**——生成物的法律身份与手写文件对齐。

**COPYING 与 spec 的口径差**。COPYING 是完整的 GPLv2 June 1991 文本。qperf.spec.in:4 的 License 字段写 `BSD 3-Clause, GPL v2`——"3-Clause"与文件头的两条款 BSD 对不上，属于打包元数据的惰性标注（SPDX 时代以前常见），实际权利义务以文件头为准。谁想按 BSD 路线二次分发，法律上应引用各源文件头的 OpenIB 许可文本而非 spec 标签。

**版本宏漂移三角**。qperf.c:63-65 定义 `VER_MAJ 0 / VER_MIN 4 / VER_INC 11`（0.4.11）；configure.ac:1 是 `AC_INIT(qperf, 0.4.10, ...)`；检入的 qperf.spec 同为 0.4.10（qperf.spec:3）。README:7-12 "Changing version"一节自己立了法：改版本要动 src/qperf.c 的三个宏、configure（README:9 还用旧名 configure.in）、qperf.spec 的 Version 行，且 spec 必须最后改免得被 cleanup 删。0.4.10→0.4.11 那次只改了 qperf.c——于是运行时 `qperf -V` 报 0.4.11，`rpm -qi` 报 0.4.10。更微妙的是协议层：server 校验 ver_maj/ver_min（qperf.c:1363-1364），ver_inc 仅装饰（qperf.c:1388-1409 的 version_error 报错文案会带出两端完整版本），所以 0.4.10 与 0.4.11 互联不触发版本错误——漂移无声。

**死原型三件**（python 全量交叉核对 qperf.h 原型 vs 五个 .c 定义所得）：`check_remote_error`（qperf.h:257，挂在"Functions prototypes in support.c"节里）全仓无定义；`run_client_bug`/`run_server_bug`（qperf.h:308-309，挂在"RDMA tests in rdma.c"节首）同样有声明无实体无调用——名字暗示曾计划一个 bug 自检测试，半途而废只留壳。**错位注释**：`run_client_rds_bw` 等四个 RDS 原型排在"Socket tests in socket.c"节注释（qperf.h:281）之下，实际定义却在 rds.c:123——RDS 从 socket.c 拆出成独立文件时没人挪原型。**死存储**：ServerAddr/ServerAddrLen（qperf.h:369-370 声明，qperf.c:280-281 定义）只在 client_send_request 里被写入（qperf.c:1527-1528），全仓零读取——本想缓存对端地址供后续使用，最终没人消费。

**化石代码**：rd_params 开头一行被注释的条件（rdma.c:1429 `//if (transport == IBV_QPT_RC || transport == IBV_QPT_UD) {`）与下一行生效版（rdma.c:1430 只判 RC）——某次提交把 UD 从 use_cm 白名单里除名，注释残留记录了这个决策现场。同样气质的还有 cleanup:36 引用已不存在的 configure.in（11 篇）与 spec changelog 里孤零零的 `Sat Oct 20 2007 - johann@georgex.org Initial package`（qperf.spec:37-39）——七年零 changelog。

**AUTHORS** 致谢名单四人（Dotan Barak/Ralph Campbell/Yevgeny Kliteynik/Dave Olson），作者 Johann George 一人——与版权行互证这是个人项目被 QLogic 收编、再被社区零星修补的形态。

## 三、外部连接

- **协议层**：版本三连经 REQ 头四个字段上线（08 篇），ver_maj/ver_min 是兼容门、ver_inc 是诊断信息；version_error 的"谁升级"判定完全依赖两端各自的三宏。
- **构建层**：configure.ac 的 0.4.10 经 @VERSION@ 注入 spec（11 篇）；spec 的 Release 字段固定 "1"。
- **展示层**：`--version`（qperf.c:954-956）打的是 VER_ 三宏；man 页标题只写 "qperf" 不带版本（mkman 的 .TH 行）。

## 四、数据流

一次版本考古的取证路径：`grep -n "VER_" src/qperf.c` 得 0.4.11 → `head -1 configure.ac` 得 0.4.10 → `diff qperf.spec.in qperf.spec` 确认检入 spec 是 configure 展开产物（Version 与 BuildRequires 两处差异）→ README:17-22 读到"四处同步"自规 → 结论：漂移是协议允许的（ver_inc 不卡），但 RPM 元数据已落后一个增量版。许可证取证同理：五个文件头 + COPYING + spec.in:4 三方对照，2-clause 与 3-Clause 的矛盾即浮出。

## 五、设计决策

1. **双许可"二选一"而非双许可叠加**：OpenIB 时代 OFED 组件的标准姿态——GPL 世界与 BSD 世界都能收录；代价是每个文件的头部文本必须逐字一致，任何一处漂移都会造成"同一项目不同文件不同许可"的合规噪音。
2. **ver_inc 不参与兼容判定**：增量版互通，minor 才是 ABI 线（REQ 结构注释明言结构变更升 VER_MIN）——版本漂移被刻意设计成"可容忍"，这也解释了为何漂移能存活至今。
3. **检入生成的 spec**：为 OFED 打包脚本服务的便利性优先（cleanup:28 注释），把"生成物进版本库"的经典风险（陈旧漂移）摆在了明面上。
4. **死代码不清算**：三个死原型、一对死存储、一行注释化石在数次重构中幸存——这个仓库的维护节奏是"加功能>清偿债"，读者应以"存在的即可能过时"为默认假设。

## 六、新人提示

- 引用 qperf 版本前先问"哪个版本"：论文/报告写 0.4.11（源码宏），复现 RPM 环境写 0.4.10（spec），两者是同一份代码的两个标签。
- 按此仓库代码做二次分发时，逐字保留文件头双许可文本是最小合规动作；spec 的 "3-Clause" 标签不要照抄进你的 NOTICE 文件。
- 死原型不是无害装饰：未来若有人真实现 run_client_bug，Tests 表与 REQ 协议的 req_index 语义就会复活一段未定义行为——清理时删原型比留着安全。
- rdma.c:1429 那行注释是"UD 为何没有 -cm"的最权威史料，回答用户"ud_lat 能否用连接管理器"时直接引它，比猜测可靠。
- 想快速判断手里的 qperf 克隆有没有被动过：核对三处版本号是否一致 + grep run_client_bug 是否仍无定义——两点异常都指向"中间人改过但没改干净"。
